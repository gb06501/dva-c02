### 2.1.5 Assume an IAM role

#### 2.1.5.1 Exam and Task Context

##### 2.1.5.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.1 is **Implement authentication and/or authorization for applications and AWS services**.
- Skill 2.1.5 is **Assume an IAM role**.

##### 2.1.5.1.2 Position Inside Task 2.1
- 2.1.1 → establish identity/federation.
- 2.1.2 → use bearer tokens for application/API access.
- 2.1.3 → configure programmatic AWS credentials.
- 2.1.4 → use credentials to make authenticated AWS API calls.
- **2.1.5 → exchange the current identity/session for temporary credentials representing an IAM role.**
- 2.1.6 → define the permissions available to IAM principals.

##### 2.1.5.1.3 Core Question
- **How can a principal temporarily become an IAM role and use the role's permissions instead of maintaining permanent credentials for that access?**

#### 2.1.5.2 Core Mental Model

##### 2.1.5.2.1 Role Assumption Flow

`caller identity`
→ allowed to request role?
→ target role trusts caller?
→ AWS STS AssumeRole
→ temporary security credentials
→ assumed-role session
→ authenticated AWS API calls
→ permissions of role session

##### 2.1.5.2.2 The Role Is Not a User
- An IAM role has:
  - permissions,
  - a trust policy,
  - no permanent password,
  - no permanent access keys.
- A trusted principal **assumes** the role and receives temporary credentials.

##### 2.1.5.2.3 Central Principle
- **A role separates identity from permissions.**
- The caller proves who it is.
- The role defines a permission set the caller may temporarily adopt.

#### 2.1.5.3 AWS Security Token Service

##### 2.1.5.3.1 Purpose
- AWS STS issues temporary security credentials.

##### 2.1.5.3.2 AssumeRole
- `AssumeRole` creates a role session and returns:
  - access key ID,
  - secret access key,
  - session token,
  - expiration.

##### 2.1.5.3.3 Result
- Subsequent AWS API calls made with these credentials are authenticated as the **assumed-role session**.

#### 2.1.5.4 Role Anatomy

##### 2.1.5.4.1 Trust Policy
- Defines **who or what may assume the role**.
- Attached directly to the role.
- It is a resource-based policy.

##### 2.1.5.4.2 Permissions Policy
- Defines **what the role may do after it has been assumed**.

##### 2.1.5.4.3 Mental Model

`TRUST POLICY`
→ Who may become this role?

`PERMISSIONS POLICY`
→ What may this role do?

##### 2.1.5.4.4 Exam Trap
- Do not confuse:
  - permission to **assume** a role,
  with
  - permissions **granted by** the role.

#### 2.1.5.5 Two-Sided Authorization to Assume a Role

##### 2.1.5.5.1 Caller Side
- Caller generally needs permission for:
  - `sts:AssumeRole`
  - on the target role.

##### 2.1.5.5.2 Target Role Side
- Target role trust policy must trust the appropriate principal/account.

##### 2.1.5.5.3 Cross-Account Mental Model

`Account A principal`
├── identity policy → allows sts:AssumeRole on Role B
│
└── requests Role B
        │
        ▼
`Account B Role B`
└── trust policy → trusts Account A/principal

Both sides must align.

##### 2.1.5.5.4 Same-Account Nuance
- Because a role trust policy is a resource-based policy, some same-account cases can grant the principal directly through the role trust policy without a separate identity-based `sts:AssumeRole` allow.
- For exam reasoning, always inspect both:
  - **caller authorization**
  - **role trust**

#### 2.1.5.6 Trust Policy

##### 2.1.5.6.1 Principal
- Trust policy identifies trusted principals such as:
  - AWS account,
  - IAM role,
  - IAM user,
  - AWS service,
  - federated identity provider.

##### 2.1.5.6.2 Action
- For ordinary role assumption:
  - `sts:AssumeRole`.

##### 2.1.5.6.3 Conditions
- Can restrict assumption based on context such as:
  - external ID,
  - MFA,
  - source identity,
  - session name,
  - principal tags,
  - organization/account conditions.

##### 2.1.5.6.4 Principle
- Trust only the principals that actually require the role.

#### 2.1.5.7 Permissions Policy

##### 2.1.5.7.1 Purpose
- Defines the permissions available after role assumption.

##### 2.1.5.7.2 Example
- Role may allow:
  - `s3:GetObject`
  - on a specific bucket.

##### 2.1.5.7.3 Important
- A caller does **not** automatically retain its original identity permissions while operating through the assumed-role credentials.
- Requests using role credentials are evaluated as the role session.

#### 2.1.5.8 Temporary Credentials

##### 2.1.5.8.1 Components
- Access key ID.
- Secret access key.
- Session token.
- Expiration.

##### 2.1.5.8.2 Usage

`AssumeRole`
→ temporary credentials
→ SDK/CLI
→ SigV4 signed AWS request

##### 2.1.5.8.3 Expiration
- Credentials stop working after the session expires.

##### 2.1.5.8.4 Connection
- Credential mechanics → 2.1.3.
- Signed API calls → 2.1.4.

#### 2.1.5.9 Role Session

##### 2.1.5.9.1 Definition
- Assuming a role creates a temporary **role session**.

##### 2.1.5.9.2 Principal ARN
- Requests appear as an STS assumed-role principal conceptually like:

`arn:aws:sts::<account>:assumed-role/<role-name>/<session-name>`

##### 2.1.5.9.3 Importance
- AWS evaluates subsequent requests in the context of this role session.

#### 2.1.5.10 Role Session Name

##### 2.1.5.10.1 Purpose
- Identifies a particular session of the role.

##### 2.1.5.10.2 Observability
- Session name appears in assumed-role identity information and can appear in CloudTrail records.

##### 2.1.5.10.3 Security
- Trust policies can constrain `sts:RoleSessionName`.

##### 2.1.5.10.4 Operational Value
- Meaningful session names improve traceability when many principals use the same role.

#### 2.1.5.11 Session Duration

##### 2.1.5.11.1 Temporary Nature
- Role sessions have a limited lifetime.

##### 2.1.5.11.2 Maximum Session Duration
- IAM role configuration defines its maximum session duration.

##### 2.1.5.11.3 AssumeRole
- Caller can request a duration within allowed limits.

##### 2.1.5.11.4 Principle
- Use the shortest practical session duration for the workload/use case.

#### 2.1.5.12 Session Policies

##### 2.1.5.12.1 Purpose
- Optional policies passed when creating a role session.

##### 2.1.5.12.2 Effective Permissions

`role permissions`
∩
`session policy`
=
`session permissions`

##### 2.1.5.12.3 Critical Rule
- Session policies can **reduce** permissions.
- They cannot grant permissions beyond the role's own permissions.

##### 2.1.5.12.4 Use Case
- One broad role exists, but a particular session should receive a narrower subset.

#### 2.1.5.13 Session Tags

##### 2.1.5.13.1 Purpose
- Tags can be passed into role sessions.

##### 2.1.5.13.2 Authorization
- Policies can use session/principal tags for attribute-based access control.

##### 2.1.5.13.3 Example Mental Model

`role session tag: project=alpha`
→ policy condition checks `project`
→ access only Alpha resources

##### 2.1.5.13.4 Boundary
- Detailed fine-grained authorization belongs mainly to 2.1.7.

#### 2.1.5.14 Source Identity

##### 2.1.5.14.1 Purpose
- Records an identity value representing the original actor behind a role session.

##### 2.1.5.14.2 Benefit
- Helps preserve traceability across role assumptions.

##### 2.1.5.14.3 CloudTrail
- Source identity can be used to determine who originally assumed/used the role.

##### 2.1.5.14.4 Role Chaining
- Source identity can persist through chained role sessions when configured correctly.

#### 2.1.5.15 Cross-Account Access

##### 2.1.5.15.1 Classic Use Case
- Principal in Account A needs resources in Account B.

##### 2.1.5.15.2 Pattern

`Account A`
`developer / workload`
        │
        │ sts:AssumeRole
        ▼
`Account B`
`TargetRole`
        │
        ▼
temporary Role B credentials
        │
        ▼
Account B resources

##### 2.1.5.15.3 Benefit
- No IAM user and permanent access key need to be created in Account B.

##### 2.1.5.15.4 AWS Principle
- IAM roles are the primary general-purpose mechanism for delegated cross-account access.

#### 2.1.5.16 Same-Account Role Assumption

##### 2.1.5.16.1 Use Cases
- Privilege separation.
- Temporary administrative access.
- Application switches to a narrower or specialized permission set.

##### 2.1.5.16.2 Example

`Developer identity`
→ assume `DeploymentRole`
→ deploy application
→ session expires
→ developer no longer has deployment-role credentials

#### 2.1.5.17 Privilege Separation

##### 2.1.5.17.1 Pattern
- Normal identity has limited everyday permissions.
- Elevated role is assumed only when required.

##### 2.1.5.17.2 Benefit
- Reduces standing privileges.

##### 2.1.5.17.3 Example
- Developer:
  - normal → read development resources.
  - deployment role → deploy production release.

#### 2.1.5.18 AWS Service Roles

##### 2.1.5.18.1 Concept
- AWS services can assume roles to perform actions on your behalf.

##### 2.1.5.18.2 Trust Policy
- Trusts an AWS service principal.

##### 2.1.5.18.3 Examples
- Lambda execution role.
- EC2 role.
- ECS task role.

##### 2.1.5.18.4 Important
- Your application usually does not call `AssumeRole` manually for these managed runtime roles.
- AWS service/runtime obtains and rotates temporary credentials.

#### 2.1.5.19 Lambda Execution Role

##### 2.1.5.19.1 Trust
- Role trusts the Lambda service principal.

##### 2.1.5.19.2 Permissions
- Role permissions define AWS resources the function can access.

##### 2.1.5.19.3 Runtime
- Lambda assumes the execution role and supplies temporary credentials to function runtime.

##### 2.1.5.19.4 Developer Pattern
- Function SDK uses those credentials automatically.

#### 2.1.5.20 EC2 Role

##### 2.1.5.20.1 Trust
- Role trusts EC2 service.

##### 2.1.5.20.2 Attachment
- Role is associated with EC2 through an instance profile.

##### 2.1.5.20.3 Runtime
- Temporary credentials become available through the instance metadata credential mechanism.

##### 2.1.5.20.4 Principle
- Do not manually assume the same role merely to refresh EC2 credentials; the runtime handles credential rotation.

#### 2.1.5.21 ECS and Other Workload Roles

##### 2.1.5.21.1 ECS
- Task role provides application permissions to ECS tasks.

##### 2.1.5.21.2 EKS
- Supported workload identity/federation mechanisms map workloads to IAM roles.

##### 2.1.5.21.3 General Pattern

`AWS workload identity`
→ trusted role
→ temporary credentials
→ AWS API

#### 2.1.5.22 Federated Role Assumption

##### 2.1.5.22.1 SAML
- Federated users can obtain role credentials through:
  - `AssumeRoleWithSAML`.

##### 2.1.5.22.2 OIDC/Web Identity
- Web/OIDC identity can obtain role credentials through:
  - `AssumeRoleWithWebIdentity`.

##### 2.1.5.22.3 Ordinary AWS Principal
- IAM user/role commonly uses:
  - `AssumeRole`.

##### 2.1.5.22.4 Connection
- Federation concepts were introduced in 2.1.1.

#### 2.1.5.23 AssumeRoleWithWebIdentity

##### 2.1.5.23.1 Input
- Valid web identity/OIDC token.

##### 2.1.5.23.2 Trust
- Role trust policy trusts configured OIDC provider and constrains relevant claims.

##### 2.1.5.23.3 Output
- Temporary AWS role credentials.

##### 2.1.5.23.4 Typical Use
- External workloads.
- CI/CD OIDC.
- Web identity federation.
- Supported Kubernetes workload federation patterns.

#### 2.1.5.24 AssumeRoleWithSAML

##### 2.1.5.24.1 Input
- SAML assertion from trusted SAML identity provider.

##### 2.1.5.24.2 Output
- Temporary AWS credentials representing a role.

##### 2.1.5.24.3 Typical Use
- Enterprise workforce federation.

#### 2.1.5.25 External ID

##### 2.1.5.25.1 Problem
- Third-party organization/service needs to assume a role in your account.

##### 2.1.5.25.2 External ID
- Shared identifier included in AssumeRole request and required by trust-policy condition.

##### 2.1.5.25.3 Purpose
- Helps prevent the **confused deputy problem** in third-party cross-account access.

##### 2.1.5.25.4 Pattern

`third party`
→ AssumeRole + correct ExternalId
→ trust-policy condition succeeds

##### 2.1.5.25.5 Exam Trigger
- "Third-party vendor accesses multiple customer AWS accounts"
  → think **role + external ID**.

#### 2.1.5.26 MFA-Protected Role Assumption

##### 2.1.5.26.1 Trust Policy
- Can require MFA context when role is assumed.

##### 2.1.5.26.2 Use Case
- Sensitive/elevated human-access roles.

##### 2.1.5.26.3 Principle
- Add stronger authentication requirements to privileged role assumption.

#### 2.1.5.27 Role Chaining

##### 2.1.5.27.1 Definition
- An assumed role uses its temporary credentials to assume another role.

##### 2.1.5.27.2 Flow

`Identity`
→ Role A
→ Role B

##### 2.1.5.27.3 Use Case
- Multi-account delegation.
- Layered access paths.

##### 2.1.5.27.4 Trade-Off
- More complex trust and traceability.
- Chained sessions have additional session-duration constraints.

##### 2.1.5.27.5 Exam Mindset
- Do not build unnecessary role chains when direct trust/delegation is simpler.

#### 2.1.5.28 Role Re-Assumption

##### 2.1.5.28.1 AWS Compute Roles
- EC2, ECS, EKS-supported mechanisms, and Lambda already provide renewable temporary credentials.

##### 2.1.5.28.2 Usually Unnecessary
- Workload should not repeatedly assume its own role merely to refresh credentials.

##### 2.1.5.28.3 Exceptions
- Re-assumption may be used when deliberately applying:
  - session tags,
  - session policy,
  - other session-specific controls.

#### 2.1.5.29 AWS CLI Role Profiles

##### 2.1.5.29.1 Pattern
- CLI profile can define:
  - target `role_arn`,
  - source profile/credential source.

##### 2.1.5.29.2 Flow

`source credentials`
→ CLI calls STS AssumeRole
→ caches/uses temporary role credentials
→ signs target AWS API requests

##### 2.1.5.29.3 Benefit
- User does not manually copy temporary access keys.

#### 2.1.5.30 SDK Assume-Role Providers

##### 2.1.5.30.1 Pattern
- SDK credential provider can assume configured role.

##### 2.1.5.30.2 Benefit
- Provider handles:
  - AssumeRole call,
  - temporary credentials,
  - credential refresh.

##### 2.1.5.30.3 Principle
- Prefer credential-provider abstraction over manually copying STS credentials through application code.

#### 2.1.5.31 Effective Permissions of a Role Session

##### 2.1.5.31.1 Basic Model

`role permissions`
∩
`session policy`
∩
`applicable boundaries / SCPs / resource policies / explicit denies`
→ effective access

##### 2.1.5.31.2 Session Policy
- Narrows the role.
- Never expands it.

##### 2.1.5.31.3 Explicit Deny
- Applicable explicit deny overrides allow.

##### 2.1.5.31.4 Boundary
- Full IAM policy evaluation belongs to 2.1.6.

#### 2.1.5.32 Original Principal Permissions

##### 2.1.5.32.1 Before AssumeRole
- Caller uses original identity/session permissions.

##### 2.1.5.32.2 After AssumeRole
- Calls made using new STS credentials represent the assumed-role session.

##### 2.1.5.32.3 Important
- Role assumption is not simply "add the role permissions on top of the caller's permissions."

##### 2.1.5.32.4 Mental Model
- **Switch security context**, not **permission union**.

#### 2.1.5.33 Resource-Based Policies and Role Sessions

##### 2.1.5.33.1 Resource Policies
- Can grant access to:
  - IAM role principal,
  - sometimes role-session principal.

##### 2.1.5.33.2 AWS Guidance
- Prefer granting to the IAM role principal where possible rather than individual role-session ARNs.

##### 2.1.5.33.3 Reason
- More stable and manageable authorization model.

#### 2.1.5.34 CloudTrail and Assumed Roles

##### 2.1.5.34.1 Audit
- CloudTrail can record:
  - AssumeRole event,
  - subsequent actions using role session.

##### 2.1.5.34.2 Useful Identity Information
- Role ARN.
- Assumed-role session ARN.
- Session name.
- Source identity where configured.

##### 2.1.5.34.3 Principle
- Role assumption improves delegation but session identity must remain traceable.

##### 2.1.5.35.2 Human Privilege Elevation

##### 2.1.5.35.3 AWS Workload

##### 2.1.5.35.4 External CI/CD

##### 2.1.5.35.5 Third Party

#### 2.1.5.36 Assume-Role Decision Tree

##### 2.1.5.36.1 AWS Principal Needs Different Permissions
- → `AssumeRole`.

##### 2.1.5.36.2 Cross-Account AWS Principal
- → target role trust + caller `sts:AssumeRole`.

##### 2.1.5.36.3 OIDC Identity
- → `AssumeRoleWithWebIdentity`.

##### 2.1.5.36.4 SAML Identity
- → `AssumeRoleWithSAML`.

##### 2.1.5.36.5 AWS Service/Compute Runtime
- → service/workload role; AWS runtime usually performs assumption/credential delivery.

##### 2.1.5.36.6 Third-Party Vendor
- → cross-account role + external ID condition.

##### 2.1.5.36.7 Need Narrower Session
- → session policy and/or session tags/conditions.

#### 2.1.5.37 Common Exam Traps

##### 2.1.5.37.1 "Role Has Access Keys"
- False.
- Role credentials are temporary and generated for sessions.

##### 2.1.5.37.2 "Trust Policy Defines What S3 Actions Role Can Perform"
- False.
- Trust policy defines who may assume role.
- Permissions policy defines role actions.

##### 2.1.5.37.3 "Caller Permission Alone Is Enough for Cross-Account AssumeRole"
- False.
- Target role must also trust the caller/account.

##### 2.1.5.37.4 "Assuming Role Adds Permissions to Existing Identity"
- False.
- New credentials represent the role session.

##### 2.1.5.37.5 "Session Policy Can Grant Extra Permissions"
- False.
- It can only restrict the role's permissions.

##### 2.1.5.37.6 "Cross-Account Access Requires IAM User in Target Account"
- False.
- Role assumption is the normal delegated-access pattern.

##### 2.1.5.37.7 "Third-Party Access → Share IAM User Credentials"
- Wrong.
- Prefer cross-account role; external ID when appropriate.

##### 2.1.5.37.8 "Lambda Must Call AssumeRole for Its Execution Role"
- Normally false.
- Lambda already receives execution-role credentials.

##### 2.1.5.37.9 "AssumeRole Credentials Are Permanent"
- False.
- They expire.

##### 2.1.5.37.10 "External ID Is a Password"
- Incorrect mental model.
- It is a trust-condition mechanism primarily used to mitigate confused-deputy risk.

##### 2.1.5.37.11 "Role Session Name Is Cosmetic"
- False.
- It contributes to session identity and auditability.

##### 2.1.5.37.12 "Role Chaining Is Always Preferred for Multi-Account Access"
- False.
- Use the simplest trust/delegation model that satisfies requirements.
