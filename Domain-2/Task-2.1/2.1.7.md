### 2.1.7 Implement application-level authorization for fine-grained access control

#### 2.1.7.1 Exam and Task Context

##### 2.1.7.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.1 is **Implement authentication and/or authorization for applications and AWS services**.
- Skill 2.1.7 is **Implement application-level authorization for fine-grained access control**.
- This is one of the new skills added in the current exam-guide revision.

##### 2.1.7.1.2 Position Inside Task 2.1
- 2.1.1 → establish identity and federation.
- 2.1.2 → secure application APIs with bearer tokens.
- 2.1.3 → configure AWS programmatic credentials.
- 2.1.4 → make authenticated AWS API calls.
- 2.1.5 → assume IAM roles.
- 2.1.6 → define permissions for IAM principals.
- **2.1.7 → apply authorization inside the application to specific operations and data.**
- 2.1.8 → handle authentication between services in a microservice architecture.

##### 2.1.7.1.3 Core Question
- **After the caller is authenticated, exactly which application operation and which application data may that caller access?**

#### 2.1.7.2 Core Mental Model

Authentication answers:

`Who is the caller?`

Application authorization answers:

`May this caller perform this operation on this resource/data under this context?`

A useful model is:

`principal`
→ `claims / groups / roles / attributes`
→ `application action`
→ `application resource`
→ `authorization rule`
→ `ALLOW / DENY`

Fine-grained means the decision is more precise than:
- authenticated vs unauthenticated,
- administrator vs non-administrator,
- entire API allowed vs denied.

It can operate at:
- API route/method,
- GraphQL field,
- business action,
- object/item,
- tenant,
- owner,
- attribute,
- state,
- scope.

#### 2.1.7.3 IAM Authorization vs Application Authorization

##### 2.1.7.3.1 IAM Authorization
- Controls access to AWS APIs/resources.
- Example:
  - may this Lambda execution role call `dynamodb:GetItem` on table X?

##### 2.1.7.3.2 Application Authorization
- Controls access to domain/application operations.
- Example:
  - may user Alice update **order 123**?
  - may an editor publish an article?
  - may a user read only records belonging to their tenant?

##### 2.1.7.3.3 Critical Distinction
- A backend role may be allowed by IAM to read an entire DynamoDB table.
- Application code may still need to restrict each user to only their own records.
- IAM permission to the backend is **not** automatically end-user authorization.

#### 2.1.7.4 Authorization Inputs

A fine-grained decision commonly uses:

##### 2.1.7.4.1 Principal
- User or service identity.

##### 2.1.7.4.2 Claims
- Token attributes such as:
  - `sub`,
  - username,
  - groups,
  - scopes,
  - custom claims.

##### 2.1.7.4.3 Action
- Domain operation:
  - `readOrder`,
  - `editPost`,
  - `approveInvoice`,
  - `deleteComment`.

##### 2.1.7.4.4 Resource
- Application resource:
  - order,
  - document,
  - project,
  - tenant record,
  - GraphQL field.

##### 2.1.7.4.5 Context
- Additional information:
  - ownership,
  - tenant,
  - time,
  - resource state,
  - source application,
  - requested fields.

#### 2.1.7.5 Coarse-Grained vs Fine-Grained

##### 2.1.7.5.1 Coarse-Grained
- User can access whole API or service.
- Example:
  - authenticated users may invoke `/orders`.

##### 2.1.7.5.2 Fine-Grained
- Access differs by:
  - operation,
  - resource,
  - data owner,
  - role/group,
  - scope,
  - field.

Example:

`GET /orders/123`
→ caller owns order 123
→ allow

`GET /orders/456`
→ caller does not own order 456
→ deny

##### 2.1.7.5.3 Exam Mindset
- If the requirement says:
  - only own data,
  - only group X,
  - only read but not write,
  - specific GraphQL fields,
  - tenant isolation,
  - action-specific access,
then think **fine-grained application authorization**.

#### 2.1.7.6 RBAC — Role-Based Access Control

##### 2.1.7.6.1 Model
- Permissions are assigned to roles.
- Users receive roles.

`user`
→ `role`
→ `permissions`

##### 2.1.7.6.2 Examples
- Reader:
  - read articles.
- Editor:
  - read + edit.
- Publisher:
  - read + edit + publish.

##### 2.1.7.6.3 AWS Building Block
- Amazon Cognito user-pool groups can represent application roles.
- Group membership is included in tokens in the `cognito:groups` claim.

##### 2.1.7.6.4 Strength
- Simple and understandable for stable permission sets.

##### 2.1.7.6.5 Limitation
- Role explosion can occur when authorization depends on many resource-specific attributes.

#### 2.1.7.7 Cognito User-Pool Groups

##### 2.1.7.7.1 Purpose
- Cognito groups organize users into permission categories.

##### 2.1.7.7.2 Token Claims
- Group membership appears in Cognito ID and access tokens through:
  - `cognito:groups`.

##### 2.1.7.7.3 Application Use
- Backend can inspect verified group claims to make authorization decisions.

##### 2.1.7.7.4 Example

`cognito:groups = ["Editors"]`

Application rule:

`if user ∈ Editors`
→ allow `editArticle`

##### 2.1.7.7.5 Important
- The existence of a group claim does not itself enforce business authorization.
- The API/application must map that claim to allowed operations.

#### 2.1.7.8 OAuth Scopes

##### 2.1.7.8.1 Purpose
- Represent granted API permissions.

##### 2.1.7.8.2 Example
- `orders.read`
- `orders.write`
- `payments.refund`

##### 2.1.7.8.3 Cognito
- Cognito resource servers can define custom OAuth scopes.
- Custom scopes appear in the access token's `scope` claim.

##### 2.1.7.8.4 API Decision
- Protected API verifies the required scope for the requested operation.

Example:

`POST /orders`
→ requires `orders.write`

##### 2.1.7.8.5 Strength
- Natural for operation-level API authorization.

#### 2.1.7.9 Groups vs Scopes

##### 2.1.7.9.1 Group
- Describes **who the user is within the application's role model**.

Example:
- Editor.
- Administrator.
- Support.

##### 2.1.7.9.2 Scope
- Describes **what access the token was granted to an API/resource server**.

Example:
- `orders.read`.

##### 2.1.7.9.3 Mental Model

`group`
→ role/membership

`scope`
→ granted API capability

##### 2.1.7.9.4 They Can Work Together
- Group determines which scopes a user/client can obtain.
- API checks scopes.
- Backend can additionally use group membership for domain decisions.

#### 2.1.7.10 API Gateway JWT Authorization

##### 2.1.7.10.1 HTTP API
- API Gateway JWT authorizers can validate JWTs from Cognito or compatible OIDC providers.

##### 2.1.7.10.2 Route-Level Scopes
- Different routes can require different authorization scopes.

Example:

`GET /orders`
→ `orders.read`

`POST /orders`
→ `orders.write`

##### 2.1.7.10.3 Validation
- API Gateway validates token details such as:
  - signature,
  - issuer,
  - audience/client,
  - expiration,
  - required scopes.

##### 2.1.7.10.4 Benefit
- Unauthorized requests can be rejected before reaching backend Lambda/application code.

#### 2.1.7.11 API Gateway Cognito Authorizer

##### 2.1.7.11.1 REST API
- REST APIs can use a Cognito user-pool authorizer.

##### 2.1.7.11.2 Access Token
- Method can require OAuth scopes.

##### 2.1.7.11.3 ID or Access Token
- Cognito tokens can also expose group/identity claims to backend code.

##### 2.1.7.11.4 Fine-Grained Pattern
- API Gateway:
  - coarse/route permission.
- Backend:
  - resource ownership or business-state checks.

#### 2.1.7.12 Native Authorizer vs Application Logic

##### 2.1.7.12.1 Native Authorizer
Use when authorization can be expressed with:
- valid JWT,
- required issuer/audience,
- required OAuth scopes.

##### 2.1.7.12.2 Backend Application Authorization
Use when decision depends on:
- object ownership,
- tenant,
- database state,
- domain rules,
- resource attributes,
- workflow state.

##### 2.1.7.12.3 Best Pattern
- Reject invalid/obviously unauthorized requests at the API boundary.
- Perform resource-specific business authorization in the application where required.

#### 2.1.7.13 Lambda Authorizers

##### 2.1.7.13.1 Purpose
- API Gateway Lambda authorizers support custom authorization logic.

##### 2.1.7.13.2 Inputs
Can use:
- bearer token,
- headers,
- query parameters,
- request context,
depending on authorizer type/API.

##### 2.1.7.13.3 Output
- REST API Lambda authorizer commonly returns an IAM policy controlling invocation.

##### 2.1.7.13.4 Use Cases
- Legacy tokens.
- Custom identity systems.
- Authorization rules not supported by native JWT/Cognito authorizers.

##### 2.1.7.13.5 Trade-Off
- Additional:
  - Lambda execution,
  - latency,
  - code,
  - testing,
  - security responsibility.

##### 2.1.7.13.6 Rule
- Prefer native JWT/Cognito authorization when it satisfies requirements.

#### 2.1.7.14 Ownership-Based Authorization

##### 2.1.7.14.1 Requirement
- User may access only resources they own.

##### 2.1.7.14.2 Pattern

`authenticated user sub`
→ compare with
`resource.ownerId`
→ allow/deny

##### 2.1.7.14.3 Stable Identity
- Prefer a stable immutable identity claim such as Cognito `sub` rather than mutable display attributes such as email where appropriate.

##### 2.1.7.14.4 Example
- DynamoDB item:

`PK = ORDER#123`
`ownerId = <Cognito sub>`

Request:

`token.sub == item.ownerId`
→ allow

#### 2.1.7.15 Why Authentication Is Not Ownership

##### 2.1.7.15.1 Incorrect Pattern
- "User has a valid JWT, therefore return requested record."

##### 2.1.7.15.2 Correct Pattern
- Valid token proves identity.
- Application must still check that the identity is authorized for the requested record.

##### 2.1.7.15.3 Security Risk
- Failure to perform object-level authorization can cause **insecure direct object reference / broken object-level authorization**.

#### 2.1.7.16 Tenant-Based Authorization

##### 2.1.7.16.1 Requirement
- Users may access resources only within their tenant.

##### 2.1.7.16.2 Pattern

`principal.tenantId`
→ must equal
`resource.tenantId`

##### 2.1.7.16.3 Data Query
- Prefer designing queries so unauthorized tenant data is not fetched unnecessarily.

##### 2.1.7.16.4 Boundary
- Full multi-tenant data-access modeling belongs to Skill 2.3.6.
- Here, tenant identity is an example of an application authorization attribute.

#### 2.1.7.17 ABAC — Attribute-Based Access Control

##### 2.1.7.17.1 Model
- Authorization uses attributes of:
  - principal,
  - resource,
  - action,
  - context.

##### 2.1.7.17.2 Example

`user.department = finance`
AND
`document.department = finance`
AND
`action = read`
→ allow

##### 2.1.7.17.3 Difference From RBAC
- RBAC:
  - role determines access.
- ABAC:
  - attributes and policy conditions determine access.

##### 2.1.7.17.4 Strength
- Can avoid huge numbers of role combinations.

#### 2.1.7.18 ACL-Style Authorization

##### 2.1.7.18.1 Model
- Resource maintains list of principals/groups and permissions.

Example:

`document 123 ACL`
- Alice → read/write
- Bob → read

##### 2.1.7.18.2 Fit
- Useful where access differs per resource.

##### 2.1.7.18.3 Trade-Off
- Can be harder to manage at very large scale.

#### 2.1.7.19 Authorization Decision Location

##### 2.1.7.19.1 API Boundary
- API Gateway authorizer.
- Good for:
  - identity validation,
  - route-level scopes.

##### 2.1.7.19.2 Application Service
- Lambda/backend code.
- Good for:
  - ownership,
  - business state,
  - resource-specific decisions.

##### 2.1.7.19.3 Data Access Layer
- Query/filter design can enforce tenant/owner boundaries.

##### 2.1.7.19.4 GraphQL Resolver
- AppSync resolver can apply field/resource-specific rules.

##### 2.1.7.19.5 Principle
- Enforce authorization as close as practical to the protected operation/data, while avoiding duplicated inconsistent rules.

#### 2.1.7.20 AWS AppSync Authorization

##### 2.1.7.20.1 In-Scope Relevance
- AWS AppSync is explicitly in the DVA-C02 in-scope service list.
- It provides a strong AWS-native example of fine-grained application authorization.

##### 2.1.7.20.2 Authorization Modes
AppSync supports:
- API key,
- AWS Lambda,
- AWS IAM,
- OIDC,
- Amazon Cognito user pools.

##### 2.1.7.20.3 Fine-Grained Control
- Authorization can be applied at:
  - API,
  - type,
  - field,
  - resolver/data level.

#### 2.1.7.21 AppSync + Cognito Groups

##### 2.1.7.21.1 Group-Based Access
- AppSync can use Cognito group claims to control GraphQL operations/fields.

Example:
- Readers:
  - query posts.
- Bloggers:
  - query posts,
  - create posts.

##### 2.1.7.21.2 GraphQL Schema
- Cognito authorization directives can restrict fields/types by group.

##### 2.1.7.21.3 Benefit
- Authorization rule becomes part of the GraphQL schema/API contract.

#### 2.1.7.22 AppSync Field-Level Authorization

##### 2.1.7.22.1 Fine-Grained Meaning
- Different GraphQL fields can use different authorization rules/modes.

Example:
- `Post.title`
  - readable broadly.
- `Post.internalNotes`
  - restricted to Admin group.

##### 2.1.7.22.2 Additional Authorization Modes
- AppSync can configure a default authorization mode and additional modes.
- Schema directives can control which modes apply to specific fields/types.

#### 2.1.7.23 AppSync Owner-Based Authorization

##### 2.1.7.23.1 Resolver Context
- AppSync passes caller identity information into resolver context.

##### 2.1.7.23.2 Pattern

`context.identity`
→ compare to
`resource owner`

##### 2.1.7.23.3 Example
- Only user who created a post may update it.

##### 2.1.7.23.4 Data Enforcement
- Resolver logic can reject unauthorized access or constrain DynamoDB operations.

#### 2.1.7.24 AppSync Data-Level Authorization

##### 2.1.7.24.1 Resolver Logic
- Fine-grained authorization can use:
  - user identity,
  - group membership,
  - resource ownership,
  - request conditions.

##### 2.1.7.24.2 Important
- API-level authentication does not automatically protect every returned field/data item.
- Resolver logic may be necessary for object-level policy.

#### 2.1.7.25 IAM as Application Authorization Input

##### 2.1.7.25.1 IAM-Protected AppSync/API Gateway
- AWS principals can be authorized with IAM.

##### 2.1.7.25.2 Strength
- Natural for:
  - internal AWS applications,
  - workloads,
  - service-to-service callers.

##### 2.1.7.25.3 Limit
- IAM controls AWS API/resource access.
- Domain-specific end-user ownership/business rules may still require application logic.

#### 2.1.7.26 DynamoDB Fine-Grained Access Context

##### 2.1.7.26.1 IAM Conditions
- DynamoDB supports IAM condition-based fine-grained access patterns for some operations and attributes.

##### 2.1.7.26.2 Example Concept
- Restrict access based on leading partition-key values in supported IAM policies.

##### 2.1.7.26.3 Application-Level Caveat
- This is AWS-resource authorization and can support data isolation.
- It does not replace broader application business authorization when backend uses one execution role for many users.

#### 2.1.7.27 Backend-for-Frontend Pattern

##### 2.1.7.27.1 Architecture

`client`
→ JWT
→ API Gateway
→ Lambda/backend
→ DynamoDB

##### 2.1.7.27.2 API Gateway
- Validates token/scopes.

##### 2.1.7.27.3 Backend
- Reads verified identity claims.
- Applies:
  - ownership,
  - tenant,
  - business authorization.

##### 2.1.7.27.4 DynamoDB
- Backend role has only infrastructure permissions needed by application.
- Application code ensures user-level authorization.

#### 2.1.7.28 Never Trust Client-Supplied Identity Attributes

##### 2.1.7.28.1 Bad Pattern
Client sends:

```json
{
  "userId": "123",
  "tenantId": "tenant-a"
}
```

Backend trusts these values as authorization identity.

##### 2.1.7.28.2 Correct Pattern
- Derive identity from:
  - validated JWT claims,
  - trusted authorizer context,
  - authenticated IAM principal.

##### 2.1.7.28.3 Rule
- Request body/path data can identify a **target resource**.
- It should not be accepted as proof of caller identity.

#### 2.1.7.29 Subject Claim — `sub`

##### 2.1.7.29.1 Purpose
- OIDC/Cognito subject claim identifies the authenticated principal within the issuer.

##### 2.1.7.29.2 Use
- Often a stronger owner identifier than:
  - email,
  - display name,
  - username-like mutable attributes.

##### 2.1.7.29.3 Rule
- Store an immutable trusted principal identifier with owned resources when owner-based authorization is required.

#### 2.1.7.30 Deny by Default

##### 2.1.7.30.1 Application Principle
- If no authorization rule explicitly permits the operation:
  - deny.

##### 2.1.7.30.2 Why
- Prevents new routes/actions from becoming accidentally accessible when authorization configuration is forgotten.

##### 2.1.7.30.3 Similarity to IAM
- Mirrors IAM's default-deny mindset.

#### 2.1.7.31 Centralized vs Distributed Authorization Logic

##### 2.1.7.31.1 Centralized
- Shared policy/authorizer component.
- Benefit:
  - consistency,
  - easier governance.

##### 2.1.7.31.2 Distributed
- Each service implements rules.
- Benefit:
  - domain context available locally.
- Risk:
  - duplicated/inconsistent logic.

##### 2.1.7.31.3 Practical Model
- Centralize reusable identity/policy rules where useful.
- Keep business-specific authorization near the domain operation.

#### 2.1.7.32 Authorization Caching

##### 2.1.7.32.1 Why
- Authorizer results may be cacheable to reduce latency/cost.

##### 2.1.7.32.2 Risk
- Permission changes may not take effect immediately while cached decision remains valid.

##### 2.1.7.32.3 Rule
- Cache duration must match acceptable authorization-staleness risk.

#### 2.1.7.33 TOCTOU — Authorization and State Changes

##### 2.1.7.33.1 Problem
- Application:
  1. checks resource state,
  2. authorizes,
  3. resource changes,
  4. operation executes based on stale assumption.

##### 2.1.7.33.2 Mitigation
- When authorization depends on mutable resource state, couple authorization with atomic/conditional update where practical.

##### 2.1.7.33.3 Example
- DynamoDB condition expression can ensure the owner/status still matches when update occurs.

#### 2.1.7.34 Read Authorization

##### 2.1.7.34.1 Avoid Fetch-All-Then-Filter
- Fetching unauthorized data and filtering afterward increases:
  - exposure risk,
  - cost,
  - accidental leakage risk.

##### 2.1.7.34.2 Better
- Design data access so query itself limits data by:
  - tenant,
  - owner,
  - authorized partition,
where possible.

##### 2.1.7.34.3 Connection
- Multi-tenant data access is expanded in Skill 2.3.6.

#### 2.1.7.35 Write Authorization

##### 2.1.7.35.1 Verify
- caller may perform action,
- caller may modify target resource,
- resource is in appropriate state.

##### 2.1.7.35.2 Protect Sensitive Fields
- A user may have permission to update a resource but not every field.

Example:
- user can update shipping address,
- cannot update order owner or payment status.

##### 2.1.7.35.3 Fine-Grained Meaning
- Authorization can apply to individual attributes/fields, not just whole records.

#### 2.1.7.36 Horizontal vs Vertical Authorization

##### 2.1.7.36.1 Vertical
- Different privilege levels.

Example:
- User vs Admin.

##### 2.1.7.36.2 Horizontal
- Same role, different resource ownership.

Example:
- Customer A may read their order but not Customer B's order.

##### 2.1.7.36.3 Exam Relevance
- Fine-grained authorization includes both.

#### 2.1.7.37 Authorization Error Handling

##### 2.1.7.37.1 Unauthorized / Unauthenticated
- If identity is invalid/missing:
  - authentication failure.

##### 2.1.7.37.2 Forbidden
- Identity known, action not allowed:
  - authorization failure.

##### 2.1.7.37.3 Data Leakage
- Avoid error responses that reveal sensitive resource existence unnecessarily.

#### 2.1.7.38 Logging Authorization Decisions

##### 2.1.7.38.1 Useful Data
- principal identifier,
- requested action,
- resource identifier,
- allow/deny result,
- policy/rule reason,
- request/trace ID.

##### 2.1.7.38.2 Avoid
- logging complete bearer tokens,
- sensitive data,
- secrets.

##### 2.1.7.38.3 Benefit
- Debugging.
- Auditability.
- Security incident analysis.

#### 2.1.7.39 Testing Authorization

##### 2.1.7.39.1 Positive Tests
- Authorized principal can perform allowed operation.

##### 2.1.7.39.2 Negative Tests
- Wrong group denied.
- Missing scope denied.
- Wrong owner denied.
- Wrong tenant denied.
- Unauthenticated caller denied.

##### 2.1.7.39.3 Boundary Tests
- User in multiple groups.
- Expired token.
- Resource ownership changes.
- Missing claim.
- Malformed authorization context.

##### 2.1.7.39.4 Principle
- Security testing must include denial cases, not only successful paths.

#### 2.1.7.40 Application Authorization Decision Tree

##### 2.1.7.40.1 Route Needs One API Capability
- Use OAuth scope + API Gateway JWT/Cognito authorizer.

##### 2.1.7.40.2 Access Based on User Role
- Use Cognito group/RBAC claim.

##### 2.1.7.40.3 Access Depends on Resource Owner
- Compare trusted principal identity to stored owner.

##### 2.1.7.40.4 Access Depends on Tenant
- Match trusted tenant identity to resource/data partition.

##### 2.1.7.40.5 AppSync GraphQL Field-Level Access
- Use Cognito/IAM/OIDC authorization modes and schema/resolver rules.

##### 2.1.7.40.6 Complex Custom API Rule
- Backend authorization logic or Lambda authorizer if API-boundary custom logic is appropriate.

#### 2.1.7.41 Common Exam Traps

##### 2.1.7.41.1 "Valid JWT Means User May Access Any Record"
- False.
- Authentication is not object-level authorization.

##### 2.1.7.41.2 "IAM Role for Lambda Solves End-User Authorization"
- False.
- It authorizes the Lambda workload against AWS resources.

##### 2.1.7.41.3 "ID Token Is Always Best for API Authorization"
- False.
- Access-token scopes are the natural OAuth API authorization mechanism.

##### 2.1.7.41.4 "Client-Supplied userId Is Trusted Identity"
- False.

##### 2.1.7.41.5 "Cognito Group Automatically Enforces Application Permissions"
- False.
- Group is a claim/input; application/API enforcement is still required.

##### 2.1.7.41.6 "OAuth Scope Solves Ownership"
- False.
- Scope can say `orders.write`; it does not necessarily say which order belongs to caller.

##### 2.1.7.41.7 "Admin/User RBAC Is Fine-Grained Enough for Every System"
- False.
- Ownership, tenant, attributes, and business state may require finer policies.

##### 2.1.7.41.8 "Fetch All Data Then Filter Is Equivalent to Authorized Query"
- Functionally possible but weaker from least-exposure/cost/security perspective.

##### 2.1.7.41.9 "AppSync Authentication Mode Automatically Enforces Owner Rules"
- False.
- Fine-grained resource ownership may require field/resolver logic.

##### 2.1.7.41.10 "Lambda Authorizer Is Always Required"
- False.
- Native Cognito/JWT authorizers should be preferred when sufficient.

#### 2.1.7.44 Task 2.1 Big Picture

The authentication/authorization model is now:

`principal`
→ 2.1.1 establish identity
→ 2.1.2 carry identity/authorization in tokens
→ application/API validates token
→ **2.1.7 decide which application action/data is allowed**

Parallel AWS-service path:

`workload`
→ 2.1.3 credentials
→ 2.1.4 authenticated AWS call
→ 2.1.5 role session
→ 2.1.6 IAM authorization

The critical separation is:

**IAM answers what the workload may do to AWS resources.**

**Application authorization answers what the end user may do inside the application's domain.**

#### 2.1.7.46 Exam-Level Knowledge Frame

Know these decision patterns:

**Authenticated user + route permission**
→ access token scope.

**Application role**
→ Cognito group / RBAC.

**Specific object belongs to user**
→ owner-based authorization using trusted identity claim.

**Tenant isolation**
→ tenant attribute + data access rule.

**Complex attribute/context decision**
→ application ABAC/custom authorization logic.

**GraphQL field/data authorization**
→ AppSync authorization directives/resolvers.

**Simple JWT/scopes**
→ native API Gateway authorizer.

**Custom API authorization**
→ Lambda authorizer when native authorizer is insufficient.

Final principle:

**Fine-grained authorization is a decision about principal + action + application resource + context, made after authentication and enforced at the appropriate API, application, resolver, or data-access boundary.**
