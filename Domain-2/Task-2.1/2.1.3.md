### 2.1.3 Configure programmatic access to AWS

#### 2.1.3.1 Exam and Task Context

##### 2.1.3.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.1 is **Implement authentication and/or authorization for applications and AWS services**.
- Skill 2.1.3 is **Configure programmatic access to AWS**.

##### 2.1.3.1.2 Position Inside Task 2.1
- 2.1.1 established federated identity.
- 2.1.2 established bearer-token based application/API access.
- 2.1.3 now answers:

  **How does a developer, CLI, SDK, workload, or application obtain AWS credentials that can be used for AWS API access?**

- 2.1.4 then uses those credentials to make authenticated AWS service calls.
- 2.1.5 explains role assumption in more depth.
- 2.1.6 defines the permissions attached to the resulting principal/session.

#### 2.1.3.2 Core Mental Model

##### 2.1.3.2.1 Programmatic Access
- Programmatic access means accessing AWS through:
  - AWS SDKs,
  - AWS CLI,
  - AWS APIs,
  - automation tools,
  rather than manually through the AWS Management Console.

##### 2.1.3.2.2 Credential Chain

  `principal/workload`
  → obtain AWS credentials
  → SDK/CLI credential provider
  → sign AWS API request
  → AWS authenticates principal
  → IAM authorization evaluates permissions

##### 2.1.3.2.3 Security Principle
- Prefer **temporary credentials** whenever possible.
- Avoid distributing or embedding long-lived IAM-user access keys.

#### 2.1.3.3 AWS Credential Types

##### 2.1.3.3.1 Long-Term Credentials
- Typically IAM-user access keys:
  - access key ID,
  - secret access key.
- They remain valid until:
  - disabled,
  - deleted,
  - rotated.

##### 2.1.3.3.2 Temporary Credentials
- Generated dynamically through mechanisms such as:
  - IAM roles,
  - AWS STS,
  - IAM Identity Center,
  - workload federation.
- Include:
  - access key ID,
  - secret access key,
  - session token,
  - expiration.

##### 2.1.3.3.3 AWS Recommendation
- AWS strongly recommends temporary credentials over long-term IAM-user credentials for most programmatic access scenarios.

#### 2.1.3.4 Access Key Anatomy

##### 2.1.3.4.1 Access Key ID
- Public identifier for an AWS credential.

##### 2.1.3.4.2 Secret Access Key
- Secret cryptographic material used to sign AWS API requests.

##### 2.1.3.4.3 Session Token
- Required when using temporary credentials.

##### 2.1.3.4.4 Important Distinction
- Temporary AWS credentials are not just:
  - access key + secret key.
- The session token must also be supplied.

#### 2.1.3.5 Long-Term vs Temporary Credentials

##### 2.1.3.5.1 Long-Term
- Easier to misuse.
- Must be rotated/revoked manually.
- Dangerous if:
  - embedded in source code,
  - committed to a repository,
  - stored in CI/CD configuration,
  - copied to a server.

##### 2.1.3.5.2 Temporary
- Expire automatically.
- Obtained dynamically.
- Commonly tied to IAM roles or federated identities.
- Reduce exposure window.

##### 2.1.3.5.3 Decision
- If temporary credentials are available:
  - prefer them.
- Create/use IAM-user access keys only when no better supported mechanism exists.

#### 2.1.3.6 Credential Provider Chain

##### 2.1.3.6.1 Definition
- AWS SDKs and tools search a sequence of credential sources.
- When valid credentials are found, the search stops.
- This sequence is called the **credential provider chain**.

##### 2.1.3.6.2 Benefit
- Application code does not need to hard-code credentials.
- The same application can run:
  - locally,
  - on EC2,
  - in ECS,
  - in Lambda,
  - in another environment
  while credentials are supplied through the appropriate provider.

##### 2.1.3.6.3 Refresh
- Standardized SDK credential providers can automatically refresh temporary credentials when they expire.

##### 2.1.3.6.4 Important Caveat
- Exact provider order differs by SDK/tool.
- Understand the concept, not one universal sequence.

#### 2.1.3.7 Common Credential Providers

##### 2.1.3.7.1 Environment Variables
- Examples:
  - `AWS_ACCESS_KEY_ID`
  - `AWS_SECRET_ACCESS_KEY`
  - `AWS_SESSION_TOKEN`
- Useful in controlled temporary environments.
- Risky if long-lived secrets are injected or exposed carelessly.

##### 2.1.3.7.2 Shared Credentials File
- Common local path:
  - `~/.aws/credentials`.

##### 2.1.3.7.3 Shared Config File
- Common local path:
  - `~/.aws/config`.

##### 2.1.3.7.4 IAM Identity Center Provider
- SDK/CLI can obtain temporary credentials associated with an IAM Identity Center session/profile.

##### 2.1.3.7.5 Assume-Role Provider
- SDK/CLI can use one identity to assume an IAM role and obtain temporary credentials.

##### 2.1.3.7.6 Web Identity/OIDC Provider
- External identity token can be exchanged for role credentials.

##### 2.1.3.7.7 Container Credential Provider
- Used by containerized workloads such as ECS/EKS-supported patterns.

##### 2.1.3.7.8 EC2 Instance Metadata Provider
- Applications on EC2 can receive temporary credentials from an attached IAM role/instance profile.

#### 2.1.3.8 Local Developer Access

##### 2.1.3.8.1 Goal
- Developer running code on a workstation needs temporary credentials.

##### 2.1.3.8.2 Preferred Modern Patterns
- IAM Identity Center profile.
- AWS CLI login/local-development session.
- Assume-role profile.

##### 2.1.3.8.3 Avoid
- Hard-coded access keys in:
  - application code,
  - `.env` files committed to source control,
  - scripts checked into repositories.

#### 2.1.3.9 AWS CLI Profiles

##### 2.1.3.9.1 Purpose
- Profiles group configuration and credential-source information.

##### 2.1.3.9.2 Files
- `~/.aws/config`
- `~/.aws/credentials`

##### 2.1.3.9.3 Named Profiles
- Allow multiple AWS identities/accounts/roles to coexist locally.

##### 2.1.3.9.4 Example Mental Model

  `profile dev`
  → account A / role Developer

  `profile prod`
  → account B / role ReadOnly

##### 2.1.3.9.5 Security
- A profile can reference temporary/federated credentials rather than storing permanent keys.

#### 2.1.3.10 AWS CLI Environment Selection

##### 2.1.3.10.1 Default Profile
- Used when no explicit profile is selected.

##### 2.1.3.10.2 Named Profile
- Can be selected explicitly with CLI options or relevant environment configuration.

##### 2.1.3.10.3 Principle
- Do not assume "profile" itself is a credential.
- It is configuration describing where/how credentials and other settings are obtained.

#### 2.1.3.11 IAM Identity Center for Developer Access

##### 2.1.3.11.1 Purpose
- Centralized workforce identity and account access.

##### 2.1.3.11.2 Programmatic Flow

  `developer`
  → authenticate to IAM Identity Center
  → select account/permission set
  → CLI/SDK obtains temporary credentials
  → AWS API access

##### 2.1.3.11.3 Benefit
- Human developers do not need permanent IAM-user access keys.

##### 2.1.3.11.4 Current AWS Guidance
- Preferred for workforce access across AWS accounts.

#### 2.1.3.12 IAM Roles for AWS Workloads

##### 2.1.3.12.1 Principle
- Workloads running on AWS should normally use IAM roles rather than embedded access keys.

##### 2.1.3.12.2 Result
- AWS infrastructure provides temporary credentials to the workload.

##### 2.1.3.12.3 Benefit
- No secret distribution.
- Automatic credential rotation/refresh.
- Permissions follow the role.

#### 2.1.3.13 EC2 Instance Roles

##### 2.1.3.13.1 Instance Profile
- IAM role is associated with an EC2 instance through an instance profile.

##### 2.1.3.13.2 Credential Delivery
- Code running on the EC2 instance can obtain temporary role credentials through the EC2 Instance Metadata Service.

##### 2.1.3.13.3 SDK Behavior
- SDK credential provider chain can discover these credentials automatically.

##### 2.1.3.13.4 Exam Rule
- EC2 application needs AWS API access:
  - attach IAM role.
- Do not place static IAM-user credentials on the instance.

#### 2.1.3.14 Lambda Execution Roles

##### 2.1.3.14.1 Purpose
- Lambda assumes an execution role when the function runs.

##### 2.1.3.14.2 Programmatic Access
- AWS SDK calls inside Lambda automatically use temporary credentials associated with the execution role.

##### 2.1.3.14.3 Developer Requirement
- Configure the role with required permissions.
- Do not supply access keys manually.

##### 2.1.3.14.4 Connection
- Detailed Lambda integration was covered in Domain 1.
- Here the important point is credential acquisition.

#### 2.1.3.15 ECS Task Roles

##### 2.1.3.15.1 Purpose
- ECS tasks can receive temporary AWS credentials through a task role.

##### 2.1.3.15.2 SDK
- Container credential provider retrieves the role credentials.

##### 2.1.3.15.3 Benefit
- Permissions belong to the task/application rather than the underlying host.

#### 2.1.3.16 EKS / Container Workload Identity

##### 2.1.3.16.1 Principle
- Kubernetes workloads should receive AWS identity through supported workload-role mechanisms instead of static credentials.

##### 2.1.3.16.2 SDK Provider
- Depending on architecture, credentials can come through:
  - web identity/OIDC,
  - container credential provider.

##### 2.1.3.16.3 Exam Depth
- Understand workload-role federation conceptually.
- Do not expand into cluster-administration detail unless another skill requires it.

#### 2.1.3.17 External Workloads

##### 2.1.3.17.1 Problem
- Application runs outside AWS but needs AWS API access.

##### 2.1.3.17.2 Preferred Patterns
- OIDC federation.
- IAM Roles Anywhere for appropriate X.509-based workload identity scenarios.
- Other supported federation mechanisms.

##### 2.1.3.17.3 Avoid
- Permanent access key copied to:
  - GitHub Actions,
  - external CI,
  - on-prem server,
  - developer script
  when federation is possible.

#### 2.1.3.18 OIDC Workload Federation

##### 2.1.3.18.1 Flow

  `external workload`
  → obtain OIDC token
  → STS `AssumeRoleWithWebIdentity`
  → temporary AWS credentials
  → AWS SDK/API

##### 2.1.3.18.2 Benefit
- No AWS secret needs to be stored in the external platform.

##### 2.1.3.18.3 Connection
- Federation was introduced in 2.1.1.
- Here the focus is resulting programmatic AWS credentials.

#### 2.1.3.19 Assume-Role Profiles

##### 2.1.3.19.1 Pattern
- CLI/SDK starts with one credential source.
- Then assumes another IAM role.

##### 2.1.3.19.2 Result
- Temporary credentials for the target role.

##### 2.1.3.19.3 Use Case
- Cross-account access.
- Privilege separation.
- Different roles for:
  - development,
  - deployment,
  - production read-only.

##### 2.1.3.19.4 Connection
- Role assumption behavior is expanded in Skill 2.1.5.

#### 2.1.3.20 Credential Refresh

##### 2.1.3.20.1 Temporary Credentials Expire
- Applications must not assume temporary credentials remain valid forever.

##### 2.1.3.20.2 SDK Providers
- Standard credential providers can refresh expiring credentials automatically.

##### 2.1.3.20.3 Developer Rule
- Prefer provider-based credential acquisition over manually caching/storing temporary credentials.

#### 2.1.3.21 Credentials in Application Code

##### 2.1.3.21.1 Bad Pattern

  `new Client(accessKey, secretKey)`

  with hard-coded static values.

##### 2.1.3.21.2 Better Pattern

  `new Client()`

  → SDK credential provider chain resolves credentials from environment/runtime.

##### 2.1.3.21.3 Benefit
- Same code can move between environments without changing credential logic.

#### 2.1.3.22 Region and Credentials Are Different

##### 2.1.3.22.1 Credentials
- Establish caller identity.

##### 2.1.3.22.2 Region
- Selects service endpoint/target Region where relevant.

##### 2.1.3.22.3 Profile
- Can contain both:
  - credential-source configuration,
  - non-secret configuration such as Region.

##### 2.1.3.22.4 Exam Trap
- Correct credentials do not automatically mean the client is configured for the intended Region.

#### 2.1.3.23 Programmatic Access and IAM Permissions

##### 2.1.3.23.1 Credentials Authenticate
- Credential set establishes the principal/session.

##### 2.1.3.23.2 Policies Authorize
- IAM policies determine:
  - allowed actions,
  - resources,
  - conditions.

##### 2.1.3.23.3 Important Distinction
- Valid credentials do not imply access to every AWS service.

##### 2.1.3.23.4 Connection
- Permission design is Skill 2.1.6.

#### 2.1.3.24 Root Credentials

##### 2.1.3.24.1 AWS Root User
- Has extremely powerful account-wide privileges.

##### 2.1.3.24.2 Programmatic Access
- Do not create/use root-user access keys for normal application/developer programmatic access.

##### 2.1.3.24.3 Principle
- Use roles/federated identities and least-privilege permissions.

#### 2.1.3.25 Access-Key Rotation

##### 2.1.3.25.1 If Long-Term Keys Must Exist
- Rotate them.
- Disable/delete unused keys.
- Monitor their use.

##### 2.1.3.25.2 Better Strategy
- Prefer removing the need for long-term keys through temporary credentials/federation.

##### 2.1.3.25.3 Exam Mindset
- "Rotate static keys" is second best.
- "Avoid static keys through roles/federation" is usually better.

#### 2.1.3.26 Secret Storage

##### 2.1.3.26.1 Do Not Store Access Keys in Code
- Never commit secrets to source repositories.

##### 2.1.3.26.2 Secrets Manager
- AWS documentation mentions Secrets Manager as an option when a long-term secret must be stored securely.

##### 2.1.3.26.3 Important Boundary
- Storing a long-term AWS key in Secrets Manager is safer than hard-coding it.
- But using temporary role credentials is usually better when supported.

##### 2.1.3.26.4 Connection
- Secret-management depth belongs to Task 2.3.

#### 2.1.3.27 Environment Variables

##### 2.1.3.27.1 Supported
- SDKs can read credential environment variables.

##### 2.1.3.27.2 Useful For
- Temporary automation environments.
- CI processes when variables contain short-lived credentials.

##### 2.1.3.27.3 Risk
- Environment variables can leak through:
  - debugging,
  - process inspection,
  - logging,
  - misconfigured CI.

##### 2.1.3.27.4 Principle
- Environment variables are a delivery mechanism, not a reason to use permanent keys.

#### 2.1.3.28 Shared Credential Files

##### 2.1.3.28.1 Use
- Useful for local development tooling.

##### 2.1.3.28.2 Risk
- Contains secrets if using long-term access keys.

##### 2.1.3.28.3 Protection
- Restrict filesystem permissions.
- Do not commit `.aws/credentials`.

##### 2.1.3.28.4 Modern Preference
- Profiles backed by IAM Identity Center/assume-role sessions reduce dependence on stored long-term keys.

#### 2.1.3.29 Multi-Account Access

##### 2.1.3.29.1 Common Pattern
- One developer/workload accesses multiple accounts.

##### 2.1.3.29.2 Mechanisms
- IAM Identity Center permission sets/profiles.
- Assume-role chains.
- Named profiles.

##### 2.1.3.29.3 Principle
- Use separate role sessions/permissions rather than maintaining a permanent access-key pair in every account.

#### 2.1.3.30 Cross-Account Access

##### 2.1.3.30.1 Pattern

  `source identity`
  → `AssumeRole in target account`
  → temporary target-account credentials

##### 2.1.3.30.2 Benefit
- Centralized identity.
- No permanent target-account IAM-user key required.

##### 2.1.3.30.3 Trust
- Target role trust policy must allow the source principal.

##### 2.1.3.30.4 Connection
- Role assumption is Skill 2.1.5.

#### 2.1.3.31 CI/CD Programmatic Access

##### 2.1.3.31.1 Requirement
- Build/deployment systems need AWS API access.

##### 2.1.3.31.2 Preferred Pattern
- Workload identity federation / OIDC.
- Short-lived role credentials.

##### 2.1.3.31.3 Avoid
- Long-lived IAM user keys stored as CI secrets when federated role access is supported.

##### 2.1.3.31.4 Benefit
- Reduces credential-rotation burden and secret-leak impact.

#### 2.1.3.32 CloudShell

##### 2.1.3.32.1 Purpose
- Browser-based shell from AWS Management Console.

##### 2.1.3.32.2 Authentication
- Pre-authenticated through the user's AWS session.

##### 2.1.3.32.3 Benefit
- No local access-key configuration is required for ordinary use.

##### 2.1.3.32.4 Exam Value
- Another example of avoiding unnecessary long-term developer credentials.

#### 2.1.3.33 Programmatic Access Decision Tree

##### 2.1.3.33.1 Human Developer in Organization
- → IAM Identity Center / federated temporary credentials.

##### 2.1.3.33.2 Lambda Function
- → Lambda execution role.

##### 2.1.3.33.3 EC2 Application
- → EC2 IAM role/instance profile.

##### 2.1.3.33.4 ECS Task
- → ECS task role.

##### 2.1.3.33.5 EKS/Container Workload
- → supported workload identity / role federation.

##### 2.1.3.33.6 External CI or Workload
- → OIDC federation / IAM role / supported workload identity.

##### 2.1.3.33.7 Cross-Account Access
- → assume role.

##### 2.1.3.33.8 Legacy Tool With No Temporary-Credential Support
- → long-term IAM-user key only as a last resort, securely stored/rotated.

#### 2.1.3.34 Common Exam Traps

##### 2.1.3.34.1 "Application Needs AWS Access → Create IAM User"
- Wrong default.
- Prefer an IAM role or federated temporary credentials.

##### 2.1.3.34.2 "Store Keys in Source Code"
- Wrong.

##### 2.1.3.34.3 "Temporary Credentials Need Only Access Key + Secret"
- Wrong.
- Session token is also required.

##### 2.1.3.34.4 "SDK Must Be Passed Credentials Explicitly"
- Wrong.
- Use the credential provider chain.

##### 2.1.3.34.5 "Environment Variables Are Automatically Secure"
- False.
- They can still leak.

##### 2.1.3.34.6 "Access Key Gives Permissions"
- Credentials establish identity.
- IAM policy grants permissions.

##### 2.1.3.34.7 "Role Credentials Need Manual Rotation"
- Normally no.
- Temporary role credentials expire and SDK providers can refresh them.

##### 2.1.3.34.8 "Every Account Needs a Separate Permanent Developer Key"
- Wrong.
- Use IAM Identity Center/role assumption.

##### 2.1.3.34.9 "CI/CD Secret Store Makes Long-Term Keys Best Practice"
- Wrong.
- Secure storage helps, but federated short-lived credentials are usually better.

##### 2.1.3.34.10 "Root Access Key Is Convenient for Automation"
- Wrong and dangerous.

#### 2.1.3.37 Task 2.1 Big Picture

##### 2.1.3.37.1 Chain

  `principal`
  → 2.1.1 federated identity
  → 2.1.2 application bearer token
  OR
  → 2.1.3 AWS programmatic credentials

##### 2.1.3.37.2 Key Distinction

#### 2.1.3.39 Exam-Level Knowledge Frame

##### 2.1.3.39.1 Credentials
- Long-term:
  - access key ID + secret access key.
- Temporary:
  - access key ID + secret access key + session token + expiration.

##### 2.1.3.39.2 Preferred Sources
- IAM Identity Center for humans.
- IAM roles for AWS workloads.
- OIDC/federation for external workloads.
- Assume role for cross-account/privilege separation.

##### 2.1.3.39.3 SDK
- Use the credential provider chain.
- Avoid hard-coded credentials.
- Let standardized providers refresh temporary credentials.

##### 2.1.3.39.4 Final Principle
- **Configure identity and credential sources around the execution environment; do not bake AWS secrets into application code.**
