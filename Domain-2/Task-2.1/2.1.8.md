### 2.1.8 Handle cross-service authentication in microservice architectures

#### 2.1.8.1 Exam and Task Context

##### 2.1.8.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.1 is **Implement authentication and/or authorization for applications and AWS services**.
- Skill 2.1.8 is **Handle cross-service authentication in microservice architectures**.
- This is the final skill in Task 2.1.

##### 2.1.8.1.2 Position Inside Task 2.1
- 2.1.1 → establish trusted identity/federation.
- 2.1.2 → secure application/API access with bearer tokens.
- 2.1.3 → configure AWS programmatic credentials.
- 2.1.4 → make authenticated AWS service calls.
- 2.1.5 → assume IAM roles.
- 2.1.6 → define IAM permissions.
- 2.1.7 → implement fine-grained application authorization.
- **2.1.8 → apply those identity and trust concepts when one service or microservice calls another service.**

##### 2.1.8.1.3 Core Question
- **When service A calls service B, how does service B know who/what is calling, and how is that caller granted only the required access?**

#### 2.1.8.2 Core Mental Model

A microservice call needs two separate answers:

`Who is service A?`
→ authentication

`What may service A do to service B?`
→ authorization

A useful model is:

`service A workload identity`
→ `credential/token`
→ `authenticated call`
→ `service B trust boundary`
→ `authorization policy`
→ `ALLOW / DENY`

The caller might authenticate using:
- AWS IAM role credentials + SigV4,
- bearer token/JWT,
- service principal/resource policy,
- an AWS-managed service integration.

#### 2.1.8.3 Service Identity vs User Identity

##### 2.1.8.3.1 User Identity
- Represents the end user.
- Often carried in:
  - Cognito/OIDC JWT,
  - access token,
  - application session.

##### 2.1.8.3.2 Service Identity
- Represents the workload/service making the network/API call.
- Often represented by:
  - Lambda execution role,
  - ECS task role,
  - EC2 role,
  - EKS workload identity,
  - assumed IAM role,
  - AWS service principal.

##### 2.1.8.3.3 Critical Distinction
- A service may act:
  - **on its own behalf**, or
  - **on behalf of an end user**.
- Those are not the same identity problem.

#### 2.1.8.4 Two Common Microservice Authentication Models

##### 2.1.8.4.1 AWS-Native IAM Model

`Microservice A`
→ IAM role credentials
→ SigV4 signed call
→ AWS service/API
→ IAM authorization

Typical targets:
- API Gateway with `AWS_IAM`,
- SQS,
- SNS,
- EventBridge,
- DynamoDB,
- S3,
- Lambda invocation.

##### 2.1.8.4.2 Token-Based Application Model

`Microservice A`
→ OAuth/OIDC access token
→ `Authorization: Bearer`
→ Microservice B/API
→ JWT validation
→ application authorization

Typical when:
- B is an application API,
- domain-level scopes/claims matter,
- the caller is not naturally modeled as an AWS IAM principal.

#### 2.1.8.5 IAM Role Credentials for Workloads

##### 2.1.8.5.1 Principle
- AWS workloads should use workload-associated IAM roles rather than static access keys.

##### 2.1.8.5.2 Examples
- Lambda:
  - execution role.
- ECS:
  - task role.
- EC2:
  - instance role.
- EKS:
  - supported pod/workload identity.

##### 2.1.8.5.3 Benefit
- Temporary credentials.
- Automatic rotation/refresh.
- No long-lived AWS secret embedded in the microservice.

#### 2.1.8.6 Lambda Service Identity

##### 2.1.8.6.1 Execution Role
- Lambda assumes the function's execution role.
- Function receives temporary AWS credentials.

##### 2.1.8.6.2 Outbound AWS Call
- SDK inside Lambda signs calls with the execution-role credentials.

##### 2.1.8.6.3 Example

`Lambda A`
→ execution-role credentials
→ SigV4
→ `SQS SendMessage`

##### 2.1.8.6.4 Authorization
- Execution role needs `sqs:SendMessage` on the target queue.

#### 2.1.8.7 ECS Task Identity

##### 2.1.8.7.1 Task Role
- ECS task role is the application identity of the containers in the task.

##### 2.1.8.7.2 Credential Provider
- AWS SDK container credential provider retrieves temporary task-role credentials.

##### 2.1.8.7.3 Important Distinction
- Task role permissions belong to the application.
- EC2 container-instance role belongs to the ECS infrastructure/host and should not be used as the application's business identity.

#### 2.1.8.8 EC2 Service Identity

##### 2.1.8.8.1 Instance Role
- EC2 workload obtains temporary credentials through instance metadata.

##### 2.1.8.8.2 SDK
- SDK credential provider chain can discover these credentials automatically.

##### 2.1.8.8.3 Microservice Pattern
- Application signs outbound AWS API requests using the instance-role identity.

#### 2.1.8.9 EKS Workload Identity

##### 2.1.8.9.1 Principle
- Individual Kubernetes workloads should receive an IAM identity appropriate to the pod/service account instead of relying on static keys.

##### 2.1.8.9.2 Current AWS Mechanisms
- EKS Pod Identity.
- OIDC/web-identity based mechanisms such as IRSA where applicable.

##### 2.1.8.9.3 Benefit
- Fine-grained workload permissions.
- Avoids sharing node credentials among unrelated applications.

##### 2.1.8.9.4 Exam Depth
- Understand workload-to-role mapping.
- Detailed EKS security administration is beyond this skill.

#### 2.1.8.10 Service A Calling AWS Service B

##### 2.1.8.10.1 Pattern

`workload role`
→ AWS SDK
→ SigV4
→ AWS service endpoint
→ IAM policy evaluation

##### 2.1.8.10.2 Example
- Order service:
  - Lambda execution role.
- Calls:
  - `sqs:SendMessage`.
- Target:
  - payment-processing queue.

##### 2.1.8.10.3 Required Controls
- Caller identity policy must allow the action.
- Target resource policy must also allow it where the service/resource policy model requires or adds restrictions.

#### 2.1.8.11 API Gateway as a Service Boundary

##### 2.1.8.11.1 AWS IAM Authorization
- API Gateway routes/methods can require `AWS_IAM`.

##### 2.1.8.11.2 Caller
- AWS workload signs HTTP request using SigV4.

##### 2.1.8.11.3 Permission
- Caller needs appropriate:
  - `execute-api:Invoke`.

##### 2.1.8.11.4 Flow

`Service A`
→ IAM role credentials
→ SigV4
→ API Gateway
→ IAM authorization
→ Service B backend

##### 2.1.8.11.5 Fit
- Strong AWS-native service-to-service authentication pattern.

#### 2.1.8.12 API Gateway JWT Boundary

##### 2.1.8.12.1 Alternative
- Service A presents an OAuth/OIDC bearer token.

##### 2.1.8.12.2 API Gateway
- JWT/Cognito authorizer validates:
  - issuer,
  - signature,
  - audience,
  - expiration,
  - scopes.

##### 2.1.8.12.3 Fit
- Useful when service authorization is expressed through application scopes/claims rather than IAM identities.

##### 2.1.8.12.4 Connection
- Bearer-token mechanics → 2.1.2.
- Application authorization → 2.1.7.

#### 2.1.8.13 IAM vs JWT for Service-to-Service Calls

##### 2.1.8.13.1 IAM/SigV4
Best when:
- both sides are AWS-integrated,
- caller already has IAM role identity,
- target supports IAM authentication,
- AWS-resource permissions are the main authorization model.

##### 2.1.8.13.2 JWT/OAuth
Best when:
- target is an application API,
- scopes/claims are central,
- caller might not be an AWS principal,
- identity needs to cross platform/cloud boundaries.

##### 2.1.8.13.3 Rule
- Do not choose JWT merely because the architecture is "microservices."
- Use the authentication mechanism that matches the trust boundary and target service.

#### 2.1.8.14 AWS Service Principals

##### 2.1.8.14.1 Definition
- AWS services can act as principals.

Examples:
- `lambda.amazonaws.com`
- `events.amazonaws.com`
- `states.amazonaws.com`
- `sns.amazonaws.com`

##### 2.1.8.14.2 Use
- Service principal appears in:
  - role trust policies,
  - resource-based policies.

##### 2.1.8.14.3 Meaning
- The AWS service itself is trusted to perform a defined action.

#### 2.1.8.15 Service Role

##### 2.1.8.15.1 Definition
- IAM role assumed by an AWS service to perform actions on your behalf.

##### 2.1.8.15.2 Trust Policy
- Trusts the service principal.

##### 2.1.8.15.3 Permissions Policy
- Grants only actions/resources required by the integration.

##### 2.1.8.15.4 Example
- Step Functions state machine assumes an execution role to call Lambda, SQS, DynamoDB, or other integrated AWS services.

#### 2.1.8.16 Step Functions Cross-Service Authentication

##### 2.1.8.16.1 Execution Role
- Step Functions uses an IAM role to access AWS services on behalf of the state machine.

##### 2.1.8.16.2 Flow

`Step Functions state machine`
→ assumes execution role
→ calls target AWS service
→ IAM authorization

##### 2.1.8.16.3 Least Privilege
- Execution role should include only service actions/resources required by state definitions.

#### 2.1.8.17 EventBridge Targets

##### 2.1.8.17.1 Event Delivery
- EventBridge sends matched events to target services.

##### 2.1.8.17.2 Authorization
- Depending on target type, authorization can involve:
  - resource-based policy on target,
  - IAM role used by EventBridge,
  - service-specific integration permissions.

##### 2.1.8.17.3 Principle
- Do not assume every AWS integration authenticates identically.
- Check the target service's documented permission model.

#### 2.1.8.18 SNS to SQS

##### 2.1.8.18.1 Pattern

`SNS topic`
→ publishes
→ `SQS queue`

##### 2.1.8.18.2 Queue Policy
- SQS queue resource policy allows SNS service principal to call:
  - `sqs:SendMessage`.

##### 2.1.8.18.3 Restriction
- Policy should restrict the allowed source topic with:
  - `aws:SourceArn`.

##### 2.1.8.18.4 Why
- Trusting only `sns.amazonaws.com` broadly can allow unintended SNS resources to send messages.

#### 2.1.8.19 AWS Service Invoking Lambda

##### 2.1.8.19.1 Resource-Based Policy
- Lambda function resource policy can permit another AWS service to invoke the function.

##### 2.1.8.19.2 Principal
- AWS service principal.

##### 2.1.8.19.3 Action
- Typically:
  - `lambda:InvokeFunction`.

##### 2.1.8.19.4 Source Restriction
- Use:
  - `aws:SourceArn`
  - and/or `aws:SourceAccount`
  where supported/appropriate.

#### 2.1.8.20 Identity Policy vs Resource Policy in Cross-Service Calls

##### 2.1.8.20.1 Identity-Based Policy
- Attached to caller role.
- Says:
  - caller may invoke/send/write to target.

##### 2.1.8.20.2 Resource-Based Policy
- Attached to target resource.
- Says:
  - this principal/service may access me.

##### 2.1.8.20.3 Microservice Mental Model
- Cross-service access can require one or both policy directions depending on the service integration.

##### 2.1.8.20.4 Connection
- Policy types and evaluation → 2.1.6.

#### 2.1.8.21 Cross-Service Confused Deputy Problem

##### 2.1.8.21.1 Definition
- A less-privileged actor causes a more-privileged service to access a resource in an unintended way.

##### 2.1.8.21.2 AWS Context
- Calling AWS service uses its service principal to access another service/resource.

##### 2.1.8.21.3 Risk
- Target resource policy trusts the service principal too broadly.

Example:
- resource trusts `service.amazonaws.com`
- but does not restrict **which source resource/account** the service is acting for.

#### 2.1.8.22 `aws:SourceArn`

##### 2.1.8.22.1 Purpose
- Restrict cross-service access to calls made on behalf of a specific AWS resource.

##### 2.1.8.22.2 Example
- SQS queue accepts SNS messages only from:
  - one SNS topic ARN.

##### 2.1.8.22.3 AWS Guidance
- AWS recommends using `aws:SourceArn` when granting access to AWS service principals where supported.

#### 2.1.8.23 `aws:SourceAccount`

##### 2.1.8.23.1 Purpose
- Restrict cross-service request to a specific AWS account.

##### 2.1.8.23.2 Use
- Useful when:
  - full source ARN is not suitable,
  - policy should permit multiple source resources from one account.

##### 2.1.8.23.3 Combined Use
- Some service patterns use both:
  - `aws:SourceArn`
  - `aws:SourceAccount`.

#### 2.1.8.24 `aws:SourceOrgID` and `aws:SourceOrgPaths`

##### 2.1.8.24.1 Current AWS Guidance
- AWS also supports organization-level context keys for service-principal calls where applicable.

##### 2.1.8.24.2 Use
- Restrict access to resources originating from:
  - a specific AWS Organization,
  - a specific organization path.

##### 2.1.8.24.3 Exam Depth
- Recognize these as broader organization-level confused-deputy controls.
- Core exam focus remains `SourceArn` / `SourceAccount`.

#### 2.1.8.25 External ID vs SourceArn

##### 2.1.8.25.1 External ID
- Used primarily for third-party cross-account `AssumeRole`.
- Prevents confused deputy involving a third-party role-assuming service/provider.

##### 2.1.8.25.2 SourceArn / SourceAccount
- Used primarily in AWS **cross-service** resource/trust policies.

##### 2.1.8.25.3 Exam Distinction
- Third-party vendor assumes your role:
  - think `ExternalId`.
- AWS service principal accesses your resource:
  - think `SourceArn` / `SourceAccount`.

#### 2.1.8.26 Downstream User Identity Propagation

##### 2.1.8.26.1 Scenario
- User calls Service A.
- Service A calls Service B.
- Service B needs to know the original user.

##### 2.1.8.26.2 Option
- Propagate a verified user token/identity context downstream.

##### 2.1.8.26.3 Risk
- Blindly forwarding arbitrary client headers is unsafe.

##### 2.1.8.26.4 Principle
- Downstream service should rely only on:
  - a token it can validate,
  - trusted identity context from a trusted gateway/service,
  - or a new service-issued token representing delegated user context.

#### 2.1.8.27 Service Identity + User Context

##### 2.1.8.27.1 Two-Layer Model

`Service A → Service B`
authentication:
→ Service A's workload identity

authorization context:
→ original user's trusted claims

##### 2.1.8.27.2 Why
- Service B may need to know:
  - **which service is calling**
  - and **which user operation is being performed**.

##### 2.1.8.27.3 Security
- Do not collapse user identity and service identity into one unverified header.

#### 2.1.8.28 Token Forwarding

##### 2.1.8.28.1 Direct Forwarding
- Service A forwards the same end-user access token to Service B.

##### 2.1.8.28.2 Valid Only If
- Token audience/scope is intended for Service B or shared resource server.

##### 2.1.8.28.3 Risk
- A token issued for API A should not automatically be accepted by API B.

##### 2.1.8.28.4 Rule
- Validate:
  - issuer,
  - audience,
  - scope,
  - expiration
  at each trust boundary.

#### 2.1.8.29 Machine-to-Machine OAuth

##### 2.1.8.29.1 Client Credentials Flow
- OAuth 2.0 client credentials can issue access tokens to non-human clients.

##### 2.1.8.29.2 Cognito
- Cognito supports machine-to-machine authorization using client credentials and scopes.

##### 2.1.8.29.3 Flow

`Service A client identity`
→ authorization server
→ access token
→ Service B
→ validate scope
→ allow/deny

##### 2.1.8.29.4 Fit
- Useful for application-level API authorization where IAM is not the chosen trust model.

#### 2.1.8.30 Shared Secrets Between Services

##### 2.1.8.30.1 Weak Default Pattern
- Both services share one static API key/secret.

##### 2.1.8.30.2 Problems
- Long-lived.
- Harder to rotate.
- Poor caller attribution if shared.
- Secret distribution burden.

##### 2.1.8.30.3 Better AWS-Native Alternatives
- IAM roles + SigV4.
- OAuth short-lived access tokens.
- workload federation.

##### 2.1.8.30.4 Scope
- Secrets management itself belongs to Task 2.3.

#### 2.1.8.31 Network Reachability Is Not Authentication

##### 2.1.8.31.1 VPC
- Private networking controls reachability.

##### 2.1.8.31.2 Security Group
- Controls network traffic.

##### 2.1.8.31.3 Authentication
- Proves caller identity.

##### 2.1.8.31.4 Important Rule
- "Only reachable inside VPC" does **not** eliminate the need for application/service authentication where the threat model requires it.

#### 2.1.8.32 TLS vs Authentication

##### 2.1.8.32.1 TLS
- Encrypts transport and authenticates server endpoint via certificates.

##### 2.1.8.32.2 IAM/JWT
- Authenticates caller/application identity.

##### 2.1.8.32.3 Principle
- Encryption in transit and caller authentication are distinct controls.
- Encryption depth belongs to Task 2.2.

#### 2.1.8.33 mTLS Context

##### 2.1.8.33.1 Concept
- Mutual TLS authenticates both client and server using certificates.

##### 2.1.8.33.2 AWS Context
- Some AWS/API architectures can use mTLS for client authentication.

##### 2.1.8.33.3 Exam Scope Caution
- Skill wording is broad enough that mTLS is conceptually relevant, but current DVA-C02 in-scope services emphasize IAM, Cognito, API Gateway, and AWS-native service integrations.
- Do not make mTLS a primary exam target unless a scenario explicitly points to certificate-based mutual authentication.

#### 2.1.8.34 Async Microservice Authentication

##### 2.1.8.34.1 Important Shift
- In asynchronous architecture, Service A may not directly call Service B.

Pattern:

`Service A`
→ `SQS / SNS / EventBridge`
→ `Service B`

##### 2.1.8.34.2 Authentication Boundaries
1. Service A authenticates to the messaging service.
2. Messaging service is authorized to deliver to target where necessary.
3. Service B authenticates to read/process messages through its workload role.

##### 2.1.8.34.3 Benefit
- Services do not need direct mutual runtime credentials for every communication path.

#### 2.1.8.35 SQS Consumer Identity

##### 2.1.8.35.1 Pull Consumer
- Consumer service polls SQS using its workload IAM role.

##### 2.1.8.35.2 Permissions
- Typical:
  - `sqs:ReceiveMessage`
  - `sqs:DeleteMessage`
  - `sqs:GetQueueAttributes`
  as required.

##### 2.1.8.35.3 Producer
- Producer separately needs:
  - `sqs:SendMessage`.

##### 2.1.8.35.4 Principle
- Producer and consumer identities should receive separate least-privilege permissions.

#### 2.1.8.36 EventBridge Publisher Identity

##### 2.1.8.36.1 Application Event
- Application calls EventBridge API using its IAM role.

##### 2.1.8.36.2 Authentication
- SDK signs `PutEvents`.

##### 2.1.8.36.3 Authorization
- IAM policy must allow event-bus access.

##### 2.1.8.36.4 Delivery
- EventBridge then handles authenticated delivery to targets through target-specific permission model.

#### 2.1.8.37 Lambda Event Source Mappings

##### 2.1.8.37.1 Pull-Based Integrations
- Lambda service can poll sources such as SQS on behalf of a function.

##### 2.1.8.37.2 Execution Role
- Function execution role requires appropriate permissions for the source.

##### 2.1.8.37.3 Important
- Application code itself is not manually authenticating to SQS for each event when Lambda service manages the event source mapping.

#### 2.1.8.38 Direct Lambda Invocation

##### 2.1.8.38.1 Service A Calls Lambda B
- Caller uses AWS credentials.
- SDK signs `Invoke`.

##### 2.1.8.38.2 IAM
- Caller needs:
  - `lambda:InvokeFunction`.

##### 2.1.8.38.3 Resource Policy
- Cross-account or service-principal scenarios can require Lambda resource-based permissions.

#### 2.1.8.39 Cross-Account Microservices

##### 2.1.8.39.1 Pattern
- Microservice A in Account A calls resources in Account B.

##### 2.1.8.39.2 Options
- Assume role in Account B.
- Resource-based policy directly trusts caller where supported.

##### 2.1.8.39.3 Role Pattern

`Service A role`
→ `sts:AssumeRole`
→ target-account role
→ target resource

##### 2.1.8.39.4 Connection
- Role assumption → 2.1.5.
- Cross-account permissions → 2.1.6.

#### 2.1.8.40 Least Privilege Between Services

##### 2.1.8.40.1 Avoid Shared Broad Role
- Multiple microservices should not all use one powerful IAM role simply for convenience.

##### 2.1.8.40.2 Prefer
- Role per workload/function where practical.
- Permissions per service responsibility.

##### 2.1.8.40.3 Example
- Order service:
  - send to payment queue.
- Payment service:
  - consume payment queue.
- Reporting service:
  - read reporting data.

##### 2.1.8.40.4 Benefit
- Smaller blast radius and better attribution.

#### 2.1.8.41 Service-to-Service Authorization Matrix

A useful design artifact:

| Caller | Target | Authentication | Required Authorization |
| --- | --- | --- | --- |
| Lambda A | SQS | IAM role + SigV4 | `sqs:SendMessage` |
| ECS service | API Gateway | IAM + SigV4 | `execute-api:Invoke` |
| SNS | SQS | AWS service principal | Queue resource policy + `SourceArn` |
| EventBridge | Lambda | AWS service principal/integration | Lambda resource permission |
| Step Functions | DynamoDB | execution role | DynamoDB action on table |
| Service A | Service B HTTP API | JWT/OAuth | required scope/claim |

The point is not to memorize this table verbatim.
The point is to identify:
- caller identity,
- credential type,
- trust policy/resource policy,
- target permission.

#### 2.1.8.42 Credential Rotation

##### 2.1.8.42.1 IAM Workload Roles
- Temporary credentials rotate automatically through runtime/provider mechanisms.

##### 2.1.8.42.2 OAuth Tokens
- Short-lived access tokens expire.
- Service obtains new tokens as needed.

##### 2.1.8.42.3 Shared Static Secrets
- Require explicit rotation and distribution.

##### 2.1.8.42.4 Principle
- Prefer renewable short-lived credentials over shared permanent credentials.

#### 2.1.8.43 Identity Propagation and Logging

##### 2.1.8.43.1 Service Identity
- Log:
  - caller role/session,
  - service principal where relevant.

##### 2.1.8.43.2 User Context
- Where a downstream call represents a user operation, carry safe traceable user identifier.

##### 2.1.8.43.3 Correlation
- Use:
  - request ID,
  - trace ID,
  - session/source identity
  where appropriate.

##### 2.1.8.43.4 Avoid
- Logging:
  - complete bearer tokens,
  - AWS secret keys,
  - session tokens.

#### 2.1.8.44 CloudTrail Context

##### 2.1.8.44.1 AWS API Audit
- CloudTrail records many authenticated AWS API actions.

##### 2.1.8.44.2 Useful Identity Data
- Principal.
- Assumed role session.
- source identity/session information where applicable.

##### 2.1.8.44.3 Benefit
- Helps determine which workload or role performed an AWS action.

#### 2.1.8.45 Authentication Failure Patterns

##### 2.1.8.45.1 IAM/SigV4
- Missing credentials.
- Expired credentials.
- Missing session token.
- invalid signature.
- wrong Region/service.
- role not available.

##### 2.1.8.45.2 JWT/OAuth
- Invalid issuer.
- invalid signature.
- wrong audience.
- expired token.
- missing required scope.

##### 2.1.8.45.3 Service Principal
- Resource policy does not trust service.
- `SourceArn`/`SourceAccount` condition does not match.

#### 2.1.8.46 Authorization Failure Patterns

##### 2.1.8.46.1 Caller Authenticated but Denied
- Missing IAM action.
- Wrong resource ARN.
- resource-based policy denies or lacks trust.
- SCP/boundary/session policy limits access.
- OAuth token lacks scope.
- application policy denies action.

##### 2.1.8.46.2 Debugging
- Separate:
  - **authentication failed**
  from
  - **authentication succeeded but authorization failed**.

#### 2.1.8.47 Trust Boundary Decision Tree

##### 2.1.8.47.1 AWS Workload → AWS Service
- Use workload IAM role + SDK/SigV4.

##### 2.1.8.47.2 AWS Workload → IAM-Protected API Gateway
- Use IAM credentials + SigV4 + `execute-api:Invoke`.

##### 2.1.8.47.3 Service → Application API with OAuth Semantics
- Use short-lived access token with appropriate audience/scopes.

##### 2.1.8.47.4 AWS Service → AWS Resource
- Use service principal plus role/resource policy according to integration.
- Restrict with `SourceArn`/`SourceAccount` where appropriate.

##### 2.1.8.47.5 Cross-Account Workload
- Assume target role or use supported resource-based delegation.

##### 2.1.8.47.6 Async Communication
- Authenticate independently to queue/topic/event bus rather than inventing direct service credentials.

#### 2.1.8.48 Common Exam Traps

##### 2.1.8.48.1 "Private VPC Means Authenticated"
- False.
- Network isolation and identity authentication are different controls.

##### 2.1.8.48.2 "All Microservices Should Share One IAM Role"
- Poor design.
- Violates least privilege and weakens attribution.

##### 2.1.8.48.3 "Put AWS Access Keys in Service Configuration"
- Wrong.
- Prefer workload roles/temporary credentials.

##### 2.1.8.48.4 "Service Principal Alone Is Always Safe"
- False.
- Restrict source with `SourceArn`/`SourceAccount` when relevant to prevent confused deputy.

##### 2.1.8.48.5 "JWT Issued for Service A Is Automatically Valid for Service B"
- False.
- Audience/scope must match target trust boundary.

##### 2.1.8.48.6 "IAM Role Proves End-User Authorization"
- False.
- It proves workload identity and AWS permissions.
- User/domain authorization may still be required.

##### 2.1.8.48.7 "SQS Message Contains Authentication"
- Not inherently.
- Producer authenticates to SQS; consumer authenticates to SQS.
- Message payload identity must be explicitly modeled if needed.

##### 2.1.8.48.8 "EventBridge/SNS/Lambda Integrations Need No IAM"
- False.
- AWS-managed integrations still rely on roles, service principals, and/or resource-based permissions.

##### 2.1.8.48.9 "External ID and SourceArn Are the Same"
- False.
- External ID → third-party AssumeRole confused-deputy mitigation.
- SourceArn/SourceAccount → AWS cross-service confused-deputy protection.

##### 2.1.8.48.10 "TLS Replaces Authentication"
- False.
- TLS protects transport; caller identity still needs an authentication model.

#### 2.1.8.49 Task 2.1 Full Integration

#### 2.1.8.51 Exam-Level Knowledge Frame

Know these patterns:

**AWS workload → AWS service**
→ IAM role + temporary credentials + SigV4.

**AWS workload → API Gateway**
→ `AWS_IAM` + SigV4, or JWT if application-token model fits.

**AWS service → AWS resource**
→ service principal + resource policy/service role.

**SNS → SQS**
→ queue policy + SNS service principal + `SourceArn`.

**AWS service invokes Lambda**
→ Lambda resource policy + service principal + source restriction.

**Step Functions → AWS services**
→ state-machine execution role.

**External/application microservice**
→ OAuth/OIDC bearer token when IAM is not the trust model.

**Cross-account**
→ role assumption or supported resource policy.

**Confused deputy**
→ `SourceArn` / `SourceAccount` for cross-service; `ExternalId` for third-party role assumption.

Final principle:

**Each microservice should have its own trusted workload identity, use short-lived credentials or tokens, authenticate every relevant trust boundary, and receive only the permissions needed for its service responsibility.**
