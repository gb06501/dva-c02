### 2.1.2 Secure applications by using bearer tokens

#### 2.1.2.1 Exam and Task Context

##### 2.1.2.1.1 Domain
- Domain 2 is **Security**.
- Task 2.1 is **Implement authentication and/or authorization for applications and AWS services**.
- Skill 2.1.2 is **Secure applications by using bearer tokens**.
- The exam guide's Task 2.1 knowledge explicitly associates bearer tokens with:
  - JSON Web Token (JWT),
  - OAuth,
  - AWS Security Token Service (AWS STS).

##### 2.1.2.1.2 Position Inside Task 2.1
- 2.1.1 established:
  - principal,
  - identity provider,
  - federation,
  - trust.
- 2.1.2 now asks:

  **After identity has been established, how can a client carry proof of authentication/authorization to an application securely?**

- Later skills continue toward:
  - AWS programmatic credentials,
  - authenticated AWS API calls,
  - IAM role assumption,
  - IAM permissions,
  - fine-grained authorization,
  - service-to-service authentication.

#### 2.1.2.2 Core Mental Model

##### 2.1.2.2.1 Bearer Token
- A bearer token is a credential presented by a client to a protected resource.
- The essential property is:

  **whoever possesses a valid bearer token can present it.**

##### 2.1.2.2.2 Flow

  `principal`
  → authenticates/authorizes
  → `authorization server / IdP`
  → receives `bearer token`
  → sends token with request
  → `resource server / API`
  → validates token
  → authorizes request

##### 2.1.2.2.3 Security Consequence
- Possession matters.
- A stolen valid bearer token can potentially be replayed until it expires or is otherwise rejected.
- Therefore protect bearer tokens:
  - in transit,
  - at rest/client storage,
  - from logs,
  - from accidental exposure.

#### 2.1.2.3 Authentication, Token Issuance, Authorization

##### 2.1.2.3.1 Authentication
- Establishes who the principal is.

##### 2.1.2.3.2 Token Issuance
- Trusted authorization server/IdP issues token after the appropriate authentication/authorization flow.

##### 2.1.2.3.3 Resource Authorization
- API validates token and evaluates:
  - issuer,
  - signature,
  - expiration,
  - audience,
  - scopes/claims,
  depending on the authorizer and token type.

##### 2.1.2.3.4 Separation
- The API normally does not ask for the user's password on every request.
- It receives a token representing a previously established session/authorization.

#### 2.1.2.4 OAuth 2.0 Context

##### 2.1.2.4.1 Purpose
- OAuth 2.0 is an authorization framework.
- It allows clients to obtain access tokens for protected resources.

##### 2.1.2.4.2 Important Roles
- Resource owner.
- Client.
- Authorization server.
- Resource server.

##### 2.1.2.4.3 AWS Mapping Example
- Cognito user pool:
  - authorization server/token issuer.
- Browser/mobile application:
  - client.
- API Gateway/API:
  - protected resource/resource server boundary.
- Cognito access token:
  - bearer token.

##### 2.1.2.4.4 Scope Boundary
- Do not memorize every OAuth flow here.
- Understand why an access token exists and how the protected API uses it.

#### 2.1.2.5 OpenID Connect Context

##### 2.1.2.5.1 OIDC
- OpenID Connect adds an identity layer to OAuth 2.0.

##### 2.1.2.5.2 Result
- OIDC introduces the ID token for authenticated identity information.

##### 2.1.2.5.3 Cognito
- Cognito user pools act as OIDC identity providers and issue JWTs.

#### 2.1.2.6 JSON Web Token — JWT

##### 2.1.2.6.1 Purpose
- Compact token format used to carry verifiable claims.

##### 2.1.2.6.2 Structure

  `header.payload.signature`

##### 2.1.2.6.3 Header
- Metadata about token/signing algorithm.
- Commonly includes key identifier (`kid`).

##### 2.1.2.6.4 Payload
- Contains claims.

##### 2.1.2.6.5 Signature
- Allows receiver to verify token integrity and authenticity against the trusted issuer's signing key.

#### 2.1.2.7 JWT Is Encoded, Not Secret

##### 2.1.2.7.1 Base64url
- JWT header and payload are encoded.
- They are not automatically encrypted.

##### 2.1.2.7.2 Consequence
- Anyone possessing a normal signed JWT can decode/read its claims.

##### 2.1.2.7.3 Rule
- Do not place secrets in JWT claims merely because the token looks unreadable.

##### 2.1.2.7.4 Signature Purpose
- Signature proves integrity/authenticity.
- It does not hide the payload.

#### 2.1.2.8 JWT Claims

##### 2.1.2.8.1 Issuer — `iss`
- Identifies the token issuer.
- Receiver must trust the expected issuer.

##### 2.1.2.8.2 Audience — `aud`
- Identifies intended audience where applicable.
- Helps prevent accepting a token intended for another client/resource.

##### 2.1.2.8.3 Expiration — `exp`
- Time after which token must not be accepted.

##### 2.1.2.8.4 Issued At — `iat`
- Time token was issued.

##### 2.1.2.8.5 Subject — `sub`
- Stable identifier for the principal within the issuer.

##### 2.1.2.8.6 Scope — `scope`
- Access token authorization scope.

##### 2.1.2.8.7 Cognito-Specific Claims
- Examples:
  - `token_use`,
  - `cognito:groups`,
  - `client_id`,
  depending on token type.

#### 2.1.2.9 Cognito Token Types

##### 2.1.2.9.1 Authentication Result
- A successful Cognito user-pool session can return:
  - ID token,
  - access token,
  - refresh token.

##### 2.1.2.9.2 Mental Model

  `ID token`
  → **who the user is**

  `access token`
  → **what protected APIs/resources the session may access**

  `refresh token`
  → **obtain new ID/access tokens without full sign-in again**

#### 2.1.2.10 ID Token

##### 2.1.2.10.1 Purpose
- Verifiable statement about authenticated identity.

##### 2.1.2.10.2 Typical Claims
- username,
- name,
- email,
- other user attributes.

##### 2.1.2.10.3 Application Use
- Build user session/profile.
- Identify authenticated user.

##### 2.1.2.10.4 Do Not Confuse
- Identity information is not the same as API authorization scope.

#### 2.1.2.11 Access Token

##### 2.1.2.11.1 Purpose
- Verifiable statement of access rights.

##### 2.1.2.11.2 Cognito Contents
- Can contain:
  - scopes,
  - user groups,
  - username,
  - token purpose,
  - expiration and issuer information.

##### 2.1.2.11.3 Primary API Use
- Present to protected APIs to authorize operations.

##### 2.1.2.11.4 Cognito Marker
- `token_use = access`.

#### 2.1.2.12 Refresh Token

##### 2.1.2.12.1 Purpose
- Maintain a signed-in session by obtaining new ID/access tokens.

##### 2.1.2.12.2 Difference
- It is not normally the token presented to business APIs for ordinary authorization.

##### 2.1.2.12.3 Security
- Refresh tokens are valuable long-lived session artifacts and require strong protection.

##### 2.1.2.12.4 Cognito
- Cognito refresh tokens are opaque rather than readable JWTs.

#### 2.1.2.13 ID Token vs Access Token

##### 2.1.2.13.1 ID Token
- Identity-focused.
- Answers roughly:
  - **who authenticated?**

##### 2.1.2.13.2 Access Token
- Authorization-focused.
- Answers roughly:
  - **what access was granted?**

##### 2.1.2.13.3 Exam Preference
- When an API requires authorization scopes, use the **access token**.
- AWS API Gateway documentation recommends configuring routes around access-token authorization scopes unless ID tokens are specifically required.

#### 2.1.2.14 Bearer Token in HTTP

##### 2.1.2.14.1 Typical Request

  `Authorization: Bearer <token>`

##### 2.1.2.14.2 API Gateway
- JWT authorizer identity source is commonly:
  - `$request.header.Authorization`.

##### 2.1.2.14.3 Security
- Send tokens over HTTPS/TLS.
- Avoid token exposure in:
  - URLs,
  - logs,
  - error messages.

#### 2.1.2.15 Token Validation

##### 2.1.2.15.1 Never Trust Token Merely Because It Parses
- Decoding JSON does not prove authenticity.

##### 2.1.2.15.2 Validation Model

  `receive token`
  → identify expected issuer
  → obtain trusted public key
  → verify signature
  → validate claims
  → evaluate authorization requirements
  → allow/deny

##### 2.1.2.15.3 Core Checks
- Signature.
- Issuer.
- Expiration.
- Audience/client where applicable.
- Token purpose.
- Required scopes/claims.

#### 2.1.2.16 Signature Verification

##### 2.1.2.16.1 Issuer Signing
- Cognito signs ID and access tokens.

##### 2.1.2.16.2 Public Keys
- Public signing keys are advertised through the user pool's JWKS endpoint.

##### 2.1.2.16.3 `kid`
- Token header identifies which signing key was used.

##### 2.1.2.16.4 Validation
- Authorizer/library selects the corresponding trusted public key and verifies the signature.

#### 2.1.2.17 JWKS

##### 2.1.2.17.1 Meaning
- JSON Web Key Set.

##### 2.1.2.17.2 Purpose
- Publishes public keys that verifiers can use to validate JWT signatures.

##### 2.1.2.17.3 Key Rotation
- Signing keys can rotate.
- Applications should not hard-code one signing key indefinitely.

##### 2.1.2.17.4 API Gateway
- API Gateway retrieves issuer public keys and can cache them.
- AWS recommends allowing overlap/grace during key rotation.

#### 2.1.2.18 Expiration

##### 2.1.2.18.1 `exp`
- Token becomes invalid after expiration.

##### 2.1.2.18.2 Security Trade-Off
- Shorter token lifetime:
  - limits stolen-token usefulness,
  - increases refresh frequency.
- Longer lifetime:
  - fewer refreshes,
  - longer exposure if stolen.

##### 2.1.2.18.3 Principle
- Token lifetime is part of session-risk design.

#### 2.1.2.19 Audience and Client Validation

##### 2.1.2.19.1 Problem
- A correctly signed token can still be intended for another application.

##### 2.1.2.19.2 Audience
- Validate intended recipient/client where token format and authorizer require it.

##### 2.1.2.19.3 Security Goal
- Prevent token substitution across applications/resources.

#### 2.1.2.20 Token Purpose Validation

##### 2.1.2.20.1 Cognito
- Tokens contain a `token_use` claim.

##### 2.1.2.20.2 Values
- ID token → `id`.
- Access token → `access`.

##### 2.1.2.20.3 Why
- Application should not accidentally accept the wrong token type for an authorization decision.

#### 2.1.2.21 OAuth Scopes

##### 2.1.2.21.1 Purpose
- Represent categories of access granted to a client.

##### 2.1.2.21.2 Example

  `orders/read`
  `orders/write`

##### 2.1.2.21.3 API Authorization
- Route/method can require a scope.
- Access token must contain the required scope.

##### 2.1.2.21.4 Benefit
- Authorization is more precise than simply asking:
  - "Is this user authenticated?"

#### 2.1.2.22 Cognito Resource Servers and Custom Scopes

##### 2.1.2.22.1 Resource Server
- Represents an API/resource protected by Cognito authorization.

##### 2.1.2.22.2 Custom Scope
- Defines an application-specific permission exposed by that resource server.

##### 2.1.2.22.3 Flow

  `client requests scope`
  → Cognito authorizes scope
  → access token contains scope
  → API requires scope
  → request allowed/denied

##### 2.1.2.22.4 Connection
- This is the bridge from authentication into application-level authorization.
- More fine-grained authorization belongs to Skill 2.1.7.

#### 2.1.2.23 Cognito Groups

##### 2.1.2.23.1 Purpose
- Organize users into groups.

##### 2.1.2.23.2 Token Claim
- Cognito can include `cognito:groups` in tokens.

##### 2.1.2.23.3 Application Use
- Group membership can contribute to role/RBAC-style authorization decisions.

##### 2.1.2.23.4 Boundary
- Groups are claims.
- Application/API still needs authorization logic that interprets them.

#### 2.1.2.24 API Gateway REST API + Cognito User Pool Authorizer

##### 2.1.2.24.1 Architecture

  `client`
  → authenticate with Cognito
  → obtain token
  → `Authorization` header
  → `API Gateway Cognito authorizer`
  → protected REST API method

##### 2.1.2.24.2 Authorizer Type
- `COGNITO_USER_POOLS`.

##### 2.1.2.24.3 Behavior
- API Gateway validates supplied Cognito token before allowing protected method invocation.

##### 2.1.2.24.4 Scope Authorization
- Access tokens can be checked against configured OAuth scopes.

#### 2.1.2.25 API Gateway HTTP API + JWT Authorizer

##### 2.1.2.25.1 Architecture

  `client`
  → IdP
  → JWT access token
  → `API Gateway JWT authorizer`
  → route
  → backend

##### 2.1.2.25.2 Validation
- API Gateway validates:
  - signature,
  - issuer,
  - audience/client,
  - time claims,
  - configured scopes,
  according to JWT-authorizer rules.

##### 2.1.2.25.3 Benefit
- Authentication/authorization can occur before request reaches backend code.

#### 2.1.2.26 Authorizer vs Backend Validation

##### 2.1.2.26.1 API Gateway Authorizer
- Centralizes token validation at API boundary.
- Invalid requests can be rejected before Lambda/application execution.

##### 2.1.2.26.2 Application Validation
- Application can validate JWT itself when architecture requires it.

##### 2.1.2.26.3 Principle
- Do not manually reimplement cryptographic validation when a trusted AWS authorizer or well-tested JWT/OIDC library fits the requirement.

#### 2.1.2.27 Lambda Authorizer Context

##### 2.1.2.27.1 Purpose
- API Gateway Lambda authorizer allows custom authorization logic.

##### 2.1.2.27.2 Use
- Useful when built-in Cognito/JWT authorization is insufficient for required custom logic.

##### 2.1.2.27.3 Trade-Off
- More flexibility.
- More code, latency, maintenance, and security responsibility.

##### 2.1.2.27.4 Decision
- Prefer native JWT/Cognito authorizers when their capabilities satisfy requirements.

#### 2.1.2.28 Token-Based API Pattern

##### 2.1.2.28.1 End-to-End

  `user`
  → authenticate
  → `Cognito / IdP`
  → access token
  → `API Gateway`
  → validate JWT
  → validate required scope
  → `Lambda/application`
  → business operation

##### 2.1.2.28.2 Security Boundary
- Backend receives requests only after token checks when authorizer is correctly configured.

#### 2.1.2.29 Bearer Token vs AWS Credentials

##### 2.1.2.29.1 Bearer Token
- Typically presented directly to application/API.
- Example:
  - Cognito JWT access token.

##### 2.1.2.29.2 AWS Temporary Credentials
- Access key ID + secret access key + session token.
- Used to cryptographically sign AWS API requests.

##### 2.1.2.29.3 Important Distinction
- A Cognito JWT access token is not an AWS access key.
- AWS SDK/SigV4 credentials are not simply sent as an OAuth bearer token.

##### 2.1.2.29.4 Task Connection
- AWS credential configuration is Skill 2.1.3.
- Authenticated AWS calls are Skill 2.1.4.

#### 2.1.2.30 AWS STS Session Token Context

##### 2.1.2.30.1 Exam Guide
- Task 2.1 knowledge lists AWS STS as an example alongside JWT and OAuth under bearer-token knowledge.

##### 2.1.2.30.2 Important Precision
- STS temporary AWS credentials contain:
  - access key ID,
  - secret access key,
  - session token.

##### 2.1.2.30.3 Usage
- The session token accompanies temporary AWS credentials.
- AWS requests are authenticated using the credential set and AWS request signing.

##### 2.1.2.30.4 Do Not Collapse Concepts
- OAuth bearer access token and STS temporary credential session token participate in different authentication mechanisms.
- The exam guide groups them as token-related knowledge, but AWS API authentication with STS credentials is expanded by subsequent skills.

#### 2.1.2.31 Machine-to-Machine Access Tokens

##### 2.1.2.31.1 Cognito Client Credentials
- Cognito supports OAuth 2.0 client-credentials flow for machine-to-machine authorization.

##### 2.1.2.31.2 Result
- Non-human client can receive an access token containing authorized scopes.

##### 2.1.2.31.3 Use
- Service calls protected API using bearer access token.

##### 2.1.2.31.4 Boundary
- Cross-service authentication is explored more deeply in Skill 2.1.8.

#### 2.1.2.32 Token Storage

##### 2.1.2.32.1 Threat
- Token theft can become session theft.

##### 2.1.2.32.2 Avoid
- Source-code embedding.
- Plaintext persistent storage without need/protection.
- Logging complete tokens.
- Sending tokens to unrelated services.

##### 2.1.2.32.3 Client Design
- Storage mechanism depends on application type and threat model.
- Minimize exposure and lifetime.

#### 2.1.2.33 Token Transport

##### 2.1.2.33.1 HTTPS
- Bearer tokens must be protected in transit.

##### 2.1.2.33.2 Authorization Header
- Standard application pattern:

  `Authorization: Bearer <token>`

##### 2.1.2.33.3 Avoid Query Strings
- URLs are more likely to appear in:
  - browser history,
  - proxies,
  - logs,
  - analytics.
- Prefer headers for ordinary API bearer-token transport.

#### 2.1.2.34 Token Logging

##### 2.1.2.34.1 Risk
- Logs are commonly copied, indexed, retained, and accessible to operational systems.

##### 2.1.2.34.2 Rule
- Do not log complete bearer tokens.

##### 2.1.2.34.3 Diagnostics
- Log safe metadata instead:
  - request ID,
  - issuer,
  - subject where appropriate,
  - authorization outcome,
  - non-sensitive error reason.

#### 2.1.2.35 Token Revocation and Expiration

##### 2.1.2.35.1 Short-Lived Access
- Access tokens naturally stop working at expiration.

##### 2.1.2.35.2 Refresh Token
- Can obtain replacement tokens while session remains valid.

##### 2.1.2.35.3 Cognito
- Supports refresh-token revocation.

##### 2.1.2.35.4 Architectural Consequence
- Stateless JWT validation makes APIs scalable, but immediate invalidation behavior differs from simply checking a centralized server-side session on every request.

#### 2.1.2.36 Stateless Authorization

##### 2.1.2.36.1 JWT Benefit
- Token contains signed claims.
- API can validate token without retrieving session state from the issuer on every request.

##### 2.1.2.36.2 Scalability
- Useful for distributed APIs/microservices.

##### 2.1.2.36.3 Trade-Off
- Previously issued token may remain usable until expiry unless architecture has an additional revocation mechanism.

#### 2.1.2.37 Token Replay

##### 2.1.2.37.1 Threat
- Attacker obtains valid bearer token and sends it again.

##### 2.1.2.37.2 Mitigations
- TLS.
- Short lifetimes.
- Secure storage.
- Avoid logging.
- Appropriate revocation/session controls.

##### 2.1.2.37.3 Core Principle
- Treat bearer tokens like credentials, not harmless identifiers.

#### 2.1.2.38 Scope vs Role/Group

##### 2.1.2.38.1 Scope
- Permission requested/granted for an API/resource.
- Example:
  - `orders/read`.

##### 2.1.2.38.2 Group/Role Claim
- Describes principal membership/role.
- Example:
  - `Administrators`.

##### 2.1.2.38.3 Authorization Models
- Scope-based:
  - "Does token permit this API operation?"
- Role/group-based:
  - "Does principal belong to a role allowed to perform it?"

##### 2.1.2.38.4 Connection
- Fine-grained application authorization belongs to 2.1.7.

#### 2.1.2.39 Token Validation Decision Tree

##### 2.1.2.39.1 Protected HTTP API + Cognito User Pool
- REST API:
  - Cognito user-pool authorizer.
- HTTP API:
  - JWT authorizer is a strong native option.

##### 2.1.2.39.2 External OIDC Provider + HTTP API
- Configure JWT authorizer with expected issuer/audience.

##### 2.1.2.39.3 Need Custom Authorization Logic
- Consider Lambda authorizer.

##### 2.1.2.39.4 Need Direct AWS API Access
- Bearer JWT alone is generally not the AWS SDK credential.
- Obtain/use AWS credentials as covered by 2.1.3–2.1.5.

#### 2.1.2.40 Common Exam Traps

##### 2.1.2.40.1 Decode = Validate
- False.
- A JWT can be decoded without proving authenticity.
- Verify signature and claims.

##### 2.1.2.40.2 JWT Payload Is Encrypted
- False by default.
- Signed JWT claims are readable.

##### 2.1.2.40.3 ID Token and Access Token Are Interchangeable
- Wrong.
- ID token is identity-oriented.
- Access token is authorization-oriented.

##### 2.1.2.40.4 Authentication Alone Protects Every Operation
- Wrong.
- API must evaluate authorization requirements such as scopes/claims.

##### 2.1.2.40.5 Valid Signature Is Enough
- Wrong.
- Also validate relevant claims:
  - issuer,
  - expiration,
  - audience/client,
  - token purpose,
  - scopes.

##### 2.1.2.40.6 Bearer Token Can Safely Be Logged
- Wrong.
- Possession can enable replay.

##### 2.1.2.40.7 Access Token = AWS Access Key
- Wrong.
- Different credential systems.

##### 2.1.2.40.8 STS Session Token Used Alone
- Wrong.
- STS session token is part of a temporary AWS credential set.

##### 2.1.2.40.9 Custom Lambda Authorizer Is Always Required
- Wrong.
- API Gateway has native Cognito/JWT authorizers.

##### 2.1.2.40.10 Long-Lived Access Token Is Always Convenient
- Security trade-off.
- Longer validity increases stolen-token exposure.

#### 2.1.2.44 Exam-Level Knowledge Frame

##### 2.1.2.44.1 Bearer Token
- Possession grants ability to present the credential.
- Protect it accordingly.

##### 2.1.2.44.2 JWT
- `header.payload.signature`.
- Signed, not inherently encrypted.
- Validate signature and claims.

##### 2.1.2.44.3 Cognito
- User pool can issue:
  - ID token,
  - access token,
  - refresh token.
- Access token is the primary token for scope-based API authorization.

##### 2.1.2.44.4 API Gateway
- REST API:
  - Cognito user-pool authorizer.
- HTTP API:
  - JWT authorizer.
- Native authorizers can reject invalid/unauthorized requests before backend execution.

##### 2.1.2.44.5 Security
- HTTPS.
- no token logging.
- appropriate expiration.
- verify issuer/signature/audience/token purpose/scopes as applicable.

##### 2.1.2.44.6 Critical Distinction
- **Bearer JWT → protected application/API.**
- **AWS temporary credentials → signed AWS API calls.**
