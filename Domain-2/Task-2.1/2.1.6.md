### 2.1.6 Define permissions for IAM principals

#### 2.1.6.1 Exam and Task Context
- Domain 2 is **Security**.
- Task 2.1 is **Implement authentication and/or authorization for applications and AWS services**.
- Skill 2.1.6 is **Define permissions for IAM principals**.
- Previous skills established identity, tokens, credentials, authenticated calls, and role assumption.
- This skill answers: **Given an authenticated principal, what may it do, to which resources, and under what conditions?**

#### 2.1.6.2 Core Mental Model
AWS authorization evaluates the request as:

`Principal → Action → Resource → Condition/context → policy evaluation → Allow / Deny`

AWS documentation describes this request context using the **PARC** model:
- **Principal** — who makes the request.
- **Action** — what operation is requested.
- **Resource** — which AWS resource is targeted.
- **Condition** — contextual constraints.

Authorization starts with **implicit deny**. An applicable allow is required, and an applicable explicit deny overrides an allow.

#### 2.1.6.3 IAM Principals
- A principal is an authenticated entity making an AWS request.
- Common principals:
  - IAM user,
  - IAM role,
  - assumed-role session,
  - federated principal/session,
  - AWS service principal.
- IAM groups organize permissions for users but are **not principals** themselves.

#### 2.1.6.4 IAM Policy Mental Model
An IAM policy is a JSON permissions document. A typical statement answers:

- `Effect` → Allow or Deny?
- `Action` → Which AWS operation?
- `Resource` → Which resource?
- `Condition` → Under which circumstances?
- `Principal` → Who? — used where applicable, particularly resource-based policies.

Example:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::example-bucket/*"
  }]
}
```

Meaning: allow the identity to which this identity-based policy is attached to read objects from the specified bucket.

#### 2.1.6.5 Policy Elements

##### 2.1.6.5.1 Version
- Defines the IAM policy language version.
- Common current value: `2012-10-17`.
- It is not the policy's revision number.

##### 2.1.6.5.2 Statement
- Contains one or more permission rules.
- Statement order is not "first match wins."

##### 2.1.6.5.3 Effect
- Required.
- Values:
  - `Allow`
  - `Deny`
- Default access is denied.
- Explicit deny overrides allow.

##### 2.1.6.5.4 Action
- AWS operation affected by the statement.
- Format: `service:operation`.
- Examples:
  - `s3:GetObject`
  - `sqs:SendMessage`
  - `dynamodb:GetItem`
  - `lambda:InvokeFunction`
- Wildcards are supported, but least privilege favors only required actions.

##### 2.1.6.5.5 Resource
- AWS resource(s) affected by the statement.
- Normally represented by ARN.
- Example:
  - `arn:aws:s3:::example-bucket/*`
- Some actions do not support resource-level restriction and therefore require `Resource: "*"`.

##### 2.1.6.5.6 Principal
- Specifies who is allowed/denied in a resource-based policy.
- Can represent:
  - AWS accounts,
  - users,
  - roles,
  - federated identities,
  - AWS services.
- Identity-based policies do not contain `Principal`; attachment identifies the principal.

##### 2.1.6.5.7 Condition
- Optional contextual restriction.
- Compares request-context values using condition operators.
- Examples:
  - source account,
  - source ARN,
  - source IP,
  - principal/resource/request tags,
  - requested Region,
  - MFA,
  - secure transport.

#### 2.1.6.6 Identity-Based Policies
- Attached to:
  - users,
  - groups,
  - roles.
- Define what the attached identity may do.
- Main forms:
  - AWS managed policies,
  - customer managed policies,
  - inline policies.

##### 2.1.6.6.1 AWS Managed Policies
- Created and maintained by AWS.
- Reusable.
- Convenient but often more general than an application's exact least-privilege requirements.

##### 2.1.6.6.2 Customer Managed Policies
- Created and maintained in your account.
- Reusable across identities.
- Appropriate for centrally managed, application-specific permissions.

##### 2.1.6.6.3 Inline Policies
- Embedded directly in one user, group, or role.
- Strong one-to-one relationship with that identity.
- Managed policies are generally better when reuse and centralized management are desired.

#### 2.1.6.7 Resource-Based Policies
- Attached to a resource rather than an IAM identity.
- Explicitly identify `Principal`.
- Examples:
  - S3 bucket policy,
  - SQS queue policy,
  - SNS topic policy,
  - Lambda resource-based policy,
  - KMS key policy,
  - IAM role trust policy.

Mental distinction:

`Identity policy`
→ **What may this identity do?**

`Resource policy`
→ **Who may do what to this resource?**

#### 2.1.6.8 Role Trust Policies
- An IAM role trust policy is a resource-based policy.
- It defines who may assume the role.
- Common action: `sts:AssumeRole`.
- Trust policy does **not** define the ordinary AWS service permissions available after assumption.
- Role assumption itself was covered in 2.1.5.

#### 2.1.6.9 Permissions Boundaries
- Set the maximum permissions that identity-based policies can grant to an IAM user or role.
- A boundary does **not grant** permission.

Mental model:

`identity-based permissions ∩ permissions boundary = maximum effective identity permissions`

Use case:
- delegate creation/management of roles while preventing delegated administrators from exceeding an approved permission ceiling.

#### 2.1.6.10 AWS Organizations SCPs
- Service Control Policies act as organization/account/OU permission guardrails.
- SCPs do **not grant** permissions.
- They restrict what permissions can ultimately be exercised in affected member accounts.

Mental model:

`IAM authorization ∩ SCP guardrail → potentially allowed`

Exam clue:
- "Prevent accounts in this OU from ever performing action X" → consider SCP.

#### 2.1.6.11 Session Policies
- Apply to temporary sessions such as assumed-role sessions.
- They restrict the session.

`role permissions ∩ session policy = session permissions`

- Session policies cannot grant more than the role already permits.
- This connects directly to 2.1.5.

#### 2.1.6.12 Policy Evaluation Logic

High-level sequence:

1. Authenticate principal.
2. Build request context.
3. Identify applicable policies.
4. Begin with implicit deny.
5. Find applicable allows.
6. Apply boundaries/guardrails/session restrictions.
7. Check explicit denies.
8. Allow only if authorization survives all applicable controls.

Core rule:

`No Allow → DENY`

`Allow → potentially ALLOW`

`Allow + applicable explicit Deny → DENY`

#### 2.1.6.13 Combining Policy Types
A useful exam mental model is:

`identity-based allows`
`+ resource-based allows where applicable`
→ constrained by:
- permissions boundaries,
- SCPs,
- session policies,
- other applicable policy controls
→ overridden by applicable explicit denies.

IAM has important nuances for role sessions, resource policies, and cross-account access, so this is a reasoning frame rather than a replacement for AWS's formal evaluation logic.

#### 2.1.6.14 Least Privilege
Grant only what is required.

Reduce permission scope across four dimensions:

`Principal`
→ only intended caller

`Action`
→ only required API operations

`Resource`
→ only required resources

`Condition`
→ only required circumstances

Avoid broad constructs such as:
- `Action: "*"`
- `Resource: "*"`
when narrower permissions are supported and sufficient.

#### 2.1.6.15 Resource-Level Permissions
- Prefer specific resource ARNs when supported.
- Not every AWS action supports resource-level permissions.
- The AWS Service Authorization Reference is the source of truth for:
  - actions,
  - resource types,
  - condition keys,
  - dependent actions.

#### 2.1.6.16 Dependent Actions
- Some operations require additional IAM permissions.
- A request can fail even when the obvious primary action is allowed.
- Check service documentation/Service Authorization Reference when an operation has dependent actions.

#### 2.1.6.17 Conditions as Permission Refinement

Examples of useful restrictions:

##### 2.1.6.17.1 Source
- `aws:SourceArn`
- `aws:SourceAccount`

##### 2.1.6.17.2 Principal
- principal ARN/account,
- organization ID,
- principal tags.

##### 2.1.6.17.3 Resource
- resource tags.

##### 2.1.6.17.4 Request
- request tags,
- requested Region,
- service-specific request attributes.

##### 2.1.6.17.5 Environment
- IP address where appropriate,
- time,
- TLS/secure transport,
- MFA context.

#### 2.1.6.18 `aws:SourceArn` and `aws:SourceAccount`
- Frequently used in resource policies when an AWS service acts as principal.
- Restrict access to calls originating from the intended source resource/account.
- Help mitigate confused-deputy scenarios.
- Important bridge into 2.1.8 cross-service authentication.

#### 2.1.6.19 Role-Based Access Control — RBAC
- Permissions are grouped around roles/job functions.
- Example roles:
  - Developer,
  - Deployment,
  - Operations,
  - ReadOnly.
- Principal assumes/receives the appropriate role.

Mental model:

`identity → role → permissions`

#### 2.1.6.20 Attribute-Based Access Control — ABAC
- Authorization depends on attributes such as tags.

Example:

`PrincipalTag/project = alpha`
+
`ResourceTag/project = alpha`
→ permit matching project access.

Benefits:
- scales across many resources,
- avoids enumerating every resource ARN,
- supports dynamic authorization.

Requires:
- consistent tags,
- controlled tag modification,
- appropriate condition design.

#### 2.1.6.21 Policy Variables
- IAM policy variables can substitute request/principal values into policy elements where supported.
- Example concept:
  - each user receives access to a resource path matching their identity/tag.
- Useful for scalable dynamic policies.

#### 2.1.6.22 Wildcards

##### 2.1.6.22.1 Action Wildcards
- Example:
  - `s3:Get*`

##### 2.1.6.22.2 Resource Wildcards
- Example:
  - `arn:aws:s3:::bucket/project-a/*`

##### 2.1.6.22.3 Risk
- Wildcards broaden authorization.
- Use intentionally and only where required.

#### 2.1.6.23 `NotAction` and `NotResource`
- Express complements/exceptions.
- Meaning depends on `Effect` and policy scope.
- `NotAction` does **not** automatically mean "deny this action."
- These constructs can easily create unexpectedly broad permissions; reason through them carefully.

#### 2.1.6.24 Example — Lambda Reads DynamoDB
Requirement:
- one Lambda function reads one table.

Architecture:

`Lambda`
→ execution role
→ identity-based IAM policy
→ required DynamoDB read actions
→ specific table ARN

Avoid:
- `dynamodb:*`
- `Resource: "*"`
unless genuinely required.

#### 2.1.6.25 Example — Lambda Sends to SQS
Requirement:
- function sends messages to one queue.

Permission:

`Action: sqs:SendMessage`
→ `Resource: <specific queue ARN>`

Authentication:
- Lambda runtime supplies execution-role credentials.

Authorization:
- IAM determines whether execution role may send to that queue.

#### 2.1.6.26 Example — S3 Read
Object read:
- `s3:GetObject`
- `arn:aws:s3:::bucket/*`

Bucket listing:
- `s3:ListBucket`
- `arn:aws:s3:::bucket`

Important exam distinction:
- **bucket ARN ≠ object ARN**
- required resources depend on the operation.

#### 2.1.6.27 Cross-Account Authorization
Cross-account access is a trust boundary.

Reason using:

`Principal in Account A`
→ identity-side permission
→ resource/role trust in Account B
→ applicable guardrails
→ allow/deny

Do not assume that simply naming another account's principal in one place automatically completes every cross-account authorization model.

#### 2.1.6.28 IAM Access Analyzer
Useful for:
- policy validation,
- identifying supported external/public access,
- refining permissions,
- generating policy candidates from observed access in supported workflows.

Mindset:
- use tooling to move from broad initial permissions toward verified least privilege.

#### 2.1.6.29 IAM Policy Simulator
- Helps test how policies evaluate actions/resources.
- Useful for policy development and troubleshooting.
- It does not eliminate the need to understand real request context and service-specific authorization behavior.

#### 2.1.6.30 AccessDenied Troubleshooting
Use PARC systematically:

1. **Principal**
   - Which user/role/session actually made the request?
2. **Action**
   - Which IAM action corresponds to the failed operation?
3. **Resource**
   - Which exact ARN/resource was evaluated?
4. **Allow**
   - Is an applicable allow present?
5. **Condition**
   - Do condition keys match actual request context?
6. **Boundaries**
   - permissions boundary?
   - SCP?
   - session policy?
   - endpoint/resource policy?
7. **Explicit Deny**
   - Is any applicable policy denying the request?

#### 2.1.6.31 Authentication vs Authorization Failure
Authentication failure:
- AWS cannot establish caller identity.
- Primarily 2.1.3–2.1.5.

Authorization failure:
- AWS knows the caller,
- but IAM denies the requested operation.

2.1.6 primarily concerns the second case.

#### 2.1.6.32 Permission Design Workflow

`workload requirement`
→ identify required AWS API operation
→ map operation to IAM Action
→ identify supported Resource ARN
→ add useful Conditions
→ attach policy to correct identity/resource
→ test
→ observe actual access
→ reduce toward least privilege

#### 2.1.6.33 Common Exam Traps
- **No explicit deny means allowed** → false; implicit deny exists.
- **Any allow beats deny** → false; explicit deny wins.
- **Permissions boundary grants permissions** → false; it limits.
- **SCP grants permissions** → false; it limits.
- **Identity policy needs Principal** → false.
- **Resource-based policy normally identifies Principal** → true.
- **IAM group is a principal** → false.
- **Every action supports resource-level restriction** → false.
- **`Resource: "*"` is always required** → false.
- **Session policy can expand a role** → false.
- **AWS managed policy automatically means least privilege** → false.
- **Statements are processed top-to-bottom** → false.
- **`NotAction` means deny** → false.
- **Authenticated means authorized** → false.

#### 2.1.6.37 Exam-Level Knowledge Frame
Know these cold:

**Policy**
→ Effect + Action + Resource + optional Condition  
→ Principal where resource-based.

**Evaluation**
→ implicit deny by default  
→ applicable allow required  
→ explicit deny wins  
→ boundaries/SCPs/session policies can restrict.

**Policy placement**
→ identity-based = what identity may do  
→ resource-based = who may do what to resource.

**Least privilege**
→ narrow Principal + Action + Resource + Condition.

**Troubleshooting**
→ use PARC.

Final principle:

**Authentication identifies the caller; IAM authorization determines whether that caller may perform the requested action on the requested resource under the current request context.**
