### 2.1.4 Make authenticated calls to AWS services

#### 2.1.4.1 Exam and Task Context

##### 2.1.4.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.1 is **Implement authentication and/or authorization for applications and AWS services**.
- Skill 2.1.4 is **Make authenticated calls to AWS services**.
- This is the point where identity and credential configuration become an actual AWS API request.

##### 2.1.4.1.2 Position Inside Task 2.1
- 2.1.1 → establish identity/federation.
- 2.1.2 → secure application/API access with bearer tokens.
- 2.1.3 → obtain/configure AWS programmatic credentials.
- 2.1.4 → use those credentials to authenticate AWS API requests.
- 2.1.5 → assume IAM roles in more depth.
- 2.1.6 → determine what the authenticated principal is authorized to do.

##### 2.1.4.1.3 Core Question
- **How does AWS know that an API request really came from the AWS principal associated with the credentials?**

#### 2.1.4.2 Core Mental Model

##### 2.1.4.2.1 Request Flow

  `application`
  → obtain credentials
  → construct AWS request
  → sign request
  → send over HTTPS
  → AWS verifies signature
  → AWS identifies principal
  → IAM authorization evaluates request
  → allow / deny

##### 2.1.4.2.2 Fundamental Distinction
- **Authentication**
  - proves which AWS principal sent the request.
- **Authorization**
  - determines whether that principal may perform the requested action.

##### 2.1.4.2.3 Key Principle
- For most AWS service APIs, authentication is implemented through **AWS request signing**, usually Signature Version 4 (SigV4).
- AWS SDKs and the AWS CLI normally perform signing automatically.

#### 2.1.4.3 AWS API Requests

##### 2.1.4.3.1 Request Components
- An AWS API request typically includes:
  - service endpoint,
  - Region where relevant,
  - API action/operation,
  - parameters/body,
  - HTTP headers,
  - date/time,
  - authentication/signature information.

##### 2.1.4.3.2 Endpoint
- Identifies the AWS service and often the Region.

##### 2.1.4.3.3 Action
- The requested AWS operation.
- Examples:
  - `GetItem`,
  - `PutObject`,
  - `Invoke`,
  - `SendMessage`.

##### 2.1.4.3.4 Authentication Information
- Signed request contains enough information for AWS to:
  - identify credential used,
  - reproduce signature calculation,
  - verify request integrity/authenticity.

#### 2.1.4.4 Why AWS Requests Are Signed

##### 2.1.4.4.1 Identity
- The signature proves possession of the secret material associated with the AWS credentials.

##### 2.1.4.4.2 Integrity
- Signature covers selected request elements.
- If signed content changes after signing, verification fails.

##### 2.1.4.4.3 Replay Resistance
- Request includes timestamp/date information.
- Credential scope and timestamp reduce usefulness of replaying old signed requests.

##### 2.1.4.4.4 Authorization Input
- Once AWS authenticates the principal, IAM can evaluate:
  - action,
  - resource,
  - principal,
  - conditions.

#### 2.1.4.5 Signature Version 4 — SigV4

##### 2.1.4.5.1 Purpose
- SigV4 is the standard AWS protocol for adding authentication information to AWS API requests.

##### 2.1.4.5.2 High-Level Steps

  1. Create canonical request.
  2. Hash canonical request.
  3. Create string to sign.
  4. Derive signing key from credentials and scope.
  5. Calculate signature.
  6. Add signature/authentication information to request.

##### 2.1.4.5.3 Developer Reality
- You normally do **not** implement these steps manually.
- AWS recommends using:
  - AWS SDK,
  - AWS CLI.

#### 2.1.4.6 Canonical Request

##### 2.1.4.6.1 Purpose
- Converts request into a deterministic normalized form before signing.

##### 2.1.4.6.2 Conceptual Contents
- HTTP method.
- Canonical URI.
- Canonical query string.
- Canonical headers.
- Signed headers list.
- Payload hash.

##### 2.1.4.6.3 Why
- Client and AWS must independently calculate exactly the same representation.
- Any mismatch causes signature verification failure.

##### 2.1.4.6.4 Exam Depth
- Understand the role of canonicalization.
- Do not memorize the byte-level algorithm unless explicitly required.

#### 2.1.4.7 Credential Scope

##### 2.1.4.7.1 SigV4 Scope
- SigV4 derives a signing key scoped to:
  - date,
  - Region,
  - service,
  - `aws4_request`.

##### 2.1.4.7.2 Consequence
- SigV4 signature is tied to:
  - the intended service,
  - intended Region,
  - date.

##### 2.1.4.7.3 Example Mental Model
- Credentials may be valid broadly according to IAM,
- but each signature is derived for a specific service/Region/time scope.

#### 2.1.4.8 Authorization Header

##### 2.1.4.8.1 Common Pattern
- Authentication information is commonly sent in the HTTP `Authorization` header.

##### 2.1.4.8.2 SigV4 Header Includes
- signing algorithm,
  - credential/scope,
  - list of signed headers,
  - signature.

##### 2.1.4.8.3 Additional Headers
- Common signed AWS requests also include:
  - `host`,
  - `x-amz-date`.

##### 2.1.4.8.4 Temporary Credentials
- When using STS temporary credentials, request also requires:
  - `x-amz-security-token`
  or equivalent query parameter.

#### 2.1.4.9 AWS SDK Authentication

##### 2.1.4.9.1 Normal Path
- Application creates AWS SDK client.
- SDK:
  - finds credentials from provider chain,
  - selects endpoint/Region,
  - serializes request,
  - signs request,
  - sends request.

##### 2.1.4.9.2 Mental Model

  `SDK client operation`
  → credentials provider
  → SigV4 signer
  → HTTPS request
  → AWS service

##### 2.1.4.9.3 Benefit
- Application code focuses on:
  - service operation,
  - business parameters,
  rather than cryptographic signing details.

#### 2.1.4.10 AWS CLI Authentication

##### 2.1.4.10.1 Flow
- CLI resolves credentials/profile.
- CLI signs request automatically.
- CLI sends request to AWS endpoint.

##### 2.1.4.10.2 Example
- `aws s3api get-object ...`
- Developer does not manually create SigV4 header.

##### 2.1.4.10.3 Connection
- Credential configuration was covered in 2.1.3.

#### 2.1.4.11 Temporary Credentials and Signing

##### 2.1.4.11.1 Credential Set
- Temporary AWS credentials include:
  - access key ID,
  - secret access key,
  - session token.

##### 2.1.4.11.2 Signature
- Secret access key participates in SigV4 derivation.

##### 2.1.4.11.3 Session Token
- Session token must accompany the signed request.

##### 2.1.4.11.4 Exam Trap
- Correct SigV4 calculation with access key + secret is still insufficient if the temporary credential's session token is omitted.

#### 2.1.4.12 HTTPS

##### 2.1.4.12.1 Request Signing Is Not Transport Encryption
- Signature authenticates request and protects signed-content integrity.
- HTTPS/TLS protects confidentiality in transit.

##### 2.1.4.12.2 Correct Model

  `SigV4`
  → authentication + request integrity

  `TLS/HTTPS`
  → encrypted transport

##### 2.1.4.12.3 Security
- Use HTTPS for AWS API calls.
- Do not treat SigV4 as a replacement for TLS.

#### 2.1.4.13 Request Time

##### 2.1.4.13.1 `x-amz-date`
- SigV4 requests include request timestamp.

##### 2.1.4.13.2 Why
- Part of signature calculation.
- Helps protect against replay.

##### 2.1.4.13.3 Clock Skew
- If client system clock is significantly incorrect, signed requests can fail.

##### 2.1.4.13.4 Operational Implication
- Accurate system time matters for AWS request authentication.

#### 2.1.4.14 Signature Version 4a — SigV4a

##### 2.1.4.14.1 Purpose
- SigV4a extends AWS signing for requests valid across multiple Regions.

##### 2.1.4.14.2 Difference
- SigV4:
  - signing scope includes one Region.
- SigV4a:
  - signature can be verified across a Region set.

##### 2.1.4.14.3 Example AWS Use
- Multi-Region access patterns such as supported S3 Multi-Region Access Point requests.

##### 2.1.4.14.4 Exam Depth
- Recognize SigV4a as multi-Region signing.
- SigV4 remains the core model for ordinary AWS service calls.

#### 2.1.4.15 SDK Authentication Scheme Selection

##### 2.1.4.15.1 Service Model
- Modern AWS SDKs can select supported authentication scheme based on service definition.

##### 2.1.4.15.2 Examples
- SigV4.
- SigV4a.
- HTTP bearer authentication for supported services.

##### 2.1.4.15.3 Principle
- Let the SDK select appropriate authentication scheme unless there is a specific reason to override it.

#### 2.1.4.16 Manual HTTP Calls

##### 2.1.4.16.1 When
- Custom HTTP client.
- Unsupported environment.
- Low-level protocol integration.

##### 2.1.4.16.2 Requirement
- Developer must sign the request correctly if the target AWS API uses IAM/SigV4 authentication.

##### 2.1.4.16.3 Risk
- Manual signing is easy to implement incorrectly.

##### 2.1.4.16.4 AWS Recommendation
- Prefer AWS SDKs or CLI whenever possible.

#### 2.1.4.17 Presigned Requests

##### 2.1.4.17.1 Concept
- SigV4 authentication information can be placed in query parameters instead of Authorization header.

##### 2.1.4.17.2 Result
- A signed URL can temporarily authorize a specific AWS operation.

##### 2.1.4.17.3 Common Example
- Amazon S3 presigned URL.

##### 2.1.4.17.4 Flow

  `trusted backend`
  → signs specific S3 request
  → creates presigned URL
  → client uses URL
  → S3 validates signature
  → operation allowed within expiry/permissions

#### 2.1.4.18 Presigned URL Security Model

##### 2.1.4.18.1 Bearer-Like Property
- Anyone possessing a valid presigned URL can use it while it remains valid, subject to its constraints.

##### 2.1.4.18.2 Authorization
- URL cannot grant more permission than the credentials used to sign it possess.

##### 2.1.4.18.3 Expiration
- URL is valid only for configured duration and underlying credential validity.

##### 2.1.4.18.4 Temporary Credentials
- If signed with temporary credentials, the presigned URL cannot outlive those credentials.

##### 2.1.4.18.5 Exam Trap
- A presigned URL does not make an S3 object permanently public.

#### 2.1.4.19 Header Signing vs Query Signing

##### 2.1.4.19.1 Header Signing
- Normal AWS SDK/API request.
- SigV4 authentication information placed in `Authorization` header.

##### 2.1.4.19.2 Query Signing
- Authentication parameters included in URL query string.
- Creates presigned-request pattern.

##### 2.1.4.19.3 Same Foundation
- Both use AWS request-signing concepts.

#### 2.1.4.20 API Gateway with IAM Authentication

##### 2.1.4.20.1 IAM-Protected API
- API Gateway methods/routes can require AWS IAM authorization.

##### 2.1.4.20.2 Caller
- Caller must have AWS credentials.
- Request must be SigV4 signed.

##### 2.1.4.20.3 Permission
- IAM principal must have appropriate `execute-api:Invoke` permission.

##### 2.1.4.20.4 Flow

  `client`
  → AWS credentials
  → SigV4-signed HTTP request
  → API Gateway
  → IAM authorization
  → backend

#### 2.1.4.21 API Gateway IAM vs JWT

##### 2.1.4.21.1 JWT/Cognito Authorizer
- Client presents bearer token.
- API Gateway validates token/claims/scopes.

##### 2.1.4.21.2 IAM Authorization
- Client uses AWS credentials.
- Request is SigV4 signed.
- IAM policies authorize `execute-api:Invoke`.

##### 2.1.4.21.3 Decision
- End-user web/mobile API → JWT/Cognito commonly fits.
- AWS principal/workload calling API → IAM/SigV4 can fit.

##### 2.1.4.21.4 Task Connection
- Bearer-token path = Skill 2.1.2.
- AWS-credential path = Skills 2.1.3–2.1.4.

#### 2.1.4.22 S3 Authenticated Calls

##### 2.1.4.22.1 Direct SDK Call
- SDK signs S3 request using AWS credentials.

##### 2.1.4.22.2 Presigned URL
- Backend signs request in advance.
- Client performs S3 operation without possessing backend AWS credentials.

##### 2.1.4.22.3 Security
- Backend's IAM permissions constrain what can be presigned.

##### 2.1.4.22.4 Use Case
- Browser/mobile client uploads/downloads specific object directly from S3.

#### 2.1.4.23 DynamoDB Authenticated Calls

##### 2.1.4.23.1 SDK
- Application obtains credentials from runtime/provider.
- SDK signs DynamoDB request.

##### 2.1.4.23.2 Example

  `dynamoDbClient.getItem(...)`
  → provider chain
  → temporary role credentials
  → SigV4
  → DynamoDB

##### 2.1.4.23.3 IAM
- Permission policy determines allowed:
  - DynamoDB action,
  - table/index/resource,
  - optional conditions.

#### 2.1.4.24 Lambda Calling AWS Services

##### 2.1.4.24.1 Execution Role
- Lambda runtime supplies temporary execution-role credentials.

##### 2.1.4.24.2 SDK
- Function code creates client and calls AWS API.
- SDK signs request automatically.

##### 2.1.4.24.3 Correct Pattern
- Do not put AWS access keys in Lambda environment variables for ordinary AWS service access.

##### 2.1.4.24.4 Example

  `Lambda execution role`
  → SDK credentials
  → SigV4 signed SQS/DynamoDB/S3 call

#### 2.1.4.25 EC2/ECS/EKS Calling AWS Services

##### 2.1.4.25.1 Runtime Role
- Workload obtains temporary AWS credentials from its assigned role mechanism.

##### 2.1.4.25.2 SDK
- Provider chain discovers credentials.
- SDK signs requests.

##### 2.1.4.25.3 Principle
- Authentication code should generally be the same regardless of whether credentials came from:
  - instance role,
  - task role,
  - workload identity,
  - assume-role provider.

#### 2.1.4.26 Cross-Account Calls

##### 2.1.4.26.1 Typical Flow

  `source principal`
  → assume target role
  → temporary target-role credentials
  → signed AWS API call

##### 2.1.4.26.2 Authentication
- API call is authenticated as the **assumed role session**, not the original principal directly.

##### 2.1.4.26.3 Authorization
- Target role policies and resource policies determine access.

##### 2.1.4.26.4 Connection
- AssumeRole mechanics belong primarily to Skill 2.1.5.

#### 2.1.4.27 Resource Policies

##### 2.1.4.27.1 Authenticated Principal
- Some AWS services also evaluate a resource-based policy.

##### 2.1.4.27.2 Examples
- S3 bucket policy.
- SQS queue policy.
- SNS topic policy.
- Lambda resource policy.

##### 2.1.4.27.3 Distinction
- SigV4 proves identity.
- Identity policy/resource policy determine access.

##### 2.1.4.27.4 Connection
- Detailed IAM permissions belong to 2.1.6.

#### 2.1.4.28 AWS Service-to-Service Calls

##### 2.1.4.28.1 Managed Integration
- Sometimes one AWS service invokes another without application code manually signing the request.

##### 2.1.4.28.2 Trust
- Authentication/authorization is represented by:
  - service principal,
  - execution role,
  - resource policy,
  depending on integration.

##### 2.1.4.28.3 Example
- API Gateway invokes Lambda.
- Lambda resource policy allows API Gateway service principal.

##### 2.1.4.28.4 Boundary
- Cross-service authentication is expanded in Skill 2.1.8.

#### 2.1.4.29 Authentication Failures

##### 2.1.4.29.1 Missing Authentication
- Request uses IAM authentication but is unsigned.

##### 2.1.4.29.2 Invalid Credentials
- Access key incorrect/disabled.
- Session expired.
- Session token missing.

##### 2.1.4.29.3 Signature Mismatch
- Canonical request differs.
- Wrong secret key.
- Wrong Region/service scope.
- Request changed after signing.

##### 2.1.4.29.4 Clock Skew
- Timestamp outside accepted range.

##### 2.1.4.29.5 Authorization Failure
- Signature valid and principal authenticated,
- but IAM does not allow requested action.

#### 2.1.4.30 Authentication Error vs Authorization Error

##### 2.1.4.30.1 Authentication Error
- AWS cannot prove caller identity.
- Examples:
  - invalid signature,
  - invalid/expired token,
  - missing credentials.

##### 2.1.4.30.2 Authorization Error
- AWS knows caller identity but denies requested action.

##### 2.1.4.30.3 Exam Mindset
- Distinguish:
  - **Who are you? failed**
  from
  - **You are authenticated, but not allowed.**

#### 2.1.4.31 Signature Mismatch Debugging

##### 2.1.4.31.1 Check Credential Source
- Are the credentials expected?
- Has another provider overridden them?

##### 2.1.4.31.2 Check Session Token
- Is temporary credential session token included?

##### 2.1.4.31.3 Check Region
- Request signed for correct Region?

##### 2.1.4.31.4 Check Service
- Correct service signing name?

##### 2.1.4.31.5 Check Time
- Client clock correct?

##### 2.1.4.31.6 Check Request Mutation
- Did proxy/client modify signed headers, URI, query parameters, or payload after signing?

#### 2.1.4.32 SDK Retry vs Authentication Failure

##### 2.1.4.32.1 Transient Errors
- SDK retry can help for:
  - throttling,
  - temporary service failures.

##### 2.1.4.32.2 Authentication Errors
- Repeating the same invalid signature/expired credentials usually does not solve the problem.

##### 2.1.4.32.3 Credential Refresh
- If temporary credentials expired, provider may refresh them and retry.

##### 2.1.4.32.4 Rule
- Diagnose security/authentication failures rather than blindly retrying them.

#### 2.1.4.33 Endpoint and Region

##### 2.1.4.33.1 Endpoint
- The selected endpoint affects request destination.

##### 2.1.4.33.2 SigV4
- Region is part of signing scope for ordinary regional SigV4.

##### 2.1.4.33.3 Consequence
- A request sent to one Region but signed for another can fail authentication.

##### 2.1.4.33.4 SDK
- Correct Region configuration matters for both:
  - endpoint selection,
  - request signing.

#### 2.1.4.34 Service Signing Name

##### 2.1.4.34.1 SigV4 Scope
- Signing scope includes AWS service identifier.

##### 2.1.4.34.2 SDK
- SDK knows correct signing name from service model.

##### 2.1.4.34.3 Manual Calls
- Developer must know correct service signing name.

##### 2.1.4.34.4 Principle
- Another reason to prefer SDK over manual signing.

#### 2.1.4.35 Anonymous/Public Requests

##### 2.1.4.35.1 Some AWS Resources Can Be Public
- Example:
  - explicitly public S3 object.

##### 2.1.4.35.2 No Authentication
- A public resource may be accessed anonymously depending on resource policy/configuration.

##### 2.1.4.35.3 Skill Focus
- Skill 2.1.4 concerns authenticated AWS service calls.
- Do not assume every AWS request always requires signed authentication if the resource explicitly allows public anonymous access.

#### 2.1.4.36 SDK Client Configuration

##### 2.1.4.36.1 Main Inputs
- Region.
- Credentials/credential provider.
- Endpoint where customized.
- Retry/timeouts.
- Service-specific options.

##### 2.1.4.36.2 Security Principle
- Prefer default credential provider chain and standard endpoints/signers where possible.

##### 2.1.4.36.3 Avoid
- Manually constructing raw credentials/signatures unless necessary.

#### 2.1.4.37 Application API vs AWS API

##### 2.1.4.37.1 Application API
- Common authentication:
  - bearer JWT,
  - Cognito/JWT authorizer.

##### 2.1.4.37.2 AWS API
- Common authentication:
  - AWS credentials,
  - SigV4/SigV4a signed request.

##### 2.1.4.37.3 Critical Task-Level Distinction
- A JWT access token from Cognito is not automatically used to sign arbitrary AWS API calls.

##### 2.1.4.37.4 Bridge
- If user identity needs direct AWS access:
  - identity pool/STS can produce temporary AWS credentials.

#### 2.1.4.38 Authenticated Call Decision Tree

##### 2.1.4.38.1 Calling AWS Service From AWS SDK
- Obtain credentials via provider chain.
- Let SDK sign request.

##### 2.1.4.38.2 Calling AWS Service From CLI
- Configure profile/session.
- Let CLI sign request.

##### 2.1.4.38.3 Calling AWS Service With Raw HTTP
- Implement SigV4 correctly or use supported signing library.

##### 2.1.4.38.4 Browser/Mobile Needs Specific S3 Object
- Consider presigned URL instead of exposing AWS credentials.

##### 2.1.4.38.5 Workload Calls IAM-Protected API Gateway
- Use AWS credentials + SigV4.

##### 2.1.4.38.6 User Calls JWT-Protected API Gateway
- Use bearer access token instead; that belongs to 2.1.2.

#### 2.1.4.39 Common Exam Traps

##### 2.1.4.39.1 "AWS SDK Requires Manual SigV4 Code"
- False.
- SDK signs requests automatically.

##### 2.1.4.39.2 "Valid Credentials Alone Authorize the Operation"
- False.
- IAM/resource policies still control permissions.

##### 2.1.4.39.3 "SigV4 Encrypts the Request"
- False.
- TLS provides confidentiality.

##### 2.1.4.39.4 "Temporary Credentials Need No Session Token"
- False.
- Session token is required.

##### 2.1.4.39.5 "JWT Access Token Can Be Used as AWS Access Key"
- False.

##### 2.1.4.39.6 "Presigned URL Makes Object Public"
- False.
- It delegates a specific signed request for a limited period.

##### 2.1.4.39.7 "Presigned URL Can Grant More Than Signer's IAM Permissions"
- False.

##### 2.1.4.39.8 "401/403 Always Means Bad Password/Credentials"
- False.
- Could be:
  - signing failure,
  - expired credential,
  - missing permission,
  - resource-policy denial,
  depending on service/error.

##### 2.1.4.39.9 "Signature Mismatch Should Be Retried Forever"
- False.
- Fix signing/credential/clock/endpoint issue.

##### 2.1.4.39.10 "SigV4a Is Just a New Name for SigV4"
- False.
- SigV4a supports multi-Region verification.

#### 2.1.4.41 Task 2.1 Big Picture

##### 2.1.4.41.1 AWS Credential Branch

  `principal/workload`
  → 2.1.1 identity/federation
  → 2.1.3 credentials
  → **2.1.4 signed AWS request**
  → 2.1.6 IAM authorization
  → AWS resource

##### 2.1.4.41.2 Application Token Branch

  `principal`
  → 2.1.1 identity
  → 2.1.2 bearer token
  → application/API authorization

##### 2.1.4.41.3 Central Insight
- **AWS service authentication is generally credential + signature based; application API authentication is often bearer-token based.**

##### 2.1.4.42.1 Primary

- Do not expand into:

  - complete API Gateway authorization architecture.
- Focus on how authenticated AWS API calls are made.

#### 2.1.4.43 Exam-Level Knowledge Frame

##### 2.1.4.43.1 Normal AWS Call
- SDK/CLI gets credentials.
- SDK/CLI signs request with SigV4.
- Request goes over HTTPS.
- AWS verifies signature.
- IAM evaluates permissions.

##### 2.1.4.43.2 Temporary Credentials
- Must include session token.

##### 2.1.4.43.3 SigV4
- Region + service scoped.
- Authenticates and protects signed request integrity.
- Does not replace TLS.

##### 2.1.4.43.4 Presigned URL
- Delegates a specific signed request for a limited time.
- Common for S3.

##### 2.1.4.43.5 Debugging
- Authentication problems:
  - wrong credentials,
  - expired session,
  - missing session token,
  - wrong Region/service,
  - clock skew,
  - request mutation.
- Authorization problems:
  - valid principal,
  - insufficient policy permission.

##### 2.1.4.43.6 Final Principle
- **Use AWS SDKs/CLI to sign requests automatically; focus developer security work on correct credential source, least privilege, and correct service/Region configuration.**
