### 2.1.1 Use an identity provider to implement federated access

#### 2.1.1.1 Exam and Task Context

##### 2.1.1.1.1 Domain
- Domain 2 is **Security**, representing 26% of scored content.
- Task 2.1 is **Implement authentication and/or authorization for applications and AWS services**.
- Skill 2.1.1 is **Use an identity provider to implement federated access (for example, Amazon Cognito, IAM)**.

##### 2.1.1.1.2 Position Inside Task 2.1
- This skill establishes **identity and trust**.
- The later Task 2.1 skills continue the chain:
  - 2.1.2 → secure applications with bearer tokens.
  - 2.1.3 → configure programmatic AWS access.
  - 2.1.4 → make authenticated AWS calls.
  - 2.1.5 → assume IAM roles.
  - 2.1.6 → define IAM permissions.
  - 2.1.7 → fine-grained application authorization.
  - 2.1.8 → cross-service authentication.
- Therefore 2.1.1 should answer:

  **Where does identity come from, how is it trusted across a boundary, and how can that trusted identity become application or AWS access?**

#### 2.1.1.2 Core Mental Model

##### 2.1.1.2.1 Federation
- The identity already exists in an identity system.
- Instead of creating another permanent identity, the target system trusts identity proof from that system.

  `principal`
  → authenticates with → `Identity Provider (IdP)`
  → receives → `token / assertion`
  → target validates trust
  → `federated session`
  → application access or temporary AWS credentials

##### 2.1.1.2.2 Principle
- **Authenticate once with the appropriate identity authority; federate that trusted identity rather than distributing another long-lived credential.**

##### 2.1.1.2.3 Federation Is a Trust Relationship
- A token or assertion is useful only because the receiving system trusts its issuer.
- Trust must be explicitly configured.
- The receiver validates identity proof before creating a session.

#### 2.1.1.3 Principal, IdP, and Relying Party

##### 2.1.1.3.1 Principal
- Entity whose identity is being established.
- Can be:
  - human application user,
  - workforce user,
  - external workload/application.

##### 2.1.1.3.2 Identity Provider — IdP
- Authenticates the principal.
- Produces trusted identity information.

##### 2.1.1.3.3 Service Provider / Relying Party
- Trusts the IdP.
- Consumes the identity assertion/token.
- Depending on the architecture this can be:
  - Amazon Cognito,
  - AWS IAM/AWS STS,
  - an application.

#### 2.1.1.4 Authentication vs Authorization

##### 2.1.1.4.1 Authentication
- **Who are you?**
- The IdP verifies identity.

##### 2.1.1.4.2 Authorization
- **What may you do?**
- Enforced through mechanisms such as:
  - token scopes/claims,
  - application permissions,
  - IAM roles/policies,
  - resource policies.

##### 2.1.1.4.3 Critical Distinction
- Federation establishes trusted identity.
- It does not automatically grant broad access.
- Authorization must still apply least privilege.

#### 2.1.1.5 Why Federation

##### 2.1.1.5.1 Without Federation
- Create another account/identity.
- Issue another credential.
- Store and distribute it.
- Rotate/revoke/manage it independently.

##### 2.1.1.5.2 With Federation
- Existing identity remains authoritative.
- Target trusts the IdP.
- Access commonly uses short-lived:
  - tokens,
  - AWS role credentials.

##### 2.1.1.5.3 Security Benefit
- Reduces long-lived credentials.
- Centralizes authentication.
- Supports automatic expiration of temporary AWS sessions.

#### 2.1.1.6 Federation Standards

##### 2.1.1.6.1 SAML 2.0
- Federation standard commonly used for enterprise/workforce SSO.
- IdP authenticates user and supplies a SAML assertion.

##### 2.1.1.6.2 OpenID Connect — OIDC
- Identity layer built on OAuth 2.0.
- Common for:
  - modern web/mobile authentication,
  - external identity providers,
  - workload federation.

##### 2.1.1.6.3 Social Providers
- Cognito supports social IdPs such as:
  - Google,
  - Facebook,
  - Login with Amazon,
  - Sign in with Apple.

##### 2.1.1.6.4 Distinction
- SAML/OIDC = protocols.
- Cognito/Google/enterprise identity platform = identity providers or federation participants.

#### 2.1.1.7 Amazon Cognito — Two Different Jobs

##### 2.1.1.7.1 User Pools
- User directory and authentication service for web/mobile applications.
- From the application's perspective, a user pool is an OIDC IdP.
- Authenticates users and issues JWTs.

##### 2.1.1.7.2 Identity Pools
- Directory of federated identities used to obtain **temporary AWS credentials**.
- Accepts identities from supported IdPs.
- Maps access to IAM roles.

##### 2.1.1.7.3 Essential Exam Distinction

  `Cognito User Pool`
  → **application authentication / JWTs**

  `Cognito Identity Pool`
  → **federated identity / temporary AWS credentials**

#### 2.1.1.8 Cognito User Pool Federation

##### 2.1.1.8.1 External IdPs
- User pools can federate sign-in through:
  - social IdPs,
  - OIDC IdPs,
  - SAML IdPs.

##### 2.1.1.8.2 Flow

  `application`
  → `Cognito user pool`
  → redirect → `external IdP`
  → user authenticates
  → `IdP token/assertion`
  → `Cognito`
  → `Cognito JWTs`
  → `application`

##### 2.1.1.8.3 Cognito's Dual Role
- To external IdP:
  - Cognito is service provider/relying party.
- To application:
  - Cognito is the IdP.

##### 2.1.1.8.4 Benefit
- Application can standardize on Cognito-issued tokens even when authentication originates from different upstream IdPs.

#### 2.1.1.9 Federated User Attributes

##### 2.1.1.9.1 Claims
- External IdP sends identity claims.

##### 2.1.1.9.2 Attribute Mapping
- Cognito maps selected external claims into user-pool attributes.

##### 2.1.1.9.3 Result
- Cognito creates/maintains a federated user profile in the user pool.

##### 2.1.1.9.4 Developer Concern
- Know which upstream identity attribute becomes which application-facing attribute/claim.

#### 2.1.1.10 Cognito Managed Login

##### 2.1.1.10.1 Purpose
- Cognito can provide managed browser-based authentication pages.

##### 2.1.1.10.2 Federation
- It can redirect users to configured social, OIDC, or SAML IdPs.

##### 2.1.1.10.3 Benefit
- Application does not need to implement the complete browser federation protocol/UI itself.

#### 2.1.1.11 Cognito Identity Pools

##### 2.1.1.11.1 Purpose
- Provide temporary AWS credentials for application users.

##### 2.1.1.11.2 Identity Sources
- Cognito user pools.
- Social IdPs.
- OIDC providers.
- SAML providers.
- Developer-authenticated identities.
- Optional unauthenticated/guest identities.

##### 2.1.1.11.3 Result
- Federated identity is associated with IAM authorization and a temporary AWS role session.

#### 2.1.1.12 Identity Pool Authentication Flow

##### 2.1.1.12.1 Flow

  `user`
  → authenticate with → `IdP`
  → `token/assertion`
  → `Cognito identity pool`
  → identity/role mapping
  → `AWS STS`
  → `temporary AWS credentials`
  → `AWS service`

##### 2.1.1.12.2 Temporary Credentials
- Include:
  - access key ID,
  - secret access key,
  - session token,
  - expiration.

##### 2.1.1.12.3 Authorization
- IAM role/policies define what those credentials can do.

#### 2.1.1.13 User Pool + Identity Pool Together

##### 2.1.1.13.1 Complete Pattern

  `user`
  → `Cognito user pool`
  → `JWT`
  → `Cognito identity pool`
  → `IAM role / STS`
  → `temporary AWS credentials`
  → `AWS service`

##### 2.1.1.13.2 Mental Model
- User pool:
  - **Who is the application user?**
- Identity pool:
  - **Which temporary AWS permissions can that identity receive?**

##### 2.1.1.13.3 Important Rule
- User-pool authentication does not automatically produce AWS API credentials.

#### 2.1.1.14 Guest / Unauthenticated Identities

##### 2.1.1.14.1 Capability
- Cognito identity pools can optionally issue temporary AWS credentials to unauthenticated users.

##### 2.1.1.14.2 Use Case
- Guest application access to narrowly scoped AWS resources.

##### 2.1.1.14.3 Security
- Guest-role permissions must be tightly restricted.

##### 2.1.1.14.4 Distinction
- "Unauthenticated user" does not mean "no AWS session."
- Identity pool can create a temporary session under the unauthenticated IAM role.

#### 2.1.1.15 AWS STS

##### 2.1.1.15.1 Purpose
- AWS Security Token Service issues temporary AWS security credentials.

##### 2.1.1.15.2 Federation Role
- Trusted external identity can become an IAM role session rather than a permanent IAM user.

##### 2.1.1.15.3 Security Property
- Temporary credentials:
  - expire,
  - carry role/session permissions,
  - avoid permanent access keys.

#### 2.1.1.16 IAM Identity Providers

##### 2.1.1.16.1 Direct Federation
- IAM can establish direct trust with external:
  - SAML 2.0 IdPs,
  - OIDC IdPs.

##### 2.1.1.16.2 IAM IdP Entity
- Represents the external provider and establishes trust between AWS account and external identity system.

##### 2.1.1.16.3 Result
- Federated principal can obtain a temporary IAM role session without creation of a permanent IAM user.

#### 2.1.1.17 Direct OIDC Federation

##### 2.1.1.17.1 Flow

  `external workload/user`
  → `OIDC IdP`
  → `OIDC token`
  → STS `AssumeRoleWithWebIdentity`
  → `IAM role session`
  → temporary AWS credentials

##### 2.1.1.17.2 Strong Use Case
- Workloads outside AWS that need AWS API access.

##### 2.1.1.17.3 Security Principle
- Prefer dynamically obtained temporary credentials over storing long-lived AWS access keys outside AWS.

#### 2.1.1.18 Direct SAML Federation

##### 2.1.1.18.1 Flow

  `workforce user`
  → `enterprise SAML IdP`
  → `SAML assertion`
  → STS `AssumeRoleWithSAML`
  → `IAM role session`

##### 2.1.1.18.2 Benefit
- AWS access without creating an IAM user for every federated employee.

#### 2.1.1.19 Cognito vs IAM Federation

##### 2.1.1.19.1 Cognito
- Primarily application-user identity.
- Web/mobile authentication.
- User pools normalize external identities into Cognito JWTs.
- Identity pools can exchange trusted identity for AWS credentials.

##### 2.1.1.19.2 IAM Federation
- Direct trust between AWS and SAML/OIDC IdP.
- Useful when the goal is federated access to IAM roles/AWS resources.

##### 2.1.1.19.3 Selection
- Customer/mobile/web identity → Cognito.
- External OIDC workload → IAM OIDC federation.
- Direct enterprise SAML role federation → IAM SAML federation.

#### 2.1.1.20 IAM Identity Center Context

##### 2.1.1.20.1 Workforce Access
- Current AWS guidance recommends IAM Identity Center for centralized workforce access to multiple AWS accounts/applications.

##### 2.1.1.20.2 External Identity Source
- IAM Identity Center can federate workforce identities from an external identity provider.

##### 2.1.1.20.3 Why It Matters Here
- "Federated access" has different architectural forms:
  - application/customer federation → Cognito,
  - workforce federation → IAM Identity Center,
  - direct workload/single-account federation → IAM roles + OIDC/SAML.

##### 2.1.1.20.4 Scope
- Recognition only here; do not turn this skill into IAM Identity Center administration.

#### 2.1.1.21 Three Identity Categories

##### 2.1.1.21.1 Customer / Application Identity
- User of a web/mobile product.
- Typical AWS mechanism:
  - Cognito user pool,
  - external IdP federation,
  - identity pool if direct AWS credentials are required.

##### 2.1.1.21.2 Workforce Identity
- Employee/contractor/operator.
- Typical AWS mechanism:
  - IAM Identity Center + organizational identity source.

##### 2.1.1.21.3 Workload Identity
- Software/process outside AWS.
- Typical mechanism:
  - OIDC federation to IAM role,
  - STS temporary credentials.

##### 2.1.1.21.4 First Decision
- Ask:

  **Who is the principal?**

#### 2.1.1.22 Identity Tokens vs AWS Credentials

##### 2.1.1.22.1 Application Token
- Represents authenticated user/session information.
- Cognito user pools issue JWTs.

##### 2.1.1.22.2 AWS Credentials
- Used to sign AWS API requests.

##### 2.1.1.22.3 Critical Distinction
- An IdP JWT is **not** an AWS access key.

##### 2.1.1.22.4 Bridge
- Cognito identity pool or direct STS federation can turn trusted identity proof into temporary AWS credentials.

#### 2.1.1.23 ID Token vs Access Token

##### 2.1.1.23.1 ID Token
- Carries claims about authenticated identity.

##### 2.1.1.23.2 Access Token
- Represents authorization to access protected APIs/resources according to scopes/claims.

##### 2.1.1.23.3 Boundary
- Recognize the distinction here.
- Bearer-token mechanics/security belong primarily to Skill 2.1.2.

#### 2.1.1.24 Role Trust Policy

##### 2.1.1.24.1 Question It Answers
- **Who may assume this role?**

##### 2.1.1.24.2 Federation
- Trust can identify:
  - SAML provider,
  - OIDC provider,
  - Cognito federation principal.

##### 2.1.1.24.3 Conditions
- Trust can be restricted using provider claims/conditions such as:
  - audience,
  - subject,
  - identity pool identifier,
  depending on mechanism.

##### 2.1.1.24.4 Distinction
- Trust policy → who may assume.
- Permissions policy → what assumed identity may do.

#### 2.1.1.25 Claims

##### 2.1.1.25.1 Meaning
- Identity attributes carried in token/assertion.

##### 2.1.1.25.2 Examples
- subject,
  - email,
  - groups,
  - issuer,
  - audience.

##### 2.1.1.25.3 Uses
- Identify principal.
- Map application profile.
- Select roles.
- Support authorization decisions.

##### 2.1.1.25.4 Security
- Never trust claims before validating the issuer/token/assertion.

#### 2.1.1.26 Application Architecture Patterns

##### 2.1.1.26.1 API-Only Application

  `user`
  → `Cognito user pool / external IdP`
  → `JWT`
  → `application/API`
  → backend resources

- Client does not require AWS credentials.

##### 2.1.1.26.2 Direct AWS Resource Access

  `user`
  → `Cognito user pool / external IdP`
  → token
  → `Cognito identity pool`
  → temporary IAM credentials
  → `S3 / other AWS API`

##### 2.1.1.26.3 Decision
- User only calls your protected API → token-based application authentication can be sufficient.
- Client directly calls AWS APIs → temporary AWS credentials are needed.

#### 2.1.1.27 External Workload Pattern

##### 2.1.1.27.1 Avoid

  `external CI/workload`
  → stored permanent AWS access key
  → AWS

##### 2.1.1.27.2 Prefer

  `external workload`
  → OIDC provider
  → short-lived token
  → STS
  → temporary role credentials
  → AWS

##### 2.1.1.27.3 Reason
- Removes the need to distribute a long-lived AWS secret to the external system.

#### 2.1.1.28 Federation Decision Tree

##### 2.1.1.28.1 Web/Mobile Users Need Application Sign-In
- → Cognito user pool.

##### 2.1.1.28.2 Existing Google/Apple/Enterprise Users Need App Sign-In
- → federate external IdP into Cognito user pool.

##### 2.1.1.28.3 App User Needs Direct AWS Access
- → Cognito identity pool → temporary AWS credentials.

##### 2.1.1.28.4 Guest Needs Narrow AWS Access
- → identity-pool unauthenticated role, if requirements allow.

##### 2.1.1.28.5 External OIDC Workload Needs AWS Access
- → IAM OIDC provider + STS role federation.

##### 2.1.1.28.6 Workforce Needs Centralized Multi-Account AWS Access
- → IAM Identity Center.

##### 2.1.1.28.7 Direct SAML Federation Selected
- → IAM SAML provider + IAM role.

#### 2.1.1.29 Security Rules

##### 2.1.1.29.1 Validate Issuer
- Trust only configured IdPs.

##### 2.1.1.29.2 Validate Audience
- Identity proof intended for another application should not be accepted blindly.

##### 2.1.1.29.3 Validate Expiration
- Expired proof must not establish a new trusted session.

##### 2.1.1.29.4 Least Privilege
- Federated IAM roles must grant only required permissions.

##### 2.1.1.29.5 Prefer Temporary Credentials
- Do not replace federation with embedded IAM-user access keys.

#### 2.1.1.30 Common Exam Traps

##### 2.1.1.30.1 Create IAM Users for Mobile Users
- Wrong.
- Use application identity/federation such as Cognito.

##### 2.1.1.30.2 Store AWS Access Keys in Browser/Mobile App
- Wrong.
- Use federation and temporary credentials.

##### 2.1.1.30.3 User Pool = AWS Credentials
- Wrong.
- User pool → authentication/JWTs.
- Identity pool → temporary AWS credentials.

##### 2.1.1.30.4 Identity Pool = User Directory
- Wrong.
- User pool is the application user directory.
- Identity pool federates identities to AWS credentials.

##### 2.1.1.30.5 Federation Completes Authorization
- Wrong.
- IAM/application permissions still determine allowed actions.

##### 2.1.1.30.6 OIDC Token = AWS Credential
- Wrong.
- OIDC token is identity proof.
- STS produces AWS temporary credentials.

##### 2.1.1.30.7 Temporary Means Unlimited
- Wrong.
- Temporary credentials are constrained by IAM role/session permissions.

##### 2.1.1.30.8 IAM User for External CI
- Poor default.
- Prefer OIDC federation and temporary role credentials.

##### 2.1.1.30.9 Cognito for Employee AWS Console Access
- Wrong default mental model.
- Current AWS guidance favors IAM Identity Center for workforce access.

#### 2.1.1.34 Exam-Level Knowledge Frame

##### 2.1.1.34.1 Federation
- Existing identity crosses a trust boundary.
- Avoid duplicate permanent identities/static credentials.

##### 2.1.1.34.2 Cognito
- User pool → authenticate app users, federate IdPs, issue JWTs.
- Identity pool → federate identities, map IAM roles, obtain temporary AWS credentials.

##### 2.1.1.34.3 IAM/STS
- IAM trusts OIDC/SAML provider.
- Federated principal obtains role session.
- STS supplies temporary credentials.

##### 2.1.1.34.4 Choose by Principal
- Customer/app user → Cognito.
- Workforce → IAM Identity Center context.
- External workload → OIDC/IAM role federation.

##### 2.1.1.34.5 Final Principle
- **Federation establishes trusted identity; authorization determines what that identity may do.**
