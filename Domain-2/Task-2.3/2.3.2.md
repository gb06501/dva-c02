### 2.3.2 Encrypt environment variables that contain sensitive data

#### 2.3.2.1 Exam and Task Context

##### 2.3.2.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.3 is **Manage sensitive data in application code**.
- Skill 2.3.2 is **Encrypt environment variables that contain sensitive data**.
- 2.3.1 established classification:
  - identify which values are sensitive,
  - determine their handling requirements.
- 2.3.2 now asks how sensitive configuration values are protected when supplied to application runtime through environment variables.

##### 2.3.2.1.2 Core Question
- **If an application needs a sensitive value at runtime, how should that value be protected at rest, in transit, and from unauthorized viewers?**

#### 2.3.2.2 Core Mental Model

For AWS Lambda:

`environment variable`
→ stored in Lambda configuration
→ encrypted at rest by Lambda
→ optionally protected with customer managed KMS key
→ decrypted/available to runtime when function executes

For stronger protection:

`sensitive value`
→ client-side encryption before configuration
→ encrypted value stored as environment variable
→ function uses `kms:Decrypt`
→ plaintext exists only inside authorized runtime

But the first architectural decision is:

**Is an environment variable actually the correct place for this secret?**

For database passwords, API keys, tokens, and similar secrets, AWS recommends using **AWS Secrets Manager** instead of ordinary Lambda environment variables.

#### 2.3.2.3 Environment Variables

##### 2.3.2.3.1 Purpose
- Runtime configuration passed to an application/function.
- Typical non-secret examples:
  - Region,
  - table name,
  - queue URL,
  - feature flag,
  - environment name.

##### 2.3.2.3.2 Sensitive Examples
- database password,
- API key,
- OAuth client secret,
- authorization token,
- encryption password,
- private endpoint credential.

##### 2.3.2.3.3 Classification Connection
- 2.3.1 determines whether a value is sensitive.
- 2.3.2 determines how environment-variable storage should be protected.

#### 2.3.2.4 Configuration vs Secret

A useful distinction:

`CONFIGURATION`
→ application behavior/location
→ table name, timeout, stage, Region

`SECRET`
→ grants access or authority
→ password, token, API key, private credential

##### 2.3.2.4.1 Exam Principle
- Environment variables are fine for configuration.
- For true secrets, prefer a secret-management service when supported.

#### 2.3.2.5 AWS Lambda Environment Variables

##### 2.3.2.5.1 Lambda Support
- Lambda functions can receive environment variables through function configuration.

##### 2.3.2.5.2 Configuration Methods
- AWS Management Console.
- AWS CLI.
- AWS SDK.
- AWS SAM.
- AWS CloudFormation.

##### 2.3.2.5.3 Runtime
- Function retrieves the variable using the language's normal environment-variable API.

Examples:
- Node.js → `process.env`
- Python → `os.environ`
- Java → `System.getenv`

#### 2.3.2.6 Lambda Encrypts Environment Variables at Rest

##### 2.3.2.6.1 Default Behavior
- AWS Lambda **always encrypts environment variables at rest**.

##### 2.3.2.6.2 Default Key
- By default, Lambda uses an AWS managed KMS key.

##### 2.3.2.6.3 Consequence
- You do not need to implement custom encryption merely to obtain basic at-rest encryption for Lambda environment variables.

##### 2.3.2.6.4 Exam Trap
**Lambda environment variables are not stored unencrypted by default.**

#### 2.3.2.7 AWS Managed Key

##### 2.3.2.7.1 Default
- Lambda uses an AWS managed key when you do not select a customer managed key.

##### 2.3.2.7.2 Benefits
- No additional KMS configuration.
- AWS manages key permissions/lifecycle for this use case.
- No direct KMS charges for using the default Lambda AWS managed key.

##### 2.3.2.7.3 Limitation
- Less customer control over:
  - key policy,
  - access separation,
  - rotation configuration,
  - audit/administrative boundaries.

#### 2.3.2.8 Customer Managed KMS Key

##### 2.3.2.8.1 Why Use One?
Choose a customer managed key when requirements call for:
- explicit key policy control,
- customer-controlled lifecycle,
- separation of duties,
- tighter control over who can view/manage environment variables,
- organizational compliance requirements.

##### 2.3.2.8.2 Flow

`Lambda environment variables`
→ server-side encryption
→ customer managed KMS key

##### 2.3.2.8.3 Benefit
- Users without permission to use the KMS key can be prevented from viewing encrypted environment variables in plaintext.

#### 2.3.2.9 KMS Key Permissions

When configuring a customer managed KMS key, relevant permissions can include:

- `kms:ListAliases`
- `kms:CreateGrant`
- `kms:Encrypt`
- `kms:Decrypt`

##### 2.3.2.9.1 Configure Key
- Principal configuring Lambda with the key may need:
  - `kms:CreateGrant`
  - `kms:Encrypt`

##### 2.3.2.9.2 View/Manage Environment Variables
- `kms:Decrypt` can be required to view/manage variables encrypted with the customer managed key.

##### 2.3.2.9.3 Principle
- Key usage must follow least privilege.

#### 2.3.2.10 Lambda Uses a KMS Grant

##### 2.3.2.10.1 Service Integration
- When a customer managed KMS key is configured, Lambda uses permissions to create a KMS grant.

##### 2.3.2.10.2 Purpose
- The grant allows Lambda to use the key for the function's encryption workflow.

##### 2.3.2.10.3 Connection
- KMS grants were introduced in 2.2.4.

#### 2.3.2.11 At-Rest Encryption vs Visibility

##### 2.3.2.11.1 At Rest
- Stored Lambda configuration is encrypted.

##### 2.3.2.11.2 Authorized Management User
- A sufficiently authorized user can still request/view the environment variable in plaintext through supported management interfaces.

##### 2.3.2.11.3 Therefore
**Encryption at rest does not mean administrators can never see the value.**

##### 2.3.2.11.4 Customer Managed Key
- Can provide an additional authorization boundary over who may decrypt/view environment variables.

#### 2.3.2.12 Denying Environment Variable Visibility

##### 2.3.2.12.1 Pattern
- Explicitly deny `kms:Decrypt` for users who should manage Lambda but must not view sensitive environment-variable values.

##### 2.3.2.12.2 Result
- User may retain some Lambda management permissions while lacking decryption access.

##### 2.3.2.12.3 Security Principle
- Separate:
  - application/function administration,
  - secret plaintext access.

#### 2.3.2.13 Encryption in Transit — Management Plane

##### 2.3.2.13.1 Lambda API
- Lambda management/API communication uses HTTPS/TLS.

##### 2.3.2.13.2 Meaning
- Values sent to Lambda are protected on the network transport.

##### 2.3.2.13.3 Additional Protection
- Lambda console also provides client-side encryption helpers for environment-variable values that need another layer of protection before being sent/stored.

#### 2.3.2.14 Client-Side Encryption Helper

##### 2.3.2.14.1 Purpose
- Encrypt a sensitive environment-variable value client-side.

##### 2.3.2.14.2 Flow

`plaintext value`
→ Lambda console encryption helper
→ KMS customer managed key
→ ciphertext environment variable
→ Lambda stores ciphertext

At runtime:

`ciphertext environment variable`
→ function calls KMS `Decrypt`
→ plaintext secret

##### 2.3.2.14.3 Important
- This is different from Lambda's ordinary server-side at-rest encryption.

#### 2.3.2.15 Server-Side vs Client-Side for Lambda Env Vars

`SERVER-SIDE`
→ Lambda stores environment variable encrypted at rest
→ Lambda/runtime can provide plaintext to function

`CLIENT-SIDE HELPER`
→ value itself is stored as ciphertext
→ function code must decrypt it

##### 2.3.2.15.1 Connection
- This directly applies the client/server-side distinction from 2.2.3.

#### 2.3.2.16 Client-Side Decryption Permission

##### 2.3.2.16.1 Function Role
- Function's execution role needs:
  - `kms:Decrypt`
for the key used to encrypt the value client-side.

##### 2.3.2.16.2 Runtime Code
- Function must explicitly call/delegate decryption before using the value.

##### 2.3.2.16.3 Trade-Off
- Stronger plaintext boundary.
- More code and KMS runtime dependency.

#### 2.3.2.17 When Client-Side Env Encryption Fits

Use when requirement says:
- sensitive value should remain encrypted in Lambda configuration views,
- value should be encrypted before Lambda receives/stores it,
- only runtime execution role should be able to decrypt,
- administrators should not automatically see plaintext.

##### 2.3.2.17.1 But
For true secrets, still consider whether Secrets Manager is the better architecture.

#### 2.3.2.18 Secrets Manager Is Usually Better for Secrets

##### 2.3.2.18.1 AWS Guidance
- AWS recommends **AWS Secrets Manager** instead of Lambda environment variables for:
  - database credentials,
  - API keys,
  - authorization tokens,
  - other sensitive information.

##### 2.3.2.18.2 Why
Secrets Manager is built for:
- encrypted secret storage,
- IAM-controlled retrieval,
- secret rotation,
- centralized lifecycle management,
- runtime retrieval.

##### 2.3.2.18.3 Connection
- Skill 2.3.3 covers secret-management services in depth.

#### 2.3.2.19 Environment Variable vs Secrets Manager

| Requirement | Environment Variable | Secrets Manager |
| --- | --- | --- |
| Ordinary configuration | Strong fit | Usually unnecessary |
| Small static sensitive config | Possible | Often better |
| Database credential | Avoid if possible | Strong fit |
| API key/token | Avoid if possible | Strong fit |
| Automatic rotation | No native env-var secret rotation model | Supported for secrets |
| Runtime retrieval | Automatic env var | API/extension/cache |
| Separate secret lifecycle | Weak | Strong |
| Centralized secret management | Weak | Strong |

#### 2.3.2.20 SSM Parameter Store Context

##### 2.3.2.20.1 SecureString
- Systems Manager Parameter Store supports encrypted `SecureString` parameters backed by AWS KMS.

##### 2.3.2.20.2 Use
- Secure configuration values and parameters.

##### 2.3.2.20.3 Decision
- Parameter Store can be a good fit for encrypted configuration.
- Secrets Manager is stronger when secret-specific lifecycle/rotation features are required.

##### 2.3.2.20.4 Boundary
- Detailed comparison belongs in 2.3.3.

#### 2.3.2.21 Infrastructure as Code

##### 2.3.2.21.1 Risk
Defining plaintext secrets directly inside:
- SAM templates,
- CloudFormation templates,
- Terraform configuration,
- source-controlled deployment files
can expose them.

##### 2.3.2.21.2 Better
- Use references to managed secrets/parameters.
- Avoid hard-coded secret values in templates.

##### 2.3.2.21.3 Principle
**Encrypting at runtime does not undo source-control exposure.**

#### 2.3.2.22 CloudFormation Dynamic References — Context

##### 2.3.2.22.1 Purpose
- CloudFormation can reference values from supported secret stores rather than embedding plaintext in templates.

##### 2.3.2.22.2 Examples
- Secrets Manager.
- Systems Manager Parameter Store.

##### 2.3.2.22.3 Benefit
- Template stores reference, not raw secret value.

##### 2.3.2.22.4 Scope
- Detailed secret retrieval belongs to 2.3.3.

#### 2.3.2.23 SAM Environment Variables

##### 2.3.2.23.1 Configuration
- AWS SAM can define Lambda environment variables.

##### 2.3.2.23.2 Risk
- Plaintext secret inside SAM template can enter:
  - source control,
  - CI/CD artifacts,
  - deployment histories.

##### 2.3.2.23.3 Rule
- Treat IaC source as a potential disclosure path.

#### 2.3.2.24 Runtime Retrieval

##### 2.3.2.24.1 Environment Variable
- Available immediately inside process environment.

##### 2.3.2.24.2 Secret Store
- Retrieved at runtime through:
  - AWS SDK,
  - supported Lambda extension,
  - library/caching layer.

##### 2.3.2.24.3 Trade-Off
Environment variable:
- simplest,
- static for function version/configuration.

Secret store:
- extra retrieval step,
- stronger centralized secret lifecycle.

#### 2.3.2.25 Published Lambda Versions

##### 2.3.2.25.1 Versioning
- Environment variables are part of a published Lambda version's immutable configuration.

##### 2.3.2.25.2 Consequence
- Changing an environment variable affects unpublished configuration and requires publishing/deploying a new version when immutable versioned behavior is required.

##### 2.3.2.25.3 Secret Rotation
- This is another reason externally managed secrets can be preferable: secret value can rotate independently of function deployment.

#### 2.3.2.26 Rotation

##### 2.3.2.26.1 Environment Variable
- Updating a secret stored directly as an environment variable generally means updating function configuration.

##### 2.3.2.26.2 Secrets Manager
- Secret can rotate independently and application retrieves current value.

##### 2.3.2.26.3 Exam Clue
**Secret must rotate regularly without redeploying function**
→ Secrets Manager is generally superior.

#### 2.3.2.27 Logging

##### 2.3.2.27.1 Major Risk
Even encrypted environment variables become plaintext inside the process when used.

##### 2.3.2.27.2 Never Log
- entire environment,
- secret variable values,
- decrypted client-side values,
- tokens,
- passwords.

##### 2.3.2.27.3 Connection
- 2.3.4 and 2.3.5 address sanitization/masking.

#### 2.3.2.28 Error Handling

##### 2.3.2.28.1 Bad Pattern
Exception includes:
- configuration dump,
- secret value,
- Authorization header,
- decrypted environment variable.

##### 2.3.2.28.2 Better
Log:
- variable name,
- retrieval/decryption failure,
- request/correlation ID,
without the sensitive value.

#### 2.3.2.29 Lambda Console Visibility

##### 2.3.2.29.1 Sensitive Area
- Users with permissions may view function configuration.

##### 2.3.2.29.2 Customer Managed Key
- KMS authorization can limit who may decrypt/view values.

##### 2.3.2.29.3 Client-Side Helper
- Stores ciphertext such that plaintext is not simply displayed as the original configured value.

#### 2.3.2.30 Execution Role vs Deployment/Admin Role

##### 2.3.2.30.1 Execution Role
- Runtime identity of Lambda.
- May need secret/KMS retrieval permissions.

##### 2.3.2.30.2 Deployment/Admin Role
- Configures function.

##### 2.3.2.30.3 Security Design
- These principals do not need identical access.

##### 2.3.2.30.4 Example
Deployment role:
- update function configuration.

Execution role:
- `kms:Decrypt` / `secretsmanager:GetSecretValue`.

This supports separation of duties.

#### 2.3.2.31 KMS Key Policy

##### 2.3.2.31.1 Customer Managed Key
- Key policy must permit intended principals/use.

##### 2.3.2.31.2 Runtime Client-Side Decryption
- execution role needs authorization.

##### 2.3.2.31.3 Management
- users viewing/managing environment variables may require KMS decrypt rights.

##### 2.3.2.31.4 Connection
- KMS authorization was covered in 2.2.4.

#### 2.3.2.32 CloudTrail

##### 2.3.2.32.1 KMS
- Customer managed key usage can be audited through CloudTrail.

##### 2.3.2.32.2 Benefit
- Visibility into operations such as:
  - `Decrypt`,
  - `DescribeKey`,
  - `GenerateDataKey`,
depending on Lambda/KMS workflow.

##### 2.3.2.32.3 Security
- Audit key usage when sensitive configuration requires stronger controls.

#### 2.3.2.33 CloudWatch Logs

##### 2.3.2.33.1 Separate Data Store
- CloudWatch Logs are not the same storage boundary as Lambda configuration.

##### 2.3.2.33.2 Consequence
- Accidentally logging a secret creates a new sensitive-data copy.

##### 2.3.2.33.3 Encryption
- CloudWatch Logs has its own encryption controls.
- But encryption does not justify logging secrets.

#### 2.3.2.34 Environment Variable Size / Suitability

##### 2.3.2.34.1 Configuration Mechanism
- Environment variables are intended for relatively small configuration values.

##### 2.3.2.34.2 Not a Secret Database
- Do not use environment variables as a general repository for many credentials or large secret documents.

##### 2.3.2.34.3 Principle
- Choose storage mechanism based on data purpose and lifecycle.

#### 2.3.2.35 Plaintext in Memory

##### 2.3.2.35.1 Important
- An application that uses a secret eventually needs plaintext or usable credential material in memory.

##### 2.3.2.35.2 Encryption Goal
- Minimize where and how long plaintext exists.

##### 2.3.2.35.3 Rule
- At-rest encryption protects storage, not memory after authorized decryption.

#### 2.3.2.36 Lambda SnapStart / Other Runtime Data

##### 2.3.2.36.1 Broader Encryption Context
- Lambda encrypts multiple function-related artifacts at rest, not only environment variables.

##### 2.3.2.36.2 Skill Focus
- For 2.3.2, remain focused on sensitive environment-variable configuration rather than general Lambda storage security.

#### 2.3.2.37 Environment Variables in Containers

##### 2.3.2.37.1 Generic Risk
- ECS/EKS/container environments can also expose secrets through process environment.

##### 2.3.2.37.2 Better Pattern
- Integrate with managed secret stores and workload IAM roles rather than hard-coding secrets into container definitions/images.

##### 2.3.2.37.3 Scope
- The exam skill is best grounded in Lambda because AWS documentation explicitly provides KMS environment-variable encryption and client-side helpers.

#### 2.3.2.38 Secrets in Container Images

##### 2.3.2.38.1 Bad Pattern
- Bake secrets into:
  - Dockerfile,
  - image layer,
  - source code,
  - build argument that remains in image history.

##### 2.3.2.38.2 Better
- Inject/retrieve at runtime through approved secret-management mechanism.

##### 2.3.2.38.3 Principle
- A secret encrypted as an environment variable later is still compromised if it was already embedded in the image/source.

#### 2.3.2.39 Decision Flow

##### 2.3.2.39.1 Step 1 — Is Value Sensitive?
- If no → normal environment variable.
- If yes → continue.

##### 2.3.2.39.2 Step 2 — Is It a True Secret?
Examples:
- database password,
- API key,
- token.

If yes:
→ prefer Secrets Manager or appropriate secret store.

##### 2.3.2.39.3 Step 3 — Must It Remain an Environment Variable?
If yes:
→ Lambda already encrypts it at rest.

##### 2.3.2.39.4 Step 4 — Need Customer Control?
If yes:
→ use customer managed KMS key.

##### 2.3.2.39.5 Step 5 — Must Value Be Encrypted Before Lambda Stores It?
If yes:
→ use client-side encryption helper / explicit application-side encryption.

##### 2.3.2.39.6 Step 6 — Runtime Decryption
→ execution role needs `kms:Decrypt`.

##### 2.3.2.39.7 Step 7 — Prevent Leakage
- no logging,
- no source-control plaintext,
- no debug dumps,
- least-privilege permissions.

#### 2.3.2.40 Exam Scenario Mapping

##### 2.3.2.40.1 "Lambda env vars need encryption at rest"
- Lambda already encrypts them.
- Customer managed KMS key only if additional control is required.

##### 2.3.2.40.2 "Only selected administrators may view env var plaintext"
- customer managed KMS key + KMS permissions.

##### 2.3.2.40.3 "Encrypt value before Lambda stores it"
- client-side encryption helper.

##### 2.3.2.40.4 "Database password stored in Lambda env var"
- AWS recommends Secrets Manager instead.

##### 2.3.2.40.5 "Secret rotates without redeploying function"
- Secrets Manager.

##### 2.3.2.40.6 "Runtime needs to decrypt client-encrypted variable"
- Lambda execution role needs `kms:Decrypt`.

#### 2.3.2.41 Common Exam Traps

##### 2.3.2.41.1 "Lambda Env Vars Are Plaintext at Rest by Default"
- False.

##### 2.3.2.41.2 "Customer Managed Key Is Required for Any Lambda Env Var Encryption"
- False.
- Lambda uses AWS managed KMS encryption by default.

##### 2.3.2.41.3 "At-Rest Encryption Means Nobody Can View Value"
- False.
- Authorized users/runtime can decrypt/view it.

##### 2.3.2.41.4 "Client-Side Encryption Helper Is Same as Default Lambda Encryption"
- False.

##### 2.3.2.41.5 "TLS Alone Solves Stored Environment Variable Security"
- False.

##### 2.3.2.41.6 "Environment Variables Are Best Place for Database Passwords"
- False.
- AWS recommends Secrets Manager.

##### 2.3.2.41.7 "Putting Secret in CloudFormation Template Is Safe Because Lambda Encrypts It Later"
- False.
- Source/template exposure already occurred.

##### 2.3.2.41.8 "Execution Role and Deployment Role Need Same KMS Permissions"
- False.

##### 2.3.2.41.9 "Logging Decrypted Secret Is Safe Because CloudWatch Is Encrypted"
- False.

##### 2.3.2.41.10 "Encrypting Env Var Solves Secret Rotation"
- False.
- Encryption and lifecycle/rotation are different problems.

#### 2.3.2.45 Exam-Level Knowledge Frame

Know these cold:

**Lambda environment variables**
→ encrypted at rest by default.

**Default encryption**
→ AWS managed KMS key.

**Customer managed KMS key**
→ more control over key policy/lifecycle and who may decrypt/view configuration.

**Client-side helper**
→ encrypt value before Lambda stores it; function decrypts at runtime.

**Runtime client-side decryption**
→ execution role needs `kms:Decrypt`.

**Database credentials/API keys/tokens**
→ prefer Secrets Manager rather than Lambda environment variables.

**Environment variable encryption**
→ protects storage, not logs, source code, templates, or runtime memory.

**Encryption**
→ does not solve secret rotation.

Fastest exam discriminator:

**Ordinary config?**
→ environment variable.

**Sensitive env var but must stay env var?**
→ Lambda encryption + customer managed KMS key if extra control needed.

**True rotating secret?**
→ Secrets Manager.

Final principle:

**Lambda already encrypts environment variables at rest. Use a customer managed KMS key when you need tighter authorization/control, use client-side encryption only when the plaintext boundary requires it, and prefer a dedicated secret-management service for credentials and other true secrets.**
