### 2.3.5 Implement application-level data masking and sanitization

#### 2.3.5.1 Exam and Task Context

##### 2.3.5.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.3 is **Manage sensitive data in application code**.
- Skill 2.3.5 is **Implement application-level data masking and sanitization**.
- The exam guide explicitly separates:
  - 2.3.4 → **Sanitize sensitive data**
  - 2.3.5 → **Implement application-level data masking and sanitization**
- Therefore 2.3.5 is the implementation-oriented continuation of 2.3.4.

##### 2.3.5.1.2 Core Question
- **How should application code transform sensitive fields so each destination receives only the representation it actually needs?**

#### 2.3.5.2 Core Mental Model

`INTERNAL DATA`
→ identify destination
→ select permitted fields
→ apply field-level transformation
→ emit sanitized representation

Typical transformations:

`KEEP`
→ destination needs full value

`OMIT`
→ destination does not need field

`ERASE`
→ replace sensitive value irreversibly

`PARTIAL MASK`
→ expose only useful fragment

`ENCRYPT`
→ original value must remain recoverable by authorized consumer

The implementation principle is:

**Create a safe representation before serialization, logging, returning, or publishing the data.**

#### 2.3.5.3 Application-Level Means Code Owns the Decision

AWS services provide:
- encryption,
- logging,
- request validation,
- transport,
- storage.

But the application understands:
- which field is a password,
- which caller needs an email address,
- whether support needs only the last four digits,
- which event consumer needs which customer attributes.

Therefore masking often belongs close to the application's data model and boundary logic.

#### 2.3.5.4 Field-Level Policy

Example internal object:

```text
customer
├── id
├── name
├── email
├── ssn
├── paymentCard
└── authToken
```

Possible API representation:

```text
id
name
masked email
masked paymentCard
```

Removed:
- SSN
- auth token

Possible operational log:

```text
customerId
operation
requestId
```

Removed:
- name
- email
- SSN
- card
- token

Same source object, different safe representations.

#### 2.3.5.5 Prefer Explicit Output Models

Bad:

`database/domain object`
→ serialize directly

Better:

`database/domain object`
→ explicit response/log/event model
→ sanitize/mask
→ serialize

Benefits:
- allowlist of fields,
- easier review,
- fewer accidental disclosures,
- destination-specific contracts.

#### 2.3.5.6 Omit Before Masking

Ask first:

**Does the destination need this field at all?**

If no:
→ omit it.

Only if some representation is required:
→ mask it.

This reduces unnecessary data copies.

#### 2.3.5.7 Full Erasure

Input:

```json
{
  "username": "alice",
  "password": "SuperSecret"
}
```

Safe representation:

```json
{
  "username": "alice",
  "password": "*****"
}
```

Or preferably, if unnecessary:

```json
{
  "username": "alice"
}
```

##### 2.3.5.7.1 Property
- Irreversible in the sanitized representation.

##### 2.3.5.7.2 Use
- password,
- access token,
- API key,
- secret,
- other values that destination must never receive.

#### 2.3.5.8 Partial Masking

Examples:

`4111111111111111`
→ `************1111`

`jane@example.com`
→ `j***@example.com`

`123-45-6789`
→ `***-**-6789`

##### 2.3.5.8.1 Purpose
- retain recognition/support value,
- hide unnecessary sensitive portion.

##### 2.3.5.8.2 Important
- Masking format is a business/security policy decision.
- AWS does not define one universal format for every data class.

#### 2.3.5.9 Dynamic Masking

Dynamic mask:
- replacement length can correspond to original length.

Example:

`secret123`
→ `*********`

Useful when:
- preserving rough representation is useful.

But:
- length itself can leak information.

Therefore choose based on policy.

#### 2.3.5.10 Fixed Mask

Example:

`any secret`
→ `*****`

Benefit:
- does not reveal original length.

Useful for:
- passwords,
- tokens,
- values where no fragment should be visible.

#### 2.3.5.11 Custom Mask

Application may use:
- `REDACTED`
- `XXXXX`
- `[SECRET]`
- organization-defined marker.

Purpose:
- clearly communicate that transformation occurred.

#### 2.3.5.12 Regex-Based Partial Masking

A regex can retain selected fragments.

Conceptually:

`jane@example.com`
→ keep first character
→ mask local part
→ retain domain

Result:

`j***@example.com`

##### 2.3.5.12.1 Caution
- Regex must match expected format.
- Test malformed/unexpected values.
- Do not assume regex-based masking itself validates the data.

#### 2.3.5.13 Nested Objects

Sensitive fields often exist deeply:

```text
order.customer.identity.ssn
order.payment.card.number
order.authentication.token
```

Implementation should support:
- explicit nested field paths,
- recursive transformation where appropriate.

##### 2.3.5.13.1 AWS Context
Powertools for AWS Lambda Data Masking supports targeting fields in nested data.

#### 2.3.5.14 Arrays and Collections

Payloads can contain:
- lists of customers,
- multiple payment records,
- nested collections.

Masking logic must apply consistently to every relevant element.

##### 2.3.5.14.1 Test
- empty arrays,
- missing fields,
- null values,
- mixed structures,
- unexpected data types.

#### 2.3.5.15 AWS Lambda Powertools Data Masking

AWS provides a concrete application-level utility in **Powertools for AWS Lambda**.

Its Data Masking utility supports:
- erase,
- encrypt,
- decrypt,
- nested-field selection,
- custom masking rules.

This is highly aligned with the wording of skill 2.3.5.

#### 2.3.5.16 Powertools `erase`

Conceptual TypeScript:

```typescript
const masker = new DataMasking();

const safe = masker.erase(data, {
  fields: ["email", "customer.ssn"]
});
```

Default erased values become:

`*****`

##### 2.3.5.16.1 Property
- Erasure is irreversible.

#### 2.3.5.17 Powertools Custom Masking Rules

Current TypeScript Powertools documentation supports rules such as:

- `regexPattern` + `maskFormat`
- `dynamicMask`
- `customMask`

Conceptually:

```text
email
→ regex partial mask

ssn
→ dynamic mask

internalSecret
→ fixed custom mask
```

This allows different policies per field.

#### 2.3.5.18 Top-Level vs Per-Field Rules

A common policy can be applied broadly.

Then:
- individual fields can override the general rule.

Mental model:

`DEFAULT MASK POLICY`
→ many selected fields

`FIELD-SPECIFIC POLICY`
→ override where business need differs.

#### 2.3.5.19 Missing Fields

Application masking must define behavior when expected sensitive field is absent.

Possible strategies:
- fail transformation,
- ignore missing field,
- apply schema validation earlier.

##### 2.3.5.19.1 Security Mindset
Unexpected payload structure should not silently cause sensitive fields to bypass protection.

#### 2.3.5.20 Encryption Through Powertools

Powertools Data Masking can also encrypt data using an encryption provider.

AWS documentation integrates it with:
- AWS Encryption SDK,
- AWS KMS.

Flow:

`plaintext field`
→ Data Masking
→ AWS Encryption SDK
→ data key
→ ciphertext
→ encrypted data key protected by KMS

##### 2.3.5.20.1 Use
- original value must remain recoverable.

#### 2.3.5.21 Envelope Encryption

Powertools documentation describes envelope encryption:

`KMS/master key`
→ protects data key

`data key`
→ encrypts sensitive data

Benefits:
- scalable data encryption,
- master key need not directly encrypt every large payload,
- compromise scope can be limited to a data key.

##### 2.3.5.21.1 Connection
- Task 2.2 introduced KMS and encryption mechanics.
- 2.3.5 applies them to application fields.

#### 2.3.5.22 Encryption Context

AWS Encryption SDK/KMS workflows can use an **encryption context**.

Example conceptual context:

```text
tenantId = acme
classification = confidential
```

##### 2.3.5.22.1 Properties
- non-secret key/value metadata,
- cryptographically bound to encrypted data,
- same context must be supplied as required during decryption.

##### 2.3.5.22.2 Important
- Do not put secrets into encryption context.

#### 2.3.5.23 Encryption Is Not Masking

Masked:

`************1111`
→ intended for safe human-visible representation.

Encrypted:

`ciphertext`
→ intended for authorized recovery.

Do not confuse the two.

#### 2.3.5.24 Masking Is Not Hashing

Hashing:
→ deterministic one-way transformation for specific use cases.

Masking:
→ creates a safe human/system representation.

Example:

`customer@example.com`
→ mask: `c***@example.com`

A hash would instead produce an opaque digest.

##### 2.3.5.24.1 Scope
- Hashing is a general security concept; the exam skill specifically emphasizes masking/sanitization.

#### 2.3.5.25 Masking Is Not Authorization

Authorization:

`May caller see this field?`

Masking:

`What representation may caller see?`

Example:

unauthorized:
→ omit/deny.

authorized support agent:
→ last four digits.

authorized payment processor:
→ full value if genuinely required.

#### 2.3.5.26 API Response Implementation

Recommended flow:

`request`
→ authenticate
→ authorize
→ load domain data
→ map to response DTO
→ mask sensitive fields
→ serialize
→ return.

##### 2.3.5.26.1 Important
- Masking occurs before response leaves application boundary.

#### 2.3.5.27 Logging Implementation

Recommended flow:

`application object`
→ construct safe log object
→ redact/mask
→ structured logger
→ CloudWatch Logs.

Bad:

`logger.info(JSON.stringify(request))`

Better:

```text
logger.info({
  requestId,
  customerId,
  operation
})
```

##### 2.3.5.27.1 Principle
- Logging should use an allowlist mindset.

#### 2.3.5.28 API Gateway Logging Context

API Gateway itself redacts certain sensitive values from execution logs, including:
- authorization headers,
- API key values,
- similar sensitive request parameters.

##### 2.3.5.28.1 But
This does not sanitize:
- your Lambda logs,
- custom application logs,
- arbitrary sensitive fields in request bodies,
- downstream events created by your application.

##### 2.3.5.28.2 Exam Principle
**Service-level redaction does not remove application-level responsibility.**

#### 2.3.5.29 Error Handling Implementation

Internal exception:

```text
Authentication failed:
token=abc123
customer=jane@example.com
```

Safe log:

```text
Authentication failed
requestId=...
customerId=...
```

Client response:

```json
{
  "code": "AUTHENTICATION_FAILED",
  "requestId": "..."
}
```

Different destinations:
→ different sanitized representations.

#### 2.3.5.30 Event Publishing

Before publishing to:
- SNS,
- SQS,
- EventBridge,
- Kinesis,

construct event contract containing only required fields.

Bad:

`publish entire customer object`

Better:

```text
CustomerAddressChanged
├── customerId
├── addressChangeId
└── timestamp
```

Consumer needing full data can retrieve it through authorized interface if architecture requires.

##### 2.3.5.30.1 Benefit
- reduces propagation of PII across event topology.

#### 2.3.5.31 Fanout Amplifies Exposure

One SNS event may reach:
- queue A,
- queue B,
- Lambda C,
- archive D.

If payload contains unnecessary PII:
→ one disclosure decision creates many copies.

Therefore sanitize/minimize at producer boundary.

#### 2.3.5.32 Analytics Export

Operational data:

```text
customerId
email
address
order
payment
```

Analytics may need only:

```text
pseudonymousCustomerId
region
product
amount
timestamp
```

Application/data pipeline should remove fields not needed for analysis.

#### 2.3.5.33 Non-Production Copy

Before production data reaches:
- dev,
- test,
- demo,

apply appropriate:
- masking,
- pseudonymization,
- erasure.

Prefer synthetic data when possible.

#### 2.3.5.34 Sanitization Middleware

For repeated patterns, transformation can be centralized in:
- middleware,
- serializers,
- logging wrappers,
- response mappers,
- event builders.

##### 2.3.5.34.1 Benefit
- consistency,
- fewer forgotten fields.

##### 2.3.5.34.2 Risk
- generic middleware may not understand business semantics.

Therefore:
- centralized mechanism,
- explicit field policy.

#### 2.3.5.35 Schema-Driven Sanitization

A useful architecture:

`schema`
→ identifies fields/classification
→ sanitizer applies policy
→ safe representation.

Potential benefits:
- consistent handling,
- testability,
- less duplicated masking logic.

##### 2.3.5.35.1 Exam Depth
- Architectural concept; no requirement to know a specific AWS schema-masking service.

#### 2.3.5.36 Central Policy vs Scattered String Replacement

Bad:

```text
replace("password", "*****")
```

in many unrelated code locations.

Better:
- named sensitive fields,
- reusable sanitizer/masker,
- explicit transformation policy,
- automated tests.

##### 2.3.5.36.1 Why
- easier to update when data model changes.

#### 2.3.5.37 Sanitization Failure

Security-sensitive transformation failures should be **fail-safe**.

Example:
- sanitizer expected `customer.ssn`,
- payload schema unexpectedly changed.

Unsafe:
→ return/log original object.

Safer:
→ fail operation or omit sensitive payload according to policy.

##### 2.3.5.37.1 Principle
**Do not fall back to plaintext because masking failed.**

#### 2.3.5.38 Testing Masking Logic

Tests should verify:

Input:
→ expected safe output.

Also test:
- nested fields,
- missing fields,
- nulls,
- unexpected types,
- arrays,
- malformed values,
- policy changes.

##### 2.3.5.38.1 Negative Assertion
Especially valuable:

**Assert that secret/PII does NOT appear in output.**

#### 2.3.5.39 Powertools Testing

AWS Powertools documentation demonstrates testing erase operations directly.

For encrypt/decrypt:
- use a mock encryption provider,
- avoid requiring real KMS keys in unit tests.

##### 2.3.5.39.1 Benefit
- deterministic security tests,
- no unnecessary AWS dependency in unit tests.

#### 2.3.5.40 Integration Testing

Test complete boundaries:

`API request`
→ Lambda
→ response

Verify:
- forbidden fields absent,
- masked fields correctly represented.

`Lambda`
→ CloudWatch log format

Verify:
- no secret values.

`producer`
→ event

Verify:
- payload contract contains only intended fields.

#### 2.3.5.41 Do Not Mutate Canonical Data Accidentally

Masking is often for a **representation**, not the source of truth.

Example:

`database customer`
→ clone/map
→ mask response copy.

Do not accidentally:
→ overwrite actual card/email/identifier with `*****`
unless irreversible erasure is explicitly intended.

#### 2.3.5.42 Transformation Ordering

A useful flow:

`VALIDATE`
→ `AUTHORIZE`
→ `SELECT`
→ `MASK/SANITIZE`
→ `SERIALIZE`
→ `SEND/LOG`.

Why:
- validate structure first,
- authorization determines permitted data,
- selection minimizes fields,
- masking transforms remaining sensitive representation.

#### 2.3.5.43 Serialization Boundary

A strong implementation rule:

**Sensitive fields should already be safe before generic serialization/logging code sees the object intended for output.**

This reduces accidental leakage through:
- JSON serialization,
- exception formatting,
- debug logging.

#### 2.3.5.44 Reusable Safe Views

One domain object can have explicit views:

`Customer`
→ `CustomerPublicView`
→ `CustomerSupportView`
→ `CustomerAuditView`
→ `CustomerEventView`

Each view defines:
- fields,
- masking,
- purpose.

This is safer than a single "customer JSON" reused everywhere.

#### 2.3.5.45 IAM Cannot Mask a Field in Application Memory

IAM controls AWS API/resource permissions.

It does not automatically transform:

```text
"ssn": "123-45-6789"
```

into:

```text
"ssn": "***-**-6789"
```

That transformation is application/data-layer responsibility.

##### 2.3.5.45.1 Important
- Authorization and representation are separate layers.

#### 2.3.5.46 KMS Cannot Decide Business-Level Visibility

KMS can:
- encrypt,
- decrypt,
- authorize cryptographic operations.

KMS does not know:
- support agent should see last four digits,
- analytics should not receive email,
- API caller should receive masked account number.

Application policy decides that.

#### 2.3.5.47 Secrets Manager Is Not a Sanitizer

Secrets Manager:
→ securely stores/retrieves secrets.

After retrieval:
→ application must still prevent secret from entering logs/responses/events.

Connection:

2.3.3 protects **storage/retrieval**.

2.3.5 protects **representation/exposure**.

#### 2.3.5.48 API Gateway Is Not the Full Sanitization Layer

API Gateway can:
- validate requests,
- provide configured logging,
- redact some sensitive logging values.

Application still must:
- authorize fields,
- transform business data,
- sanitize custom logs,
- sanitize responses/events.

#### 2.3.5.49 AWS WAF Is Not a Data Masker

WAF:
→ inspect/block web traffic.

Data masking:
→ transform sensitive application data.

Different problems.

#### 2.3.5.50 Decision Flow

##### 2.3.5.50.1 Step 1 — Identify Destination
- API response?
- log?
- event?
- analytics?
- test data?

##### 2.3.5.50.2 Step 2 — Define Allowed Fields
Prefer allowlist.

##### 2.3.5.50.3 Step 3 — Authorize
Determine whether caller/consumer may receive each data category.

##### 2.3.5.50.4 Step 4 — Choose Representation
- omit,
- full,
- erase,
- partial mask,
- encrypt.

##### 2.3.5.50.5 Step 5 — Transform in Application
- DTO/mapper,
- sanitizer,
- Powertools Data Masking,
- serializer/middleware.

##### 2.3.5.50.6 Step 6 — Emit
Only transformed representation crosses boundary.

##### 2.3.5.50.7 Step 7 — Test Negative Cases
Assert sensitive values never appear where prohibited.

#### 2.3.5.51 Exam Scenario Mapping

##### 2.3.5.51.1 "Lambda logs customer object containing SSN"
→ construct sanitized log object / erase SSN before logging.

##### 2.3.5.51.2 "Support must recognize card but not see full number"
→ partial mask; retain permitted digits.

##### 2.3.5.51.3 "Field must be recoverable by authorized process"
→ encrypt rather than erase.

##### 2.3.5.51.4 "Different API roles can see different representations"
→ authorize first, then create role-appropriate masked response.

##### 2.3.5.51.5 "Nested JSON contains several sensitive fields"
→ field-level/nested masking utility or explicit mapper.

##### 2.3.5.51.6 "Need AWS-supported Lambda utility"
→ Powertools Data Masking.

##### 2.3.5.51.7 "API Gateway already redacts Authorization header"
→ still sanitize Lambda/application logs and business payload fields.

##### 2.3.5.51.8 "Masking fails unexpectedly"
→ do not fall back to emitting plaintext.

#### 2.3.5.52 Common Exam Traps

##### 2.3.5.52.1 "Masking and Encryption Are Equivalent"
- False.

##### 2.3.5.52.2 "Mask Every Field Even If It Can Be Omitted"
- Usually unnecessary.
- Minimize first.

##### 2.3.5.52.3 "IAM Automatically Performs Field Masking"
- False.

##### 2.3.5.52.4 "KMS Determines Which Digits Users May See"
- False.

##### 2.3.5.52.5 "Secrets Manager Prevents Retrieved Secret From Being Logged"
- False.

##### 2.3.5.52.6 "API Gateway Redaction Protects All Application Logs"
- False.

##### 2.3.5.52.7 "AWS WAF Masks Sensitive Response Fields"
- False.

##### 2.3.5.52.8 "Masked Copy Should Replace Canonical Source Data"
- Not unless irreversible source erasure is explicitly intended.

##### 2.3.5.52.9 "If Sanitizer Fails, Return Original Object"
- Unsafe.

##### 2.3.5.52.10 "One Sanitized Representation Fits Every Destination"
- False.
- Sanitization is purpose/destination specific.

#### 2.3.5.56 Exam-Level Knowledge Frame

Know these cold:

**Application-level masking**
→ code creates destination-specific safe representation.

**Minimize first**
→ omit fields destination does not need.

**Erase**
→ irreversible replacement.

**Partial mask**
→ retain only useful fragment.

**Encrypt**
→ use when authorized recovery is required.

**Explicit DTO/output model**
→ safer than serializing internal object directly.

**Powertools Data Masking**
→ erase/encrypt/decrypt + field-level/nested transformations.

**API Gateway**
→ can redact some sensitive values in its own logs, but does not sanitize arbitrary application payloads/logs.

**IAM**
→ authorization, not field transformation.

**KMS**
→ cryptography, not business-level masking policy.

**Testing**
→ assert sensitive plaintext does not appear in prohibited outputs.

Fastest exam discriminator:

**Field not required?**
→ omit.

**Need recognizable representation?**
→ mask.

**Never reveal it?**
→ erase/redact.

**Need authorized recovery?**
→ encrypt.

**Need AWS-supported Lambda implementation utility?**
→ Powertools Data Masking.

Final principle:

**Do not pass internal objects directly across application boundaries. Select only the fields the destination is authorized to receive, transform sensitive fields before serialization, and test that plaintext never appears in prohibited responses, logs, or events.**
