### 2.3.6 Implement data access patterns for multi-tenant applications

#### 2.3.6.1 Exam and Task Context

##### 2.3.6.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.3 is **Manage sensitive data in application code**.
- Skill 2.3.6 is **Implement data access patterns for multi-tenant applications**.
- This is the final skill of Task 2.3 and Domain 2.
- Previous skills established:
  - 2.3.1 → classify sensitive data.
  - 2.3.2 → protect sensitive environment variables.
  - 2.3.3 → store/retrieve secrets securely.
  - 2.3.4 → decide how sensitive data should be sanitized.
  - 2.3.5 → implement masking/sanitization.
- 2.3.6 adds another security dimension:
  - **Which tenant is allowed to access which data?**

##### 2.3.6.1.2 Core Question
- **How do you ensure that an authenticated application user can access only resources belonging to the user's tenant?**

#### 2.3.6.2 Core Mental Model

`AUTHENTICATE USER`
→ establish identity

`RESOLVE TENANT CONTEXT`
→ tenantId

`AUTHORIZE REQUEST`
→ user/action/resource permitted?

`ENFORCE TENANT ISOLATION`
→ requested data must belong to tenantId

`QUERY DATA`
→ tenant boundary included in access path

Core rule:

**Authenticated ≠ tenant isolated.**

#### 2.3.6.3 Tenant

A tenant is an organizational/customer boundary in a shared application.

Examples:
- Customer A.
- Customer B.
- Business unit A.
- SaaS subscriber A.

A tenant can contain:
- many users,
- roles,
- resources,
- records,
- configuration.

#### 2.3.6.4 Multi-Tenancy

Multi-tenancy means multiple tenants use a common application/platform.

Resources can be:
- physically separated,
- logically separated,
- or a mixture.

The architectural goal is:

`Tenant A`
→ Tenant A resources only.

`Tenant B`
→ Tenant B resources only.

#### 2.3.6.5 Tenant Isolation

AWS defines tenant isolation as explicit mechanisms that prevent one tenant from accessing another tenant's resources.

It is separate from basic authentication and general authorization.

A user can be:
- authenticated,
- authorized to call an API,
and still be incorrectly allowed to access another tenant's object if tenant context is not enforced.

#### 2.3.6.6 Authentication vs Authorization vs Isolation

`AUTHENTICATION`
→ Who are you?

`AUTHORIZATION`
→ What operation may you perform?

`TENANT ISOLATION`
→ On whose resources may you perform it?

Example:

Alice:
- authenticated,
- role = editor,
- tenant = A.

`PUT /documents/123`

Correct decision requires:
- Alice is authenticated,
- editor can update documents,
- document 123 belongs to tenant A.

#### 2.3.6.7 Tenant Context

Every tenant-aware request needs trusted tenant context.

Potential source:
- validated JWT claim,
- trusted Cognito attribute,
- server-side session,
- resolved mapping from authenticated principal.

##### 2.3.6.7.1 Critical Rule
Do not trust a tenant ID merely because the client sends:

`X-Tenant-ID: tenant-b`

or:

`?tenantId=tenant-b`

The authenticated identity must be authorized for that tenant.

#### 2.3.6.8 Cognito Tenant Context

Amazon Cognito documentation recommends:
- validating tenancy in the application,
- using Verified Permissions where appropriate,
- making tenant-identifying custom attributes immutable/read-only,
- ensuring users cannot modify the criteria used to authorize tenant access.

Mental model:

`Cognito token`
→ verified identity/tenant claim
→ application authorization
→ tenant-scoped data access.

#### 2.3.6.9 Tenant ID as a Security Attribute

A tenant identifier is not merely business metadata.

It participates in security decisions:

`principal.tenantId`
must match
`resource.tenantId`.

Therefore:
- protect its integrity,
- derive it from trusted identity context,
- propagate it through service calls.

#### 2.3.6.10 Tenant Context Propagation

In distributed applications:

`API Gateway`
→ `Lambda A`
→ `SQS`
→ `Lambda B`
→ `DynamoDB`

tenant context may need to travel through each hop.

Each component must preserve/enforce the boundary.

##### 2.3.6.10.1 Principle
**Tenant isolation is end-to-end, not only an API-edge check.**

#### 2.3.6.11 Data Partitioning vs Tenant Isolation

AWS explicitly distinguishes:

`DATA PARTITIONING`
→ how tenant data is stored/organized.

`TENANT ISOLATION`
→ how cross-tenant access is prevented.

Partitioning alone does not guarantee isolation.

Example:

DynamoDB item contains `tenantId`.

That organizes data.

But if application can query another tenant's key:
→ isolation has failed.

#### 2.3.6.12 Core Partitioning Models

AWS multi-tenant guidance commonly uses:

`SILO`
→ dedicated resources per tenant.

`POOL`
→ tenants share resources; data is logically partitioned.

`BRIDGE / HYBRID`
→ combination of dedicated and shared constructs.

#### 2.3.6.13 Silo Model

Example:

`Tenant A`
→ DynamoDB Table A

`Tenant B`
→ DynamoDB Table B

or:

`Tenant A`
→ database/cluster A

`Tenant B`
→ database/cluster B.

##### 2.3.6.13.1 Advantages
- strong isolation.
- easier per-tenant performance separation.
- can satisfy strict regulatory/customer requirements.

##### 2.3.6.13.2 Trade-Offs
- more resources.
- higher cost.
- greater operational complexity.
- slower tenant onboarding.
- harder centralized operations.

#### 2.3.6.14 Pool Model

Example:

`Shared DynamoDB Table`
→ Tenant A items
→ Tenant B items
→ Tenant C items.

All tenants use shared infrastructure.

Isolation is logical.

##### 2.3.6.14.1 Advantages
- efficient resource sharing.
- lower operational overhead.
- simpler onboarding.
- cost efficiency.

##### 2.3.6.14.2 Trade-Offs
- isolation must be designed explicitly.
- noisy-neighbor concerns.
- data-access mistakes can expose another tenant.

#### 2.3.6.15 Bridge / Hybrid Model

Mix:
- pooled tenants,
- siloed premium/regulatory tenants,
- separate databases/schemas for some tenants,
- shared resources elsewhere.

Example:

`Standard tenants`
→ shared table.

`Regulated tenant`
→ dedicated table/database.

##### 2.3.6.15.1 Benefit
- isolation level can match tenant requirements.

##### 2.3.6.15.2 Cost
- more architecture/data-access complexity.

#### 2.3.6.16 DynamoDB Pool Pattern

AWS SaaS guidance gives a canonical pattern:

`tenant identifier`
→ part of DynamoDB partition key.

Example:

`PK = TENANT#A`
`SK = ORDER#123`

or more commonly in a single-table model:

`PK = TENANT#A#ORDER#123`
`SK = ...`

The important idea:

**tenant identity is part of the access key.**

#### 2.3.6.17 Why Tenant ID Belongs in Access Path

Unsafe model:

`GetItem(orderId=123)`
→ fetch
→ check tenant afterward.

Safer model:

`GetItem(PK=TENANT#A#ORDER#123)`
→ tenant is embedded in lookup.

Benefit:
- accidental cross-tenant access becomes harder.
- tenant boundary is part of data model.

#### 2.3.6.18 Composite Keys

A common pooled DynamoDB pattern:

`PK = TENANT#<tenantId>#<entityType>#<entityId>`

Example:

`TENANT#A#ORDER#123`

This provides:
- tenant namespace,
- resource identity,
- query locality.

#### 2.3.6.19 Query by Tenant

Example:

`PK begins/equals tenant-specific partition`

rather than:

`Scan table`
→ filter tenant in application.

##### 2.3.6.19.1 Why
- security boundary is closer to data access.
- avoids unnecessarily retrieving other tenants' records.
- more efficient than broad scans.

#### 2.3.6.20 FilterExpression Is Not the Primary Isolation Boundary

DynamoDB filtering occurs after items are read by the query/scan operation.

Therefore:

`retrieve broad dataset`
→ `FilterExpression tenantId=A`

is weaker than:

`key condition inherently scopes tenant A`.

##### 2.3.6.20.1 Exam Mindset
**Design the key/access pattern around tenant scope instead of relying only on post-read filtering.**

#### 2.3.6.21 IAM Fine-Grained DynamoDB Access

IAM can constrain DynamoDB access using conditions.

A particularly relevant mechanism:

`dynamodb:LeadingKeys`

This can restrict which partition-key values a principal may access.

Concept:

`principal for Tenant A`
→ permitted only keys beginning with Tenant A identifier.

##### 2.3.6.21.1 Defense in Depth
Application query:
→ tenant scoped.

IAM policy:
→ tenant scoped.

Both reinforce isolation.

#### 2.3.6.22 Tenant-Specific IAM Role

Pattern:

`Tenant A request`
→ assume/use Tenant A scoped role
→ IAM permits Tenant A resources/keys only.

Useful especially in silo or strongly isolated architectures.

##### 2.3.6.22.1 AWS STS
- `AssumeRole` provides temporary credentials.
- temporary credentials can carry tenant-scoped permissions.

#### 2.3.6.23 ABAC Context

Attribute-based access control can use:

`principal attributes`
+
`resource attributes`
+
`conditions`

Example concept:

`principal.tenantId = A`
AND
`resource.tenantId = A`
→ allow.

##### 2.3.6.23.1 Benefit
- scalable compared with creating unique static policies for every combination.

#### 2.3.6.24 Session Tags

STS sessions can carry tags/attributes.

Conceptually:

`AssumeRole`
→ session tag `tenantId=A`
→ IAM condition uses tenant tag.

##### 2.3.6.24.1 Use
- propagate tenant context into AWS authorization decisions where supported.

##### 2.3.6.24.2 Important
- only trusted components should be allowed to establish security-sensitive session tags.

#### 2.3.6.25 Application-Level Authorization

Not every tenant decision can be expressed directly in IAM.

Application may need:

`token tenant`
→ compare with requested resource tenant
→ reject mismatch.

Example:

`token.tenantId = A`
`resource.tenantId = B`

→ `403 Forbidden`.

##### 2.3.6.25.1 Connection
- Skill 2.1.7 introduced ownership/tenant-aware authorization.
- 2.3.6 applies it systematically to the data-access architecture.

#### 2.3.6.26 Amazon Verified Permissions

Amazon Verified Permissions provides centralized fine-grained application authorization using Cedar policies.

It can evaluate:
- principal,
- action,
- resource,
- context.

For multi-tenant applications, policies can incorporate tenant context.

##### 2.3.6.26.1 Cognito Integration
AWS recommends Verified Permissions as an option for validating tenancy in applications using Cognito.

#### 2.3.6.27 Verified Permissions Does Not Replace Data Partitioning

Verified Permissions:
→ authorization decision.

Database:
→ actual tenant data storage/access.

Correct flow:

`identity`
→ Verified Permissions decision
→ tenant-scoped query
→ data store.

Do not:
→ authorize route broadly
→ perform unscoped database query.

#### 2.3.6.28 Policy Store Models

AWS guidance discusses multi-tenant Verified Permissions designs such as:
- shared multi-tenant policy store,
- per-tenant policy store,
- tiered models.

##### 2.3.6.28.1 Exam Depth
Know the principle:
- authorization policies themselves must preserve tenant boundaries.
- dedicated policy stores can provide stronger tenant-level separation/customization.
- shared stores require careful tenant-aware policy design.

#### 2.3.6.29 PostgreSQL Pool Pattern

AWS Prescriptive Guidance for RDS/Aurora PostgreSQL:

`shared database/schema`
→ tenant rows coexist.

Tenant isolation can use:
- PostgreSQL Row-Level Security (RLS).

Example conceptual policy:

`row.tenant_id`
must equal
`current tenant context`.

##### 2.3.6.29.1 AWS Guidance
- RLS is the key database-level isolation mechanism for pooled PostgreSQL.

#### 2.3.6.30 Row-Level Security

RLS can restrict:
- SELECT rows,
- INSERT,
- UPDATE,
- DELETE

according to tenant policy.

Benefit:
- tenant isolation is enforced at database layer rather than relying exclusively on every application query author.

##### 2.3.6.30.1 Defense in Depth
Application:
→ tenant-aware query.

Database:
→ RLS tenant policy.

#### 2.3.6.31 PostgreSQL Bridge Pattern

AWS documents bridge options such as:
- database per tenant within shared instance/cluster,
- schema per tenant.

Application/data-access layer maintains mapping:

`tenantId`
→ database/schema.

##### 2.3.6.31.1 Trade-Off
- stronger logical separation than one shared schema,
- more provisioning/operational complexity.

#### 2.3.6.32 S3 Tenant Data

Conceptual pooled pattern:

`bucket`
→ `tenant-a/...`
→ `tenant-b/...`

IAM/resource policies can restrict prefixes.

Example mental model:

`Tenant A principal`
→ `s3://bucket/tenant-a/*`

not:
→ entire bucket.

##### 2.3.6.32.1 Important
Prefix organization alone is not isolation.
Authorization policy must enforce it.

#### 2.3.6.33 Siloed S3 Pattern

Alternative:

`Tenant A`
→ Bucket A.

`Tenant B`
→ Bucket B.

Provides stronger resource-level separation but:
- increases resource/policy/operations footprint.

#### 2.3.6.34 SQS / Event Isolation

Multi-tenant event-driven systems can use:

Pool:
`shared queue`
→ messages include trusted tenant context.

Silo:
`queue per tenant`.

##### 2.3.6.34.1 Producer
- publishes correct tenant context.

##### 2.3.6.34.2 Consumer
- preserves/enforces tenant context before data access.

##### 2.3.6.34.3 Critical
A queue is not automatically a tenant boundary.

#### 2.3.6.35 EventBridge Context

Shared bus:
→ events from multiple tenants.

Potential controls:
- tenant-aware event detail,
- routing rules,
- IAM/resource policies,
- consumer-side enforcement.

Silo:
→ dedicated bus/resources where stronger isolation is required.

##### 2.3.6.35.1 Principle
- isolation strategy varies by AWS service.

#### 2.3.6.36 Tenant Context in Events

Example event:

```json
{
  "tenantId": "tenant-a",
  "orderId": "123",
  "eventType": "OrderCreated"
}
```

##### 2.3.6.36.1 Security Requirement
Consumer must not trust arbitrary tenant ID if event producer is not trusted.

##### 2.3.6.36.2 Better
- restrict producers,
- establish trusted event contracts,
- enforce tenant access at downstream data layer.

#### 2.3.6.37 Do Not Accept Tenant Override

Dangerous API:

`GET /orders/123?tenantId=B`

when caller's trusted tenant is A.

Correct:
- tenant comes from trusted identity context,
- client cannot override it to gain access.

#### 2.3.6.38 Object-Level Authorization

Classic vulnerability:

`GET /orders/123`
→ authenticated user changes `123` to `124`
→ receives another tenant's order.

Fix:

`principal tenant`
+
`resource ownership`
+
`tenant-scoped lookup`
→ must match.

##### 2.3.6.38.1 Principle
**Never authorize only the route; authorize the requested object/data.**

#### 2.3.6.39 Tenant Isolation and Admin Users

Some users may legitimately access:
- multiple tenants,
- all tenants,
- support views.

Do not bypass tenant isolation globally.

Instead:
- explicitly model privileged access,
- authorize it,
- audit it,
- minimize exposed fields.

#### 2.3.6.40 Tenant Isolation and Data Masking

Tenant isolation:
→ whether Tenant A can access Tenant B record.

Masking:
→ representation of fields within an authorized record.

Incorrect:

Tenant A requests Tenant B record
→ mask SSN
→ return rest.

Correct:

Tenant A requests Tenant B record
→ deny access.

#### 2.3.6.41 Tenant Isolation and Encryption

Encryption:
→ protects confidentiality at storage/transport boundaries.

Tenant isolation:
→ controls which tenant can access decrypted resources.

A shared encrypted table can still have a cross-tenant authorization bug.

##### 2.3.6.41.1 Principle
**Encryption does not replace tenant-aware authorization.**

#### 2.3.6.42 Per-Tenant KMS Keys

Silo/high-isolation designs can use:
- separate customer managed KMS key per tenant.

Benefits:
- cryptographic separation,
- tenant-specific key lifecycle/access.

Trade-Offs:
- key management overhead,
- cost,
- quotas/operations.

##### 2.3.6.42.1 Use
- stronger compliance/customer isolation requirements.

#### 2.3.6.43 Noisy Neighbor

Tenant isolation is not only confidentiality.

Shared resources can create performance coupling:

`Tenant A heavy workload`
→ degrades Tenant B.

Silo:
→ stronger performance isolation.

Pool:
→ greater efficiency but noisy-neighbor risk.

##### 2.3.6.43.1 AWS Guidance
- partitioning model should consider security, compliance, performance, cost, and operational complexity.

#### 2.3.6.44 Tenant Tiering

Example:

`Free / Standard`
→ pooled.

`Enterprise`
→ dedicated resources.

This hybrid approach lets isolation level match:
- SLA,
- compliance,
- customer requirement,
- performance.

#### 2.3.6.45 Cache Isolation

Cache keys must include tenant context.

Unsafe:

`customer:123`

Safer:

`tenant:A:customer:123`

Otherwise:
- cached data from Tenant A could be returned to Tenant B.

##### 2.3.6.45.1 Principle
Every shared data layer needs tenant-aware keys/boundaries.

#### 2.3.6.46 Idempotency Isolation

Idempotency key should be tenant-aware where IDs can collide.

Unsafe:

`idempotencyKey = request-123`

Safer conceptual key:

`tenant-A#request-123`

Prevents one tenant's request state from colliding with another tenant.

#### 2.3.6.47 Observability

Logs/metrics/traces should include safe tenant context when operationally useful.

Benefits:
- troubleshoot tenant-specific issues,
- monitor noisy neighbors,
- audit access.

But:
- do not put unnecessary tenant-sensitive data into telemetry.
- sanitize according to 2.3.4/2.3.5.

#### 2.3.6.48 Audit Cross-Tenant Attempts

Security-relevant events:
- tenant mismatch,
- forbidden resource access,
- suspicious repeated object IDs.

Log:
- principal,
- trusted tenant identifier,
- requested resource identifier,
- action,
- decision,
- request ID.

Do not log unnecessary sensitive payloads.

#### 2.3.6.49 Background Jobs

Tenant isolation must also apply outside synchronous APIs:

`scheduled Lambda`
`SQS consumer`
`batch processor`
`stream consumer`

Each job must know:
- which tenant it is processing,
- which resources are permitted.

##### 2.3.6.49.1 Common Failure
- API enforces tenant isolation,
- background worker uses unrestricted table scan.

#### 2.3.6.50 Service-to-Service Calls

Downstream service should not blindly trust:

`tenantId` supplied by arbitrary caller.

Use:
- authenticated service identity,
- trusted request/event path,
- tenant-aware authorization.

##### 2.3.6.50.1 Principle
**Tenant context must have provenance.**

#### 2.3.6.51 Testing Tenant Isolation

Essential negative test:

`User A / Tenant A`
→ request Tenant B resource
→ DENIED.

Test:
- direct ID manipulation,
- list/query endpoints,
- search,
- batch operations,
- exports,
- caches,
- background processing,
- events.

##### 2.3.6.51.1 Strong Test
Attempt cross-tenant access systematically rather than only testing valid access.

#### 2.3.6.52 Data Access Layer

A strong pattern centralizes tenant-aware access:

`repository.getOrder(tenantId, orderId)`

instead of:

`repository.getOrder(orderId)`.

##### 2.3.6.52.1 Benefit
- tenant context becomes mandatory API input.
- reduces accidental unscoped queries.

#### 2.3.6.53 Avoid Optional Tenant Context

Dangerous:

`findOrders(tenantId = null)`
→ means all tenants.

Better:
- tenant-scoped methods require tenant ID.
- administrative cross-tenant methods are separate and explicit.

##### 2.3.6.53.1 Principle
**Make unsafe cross-tenant access difficult to express accidentally.**

#### 2.3.6.54 Centralize Tenant Resolution

Good flow:

`validated identity`
→ TenantContext resolver
→ immutable request context
→ authorization/data layer.

Avoid:
- each controller independently parsing tenant IDs,
- trusting different headers in different services.

#### 2.3.6.55 Defense in Depth

Strong pooled architecture can combine:

1. trusted tenant claim.
2. application authorization.
3. tenant-scoped data-access API.
4. tenant-prefixed DynamoDB key / database RLS.
5. IAM conditions where supported.
6. audit logging.
7. negative cross-tenant tests.

No single control should be treated as universally sufficient.

##### 2.3.6.56.1 Step 1 — Determine Isolation Requirement

##### 2.3.6.56.2 Step 2 — Choose Partition Model

- silo,
- bridge/hybrid.

##### 2.3.6.56.3 Step 3 — Establish Trusted Tenant Context
- Cognito/JWT/session/identity mapping.

##### 2.3.6.56.4 Step 4 — Authorize
- IAM,
- application logic,
- Verified Permissions,
- database policy,
depending on boundary.

##### 2.3.6.56.5 Step 5 — Encode Tenant into Access Pattern
Examples:
- DynamoDB partition key,
- S3 prefix/bucket,
- database row/schema/database,
- cache key,
- event context.

##### 2.3.6.56.6 Step 6 — Enforce at Data Boundary
- scoped key/query,
- IAM condition,
- RLS,
- dedicated resource.

##### 2.3.6.56.7 Step 7 — Test Cross-Tenant Failure
- explicitly verify Tenant A cannot access Tenant B.

#### 2.3.6.57 Exam Scenario Mapping

##### 2.3.6.57.1 "Many tenants, shared DynamoDB table"
→ pool model + tenant identifier in partition/access key + tenant-aware authorization.

##### 2.3.6.57.2 "Strict regulatory requirement for physical separation"
→ silo model.

##### 2.3.6.57.3 "Shared PostgreSQL database"
→ pool + row-level security.

##### 2.3.6.57.4 "Premium tenant needs dedicated infrastructure"
→ hybrid/tiered model.

##### 2.3.6.57.5 "Authenticated user changes object ID and sees another tenant's record"
→ missing object-level/tenant authorization.

##### 2.3.6.57.6 "Client supplies tenantId parameter"
→ do not trust it alone; resolve/validate against trusted identity.

##### 2.3.6.57.7 "Need centralized fine-grained app authorization"
→ Amazon Verified Permissions is relevant.

##### 2.3.6.57.8 "DynamoDB principal should access only tenant partition"
→ tenant-key design + IAM fine-grained conditions such as `dynamodb:LeadingKeys`.

##### 2.3.6.57.9 "Different tenant records collide in cache"
→ tenant ID missing from cache key.

#### 2.3.6.58 Common Exam Traps

##### 2.3.6.58.1 "Authentication Provides Tenant Isolation"
- False.

##### 2.3.6.58.2 "Authorization to API Route Automatically Provides Object Isolation"
- False.

##### 2.3.6.58.3 "Tenant ID Column Alone Provides Isolation"
- False.

##### 2.3.6.58.4 "DynamoDB FilterExpression Is Best Tenant Boundary"
- False.
- Prefer tenant-scoped key/access patterns.

##### 2.3.6.58.5 "Encryption Prevents Cross-Tenant Application Access"
- False.

##### 2.3.6.58.6 "Masking Another Tenant's Data Makes Access Acceptable"
- False.

##### 2.3.6.58.7 "Client-Supplied Tenant ID Can Be Trusted"
- False.

##### 2.3.6.58.8 "Pool Is Always Less Secure"
- False.
- It can provide strong logical isolation when correctly implemented.

##### 2.3.6.58.9 "Silo Is Always Best"
- False.
- Strong isolation comes with cost/operational trade-offs.

##### 2.3.6.58.10 "Partitioning and Isolation Are Synonyms"
- False.

##### 2.3.6.58.11 "Only API Requests Need Tenant Isolation"
- False.
- Background jobs, caches, events, exports, and data pipelines also need it.

##### 2.3.6.58.12 "Verified Permissions Replaces Tenant-Scoped Data Access"
- False.

#### 2.3.6.61 Domain 2 Big Picture

Domain 2 builds a layered security model:

`IDENTITY`
→ authenticate users/services

`AUTHORIZATION`
→ permit actions/resources

`CRYPTOGRAPHY`
→ protect confidentiality

`SENSITIVE DATA MANAGEMENT`
→ classify, store, sanitize, mask

`TENANT ISOLATION`
→ ensure one customer's identity cannot cross another customer's data boundary

The final mindset:

**Security is not one control. Identity, authorization, encryption, sensitive-data handling, and tenant isolation solve different boundaries and must work together.**

#### 2.3.6.63 Exam-Level Knowledge Frame

Know these cold:

**Tenant isolation**
→ Tenant A cannot access Tenant B resources.

**Authentication**
→ identity, not isolation.

**Authorization**
→ permitted operation; still needs tenant/resource context.

**Data partitioning**
→ storage organization, not automatically isolation.

**Pool**
→ shared resources + logical tenant partition.

**Silo**
→ dedicated resources per tenant.

**Hybrid/bridge**
→ combination of shared and dedicated constructs.

**DynamoDB pooled pattern**
→ tenant ID in partition/access key.

**PostgreSQL pooled pattern**
→ tenant-aware rows + RLS.

**Trusted tenant context**
→ derive from validated identity, not arbitrary client parameter.

**Verified Permissions**
→ centralized fine-grained application authorization; can incorporate tenant context.

**Defense in depth**
→ identity + authorization + tenant-scoped access path + data-layer enforcement + tests.

Fastest exam discriminator:

**Shared table with many tenants?**
→ pool + tenant-aware partition/access key.

**Strict physical isolation?**
→ silo.

**Authenticated user can read another tenant's object?**
→ tenant/object-level authorization failure.

**Shared PostgreSQL?**
→ RLS.

**Client chooses tenantId?**
→ verify/derive it from trusted identity context.

Final principle:

**Tenant identity must become part of the data-access boundary. Do not fetch data globally and then hope application code filters correctly; design queries, keys, policies, and database controls so cross-tenant access is difficult or impossible by construction.**
