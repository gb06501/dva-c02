### 2.3.1 Describe data classification (for example, personally identifiable information [PII], protected health information [PHI])

#### 2.3.1.1 Exam and Task Context

##### 2.3.1.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.3 is **Manage sensitive data in application code**.
- Skill 2.3.1 is **Describe data classification (for example, personally identifiable information [PII], protected health information [PHI])**.
- This is the first skill of Task 2.3.
- The remaining skills turn classification into implementation:
  - 2.3.2 → encrypt sensitive environment variables.
  - 2.3.3 → use secret-management services.
  - 2.3.4 → sanitize sensitive data.
  - 2.3.5 → implement masking and sanitization.
  - 2.3.6 → implement multi-tenant data-access patterns.

##### 2.3.1.1.2 Core Question
- **What kind of data is the application handling, how sensitive is it, and what controls should that classification drive?**

#### 2.3.1.2 Core Mental Model

Data protection starts before encryption:

`DATA`
→ identify
→ classify
→ determine sensitivity/criticality
→ choose controls
→ enforce throughout lifecycle

Classification answers:

**What is this data?**

Then security architecture answers:

**How must this class of data be handled?**

#### 2.3.1.3 What Data Classification Means

##### 2.3.1.3.1 AWS Definition
- Data classification identifies and categorizes data based on characteristics such as sensitivity and criticality.

##### 2.3.1.3.2 Purpose
Classification helps determine:
- access controls,
- encryption requirements,
- retention,
- sharing rules,
- masking/sanitization,
- monitoring,
- deletion,
- regulatory handling.

##### 2.3.1.3.3 Key Principle
**Classification is the input to protection decisions, not the protection mechanism itself.**

#### 2.3.1.4 Classification Is Risk-Based

Data sensitivity depends on:
- business value,
- confidentiality requirement,
- legal/regulatory obligations,
- privacy impact,
- consequences of unauthorized disclosure,
- consequences of modification/loss.

A field is not sensitive merely because it is stored in a database, and sensitive data does not become non-sensitive because it is moved to another AWS service.

#### 2.3.1.5 Example Classification Levels

AWS Prescriptive Guidance gives common increasing-sensitivity categories such as:

`PUBLIC`
→ `PRIVATE`
→ `INTERNAL`
→ `CONFIDENTIAL`
→ `RESTRICTED`

##### 2.3.1.5.1 Important
- These are examples, not a mandatory universal AWS classification taxonomy.
- Organizations define their own categories and classification criteria.

#### 2.3.1.6 Public Data

##### 2.3.1.6.1 Meaning
- Intended or approved for public disclosure.

##### 2.3.1.6.2 Examples
- public product documentation,
- published marketing material,
- public website content.

##### 2.3.1.6.3 Important
Public does not mean:
- integrity is irrelevant,
- anyone should be allowed to modify it.

Confidentiality and integrity are separate concerns.

#### 2.3.1.7 Internal Data

##### 2.3.1.7.1 Meaning
- Intended for internal organizational use.

##### 2.3.1.7.2 Examples
- internal procedures,
- non-public operational documentation,
- routine internal communications.

##### 2.3.1.7.3 Controls
May require:
- authenticated access,
- no public exposure,
- standard encryption/retention controls.

#### 2.3.1.8 Confidential / Restricted Data

##### 2.3.1.8.1 Meaning
- Disclosure can create significant business, privacy, legal, or security impact.

##### 2.3.1.8.2 Examples
- customer PII,
- health information,
- credentials,
- payment information,
- trade secrets,
- sensitive intellectual property.

##### 2.3.1.8.3 Controls
Typically stronger:
- least-privilege access,
- encryption,
- auditing,
- restricted logging,
- masking,
- retention/deletion policies,
- controlled sharing.

#### 2.3.1.9 Sensitive Data Categories Relevant to AWS Developers

A practical developer classification tree:

`SENSITIVE DATA`
│
├── Personal information
│   ├── PII
│   └── PHI / health information
│
├── Financial information
│   ├── credit card data
│   └── bank/account information
│
├── Credentials / secrets
│   ├── passwords
│   ├── API keys
│   ├── AWS secret access keys
│   ├── tokens
│   └── private keys
│
├── Business-sensitive data
│   ├── intellectual property
│   ├── source/data assets
│   └── confidential business records
│
└── Organization-specific sensitive data
    └── defined by policy/regulation/business context

#### 2.3.1.10 Personally Identifiable Information — PII

##### 2.3.1.10.1 Concept
- Information that can identify, relate to, or be associated with an individual, depending on applicable policy/regulation/context.

##### 2.3.1.10.2 AWS/Macie Examples
Amazon Macie can detect many PII types such as:
- full names,
- dates of birth,
- mailing addresses,
- phone numbers,
- passport numbers,
- driver's license numbers,
- national identification numbers,
- Social Security numbers,
- taxpayer identifiers,
- GPS coordinates,
- vehicle identification numbers.

##### 2.3.1.10.3 Important
- PII is broader than just government identification numbers.

#### 2.3.1.11 Direct Identifiers

##### 2.3.1.11.1 Examples
- full name,
- passport number,
- national ID,
- driver's license number,
- email address in many contexts,
- phone number in many contexts.

##### 2.3.1.11.2 Risk
- Can directly identify a person or strongly associate data with an individual.

#### 2.3.1.12 Indirect / Quasi-Identifiers

##### 2.3.1.12.1 Concept
- Individual values may not uniquely identify a person.
- Combinations can make identification possible.

##### 2.3.1.12.2 Examples
- birth date,
- ZIP/postal code,
- location,
- job title,
- demographic attributes.

##### 2.3.1.12.3 Developer Mindset
**Classification must consider combinations of fields, not only individual columns.**

#### 2.3.1.13 Protected / Personal Health Information — PHI

##### 2.3.1.13.1 Exam Context
- The exam guide explicitly names PHI as a data-classification example.

##### 2.3.1.13.2 Macie Category
Amazon Macie includes a personal-information PHI category for health-related identifiers/data types.

##### 2.3.1.13.3 Examples
- health insurance identification numbers,
- medical identification numbers,
- health-related information tied to a person.

##### 2.3.1.13.4 Regulatory Context
- Whether data is legally "protected health information" depends on applicable law and organizational/regulatory context.
- Do not infer compliance status solely from an AWS service or technical label.

#### 2.3.1.14 PII vs PHI

`PII`
→ personal identifying information broadly

`PHI`
→ health-related personal information within applicable health/privacy context

##### 2.3.1.14.1 Relationship
- PHI commonly contains or is associated with personally identifying information.
- The exact legal definitions depend on applicable regulation.

##### 2.3.1.14.2 Exam Goal
Recognize:
- both are sensitive,
- PHI has health-information context,
- classification drives stronger handling requirements.

#### 2.3.1.15 Financial Information

##### 2.3.1.15.1 Examples
Amazon Macie can detect financial data such as:
- credit card numbers,
- credit card verification codes,
- credit card expiration dates,
- bank account numbers,
- IBANs,
- magnetic stripe data.

##### 2.3.1.15.2 Developer Consequence
Do not expose such values through:
- logs,
- exceptions,
- analytics events,
- URLs,
- test fixtures,
- debug responses.

#### 2.3.1.16 Credentials Are Sensitive Data

##### 2.3.1.16.1 Examples
Macie includes detection for credentials such as:
- AWS secret access keys,
- HTTP Basic Authorization headers,
- JWTs,
- OpenSSH private keys,
- PGP private keys,
- PKCS private keys,
- PuTTY private keys,
- selected API keys.

##### 2.3.1.16.2 Connection
This directly leads into Skill 2.3.3:
- sensitive credentials should be stored in appropriate secret-management systems rather than source code.

#### 2.3.1.17 Secrets vs PII

##### 2.3.1.17.1 Secret
- Value whose disclosure can grant access or cryptographic capability.

Examples:
- password,
- API key,
- token,
- private key.

##### 2.3.1.17.2 PII
- Information related to an identifiable person.

##### 2.3.1.17.3 Difference
A secret is classified primarily because of **access/security impact**.
PII is classified primarily because of **privacy/identity impact**.

Both are sensitive but require different handling patterns.

#### 2.3.1.18 Data Classification Drives Access Control

##### 2.3.1.18.1 Public
- Broad read access may be acceptable.

##### 2.3.1.18.2 Sensitive
- Restrict to required principals/workloads.

##### 2.3.1.18.3 Highly Sensitive
May require:
- separate roles,
- fine-grained permissions,
- stronger audit controls,
- tenant isolation,
- purpose-specific access.

##### 2.3.1.18.4 Principle
**Higher sensitivity → smaller authorized audience.**

#### 2.3.1.19 Data Classification Drives Encryption

##### 2.3.1.19.1 At Rest
Sensitive data may require:
- service-side encryption,
- customer managed KMS keys,
- client-side encryption for stronger trust boundaries.

##### 2.3.1.19.2 In Transit
- TLS/HTTPS.

##### 2.3.1.19.3 Connection
- Task 2.2 established the mechanisms.
- Task 2.3 establishes **which data requires which handling**.

#### 2.3.1.20 Data Classification Drives Key Choice

Example policy:

`PUBLIC`
→ standard service encryption

`CONFIDENTIAL`
→ customer managed KMS key

`RESTRICTED`
→ dedicated key + narrow key policy + additional controls

##### 2.3.1.20.1 Important
- This mapping is organization-specific.
- AWS does not prescribe one universal key choice for every classification level.

#### 2.3.1.21 Data Classification Drives Retention

Sensitive data should not be retained indefinitely merely because storage is inexpensive.

Classification can define:
- minimum retention,
- maximum retention,
- archival rules,
- deletion requirements,
- legal holds.

##### 2.3.1.21.1 AWS Examples
Implementation can involve:
- S3 Lifecycle,
- DynamoDB TTL,
- backup retention,
- log retention.

#### 2.3.1.22 Data Classification Drives Logging

##### 2.3.1.22.1 High-Risk Pattern
Application logs:
- passwords,
- tokens,
- Authorization headers,
- PII,
- PHI,
- payment data.

##### 2.3.1.22.2 Better
- log identifiers/reference IDs,
- redact sensitive fields,
- mask values,
- sanitize payloads before logging.

##### 2.3.1.22.3 Connection
- Skills 2.3.4 and 2.3.5 expand sanitization and masking.

#### 2.3.1.23 Data Classification Drives Observability Design

Before logging/tracing an object:

`request`
→ classify fields
→ decide observable vs sensitive
→ redact/mask/drop sensitive fields
→ emit telemetry

##### 2.3.1.23.1 Important
- CloudWatch Logs, traces, analytics systems, and error monitoring are still data stores.
- Sensitive data copied into observability systems remains sensitive.

#### 2.3.1.24 Data Classification Drives API Design

##### 2.3.1.24.1 Input
- Validate and protect sensitive fields.

##### 2.3.1.24.2 Output
- Return only data caller needs.

##### 2.3.1.24.3 Error Responses
- Do not expose sensitive internal data.

##### 2.3.1.24.4 Principle
**Minimize sensitive data crossing API boundaries.**

#### 2.3.1.25 Data Minimization

##### 2.3.1.25.1 Question
Does the application actually need this sensitive field?

##### 2.3.1.25.2 Better
If not needed:
- do not collect it,
- do not store it,
- do not copy it,
- do not log it.

##### 2.3.1.25.3 Security Benefit
- Data that does not exist cannot be leaked from the workload.

#### 2.3.1.26 Data Discovery

Classification requires knowing where sensitive data exists.

Potential locations:
- S3 objects,
- databases,
- logs,
- backups,
- snapshots,
- queues/messages,
- caches,
- configuration,
- environment variables,
- source repositories,
- analytics exports.

##### 2.3.1.26.1 Principle
**Inventory before protection.**

#### 2.3.1.27 Amazon Macie

##### 2.3.1.27.1 Purpose
- Amazon Macie automates discovery, logging, and reporting of sensitive data in Amazon S3.

##### 2.3.1.27.2 Detection
- Uses managed data identifiers and other techniques such as pattern matching/machine learning to identify sensitive data.

##### 2.3.1.27.3 Categories
Macie managed identifiers cover categories including:
- credentials,
- financial information,
- personal information: PII,
- personal information: PHI.

#### 2.3.1.28 Macie Managed Data Identifiers

##### 2.3.1.28.1 Definition
- Built-in criteria/techniques for detecting specific sensitive-data types.

##### 2.3.1.28.2 Examples
- AWS secret access key,
- credit card number,
- passport number,
- SSN,
- health/medical identifiers.

##### 2.3.1.28.3 Benefit
- Avoid writing all sensitive-data detection rules manually.

#### 2.3.1.29 Macie Custom Data Identifiers

##### 2.3.1.29.1 Purpose
- Detect organization-specific sensitive data.

##### 2.3.1.29.2 Mechanism
- Custom criteria based on regex with optional keywords/proximity configuration.

##### 2.3.1.29.3 Examples
- employee IDs,
- customer account numbers,
- proprietary internal identifiers.

#### 2.3.1.30 Macie Allow Lists

##### 2.3.1.30.1 Purpose
- Define text/patterns that Macie should ignore as sensitive-data exceptions.

##### 2.3.1.30.2 Example
- known sample/test values,
- public organization contact values.

##### 2.3.1.30.3 Benefit
- Reduce unwanted findings/false positives for known exceptions.

#### 2.3.1.31 Macie Automated Sensitive Data Discovery

##### 2.3.1.31.1 Purpose
- Broad ongoing visibility into sensitive data in S3.

##### 2.3.1.31.2 Behavior
- Macie evaluates S3 inventory and samples representative objects for analysis.

##### 2.3.1.31.3 Output
- sensitivity information,
- findings,
- discovery results.

#### 2.3.1.32 Macie Sensitive Data Discovery Jobs

##### 2.3.1.32.1 Purpose
- Define targeted analysis of S3 objects.

##### 2.3.1.32.2 Configuration
Can select:
- S3 scope,
- managed identifiers,
- custom identifiers,
- allow lists,
- schedule.

##### 2.3.1.32.3 Exam Clue
**Find PII or credentials stored in S3**
→ Amazon Macie.

#### 2.3.1.33 Macie Scope Boundary

##### 2.3.1.33.1 Primary Data Store
- Macie is optimized for Amazon S3 sensitive-data discovery.

##### 2.3.1.33.2 Other Data
AWS documentation notes data from other stores can be exported to S3 for analysis, for example:
- RDS/Aurora snapshot exports,
- DynamoDB exports.

##### 2.3.1.33.3 Exam Trap
- Do not treat Macie as a universal live scanner for every AWS database/service.

#### 2.3.1.34 Classification Is More Than Macie

##### 2.3.1.34.1 Macie
- Helps discover/classify sensitive data in S3.

##### 2.3.1.34.2 Organization
Still defines:
- classification policy,
- business sensitivity,
- legal obligations,
- handling requirements,
- ownership.

##### 2.3.1.34.3 Important
**A discovery tool detects patterns; governance determines what classification means.**

#### 2.3.1.35 Data Ownership

For each sensitive dataset, understand:
- owner,
- producer,
- consumers,
- storage location,
- classification,
- retention,
- permitted sharing.

##### 2.3.1.35.1 AWS Guidance
- Workload owners should understand the type/classification of data, business process, storage location, and ownership.

#### 2.3.1.36 Resource Tags and Classification

##### 2.3.1.36.1 Use
- Tags can help identify and organize resources by data classification.

Example conceptual tags:
- `DataClassification=Confidential`
- `DataOwner=CustomerPlatform`

##### 2.3.1.36.2 Warning
- Do not put sensitive values themselves into tags.
- Tags are metadata, not a secret store.

#### 2.3.1.37 Classification Labels vs Sensitive Values

Good:

`DataClassification=Restricted`

Bad:

`CustomerSSN=...`

##### 2.3.1.37.1 Principle
- Classification metadata describes sensitivity.
- It should not reproduce the sensitive data.

#### 2.3.1.38 Data Lifecycle

Classification must follow data through:

`collect`
→ `process`
→ `transmit`
→ `store`
→ `copy`
→ `backup`
→ `archive`
→ `delete`

##### 2.3.1.38.1 Important
A backup of restricted data is still restricted data.

A log containing PII is still PII.

A copied S3 object containing credentials is still sensitive.

#### 2.3.1.39 Derived Data

##### 2.3.1.39.1 Problem
Data derived from sensitive source data may remain sensitive.

Examples:
- analytics extracts,
- reports,
- transformed datasets,
- exports,
- ML features.

##### 2.3.1.39.2 Rule
- Re-evaluate classification after transformation.
- Do not automatically assume transformed data is anonymous/non-sensitive.

#### 2.3.1.40 Masked / Sanitized Data

##### 2.3.1.40.1 Masking
- Obscures some sensitive content while retaining useful representation.

##### 2.3.1.40.2 Sanitization
- Removes or transforms sensitive content to make output safer for its intended use.

##### 2.3.1.40.3 Connection
- Expanded in 2.3.4 and 2.3.5.

##### 2.3.1.40.4 Important
- Classification should determine what must be masked/sanitized.

#### 2.3.1.41 Test Data

##### 2.3.1.41.1 Bad Pattern
- Copy production PII/PHI into development environment without controls.

##### 2.3.1.41.2 Better
- synthetic data,
- anonymized/sanitized datasets,
- masked values,
- least possible sensitive production data.

##### 2.3.1.41.3 Principle
**Development environment does not downgrade data classification.**

#### 2.3.1.42 Environment Variables

##### 2.3.1.42.1 Sensitive Values
Environment variables can contain:
- credentials,
- database passwords,
- tokens,
- API keys.

##### 2.3.1.42.2 Classification
These should be recognized as sensitive before deciding how to store/encrypt them.

##### 2.3.1.42.3 Connection
- Skill 2.3.2 specifically addresses encryption of sensitive environment variables.

#### 2.3.1.43 Secrets

##### 2.3.1.43.1 Classification
- Secrets are high-sensitivity application data.

##### 2.3.1.43.2 Handling
Should generally not be:
- hard-coded,
- committed,
- logged,
- returned in API responses.

##### 2.3.1.43.3 Connection
- Skill 2.3.3 covers AWS secret-management services.

##### 2.3.1.44.2 Both Matter

#### 2.3.1.45 Classification Decision Flow

##### 2.3.1.45.1 Step 1 — Identify Data
What fields/objects/messages does the workload process?

##### 2.3.1.45.2 Step 2 — Identify Category
Does it contain:
- PII?
- PHI?
- financial data?
- credentials?
- proprietary/business-sensitive data?

##### 2.3.1.45.3 Step 3 — Determine Sensitivity
What is the consequence of:
- disclosure?
- modification?
- loss?

##### 2.3.1.45.4 Step 4 — Identify Obligations
- organizational policy?
- contractual requirement?
- legal/regulatory requirement?

##### 2.3.1.45.5 Step 5 — Apply Classification
Example:
- public,
- internal,
- confidential,
- restricted.

##### 2.3.1.45.6 Step 6 — Apply Controls
- access,
- encryption,
- secrets storage,
- masking,
- logging rules,
- retention,
- tenant isolation.

##### 2.3.1.45.7 Step 7 — Monitor
- audit access,
- discover unexpected sensitive data,
- review classification as data/use changes.

#### 2.3.1.46 Developer Decision Model

Before storing any field, ask:

1. **Do we need it?**
2. **Is it personal, health, financial, credential, or business-sensitive data?**
3. **Who needs plaintext access?**
4. **Can it appear in logs/traces?**
5. **Must it be encrypted with stronger controls?**
6. **How long must it exist?**
7. **Can it be masked/sanitized outside the primary workflow?**
8. **Does tenant ownership constrain access?**

#### 2.3.1.47 Common Exam Traps

##### 2.3.1.47.1 "Classification Means Encryption"
- False.
- Classification determines which controls are appropriate.

##### 2.3.1.47.2 "PII Means Only SSN/Passport Numbers"
- False.
- PII is broader.

##### 2.3.1.47.3 "PHI and PII Are Unrelated"
- False.
- Health information can also identify/relate to individuals.

##### 2.3.1.47.4 "Credentials Are Not Data"
- False.
- Credentials are highly sensitive data.

##### 2.3.1.47.5 "Encrypted Data No Longer Needs Classification"
- False.
- Encryption is a control; the underlying data remains sensitive.

##### 2.3.1.47.6 "Internal Network Means Data Is Non-Sensitive"
- False.

##### 2.3.1.47.7 "Development Copy of Production PII Is Less Sensitive"
- False.

##### 2.3.1.47.8 "Logs Are Outside the Data-Classification Scope"
- False.

##### 2.3.1.47.9 "Backups Change Classification"
- False.

##### 2.3.1.47.10 "Macie Defines the Organization's Classification Policy"
- False.
- Macie discovers sensitive-data patterns; organization defines classification/governance.

##### 2.3.1.47.11 "Macie Scans Every AWS Data Store Natively"
- False.
- Its core sensitive-data discovery scope is S3.

##### 2.3.1.47.12 "Tags Are a Safe Place for Sensitive Values"
- False.

#### 2.3.1.51 Exam-Level Knowledge Frame

Know these cold:

**Data classification**
→ categorize data based on sensitivity/criticality.

**PII**
→ information capable of identifying or relating to individuals.

**PHI**
→ sensitive health-related personal information in applicable health/privacy context.

**Credentials**
→ passwords, keys, tokens and similar access-enabling data are sensitive.

**Classification drives**
→ access + encryption + retention + logging + masking + sanitization.

**Amazon Macie**
→ discovers sensitive data in S3.

**Managed data identifiers**
→ AWS-provided detectors for categories such as credentials, financial data, PII and PHI.

**Custom data identifiers**
→ organization-specific detection patterns.

**Allow lists**
→ known exceptions Macie should ignore.

**Classification does not disappear after encryption**
→ encrypted PII is still PII.

**Copies inherit sensitivity**
→ logs, backups, exports and development copies can remain sensitive.

Fastest exam discriminator:

**Question asks "what kind of data is this?"**
→ classification.

**Question asks "find PII/credentials in S3"**
→ Macie.

**Question asks "how should sensitive value be stored?"**
→ subsequent Task 2.3 controls such as encryption/secrets management.

Final principle:

**First identify and classify the data. Then apply controls proportionate to its sensitivity, ownership, regulatory context, and business impact throughout the entire data lifecycle.**
