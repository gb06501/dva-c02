### 2.3.4 Sanitize sensitive data

#### 2.3.4.1 Exam and Task Context

##### 2.3.4.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.3 is **Manage sensitive data in application code**.
- Skill 2.3.4 is **Sanitize sensitive data**.
- The exam guide separates this from:
  - 2.3.5 → **Implement application-level data masking and sanitization**.
- Therefore 2.3.4 should establish the **purpose, boundaries, techniques, and decision model** for sanitization; 2.3.5 will focus more directly on implementing masking/sanitization in application logic.

##### 2.3.4.1.2 Core Question
- **Before sensitive or untrusted data crosses a boundary, what information should be removed, transformed, rejected, or protected so that the destination receives only safe and necessary data?**

#### 2.3.4.2 Core Mental Model

`DATA ENTERS OR LEAVES A TRUST BOUNDARY`
→ classify fields
→ validate structure
→ identify sensitive/untrusted content
→ apply appropriate transformation
→ emit only what destination needs

Possible actions:

`KEEP`
→ safe and required

`REDACT / ERASE`
→ sensitive value not required

`MASK`
→ partial representation required

`ENCRYPT`
→ original value must remain recoverable by authorized users

`REJECT`
→ malformed or unacceptable input

Core principle:

**Sanitization minimizes unnecessary exposure; it is not merely encryption.**

#### 2.3.4.3 What Sanitization Means

Sanitization is the process of making data safe for a particular destination or purpose by:
- removing sensitive fields,
- replacing sensitive values,
- masking portions,
- transforming values,
- validating/rejecting unacceptable input,
- preventing sensitive information from appearing in outputs.

The correct operation depends on whether the original value must remain usable or recoverable.

#### 2.3.4.4 Classification Comes First

From 2.3.1:

`DATA`
→ identify
→ classify

Then:

`CLASSIFICATION`
→ determine sanitization rule.

Examples:

`password`
→ remove completely

`credit card`
→ perhaps retain last four digits only

`customer ID`
→ may remain if required and policy allows

`access token`
→ remove completely

`health information`
→ remove/mask unless destination explicitly requires it

#### 2.3.4.5 Sanitization Is Contextual

The same field can require different handling at different boundaries.

Example:

`email address`

Inside authorized business workflow:
→ plaintext may be required.

Application log:
→ probably remove/mask.

Analytics export:
→ pseudonymize/remove depending on purpose.

Public API response:
→ include only if caller is authorized and response requires it.

Therefore:

**Safe data is destination-dependent.**

#### 2.3.4.6 Major Sanitization Boundaries

Developers should think about:

`INPUT`
→ external request/event

`PROCESSING`
→ application memory/business logic

`OUTPUT`
→ API/event/message

`OBSERVABILITY`
→ logs/traces/metrics

`ERROR HANDLING`
→ exceptions/error responses

`ANALYTICS`
→ exports/reporting

`NON-PRODUCTION`
→ test/debug data

Every boundary can create a new sensitive-data copy.

#### 2.3.4.7 Redaction / Erasure

##### 2.3.4.7.1 Meaning
- Remove or replace sensitive information so the original value is no longer present in the sanitized representation.

Example:

`"password": "secret123"`

becomes:

`"password": "*****"`

or the field is omitted.

##### 2.3.4.7.2 AWS Powertools Terminology
- Powertools for AWS Lambda Data Masking supports **erase** operations.
- Erasing is irreversible for that transformed value.

##### 2.3.4.7.3 Best Fit
- logs,
- diagnostics,
- responses where value is unnecessary,
- analytics copies that do not need original sensitive field.

#### 2.3.4.8 Masking

##### 2.3.4.8.1 Meaning
- Hide some or all sensitive information while preserving a useful representation.

Examples:

`4111111111111111`
→ `************1111`

`john@example.com`
→ partially obscured representation

##### 2.3.4.8.2 Purpose
- Human recognition without exposing full value.

##### 2.3.4.8.3 Connection
- 2.3.5 expands application-level masking implementation.

#### 2.3.4.9 Encryption

##### 2.3.4.9.1 Meaning
- Transform plaintext into ciphertext using cryptographic keys.

##### 2.3.4.9.2 Difference from Erasure
Encryption:
→ reversible with authorized key.

Erasure/redaction:
→ original value intentionally unavailable from sanitized copy.

##### 2.3.4.9.3 AWS Powertools
- Data Masking utility supports encrypt/decrypt in addition to erase.

#### 2.3.4.10 Sanitization vs Encryption

`SANITIZATION`
→ minimize/remove sensitive content for a purpose

`ENCRYPTION`
→ preserve data while protecting confidentiality

Example:

A password in an application log should normally be:
→ **removed**

not merely:
→ encrypted and logged.

##### 2.3.4.10.1 Exam Principle
**If downstream system does not need the sensitive value, do not send/store it merely because you can encrypt it.**

#### 2.3.4.11 Sanitization vs Validation

`VALIDATION`
→ Is input structurally/semantically acceptable?

`SANITIZATION`
→ What content is safe/necessary to retain or expose?

Example:

Request:
`{"email":"a@b.com","password":"secret"}`

Validation:
→ required fields and schema valid.

Sanitized logging:
`{"email":"a@b.com","password":"*****"}`

These are complementary controls.

#### 2.3.4.12 API Gateway Request Validation

##### 2.3.4.12.1 AWS Capability
API Gateway REST APIs can validate:
- required request parameters,
- request body against a configured model/schema.

##### 2.3.4.12.2 Failure
- Invalid request can be rejected before backend integration.
- API Gateway returns a 400 response.

##### 2.3.4.12.3 Boundary
- API Gateway validation is **not** application-specific sanitization.
- Backend still owns semantic validation and sensitive-data handling.

#### 2.3.4.13 Input Sanitization

Input from users or external systems is untrusted.

Typical flow:

`external input`
→ validate expected schema/type/size
→ reject unexpected values
→ safely process content
→ never trust input merely because API Gateway accepted it.

##### 2.3.4.13.1 Important
- Do not "sanitize" arbitrary malicious SQL by trying to strip strings and then concatenate it into SQL.
- Use safe APIs such as parameterized database operations.

#### 2.3.4.14 Injection Prevention

##### 2.3.4.14.1 SQL Injection
- Avoid constructing database statements from raw untrusted strings.
- Use parameterized/prepared operations supported by database libraries.

##### 2.3.4.14.2 XSS
- Treat untrusted output according to its rendering context.
- Appropriate encoding/escaping is generally destination/context specific.

##### 2.3.4.14.3 AWS WAF
- AWS WAF can detect/block request patterns such as:
  - SQL injection,
  - cross-site scripting.

##### 2.3.4.14.4 Critical
**WAF complements application security; it does not replace secure coding and sanitization.**

#### 2.3.4.15 Allowlist Mindset

Safer input handling:

`KNOWN EXPECTED FORMAT`
→ accept

rather than:

`KNOWN BAD STRINGS`
→ remove
→ assume remainder is safe.

Examples:
- known enum values,
- expected numeric range,
- schema-defined fields,
- permitted content types.

##### 2.3.4.15.1 Principle
**Prefer defining what is valid over trying to enumerate every malicious input.**

#### 2.3.4.16 Output Sanitization

Before returning an object:

`internal object`
→ select fields required by caller
→ remove internal/sensitive fields
→ apply authorization
→ mask where needed
→ serialize response.

##### 2.3.4.16.1 Bad Pattern
Return database/domain object directly.

It might contain:
- password hash,
- internal IDs,
- tenant metadata,
- secrets,
- administrative flags.

##### 2.3.4.16.2 Better
Use explicit response models/DTOs.

#### 2.3.4.17 Data Minimization

Sanitization follows a strong rule:

**If the destination does not need a field, remove it.**

This is usually stronger than:
- hiding it in UI only,
- encrypting an unnecessary copy,
- relying on consumers not to use it.

#### 2.3.4.18 Log Sanitization

Lambda application logs are normally sent to CloudWatch Logs when logging permissions are configured.

Therefore anything logged can become:
- persistent,
- searchable,
- accessible to operations/users,
- copied to downstream log systems.

Before logging:

`event / request / object`
→ remove credentials
→ remove tokens
→ remove passwords
→ remove unnecessary PII/PHI
→ log safe identifiers and operational context.

#### 2.3.4.19 Do Not Log Whole Events by Default

Bad:

`logger.info(event)`

Possible contents:
- Authorization header,
- cookies,
- request body,
- PII,
- tokens,
- API keys.

Better:

log explicitly selected fields:
- request ID,
- operation,
- resource identifier,
- status,
- duration,
- safe business identifier.

##### 2.3.4.19.1 Powertools Context
- Powertools Logger does not require full-event logging by default.
- Logging/redaction behavior should be deliberate.

#### 2.3.4.20 Structured Logging Helps Sanitization

Structured logs:

`{`
`  "requestId": "...",`
`  "customerId": "...",`
`  "operation": "createOrder"`
`}`

make it easier to:
- define allowed fields,
- transform specific values,
- consistently redact sensitive fields.

Compared with arbitrary concatenated strings, structured data is easier to sanitize reliably.

#### 2.3.4.21 Error Sanitization

Internal error:

`Database connection failed for user X with password Y at host Z`

External/log-safe version:

`Database authentication failed`
+ correlation/request ID.

##### 2.3.4.21.1 Do Not Expose
- credentials,
- secret values,
- stack details unnecessarily,
- internal service topology,
- raw database errors containing sensitive values.

#### 2.3.4.22 API Error Responses

Public error response should usually expose:
- safe error code,
- understandable message,
- correlation/request ID.

Internal diagnostic details can be logged separately after sanitization.

##### 2.3.4.22.1 Principle
**Client-facing errors and developer diagnostics have different information requirements.**

#### 2.3.4.23 HTTP Headers

Potentially sensitive:
- `Authorization`,
- cookies,
- session tokens,
- API keys,
- signed URLs/query parameters.

Do not blindly log all headers.

#### 2.3.4.24 Query Strings

Sensitive values in query strings can propagate into:
- access logs,
- proxies,
- tracing,
- browser history,
- monitoring.

##### 2.3.4.24.1 Design Rule
- Avoid putting secrets in URLs/query strings.
- Sanitize query parameters before logging.

#### 2.3.4.25 Event-Driven Applications

Sensitive data can appear in:
- SQS messages,
- SNS notifications,
- EventBridge events,
- Kinesis records,
- DynamoDB Streams.

##### 2.3.4.25.1 Producer Responsibility
- Publish only data consumers require.

##### 2.3.4.25.2 Consumer Responsibility
- Sanitize before logging, forwarding, or creating derivative events.

##### 2.3.4.25.3 Principle
**An event bus/queue does not change the classification of the payload.**

#### 2.3.4.26 Event Envelope vs Payload

Often operational metadata can be logged safely:

`event ID`
`source`
`event type`
`timestamp`

while business payload may contain sensitive data.

Useful pattern:

`LOG ENVELOPE METADATA`
→ avoid dumping full payload.

#### 2.3.4.27 Dead-Letter Queues

Failed messages can be copied into:
- SQS DLQ,
- other failure destinations.

##### 2.3.4.27.1 Consequence
- Sensitive payload remains sensitive in DLQ.
- Access/retention/encryption must reflect classification.

##### 2.3.4.27.2 Sanitization Decision
- Do not remove data needed for legitimate replay unless architecture permits it.
- Instead minimize payload at producer and protect failure storage appropriately.

#### 2.3.4.28 Tracing

Trace data can include:
- request metadata,
- annotations,
- custom metadata,
- exceptions.

##### 2.3.4.28.1 Rule
- Do not put secrets or sensitive payloads into trace attributes/metadata merely for debugging.

##### 2.3.4.28.2 Connection
- Observability is another data destination requiring sanitization.

#### 2.3.4.29 Metrics

Metrics should generally contain:
- numeric measurements,
- low-cardinality dimensions.

Do not use sensitive customer data as metric dimensions.

##### 2.3.4.29.1 Benefit
- privacy,
- cost/cardinality control,
- safer observability.

#### 2.3.4.30 AWS Lambda Powertools Data Masking

##### 2.3.4.30.1 Purpose
Powertools Data Masking can:
- erase,
- encrypt,
- decrypt
sensitive information.

##### 2.3.4.30.2 Field-Level Operations
- Sensitive fields in nested data structures can be targeted.

##### 2.3.4.30.3 Erasure
- Replaces sensitive information with a non-sensitive placeholder.
- Original erased value cannot be recovered from the transformed data.

##### 2.3.4.30.4 Exam Relevance
This provides a concrete AWS-supported application-level tool for the sanitization/masking skills.

#### 2.3.4.31 Powertools Erase Example — Conceptual

Input:

`{`
`  "customer": "Alice",`
`  "password": "secret"`
`}`

Sanitized:

`{`
`  "customer": "Alice",`
`  "password": "*****"`
`}`

##### 2.3.4.31.1 Use
- safe log/event/output copy where original password is unnecessary.

#### 2.3.4.32 Field-Level Sanitization

Rather than sanitizing an entire payload uniformly:

`customer.name`
→ keep

`customer.ssn`
→ erase/mask

`payment.card`
→ mask

`auth.token`
→ erase

`order.id`
→ keep

##### 2.3.4.32.1 Benefit
- retain useful operational/business context while protecting sensitive fields.

#### 2.3.4.33 Full-Payload Removal

Sometimes safest operation is not field-level masking.

If destination does not require payload:
- do not send/log payload at all.

Example:
- log `eventId` instead of sanitized copy of a huge customer record.

##### 2.3.4.33.1 Principle
**Avoid collecting data first and sanitizing later when you can avoid collecting/copying it entirely.**

#### 2.3.4.34 Irreversible vs Reversible Transformation

`ERASE / REDACT`
→ irreversible

`MASK`
→ generally intended for limited representation, not recovery

`ENCRYPT`
→ reversible with key

Choose based on downstream need.

##### 2.3.4.34.1 Decision
Does destination need original value later?

No:
→ erase/redact.

Only recognition:
→ mask.

Yes, authorized recovery:
→ encrypt.

#### 2.3.4.35 Tokenization / Pseudonymization Context

Another architectural approach can replace sensitive value with a non-sensitive or less-sensitive reference/token.

Example:

`customer identity`
→ internal opaque identifier.

##### 2.3.4.35.1 Benefit
- downstream systems may operate without original PII.

##### 2.3.4.35.2 Scope
- General security/privacy concept; not a dedicated DVA-C02 service requirement in the exam-guide skill.

#### 2.3.4.36 Non-Production Data

Before copying production data to:
- development,
- testing,
- troubleshooting,
- demos,

sanitize fields not required by those environments.

Preferred:
- synthetic data,
- masked data,
- anonymized/sanitized extracts.

##### 2.3.4.36.1 Principle
**Changing environment does not reduce classification.**

#### 2.3.4.37 Backups and Raw Archives

If sanitized dataset is created from sensitive source:

`raw source`
→ still sensitive

`sanitized derivative`
→ may have lower exposure requirements depending on transformation.

##### 2.3.4.37.1 Important
- Sanitizing a derivative does not sanitize the original backup/source.

#### 2.3.4.38 Sanitization Must Happen Before Exposure

Bad:

`log plaintext`
→ sanitize later in downstream processor.

The sensitive value has already crossed the boundary.

Better:

`sanitize in application`
→ emit safe log.

##### 2.3.4.38.1 Principle
**Sanitize before the first unnecessary copy is created.**

#### 2.3.4.39 Authorization Is Not Sanitization

Authorization:
→ determines whether caller may access data.

Sanitization:
→ determines what representation/content crosses boundary.

Both may apply:

`authorized user`
→ allowed customer record
→ response still omits internal secrets.

#### 2.3.4.40 Multi-Tenant Context

A tenant ID is not sufficient sanitization.

If Tenant A is not authorized to see Tenant B's data:
→ access must be denied.

Do not:
→ fetch Tenant B record
→ merely mask some fields
→ return it.

##### 2.3.4.40.1 Connection
- 2.3.6 handles tenant-aware data access.

#### 2.3.4.41 WAF vs Sanitization

AWS WAF:
→ filters malicious web requests/patterns.

Application sanitization:
→ protects sensitive/untrusted data at application boundaries.

##### 2.3.4.41.1 Example
WAF may block SQL injection pattern.

Application still must:
- validate input,
- use safe database APIs,
- sanitize logs/output.

#### 2.3.4.42 API Gateway vs Sanitization

API Gateway request validation:
→ schema/required-parameter checks.

Application:
→ business validation,
→ authorization,
→ sensitive-data sanitization.

##### 2.3.4.42.1 Exam Rule
**Gateway validation reduces invalid traffic but does not remove application responsibility.**

#### 2.3.4.43 Decision Flow

##### 2.3.4.43.1 Step 1 — Identify Boundary
Where is data going?
- log,
- API,
- event,
- analytics,
- test environment,
- external system.

##### 2.3.4.43.2 Step 2 — Classify Fields
- secret?
- PII?
- PHI?
- financial?
- internal?
- public?

##### 2.3.4.43.3 Step 3 — Ask What Destination Needs
- full value?
- partial representation?
- identifier only?
- no sensitive value?

##### 2.3.4.43.4 Step 4 — Choose Action
- keep,
- reject,
- erase/redact,
- mask,
- encrypt.

##### 2.3.4.43.5 Step 5 — Apply Before Crossing Boundary
- application code/middleware,
- response transformation,
- logging formatter,
- event producer.

##### 2.3.4.43.6 Step 6 — Verify
- tests ensure sensitive fields do not leak,
- inspect logs/traces/errors,
- review downstream copies.

#### 2.3.4.44 Exam Scenario Mapping

##### 2.3.4.44.1 "Password appears in CloudWatch Logs"
→ sanitize/redact before logging.

##### 2.3.4.44.2 "Need last four digits of card for support"
→ mask rather than expose full card.

##### 2.3.4.44.3 "Need original sensitive value later"
→ encryption, not irreversible erase.

##### 2.3.4.44.4 "API receives malformed request"
→ request validation/reject input.

##### 2.3.4.44.5 "Protect API from common SQLi/XSS patterns"
→ AWS WAF can provide an additional protection layer.

##### 2.3.4.44.6 "Backend logs entire API Gateway event"
→ avoid; select safe fields and redact sensitive values.

##### 2.3.4.44.7 "Need sanitized copy of nested object in Lambda"
→ application-level masking/erase; Powertools Data Masking is a relevant AWS-supported utility.

#### 2.3.4.45 Common Exam Traps

##### 2.3.4.45.1 "Encryption and Sanitization Are the Same"
- False.

##### 2.3.4.45.2 "Encrypted Logs May Safely Contain Passwords"
- False.

##### 2.3.4.45.3 "API Gateway Validation Fully Sanitizes Requests"
- False.

##### 2.3.4.45.4 "AWS WAF Replaces Secure Application Code"
- False.

##### 2.3.4.45.5 "Authorized Caller Should Receive Entire Internal Object"
- False.
- Return only required fields.

##### 2.3.4.45.6 "Sanitize After Writing to Logs"
- Too late for the original log copy.

##### 2.3.4.45.7 "Masking Is Appropriate When Original Value Must Be Cryptographically Recoverable"
- Not by itself; use encryption for recoverability.

##### 2.3.4.45.8 "Deleting Sensitive Field From API Response Also Deletes It From Source"
- False.

##### 2.3.4.45.9 "Queue/Event Payload Is Safe Because Service Is Internal"
- False.

##### 2.3.4.45.10 "A DLQ Changes Data Classification"
- False.

##### 2.3.4.45.11 "Test Environments Can Use Raw Production PII Because They Are Non-Production"
- False.

##### 2.3.4.45.12 "Sanitization Can Replace Authorization"
- False.

#### 2.3.4.49 Exam-Level Knowledge Frame

Know these cold:

**Sanitize**
→ make data safe for its destination/purpose.

**Redact/erase**
→ remove sensitive value irreversibly from transformed representation.

**Mask**
→ hide all/part while retaining useful representation.

**Encrypt**
→ reversible confidentiality protection.

**Validate**
→ determine whether input meets expected rules/schema.

**Data minimization**
→ do not transmit/store/log fields destination does not need.

**CloudWatch logs**
→ persistent data destination; sanitize before logging.

**API Gateway request validation**
→ validates basic request structure/schema; does not replace application sanitization.

**AWS WAF**
→ defense-in-depth against malicious request patterns; does not replace secure coding.

**Powertools Data Masking**
→ AWS-supported developer utility that can erase, encrypt, and decrypt sensitive fields/data.

Fastest exam discriminator:

**Destination does not need original value?**
→ erase/redact.

**Destination needs recognizable partial value?**
→ mask.

**Authorized consumer must recover original?**
→ encrypt.

**Input is malformed/unexpected?**
→ validate/reject.

Final principle:

**Classify first, minimize second, and sanitize before data crosses a boundary. Keep only what the destination needs; remove or mask what it does not, and use encryption only when the original value must remain recoverable.**
