### 2.3.3 Use secret management services to secure sensitive data

#### 2.3.3.1 Exam and Task Context

##### 2.3.3.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.3 is **Manage sensitive data in application code**.
- Skill 2.3.3 is **Use secret management services to secure sensitive data**.
- 2.3.1 established how to identify/classify sensitive data.
- 2.3.2 covered sensitive environment variables.
- 2.3.3 moves true secrets out of application code/configuration and into purpose-built managed storage.

##### 2.3.3.1.2 Core Question
- **Where should an application store credentials and other secrets, how should it retrieve them securely, and when should Secrets Manager be chosen over Parameter Store?**

#### 2.3.3.2 Core Mental Model

Bad:

`SOURCE CODE / CONFIG FILE / ENVIRONMENT VARIABLE`
→ contains long-lived credential

Better:

`APPLICATION`
→ authenticates with IAM role
→ retrieves secret at runtime
→ secret store authorizes request
→ KMS protects secret at rest
→ application uses secret
→ does not log/store unnecessary copies

Core principle:

**The application should possess permission to retrieve a secret, not contain the secret itself.**

#### 2.3.3.3 What Is a Secret?

Typical secrets:
- database username/password,
- API key,
- OAuth client secret,
- authentication token,
- private key,
- certificate private material,
- third-party service credential.

A secret is different from ordinary configuration because disclosure can grant authority or access.

#### 2.3.3.4 Primary AWS Choices

For this skill, the two key AWS services are:

`AWS Secrets Manager`
→ purpose-built secret lifecycle management

`AWS Systems Manager Parameter Store`
→ hierarchical configuration storage
→ `SecureString` supports encrypted sensitive configuration

The exam decision is not simply "which can encrypt a string?"

It is:

**What lifecycle does this value require?**

#### 2.3.3.5 AWS Secrets Manager

##### 2.3.3.5.1 Purpose
- Store, retrieve, manage, and rotate secrets.

##### 2.3.3.5.2 Strong Fits
- database credentials,
- API keys,
- OAuth tokens,
- private keys/certificates,
- credentials requiring rotation,
- secrets requiring cross-account access,
- secrets requiring fine-grained auditability.

##### 2.3.3.5.3 Encryption
- Secrets Manager encrypts secrets at rest using AWS KMS.

#### 2.3.3.6 Secret Retrieval

Typical application flow:

`Lambda / EC2 / ECS workload`
→ IAM role credentials
→ `secretsmanager:GetSecretValue`
→ Secrets Manager
→ authorized secret value

##### 2.3.3.6.1 Key Point
- Do not hard-code AWS access keys to retrieve the secret.
- Use workload IAM roles/temporary credentials.

#### 2.3.3.7 `GetSecretValue`

##### 2.3.3.7.1 Purpose
- Retrieve a secret value.

##### 2.3.3.7.2 IAM
Application normally needs:
- `secretsmanager:GetSecretValue`

on:
- specific secret ARN.

##### 2.3.3.7.3 KMS
If the secret uses a customer managed KMS key, the caller can also require:
- `kms:Decrypt`

for that key.

#### 2.3.3.8 Least Privilege

Bad:

`secretsmanager:*`
→ `Resource: *`

Better:

`secretsmanager:GetSecretValue`
→ specific secret ARN

and only required KMS permissions.

##### 2.3.3.8.1 Principle
**Application that consumes a secret normally does not need permission to modify, rotate, or delete it.**

#### 2.3.3.9 Secret ARN

##### 2.3.3.9.1 Resource-Level Authorization
- IAM policies can scope access to specific secrets.

##### 2.3.3.9.2 Benefit
- Application A can retrieve Secret A without receiving access to all secrets.

#### 2.3.3.10 KMS Encryption

Secrets Manager uses AWS KMS for encryption at rest.

Choices include:
- AWS managed key,
- customer managed KMS key.

##### 2.3.3.10.1 Customer Managed Key
Use when requirements need:
- explicit key policy,
- cross-account use,
- stronger separation of duties,
- customer-controlled key lifecycle.

##### 2.3.3.10.2 Connection
- KMS mechanics were covered in Task 2.2.

#### 2.3.3.11 Secret Rotation

##### 2.3.3.11.1 Meaning
Rotation updates:
1. the stored secret,
2. the credential in the target database/service.

##### 2.3.3.11.2 Critical
**Changing only the Secrets Manager value is not credential rotation if the target system still expects the old credential.**

#### 2.3.3.12 Secrets Manager Rotation Models

Current AWS Secrets Manager supports:
- managed rotation for supported managed secrets,
- managed external-secret rotation for supported integrations,
- Lambda-function-based rotation for other secret types.

##### 2.3.3.12.1 Exam Mindset
Older material often equates Secrets Manager rotation entirely with Lambda.
Current AWS behavior is broader.

#### 2.3.3.13 Lambda-Based Rotation

Conceptual flow:

`Secrets Manager`
→ invokes rotation Lambda
→ create new secret
→ update target service/database
→ test new secret
→ mark new version current

##### 2.3.3.13.1 Four Rotation Steps
- `createSecret`
- `setSecret`
- `testSecret`
- `finishSecret`

#### 2.3.3.14 Secret Versions

Secrets Manager can maintain multiple secret versions.

Important staging labels:

`AWSCURRENT`
→ current secret

`AWSPENDING`
→ new value during rotation

`AWSPREVIOUS`
→ previous value after rotation, when applicable

##### 2.3.3.14.1 Benefit
- Supports controlled transition and recovery during rotation.

#### 2.3.3.15 Rotation Is Designed for Idempotency

##### 2.3.3.15.1 Rotation Token
- Rotation workflows identify the pending secret version using a unique token/version identifier.

##### 2.3.3.15.2 Why
- Rotation steps can be retried safely.

##### 2.3.3.15.3 Developer Relevance
- Rotation functions must tolerate repeated invocation of a step.

#### 2.3.3.16 Database Credentials

Secrets Manager is a strong fit for:
- Amazon RDS credentials,
- Aurora credentials,
- other database credentials.

##### 2.3.3.16.1 Rotation
- Can update password in both Secrets Manager and database.

##### 2.3.3.16.2 Exam Clue
**Store and automatically rotate database password**
→ Secrets Manager.

#### 2.3.3.17 Single-User Rotation

##### 2.3.3.17.1 Concept
- Rotate password for the same database user.

##### 2.3.3.17.2 Benefit
- Simpler model.

##### 2.3.3.17.3 Consideration
- Short transition period can exist while credential changes propagate.

#### 2.3.3.18 Alternating-User Rotation

##### 2.3.3.18.1 Concept
- Alternate between two database users/credentials.

##### 2.3.3.18.2 Benefit
- Can support workflows where old connections need continuity during rotation.

##### 2.3.3.18.3 Exam Depth
- Understand why alternating credentials exist; implementation internals are secondary.

#### 2.3.3.19 Runtime Retrieval vs Deployment-Time Injection

##### 2.3.3.19.1 Runtime Retrieval
Application retrieves secret when needed.

Benefits:
- current secret can be used after rotation,
- no deployment required merely to update secret,
- source/template does not contain plaintext.

##### 2.3.3.19.2 Deployment-Time Injection
Secret copied into:
- environment variable,
- configuration file,
- container/task definition.

Risk:
- creates another copy,
- rotation can require restart/redeployment,
- plaintext can become visible through configuration interfaces.

##### 2.3.3.19.3 Preferred Mental Model
**Reference/retrieve the secret rather than duplicate it.**

#### 2.3.3.20 Lambda + Secrets Manager

Flow:

`Lambda execution role`
→ `GetSecretValue`
→ Secrets Manager
→ secret
→ connect to dependency

##### 2.3.3.20.1 IAM
- execution role gets only required secret access.

##### 2.3.3.20.2 Benefit
- secret is not hard-coded in function package.

#### 2.3.3.21 AWS Parameters and Secrets Lambda Extension

##### 2.3.3.21.1 Purpose
- Retrieve values from:
  - Secrets Manager,
  - Parameter Store
through a local HTTP endpoint available to the Lambda execution environment.

##### 2.3.3.21.2 Benefit
- runtime-agnostic,
- built-in caching,
- fewer direct SDK calls.

##### 2.3.3.21.3 Cache
- Secret values can be cached in the execution environment.

#### 2.3.3.22 Powertools for AWS Lambda Parameters Utility

##### 2.3.3.22.1 Purpose
- Application-library approach for retrieving parameters/secrets.

##### 2.3.3.22.2 Providers
Can integrate with services including:
- Secrets Manager,
- Parameter Store,
- AppConfig.

##### 2.3.3.22.3 Benefit
- caching and transformations can be integrated into application code.

#### 2.3.3.23 Secret Caching

Without cache:

`every invocation`
→ Secrets Manager API
→ latency + API cost

With cache:

`invocation`
→ local cache
→ Secrets Manager only when cache expires

##### 2.3.3.23.1 Benefits
- lower latency,
- fewer API calls,
- lower cost.

##### 2.3.3.23.2 Trade-Off
- cached value may briefly become stale after rotation.

#### 2.3.3.24 Rotation vs Cache TTL

If secret rotates:

`Secrets Manager`
→ new `AWSCURRENT`

but:

`application cache`
→ may still hold old value until TTL expires.

##### 2.3.3.24.1 Decision
Balance:
- freshness,
- performance,
- cost.

##### 2.3.3.24.2 Exam Principle
**Caching improves performance but introduces secret-freshness considerations.**

#### 2.3.3.25 Parameter Store

##### 2.3.3.25.1 Purpose
- Central hierarchical store for application configuration.

Parameter types:
- `String`
- `StringList`
- `SecureString`

##### 2.3.3.25.2 Typical Uses
- AMI IDs,
- endpoint URLs,
- resource identifiers,
- environment configuration,
- tuning parameters,
- encrypted configuration values.

#### 2.3.3.26 `SecureString`

##### 2.3.3.26.1 Purpose
- Store configuration values requiring encryption.

##### 2.3.3.26.2 Encryption
- Parameter Store uses AWS KMS.

##### 2.3.3.26.3 Key Options
- AWS managed key,
- customer managed symmetric KMS key.

##### 2.3.3.26.4 Important
- Only the parameter value is encrypted.
- Parameter name, description, and other metadata are not encrypted.

#### 2.3.3.27 Retrieving `SecureString`

Typical API:

`GetParameter`
→ `WithDecryption=true`

Flow:

`application IAM role`
→ Parameter Store
→ KMS decrypt
→ plaintext parameter

##### 2.3.3.27.1 Security
- Do not log the retrieved value.

#### 2.3.3.28 Parameter Store Hierarchies

Example:

`/myapp/prod/database/host`
`/myapp/prod/database/username`
`/myapp/prod/feature-x/enabled`

##### 2.3.3.28.1 Benefit
- Organizes configuration by:
  - application,
  - stage,
  - subsystem.

##### 2.3.3.28.2 IAM
- Hierarchies can support structured permission models.

#### 2.3.3.29 Secrets Manager vs Parameter Store

| Requirement | Secrets Manager | Parameter Store |
| --- | --- | --- |
| Database password | Preferred | Possible SecureString |
| API key/token | Preferred | Possible SecureString |
| Static application config | Usually unnecessary | Strong fit |
| Automatic secret rotation | Strong fit | Not native secret rotation |
| Cross-account secret use | Strong fit | More limited/context-dependent |
| Fine-grained secret audit/lifecycle | Strong fit | Configuration-oriented |
| Hierarchical configuration | Possible naming conventions | Strong fit |
| KMS encryption | Yes | `SecureString` |
| Runtime retrieval | Yes | Yes |

#### 2.3.3.30 AWS Recommendation

Current AWS Systems Manager documentation explicitly recommends:

**Secrets Manager**
for credentials such as:
- usernames/passwords,
- database credentials,
- API keys,
- tokens,
especially when requiring:
- automatic rotation,
- cross-account access,
- fine-grained audit logging.

Use Parameter Store primarily for:
- configuration,
- encrypted configuration through `SecureString`.

#### 2.3.3.31 Parameter Store Does Not Provide Native Automatic Secret Rotation

##### 2.3.3.31.1 Important
- Parameter Store has parameter policies and lifecycle capabilities.
- It does not provide Secrets Manager's automatic credential-rotation service.

##### 2.3.3.31.2 Integration
- Parameter Store can reference Secrets Manager secrets.

##### 2.3.3.31.3 Exam Clue
**Automatic credential rotation**
→ Secrets Manager.

#### 2.3.3.32 Parameter Policies

Advanced Parameter Store parameters can use policies such as:
- expiration,
- expiration notification,
- no-change notification.

##### 2.3.3.32.1 Important
These are **not equivalent to automatic secret rotation**.

#### 2.3.3.33 Secrets Manager Resource Policies

##### 2.3.3.33.1 Purpose
- Secrets can have resource-based policies.

##### 2.3.3.33.2 Use
- cross-account access,
- explicit principal authorization.

##### 2.3.3.33.3 Connection
- Similar multi-policy thinking to cross-account KMS from 2.2.6.

#### 2.3.3.34 Cross-Account Secret Access

Typical model:

`Account A`
→ owns secret
→ secret resource policy trusts Account B role
→ customer managed KMS key permits Account B role

`Account B role`
→ IAM policy allows `GetSecretValue`
→ IAM/KMS permissions permit decrypt

##### 2.3.3.34.1 Important
Cross-account encrypted secret can involve both:
- Secrets Manager authorization,
- KMS authorization.

#### 2.3.3.35 Customer Managed KMS Key for Cross-Account Secrets

##### 2.3.3.35.1 Why
- Cross-account decryption requires key policy control.

##### 2.3.3.35.2 Therefore
- Customer managed KMS key is normally required for explicit cross-account secret sharing.

##### 2.3.3.35.3 Connection
- Direct application of 2.2.6.

#### 2.3.3.36 CloudTrail

##### 2.3.3.36.1 Audit
- Secrets Manager API activity can be recorded in CloudTrail.

##### 2.3.3.36.2 Useful Events
- secret retrieval,
- secret updates,
- rotation configuration,
- deletion,
- resource-policy changes.

##### 2.3.3.36.3 Important
- Never put secret values into request parameters/fields that AWS documentation warns may be logged.

#### 2.3.3.37 Secret Names and Metadata

##### 2.3.3.37.1 Metadata Is Not the Secret Store
Avoid putting sensitive values into:
- secret names,
- descriptions,
- tags.

##### 2.3.3.37.2 Why
- Metadata can appear in logs, consoles, inventory, billing/diagnostic systems.

#### 2.3.3.38 Secrets in Source Code

Bad:

`const password = "..."`

Problems:
- source-control history,
- forks/clones,
- build artifacts,
- code review,
- logs,
- developer machines.

Better:

`application`
→ IAM role
→ secret manager
→ runtime secret

#### 2.3.3.39 Secrets in Git History

##### 2.3.3.39.1 If Exposed
- Removing the line from current source is insufficient.

##### 2.3.3.39.2 Response
- revoke/rotate credential,
- remove from repository/history where appropriate,
- investigate use,
- replace with managed secret retrieval.

##### 2.3.3.39.3 Principle
**Exposed secret is a credential incident, not merely a code-cleanup task.**

#### 2.3.3.40 Secrets in Logs

Never log:
- `GetSecretValue` result,
- database password,
- token,
- API key,
- private key.

##### 2.3.3.40.1 Rotation Lambda
AWS explicitly warns rotation-function developers to ensure debug/log statements do not expose sensitive information.

#### 2.3.3.41 Secrets in Exceptions

Bad:

`Authentication failed using password <secret>`

Better:

`Authentication failed for database connection`

with:
- correlation ID,
- dependency name,
- error category,
without secret.

#### 2.3.3.42 Secrets in URLs

##### 2.3.3.42.1 Risk
Credentials embedded in URLs can leak through:
- logs,
- proxies,
- tracing,
- browser history,
- diagnostics.

##### 2.3.3.42.2 Principle
- Do not encode secrets into observable metadata unnecessarily.

#### 2.3.3.43 Secrets and IAM Roles

##### 2.3.3.43.1 Best Pattern
Use:
- Lambda execution role,
- EC2 instance profile,
- ECS task role,
- EKS workload identity/role mechanisms,

to authenticate to AWS.

##### 2.3.3.43.2 Then
Use IAM authorization to retrieve application secrets.

##### 2.3.3.43.3 Key Principle
**Do not store AWS access keys as the mechanism for obtaining another secret when workload roles can be used.**

#### 2.3.3.44 Secret Zero

##### 2.3.3.44.1 Problem
How does application authenticate to the secret store without storing another secret?

##### 2.3.3.44.2 AWS Answer
- IAM role / temporary AWS credentials.

##### 2.3.3.44.3 Mental Model

`AWS workload identity`
→ authorizes secret retrieval
→ no hard-coded bootstrap credential.

#### 2.3.3.45 RDS IAM Authentication Context

##### 2.3.3.45.1 Alternative
Some database scenarios can avoid long-lived database passwords by using IAM database authentication.

##### 2.3.3.45.2 Exam Mindset
Before managing a static secret, ask:
**Can the architecture replace the secret with temporary identity-based credentials?**

##### 2.3.3.45.3 Scope
- Secret management remains the focus; IAM database authentication is an architectural alternative.

#### 2.3.3.46 Temporary Credentials vs Stored Secrets

Prefer where possible:

`temporary identity credential`
over
`long-lived static credential`

Examples:
- IAM role credentials instead of AWS access keys.
- IAM-auth tokens where service supports them.

##### 2.3.3.46.1 Why
- smaller exposure window,
- no manual static-secret distribution.

#### 2.3.3.47 Secrets Manager Rotation and Application Design

A rotation-capable application should:
- retrieve current secret dynamically,
- avoid permanently caching it,
- handle authentication failure/retry appropriately,
- refresh cache after rotation,
- avoid assuming credential never changes.

#### 2.3.3.48 Availability and Caching

##### 2.3.3.48.1 Direct API Every Time
Advantages:
- freshest secret.

Disadvantages:
- extra latency,
- more API calls,
- dependency on service call for each retrieval.

##### 2.3.3.48.2 Cache
Advantages:
- faster,
- cheaper,
- fewer external calls.

Disadvantages:
- stale-secret window.

##### 2.3.3.48.3 Design
- choose TTL based on rotation/freshness requirements.

#### 2.3.3.49 Secret Deletion

##### 2.3.3.49.1 Lifecycle
Secrets should have controlled deletion rather than indefinite accumulation.

##### 2.3.3.49.2 Risk
- deleting secret still used by workload causes outage.

##### 2.3.3.49.3 Principle
- verify consumers before deletion.

#### 2.3.3.50 Multi-Environment Design

Example:

`/dev`
→ dev secret

`/test`
→ test secret

`/prod`
→ prod secret

##### 2.3.3.50.1 Rule
- Do not reuse production credentials in development/test.

##### 2.3.3.50.2 IAM
- roles should access only environment-appropriate secrets.

#### 2.3.3.51 Infrastructure as Code

##### 2.3.3.51.1 Good
IaC defines:
- secret resource,
- permissions,
- references.

##### 2.3.3.51.2 Bad
IaC contains:
- plaintext secret value committed to source.

##### 2.3.3.51.3 Dynamic References
CloudFormation can reference:
- Secrets Manager,
- Parameter Store,
without embedding plaintext directly in the template.

#### 2.3.3.52 Secret Rotation vs KMS Key Rotation

`SECRET ROTATION`
→ changes credential value
→ password/token changes in target service

`KMS KEY ROTATION`
→ changes cryptographic key material protecting secret at rest

##### 2.3.3.52.1 Critical Exam Distinction
These solve different problems.

##### 2.3.3.52.2 Example
Database password can rotate while KMS key stays same.

KMS key can rotate while database password stays same.

#### 2.3.3.53 Secret Rotation vs Environment Variable Update

Environment variable:
→ update Lambda configuration
→ possibly publish/deploy new version

Secrets Manager:
→ rotate secret independently
→ application retrieves current value

##### 2.3.3.53.1 Connection
- This is why 2.3.3 is the architectural progression from 2.3.2.

#### 2.3.3.54 Decision Flow

##### 2.3.3.54.1 Step 1 — Is It Sensitive?
If no:
→ ordinary configuration store may be sufficient.

##### 2.3.3.54.2 Step 2 — Is It a Credential/Secret?
If yes:
→ prefer Secrets Manager.

##### 2.3.3.54.3 Step 3 — Is It Encrypted Configuration?
If yes and rotation is not required:
→ Parameter Store `SecureString` may fit.

##### 2.3.3.54.4 Step 4 — Does It Need Automatic Rotation?
If yes:
→ Secrets Manager.

##### 2.3.3.54.5 Step 5 — Does It Need Cross-Account Secret Access?
→ Secrets Manager + resource policy + customer managed KMS key as required.

##### 2.3.3.54.6 Step 6 — How Does Workload Authenticate?
→ IAM role / temporary credentials.

##### 2.3.3.54.7 Step 7 — Runtime Retrieval
→ SDK / extension / Powertools / supported integration.

##### 2.3.3.54.8 Step 8 — Cache?
→ balance freshness vs latency/cost.

##### 2.3.3.54.9 Step 9 — Prevent Secondary Exposure
→ no logs, source, templates, URLs, debug output.

#### 2.3.3.55 Exam Scenario Mapping

##### 2.3.3.55.1 "Store DB password securely and rotate automatically"
→ Secrets Manager.

##### 2.3.3.55.2 "Store encrypted application configuration"
→ Parameter Store `SecureString`.

##### 2.3.3.55.3 "Lambda needs API key without hard-coding"
→ Secrets Manager + execution-role `GetSecretValue`.

##### 2.3.3.55.4 "Reduce Secrets Manager API calls from Lambda"
→ caching / Parameters and Secrets Lambda Extension / appropriate utility.

##### 2.3.3.55.5 "Secret changed but Lambda still uses old credential"
→ inspect cache TTL/version freshness.

##### 2.3.3.55.6 "Need secret from another account"
→ secret resource policy + IAM + customer managed KMS authorization.

##### 2.3.3.55.7 "Need static hierarchy of config values"
→ Parameter Store.

##### 2.3.3.55.8 "Avoid static AWS access key in app"
→ IAM role.

#### 2.3.3.56 Common Exam Traps

##### 2.3.3.56.1 "Secrets Manager and Parameter Store Are Identical"
- False.

##### 2.3.3.56.2 "SecureString Provides Native Automatic Credential Rotation"
- False.

##### 2.3.3.56.3 "Rotation Means Only Updating Stored Secret"
- False.
- Target credential must also change.

##### 2.3.3.56.4 "Lambda Must Store AWS Access Keys to Call Secrets Manager"
- False.
- Use execution role.

##### 2.3.3.56.5 "KMS Key Rotation Rotates Database Password"
- False.

##### 2.3.3.56.6 "Caching Has No Effect on Rotation"
- False.
- Cached secret can become temporarily stale.

##### 2.3.3.56.7 "Encrypting Secret Makes It Safe to Log"
- False.

##### 2.3.3.56.8 "Secret Name/Tag Can Safely Contain the Secret"
- False.

##### 2.3.3.56.9 "Deleting Secret From Git Fixes Exposure"
- False.
- Rotate/revoke exposed credential.

##### 2.3.3.56.10 "Application Needs Secret-Administration Permissions to Read Secret"
- False.

##### 2.3.3.56.11 "Environment Variable Is Always Simpler and Therefore Better"
- False.
- Secret lifecycle often favors runtime secret retrieval.

##### 2.3.3.56.12 "Parameter Store `String` Is Fine for Passwords"
- False.
- Use `SecureString`; AWS recommends Secrets Manager for true credentials/secrets.

#### 2.3.3.60 Exam-Level Knowledge Frame

Know these cold:

**Secrets Manager**
→ credentials/secrets + lifecycle + rotation.

**Parameter Store**
→ configuration hierarchy.

**`SecureString`**
→ KMS-encrypted parameter value.

**Database password / API key / token**
→ prefer Secrets Manager.

**Automatic credential rotation**
→ Secrets Manager.

**Runtime authentication to secret store**
→ IAM role, not hard-coded AWS keys.

**`GetSecretValue`**
→ retrieve Secrets Manager secret.

**`GetParameter` + `WithDecryption=true`**
→ retrieve decrypted `SecureString`.

**Secret rotation**
→ update secret AND target service credential.

**KMS rotation**
→ not the same as secret rotation.

**Caching**
→ reduces latency/API calls but may temporarily serve stale credentials after rotation.

**Cross-account secret**
→ resource authorization + IAM + KMS authorization.

Fastest exam discriminator:

**Is it configuration?**
→ Parameter Store.

**Is it a credential?**
→ Secrets Manager.

**Must it rotate automatically?**
→ Secrets Manager.

Final principle:

**Keep credentials out of code. Give the workload an IAM identity, authorize that identity to retrieve only the required secret at runtime, and use Secrets Manager when the value needs a true secret lifecycle such as rotation, cross-account access, or fine-grained auditing.**
