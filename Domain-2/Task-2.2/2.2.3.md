### 2.2.3 Describe differences between client-side encryption and server-side encryption

#### 2.2.3.1 Exam and Task Context

##### 2.2.3.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.2 is **Implement encryption by using AWS services**.
- Skill 2.2.3 is **Describe differences between client-side encryption and server-side encryption**.
- 2.2.1 established **where** encryption is needed: at rest vs in transit.
- 2.2.2 covered certificates and TLS trust.
- 2.2.3 now asks **where stored-data encryption and decryption happen, and who controls that process**.

##### 2.2.3.1.2 Core Question
- **Does the application encrypt data before AWS receives it, or does the AWS service encrypt data after receiving it?**

#### 2.2.3.2 Core Mental Model

There are two fundamentally different trust boundaries:

`CLIENT-SIDE ENCRYPTION`

`plaintext`
→ application/client encrypts
→ ciphertext crosses network
→ AWS service stores ciphertext

versus:

`SERVER-SIDE ENCRYPTION`

`plaintext`
→ protected in transit with TLS
→ AWS service receives plaintext
→ AWS service encrypts before persistence
→ ciphertext stored

The critical distinction is therefore:

**Who sees plaintext, who performs encryption, and who manages the encryption workflow?**

#### 2.2.3.3 Server-Side Encryption — SSE

##### 2.2.3.3.1 Definition
- AWS service performs encryption after receiving the data.
- Service decrypts data when an authorized request retrieves it.

##### 2.2.3.3.2 Typical Flow

`application plaintext`
→ HTTPS/TLS
→ `AWS service`
→ service-side encryption
→ `encrypted storage`

Read:

`encrypted storage`
→ service-side decryption
→ HTTPS/TLS
→ `application plaintext`

##### 2.2.3.3.3 Developer Experience
- Application normally sends and receives plaintext through the service API.
- Encryption/decryption at the storage boundary is transparent to application logic.

#### 2.2.3.4 Client-Side Encryption — CSE

##### 2.2.3.4.1 Definition
- Client/application encrypts data before sending it to AWS.

##### 2.2.3.4.2 Typical Flow

`application plaintext`
→ client-side encryption
→ `ciphertext`
→ HTTPS/TLS
→ `AWS service`
→ ciphertext stored

Read:

`ciphertext stored`
→ AWS returns ciphertext
→ client-side decryption
→ `application plaintext`

##### 2.2.3.4.3 Consequence
- Storage service does not need plaintext to persist the object/value.

#### 2.2.3.5 The Trust-Boundary Difference

##### 2.2.3.5.1 Server-Side
AWS service receives plaintext inside the protected AWS service request boundary.

Trust boundary:

`client`
→ plaintext sent over TLS
→ `AWS service trusted with plaintext`

##### 2.2.3.5.2 Client-Side
AWS storage service receives ciphertext.

Trust boundary:

`client/application trusted with plaintext`
→ ciphertext only
→ `AWS storage service`

##### 2.2.3.5.3 Exam Insight
If requirement says:

- **AWS/storage service must never receive plaintext**
- **encrypt before upload**
- **application controls encryption/decryption**

→ think **client-side encryption**.

#### 2.2.3.6 Server-Side Encryption Advantages

##### 2.2.3.6.1 Simplicity
- Little or no custom cryptographic application logic.

##### 2.2.3.6.2 Managed Integration
- AWS service handles:
  - encryption,
  - decryption,
  - storage integration.

##### 2.2.3.6.3 AWS KMS Integration
- Many AWS services can use KMS keys.

##### 2.2.3.6.4 Operational Benefit
- Less application-side key/data-key handling.

##### 2.2.3.6.5 Strong Default
- Prefer native server-side encryption when it satisfies the security and control requirements.

#### 2.2.3.7 Server-Side Encryption Trade-Off

##### 2.2.3.7.1 Plaintext Boundary
- AWS service receives data before performing storage encryption.

##### 2.2.3.7.2 Application Control
- Application has less control over the exact encryption workflow.

##### 2.2.3.7.3 Requirement Mismatch
- Not sufficient when policy explicitly requires encryption **before data leaves the application/client boundary**.

#### 2.2.3.8 Client-Side Encryption Advantages

##### 2.2.3.8.1 Stronger Application-Controlled Boundary
- Data is encrypted before upload.

##### 2.2.3.8.2 Storage Sees Ciphertext
- Storage service stores encrypted payload.

##### 2.2.3.8.3 Cryptographic Control
- Application can control:
  - encryption algorithm through supported SDK/library,
  - encryption context/metadata,
  - key source,
  - decryption behavior.

##### 2.2.3.8.4 Requirement Fit
Useful when:
- compliance requires pre-upload encryption,
- application must retain encryption control,
- storage service must not receive application plaintext.

#### 2.2.3.9 Client-Side Encryption Trade-Offs

##### 2.2.3.9.1 Complexity
Application must handle:
- encryption/decryption workflow,
- encryption metadata,
- key/data-key lifecycle,
- error handling.

##### 2.2.3.9.2 Service Features
- AWS service cannot inspect encrypted application payload unless application decrypts/provides plaintext.
- Some service-side processing/search/transformation features may become unavailable or less useful.

##### 2.2.3.9.3 Key Loss
- If application loses access to required decryption key/material, data can become permanently unusable.

#### 2.2.3.10 Encryption in Transit Still Matters

##### 2.2.3.10.1 Server-Side Encryption
- Plaintext travels from client to AWS service.
- TLS is essential to protect that path.

##### 2.2.3.10.2 Client-Side Encryption
- Payload itself is ciphertext before transport.
- HTTPS/TLS should still be used.

##### 2.2.3.10.3 Why TLS Still Matters
TLS also protects:
- request metadata,
- authentication headers,
- integrity,
- endpoint authenticity.

##### 2.2.3.10.4 Rule
**Client-side encryption does not replace TLS.**

#### 2.2.3.11 Amazon S3 as the Core Exam Example

S3 exposes the distinction particularly clearly.

`SSE`
→ S3 performs storage encryption.

`CSE`
→ application encrypts object before upload.

This makes S3 the primary mental model for this skill.

#### 2.2.3.12 S3 Server-Side Encryption

##### 2.2.3.12.1 Current Baseline
- Amazon S3 automatically encrypts new object uploads at rest.
- Current S3 default encryption uses SSE-S3 unless another encryption configuration is selected.

##### 2.2.3.12.2 Meaning
- Application uploads object.
- S3 encrypts before persistence.
- S3 decrypts transparently on authorized retrieval.

#### 2.2.3.13 SSE-S3

##### 2.2.3.13.1 Key Management
- S3 manages encryption keys.

##### 2.2.3.13.2 Developer Experience
- Minimal configuration.
- No KMS key permissions required for normal object encryption/decryption path.

##### 2.2.3.13.3 Fit
- Simple server-side encryption when additional KMS key control is not required.

#### 2.2.3.14 SSE-KMS

##### 2.2.3.14.1 Key Management
- Uses AWS KMS keys.

##### 2.2.3.14.2 Benefits
Compared with SSE-S3, KMS provides additional controls such as:
- key policies,
- IAM-based key authorization,
- auditability through CloudTrail,
- customer managed key options.

##### 2.2.3.14.3 Permissions
- Caller may require both:
  - S3 permission,
  - appropriate KMS permission.

##### 2.2.3.14.4 Example

`PutObject`
+
`kms:GenerateDataKey`
→ depending on operation/configuration.

Retrieval can require:

`GetObject`
+
`kms:Decrypt`

#### 2.2.3.15 S3 Bucket Keys

##### 2.2.3.15.1 Purpose
- S3 Bucket Keys can reduce AWS KMS request traffic/cost for SSE-KMS.

##### 2.2.3.15.2 Mental Model
Instead of requiring KMS interaction for each individual object encryption path in the same way:

`KMS`
→ bucket-level key material
→ object-level data keys

##### 2.2.3.15.3 Exam Clue
- **Reduce KMS request cost for S3 SSE-KMS** → consider **S3 Bucket Keys**.

#### 2.2.3.16 DSSE-KMS

##### 2.2.3.16.1 Current S3 Capability
- Amazon S3 supports dual-layer server-side encryption with AWS KMS keys:
  - **DSSE-KMS**.

##### 2.2.3.16.2 Purpose
- Applies two independent layers of encryption at the object level.

##### 2.2.3.16.3 Exam Scope
- Recognize it as an S3 server-side encryption option for requirements demanding multiple encryption layers.
- Do not confuse it with client-side encryption.

#### 2.2.3.17 SSE-C — Context

##### 2.2.3.17.1 Model
- Customer supplies encryption key with S3 request.
- S3 performs encryption/decryption.

##### 2.2.3.17.2 Therefore
- **SSE-C is still server-side encryption.**

##### 2.2.3.17.3 Why
- Encryption operation occurs in S3, not in client.

##### 2.2.3.17.4 Important Exam Trap
**Customer-provided key ≠ client-side encryption.**

#### 2.2.3.18 S3 Encryption Comparison

| Mode | Who encrypts data? | Key control | AWS receives plaintext payload? |
| --- | --- | --- | --- |
| SSE-S3 | S3 | S3 | Yes |
| SSE-KMS | S3 | KMS / customer key choice | Yes |
| DSSE-KMS | S3 | KMS | Yes |
| SSE-C | S3 | Customer supplies key | Yes |
| Client-side encryption | Client/application | Client/application/KMS-backed workflow | No, storage receives ciphertext |

#### 2.2.3.19 S3 Client-Side Encryption

##### 2.2.3.19.1 Pattern

`plaintext object`
→ client encryption library
→ encrypted object
→ `PutObject`
→ S3 stores ciphertext

##### 2.2.3.19.2 Retrieval

`GetObject`
→ encrypted object
→ client decryption library
→ plaintext

##### 2.2.3.19.3 AWS Tooling
- AWS provides client-side encryption SDK/library patterns for S3.
- Modern AWS guidance should be followed rather than implementing cryptography manually.

#### 2.2.3.20 AWS Encryption SDK

##### 2.2.3.20.1 Purpose
- Client-side encryption library designed to help applications encrypt/decrypt data using AWS-supported cryptographic patterns.

##### 2.2.3.20.2 Features
- Envelope encryption.
- Data-key management.
- Encryption metadata.
- Integration with AWS KMS keyrings/key providers.

##### 2.2.3.20.3 Developer Principle
- Prefer established AWS cryptographic SDKs/libraries over writing custom encryption algorithms/protocols.

#### 2.2.3.21 Client-Side Envelope Encryption

##### 2.2.3.21.1 Pattern

`KMS key`
→ generate/protect data key

`plaintext data key`
→ encrypt application data

`encrypted data key`
+
`encrypted application data`
→ stored together

##### 2.2.3.21.2 Decryption

`encrypted data key`
→ KMS decrypt
→ plaintext data key
→ decrypt ciphertext

##### 2.2.3.21.3 Benefit
- KMS protects key material.
- Application performs bulk encryption locally.

#### 2.2.3.22 KMS Does Not Mean Server-Side Encryption

##### 2.2.3.22.1 SSE-KMS
- AWS service uses KMS in server-side encryption workflow.

##### 2.2.3.22.2 Client-Side KMS
- Application can use KMS/data keys in client-side encryption workflow.

##### 2.2.3.22.3 Critical Rule
**KMS identifies the key-management mechanism, not where the payload encryption necessarily happens.**

#### 2.2.3.23 KMS Direct Encryption

##### 2.2.3.23.1 KMS Encrypt API
- KMS can directly encrypt small amounts of data within API size limits.

##### 2.2.3.23.2 Large Payload
- Use envelope encryption:
  - data key encrypts bulk data,
  - KMS protects data key.

##### 2.2.3.23.3 Exam Mindset
- Do not send large files to KMS `Encrypt`.
- Use data keys / encryption SDK.

#### 2.2.3.24 DynamoDB Server-Side Encryption

##### 2.2.3.24.1 Service Behavior
- DynamoDB encrypts data at rest.

##### 2.2.3.24.2 KMS
- DynamoDB encryption integrates with AWS KMS.

##### 2.2.3.24.3 Application
- Application normally sends plaintext item attributes over TLS.
- DynamoDB handles storage encryption transparently.

#### 2.2.3.25 DynamoDB Client-Side Encryption

##### 2.2.3.25.1 Requirement
- If specific attributes must remain unreadable to DynamoDB storage/service processing boundary, application can encrypt attributes before sending them.

##### 2.2.3.25.2 Trade-Off
Encrypted attributes may no longer work naturally for:
- querying,
- indexing,
- filtering,
- conditional expressions,
depending on what is encrypted.

##### 2.2.3.25.3 AWS Context
- AWS Database Encryption SDK provides client-side encryption patterns for supported database workloads including DynamoDB.

#### 2.2.3.26 AWS Database Encryption SDK

##### 2.2.3.26.1 Purpose
- Provides client-side encryption for database records/fields using AWS-supported cryptographic patterns.

##### 2.2.3.26.2 Benefit
- Fine-grained control over which attributes are encrypted.

##### 2.2.3.26.3 Trade-Off
- Application must understand which fields need to remain queryable/indexable.

#### 2.2.3.27 RDS / Aurora

##### 2.2.3.27.1 Server-Side At-Rest Encryption
- RDS/Aurora can encrypt database storage using AWS KMS-integrated mechanisms.

##### 2.2.3.27.2 Application-Level Encryption
- Application can additionally encrypt sensitive fields before writing them.

##### 2.2.3.27.3 Trade-Off
- Database cannot naturally operate on encrypted application fields without application-aware techniques.

##### 2.2.3.27.4 Distinction
- RDS storage encryption ≠ column/application encryption.

#### 2.2.3.28 EBS / EFS

##### 2.2.3.28.1 Native Encryption
- EBS and EFS provide service/storage-level encryption at rest.

##### 2.2.3.28.2 Application Encryption
- Application could encrypt file content itself before writing.

##### 2.2.3.28.3 Exam Focus
- Prefer native service encryption unless requirement explicitly needs application-controlled ciphertext.

#### 2.2.3.29 Lambda Environment Variables

##### 2.2.3.29.1 At Rest
- Lambda encrypts environment variables at rest.

##### 2.2.3.29.2 KMS
- Customer managed KMS key can provide additional key-control options.

##### 2.2.3.29.3 Client-Side Helper
- For sensitive values that must be encrypted before deployment/configuration, Lambda console/tooling supports encryption-helper workflows using KMS.

##### 2.2.3.29.4 Better Secret Pattern
- For actual secrets, Secrets Manager/Parameter Store may be more appropriate; this belongs mainly to Task 2.3.

#### 2.2.3.30 Who Manages Keys?

##### 2.2.3.30.1 Server-Side
Depending on mode:
- AWS service.
- AWS KMS.
- customer managed KMS key.
- customer-provided key for supported service modes.

##### 2.2.3.30.2 Client-Side
Application controls encryption workflow and key source:
- AWS KMS-backed data keys,
- application-managed key material,
- supported cryptographic SDK/keyring.

##### 2.2.3.30.3 Important
- "Customer managed KMS key" does not mean customer directly handles raw KMS key material.

#### 2.2.3.31 Customer Managed KMS Key

##### 2.2.3.31.1 Control
Customer controls:
- key policy,
- aliases/tags,
- enable/disable,
- grants,
- rotation configuration where supported,
- deletion scheduling.

##### 2.2.3.31.2 Key Material
- Standard AWS KMS key material remains protected by KMS/HSM boundary unless using supported imported/external key mechanisms.

##### 2.2.3.31.3 Exam Trap
**Customer managed key ≠ customer possesses plaintext KMS key material.**

#### 2.2.3.32 Authorization Difference

##### 2.2.3.32.1 SSE-S3
- Access primarily governed by S3 authorization.

##### 2.2.3.32.2 SSE-KMS
- Access can depend on:
  - S3 permissions,
  - KMS permissions/key policy.

##### 2.2.3.32.3 Client-Side Encryption
- Storage permission can return ciphertext.
- Caller also needs access to the decryption mechanism/key to obtain plaintext.

##### 2.2.3.32.4 Mental Model

`data access`
+
`decryption-key access`
→ plaintext access

#### 2.2.3.33 Separation of Duties

##### 2.2.3.33.1 Possible Design
- Storage administrators can access encrypted objects but cannot decrypt them.
- Application security/key administrators control decryption authorization.

##### 2.2.3.33.2 Client-Side Encryption
- Can create a stronger separation between:
  - storage access,
  - plaintext access.

##### 2.2.3.33.3 SSE-KMS
- Can also separate S3 and KMS permissions to a meaningful degree.

#### 2.2.3.34 Service-Side Processing

##### 2.2.3.34.1 Server-Side Encryption
- AWS service decrypts transparently when authorized, enabling normal service features.

##### 2.2.3.34.2 Client-Side Encryption
- Service sees ciphertext.
- Service cannot understand encrypted fields/object contents.

##### 2.2.3.34.3 Example
If DynamoDB attribute is client-encrypted:
- equality/range/query semantics on plaintext value may no longer be available in the normal way.

#### 2.2.3.35 Search and Analytics Trade-Off

Client-side encryption can conflict with:
- full-text search,
- indexing,
- server-side transformations,
- content inspection,
- analytics.

Therefore ask:

**Does AWS service need to understand the plaintext to perform required functionality?**

If yes, full client-side encryption may not fit that portion of the data.

#### 2.2.3.36 Encryption Metadata

##### 2.2.3.36.1 Client-Side
Encrypted payload may require metadata describing:
- algorithm,
- encrypted data key,
- key identifier,
- encryption context,
- framing/version information.

##### 2.2.3.36.2 SDK Benefit
- AWS Encryption SDK/database encryption libraries manage this structure rather than requiring custom formats.

#### 2.2.3.37 Key Reuse

##### 2.2.3.37.1 Bad Pattern
- Use one raw symmetric key directly for every payload indefinitely.

##### 2.2.3.37.2 Better Pattern
- Envelope encryption/data keys.
- KMS protects data-key hierarchy.

##### 2.2.3.37.3 Benefit
- Limits exposure and simplifies scalable key management.

#### 2.2.3.38 Encryption Context

##### 2.2.3.38.1 KMS
- Non-secret additional authenticated data can bind cryptographic operation to context.

##### 2.2.3.38.2 Example Concept
- application,
- tenant,
- object purpose.

##### 2.2.3.38.3 Security
- Encryption context is logged and should not contain secrets.

##### 2.2.3.38.4 Connection
- Expanded in 2.2.4.

#### 2.2.3.39 Double Encryption

##### 2.2.3.39.1 Possible Pattern

`client-side encryption`
→ ciphertext
→ S3
→ server-side encryption of ciphertext

##### 2.2.3.39.2 Meaning
- Client controls inner encryption.
- S3 additionally encrypts stored object.

##### 2.2.3.39.3 Important
- This is different from S3 DSSE-KMS, which is AWS server-side dual-layer encryption.

#### 2.2.3.40 Client-Side + TLS + Server-Side

A high-control architecture can use all three:

`plaintext`
→ client-side encryption
→ `ciphertext`
→ TLS
→ AWS service
→ server-side encryption
→ stored encrypted representation

Each layer protects a different boundary.

#### 2.2.3.41 Data Lifecycle Question

When evaluating encryption, follow the data:

`created`
→ `encrypted?`
→ `transmitted`
→ `stored`
→ `read`
→ `decrypted`
→ `processed`
→ `re-encrypted/stored`

The key exam question is:

**At which point does plaintext exist?**

#### 2.2.3.42 Client-Side Encryption Decision Clues

Choose/consider client-side encryption when requirement says:
- encrypt before upload,
- AWS storage must not see plaintext,
- application controls cryptography,
- separate storage access from plaintext access,
- encrypt selected fields before database write,
- maintain ciphertext outside application trust boundary.

#### 2.2.3.43 Server-Side Encryption Decision Clues

Choose/consider server-side encryption when requirement says:
- encrypt stored AWS data,
- minimal application changes,
- use native AWS service encryption,
- centrally control key through KMS,
- preserve normal AWS service processing,
- reduce cryptographic implementation burden.

#### 2.2.3.44 Decision Flow

##### 2.2.3.44.1 Step 1
Does AWS service receiving plaintext violate requirement?

- No → server-side encryption is likely sufficient.
- Yes → client-side encryption required.

##### 2.2.3.44.2 Step 2
Need customer-controlled key policy/audit?

- Yes → consider KMS-backed encryption.

##### 2.2.3.44.3 Step 3
Need service to query/process plaintext?

- Yes → client-side encryption may limit functionality.

##### 2.2.3.44.4 Step 4
Need minimal code/operations?

- Yes → prefer native server-side encryption.

##### 2.2.3.44.5 Step 5
Need multiple encryption boundaries?

- Combine client-side + TLS + server-side where justified.

#### 2.2.3.45 Common Exam Traps

##### 2.2.3.45.1 "SSE-KMS Is Client-Side Because Customer Controls KMS Key"
- False.
- S3/service performs encryption.

##### 2.2.3.45.2 "SSE-C Is Client-Side Encryption"
- False.
- Customer supplies key, but S3 performs encryption.

##### 2.2.3.45.3 "Client-Side Encryption Replaces HTTPS"
- False.

##### 2.2.3.45.4 "KMS Means Server-Side Encryption"
- False.
- KMS can support both server-side and client-side workflows.

##### 2.2.3.45.5 "Client-Side Encryption Is Always More Secure"
- Too simplistic.
- It changes trust boundary but adds implementation/key-management complexity and can reduce service functionality.

##### 2.2.3.45.6 "S3 Has to Receive Plaintext to Store an Object"
- False with client-side encryption.

##### 2.2.3.45.7 "AWS Service Can Query Client-Encrypted Fields Normally"
- Generally false unless encryption scheme/application design explicitly supports the required operation.

##### 2.2.3.45.8 "Customer Managed KMS Key Means Raw Key Is Given to Customer"
- False.

##### 2.2.3.45.9 "Use KMS Encrypt for Large Files"
- Wrong pattern.
- Use envelope encryption/data keys.

##### 2.2.3.45.10 "S3 Default Encryption Means Every Encryption Requirement Is Solved"
- False.
- Requirements may demand KMS control, client-side encryption, transport enforcement, cross-account controls, or dual layers.

`SERVER-SIDE`
→ client sends plaintext over TLS
→ AWS service encrypts

→ client encrypts

#### 2.2.3.49 Exam-Level Knowledge Frame

Know these cold:

**Server-side encryption**
→ AWS service encrypts after receiving data.

**Client-side encryption**
→ application encrypts before AWS receives data.

**SSE-S3**
→ S3 encrypts, S3-managed keys.

**SSE-KMS**
→ S3 encrypts, KMS key.

**SSE-C**
→ customer supplies key, but S3 still encrypts.

**DSSE-KMS**
→ two server-side encryption layers using KMS.

**Client-side + KMS**
→ application can use KMS/data keys while performing encryption locally.

**Envelope encryption**
→ KMS key protects data key; data key encrypts bulk payload.

**TLS**
→ still required regardless of CSE/SSE.

The fastest exam discriminator is:

**Ask where plaintext stops existing.**

If plaintext reaches AWS storage service:
→ server-side encryption.

If application turns it into ciphertext before upload:
→ client-side encryption.

Final principle:

**Client-side and server-side encryption can use the same AWS key-management ecosystem, but they place the plaintext boundary and cryptographic responsibility in fundamentally different locations.**
