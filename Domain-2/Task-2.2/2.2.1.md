### 2.2.1 Define encryption at rest and in transit

#### 2.2.1.1 Exam and Task Context

##### 2.2.1.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.2 is **Implement encryption by using AWS services**.
- Skill 2.2.1 is **Define encryption at rest and in transit**.
- This skill establishes the conceptual frame for the remaining Task 2.2 skills:
  - certificate management,
  - client-side vs server-side encryption,
  - encryption/decryption keys,
  - certificates and SSH keys,
  - cross-account encryption,
  - key rotation.

##### 2.2.1.1.2 Core Question
- **Where is the data in its lifecycle, what threat is encryption addressing there, and which AWS mechanism protects it?**

#### 2.2.1.2 Core Mental Model

Data normally exists in two security-relevant states for this skill:

`stored somewhere`
→ **data at rest**

`moving between systems`
→ **data in transit**

Therefore:

`data at rest`
→ encrypt stored data

`data in transit`
→ encrypt communication channel/data while moving

A secure application commonly needs **both**.

#### 2.2.1.3 Encryption — Purpose

##### 2.2.1.3.1 Confidentiality
- Encryption transforms readable plaintext into ciphertext.
- Without the appropriate key, ciphertext should be unintelligible.

##### 2.2.1.3.2 Encryption Does Not Replace Access Control
- IAM/access control determines who may access a resource or use a key.
- Encryption protects the confidentiality of the data.
- Strong systems normally combine:
  - authorization,
  - encryption,
  - key management.

##### 2.2.1.3.3 Encryption Does Not Mean Hashing
- Encryption is reversible with the appropriate key.
- Hashing is designed as a one-way transformation.
- Do not treat password hashing and data encryption as interchangeable concepts.

#### 2.2.1.4 Data at Rest

##### 2.2.1.4.1 AWS Definition
- Data at rest is data persisted in non-volatile storage for any duration.

##### 2.2.1.4.2 Examples
- S3 objects.
- DynamoDB table data.
- RDS/Aurora database storage.
- EBS volumes and snapshots.
- EFS file systems.
- Application artifacts.
- Backups.
- Logs persisted to storage.

##### 2.2.1.4.3 Threat Model
Encryption at rest helps protect data if stored data or underlying storage is accessed outside the intended authorization path.

#### 2.2.1.5 Encryption at Rest

##### 2.2.1.5.1 Mental Model

`plaintext`
→ encryption algorithm + encryption key
→ `ciphertext stored`

Later:

`ciphertext`
→ decryption + authorized key use
→ `plaintext`

##### 2.2.1.5.2 AWS Pattern
- Many AWS services provide built-in encryption at rest.
- AWS KMS integrates with many AWS services to control encryption keys.

##### 2.2.1.5.3 Responsibility
- The exact encryption model depends on the AWS service.
- Some services encrypt by default.
- Some allow choosing a key.
- Some support customer managed KMS keys for additional control.

#### 2.2.1.6 Data in Transit

##### 2.2.1.6.1 AWS Definition
- Data in transit is data sent from one system to another.

##### 2.2.1.6.2 Examples
- Browser → API Gateway.
- Application → AWS service API.
- Service A → Service B.
- Application → database.
- Client → load balancer.
- On-premises → AWS.

##### 2.2.1.6.3 Security Goals
- Confidentiality:
  - observers should not read transmitted data.
- Integrity:
  - unauthorized modification should be detectable/prevented.
- Endpoint authentication:
  - TLS certificates help clients verify the server they are communicating with.

#### 2.2.1.7 Encryption in Transit

##### 2.2.1.7.1 Primary AWS Pattern

`client`
→ HTTPS/TLS
→ `AWS endpoint`

##### 2.2.1.7.2 AWS APIs
- AWS service APIs provide HTTPS endpoints using TLS.
- AWS recommends secure TLS protocols and cipher suites.
- Current AWS guidance requires clients calling AWS service endpoints to support at least TLS 1.2 and recommends TLS 1.3.

##### 2.2.1.7.3 Important
- `HTTPS = HTTP over TLS`.
- HTTP alone does not provide transport encryption.

#### 2.2.1.8 At Rest vs In Transit

| Question | At Rest | In Transit |
| --- | --- | --- |
| Where is data? | Persisted in storage | Moving between systems |
| Typical mechanism | Storage/service encryption | TLS/HTTPS |
| Key AWS service | AWS KMS | AWS Certificate Manager / service TLS configuration |
| Example | encrypted S3 object | HTTPS request to S3 |
| Main goal | protect stored data | protect data while communicating |

A single piece of data can require both protections during its lifecycle.

#### 2.2.1.9 Example — S3

##### 2.2.1.9.1 At Rest
- Object is stored encrypted.
- S3 supports server-side encryption.
- Depending on configuration, encryption can use:
  - S3-managed keys,
  - AWS KMS keys,
  - other supported S3 encryption mechanisms.

##### 2.2.1.9.2 In Transit
- Client communicates with S3 through HTTPS/TLS.

##### 2.2.1.9.3 Combined Model

`application`
→ HTTPS/TLS
→ `S3`
→ encrypted object at rest

##### 2.2.1.9.4 Exam Insight
- Enabling S3 encryption at rest does not itself force clients to use HTTPS.
- Transport encryption can be separately enforced through policy controls such as secure-transport conditions.

#### 2.2.1.10 Example — DynamoDB

##### 2.2.1.10.1 At Rest
- DynamoDB encrypts table data at rest.
- AWS KMS participates in the service's encryption architecture.

##### 2.2.1.10.2 In Transit
- SDK/API calls use HTTPS/TLS.

##### 2.2.1.10.3 Developer View

`application`
→ HTTPS AWS API call
→ `DynamoDB`
→ encrypted persistent data

#### 2.2.1.11 Example — RDS / Aurora

##### 2.2.1.11.1 At Rest
- Database storage can be encrypted using AWS KMS-supported service encryption.
- Related encrypted resources can include storage, backups, snapshots, and replicas according to service capabilities.

##### 2.2.1.11.2 In Transit
- Database clients can use TLS connections to database endpoints.

##### 2.2.1.11.3 Distinction
- Database storage encryption and database connection TLS solve different problems.

#### 2.2.1.12 Example — EBS

##### 2.2.1.12.1 At Rest
- EBS supports encrypted volumes.
- Encryption also applies to associated snapshot/data paths according to EBS encryption behavior.
- AWS KMS keys are used in the encryption architecture.

##### 2.2.1.12.2 Developer-Level Focus
- Recognize EBS as persistent block storage requiring at-rest protection.
- Detailed EC2 storage administration is not the center of this skill.

#### 2.2.1.13 Example — EFS

##### 2.2.1.13.1 At Rest
- EFS supports encryption at rest.

##### 2.2.1.13.2 In Transit
- EFS supports TLS for data in transit between clients and the file system through supported mount mechanisms.

##### 2.2.1.13.3 Exam Insight
- Same service can expose separate settings/mechanisms for:
  - encryption at rest,
  - encryption in transit.

#### 2.2.1.14 AWS KMS

##### 2.2.1.14.1 Purpose
- AWS KMS is a managed service for creating and controlling cryptographic keys used to encrypt/sign data.

##### 2.2.1.14.2 Role in This Skill
- KMS is primarily the central AWS key-management concept behind many at-rest encryption implementations.

##### 2.2.1.14.3 Integration
Examples include:
- S3.
- EBS.
- RDS.
- DynamoDB.
- Lambda.
- other KMS-integrated AWS services.

##### 2.2.1.14.4 Important
- KMS is **key management**, not simply "a storage encryption switch."
- Individual AWS services define how they integrate with KMS.

#### 2.2.1.15 KMS Key Hierarchy — High-Level

A common AWS encryption pattern is:

`KMS key`
→ protects
`data key`
→ encrypts
`application/service data`

This is the basis of **envelope encryption**.

Detailed key use belongs mainly to Skill 2.2.4.

#### 2.2.1.16 Envelope Encryption

##### 2.2.1.16.1 Why
- Large application data is normally not sent directly to KMS for bulk encryption.

##### 2.2.1.16.2 Pattern

`KMS key`
→ encrypts/protects data key

`data key`
→ encrypts actual data

##### 2.2.1.16.3 Stored Result
Typically:
- encrypted data,
- encrypted copy of data key.

##### 2.2.1.16.4 Decryption

`encrypted data key`
→ KMS decrypt
→ plaintext data key
→ decrypt data

##### 2.2.1.16.5 Exam Depth
- Understand the concept now.
- APIs and key usage are expanded in 2.2.4.

#### 2.2.1.17 Symmetric Encryption

##### 2.2.1.17.1 Model
- Same secret key is used for encryption and decryption.

`key + plaintext`
→ ciphertext

`same key + ciphertext`
→ plaintext

##### 2.2.1.17.2 Strength
- Efficient for bulk data encryption.

##### 2.2.1.17.3 AWS Context
- AWS services integrated with KMS use symmetric encryption KMS keys for encrypting service data.

#### 2.2.1.18 Asymmetric Encryption

##### 2.2.1.18.1 Model
Uses a key pair:
- public key,
- private key.

##### 2.2.1.18.2 Encryption Pattern
- Public key can encrypt.
- Private key decrypts.

##### 2.2.1.18.3 Signature Pattern
- Private key signs.
- Public key verifies.

##### 2.2.1.18.4 AWS Context
- KMS supports asymmetric keys for supported cryptographic operations.
- However, integrated AWS services use symmetric KMS keys for their service-side data encryption.

#### 2.2.1.19 TLS — High-Level

##### 2.2.1.19.1 Purpose
TLS protects communication between endpoints.

##### 2.2.1.19.2 Provides
- encryption,
- integrity,
- server authentication,
- optionally client authentication depending on architecture.

##### 2.2.1.19.3 Common Pattern

`client`
→ validates server certificate
→ establishes secure session
→ encrypted application traffic

##### 2.2.1.19.4 Exam Scope
- Understand what TLS achieves.
- Detailed certificate lifecycle follows in 2.2.2.

#### 2.2.1.20 Certificates

##### 2.2.1.20.1 Role
- X.509 certificates bind identity information to a public key and are central to TLS endpoint authentication.

##### 2.2.1.20.2 AWS Service
- AWS Certificate Manager (ACM) manages certificates for supported AWS integrations.

##### 2.2.1.20.3 Examples
- CloudFront.
- Elastic Load Balancing.
- API Gateway custom domains.

##### 2.2.1.20.4 Boundary
- Certificate management belongs primarily to Skill 2.2.2.

#### 2.2.1.21 TLS Termination

##### 2.2.1.21.1 Concept
- An AWS edge/proxy/load-balancing service can terminate the TLS connection.

Pattern:

`client`
→ HTTPS/TLS
→ `load balancer / CloudFront / API Gateway`
→ backend connection

##### 2.2.1.21.2 Important
- The backend leg is a separate connection.
- Whether it is also encrypted must be evaluated separately.

##### 2.2.1.21.3 Exam Trap
- HTTPS from client to load balancer does not automatically mean every downstream hop uses TLS.

#### 2.2.1.22 End-to-End Transit Protection

Consider every network hop:

`client`
→ TLS
→ `edge/API/load balancer`
→ TLS
→ `application`
→ TLS
→ `database/service`

The requirement "encrypt data in transit" may apply to all relevant hops, not merely the public-facing connection.

#### 2.2.1.23 Encryption vs Signing

##### 2.2.1.23.1 Encryption
- Protects confidentiality.

##### 2.2.1.23.2 Digital Signature
- Provides authenticity/integrity properties.
- Does not hide the content.

##### 2.2.1.23.3 Exam Trap
- Signing a payload does not encrypt it.

#### 2.2.1.24 Encryption vs Encoding

##### 2.2.1.24.1 Encoding
Examples:
- Base64.
- URL encoding.

##### 2.2.1.24.2 Purpose
- Changes representation/transport format.

##### 2.2.1.24.3 Security
- Encoding is not encryption.
- Anyone who knows the encoding can reverse it.

#### 2.2.1.25 Encryption vs Compression

##### 2.2.1.25.1 Compression
- Reduces data size/redundancy.

##### 2.2.1.25.2 Encryption
- Protects confidentiality.

##### 2.2.1.25.3 Rule
- Compression does not provide a security boundary.

#### 2.2.1.26 Server-Side vs Client-Side Encryption — Preview

##### 2.2.1.26.1 Server-Side
- Data reaches AWS service.
- Service encrypts it before persistence.

##### 2.2.1.26.2 Client-Side
- Application encrypts data before sending it to AWS storage/service.

##### 2.2.1.26.3 Important
- Both can provide encryption at rest.
- Trust boundary and key ownership differ.

##### 2.2.1.26.4 Boundary
- Detailed comparison is Skill 2.2.3.

#### 2.2.1.27 Encryption at Rest Does Not Necessarily Mean KMS

##### 2.2.1.27.1 Service-Managed Encryption
- AWS services can provide encryption using service-managed mechanisms.

##### 2.2.1.27.2 KMS-Integrated Encryption
- Customer can often choose an AWS KMS key option for more key-level control.

##### 2.2.1.27.3 Application Encryption
- Application can encrypt data itself.

##### 2.2.1.27.4 Exam Rule
- First identify the required control and service capability.
- Do not automatically choose a customer managed KMS key for every encryption question.

#### 2.2.1.28 Key Ownership and Control

A useful spectrum:

`AWS/service managed`
→ less customer key administration

`AWS managed KMS key`
→ KMS integration with AWS-managed lifecycle

`customer managed KMS key`
→ greater customer control over:
- key policy,
- grants,
- lifecycle,
- rotation choices,
- auditing context.

##### 2.2.1.28.1 Trade-Off
- More control also means more responsibility.

#### 2.2.1.29 Encryption and IAM

##### 2.2.1.29.1 Data Permission
Example:
- `s3:GetObject`

##### 2.2.1.29.2 Key Permission
With customer managed KMS encryption, caller may also require permission to use the relevant KMS key.

##### 2.2.1.29.3 Mental Model

`authorized to access encrypted resource`
+
`authorized to use required encryption key`
→ successful plaintext access

##### 2.2.1.29.4 Connection
- IAM authorization was covered in 2.1.6.
- Cross-account key permissions appear in 2.2.6.

#### 2.2.1.30 Encryption and Availability

##### 2.2.1.30.1 Key Is a Dependency
- Encrypted data is useful only while authorized systems can decrypt it.

##### 2.2.1.30.2 Misconfiguration
- Disabling/deleting/inaccessible keys can make data unavailable.

##### 2.2.1.30.3 Principle
- Encryption design must consider both:
  - confidentiality,
  - legitimate availability.

#### 2.2.1.31 Encryption and Auditability

##### 2.2.1.31.1 KMS
- KMS API usage can be audited through AWS CloudTrail.

##### 2.2.1.31.2 Benefit
- Helps answer:
  - which principal used a key,
  - which operation occurred,
  - when key usage occurred.

##### 2.2.1.31.3 Security
- Key permissions should follow least privilege.

#### 2.2.1.32 Encryption Context — Preview

##### 2.2.1.32.1 KMS Concept
- Encryption context is optional non-secret additional authenticated data for supported symmetric KMS cryptographic operations.

##### 2.2.1.32.2 Benefit
- Can bind ciphertext use to contextual information.
- Can participate in authorization conditions.
- Appears in CloudTrail, so it must not contain sensitive plaintext.

##### 2.2.1.32.3 Boundary
- Detailed cryptographic key use belongs to 2.2.4.

#### 2.2.1.33 In-Transit Encryption Enforcement

##### 2.2.1.33.1 Do Not Merely Support TLS
- Security requirements can require that plaintext protocols are rejected.

##### 2.2.1.33.2 Examples
- Only HTTPS listener.
- Redirect HTTP → HTTPS where appropriate.
- S3 policy denies requests not using secure transport.
- Database requires TLS where supported/configured.

##### 2.2.1.33.3 Principle
- **Available encryption** is weaker than **enforced encryption**.

#### 2.2.1.34 S3 Secure Transport

##### 2.2.1.34.1 Condition
- S3 bucket policies can use AWS global condition context to enforce secure transport.

##### 2.2.1.34.2 Pattern

`request is not using TLS`
→ explicit deny

##### 2.2.1.34.3 Exam Meaning
- SSE protects objects at rest.
- HTTPS/bucket policy protects transit.
- These are independent controls.

#### 2.2.1.35 CloudFront

##### 2.2.1.35.1 Viewer Connection
- CloudFront can require/redirect viewers to HTTPS.

##### 2.2.1.35.2 Origin Connection
- CloudFront-to-origin protocol is separately configurable according to origin type/settings.

##### 2.2.1.35.3 Exam Insight
- Analyze both:
  - viewer → CloudFront,
  - CloudFront → origin.

#### 2.2.1.36 Elastic Load Balancing

##### 2.2.1.36.1 Front End
- Load balancer can terminate TLS using a certificate.

##### 2.2.1.36.2 Back End
- Traffic from load balancer to target can be a separately configured protocol.

##### 2.2.1.36.3 Certificate
- ACM commonly supplies certificates for supported ELB HTTPS/TLS listeners.

#### 2.2.1.37 API Gateway

##### 2.2.1.37.1 Client Side
- API Gateway APIs are invoked over HTTPS.

##### 2.2.1.37.2 Custom Domain
- TLS certificate is associated with the custom domain.

##### 2.2.1.37.3 Backend
- Integration connection is a separate trust/transport boundary.

##### 2.2.1.37.4 Connection
- API authentication is Task 2.1.
- TLS protects the transport channel.

#### 2.2.1.38 Private Network Does Not Equal Encryption

##### 2.2.1.38.1 Private IP/VPC
- Controls network path/reachability.

##### 2.2.1.38.2 Encryption
- Protects data confidentiality/integrity on that path.

##### 2.2.1.38.3 Exam Trap
- "Traffic stays in the VPC" is not equivalent to "application traffic is encrypted with TLS."

#### 2.2.1.39 Encryption and Backups

##### 2.2.1.39.1 At Rest Includes Copies
Think beyond primary data:
- snapshots,
- backups,
- replicas,
- exported data,
- logs,
- caches where persisted.

##### 2.2.1.39.2 Principle
- Sensitive data remains sensitive when copied.

#### 2.2.1.42 Common Exam Traps

##### 2.2.1.42.1 "Encrypted at Rest Means Encrypted in Transit"
- False.
- They are independent data states and controls.

##### 2.2.1.42.2 "HTTPS Encrypts Stored Data"
- False.
- HTTPS protects data in transit.

##### 2.2.1.42.3 "SSE Forces HTTPS"
- False.
- SSE is at-rest encryption.

##### 2.2.1.42.4 "Private VPC Traffic Is the Same as TLS"
- False.

##### 2.2.1.42.5 "Base64 Is Encryption"
- False.

##### 2.2.1.42.6 "Hashing Is Encryption"
- False.

##### 2.2.1.42.7 "Signing Encrypts Data"
- False.

##### 2.2.1.42.8 "Every Encryption Requirement Needs a Customer Managed KMS Key"
- False.
- Requirement determines key/control model.

##### 2.2.1.42.9 "KMS Directly Encrypts Every Large Object"
- Usually wrong mental model.
- Envelope encryption/data keys are central for larger data.

##### 2.2.1.42.10 "TLS to the Load Balancer Means End-to-End TLS"
- False.
- Each downstream connection must be evaluated.

##### 2.2.1.42.11 "Encryption Removes Need for IAM"
- False.

##### 2.2.1.42.12 "Having TLS Available Means Transit Encryption Is Enforced"
- False.
- Plaintext paths may need to be explicitly blocked.

#### 2.2.1.46 Exam-Level Knowledge Frame

Know these cold:

**Data at rest**
→ persisted data.

**Encryption at rest**
→ stored ciphertext protected by encryption key.

**Data in transit**
→ data moving between systems.

**Encryption in transit**
→ TLS/HTTPS or another secure encrypted transport.

**KMS**
→ managed cryptographic key service integrated with AWS services.

**Envelope encryption**
→ KMS key protects data key; data key encrypts data.

**TLS**
→ confidentiality + integrity + endpoint authentication.

**Certificate**
→ binds endpoint identity to public key for TLS trust.

**SSE**
→ server encrypts before storage.

**Client-side encryption**
→ application encrypts before transmission/storage service receives plaintext.

**IAM**
→ controls who may access resources/use keys.

Final principle:

**Encryption at rest protects persisted data; encryption in transit protects data while it moves. They address different stages of the data lifecycle and normally must be considered independently.**

##### 2.2.1.47.2 AWS Well-Architected Security Pillar
- Defines data at rest as persisted data in non-volatile storage.

- KMS creates and controls cryptographic keys.
- KMS integrates with AWS services for encryption.
- AWS service integrations use symmetric KMS keys for service-side data encryption.
- KMS key material is protected by AWS KMS HSMs.
