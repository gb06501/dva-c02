### 2.2.7 Enable and disable key rotation

#### 2.2.7.1 Exam and Task Context

##### 2.2.7.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.2 is **Implement encryption by using AWS services**.
- Skill 2.2.7 is **Enable and disable key rotation**.
- This is the final skill in Task 2.2.
- The preceding skills established:
  - 2.2.1 → encryption at rest and in transit.
  - 2.2.2 → certificate management.
  - 2.2.3 → client-side vs server-side encryption.
  - 2.2.4 → use encryption/decryption keys.
  - 2.2.5 → development certificates and SSH keys.
  - 2.2.6 → encryption across account boundaries.
- 2.2.7 focuses on the **lifecycle of KMS key material over time**.

##### 2.2.7.1.2 Core Question
- **How does AWS KMS rotate cryptographic key material without changing the logical KMS key that applications and AWS services reference?**

#### 2.2.7.2 Core Mental Model

A KMS key is a logical key resource.

Rotation changes the **backing cryptographic key material** used for new cryptographic operations while preserving the same logical KMS key identity.

Mental model:

`KMS key ARN / key ID / alias`
→ remains the same

while:

`old key material`
→ retained for old ciphertext

`new key material`
→ used for new encryption

This is why encrypted data does not need to be re-encrypted merely because automatic KMS key rotation occurs.

#### 2.2.7.3 Key Rotation — Purpose

##### 2.2.7.3.1 Security Goal
- Reduce the amount of data protected by one version of cryptographic key material.
- Support security/compliance requirements around cryptographic lifecycle.

##### 2.2.7.3.2 Important
- Rotation is not a response to known key compromise by itself.
- A compromised key can require stronger remediation such as:
  - disabling the key,
  - replacing access,
  - creating a new KMS key,
  - re-encrypting data,
depending on the situation.

#### 2.2.7.4 Automatic KMS Key Rotation

##### 2.2.7.4.1 Customer Managed Symmetric Keys
- AWS KMS supports automatic rotation for eligible customer managed symmetric encryption KMS keys.

##### 2.2.7.4.2 Behavior
When rotation occurs:
- KMS generates new cryptographic key material.
- The logical KMS key remains the same.
- Key ID remains the same.
- Key ARN remains the same.
- Aliases remain associated with the same logical KMS key.

##### 2.2.7.4.3 Application Impact
- Applications do not need to change the KMS key reference.

#### 2.2.7.5 Old Ciphertext Still Works

##### 2.2.7.5.1 Key-Material History
- AWS KMS retains previous key material required to decrypt ciphertext created under older key-material versions.

##### 2.2.7.5.2 Decryption
- KMS determines which backing key material is required for ciphertext encrypted using the KMS key.

##### 2.2.7.5.3 Critical Exam Rule
**Automatic rotation does not make previously encrypted data unreadable.**

#### 2.2.7.6 New Encryption After Rotation

##### 2.2.7.6.1 New Data
- New encryption operations use the current key material.

##### 2.2.7.6.2 Existing Data
- Existing ciphertext remains encrypted under the previous key-material version until:
  - accessed/decrypted/re-encrypted,
  - or explicitly migrated through another process.

##### 2.2.7.6.3 Important
**Rotation does not automatically re-encrypt all existing data.**

#### 2.2.7.7 Enable Automatic Rotation

##### 2.2.7.7.1 Console/API
- Automatic rotation can be enabled for supported KMS keys through:
  - AWS Management Console,
  - AWS CLI,
  - AWS SDK/API.

##### 2.2.7.7.2 API Concept
- `EnableKeyRotation`.

##### 2.2.7.7.3 Permission
- Caller needs appropriate KMS administrative permission.

#### 2.2.7.8 Disable Automatic Rotation

##### 2.2.7.8.1 API Concept
- `DisableKeyRotation`.

##### 2.2.7.8.2 Effect
- Stops future automatic rotation events.
- Does not remove historical key material already created by previous rotations.
- Does not change ciphertext already protected with the key.

##### 2.2.7.8.3 Important
Disabling rotation does **not**:
- disable the KMS key,
- decrypt data,
- delete old key material.

#### 2.2.7.9 Rotation Period

##### 2.2.7.9.1 Current AWS KMS Capability
- AWS KMS supports configurable automatic rotation periods for eligible customer managed symmetric encryption keys.

##### 2.2.7.9.2 Current Range
- Rotation period can be configured within AWS-supported limits rather than being restricted only to a fixed annual interval.

##### 2.2.7.9.3 Exam Mindset
- Understand that rotation can be configured.
- Do not assume the historical "exactly once every 365 days" model is the only current behavior.

#### 2.2.7.10 Default Rotation Period Context

##### 2.2.7.10.1 Historical Model
- AWS KMS historically used an annual automatic-rotation model.

##### 2.2.7.10.2 Current Guidance
- Current AWS KMS supports customer-configurable rotation periods for supported keys.

##### 2.2.7.10.3 Exam Rule
- Prefer the current service behavior over old memorized certification material.

#### 2.2.7.11 Eligible Keys

##### 2.2.7.11.1 Typical Supported Case
- Customer managed symmetric encryption KMS keys with AWS KMS-generated key material.

##### 2.2.7.11.2 Why
- AWS KMS controls the underlying key material lifecycle.

#### 2.2.7.12 Keys That Do Not Use Automatic Rotation the Same Way

Automatic rotation behavior differs or is unavailable for key categories such as:
- asymmetric KMS keys,
- HMAC KMS keys,
- keys with imported key material,
- keys in custom key stores,
- keys in external key stores,
depending on current AWS capabilities and key origin.

##### 2.2.7.12.1 Exam Principle
**Always identify key type and origin before assuming automatic rotation is available.**

#### 2.2.7.13 AWS Managed Keys

##### 2.2.7.13.1 Ownership
- AWS services create/manage these KMS keys.

##### 2.2.7.13.2 Rotation
- AWS manages rotation according to the service/KMS lifecycle.
- Customer cannot configure their rotation behavior the same way as a customer managed key.

##### 2.2.7.13.3 Exam Distinction
**Customer managed key**
→ customer can configure supported rotation.

**AWS managed key**
→ AWS controls lifecycle/rotation.

#### 2.2.7.14 AWS Owned Keys

##### 2.2.7.14.1 Ownership
- Fully owned and managed by AWS services.
- Not visible/manageable like customer KMS keys.

##### 2.2.7.14.2 Rotation
- AWS manages their cryptographic lifecycle.

##### 2.2.7.14.3 Exam
- No customer rotation configuration.

#### 2.2.7.15 Imported Key Material

##### 2.2.7.15.1 Origin
- Customer supplies key material to AWS KMS.

##### 2.2.7.15.2 Rotation Responsibility
- Customer must manage replacement/rotation of imported key material according to supported KMS workflows.

##### 2.2.7.15.3 Why
- AWS cannot simply generate new customer-owned imported key material on the customer's behalf.

#### 2.2.7.16 Manual Rotation

##### 2.2.7.16.1 Concept
When automatic rotation does not fit, manually rotate by:

`create new KMS key`
→ update alias/application/service configuration
→ use new key for new encryption
→ preserve old key for old ciphertext
→ optionally re-encrypt/migrate existing data

##### 2.2.7.16.2 Important
- Manual rotation normally means creating a **new KMS key**, unlike automatic rotation which changes key material inside the same logical KMS key.

#### 2.2.7.17 Automatic vs Manual Rotation

| Characteristic | Automatic KMS Rotation | Manual Rotation |
| --- | --- | --- |
| Logical KMS key | Same | New KMS key |
| ARN/key ID | Same | Changes |
| Application config | Usually unchanged | Usually update key reference/alias |
| Old ciphertext | Decrypts automatically | Requires old key to remain available |
| Suitable for | Eligible KMS-generated symmetric keys | Unsupported key types/custom requirements |
| Customer effort | Lower | Higher |

#### 2.2.7.18 Alias-Assisted Manual Rotation

##### 2.2.7.18.1 Pattern

Before:

`alias/app-data`
→ `Key A`

After manual rotation:

`alias/app-data`
→ `Key B`

##### 2.2.7.18.2 Benefit
- Application can continue referencing a stable alias while logical KMS key behind alias changes.

##### 2.2.7.18.3 Important
- Existing ciphertext encrypted under Key A still requires Key A for decryption.

#### 2.2.7.19 Key ID/ARN vs Alias During Manual Rotation

##### 2.2.7.19.1 Hard-Coded Key ARN
- Application must be updated when new logical KMS key is created.

##### 2.2.7.19.2 Alias
- Alias can be repointed to new KMS key.

##### 2.2.7.19.3 Exam Mindset
- Alias is useful for logical key naming and migration.
- Alias does not magically make ciphertext encrypted under old key decrypt with new key.

#### 2.2.7.20 Re-Encrypting Existing Data

##### 2.2.7.20.1 Not Required for Automatic Rotation
- Old ciphertext remains decryptable through KMS key's retained key-material versions.

##### 2.2.7.20.2 May Be Required for Manual Key Migration
If requirement says:
- all data must now be protected under a new KMS key,
then existing ciphertext/resources may need:
- copy,
- rewrite,
- re-encryption,
- service-specific migration.

##### 2.2.7.20.3 Important
**Key rotation and data re-encryption are separate operations.**

#### 2.2.7.21 `ReEncrypt`

##### 2.2.7.21.1 KMS Operation
- `ReEncrypt` can decrypt KMS ciphertext under one KMS key and encrypt it under another KMS key without returning plaintext to the caller.

##### 2.2.7.21.2 Use
- Key migration.
- Cross-account key change.
- Manual rotation workflows for KMS ciphertext.

##### 2.2.7.21.3 Service Data
- AWS managed services often require service-specific rewrite/copy mechanisms rather than raw `ReEncrypt` on stored objects.

#### 2.2.7.22 Rotation and Envelope Encryption

##### 2.2.7.22.1 Data Key
- Application data is encrypted with data key.

##### 2.2.7.22.2 KMS Key
- KMS key encrypts/protects the data key.

##### 2.2.7.22.3 Automatic Rotation
- New `GenerateDataKey` operations use current KMS key material.
- Previously encrypted data keys remain decryptable using historical KMS key material.

##### 2.2.7.22.4 Benefit
- Rotation is transparent to stored encrypted data keys.

#### 2.2.7.23 Rotation and AWS Service Encryption

##### 2.2.7.23.1 SSE-KMS Example
- S3 uses KMS key in service-side encryption workflow.

##### 2.2.7.23.2 Automatic Rotation
- S3 continues referring to same logical KMS key.
- New KMS operations use current backing key material.
- Existing objects remain readable.

##### 2.2.7.23.3 Application
- No need to change bucket configuration just because the KMS key automatically rotates.

#### 2.2.7.24 Rotation Does Not Change Permissions

##### 2.2.7.24.1 Key Policy
- Rotation does not automatically change key policy.

##### 2.2.7.24.2 IAM
- Principal permissions remain as configured.

##### 2.2.7.24.3 Alias
- Same alias remains associated with same logical key for automatic rotation.

##### 2.2.7.24.4 Critical
**Rotation changes cryptographic material, not IAM authorization.**

#### 2.2.7.25 Rotation Does Not Disable the Key

##### 2.2.7.25.1 Automatic Rotation
- Key remains enabled and usable.

##### 2.2.7.25.2 Disable Rotation
- Key remains enabled.

##### 2.2.7.25.3 Disable Key
- Separate administrative operation.

#### 2.2.7.26 Disable Key vs Disable Rotation

`DisableKeyRotation`
→ stop future rotations

`DisableKey`
→ stop cryptographic use of KMS key

These are fundamentally different.

##### 2.2.7.26.1 Exam Trap
- "Stop applications from decrypting immediately" → disabling rotation is **not** enough.

#### 2.2.7.27 Rotation vs Deletion

##### 2.2.7.27.1 Rotation
- Preserves ability to decrypt old ciphertext.

##### 2.2.7.27.2 Key Deletion
- Eventually removes KMS key and its key material.
- Can make dependent ciphertext permanently unrecoverable.

##### 2.2.7.27.3 Rule
- Never confuse lifecycle hygiene with destructive key deletion.

#### 2.2.7.28 Key Compromise

##### 2.2.7.28.1 Rotation Alone
- Does not erase the compromised key material from historical decrypt capability.
- Old ciphertext still depends on old key material.

##### 2.2.7.28.2 Potential Response
Depending on requirements:
1. stop unauthorized access,
2. disable/restrict compromised key,
3. create replacement key,
4. re-encrypt sensitive data,
5. update applications/services,
6. retain old key only as long as required for migration,
7. schedule deletion when safe.

##### 2.2.7.28.3 Exam Insight
**Routine rotation ≠ compromise remediation.**

#### 2.2.7.29 Compliance-Driven Rotation

##### 2.2.7.29.1 Requirement
- Policy may require cryptographic key material rotation on a defined cadence.

##### 2.2.7.29.2 Best Fit
- Enable supported automatic KMS key rotation when it satisfies requirement.

##### 2.2.7.29.3 Benefit
- Lower operational burden.
- No application key-reference changes.

#### 2.2.7.30 Rotation Status

##### 2.2.7.30.1 KMS

##### 2.2.7.30.2 API Concepts

- rotation-period configuration/status APIs according to current KMS API.

##### 2.2.7.30.3 Use

#### 2.2.7.32 Multi-Region Keys

##### 2.2.7.32.1 Related Keys
- Multi-Region keys consist of related primary/replica KMS keys.

##### 2.2.7.32.2 Rotation
- Rotation behavior must follow current AWS KMS multi-Region key rules.

##### 2.2.7.32.3 Exam Depth

#### 2.2.7.33 Cross-Account Context

##### 2.2.7.33.1 Key Owner
- The key-owning account controls rotation configuration.

##### 2.2.7.33.2 External Consumers
- Accounts using the key cross-account continue using same logical key after automatic rotation.

##### 2.2.7.33.3 Benefit
- Consumers normally do not need configuration changes for automatic rotation.

##### 2.2.7.33.4 Connection
- Cross-account access covered in 2.2.6.

#### 2.2.7.34 CloudTrail

##### 2.2.7.34.1 Audit

##### 2.2.7.34.2 Useful Lifecycle Events
- enabling/disabling key rotation,

#### 2.2.7.35 Least Privilege for Rotation Administration

##### 2.2.7.35.1 Application Role
Typically needs:
- `kms:Encrypt`,
- `kms:Decrypt`,
- `kms:GenerateDataKey`,
as required.

##### 2.2.7.35.2 Security Administrator
May need:
- enable/disable rotation,
- key lifecycle operations.

##### 2.2.7.35.3 Separation of Duties
- Application should not automatically receive key-administration permissions.

#### 2.2.7.36 Rotation Decision Flow

##### 2.2.7.36.1 Step 1 — Identify Key Type
- Customer managed?
- AWS managed?
- AWS owned?
- symmetric?
- asymmetric?
- imported?
- external/custom key store?

##### 2.2.7.36.2 Step 2 — Does Automatic Rotation Apply?
- If supported:
  - enable/configure automatic rotation.

##### 2.2.7.36.3 Step 3 — Unsupported or Custom Requirement?
- Create new key and perform manual rotation.

##### 2.2.7.36.4 Step 4 — Existing Data
- Automatic rotation:
  - normally no re-encryption required.
- New logical key:
  - determine whether existing data must be migrated.

##### 2.2.7.36.5 Step 5 — Alias
- Use alias to simplify manual key migration where appropriate.

#### 2.2.7.37 Common Exam Traps

##### 2.2.7.37.1 "Automatic Rotation Creates a New KMS Key ARN"
- False.

##### 2.2.7.37.2 "Automatic Rotation Requires Application Configuration Change"
- False.

##### 2.2.7.37.3 "Old Ciphertext Cannot Be Decrypted After Rotation"
- False.

##### 2.2.7.37.4 "Automatic Rotation Re-Encrypts Existing Data"
- False.

##### 2.2.7.37.5 "DisableKeyRotation Disables the KMS Key"
- False.

##### 2.2.7.37.6 "Rotation Fixes a Compromised Key Automatically"
- False.

##### 2.2.7.37.7 "Every KMS Key Type Supports Automatic Rotation"
- False.

##### 2.2.7.37.8 "AWS Managed Keys Have Customer-Configurable Rotation"
- False.

##### 2.2.7.37.9 "Manual Rotation Keeps Same Key ID"
- False.
- Manual rotation normally creates a new logical KMS key.

##### 2.2.7.37.10 "Alias Repointing Makes New Key Decrypt Old Ciphertext"
- False.
- Old ciphertext still requires old KMS key.

##### 2.2.7.37.11 "Key Rotation and Data Re-Encryption Are the Same"
- False.

##### 2.2.7.37.12 "Deleting Old Key Immediately After Manual Rotation Is Safe"
- False unless all dependent ciphertext has been migrated and old key is no longer required.

#### 2.2.7.41 Exam-Level Knowledge Frame

Know these cold:

**Automatic rotation**
→ same logical KMS key.

**Key ARN/key ID**
→ unchanged.

**Old key material**
→ retained for old ciphertext.

**New encryption**
→ uses current key material.

**Existing ciphertext**
→ is not automatically re-encrypted.

**Disable rotation**
→ stops future rotation only.

**Disable key**
→ stops cryptographic use.

**Manual rotation**
→ new KMS key + configuration/alias migration.

**AWS managed key**
→ AWS controls rotation.

**Customer managed eligible symmetric KMS key**
→ customer can configure supported automatic rotation.

**Imported/unsupported key type**
→ manual/customer-managed lifecycle may be required.

Fastest exam discriminator:

**Does the requirement ask to rotate key material without changing the key reference?**
→ automatic KMS rotation.

**Does the requirement require a new logical key or unsupported key type?**
→ manual rotation.

Final principle:

**KMS automatic rotation changes backing key material while preserving the logical KMS key, so applications keep the same key reference and previously encrypted data remains decryptable.**
