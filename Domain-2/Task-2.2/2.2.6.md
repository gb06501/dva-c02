### 2.2.6 Use encryption across account boundaries

#### 2.2.6.1 Exam and Task Context

##### 2.2.6.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.2 is **Implement encryption by using AWS services**.
- Skill 2.2.6 is **Use encryption across account boundaries**.
- The exam-guide Markdown explicitly places this after:
  - 2.2.4 → use encryption keys to encrypt or decrypt data.
  - 2.2.5 → generate certificates and SSH keys.
- It is followed by:
  - 2.2.7 → enable and disable key rotation.

##### 2.2.6.1.2 Core Question
- **How can a principal or AWS service in one AWS account use encrypted data protected by a KMS key owned by another AWS account?**

#### 2.2.6.2 Core Mental Model

Cross-account encryption is primarily a **two-sided authorization problem**:

`ACCOUNT A — KEY OWNER`
→ KMS key policy says Account B/principal may use key

AND

`ACCOUNT B — CALLER`
→ IAM policy says principal may use Account A's key

Only when both sides allow the operation can the external principal use the KMS key.

Core rule:

**Cross-account KMS access normally requires permission from both accounts.**

#### 2.2.6.3 Key Ownership

##### 2.2.6.3.1 KMS Key Belongs to One Account
- A KMS key belongs to the AWS account in which it was created.
- The key policy is defined and managed in that owning account.

##### 2.2.6.3.2 External Use
- A principal in another account can be authorized to perform supported operations on the key.
- This does **not** transfer ownership of the key.

#### 2.2.6.4 The Two-Policy Model

##### 2.2.6.4.1 Account A — Key Policy
The KMS key policy must authorize:
- Account B,
- or a specific principal in Account B.

##### 2.2.6.4.2 Account B — IAM Policy
The external principal must also receive IAM permission to use the external KMS key.

##### 2.2.6.4.3 Effective Access

`KEY POLICY ALLOW`
+
`CALLER IAM ALLOW`
+
`NO APPLICABLE DENY`
→ cross-account key use

##### 2.2.6.4.4 Critical Exam Rule
**Key policy alone is not enough. IAM policy in the external account alone is not enough.**

#### 2.2.6.5 Why Two Sides?

##### 2.2.6.5.1 Resource Owner
Account A decides:
- which external accounts/principals may use its key,
- which KMS operations they may perform.

##### 2.2.6.5.2 Caller Account
Account B decides:
- which of its principals actually receive the delegated permission.

##### 2.2.6.5.3 Mental Model

`Account A`
→ "Account B may use my key"

`Account B`
→ "Role X may exercise that permission"

#### 2.2.6.6 Account Principal vs Specific Role

##### 2.2.6.6.1 Account-Level Delegation
Key policy can name the external account principal:

`arn:aws:iam::<ACCOUNT-B-ID>:root`

This allows Account B to delegate the permitted operations through IAM.

##### 2.2.6.6.2 Specific Principal
Key policy can instead authorize a specific external IAM role/user where appropriate.

##### 2.2.6.6.3 Least Privilege
- Prefer the narrowest practical trust relationship.
- Avoid broad external-account permissions when only one workload role needs access.

#### 2.2.6.7 Cross-Account Cryptographic Operations

AWS KMS supports selected operations across accounts.

Important examples:
- `kms:Encrypt`
- `kms:Decrypt`
- `kms:ReEncrypt*`
- `kms:GenerateDataKey*`
- `kms:DescribeKey`

Other supported cross-account operations include selected grant/public-key/rotation-status operations.

##### 2.2.6.7.1 Important
- Not every KMS management operation works cross-account.
- Granting an unsupported cross-account operation has no useful effect.

#### 2.2.6.8 Key Administration vs Key Usage

##### 2.2.6.8.1 Key Usage
External principals can be authorized for supported cryptographic operations.

##### 2.2.6.8.2 Administration
Key ownership and many administrative operations remain with the key-owning account.

##### 2.2.6.8.3 Exam Mindset
A consumer account normally needs:
- use of the key,
not:
- ownership/administration of the key.

#### 2.2.6.9 Customer Managed KMS Keys

##### 2.2.6.9.1 Primary Cross-Account Choice
- Customer managed KMS keys provide customer-controlled key policies.
- This makes them the normal choice when explicit cross-account KMS access is required.

##### 2.2.6.9.2 Why
Customer controls:
- external principals/accounts,
- allowed operations,
- conditions,
- lifecycle.

#### 2.2.6.10 AWS Managed Keys and Cross-Account Access

##### 2.2.6.10.1 Limitation
- AWS managed key policies are controlled by the AWS service.
- Customers cannot edit those key policies to establish arbitrary cross-account trust.

##### 2.2.6.10.2 Exam Rule
If a scenario requires **explicit cross-account encrypted-resource sharing**, a **customer managed KMS key** is typically required.

##### 2.2.6.10.3 Trap
Do not assume:

`aws/s3`
or another AWS managed key

can simply be edited to trust another account.

#### 2.2.6.11 Key ARN

##### 2.2.6.11.1 Cross-Account Identification
- Use the KMS key ARN or supported alias ARN when referencing a key in another account for supported cryptographic operations.

##### 2.2.6.11.2 Why
A bare:
- key ID,
- alias name

can be interpreted relative to the caller's own account.

##### 2.2.6.11.3 Exam Rule
**Cross-account KMS key → think full ARN.**

#### 2.2.6.12 Example Architecture

Account A owns data and key:

`Account A`
├── S3 bucket
└── customer managed KMS key

Account B contains application:

`Account B`
└── application role

Required permissions:

`S3 bucket policy`
→ allow Account B role to access object

`KMS key policy`
→ allow Account B role/account to use key

`Account B IAM policy`
→ allow S3 operation
→ allow KMS operation

#### 2.2.6.13 Resource Access and Key Access Are Separate

##### 2.2.6.13.1 Encrypted S3 Object
To read an SSE-KMS object cross-account, caller can need:

`S3 permission`
+
`KMS decrypt permission`

##### 2.2.6.13.2 Therefore
Granting:
- `s3:GetObject`

does not automatically grant:
- `kms:Decrypt`.

##### 2.2.6.13.3 Conversely
Granting:
- `kms:Decrypt`

does not automatically grant:
- `s3:GetObject`.

##### 2.2.6.13.4 Core Rule
**Access to ciphertext and permission to decrypt ciphertext are separate authorization decisions.**

#### 2.2.6.14 S3 SSE-KMS Cross-Account Read

##### 2.2.6.14.1 Flow

`Account B role`
→ `s3:GetObject`
→ Account A bucket

S3 needs/uses:
→ Account A KMS key

KMS evaluates:
- key policy in Account A,
- IAM policy of caller in Account B,
- applicable grants/denies/conditions.

##### 2.2.6.14.2 Result
Only if both resource and key access succeed:
→ plaintext object returned to authorized caller over TLS.

#### 2.2.6.15 S3 Bucket Policy

##### 2.2.6.15.1 Purpose
- Resource policy controlling cross-account S3 access.

##### 2.2.6.15.2 Example Concept
Allow:

`arn:aws:iam::<ACCOUNT-B>:role/ApplicationRole`

to:
- `s3:GetObject`

on:
- specific bucket prefix/object resources.

##### 2.2.6.15.3 Not Enough
- Bucket policy cannot replace KMS authorization for SSE-KMS data.

#### 2.2.6.16 KMS Key Policy

##### 2.2.6.16.1 Purpose
- Primary resource policy for KMS key.

##### 2.2.6.16.2 Cross-Account
Must allow:
- external account or principal,
- required supported operations.

##### 2.2.6.16.3 Example Operations
For read:
- `kms:Decrypt`
- potentially `kms:DescribeKey`.

For write:
- `kms:Encrypt`
- `kms:GenerateDataKey*`
- potentially `kms:ReEncrypt*`.

#### 2.2.6.17 External Account IAM Policy

##### 2.2.6.17.1 Purpose
- Delegates externally granted KMS permissions to actual role/user.

##### 2.2.6.17.2 Resource
- Reference external KMS key ARN.

##### 2.2.6.17.3 Least Privilege
Example conceptual read permission:

`Action: kms:Decrypt`
`Resource: arn:aws:kms:<region>:<ACCOUNT-A>:key/<key-id>`

#### 2.2.6.18 KMS Grants

##### 2.2.6.18.1 Purpose
- Another mechanism for delegating KMS key usage.

##### 2.2.6.18.2 Cross-Account
- A grant can authorize a principal in another AWS account.

##### 2.2.6.18.3 AWS Services
- AWS services integrated with KMS frequently use grants for temporary/limited use of a KMS key on behalf of a user.

##### 2.2.6.18.4 Exam Priority
Understand:
1. key policy,
2. IAM policy,
3. grants as additional/delegated mechanism.

#### 2.2.6.19 `kms:CreateGrant`

##### 2.2.6.19.1 Purpose
- Allows creation of KMS grants.

##### 2.2.6.19.2 Security
- Powerful permission because it can delegate key usage.

##### 2.2.6.19.3 AWS Service Pattern
Key policy may allow:

`kms:CreateGrant`

with a condition such as:

`kms:GrantIsForAWSResource = true`

to constrain grant creation to integrated AWS-service resource usage.

#### 2.2.6.20 `kms:ViaService`

##### 2.2.6.20.1 Purpose
- KMS policy condition can restrict key usage to requests made through a specified AWS service.

##### 2.2.6.20.2 Example Concept
Allow key use only when operation comes through:
- S3,
- DynamoDB,
- another supported KMS-integrated service.

##### 2.2.6.20.3 Benefit
- Prevent direct KMS use outside intended service path.

#### 2.2.6.21 Encryption Context Across Accounts

##### 2.2.6.21.1 Context
- Cross-account key permissions can also be constrained by encryption context.

##### 2.2.6.21.2 Benefit
Example:
- allow decrypt only for ciphertext associated with expected application/resource context.

##### 2.2.6.21.3 Reminder
- Encryption context is non-secret.

#### 2.2.6.22 Cross-Account `Decrypt`

##### 2.2.6.22.1 Requirements

Account A:
- KMS key policy allows Account B/role `kms:Decrypt`.

Account B:
- role IAM policy allows `kms:Decrypt` on Account A key ARN.

##### 2.2.6.22.2 Optional Additional Constraints
- encryption context,
- `kms:ViaService`,
- Organizations conditions,
- service-specific conditions.

#### 2.2.6.23 Cross-Account `Encrypt`

##### 2.2.6.23.1 Requirement
External principal can encrypt using Account A key when both sides authorize appropriate operation.

##### 2.2.6.23.2 Use Case
- Central security account owns encryption keys.
- Workload accounts encrypt data under centrally governed keys.

#### 2.2.6.24 Centralized Key Management Pattern

Architecture:

`Security / Key Account`
└── customer managed KMS keys
    ├── trust Workload Account A
    ├── trust Workload Account B
    └── trust Workload Account C

Workload accounts:
→ use centrally controlled keys for approved cryptographic operations.

##### 2.2.6.24.1 Benefits
- centralized key policy ownership,
- separation of duties,
- centralized lifecycle governance,
- consistent security controls.

##### 2.2.6.24.2 Trade-Off
- Cross-account policies and service integration become more complex.

#### 2.2.6.25 Decentralized Key Pattern

Each workload account owns its own:
- customer managed KMS key.

##### 2.2.6.25.1 Benefits
- simpler ownership boundary,
- reduced cross-account dependencies.

##### 2.2.6.25.2 Trade-Off
- more distributed governance and lifecycle management.

##### 2.2.6.25.3 Exam
Choose based on explicit ownership/control requirement, not an assumption that centralized is always superior.

#### 2.2.6.26 AssumeRole vs Direct Cross-Account KMS Access

##### 2.2.6.26.1 Direct
- Account B principal directly uses Account A KMS key through cross-account permissions.

##### 2.2.6.26.2 AssumeRole
Alternative:
- principal assumes role in Account A,
- role in Account A has permission to use local KMS key.

##### 2.2.6.26.3 Difference
Direct:
`B principal`
→ external KMS key.

AssumeRole:
`B principal`
→ STS
→ `A role`
→ local KMS key.

##### 2.2.6.26.4 Exam Mindset
- Both can establish cross-account access.
- Use architecture required by trust/ownership/resource access pattern.

#### 2.2.6.27 Cross-Account Service Use

##### 2.2.6.27.1 Important
- AWS KMS cross-account authorization does not automatically mean every AWS service supports every cross-account-key scenario.

##### 2.2.6.27.2 Service Documentation
- Verify service-specific KMS behavior.

##### 2.2.6.27.3 Exam Principle
- KMS policy establishes cryptographic permission.
- Service-specific permissions/integration requirements still apply.

#### 2.2.6.28 SQS Cross-Account Encryption Context

##### 2.2.6.28.1 SQS
- SQS can use KMS for server-side encryption.

##### 2.2.6.28.2 Cross-Account Producer/Consumer
Permissions can involve:
- queue resource policy,
- IAM permissions,
- KMS key policy,
- required KMS operations.

##### 2.2.6.28.3 Mental Model
Again separate:

`may access queue?`
from
`may use encryption key?`

#### 2.2.6.29 SNS Cross-Account Encryption Context

##### 2.2.6.29.1 SNS
- SNS supports KMS server-side encryption.

##### 2.2.6.29.2 Cross-Service / Cross-Account
- Topic policy and KMS key policy can both matter.

##### 2.2.6.29.3 Developer Exam Pattern
When encrypted event/messaging integration fails:
- check service/resource permissions,
- then KMS permissions.

#### 2.2.6.30 DynamoDB Cross-Account Context

##### 2.2.6.30.1 Encryption
- DynamoDB encrypts data at rest.

##### 2.2.6.30.2 Cross-Account Access
- Resource/API authorization and encryption-key authorization are conceptually separate.

##### 2.2.6.30.3 Scope
- Do not assume the exact S3 cross-account model applies identically to every service.
- Service-specific KMS integration rules control implementation.

#### 2.2.6.31 Secrets Manager Cross-Account Context

##### 2.2.6.31.1 Relevance
- Secrets Manager can use customer managed KMS keys.
- Cross-account secret access can therefore involve:
  - secret resource policy,
  - caller IAM permission,
  - KMS key policy/permission.

##### 2.2.6.31.2 Connection
- Secret-management details belong mainly to Task 2.3.

##### 2.2.6.31.3 Mental Model
Encrypted resource sharing often requires:

`resource authorization`
+
`KMS authorization`.

#### 2.2.6.32 Cross-Account Copies

##### 2.2.6.32.1 General Problem
When copying encrypted data from Account A to Account B, the destination may need encryption under a different key.

##### 2.2.6.32.2 Conceptual Flow

`ciphertext under Key A`
→ authorized decrypt/re-encryption path
→ `ciphertext under Key B`

##### 2.2.6.32.3 KMS
- `ReEncrypt` can change KMS key protection for supported KMS ciphertext workflows without returning plaintext to caller.
- AWS service copy operations may implement service-specific encryption behavior.

#### 2.2.6.33 `ReEncrypt`

##### 2.2.6.33.1 Purpose
- Decrypt under source KMS key and encrypt under destination KMS key within KMS.

##### 2.2.6.33.2 Cross-Account
Can be useful when authorized across key/account boundaries.

##### 2.2.6.33.3 Permissions
Need appropriate permissions for:
- source key,
- destination key.

#### 2.2.6.34 Cross-Account S3 Copy Mental Model

For SSE-KMS object:

`source object`
→ permission to read source
→ permission to decrypt source key
→ copy
→ permission to write destination
→ permission to use destination key
→ destination encrypted object

##### 2.2.6.34.1 Four Boundaries
1. source resource access,
2. source key access,
3. destination resource access,
4. destination key access.

#### 2.2.6.35 Multi-Region Is Not Cross-Account

##### 2.2.6.35.1 Multi-Region Key
- Addresses compatible key material across AWS Regions.

##### 2.2.6.35.2 Cross-Account
- Addresses authorization between AWS accounts.

##### 2.2.6.35.3 Independent Dimensions
You can have:
- same account / cross Region,
- cross account / same Region,
- cross account / cross Region.

##### 2.2.6.35.4 Trap
Do not choose multi-Region KMS key merely because accounts differ.

#### 2.2.6.36 Organizations Does Not Automatically Share KMS Keys

##### 2.2.6.36.1 AWS Organizations
- Accounts being in same organization does not automatically grant KMS access.

##### 2.2.6.36.2 Still Need
- key policy,
- caller permissions,
- service/resource permissions.

##### 2.2.6.36.3 Conditions
- Organization identifiers can be used in policy conditions to constrain trusted principals where supported.

#### 2.2.6.37 SCPs

##### 2.2.6.37.1 Effect
- Service control policies can restrict permissions available to principals in organization accounts.

##### 2.2.6.37.2 Important
Even when:
- key policy allows,
- IAM policy allows,

an applicable SCP deny can still block the operation.

##### 2.2.6.37.3 Authorization Model

`key policy`
+
`IAM policy`
+
`grants`
subject to
`SCP / explicit denies / endpoint policies`
→ effective permission.

#### 2.2.6.38 VPC Endpoint Policies

##### 2.2.6.38.1 KMS Interface Endpoint
- If KMS is accessed through a VPC endpoint, endpoint policy can further restrict access.

##### 2.2.6.38.2 Troubleshooting
A cross-account KMS call can fail even when IAM/key policy appear correct if endpoint policy denies it.

#### 2.2.6.39 CloudTrail Cross-Account Visibility

##### 2.2.6.39.1 Audit
- Cross-account KMS operations can be logged in CloudTrail.

##### 2.2.6.39.2 Important AWS Behavior
- Operations using a KMS key in another account are logged in:
  - caller account,
  - key-owner account.

##### 2.2.6.39.3 Benefit
- Both sides can audit use of the shared key.

#### 2.2.6.40 Separation of Duties

##### 2.2.6.40.1 Key Account
Security team controls:
- key policy,
- lifecycle,
- key administration.

##### 2.2.6.40.2 Workload Account
Application team receives:
- encrypt/decrypt/data-key permissions only.

##### 2.2.6.40.3 Benefit
- Application cannot administer/delete key merely because it can use it.

#### 2.2.6.41 Least Privilege

##### 2.2.6.41.1 Producer
May need:
- `kms:Encrypt`,
- `kms:GenerateDataKey*`.

##### 2.2.6.41.2 Consumer
May need:
- `kms:Decrypt`.

##### 2.2.6.41.3 Copier
May need:
- decrypt/re-encrypt on source,
- encrypt/data-key permission on destination.

##### 2.2.6.41.4 Principle
Do not grant `kms:*` for a workload that only decrypts.

#### 2.2.6.42 Explicit Deny

##### 2.2.6.42.1 AWS Authorization
- Explicit deny overrides allow.

##### 2.2.6.42.2 Sources
Could come from:
- IAM policy,
- key policy,
- SCP,
- VPC endpoint policy,
- other applicable policy boundary.

##### 2.2.6.42.3 Troubleshooting
Do not stop after finding one Allow.

#### 2.2.6.43 Troubleshooting Cross-Account KMS

Check in this order:

1. **Correct KMS key/account/Region?**
2. **Key policy in key-owner account allows caller/account?**
3. **IAM policy in caller account delegates required KMS action?**
4. **Correct KMS key ARN referenced?**
5. **Resource policy allows cross-account resource access?**
6. **Required AWS-service permissions exist?**
7. **Encryption context/conditions match?**
8. **Grant exists if service workflow needs one?**
9. **Any SCP/endpoint/explicit deny?**
10. **Key enabled and usable?**

#### 2.2.6.44 `AccessDeniedException`

##### 2.2.6.44.1 Common Causes
- external account absent from key policy,
- caller IAM policy missing KMS permission,
- wrong key ARN,
- explicit deny,
- service-specific grant/permission missing,
- encryption-context condition mismatch.

##### 2.2.6.44.2 Exam Pattern
If cross-account encrypted resource is accessible but decryption fails:
→ investigate KMS authorization.

#### 2.2.6.45 Decision Flow

##### 2.2.6.45.1 Step 1 — Is Resource Cross-Account?
- Identify resource owner.
- Identify caller account.

##### 2.2.6.45.2 Step 2 — Is It KMS Encrypted?
- Identify KMS key owner.

##### 2.2.6.45.3 Step 3 — Is Key Customer Managed?
- Cross-account explicit trust usually requires customer managed KMS key.

##### 2.2.6.45.4 Step 4 — Authorize Key Owner Side
- Update key policy.

##### 2.2.6.45.5 Step 5 — Authorize Caller Side
- Add IAM policy to external role/user.

##### 2.2.6.45.6 Step 6 — Authorize Resource
- Bucket/topic/queue/secret/etc. policy or relevant service mechanism.

##### 2.2.6.45.7 Step 7 — Restrict
Use least privilege:
- actions,
- resource ARN,
- service conditions,
- encryption context,
- organization/account/principal constraints.

#### 2.2.6.46 Common Exam Traps

##### 2.2.6.46.1 "IAM Policy in Account B Is Enough"
- False.

##### 2.2.6.46.2 "Key Policy in Account A Is Enough"
- False for delegated cross-account principal use.

##### 2.2.6.46.3 "S3 Bucket Policy Automatically Grants KMS Decrypt"
- False.

##### 2.2.6.46.4 "KMS Decrypt Automatically Grants S3 GetObject"
- False.

##### 2.2.6.46.5 "AWS Managed KMS Key Can Be Freely Modified for Cross-Account Trust"
- False.

##### 2.2.6.46.6 "Same AWS Organization Means Shared KMS Access"
- False.

##### 2.2.6.46.7 "Multi-Region Key Solves Cross-Account Access"
- False.

##### 2.2.6.46.8 "Cross-Account User Can Administer Everything on Key"
- False.
- Only supported cross-account operations are effective.

##### 2.2.6.46.9 "Bare Key ID Is Best Cross-Account Reference"
- False.
- Use full key ARN/appropriate ARN identifier.

##### 2.2.6.46.10 "One Allow Means Access Works"
- False.
- Explicit denies and other policy layers still apply.

##### 2.2.6.46.11 "Encrypted Resource Permission Equals Plaintext Permission"
- False.
- Resource and KMS authorization are separate.

##### 2.2.6.46.12 "All AWS Services Behave Identically with External KMS Keys"
- False.
- Service-specific KMS integration rules matter.

#### 2.2.6.50 Exam-Level Knowledge Frame

Know these cold:

**Cross-account KMS**
→ authorization from key-owner account + caller account.

**Key-owner account**
→ key policy grants external trust.

**Caller account**
→ IAM policy delegates key usage to principal.

**Encrypted resource**
→ resource access is separate from key access.

**S3 SSE-KMS cross-account**
→ S3 permission + KMS permission.

**Customer managed KMS key**
→ normal choice for explicit cross-account key policy control.

**AWS managed key**
→ customer cannot edit policy for arbitrary cross-account trust.

**Key ARN**
→ use full external key identifier.

**Grants**
→ additional KMS delegation mechanism, often used by AWS services.

**CloudTrail**
→ cross-account KMS use is auditable from both caller and key-owner accounts.

The fastest exam discriminator is:

**Cross-account encrypted resource? Think two locks.**

`LOCK 1`
→ Can I access the resource?

`LOCK 2`
→ Can I use the KMS key?

For direct cross-account KMS use, the second lock itself normally requires agreement from both accounts:

`key policy`
+
`caller IAM policy`.

Final principle:

**Cross-account encryption is not primarily about a different encryption algorithm. It is about extending cryptographic authorization across an AWS account trust boundary while keeping resource access, key usage, and key administration independently controlled.**
