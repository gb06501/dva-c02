### 2.2.4 Use encryption and decryption keys

#### 2.2.4.1 Exam and Task Context

##### 2.2.4.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.2 is **Implement encryption by using AWS services**.
- Skill 2.2.4 is **Use encryption and decryption keys**.
- Earlier skills established:
  - 2.2.1 → where encryption applies: at rest vs in transit.
  - 2.2.2 → certificate/PKI management.
  - 2.2.3 → who encrypts stored data: client vs server.
- 2.2.4 now focuses on **how cryptographic keys are selected, authorized, and used to encrypt/decrypt data**.

##### 2.2.4.1.2 Core Question
- **Which key should protect the data, who may use that key, and should KMS encrypt the payload directly or protect a data key that encrypts the payload?**

#### 2.2.4.2 Core Mental Model

For AWS application encryption:

`principal`
→ authorization to use KMS key
→ cryptographic operation
→ KMS key
→ ciphertext / plaintext

For real application payloads, the more important scalable pattern is:

`KMS key`
→ protects
`data key`
→ encrypts
`application data`

This is **envelope encryption**.

#### 2.2.4.3 AWS KMS

##### 2.2.4.3.1 Purpose
- AWS Key Management Service (AWS KMS) creates and controls cryptographic keys.
- KMS key material is protected by AWS KMS hardware security modules.
- KMS keys cannot be exported from KMS in plaintext.

##### 2.2.4.3.2 Developer Role
Applications normally interact with KMS through:
- AWS SDK,
- AWS service integrations,
- AWS Encryption SDK,
- AWS Database Encryption SDK,
- other AWS-supported encryption libraries.

#### 2.2.4.4 KMS Key vs Data Key

##### 2.2.4.4.1 KMS Key
- Long-lived cryptographic key managed by AWS KMS.
- Used through KMS API operations.
- Plaintext KMS key material does not leave KMS.

##### 2.2.4.4.2 Data Key
- Cryptographic key generated for encrypting application data.
- Can be returned to application in plaintext for immediate local use.
- Encrypted copy can be stored alongside ciphertext.

##### 2.2.4.4.3 Critical Distinction

`KMS key`
→ protects keys

`data key`
→ protects bulk data

#### 2.2.4.5 Symmetric Encryption KMS Key

##### 2.2.4.5.1 Default
- `SYMMETRIC_DEFAULT`.
- AWS KMS uses AES-256-GCM for symmetric encryption KMS keys.

##### 2.2.4.5.2 Same Key
- Same KMS key is used for encryption and decryption.

##### 2.2.4.5.3 Primary AWS Use
- Most common KMS key type.
- AWS services integrated with KMS use symmetric encryption KMS keys for service-side data encryption.

##### 2.2.4.5.4 Exam Default
- If an AWS service needs a KMS key to encrypt stored data:
  - think **symmetric encryption KMS key**.

#### 2.2.4.6 Asymmetric KMS Key

##### 2.2.4.6.1 Structure
- Public key.
- Private key.

##### 2.2.4.6.2 Encryption
- Public key encrypts.
- Private key decrypts.

##### 2.2.4.6.3 AWS KMS Behavior
- Private key remains protected inside KMS.
- Public key can be downloaded and used outside KMS.

##### 2.2.4.6.4 Strong Use Case
- Data must be encrypted outside AWS/by a caller that cannot invoke KMS, then decrypted through KMS.

##### 2.2.4.6.5 Important
- AWS services integrated with KMS use **symmetric**, not asymmetric, KMS keys for service encryption.

#### 2.2.4.7 Key Usage

A KMS key has a defined cryptographic purpose.

Possible current key usages include:
- `ENCRYPT_DECRYPT`
- `SIGN_VERIFY`
- `GENERATE_VERIFY_MAC`
- `KEY_AGREEMENT`

##### 2.2.4.7.1 Exam Focus
For this skill:
- primary → `ENCRYPT_DECRYPT`.

##### 2.2.4.7.2 Important
- Key usage is chosen at key creation.
- One KMS key cannot simply be repurposed for every cryptographic operation.

#### 2.2.4.8 Key Spec

##### 2.2.4.8.1 Purpose
- Defines cryptographic configuration/type of KMS key.

##### 2.2.4.8.2 Common Exam Value
- `SYMMETRIC_DEFAULT`.

##### 2.2.4.8.3 Important
- Key spec is selected at creation and cannot later be changed.

#### 2.2.4.9 `Encrypt`

##### 2.2.4.9.1 Purpose
- Encrypt small plaintext directly using a KMS key.

##### 2.2.4.9.2 Flow

`plaintext`
→ `kms:Encrypt`
→ KMS key
→ `ciphertext blob`

##### 2.2.4.9.3 Limitation
- Direct KMS encryption is for relatively small payloads.
- Current symmetric KMS direct encryption supports plaintext under the documented KMS API limit (commonly 4 KiB).

##### 2.2.4.9.4 Exam Rule
- Small secret/value → direct KMS encryption may fit.
- Large object/file → use envelope encryption/data key.

#### 2.2.4.10 `Decrypt`

##### 2.2.4.10.1 Purpose
- Decrypt ciphertext produced under a KMS encryption key.

##### 2.2.4.10.2 Flow

`ciphertext`
→ `kms:Decrypt`
→ authorized KMS key
→ `plaintext`

##### 2.2.4.10.3 Symmetric Ciphertext
- KMS ciphertext blob includes metadata allowing KMS to identify relevant key information.

##### 2.2.4.10.4 Authorization
- Caller needs permission to perform `kms:Decrypt`.

#### 2.2.4.11 `GenerateDataKey`

##### 2.2.4.11.1 Purpose
- Generate a symmetric data key for local application encryption.

##### 2.2.4.11.2 Returns
Typically:
- plaintext data key,
- encrypted copy of data key.

##### 2.2.4.11.3 Flow

`GenerateDataKey`
→ plaintext data key
→ encrypt application data

and

`GenerateDataKey`
→ encrypted data key
→ store with ciphertext

#### 2.2.4.12 Envelope Encryption

##### 2.2.4.12.1 Encryption

`KMS key`
→ `GenerateDataKey`
→
├── plaintext data key
│   → encrypt payload
│   → discard plaintext data key
│
└── encrypted data key
    → store with encrypted payload

##### 2.2.4.12.2 Decryption

`encrypted data key`
→ `kms:Decrypt`
→ plaintext data key
→ decrypt payload
→ discard plaintext data key

##### 2.2.4.12.3 Why
- Efficient for large data.
- KMS key never leaves KMS.
- Encrypted data key can safely be stored with encrypted data.

#### 2.2.4.13 Why Not Use KMS `Encrypt` for Large Data?

##### 2.2.4.13.1 KMS Is a Key Service
- It is not intended as a bulk-data encryption engine.

##### 2.2.4.13.2 Data Keys
- Symmetric algorithms are efficient for large payloads.
- KMS protects the data key.

##### 2.2.4.13.3 Exam Clue
**Encrypt a large file with KMS**
→ `GenerateDataKey` / AWS Encryption SDK
→ not direct `Encrypt` of the whole file.

#### 2.2.4.14 Plaintext Data Key Handling

##### 2.2.4.14.1 Sensitive
- Plaintext data key is secret.

##### 2.2.4.14.2 Use
- Keep only as long as required to encrypt/decrypt data.

##### 2.2.4.14.3 Cleanup
- Remove/zero plaintext key material from memory as soon as practical.

##### 2.2.4.14.4 Storage
- Store **encrypted data key**, not plaintext data key.

#### 2.2.4.15 KMS Does Not Store Data Keys

##### 2.2.4.15.1 KMS Generates Them
- KMS can generate and encrypt/decrypt data keys.

##### 2.2.4.15.2 Application Responsibility
- KMS does not store, track, or manage generated data keys for the application.

##### 2.2.4.15.3 Pattern
Store:

`encrypted payload`
+
`encrypted data key`
+
required encryption metadata

#### 2.2.4.16 `GenerateDataKeyWithoutPlaintext`

##### 2.2.4.16.1 Purpose
- Generate encrypted data key without returning plaintext copy.

##### 2.2.4.16.2 Use Case
- Provision encrypted key material for later use rather than immediate encryption.

##### 2.2.4.16.3 Later
- Call `Decrypt` when plaintext key is actually required.

#### 2.2.4.17 Encryption Context

##### 2.2.4.17.1 Definition
- Optional set of non-secret key-value pairs used as additional authenticated data with symmetric KMS cryptographic operations.

##### 2.2.4.17.2 Example

`application = orders`
`tenant = tenant-123`

##### 2.2.4.17.3 Encryption
- Context becomes cryptographically bound to ciphertext.

##### 2.2.4.17.4 Decryption
- Exact matching encryption context is required when decrypting ciphertext encrypted with that context.

#### 2.2.4.18 Encryption Context Is Not Secret

##### 2.2.4.18.1 CloudTrail
- Encryption context can appear in logs.

##### 2.2.4.18.2 Therefore
Do not put:
- passwords,
- tokens,
- PII,
- secrets
into encryption context.

##### 2.2.4.18.3 Purpose
Use contextual identifiers useful for:
- authorization,
- auditability,
- cryptographic binding.

#### 2.2.4.19 Encryption Context and IAM

##### 2.2.4.19.1 Policy
- KMS permissions can be conditioned on encryption context.

##### 2.2.4.19.2 Example Concept

Allow decrypt only when:

`kms:EncryptionContext:application = orders`

##### 2.2.4.19.3 Benefit
- Key access can be constrained to expected application/data context.

#### 2.2.4.20 KMS Authorization Layers

Using a KMS key can depend on:
- key policy,
- IAM identity policy,
- grants,
- permissions boundaries/session policies/SCPs where applicable.

##### 2.2.4.20.1 Key Policy
- Every KMS key has a key policy.
- It is the primary authorization mechanism controlling the KMS key.

##### 2.2.4.20.2 IAM
- IAM permissions can participate when key policy allows the appropriate IAM delegation model.

#### 2.2.4.21 Key Policy

##### 2.2.4.21.1 Controls
Who can:
- administer key,
- use key,
- delegate use.

##### 2.2.4.21.2 Example Cryptographic Permissions
- `kms:Encrypt`
- `kms:Decrypt`
- `kms:GenerateDataKey`
- `kms:ReEncrypt*`

##### 2.2.4.21.3 Least Privilege
- Do not grant broad `kms:*` merely because an application needs decrypt.

#### 2.2.4.22 KMS Grants

##### 2.2.4.22.1 Purpose
- Delegate permission to use a KMS key.

##### 2.2.4.22.2 AWS Services
- Integrated AWS services often use grants to obtain limited key permissions on behalf of users/resources.

##### 2.2.4.22.3 Exam Understanding
- Key policy/IAM are primary design concepts.
- Recognize grants as another KMS authorization mechanism.

#### 2.2.4.23 KMS Key Identifier

A KMS key can commonly be referenced through:
- key ID,
- key ARN,
- alias name,
- alias ARN,
depending on API/context.

##### 2.2.4.23.1 Cross-Account
- Full ARN is commonly required/safer to identify key in another account.

#### 2.2.4.24 KMS Alias

##### 2.2.4.24.1 Purpose
- Friendly name pointing to KMS key.

Example:
- `alias/orders-data`

##### 2.2.4.24.2 Benefit
- Application configuration can reference logical purpose rather than hard-coded opaque key ID.

##### 2.2.4.24.3 Important
- Alias is not key material.
- Alias can be repointed to another compatible KMS key.

#### 2.2.4.25 AWS Owned Keys

##### 2.2.4.25.1 Ownership
- AWS service owns and manages key.

##### 2.2.4.25.2 Customer Control
- Customer does not manage key policy/lifecycle directly.

##### 2.2.4.25.3 Use
- Transparent service encryption where customer-specific KMS control is not required.

#### 2.2.4.26 AWS Managed Keys

##### 2.2.4.26.1 Ownership
- KMS keys in customer account created/managed by AWS service for that service.

##### 2.2.4.26.2 Naming
Often aliases such as:
- `aws/s3`
- `aws/dynamodb`

##### 2.2.4.26.3 Control
- Less customer control than customer managed keys.

#### 2.2.4.27 Customer Managed Keys

##### 2.2.4.27.1 Created/Controlled by Customer
Customer controls:
- key policy,
- aliases,
- grants,
- enable/disable,
- lifecycle,
- rotation configuration where supported,
- deletion scheduling.

##### 2.2.4.27.2 Best Fit
When requirement says:
- control who may use key,
- cross-account key use,
- explicit key policy,
- separate application keys,
- customer-controlled lifecycle,
- enhanced audit/control.

#### 2.2.4.28 Key Selection Mental Model

`Need only transparent AWS-managed encryption?`
→ service default/AWS owned key may be enough.

`Need KMS integration without custom lifecycle?`
→ AWS managed key may fit.

`Need explicit policies, cross-account use, lifecycle control?`
→ customer managed KMS key.

#### 2.2.4.29 Service Integration Example — S3 SSE-KMS

##### 2.2.4.29.1 Upload

`application`
→ S3 `PutObject`
→ S3 uses KMS key/data-key workflow
→ encrypted object

##### 2.2.4.29.2 Download

`GetObject`
→ S3 uses KMS to decrypt required key material
→ plaintext returned over TLS

##### 2.2.4.29.3 Caller Permissions
Depending on operation:
- S3 access.
- appropriate KMS access.

#### 2.2.4.30 Client-Side Example

##### 2.2.4.30.1 Encrypt

`GenerateDataKey`
→ plaintext key + encrypted key

`plaintext key`
→ local encryption
→ ciphertext

Store:
- ciphertext,
- encrypted key.

##### 2.2.4.30.2 Decrypt

retrieve:
- ciphertext,
- encrypted key

`encrypted key`
→ KMS `Decrypt`
→ plaintext data key
→ local decryption.

#### 2.2.4.31 AWS Encryption SDK

##### 2.2.4.31.1 Purpose
- Implements client-side envelope encryption patterns.

##### 2.2.4.31.2 Benefit
- Avoid implementing cryptographic framing and data-key handling manually.

##### 2.2.4.31.3 Exam Principle
- For application-level encryption:
  - prefer AWS-supported encryption SDK/library over custom cryptography.

#### 2.2.4.32 Asymmetric Encryption Flow

##### 2.2.4.32.1 Outside KMS

`GetPublicKey`
→ download public key

external system:
`public key + plaintext`
→ ciphertext

AWS:
`ciphertext`
→ KMS `Decrypt`
→ plaintext

##### 2.2.4.32.2 Strong Use Case
- External producer cannot authenticate/call KMS for encryption.
- Producer can still encrypt using public key.
- Only KMS-authorized principals can use private key for decryption.

#### 2.2.4.33 Symmetric vs Asymmetric

| Characteristic | Symmetric | Asymmetric |
| --- | --- | --- |
| Keys | Same secret key | Public/private pair |
| Performance | Faster | Slower |
| AWS service integrations | Yes | Not for service-side data encryption |
| Public key export | N/A | Yes |
| Private key leaves KMS | No | No |
| Envelope encryption | Primary model | Specialized use |
| Typical exam default | Yes | Only when requirement demands public/private separation |

#### 2.2.4.34 Signing Is Not Encryption

##### 2.2.4.34.1 Signing
- Private-key/signing operation proves authenticity/integrity.

##### 2.2.4.34.2 Encryption
- Protects confidentiality.

##### 2.2.4.34.3 KMS
- Asymmetric KMS keys can have different key usages, but a key configured for signing is not an encryption key.

#### 2.2.4.35 HMAC Is Not Encryption

##### 2.2.4.35.1 HMAC KMS Key
- Used with:
  - `GenerateMac`
  - `VerifyMac`

##### 2.2.4.35.2 Purpose
- Integrity/authenticity.

##### 2.2.4.35.3 Not
- Data confidentiality.

##### 2.2.4.35.4 Exam Rule
- "Encrypt/decrypt data" → do not choose HMAC key.

#### 2.2.4.36 Re-Encryption

##### 2.2.4.36.1 `ReEncrypt`
- KMS can decrypt ciphertext under one KMS key and re-encrypt under another without exposing plaintext to caller.

##### 2.2.4.36.2 Use
- Move protected key/data between KMS keys.
- Change protection boundary.

##### 2.2.4.36.3 Cross-Account
- Relevant to later Skill 2.2.6.

#### 2.2.4.37 Multi-Region Keys

##### 2.2.4.37.1 Concept
- Related KMS keys in different Regions can share the same key material and key ID.

##### 2.2.4.37.2 Use
- Applications requiring compatible cryptographic operations across Regions.

##### 2.2.4.37.3 Important
- Multi-Region keys are not globally shared objects.
- Each regional key has independent ARN/policy and must be managed in its Region.

##### 2.2.4.37.4 Exam Scope
- Recognize when cross-Region cryptographic portability is explicitly required.
- Do not choose multi-Region keys by default.

#### 2.2.4.38 Key Origin

Possible KMS key material origins include:
- `AWS_KMS`
- imported/external key material,
- AWS CloudHSM custom key store,
- external key store.

##### 2.2.4.38.1 Exam Default
- Standard AWS KMS-generated key material unless requirement specifically asks for BYOK/HSM/external control.

#### 2.2.4.39 Imported Key Material

##### 2.2.4.39.1 Purpose
- Bring your own cryptographic key material into KMS-supported key.

##### 2.2.4.39.2 Responsibility
- Customer has additional lifecycle/durability responsibilities for imported material.

##### 2.2.4.39.3 Exam Clue
- Requirement explicitly says:
  - bring your own key material,
  - externally generated key,
  - control origin.

#### 2.2.4.40 CloudHSM vs KMS — Boundary

##### 2.2.4.40.1 KMS
- Managed key service.
- Primary DVA encryption/key-management choice.

##### 2.2.4.40.2 CloudHSM
- Dedicated HSM control/use cases.
- Greater cryptographic infrastructure responsibility.

##### 2.2.4.40.3 Exam Rule
- Do not jump to CloudHSM when KMS satisfies requirement.

#### 2.2.4.41 KMS Key State

A KMS key can have lifecycle states such as:
- enabled,
- disabled,
- pending deletion,
- pending import,
depending on key type/origin.

##### 2.2.4.41.1 Availability
- Disabled/deleted key can prevent decryption of dependent data.

##### 2.2.4.41.2 Operational Principle
- Key lifecycle is part of data availability.

#### 2.2.4.42 Deleting a KMS Key

##### 2.2.4.42.1 Consequence
- Data encrypted solely under deleted key may become unrecoverable.

##### 2.2.4.42.2 Safety
- KMS uses scheduled deletion rather than immediate deletion.

##### 2.2.4.42.3 Exam Mindset
- Never treat key deletion as ordinary cleanup without checking dependent ciphertext/resources.

#### 2.2.4.43 CloudTrail

##### 2.2.4.43.1 Audit
KMS API activity can be recorded through CloudTrail.

##### 2.2.4.43.2 Useful Events
- `Encrypt`
- `Decrypt`
- `GenerateDataKey`
- key administration operations.

##### 2.2.4.43.3 Benefit
- Trace which principal used or managed a key.

#### 2.2.4.44 Least Privilege

##### 2.2.4.44.1 Encrypt-Only Producer
May need:
- `kms:Encrypt`
or
- `kms:GenerateDataKey`
depending on pattern.

##### 2.2.4.44.2 Decrypting Consumer
Needs:
- `kms:Decrypt`.

##### 2.2.4.44.3 Separation
- Not every producer needs decrypt permission.

##### 2.2.4.44.4 Strong Pattern
Grant only cryptographic operations required by service responsibility.

#### 2.2.4.45 Key-per-Application / Key-per-Boundary

##### 2.2.4.45.1 Benefit
Separate KMS keys can provide:
- independent access policies,
- independent audit boundaries,
- blast-radius reduction,
- lifecycle separation.

##### 2.2.4.45.2 Trade-Off
- More keys/policies increase management complexity and cost.

##### 2.2.4.45.3 Principle
- Choose key boundaries based on security/ownership requirements, not one key per object.

#### 2.2.4.46 Caching Data Keys

##### 2.2.4.46.1 Benefit
- Reduce KMS calls/latency/cost in high-throughput client-side encryption.

##### 2.2.4.46.2 Risk
- Reusing plaintext data keys increases exposure.

##### 2.2.4.46.3 SDK
- Use supported encryption SDK caching mechanisms/policies rather than inventing unsafe caching.

##### 2.2.4.46.4 Exam Depth
- Recognize performance/security trade-off; not a primary DVA configuration topic.

#### 2.2.4.47 KMS Throttling / API Dependency

##### 2.2.4.47.1 Runtime
- Direct application KMS calls are API calls with quotas/latency.

##### 2.2.4.47.2 Design
- Envelope encryption avoids using KMS for every block of application data.

##### 2.2.4.47.3 Managed Services
- Service integrations optimize encryption workflows according to service implementation.

#### 2.2.4.48 Failure Patterns

##### 2.2.4.48.1 `AccessDeniedException`
Possible causes:
- IAM policy missing.
- key policy missing.
- explicit deny.
- grant absent.
- wrong principal/account.

##### 2.2.4.48.2 Invalid Ciphertext
Possible causes:
- wrong key/algorithm,
- corrupted ciphertext,
- mismatched encryption context.

##### 2.2.4.48.3 Disabled Key
- Cryptographic operation unavailable.

##### 2.2.4.48.4 Wrong Region
- KMS key is regional unless using related multi-Region key design.

#### 2.2.4.49 Decision Flow

##### 2.2.4.49.1 Step 1 — What Is Being Protected?
- Small value?
- Large payload?
- AWS service data?
- External/offline producer data?

##### 2.2.4.49.2 Step 2 — AWS Service Encryption?
- Use symmetric KMS key where KMS integration is required.

##### 2.2.4.49.3 Step 3 — Large Client-Side Payload?
- Use data key + envelope encryption.

##### 2.2.4.49.4 Step 4 — External Party Must Encrypt Without KMS Access?
- Consider asymmetric KMS key/public key.

##### 2.2.4.49.5 Step 5 — Who Needs Decrypt?
- Grant `kms:Decrypt` only to required consumers.

##### 2.2.4.49.6 Step 6 — Need Context Restriction?
- Use encryption context + KMS policy conditions where appropriate.

##### 2.2.4.49.7 Step 7 — Need Customer Lifecycle/Cross-Account Control?
- Use customer managed KMS key.

#### 2.2.4.50 Common Exam Traps

##### 2.2.4.50.1 "KMS Key Material Can Be Downloaded"
- False for KMS keys.
- Plaintext KMS key material does not leave KMS.

##### 2.2.4.50.2 "Data Keys Stay Inside KMS"
- False.
- Plaintext data key can be returned for local use.

##### 2.2.4.50.3 "KMS Stores My Generated Data Keys"
- False.

##### 2.2.4.50.4 "Use KMS Encrypt for a 100 MB File"
- Wrong.
- Use envelope encryption/data key.

##### 2.2.4.50.5 "AWS Services Use Asymmetric KMS Keys for SSE"
- False.
- Integrated AWS services use symmetric encryption KMS keys.

##### 2.2.4.50.6 "Encryption Context Is Secret Metadata"
- False.
- It can be logged and must not contain secrets.

##### 2.2.4.50.7 "Any KMS Key Can Encrypt Data"
- False.
- Key usage/spec determines allowed cryptographic operations.

##### 2.2.4.50.8 "HMAC Key Encrypts Data"
- False.

##### 2.2.4.50.9 "Signing and Encryption Are the Same"
- False.

##### 2.2.4.50.10 "IAM Allow Alone Always Grants KMS Access"
- Too simplistic.
- KMS key policy is central to authorization.

##### 2.2.4.50.11 "Customer Managed Key Means Customer Holds Raw Key"
- False.

##### 2.2.4.50.12 "Deleting Key Only Deletes Configuration"
- False.
- It can make ciphertext permanently unrecoverable.

##### 2.2.4.50.13 "Alias Is a Cryptographic Key"
- False.
- Alias is a logical pointer/name.

#### 2.2.4.54 Exam-Level Knowledge Frame

Know these cold:

**KMS key**
→ long-lived key managed inside KMS.

**Data key**
→ key used locally to encrypt bulk application data.

**Envelope encryption**
→ KMS key encrypts data key; data key encrypts payload.

**`Encrypt`**
→ direct encryption of small payload.

**`Decrypt`**
→ decrypt KMS ciphertext/encrypted data key.

**`GenerateDataKey`**
→ plaintext data key + encrypted data key.

**Symmetric KMS key**
→ default for AWS service encryption.

**Asymmetric KMS key**
→ public/private pair; useful when public key must be usable outside KMS.

**Encryption context**
→ non-secret authenticated context; must match for decryption.

**Key policy**
→ central KMS authorization control.

**Customer managed key**
→ use when explicit lifecycle/policy/cross-account control is required.

The fastest exam discriminator:

**Large data?**
→ data key/envelope encryption.

**AWS service SSE?**
→ symmetric KMS key.

**External party encrypts without AWS credentials?**
→ asymmetric public key may fit.

**Need decrypt?**
→ explicitly authorize `kms:Decrypt`.

Final principle:

**Use KMS keys as protected root/key-encryption keys and data keys for bulk encryption. Keep plaintext key material exposure minimal and grant cryptographic operations only to principals that actually need them.**
