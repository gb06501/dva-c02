### 2.2.2 Describe certificate management (for example, AWS Private CA)

#### 2.2.2.1 Exam and Task Context

##### 2.2.2.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.2 is **Implement encryption by using AWS services**.
- Skill 2.2.2 is **Describe certificate management (for example, AWS Private CA)**.
- This skill follows 2.2.1, which established the difference between encryption at rest and encryption in transit.
- 2.2.2 now focuses on the **identity and trust mechanism behind TLS and certificate-based communication**.

##### 2.2.2.1.2 Core Question
- **How are certificates issued, trusted, renewed, deployed, and used to establish trusted encrypted communication in AWS?**

#### 2.2.2.2 Core Mental Model

A certificate-management lifecycle is:

`key pair`
→ `certificate request`
→ `certificate authority verifies/approves`
→ `certificate issued`
→ `certificate deployed`
→ `client validates trust`
→ `TLS session established`
→ `certificate renewed/replaced before expiration`

The key principle is:

**A certificate does not merely enable encryption; it binds an identity to a public key and lets another party decide whether that identity should be trusted.**

#### 2.2.2.3 X.509 Certificates

##### 2.2.2.3.1 Purpose
- X.509 certificates are the standard certificate format used in TLS.

##### 2.2.2.3.2 Certificate Contains
Typical information includes:
- subject/identity,
- public key,
- issuer,
- validity period,
- serial number,
- extensions,
- CA signature.

##### 2.2.2.3.3 Important
- Certificate contains the **public key**.
- The private key is separate and must be protected.

#### 2.2.2.4 Public and Private Keys

##### 2.2.2.4.1 Key Pair
- Public key:
  - can be distributed.
- Private key:
  - must remain secret.

##### 2.2.2.4.2 TLS
- Certificate proves that a trusted CA has bound a public key to an identity.

##### 2.2.2.4.3 Private Key Security
- If private key is compromised, attacker may impersonate the certificate holder until:
  - certificate expires,
  - certificate is revoked,
  - key/certificate is replaced.

#### 2.2.2.5 Certificate Authority — CA

##### 2.2.2.5.1 Purpose
- CA signs certificates and acts as a trust anchor/intermediate trust authority.

##### 2.2.2.5.2 Trust Model

`client trusts CA`
→ CA signed server certificate
→ client trusts certificate subject if validation succeeds

##### 2.2.2.5.3 Types
- Public CA.
- Private CA.

#### 2.2.2.6 Public Certificates

##### 2.2.2.6.1 Purpose
- Used when public clients such as browsers must trust the endpoint.

##### 2.2.2.6.2 Trust
- Issued by public CAs whose root certificates are trusted by major operating systems/browsers.

##### 2.2.2.6.3 AWS Context
- AWS Certificate Manager (ACM) can issue and manage public certificates for supported AWS services.

#### 2.2.2.7 Private Certificates

##### 2.2.2.7.1 Purpose
- Used for internal/private identities where public browser trust is not required.

##### 2.2.2.7.2 Examples
- Internal service-to-service TLS.
- Internal load balancer endpoints.
- Private application infrastructure.
- Device/client certificates in controlled environments.

##### 2.2.2.7.3 Trust
- Clients must explicitly trust the private CA chain.

#### 2.2.2.8 AWS Certificate Manager — ACM

##### 2.2.2.8.1 Purpose
- ACM provisions, manages, and deploys public and private TLS certificates for supported AWS services.

##### 2.2.2.8.2 Typical Integrations
- Elastic Load Balancing.
- Amazon CloudFront.
- Amazon API Gateway.
- Other supported AWS services.

##### 2.2.2.8.3 Managed Lifecycle
- ACM can handle certificate renewal for eligible ACM-issued certificates integrated with supported AWS services.

##### 2.2.2.8.4 Benefit
- Removes much of the manual certificate generation, storage, deployment, and renewal work.

#### 2.2.2.9 ACM Public Certificate Flow

##### 2.2.2.9.1 Flow

`request certificate`
→ validate domain ownership
→ ACM issues certificate
→ attach certificate to supported AWS service
→ ACM monitors/renews certificate

##### 2.2.2.9.2 Domain Validation
- DNS validation.
- Email validation where supported.

##### 2.2.2.9.3 Preferred Automation
- DNS validation is generally better suited to automated renewal because validation can remain continuously provable.

#### 2.2.2.10 Domain Name

##### 2.2.2.10.1 Certificate Identity
- Public TLS certificates identify domain names.

##### 2.2.2.10.2 Examples
- `api.example.com`
- `www.example.com`

##### 2.2.2.10.3 Wildcard
- Example:
  - `*.example.com`

##### 2.2.2.10.4 Important
- Wildcard certificate does not normally cover the parent/root name itself.
- `*.example.com` does not mean `example.com`.

#### 2.2.2.11 Subject Alternative Name — SAN

##### 2.2.2.11.1 Purpose
- Certificate can identify multiple DNS names through SAN entries.

##### 2.2.2.11.2 Example
One certificate:
- `api.example.com`
- `auth.example.com`
- `www.example.com`

##### 2.2.2.11.3 Modern TLS
- SAN is the primary mechanism clients use for hostname matching.

#### 2.2.2.12 Certificate Validation

##### 2.2.2.12.1 Client Checks
A TLS client normally validates:
- certificate chain,
- issuer trust,
- certificate signature,
- expiration/validity,
- hostname identity,
- revocation status where applicable.

##### 2.2.2.12.2 Failure
- If validation fails, secure connection should not be trusted.

#### 2.2.2.13 Certificate Chain

##### 2.2.2.13.1 Structure

`root CA`
→ signs `intermediate CA`
→ signs `leaf/server certificate`

##### 2.2.2.13.2 Root CA
- Trust anchor.
- Self-signed root certificate.

##### 2.2.2.13.3 Intermediate CA
- Allows root key to remain more protected/offline while intermediates issue certificates.

##### 2.2.2.13.4 Leaf Certificate
- Certificate presented by server/application/device.

#### 2.2.2.14 Root CA

##### 2.2.2.14.1 Importance
- Root CA is highest trust anchor in a PKI hierarchy.

##### 2.2.2.14.2 Security
- Compromise of root CA private key can compromise the entire trust hierarchy.

##### 2.2.2.14.3 Best Practice
- Root CA should typically issue subordinate CAs rather than directly issuing every application certificate.

#### 2.2.2.15 Intermediate / Subordinate CA

##### 2.2.2.15.1 Purpose
- Delegates certificate issuance.

##### 2.2.2.15.2 Benefits
- Segmentation.
- Reduced root-key exposure.
- Different policies for different environments or use cases.

##### 2.2.2.15.3 Example
- Root CA.
- Production issuing CA.
- Development issuing CA.

#### 2.2.2.16 AWS Private CA

##### 2.2.2.16.1 Purpose
- AWS Private CA is a managed private certificate authority service.

##### 2.2.2.16.2 Use
- Create/manage private CA hierarchies.
- Issue private certificates.
- Support private PKI workloads without operating CA infrastructure manually.

##### 2.2.2.16.3 Typical Workloads
- Internal TLS.
- Service-to-service authentication.
- Private API endpoints.
- Internal load balancers.
- Devices/clients.
- Private infrastructure identities.

#### 2.2.2.17 Private CA Hierarchy

##### 2.2.2.17.1 Root CA

`AWS Private CA root`
→ signs subordinate CA

##### 2.2.2.17.2 Subordinate CA

`subordinate CA`
→ issues end-entity certificates

##### 2.2.2.17.3 Design Benefit
- Different subordinate CAs can represent:
  - environment,
  - business unit,
  - workload type,
  - region,
  - security domain.

#### 2.2.2.18 ACM + AWS Private CA

##### 2.2.2.18.1 Relationship
- ACM can request/manage private certificates issued by AWS Private CA.

##### 2.2.2.18.2 Pattern

`ACM`
→ requests private certificate
→ `AWS Private CA`
→ issues certificate
→ ACM deploys to supported service

##### 2.2.2.18.3 Benefit
- Managed certificate deployment with a private PKI trust model.

#### 2.2.2.19 Public CA vs Private CA

| Requirement | Public CA | Private CA |
| --- | --- | --- |
| Public browser trust | Yes | No, unless trust explicitly installed |
| Internet-facing website | Typical | Usually not |
| Internal service identity | Possible but unnecessary | Strong fit |
| Client/device certificates | Possible | Common fit |
| Internal organizational trust | Less controlled | Strong fit |
| CA hierarchy control | Limited | High |

#### 2.2.2.20 Certificate Request / CSR

##### 2.2.2.20.1 CSR
- Certificate Signing Request.

##### 2.2.2.20.2 Contains
- public key,
- requested identity information,
- requested extensions,
- signature proving possession of private key.

##### 2.2.2.20.3 CA
- CA validates request according to policy, then signs/returns certificate.

##### 2.2.2.20.4 Exam Depth
- Understand CSR role.
- Detailed OpenSSL commands belong more naturally to 2.2.5.

#### 2.2.2.21 Certificate Issuance

##### 2.2.2.21.1 Steps
1. Generate or reference key pair.
2. Create request/identity.
3. CA validates request/policy.
4. CA signs certificate.
5. Certificate returned/deployed.

##### 2.2.2.21.2 Managed AWS
- ACM abstracts many of these steps for supported integrations.

#### 2.2.2.22 Certificate Expiration

##### 2.2.2.22.1 Validity
- Certificates have:
  - `Not Before`
  - `Not After`

##### 2.2.2.22.2 Expired Certificate
- Should no longer be trusted.

##### 2.2.2.22.3 Operational Risk
- Expired TLS certificate can cause application outage.

##### 2.2.2.22.4 Management Requirement
- Certificate renewal must occur before expiration.

#### 2.2.2.23 ACM Managed Renewal

##### 2.2.2.23.1 Public Certificates
- ACM attempts automatic renewal for eligible ACM-issued certificates.

##### 2.2.2.23.2 Conditions
- Certificate must remain in use with supported ACM-integrated services.
- Domain validation must still succeed.

##### 2.2.2.23.3 Developer Mindset
- Prefer managed renewal instead of manually replacing certificates when AWS supports it.

#### 2.2.2.24 Private Certificate Renewal

##### 2.2.2.24.1 ACM-Managed Private Certificates
- ACM can manage renewal for supported private certificates issued through AWS Private CA.

##### 2.2.2.24.2 Directly Issued Certificates
- Certificates issued directly from AWS Private CA can require application/workflow responsibility for renewal and deployment.

##### 2.2.2.24.3 Exam Insight
- **AWS manages the CA infrastructure, but not every certificate lifecycle scenario becomes fully automatic.**

#### 2.2.2.25 Certificate Revocation

##### 2.2.2.25.1 Why
- Certificate may need to become invalid before its expiration.

Examples:
- private key compromise,
- identity no longer valid,
- device/service decommissioned.

##### 2.2.2.25.2 Mechanisms
- Certificate Revocation List (CRL).
- Online Certificate Status Protocol (OCSP), depending on PKI/service support.

##### 2.2.2.25.3 AWS Private CA
- Supports revocation configurations for private certificates.

#### 2.2.2.26 CRL

##### 2.2.2.26.1 Meaning
- List of revoked certificate serial numbers published by CA.

##### 2.2.2.26.2 Client
- Client can check CRL to determine whether certificate was revoked.

##### 2.2.2.26.3 Trade-Off
- CRLs need:
  - publication,
  - distribution,
  - freshness.

#### 2.2.2.27 OCSP

##### 2.2.2.27.1 Meaning
- Online protocol for querying certificate revocation status.

##### 2.2.2.27.2 Benefit
- More direct/fresh status check than downloading full revocation list.

##### 2.2.2.27.3 AWS Private CA
- Current AWS Private CA supports managed OCSP capabilities in supported configurations.

#### 2.2.2.28 Certificate Storage

##### 2.2.2.28.1 Certificate
- Public certificate is not secret.

##### 2.2.2.28.2 Private Key
- Must remain confidential.

##### 2.2.2.28.3 ACM
- For ACM-issued certificates used with integrated AWS services, private key is managed securely by AWS and is generally not exportable for standard public ACM certificates.

##### 2.2.2.28.4 Imported Certificate
- Customer supplies certificate and private key to ACM.
- Customer remains responsible for original private-key handling and certificate renewal workflow.

#### 2.2.2.29 ACM Certificate Import

##### 2.2.2.29.1 Use
- Import externally issued certificate into ACM for use by supported AWS services.

##### 2.2.2.29.2 Required Material
- certificate,
- private key,
- certificate chain.

##### 2.2.2.29.3 Important
- ACM does not automatically renew most imported certificates.
- You must obtain and re-import replacement certificate before expiration.

#### 2.2.2.30 Managed Certificate vs Imported Certificate

##### 2.2.2.30.1 ACM-Issued
- AWS handles supported renewal lifecycle.
- Private key managed by ACM.

##### 2.2.2.30.2 Imported
- You bring certificate/private key.
- Renewal/replacement is generally your responsibility.

##### 2.2.2.30.3 Exam Decision
- If supported AWS service and public/private ACM issuance fits:
  - prefer ACM-managed certificate lifecycle.
- Import only when external CA/certificate requirement demands it.

#### 2.2.2.31 CloudFront Certificate Region

##### 2.2.2.31.1 Important AWS Detail
- ACM certificate used with CloudFront must be in **US East (N. Virginia), `us-east-1`**.

##### 2.2.2.31.2 Why It Matters
- One of the most common AWS certificate exam traps.

##### 2.2.2.31.3 API Gateway / ELB
- Certificates normally need to exist in the Region appropriate to the regional service configuration.

#### 2.2.2.32 Elastic Load Balancing

##### 2.2.2.32.1 HTTPS/TLS Listener
- Load balancer presents certificate to clients.

##### 2.2.2.32.2 ACM Integration
- Certificate can be selected from ACM.

##### 2.2.2.32.3 Rotation
- Managed certificate renewal can be deployed without application code changes.

#### 2.2.2.33 API Gateway Custom Domains

##### 2.2.2.33.1 Custom Domain
- Uses TLS certificate for custom API hostname.

##### 2.2.2.33.2 Certificate
- ACM certificate associated with API Gateway custom domain.

##### 2.2.2.33.3 Regional vs Edge
- Certificate Region requirements depend on endpoint type.
- Edge-optimized APIs historically use CloudFront-backed certificate requirements in `us-east-1`.

#### 2.2.2.34 CloudFront

##### 2.2.2.34.1 Viewer Certificate
- CloudFront distribution uses certificate for viewer HTTPS connections.

##### 2.2.2.34.2 Custom Domain
- Certificate SAN/CN must cover the alternate domain name.

##### 2.2.2.34.3 Region
- ACM certificate must be in `us-east-1`.

#### 2.2.2.35 Internal TLS

##### 2.2.2.35.1 Requirement
- Internal services should establish trusted encrypted communication.

##### 2.2.2.35.2 Private PKI Pattern

`Private CA`
→ issue internal service certificate
→ service presents certificate
→ internal client trusts private CA
→ TLS established

##### 2.2.2.35.3 Benefit
- Internal names do not need publicly trusted certificates.

#### 2.2.2.36 Mutual TLS — mTLS

##### 2.2.2.36.1 Normal TLS
- Client authenticates server certificate.

##### 2.2.2.36.2 mTLS
- Both sides present/validate certificates.

`client certificate`
↔
`server certificate`

##### 2.2.2.36.3 Use
- Strong service/client identity.
- Private service-to-service communication.
- Device/client authentication.

##### 2.2.2.36.4 AWS Context
- API Gateway supports mTLS for custom domains.
- Private CA can issue client certificates in suitable architectures.

#### 2.2.2.37 API Gateway mTLS

##### 2.2.2.37.1 Client Certificate
- Client presents certificate.

##### 2.2.2.37.2 Truststore
- API Gateway validates client certificate against configured truststore.

##### 2.2.2.37.3 Truststore Storage
- Truststore is commonly stored in Amazon S3 according to API Gateway mTLS configuration.

##### 2.2.2.37.4 Distinction
- mTLS authenticates client certificate.
- Application authorization may still need:
  - IAM,
  - JWT,
  - custom logic,
  depending on architecture.

#### 2.2.2.38 Certificate Truststore

##### 2.2.2.38.1 Meaning
- Set of CA certificates trusted by a client/server.

##### 2.2.2.38.2 Public PKI
- Operating systems/browsers contain public root CA truststores.

##### 2.2.2.38.3 Private PKI
- Organization must distribute/install private CA trust chain to clients that should trust it.

#### 2.2.2.39 Keystore

##### 2.2.2.39.1 Concept
- Stores private key and associated certificate chain for an application/server.

##### 2.2.2.39.2 Distinction
- Truststore:
  - who do I trust?
- Keystore:
  - what identity/private key do I present?

##### 2.2.2.39.3 Developer Context
- Particularly relevant for Java/TLS applications.

#### 2.2.2.40 Certificate Rotation vs Key Rotation

##### 2.2.2.40.1 Certificate Renewal/Rotation
- Replaces expiring/revoked certificate and possibly its key pair.

##### 2.2.2.40.2 KMS Key Rotation
- Rotates cryptographic backing material for a KMS key.

##### 2.2.2.40.3 Distinction
- These are separate lifecycle concepts.
- KMS key rotation belongs to 2.2.7.

#### 2.2.2.41 Certificate Pinning

##### 2.2.2.41.1 Concept
- Client trusts a specific certificate/public key rather than general CA trust.

##### 2.2.2.41.2 Risk
- Certificate/key rotation becomes operationally harder.

##### 2.2.2.41.3 Exam Depth
- Recognize concept only.
- Not a primary AWS DVA certificate-management mechanism.

#### 2.2.2.42 Certificate Monitoring

##### 2.2.2.42.1 Risk
- Expired certificate causes outages.

##### 2.2.2.42.2 Monitor
- Expiration date.
- Renewal status.
- certificate deployment.
- validation state.

##### 2.2.2.42.3 ACM
- Provides certificate status information and managed renewal workflows.

#### 2.2.2.43 Private CA Security

##### 2.2.2.43.1 CA Permissions
- Restrict who can:
  - issue certificates,
  - revoke certificates,
  - modify CA configuration.

##### 2.2.2.43.2 IAM
- AWS Private CA APIs use IAM permissions.

##### 2.2.2.43.3 Principle
- CA is a high-value trust authority.
- Access must be tightly controlled.

#### 2.2.2.44 CA Lifecycle

##### 2.2.2.44.1 CA Creation
- Create/configure root or subordinate CA.

##### 2.2.2.44.2 Activation
- CA certificate must establish its place in hierarchy.

##### 2.2.2.44.3 Operation
- Issue/revoke certificates.

##### 2.2.2.44.4 Rotation/Replacement
- CA itself can eventually require replacement as certificate/key lifetime ends.

##### 2.2.2.44.5 Destruction
- Deleting a CA affects ability to issue/manage certificates and trust chain.
- CA lifecycle must be planned carefully.

#### 2.2.2.45 Development vs Production PKI

##### 2.2.2.45.1 Development
- May use:
  - self-signed certificates,
  - local/private development CA,
  - short-lived development certificates.

##### 2.2.2.45.2 Production
- Use managed trusted CA/certificate lifecycle.
- Avoid ad-hoc self-signed certificates for public production endpoints.

##### 2.2.2.45.3 Connection
- Generating development certificates is explicitly Skill 2.2.5.

#### 2.2.2.46 Self-Signed Certificate

##### 2.2.2.46.1 Definition
- Certificate signed by its own private key rather than a trusted external CA.

##### 2.2.2.46.2 Use
- Local development/testing.
- Root CA certificate itself is self-signed by design.

##### 2.2.2.46.3 Problem
- Ordinary clients do not trust arbitrary self-signed application certificates automatically.

##### 2.2.2.46.4 Exam Rule
- Public production website → public trusted certificate, not random self-signed certificate.

#### 2.2.2.47 Certificate Decision Tree

##### 2.2.2.47.1 Public Internet Endpoint
- Need browser/public trust.
- → ACM public certificate.

##### 2.2.2.47.2 Internal Service
- Need private organizational trust.
- → AWS Private CA/private certificate.

##### 2.2.2.47.3 Existing External Certificate
- → import into ACM if supported/useful.

##### 2.2.2.47.4 CloudFront Custom Domain
- → ACM certificate in `us-east-1`.

##### 2.2.2.47.5 Internal Client Authentication
- → private CA + client certificate / mTLS where suitable.

##### 2.2.2.47.6 Local Development
- → self-signed/private development certificate may be suitable.

#### 2.2.2.48 Common Exam Traps

##### 2.2.2.48.1 "Certificate Contains Private Key"
- False.
- Certificate contains public key; private key is separate.

##### 2.2.2.48.2 "Public CA and Private CA Are Interchangeable"
- False.
- Trust distribution differs.

##### 2.2.2.48.3 "Private CA Certificate Is Automatically Trusted by Browsers"
- False.

##### 2.2.2.48.4 "ACM Certificate Is Always Exportable"
- False.
- Standard ACM-managed public certificate private keys are not generally exportable.

##### 2.2.2.48.5 "Imported ACM Certificates Auto-Renew"
- Generally false.
- Customer must manage renewal/re-import.

##### 2.2.2.48.6 "CloudFront Can Use ACM Certificate From Any Region"
- False.
- ACM certificate must be in `us-east-1`.

##### 2.2.2.48.7 "Wildcard Covers Root Domain"
- False.
- `*.example.com` does not automatically cover `example.com`.

##### 2.2.2.48.8 "Certificate Expiration Is Only Security Issue"
- False.
- It is also an availability risk.

##### 2.2.2.48.9 "mTLS Removes Need for Authorization"
- False.
- mTLS authenticates identity; authorization can still be required.

##### 2.2.2.48.10 "Self-Signed Certificate Is Publicly Trusted"
- False.

##### 2.2.2.48.11 "Private CA Means No Lifecycle Management"
- False.
- Certificates and CA hierarchy still require issuance, renewal, revocation, and access control.

#### 2.2.2.50 Task 2.2 Big Picture

`Data in transit`
→ TLS
→ certificate
→ certificate chain
→ trusted CA
→ certificate lifecycle

The certificate-management hierarchy is:

`ROOT CA`
→ `SUBORDINATE / INTERMEDIATE CA`
→ `LEAF CERTIFICATE`
→ deployed to endpoint/client
→ trusted by peer

AWS implementation choices:

`Public trust`
→ ACM public certificates

`Private organizational trust`
→ AWS Private CA

`Existing external certificate`
→ ACM import

#### 2.2.2.52 Exam-Level Knowledge Frame

Know these cold:

**Certificate**
→ public key + identity + issuer signature + validity.

**Private key**
→ secret, separate from certificate.

**Public CA**
→ publicly trusted internet identity.

**Private CA**
→ internal trust domain.

**ACM**
→ managed certificate provisioning/deployment/renewal for supported AWS services.

**AWS Private CA**
→ managed private PKI/CA hierarchy.

**Certificate chain**
→ root → intermediate → leaf.

**DNS validation**
→ good fit for automated ACM renewal.

**Imported certificate**
→ renewal is generally your responsibility.

**CloudFront ACM certificate**
→ `us-east-1`.

**mTLS**
→ both client and server certificate authentication.

Final principle:

**Certificate management is the lifecycle of establishing and maintaining cryptographic identity and trust: issue, deploy, validate, renew, revoke, and replace certificates without breaking the application's encrypted communication.**
