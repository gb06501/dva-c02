### 2.2.5 Generate certificates and SSH keys for development purposes

#### 2.2.5.1 Exam and Task Context

##### 2.2.5.1.1 Domain and Task
- Domain 2 is **Security**.
- Task 2.2 is **Implement encryption by using AWS services**.
- Skill 2.2.5 is **Generate certificates and SSH keys for development purposes**.
- Earlier skills established:
  - 2.2.1 → encryption at rest vs in transit.
  - 2.2.2 → certificate management and PKI.
  - 2.2.3 → client-side vs server-side encryption.
  - 2.2.4 → encryption/decryption keys and KMS.
- 2.2.5 narrows the focus to **developer-created cryptographic identities and credentials used for development/test access and TLS**.

##### 2.2.5.1.2 Core Question
- **When development requires a certificate or SSH key pair, what must be generated, where should private material remain, and how is the public identity distributed or trusted?**

#### 2.2.5.2 Core Mental Model

Both certificates and SSH authentication are based on asymmetric key pairs:

`PRIVATE KEY`
→ secret
→ proves identity / performs private-key operation

`PUBLIC KEY`
→ distributable
→ allows peers to verify or encrypt as appropriate

But their trust models differ:

`TLS certificate`
→ public key + identity
→ signed by CA
→ PKI trust

`SSH key`
→ public key explicitly installed/authorized
→ private key proves possession
→ SSH trust

#### 2.2.5.3 Key Pair Fundamentals

##### 2.2.5.3.1 Private Key
- Must remain secret.
- Should remain with the entity that owns the identity.

##### 2.2.5.3.2 Public Key
- Can be distributed.
- Does not need secrecy.

##### 2.2.5.3.3 Core Security Rule
**Never distribute a private key merely because the public key must be shared.**

#### 2.2.5.4 Certificates vs Raw Public Keys

##### 2.2.5.4.1 Raw Public Key
- Cryptographic public key without a CA identity assertion.

##### 2.2.5.4.2 Certificate
- Binds a public key to identity information.
- Signed by a CA or self-signed.

##### 2.2.5.4.3 SSH
- Often uses explicitly authorized public keys rather than X.509 PKI certificates for normal EC2 login patterns.

#### 2.2.5.5 Development Certificates

##### 2.2.5.5.1 Typical Uses
- Local HTTPS.
- Development API.
- Test service-to-service TLS.
- Local certificate validation.
- mTLS development.
- Testing certificate-dependent application behavior.

##### 2.2.5.5.2 Requirement
- Development certificate does not automatically need public trust.

#### 2.2.5.6 Self-Signed Certificate

##### 2.2.5.6.1 Definition
- Certificate signed by the same private key corresponding to its public key.

##### 2.2.5.6.2 Fit
Useful for:
- local development,
- isolated testing,
- controlled environments.

##### 2.2.5.6.3 Limitation
- Browsers/clients do not automatically trust arbitrary self-signed certificates.

##### 2.2.5.6.4 Production
- Do not use an ad-hoc self-signed application certificate when public CA trust is required.

#### 2.2.5.7 Development Private CA

##### 2.2.5.7.1 Alternative
Instead of separately trusting every self-signed leaf certificate:

`development root CA`
→ signs development certificates
→ developers trust development CA

##### 2.2.5.7.2 Benefit
- More realistic PKI testing.
- Easier trust management across multiple development services.

##### 2.2.5.7.3 AWS Context
- AWS Private CA can provide managed private PKI where an AWS-managed private CA is justified.
- For purely local development, a local CA may be simpler.

#### 2.2.5.8 Certificate Generation Flow

##### 2.2.5.8.1 Generic Flow

`generate private key`
→ derive public key
→ create CSR
→ CA signs CSR
→ certificate issued

##### 2.2.5.8.2 Self-Signed

`generate private key`
→ create certificate
→ sign certificate with same private key

##### 2.2.5.8.3 AWS-Managed

`request certificate`
→ ACM / AWS Private CA workflow
→ certificate issued/managed

#### 2.2.5.9 Certificate Signing Request — CSR

##### 2.2.5.9.1 Contains
- public key,
- requested subject information,
- requested SANs/extensions,
- signature proving possession of private key.

##### 2.2.5.9.2 Does Not Contain
- private key.

##### 2.2.5.9.3 Flow

`developer generates key pair`
→ `CSR`
→ `CA`
→ signed certificate

#### 2.2.5.10 Subject Alternative Name — SAN

##### 2.2.5.10.1 Importance
- Modern TLS clients validate hostname against SAN.

##### 2.2.5.10.2 Development Example
Certificate for:
- `localhost`
- `api.dev.example.com`

must contain appropriate SAN entries.

##### 2.2.5.10.3 Exam/Developer Trap
- Creating a certificate with an identity that does not match the hostname causes TLS validation failure.

#### 2.2.5.11 OpenSSL

##### 2.2.5.11.1 Role
- Common development tool for:
  - generating keys,
  - creating CSRs,
  - creating self-signed certificates,
  - inspecting certificates.

##### 2.2.5.11.2 Conceptual Example

`openssl`
→ generate private key
→ create CSR/certificate
→ inspect certificate

##### 2.2.5.11.3 Exam Scope
- Understand what the tool generates and why.
- Memorizing every OpenSSL CLI flag is not the goal of DVA-C02.

#### 2.2.5.12 Certificate File Concepts

Common formats/extensions encountered by developers:

- `.pem`
- `.crt` / `.cer`
- `.key`
- `.csr`
- `.p12` / `.pfx`

##### 2.2.5.12.1 PEM
- Text/Base64-armored representation commonly used for certificates and keys.

##### 2.2.5.12.2 PKCS#12
- Binary container that can bundle:
  - certificate,
  - private key,
  - certificate chain.

##### 2.2.5.12.3 Important
- File extension alone does not guarantee content.
- A PEM file may contain a certificate, public key, private key, or chain.

#### 2.2.5.13 Protect Development Private Keys

##### 2.2.5.13.1 Never Commit
Do not commit private keys to:
- Git,
- application source,
- container image,
- public artifact.

##### 2.2.5.13.2 Filesystem
- Restrict file permissions.

##### 2.2.5.13.3 Encryption
- Protect private-key files with passphrases where workflow supports it.

##### 2.2.5.13.4 CI/CD
- Use managed secret/credential mechanisms rather than repository files.

#### 2.2.5.14 AWS Certificate Manager — Development Context

##### 2.2.5.14.1 ACM Public Certificates
- Useful for development/test environments with real DNS names and supported AWS integrations.

##### 2.2.5.14.2 Managed Benefit
- AWS handles eligible certificate renewal and deployment lifecycle.

##### 2.2.5.14.3 Limitation
- ACM-managed certificates are designed for supported AWS service integrations rather than arbitrary local developer certificate files.

#### 2.2.5.15 AWS Private CA — Development Context

##### 2.2.5.15.1 Use
- Managed private certificates for internal development/test infrastructure.

##### 2.2.5.15.2 Benefit
- Development can use a production-like private PKI model.

##### 2.2.5.15.3 Trade-Off
- AWS Private CA is a managed paid PKI service.
- It may be excessive for simple local development.

#### 2.2.5.16 SSH

##### 2.2.5.16.1 Purpose
- Secure Shell provides encrypted remote access and secure transport capabilities.

##### 2.2.5.16.2 Common AWS Developer Use
- Authenticate to EC2 Linux instances.

##### 2.2.5.16.3 Authentication
- Common EC2 pattern uses asymmetric SSH key pair authentication rather than password authentication.

#### 2.2.5.17 SSH Key Pair

##### 2.2.5.17.1 Private Key
- Kept by developer/client.

##### 2.2.5.17.2 Public Key
- Installed/associated with remote system.

##### 2.2.5.17.3 Authentication Flow

`client proves possession of private key`
→ server verifies against authorized public key
→ login accepted

##### 2.2.5.17.4 Important
- Private key is not sent to server during normal SSH authentication.

#### 2.2.5.18 EC2 Key Pairs

##### 2.2.5.18.1 Purpose
- EC2 key pairs support public-key authentication to instances.

##### 2.2.5.18.2 AWS Stores
- Public key material.

##### 2.2.5.18.3 Developer Holds
- Private key.

##### 2.2.5.18.4 Critical
- AWS does not retain a recoverable copy of the private key for a normally generated EC2 key pair.

#### 2.2.5.19 Creating EC2 Key Pair in AWS

##### 2.2.5.19.1 Flow

`EC2 CreateKeyPair`
→ AWS creates key pair
→ stores public key
→ returns private key material once

##### 2.2.5.19.2 Responsibility
- Developer must securely store private key when it is returned.

##### 2.2.5.19.3 Lost Private Key
- Cannot simply download the same private key again from EC2.

#### 2.2.5.20 Importing an EC2 Public Key

##### 2.2.5.20.1 Alternative

`developer generates SSH key locally`
→ keeps private key
→ imports public key to EC2

##### 2.2.5.20.2 Benefit
- Private key never needs to be generated by or transmitted from AWS.

##### 2.2.5.20.3 Exam Insight
- AWS only needs the public key for instance login authorization.

#### 2.2.5.21 `ssh-keygen`

##### 2.2.5.21.1 Purpose
- Standard tool for generating SSH key pairs.

##### 2.2.5.21.2 Output
Typically:
- private key file,
- public key file (`.pub`).

##### 2.2.5.21.3 Conceptual Example

`ssh-keygen`
→ private key
→ public key

##### 2.2.5.21.4 Security
- Protect private key.
- Public `.pub` key can be copied/imported.

#### 2.2.5.22 RSA and ED25519 — Context

##### 2.2.5.22.1 SSH
- Modern SSH supports multiple key algorithms.

##### 2.2.5.22.2 EC2
- EC2 key-pair algorithm support depends on platform/use case.
- RSA remains broadly supported.
- ED25519 is supported for appropriate Linux instance scenarios.

##### 2.2.5.22.3 Exam Scope
- Understand that SSH key type matters for compatibility.
- Do not over-focus on cryptographic algorithm internals.

#### 2.2.5.23 `.pem` and `.ppk`

##### 2.2.5.23.1 PEM
- Common private-key format used by OpenSSH/AWS workflows.

##### 2.2.5.23.2 PPK
- PuTTY private-key format.

##### 2.2.5.23.3 Windows/PuTTY Context
- Key may need appropriate format/conversion depending on SSH client.

##### 2.2.5.23.4 Exam Depth
- Recognize format distinction; exact conversion commands are secondary.

#### 2.2.5.24 SSH Private-Key Permissions

##### 2.2.5.24.1 OpenSSH
- Rejects private-key files that are too broadly accessible.

##### 2.2.5.24.2 Common Pattern
- Restrict private key to owner-only access.

##### 2.2.5.24.3 Security Principle
- Private key should not be readable by other users.

#### 2.2.5.25 SSH Agent

##### 2.2.5.25.1 Purpose
- Holds decrypted private-key credentials in memory for SSH client operations.

##### 2.2.5.25.2 Benefit
- Avoid repeatedly entering passphrase.

##### 2.2.5.25.3 Risk
- Agent access is itself security-sensitive.

##### 2.2.5.25.4 Exam Scope
- Developer context only, not core AWS service knowledge.

#### 2.2.5.26 SSH Key Passphrase

##### 2.2.5.26.1 Purpose
- Encrypt/protect private key file.

##### 2.2.5.26.2 Benefit
- Stolen key file alone may not immediately provide access.

##### 2.2.5.26.3 Trade-Off
- Automation requires secure method to unlock/use key.

#### 2.2.5.27 EC2 Instance Launch

##### 2.2.5.27.1 Linux
- Selected EC2 public key is placed into the instance's authorized-key configuration through image/cloud-init mechanisms.

##### 2.2.5.27.2 Login

`developer private key`
→ SSH
→ instance verifies against public key

##### 2.2.5.27.3 Important
- EC2 key pair is primarily an **initial access/bootstrap mechanism**, not a general AWS IAM credential.

#### 2.2.5.28 SSH Key Is Not AWS Access Key

##### 2.2.5.28.1 SSH Key
- Authenticates SSH/public-key protocol access.

##### 2.2.5.28.2 AWS Access Key
- Access key ID + secret access key authenticate AWS API requests.

##### 2.2.5.28.3 KMS Key
- Cryptographic key managed by KMS.

##### 2.2.5.28.4 Critical Exam Distinction
These three "keys" solve completely different problems.

#### 2.2.5.29 Key Vocabulary Map

`SSH KEY PAIR`
→ remote host authentication

`AWS ACCESS KEY`
→ AWS API authentication

`KMS KEY`
→ encryption/key management

`TLS PRIVATE KEY + CERTIFICATE`
→ TLS endpoint/client identity

`DATA KEY`
→ bulk payload encryption

Do not interchange them.

#### 2.2.5.30 EC2 Instance Connect

##### 2.2.5.30.1 Purpose
- Provides a mechanism to push a temporary SSH public key to supported EC2 instances for short-lived access.

##### 2.2.5.30.2 Benefit
- Reduces dependence on permanently installed shared SSH public keys.

##### 2.2.5.30.3 IAM
- Access can be controlled through IAM permissions.

##### 2.2.5.30.4 Developer Mindset
- Prefer short-lived, attributable access over long-lived shared credentials when supported.

#### 2.2.5.31 Systems Manager Session Manager

##### 2.2.5.31.1 Alternative to SSH Key Management
- Session Manager can provide shell access to managed EC2 instances without opening inbound SSH or managing SSH keys for that access path.

##### 2.2.5.31.2 Benefits
- IAM-based access control.
- No inbound port 22 requirement.
- Centralized session capabilities/auditing.

##### 2.2.5.31.3 Exam Decision
If scenario asks to:
- avoid SSH key distribution,
- avoid opening SSH port,
- use IAM-controlled instance access

→ consider **Systems Manager Session Manager**.

#### 2.2.5.32 SSH Network Access

##### 2.2.5.32.1 Authentication Is Not Reachability
- Correct SSH key does not make port 22 reachable.

##### 2.2.5.32.2 Network
- Security group/network path must allow connection where direct SSH is used.

##### 2.2.5.32.3 Distinction

`network access`
+
`SSH authentication`
→ successful SSH session

#### 2.2.5.33 SSH Host Key

##### 2.2.5.33.1 Different Key
- SSH server has host key identifying the server.

##### 2.2.5.33.2 Client Key
- Developer's SSH key authenticates client/user.

##### 2.2.5.33.3 Trust
- Client checks server host key, often stored in `known_hosts`.

##### 2.2.5.33.4 Exam Depth
- Recognize distinction; EC2 key pair questions normally focus on client authentication.

#### 2.2.5.34 TLS Certificate vs SSH Key

| Characteristic | TLS Certificate | SSH User Key |
| --- | --- | --- |
| Primary use | TLS identity/trust | SSH login authentication |
| Public identity | Certificate | Public key |
| Trust | CA chain / truststore | Authorized public key |
| Private key holder | Endpoint/client | SSH client/user |
| AWS example | ACM / Private CA | EC2 key pair |
| Typical protocol | HTTPS/TLS | SSH |

#### 2.2.5.35 Certificate Private Key vs SSH Private Key

##### 2.2.5.35.1 Similarity
- Both are secret asymmetric private keys.

##### 2.2.5.35.2 Difference
- Used by different protocols/trust systems.

##### 2.2.5.35.3 Rule
- Do not casually reuse one private key for unrelated protocol identities.

#### 2.2.5.36 Development Credential Lifecycle

A developer credential should have lifecycle:

`generate`
→ `store securely`
→ `distribute public component`
→ `use`
→ `rotate/replace`
→ `revoke/remove`
→ `destroy private material`

##### 2.2.5.36.1 Principle
- Development does not mean unmanaged.

#### 2.2.5.37 Team Development

##### 2.2.5.37.1 Bad Pattern
- One SSH private key shared by entire team.

##### 2.2.5.37.2 Problems
- No individual attribution.
- Difficult revocation.
- Key spreads across machines.
- One compromise affects everyone.

##### 2.2.5.37.3 Better
- Individual identities/keys.
- IAM-controlled temporary access where available.
- Session Manager for EC2 administration where appropriate.

#### 2.2.5.38 CI/CD

##### 2.2.5.38.1 Avoid
- Developer SSH private key embedded in pipeline.

##### 2.2.5.38.2 Prefer
- IAM roles/workload federation for AWS API access.
- Managed secrets only when a protocol truly requires a private credential.

##### 2.2.5.38.3 Connection
- AWS API access belongs to Task 2.1.
- Secrets management belongs to Task 2.3.

#### 2.2.5.39 Git and Private Keys

##### 2.2.5.39.1 Never Commit
- TLS private keys.
- SSH private keys.
- AWS secret access keys.

##### 2.2.5.39.2 If Committed
- Removing from latest Git commit is not sufficient.
- Assume credential may be compromised.
- Revoke/replace it.

##### 2.2.5.39.3 Principle
**Credential exposure → rotate/revoke, not merely delete the file.**

#### 2.2.5.40 Certificate Trust Failure Patterns

Common causes:
- expired certificate,
- hostname/SAN mismatch,
- untrusted CA,
- incomplete certificate chain,
- certificate not yet valid,
- revoked certificate,
- wrong truststore.

##### 2.2.5.40.1 Debugging
Inspect:
- subject/SAN,
- issuer,
- validity,
- chain,
- trust anchor.

#### 2.2.5.41 SSH Failure Patterns

Common causes:
- wrong private key,
- public key not installed,
- wrong OS username,
- private-key file permissions too open,
- port 22 blocked,
- instance unreachable,
- incompatible key format/algorithm,
- key removed/rotated.

##### 2.2.5.41.1 Debugging
Separate:
- network failure,
- host trust failure,
- user authentication failure.

#### 2.2.5.42 Certificate Decision Flow

##### 2.2.5.42.1 Local Development Only
- self-signed certificate or local development CA.

##### 2.2.5.42.2 Public AWS Development Endpoint
- ACM public certificate where supported.

##### 2.2.5.42.3 Internal AWS PKI
- AWS Private CA/private certificate.

##### 2.2.5.42.4 Need mTLS
- client certificate + server certificate + appropriate truststores.

##### 2.2.5.42.5 Need Production-Like PKI Testing
- development private CA hierarchy may fit.

#### 2.2.5.43 SSH Decision Flow

##### 2.2.5.43.1 Need Direct EC2 SSH
- generate/import EC2-compatible SSH public key.
- protect private key.
- configure network access.

##### 2.2.5.43.2 Need Short-Lived SSH Access
- consider EC2 Instance Connect.

##### 2.2.5.43.3 Want No SSH Keys / No Inbound SSH
- consider Systems Manager Session Manager.

##### 2.2.5.43.4 Team Access
- individual identity/access, not shared private key.

- False.

##### 2.2.5.44.7 "KMS Key Is SSH Key"
- False.

##### 2.2.5.44.8 "Self-Signed Certificate Is Automatically Browser Trusted"
- False.

##### 2.2.5.44.9 "Private CA Certificate Is Automatically Publicly Trusted"
- False.

#### 2.2.5.46 Task 2.2 Big Picture

The word **key** now splits into distinct branches:

`CRYPTOGRAPHIC KEYS`
│
├── `KMS KEY`
│   → protects encryption keys/data
│
├── `DATA KEY`
│   → encrypts bulk application data
│
├── `TLS PRIVATE KEY`
│   → proves certificate identity
│
├── `SSH PRIVATE KEY`
│   → proves SSH client identity
│
└── `AWS ACCESS KEY`
    → signs/authenticates AWS API requests
    → not an encryption key

This distinction is essential for DVA-C02.

#### 2.2.5.48 Exam-Level Knowledge Frame

Know these cold:

**Certificate**
→ identity + public key + issuer signature.

**CSR**
→ public key + requested identity + proof of private-key possession; no private key inside.

**Self-signed certificate**
→ useful for controlled development; not automatically publicly trusted.

**SSH key pair**
→ public key on server/AWS; private key with developer.

**EC2-generated key pair**
→ AWS returns private key once; protect it.

**Imported EC2 key**
→ generate locally; import only public key.

**`ssh-keygen`**
→ generates SSH key pair.

**OpenSSL**
→ common certificate/key/CSR development tool.

**EC2 Instance Connect**
→ short-lived SSH public-key access model.

**Session Manager**
→ can eliminate direct SSH key and inbound port-22 requirements.

**AWS access key**
→ AWS API credential, not SSH/encryption key.

The fastest exam discriminator:

**What protocol is the key for?**

`HTTPS/TLS`
→ certificate + TLS private key.

`SSH`
→ SSH key pair.

`AWS API`
→ IAM credentials/access keys or role credentials.

`Data encryption`
→ KMS/data key.

Final principle:

**Generate the credential type required by the protocol, keep its private component private, distribute only the public/trust component, and prefer managed or short-lived access mechanisms over shared long-lived development keys.**
