### 3.1.5 Configure environment-specific application settings

#### 3.1.5.1 Exam and Task Context

##### 3.1.5.1.1 Domain and Task
- **Domain 3:** Deployment.
- **Task 3.1:** Prepare application artifacts to be deployed to AWS.
- **Skill 3.1.5:** **Configure environment-specific application settings (for example, environment variables, configuration files).**

This completes Task 3.1.

Core question:

**How can the same tested application artifact behave correctly in development, test, staging, and production without changing application code?**

---

#### 3.1.5.2 Core Mental Model

```text
ONE APPLICATION ARTIFACT
        |
        +--> dev configuration
        |      → dev behavior
        |
        +--> test configuration
        |      → test behavior
        |
        '--> prod configuration
               → prod behavior
```

Central principle:

```text
separate configuration from code
```

Strong deployment model:

```text
BUILD ONCE
→ CONFIGURE PER ENVIRONMENT
→ DEPLOY SAME TESTED ARTIFACT
```

---

#### 3.1.5.3 What Is Environment-Specific Configuration?

Examples:

```text
DynamoDB table name
S3 bucket name
API endpoint
queue URL
topic ARN
database hostname
log level
feature flag
timeout threshold
application mode
```

These describe:
- deployment/runtime context.

They should normally not require:
- application source changes.

---

#### 3.1.5.4 Configuration vs Code

Weak:

```java
if (environment.equals("prod")) {
    table = "orders-prod";
} else {
    table = "orders-dev";
}
```

Better:

```text
TABLE_NAME
→ supplied externally
```

Application:

```text
read TABLE_NAME
→ use selected resource
```

Benefits:
- fewer environment branches in code,
- same artifact can be promoted,
- less artifact drift.

---

#### 3.1.5.5 Configuration vs Secret

Configuration:

```text
behavior / resource reference
```

Examples:
- table name,
- log level,
- feature flag.

Secret:

```text
sensitive credential/confidential material
```

Examples:
- database password,
- API key,
- authorization token.

Critical rule:

```text
environment-specific
≠ automatically safe to store as ordinary configuration
```

Use dedicated secret storage for:
- credentials/secrets.

---

#### 3.1.5.6 Lambda Environment Variables

Lambda environment variables are:
- key/value pairs in function configuration.

Example:

```text
TABLE_NAME=orders-prod
LOG_LEVEL=INFO
```

Application code:
- reads them from the runtime environment.

Use for:
- relatively small,
- deployment-time,
- non-secret settings.

---

#### 3.1.5.7 Lambda Environment Variables Are Version-Specific

AWS documents that environment variables are:
- part of Lambda function configuration.

When a Lambda version is published:
- environment-variable values are locked with that version.

Mental model:

```text
Lambda version
→ code
+
version-specific configuration
```

---

#### 3.1.5.8 Lambda Environment Variables Are Literal Strings

Lambda does not automatically expand values.

Example:

```text
BUCKET=${ENV}-bucket
```

does not automatically become:

```text
BUCKET=prod-bucket
```

unless:
- application code,
- deployment tooling

performs expansion.

---

#### 3.1.5.9 Lambda Environment Variable Size and Fit

Environment variables have:
- a total size limit per function.

Exam implication:

```text
small key/value deployment configuration
→ environment variable

large/dynamic configuration document
→ use a more appropriate configuration service
```

Possible alternatives:
- AppConfig,
- Parameter Store,
- Amazon S3.

---

#### 3.1.5.10 Lambda Environment Variable Encryption

Lambda encrypts environment variables at rest.

Default:
- AWS managed KMS key.

Optional:
- customer managed KMS key.

But:

```text
encrypted environment-variable storage
≠ best place for credentials
```

AWS recommends:
- Secrets Manager

for sensitive credentials.

---

#### 3.1.5.11 Environment Variables Through IaC

Environment variables can be defined through:
- AWS SAM,
- CloudFormation,
- deployment automation.

Example:

```yaml
Environment:
  Variables:
    TABLE_NAME: orders-prod
    LOG_LEVEL: INFO
```

Benefit:
- repeatable,
- reviewable,
- version-controlled deployment configuration.

---

#### 3.1.5.12 CloudFormation and SAM Parameters

CloudFormation parameters let one template accept:
- environment-specific values.

Concept:

```text
same template
+
dev parameters
→ dev stack

same template
+
prod parameters
→ prod stack
```

SAM:
- uses CloudFormation parameter mechanisms.

Parameter overrides can be supplied by:
- deployment automation.

Use when:

```text
same infrastructure definition
+
different deployment values
```

---

#### 3.1.5.13 Do Not Hard-Code Resource Identifiers

Avoid embedding environment-specific identifiers directly in application code.

Example:

```text
arn:aws:sns:eu-west-1:123456789012:orders-prod
```

Better:

```text
TOPIC_ARN
→ deployment configuration
```

This supports:
- multiple accounts,
- multiple Regions,
- multiple environments

without rebuilding business logic.

---

#### 3.1.5.14 Systems Manager Parameter Store

Parameter Store provides:
- centralized,
- hierarchical

configuration storage.

Example hierarchy:

```text
/orders/dev/table-name
/orders/test/table-name
/orders/prod/table-name
```

Useful for:
- centrally managed application settings,
- hierarchical naming,
- runtime retrieval.

---

#### 3.1.5.15 Parameter Store Types

Parameter Store supports types including:

```text
String
StringList
SecureString
```

`SecureString`:
- uses KMS encryption.

But for:
- credentials,
- rotation,
- dedicated secret lifecycle,

Secrets Manager is generally the stronger fit.

---

#### 3.1.5.16 Parameters and Secrets Lambda Extension

Lambda can use the AWS Parameters and Secrets Lambda Extension to:
- retrieve,
- locally cache

values from:
- Parameter Store,
- Secrets Manager.

Benefit:

```text
avoid remote retrieval on every invocation
```

This can reduce:
- latency,
- API calls,
- cost.

---

#### 3.1.5.17 Static vs Dynamic Configuration

##### Static / Deployment-Time

Changes:
- infrequently,
- typically with a deployment/configuration update.

Examples:
- table name,
- queue URL,
- environment label.

Possible mechanisms:
- environment variables,
- CloudFormation/SAM parameters.

##### Dynamic / Runtime

Needs to change:
- independently of application deployment.

Examples:
- feature flag,
- logging level,
- throttling rule,
- operational limit.

Strong fit:
- AWS AppConfig.

---

#### 3.1.5.18 AWS AppConfig

AWS AppConfig manages:
- application configuration,
- feature flags,
- validation,
- controlled deployment,
- runtime retrieval.

Typical examples:
- feature flags,
- allow/block lists,
- log levels,
- service limits,
- throttling rules.

Use AppConfig when configuration itself needs:
- a deployment lifecycle.

---

#### 3.1.5.19 Why AppConfig Exists

Environment variables work well for:
- simple deployment configuration.

AppConfig is stronger when configuration needs:
- frequent changes,
- validation,
- gradual rollout,
- monitoring,
- rollback,
- no code redeployment.

Decision:

```text
simple static setting?
→ environment variable / deployment parameter

dynamic behavior configuration?
→ AppConfig
```

---

#### 3.1.5.20 AppConfig Structure

Core hierarchy:

```text
APPLICATION
   |
   v
ENVIRONMENT
   |
   v
CONFIGURATION PROFILE
   |
   v
CONFIGURATION VERSION
   |
   v
DEPLOYMENT STRATEGY
```

##### Application
- organizational namespace for related configuration.

##### Environment
- logical deployment target/group.

Examples:
- Beta,
- Production.

##### Configuration Profile
Defines:
- configuration type/source,
- optional validators.

Types include:
- feature flags,
- freeform configuration.

---

#### 3.1.5.21 AppConfig Feature Flags

Feature flag:

```text
newCheckout = true/false
```

Allows:
- behavior changes without code deployment,
- controlled enablement,
- experimentation,
- environment-specific rollout.

Example:

```text
Dev
→ enabled

Prod
→ disabled initially
```

Same:
- application artifact.

---

#### 3.1.5.22 AppConfig Freeform Configuration

Freeform configuration can represent:
- JSON,
- YAML,
- text,
- other supported application configuration.

Use when:
- application behavior depends on richer structured settings,
- large numbers of environment variables would be inappropriate.

---

#### 3.1.5.23 AppConfig Validators

AppConfig can validate configuration before deployment.

Supported mechanisms include:
- JSON Schema,
- AWS Lambda validators.

Example:

```text
maxConnections = -5
```

Validator:

```text
reject before rollout
```

Purpose:
- prevent invalid configuration from reaching applications.

---

#### 3.1.5.24 AppConfig Deployment Strategy

Deployment strategy controls:
- rollout duration,
- growth behavior,
- bake time.

Mental model:

```text
configuration v8
→ gradual rollout
→ observe
→ complete
```

This is:
- deployment behavior applied to configuration.

---

#### 3.1.5.25 AppConfig Rollback

AppConfig environments can monitor:
- CloudWatch alarms.

If an alarm enters the configured state during deployment:

```text
bad configuration rollout
→ alarm
→ AppConfig rollback
```

Critical distinction:

```text
code rollback
≠ configuration rollback
```

---

#### 3.1.5.26 Configuration Changes Without Code Deployment

Defining advantage:

```text
application artifact v42 remains deployed
+
AppConfig v7 → v8
→ behavior changes
```

No application rebuild is required.

This enables:
- independent configuration lifecycle.

---

#### 3.1.5.27 AppConfig Configuration Sources

Supported sources can include:
- AppConfig hosted configuration,
- Systems Manager Parameter Store,
- Secrets Manager,
- Amazon S3.

Exam principle:

```text
AppConfig
→ adds controlled validation/deployment/retrieval around configuration
```

rather than merely:
- storing one key/value.

---

#### 3.1.5.28 AppConfig Runtime Retrieval

Applications can retrieve AppConfig data using:
- AppConfig Agent,
- AppConfigData API,
- Lambda/runtime integration where appropriate.

Agents/extensions can:
- cache configuration locally.

Benefit:
- lower latency,
- fewer remote API calls.

---

#### 3.1.5.29 AWS Secrets Manager

Secrets Manager is designed for:
- credentials,
- API keys,
- passwords,
- confidential values.

Use when:

```text
value is secret
→ Secrets Manager
```

AWS specifically recommends:
- Secrets Manager rather than Lambda environment variables

for sensitive credentials.

---

#### 3.1.5.30 Secret Rotation

Secrets Manager supports:
- secret rotation workflows.

Benefit:

```text
credential changes
→ application retrieves current secret
→ no artifact rebuild
```

This separates:
- code lifecycle

from:
- credential lifecycle.

---

#### 3.1.5.31 Store Secret Reference, Not Secret

Useful pattern:

```text
DB_SECRET_ARN=<secret ARN>
```

Environment variable contains:
- which secret to retrieve.

Secrets Manager contains:
- the actual secret.

This keeps:
- deployment-specific reference

separate from:
- sensitive value.

---

#### 3.1.5.32 Configuration by Account and Region

Common environment model:

```text
Dev account
Test account
Prod account
```

Resources differ naturally between accounts.

They can also differ by Region:

```text
eu-west-1 bucket
us-east-1 bucket
```

Therefore:
- resource identifiers should usually be injected/resolved per deployment.

Avoid hard-coding:
- account-specific,
- Region-specific

resource names when portability is required.

---

#### 3.1.5.33 Configuration Precedence

Applications can receive values from:
- packaged defaults,
- environment variables,
- Parameter Store,
- AppConfig,
- runtime arguments.

Define:
- deterministic precedence.

Example conceptual order:

```text
safe default
→ deployment override
→ dynamic configuration
```

Exact precedence:
- is application design,
- not a universal AWS rule.

---

#### 3.1.5.34 Defaults and Fail-Fast Validation

Safe defaults can be useful for:
- non-sensitive,
- environment-independent values.

Avoid dangerous defaults such as:

```text
missing TABLE_NAME
→ silently use production table
```

For required configuration:

```text
missing / invalid value
→ detect during initialization or deployment testing
```

Validate:
- existence,
- type,
- allowed range,
- URL/identifier format.

---

#### 3.1.5.35 Configuration Values and Types

Environment variables are:
- strings.

Application may need to parse:

```text
TIMEOUT="30"
→ integer
```

```text
FEATURE_ENABLED="true"
→ boolean
```

Invalid parsing:
- is configuration failure.

AppConfig validators can prevent:
- some classes of invalid configuration before rollout.

---

#### 3.1.5.36 Configuration Files

The exam guide explicitly mentions:
- configuration files.

They can be appropriate for:
- static non-secret settings,
- schemas,
- defaults,
- local application configuration.

Decision:

```text
changes by environment?
→ externalize or inject

needs dynamic runtime updates?
→ AppConfig / Parameter Store

secret?
→ Secrets Manager
```

---

#### 3.1.5.37 S3-Hosted Configuration

Amazon S3 can store:
- larger configuration objects/files.

Possible use:
- larger freeform configuration,
- configuration already managed as an S3 object.

AppConfig can also use:
- supported S3-backed configuration.

Use when:
- size/shape makes many environment variables inappropriate.

---

#### 3.1.5.38 Environment Parity

Goal:

```text
environments differ mainly in values
not unnecessarily in application code
```

Example:

```text
Dev:
TABLE_NAME=orders-dev

Prod:
TABLE_NAME=orders-prod
```

Same:
- handler,
- application logic,
- deployment package.

This reduces:
- environment drift.

---

#### 3.1.5.39 Build Once, Configure Per Environment

Strong model:

```text
commit abc123
→ build artifact v42 once

v42 + dev config
→ dev

v42 + test config
→ test

v42 + prod config
→ prod
```

Benefit:
- production can run the same bytes tested earlier.

Avoid unnecessary:

```text
build-dev.zip
build-test.zip
build-prod.zip
```

when code is identical and only configuration differs.

---

#### 3.1.5.40 Configuration Versioning

Deployment state can be modeled as:

```text
application artifact version
+
configuration version
+
infrastructure version
```

AppConfig explicitly supports:
- versioned configuration deployments.

This helps answer:
- which code?
- which configuration?
- which environment?

---

#### 3.1.5.41 Configuration Change Is Operationally Significant

Configuration can break production as strongly as code.

Therefore:
- validate it,
- deploy deliberately,
- monitor it,
- roll back when needed.

AppConfig formalizes:
- this controlled configuration lifecycle.

---

#### 3.1.5.42 IAM and KMS

Applications retrieving configuration need:
- appropriate IAM permissions.

Examples:

```text
Parameter Store
→ ssm:GetParameter / related actions

Secrets Manager
→ secretsmanager:GetSecretValue

AppConfig
→ permissions required by retrieval mechanism
```

If customer-managed KMS keys protect values:
- suitable KMS permissions may also be required.

Apply:
- least privilege.

Detailed IAM:
- Domain 2.

---

#### 3.1.5.43 Configuration Drift

Manual environment changes can cause:

```text
deployed environment
≠ intended declarative configuration
```

Prefer where practical:
- IaC,
- controlled configuration deployment,
- versioned configuration,
- repeatable parameter sets.

Goal:
- reproducible environments.

---

#### 3.1.5.44 Failure Pattern Summary

| Symptom / requirement | Correct direction |
|---|---|
| Dev function accesses production table | externalize resource identifier |
| Required environment variable missing | validate configuration during deployment/startup |
| Production uses test resource name | fix environment-specific deployment value |
| Database password differs by environment | Secrets Manager |
| Frequently changed operational rule requires redeployment | AppConfig |
| Need validate JSON before rollout | AppConfig validator |
| Need gradual configuration rollout | AppConfig deployment strategy |
| Bad configuration causes CloudWatch alarm | AppConfig rollback |
| Need hierarchical centralized settings | Parameter Store |
| Same template, different environment values | CloudFormation/SAM parameters |
| Need large dynamic configuration file | AppConfig freeform / suitable external source |
| Need secret without remote fetch every invocation | Parameters and Secrets Lambda Extension / caching |

#### 3.1.5.46 Common Exam Traps

##### "Environment-specific means hard-code `if prod`"
- Wrong.

##### "Environment variable is best for every setting"
- False.

##### "Encrypted Lambda environment variables are automatically best for passwords"
- False.
- AWS recommends Secrets Manager.

##### "Parameter Store and Secrets Manager are identical"
- False.

##### "AppConfig stores application code"
- False.

##### "AppConfig change requires application rebuild"
- False.

##### "Feature flag requires new application version"
- Not when dynamic configuration is externalized.

##### "Different environment requires different source branch"
- False.

##### "Different environment requires different application artifact"
- False.

##### "Configuration changes are harmless compared with code"
- False.

##### "Secret in source-controlled configuration file is acceptable if encrypted later"
- Wrong deployment practice.

#### 3.1.5.49 Exam-Level Knowledge Frame

Know these cold.

**Environment variable**  
→ small deployment/runtime key-value configuration.

**Lambda environment variable**  
→ version-specific function configuration; literal string value.

**CloudFormation/SAM parameter**  
→ deployment-time value supplied to reusable infrastructure/template.

**Parameter Store**  
→ centralized hierarchical parameters/configuration.

**Secrets Manager**  
→ credentials/secrets with dedicated lifecycle and rotation capabilities.

**AppConfig**  
→ dynamic application configuration and feature flags.

**AppConfig environment**  
→ logical configuration deployment target/group.

**Configuration profile**  
→ source/type/set of AppConfig configuration.

**Validator**  
→ rejects invalid configuration before rollout.

**Deployment strategy**  
→ controls configuration rollout.

**CloudWatch alarm + AppConfig**  
→ can trigger automatic rollback of problematic configuration.

**Same artifact**  
→ should normally support multiple environments through external configuration.

Fastest exam discriminator:

```text
table/bucket/queue name differs?
→ environment configuration

password/API key?
→ Secrets Manager

hierarchical centralized setting?
→ Parameter Store

feature flag / dynamic behavior?
→ AppConfig

need config validation + gradual rollout + rollback?
→ AppConfig

same template, different environment values?
→ CloudFormation/SAM parameters

large dynamic configuration?
→ AppConfig freeform / suitable external source

simple Lambda deployment setting?
→ environment variable
```

Final principle:

**Environment differences belong in configuration, not application code. Keep the deployable artifact stable, inject simple deployment settings externally, keep secrets in dedicated secret storage, and use AppConfig when configuration itself needs validation, controlled rollout, monitoring, and rollback independent of code deployment.**
