### 3.1.2 Organize files and a directory structure for application deployment

#### 3.1.2.1 Exam and Task Context

##### 3.1.2.1.1 Domain and Task
- **Domain 3:** Deployment.
- **Task 3.1:** Prepare application artifacts to be deployed to AWS.
- **Skill 3.1.2:** **Organize files and a directory structure for application deployment.**

Relationship to 3.1.1:

```text
3.1.1
→ what does the application need?

3.1.2
→ where must those files be placed so the runtime/build/deployment tool can use them?
```

Core question:

**How should source files, dependencies, generated output, infrastructure definitions, and runtime files be organized so the resulting AWS deployment artifact has the exact structure expected by its target?**

---

#### 3.1.2.2 Core Mental Model

```text
SOURCE PROJECT
    |
    v
separate source / tests / build / infrastructure
    |
    v
build / compile / bundle
    |
    v
generated deployment output
    |
    v
arrange according to target runtime contract
    |
    v
ZIP / JAR / image / other artifact
    |
    v
inspect + test exact artifact
    |
    v
deploy
```

Central principle:

```text
repository structure
≠ deployment structure
```

Correct files in the wrong location can still produce:
- a broken deployment.

---

#### 3.1.2.3 Source Structure vs Deployment Structure

##### Source Repository Structure

Optimized for:
- development,
- maintainability,
- testing,
- build definitions,
- infrastructure definitions.

Example:

```text
project/
├── src/
├── tests/
├── infrastructure/
├── template.yaml
├── package.json
└── README.md
```

##### Deployment Artifact Structure

Optimized for:
- the target runtime.

Example:

```text
function.zip
├── lambda_function.py
├── requests/
└── ...
```

The two structures:
- do not need to be identical.

---

#### 3.1.2.4 Build Process Bridges the Two

Typical flow:

```text
repository
→ dependency resolution
→ compile/bundle
→ staging/build directory
→ package
→ deployment artifact
```

Therefore:

```text
source tree
≠ automatically deployable artifact
```

Build systems can:
- transform directory layout,
- bundle modules,
- compile source,
- install dependencies,
- generate runtime files.

Validate:
- generated output,
not only:
- source structure.

---

#### 3.1.2.5 Lambda ZIP Structure

AWS Lambda ZIP packages have:
- runtime-specific layout expectations.

A ZIP can upload successfully but fail at runtime if:
- handler location is wrong,
- dependencies are misplaced,
- required executable is absent,
- permissions are wrong.

---

#### 3.1.2.6 Python Lambda ZIP

For the standard Python ZIP model, the handler module and dependencies must be available from:
- the root of the ZIP package.

Correct:

```text
function.zip
├── lambda_function.py
├── requests/
├── urllib3/
└── ...
```

Common mistake:

```text
function.zip
└── my-project/
    ├── lambda_function.py
    └── requests/
```

If handler configuration is:

```text
lambda_function.handler
```

Lambda must be able to import:
- `lambda_function`

from the deployment search path.

Exam rule:

```text
package the required contents at the expected level
not necessarily the containing project directory
```

---

#### 3.1.2.7 Node.js Lambda ZIP

Typical structure:

```text
function.zip
├── index.mjs
├── package.json
└── node_modules/
    └── ...
```

The handler module must:
- match Lambda handler configuration,
- be available in the deployment package.

Dependencies must:
- be installed in an expected path,
- or bundled into generated JavaScript,
- or be supplied through another supported mechanism.

Bundling can transform:

```text
src/
├── handler.ts
├── service.ts
└── ...
```

into:

```text
dist/
└── index.js
```

Principle:

```text
deploy runtime output
not every development file
```

---

#### 3.1.2.8 Java Lambda Artifact

Java Lambda can use:
- JAR,
- ZIP,
- container image.

A build tool can produce a ZIP containing:
- application JAR,
- dependency JARs.

Concept:

```text
deployment.zip
└── lib/
    ├── application.jar
    ├── dependency-a.jar
    └── dependency-b.jar
```

For compiled languages:

```text
source layout
→ build
→ runtime artifact layout
```

can differ substantially.

---

#### 3.1.2.9 Go Lambda ZIP

For Lambda Go OS-only runtime packaging, the executable is:

```text
bootstrap
```

and must be:
- at the ZIP root,
- executable,
- built for Linux,
- built for the function architecture.

Example:

```text
function.zip
└── bootstrap
```

Architecture:

```text
x86_64
or
arm64
```

Connection:

```text
3.1.1
→ build the compatible executable

3.1.2
→ place/name it as Lambda expects
```

---

#### 3.1.2.10 Lambda Layer Structure

A Lambda layer:
- is not an arbitrary ZIP.

Lambda extracts layer contents into:

```text
/opt
```

Runtime libraries search:
- documented subdirectories.

Therefore:
- top-level directory structure matters.

---

#### 3.1.2.11 Layer Directory Reference

| Runtime/content | Typical required layer path |
|---|---|
| Python | `python/...` |
| Node.js | `nodejs/node_modules/...` or supported runtime-specific path |
| Java | `java/lib/...` |
| Executables | `bin/...` |
| Native/shared libraries | `lib/...` |

Python:

```text
layer.zip
└── python/
    └── requests/
```

Node.js:

```text
layer.zip
└── nodejs/
    └── node_modules/
        └── ...
```

Java:

```text
layer.zip
└── java/
    └── lib/
        └── library.jar
```

Exam clue:

```text
layer attached
+
dependency cannot be found
→ inspect layer directory structure
```

---

#### 3.1.2.12 Runtime Search Paths

For Lambda ZIP-based functions:

```text
/var/task
→ function deployment package

/opt
→ Lambda layers
```

Language runtimes use:
- documented search-path precedence.

For Python, the deployment package under `/var/task` is searched before:
- layer paths,
- runtime-provided libraries.

Therefore:

```text
directory placement
→ can determine which dependency version executes
```

This is why:
- ZIP root,
- layer root,
- duplicate dependency versions

matter operationally.

---

#### 3.1.2.13 Handler Configuration Must Match Layout

Python example:

```text
lambda_function.py

def handler(event, context):
    ...
```

Handler:

```text
lambda_function.handler
```

Meaning:

```text
module
+
function
```

If build output changes:
- module location,
- module name,
- directory hierarchy,

handler configuration may need to change.

Correct source code with:
- incorrect handler path

can still fail at runtime.

---

#### 3.1.2.14 File Permissions

Lambda ZIP packages use:
- POSIX file permissions.

Permissions matter especially for:
- custom runtime executables,
- binaries,
- Go `bootstrap`.

Therefore:

```text
correct file
+
correct path
+
wrong permission
→ runtime failure
```

Artifact validation should include:
- permissions where relevant.

---

#### 3.1.2.15 Container Image Structure

Container deployment does not use:
- Lambda ZIP-root conventions.

Instead:

```text
Dockerfile
→ build context
→ image filesystem
→ runtime configuration
→ image
→ ECR
→ deployment
```

For a container:

```text
image filesystem
→ deployment filesystem
```

Files must be placed where:
- runtime,
- application,
- Lambda Runtime Interface Client where applicable

expect them.

---

#### 3.1.2.16 Dockerfile Defines Artifact Layout

Conceptual Dockerfile:

```dockerfile
FROM <base>
COPY <runtime-files> <destination>
RUN <install-runtime-dependencies>
CMD ["handler"]
```

It defines:
- base filesystem,
- copied files,
- installed dependencies,
- working directories,
- runtime command.

The source repository layout:
- influences the build,
but:
- does not itself define the final image layout.

---

#### 3.1.2.17 Build Context and `.dockerignore`

Container build:

```text
docker build <context>
```

The build context controls:
- files available to `COPY`/`ADD`,
- build transfer size,
- accidental file inclusion.

A broad:

```dockerfile
COPY . .
```

can accidentally include:
- `.git`,
- tests,
- local configuration,
- credentials,
- build output,
- documentation.

Use `.dockerignore` to exclude:
- unnecessary build-context files.

Important distinction:

```text
.gitignore
→ source-versioning exclusion

.dockerignore
→ container build-context exclusion
```

`.gitignore` does not automatically:
- protect Docker build context.

---

#### 3.1.2.18 Source, Tests, Build, Infrastructure, Runtime

A useful conceptual separation:

```text
project/
├── src/
├── tests/
├── infrastructure/
├── build-definition
└── docs/
```

Generated runtime artifact:

```text
artifact/
├── executable/code
├── runtime dependencies
└── required runtime resources
```

Tests, IaC, documentation, and build tooling:
- can be necessary for development/deployment,
- but do not automatically belong in the runtime artifact.

---

#### 3.1.2.19 Infrastructure as Code Files

Repositories may contain:
- AWS SAM templates,
- CloudFormation templates,
- CDK source,
- pipeline/build configuration.

These files:
- describe deployment/resources,
- are not automatically application runtime files.

Concept:

```text
application artifact
→ what executes

IaC/template
→ what provisions/configures deployment
```

Keep the roles distinct.

---

#### 3.1.2.20 AWS SAM Project Structure

A SAM project can separate:

```text
sam-app/
├── template.yaml
├── function/
│   ├── app.py
│   └── requirements.txt
└── events/
```

The SAM template:
- identifies the application code location.

Example:

```yaml
Function:
  Type: AWS::Serverless::Function
  Properties:
    CodeUri: function/
```

`CodeUri` connects:

```text
resource definition
→ source/code location
```

If `CodeUri` is wrong:
- wrong files can be built or deployed.

---

#### 3.1.2.21 SAM Build Output

`sam build` transforms source into:
- generated deployment material.

Concept:

```text
project/
├── template.yaml
└── function/
```

becomes build output such as:

```text
.aws-sam/
└── build/
    ├── template.yaml
    └── Function/
        └── runtime files
```

Important:

```text
.aws-sam/build
→ generated output

source directories
→ maintained development input
```

Do not confuse:
- generated build directory

with:
- source of truth.

---

#### 3.1.2.22 Generated Files

Examples:

```text
dist/
build/
.aws-sam/build/
compiled classes
bundled JavaScript
generated binaries
```

Generated files are normally:
- produced by the build,
- consumed by packaging/deployment.

Whether they belong in source control:
- depends on project strategy.

The exam-relevant distinction is:

```text
source input
≠ generated deployable output
```

---

#### 3.1.2.23 `.gitignore` Boundary

Typical source exclusions:

```text
node_modules/
dist/
.env
.aws-sam/
IDE files
temporary files
```

But:

```text
.gitignore
```

controls:
- source-versioning behavior.

It does not directly control:
- ZIP contents,
- Docker build context,
- runtime artifact.

Those require:
- build/package rules,
- `.dockerignore`,
- explicit packaging configuration.

---

#### 3.1.2.24 Configuration and Secrets

Stable, non-sensitive runtime resources may be packaged if:
- application requires them locally,
- they are artifact-specific.

Environment-specific configuration should normally:
- remain external.

Secrets should not be hidden inside:

```text
source tree
ZIP
JAR
container image
```

Danger pattern:

```text
project/
├── .env
└── Dockerfile

Dockerfile:
COPY . .
```

This can embed:
- secrets into image layers.

Connection to 3.1.1:

```text
artifact
→ code + stable runtime files

environment
→ runtime configuration + secrets + resource identifiers
```

---

#### 3.1.2.25 Package Only Runtime-Required Files

Usually exclude unnecessary:
- tests,
- documentation,
- local caches,
- IDE metadata,
- build tools,
- repository metadata.

Benefits:
- smaller artifact,
- less accidental exposure,
- clearer runtime contents.

But do not remove required:
- templates,
- schemas,
- certificates,
- migration files,
- localization resources,
- dynamic modules,
- static assets.

Rule:

```text
minimal
≠ incomplete
```

---

#### 3.1.2.26 Static Assets and Relative Paths

Applications may require:
- HTML,
- CSS,
- JavaScript,
- templates,
- images,
- schemas.

If runtime loads them locally:
- preserve expected relative paths.

Example:

```text
./config/schema.json
```

assumes:
- a specific runtime layout/working directory.

Build transformations can break:
- relative-path assumptions.

Validate:
- actual packaged paths.

---

#### 3.1.2.27 Case Sensitivity

Local development can hide filename problems.

Example:

```text
code expects:
Config.json

artifact contains:
config.json
```

Linux-based runtime:
- treats these as different filenames.

Therefore:
- validate deployment artifacts in a target-compatible environment.

---

#### 3.1.2.28 Multiple Functions and Services

One repository can contain:
- multiple independently deployable components.

Example:

```text
application/
├── template.yaml
├── create-order/
│   ├── app.py
│   └── requirements.txt
└── cancel-order/
    ├── app.py
    └── requirements.txt
```

SAM/CloudFormation can map:
- each resource to its corresponding code location.

Rule:

```text
one repository
≠ one deployment artifact
```

Each independently deployed component:
- can have its own build/artifact.

---

#### 3.1.2.29 Monorepo

A monorepo can contain:

```text
repo/
├── services/
│   ├── orders/
│   └── payments/
├── libraries/
└── infrastructure/
```

AWS does not require:
- one repository per service.

The deployment pipeline must know:
- which paths belong to which component,
- which build context to use,
- which artifact to produce.

Keep this at:
- deployment-structure level,
not:
- repository-strategy theory.

---

#### 3.1.2.30 Shared Code

Shared code can be provided through:
- language packages,
- Lambda layers,
- compiled/bundled output,
- shared source modules.

3.1.1 decides primarily:
- how the dependency is supplied.

3.1.2 asks:
- whether build/runtime paths place it where it can be found.

---

#### 3.1.2.31 Artifact Size and Duplication

Poor structure can duplicate:
- dependencies,
- generated assets,
- unnecessary files.

Example:

```text
Function A ZIP → shared library
Function B ZIP → shared library
Function C ZIP → shared library
```

A layer:
- may reduce duplication for suitable ZIP-based Lambda functions.

But:
- do not introduce layers mechanically.

Artifact structure should first satisfy:
- runtime correctness,
- deployment independence.

---

#### 3.1.2.32 Directory Structure as Runtime Contract

Think of deployment structure as a contract between:

```text
BUILD SYSTEM
    |
    v
DEPLOYMENT ARTIFACT
    |
    v
AWS RUNTIME
```

Examples:

```text
Python Lambda
→ handler/dependencies at expected package path

Go Lambda
→ bootstrap at ZIP root

Lambda layer
→ language-specific root directory

SAM
→ CodeUri identifies correct source location

container
→ Dockerfile COPY/runtime paths create correct filesystem
```

This is the central mental model of the skill.

---

#### 3.1.2.33 Failure Pattern Summary

| Symptom | First structural check |
|---|---|
| Lambda handler/module not found | ZIP root + handler configuration |
| Python layer attached but import fails | top-level `python/` path |
| Node.js layer dependency missing | `nodejs/node_modules/...` path |
| Java layer library missing | `java/lib/...` |
| Go Lambda does not start | `bootstrap`, root location, Linux architecture, executable permission |
| SAM deploys wrong function files | `CodeUri` + generated build output |
| Container contains unwanted local files | build context + `COPY` + `.dockerignore` |
| Source tests pass but deployment fails | inspect/test generated artifact |
| Different dependency version executes | runtime search-path precedence |
| Runtime cannot find local asset | packaged relative path/case |

---

#### 3.1.2.34 Decision Flow

```text
identify deployment target
        |
        v
ZIP / layer / container / other
        |
        v
check target runtime layout contract
        |
        +--> handler/module location
        +--> dependency path
        +--> executable name
        +--> layer root
        +--> permissions
        |
        v
separate source from generated output
        |
        v
package runtime-required files only
        |
        v
keep environment-specific config/secrets external
        |
        v
inspect generated ZIP/image
        |
        v
test exact artifact
```

#### 3.1.2.35 Common Exam Traps

##### "ZIP upload succeeded, so structure is correct"
- False.
- Runtime initialization/import can still fail.

##### "ZIP the containing project folder"
- Often wrong.
- Package contents at the level expected by the runtime.

##### "Lambda layer ZIP can use any directory structure"
- False.

##### "Source tree must equal deployment tree"
- False.
- Build systems commonly transform it.

##### "Everything in Git belongs in production artifact"
- False.

##### "`.gitignore` protects Docker build context"
- False.
- `.dockerignore` controls Docker build-context exclusions.

##### "Configuration and secrets should sit beside source"
- Wrong for environment-specific/sensitive values.

##### "One repository means one artifact"
- False.

##### "File location cannot affect dependency version"
- False.
- Runtime search-path precedence can determine which version loads.

##### "Minimal package means remove every non-code file"
- False.
- Required runtime resources must remain.

#### 3.1.2.38 Exam-Level Knowledge Frame

Know these cold.

**Source directory**  
→ developer/build organization.

**Deployment directory**  
→ runtime organization.

**Lambda Python ZIP**  
→ handler module and dependencies available at expected package/root path.

**Lambda Node.js ZIP**  
→ handler and runtime dependencies/bundle in expected package paths.

**Go Lambda ZIP**  
→ Linux-compatible executable named `bootstrap` at ZIP root.

**Lambda layer**  
→ extracted under `/opt` and must use supported runtime-specific paths.

**Python layer**  
→ `python/...`.

**Node.js layer**  
→ `nodejs/node_modules/...` or supported runtime-specific path.

**Java layer**  
→ `java/lib/...`.

**SAM `CodeUri`**  
→ identifies application code location.

**Container**  
→ Dockerfile + build context determine final image filesystem.

**`.dockerignore`**  
→ excludes files from Docker build context.

**Generated build directory**  
→ build output, not necessarily source of truth.

Fastest exam discriminator:

```text
handler/module not found?
→ ZIP path + handler configuration

layer attached but dependency missing?
→ layer root structure

Go Lambda cannot start?
→ bootstrap + Linux architecture + permissions

SAM packages wrong files?
→ CodeUri + build output

container includes local files?
→ build context + COPY + .dockerignore

source works but deployment fails?
→ inspect exact generated artifact
```

Final principle:

**Repository structure serves developers and build tooling; deployment structure is a runtime contract. Build source into the exact filesystem/archive layout expected by the target AWS runtime, package only required runtime material, and validate the generated artifact rather than assuming the repository itself is deployable.**
