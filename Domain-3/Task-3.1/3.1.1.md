### 3.1.1 Manage the dependencies of the code module within the package

#### 3.1.1.1 Exam and Task Context

##### 3.1.1.1.1 Domain and Task
- **Domain 3:** Deployment.
- **Task 3.1:** Prepare application artifacts to be deployed to AWS.
- **Skill 3.1.1:** Manage the dependencies of the code module, including examples such as:
  - environment variables,
  - configuration files,
  - container images.

The exam wording is intentionally broader than:
- third-party libraries.

Core question:

**What does the deployed application require to run, which dependencies belong inside the artifact, and which should be supplied externally at deployment or runtime?**

---

#### 3.1.1.2 Core Mental Model

```text
SOURCE CODE
    |
    v
identify dependencies
    |
    +--> build-time only
    |      → exclude from runtime artifact where possible
    |
    +--> runtime library/native dependency
    |      → package / layer / image / platform-provided runtime
    |
    +--> environment-specific configuration
    |      → externalize/inject
    |
    +--> secret
    |      → secure external store
    |
    '--> external AWS resource
           → provision separately + reference/configure
    |
    v
build for target runtime / OS / architecture
    |
    v
version dependencies
    |
    v
immutable deployable artifact
    |
    v
test and promote the same artifact
```

Central principle:

```text
package what must travel with the code
externalize what should vary independently
```

---

#### 3.1.1.3 Dependency Categories

A deployable application can depend on:

```text
language packages/libraries
runtime
native/OS libraries
shared code
configuration
environment variables
secrets
container base image
external AWS services/resources
```

These dependencies have:
- different lifecycle,
- different security requirements,
- different packaging mechanisms.

Do not treat them all as:
- files to place in one ZIP.

---

#### 3.1.1.4 Build-Time vs Runtime Dependencies

##### Build-time
Needed only to create the artifact.

Examples:

```text
compiler
Maven / Gradle
npm build tooling
pip build tooling
Docker build stages
build plugins
test frameworks
```

Normally:
- remove/exclude from the final runtime artifact when unnecessary.

##### Runtime
Needed while the application executes.

Examples:

```text
Java libraries
Node modules
Python packages
native libraries
Lambda Runtime Interface Client
runtime configuration
```

Runtime dependencies must be:
- packaged,
- supplied through a supported mechanism,
- or supplied by the execution platform.

---

#### 3.1.1.5 Dependency Manifests and Version Control

Common ecosystems:

```text
Java
→ pom.xml / Gradle

Node.js
→ package.json + lock file

Python
→ requirements.txt / equivalent

.NET
→ project/package references

Go
→ go.mod + go.sum
```

Package managers:
- resolve dependency graphs,
- retrieve direct and transitive dependencies,
- construct the build/runtime artifact.

Use controlled versions so:

```text
same source
+
same dependency definition
+
same build process
→ equivalent artifact
```

---

#### 3.1.1.6 Pinning, Locking, and Transitive Dependencies

Loose dependency selection can produce:
- different builds at different times.

Controlled/pinned versions improve:
- reproducibility,
- test confidence,
- rollback confidence.

Transitive dependency:

```text
application A
→ library B
→ library C
```

`C` still affects:
- compatibility,
- vulnerabilities,
- runtime behavior.

Therefore:
- manifests,
- lock files,
- dependency scanning,
- tested resolved artifacts

matter even when a dependency is not declared directly.

---

#### 3.1.1.7 Immutable Artifact and Promotion

Preferred deployment model:

```text
BUILD ONCE
→ artifact v1

TEST artifact v1
→ approve

PROMOTE artifact v1
→ production
```

Avoid unnecessary:

```text
rebuild for dev
rebuild for test
rebuild for prod
```

because dependency resolution or build environment changes can create:
- artifact drift.

The tested artifact should be:
- identifiable,
- immutable,
- promotable.

---

#### 3.1.1.8 Lambda Deployment Package Boundary

AWS Lambda supports two primary package types:

```text
ZIP archive
container image
```

Both must provide:
- function code,
- runtime dependencies required by the function.

The packaging mechanism changes:
- where dependencies are placed,
- how OS/runtime dependencies are supplied.

---

#### 3.1.1.9 Lambda ZIP Dependencies

Concept:

```text
function code
+
compatible runtime libraries
→ ZIP deployment package
```

For interpreted languages:
- dependencies generally must be in the expected deployment-package structure,
- or supplied through Lambda layers/runtime behavior.

Example Python layout:

```text
deployment.zip
├── lambda_function.py
├── requests/
├── urllib3/
└── ...
```

AWS currently recommends packaging all Python function dependencies, including SDK dependencies when you depend on them, to avoid runtime-library version misalignment.

Python search precedence matters:

```text
/var/task
→ deployment package

/opt/...
→ layers

runtime-provided libraries
→ later in search path
```

A packaged dependency can therefore:
- override a runtime-provided version.

---

#### 3.1.1.10 Native Dependencies and Target Compatibility

Packages containing:
- compiled extensions,
- native binaries,
- OS-specific libraries

must match the deployment environment.

Check:

```text
operating system
architecture
runtime version
binary compatibility
```

Example:

```text
dependency compiled on macOS
≠ guaranteed to run on Lambda Linux
```

Lambda architectures include:

```text
x86_64
arm64
```

Native dependencies must match:
- the architecture of the deployed function/image.

Rule:

```text
build native dependencies for the target
not merely for the developer workstation
```

---

#### 3.1.1.11 Lambda Layers

A Lambda layer is:
- a ZIP archive containing supplementary code or data.

Common contents:

```text
shared libraries
dependencies
custom runtime
configuration files
```

Lambda extracts layers under:

```text
/opt
```

A function can use:
- up to five layers.

Layers are available for:
- ZIP-based Lambda functions.

For container-image Lambda functions:
- package dependencies into the image.

---

#### 3.1.1.12 Layer Versioning and Reuse

Layers are versioned.

Example:

```text
SharedLibrary
→ version 7

Function A
→ layer version 7

Function B
→ layer version 7
```

A new layer version:
- should not silently alter an already tested function deployment.

Principle:

```text
deployed dependency version
→ identifiable and controlled
```

Use layers when:
- several ZIP-based functions share a dependency,
- independent layer versioning provides value.

Do not use them automatically:
- just because code is reusable.

---

#### 3.1.1.13 Go and Rust

AWS recommends against using layers to manage dependencies for:
- Go,
- Rust.

Reason:
- these applications normally compile into a single executable containing dependencies,
- layers add complexity and can add initialization work.

Preferred:

```text
source + dependencies
→ compiled executable
→ deployment package
```

---

#### 3.1.1.14 Java and Other Packaged Runtimes

Java Lambda artifacts can include:

```text
JAR
ZIP containing JARs/classes
container image
```

Maven/Gradle:
- resolve dependencies,
- build the deployable artifact.

General rule:

```text
runtime libraries required by the application
→ must be present or otherwise supplied at runtime
```

---

#### 3.1.1.15 Container Image as Dependency Boundary

A container image can include:

```text
base operating system
runtime
system libraries
application dependencies
application code
```

Compared with a ZIP:
- the image defines a broader execution dependency boundary.

Lambda image flow:

```text
base image
→ runtime / Runtime Interface Client
→ dependencies
→ function code
→ build image
→ push to Amazon ECR
→ Lambda deployment
```

---

#### 3.1.1.16 Lambda Base Images and Runtime Interface Client

AWS Lambda base images include:
- operating system,
- language runtime,
- Lambda Runtime Interface Client,
- required Lambda components.

Application adds:
- code,
- dependencies.

If using:
- AWS OS-only base image,
- compatible non-AWS base image,

the image must include:
- a Lambda Runtime Interface Client.

Current Lambda container requirements include:
- Linux-based image,
- one target architecture per function image.

---

#### 3.1.1.17 Base Image Is a Dependency

Dockerfile:

```dockerfile
FROM <base-image>
```

The base image determines:
- OS libraries,
- runtime baseline,
- package manager,
- security patch baseline,
- architecture compatibility.

If the base image changes:

```text
same application source
→ potentially different artifact
```

AWS periodically updates Lambda base images.

To adopt an update:

```text
rebuild image
→ test
→ push new image
→ update function
```

An existing Lambda deployment does not automatically absorb:
- future base-image changes.

---

#### 3.1.1.18 Image Tags vs Digests

Tag:

```text
myapp:1.4
```

is:
- human-friendly,
- potentially mutable.

Digest:

```text
sha256:...
```

identifies:
- immutable image content.

For deterministic builds/releases:
- control base-image and application-image identity.

Avoid assuming:

```text
latest
→ reproducible
```

---

#### 3.1.1.19 Multi-Stage Container Builds

Pattern:

```text
BUILD STAGE
→ compiler / build tooling

RUNTIME STAGE
→ only runtime necessities
```

Benefits:
- smaller runtime image,
- fewer unnecessary packages,
- smaller attack surface,
- clearer build/runtime dependency boundary.

Keep this as:
- deployment-engineering context,
not:
- a deep Docker-design topic.

---

#### 3.1.1.20 Amazon ECR vs CodeArtifact

##### Amazon ECR

```text
container images
→ ECR
```

ECR stores:
- built container-image artifacts.

##### AWS CodeArtifact

```text
software packages/libraries
→ CodeArtifact
```

CodeArtifact integrates with common package tooling such as:
- Maven/Gradle,
- npm/yarn,
- pip/twine,
- NuGet.

Fast distinction:

```text
private library/package dependency?
→ CodeArtifact

container image?
→ ECR
```

---

#### 3.1.1.21 Source Repository vs Package Repository vs Image Repository

```text
Git repository
→ source code + build definitions

CodeArtifact
→ reusable software packages

ECR
→ deployable container images
```

These are:
- different lifecycle objects.

Do not treat:
- source version control

as:
- the runtime artifact repository.

---

#### 3.1.1.22 Environment Variables

The exam guide explicitly includes:
- environment variables

as dependencies.

Example:

```text
TABLE_NAME
API_ENDPOINT
FEATURE_MODE
ENVIRONMENT
```

They let the same application artifact use:
- different runtime configuration.

Preferred model:

```text
immutable code/artifact
+
deployment/runtime configuration
```

instead of:

```text
environment-specific values compiled into code
```

---

#### 3.1.1.23 Environment Variables Are Runtime Configuration

Useful distinction:

```text
code + libraries
→ artifact

environment variables
→ version/deployment configuration
```

Lambda environment variables:
- are configured separately from code,
- become locked with a published Lambda version,
- are literal strings rather than automatically expanded expressions.

For sensitive values such as credentials:
- AWS recommends Secrets Manager instead of plain environment variables.

---

#### 3.1.1.24 Configuration Files

Configuration files can be:

```text
JSON
YAML
properties
other formats
```

Decision:

```text
static + artifact-specific?
→ may belong in package/image

environment-specific / frequently changing?
→ prefer external configuration
```

Do not make a new code artifact solely because:
- runtime configuration changed,
unless the architecture intentionally requires it.

---

#### 3.1.1.25 AWS AppConfig

AWS AppConfig manages:
- feature flags,
- dynamic/free-form application configuration.

Examples:

```text
feature flags
logging levels
allow/block lists
service limits
throttling rules
```

Primary advantage:

```text
change application behavior
without redeploying code
```

AWS AppConfig can use configuration from:
- AppConfig hosted configuration,
- Systems Manager Parameter Store,
- Secrets Manager,
- Amazon S3.

Detailed environment-specific configuration belongs primarily to:
- 3.1.5.

---

#### 3.1.1.26 Parameter Store and Secrets Manager

##### Systems Manager Parameter Store
Use for centralized:
- parameters,
- configuration values,
- secure strings where appropriate.

##### AWS Secrets Manager
Use for:
- database credentials,
- API credentials,
- passwords,
- other secrets.

Core distinction:

```text
configuration
→ controls application behavior

secret
→ confidential credential/material
```

Do not bake secrets into:
- source repository,
- ZIP/JAR,
- image,
- configuration file inside artifact.

---

#### 3.1.1.27 External AWS Resources Are Runtime Dependencies

Applications can depend on:

```text
DynamoDB
SQS
SNS
S3
API Gateway
other AWS resources
```

These resources are not:
- code libraries to package.

They should normally be:
- provisioned separately,
- referenced through configuration/identifiers,
- accessed through appropriate IAM permissions.

Example:

```text
Lambda artifact
+
TABLE_NAME
+
execution role
→ DynamoDB access
```

---

#### 3.1.1.28 IAM Role as a Runtime Dependency

Application code may require permission to:
- call AWS APIs.

Correct model:

```text
execution role / temporary credentials
→ authorize runtime AWS API access
```

Incorrect model:

```text
package static AWS credentials in artifact
```

Domain 2 defines:
- authentication/authorization details.

This skill preserves:
- the secure deployment boundary.

---

#### 3.1.1.29 Runtime Version as a Dependency

Runtime version affects:
- language capabilities,
- included libraries,
- native compatibility,
- security support,
- behavior of packaged dependencies.

Therefore:

```text
application code
+
dependency versions
+
runtime version
+
architecture
→ effective runtime artifact
```

Control and test:
- the actual combination deployed.

---

#### 3.1.1.30 Build Environment Compatibility

A build can succeed locally yet fail in AWS because of:

```text
OS mismatch
architecture mismatch
runtime mismatch
native library mismatch
```

For native/runtime-sensitive dependencies:
- build in an environment compatible with the target,
- or use platform-compatible artifacts/wheels/images.

Do not rely on:

```text
works on my workstation
```

as deployment validation.

---

#### 3.1.1.31 Package Only What the Runtime Needs

Exclude unnecessary:
- build tools,
- tests,
- local caches,
- temporary files,
- unused dependencies.

Benefits:
- smaller artifacts,
- faster deployment,
- lower attack surface,
- easier dependency understanding.

But:

```text
smallest possible
≠ correct target
```

The artifact must remain:
- complete for runtime execution.

---

#### 3.1.1.32 Build Dependencies Before Production

Avoid designs where production startup must:
- fetch arbitrary package versions,
- resolve dependencies from public repositories,
- compile native libraries.

Preferred:

```text
CI/build environment
→ resolve dependencies
→ build artifact
→ scan/test
→ publish immutable artifact
→ deploy
```

This improves:
- determinism,
- security,
- rollback,
- availability.

---

#### 3.1.1.33 Configuration at Build Time vs Runtime

Build-time configuration becomes:
- part of artifact identity.

Runtime configuration remains:
- independently changeable.

Ask:

```text
Does this value define the artifact?
or
Does this value define the deployment environment?
```

Examples:

```text
compile-time feature included in binary
→ build-time

database endpoint
→ runtime

environment name
→ runtime

secret
→ external runtime retrieval/injection
```

---

#### 3.1.1.34 Environment Promotion

Preferred:

```text
same artifact
+
different external configuration
→ dev / test / prod
```

This reduces:
- dependency drift,
- environment-specific rebuild differences.

Environment-specific runtime values still need:
- independent validation.

---

#### 3.1.1.35 Dependency Updates

A dependency update should normally produce:
- a new tested artifact or layer/image version.

Process:

```text
change dependency version
→ build
→ test
→ scan
→ publish new artifact
→ deploy/promote
```

Do not silently replace:
- dependencies used by an immutable deployed artifact.

---

#### 3.1.1.36 Failure Patterns

| Symptom | Likely cause / direction |
|---|---|
| Lambda cannot import library | dependency absent or wrong package/layer structure |
| Native package works locally but not Lambda | OS/architecture/runtime incompatibility |
| Runtime `NoSuchMethod` / module conflict | incompatible dependency versions |
| Dev/test/prod need different endpoint | externalize runtime configuration |
| Secret found inside ZIP/image | move to Secrets Manager/secure external store |
| Same source rebuild produces different container | floating dependency/base tag such as `latest` |
| Container deployment lacks Lambda runtime integration | include Runtime Interface Client / use compatible Lambda base image |
| Package repository needed for Maven/npm/Python/NuGet | CodeArtifact |
| Container image repository needed | ECR |

#### 3.1.1.38 Common Exam Traps

##### "Dependency means only third-party library"
- False.
- The exam explicitly includes configuration and container-image context.

##### "Every dependency belongs inside the ZIP"
- False.
- Environment-specific configuration, secrets, IAM, and AWS resources usually do not.

##### "Put secrets in packaged configuration"
- Wrong.

##### "Lambda layer works with container-image functions"
- False.
- Layers are for ZIP-based functions.

##### "Layers are best for Go/Rust dependencies"
- False.
- AWS recommends packaging those dependencies with the compiled executable.

##### "Native dependencies built on any OS will work"
- False.

##### "ECR stores Maven/npm packages"
- Wrong.
- Use CodeArtifact for software packages.

##### "CodeArtifact is a container registry"
- False.

##### "Rebuild independently for every environment"
- Usually weaker than promoting the same tested artifact.

##### "`latest` guarantees reproducibility"
- False.

##### "Runtime configuration change always requires code rebuild"
- False.

##### "Runtime-provided Python SDK dependencies can never conflict"
- False.
- Packaged/layer dependencies can create version-misalignment issues.

#### 3.1.1.41 Exam-Level Knowledge Frame

Know these cold.

**Dependency**  
→ anything the application requires to build or run correctly.

**Build-time dependency**  
→ needed to produce the artifact, not necessarily at runtime.

**Runtime dependency**  
→ must be packaged or supplied by runtime/platform.

**Environment-specific configuration**  
→ prefer runtime/external configuration.

**Secret**  
→ do not bake into the artifact.

**Lambda ZIP**  
→ function code + compatible runtime dependencies.

**Lambda layer**  
→ reusable supplementary dependencies/code/data for ZIP-based functions.

**Lambda container image**  
→ OS/runtime/system libraries/dependencies/code in one image boundary.

**Runtime Interface Client**  
→ required when a custom/non-Lambda base image must integrate with Lambda Runtime API.

**ECR**  
→ container-image registry.

**CodeArtifact**  
→ software-package repository.

**AppConfig**  
→ dynamic application configuration / feature flags independent of code deployment.

**Native dependency**  
→ must match target OS/runtime/architecture.

**Reproducibility**  
→ controlled dependencies + immutable artifact identity.

Fastest exam discriminator:

```text
shared dependency across ZIP Lambdas?
→ layer may fit

Go/Rust Lambda dependency?
→ compile/package with executable

custom OS/native dependency stack?
→ container image may fit

secret?
→ Secrets Manager / secure external store

environment-specific value?
→ external runtime configuration

private package repository?
→ CodeArtifact

container image repository?
→ ECR

native library works locally only?
→ rebuild for target Linux/architecture

same artifact across dev/test/prod?
→ externalize environment-specific config
```

Final principle:

**Build a complete but minimal immutable artifact. Package code and true runtime dependencies together, externalize environment-specific configuration and secrets, control dependency versions, and build for the exact runtime, operating system, and architecture that will execute the application.**
