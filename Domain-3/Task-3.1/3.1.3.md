### 3.1.3 Use code repositories in deployment environments

#### 3.1.3.1 Exam and Task Context

##### 3.1.3.1.1 Domain and Task
- **Domain 3:** Deployment.
- **Task 3.1:** Prepare application artifacts to be deployed to AWS.
- **Skill 3.1.3:** **Use code repositories in deployment environments.**

This skill is primarily about:

```text
source code
→ versioned repository
→ identifiable revision
→ build/test/package
→ immutable deployment artifact
→ deployment
```

Core question:

**Which exact source revision produced the deployed application, and how does AWS consume that repository as deployment input?**

---

#### 3.1.3.2 Core Mental Model

```text
DEVELOPER CHANGE
      |
      v
    COMMIT
      |
      v
 GIT REPOSITORY
      |
      +--> branch
      +--> tag
      '--> commit SHA
              |
              v
      SOURCE INTEGRATION
              |
              v
      BUILD / TEST / PACKAGE
              |
              v
      IMMUTABLE ARTIFACT
              |
              v
          DEPLOYMENT
```

Central principle:

```text
repository
→ versioned source and history

artifact
→ built deployable output
```

Do not confuse them.

---

#### 3.1.3.3 Repository as Source of Version History

A Git repository can store:
- source files,
- commit history,
- branches,
- tags,
- dependency manifests,
- build definitions,
- infrastructure definitions.

Its deployment role is to provide:
- an identifiable source revision.

A deployment should ideally be traceable to:
- the commit that produced it.

---

#### 3.1.3.4 Commit, Branch, and Tag

##### Commit
A commit identifies:
- a specific source state.

Useful for:
- traceability,
- comparison,
- reproducibility,
- rollback reference.

##### Branch
A branch is:
- a movable reference.

Examples:

```text
main
develop
feature/order-api
```

Important:

```text
branch name
≠ immutable application version
```

##### Tag
A tag is:
- a named reference to a commit.

Typical use:
- releases,
- approved source revisions.

Example:

```text
v2.4.1
→ commit abc123...
```

Detailed release/branch strategy belongs primarily to:
- 3.4.9.

---

#### 3.1.3.5 Commit vs Artifact Identity

Commit:

```text
identifies source
```

Artifact version/digest:

```text
identifies build output
```

They are related but not identical.

One commit can theoretically create different outputs if:
- dependencies float,
- build environment changes,
- build parameters differ.

Strong traceability therefore preserves:

```text
source revision
+
build execution
+
artifact identity
+
deployment identity
```

---

#### 3.1.3.6 Repository Is Not an Artifact Repository

Keep these roles separate:

| Service / object | Primary role |
|---|---|
| Git repository / CodeCommit / GitHub / GitLab / Bitbucket | source + version history |
| AWS CodeArtifact | software package repository |
| Amazon ECR | container image repository |
| Amazon S3 | object/artifact storage and possible pipeline source |
| Deployment artifact | built runtime output |

Fast distinction:

```text
source code?
→ Git repository

npm/Maven/Python/NuGet package?
→ CodeArtifact

container image?
→ ECR
```

---

#### 3.1.3.7 Source-to-Deployment Chain

Typical deployment flow:

```text
repository
→ source action
→ build
→ test
→ package
→ artifact/image
→ deploy
```

The repository is normally:
- near the beginning of the deployment lifecycle.

The runtime should normally receive:
- a built artifact,
not:
- a Git working copy.

---

#### 3.1.3.8 AWS CodeCommit

AWS CodeCommit is:
- an AWS-managed Git-compatible source repository.

It supports:
- repositories,
- commits,
- branches,
- pull requests,
- Git operations,
- IAM-based access.

The source records that CodeCommit became available to new customers again on:
- **November 25, 2025**.

Exam relevance:

```text
AWS-managed Git repository?
→ CodeCommit
```

---

#### 3.1.3.9 Repository Authentication and Permissions

Repository access should follow:
- least privilege.

Examples:

```text
developer
→ read/write source

build service
→ read source

pipeline
→ access configured source

runtime role
→ normally no repository access
```

Important distinction:

```text
pipeline/build role
≠ Lambda/application execution role
```

Runtime code normally does not need:
- Git credentials,
- repository write access,
- `.git` history.

---

#### 3.1.3.10 AWS CodeConnections

AWS CodeConnections connects supported external Git providers to:
- AWS developer services.

Examples:
- GitHub,
- GitHub Enterprise Server,
- GitLab.com,
- GitLab self-managed,
- Bitbucket Cloud.

Mental model:

```text
external Git repository
→ CodeConnections
→ CodePipeline / CodeBuild
→ AWS delivery workflow
```

Current source guidance favors:
- connection/GitHub App integration

over:
- the older GitHub OAuth source action.

---

#### 3.1.3.11 External Git Providers

Provider-specific details differ,
but the common model is:

```text
Git provider
→ authenticated AWS connection
→ selected repository/revision
→ build or pipeline
```

For exam scenarios:

```text
GitHub/GitLab/Bitbucket into CodePipeline
→ CodeConnections
```

---

#### 3.1.3.12 CodePipeline Source Action

A CodePipeline pipeline can begin with:
- a **Source** action.

Current source types include:
- CodeCommit,
- supported external Git repositories through connections,
- Amazon S3,
- Amazon ECR.

Important distinction:

```text
CodePipeline source
```

is broader than:

```text
Git code repository
```

ECR and S3 can be:
- pipeline sources,
but are not:
- Git repositories.

---

#### 3.1.3.13 CodeCommit Source Change Detection

A CodeCommit source action can select:
- repository,
- branch.

Current source guidance recommends:
- EventBridge-based source change detection.

Concept:

```text
commit/push
→ source-change event
→ pipeline starts
```

Detailed commit-trigger CI/CD behavior belongs primarily to:
- 3.4.6.

For 3.1.3, know:
- the repository is deployment-ready source.

---

#### 3.1.3.14 CodePipeline Source Artifact

A source action produces:
- a source output artifact.

Concept:

```text
repository revision
→ source action
→ SourceArtifact
→ CodeBuild
```

Do not confuse:

```text
SourceArtifact
```

with:

```text
final deployable artifact
```

Build/test/package stages can:
- transform the source artifact further.

---

#### 3.1.3.15 Default Source Snapshot vs Full Clone

A normal CodePipeline source output can provide:
- a source snapshot.

For supported Git source actions, **Full clone** can preserve:
- Git metadata.

Use Full clone when downstream CodeBuild needs:
- commit history,
- tags,
- branch information,
- Git commands such as `git describe`.

Decision:

```text
need source files only?
→ normal source snapshot

need Git history/tags/metadata in CodeBuild?
→ Full clone
```

Full clone is:
- not automatically better.

Use it only when:
- the build requires Git metadata.

---

#### 3.1.3.16 AWS CodeBuild as Repository Consumer

CodeBuild can consume source from:
- CodeCommit,
- GitHub,
- GitHub Enterprise,
- GitLab,
- GitLab self-managed,
- Bitbucket,
- Amazon S3,
- CodePipeline.

Two common models:

```text
Git repository
→ CodeBuild
→ build/test/package
```

or:

```text
Git repository
→ CodePipeline
→ CodeBuild
→ deploy
```

Use CodePipeline when:
- multi-stage orchestration is needed.

---

#### 3.1.3.17 Repository Contains Build Instructions

A repository can version build/deployment definitions such as:

```text
buildspec.yml
Dockerfile
template.yaml
package.json
pom.xml
requirements.txt
```

This allows:
- source,
- dependency declarations,
- build instructions,
- infrastructure definitions

to evolve together under version control.

---

#### 3.1.3.18 CodeBuild `buildspec.yml`

`buildspec.yml` can define phases such as:

```text
install
pre_build
build
post_build
```

and:
- build artifacts.

Therefore a repository can version:

```text
application code
+
build procedure
```

This improves:
- repeatability,
- traceability.

---

#### 3.1.3.19 Infrastructure as Code in Repository

Repositories may contain:
- AWS SAM templates,
- CloudFormation templates,
- CDK source.

Benefits:
- infrastructure changes are versioned,
- code and infrastructure can be reviewed together,
- pipeline can deploy IaC.

Detailed IaC handling belongs to:
- 3.3.x / 3.4.x.

---

#### 3.1.3.20 Secrets Must Not Be Committed

A Git repository preserves:
- historical versions.

Therefore:

```text
secret committed
→ later deleted
≠ secret was never exposed
```

Do not commit:
- passwords,
- API keys,
- access credentials,
- private keys.

If a secret is accidentally committed:
- rotate/revoke it,
- remove it from current source,
- remediate repository history according to policy,
- move it to an appropriate secret store.

Deleting the latest copy alone:
- is insufficient.

---

#### 3.1.3.21 Environment Configuration and Source

Avoid separate copies of source just to change:
- endpoint,
- table name,
- feature flag,
- secret.

Preferred:

```text
same source / artifact
+
environment-specific configuration
```

Environment-specific configuration belongs primarily to:
- 3.1.5.

A repository can still contain:
- non-secret defaults,
- schemas,
- configuration definitions/templates.

---

#### 3.1.3.22 Environment Branches

Some organizations map branches to environments:

```text
develop
→ development

release
→ staging

main
→ production
```

This is:
- possible,
- not an AWS requirement.

Risk:
- source branches can diverge,
- environment differences become code differences.

Do not assume:
- one branch per environment is the preferred exam answer.

---

#### 3.1.3.23 Artifact Promotion vs Rebuild Per Environment

Source-promotion model:

```text
commit
→ rebuild separately for each environment
```

Artifact-promotion model:

```text
commit
→ build once
→ test artifact
→ promote same artifact
```

Artifact promotion gives stronger confidence that:

```text
production runs the same bytes that were tested
```

The repository:
- remains source of truth for source code.

Artifact storage:
- carries deployable output.

---

#### 3.1.3.24 Monorepo vs Polyrepo

##### Monorepo

```text
repo/
├── orders/
├── payments/
├── notifications/
└── infrastructure/
```

One repository can:
- contain multiple deployable components,
- feed multiple pipelines,
- build selected paths.

##### Polyrepo

```text
orders-repo
payments-repo
notifications-repo
```

Each repository:
- has independent source history/pipeline.

Exam depth:
- know both are possible.

AWS does not require:
- one repository per service.

---

#### 3.1.3.25 Same Repository, Multiple Pipelines

One repository can feed:
- development pipeline,
- release pipeline,
- multiple service-specific pipelines.

The repository does not define:
- one fixed deployment topology.

Source selection can be based on:
- branch,
- tag,
- path,
- other supported trigger/filter behavior.

Detailed trigger filtering belongs mainly to:
- 3.4.6 / 3.4.9.

---

#### 3.1.3.26 Build From the Intended Revision

A pipeline should build:
- the triggering commit,
- the explicitly selected revision,
- the intended tag/branch state.

Avoid:

```text
pipeline triggered by commit A
→ build script independently clones latest main
→ commit B arrives
→ build accidentally produces B
```

Preferred:

```text
build the source revision supplied by the pipeline/source integration
```

This preserves:
- source-to-artifact traceability.

---

#### 3.1.3.27 Avoid Runtime Git Pull

Poor deployment model:

```text
application starts
→ git pull latest
→ install dependencies
→ run
```

Problems:
- non-deterministic runtime,
- deployment depends on repository availability,
- untested changes can appear,
- rollback becomes harder.

Preferred:

```text
repository
→ controlled build
→ tested immutable artifact
→ deployment
```

---

#### 3.1.3.28 ECR as Pipeline Source

Amazon ECR stores:
- container images.

It is not:
- a Git repository.

But CodePipeline can use:
- ECR as a source action.

Example:

```text
new image pushed to ECR
→ pipeline starts
```

This demonstrates:

```text
pipeline source
≠ always source-code repository
```

---

#### 3.1.3.29 S3 as Pipeline Source

Amazon S3 can provide:
- versioned object source to CodePipeline.

Example:

```text
application.zip
→ versioned S3 object
→ CodePipeline source
```

Again:

```text
S3
≠ Git repository
```

It is:
- an object store that can act as a pipeline source.

---

#### 3.1.3.30 Traceability

A mature deployment should answer:

```text
Which commit is running?
Which pipeline execution processed it?
Which build created the artifact?
Which artifact/image version was deployed?
Which environment/configuration was applied?
```

Traceability chain:

```text
commit
→ pipeline
→ build
→ artifact
→ deployment
```

The repository revision is:
- the source identity at the beginning.

---

#### 3.1.3.31 Git Revert vs Deployment Rollback

Git revert:

```text
creates a new source state
```

Deployment rollback:

```text
restores/redirects to a previously deployed artifact/version
```

These are:
- not necessarily the same operation.

If an earlier tested artifact still exists:
- deployment rollback can use it without rebuilding source.

Detailed rollback strategies:
- later Domain 3 skills.

---

#### 3.1.3.32 Pull Requests and Protected Branches

Repositories may enforce:
- pull/merge requests,
- required reviews,
- status checks,
- branch restrictions.

These support:
- controlled source changes,
- deployment quality.

But:
- provider-specific Git governance is not the primary exam depth for this skill.

Know the role:
- protect important deployment-driving source references.

---

#### 3.1.3.33 Cross-Account Context

Repository/source can exist:
- in one account/context,

while deployment targets exist:
- in other AWS accounts.

Concept:

```text
central source / pipeline account
→ deployment roles
→ dev / test / prod accounts
```

Repository location does not imply:
- runtime must be in the same AWS account.

Cross-account deployment mechanics are:
- broader than 3.1.3.

#### 3.1.3.34 Failure Pattern Summary

| Symptom | First check |
|---|---|
| Pipeline builds wrong source | configured branch/tag/revision |
| GitHub/GitLab source unavailable | CodeConnections status, provider authorization, IAM |
| `git describe` fails in CodeBuild | source snapshot lacks Git metadata; consider Full clone |
| Secret found in repository history | rotate/revoke + remediate history |
| Pipeline triggered by A but build creates B | build is re-cloning moving branch instead of supplied revision |
| Build succeeds but wrong artifact deployed | verify commit → build → artifact → deployment chain |
| Runtime tries to clone repository | deployment model is wrong; deploy built artifact |
| Need npm/Maven/Python package | CodeArtifact, not source Git |
| Need container image | ECR, not source Git |

#### 3.1.3.36 Common Exam Traps

##### "CodeArtifact is a Git repository"
- False.
- It stores software packages.

##### "ECR stores application source history"
- False.
- It stores container images.

##### "S3 source means S3 is Git"
- False.

##### "Pipeline source artifact is the final deployment artifact"
- Not necessarily.
- Build stages can transform it.

##### "Branch is immutable"
- False.
- It is a movable reference.

##### "Removing a secret in a later commit removes exposure"
- False.

##### "Lambda/runtime should clone the Git repository"
- Normally wrong.

##### "Every environment needs its own repository"
- False.

##### "Full clone is always better"
- False.
- Use it when Git metadata is actually required.

##### "GitHub OAuth is the preferred current CodePipeline integration"
- No.
- Current source guidance favors CodeConnections/GitHub App integration.

##### "Repository commit trigger belongs entirely to 3.1.3"
- No.
- 3.1.3 establishes repository/source identity; 3.4.6 covers commit-triggered CI/CD behavior in depth.

#### 3.1.3.39 Exam-Level Knowledge Frame

Know these cold.

**Git repository**  
→ source + version history.

**Commit**  
→ identifiable source revision.

**Branch**  
→ movable source reference.

**Tag**  
→ named reference to a commit.

**CodeCommit**  
→ AWS-managed Git-compatible repository.

**CodeConnections**  
→ connects supported external Git providers to AWS developer services.

**CodePipeline source action**  
→ turns a selected source revision/change into pipeline input.

**CodeBuild**  
→ can consume repository source directly or through CodePipeline.

**Full clone**  
→ preserves Git metadata for downstream CodeBuild when required.

**CodeArtifact**  
→ software-package repository, not source Git.

**ECR**  
→ container-image repository, not source Git.

**S3**  
→ object store that can act as pipeline source, not Git.

**Traceability**  
→ commit → build → artifact → deployment.

Fastest exam discriminator:

```text
AWS-managed Git?
→ CodeCommit

GitHub/GitLab/Bitbucket into AWS pipeline?
→ CodeConnections

need Git history/tags in CodeBuild?
→ Full clone

need package repository?
→ CodeArtifact

need container image repository?
→ ECR

need source files only?
→ normal source snapshot

need exact source identity?
→ commit/revision

runtime wants latest Git source?
→ wrong model; build and deploy artifact
```

Final principle:

**Treat the code repository as the versioned source of a deployment, not as the deployment itself. Select an identifiable revision, let the build process transform that revision into an immutable artifact, and preserve traceability from commit through build and artifact to the deployed version.**
