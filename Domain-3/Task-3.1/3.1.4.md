### 3.1.4 Apply application requirements for resources

#### 3.1.4.1 Exam and Task Context

##### 3.1.4.1.1 Domain and Task
- **Domain 3:** Deployment.
- **Task 3.1:** Prepare application artifacts to be deployed to AWS.
- **Skill 3.1.4:** **Apply application requirements for resources (for example, memory, cores).**

Core question:

**What compute, memory, storage, and scaling resources does the workload require, and how are those requirements expressed by the selected AWS compute service?**

---

#### 3.1.4.2 Core Mental Model

```text
APPLICATION CHARACTERISTICS
        |
        v

        |
        +--> CPU
        +--> memory
        +--> storage / temporary storage
        +--> network / I/O
        +--> concurrency / throughput

        |
```

Goal:

```text
sufficient resources
+

+

```

not:

```text
largest possible configuration
```

---

#### 3.1.4.3 Resource Dimensions

Applications can be constrained by:
- CPU,
- memory,
- network throughput,
- disk/storage,
- temporary storage,
- concurrency,
- execution duration.

The exam wording names:
- memory,
- cores

as examples,
not:
- an exhaustive list.

---

#### 3.1.4.4 CPU-, Memory-, and I/O-Bound Workloads

##### CPU-Bound
Examples:
- compression,
- encryption,
- image processing,
- calculation,
- transformation.

Typical signs:
- high CPU utilization,
- sufficient memory,
- duration improves with more CPU.

##### Memory-Bound
Examples:
- large in-memory datasets,
- JVM heap,
- caching,
- large libraries.

Typical signs:
- high memory use,
- garbage collection pressure,
- out-of-memory failures.

##### I/O-Bound
Examples:
- database calls,
- S3 access,
- external APIs,
- network waits.

Important:

```text
more CPU
≠ automatic fix for remote latency
```

First determine:
- where time/resources are actually consumed.

---

#### 3.1.4.5 Vertical vs Horizontal Scaling

Two different questions:

```text
How much resource does one execution unit need?
→ vertical sizing

How many execution units are required?
→ horizontal scaling
```

Examples:

```text
one request needs 3 GB memory
→ increase memory per execution unit

traffic doubled but each task is healthy
→ increase task/instance count
```

Critical rule:

```text
horizontal scaling
cannot fix
a per-request resource requirement
```

---

#### 3.1.4.6 AWS Lambda Resource Model

For standard Lambda functions, the main resource control is:

```text
MemorySize
```

Current source values:

```text
128 MB → 10,240 MB
```

in:
- 1 MB increments.

Critical AWS behavior:

```text
Lambda CPU
→ allocated proportionally to configured memory
```

At approximately:

```text
1,769 MB
→ 1 vCPU equivalent
```

Therefore:

```text
need more Lambda CPU?
→ increase MemorySize and benchmark
```

Lambda CPU is not normally configured as:

```text
CPU = 2
```

independently.

---

#### 3.1.4.7 Lambda Memory and Cost

Increasing Lambda memory gives:
- more memory,
- more proportional CPU.

Potential result:

```text
higher MemorySize
→ shorter duration
```

Therefore:

```text
more memory
≠ automatically higher total cost
```

because execution can finish faster.

Optimize:
- performance and cost together.

---

#### 3.1.4.8 Lambda Right-Sizing

Measure:
- duration,
- memory use,
- errors,
- timeout behavior,
- representative workload performance.

Possible pattern:

```text
CPU-heavy function
+
memory available
+
long duration
→ test larger MemorySize
```

For empirical comparison:
- AWS Lambda Power Tuning can test multiple memory configurations and compare duration/cost.

Detailed optimization:
- belongs primarily to Domain 4.

---

#### 3.1.4.9 Lambda Timeout Is Separate

Lambda timeout controls:

```text
maximum execution duration
```

Current maximum:

```text
900 seconds / 15 minutes
```

Distinction:

```text
increase MemorySize
→ more memory + CPU

increase timeout
→ function is allowed to run longer
```

Therefore:

```text
CPU bottleneck
→ do not solve by blindly increasing timeout
```

---

#### 3.1.4.10 Lambda Ephemeral Storage Is Separate

Lambda temporary storage:

```text
/tmp
```

is a separate resource dimension.

Use more ephemeral storage when:
- workload needs larger temporary files,
- intermediate artifacts exceed default temporary capacity.

Do not assume:

```text
temporary disk requirement
→ increase MemorySize
```

---

#### 3.1.4.11 Lambda Architecture

Lambda supports architectures including:
- `x86_64`,
- `arm64`.

Architecture affects:
- binary compatibility,
- native dependencies,
- performance/cost characteristics.

Connection to 3.1.1:

```text
artifact architecture
must match
runtime architecture
```

---

#### 3.1.4.12 Lambda Concurrency Is Not Per-Invocation CPU

Concurrency:

```text
how many executions run simultaneously
```

Memory/CPU sizing:

```text
resources available to each execution
```

Example:

```text
one invocation is CPU-bound
→ increase memory may help

many requests arrive simultaneously
→ concurrency/scaling matters
```

Do not solve:
- every throughput problem

with:
- more memory per invocation.

---

#### 3.1.4.13 Reserved vs Provisioned Concurrency

Reserved concurrency:
- reserves function concurrency,
- also caps maximum function concurrency.

Use for:
- workload isolation,
- downstream protection.

Provisioned concurrency:
- pre-initializes execution environments.

Use primarily for:
- lower startup/cold-start latency.

Distinction:

```text
slow computation
→ CPU/memory sizing

cold-start latency
→ provisioned concurrency may help
```

Provisioned concurrency:
- does not give each invocation more CPU.

Detailed concurrency:
- 4.3.1.

---

#### 3.1.4.14 Amazon ECS Resource Model

ECS resource requirements are expressed in:
- task definitions.

Important dimensions:
- task CPU,
- task memory,
- container CPU,
- container memory,
- memory reservation.

Concept:

```text
task-level resources
→ total resources available to task

container-level settings
→ allocation/limits among containers
```

---

#### 3.1.4.15 ECS on AWS Fargate

Fargate requires:
- supported task CPU/memory combinations.

You cannot choose:
- arbitrary pairs.

Key conversion:

```text
1024 CPU units = 1 vCPU
```

Examples:

```text
256  → 0.25 vCPU
512  → 0.5 vCPU
1024 → 1 vCPU
2048 → 2 vCPU
```

Exam principle:

```text
Fargate CPU + memory
→ must form a documented valid combination
```

---

#### 3.1.4.16 Fargate CPU/Memory Pairing

Representative source combinations:

```text
256 CPU
→ 512 MiB / 1 GB / 2 GB

512 CPU
→ 1–4 GB

1024 CPU
→ 2–8 GB

2048 CPU
→ 4–16 GB

4096 CPU
→ 8–30 GB
```

Larger supported combinations also exist.

Do not memorize every pair mechanically.

Know the rule:

```text
invalid pair
→ task-definition/deployment failure
```

---

#### 3.1.4.17 ECS Task vs Container Resources

Example:

```text
Task
CPU: 1024
Memory: 2048

├── app container
└── sidecar container
```

Both containers:
- consume task resources.

Container-level controls can define:
- CPU allocation behavior,
- memory reservation,
- memory hard limit.

---

#### 3.1.4.18 ECS Memory Reservation vs Hard Limit

Container:

```text
memoryReservation
→ soft reservation
```

```text
memory
→ hard limit
```

If the container exceeds:
- the hard memory limit,

it can:
- be terminated.

Exam distinction:

```text
soft reservation
≠ hard maximum
```

---

#### 3.1.4.19 ECS on EC2 vs Fargate

Fargate:

```text
AWS manages underlying compute
→ choose supported task CPU/memory
```

ECS on EC2:

```text
tasks run on cluster EC2 instances
→ cluster must have enough remaining capacity
```

Example:

```text
task needs 4 GB
+
no cluster instance has enough free memory
→ task cannot be placed
```

---

#### 3.1.4.20 Task Size vs Task Count

Task size:

```text
CPU/memory per task
```

Task count:

```text
number of running tasks
```

If:
- individual tasks are healthy,
- service is overloaded because of request volume,

then:

```text
increase task count
```

may be appropriate.

If:
- one request itself needs more CPU/memory,

then:

```text
increase per-task resources
```

may be required.

---

#### 3.1.4.21 ECS Service Auto Scaling

Application Auto Scaling can adjust:
- ECS desired task count

using metrics such as:
- CPU utilization,
- memory utilization.

Model:

```text
task definition
→ resources per task

service scaling
→ number of tasks
```

Do not confuse:
- vertical sizing

with:
- horizontal scaling.

---

#### 3.1.4.22 Amazon EC2 Resource Model

EC2 instance type defines characteristics such as:
- vCPU,
- memory,
- network performance,
- storage capabilities.

Conceptual instance families:

```text
general purpose
→ balanced

compute optimized
→ CPU-heavy

memory optimized
→ memory-heavy

storage optimized
→ storage/IO-heavy
```

Use workload characteristics to select:
- an appropriate instance family/size.

---

#### 3.1.4.23 EC2 Vertical vs Horizontal Scaling

Vertical:

```text
larger/smaller instance type
```

Horizontal:

```text
more/fewer instances
```

Typical horizontal mechanism:
- Auto Scaling group.

Again:

```text
instance size
≠ instance count
```

---

#### 3.1.4.24 Managed Compute Still Requires Sizing

Services such as:
- Lambda,
- Fargate,
- App Runner,
- Elastic Beanstalk

abstract infrastructure,
but do not eliminate:
- resource decisions.

Examples:

```text
Lambda
→ memory / timeout / ephemeral storage / concurrency controls

Fargate
→ task CPU / memory

App Runner
→ CPU / memory

Elastic Beanstalk
→ instance type / environment capacity
```

Principle:

```text
managed compute
≠ resource-free compute
```

---

#### 3.1.4.25 CodeBuild Resource Requirements

Build infrastructure can also be resource constrained.

CodeBuild compute provides:
- CPU,
- memory,
- disk.

Examples of heavy builds:
- Java compilation,
- container builds,
- memory-intensive tests.

If:

```text
CodeBuild OOM
```

correct direction:

```text
increase CodeBuild compute
```

not:

```text
increase production Lambda memory
```

Always identify:

```text
which execution environment is constrained?
```

---

#### 3.1.4.26 Build Resources vs Runtime Resources

Important distinction:

```text
CodeBuild resources
→ build/test/package workload

Lambda/ECS/EC2 resources
→ application runtime workload
```

These:
- can require different resource sizes.

A build can need:
- more memory than runtime,

or:
- less.

---

#### 3.1.4.27 Infrastructure as Code

Resource requirements should preferably be:
- versioned,
- repeatable,
- reviewable.

Example SAM:

```yaml
MemorySize: 1024
Timeout: 30
```

Example ECS:

```text
cpu: 1024
memory: 2048
```

SAM `Globals` can provide shared Lambda defaults:

```yaml
Globals:
  Function:
    MemorySize: 1024
    Timeout: 30
```

Individual functions can:
- override when workloads differ.

---

#### 3.1.4.28 Do Not Size Every Component Identically

Different workloads need:
- different resource allocations.

Example:

```text
router
→ lightweight

image processor
→ CPU/memory intensive

report generator
→ memory intensive
```

Shared defaults can improve consistency,
but:

```text
one size
≠ correct for every function/task
```

---

#### 3.1.4.29 Measure and Right-Size

Use a feedback loop:

```text
configure
→ deploy
→ generate representative load
→ observe
→ compare latency/errors/utilization/cost
→ adjust
```

Supporting CloudWatch evidence can include:
- Lambda duration/errors,
- ECS CPU utilization,
- ECS memory utilization,
- EC2 CPU utilization.

Resource sizing is:
- empirical.

---

#### 3.1.4.30 Interpret CPU and Memory Signals

High CPU:
- may indicate CPU pressure,
- or aggregate demand.

Possible response:
- more CPU per unit,
- more execution units,
- code optimization.

High memory:
- may indicate memory pressure,
- large working set,
- leak,
- cache pressure.

Possible response:
- more memory,
- reduce memory footprint,
- fix leak,
- scale when workload can distribute.

Correct answer depends on:

```text
per-unit bottleneck
vs
aggregate load
```

---

#### 3.1.4.31 Out-of-Memory and Timeout Failures

##### OOM
If process/container exceeds memory:

```text
correct resource dimension
→ memory
```

Possible response:
- increase memory,
- reduce memory usage.

##### Timeout
Timeout can result from:
- insufficient compute,
- downstream latency,
- inefficient code,
- timeout configured too low.

Do not automatically:

```text
timeout failure
→ increase timeout
```

First identify:
- why execution is slow.

---

#### 3.1.4.32 Cost Principle

Over-provisioning:

```text
unused capacity
→ unnecessary cost
```

Under-provisioning:

```text
latency
errors
OOM
throttling
poor throughput
```

Target:

```text
smallest resource configuration
that reliably satisfies
workload and service-level requirements
```

---

#### 3.1.4.33 Environment-Specific Resource Configuration

Resource settings can legitimately differ by environment.

Example:

```text
development
→ fewer ECS tasks

production
→ larger desired count
```

But differences should be based on:
- expected workload,
- reliability requirements,
not:
- arbitrary environment naming.

Detailed environment-specific settings:
- 3.1.5.

---

#### 3.1.4.34 Architecture Compatibility

Resource selection must remain compatible with:
- deployed artifact architecture,
- native dependencies.

Example:

```text
ARM64 binary
→ ARM64-compatible runtime
```

Connection:

```text
3.1.1
→ dependency/runtime compatibility

3.1.4
→ compute/resource selection
```

#### 3.1.4.35 Failure Pattern Summary

| Symptom | Correct direction |
|---|---|
| Lambda CPU-bound, memory available | increase `MemorySize` and benchmark |
| Lambda out of memory | increase memory or reduce memory use |
| Lambda needs larger temporary files | increase ephemeral storage |
| Lambda cold-start latency | consider provisioned concurrency |
| Fargate task rejected for CPU/memory | choose valid documented pair |
| ECS container killed for memory | increase hard limit / reduce usage |
| ECS/EC2 task cannot be placed | add cluster capacity or reduce valid requirements |
| Healthy ECS tasks but service overloaded | scale task count |
| One request needs more compute | increase per-task/per-function resources |
| CodeBuild OOM | increase CodeBuild compute |
| Timeout occurs | identify CPU/code/dependency/timeout cause before changing setting |

#### 3.1.4.37 Common Exam Traps

##### "Lambda CPU is configured independently"
- False.
- CPU scales proportionally with memory.

##### "More Lambda memory always costs more overall"
- False as an absolute statement.
- Shorter execution may offset higher per-duration allocation.

##### "Increase timeout to fix CPU bottleneck"
- Wrong.
- Timeout adds time, not compute.

##### "Lambda temporary storage is the same as memory"
- False.

##### "Provisioned concurrency gives more CPU"
- False.
- It primarily reduces startup latency.

##### "Any Fargate CPU/memory pair works"
- False.

##### "Horizontal scaling solves per-request memory requirement"
- False.

##### "Task count and task size are the same"
- False.

##### "Serverless means no resource configuration"
- False.

##### "CodeBuild compute determines runtime size"
- False.

##### "More CPU always fixes I/O-bound latency"
- False.

#### 3.1.4.40 Exam-Level Knowledge Frame

Know these cold.

**Lambda memory**  
→ `128 MB–10,240 MB`.

**Lambda CPU**  
→ proportional to configured memory.

**1,769 MB Lambda**  
→ approximately one vCPU equivalent according to AWS.

**Lambda timeout**  
→ separate from CPU/memory.

**Lambda ephemeral storage**  
→ separate from memory.

**Lambda concurrency**  
→ simultaneous execution capacity, not per-invocation CPU.

**Fargate**  
→ requires supported task CPU/memory combinations.

**1024 ECS CPU units**  
→ `1 vCPU`.

**ECS task resources**  
→ overall task capacity.

**Container resources**  
→ allocation/limits inside the task.

**Vertical scaling**  
→ more resources per execution unit.

**Horizontal scaling**  
→ more execution units.

**CodeBuild compute**  
→ build resources, not application runtime resources.

**CloudWatch**  
→ measurement feedback for right-sizing.

Fastest exam discriminator:

```text
Lambda CPU bottleneck?
→ increase memory and measure

Lambda needs temporary disk?
→ ephemeral storage

cold-start problem?
→ provisioned concurrency

Fargate CPU/memory rejected?
→ valid supported combination

healthy ECS tasks but service overloaded?
→ more tasks

single request needs more resources?
→ larger execution unit

build OOM?
→ CodeBuild compute

timeout?
→ identify actual bottleneck first
```

Final principle:

**Translate workload characteristics into the resource controls of the selected AWS compute service. Keep per-execution sizing separate from horizontal scaling, distinguish runtime resources from build resources, express the configuration reproducibly, and validate the deployed workload before right-sizing for reliability, performance, and cost.**
