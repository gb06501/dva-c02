### 3.3.3 Create application environments that use approved versions for integration testing

#### 3.3.3.1 Exam and Task Context

##### 3.3.3.1.1 Domain
- **Domain 3:** Deployment
##### 3.3.3.1.2 Task
- **Task 3.3:** Automate deployment testing.
##### 3.3.3.1.3 Skill
- **Skill 3.3.3:** **Create application environments that use approved versions for integration testing.**
- The exam guide explicitly gives these examples:
  - **Lambda aliases**
  - **container image tags**
  - **AWS Amplify branches**
  - **AWS Copilot environments**

This skill is fundamentally about **version identity and environment stability**.

The central question is:

**How do you make an integration-test environment point to a known, approved application version instead of a moving development target?**

#### 3.3.3.2 Core Mental Model

`candidate build/version`
→ `approve`
→ `bind environment to approved version`
→ `run integration tests`
→ `promote or reject`

The key principle is:

**Integration testing should run against a known version, not an ambiguous moving target.**

#### 3.3.3.3 Why "Approved Version" Matters

Suppose a test environment points to:
- Lambda `$LATEST`,
- container tag `latest`,
- an actively changing Git branch without deployment controls.

Then during a test run:
→ the underlying code can change.

That creates ambiguity:

`test passed against which version?`

The skill therefore focuses on:
→ **stable references to specific deployable versions**.

#### 3.3.3.4 Version Identity vs Environment Identity

**Version identity**
→ which code/artifact is deployed?

Examples:
- Lambda version `42`
- ECR image digest/tag
- Git commit/Amplify branch deployment
- Copilot workload/environment deployment state

**Environment identity**
→ where is it deployed?

Examples:
- integration
- staging
- test
- prod

A stable integration environment needs:
→ both.

#### 3.3.3.5 Approved Version

"Approved" does not necessarily mean:
→ manually signed off by a human.

In exam context it can mean:
- version passed earlier validation,
- pipeline selected it,
- release candidate was accepted,
- environment intentionally points to it.

The important property:
→ **the version is deliberately selected and identifiable.**

#### 3.3.3.6 Anti-Pattern: Moving Target

Weak:

`integration environment → $LATEST`

or:

`integration environment → image:latest`

Potential problem:
→ tests can run against a different code revision than expected.

Better:
→ stable version/alias/tag/digest/branch deployment appropriate to the service.

#### 3.3.3.7 Lambda Versions and Aliases

#### 3.3.3.8 Lambda `$LATEST`

When Lambda code is deployed without publishing a version:
→ code resides in `$LATEST`.

`$LATEST` is mutable.

Deploying code again:
→ overwrites `$LATEST`.

Therefore:

**`$LATEST` is not a strong approved-version boundary.**

#### 3.3.3.9 Published Lambda Version

When you publish a Lambda version:
→ Lambda creates an immutable snapshot of the function code and qualifying configuration.

Example:

`my-function:42`

Once published:
→ the version's code/configuration is immutable.

This makes published versions suitable for:
- beta testing,
- integration testing,
- stable release references.

#### 3.3.3.10 Lambda Version Mental Model

`$LATEST`
→ publish → version 1
→ change → publish → version 2
→ change → publish → version 3

Versions are:
→ immutable snapshots.

`$LATEST`
→ mutable development state.

#### 3.3.3.11 Lambda Alias

A Lambda alias is:
→ a named pointer to a published function version.

Examples:

`dev`
→ version 43

`integration`
→ version 42

`prod`
→ version 40

The alias ARN remains stable while:
→ the target version can be changed deliberately.

#### 3.3.3.12 Why Alias Is Ideal for Integration Testing

Clients/integrations can call:

`function:integration`

rather than:

`function:42`

Then when version 43 becomes approved:

`integration alias`
→ update from 42 to 43.

Integration clients do not need:
→ new function ARN configuration.

This decouples:
- stable environment reference,
from
- changing approved version.

#### 3.3.3.13 Alias Can Point Only to Published Version

An alias:
→ points to a published version.

It cannot point to:
→ another alias.

A weighted alias also uses published versions, not `$LATEST`.

#### 3.3.3.14 Lambda Alias + API Gateway

A useful architecture:

`API Gateway integration stage`
→ Lambda `integration` alias
→ published version 42.

When version 43 is approved:

`integration alias`
→ version 43.

API Gateway integration can remain unchanged if it references:
→ alias ARN.

#### 3.3.3.15 Lambda Alias + Event Sources

AWS documentation states event-source mappings and resource policies can reference an alias ARN.

Benefit:

`event source`
→ alias
→ approved version.

When alias changes:
→ event-source mapping does not need to be rewritten for the new version.

#### 3.3.3.16 Alias and Weighted Routing

A Lambda alias can split traffic between:
→ two published versions.

Example:

`integration`
- 90% → version 42
- 10% → version 43

This is useful for:
- canary-style validation,
- controlled comparison.

But for deterministic integration tests:
→ routing 100% to one approved version is usually clearer.

#### 3.3.3.18 AWS Amplify Branches

#### 3.3.3.19 Branch ≠ Immutable Version

**Amplify branch**
→ environment/deployment lane.

**Git commit**
→ immutable source revision.

The branch normally points to:
→ changing commits over time.

Therefore test traceability should include:
→ branch + commit/deployment identity.

#### 3.3.3.20 Environment Stability

#### 3.3.3.21 Decision Flow

1. **Lambda?**
   → publish version.
   → point stable alias to approved version.

2. **Container?**
   → use unique version tag and/or digest.
   → enable ECR tag immutability where stable tag identity is required.

3. **Amplify Hosting?**
   → use separate branch deployment for integration/test.
   → track deployed commit.

4. **Copilot in exam context?**
   → separate environment with known deployed workload version.
   → remember current end-of-support status.

5. **Need deterministic integration tests?**
   → freeze version target during test execution.

6. **Need same artifact later in production?**
   → promote approved version; do not rebuild unnecessarily.

#### 3.3.3.22 Exam-Level Knowledge Frame

Know these cold:

**Lambda `$LATEST`**
→ mutable development state.

**Published Lambda version**
→ immutable snapshot.

**Lambda alias**
→ named pointer to published version.

**Alias ARN**
→ stable integration target while version changes deliberately.

**Weighted alias**
→ split traffic between two published versions.

**Container tag**
→ human-readable image reference; may be mutable.

**ECR tag immutability**
→ prevents overwriting existing tags.

**Image digest**
→ exact immutable image content identity.

**Amplify branch**
→ separately deployed application environment/lane.

**Branch**
→ moving Git reference, not immutable commit.

**Copilot environment**
→ exam-guide environment abstraction for ECS workloads; current CLI is end-of-support.

**Approved-version integration environment**
→ environment + deliberately selected stable application version.

Fastest discriminator:

`Stable Lambda test target?`
→ published version + alias.

`Exact container image?`
→ digest.

`Human-readable stable image version?`
→ immutable tag.

`Frontend test environment?`
→ Amplify branch.

`ECS environment abstraction in exam guide?`
→ Copilot environment.

`Need same bytes in prod?`
→ promote same approved artifact.

#### 3.3.3.23 Final Principle

**An integration-test environment is only trustworthy if you can identify exactly which application version it is running. Use immutable or deliberately controlled version references—published Lambda versions behind aliases, immutable container tags or digests, known Amplify branch deployments, and environment abstractions—to freeze the test target long enough to validate it and then promote the same approved artifact forward.**

#### 3.3.3.25 Current Official AWS Notes

- Lambda published versions are immutable snapshots; aliases point to versions and can be updated deliberately.
- Lambda aliases can split traffic between two published versions.
- ECR supports immutable tags to prevent an existing tag from being overwritten.
- Amplify Hosting creates independent branch deployments and AWS explicitly describes `develop` as an integration-branch pattern alongside `main`.
- AWS Copilot CLI is still named in the exam guide, but current AWS ECS documentation states that it reached end of support on June 12, 2026.

#### 3.3.3.26 Practical Pattern Summary

| Requirement | Approved-version mechanism |
|---|---|
| Stable Lambda integration target | published version + alias |
| Avoid mutable Lambda code during test | do not target `$LATEST` |
| Stable container identity | immutable tag policy and/or image digest |
| ECS/Fargate release identity | task definition/image revision |
| Amplify validation environment | controlled branch deployment |
| Production should run exact tested bits | promote immutable artifact rather than rebuild |
| Environment changes mid-test | freeze/pin approved revision |
