### 3.3.1 Create application test events

#### 3.3.1.1 Exam and Task Context

##### 3.3.1.1.1 Domain
- **Domain 3:** Deployment

##### 3.3.1.1.2 Task
- **Task 3.3:** Automate deployment testing.

##### 3.3.1.1.3 Skill
- **Skill 3.3.1:** **Create application test events (for example, JSON payloads for testing AWS Lambda, Amazon API Gateway, and AWS SAM resources).**
- This is the first skill in Task 3.3.

The exam guide explicitly identifies:
- JSON test payloads,
- AWS Lambda,
- Amazon API Gateway,
- AWS SAM resources.

The focus is therefore not merely understanding event-driven architecture. It is:

**How do you create reproducible application inputs that can be used to automate tests against serverless application components and resources?**

---

#### 3.3.1.2 Core Mental Model

`known test scenario`
→ `representative event payload`
→ `invoke target`
→ `assert expected behavior`
→ `repeat automatically`

A test event is:

**controlled input representing what the application receives at a particular invocation boundary.**

Examples:

`API Gateway request event`
→ Lambda handler

`S3 event`
→ Lambda handler

`SQS event`
→ Lambda handler

`custom JSON`
→ Lambda handler

The key purpose is:
→ repeatability.

---

#### 3.3.1.3 Why Test Events Matter for Automation

Manual testing:

`developer enters test input`
→ invokes function
→ visually checks output.

Automated testing:

`stored/generated event`
→ automated invocation
→ automated assertion
→ pass/fail.

Therefore a test event should ideally be:
- deterministic,
- reproducible,
- representative,
- version-controlled where appropriate,
- safe for the target environment.

---

#### 3.3.1.4 Test Event vs Real Event Source

This distinction carries directly from 3.2.5.

**Test event payload**
→ represents the event delivered to the application.

**Real integration event**
→ originates from the actual AWS service.

Example:

`SQS-shaped JSON → Lambda`
tests:
→ Lambda's handling of an SQS event.

`SendMessage → SQS → event source mapping → Lambda`
tests:
→ actual SQS/Lambda integration.

3.3.1 focuses primarily on:
→ creating the first kind of reusable test input.

Do not confuse:
**event simulation**
with
**integration validation**.

---

#### 3.3.1.5 JSON as the Common Test-Event Format

Lambda event inputs are JSON-compatible data structures.

Typical test event:

```json
{
  "orderId": "test-123",
  "action": "CREATE"
}
```

Lambda receives:
→ the event object.

For AWS-service integrations, the JSON structure should represent:
→ the event schema produced by that service/integration.

---

#### 3.3.1.6 Custom Lambda Test Event

For a directly invoked function:

```json
{
  "customerId": "C123",
  "amount": 42
}
```

Use when:
→ the function contract itself expects custom JSON.

This is different from:
→ a service-generated event envelope such as SQS or API Gateway.

---

#### 3.3.1.7 Service Event Envelopes

AWS services often wrap application data inside:
→ service-specific event structures.

Example conceptual SQS structure:

```json
{
  "Records": [
    {
      "body": "{\"orderId\":\"123\"}"
    }
  ]
}
```

The application payload is:
→ inside `body`.

Therefore:

**business payload ≠ complete Lambda event**

when Lambda is triggered by an AWS service.

---

#### 3.3.1.8 Why Exact Event Shape Matters

A Lambda handler may depend on:
- `Records`,
- `body`,
- headers,
- query parameters,
- path parameters,
- event metadata,
- source ARN,
- request context.

A test event that omits relevant structure can:
→ exercise an unrealistic code path.

Exam principle:

**Create the payload for the invocation boundary being tested.**

---

#### 3.3.1.9 API Gateway Proxy Event

For Lambda proxy integration, API Gateway sends an event containing request information such as:
- HTTP method,
- path,
- headers,
- query parameters,
- path parameters,
- request context,
- body.

The exact event shape differs between:
- REST API payload formats,
- HTTP API payload versions.

Therefore:
→ use the event format corresponding to the configured API.

---

#### 3.3.1.10 API Gateway REST API vs HTTP API Event

Do not assume all API Gateway Lambda events are identical.

Important distinction:

**REST API / payload format 1.0 style**
and
**HTTP API payload format 2.0 style**

can expose different JSON structures.

A test event should match:
→ the integration's actual payload format.

---

#### 3.3.1.11 SQS Body Is Usually a String

Important:

SQS message body is represented in the Lambda event as:
→ a string.

If business message is JSON:

```json
{
  "orderId": "123"
}
```

the SQS event conceptually contains:

```json
{
  "body": "{\"orderId\":\"123\"}"
}
```

The consumer may therefore need:
1. read `body`,
2. parse JSON.

Exam trap:
→ putting business fields directly beside SQS record metadata may not represent the real event.

---

#### 3.3.1.12 SQS Batch Event

Lambda can receive multiple SQS records in one invocation.

Therefore include test scenarios for:

```text
Records[0]
Records[1]
Records[2]
...
```

Do not create only:
→ single-record events

if the handler is expected to process batches.

---

#### 3.3.1.13 AWS SAM `generate-event`

AWS SAM CLI provides:

`sam local generate-event`

Purpose:
→ generate sample event payloads for supported AWS services.

This avoids manually reconstructing:
→ complex AWS event envelopes.

Mental model:

`AWS service/event type`
→ `sam local generate-event`
→ representative JSON
→ customize
→ save/use in test.

---

#### 3.3.1.14 Discover Supported SAM Events

The CLI can expose:
→ supported services and event types.

Exam-level knowledge:
→ you do not need to memorize every generated event subtype.

Know the purpose:

**Generate representative AWS service event payloads for local testing.**

---

#### 3.3.1.15 Generate an Event to a File

Conceptual workflow:

```text
sam local generate-event ...
→ event.json
```

Then:

```text
sam local invoke Function --event event.json
```

This creates a repeatable local test.

---

#### 3.3.1.16 Customize Generated Events

Generated events are:
→ starting points.

Modify fields to match test scenario:
- bucket name,
- object key,
- queue message,
- API path,
- business payload,
- event type.

Do not assume:
→ generated default values match your application contract.

---

#### 3.3.1.17 `sam local invoke`

`sam local invoke`
→ runs a Lambda function locally.

With:

`--event event.json`

it supplies:
→ the test event to the function.

Mental model:

`stored JSON`
→ local Lambda runtime
→ function result/logs.

This is a core local automated-test building block.

---

#### 3.3.1.18 stdin / Piped Event Generation

SAM CLI workflows can conceptually combine:

`generate event`
→ pipe into
`local invoke`.

This is useful for:
→ quick tests without permanently storing the event.

For reusable automated suites:
→ version-controlled test fixtures are often clearer.

---

#### 3.3.1.19 Lambda Console Test Events

AWS Lambda console allows developers to:
→ create and save test events.

These events invoke the function with:
→ the specified JSON.

Useful for:
- interactive development,
- reproducing scenarios,
- quick manual verification.

But Task 3.3 emphasizes:
→ automation.

Therefore console events are useful context, while file/generated events and automated invocations are more central.

---

#### 3.3.1.20 Private vs Shareable Lambda Test Events

Lambda supports saved test events associated with development workflows.

AWS SAM provides remote test-event capabilities for:
→ shareable test events.

This enables a team to:
→ reuse known event scenarios.

---

#### 3.3.1.21 `sam remote test-event`

AWS SAM CLI provides:

`sam remote test-event`

for managing shareable test events associated with deployed Lambda functions.

Conceptually:

`known cloud test event`
→ list/fetch/put/delete
→ reuse in team testing.

This is distinct from:
→ generating a generic service sample event.

---

#### 3.3.1.22 `generate-event` vs `remote test-event`

**`sam local generate-event`**
→ generate generic/sample AWS service event payload.

**`sam remote test-event`**
→ manage reusable test events associated with deployed Lambda testing.

Do not confuse them.

---

#### 3.3.1.23 `sam remote invoke`

`sam remote invoke`
→ invokes supported deployed AWS resources from SAM CLI.

For Lambda:

`test event`
→ remote invoke
→ deployed function.

This allows:
→ similar test inputs to be exercised against actual deployed code.

But direct remote invocation still bypasses:
→ upstream event-source integration.

---

#### 3.3.1.24 Local → Remote Testing Progression

Strong development pattern:

`event fixture`
→ local invoke
→ handler works

then:

`same/representative event`
→ remote invoke
→ deployed function works

then, where integration matters:

`real AWS source`
→ consumer
→ full path works.

Three different confidence levels.

---

#### 3.3.1.25 Event Versioning

Event-driven systems evolve.

If event contract has versions:

`OrderCreated v1`
`OrderCreated v2`

store/test:
→ representative events for versions the consumer supports.

This protects:
→ backward compatibility expectations.

---

#### 3.3.1.26 Schema Validation

If the application uses explicit event schemas:
→ test events should conform to valid schema for positive cases.

Negative cases can intentionally violate:
→ selected schema rules.

The exam skill itself does not require a specific schema-registry technology.

---

#### 3.3.1.27 CloudFormation/SAM Parameters and Test Events

Environment-specific values should not necessarily be hard-coded into fixtures.

Example:
→ development queue ARN changes between stacks.

Test runner can inject:
- resource identifiers,
- unique IDs,
- endpoint values

at runtime.

Keep fixture:
→ reusable where possible.

---

#### 3.3.1.28 Exam-Level Knowledge Frame

Know these cold:

**Test event**
→ reproducible input supplied to application/component.

**Service event envelope**
→ AWS-service-specific JSON surrounding business payload.

**`sam local generate-event`**
→ generate representative AWS service sample event.

**`sam local invoke --event`**
→ locally invoke Lambda with supplied event.

**API Gateway event**
→ includes HTTP request context; exact structure depends on API/payload format.

**SQS event**
→ `Records` array; body is a string.

**SNS event**
→ SNS envelope; Message can contain stringified business JSON.

**S3 event**
→ bucket/object notification metadata.

**DynamoDB Streams event**
→ records with DynamoDB AttributeValue representations.

**Kinesis event**
→ record data Base64 encoded.

**EventBridge event**
→ envelope with source/detail-type/detail.

**Direct test event**
≠ real source integration test.

Fastest discriminator:

`Need AWS sample event?`
→ `sam local generate-event`.

`Need local Lambda test with JSON?`
→ `sam local invoke --event`.

`Need SQS Lambda fixture?`
→ `Records[]` + string `body`.

`Need Kinesis fixture?`
→ Base64 record data.

`Need DynamoDB Streams fixture?`
→ AttributeValue structure.

`Need API Gateway fixture?`
→ correct REST/HTTP API payload format.

`Need routing/trigger proof?`
→ real AWS source, not direct test event.

---

#### 3.3.1.29 Final Principle

**Create test events at the application's real invocation boundary. Preserve the AWS service envelope, encoding, batching, and payload format that the consumer actually receives; store or generate representative positive and negative scenarios; then use those events as deterministic inputs for automated tests. A test event validates application handling of an event contract—it does not by itself validate the upstream AWS integration that produces that event.**

#### 3.3.1.31 Practical Pattern Summary

| Requirement | Test-event approach |
|---|---|
| Need representative AWS service event | `sam local generate-event` |
| Reuse deterministic regression input | version-controlled sanitized fixture |
| Test malformed/boundary input | negative/boundary fixture |
| Need local Lambda execution | `sam local invoke --event` |
| Need deployed Lambda execution | `sam remote invoke` |
| Need real routing/trigger proof | invoke actual AWS event source |
| Event contains batch | preserve real service envelope/batch shape |
| Fixture would contain secret/PII | sanitize or inject secure runtime value |
