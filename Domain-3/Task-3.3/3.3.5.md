### 3.3.5 Manage environments in individual AWS services

#### 3.3.5.1 Exam and Task Context

##### 3.3.5.1.1 Domain
- **Domain 3:** Deployment
##### 3.3.5.1.2 Task
- **Task 3.3:** Automate deployment testing.
##### 3.3.5.1.3 Skill
- **Skill 3.3.5:** **Manage environments in individual AWS services.**
- The exam guide explicitly gives:
  - **differentiating between development, test, and production in Amazon API Gateway**

The wording is important.

This is not simply:

`create three AWS accounts called dev/test/prod`

Instead, AWS services often provide their own mechanisms for representing:
→ environments, stages, aliases, branches, versions, or deployment targets.

The exam skill asks you to recognize and use:
→ **the environment abstraction appropriate to the AWS service.**

---

#### 3.3.5.2 Core Mental Model

`application lifecycle environment`
→ map it onto
`service-specific environment mechanism`

Examples:

```text
API Gateway
dev / test / prod
→ stages

Lambda
dev / test / prod
→ aliases pointing to published versions

Amplify
dev / test / prod
→ branch deployments

ECS
dev / test / prod
→ separate services/stacks/environment-specific deployments

AppConfig
dev / test / prod
→ environments

CloudFormation / SAM
dev / test / prod
→ separate stacks + parameters/configuration
```

The exact mechanism:
→ depends on the service.

---

#### 3.3.5.3 Why AWS Services Have Different Environment Models

There is no universal AWS object named:

`Environment`

that all services use.

Instead:

`API Gateway`
→ Stage.

`Lambda`
→ Alias/version combination.

`Amplify`
→ Branch deployment.

`AppConfig`
→ explicit Environment resource.

`CloudFormation`
→ typically separate stacks/parameters.

Therefore exam questions often ask indirectly:

**Which service feature should distinguish dev/test/prod?**

---

#### 3.3.5.4 Environment Is a Logical Concept

`development`
`test`
`production`

are:
→ lifecycle concepts.

AWS implements those concepts through:
→ service-specific constructs.

Important:

**Environment name alone does not create isolation.**

Calling something:
`prod`

does not automatically give it:
- separate IAM,
- separate data,
- separate network,
- separate account,
- stronger protection.

Those must be designed explicitly.

---

#### 3.3.5.5 API Gateway: Primary Exam Example

The exam guide explicitly uses API Gateway:

**differentiate between development, test, and production in API Gateway.**

The primary mechanism is:
→ **stages**.

Example:

```text
Orders API
├── dev
├── test
└── prod
```

Each stage represents:
→ a deployed API lifecycle environment.

---

#### 3.3.5.6 API Gateway REST API Deployment Model

For REST APIs:

`API configuration`
→ `deployment`
→ `stage`.

A deployment is:
→ snapshot of API configuration.

A stage is:
→ named reference to a deployment.

Example:

`dev`
→ deployment 17.

`test`
→ deployment 15.

`prod`
→ deployment 12.

Thus environments can:
→ intentionally run different API deployments.

---

#### 3.3.5.7 Stage URL

A REST API stage is normally represented in the invoke URL:

```text
https://{api-id}.execute-api.{region}.amazonaws.com/dev
https://{api-id}.execute-api.{region}.amazonaws.com/test
https://{api-id}.execute-api.{region}.amazonaws.com/prod
```

Therefore:

`stage`
→ environment-specific endpoint.

This is especially useful for:
→ automated integration testing.

---

#### 3.3.5.8 API Gateway Stage Variables

REST API stages can define:
→ stage variables.

These are environment-specific key/value configuration.

Example:

```text
dev:
  lambdaAlias = dev

test:
  lambdaAlias = integration

prod:
  lambdaAlias = prod
```

Then API integration can use:
→ stage-specific value.

Mental model:

`same API definition`
+
`different stage configuration`
→ different environment behavior.

---

#### 3.3.5.9 Stage Variable Use Case

Example:

```text
API stage: test
stage variable: lambdaAlias=integration
        |
        v
Lambda alias: integration
        |
        v
Lambda version 42
```

Production:

```text
API stage: prod
stage variable: lambdaAlias=prod
        |
        v
Lambda alias: prod
        |
        v
Lambda version 40
```

This connects:
- 3.3.2 API deployment,
- 3.3.3 approved versions,
- 3.3.5 service environments.

---

#### 3.3.5.10 Stage Variables Are Configuration, Not Secrets

Do not store:
- passwords,
- access keys,
- secret tokens

in API Gateway stage variables.

Use appropriate secret-management mechanisms instead.

Exam discriminator:

`environment-specific backend identifier`
→ stage variable can fit.

`secret`
→ not stage variable.

---

#### 3.3.5.11 API Gateway HTTP API Stages

HTTP APIs also support:
→ stages.

A stage can represent:
- dev,
- test,
- prod.

HTTP API stages can also support:
→ automatic deployment.

This is useful for environments such as:
→ development.

---

#### 3.3.5.12 `$default` Stage

HTTP APIs can use:
→ `$default`.

With `$default`, clients can invoke through:
→ the base API URL without explicit stage path.

Therefore:

**stage exists**
does not always mean:
→ stage name is visible in URL.

---

#### 3.3.5.13 Auto-Deploy and Environment Behavior

Development environment:

`change API`
→ automatically deploy to dev stage.

Test/production:

may use:
→ more controlled deployment workflow.

Exam principle:

**Choose stage deployment behavior based on lifecycle requirements.**

Do not assume:
→ auto-deploy should always be enabled everywhere.

---

#### 3.3.5.14 API Gateway Stage Settings

Stages can carry environment-specific operational configuration such as:
- logging-related settings,
- throttling-related settings,
- caching for REST APIs where applicable,
- tracing/settings depending on API type/configuration,
- stage variables for REST APIs.

Therefore stages are not only:
→ names in URLs.

They can also define:
→ environment-specific runtime behavior.

---

#### 3.3.5.15 API Gateway Canary

REST API stages can use:
→ canary release settings.

Concept:

```text
prod stage
├── 90% → current deployment
└── 10% → candidate deployment
```

This is:
→ release traffic management within an environment.

It is not the same as:
→ a separate test environment.

Keep these separate:

`test stage`
→ environment separation.

`prod canary`
→ release strategy inside production stage.

---

#### 3.3.5.16 Lambda Environment Model

Lambda does not have an API-Gateway-style `Stage` object.

Instead, key mechanisms are:
- `$LATEST`,
- published versions,
- aliases.

For stable lifecycle environments:

```text
alias dev
→ version 44

alias test
→ version 42

alias prod
→ version 40
```

---

#### 3.3.5.17 AWS AppConfig Environment Model

AWS AppConfig explicitly has:
→ **Environment** resources.

An AppConfig application can contain environments such as:
- Development
- Test
- Production.

Configuration profiles are:
→ deployed into environments.

This is a very direct example of:
**service-specific environment management**.

---

#### 3.3.5.18 AppConfig Core Hierarchy

Conceptually:

```text
AppConfig Application
├── Configuration Profile
└── Environments
    ├── Development
    ├── Test
    └── Production
```

A configuration version:
→ is deployed to a target environment.

---

#### 3.3.5.19 AWS Amplify Environment Model

Amplify Hosting commonly maps:
→ Git branches to deployed environments.

Example:

```text
develop
→ integration/development URL

main
→ production URL
```

Feature branches can provide:
→ additional isolated deployments.

Thus:

`branch deployment`
→ Amplify lifecycle environment/lane.

---

#### 3.3.5.20 CloudFormation / SAM Environment Model

CloudFormation does not require:
→ one universal environment object.

Typical model:

```text
orders-dev stack
orders-test stack
orders-prod stack
```

Each stack:
→ separate deployed environment.

Same template can be used with:
→ different parameters.

---

#### 3.3.5.21 Same Template, Separate Stacks

Strong pattern:

```text
template.yaml
+ dev parameters
→ orders-dev

template.yaml
+ test parameters
→ orders-test

template.yaml
+ prod parameters
→ orders-prod
```

Benefits:
- repeatability,
- separation,
- lower drift,
- automated creation/update.

---

#### 3.3.5.22 Environment Boundaries

Service-specific environment mechanisms exist at different abstraction levels.

###### 3.3.5.22.0.1 Lifecycle routing
- API Gateway stage
- Lambda alias
- Amplify branch

###### 3.3.5.22.0.2 Configuration deployment
- AppConfig environment

###### 3.3.5.22.0.3 Infrastructure boundary
- CloudFormation stack
- ECS service/cluster
- separate S3/DynamoDB/SQS/SNS resources

###### 3.3.5.22.0.4 Strong organizational isolation
- AWS account

Do not assume:
→ these are interchangeable.

---

#### 3.3.5.23 Decision Flow

1. **API Gateway environment?**
   → stage.

2. **Lambda stable environment reference?**
   → alias pointing to published version.

3. **AppConfig configuration environment?**
   → AppConfig Environment.

4. **Amplify hosted environment?**
   → branch deployment.

5. **CloudFormation/SAM environment?**
   → separate stack + parameters/configuration.

6. **ECS runtime environment?**
   → separate service/stack/cluster as architecture requires, running selected task/image version.

7. **S3/DynamoDB/SQS/SNS environment?**
   → separate resources/configuration or stronger account boundary.

8. **Need strong organizational isolation?**
   → separate AWS accounts may complement service-specific constructs.

9. **Need exact release identity?**
   → environment mechanism alone is insufficient; pair with approved version/artifact.

10. **Need automated integration testing?**
    → ensure entire dependency chain resolves to non-production environment resources.

#### 3.3.5.25 Exam-Level Knowledge Frame

Know these cold:

**Environment**
→ lifecycle target such as dev/test/prod.

**API Gateway**
→ stages represent API environments.

**API Gateway deployment**
→ API configuration snapshot.

**API Gateway stage**
→ named reference/environment pointing to deployment.

**Stage variable**
→ REST API stage-specific non-secret configuration.

**Lambda**
→ published version = immutable release; alias = stable named pointer/environment reference.

**AppConfig**
→ has explicit Environment resources.

**Amplify**
→ branch deployments can represent lifecycle environments.

**CloudFormation/SAM**
→ separate stacks + parameters commonly represent environments.

**ECR**
→ artifact repository/version identity, not runtime environment.

**CodePipeline stage**
→ pipeline workflow concept, not API Gateway stage.

**AWS account**
→ stronger isolation boundary that can complement service-specific environment mechanisms.

Fastest discriminator:

`API dev/test/prod?`
→ API Gateway stages.

`Lambda dev/test/prod stable names?`
→ aliases.

`Runtime config dev/test/prod?`
→ AppConfig environments/configuration.

`Amplify dev/prod?`
→ branch deployments.

`IaC environments?`
→ separate stacks + parameters.

`Container exact version?`
→ tag/digest, but runtime environment still ECS/service/stack.

`Strong isolation?`
→ separate accounts plus service-specific resources where appropriate.

---

#### 3.3.5.26 Final Principle

**Development, test, and production are lifecycle concepts, but AWS services represent them differently. Use the service-native abstraction where one exists—API Gateway stages, Lambda aliases, AppConfig environments, Amplify branch deployments—and use separate resources/stacks/accounts where a service has no native stage concept. Then ensure the entire dependency chain points to resources belonging to the intended environment. Environment identity tells you where the application runs; approved artifact/version identity tells you exactly what is running there.**

#### 3.3.5.28 Practical Pattern Summary

| Service/context | Environment mechanism |
|---|---|
| API Gateway | stage |
| Lambda | alias/version + environment configuration |
| AppConfig | AppConfig environment |
| CloudFormation/SAM | separate stack + parameters |
| ECS/Fargate | service/task definition + environment config |
| Amplify | branch deployment |
| Separate strong isolation boundary | AWS account |
| Environment-specific secret | Secrets Manager / secure config, not stage variable |
| Promote release | promote artifact/version, not the environment itself |

Core rule:

```text
"environment"
→ logical deployment boundary
→ represented differently by each AWS service
```
