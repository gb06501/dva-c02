### 3.3.6 Use Amazon Q Developer to generate automated tests

#### 3.3.6.1 Exam and Task Context

##### 3.3.6.1.1 Domain
- **Domain 3:** Deployment

##### 3.3.6.1.2 Task
- **Task 3.3:** Automate deployment testing.

##### 3.3.6.1.3 Skill
- **Skill 3.3.6:** **Use Amazon Q Developer to generate automated tests.**

This is the final skill in Task 3.3.

The exam guide is intentionally concise here. It names Amazon Q Developer as the tool and test generation as the capability. The deeper exam context comes from understanding where generated tests fit into the deployment-testing workflow.

The central question is:

**How can Amazon Q Developer accelerate creation of tests while the developer still owns test intent, correctness, and execution?**

---

#### 3.3.6.2 Core Mental Model

```text
application code + developer intent + project context
                |
                v
       Amazon Q Developer
                |
                v
        generated test code
                |
                v
        developer review
                |
                v
        build / execute tests
                |
                v
        pass or fail deployment
```

The important principle is:

**Amazon Q generates test code; it does not replace the test runner, deployment environment, assertions, or developer validation.**

---

#### 3.3.6.3 What Amazon Q Developer Is

Amazon Q Developer is:
→ an AI-powered development assistant.

In the IDE it can help with tasks such as:
- answering development questions,
- generating and updating code,
- generating tests,
- explaining/refactoring/fixing code,
- reviewing code,
- working with project/workspace context.

For this exam skill, narrow the focus to:

→ **automated test generation**.

---

#### 3.3.6.4 Exam Boundary

Do not turn 3.3.6 into:
→ a complete Amazon Q Developer product exam.

The skill is specifically:

**Use Amazon Q Developer to generate automated tests.**

Therefore prioritize:
- giving Q relevant code/context,
- requesting test generation,
- reviewing generated tests,
- running them with the project's test framework,
- incorporating useful tests into automated validation.

Features such as:
- code transformation,
- documentation generation,
- general AWS questions,
- broad code reviews

are useful Amazon Q capabilities but:
→ not the center of 3.3.6.

---

#### 3.3.6.5 Current AWS Terminology

Current Amazon Q Developer documentation describes:
→ **Unit test generation**.

AWS notes that this capability:

Therefore:

**Current concept**
→ generate unit tests through Amazon Q Developer.

**Older material / exam question**
→ may refer to `/test`.

Recognize both.

Do not assume:
→ `/test` must still be the current UI/workflow name.

---

#### 3.3.6.6 Generate Tests from Selected Code

In supported IDE workflows, a developer can:

1. select code,
2. invoke Amazon Q,
3. choose/request **Generate tests**,
4. review the generated code,
5. insert/use the generated tests.

Conceptually:

```text
selected function/class
        |
        v
Generate tests
        |
        v
test cases + assertions
```

The code selection gives Q:
→ focused context.

---

#### 3.3.6.7 Generate Tests Through Chat

Amazon Q can also use:
→ conversational prompts.

Example intent:

```text
Generate unit tests for this service.
Cover:
- valid request
- missing required field
- dependency timeout
- duplicate request
```

Better context generally gives:
→ more targeted tests.

---

#### 3.3.6.8 Context Matters

Test quality depends heavily on:
→ the context available to Amazon Q.

Useful context includes:
- implementation code,
- method/function signature,
- surrounding classes,
- imports,
- existing test conventions,
- expected behavior,
- test framework,
- edge cases,
- dependency behavior.

Weak:

`write tests`

Better:

`Generate JUnit tests for createOrder. Cover valid input, invalid quantity, duplicate order ID, and repository failure.`

---

#### 3.3.6.9 Project / Workspace Context

Amazon Q IDE capabilities can use:
→ project/workspace context.

This can help it understand:
- related classes,
- interfaces,
- existing conventions,
- dependencies,
- surrounding implementation.

But generated output still requires:
→ review.

Context improves generation.
It does not guarantee correctness.

---

#### 3.3.6.10 Unit Test Mental Model

A unit test normally validates:
→ a small isolated unit of behavior.

Typical structure:

```text
Arrange
→ create inputs/dependencies

Act
→ execute code under test

Assert
→ verify result/behavior
```

Amazon Q can help generate:
→ this test code.

---

#### 3.3.6.11 Test Generation ≠ Test Execution

Very important distinction:

**Amazon Q Developer**
→ generates test code.

**JUnit / pytest / Jest / other framework**
→ executes tests.

**CI/CD/build system**
→ automates when those tests run.

Do not answer:

`Amazon Q runs the entire deployment pipeline`

when requirement is:
→ generate automated tests.

---

#### 3.3.6.12 Test Generation ≠ Deployment Testing Environment

3.3.1–3.3.5 established:
- test events,
- API targets,
- approved versions,
- IaC,
- service-specific environments.

Amazon Q does not replace those.

Instead:

```text
Q-generated tests
        |
        v
execute against code/test target
        |
        v
environment created by previous skills
```

---

#### 3.3.6.13 Unit Tests vs Integration Tests

Amazon Q documentation explicitly emphasizes:
→ unit test generation.

Unit tests:
→ test isolated application units.

Integration tests:
→ verify interactions among real or test components/services.

Amazon Q can assist developers in writing broader test code through general coding assistance, but for the exact 3.3.6 exam wording and current AWS documentation:
→ **unit test generation is the clearest directly documented capability.**

Do not silently equate:
`generate unit tests`
with
`automatically construct a complete AWS integration-test environment`.

---

#### 3.3.6.14 Mocking Dependencies

For unit testing, external dependencies are often:
→ mocked/stubbed/faked.

Example:

```text
OrderService
    |
    +-- DynamoDB repository
```

Unit test:

```text
OrderService
    |
    +-- mocked repository
```

Amazon Q can help generate:
- mock setup,
- expected responses,
- assertions.

The developer must verify:
→ mocks represent intended dependency behavior.

---

#### 3.3.6.15 AWS SDK Code

Amazon Q is useful when application code calls:
- DynamoDB,
- S3,
- SQS,
- SNS,
- Lambda,
- other AWS SDK clients.

For unit tests, dependencies can often be:
→ mocked at SDK/client/repository boundary.

This gives:
- faster tests,
- deterministic behavior,
- no real AWS resource requirement.

But remember 3.2.2:
→ integration tests and mocked APIs are a separate broader testing skill.

---

#### 3.3.6.16 Generated Tests Must Be Reviewed

Generative AI output can:
- misunderstand requirements,
- assert wrong behavior,
- miss edge cases,
- use incorrect APIs,
- create brittle tests,
- over-mock,
- compile incorrectly,
- reproduce implementation assumptions instead of business intent.

Therefore workflow must be:

`generate`
→ `review`
→ `run`
→ `correct`
→ `commit`.

Not:

`generate`
→ `trust automatically`.

---

#### 3.3.6.17 Tests Should Validate Requirements, Not Implementation Accident

Bad generated test:

→ asserts an internal implementation detail that is not part of expected behavior.

Better:

→ asserts externally observable contract.

Example:

Weak:
`verify private helper conceptually executes exactly twice`

Better:
`given duplicate order, service returns DuplicateOrderException`.

Developer review is necessary to:
→ keep tests behavior-oriented.

---

#### 3.3.6.18 Existing Test Style

If project already uses:
- JUnit 5,
- Mockito,
- AssertJ,
- pytest,
- Jest,

give Q enough context to follow:
→ existing test conventions.

This reduces:
- incompatible framework choices,
- unnecessary dependencies,
- inconsistent style.

---

#### 3.3.6.19 Do Not Add Unnecessary Dependencies

Generated test may suggest:
→ a new testing library.

Before accepting:
→ check whether existing project framework already solves the need.

This aligns with normal dependency-management principles:
→ generated code should fit the project, not unnecessarily expand it.

---

#### 3.3.6.20 Test File Placement

Generated tests still need to be:
→ placed where the build/test tooling discovers them.

Example Java/Maven convention:

```text
src/main/java/...
src/test/java/...
```

Amazon Q can generate code, but:
→ build-system conventions still apply.

---

#### 3.3.6.21 Compilation Is First Validation

Generated test code should:
→ compile.

Then:
→ execute.

Then:
→ verify meaningful behavior.

Three checkpoints:

```text
generated code
→ compiles?
→ tests execute?
→ assertions represent requirements?
```

Passing compilation alone:
→ does not mean the test is correct.

---

#### 3.3.6.22 A Passing Generated Test Can Still Be Wrong

Example:

Implementation mistakenly returns:
`200`

for invalid input.

Q observes current implementation and generates:

`invalid input → expect 200`.

Test passes.

But business requirement says:
→ `400`.

Therefore:

**Generated tests derived from implementation are not an independent source of truth.**

Requirements/specification remain:
→ authoritative.

---

#### 3.3.6.23 Automated Testing Workflow

A useful complete model:

```text
developer writes code
        |
        v
Amazon Q generates candidate unit tests
        |
        v
developer reviews/corrects tests
        |
        v
tests committed to repository
        |
        v
CI build executes tests
        |
        +-- fail → reject candidate
        |
        +-- pass → continue deployment validation
```

This places Amazon Q:
→ at test-authoring time.

CI/CD:
→ executes/enforces tests later.

---

#### 3.3.6.24 Connection to CI/CD

Once generated tests are:
- reviewed,
- committed,
- executable,

they can run automatically during:
- build,
- pull request validation,
- CI pipeline,
- deployment validation.

Amazon Q does not need to:
→ regenerate tests on every deployment.

The generated tests become:
→ normal project test code.

---

#### 3.3.6.25 Decision Flow

1. **Need help creating automated unit tests?**
   → Amazon Q Developer.

2. **Need tests for a specific method/class?**
   → provide/select that code and request Generate tests.

3. **Need edge cases?**
   → explicitly request boundary/negative scenarios.

4. **Project already has test framework?**
   → give Q project context and follow existing framework/conventions.

5. **Tests generated?**
   → review assertions and dependencies.

6. **Do they compile?**
   → fix generation/context if not.

7. **Do they reflect requirements?**
   → correct assertions if necessary.

8. **Need automated enforcement?**
   → commit tests and run them in build/CI workflow.

9. **Need deployed AWS integration validation?**
   → use the environment/test mechanisms from 3.3.1–3.3.5; Q-generated unit tests do not replace them.

#### 3.3.6.28 Final Principle

**Amazon Q Developer accelerates test authoring, not test ownership. Give it relevant code and testing intent, use it to generate candidate unit tests—including boundary and negative cases—then review the assertions against requirements, run the tests with the project's normal test framework, and commit useful tests so CI/CD can enforce them. The AI generates test code; the developer and delivery system determine whether that code is correct and whether a deployment is allowed to progress.**

#### 3.3.6.31 Final Verified Principle

**For DVA-C02 Skill 3.3.6, Amazon Q Developer is an AI-assisted test-authoring tool, not the test runner or CI/CD system. Use selected code, project context, and explicit testing intent to generate candidate unit tests, including negative and boundary cases. Review generated assertions against requirements, ensure the tests compile and execute with the project's normal framework, and commit useful tests so the delivery workflow can enforce them. Current AWS documentation calls the capability unit test generation / Generate tests; older material may refer to `/test`.**

#### 3.3.6.32 Practical Pattern Summary

| Requirement | Amazon Q Developer role |
|---|---|
| Generate unit tests for selected code | ask Q Developer to generate tests |
| Need edge/error cases | explicitly request boundary/negative scenarios |
| Code uses AWS SDK dependency | generate tests with appropriate mocks/test doubles |
| Generated test does not compile | review imports/framework/project context and fix |
| Generated test passes but validates bug | review expected behavior against requirements |
| Need integration/deployment test | Q can help write code, but AWS test environment still must execute it |
| Need CI validation | commit generated tests and run normal test tooling/pipeline |

Core rule:

```text
Amazon Q Developer
→ assists test-code generation

test framework / build / AWS environment
→ executes and validates tests
```
