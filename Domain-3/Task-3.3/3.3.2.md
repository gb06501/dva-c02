### 3.3.2 Deploy API resources to various environments

#### 3.3.2.1 Exam and Task Context

##### 3.3.2.1.1 Domain
- **Domain 3:** Deployment

##### 3.3.2.1.2 Task
- **Task 3.3:** Automate deployment testing.

##### 3.3.2.1.3 Skill
- **Skill 3.3.2:** **Deploy API resources to various environments.**

The exam guide does not provide a narrower example for this skill. Its position between:
- 3.3.1 creating test events, and
- 3.3.3 creating environments with approved versions

gives the key context:

**Create repeatable API deployments in environment-specific targets so automated tests can exercise the appropriate version without changing production.**

---

#### 3.3.2.2 Core Mental Model

`one API definition`
→ `deployable infrastructure/configuration`
→ `development environment`
→ `test environment`
→ `production environment`

For automated deployment testing:

`build/deploy candidate API`
→ `non-production endpoint`
→ `automated tests`
→ `approved/promoted release`

The important concept is:
→ **environment-aware, repeatable deployment**.

---

#### 3.3.2.3 API Resource vs API Endpoint

Distinguish:

**API resources/configuration**
→ routes/resources, methods, integrations, authorizers, models, mappings and deployment configuration.

**API endpoint**
→ callable URL exposed by the deployed API/stage/environment.

3.3.2 focuses on:
→ deploying API resources into the target environments.

3.2.3 focused more on:
→ testing through development endpoints.

---

#### 3.3.2.4 Primary In-Scope API Service: Amazon API Gateway

For DVA-C02, Amazon API Gateway is the central managed API deployment service.

An API can include:
- routes/resources,
- HTTP methods,
- Lambda integrations,
- HTTP integrations,
- authorization,
- request/response behavior,
- stage configuration.

These should be:
→ reproducibly deployable.

---

#### 3.3.2.5 REST API Deployment Model

For an API Gateway REST API:

`API configuration`
→ `deployment`
→ `stage`
→ `invoke URL`

A deployment represents:
→ a snapshot of API configuration.

A stage references:
→ a deployment.

Typical stages:
- `dev`
- `test`
- `staging`
- `prod`

---

#### 3.3.2.6 Environment Model with REST API Stages

Concept:

```text
REST API
├── dev stage
│   └── development deployment
├── test stage
│   └── tested deployment
└── prod stage
    └── production deployment
```

This provides:
→ lifecycle-specific API endpoints.

---

#### 3.3.2.7 Deployment vs Stage

Know this distinction cold:

**Deployment**
→ snapshot/release of API configuration.

**Stage**
→ named lifecycle reference to a deployment.

Therefore:

`create deployment`
does not mean:
→ "create another API definition."

And:

`stage`
does not mean:
→ "copy the source code."

---

#### 3.3.2.8 Deploying Changes to a REST API

Relevant API configuration changes must be:
→ deployed/redeployed to a stage

before clients of that stage see them.

Automated flow:

`change API`
→ create/update deployment
→ associate with test stage
→ invoke test endpoint
→ assert.

---

#### 3.3.2.9 HTTP API Deployment Model

API Gateway HTTP APIs also use:
→ stages and deployments.

HTTP API stages can additionally support:
→ automatic deployments.

When auto-deploy is enabled:

`API configuration change`
→ automatically released to stage.

This can be useful in:
→ fast development environments.

---

#### 3.3.2.10 `$default` Stage

HTTP APIs can use:
→ `$default`.

The `$default` stage is served from:
→ the base API URL without an explicit stage path segment.

Do not assume:
→ every environment necessarily appears as `/dev` or `/prod` in the URL.

---

#### 3.3.2.11 Auto-Deploy Trade-Off

Automatic deployment can simplify:
→ rapid development.

But for controlled automated testing/release:

`explicit candidate`
→ `explicit deployment`
→ `test`
→ `promote`

can provide clearer release boundaries.

Exam questions normally signal:
- speed/automatic publishing, or
- controlled version promotion.

Choose accordingly.

---

#### 3.3.2.12 API Gateway Stage Variables

For REST APIs, stage variables can provide:
→ environment-specific non-secret values.

Example:

`dev`
```text
lambdaAlias = dev
backendUrl = https://dev.internal
```

`prod`
```text
lambdaAlias = prod
backendUrl = https://prod.internal
```

Same API structure can therefore:
→ route to different environment-specific backends.

---

#### 3.3.2.13 Stage Variables Are Not Secrets

Do not place:
- passwords,
- API keys,
- credentials

in stage variables.

They are:
→ configuration values, not secure secret storage.

This remains a common exam trap.

---

#### 3.3.2.14 Stage Variables vs Separate API Resources

Stage variables can reduce duplication when:
→ API structure is the same but backend/configuration differs.

Separate API stacks/resources may be appropriate when:
- stronger isolation is required,
- environments live in separate accounts,
- lifecycle must be independently managed.

Do not assume:
→ stages are always the only environment boundary.

---

#### 3.3.2.15 Parameters

Use template parameters for values that legitimately vary by environment.

Examples:
- environment name,
- backend alias/name,
- log level,
- domain configuration,
- feature configuration.

Avoid:
→ maintaining manually divergent templates when parameters solve the difference.

---

#### 3.3.2.16 Stack Outputs

IaC deployment can output:
→ environment-specific API URL.

Example:

`TestApiUrl`

Automated test runner:
→ obtains output
→ calls API
→ asserts behavior.

This directly connects deployment with:
→ automated deployment testing.

---

#### 3.3.2.17 Automated API Deployment Test Flow

```text
source/template
      |
      v
deploy API to test environment
      |
      v
retrieve test endpoint
      |
      v
send test requests/events
      |
      v
assert response + side effects
      |
      +--> pass → candidate can progress
      |
      └--> fail → stop/fix
```

This is the central 3.3.2 context.

---

#### 3.3.2.18 API Gateway + Lambda Environment Pairing

Common architecture:

`API dev stage`
→ Lambda `dev` alias/version.

`API test stage`
→ Lambda `test` alias/version.

`API prod stage`
→ Lambda `prod` alias/version.

This allows:
→ API environment and backend version to evolve independently but deliberately.

3.3.3 expands the approved-version aspect.

---

#### 3.3.2.19 API Stage ≠ Lambda Alias

Again:

`API Gateway stage`
→ API deployment lifecycle.

`Lambda alias`
→ pointer to Lambda version(s).

Names may both be:
`dev`, `test`, `prod`.

But they are:
→ different resources solving different versioning problems.

---

#### 3.3.2.20 Environment-Specific Backend

A test API must not accidentally call:
→ production backend.

Environment deployment must correctly configure:
- Lambda target,
- service endpoint,
- table/queue/topic identifiers,
- permissions.

Automated testing is only safe if:
→ the complete dependency path is environment-aware.

---

#### 3.3.2.21 Resource Policies

API Gateway resource policies can restrict:
→ who/what can invoke an API.

A test deployment can fail automated invocation even when:
→ API code/integration is correct,

if:
→ test runner is not allowed by policy.

This is another reason to test the deployed API rather than only Lambda.

---

#### 3.3.2.22 API Definition Formats

API resources can be represented using:
- OpenAPI definitions,
- SAM/CloudFormation resource definitions.

The key 3.3.2 concern:
→ definition must be deployable consistently to environment targets.

Do not overfocus on:
→ hand-configuring API Gateway console resources.

---

#### 3.3.2.23 OpenAPI

API Gateway can import/use:
→ OpenAPI API definitions.

This can make:
→ routes/methods/schema/integration-related API definition reproducible.

Mental model:

`API contract/definition`
→ deployment tooling/IaC
→ environment-specific API.

---

#### 3.3.2.24 API Contract Consistency

Using the same source API definition across environments helps ensure:

`dev contract`
≈ `test contract`
≈ `prod contract`

while environment-specific values differ intentionally.

This reduces:
→ configuration drift.

---

#### 3.3.2.25 Avoid Manual Stage Drift

Bad:

`dev stage`
→ manually modified.

`test stage`
→ different manual modification.

`prod stage`
→ unknown configuration.

Better:

`version-controlled definition`
→ automated/repeatable deployment.

This is central to automated deployment testing.

---

#### 3.3.2.26 Deployment Candidate

A useful mental model:

`source revision`
+
`API definition`
+
`backend version`
→ deployment candidate.

Deploy candidate to:
→ test environment.

Then automated tests determine:
→ whether it is acceptable to progress.

---

#### 3.3.2.27 Approved Version Boundary

3.3.2:
→ deploy API resources to environment.

3.3.3:
→ ensure environment uses approved application versions.

Together:

`correct infrastructure`
+
`correct approved backend version`
→ stable integration-test environment.

---

#### 3.3.2.28 Failure Pattern: Local API Test Passes, Test Environment Fails

Likely differences:
- IAM,
- authorizer,
- stage configuration,
- integration target,
- resource policy,
- real backend,
- network/configuration.

This is exactly why:
→ deployed API testing exists.

---

#### 3.3.2.29 Failure Pattern: Auto-Deploy Publishes Unintended Change

Development HTTP API with auto-deploy:
→ change becomes available immediately.

If controlled test release is required:
→ use deployment workflow appropriate to that control requirement.

Do not mechanically choose auto-deploy merely because it is convenient.

---

#### 3.3.2.30 Exam-Level Knowledge Frame

Know these cold:

**API deployment**
→ snapshot/release of API configuration.

**API stage**
→ named lifecycle reference to deployment.

**REST API**
→ relevant API changes must be deployed/redeployed to stage.

**HTTP API**
→ stage can use automatic deployment.

**`$default`**
→ HTTP API stage available from base API URL.

**Stage variable**
→ non-secret stage-specific configuration.

**IaC**
→ reproducibly deploy API resources across environments.

**Stack output**
→ useful way to expose environment endpoint to automated tests.

**Canary**
→ percentage-based candidate deployment within REST API stage.

**Custom domain**
→ friendly client-facing API name; mapping still targets API/stage.

Fastest discriminator:

`Need dev/test/prod API endpoints?`
→ environment-specific stages/stacks.

`Need repeatable API deployment?`
→ SAM/CloudFormation/OpenAPI-based definition.

`Need automatically published HTTP API development changes?`
→ auto-deploy.

`Need different backend by REST API stage?`
→ stage/environment configuration.

`Need automated deployment test?`
→ deploy non-prod API → discover endpoint → invoke → assert.

`Need limited live candidate traffic?`
→ canary.

---

#### 3.3.2.31 Final Principle

**Deploy API resources from a reproducible definition into explicitly targeted environments, keep environment-specific configuration separate from the API's shared definition, expose/discover the correct non-production endpoint, and run automated tests against that deployed API before a candidate progresses. API Gateway stages are one lifecycle mechanism; separate stacks/accounts provide stronger environment isolation when required.**

#### 3.3.2.33 Practical Pattern Summary

| Requirement | Correct direction |
|---|---|
| Integration test needs temporary isolated resources | create dedicated test environment/resources |
| Need deterministic teardown | IaC-created environment + cleanup |
| Tests require endpoint/resource identifiers | consume stack outputs/configuration |
| Shared test environment causes collisions | unique IDs or isolated environment |
| Need HTTPS/custom domain in test | include DNS/certificate only when requirement actually depends on them |
| Need auth behavior | test with real development auth configuration |
| Environment setup succeeds but app fails | deployment success ≠ test success |
