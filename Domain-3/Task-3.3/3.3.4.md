### 3.3.4 Implement and deploy infrastructure as code (IaC) templates

#### 3.3.4.1 Exam and Task Context

##### 3.3.4.1.1 Domain
- **Domain 3:** Deployment
##### 3.3.4.1.2 Task
- **Task 3.3:** Automate deployment testing.
##### 3.3.4.1.3 Skill
- **Skill 3.3.4:** **Implement and deploy infrastructure as code (IaC) templates.**
- The exam guide explicitly gives:
  - **AWS SAM templates**
  - **AWS CloudFormation templates**

The focus is not generic infrastructure administration. It is:

**Represent the application environment as code so test infrastructure can be created, updated, reproduced, and deployed automatically.**

---

##### 3.3.4.1.4 Core Mental Model

`template in source control`
→ `validate/build`
→ `parameters for target environment`
→ `preview changes`
→ `deploy stack`
→ `test application`
→ `update template`
→ `repeat`

IaC turns:

`manual resource configuration`

into:

`versioned desired state → AWS creates/updates resources`.

---

#### 3.3.4.2 Infrastructure as Code

IaC means:
→ infrastructure configuration is represented in machine-readable definitions rather than being manually recreated.

Benefits relevant to this skill:
- repeatability,
- consistency,
- automation,
- version control,
- reviewability,
- reproducible test environments,
- reduced configuration drift.

For DVA-C02, the primary technologies are:
→ **AWS CloudFormation and AWS SAM**.

---

#### 3.3.4.3 CloudFormation Core Model

`CloudFormation template`
→ `CloudFormation stack`
→ AWS resources.

A **template** is:
→ the desired infrastructure definition.

A **stack** is:
→ the deployed collection of resources CloudFormation manages as a unit.

Do not confuse:
`template`
with
`stack`.

---

##### 3.3.4.3.1 Declarative Desired State

CloudFormation is declarative.

You describe:

**what resources and configuration should exist**

rather than scripting every individual create/update/delete operation.

Example:

```yaml
Resources:
  OrdersTable:
    Type: AWS::DynamoDB::Table
    Properties:
      BillingMode: PAY_PER_REQUEST
```

CloudFormation determines:
→ the service API operations needed to reach that state.

---

#### 3.3.4.4 CloudFormation Template Structure

High-value sections include:

```text
AWSTemplateFormatVersion
Description
Metadata
Parameters
Mappings
Conditions
Transform
Resources
Outputs
```

The only universally required core section for defining infrastructure is:
→ **Resources**.

You do not need every section in every template.

---

##### 3.3.4.4.1 Resources

`Resources`
→ defines AWS resources managed by the stack.

Each resource has:
- logical ID,
- resource type,
- properties.

Example:

```yaml
Resources:
  OrdersFunction:
    Type: AWS::Lambda::Function
    Properties:
      ...
```

`OrdersFunction`
→ logical ID.

`AWS::Lambda::Function`
→ resource type.

---

##### 3.3.4.4.2 Logical ID vs Physical ID

**Logical ID**
→ name inside the template.

Example:
`OrdersTable`

**Physical ID**
→ actual deployed AWS resource identifier/name.

CloudFormation uses logical IDs to:
→ track resources across stack updates.

Changing logical IDs carelessly can cause:
→ CloudFormation to interpret a resource as removed/new.

---

#### 3.3.4.5 Parameters

`Parameters`
→ values supplied when the stack is deployed.

Use for environment differences such as:
- environment name,
- capacity/configuration,
- feature configuration,
- approved artifact/version references.

Example:

```yaml
Parameters:
  Environment:
    Type: String
    AllowedValues:
      - dev
      - test
      - prod
```

This supports:

`same template + different parameter values`
→ different environments.

---

##### 3.3.4.5.1 Parameter Constraints

Parameters can include constraints such as:
- `AllowedValues`
- `AllowedPattern`
- `MinValue`
- `MaxValue`
- `MinLength`
- `MaxLength`

Purpose:
→ reject invalid configuration earlier.

Exam clue:
**Only dev/test/prod are valid**
→ `AllowedValues`.

---

##### 3.3.4.5.2 Sensitive Parameters

CloudFormation supports:
→ `NoEcho`.

This masks parameter values in many CloudFormation displays.

But:

`NoEcho`
does not magically make a template a secret-management system.

For application secrets:
→ use appropriate secret services such as Secrets Manager or Systems Manager Parameter Store where required.

---

#### 3.3.4.6 Outputs

`Outputs`
→ values exposed after stack deployment.

Examples:
- API endpoint,
- Lambda ARN,
- table name,
- queue URL.

For automated testing:

`deploy stack`
→ read output `TestApiUrl`
→ invoke API
→ assert.

Outputs connect:
→ infrastructure deployment to test automation.

---

##### 3.3.4.6.1 Exported Outputs

A stack output can be exported.

Another stack in the same account and Region can use:
→ `Fn::ImportValue`.

Mental model:

`network stack`
→ exports subnet ID.

`application stack`
→ imports subnet ID.

Use for:
→ controlled cross-stack sharing.

---

#### 3.3.4.7 Intrinsic Functions

CloudFormation intrinsic functions allow templates to:
→ reference and calculate deployment-time values.

Important examples:

`Ref`
→ reference parameter/resource value.

`Fn::GetAtt`
→ retrieve resource attribute.

`Fn::Sub`
→ substitute values into strings.

`Fn::Join`
→ join values.

`Fn::If`
→ conditional value.

`Fn::ImportValue`
→ consume exported stack output.

You should recognize these rather than memorize every intrinsic function.

---

##### 3.3.4.7.1 `Ref`

For a parameter:

`!Ref Environment`
→ parameter value.

For a resource:
→ return value depends on resource type.

Do not assume:
→ `Ref` always returns ARN.

---

##### 3.3.4.7.2 `Fn::GetAtt`

Used when you need:
→ an attribute exposed by a resource.

Example concept:

`!GetAtt OrdersFunction.Arn`

Exam distinction:

`Ref`
→ default reference value.

`GetAtt`
→ named resource attribute.

---

##### 3.3.4.7.3 `Fn::Sub`

Useful for environment-specific names:

```yaml
TableName: !Sub '${Environment}-orders'
```

This avoids:
→ maintaining separate templates for each environment.

---

#### 3.3.4.8 AWS SAM

AWS SAM is:
→ a serverless-focused infrastructure-as-code framework built on CloudFormation.

A SAM template can define resources such as:
- Lambda functions,
- APIs,
- state machines,
- layers,
- event sources.

SAM uses:

```yaml
Transform: AWS::Serverless-2016-10-31
```

The transform expands SAM shorthand into:
→ CloudFormation resources.

---

##### 3.3.4.8.1 SAM Is Not Separate from CloudFormation

Mental model:

`SAM template`
→ SAM transform
→ CloudFormation
→ AWS resources.

Therefore:

**SAM simplifies serverless IaC; CloudFormation remains the deployment engine.**

---

#### 3.3.4.9 `AWS::Serverless::Function`

SAM example:

```yaml
Resources:
  OrdersFunction:
    Type: AWS::Serverless::Function
    Properties:
      Runtime: java21
      Handler: ...
      CodeUri: ...
```

SAM can express a Lambda function more compactly than:
→ raw CloudFormation resources plus related configuration.

---

#### 3.3.4.10 SAM Events

SAM function definitions can declare event sources.

Concept:

```yaml
Events:
  OrdersApi:
    Type: Api
    Properties:
      Path: /orders
      Method: post
```

SAM can generate/manage:
→ related API Gateway integration resources.

This is why SAM is especially useful for:
→ serverless application stacks.

---

#### 3.3.4.11 SAM Globals

`Globals`
→ shared properties for supported SAM resource types.

Example:
→ common runtime settings or environment variables for functions.

Benefit:
→ reduce duplication.

But:
→ only supported SAM properties/resources can use the Globals mechanism as defined by SAM.

---

#### 3.3.4.12 Build and Deploy

Typical SAM lifecycle:

`template + source`
→ `sam build`
→ `sam deploy`.

`sam build`
→ prepares application artifacts.

`sam deploy`
→ deploys through CloudFormation.

For existing stack:
→ update.

For new stack:
→ create.

---

#### 3.3.4.13 CloudFormation Deployment

AWS CLI can deploy a template with:

`aws cloudformation deploy`

Conceptually it:
→ creates a change set,
→ executes it,
→ creates or updates the named stack.

Existing stack name:
→ update.

New stack name:
→ create.

---

#### 3.3.4.14 Change Sets

A CloudFormation change set answers:

**What would this template/parameter update change?**

Flow:

`current stack`
+
`new template/parameters`
→ `change set`
→ review
→ execute.

Change sets can show actions such as:
- Add,
- Modify,
- Remove,
- Replacement implications.

---

##### 3.3.4.14.1 Change Set ≠ Guarantee

A change set previews:
→ proposed infrastructure changes.

It does **not** guarantee:
→ stack update will succeed.

Runtime/service-specific failures can still occur during execution.

Exam trap:

**Preview changes**
→ change set.

**Guarantee successful deployment**
→ no; change set cannot guarantee it.

---

#### 3.3.4.15 Resource Update Behavior

A property change can result in:
- update with no interruption,
- update with interruption,
- resource replacement.

Behavior is:
→ resource/property specific.

Therefore a seemingly small template change can:
→ replace a resource.

This is why change-set review matters.

---

#### 3.3.4.16 IAM Capabilities

Templates can create/update IAM resources.

CloudFormation may require explicit acknowledgement:

- `CAPABILITY_IAM`
- `CAPABILITY_NAMED_IAM`

Concept:

**CloudFormation is about to create/change permissions; acknowledge that capability.**

This is separate from:
→ whether the deployment identity actually has permission.

---

##### 3.3.4.16.1 `CAPABILITY_IAM` vs `CAPABILITY_NAMED_IAM`

High-level distinction:

`CAPABILITY_IAM`
→ template contains IAM resources.

`CAPABILITY_NAMED_IAM`
→ template contains IAM resources with custom names.

Know the concept more than command syntax.

---

#### 3.3.4.17 Deployment Identity vs Runtime Role

**Deployment identity**
→ permissions to create/update infrastructure.

**Lambda execution role**
→ permissions Lambda uses at runtime.

They are not the same.

A deployment can fail because:
→ CloudFormation/deployer lacks permissions,

even when:
→ Lambda execution role is correct.

---

#### 3.3.4.18 Packaging Local Artifacts

CloudFormation templates may reference local artifacts/templates that need:
→ upload to S3 before deployment.

`aws cloudformation package`
can:
→ upload local artifacts,
→ rewrite template references to S3 locations.

SAM tooling can handle serverless application packaging/deployment workflows more directly.

---

#### 3.3.4.19 Template Validation

CloudFormation provides template validation mechanisms.

Validation can identify:
→ structural/template problems.

But:

`template valid`
≠
`stack deploys successfully`
≠
`application works`.

Three layers:

`template validation`
→ syntax/structure.

`deployment`
→ infrastructure successfully created/updated.

`application tests`
→ behavior is correct.

---

#### 3.3.4.20 Drift

Drift occurs when:
→ actual resource configuration differs from CloudFormation's expected configuration.

Typical cause:
→ manual change outside CloudFormation.

Example:

`template says MemorySize=512`
but
developer manually changes Lambda to `1024`.

Now:
→ stack has drift.

---

##### 3.3.4.20.1 Why Drift Matters

IaC assumes:
→ template represents desired state.

Manual modifications undermine:
- reproducibility,
- predictable updates,
- test environment consistency.

Preferred workflow:

`change template`
→ deploy.

Not:

`change console`
→ forget to update template`.

---

#### 3.3.4.21 Infrastructure Test Boundary

Successful IaC deployment proves:
→ infrastructure provisioning/update completed.

It does not prove:
→ application behavior.

Therefore:

`deploy IaC`
→ `retrieve outputs`
→ `run tests`.

Do not stop at:
→ `CREATE_COMPLETE`.

---

#### 3.3.4.22 Decision Flow

1. **Need repeatable AWS environment?**
   → CloudFormation/SAM template.

2. **Serverless application?**
   → SAM can simplify definition.

3. **Environment values differ?**
   → parameters/configuration.

4. **Need deployment result consumed by tests?**
   → outputs.

5. **Need resource attribute inside template?**
   → `GetAtt`.

6. **Need parameter/resource reference?**
   → `Ref`.

7. **Need constructed environment-specific string?**
   → `Sub`.

8. **Need preview before update?**
   → change set.

9. **Need modular CloudFormation hierarchy?**
   → nested stacks.

10. **Need independent stacks to share a value?**
    → exports + `ImportValue`.

11. **Need to preserve stateful resource on deletion?**
    → appropriate `DeletionPolicy`.

12. **Template contains IAM resources?**
    → capability acknowledgement may be required.

13. **Deployment succeeds?**
    → continue to application/integration tests.

#### 3.3.4.24 Exam-Level Knowledge Frame

Know these cold:

**IaC**
→ infrastructure represented as versioned declarative definitions.

**CloudFormation template**
→ desired AWS resource definition.

**CloudFormation stack**
→ deployed resources managed as a unit.

**Resources**
→ AWS objects to create/manage.

**Parameters**
→ deployment-time input values.

**Outputs**
→ values exposed after deployment.

**`Ref`**
→ reference parameter/resource value.

**`GetAtt`**
→ retrieve named resource attribute.

**`Sub`**
→ construct strings with substitutions.

**Conditions**
→ conditional resource/property behavior.

**Change set**
→ preview proposed stack changes.

**SAM**
→ serverless abstraction transformed/deployed through CloudFormation.

**`sam build`**
→ prepare application.

**`sam deploy`**
→ create/update stack.

**Nested stack**
→ child CloudFormation stack managed from parent hierarchy.

**Export/ImportValue**
→ share values between independent stacks in same account/Region.

**DeletionPolicy**
→ resource handling when deleted from stack/template.

**Drift**
→ actual resource differs from expected IaC state.

Fastest discriminator:

`Serverless IaC?`
→ SAM.

`General AWS IaC?`
→ CloudFormation.

`Environment-specific values?`
→ Parameters.

`Need value after deployment?`
→ Outputs.

`Need resource ARN/attribute?`
→ GetAtt.

`Need preview?`
→ Change set.

`Need modular hierarchy?`
→ Nested stacks.

`Need independent stack sharing?`
→ Export/ImportValue.

`Need repeatable test environment?`
→ IaC + parameters + approved artifact.

---

#### 3.3.4.25 Final Principle

**Infrastructure used for deployment testing should be reproducible from code. Define the desired AWS resources with CloudFormation or the serverless-focused SAM abstraction, parameterize legitimate environment differences, expose test-relevant values through outputs, preview risky updates with change sets, and deploy the template as the authoritative source of environment state. Infrastructure deployment is the prerequisite for testing—not proof that the application itself works.**

#### 3.3.4.27 Practical Pattern Summary

| Requirement | IaC direction |
|---|---|
| Repeatable test environment | CloudFormation/SAM template |
| Same template across environments | parameters/configuration, not duplicated templates |
| Preview risky infrastructure changes | change set |
| Protect stateful resource on delete/replace | `DeletionPolicy` / `UpdateReplacePolicy` |
| Need generated endpoint/resource IDs in tests | stack outputs |
| Manual console drift | redeploy/restore desired IaC state |
| Need reusable serverless definition | SAM |
| Need general AWS infrastructure definition | CloudFormation |
