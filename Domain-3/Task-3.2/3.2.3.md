### 3.2.3 Test applications by using development endpoints

#### 3.2.3.1 Exam and Task Context

##### 3.2.3.1.1 Domain
- **Domain 3:** Deployment

##### 3.2.3.1.2 Task
- **Task 3.2:** Test applications in development environments.

##### 3.2.3.1.3 Skill
- **Skill 3.2.3:** Test applications by using development endpoints (for example, API Gateway stages).
- The exam guide explicitly names **API Gateway stages**, so stages are the primary AWS model for this skill.

#### 3.2.3.2 Core Mental Model

`API configuration → deployment snapshot → stage → callable endpoint → test → observe → iterate`

Example:

`API`
- `dev` stage → development deployment
- `test` stage → validated deployment
- `prod` stage → production deployment

**A development endpoint lets clients and tests exercise a non-production deployment through a real AWS endpoint.**

#### 3.2.3.3 API Gateway Deployment vs Stage

For API Gateway, a **deployment** represents a snapshot of API configuration.

A **stage** is a logical reference to a lifecycle state such as:
- `dev`
- `beta`
- `test`
- `prod`
- `v2`

A stage is therefore not the API definition itself. It makes a deployment available for clients to invoke.

For REST APIs, relevant API configuration changes must be redeployed to an existing or new stage before clients see them.

#### 3.2.3.4 Stage as Development Endpoint

Conceptually:

`deployment A → dev stage → /dev/...`

`deployment B → prod stage → /prod/...`

A stage name normally appears in the invoke URL, for example:

`https://{api-id}.execute-api.{region}.amazonaws.com/dev/orders`

This gives development a real AWS endpoint without directing tests to production.

#### 3.2.3.5 HTTP API `$default` Stage

API Gateway HTTP APIs can use the special `$default` stage.

It is served from the base API URL without an explicit stage-name path segment.

Recognize this as HTTP API stage behavior; do not assume every invoke URL must contain `/dev` or `/prod`.

#### 3.2.3.6 HTTP API Automatic Deployments

HTTP API stages can enable automatic deployments.

When enabled:
`API change → automatically released to stage`

Without automatic deployment:
`API change → deployment → stage`

Exam clue:
**Automatically make HTTP API changes available in a development stage** → automatic deployments may be appropriate.

#### 3.2.3.7 Why Separate Development Stages?

A development stage provides:
- non-production testing endpoint,
- independent deployment lifecycle,
- environment-specific integration configuration,
- safer testing,
- isolation from production consumers.

This directly implements Task 3.2's development-environment focus.

#### 3.2.3.8 Stage Variables

API Gateway stage variables are stage-specific key/value configuration.

They act similarly to environment variables.

Example:

`dev`
- `backendUrl = dev.internal.example`
- `lambdaAlias = dev`

`prod`
- `backendUrl = prod.internal.example`
- `lambdaAlias = prod`

The same API definition can therefore interact with different backends by stage.

#### 3.2.3.9 Stage Variables Are Not Secrets

AWS explicitly states that stage variables are **not intended for sensitive data such as credentials**.

Good:
- environment name,
- backend identifier,
- non-secret endpoint.

Bad:
- password,
- API key,
- credential.

This follows 3.1.5:

`configuration ≠ secret`

#### 3.2.3.10 Stage Variables in REST APIs

REST API stage variables can participate in supported:
- parameter mappings,
- mapping templates,
- HTTP integration URIs,
- AWS integration URIs,
- Lambda integration configuration.

Mental model:

`same API + stage-specific value → environment-specific integration`

#### 3.2.3.11 API Gateway Stage vs Lambda Alias

These are different AWS objects.

`API Gateway stage`
→ named lifecycle reference to an API deployment.

`Lambda alias`
→ named pointer to one or more Lambda versions.

A useful design can combine them:

`API dev stage → Lambda dev alias`

`API prod stage → Lambda prod alias`

But never treat stage and alias as synonyms.

#### 3.2.3.12 Development Endpoint Testing Loop

1. Deploy API/application to development.
2. Obtain the development endpoint.
3. Send representative request.
4. Verify status, headers, body and side effects.
5. Inspect CloudWatch evidence when necessary.
6. Modify code/configuration.
7. Redeploy/synchronize.
8. Retest.

This tests the real API boundary rather than only the Lambda handler.

#### 3.2.3.13 Why Direct Lambda Invocation Is Insufficient

Architecture:

`Client → API Gateway → Lambda`

Direct Lambda invocation tests:
`Lambda`

Development endpoint tests:
`API Gateway → Lambda`

Therefore only endpoint testing validates API-specific behavior such as:
- routes/methods,
- authorization,
- integration configuration,
- request transformation,
- response behavior,
- CORS,
- stage configuration.

#### 3.2.3.14 API Contract Testing

A development endpoint can verify:
- path/route,
- HTTP method,
- query/path parameters,
- request body,
- authentication/authorization,
- status code,
- response headers,
- response body.

This validates what the API consumer actually sees.

#### 3.2.3.15 Authorization

If API Gateway uses an authorizer or other API authorization mechanism, direct Lambda invocation bypasses that API layer.

Requirement:
**verify actual API authorization behavior**
→ call the deployed development endpoint.

#### 3.2.3.16 Request/Response Mapping

API Gateway can transform requests/responses.

Direct Lambda invocation bypasses those mappings.

If a question concerns:
- headers,
- query parameters,
- path parameters,
- mapping templates,
- client-visible error mapping,

test the API endpoint.

#### 3.2.3.17 Stage-Level Configuration

Depending on API type and feature, stage configuration can include concepts such as:
- logging,
- metrics,
- throttling,
- stage variables,
- REST API caching,
- REST API canary settings.

Development and production can therefore have different operational settings.

#### 3.2.3.18 REST API Caching and Testing

A REST API stage can use caching.

Debugging clue:

`backend changed but response still appears old`
→ check whether stage caching affects the observed response.

Do not automatically conclude the new backend code was not deployed.

#### 3.2.3.19 Local Development Endpoint with AWS SAM

AWS SAM CLI provides:

`sam local start-api`

It runs Lambda functions locally behind a local HTTP server based on `Api` or `HttpApi` event definitions.

Typical endpoint:

`http://127.0.0.1:3000/...`

Purpose:
→ fast local API request/response testing before cloud deployment.

#### 3.2.3.20 Local vs Cloud Endpoint

`sam local start-api`
→ local development endpoint
→ fast feedback
→ local Lambda runtime emulation.

`API Gateway dev stage`
→ real AWS endpoint
→ actual stage/integration/IAM/cloud behavior.

Therefore:

**Local success does not prove the deployed API works.**

#### 3.2.3.21 SAM Environment Configuration

`sam local start-api --env-vars env.json`

can provide local environment-variable overrides.

This helps reproduce development configuration locally, but it still does not reproduce the complete AWS environment.

#### 3.2.3.22 SAM Authorizer Caveat

AWS SAM documentation notes limitations in reproducing some cloud authorizer behavior locally.

Application-critical authorization behavior should therefore be tested against AWS.

Exam principle:
**real cloud behavior requirement → deployed development endpoint**

#### 3.2.3.23 Fast Cloud Iteration

A serverless development loop can be:

`edit → sam sync --watch → API Gateway dev endpoint → test → logs → edit`

This combines:
- rapid synchronization from 3.2.1,
- development endpoint testing from 3.2.3.

#### 3.2.3.24 Endpoint Discovery

Tests need the correct endpoint.

Prefer environment/deployment discovery rather than hard-coding.

A CloudFormation/SAM stack output can expose, for example:

`DevApiUrl = https://.../dev`

Then integration tests can consume that output/configuration.

#### 3.2.3.25 Endpoint Is Environment Configuration

Development:
`API_URL = development endpoint`

Production:
`API_URL = production endpoint`

Do not bake production endpoint assumptions into reusable application/test logic.

This connects directly to 3.1.5.

#### 3.2.3.26 Multiple Stages Do Not Necessarily Mean Multiple APIs

One API Gateway API can have multiple stages.

Therefore:
`dev endpoint + prod endpoint`
does not automatically require two separate API definitions.

However, stages and AWS accounts are different isolation concepts:

`stage`
→ API lifecycle abstraction.

`AWS account`
→ security/administrative isolation boundary.

Do not confuse them.

#### 3.2.3.27 Decision Flow

##### 3.2.3.27.1 Step 1 — Need fast local HTTP testing?
→ `sam local start-api`.

##### 3.2.3.27.2 Step 2 — Need actual API Gateway behavior?
→ deployed development stage.

##### 3.2.3.27.3 Step 3 — Need dev/prod lifecycle endpoints?
→ API Gateway stages.

##### 3.2.3.27.4 Step 4 — Need different non-secret backend configuration per stage?
→ stage variables/stage-specific integration configuration.

##### 3.2.3.27.5 Step 5 — Need authorization, mapping or CORS validation?
→ actual API endpoint.

##### 3.2.3.27.6 Step 6 — REST API configuration changed?
→ redeploy to intended stage.

##### 3.2.3.27.7 Step 7 — HTTP API should release changes automatically?
→ automatic deployments.

##### 3.2.3.27.8 Step 8 — Need limited traffic to candidate REST API deployment?
→ canary.

##### 3.2.3.27.9 Step 9 — Need candidate to use different stage configuration?
→ canary stage-variable override.

#### 3.2.3.28 Practical Pattern Summary

| Requirement | Correct direction |
|---|---|
| Test real non-production API behavior | invoke development API Gateway stage |
| Same API, different backends by stage | stage variables / stage-specific integration configuration |
| HTTP API without explicit stage path | `$default` stage |
| Automatically release HTTP API changes to dev stage | automatic deployments |
| Direct Lambda works but endpoint fails | inspect API Gateway route/auth/mapping/stage |
| Need gradual production traffic shift | canary; not the same as a development stage |
| Sensitive credential | never store in stage variables |

#### 3.2.3.29 Common Exam Traps

##### 3.2.3.29.1 Stage = deployment
→ False.
Deployment is the API snapshot; stage references a deployment.

##### 3.2.3.29.2 Stage variable = secret store
→ False.

##### 3.2.3.29.3 Direct Lambda invocation tests API Gateway
→ False.

##### 3.2.3.29.4 `sam local start-api` is a real API Gateway stage
→ False.

##### 3.2.3.29.5 Development stage = canary
→ False.

##### 3.2.3.29.6 Every REST API configuration change is immediately callable
→ False; redeployment is required for relevant API changes.

##### 3.2.3.29.7 Canary requires a separate public API
→ False.

##### 3.2.3.29.8 Lambda alias = API Gateway stage
→ False.

##### 3.2.3.29.9 Local endpoint success guarantees cloud success
→ False.

#### 3.2.3.31 Exam-Level Knowledge Frame

Know these cold:

**API deployment**
→ snapshot of API configuration.

**API stage**
→ named lifecycle reference to deployment.

**Development stage**
→ real non-production AWS endpoint.

**Stage variable**
→ stage-specific non-secret key/value configuration.

**REST API change**
→ relevant API configuration must be redeployed to become callable.

**HTTP API automatic deployment**
→ changes can automatically release to a stage.

**HTTP API `$default` stage**
→ base API URL without explicit stage path.

**`sam local start-api`**
→ local HTTP endpoint for API-triggered Lambda testing.

**REST API canary**
→ percentage of stage traffic routed to candidate deployment.

**Canary stage-variable override**
→ candidate can use different stage-variable values.

Fastest discriminator:

`dev/prod API endpoints?`
→ stages.

`different backend per stage?`
→ stage variables/configuration.

`local API testing?`
→ `sam local start-api`.

`real API Gateway behavior?`
→ deployed dev stage.

`REST API still old?`
→ redeploy.

`10% candidate traffic?`
→ canary.

#### 3.2.3.32 Final Principle

**Use API Gateway stages to expose lifecycle-specific cloud endpoints and test new behavior through non-production stages. Use stage-specific configuration to keep development isolated from production. AWS SAM accelerates local endpoint testing, but only a deployed development endpoint validates the actual API Gateway and AWS integration path.**
