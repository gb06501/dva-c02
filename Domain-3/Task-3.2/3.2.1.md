### 3.2.1 Test deployed code by using AWS services and tools

#### 3.2.1.1 Exam and Task Context

##### 3.2.1.1.1 Domain and Task
- **Domain 3:** Deployment.
- **Task 3.2:** Test applications in development environments.
- **Skill 3.2.1:** **Test deployed code by using AWS services and tools.**

Transition from Task 3.1:

```text
Task 3.1
→ prepare deployment-ready application

Task 3.2
→ prove the deployed application works in AWS
```

Core question:

**How do you verify that deployed code actually behaves correctly in its AWS development environment?**

---

#### 3.2.1.2 Core Mental Model

```text
SOURCE
→ build/package
→ deploy to development environment
→ invoke deployed resource
→ observe response + logs + metrics
→ compare actual vs expected
→ fix / redeploy / retest
```

Central principle:

**A successful deployment proves that AWS accepted the deployment. It does not prove that the application works.**

---

#### 3.2.1.3 Local Testing vs Deployed Cloud Testing

##### Local Testing

```text
code
→ local runtime / mock / emulator
→ fast feedback
```

Useful for:
- logic,
- parsing,
- early feedback.

##### Cloud Testing

```text
deployed application
→ real AWS services
→ real IAM
→ real configuration
→ real networking
→ real integrations
```

Skill 3.2.1 specifically emphasizes:
- **deployed code**.

Therefore:

```text
unit/local test passes
≠ deployed application works
```

Deployment can introduce failures such as:
- wrong Lambda handler,
- missing runtime dependency,
- incorrect environment variable,
- insufficient IAM permission,
- wrong resource ARN,
- integration configuration errors,
- network/VPC problems,
- runtime differences.

---

#### 3.2.1.4 Development Environment

Test deployed code primarily in:
- development/non-production resources.

Benefits:
- safe iteration,
- isolated resources,
- controlled test data,
- reduced production risk.

Environment-specific configuration from 3.1.5 should direct the deployed application toward:
- development tables,
- development queues,
- development buckets,
- development APIs.

Avoid:
- development tests writing to production resources.

---

#### 3.2.1.5 Basic Testing Loop

```text
DEPLOY
  ↓
SELECT TEST INPUT
  ↓
INVOKE
  ↓
OBSERVE
  ↓
ASSERT
  ↓
FIX / REDEPLOY
  └────────────→ repeat
```

Observe both:
- immediate result,
- runtime evidence.

Runtime evidence can include:
- CloudWatch Logs,
- CloudWatch metrics,
- traces,
- downstream state.

---

#### 3.2.1.6 Test the Narrowest Relevant Boundary

Architecture:

```text
API Gateway
→ Lambda
→ DynamoDB
```

Direct Lambda invocation tests:

```text
Lambda
→ DynamoDB
```

Calling the API endpoint tests:

```text
API Gateway
→ Lambda
→ DynamoDB
```

Therefore:

**Test at the narrowest boundary that proves the requirement.**

Examples:

```text
business logic?
→ direct Lambda invocation

API integration?
→ API endpoint

SQS integration?
→ send message to queue

S3 notification?
→ upload object

complete workflow?
→ invoke workflow entry point
```

This avoids:
- unnecessarily broad tests,
- misleading conclusions about integrations that were bypassed.

---

#### 3.2.1.7 Lambda Console Test Events

The Lambda console can invoke:
- a deployed function

with:
- a JSON test event.

Example:

```json
{
  "orderId": "123"
}
```

Useful for:
- quick functional checks,
- handler verification,
- reproducing known input.

Important:

```text
Lambda console test event
→ directly supplies JSON to Lambda
```

It does **not necessarily reproduce**:
- API Gateway behavior,
- S3 notification configuration,
- SNS delivery,
- EventBridge routing,
- other upstream integration behavior.

---

#### 3.2.1.8 Direct Lambda Invocation

A deployed Lambda can be invoked through:
- Lambda console,
- AWS CLI,
- AWS SDK,
- `sam remote invoke`.

Concept:

```text
test payload
→ deployed Lambda
→ response
```

AWS CLI concept:

```text
aws lambda invoke
→ deployed function
→ payload
→ response/output
```

Use direct invocation when:
- Lambda behavior itself is the target.

Do not infer:

```text
direct Lambda test passed
→ upstream integration works
```

---

#### 3.2.1.9 AWS SAM CLI Testing Model

Relevant SAM CLI capabilities:

```text
sam local ...
→ local testing

sam sync
→ synchronize development changes to AWS

sam remote invoke
→ interact with deployed AWS resource

sam logs
→ inspect deployed logs
```

Key distinction:

```text
LOCAL
sam local

CLOUD
sam remote invoke
```

---

#### 3.2.1.10 `sam remote invoke`

`sam remote invoke` interacts with supported resources:
- already deployed in AWS.

Supported resource examples include:
- Lambda,
- SQS,
- Kinesis Data Streams,
- Step Functions.

Concept:

```text
Lambda
→ invoke function

SQS
→ send message

Kinesis
→ put record

Step Functions
→ start execution
```

Because the resource is deployed, remote testing exercises:
- actual AWS service,
- actual deployed configuration,
- real IAM context,
- downstream dependencies.

---

#### 3.2.1.11 `sam sync`

`sam sync` accelerates synchronization of local application changes to AWS.

Development loop:

```text
edit
→ sam sync
→ test deployed resource
→ edit
→ repeat
```

`sam sync --watch`:

```text
local change
→ detected automatically
→ synchronized to AWS
→ cloud test
```

Purpose:
- shorten development feedback loops.

---

#### 3.2.1.12 `sam sync` Production Warning

Accelerated SAM synchronization can:
- use service APIs directly,
- bypass normal CloudFormation deployment behavior for some changes.

Possible consequence:
- CloudFormation stack drift.

Therefore:

```text
sam sync
→ development workflow

controlled deployment
→ production workflow
```

Do not choose:
- `sam sync`

as the preferred production deployment mechanism.

---

#### 3.2.1.13 SAM Local Testing

Useful local commands include:

```text
sam local invoke
→ run Lambda locally

sam local start-api
→ emulate API Gateway + Lambda locally
```

Useful for:
- fast pre-deployment testing.

But they do not prove:
- deployed IAM,
- actual API Gateway configuration,
- AWS networking,
- real cloud integrations.

For 3.2.1:

```text
local test
→ useful

deployed test
→ required when proving cloud behavior
```

---

#### 3.2.1.14 Testing Deployed APIs

For an API application:

```text
client
→ development API endpoint
→ integration
→ backend
```

Possible test clients:
- browser where appropriate,
- `curl`,
- Postman,
- SDK/client,
- automated tests.

Verify:
- HTTP status,
- response body,
- headers,
- authorization,
- integration behavior.

A real stage endpoint exercises more than:
- direct backend invocation.

Detailed development endpoint configuration belongs to:
- 3.2.3.

---

#### 3.2.1.15 Step Functions Testing

For a deployed state machine:

```text
test input
→ start execution
→ inspect execution
```

Verify:
- execution status,
- state transitions,
- state input/output,
- retries,
- catches,
- errors,
- final output.

Execution history helps locate:
- the state where behavior diverged.

Do not inspect only:
- final status

when:
- orchestration behavior is the requirement.

---

#### 3.2.1.16 Test Real Event Boundaries

When integration behavior matters:
- inject input at the actual producer/event boundary.

##### SQS → Lambda

```text
send message to development queue
→ event source mapping
→ Lambda
→ downstream result
```

Validates more than:
- direct Lambda invocation.

##### Kinesis → Consumer

```text
put test record
→ stream
→ consumer
→ downstream result
```

##### EventBridge → Target

```text
publish matching event
→ rule matching
→ target invocation
→ result
```

##### S3 → Lambda

```text
upload object
→ S3 notification
→ Lambda
→ result
```

This validates:
- notification configuration,
- permissions,
- real event shape.

##### SNS → Subscribers

```text
publish test message
→ development topic
→ subscribers
→ downstream processing
```

##### DynamoDB Streams → Lambda

```text
write/update/delete item
→ DynamoDB Streams
→ event source mapping
→ Lambda
```

Principle:

**If the integration itself is under test, invoke the actual integration boundary rather than bypassing it.**

Detailed asynchronous semantics belong to:
- 3.2.5.

---

#### 3.2.1.17 Synchronous vs Asynchronous Verification

##### Synchronous

```text
request
→ service
→ immediate response
```

Verify:
- status,
- returned data,
- error,
- latency where relevant.

##### Asynchronous

```text
event/message accepted
→ processing occurs later
```

Producer success proves only:
- input was accepted at that boundary.

It does not prove:
- downstream processing completed.

Verify:
- downstream state,
- consumer logs,
- metrics,
- queue behavior,
- error destination/DLQ where applicable.

---

#### 3.2.1.18 CloudWatch Logs

CloudWatch Logs provides:
- execution-level evidence.

Logs can reveal:
- invocation started,
- input received,
- branch executed,
- dependency failure,
- exception,
- downstream response,
- timeout.

Example:

```text
API response
→ 500

CloudWatch Logs
→ AccessDeniedException on DynamoDB
```

Response:
- proves failure occurred.

Logs:
- help explain why.

---

#### 3.2.1.19 CloudWatch Metrics

Metrics provide:
- aggregate numeric runtime evidence.

Examples:
- Lambda Invocations,
- Errors,
- Duration,
- Throttles,
- API Gateway request/error metrics,
- SQS queue depth,
- service-specific metrics.

Use metrics to answer:

```text
was the function invoked?
did errors increase?
is latency abnormal?
```

Difference:

```text
METRIC
→ aggregate signal

LOG
→ execution detail
```

---

#### 3.2.1.20 AWS X-Ray

AWS X-Ray can provide:
- distributed tracing

for supported instrumented applications.

Example path:

```text
API Gateway
→ Lambda
→ downstream service
```

Trace can help identify:
- request path,
- latency contribution,
- errors.

For this skill:
- X-Ray is supporting evidence.

Detailed observability/root-cause analysis belongs primarily to:
- Domain 4.

#### 3.2.1.25 Testing Levels

```text
UNIT
→ code logic

LOCAL SERVICE
→ SAM local / emulation

DEPLOYED COMPONENT
→ direct Lambda / Step Functions invocation

INTEGRATION
→ actual AWS producer → consumer

END-TO-END
→ full development workflow
```

Use:
- increasingly broad tests as confidence grows.

Do not assume:
- every test should be end-to-end.

---

#### 3.2.1.26 Smoke, Functional, Integration, End-to-End

##### Smoke Test

Question:

**Does the deployed application basically work?**

Examples:
- Lambda returns expected response,
- `/health` returns 200,
- state machine succeeds,
- queue message is processed.

##### Functional Test

Question:

**Does expected application behavior work?**

Example:

```text
POST /orders
→ creates order
→ returns ID
```

##### Integration Test

Question:

**Do components/services work together?**

Example:

```text
API Gateway
→ Lambda
→ DynamoDB
```

3.2.2 expands:
- integration tests,
- mocked external APIs.

##### End-to-End Test

Exercises:
- a broad workflow.

Example:

```text
HTTP request
→ API Gateway
→ Lambda
→ DynamoDB
→ event
→ SQS
→ worker
→ final state
```

More realistic:
- but slower,
- more complex.

---

#### 3.2.1.27 Cloud Testing Validates Environment Reality

Cloud testing exposes conditions local tests may not.

##### IAM

```text
local mock
→ DynamoDB call succeeds

deployed Lambda
→ AccessDenied
```

Reason:
- real execution role.

##### Networking

```text
local call
→ succeeds

VPC-attached Lambda
→ timeout
```

Reason may be:
- routing,
- security,
- private connectivity.

##### Configuration

```text
code correct
+
TABLE_NAME=orders-test-old
→ application wrong
```

Cloud testing validates:
- code + deployed configuration.

##### Integration Permissions

Example:

```text
direct Lambda invoke
→ works

S3 upload
→ Lambda not invoked
```

Investigate:
- notification configuration,
- resource permission,
- filter,
- event assumptions.

---

#### 3.2.1.28 Failure Pattern Summary

| Observation | Likely interpretation / next boundary |
|---|---|
| Deployment succeeds, application fails | deployment acceptance ≠ runtime correctness |
| Lambda console test passes, API fails | inspect API Gateway integration/stage/auth/mapping |
| Direct Lambda test passes, S3 flow fails | inspect notification, permission, filter, event shape |
| SAM local passes, cloud fails | inspect IAM, configuration, networking, runtime/service differences |
| SQS send succeeds, processing fails | inspect consumer, event source mapping, queue depth, DLQ |
| Build passes, deployed app fails | invoke deployed application and inspect runtime evidence |
| `sam sync` proposed for production | reject; accelerated sync is a development workflow |
| Metric shows errors | use logs/traces for execution detail |

#### 3.2.1.30 Common Exam Traps

##### "Deployment success means the application passed testing"
- False.

##### "Direct Lambda invocation tests API Gateway"
- False.

##### "Lambda test event reproduces the upstream AWS service"
- Not necessarily.

##### "SAM local fully reproduces AWS"
- False.
- Real IAM, networking, configuration, and integrations remain cloud-specific.

##### "`sam sync` is the preferred production deployment mechanism"
- False.
- It is positioned for accelerated development workflows.

##### "Successful SQS send means consumer succeeded"
- False.

##### "CloudWatch metric gives complete failure details"
- Usually false.
- Logs/traces provide deeper execution evidence.

##### "CodeBuild is a testing framework"
- False.
- It executes test tools and can collect their reports.

##### "All testing should be end-to-end"
- False.
- Use the smallest boundary that proves the requirement.

##### "Production is the preferred development validation environment"
- False.
- Task 3.2 focuses on development environments.

#### 3.2.1.34 Exam-Level Knowledge Frame

Know these cold.

**Successful deployment**  
→ does not prove application behavior.

**Lambda console test**  
→ invoke deployed Lambda with JSON test event.

**Direct Lambda invocation**  
→ tests Lambda, not bypassed upstream integration.

**`sam local`**  
→ local serverless testing.

**`sam remote invoke`**  
→ interact with supported deployed AWS resources.

**`sam sync`**  
→ accelerated synchronization to AWS development environment.

**`sam sync --watch`**  
→ automatically synchronize detected local changes.

**`sam logs`**  
→ retrieve logs for deployed serverless resources.

**CloudWatch Logs**  
→ execution-level details.

**CloudWatch metrics**  
→ aggregate runtime evidence.

**CodeBuild**  
→ executes test commands and can collect structured test reports.

**Real integration test**  
→ inject input at the actual system boundary.

Fastest exam discriminator:

```text
quickly test deployed Lambda?
→ console / direct invoke / sam remote invoke

test API Gateway integration?
→ call development API endpoint

test SQS-triggered Lambda?
→ send message to development queue

test S3 notification flow?
→ upload object to development bucket

rapid serverless development iteration in AWS?
→ sam sync

automatically sync edits?
→ sam sync --watch

inspect deployed Lambda execution?
→ CloudWatch Logs / sam logs

need aggregate runtime evidence?
→ CloudWatch metrics

need structured managed test reports?
→ CodeBuild reports

need full event integration proof?
→ trigger the real event source
```

Final principle:

**Test the deployed application at the narrowest AWS boundary that proves the requirement. Directly invoke components when isolating logic, invoke real development endpoints or event sources when validating integrations, and use runtime evidence to confirm what actually happened in AWS.**
