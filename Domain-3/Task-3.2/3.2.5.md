### 3.2.5 Test event-driven applications

#### 3.2.5.1 Exam and Task Context

##### 3.2.5.1.1 Domain
- **Domain 3:** Deployment

##### 3.2.5.1.2 Task
- **Task 3.2:** Test applications in development environments.

##### 3.2.5.1.3 Skill
- **Skill 3.2.5:** **Test event-driven applications.**
- This is the final skill in Task 3.2.

The exam guide gives no narrower example for 3.2.5, so the skill should be understood in the context of:
- the event-driven AWS services already in scope for DVA-C02,
- Lambda event processing,
- development-environment testing,
- the testing concepts established in 3.2.1–3.2.4.

#### 3.2.5.2 Core Mental Model

A request-driven test is often:

`request → component → immediate response`

An event-driven test is more often:

`produce event → event source/router → consumer → asynchronous processing → observable side effect`

Therefore the main testing question changes from:

**"What response did I get?"**

to:

**"Did the event travel through the intended path and eventually produce the expected state or side effect?"**

#### 3.2.5.3 Why Event-Driven Testing Is Different

Event-driven systems introduce:
- asynchronous execution,
- queues and streams,
- retries,
- batching,
- duplicate delivery,
- ordering considerations,
- eventual completion,
- dead-letter/error paths,
- multiple consumers,
- event filtering and routing.

A test must often validate:
1. event shape,
2. producer behavior,
3. integration configuration,
4. consumer behavior,
5. eventual outcome.

#### 3.2.5.4 Event Source → Consumer

Typical AWS examples:

`S3 event → Lambda`

`SQS → Lambda`

`SNS → Lambda / SQS`

`EventBridge → target`

`Kinesis Data Streams → Lambda`

`DynamoDB Streams → Lambda`

These are not identical integration models.

The test should respect:
→ how the real service actually delivers events.

#### 3.2.5.5 Push vs Poll-Based Lambda Invocation

A useful Lambda distinction:

**Push/direct event sources**
→ service invokes Lambda.

Examples:
- Amazon S3,
- Amazon SNS,
- Amazon EventBridge.

**Event source mappings**
→ Lambda polls a queue or stream and invokes the function.

Examples:
- Amazon SQS,
- Kinesis Data Streams,
- DynamoDB Streams.

This distinction matters because a direct handler test does not validate the real service-to-Lambda integration.

#### 3.2.5.6 Level 1 — Handler/Event-Shape Test

Fastest test:

`sample event JSON`
→ Lambda handler
→ assert output/behavior.

Purpose:
- verify parsing,
- verify business logic,
- test edge cases,
- reproduce known event payload.

This is useful but incomplete.

It does **not** prove:
- source is configured,
- permissions work,
- event mapping exists,
- filtering works,
- polling works,
- retries behave correctly.

#### 3.2.5.7 AWS SAM Sample Events

AWS SAM CLI provides:

`sam local generate-event`

It generates sample event payloads for supported AWS services.

Examples include events for:
- S3,
- API Gateway,
- DynamoDB,
- and other supported sources.

Mental model:

`AWS-like event shape`
→ modify test values
→ save JSON
→ pass to local Lambda.

#### 3.2.5.8 Generate + Invoke Pattern

Concept:

`sam local generate-event <service> <event>`
→ event JSON

then:

`sam local invoke --event event.json FunctionName`

This is ideal for:
→ local event-handler testing.

Example concept:

`S3 PutObject event`
→ local Lambda invocation
→ verify handler behavior.

#### 3.2.5.9 Generated Event ≠ Real Integration

A generated sample event proves:
→ the function can process that event structure.

It does not prove:
→ S3/SQS/EventBridge/Kinesis/DynamoDB actually triggers the function in AWS.

This is one of the most important exam distinctions.

#### 3.2.5.10 Level 2 — Cloud Integration Test

For important event paths:

`send/create real event in development environment`
→ actual AWS service
→ actual integration
→ actual consumer
→ assert downstream outcome.

This validates:
- resource configuration,
- IAM/resource permissions,
- event-source mapping,
- filtering/routing,
- actual service event structure,
- asynchronous processing.

AWS Lambda testing guidance explicitly recommends cloud testing because local environments cannot fully reproduce queues, event buses, databases, security policies, and managed-service integrations.

#### 3.2.5.11 SQS Visibility Timeout

AWS specifically identifies visibility timeout as an integration concern.

If too short:
→ a message can become visible again while processing,
→ duplicate invocation can occur.

A local handler test cannot validate:
→ actual queue visibility-timeout interaction.

Cloud test can expose it.

#### 3.2.5.12 Standard Queue Semantics

Amazon SQS standard queues use:
→ at-least-once delivery semantics.

Therefore a consumer should tolerate:
→ duplicate delivery.

Testing should include:
→ duplicate event/message processing where application correctness depends on it.

This connects to idempotency.

#### 3.2.5.13 Idempotency

Idempotent consumer:

`same event processed more than once`
→ does not create unintended duplicate business effect.

Example:

same order event twice
→ should not create two charges/orders if business semantics require one.

Event-driven testing should intentionally consider duplicates.

#### 3.2.5.14 Batch Processing

Queue/stream integrations can deliver:
→ multiple records in one Lambda invocation.

Test:
- empty/edge assumptions,
- one record,
- multiple records,
- one bad record among good records.

A handler written only against:
→ first record

may pass simplistic tests and fail real workloads.

#### 3.2.5.15 Partial Batch Failure

For supported Lambda event-source integrations, applications can use partial batch response behavior to report failed records rather than treating the whole batch identically.

Exam-level principle:

**Batch-oriented event consumers must be tested for partial failures, not only all-success cases.**

The exact feature/configuration depends on event source.

#### 3.2.5.16 Retry Paths

Event-driven systems frequently retry failures.

Test questions:
- What happens if consumer throws?
- Is message/event retried?
- Can duplicate side effects occur?
- Where does repeatedly failing data go?
- Does success stop retrying?

This connects back to:
- Lambda destinations,
- dead-letter queues,
- retry configuration,
- source-specific failure behavior.

#### 3.2.5.17 Dead-Letter Queue Testing

If architecture includes a DLQ:

`poison event`
→ consumer repeatedly fails
→ retry policy exhausted
→ DLQ

A complete failure-path test should verify:
→ event eventually reaches expected failure destination.

Do not only test:
→ happy path.

#### 3.2.5.18 Poison Message

A poison message/event:
→ consistently fails processing.

Examples:
- invalid schema,
- impossible business value,
- unsupported version.

Testing poison events verifies:
- retry behavior,
- DLQ/error routing,
- monitoring assumptions,
- consumer resilience.

#### 3.2.5.19 Asynchronous Assertion Pattern

Bad:

`send event`
→ sleep fixed 30 seconds
→ assert.

Better:

`send event`
→ poll observable result
→ success when expected state appears
→ fail after bounded timeout.

This reduces:
- unnecessary delay,
- timing flakiness.

#### 3.2.5.20 Event Filtering

Many event architectures filter before invocation.

Possible filters:
- EventBridge event patterns,
- SNS subscription filters,
- Lambda event filtering for supported event source mappings,
- S3 notification prefix/suffix filters.

Testing must include:
- matching events,
- non-matching events.

#### 3.2.5.21 Lambda Event Filtering

For supported event sources, Lambda event filtering can prevent records from invoking the function when filter criteria do not match.

Handler-only tests cannot prove:
→ filter configuration works.

Cloud integration test:
→ send matching/non-matching records through real source.

#### 3.2.5.22 Negative Testing

Important event-driven negative tests:

`non-matching event`
→ consumer must NOT run.

`duplicate event`
→ no duplicate business effect.

`malformed event`
→ controlled failure.

`poison event`
→ retry/DLQ behavior.

`unauthorized producer`
→ event publication rejected where applicable.

#### 3.2.5.23 Test Observability

Because asynchronous systems lack immediate responses, tests often need:
→ observable downstream evidence.

Best evidence:
- resulting data/state,
- output event/message,
- completed workflow,
- object created/updated.

Logs are useful for diagnosis but often weaker than:
→ asserting the actual business side effect.

#### 3.2.5.24 Test at the Correct Boundary

This is perhaps the most important decision rule.

Requirement:
**Does handler parse SQS payload?**
→ direct/local invocation with sample SQS event.

Requirement:
**Does SQS trigger Lambda correctly?**
→ send real message to SQS.

Requirement:
**Does EventBridge rule route correctly?**
→ publish real matching event to EventBridge.

Requirement:
**Does S3 notification work?**
→ create actual object in test bucket.

Test through:
→ the boundary whose behavior you need to prove.

#### 3.2.5.25 Mock vs Real Event Source

Mock/sample event:
- fast,
- deterministic,
- ideal for handler logic.

Real event source:
- validates AWS integration,
- IAM,
- filters,
- service behavior.

Best strategy:
→ both.

This extends 3.2.2 directly into event-driven architecture.

#### 3.2.5.26 Local vs Cloud

Local:
`generated event → sam local invoke`

Cloud:
`real event source → real AWS integration → deployed consumer`

AWS guidance emphasizes:
→ cloud testing is required for confidence in managed-service configuration.

#### 3.2.5.27 Decision Flow

1. **Need to test handler parsing/business logic?**
   → sample/mock event.

2. **Need realistic AWS-shaped event locally?**
   → `sam local generate-event`.

3. **Need local Lambda execution?**
   → `sam local invoke --event`.

4. **Need to prove service-to-consumer integration?**
   → create/send real event through development AWS resource.

5. **Queue/stream source?**
   → validate event source mapping, batch and retry behavior.

6. **Routing/filtering involved?**
   → test matching and non-matching events.

7. **Asynchronous result?**
   → poll observable side effect with bounded timeout.

8. **Duplicate delivery possible?**
   → test idempotency.

9. **Failure/retry path configured?**
   → inject failing/poison event and verify expected retry/DLQ behavior.

10. **Need reproducible known Lambda event?**
    → saved/shared test event / `sam remote test-event` where appropriate.

#### 3.2.5.28 Practical Pattern Summary

| Requirement | Correct event-driven test |
|---|---|
| Test handler parsing/business logic quickly | sample event / `sam local invoke` |
| Generate AWS-shaped sample payload | `sam local generate-event` |
| Prove SQS → Lambda integration | send real message to development queue |
| Prove EventBridge routing | publish real matching event |
| Prove S3 notification | perform real S3 action |
| Prove stream consumer | write/put real development data |
| Async outcome | poll expected state with bounded timeout |
| Duplicate delivery risk | replay and verify idempotency |
| Filtering configured | test matching and non-matching events |
| Batch processing | test multi-record and failure behavior |

Core rule:

```text
sample event
→ consumer contract

real development event source
→ integration contract
```

#### 3.2.5.29 Common Exam Traps

**Generated SAM event proves AWS integration works**
→ False.

**Direct Lambda invocation proves SQS event source mapping works**
→ False.

**Successful event publication proves consumer processed it**
→ False.

**Async result should be asserted immediately**
→ Usually false.

**Standard SQS guarantees exactly-once delivery**
→ False.

**All event services have identical retry/order semantics**
→ False.

**One-record test proves batch handler correctness**
→ False.

**Only matching filter cases need testing**
→ False; negative/non-matching cases matter.

**Logs alone always prove business success**
→ False.

**Local SAM reproduces queues, event buses, permissions and all managed-service behavior**
→ False.

**Fixed sleeps are the best async assertion strategy**
→ False.

#### 3.2.5.30 Service-Specific Testing Lens

| Service/path | What the test should prove |
|---|---|
| SQS → Lambda | polling/mapping, batch handling, retries, idempotency |
| SNS → subscribers | publication, subscriptions, fan-out, filtering |
| EventBridge → target | event pattern, routing, target invocation |
| S3 → consumer | notification/filter configuration and actual object event |
| DynamoDB Streams → Lambda | stream enabled, mapping, INSERT/MODIFY/REMOVE processing |
| Kinesis → Lambda | record ingestion, mapping, batch/ordering behavior |
| Lambda direct/sample event | handler logic and event parsing |

The table is a mental model, not a claim that every exam question tests every listed behavior.

#### 3.2.5.32 Exam-Level Knowledge Frame

Know these cold:

**Event-driven test**
→ inject event and assert eventual downstream behavior.

**Sample event**
→ validates consumer handling, not AWS integration.

**`sam local generate-event`**
→ generate supported AWS-style sample event payloads.

**`sam local invoke --event`**
→ locally invoke Lambda with supplied event.

**Cloud event test**
→ send/create actual event through actual development source.

**Event source mapping**
→ Lambda-managed polling integration for queues/streams such as SQS, Kinesis and DynamoDB Streams.

**Push event**
→ source invokes Lambda, such as S3/SNS/EventBridge integrations.

**Async assertion**
→ poll expected state with bounded timeout.

**At-least-once delivery**
→ consumer must be prepared for duplicate processing where service semantics permit it.

**Idempotency**
→ duplicate processing does not create unintended duplicate business effects.

**Filtering**
→ test both matching and non-matching events.

**Batching**
→ test multiple records and failure behavior.

**DLQ/error destination**
→ test failure path when architecture depends on it.

Fastest exam discriminator:

`Need AWS-shaped local payload?`
→ `sam local generate-event`.

`Need local handler execution?`
→ `sam local invoke`.

`Need to prove SQS → Lambda integration?`
→ send real SQS message.

`Need to prove EventBridge routing?`
→ publish real event to bus.

`Need to prove S3 notification?`
→ perform real S3 action.

`Need to prove stream consumer?`
→ put/change real development data.

`Async outcome?`
→ eventual assertion with timeout.

`Possible duplicate?`
→ test idempotency.

#### 3.2.5.33 Final Principle

**Test event-driven applications at two levels: use controlled/sample events for fast consumer logic testing, then send real events through development AWS resources to validate the actual source, permissions, filtering, polling/routing, batching, retries, and asynchronous side effects. The event path—not merely the handler—is the system under test.**
