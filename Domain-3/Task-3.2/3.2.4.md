### 3.2.4 Deploy application stack updates to existing environments

#### 3.2.4.1 Exam and Task Context

##### 3.2.4.1.1 Domain
- **Domain 3:** Deployment

##### 3.2.4.1.2 Task
- **Task 3.2:** Test applications in development environments.

##### 3.2.4.1.3 Skill
- **Skill 3.2.4:** Deploy application stack updates to existing environments.
- The exam guide gives the explicit example: **deploying an AWS SAM template to a different staging environment**.

This skill sits inside **testing**, not the later CI/CD task. The key question is therefore:

**How does a developer repeatedly update an existing non-production application stack so the next version can be tested?**

#### 3.2.4.2 Core Mental Model

`application change`
→ `update IaC/template/code`
→ `target existing development environment`
→ `preview/validate change`
→ `deploy stack update`
→ `test`
→ `repeat`

The important word is **update**.

You are not necessarily creating an entirely new application every time.

You are evolving:
`existing stack + new desired state → updated stack`

#### 3.2.4.3 Why This Skill Exists in Task 3.2

Task 3.2 is a development feedback loop:

`deploy → test → change → update → test again`

3.2.1 established how to test deployed code.

3.2.2 established mocks and real integration testing.

3.2.3 established development endpoints.

3.2.4 now answers:

**How do I put my next application/infrastructure revision into that development environment?**

#### 3.2.4.4 AWS SAM as the Primary Example

The exam guide explicitly names AWS SAM.

Typical SAM application:

`template.yaml`
→ describes serverless resources.

Examples:
- Lambda functions,
- API Gateway APIs,
- DynamoDB tables,
- event sources,
- IAM configuration,
- other CloudFormation-supported resources.

SAM is built on:
→ AWS CloudFormation.

Therefore deploying a SAM application ultimately creates or updates:
→ a CloudFormation stack.

#### 3.2.4.5 SAM Template → CloudFormation Stack

Mental model:

`SAM template`
→ SAM transformation
→ CloudFormation resources
→ CloudFormation stack

Therefore:

`sam deploy`
does not merely upload Lambda code.

It can update:
→ the complete application stack represented by the template.

#### 3.2.4.6 `sam build`

Typical SAM workflow begins with:

`sam build`

Purpose:
- prepare application for deployment,
- resolve/build dependencies,
- process functions/layers,
- create build artifacts under `.aws-sam`.

Mental model:

`source + template`
→ `sam build`
→ deployable SAM application.

#### 3.2.4.7 `sam deploy`

`sam deploy`
→ deploys the SAM application to AWS.

For an existing stack:
→ updates that stack.

For a new stack:
→ creates it.

Important:
**same command, behavior depends on target stack existence.**

#### 3.2.4.8 Guided Deployment

First-time setup commonly uses:

`sam deploy --guided`

It interactively gathers deployment settings such as:
- stack name,
- AWS Region,
- parameter values,
- permissions/capability acknowledgements,
- configuration choices.

SAM can save deployment settings in:
→ `samconfig.toml`.

Later deployments can reuse those settings.

#### 3.2.4.9 `samconfig.toml`

SAM configuration can hold environment-specific deployment parameters.

This is useful for:
- development,
- test,
- staging,
- production.

Concept:

`same SAM template`
+
`different deployment configuration`
→ different environment.

#### 3.2.4.10 SAM Configuration Environments

SAM CLI configuration supports named environments.

Conceptually:

`sam deploy --config-env dev`

`sam deploy --config-env staging`

The named configuration environment can supply different deployment settings.

This is directly relevant to the exam-guide example:
→ deploying the same SAM application to a different staging environment.

#### 3.2.4.11 Template Parameters

CloudFormation/SAM parameters allow:
→ environment-specific values without duplicating the template.

Example:

`EnvironmentName`
`LogLevel`
`TableName`
`FeatureFlag`

Deployment:

`dev`
→ `EnvironmentName=dev`

`staging`
→ `EnvironmentName=staging`

The template can then derive resource/configuration behavior.

#### 3.2.4.12 Parameter Overrides

SAM deployment can provide:
→ parameter overrides.

Mental model:

`shared template`
+
`environment-specific parameters`
→ environment-specific stack.

This connects to 3.1.5:
→ environment configuration.

#### 3.2.4.13 Environment Separation

A strong exam mental model:

`one source template`
→ `dev stack`
→ `test stack`
→ `prod stack`

Each stack can receive:
- different parameters,
- different configuration,
- different deployment timing.

Do not assume:
→ one CloudFormation stack should represent all lifecycle environments.

#### 3.2.4.14 CloudFormation Stack Update

CloudFormation update flow:

`new template / parameter values`
→ compare with existing stack
→ determine changes
→ update affected resources.

Unchanged resources:
→ generally remain unchanged.

Changed resources may be:
- updated in place,
- interrupted,
- replaced,

depending on the resource property being modified.

#### 3.2.4.15 CloudFormation Change Sets

A change set shows:
→ how a proposed stack update would affect resources before execution.

Mental model:

`new template`
→ `change set`
→ inspect proposed changes
→ execute
→ stack update.

Use when requirement says:
- preview infrastructure changes,
- review changes before applying,
- understand which resources will be modified/replaced.

#### 3.2.4.16 CloudFormation Stack Events

During an update, CloudFormation emits stack/resource events.

Examples:
- `UPDATE_IN_PROGRESS`
- `UPDATE_COMPLETE`
- `UPDATE_FAILED`
- `UPDATE_ROLLBACK_IN_PROGRESS`
- `UPDATE_ROLLBACK_COMPLETE`

These are important when:
→ deployment does not succeed.

Detailed troubleshooting belongs to Domain 4, but recognize stack events as the first deployment-state evidence.

#### 3.2.4.17 Failed Stack Update

If an update fails:
→ CloudFormation can roll the stack back toward the previous known state, depending on update behavior/configuration.

Mental model:

`update`
→ failure
→ rollback
→ previous stack state restored where possible.

Do not assume:
→ partial infrastructure modifications are simply left unmanaged.

#### 3.2.4.18 SAM Accelerate / `sam sync`

For rapid development, AWS SAM provides:

`sam sync`

Purpose:
→ synchronize local application changes to AWS faster than a full deployment workflow.

Especially useful in:
→ development environments.

#### 3.2.4.19 `sam sync --watch`

`sam sync --watch`

watches for local changes and synchronizes them to AWS.

Development loop:

`edit`
→ automatic/rapid sync
→ invoke development endpoint
→ observe
→ edit again.

This is highly relevant to Task 3.2.

#### 3.2.4.20 Code Sync vs Infrastructure Sync

SAM Accelerate distinguishes between:
- code changes,
- infrastructure/template changes.

Code-only changes can often be synchronized through faster service APIs.

Infrastructure changes require:
→ CloudFormation-based deployment/update behavior.

Exam mental model:

**fast code iteration**
→ `sam sync`.

**authoritative infrastructure deployment**
→ SAM/CloudFormation stack update.

#### 3.2.4.21 `sam sync` Is Development-Oriented

Do not treat accelerated sync as:
→ the primary production deployment strategy.

AWS positions it for:
→ rapid cloud development and testing.

That makes it particularly relevant here because 3.2.4 is inside:
**Test applications in development environments.**

#### 3.2.4.22 `sam deploy` vs `sam sync`

**`sam deploy`**
→ formal SAM/CloudFormation deployment/update.

**`sam sync`**
→ accelerated synchronization for development iteration.

Fast discriminator:

`rapidly push local changes while developing`
→ `sam sync`.

`deploy/update the application stack declaratively`
→ `sam deploy`.

#### 3.2.4.23 AWS CLI CloudFormation Update

CloudFormation can also be updated directly.

Conceptual command family:
- create stack,
- update stack,
- deploy template,
- create/execute change set.

For Developer Associate, understand the operation rather than memorizing every CLI option.

#### 3.2.4.24 Existing Environment Means Correct Target

A major practical risk:

`correct template`
+
`wrong target environment`
→ wrong stack updated.

Deployment configuration must identify:
- correct account/credentials,
- Region,
- stack name,
- parameter values.

Environment targeting is part of deployment correctness.

#### 3.2.4.25 AWS Credentials and Region

SAM/CloudFormation deployment uses:
→ AWS credentials and Region configuration.

If credentials point to:
→ wrong account,

or Region points to:
→ wrong Region,

you can update/create resources in the wrong environment.

Exam principle:
**deployment target is determined by both stack configuration and AWS execution context.**

#### 3.2.4.26 CloudFormation Capabilities

Some templates require acknowledgement of CloudFormation capabilities, particularly when creating/updating IAM resources.

Exam clue:
→ SAM deployment involving IAM resource creation may require capability acknowledgement.

Do not confuse:
→ capability acknowledgement
with
→ IAM permission to perform deployment.

Both can matter.

#### 3.2.4.27 Deployment Role / Permissions

The identity performing deployment needs permission to:
- operate CloudFormation/SAM deployment,
- upload artifacts where required,
- create/update represented resources as permitted.

Deployment authorization is separate from:
→ application runtime role.

Example:

`developer/deployment role`
→ updates Lambda.

`Lambda execution role`
→ permissions used when Lambda runs.

Do not confuse them.

#### 3.2.4.28 Runtime Role vs Deployment Identity

`deployment identity`
→ who is allowed to change infrastructure.

`Lambda execution role`
→ what function is allowed to do during execution.

A deployment can fail even if:
→ Lambda runtime permissions are correct,

because:
→ deployer lacks infrastructure permissions.

#### 3.2.4.29 Stack Update as Test Preparation

3.2.4 is not merely deployment administration.

Its purpose inside Task 3.2 is:

`prepare next version of development environment`
→ so tests can run against it.

The stack update is therefore:
→ part of the testing feedback cycle.

#### 3.2.4.30 Testing After Stack Update

A successful CloudFormation update proves:
→ infrastructure deployment completed.

It does not prove:
→ application behavior is correct.

Therefore:

`UPDATE_COMPLETE`
→ then run application/integration tests.

This connects back to 3.2.1–3.2.3.

#### 3.2.4.31 Deployment Success ≠ Application Success

CloudFormation:
`UPDATE_COMPLETE`

API request:
`500`

Both can be true.

Deployment engine verifies:
→ resource provisioning/update.

Application test verifies:
→ behavior.

Exam trap:
**stack deployed successfully**
does not mean
**application passed tests**.

#### 3.2.4.32 Do Not Overreach into CI/CD

This skill does **not** require designing a full pipeline.

The exam explicitly says pipeline design is outside the target candidate's expected job tasks.

For 3.2.4, focus on:
- stack updates,
- environment targeting,
- SAM/CloudFormation,
- fast development synchronization,
- repeatable IaC deployment.

#### 3.2.4.33 Practical Pattern Summary

| Requirement | Correct tool/concept |
|---|---|
| Prepare SAM application | `sam build` |
| Update existing SAM/CloudFormation stack | `sam deploy` |
| Initial interactive SAM deployment setup | `sam deploy --guided` |
| Reuse deployment settings | `samconfig.toml` |
| Same template, different staging environment | different stack/config + parameter values |
| Preview CloudFormation changes | change set |
| Rapid development synchronization | `sam sync` / `--watch` |
| Deployment failure investigation | CloudFormation stack events |
| Avoid wrong environment | verify account, Region, stack name, parameters |

Critical distinction:

```text
sam deploy
→ declarative stack deployment/update

sam sync
→ accelerated development iteration
```

#### 3.2.4.34 Common Exam Traps

**`sam build` deploys resources**
→ False.
It prepares build artifacts.

**`sam deploy` only updates Lambda code**
→ False.
It can deploy/update the SAM application stack.

**`sam sync` is the preferred formal production deployment mechanism**
→ False.
It is development-oriented accelerated synchronization.

**Change set applies changes immediately**
→ False.
It previews proposed changes until executed.

**CloudFormation update means every resource is replaced**
→ False.
Update behavior depends on changed properties.

**Stack update success means application tests passed**
→ False.

**SAM is unrelated to CloudFormation**
→ False.
SAM uses CloudFormation and transforms SAM resources into CloudFormation resources.

**Stage and stack are the same environment abstraction**
→ False.
API Gateway stage is API lifecycle configuration; CloudFormation stack is an IaC resource collection.

**SAM config environment is an AWS account/environment**
→ False.
It is deployment-tool configuration.

**Deployment role and Lambda execution role are the same**
→ False.

**Manual console changes are equivalent to template updates**
→ False.
They can create drift from IaC.

#### 3.2.4.35 Decision Flow

##### 3.2.4.35.1 Step 1 — Application/infrastructure changed?
   → update source/template.

##### 3.2.4.35.2 Step 2 — SAM application?
   → `sam build`.

##### 3.2.4.35.3 Step 3 — Need formal stack deployment/update?
   → `sam deploy`.

##### 3.2.4.35.4 Step 4 — Need another staging environment?
   → target separate stack/config environment and supply environment-specific parameters.

##### 3.2.4.35.5 Step 5 — Need fast development iteration?
   → `sam sync` / `sam sync --watch`.

##### 3.2.4.35.6 Step 6 — Need to preview infrastructure impact?
   → CloudFormation change set.

##### 3.2.4.35.7 Step 7 — Deployment failed?
   → inspect CloudFormation events/rollback.

##### 3.2.4.35.8 Step 8 — Deployment succeeded?
   → run development endpoint/integration/event tests.

#### 3.2.4.36 Exam-Level Knowledge Frame

Know these cold:

**SAM template**
→ serverless IaC definition transformed through CloudFormation.

**CloudFormation stack**
→ collection of AWS resources managed as a unit.

**Stack update**
→ reconcile existing stack with revised template/parameters.

**`sam build`**
→ prepare application/build artifacts.

**`sam deploy`**
→ create/update SAM-backed CloudFormation stack.

**`sam deploy --guided`**
→ interactive initial deployment configuration.

**`samconfig.toml`**
→ reusable SAM CLI deployment configuration.

**SAM config environment**
→ named SAM CLI configuration set; not an AWS environment object.

**Parameters**
→ environment-specific values for shared template.

**Change set**
→ preview proposed CloudFormation changes before execution.

**`sam sync`**
→ accelerated development synchronization.

**`sam sync --watch`**
→ watch and rapidly synchronize development changes.

**CloudFormation events**
→ deployment/update status and failure evidence.

**Deployment success**
≠ application success.

Fastest discriminator:

`prepare SAM artifact?`
→ `sam build`.

`update existing SAM stack?`
→ `sam deploy`.

`same app, different staging environment?`
→ separate stack/config + parameters.

`rapid dev iteration?`
→ `sam sync`.

`preview infrastructure changes?`
→ change set.

`deployment failed?`
→ CloudFormation events.

#### 3.2.4.37 Final Principle

**Treat a development environment as reproducible infrastructure, not a manually maintained collection of resources. Update the existing application stack from the SAM/CloudFormation definition, use environment-specific configuration to target development or staging, use accelerated SAM synchronization for fast inner-loop changes, and then retest the real deployed application.**
