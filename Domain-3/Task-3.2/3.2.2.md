### 3.2.2 Write integration tests and mock APIs for external dependencies

#### 3.2.2.1 Exam and Task Context

##### 3.2.2.1.1 Domain
- Domain 3 is **Deployment**.

##### 3.2.2.1.2 Task
- Task 3.2 is **Test applications in development environments**.

##### 3.2.2.1.3 Skill
- Skill 3.2.2 is **Write integration tests and mock APIs for external dependencies**.
- This skill has two complementary concerns:
  - **integration tests** → prove components actually work together.
  - **mocks** → isolate code from external dependencies when real integration is unnecessary, unavailable, expensive, slow, or difficult to control.

#### 3.2.2.2 Core Mental Model

`UNIT TEST`
→ test business logic in isolation.

`MOCKED DEPENDENCY TEST`
→ test how code behaves when dependency returns controlled responses.

`INTEGRATION TEST`
→ test real components/services together.

`END-TO-END TEST`
→ test a broad application workflow.

Central principle:

**Mocks provide speed and control; cloud integration tests provide realism and confidence. Use both rather than treating either as a complete substitute for the other.**

#### 3.2.2.3 What Is an Integration Test?

AWS describes tests against two or more architectural components as:
→ integration tests.

Example:

`API Gateway`
→ `Lambda`
→ `DynamoDB`.

Test:

`HTTP request`
→ deployed API
→ Lambda executes
→ DynamoDB interaction occurs
→ response/state asserted.

This validates not only application code but also:
- service configuration,
- IAM,
- event/request contracts,
- deployed infrastructure.

#### 3.2.2.4 What Is an External Dependency?

Anything outside the code unit being tested.

Examples:
- Amazon S3,
- DynamoDB,
- SQS,
- SNS,
- external HTTP API,
- payment provider,
- SaaS API,
- database,
- another microservice.

The dependency can be:
→ AWS-managed or third-party.

#### 3.2.2.5 What Is a Mock?

AWS defines a mock as an object in test code that:
→ simulates an external service.

It returns predefined behavior instead of:
→ calling the actual external dependency.

Example:

`application`
→ `mock S3 client`
→ predefined response.

No real S3 request occurs.

#### 3.2.2.6 Mock vs Real Dependency

Real:

`code`
→ AWS SDK
→ DynamoDB
→ real IAM/network/service behavior.

Mocked:

`code`
→ mock DynamoDB client
→ predefined result.

Mock test proves:
→ application reaction to the simulated contract.

It does **not** prove:
→ real DynamoDB integration works.

#### 3.2.2.7 Mock vs Fake

AWS testing guidance describes a fake as:
→ a mock-like replacement that takes shortcuts to simplify/speed testing.

Example:

`real data repository`
→ DynamoDB.

`fake repository`
→ in-memory map.

The fake can have behavior/state rather than only predefined method responses.

#### 3.2.2.8 Mock vs Emulator

`MOCK`
→ replacement object created/configured in test code.

`EMULATOR`
→ standalone/local system that mimics service APIs/behavior.

AWS explicitly distinguishes these.

For the exam:

**mock object**
≠
**local AWS service emulator**.

#### 3.2.2.9 Why Mock External APIs?

Mocks are useful when dependency is:

- slow,
- expensive,
- unavailable,
- rate-limited,
- non-deterministic,
- owned by another team,
- third-party,
- difficult to force into error conditions.

Example:

Payment provider normally succeeds.

Need test:
→ provider returns HTTP 503.

Mock:
→ deterministically return 503.

#### 3.2.2.10 Failure Testing

Mocks are particularly useful for failure scenarios.

Examples:
- HTTP 500,
- HTTP 429,
- timeout,
- malformed response,
- authorization failure,
- dependency unavailable.

These may be difficult or unsafe to reproduce against real systems.

#### 3.2.2.11 Deterministic Testing

Real dependency:
→ state may change.

Mock:
→ same input can always produce same controlled output.

This makes tests:
- repeatable,
- fast,
- suitable for large test suites.

#### 3.2.2.12 Dependency Injection

A strong design for testability:

```text
Business logic
    |
    v
Dependency interface
    |
    +--> real AWS/external client
    |
    +--> mock client in tests
```

The business logic should depend on:
→ an abstraction/client interface,

rather than constructing tightly coupled external clients everywhere.

#### 3.2.2.13 Why Integration Tests Matter in AWS

AWS cloud behavior includes:
- IAM policies,
- resource policies,
- service quotas,
- service configuration,
- event-source mappings,
- networking,
- actual service API behavior.

Mocks generally cannot prove these are correct.

#### 3.2.2.14 AWS Recommendation: Test in the Cloud

AWS Lambda testing guidance emphasizes:
→ local environments cannot fully replicate the cloud.

Cloud-based testing provides the most accurate validation because it uses:
- actual services,
- actual security policies,
- actual configuration,
- actual infrastructure.

Therefore:

**mock-heavy unit tests should still be complemented by cloud testing.**

#### 3.2.2.15 Integration-Test Environment

Use an isolated development/test stack.

Example:

```text
orders-integration-test
├── API Gateway
├── Lambda
└── DynamoDB table
```

Tests:
→ interact only with these resources.

Avoid:
→ production data/resources.

#### 3.2.2.16 Infrastructure as Code for Test Environments

AWS recommends cloud test environments that can be created using IaC.

Benefits:
- repeatability,
- isolation,
- known configuration,
- disposable environments.

Relevant tools:
- AWS SAM,
- CloudFormation,
- AWS CDK where applicable.

This connects to later 3.3.4.

#### 3.2.2.17 Integration Test Structure

Typical:

`ARRANGE`
→ deploy/find test resources and prepare data.

`ACT`
→ invoke system boundary.

`ASSERT`
→ verify response/state/events.

`CLEAN UP`
→ remove/reset test data/resources.

#### 3.2.2.18 AWS SAM Integration Testing

AWS SAM supports automated integration testing workflows.

`sam local start-lambda`
→ starts local endpoint emulating Lambda Invoke API.

Automated tests can invoke that endpoint through:
- AWS SDK,
- AWS CLI.

The same test logic can then target:
→ deployed Lambda in AWS.

#### 3.2.2.19 `sam local start-lambda`

Flow:

`automated integration test`
→ Lambda Invoke API-compatible local endpoint
→ locally running Lambda.

Benefit:
→ test code can use AWS SDK invocation pattern locally.

Then switch endpoint/target:
→ real deployed Lambda.

#### 3.2.2.20 Write Test Once, Run Local and Cloud

AWS SAM documentation describes the pattern:

`same integration test`
→ local Lambda endpoint.

Then:

`same integration test`
→ deployed AWS Lambda.

This reduces separate test implementations.

#### 3.2.2.21 `sam local start-api`

For API Gateway + Lambda applications:

`sam local start-api`
→ local HTTP server
→ Lambda functions mapped to API routes.

Useful for:
- local HTTP integration tests,
- request/response validation.

But:
→ cloud testing is still required for real AWS permissions/configuration.

#### 3.2.2.22 API Gateway Mock Integration

Amazon API Gateway supports a specific integration type:

`MOCK`.

A mock integration:
→ returns a response directly from API Gateway,
→ without invoking a backend.

This is an AWS-native mock API mechanism.

#### 3.2.2.23 Why API Gateway Mock Integration?

Use cases:
- backend not implemented yet,
- dependent frontend/team needs API contract,
- API testing,
- simulate defined responses,
- provision simple API landing/placeholder responses.

Flow:

`client`
→ API Gateway
→ configured MOCK response.

No:
→ Lambda/backend call.

#### 3.2.2.24 API Gateway MOCK Integration Type

API Gateway integration type:

`MOCK`

means:
→ API Gateway itself acts as the integration endpoint.

Contrast:

`AWS_PROXY`
→ Lambda proxy integration.

`HTTP_PROXY`
→ HTTP backend.

`MOCK`
→ no backend request.

#### 3.2.2.25 Mock Integration Request/Response

For REST APIs, mock integration can use:
- integration request mapping,
- integration response,
- status codes.

Example concept:

`scope=internal`
→ return 200.

other:
→ return 500.

This allows controlled API behavior without backend.

#### 3.2.2.26 API Gateway Mock API vs Code Mock

These are different:

`mock object in unit test`
→ exists inside test process.

`API Gateway MOCK integration`
→ deployed API endpoint returns configured response without backend.

The exam wording "mock APIs for external dependencies" makes this distinction especially useful.

#### 3.2.2.27 Mocking a Third-Party API

Application depends on:

`payment.example.com`.

Development test can point application configuration to:

`mock payment API`
→ controlled success/failure responses.

Possible implementation:
→ API Gateway mock integration or test stub service.

Then:

`application`
→ mock endpoint
→ deterministic response.

#### 3.2.2.28 Do Not Hard-Code Mock Endpoint

Use environment-specific configuration:

Development:
`PAYMENT_API_URL = mock endpoint`.

Production:
`PAYMENT_API_URL = real provider`.

This directly connects to 3.1.5.

#### 3.2.2.29 Contract Fidelity

A mock is useful only if it resembles the dependency contract sufficiently.

Model:
- request shape,
- status codes,
- response shape,
- relevant errors.

Danger:
→ mock says dependency behaves one way,
→ real dependency behaves differently.

This creates false confidence.

#### 3.2.2.30 Mock Maintenance

AWS identifies a major downside:
→ mocks must be maintained as APIs/return schemas evolve.

If AWS SDK/service API changes:
→ mock may become stale.

Therefore:
→ integration tests against actual AWS services remain important.

#### 3.2.2.31 Mock Success and Failure Paths

At minimum, mock tests should consider:
- normal success,
- expected business error,
- transient failure,
- timeout,
- malformed/unexpected response where relevant.

The exact cases depend on application contract.

#### 3.2.2.32 Test Doubles Should Not Reimplement AWS

Bad approach:
→ build a huge mock that attempts to reproduce every DynamoDB/SQS behavior.

This becomes:
- complex,
- brittle,
- potentially inaccurate.

Better:
→ mock only behavior needed by isolated test,
→ rely on cloud integration tests for actual AWS semantics.

#### 3.2.2.33 AWS SDK Client Mocking

Application code often calls AWS services through an AWS SDK client.

Testable pattern:

`business service`
→ injected SDK client/interface.

Production:
→ real SDK client.

Unit test:
→ mock/stub implementation.

This avoids:
→ network calls during unit tests.

#### 3.2.2.34 Verify Calls to Mock

Mocks can verify:
- method called,
- expected parameters supplied,
- number of calls,
- application response to result/error.

Example:

`PutItem`
expected:
- correct table,
- correct key,
- correct attributes.

#### 3.2.2.35 Do Not Over-Test Implementation

Prefer asserting business contract.

Fragile:
→ assert every internal method call.

Stronger:
→ assert important dependency interaction and externally visible result.

Mocks should support design verification, not tightly freeze implementation.

#### 3.2.2.36 Integration Test With Real AWS SDK

Integration tests can use AWS SDK from test code:

`test`
→ SDK/API call
→ deployed AWS resource.

Examples:
- invoke Lambda,
- put SQS message,
- read DynamoDB item,
- inspect S3 object.

The test itself may run:
- developer machine,
- CodeBuild,
- CI/CD environment.

#### 3.2.2.37 Credentials for Integration Tests

Integration test process needs:
→ IAM identity/role with permissions to perform test operations.

Apply least privilege.

Example:
- invoke test function,
- call test API,
- read/write test table.

Do not give:
→ broad production permissions.

#### 3.2.2.38 Test Data Isolation

Integration tests should use:
- unique IDs,
- dedicated resources,
- environment-specific prefixes,
- cleanup.

Example:

`orderId = integration-test-<unique-id>`.

This avoids collisions between:
- developers,
- parallel builds,
- previous runs.

#### 3.2.2.39 Parallel Tests

When tests run concurrently:
→ shared mutable resources can cause interference.

Mitigation:
- unique test keys,
- isolated stacks,
- isolated queues/tables where necessary.

This is especially relevant to cloud tests.

#### 3.2.2.40 Eventually Consistent / Asynchronous Behavior

Integration tests may need to wait for:
- asynchronous processing,
- event propagation,
- state transition.

Do not use arbitrary long sleep if avoidable.

Prefer:
→ poll observable state with bounded timeout/backoff.

Example:

`send SQS message`
→ poll DynamoDB until expected item exists
→ fail after timeout.

#### 3.2.2.41 Test Retries vs Application Retries

Do not let test retries hide application defects.

Test retry:
→ handles eventual observation timing.

Application retry:
→ handles transient dependency failure.

These are separate concerns.

#### 3.2.2.42 Mocking Timeout Behavior

Mocks make it easy to simulate:

`external API`
→ timeout.

Then verify application:
- retries appropriately,
- respects timeout,
- returns controlled error,
- does not duplicate unsafe side effects.

This is difficult to reproduce reliably against real external provider.

#### 3.2.2.43 Mocking Throttling

Mock:

`AWS/external API`
→ throttling/429 response.

Verify:
→ backoff/retry/error handling.

Cloud integration test:
→ still needed to validate actual IAM/configuration and real service interaction.

#### 3.2.2.44 Integration Test Cost

Cloud tests can incur:
- service charges,
- deployment time,
- resource management overhead.

AWS notes this trade-off.

Therefore:
→ use fast local/mocked tests for frequent feedback,
→ use cloud tests for realism.

#### 3.2.2.45 Testing Pyramid in AWS Context

A practical model:

```text
          E2E
       Integration
    Unit + mocked deps
```

Bottom:
- many,
- fast,
- cheap.

Top:
- fewer,
- slower,
- realistic.

Not an AWS mandatory ratio; it is a useful testing mental model.

#### 3.2.2.46 What Mocks Cannot Validate

Mocks generally cannot prove:
- IAM policies are correct,
- resource policies are correct,
- service quotas,
- AWS service configuration,
- event-source wiring,
- actual network path,
- current service API behavior.

These require:
→ real cloud tests.

#### 3.2.2.47 What Integration Tests Cannot Replace Efficiently

Real cloud integration tests are poor substitutes for exhaustive:
- business-rule permutations,
- rare failure simulation,
- fast inner-loop unit tests.

These are where:
→ mocks are valuable.

#### 3.2.2.48 Decision Flow

##### 3.2.2.48.1 Step 1 — What Question Are You Answering?

"Does my business logic react correctly?"
→ unit/mock test.

"Do AWS components actually work together?"
→ integration test.

"Does entire user workflow work?"
→ end-to-end test.

##### 3.2.2.48.2 Step 2 — Is Dependency External/Hard to Control?
Yes:
→ mock can provide controlled behavior.

##### 3.2.2.48.3 Step 3 — Do You Need to Validate IAM/Configuration/Wiring?
Yes:
→ real cloud integration test.

##### 3.2.2.48.4 Step 4 — Is Backend Unavailable but API Consumer Needs Contract?
→ API Gateway mock integration/test stub.

##### 3.2.2.48.5 Step 5 — Is Fast Local Lambda Integration Needed?
→ SAM local endpoint (`start-lambda` / `start-api`).

##### 3.2.2.48.6 Step 6 — Run Same/Equivalent Test Against Cloud
→ validate actual AWS environment.

##### 3.2.2.48.7 Step 7 — Isolate Test State
→ dedicated resources/unique data.

##### 3.2.2.48.8 Step 8 — Clean Up
→ make repeated runs deterministic.

#### 3.2.2.49 Practical Pattern Summary

| Requirement | Best testing approach |
|---|---|
| Isolate business logic from AWS/third-party dependency | mock/stub injected dependency |
| Prove actual AWS permissions/configuration/semantics | cloud integration test |
| Test external API failure deterministically | mock controlled error/timeout/throttle |
| Need real deployed dependency behavior | SDK/API call against development resource |
| Async integration test | eventual assertion with bounded timeout |
| Parallel tests share data | unique IDs / isolated resources / cleanup |
| Mock tests pass but cloud fails | inspect IAM, network, service configuration, real contract |

Core rule:

```text
mock
→ deterministic isolated behavior

real integration
→ actual AWS/dependency contract
```

Mocks and integration tests are complementary, not substitutes.

#### 3.2.2.50 Common Exam Traps

##### 3.2.2.50.1 "Mock Test Proves IAM Works"
- False.

##### 3.2.2.50.2 "Mock Test Proves AWS Service Configuration"
- False.

##### 3.2.2.50.3 "Integration Test Must Be End-to-End"
- False.
- integration can cover two or more components.

##### 3.2.2.50.4 "API Gateway MOCK Calls a Backend"
- False.
- it returns configured response without backend integration.

##### 3.2.2.50.5 "Mock and Emulator Are the Same"
- False.

##### 3.2.2.50.6 "Mocks Eliminate Need for Cloud Testing"
- False.

##### 3.2.2.50.7 "Cloud Integration Tests Eliminate Need for Unit Tests"
- False.

##### 3.2.2.50.8 "Use Production Data for Realistic Integration Testing"
- Wrong.
- isolate test environments/data.

##### 3.2.2.50.9 "Hard-Code Test Resource URLs"
- Avoid where environment outputs/configuration can discover them.

##### 3.2.2.50.10 "Mock Every AWS Behavior"
- Poor strategy.
- mock the needed contract and use real AWS integration tests for AWS semantics.

#### 3.2.2.52 Exam-Level Knowledge Frame

Know these cold:

**Unit test**
→ isolated code behavior.

**Mock**
→ replacement object with controlled external behavior.

**Fake**
→ simplified functional replacement.

**Emulator**
→ standalone system imitating service APIs/behavior.

**Integration test**
→ two or more real components working together.

**Cloud integration test**
→ validates actual AWS configuration, IAM and service behavior.

**API Gateway MOCK**
→ API Gateway returns response without backend.

**`sam local start-lambda`**
→ local Lambda Invoke-compatible endpoint for SDK/CLI tests.

**`sam local start-api`**
→ local API Gateway-like HTTP endpoint for Lambda APIs.

**Mocks cannot prove**
→ real IAM, quotas, service configuration, event wiring.

**Cloud tests cannot efficiently replace**
→ fast exhaustive isolated business-logic tests.

Fastest exam discriminator:

**Need controlled dependency failure?**
→ mock.

**Need backend-less API response?**
→ API Gateway MOCK integration.

**Need real IAM/integration confidence?**
→ cloud integration test.

**Need local SDK-driven Lambda integration test?**
→ `sam local start-lambda`.

**Need local HTTP API test?**
→ `sam local start-api`.

Final principle:

**Mock external dependencies to make isolated tests fast, deterministic, and capable of exercising difficult failure paths. Then test important integrations in an isolated AWS environment because only real cloud tests validate IAM, service configuration, event wiring, quotas, and actual managed-service behavior.**
