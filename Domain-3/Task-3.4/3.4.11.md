### 3.4.11 Configure deployment strategies for application releases

#### 3.4.11.1 Exam and Task Context

##### 3.4.11.1.1 Domain and Task
- Domain 3 is **Deployment**.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.11 is **Configure deployment strategies (for example, blue/green, canary, rolling) for application releases**.

##### 3.4.11.1.2 Position Inside Task 3.4
- 3.4.5:
  - use a deployment strategy.
- 3.4.8:
  - perform rollback.
- 3.4.11:
  - configure the rollout behavior itself.

Critical boundary:

```text
3.4.5
→ USE the strategy

3.4.11
→ CONFIGURE the strategy
```

Core question:

**Which AWS deployment settings determine how much of a release is exposed, how quickly rollout progresses, how capacity is preserved, and how health is validated?**

#### 3.4.11.2 Core Mental Model

```text
application version
        |
        v
deployment target
        |
        v
strategy configuration
        |
        +--> initial exposure
        +--> progression interval
        +--> batch/traffic size
        +--> capacity behavior
        +--> target topology
        +--> health validation
        '--> failure/rollback behavior
```

Deployment strategy is:

```text
release-risk policy
→ expressed as concrete AWS settings
```

#### 3.4.11.3 Main Configuration Dimensions

Think in these dimensions:

```text
TARGET
→ instance / task set / Lambda version / environment

INITIAL EXPOSURE
→ 100% / batch / traffic percentage

PROGRESSION
→ immediate / one wait then remainder / repeated increments

CAPACITY
→ reduced / preserved / temporarily increased

TOPOLOGY
→ in-place / replacement targets / separate environments

VALIDATION
→ health checks / alarms / lifecycle hooks / evaluation period

FAILURE
→ stop / rollback / retain old target
```

The AWS service converts those choices into:
- deployment configuration,
- deployment policy,
- alias routing,
- stage canary settings,
- or equivalent service-specific controls.

#### 3.4.11.4 All-at-Once

All-at-once means:

```text
new release
→ 100% exposure immediately
```

Configuration characteristics:
- no percentage progression,
- no batch progression,
- no evaluation interval.

Tradeoff:

```text
fastest
+
simplest
-
largest immediate blast radius
```

Service behavior differs:
- CodeDeploy Lambda/ECS:
  - all traffic shifts immediately.
- Elastic Beanstalk:
  - application version is deployed to all instances simultaneously,
  - AWS documents a short service interruption.

Exam rule:

```text
100% immediately
→ all-at-once
```

#### 3.4.11.5 Canary

Canary is a **two-step** traffic model:

```text
initial percentage
→ wait/evaluate
→ remaining traffic
```

Example:

```text
10%
→ wait 5 minutes
→ remaining 90%
```

Configuration requires:
- initial percentage,
- interval/evaluation time.

CodeDeploy concept:

```text
TimeBasedCanary
```

High-value discriminator:

```text
small percentage
→ wait
→ all remainder
= canary
```

#### 3.4.11.6 Linear

Linear uses:
- repeated equal increments,
- separated by fixed intervals.

Example:

```text
10%
→ wait
20%
→ wait
30%
→ ...
100%
```

Configuration requires:
- percentage per step,
- interval.

CodeDeploy concept:

```text
TimeBasedLinear
```

High-value discriminator:

```text
same percentage repeatedly
→ linear
```

#### 3.4.11.7 Canary vs Linear

##### 3.4.11.7.1 Canary

```text
10%
→ wait
→ 100%
```

Purpose:
- validate a small production sample before full rollout.

##### 3.4.11.7.2 Linear

```text
10%
→ 20%
→ 30%
→ ...
```

Purpose:
- progressively increase exposure in repeated equal steps.

Fast rule:

```text
initial step + remainder
→ canary

equal repeated increments
→ linear
```

#### 3.4.11.8 Rolling

Rolling updates:
- targets in batches.

```text
fleet
→ batch 1
→ batch 2
→ batch 3
→ ...
```

Primary configuration:
- batch size,
- health/progression behavior.

During rollout:
- old and new versions can coexist in the same environment.

This is target-oriented rather than:
- primarily traffic-percentage-oriented.

#### 3.4.11.9 Rolling Batch Size

Elastic Beanstalk rolling deployment can define batch size as:
- fixed instance count,
- percentage of fleet.

Example:

```text
12 instances
25% batch
→ about 3 instances per batch
```

Tradeoff:

```text
smaller batch
→ lower blast radius
→ longer deployment

larger batch
→ faster deployment
→ more simultaneous change
```

#### 3.4.11.10 Rolling with Additional Batch

Standard rolling can temporarily reduce available capacity because:
- the current batch is taken out of service while updated.

If full capacity must be maintained:

```text
RollingWithAdditionalBatch
```

Flow:

```text
launch temporary batch
→ roll update
→ maintain full capacity
→ remove extra capacity
```

Tradeoff:
- more temporary resources,
- potentially longer deployment,
- better capacity preservation.

Exam clue:

```text
rolling
+
no capacity reduction allowed
→ rolling with additional batch
```

#### 3.4.11.11 Immutable

Immutable deployment means:
- do not modify the original instances.

Instead:

```text
old Auto Scaling group
→ version A

temporary/new Auto Scaling group
→ version B
```

After health validation:

```text
new instances
→ replace old instances
```

If candidate fails:

```text
new group removed
→ old instances remain
```

Key distinction:

```text
immutable
→ replacement instances

rolling
→ existing fleet updated in batches
```

#### 3.4.11.12 Elastic Beanstalk Traffic Splitting

Traffic splitting provides:
- canary-style real-production validation.

Configuration includes:

```text
NewVersionPercent
+
EvaluationTime
```

Example:

```text
15% traffic
→ new instance set
→ evaluate 10 minutes
→ if healthy, shift remainder
```

Important distinction:

```text
traffic splitting
→ one Elastic Beanstalk environment
→ fresh candidate instance set
→ percentage of real traffic

blue/green
→ two separate environments
```

#### 3.4.11.13 Elastic Beanstalk DeploymentPolicy

Elastic Beanstalk exposes the strategy through:

```text
aws:elasticbeanstalk:command
→ DeploymentPolicy
```

Relevant values:
- `AllAtOnce`
- `Rolling`
- `RollingWithAdditionalBatch`
- `Immutable`
- `TrafficSplitting`

Example:

```yaml
option_settings:
  aws:elasticbeanstalk:command:
    DeploymentPolicy: Rolling
    BatchSizeType: Percentage
    BatchSize: 25
```

Meaning:

```text
rolling deployment
→ 25% of fleet per batch
```

#### 3.4.11.14 Elastic Beanstalk Health Settings

Deployment policy alone does not fully determine rollout safety.

Relevant health-related controls include:
- healthy threshold,
- ignore health check,
- command timeout.

Mental model:

```text
strategy
+
health gate
→ effective rollout behavior
```

If:
- unhealthy releases must not progress,

then:
- do not configure behavior that ignores failed health checks.

#### 3.4.11.15 CodeDeploy Deployment Configuration

In CodeDeploy, a **deployment configuration** controls rollout behavior.

Meaning differs by compute platform:

```text
Lambda
→ traffic shifting

ECS
→ traffic shifting

EC2 / On-Premises
→ minimum healthy hosts
```

Do not assume:
- one configuration model applies identically to every platform.

#### 3.4.11.16 CodeDeploy Lambda Strategies

Lambda CodeDeploy supports:
- all-at-once,
- canary,
- linear.

Traffic moves between:
- old published Lambda version,
- new published Lambda version,
through:
- alias routing.

Predefined examples:

```text
CodeDeployDefault.LambdaAllAtOnce
```

```text
CodeDeployDefault.LambdaCanary10Percent5Minutes
```

```text
CodeDeployDefault.LambdaLinear10PercentEvery1Minute
```

Decode the semantics:

```text
LambdaCanary10Percent5Minutes
→ 10%
→ wait 5 minutes
→ remainder
```

```text
LambdaLinear10PercentEvery1Minute
→ +10%
→ every minute
→ until complete
```

#### 3.4.11.17 Custom CodeDeploy Canary and Linear

Predefined configurations are not:
- the only possible choice.

Custom canary example:

```text
25% traffic
→ wait 45 minutes
→ remaining 75%
```

Concept:

```text
type = TimeBasedCanary
canaryPercentage = 25
canaryInterval = 45
```

Custom linear example:

```text
20%
→ every 5 minutes
→ repeat until complete
```

Concept:

```text
linearPercentage
+
linearInterval
```

#### 3.4.11.18 Lambda Alias Requirement

Gradual Lambda release requires:
- published versions,
- stable alias/traffic-routing mechanism.

Example:

```text
prod alias
├── v41
└── v42
```

During deployment:
- alias traffic weights change.

Do not use:
- repeated overwrites of `$LATEST`
as the controlled gradual-deployment model.

#### 3.4.11.19 AWS SAM DeploymentPreference

AWS SAM can configure Lambda gradual deployment using:

```text
AutoPublishAlias
+
DeploymentPreference
```

Example:

```yaml
AutoPublishAlias: live
DeploymentPreference:
  Type: Canary10Percent5Minutes
```

Conceptually:

```text
SAM
→ publish Lambda version
→ alias
→ CodeDeploy strategy
```

This is one of the clearest infrastructure-as-code paths for Lambda canary/linear deployment.

#### 3.4.11.20 Validation Hooks and Alarms

SAM/CodeDeploy can use:
- `PreTraffic`,
- `PostTraffic` hooks.

Flow:

```text
candidate prepared
→ PreTraffic validation
→ traffic shift
→ PostTraffic validation
```

CodeDeploy can also monitor:
- CloudWatch alarms.

Example:

```text
10% canary
→ error rate increases
→ CloudWatch alarm
→ deployment stops / rollback if configured
```

Key principle:

```text
rollout strategy
→ controls exposure

health signal
→ determines whether progression is acceptable
```

A canary without meaningful validation:
- only limits initial exposure,
- it does not automatically know the release is healthy.

#### 3.4.11.21 Amazon ECS CodeDeploy

For ECS blue/green deployment:

```text
original task set
→ replacement task set
```

CodeDeploy can shift traffic using:
- all-at-once,
- canary,
- linear.

Examples:

```text
CodeDeployDefault.ECSAllAtOnce
```

```text
CodeDeployDefault.ECSCanary10Percent5Minutes
```

```text
CodeDeployDefault.ECSLinear10PercentEvery1Minutes
```

The deployment configuration controls:
- production-traffic transition.

The task-set structure provides:
- blue/green topology.

#### 3.4.11.22 Blue/Green vs Traffic Progression

This distinction is critical.

```text
blue/green
→ WHERE old/new versions run

canary / linear / all-at-once
→ HOW traffic moves
```

Therefore ECS can use:

```text
blue/green
+
all-at-once
```

or:

```text
blue/green
+
canary
```

or:

```text
blue/green
+
linear
```

So:

```text
blue/green
≠ canary
```

and:

```text
blue/green
≠ automatically 50/50
```

#### 3.4.11.23 ECS Network Load Balancer Constraint

Current CodeDeploy documentation gives a strong restriction:

```text
ECS + Network Load Balancer
→ only CodeDeployDefault.ECSAllAtOnce
```

Therefore:

```text
ECS + NLB + predefined canary/linear
→ reject
```

This is a high-value exam rule.

#### 3.4.11.24 Blue/Green

Generic blue/green topology:

```text
BLUE
→ current production

GREEN
→ candidate
```

Configure:
- separate old/new target sets or environments,
- traffic switch mechanism,
- health validation,
- old-target retention/termination behavior.

Then:

```text
validate GREEN
→ move production traffic
```

The defining characteristic:
- old and new targets remain isolated and coexist separately before cutover.

#### 3.4.11.25 Elastic Beanstalk Blue/Green

Elastic Beanstalk blue/green typically uses:

```text
environment A
→ current production

environment B
→ candidate
```

After validation:

```text
swap environment URLs/CNAMEs
```

Benefits:
- strong isolation,
- clean cutover,
- fast reversal if old environment is retained.

Tradeoff:
- temporary duplicate environment cost.

#### 3.4.11.26 Rolling vs Blue/Green vs Immutable

##### 3.4.11.26.1 Rolling

```text
same environment/fleet
→ existing targets updated in batches
```

##### 3.4.11.26.2 Blue/Green

```text
separate old/new targets or environments
→ traffic switch
```

##### 3.4.11.26.3 Immutable

```text
fresh replacement instances
→ original instances untouched during validation
→ same environment ultimately continues
```

These are related:
- risk-reduction approaches.

They are not:
- the same deployment model.

#### 3.4.11.27 API Gateway Canary Context

REST API stages can support:
- canary release settings.

Concept:

```text
prod stage
├── most traffic → baseline deployment
└── configured percentage → canary deployment
```

This is:
- API Gateway's service-specific canary mechanism.

Do not confuse it with:
- CodeDeploy Lambda canary.

Same strategy concept:
- different AWS objects.

#### 3.4.11.28 EC2/On-Premises CodeDeploy

For EC2/on-premises, CodeDeploy deployment configuration focuses on:
- minimum healthy hosts.

This is different from:
- Lambda/ECS traffic percentages.

Custom threshold can use:
- `HOST_COUNT`,
- `FLEET_PERCENT`.

Example:

```text
FLEET_PERCENT = 75
```

Meaning:
- deployment progression must preserve the configured healthy-host threshold.

Exam rule:

```text
EC2 CodeDeploy rollout safety
→ minimum healthy hosts
```

#### 3.4.11.29 Deployment Configuration vs Deployment Group

CodeDeploy distinction:

```text
deployment configuration
→ HOW rollout proceeds

deployment group
→ WHICH targets/settings participate
```

Deployment group can include:
- target resources,
- alarms,
- rollback configuration,
- load balancer details,
- environment-specific deployment context.

Do not confuse:
- strategy definition,
- target grouping.

#### 3.4.11.30 Deployment Configuration vs Pipeline

CodePipeline:

```text
→ orchestrates stages/actions
```

CodeDeploy/service deployment configuration:

```text
→ controls rollout semantics
```

Example:

```text
CodePipeline Prod stage
→ CodeDeploy action
→ canary deployment configuration
```

The pipeline does not inherently define:
- the canary percentage.

#### 3.4.11.31 Deployment Strategy vs Runtime Configuration

3.4.10:

```text
runtime configuration
→ which backend/value is selected
```

3.4.11:

```text
deployment strategy
→ how exposure to a new release progresses
```

Example:

```text
API stage variable
→ selects Orders:prod

CodeDeploy canary
→ controls traffic from Lambda v41 to v42
```

Different concerns.

#### 3.4.11.32 Deployment Strategy vs Rollback

3.4.11 configures:
- rollout.

3.4.8 covers:
- recovery from bad rollout.

Strategy influences rollback characteristics:

```text
blue/green
→ old target can remain available

canary
→ small initial blast radius

rolling
→ rollback may require another batch rollout
```

But:

```text
strategy
≠ rollback itself
```

#### 3.4.11.33 Strategy Selection by Requirement

```text
100% immediately?
→ all-at-once

small initial traffic sample?
→ canary

equal repeated traffic increments?
→ linear

update instances in batches?
→ rolling

rolling with no capacity reduction?
→ rolling with additional batch

do not modify existing instances?
→ immutable

→ blue/green

Elastic Beanstalk real-traffic canary?

```

#### 3.4.11.34 Key Tradeoffs

##### 3.4.11.34.1 Blast Radius

```text
all-at-once
→ highest immediate exposure

rolling
→ batch-sized exposure

canary
→ small first traffic sample

linear
→ progressively larger exposure

blue/green before cutover
→ candidate can remain isolated
```

##### 3.4.11.34.2 Capacity

```text
rolling
→ can reduce capacity temporarily

rolling + additional batch
→ preserves capacity

immutable
→ temporary replacement capacity

traffic splitting
→ duplicate candidate capacity

blue/green
→ duplicate target/environment capacity
```

##### 3.4.11.34.3 Speed

```text
all-at-once
→ fastest

canary
→ includes evaluation wait

linear
→ repeated intervals

rolling
→ multiple target batches

immutable / blue-green
→ replacement-capacity provisioning
```

Exact duration:
- service and workload dependent.

#### 3.4.11.35 Canary Percentage and Evaluation Time

Canary percentage is a risk/signal tradeoff.

Smaller canary:

```text
blast radius ↓
signal volume ↓
```

Larger canary:

```text
signal volume ↑
blast radius ↑
```

Evaluation time must be:
- long enough to observe meaningful behavior,
- short enough to avoid unnecessary release delay.

There is no universal correct percentage/time.
The configuration should match:
- workload traffic,
- failure-detection characteristics.

#### 3.4.11.36 Linear Step Size

Smaller step:

```text
more gradual
more intervals
longer deployment
```

Larger step:

```text
faster
more traffic exposed per step
```

Again:
- risk vs speed.

#### 3.4.11.37 Common Failure Patterns

##### 3.4.11.37.1 Canary Behaves Like Linear
Cause:
- wrong deployment configuration semantics.

Remember:

```text
canary
→ first percentage + remainder

linear
→ repeated equal percentage
```

##### 3.4.11.37.2 Rolling Reduces Capacity Unexpectedly
Cause:
- standard rolling behavior.

If full capacity is mandatory:
- use rolling with additional batch.

##### 3.4.11.37.3 Beanstalk Candidate Proceeds Despite Poor Health
Check:
- health threshold,
- ignore-health-check setting,
- timeout/progression settings.

##### 3.4.11.37.4 Lambda Gradual Deployment Uses `$LATEST`
Problem:
- no stable immutable release pair.

Use:
- published versions,
- alias-based routing,
- CodeDeploy/SAM strategy.

##### 3.4.11.37.5 ECS Canary with NLB
Reject:
- predefined canary/linear configuration.

Use:
- `CodeDeployDefault.ECSAllAtOnce` for the documented NLB constraint.

##### 3.4.11.37.6 Pipeline Has Canary Stage but 100% Moves Immediately
Likely issue:
- deployment provider/configuration,
not:
- pipeline-stage naming.

##### 3.4.11.37.7 Blue/Green Assumed to Mean Gradual Traffic
Wrong.
Blue/green defines:
- old/new target topology.

Traffic shift can still be:
- all-at-once,
- canary,
- linear.

##### 3.4.11.42.3 Final Principle
- **Configure deployment strategies by translating release-risk requirements into concrete AWS rollout parameters. Canary uses an initial percentage and wait interval before shifting the remainder; linear uses repeated equal percentages at fixed intervals; rolling uses target batches; rolling with an additional batch preserves capacity; immutable uses fresh replacement instances; and blue/green keeps old and new targets or environments separate. For CodeDeploy, Lambda and ECS deployment configurations control traffic shifting while EC2/on-premises configurations control minimum healthy hosts. Elastic Beanstalk exposes deployment policy, batch size, health settings, and traffic-splitting percentage/evaluation time. Pair rollout settings with meaningful health validation, and keep target topology, traffic progression, pipeline orchestration, runtime configuration, and rollback conceptually separate.**
