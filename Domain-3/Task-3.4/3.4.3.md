### 3.4.3 Update existing IaC templates

#### 3.4.3.1 Exam and Task Context

##### 3.4.3.1.1 Domain and Task
- Domain 3 is **Deployment**.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.3 is **Update existing IaC templates (for example, AWS SAM templates, AWS CloudFormation templates)**.

##### 3.4.3.1.2 Position Inside Task 3.4
- 3.2.4:
  - deploy stack updates during development/testing.
- 3.3.4:
  - implement/deploy IaC for automated deployment testing.
- 3.4.3:
  - **change the IaC definition itself as part of application delivery**.

Core question:

**When an application release changes infrastructure or deployment configuration, how do you modify the existing declarative template safely instead of manually changing deployed resources?**

#### 3.4.3.2 Core Mental Model

```text
existing template
→ requirement changes
→ modify template
→ validate
→ preview changes
→ deploy stack update
→ CloudFormation reconciles resources
```

The source of truth should remain:
- **the version-controlled template**,

not:
- manually modified AWS resources.

#### 3.4.3.3 Infrastructure and Code Evolve Together

##### 3.4.3.3.1 Release Scope
A release can include:
- new application code,
- new environment variables,
- new queue/topic,
- new IAM permissions,
- new API routes,
- new event-source mappings.

If those resources are IaC-managed:
- update the template,
- release infrastructure and application changes together.

##### 3.4.3.3.2 Example

```text
v1:
API Gateway
→ Lambda
→ DynamoDB

v2:
API Gateway
→ Lambda
→ SQS
→ Worker Lambda
→ DynamoDB
```

The v2 release requires:
- queue,
- worker Lambda,
- permissions,
- event source,
- application code.

Those changes should be represented declaratively in:
- AWS SAM,
- AWS CloudFormation.

#### 3.4.3.4 CloudFormation Update Model

##### 3.4.3.4.1 Desired-State Change

```text
template v1
→ current desired state

template v2
→ new desired state

CloudFormation
→ calculate and apply required differences
```

##### 3.4.3.4.2 Possible Update Outcomes
A property/template change can result in:
- no interruption,
- some interruption,
- replacement,
- creation,
- deletion.

The exact effect depends on:
- resource type,
- property being modified.

##### 3.4.3.4.3 Critical Principle
- **Small template diff does not imply small operational impact.**
- Always understand:
  - property update behavior,
  - replacement risk,
  - stateful-resource consequences.

#### 3.4.3.5 Logical IDs and Resource Identity

##### 3.4.3.5.1 Logical ID
Example:

```yaml
Resources:
  OrdersTable:
    Type: AWS::DynamoDB::Table
```

`OrdersTable`:
- is the CloudFormation logical ID.

##### 3.4.3.5.2 Physical ID
- Logical ID:
  - template identity.
- Physical ID:
  - actual deployed AWS resource identity/name.

##### 3.4.3.5.3 Rename Risk
Changing a logical ID can be interpreted as:

```text
remove old resource
+
add new resource
```

not:
- rename existing resource.

This can cause:
- replacement,
- deletion,
- data risk for stateful resources.

#### 3.4.3.6 Parameters, References, and Outputs

##### 3.4.3.6.1 Parameters
Use parameters for values that vary by:
- environment,
- deployment.

Example:

```yaml
Parameters:
  Environment:
    Type: String
    AllowedValues:
      - dev
      - test
      - prod
```

##### 3.4.3.6.2 Avoid Environment Forks
Prefer:

```text
template.yaml
+
environment parameters
```

over duplicated:

```text
template-dev.yaml
template-test.yaml
template-prod.yaml
```

when architecture is otherwise the same.

##### 3.4.3.6.3 Intrinsic Functions
High-value functions:
- `Ref`
  - parameter/resource reference.
- `Fn::GetAtt`
  - resource attribute.
- `Fn::Sub`
  - string substitution.
- Conditions:
  - conditional resource/property behavior.

Use them instead of:
- hard-coded resource identities.

##### 3.4.3.6.4 Pseudo Parameters
Useful examples:
- `AWS::AccountId`
- `AWS::Region`
- `AWS::StackName`
- `AWS::Partition`
- `AWS::URLSuffix`

These improve:
- portability,
- environment independence.

##### 3.4.3.6.5 Outputs
Expose values needed after deployment, for example:
- API URL,
- queue ARN,
- resource identifier.

Pipeline/test flow:

```text
stack update
→ stack output
→ integration test
```

#### 3.4.3.7 Conditions and Environment Differences

##### 3.4.3.7.1 Conditions
Use conditions when environments genuinely differ structurally.

Example:

```yaml
Conditions:
  IsProd: !Equals [!Ref Environment, prod]
```

Then:

```yaml
Condition: IsProd
```

can control:
- resource creation,
- property selection.

##### 3.4.3.7.2 Parameters vs Conditions
- Parameter:
  - value differs.
- Condition:
  - structure/behavior differs.

Do not create complex condition logic for:
- simple configuration values.

#### 3.4.3.8 AWS SAM Template Updates

##### 3.4.3.8.1 SAM Model
AWS SAM extends CloudFormation with serverless abstractions.

Example:

```yaml
Transform: AWS::Serverless-2016-10-31
```

Common SAM resources:
- `AWS::Serverless::Function`
- `AWS::Serverless::Api`
- `AWS::Serverless::HttpApi`
- `AWS::Serverless::StateMachine`

##### 3.4.3.8.2 Update Example
Adding a Lambda environment variable:

```yaml
OrdersFunction:
  Type: AWS::Serverless::Function
  Properties:
    Handler: app.handler
    Environment:
      Variables:
        ORDERS_TABLE: !Ref OrdersTable
```

This is:
- an IaC update.

A manual Lambda console edit is:
- not equivalent.

##### 3.4.3.8.3 Event Source Example

```yaml
Events:
  QueueEvent:
    Type: SQS
    Properties:
      Queue: !GetAtt OrdersQueue.Arn
```

This keeps:
- application architecture,
- event integration
inside the declarative definition.

#### 3.4.3.9 IAM Changes in IaC

##### 3.4.3.9.1 Permissions Follow Features
If code gains a new capability such as:

```text
sqs:SendMessage
```

the IaC should also update:
- execution role/policy.

##### 3.4.3.9.2 Least Privilege
IaC makes IAM:
- reproducible.

It does not make IAM:
- automatically least privilege.

##### 3.4.3.9.3 IAM Capabilities
Some CloudFormation IAM changes require acknowledgment such as:
- `CAPABILITY_IAM`
- `CAPABILITY_NAMED_IAM`

Critical distinction:

```text
CAPABILITY_IAM
→ acknowledgement

deployment/execution role permissions
→ authorization
```

Providing a capability does not fix:
- `AccessDenied`.

#### 3.4.3.10 Validation and Build

##### 3.4.3.10.1 Template Validation
Before deployment:
- validate the template.

For SAM:
- `sam validate`.

Validation can detect:
- syntax,
- structural/template problems.

But:

**validation success does not guarantee deployment success.**

##### 3.4.3.10.2 Build Is Separate
For SAM:

```text
sam validate
→ template validation

sam build
→ build application artifacts

sam deploy
→ create/update stack
```

Do not confuse:
- template correctness,
- artifact build,
- stack deployment.

#### 3.4.3.11 CloudFormation Change Sets

##### 3.4.3.11.1 Purpose

```text
updated template
→ change set
→ inspect proposed resource operations
→ execute
```

A change set can show:
- Add,
- Modify,
- Remove,
- replacement implications.

##### 3.4.3.11.2 Change Set Is Not Deployment
Creating a change set:
- previews changes.

It does not:
- apply them.

##### 3.4.3.11.3 Change Set Is Not a Guarantee
It does not guarantee:
- IAM authorization,
- quota availability,
- application correctness,
- runtime behavior,
- successful dependencies.

##### 3.4.3.11.4 Highest-Value Use
- Detect:
  - destructive or unexpected replacements
before execution.

Especially important for:
- databases,
- buckets,
- queues with retained state,
- stable endpoints,
- other stateful resources.

#### 3.4.3.12 Resource Lifecycle Policies

##### 3.4.3.12.1 `DeletionPolicy`
Controls behavior when:
- resource is removed from template,
- stack is deleted.

Example:

```yaml
DeletionPolicy: Retain
```

##### 3.4.3.12.2 `UpdateReplacePolicy`
Controls:
- what happens to the old physical resource when an update causes replacement.

##### 3.4.3.12.3 Critical Distinction

```text
resource removed / stack deleted
→ DeletionPolicy

resource replaced during update
→ UpdateReplacePolicy
```

##### 3.4.3.12.4 Retain Does Not Mean Still Managed
If retained after removal:
- physical resource can remain,
- but may no longer be managed by that stack.

#### 3.4.3.13 Drift and Manual Changes

##### 3.4.3.13.1 Drift
Example:

```text
template:
memory = 512 MB

console:
memory = 1024 MB
```

Actual resource:
- differs from desired definition.

##### 3.4.3.13.2 Drift Detection
CloudFormation drift detection can identify:
- supported resource properties changed outside CloudFormation.

##### 3.4.3.13.3 Correct Workflow

```text
change template
→ review
→ deploy
```

not:

```text
change production resource manually
→ maybe update template later
```

If an emergency manual change is necessary:
- reconcile the template afterward.

#### 3.4.3.14 Secrets and Dynamic Values

##### 3.4.3.14.1 Do Not Hard-Code Secrets
Do not commit:
- passwords,
- API keys,
- sensitive values
into templates.

##### 3.4.3.14.2 Dynamic References
CloudFormation can reference values from services such as:
- AWS Systems Manager Parameter Store,
- AWS Secrets Manager.

##### 3.4.3.14.3 `NoEcho`
`NoEcho: true` can hide parameter display in some contexts.

It is not:
- a complete secret-management strategy.

#### 3.4.3.15 Stack Update Failures and Rollback

##### 3.4.3.15.1 Stack Events
On failure:

```text
stack update failed
→ inspect stack events
→ identify first meaningful resource failure
→ fix
→ redeploy
```

##### 3.4.3.15.2 Rollback
CloudFormation normally attempts:
- rollback toward the previous stable stack state.

##### 3.4.3.15.3 `UPDATE_ROLLBACK_FAILED`
If rollback itself fails:
- resolve the blocking issue,
- continue recovery.

For this skill:
- know rollback exists,
- know stack events are the primary evidence.

Detailed rollback strategy remains:
- later Task 3.4 material.

#### 3.4.3.16 CI/CD Integration

##### 3.4.3.16.1 Typical Pipeline

```text
source
→ validate template
→ build/package
→ create change set
→ review/approval
→ deploy
→ test
```

##### 3.4.3.16.2 Same Release Definition
Treat:

```text
application artifact version
+
template version
```

as:
- one deployable release definition.

##### 3.4.3.16.3 Environment Promotion
Prefer:
- same template,
- same tested artifact,
- environment-specific parameters/configuration.

Avoid:
- rebuilding a different artifact during promotion,
- manually re-creating infrastructure per environment.

#### 3.4.3.17 Common Failure Patterns

##### 3.4.3.17.1 Manual Resource Exists but Template Does Not
Result:
- next environment is missing it,
- future deployment can diverge.

Fix:
- encode the resource in IaC.

##### 3.4.3.17.2 Logical ID Renamed
Potential result:
- remove old,
- create new.

Check:
- change set,
- update behavior.

##### 3.4.3.17.3 Stateful Resource Replacement
Mitigate by:
- understanding property behavior,
- reviewing change set,
- lifecycle policies where appropriate,
- migration planning.

##### 3.4.3.17.4 Hard-Coded Environment ARN
Risk:
- cross-environment dependency.

Prefer:
- parameters,
- references,
- outputs,
- pseudo parameters.

##### 3.4.3.17.5 Secret in Template
Wrong.
Use:
- Secrets Manager,
- Parameter Store,
- dynamic reference where appropriate.

##### 3.4.3.17.6 Validation Passed, Deployment Failed
Possible reasons:
- missing IAM permission,
- service quota,
- invalid resource combination,
- physical-name collision,
- dependency issue.

##### 3.4.3.17.7 `CAPABILITY_IAM` but AccessDenied
Cause:
- capability is acknowledgment,
- deployment role still lacks permission.

##### 3.4.3.17.8 Correct Template, Wrong Stack
IaC correctness does not protect against:
- incorrect environment targeting.

#### 3.4.3.18 Decision Flow

##### 3.4.3.18.1 Template Evolution

```text
Application release needs AWS resource/config change?
→ update IaC template

Value differs by environment?
→ parameter

Need derived resource value?
→ Ref / GetAtt / Sub

Environment structure differs?
→ condition
```

##### 3.4.3.18.2 Safe Update

```text
Template changed?
→ validate

Need preview?
→ change set

Property may recreate resource?
→ inspect replacement behavior

Need preserve removed resource?
→ DeletionPolicy

Need preserve old replaced resource?
→ UpdateReplacePolicy
```

##### 3.4.3.18.3 Operational Controls

```text
Manual resource differs?
→ drift

Need secret?
→ reference secret-management service

SAM template validation?
→ sam validate

Build serverless artifact?
→ sam build

Apply SAM/CloudFormation update?
→ sam deploy

IAM capability supplied but AccessDenied?
→ check deployment/execution role permission
```

#### 3.4.3.19 Common Exam Traps

##### 3.4.3.19.1 Manual Console Change Is Equivalent to IaC Update
- False.

##### 3.4.3.19.2 Changing Logical ID Is Cosmetic
- False.

##### 3.4.3.19.3 Every Property Update Is In-Place
- False.

##### 3.4.3.19.4 Change Set Executes Automatically
- False.

##### 3.4.3.19.5 Change Set Guarantees Successful Deployment
- False.

##### 3.4.3.19.6 Validation Guarantees Runtime Correctness
- False.

##### 3.4.3.19.7 `CAPABILITY_IAM` Grants Permissions
- False.

##### 3.4.3.19.8 `DeletionPolicy` = `UpdateReplacePolicy`
- False.

##### 3.4.3.19.9 `Retain` Means Resource Stays Managed by Stack
- False.

##### 3.4.3.19.10 `NoEcho` = Secrets Manager
- False.

##### 3.4.3.19.11 Separate Template Required for Every Environment
- False.

##### 3.4.3.19.12 CloudFormation Success = Application Success
- False.

#### 3.4.3.22 Exam-Level Knowledge Frame

##### 3.4.3.22.1 Know These Cold

**IaC template**
→ version-controlled desired infrastructure state.

**Stack update**
→ CloudFormation reconciles current resources with revised template/parameters.

**Logical ID**
→ template identity of resource; changing it can cause remove/add semantics.

**Parameters**
→ deployment-time/environment-specific inputs.

**Outputs**
→ expose deployed values.

**`Ref` / `GetAtt` / `Sub`**
→ derive resource values instead of hard-coding.

**Conditions**
→ conditional resource/property behavior.

**Change set**
→ preview proposed stack operations.

**No interruption / Some interruption / Replacement**
→ CloudFormation property update behavior.

**`DeletionPolicy`**
→ behavior when resource is removed/stack deleted.

**`UpdateReplacePolicy`**
→ behavior of old resource during replacement update.

**Drift**
→ actual resource differs from template.

**`sam validate`**
→ validate SAM template.

**`sam build`**
→ build serverless artifacts.

**`sam deploy`**
→ deploy/update SAM-backed CloudFormation stack.

**IAM capability**
→ acknowledgment, not authorization.

##### 3.4.3.22.2 Fastest Exam Discriminator

```text
feature needs AWS resource?
→ update template

environment value differs?
→ parameter

need derived resource identifier?
→ Ref / GetAtt / Sub

preview production update?
→ change set

resource may be recreated?
→ replacement analysis

preserve removed resource?
→ DeletionPolicy

preserve replaced old resource?
→ UpdateReplacePolicy

manual change differs from template?
→ drift

SAM syntax/template check?
→ sam validate

build artifact?
→ sam build

apply stack update?
→ sam deploy

CAPABILITY_IAM + AccessDenied?
→ deployment/execution role permission
```

##### 3.4.3.22.3 Final Principle
- **When application architecture changes, update the version-controlled IaC definition rather than manually modifying deployed resources. Parameterize environment-specific values, derive resource references instead of hard-coding them, validate the template, preview destructive changes with a change set, understand replacement and lifecycle-policy consequences, deploy through CI/CD, and verify the resulting application.**
