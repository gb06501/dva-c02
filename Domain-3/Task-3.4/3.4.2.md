### 3.4.2 Describe API Gateway stages and custom domains

#### 3.4.2.1 Exam and Task Context

##### 3.4.2.1.1 Domain and Task
- Domain 3 is **Deployment**.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.2 is **Describe API Gateway stages and custom domains**.

##### 3.4.2.1.2 Position Inside Task 3.4
- This skill separates two concerns:
  - **stage** → where an API deployment is exposed,
  - **custom domain** → how clients reach that API through a stable hostname.
- The central question is:

  **Which API deployment environment should receive traffic, and what stable client-facing hostname/path should route to it?**

#### 3.4.2.2 Core Mental Model

##### 3.4.2.2.1 Default Endpoint

```text
client
→ execute-api AWS hostname
→ API Gateway stage
→ API deployment/routes
→ backend
```

##### 3.4.2.2.2 Custom Domain

```text
client
→ api.example.com
→ API Gateway custom domain
→ API mapping
→ API + stage
→ backend
```

##### 3.4.2.2.3 Essential Distinction
- Deployment:
  - **what API snapshot/configuration exists?**
- Stage:
  - **where is that deployment exposed?**
- Custom domain:
  - **what stable hostname do clients use?**
- API mapping:
  - **which API/stage receives that hostname/path?**

#### 3.4.2.3 API Gateway Stages

##### 3.4.2.3.1 Purpose
- A stage is a named API deployment environment.
- Typical names:
  - `dev`,
  - `test`,
  - `staging`,
  - `prod`.

##### 3.4.2.3.2 REST API Deployment Model

```text
API configuration
→ deployment
→ stage
```

- REST API deployment:
  - snapshot of API configuration.
- Stage:
  - references/exposes a deployment,
  - carries stage-specific settings.

Example:

```text
dev  → deployment 18
test → deployment 16
prod → deployment 12
```

##### 3.4.2.3.3 Default REST API URL
Conceptually:

```text
https://{api-id}.execute-api.{region}.amazonaws.com/{stage}
```

- The stage name normally appears in the default REST API invoke URL.

##### 3.4.2.3.4 HTTP API Stages
- HTTP APIs also support named stages.
- HTTP APIs additionally support:
  - `$default` stage.

##### 3.4.2.3.5 `$default` Stage
- `$default` can serve requests without an explicit stage path segment.

```text
https://{api-id}.execute-api.{region}.amazonaws.com/
```

- A stage can therefore exist even when its name is not visible in the URL.

##### 3.4.2.3.6 Automatic Deployment
- HTTP API stages can support automatic deployment.
- API changes can be automatically deployed to the stage.
- This changes release-control behavior; it does not change what a stage represents.

#### 3.4.2.4 Stage-Specific Configuration

##### 3.4.2.4.1 Stage Settings
Depending on API type and feature, stage-specific settings can include:
- logging,
- metrics,
- throttling,
- tracing,
- REST API caching,
- REST API stage variables,
- REST API canary settings,
- HTTP API auto-deploy.

##### 3.4.2.4.2 Stage Variables
- REST API stage variables are:
  - stage-specific key/value configuration.
- They can parameterize integrations.

Example:

```text
dev  → lambdaAlias=dev
test → lambdaAlias=test
prod → lambdaAlias=prod
```

##### 3.4.2.4.3 Stage Variables + Lambda Aliases

```text
API dev stage
→ Lambda dev alias
→ Lambda version 45

API prod stage
→ Lambda prod alias
→ Lambda version 40
```

Keep the abstractions separate:
- API Gateway stage:
  - API environment.
- Lambda alias:
  - stable Lambda version pointer.
- Lambda version:
  - exact published function version.

##### 3.4.2.4.4 Stage Variables Are Not Secret Storage
- Do not store credentials/secrets in stage variables.
- Use an appropriate secrets-management mechanism for sensitive values.

#### 3.4.2.5 Canary Within a REST API Stage

##### 3.4.2.5.1 Model

```text
prod stage
├── 90% → current deployment
└── 10% → candidate deployment
```

##### 3.4.2.5.2 Critical Distinction
- Stage:
  - environment.
- Canary:
  - traffic distribution/release mechanism within the stage.
- A canary is not another environment.

##### 3.4.2.5.3 Scope Boundary
- Recognize REST API stage canary capability here.
- Detailed canary/deployment-strategy design belongs to later Task 3.4 skills.

#### 3.4.2.6 Why Custom Domains Exist

##### 3.4.2.6.1 AWS-Generated Endpoint
Example:

```text
https://abc123.execute-api.eu-central-1.amazonaws.com/prod
```

##### 3.4.2.6.2 Stable Client Identity
Applications often prefer:

```text
https://api.example.com
```

- Custom domains decouple:
  - public API identity,
  - AWS-generated endpoint identity.

#### 3.4.2.7 Custom Domain Components

##### 3.4.2.7.1 Required Conceptual Chain

```text
domain name
+
TLS certificate
+
API Gateway custom domain
+
API mapping
+
DNS
```

##### 3.4.2.7.2 TLS Certificate
- HTTPS requires a certificate covering the hostname.
- AWS Certificate Manager (ACM) is commonly used.

##### 3.4.2.7.3 DNS
- DNS routes/resolves the custom hostname to the API Gateway custom-domain target.
- Amazon Route 53 is commonly used.
- External DNS providers can also be used.

##### 3.4.2.7.4 API Mapping
- Connects:

```text
custom domain + optional path
→ API
→ stage
```

Example:

```text
api.example.com/orders
→ Orders API
→ prod
```

#### 3.4.2.8 API Mapping

##### 3.4.2.8.1 Mapping Keys
One hostname can route different paths to different APIs/stages:

```text
api.example.com
├── /orders    → Orders API / prod
└── /customers → Customers API / prod
```

##### 3.4.2.8.2 Root Mapping
A root/empty mapping can expose:

```text
api.example.com/
→ Orders API / prod
```

- Clients do not need the internal `/prod` stage path in the public URL.

##### 3.4.2.8.3 Base Path Mapping Terminology
- Older REST API material may say:
  - **base path mapping**.
- Current terminology commonly uses:
  - **API mapping**.
- Recognize both as the domain/path-to-API-stage routing concept.

#### 3.4.2.9 Custom Domain vs Stage

##### 3.4.2.9.1 Independent Concerns
One API can have:

```text
dev
test
prod
```

while only production is exposed as:

```text
api.example.com
→ prod
```

##### 3.4.2.9.2 Environment-Specific Domains
Possible:

```text
api-dev.example.com  → dev
api-test.example.com → test
api.example.com      → prod
```

- Custom domains are not required to create environments.
- Stages already provide API environment separation.

##### 3.4.2.9.3 Stable URL During Releases
- API deployment/backend can change behind:
  - `api.example.com`.
- Clients can continue using:
  - the same hostname.

#### 3.4.2.10 Regional and Edge-Optimized Custom Domains

##### 3.4.2.10.1 Regional
- Routes to:
  - API Gateway Regional endpoint.
- ACM certificate:
  - must be in the same Region as the Regional custom domain/API endpoint.

##### 3.4.2.10.2 Edge-Optimized REST API
- Uses:
  - AWS-managed CloudFront distribution.
- ACM certificate:
  - must be in **`us-east-1`**.

##### 3.4.2.10.3 Fast Distinction

```text
Regional
→ Regional API Gateway endpoint
→ certificate in same Region

edge-optimized REST
→ AWS-managed CloudFront
→ certificate in us-east-1
```

##### 3.4.2.10.4 HTTP API
- HTTP API custom domains are:
  - Regional.
- Do not select:
  - edge-optimized custom domain for an HTTP API.

##### 3.4.2.10.5 Private REST API Context
- Private REST APIs support private-access scenarios.
- Current API Gateway capabilities include private custom domain names for supported private REST API configurations.
- Treat this as a specialized case; first identify whether the question describes public Regional/edge-optimized or explicitly private access.

#### 3.4.2.11 DNS, TLS, and Mapping Are Different Jobs

##### 3.4.2.11.1 ACM
- Proves TLS identity for the hostname.

##### 3.4.2.11.2 DNS
- Resolves/routes hostname to API Gateway target.

##### 3.4.2.11.3 API Mapping
- Selects:
  - API,
  - stage,
  - optional path mapping.

##### 3.4.2.11.4 Route 53 Alias
Common pattern:

```text
api.example.com
→ Route 53 alias
→ API Gateway custom-domain target
```

- Do not reduce the solution to "always use CNAME."
- The key requirement is:
  - DNS must route the hostname correctly.

#### 3.4.2.12 CI/CD Context

##### 3.4.2.12.1 Stage as Deployment Target

```text
Git commit
→ build/test
→ create/update API deployment
→ deploy to test stage
→ validate/approve
→ deploy to prod stage
```

##### 3.4.2.12.2 Stable Production Domain

```text
api.example.com
→ prod stage
```

- The custom domain can remain stable across releases.

##### 3.4.2.12.3 CodePipeline Stage vs API Gateway Stage
- CodePipeline stage:
  - group of CI/CD actions.
- API Gateway stage:
  - deployed API environment.
- Same word:
  - different abstraction.

#### 3.4.2.13 Common Failure Patterns

##### 3.4.2.13.1 Generated URL Works, Custom Domain Fails
Likely investigate:
- DNS,
- certificate,
- API Gateway custom-domain configuration,
- API mapping.

The backend/API deployment may already be healthy.

##### 3.4.2.13.2 TLS Error
Check:
- certificate covers hostname,
- certificate is issued/valid,
- correct certificate Region,
- custom-domain configuration.

```text
Regional → certificate same Region
edge-optimized REST → certificate us-east-1
```

##### 3.4.2.13.3 `/prod` Appears in Public URL
- Default REST endpoint normally includes:
  - stage path.
- If requirement is a clean public URL:
  - use custom domain + appropriate API mapping.

##### 3.4.2.13.4 API Changes Not Visible
- API configuration changes may need:
  - deployment to the intended stage.
- Check:
  - deployment/stage association,
  - auto-deploy behavior where applicable.

##### 3.4.2.13.5 Wrong Stage Receives Release
- Artifact/API may be correct.
- Deployment target may be wrong.
- CI/CD should explicitly target:
  - intended API Gateway stage.

#### 3.4.2.14 Decision Flow

##### 3.4.2.14.1 Environment and Routing

```text
Need dev/test/prod API environments?
→ stages

Need REST API configuration snapshot?
→ deployment

Need stable friendly hostname?
→ custom domain

Need hostname/path mapped to API stage?
→ API mapping

Need hostname resolution?
→ DNS

Need HTTPS identity?
→ certificate
```

##### 3.4.2.14.2 Endpoint-Specific Decisions

```text
Regional custom domain?
→ certificate same Region

edge-optimized REST custom domain?
→ certificate us-east-1

HTTP API custom domain?
→ Regional

HTTP API without visible stage path?
→ $default stage
```

##### 3.4.2.14.3 Stage Capabilities

```text
REST-stage-specific integration value?
→ stage variable

gradual REST API production exposure?
→ stage canary
```

#### 3.4.2.15 Common Exam Traps

##### 3.4.2.15.1 Stage = Deployment
- Wrong.
- Deployment:
  - API snapshot.
- Stage:
  - environment/reference exposing deployment.

##### 3.4.2.15.2 API Gateway Stage = CodePipeline Stage
- Wrong.
- They are unrelated abstractions with the same word.

##### 3.4.2.15.3 Custom Domain = Stage
- Wrong.
- Custom domain:
  - hostname/routing.
- Stage:
  - API deployment environment.

##### 3.4.2.15.4 Custom Domain Automatically Configures DNS
- Wrong.
- DNS routing must also be configured.

##### 3.4.2.15.5 ACM Certificate Performs DNS Routing
- Wrong.
- ACM:
  - TLS.
- DNS:
  - hostname resolution.

##### 3.4.2.15.6 Route 53 Selects API Stage
- Wrong.
- API mapping selects:
  - API/stage.

##### 3.4.2.15.7 Stage Variable Is Secret Storage
- Wrong.

##### 3.4.2.15.8 Canary Is a Separate Stage/Environment
- Wrong.
- Canary:
  - traffic split within a stage.

##### 3.4.2.15.9 Custom Domain Requires `/prod`
- Wrong.
- Mapping can hide internal stage path.

##### 3.4.2.15.10 HTTP API Uses Edge-Optimized Custom Domain
- Wrong.
- HTTP API custom domains:
  - Regional.

##### 3.4.2.15.11 Wrong ACM Region
- Regional:
  - same Region.
- Edge-optimized REST:
  - `us-east-1`.

#### 3.4.2.18 Exam-Level Knowledge Frame

##### 3.4.2.18.1 Stage
- Named API deployment environment.
- REST deployment:
  - API configuration snapshot.
- Default REST invoke URL:
  - normally includes stage path.
- HTTP API:
  - supports `$default`.

##### 3.4.2.18.2 Stage Configuration
- REST stage variable:
  - non-secret stage-specific configuration.
- REST canary:
  - traffic split within stage.

##### 3.4.2.18.3 Custom Domain
- Stable friendly client-facing hostname.
- Requires conceptually:
  - certificate,
  - API Gateway custom domain,
  - API mapping,
  - DNS.

##### 3.4.2.18.4 API Mapping
- Maps:
  - custom hostname/path,
  - to API + stage.
- Older term:
  - base path mapping.

##### 3.4.2.18.5 Certificate Region
- Regional:
  - same Region.
- Edge-optimized REST:
  - `us-east-1`.
- HTTP API:
  - Regional custom domain.

##### 3.4.2.18.6 Fastest Exam Discriminator

```text
dev/test/prod API?
→ stage

API snapshot?
→ deployment

friendly stable hostname?
→ custom domain

hostname/path → API stage?
→ API mapping

hostname resolution?
→ DNS

TLS certificate?
→ ACM

Regional cert?
→ same Region

edge-optimized REST cert?
→ us-east-1

REST environment value?
→ stage variable

REST gradual release?
→ canary
```

##### 3.4.2.18.7 Final Principle
- **API Gateway stages represent deployment environments; custom domains represent stable client-facing API identities. A REST API deployment captures an API configuration snapshot, a stage exposes that deployment with environment-specific settings, and a custom domain combines TLS, DNS, and API mappings to route a friendly hostname/path to the correct API stage. Keep deployment, stage, custom domain, mapping, and canary traffic behavior conceptually separate.**
