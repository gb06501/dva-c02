### 3.4.8 Perform application rollbacks by using existing deployment strategies

#### 3.4.8.1 Exam and Task Context

##### 3.4.8.1.1 Domain and Task
- Domain 3 is **Deployment**.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.8 is **Perform application rollbacks by using existing deployment strategies**.

##### 3.4.8.1.2 Position Inside Task 3.4
- 3.4.5:
  - deploy an application version using a strategy.
- 3.4.7:
  - orchestrate deployment across environments.
- 3.4.8:
  - recover a failed/bad release using the existing deployment mechanism.
- 3.4.11:
  - configure deployment strategies.

Critical boundary:

```text
3.4.8
→ PERFORM / recognize rollback

3.4.11
→ CONFIGURE deployment strategy
```

Core question:

**When a release is bad, how do you use the AWS deployment mechanism already in place to restore known-good application behavior?**

#### 3.4.8.2 Core Mental Model

```text
known-good version A
        |
        v
deploy version B
        |
        v
validate / monitor
        |
        +-- healthy → continue
        |
        '-- unhealthy
               |
               v
            rollback
               |
               v
      restore known-good behavior
```

Key principle:

**Rollback is a new release operation, not time travel.**

In multiple AWS services:
- rollback means:
  - redeploying a previous version,
  - rerouting traffic to a retained target,
  - or creating a new rollback execution using previous successful release context.

#### 3.4.8.3 Rollback vs Retry vs Stop vs Fix Forward

##### 3.4.8.3.1 Retry

```text
same release/action
→ try again
```

Use when:
- failure is transient,
- dependency recovered,
- no evidence release itself is bad.

##### 3.4.8.3.2 Stop

```text
halt further deployment progress
```

Stopping does not automatically:
- restore the previous release.

##### 3.4.8.3.3 Rollback

```text
bad release B
→ restore known-good release A
```

Use when:
- candidate is defective,
- health regresses,
- current release should no longer remain active.

##### 3.4.8.3.4 Fix Forward

```text
bad release B
→ corrected release C
→ deploy C
```

Use when:
- rollback is unsafe,
- previous version is incompatible with current data/state,
- corrected release can be deployed faster/safer.

Fast discriminator:

```text
transient failure?
→ retry

bad release?
→ rollback

stop rollout only?
→ stop

old release unsafe?
→ fix forward
```

#### 3.4.8.4 Known-Good Rollback Target

Rollback requires:
- an identifiable previous release.

Examples:

```text
CodeDeploy
→ previous application revision

CodePipeline
→ previous successful stage execution

Lambda
→ previous published version

ECS
→ original task set / previous task definition

Elastic Beanstalk
→ previous application version / retained old environment

CloudFormation
→ previous stable stack state
```

Strong rollback targets are immutable or versioned:

```text
commit SHA
image digest
Lambda published version
versioned application artifact
```

Weak targets:

```text
main
latest
mutable tag
$LATEST
```

Rollback must answer:

**Exactly what known-good state are we restoring?**

#### 3.4.8.5 Automatic vs Manual Rollback

##### 3.4.8.5.1 Automatic

```text
deployment failure / alarm / validation failure
→ configured rollback
→ restore known-good release
```

Benefits:
- reduced recovery time,
- consistent reaction,
- less operator delay.

##### 3.4.8.5.2 Manual

```text
operator detects bad release
→ selects known-good state
→ initiates rollback/redeployment
```

Useful when:
- failure is business-visible but not automatically detectable,
- automatic rollback is not configured,
- operator judgment is required.

Both are valid.
The service/strategy determines:
- exact mechanics.

#### 3.4.8.6 CodeDeploy Rollback Model

##### 3.4.8.6.1 Core Rule
AWS CodeDeploy rollback means:

```text
previously deployed revision
→ NEW deployment
```

Not:

```text
reactivate old deployment object
```

Example:

```text
revision A
→ deployment #1 successful

revision B
→ deployment #2 failed

rollback to A
→ deployment #3
```

The rollback gets:
- a new deployment ID.

This is a high-value exam distinction.

##### 3.4.8.6.2 Automatic Rollback
CodeDeploy can automatically roll back when configured for:
- deployment failure,
- configured CloudWatch alarm conditions.

Result:

```text
last known-good revision
→ redeployed as new deployment
```

Rollback configuration can be:
- defined on deployment group,
- overridden for an individual deployment.

##### 3.4.8.6.3 Manual Rollback
If automatic rollback is unavailable/not configured:

```text
select previous known-good revision
→ create new deployment
```

Manual rollback is still:
- a new deployment.

#### 3.4.8.7 CodeDeploy and CloudWatch Alarms

A CodeDeploy deployment group can use:
- CloudWatch alarms.

Flow:

```text
deployment starts
→ metric monitored
→ alarm enters ALARM
→ deployment stops
→ automatic rollback can restore known-good revision
```

Important distinction:

```text
alarm
→ can stop deployment

automatic rollback configuration
→ restores previous revision
```

Do not assume:
- attaching an alarm alone enables rollback.

The source material records:
- up to 10 CloudWatch alarms can be associated with a deployment group.

Useful health signals:
- 5xx/error rate,
- latency,
- unhealthy targets,
- business/application error metric,
- deployment validation failure.

#### 3.4.8.8 CodeDeploy EC2/On-Premises Rollback

For EC2/on-premises:

```text
bad revision B
→ redeploy previous revision A
```

Important:
- failed deployment may already have:
  - copied files,
  - executed lifecycle scripts,
  - modified instances.

Therefore:

```text
deployment failed
≠ instances are untouched
```

Rollback/redeployment restores:
- intended application revision.

#### 3.4.8.9 Lambda Rollback

##### 3.4.8.9.1 Published Versions and Aliases
Strong deployment model:

```text
published version 42
published version 43

prod alias
→ active release
```

During gradual release:

```text
prod alias
├── old version
└── candidate version
```

If candidate fails:

```text
traffic
→ return to previous published version
```

##### 3.4.8.9.2 Why Alias Matters
Callers use:

```text
function:prod
```

rather than:
- numbered version ARN directly.

This separates:
- stable invocation identity,
- active release identity.

##### 3.4.8.9.3 `$LATEST`
`$LATEST` is mutable.

Therefore:
- it is weak as rollback identity.

Prefer:
- published versions,
- alias-based routing.

#### 3.4.8.10 ECS Blue/Green Rollback

CodeDeploy ECS blue/green uses:

```text
original task set
+
replacement task set
```

Traffic moves:
- original → replacement.

If validation fails and rollback is configured:

```text
deployment fails
→ components return toward starting state
→ traffic returns to original task set
```

If rollback is not configured:

```text
deployment fails
→ current deployment state may remain
```

Critical exam rule:

**Failed deployment does not universally imply automatic restoration.**

#### 3.4.8.11 ECS Validation Hooks

ECS CodeDeploy lifecycle hooks can validate the replacement task set.

Example:

```text
AfterAllowTestTraffic
→ Lambda validation
→ evaluate candidate
```

If validation fails and rollback is configured:

```text
candidate rejected
→ rollback
```

Principle:

```text
rollback quality
depends on
validation quality
```

#### 3.4.8.12 Strategy-Specific Rollback

##### 3.4.8.12.1 Canary

```text
90% old
10% new
```

Failure:

```text
new → 0%
old → 100%
```

Benefit:
- failure can be detected while blast radius is small.

##### 3.4.8.12.2 Linear

```text
10% new
→ 20%
→ 30%
→ ...
```

Failure mid-rollout:

```text
stop progression
→ restore traffic to known-good target
```

##### 3.4.8.12.3 Blue/Green

```text
BLUE
→ old

GREEN
→ candidate
```

Failure after cutover:

```text
traffic
→ switch back to BLUE
```

Fast rollback depends on:
- old environment/target still existing and being healthy.

##### 3.4.8.12.4 Rolling
Mid-rollout may leave mixed fleet:

```text
some targets → A
some targets → B
```

Rollback can require:
- another rolling deployment of A.

Therefore:
- rolling rollback may take time.

##### 3.4.8.12.5 Immutable
Candidate is deployed to replacement instances.

```text
old fleet → A
new fleet → B
```

If B fails:

```text
discard new fleet
→ keep original A
```

Benefit:
- original instances were not modified.

#### 3.4.8.13 Elastic Beanstalk Rollback

##### 3.4.8.13.1 Traffic Splitting
Elastic Beanstalk traffic splitting uses:
- old instances,
- new candidate instances,
- percentage-based traffic.

If candidate fails or deployment is aborted:

```text
traffic → old instances
new instances → terminated
```

The source material records this as:
- quick rollback,
- without client-traffic impact for this strategy.

##### 3.4.8.13.2 Abort vs Rollback
Aborting an in-progress deployment:

```text
stop candidate rollout
→ return traffic to old instances
```

is not the same as:

```text
completed bad release
→ redeploy previous application version
```

##### 3.4.8.13.3 Previous Application Version
After a completed bad deployment:

```text
select previous application version
→ deploy it to environment
```

Again:
- rollback is a deployment operation.

##### 3.4.8.13.4 Blue/Green
Separate environments:

```text
blue
→ old

green
→ new
```

Cutover:
- swap environment URLs/CNAME.

Rollback:
- swap back to blue,
- if blue was retained and remains healthy.

#### 3.4.8.14 CodePipeline Stage Rollback

##### 3.4.8.14.1 Core Model
Current CodePipeline supports:
- manual stage rollback,
- automatic stage rollback.

Rollback target:

```text
previous execution
that succeeded in that stage
```

Result:

```text
NEW rollback execution
```

CodePipeline uses the target execution's:
- source revisions,
- variables,
- artifacts.

Example:

```text
Execution 101
→ Prod succeeded

Execution 102
→ Prod failed

rollback
→ new rollback execution
→ uses 101 release context
```

##### 3.4.8.14.2 Manual Stage Rollback
Flow:

```text
select stage
→ start rollback
→ choose eligible previous successful execution
→ CodePipeline creates rollback execution
```

CLI:

```text
aws codepipeline rollback-stage
```

##### 3.4.8.14.3 Automatic Stage Rollback
A stage can be configured:

```yaml
OnFailure:
  Result: ROLLBACK
```

On stage failure:

```text
rollback
→ most recent eligible successful execution
```

Prerequisite:
- successful execution of that stage must already exist in the current pipeline structure version.

#### 3.4.8.15 CodePipeline Rollback Restrictions

Current AWS restrictions from the source:

```text
source stage
→ cannot be rolled back
```

```text
rollback target
→ must belong to current pipeline structure version
```

```text
rollback execution
→ cannot itself be selected as rollback target
```

And:

```text
PARALLEL execution mode
→ stage rollback unavailable
```

Also:
- rollback-result failure conditions are unavailable in PARALLEL mode.

These are strong exam rejection rules.

#### 3.4.8.16 CodePipeline Rollback vs CodeDeploy Rollback

Do not confuse the two layers.

##### 3.4.8.16.1 CodePipeline Stage Rollback

```text
previous successful pipeline execution context
→ rerun stage
```

##### 3.4.8.16.2 CodeDeploy Rollback

```text
previous application revision
→ new CodeDeploy deployment
```

A CodePipeline rollback stage can itself invoke:
- CodeDeploy.

Therefore:

```text
pipeline rollback
≠ deployment-provider rollback
```

#### 3.4.8.17 CloudFormation Rollback Context

CloudFormation manages:
- infrastructure desired state.

If stack update fails:

```text
CloudFormation
→ rollback toward previous stable stack state
```

Exam clue:

```text
failed IaC stack update
→ CloudFormation rollback/events
```

Do not default to:
- CodeDeploy.

For SAM/CloudFormation applications:
- code and infrastructure may be deployed through the stack,
- so rollback may occur at stack level.

Always ask:

**Which deployment system owns the failed state?**

#### 3.4.8.18 Rollback and Persistent State

Deployment rollback restores:
- application/deployment state.

It does not generally undo:
- database writes,
- consumed messages,
- S3 object changes,
- external API side effects,
- other business effects.

Mental model:

```text
deployment rollback
≠ transaction rollback of everything the application did
```

Example:

```text
bad release B
→ consumed SQS messages incorrectly

rollback to A
→ restores code

but does not
→ recreate deleted messages
→ undo external side effects
```

This is why:
- state compatibility matters.

#### 3.4.8.19 Database and Schema Compatibility

A code rollback can be unsafe if release B introduced:
- destructive schema change,
- incompatible data transformation.

Example:

```text
B migrates schema
→ A no longer understands it
```

Then:

```text
code rollback available
≠ system rollback-safe
```

General engineering guidance:
- backward-compatible schema evolution,
- expand/contract migration,
- decouple schema cutover from code deployment where needed.

Keep this secondary to:
- AWS rollback mechanics.

#### 3.4.8.20 Rollback Readiness

##### 3.4.8.20.1 Preserve Previous Artifacts
Examples:
- Lambda published version,
- ECR image digest,
- Elastic Beanstalk application version,
- CodeDeploy application revision,
- pipeline artifact.

If previous artifact is deleted:

```text
known-good target
→ may no longer be deployable
```

##### 3.4.8.20.2 Prefer Immutable Identity
Strong:

```text
commit SHA
image digest
Lambda version
versioned artifact
```

Weak:

```text
main
latest
mutable tag
$LATEST
```

##### 3.4.8.20.3 Retain Old Blue/Green Target
Fast traffic reversal assumes:
- old target/environment still exists.

Destroying it immediately:
- weakens rollback capability.

#### 3.4.8.21 Monitoring During Rollback

Do not assume:

```text
rollback initiated
→ incident resolved
```

Verify:

```text
rollback execution succeeds
→ expected old version active
→ health checks recover
→ error rate normalizes
→ alarms recover
```

Rollback can itself fail.

Possible causes:
- old artifact missing,
- old version incompatible with current data/state,
- IAM failure,
- hook failure,
- drift,
- schema incompatibility.

#### 3.4.8.22 Rollback Blast Radius and Speed

Deployment strategy determines:
- how much traffic may be affected before rollback.

Conceptually:

```text
all-at-once
→ potentially 100% exposed

canary
→ small first exposure

linear
→ progressively increasing exposure

rolling
→ subset of instances

blue/green before cutover
→ potentially no production exposure
```

Rollback speed also varies:

```text
traffic switch back
→ often fast

redeploy old artifact
→ deployment time required

rebuild old source
→ slower and less deterministic
```

Therefore:
- preserve known-good artifacts,
- do not depend on rebuilding during an incident.

#### 3.4.8.23 Common Failure Patterns

##### 3.4.8.23.1 CodeDeploy Alarm Stops Deployment but Old Version Is Not Restored
Cause:
- alarm configured,
- automatic rollback not configured.

##### 3.4.8.23.2 Lambda Rollback Target Is `$LATEST`
Problem:
- mutable identity.

Better:
- published version + alias.

##### 3.4.8.23.3 ECS Validation Fails but Replacement State Remains
Possible cause:
- rollback not configured.

Failure:
- does not universally imply restoration.

##### 3.4.8.23.4 Pipeline Stage Rollback Unavailable
Check:
- source stage?
- PARALLEL execution mode?
- target execution from older pipeline structure version?
- rollback execution selected as target?

##### 3.4.8.23.5 Blue/Green Cannot Switch Back Quickly
Possible cause:
- old target/environment already destroyed.

##### 3.4.8.23.6 Rollback Restores Code but Incident Continues
Investigate:
- database/schema incompatibility,
- persistent side effects,
- corrupted data,
- external state.

#### 3.4.8.24 Decision Flow

##### 3.4.8.24.1 Identify Failure

```text
transient execution problem?
→ retry

bad application release?
→ rollback

IaC stack update failed?
→ CloudFormation rollback context
```

##### 3.4.8.24.2 Identify Owner

```text
CodeDeploy?
→ previous revision / traffic reversal

CodePipeline?
→ previous successful stage execution

Lambda?
→ previous published version via alias

ECS blue/green?
→ original task set

Elastic Beanstalk?
→ old instances / previous version / old environment
```

##### 3.4.8.24.3 Identify Strategy

```text
canary / linear?
→ return traffic to old target

blue/green?
→ switch back to retained old target

rolling?
→ redeploy previous version through fleet

immutable?
→ discard replacement fleet
```

##### 3.4.8.24.4 Validate Readiness

```text
known-good artifact exists?
old target still available?
automatic rollback configured?
health signal meaningful?
data/schema compatible?
```

##### 3.4.8.24.5 Verify Recovery

```text
rollback complete?
expected version active?
health recovered?
errors normal?
```

#### 3.4.8.25 Common Exam Traps

##### 3.4.8.25.1 Rollback Reactivates Old CodeDeploy Deployment Object
- False.
- CodeDeploy creates:
  - new deployment of previous revision.

##### 3.4.8.25.2 Failed Deployment Automatically Rolls Back
- False in general.

##### 3.4.8.25.3 CloudWatch Alarm Alone Performs Rollback
- False.
- Alarm can stop deployment.
- Automatic rollback must also be configured.

##### 3.4.8.25.4 Stop = Rollback
- False.

##### 3.4.8.25.5 Retry = Rollback
- False.

##### 3.4.8.25.6 CodePipeline Source Stage Can Roll Back
- False.

##### 3.4.8.25.7 CodePipeline Can Roll Back to Any Historical Execution
- False.

##### 3.4.8.25.8 PARALLEL Pipeline Supports Stage Rollback
- False.

##### 3.4.8.25.9 `$LATEST` Is Ideal Lambda Rollback Target
- False.

##### 3.4.8.25.10 Blue/Green Rollback Requires Rebuilding Old Release
- Usually false if old target was retained.

##### 3.4.8.25.11 Deployment Rollback Undoes Database Writes
- False.

##### 3.4.8.25.12 Rebuilding Old Source Is Best Rollback
- Usually weaker than redeploying preserved known-good artifact.

#### 3.4.8.28 Exam-Level Knowledge Frame

##### 3.4.8.28.1 Know These Cold

**CodeDeploy rollback**
→ previous known-good revision deployed again as a **new deployment**.

**Automatic CodeDeploy rollback**
→ configured deployment failure and/or alarm condition triggers restoration.

**CloudWatch alarm**
→ can stop deployment; rollback requires rollback configuration.

**Lambda rollback**
→ return alias traffic to previous published version.

**ECS blue/green rollback**
→ return traffic to original task set.

**Elastic Beanstalk traffic splitting**
→ traffic returns to old instances; new candidate instances are removed.

**Blue/green rollback**
→ route traffic back to retained old environment/target.

**Rolling rollback**
→ deploy previous version through batches again.

**Immutable failure**
→ discard replacement fleet; old fleet remains.

**CodePipeline stage rollback**
→ new rollback execution using eligible previous successful stage execution context.

**Retry**
→ same release again.

**Stop**
→ halt progression.

**Rollback**
→ restore known-good release.

##### 3.4.8.28.2 Fastest Exam Discriminator

```text
CodeDeploy bad release?
→ redeploy previous known-good revision

automatic rollback on deployment failure?
→ CodeDeploy automatic rollback

automatic rollback on health regression?
→ CloudWatch alarm + CodeDeploy automatic rollback

Lambda gradual release fails?
→ alias traffic back to previous published version

ECS blue/green fails?
→ original task set

Beanstalk traffic split fails?
→ traffic back to old instances

previous pipeline deployment was good?
→ CodePipeline stage rollback

pipeline uses PARALLEL?
→ stage rollback unavailable

transient action failure?
→ retry

failed IaC update?
→ CloudFormation rollback context
```

##### 3.4.8.28.3 Final Principle
- **Perform rollback at the layer that owns the failed release. CodeDeploy restores a known-good application revision by creating a new deployment; CodePipeline stage rollback creates a new rollback execution from an eligible previous successful execution. Traffic-shifting strategies commonly recover by returning traffic to the retained old target, while rolling strategies can require redeploying the previous version through the fleet. Keep retry, stop, rollback, and fix-forward distinct, preserve immutable known-good release identities, and verify health after rollback because deployment rollback does not automatically undo persistent application side effects.**
