### 3.4.6 Commit code to a repository to invoke build, test, and deployment actions

#### 3.4.6.1 Exam and Task Context

##### 3.4.6.1.1 Domain and Task
- Domain 3 is **Deployment**.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.6 is **Commit code to a repository to invoke build, test, and deployment actions**.

##### 3.4.6.1.2 Position Inside Task 3.4
- 3.1.3:
  - repository as versioned deployment source.
- 3.4.5:
  - deploy an application version.
- 3.4.6:
  - repository change starts automated delivery.
- 3.4.7:
  - orchestrate workflow across environments.
- 3.4.9:
  - use branches/labels for release management.

Core question:

**How does a version-controlled source change become the event that starts an automated build → test → deployment workflow?**

#### 3.4.6.2 Core Mental Model

```text
developer
   |
   v
commit
   |
   v
push / remote repository update
   |
   v
source change detected
   |
   v
pipeline execution
   |
   +--> build
   |
   +--> test
   |
   '--> deploy
```

Critical distinction:

```text
commit
≠ build
≠ pipeline execution
≠ deployment
```

The repository change:
- starts the process.

The CI/CD services:
- perform the work.

#### 3.4.6.3 Identities to Keep Separate

##### 3.4.6.3.1 Source Revision
Usually:
- Git commit SHA.

Answers:

```text
Which exact source state changed?
```

##### 3.4.6.3.2 Trigger
Usually:
- repository/source-change event.

Answers:

```text
Why did automation start?
```

##### 3.4.6.3.3 Pipeline Execution
Example:
- CodePipeline execution.

Answers:

```text
Which delivery workflow instance is processing the change?
```

##### 3.4.6.3.4 Source Artifact
Represents:
- the selected source revision entering the pipeline.

##### 3.4.6.3.5 Build Artifact
Examples:
- JAR,
- Lambda ZIP,
- container image,
- packaged SAM/CloudFormation output.

Answers:

```text
What deployable output was produced?
```

##### 3.4.6.3.6 Runtime/Deployment Version
Represents:
- what was actually released.

Strong traceability:

```text
commit SHA
→ pipeline execution
→ source artifact
→ build artifact
→ deployed version
```

#### 3.4.6.4 Commit vs Push

##### 3.4.6.4.1 Local Commit

```text
git commit
→ local repository state changes
```

A local commit:
- is not visible to the remote CI/CD integration yet.

##### 3.4.6.4.2 Push

```text
git push
→ remote repository changes
→ source integration can detect change
```

Exam clue:

```text
developer committed locally
+
pipeline did not start
→ remote repository may not have changed
```

Operationally, the important trigger boundary is:
- the configured remote repository/source reference changing.

#### 3.4.6.5 Repository as CI/CD Source of Truth

A repository commonly contains:
- application source,
- tests,
- dependency manifests,
- build instructions,
- IaC templates,
- deployment configuration,
- non-secret defaults.

Example:

```text
repo/
├── src/
├── tests/
├── buildspec.yml
├── template.yaml
└── package.json
```

A single commit can therefore change:
- code,
- tests,
- infrastructure,
- build behavior,
- deployment definition.

This is why the source revision can represent:
- the complete delivery change.

#### 3.4.6.6 Branch as Pipeline Source

A pipeline normally watches:
- a repository,
- plus a branch/source reference.

Example:

```text
repository
├── feature/*
├── develop
└── main
      |
      v
release pipeline source
```

If pipeline watches:
- `main`,

then a push only to:
- `feature/payment`

does not automatically trigger that pipeline.

Exam clue:

```text
commit exists
+
pipeline did not start
→ verify repository + configured branch/reference
```

Detailed branch/release strategy belongs to:
- 3.4.9.

#### 3.4.6.7 Source Change Detection

##### 3.4.6.7.1 Event-Driven Model

```text
repository change
→ source integration/event
→ pipeline starts
```

Prefer:
- managed event-driven integration where supported.

Avoid reasoning as though:
- every workflow must poll manually.

##### 3.4.6.7.2 External Git
Supported external repositories can integrate through:
- AWS CodeConnections.

Concept:

```text
GitHub / GitLab / Bitbucket / other supported provider
→ CodeConnections
→ CodePipeline
```

Current AWS terminology:
- **AWS CodeConnections**.

Older material may use:
- AWS CodeStar Connections,
- `codestar-connections`.

They refer to the same service lineage.

#### 3.4.6.8 AWS CodePipeline Role

##### 3.4.6.8.1 Orchestration

```text
SOURCE
  |
  v
BUILD
  |
  v
TEST
  |
  v
DEPLOY
```

CodePipeline:
- coordinates stages/actions,
- moves artifacts,
- tracks workflow execution.

It does not normally:
- compile application code itself,
- run arbitrary build commands itself.

##### 3.4.6.8.2 Service Responsibility

```text
CodePipeline
→ orchestrate

CodeBuild
→ build/test

CodeDeploy / CloudFormation / service deploy action
→ deploy
```

This responsibility boundary is a high-value exam discriminator.

#### 3.4.6.9 Source Action and Source Artifact

##### 3.4.6.9.1 Source Action

```text
repository revision
→ source action
→ source artifact
→ downstream action
```

The source action determines:
- which exact source revision enters the workflow.

##### 3.4.6.9.2 Source vs Build Artifact

```text
Git revision
    |
    v
source artifact
    |
    v
CodeBuild
    |
    v
build artifact
```

Example:

```text
source artifact
→ Java source + pom.xml + template.yaml

build artifact
→ JAR / Lambda ZIP / transformed template
```

Do not assume:
- source artifact = deployable artifact.

#### 3.4.6.10 AWS CodeBuild

##### 3.4.6.10.1 Role
CodeBuild performs build/test execution.

Typical flow:

```text
source
→ install dependencies
→ compile/build
→ run tests
→ package
→ publish artifact
```

CodeBuild is not:
- a source repository,
- a full CI/CD orchestrator.

##### 3.4.6.10.2 `buildspec.yml`
A common/default pattern is:

```text
<source-root>/buildspec.yml
```

Typical phases:

```yaml
phases:
  install:
  pre_build:
  build:
  post_build:
```

A buildspec can define:
- commands,
- phases,
- artifacts,
- test report settings.

Important correction:
- a repository-hosted `buildspec.yml` is common,
- but CodeBuild does not require every buildspec to be stored at the default repository path.

#### 3.4.6.11 Tests as Pipeline Gates

##### 3.4.6.11.1 Correct Flow

```text
commit
→ build
→ tests
     |
     +-- PASS → continue
     |
     '-- FAIL → stop
```

CI/CD does not mean:

```text
every commit
→ production
```

It means:

```text
every relevant change
→ automated verification/delivery workflow
```

##### 3.4.6.11.2 Test Reports
CodeBuild can create:
- structured test reports,
- report groups.

But:

```text
test report
≠ pipeline gate by itself
```

The test commands/build result must:
- actually signal failure,
- and the workflow must treat that action as failed.

##### 3.4.6.11.3 Important Failure Distinction
A test report can be:
- failed,
- incomplete,
- successful.

Do not assume:
- every non-successful report means an application assertion failed.

An incomplete report can reflect:
- configuration,
- permission,
- reporting,
- build execution problems.

#### 3.4.6.12 Deployment Action

After successful verification:

```text
approved build artifact
→ deploy action
→ target environment
```

Possible deployment mechanisms include:
- AWS CodeDeploy,
- AWS CloudFormation,
- AWS SAM / CloudFormation,
- Amazon ECS deployment actions,
- AWS Elastic Beanstalk,
- other supported pipeline deploy actions.

The repository trigger is:
- the start of delivery,

not:
- deployment itself.

#### 3.4.6.13 Common Delivery Flows

##### 3.4.6.13.1 Container Application

```text
commit
→ CodePipeline
→ CodeBuild
→ build container
→ push image to ECR
→ deploy image
```

Keep repositories separate:

```text
Git repository
→ source code/history

ECR
→ container images
```

##### 3.4.6.13.2 Serverless Application

```text
commit
→ pipeline
→ build/test
→ SAM build/package
→ CloudFormation/SAM deployment
→ Lambda/API resources updated
```

The commit can contain:
- code changes,
- IaC changes.

##### 3.4.6.13.3 Infrastructure Change

```text
CloudFormation/SAM template change
→ commit
→ pipeline
→ validate/build
→ stack update
```

This connects directly to:
- 3.4.3.

#### 3.4.6.14 CI vs Continuous Delivery vs Continuous Deployment

##### 3.4.6.14.1 Continuous Integration

```text
frequent source integration
→ automated build/test
```

##### 3.4.6.14.2 Continuous Delivery

```text
validated changes remain deployable
→ production release can still require approval
```

##### 3.4.6.14.3 Continuous Deployment

```text
validated change
→ automatically reaches production
```

Therefore:

```text
commit triggers pipeline
≠ commit must automatically reach production
```

#### 3.4.6.15 Manual Approval

Example:

```text
commit
→ build
→ tests
→ deploy test
→ approval
→ deploy production
```

The workflow remains:
- automated around the approval gate.

A repository change can:
- start the workflow,

without:
- granting automatic production release.

Detailed multi-environment orchestration belongs to:
- 3.4.7.

#### 3.4.6.16 Build Once, Promote

Strong model:

```text
source revision
→ build artifact
→ test artifact
→ promote same artifact
```

Weak model:

```text
build for test
→ rebuild for prod
```

Rebuilding can produce:
- a different artifact from the one tested.

Therefore preserve:
- commit identity,
- artifact identity,
- deployment traceability.

#### 3.4.6.17 Source Revision Traceability

##### 3.4.6.17.1 Commit SHA
A commit SHA:
- identifies a particular repository state.

A branch:
- is a movable pointer.

```text
main yesterday → commit A
main today     → commit B
```

Therefore:

```text
main
≠ immutable release identity
```

##### 3.4.6.17.2 Pipeline Execution
Once a pipeline starts:
- the important source identity is the revision associated with that execution.

Example:

```text
08:00 main → commit A → execution #100
08:02 main → commit B → execution #101
```

Execution #100 should remain tied to:
- A.

Execution #101:
- B.

Do not reason:

```text
both came from main
→ same source revision
```

#### 3.4.6.18 Multiple Repository Events

Repositories can produce events such as:
- push,
- pull request,
- merge.

Typical pattern:

```text
PR
→ build/test

merge to main
→ build/test/deploy
```

The configured trigger determines:
- which action occurs.

Do not assume:
- every repository event deploys production.

Detailed PR/branch strategy:
- 3.4.9.

#### 3.4.6.19 Monorepo and Multiple Pipelines

One repository can feed:
- multiple pipelines.

Example:

```text
repo
├── dev pipeline
├── integration pipeline
└── release pipeline
```

A monorepo can contain:
- multiple deployable components.

Concept:

```text
repository topology
≠ deployment topology
```

Where supported, workflows can use:
- branch filters,
- path-aware triggers,
- component-specific build logic.

For this skill, know the principle:
- one repository does not imply one pipeline or one deployable unit.

#### 3.4.6.20 Secrets and Repository Security

##### 3.4.6.20.1 Do Not Commit Secrets
Never store in Git history:
- access keys,
- passwords,
- API tokens,
- private keys,
- database credentials.

If a secret is committed:
- deleting it in a later commit does not erase exposure.

Treat it as:
- compromised,
- rotate/revoke it.

##### 3.4.6.20.2 External Repository Credentials
Prefer:
- managed repository integration such as CodeConnections.

Do not:
- hard-code repository credentials into source.

##### 3.4.6.20.3 Configuration vs Secrets
Repository can contain:
- schemas,
- build definitions,
- IaC,
- non-secret defaults.

Environment-specific/sensitive values should come from appropriate mechanisms such as:
- AWS Secrets Manager,
- Systems Manager Parameter Store,
- AppConfig,
- secure deployment parameters.

#### 3.4.6.21 IAM Role Boundaries

Different CI/CD services normally use:
- different service roles.

Example:

```text
CodePipeline role
→ orchestrates actions / accesses artifacts

CodeBuild role
→ performs build-time AWS calls

CodeDeploy role
→ performs deployment operations
```

If a pipeline action gets `AccessDenied`:
- inspect the role used by that failing action.

Do not automatically:
- modify the developer's IAM user.

Apply:
- least privilege.

#### 3.4.6.22 Common Failure Patterns

##### 3.4.6.22.1 Pipeline Did Not Start

```text
commit pushed
→ no execution
```

Check:

```text
correct repository?
→ correct branch/reference?
→ source trigger enabled?
→ connection healthy?
→ source action configured correctly?
```

Do not start by debugging:
- deployment target.

##### 3.4.6.22.2 Wrong Source Revision Built
Check:
- configured branch,
- source-action revision,
- concurrent executions,
- manual execution,
- repository integration.

Use:
- execution-specific revision,

not:
- current branch HEAD.

##### 3.4.6.22.3 Build Failed
Investigate:
- CodeBuild logs,
- buildspec commands,
- dependencies,
- compilation errors.

Expected:
- downstream deployment should not proceed.

##### 3.4.6.22.4 Tests Failed
Expected:
- stop progression.

Ensure:
- test command returns failure status,
- build action propagates failure.

##### 3.4.6.22.5 Build Succeeded but Deploy Did Not Start
Trace stages:

```text
source ✓
build ✓
test ?
approval ?
deploy ?
```

Possible blockers:
- tests,
- approval,
- missing artifact,
- deploy-action failure.

##### 3.4.6.22.6 Artifact Missing
Check:
- buildspec artifact configuration,
- output artifact names,
- pipeline input/output mapping.

Remember:

```text
build commands succeeded
≠ downstream artifact is configured correctly
```

##### 3.4.6.22.7 Permission Failure
Check:
- the service role of the failing action.

#### 3.4.6.23 Decision Flow

##### 3.4.6.23.1 Trigger

```text
Did source/tests/IaC/build definition change?
→ repository-triggered workflow may apply

Did remote repository change?
→ if no, pipeline cannot detect it

Did correct branch/reference change?
→ compare with source action

External Git?
→ CodeConnections where supported
```

##### 3.4.6.23.2 Execution

```text
workflow orchestration?
→ CodePipeline

build/test commands?
→ CodeBuild

build definition?
→ buildspec

test failure?
→ stop downstream progression

deployment?
→ CodeDeploy / CloudFormation / service-specific action
```

##### 3.4.6.23.3 Traceability

```text
production deployment
→ artifact
→ build
→ source revision
```

Always preserve:
- exact revision identity.

#### 3.4.6.24 Common Exam Traps

##### 3.4.6.24.1 Local Commit Automatically Triggers AWS
- False.
- Remote source must change.

##### 3.4.6.24.2 CodeBuild Is a Source Repository
- False.

##### 3.4.6.24.3 CodePipeline Compiles the Application
- False.
- It orchestrates.

##### 3.4.6.24.4 CodeDeploy Stores Git History
- False.

##### 3.4.6.24.5 ECR Is the Git Repository
- False.
- ECR stores container images.

##### 3.4.6.24.6 CodeArtifact Is the Git Repository
- False.
- CodeArtifact stores software packages.

##### 3.4.6.24.7 Every Commit Must Deploy to Production
- False.

##### 3.4.6.24.8 Branch Name Is Immutable Release Identity
- False.
- Commit SHA identifies an exact revision.

##### 3.4.6.24.9 Deleting Secret in Next Commit Removes Exposure
- False.
- Rotate/revoke it.

##### 3.4.6.24.10 Build Success Means Tests Passed
- Not necessarily.
- Tests must actually run and fail the action when required.

##### 3.4.6.24.11 Source Artifact = Deployment Artifact
- Not necessarily.

##### 3.4.6.24.12 External Git Cannot Trigger AWS CI/CD
- False.
- Supported providers can integrate through managed connections.

#### 3.4.6.27 Exam-Level Knowledge Frame

##### 3.4.6.27.1 Know These Cold

**Commit**
→ exact source revision.

**Push**
→ updates remote repository so CI/CD can observe the change.

**Branch**
→ movable source reference often configured as pipeline input.

**CodePipeline**
→ orchestrates CI/CD actions.

**CodeBuild**
→ executes build/test commands.

**`buildspec.yml`**
→ common CodeBuild command/artifact definition.

**CodeConnections**
→ managed integration for supported external Git providers.

**Source artifact**
→ source revision packaged/passed from source action.

**Build artifact**
→ output created by build/package stage.

**Commit SHA**
→ immutable source revision identity.

**Failed tests**
→ should stop downstream progression when configured correctly.

**CodeDeploy / service-specific deploy action**
→ performs deployment.

##### 3.4.6.27.2 Fastest Exam Discriminator

```text
source/version history?
→ Git repository

source changed; start workflow?
→ source integration / CodePipeline

external Git?
→ CodeConnections

compile/test?
→ CodeBuild

build commands?
→ buildspec

container artifact?
→ ECR

dependency package repository?
→ CodeArtifact

exact source identity?
→ commit SHA

deploy?
→ CodeDeploy / CloudFormation / service-specific action

tests fail?
→ pipeline should stop
```

##### 3.4.6.27.3 Final Principle
- **Skill 3.4.6 is about turning a version-controlled remote source change into an automated delivery event. Keep the source revision, trigger, pipeline execution, source artifact, build artifact, and deployed version separate. CodePipeline orchestrates the workflow, CodeBuild executes build/test commands, CodeConnections integrates supported external repositories, and downstream deployment actions release the validated artifact. Preserve commit-to-artifact-to-deployment traceability and ensure failed validation blocks progression.**
