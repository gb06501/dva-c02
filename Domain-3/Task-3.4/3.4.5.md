### 3.4.5 Deploy an application version by using deployment strategies

#### 3.4.5.1 Exam and Task Context

##### 3.4.5.1.1 Domain and Task
- Domain 3 is **Deployment**.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.5 is **Deploy an application version by using deployment strategies**.

##### 3.4.5.1.2 Position Inside Task 3.4
- 3.4.4:
  - manage application environments.
- 3.4.5:
  - deploy an approved version using a rollout strategy.
- 3.4.6 / 3.4.7:
  - trigger and orchestrate delivery.
- 3.4.8:
  - rollback.
- 3.4.11:
  - configure deployment strategies.

Critical boundary:

```text

→ USE a deployment strategy

```

Core question:

**Given an approved application version and a target environment, how should that version be introduced into production using the required deployment strategy?**

#### 3.4.5.2 Core Mental Model

```text
approved version
      |
      v
target environment
      |
      v
deployment strategy
      |
      v
controlled exposure
      |
      v
health / validation
      |
      v
complete or rollback
```

Keep three dimensions separate:

```text
WHAT?
→ application version

WHERE?
→ target environment

HOW?
→ deployment strategy
```

Example:

```text
Lambda version 42
→ prod alias
→ canary traffic shift
```

#### 3.4.5.3 Deployment Strategy as Risk Control

Deployment strategy controls:
- initial blast radius,
- rollout speed,
- coexistence of old/new versions,
- temporary capacity reduction,
- temporary infrastructure cost,
- observation opportunities,
- ease of stopping/reversing the release.

Typical tradeoff:

```text
speed
vs
availability
vs
blast radius
vs
temporary cost
vs
rollback simplicity
```

There is no universally best strategy.

#### 3.4.5.4 Strategy Families

##### 3.4.5.4.1 All-at-Once
Concept:

```text
old version
→ all targets / all traffic
→ new version
```

Characteristics:
- fastest rollout,
- simplest transition,
- largest immediate blast radius.

Service-specific effect matters:
- Elastic Beanstalk:
  - AWS documents a short service interruption.
- CodeDeploy Lambda/ECS:
  - all traffic shifts to the new version/task set at once.

Exam clue:

```text
fastest deployment
+
temporary interruption/risk acceptable
→ all-at-once
```

##### 3.4.5.4.2 Rolling
Targets are updated in batches:

```text
A B C D

A(new) B(old) C(old) D(old)
→
A(new) B(new) C(old) D(old)
→ ...
```

Characteristics:
- no whole-fleet replacement at once,
- old/new versions coexist temporarily,
- deployment takes longer,
- capacity can temporarily decrease.

Exam clue:

```text
update fleet in batches
→ rolling
```

##### 3.4.5.4.3 Rolling with Additional Batch
Concept:

```text
existing fleet
→ add temporary batch
→ roll deployment
→ remove temporary batch
```

Purpose:
- preserve full capacity during rollout.

Tradeoff:
- extra temporary infrastructure cost.

Exam discriminator:

```text
rolling
→ capacity can drop

rolling + additional batch
→ preserve capacity
```

This terminology is strongly associated with:
- Elastic Beanstalk.

##### 3.4.5.4.4 Canary
Expose a small percentage first:

```text
90% old
10% new
→ observe
→ 100% new if healthy
```

Purpose:
- limit initial blast radius,
- validate with real production traffic.

Exam clue:

```text
10% first
→ wait
→ remainder
→ canary
```

##### 3.4.5.4.5 Linear
Traffic increases by repeated equal increments:

```text
10% new
→ wait
20% new
→ wait
30% new
→ ...
100% new
```

Distinction:

```text
canary
→ initial partial shift + later remainder

linear
→ repeated equal increments
```

Exam clue:

```text
10% every N minutes
→ linear
```

##### 3.4.5.4.6 Blue/Green
Maintain separate old/new target sets or environments:

```text
BLUE
→ current production

GREEN
→ candidate
→ validate
→ switch traffic
```

Benefits:
- strong isolation,
- pre-cutover validation,
- rapid traffic reversal if old environment remains valid.

Tradeoffs:
- extra temporary capacity,
- data/schema compatibility must still be handled.

Critical distinction:

```text
blue/green
→ separate old/new target sets

canary/linear
→ traffic progression
```

They can be combined.

##### 3.4.5.4.7 Immutable
Do not modify existing instances.

```text
old instances
+
new instances with candidate
→ validate
→ replace old instances
```

Purpose:
- avoid partially modified existing fleet.

Tradeoff:
- additional temporary capacity.

Do not automatically equate:
- immutable,
- blue/green.

They are related replacement-oriented models but not identical.

#### 3.4.5.5 Traffic Shifting vs Instance Replacement

Useful classification:

```text
rolling
→ which existing targets are updated and when

immutable
→ create replacement instances instead of modifying existing ones

blue/green
→ separate old/new target sets/environments

canary
→ partial initial traffic exposure

linear
→ repeated incremental traffic exposure

all-at-once
→ immediate full exposure/update
```

Some AWS services combine dimensions.

Example:

```text
ECS blue/green target model
+
CodeDeploy canary traffic shift
```

#### 3.4.5.6 AWS CodeDeploy Model

##### 3.4.5.6.1 Core Objects

```text
application
→ deployment group
→ deployment
→ deployment configuration
```

Key distinction:

```text
deployment group
→ WHERE / target configuration

deployment configuration
→ HOW rollout progresses
```

##### 3.4.5.6.2 Lambda and ECS Traffic Shifting
For Lambda and ECS, CodeDeploy supports:
- all-at-once,
- canary,
- linear.

##### 3.4.5.6.3 Predefined Configuration Names
Examples:

```text
CodeDeployDefault.LambdaAllAtOnce
CodeDeployDefault.LambdaCanary10Percent5Minutes
CodeDeployDefault.LambdaLinear10PercentEvery1Minute
```

Interpretation:

```text
Canary X Percent Y Minutes
→ shift X%
→ wait Y minutes
→ shift remainder
```

```text
Linear X Percent Every Y Minutes
→ shift X%
→ wait Y
→ repeat until complete
```

##### 3.4.5.6.4 ECS Load Balancer Constraint
For CodeDeploy ECS traffic shifting:
- canary/linear scenarios require:
  - Application Load Balancer.
- with Network Load Balancer:
  - only `CodeDeployDefault.ECSAllAtOnce` is supported.

This is a high-value rejection rule.

#### 3.4.5.7 Lambda Deployment Model

##### 3.4.5.7.1 Published Version
Controlled production deployment should use:
- a published Lambda version.

```text
$LATEST
→ publish
→ version 42
```

Published version:
- immutable release identity.

##### 3.4.5.7.2 Alias
Alias:
- stable invocation target,
- mutable pointer/traffic router.

```text
prod alias
├── 90% → v41
└── 10% → v42
```

Do not make clients switch:
- version ARN to version ARN.

Prefer:
- stable alias,
- controlled alias routing.

##### 3.4.5.7.3 SAM DeploymentPreference
AWS SAM can connect:
- version publication,
- alias,
- CodeDeploy traffic shifting.

Example:

```yaml
AutoPublishAlias: live
DeploymentPreference:
  Type: Linear10PercentEvery1Minute
```

Conceptually:

```text
SAM
→ publish version
→ update alias
→ CodeDeploy controls rollout
```

Detailed strategy configuration belongs mainly to:
- 3.4.11.

#### 3.4.5.8 Deployment Validation and Health

##### 3.4.5.8.1 Pre-Traffic Validation

```text
candidate created
→ pre-traffic validation
→ traffic shift starts
```

Purpose:
- prevent obviously broken candidate from receiving normal production traffic.

##### 3.4.5.8.2 Post-Traffic Validation

```text
traffic shifted
→ validate candidate
→ complete deployment
```

Purpose:
- confirm health after exposure.

##### 3.4.5.8.3 CloudWatch Alarms

```text
candidate receives traffic
→ errors rise
→ alarm enters ALARM
→ deployment can stop / rollback behavior can trigger
```

Gradual rollout is useful only when:
- meaningful health signals exist.

##### 3.4.5.8.4 Health Signal Principle

```text
partial exposure
+
useful health signal
=
controlled release decision
```

Without health evidence:
- canary merely delays full exposure.

#### 3.4.5.9 Amazon ECS Strategies

##### 3.4.5.9.1 Rolling ECS Deployment
- Gradually replaces running tasks inside the ECS service.

##### 3.4.5.9.2 CodeDeploy Blue/Green ECS
Creates:
- replacement task set,
- separate traffic target.

Concept:

```text
BLUE task set
→ current

GREEN task set
→ candidate

CodeDeploy
→ validate
→ shift load balancer traffic
```

Traffic shift can be:
- all-at-once,
- canary,
- linear
subject to supported load-balancer configuration.

##### 3.4.5.9.3 Recognition Clues
Look for:
- task-definition revision,
- replacement task set,
- target groups,
- load balancer,
- CodeDeploy deployment group,
- traffic shifting.

#### 3.4.5.10 Elastic Beanstalk Deployment Policies

##### 3.4.5.10.1 Supported Policies
AWS documents:
- All at once.
- Rolling.
- Rolling with additional batch.
- Immutable.
- Traffic splitting.

##### 3.4.5.10.2 All at Once

```text
deploy to all existing instances simultaneously
```

Characteristics:
- quickest,
- short service interruption documented by AWS.

##### 3.4.5.10.3 Rolling

```text
deploy one batch at a time
```

Characteristics:
- no full-environment outage,
- temporary capacity reduction,
- old/new versions coexist.

##### 3.4.5.10.4 Rolling with Additional Batch

```text
launch temporary batch
→ deploy
→ roll through existing fleet
→ remove temporary batch
```

Purpose:
- maintain full capacity.

##### 3.4.5.10.5 Immutable

```text
new Auto Scaling group
→ new instances
→ candidate deployed
→ validate
→ replace old fleet
```

If candidate fails:
- original fleet remains unchanged.

##### 3.4.5.10.6 Traffic Splitting
Elastic Beanstalk:
- launches a full new set of instances,
- sends a configured percentage of traffic to them,
- evaluates health,
- then moves remaining traffic if healthy.

Therefore it combines:
- replacement capacity,
- canary-style traffic validation.

##### 3.4.5.10.7 Blue/Green
Separate Elastic Beanstalk environments:

```text
BLUE environment
→ current

GREEN environment
→ candidate

validate
→ swap environment URLs/CNAME
```

Critical distinction:

```text
traffic splitting
→ one environment
→ old/new instance sets

blue/green
→ two separate environments
→ URL/CNAME swap
```

#### 3.4.5.11 API Gateway Canary Context

REST API stages can use canary settings:

```text
prod stage
├── majority → current deployment
└── minority → canary deployment
```

Recognize service-specific implementations:

```text
API Gateway
→ stage canary

Lambda + CodeDeploy
→ alias traffic shifting

Elastic Beanstalk
→ traffic splitting

ECS + CodeDeploy
→ task-set traffic shifting
```

Same release goal:
- different AWS objects.

#### 3.4.5.12 Strategy Selection by Requirement

```text
fastest possible
→ all-at-once

update fleet in batches
→ rolling

rolling but preserve full capacity
→ rolling with additional batch

small initial production exposure
→ canary / traffic splitting

equal repeated traffic increments
→ linear

separate old and new environments/target sets
→ blue/green

do not modify existing instances
→ immutable
```

Then ask:
- which AWS service implements the strategy?

#### 3.4.5.13 Key Tradeoffs

##### 3.4.5.13.1 Blast Radius

```text
all-at-once
→ highest immediate blast radius

rolling
→ batch-sized exposure

canary
→ intentionally small first exposure

linear
→ progressively increasing exposure

blue/green
→ isolated before cutover
```

##### 3.4.5.13.2 Capacity

```text
Elastic Beanstalk rolling
→ capacity can temporarily drop

rolling with additional batch
→ preserves capacity

immutable
→ replacement capacity

blue/green
→ old and new capacity coexist
```

##### 3.4.5.13.3 Cost
Safer strategies often require temporary extra resources:
- rolling with additional batch,
- immutable,
- blue/green,
- traffic splitting.

##### 3.4.5.13.4 Speed
General intuition:
- all-at-once:
  - fastest.
- rolling:
  - batch-by-batch.
- canary/linear:
  - intentionally delayed for observation.
- immutable/blue-green:
  - require replacement capacity and validation.

Do not memorize:
- a universal absolute speed ranking across all services.

#### 3.4.5.14 Mixed-Version Compatibility

Gradual strategies can produce:

```text
old version
+
new version
```

at the same time.

Therefore consider compatibility of:
- API contracts,
- message formats,
- database schema,
- shared state.

A deployment strategy cannot make:
- incompatible application/data changes
safe by itself.

##### 3.4.5.14.1 Database Caveat

```text
v1 expects schema A
v2 requires schema B
```

If both versions coexist and schema B breaks v1:
- traffic rollback alone does not restore compatibility.

Key principle:

```text
deployment strategy
≠ data migration strategy
```

##### 3.4.5.15.1 Scaling


- Auto Scaling scaling activity,

##### 3.4.5.15.2 Load Balancing
A load balancer can implement traffic routing, but:

#### 3.4.5.16 Common Failure Patterns

##### 3.4.5.16.1 100% Traffic Moves Immediately
Expected:
- canary/linear.

Observed:
- all traffic shifted immediately.

Investigate:
- deployment configuration,
- deployment preference,
- traffic-routing settings.

##### 3.4.5.16.2 Canary Candidate Is Unhealthy
Expected:
- stop progression,
- preserve/restore known-good traffic according to configured behavior.

Check:
- validation hooks,
- CloudWatch alarms,
- target health,
- application logs.

##### 3.4.5.16.3 Rolling Reduces Capacity
This can be expected.

If requirement says:
- maintain full capacity,

use:
- rolling with additional batch,
- or another replacement-capacity strategy.

##### 3.4.5.16.4 Old and New Versions Conflict
Likely issue:
- application/data contract incompatibility.

Deployment mechanism may be:
- functioning correctly.

##### 3.4.5.16.5 Lambda Clients Still Hit Old Version
Possible cause:
- clients invoke version ARN directly instead of stable alias.

##### 3.4.5.16.6 ECS New Tasks Healthy but No Traffic
Investigate:
- deployment group,
- target groups,
- listeners,
- CodeDeploy traffic shift.

Task health alone does not prove:
- production routing moved.

##### 3.4.5.16.7 Beanstalk Short Outage
If:
- all-at-once,

short service interruption can be expected.

If requirement:
- no outage,

strategy selection is wrong.

##### 3.4.5.16.8 Traffic Rollback Does Not Restore Data Compatibility
Possible reason:
- database/schema changed incompatibly.

Traffic reversal:
- does not undo persistent data changes.

#### 3.4.5.18 Common Exam Traps

##### 3.4.5.18.1 Canary = Linear
- False.

##### 3.4.5.18.2 Blue/Green = Canary
- False.
- They can be combined.

##### 3.4.5.18.3 Rolling Always Maintains Full Capacity
- False.

##### 3.4.5.18.4 Immutable Uses No Extra Capacity
- False.

##### 3.4.5.18.5 `$LATEST` Is the Best Controlled Lambda Production Unit
- False.
- Prefer:
  - published versions + alias.

##### 3.4.5.18.6 CodePipeline Defines Canary/Linear Semantics
- False.
- It orchestrates workflow.

##### 3.4.5.18.7 Deployment Success = Application Health
- False.
- Use:
  - validation,
  - health checks,
  - alarms.

##### 3.4.5.18.8 Traffic Rollback Reverses Database Changes
- False.

##### 3.4.5.18.9 All-at-Once Always Causes Downtime
- False.
- Availability consequence is service-specific.

##### 3.4.5.18.10 Beanstalk Traffic Splitting = Blue/Green
- False.
- Traffic splitting:
  - one environment with old/new instance sets.
- Blue/green:
  - separate environments.

#### 3.4.5.21 Exam-Level Knowledge Frame

##### 3.4.5.21.1 Know These Cold

**All-at-once**
→ immediate full exposure/update.

**Rolling**
→ update targets in batches.

**Rolling with additional batch**
→ rolling while preserving capacity with temporary extra resources.

**Canary**
→ small initial traffic shift, then remainder.

**Linear**
→ repeated equal traffic increments.

**Blue/green**
→ separate old/new target sets or environments, then switch traffic.

**Immutable**
→ replacement instances instead of modifying existing ones.

**Lambda release identity**
→ published version.

**Lambda stable target**
→ alias.

**CodeDeploy deployment configuration**
→ controls traffic-shifting behavior.

**Elastic Beanstalk traffic splitting**
→ canary-style real-traffic validation using a new instance set inside one environment.

**Health signal**
→ determines whether rollout should continue.

##### 3.4.5.21.2 Fastest Exam Discriminator

```text
100% immediately?
→ all-at-once

batches?
→ rolling

batches + no capacity loss?
→ rolling with additional batch

small percentage then remainder?
→ canary

same percentage every interval?
→ linear

separate old/new environments?
→ blue/green

fresh replacement instances?
→ immutable

Lambda gradual release?
→ published version + alias + CodeDeploy

Beanstalk percentage validation?
→ traffic splitting

ECS canary/linear with NLB?
→ reject; NLB supports ECSAllAtOnce only
```

##### 3.4.5.21.3 Final Principle
- **A deployment strategy controls how an approved application version becomes active in a target environment. Keep version, target, and rollout mechanism separate. Choose the strategy from the required blast radius, availability, capacity, validation, speed, and rollback characteristics, then map that strategy to the AWS service implementing it: CodeDeploy traffic shifting for Lambda/ECS, Elastic Beanstalk deployment policies, Lambda aliases and published versions, API Gateway stage canaries, and health signals such as validation hooks and CloudWatch alarms.**
