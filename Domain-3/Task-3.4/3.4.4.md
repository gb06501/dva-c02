### 3.4.4 Manage application environments by using AWS services

#### 3.4.4.1 Exam and Task Context

##### 3.4.4.1.1 Domain and Task
- Domain 3 is **Deployment**.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.4 is **Manage application environments by using AWS services**.

##### 3.4.4.1.2 Position Inside Task 3.4
- 3.4.1:
  - package the application.
- 3.4.2:
  - manage API Gateway stages/custom domains.
- 3.4.3:
  - update IaC definitions.
- 3.4.4:
  - manage environments as explicit release targets.
- 3.4.5:
  - choose how a release transitions into an environment.

The key distinction from 3.3.5 is:

```text
3.3.5
→ recognize service-specific environment abstractions for testing

3.4.4
→ manage those environments as release targets in CI/CD
```

#### 3.4.4.2 Core Mental Model

```text
application artifact/version
        |
        v
environment target
        |
        v
environment-specific resources/configuration
        |
        v
deploy
        |
        v
validate
        |
        v
promote / replace / rollback
```

Keep two identities separate:

```text
WHERE does the release run?
→ environment identity

WHAT exact release runs there?
→ artifact/version identity
```

#### 3.4.4.3 What an Application Environment Is

##### 3.4.4.3.1 Definition
An application environment is:
- a logical or physical deployment target,
- containing the resources/configuration needed to run an application release.

Typical lifecycle names:
- development,
- test,
- staging,
- production.

##### 3.4.4.3.2 Environment Contents
An environment can include:
- compute,
- networking,
- configuration,
- permissions,
- data dependencies,
- endpoints,
- monitoring,
- selected application version.

##### 3.4.4.3.3 No Universal AWS Environment Object
AWS services represent environments differently:

```text
Elastic Beanstalk
→ Environment

API Gateway
→ Stage

Lambda
→ Alias + published version

AppConfig
→ Environment

Amplify Hosting
→ Branch deployment

CloudFormation / SAM
→ Stack + parameters/configuration

ECS
→ Service / cluster / task-definition deployment context

CodeDeploy
→ Deployment group

CodePipeline
→ workflow stages/actions targeting environments
```

Exam principle:
- identify which service owns the environment abstraction.

#### 3.4.4.4 Elastic Beanstalk Environment Model

##### 3.4.4.4.1 Application
An Elastic Beanstalk application is a logical container for:
- environments,
- application versions,
- saved configurations.

```text
Elastic Beanstalk Application
├── Version v1
├── Version v2
├── Version v3
├── dev environment
├── test environment
└── prod environment
```

##### 3.4.4.4.2 Application Version
An application version is:
- a labeled deployable source bundle/artifact,
- stored separately from the environment.

A version can:
- be uploaded without deployment,
- be deployed to one or more environments,
- be redeployed later.

Critical distinction:

```text
application version
→ what code

environment
→ where it runs
```

##### 3.4.4.4.3 Environment
An Elastic Beanstalk environment:
- is a collection of AWS resources,
- runs one application version at a time.

Therefore:

```text
Version 42
→ test environment

tests pass

Version 42
→ prod environment
```

supports:
- build once,
- promote the same approved artifact.

#### 3.4.4.5 Elastic Beanstalk Environment Management

##### 3.4.4.5.1 Environment Lifecycle
An environment can be:
- created,
- configured,
- updated,
- cloned,
- rebuilt,
- terminated.

These operations modify:
- the deployment target,

not:
- the identity of the application version itself.

##### 3.4.4.5.2 Environment Configuration
Environment-specific settings can include:
- platform,
- instance configuration,
- environment properties,
- load balancing,
- scaling,
- networking,
- deployment policy,
- health settings.

Thus:

```text
same application version
+
different environment configuration
→ different runtime behavior/capacity
```

##### 3.4.4.5.3 Saved Configuration
A saved configuration represents:
- reusable environment settings.

It can help:
- reproduce an environment,
- create similar environments,
- restore environment settings.

It does not represent:
- application code/version.

##### 3.4.4.5.4 Clone Environment
Cloning can create:
- a new environment with similar configuration.

Typical use:

```text
production-like environment
→ clone
→ staging/candidate environment
→ deploy candidate
→ validate
```

#### 3.4.4.6 Elastic Beanstalk Blue/Green

##### 3.4.4.6.1 Model

```text
BLUE
→ current production version

GREEN
→ candidate version

test GREEN
→ swap environment URLs
→ GREEN receives production traffic
```

##### 3.4.4.6.2 URL Swap
Elastic Beanstalk can swap:
- environment CNAMEs/URLs.

This allows:
- stable client-facing endpoint,
- cutover between environments,
- straightforward reversal by swapping back where appropriate.

##### 3.4.4.6.3 Blue/Green vs In-Place

```text
in-place
→ deploy new version into existing environment

blue/green
→ create separate environment
→ validate
→ switch traffic
```

Blue/green advantages:
- stronger isolation,
- pre-cutover validation,
- easier rollback path.

Trade-off:
- temporary duplication of environments/resources.

##### 3.4.4.6.4 Incompatible Platform Change
The source material specifically highlights:
- some incompatible Elastic Beanstalk platform changes require a new environment and blue/green migration rather than an in-place update.

##### 3.4.4.6.5 Persistent Data Caveat
Blue/green works cleanly when:
- application environments are replaceable,
- durable state is decoupled from them.

Do not tightly couple:
- disposable application environment,
- production database lifecycle.

#### 3.4.4.7 Environment vs Deployment Strategy

##### 3.4.4.7.1 Fundamental Distinction

```text
environment
→ WHERE deployment occurs

deployment strategy
→ HOW the new version enters that environment
```

##### 3.4.4.7.2 Elastic Beanstalk Policies
An environment can use policies such as:
- all at once,
- rolling,
- rolling with additional batch,
- immutable,
- traffic splitting.

This skill only needs the distinction:
- environment = target,
- policy = transition method.

Detailed strategy behavior belongs to:
- 3.4.5,
- 3.4.11.

#### 3.4.4.8 API Gateway Environments

##### 3.4.4.8.1 Stage
API Gateway uses:
- stages
as environment targets.

Example:

```text
dev
test
prod
```

A pipeline can:

```text
deploy candidate
→ test stage
→ validate
→ prod stage
```

##### 3.4.4.8.2 Custom Domain
Production may expose:

```text
api.example.com
→ prod stage
```

Keep separate:
- stage = environment,
- custom domain = client-facing identity.

Detailed stage/domain mechanics belong primarily to:
- 3.4.2.

#### 3.4.4.9 Lambda Environments

##### 3.4.4.9.1 Alias + Published Version
A common Lambda environment model is:

```text
dev alias
→ version 45

test alias
→ version 43

prod alias
→ version 40
```

- Alias:
  - stable environment/release pointer.
- Published version:
  - immutable release identity.

##### 3.4.4.9.2 Promotion

```text
publish v46
→ test alias → v46
→ validate
→ prod alias → v46
```

This promotes:
- the application version.

The environment identities:
- `test`,
- `prod`
remain stable.

##### 3.4.4.9.3 Weighted Alias
A Lambda alias can route between:
- two published versions.

That is:
- deployment-strategy behavior,
not:
- the definition of an environment.

#### 3.4.4.10 AppConfig Environments

##### 3.4.4.10.1 Model

```text
AppConfig Application
├── Development
├── Test
└── Production
```

Configuration versions can be deployed:
- independently to each environment.

##### 3.4.4.10.2 Important Distinction

```text
application code version
≠
runtime configuration version
```

##### 3.4.4.10.3 Environment vs Deployment Strategy
- AppConfig environment:
  - where configuration is deployed.
- AppConfig deployment strategy:
  - how configuration is rolled out.

Again:
- target ≠ rollout method.

#### 3.4.4.11 Amplify Hosting Environments

##### 3.4.4.11.1 Branch Deployments
Amplify Hosting can map Git branches to deployed environments.

Example:

```text
develop
→ integration environment

main
→ production environment

feature/*
→ temporary feature environments
```

##### 3.4.4.11.2 Branch vs Commit
- Branch:
  - moving environment lane.
- Commit:
  - exact source identity.

For release traceability:
- know which commit produced the deployed branch version.

#### 3.4.4.12 CloudFormation and SAM Environments

##### 3.4.4.12.1 Stack-Based Pattern

```text
app-dev stack
app-test stack
app-prod stack
```

using:

```text
same template
+
different parameters/configuration
```

##### 3.4.4.12.2 Promotion
Normally:

```text
approved template version
+
approved application artifact
+
prod parameters
→ update/create prod stack
```

Do not:
- turn the test stack into production.

Promote:
- artifact,
- template/definition,

not:
- environment identity.

#### 3.4.4.13 ECS Environment Management

##### 3.4.4.13.1 Runtime Target
ECS environment context can be represented through:
- cluster,
- service,
- stack/resource boundary.

Example:

```text
test service
→ task definition revision 42
→ image X

prod service
→ task definition revision 40
→ image Y
```

##### 3.4.4.13.2 Task Definition Revision
Keep separate:

```text
task definition revision
→ workload configuration/version

ECS service
→ running deployment target
```

#### 3.4.4.14 CodeDeploy Deployment Groups

##### 3.4.4.14.1 Purpose
A deployment group contains:
- deployment targets,
- deployment configuration/context.

Environment-like mapping can be:

```text
CodeDeploy Application: Orders
├── TestDeploymentGroup
└── ProdDeploymentGroup
```

##### 3.4.4.14.2 Service Context
Depending on compute platform, a deployment group can identify/configure:
- Lambda deployment target and traffic routing,
- ECS service/load-balancer target groups,
- EC2/on-premises target instances or Auto Scaling groups.

##### 3.4.4.14.3 Critical Distinction
- CodeDeploy application:
  - logical container for deployments.
- Deployment group:
  - specific deployment target/configuration.

Detailed traffic shifting belongs to:
- later deployment-strategy skills.

#### 3.4.4.15 CodePipeline Environment Orchestration

##### 3.4.4.15.1 Pipeline Role

```text
Source
→ Build
→ DeployTest
→ Test
→ Approval
→ DeployProd
```

CodePipeline:
- orchestrates delivery,
- targets service-native environments.

##### 3.4.4.15.2 Pipeline Stage Is Not Runtime Environment

```text
CodePipeline stage: DeployProd
→ workflow step

Elastic Beanstalk prod environment
→ runtime environment

API Gateway prod stage
→ API environment
```

A pipeline stage name:
- does not guarantee the deployment action points to the correct environment.

#### 3.4.4.16 Environment Isolation

##### 3.4.4.16.1 Isolation Dimensions
An environment should isolate as appropriate:
- deployment target,
- configuration,
- runtime resources,
- data dependencies,
- permissions.

##### 3.4.4.16.2 Levels

```text
logical separation
→ stages / aliases / branches

resource separation
→ separate queues / tables / services / stacks

account separation
→ stronger organizational boundary
```

##### 3.4.4.16.3 Separate Accounts
Common model:

```text
development account
test account
production account
```

This strengthens separation for:
- IAM,
- blast radius,
- quotas,
- billing,
- resource boundaries.

Service-native environment abstractions can still exist inside each account.

#### 3.4.4.17 Environment-Specific Dependencies and Permissions

##### 3.4.4.17.1 Data
A test environment should generally point to:
- test data resources.

Correct:

```text
test API
→ test Lambda
→ test DynamoDB
→ test SQS
```

Dangerous:

```text
test Lambda
→ prod DynamoDB
```

##### 3.4.4.17.2 IAM
- Test application role:
  - test resources.
- Production role:
  - production resources.

Naming something `test` or `prod`:
- does not create an IAM boundary.

##### 3.4.4.17.3 Configuration
Environment-specific configuration can include:
- table names,
- queue URLs,
- API endpoints,
- log levels,
- feature flags,
- secret references,
- resource ARNs.

Possible mechanisms include:
- Lambda environment variables,
- AppConfig,
- Parameter Store,
- Secrets Manager,
- IaC parameters.

#### 3.4.4.18 Artifact Promotion

##### 3.4.4.18.1 Strong Model

```text
artifact A
→ test
→ validate
→ prod
```

##### 3.4.4.18.2 Weak Model

```text
build A-test
→ test

rebuild source
→ A-prod
→ prod
```

The second model can produce:
- a different artifact.

Environment management should preserve:
- exact release identity,
- promotion traceability.

#### 3.4.4.19 Persistent vs Ephemeral Environments

##### 3.4.4.19.1 Persistent
Examples:
- dev,
- test,
- prod.

They:
- remain continuously available,
- are updated by the delivery workflow.

##### 3.4.4.19.2 Ephemeral
Examples:
- feature environment,
- PR environment,
- temporary integration environment.

Workflow:

```text
create
→ deploy
→ test
→ destroy
```

##### 3.4.4.19.3 Trade-Offs
Benefits:
- isolation,
- parallel testing,
- reproducibility.

Costs:
- provisioning time,
- resource cost,
- dependency setup,
- cleanup.

Exam priority:
- understand the environment concept,
- not advanced platform economics.

#### 3.4.4.20 Environment Health and Drift

##### 3.4.4.20.1 Health
Before promotion:
- validate target environment health.

Examples:
- Elastic Beanstalk environment health/status,
- ECS service/task health,
- API/Lambda CloudWatch signals.

Detailed observability:
- Domain 4.

##### 3.4.4.20.2 Drift
Manual edits can make long-lived environments diverge.

Examples:
- Lambda alias changed manually,
- Beanstalk environment config changed,
- API stage variable changed,
- CloudFormation-managed resource altered in console.

Use:
- IaC,
- controlled CI/CD
to reduce drift.

#### 3.4.4.21 Common Failure Patterns

##### 3.4.4.21.1 Wrong Environment Target
Pipeline intends:
- test,

but deploys:
- production.

Artifact can be correct while:
- release targeting is wrong.

##### 3.4.4.21.2 Test Uses Production Dependency
Risk:
- production data modified,
- tests are unsafe/misleading.

Fix:
- environment-specific configuration,
- IAM isolation.

##### 3.4.4.21.3 Alias Name Treated as Entire Environment
Lambda `test` alias points to correct version, but:
- environment variables point to production.

Conclusion:
- environment is end-to-end configuration,
- not one label.

##### 3.4.4.21.4 Beanstalk Incompatible Platform Updated In Place
Correct direction:
- new environment,
- blue/green migration.

##### 3.4.4.21.5 Green Environment Removed Too Early
After URL swap:
- allow for validation and DNS/cache behavior before destroying old environment.

##### 3.4.4.21.6 Disposable Environment Owns Production Database
Risk:
- environment replacement/termination affects durable state.

Fix:
- decouple persistent data lifecycle.

##### 3.4.4.21.7 Pipeline Stage Name Used as Proof of Target
`DeployProd`:
- is only a workflow label.

Verify:
- actual deployment provider target.

##### 3.4.4.21.8 Environment Name Used as Security Boundary
`prod` in a resource name:
- does not enforce security.

Use:
- IAM,
- accounts,
- resource isolation.

#### 3.4.4.22 Decision Flow

##### 3.4.4.22.1 Service-Native Environment

```text
managed application environment?
→ Elastic Beanstalk environment

API environment?
→ API Gateway stage

Lambda stable environment pointer?
→ alias + published version

configuration environment?
→ AppConfig environment

Git-hosted environment?
→ Amplify branch

IaC-defined environment?
→ CloudFormation / SAM stack

ECS runtime environment?
→ service / cluster / stack context

deployment-target configuration?

```

##### 3.4.4.22.2 Lifecycle

```text
need multi-environment orchestration?
→ CodePipeline targets service environments

need stronger isolation?
→ separate resources/accounts + service-native mechanisms

need Beanstalk blue/green cutover?
→ separate environment + URL swap

need exact release fidelity?
→ promote same approved artifact/version
```

- False.

##### 3.4.4.23.4 Blue/Green = In-Place Update
- False.

##### 3.4.4.23.5 API Gateway Stage = CodePipeline Stage
- False.

##### 3.4.4.23.6 Lambda Alias = Published Version
- False.
- Alias points to version.

##### 3.4.4.23.7 AppConfig Environment = Deployment Strategy
- False.

##### 3.4.4.23.8 ECR Image Tag = Runtime Environment
- False.

##### 3.4.4.23.9 CodeDeploy Deployment Group = Application Code
- False.
- It defines deployment target/configuration.

##### 3.4.4.23.10 Pipeline Stage Name Guarantees Correct Target
- False.

##### 3.4.4.23.11 Environment Name Creates Security Isolation
- False.

##### 3.4.4.23.12 Rebuilding Source for Prod Is Same as Promoting Tested Artifact
- Not guaranteed.

##### 3.4.4.26.3 Final Principle
- **Manage application environments as explicit release targets and keep environment identity separate from release identity. AWS services expose different environment abstractions, so CI/CD should target the correct service-native construct, deploy the same approved artifact/version through the lifecycle, preserve environment-specific configuration and isolation, validate before promotion, and use environment replacement mechanisms such as Elastic Beanstalk blue/green when required.**
