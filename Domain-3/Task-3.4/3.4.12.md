### 3.4.12 Automate deployment testing

#### 3.4.12.1 Exam and Task Context

##### 3.4.12.1.1 Domain and Task
- **Domain 3:** Deployment.
- The supplied DVA-C02 exam-guide excerpt lists **Task 3: Automate deployment testing** immediately after Task 3.4 and before Domain 4.
- The excerpt does **not** enumerate additional subskills beneath this task.

Therefore this page uses `3.4.12` as study organization without inventing an exam-guide skill statement.

Core question:

**How can tests and validation run automatically in the delivery/deployment process so that an unacceptable release does not silently progress?**

---

#### 3.4.12.2 Core Mental Model

```text
source / artifact
      |
      v
build
      |
      v
pre-deployment tests
      |
      +-- fail → STOP
      |
      '-- pass
             |
             v
          deploy candidate
             |
             v
      deployment validation
             |
             +-- fail → STOP
             |           |
             |           '-- rollback IF configured
             |
             '-- pass → continue
```

Central principle:

```text
deployment testing
=
test before deployment
+
validate the actual candidate during/after deployment
```

---

#### 3.4.12.3 Two Major Validation Locations

##### Before Deployment

```text
build
→ unit/integration tests
→ test result
→ deployment allowed only if successful
```

Primary AWS execution service:
- AWS CodeBuild.

##### During Deployment

```text
candidate prepared/deployed
→ lifecycle validation
→ traffic/progression allowed only if successful
```

Primary AWS mechanism:
- AWS CodeDeploy lifecycle hooks.

Critical distinction:

```text
CodeBuild test
→ validates application/build before release

CodeDeploy hook
→ validates deployment candidate in deployment lifecycle
```

---

#### 3.4.12.4 CodeBuild as Automated Test Runner

CodeBuild executes test commands defined in:
- `buildspec.yml`.

Examples:

```yaml
phases:
  build:
    commands:
      - mvn test
```

or:

```yaml
- npm test
- python -m pytest
```

The project test framework:
- defines and executes assertions.

CodeBuild:
- provides the execution environment,
- runs the commands.

If a required test command exits unsuccessfully:

```text
CodeBuild action fails
→ pipeline progression can stop
```

Exam trap:

```text
CodeBuild
≠ test framework
```

---

#### 3.4.12.5 CodeBuild Test Reports

CodeBuild can ingest structured test results through the buildspec `reports` section.

Concept:

```text
test framework
→ result file
→ CodeBuild report
→ report group
```

Example:

```yaml
reports:
  unit-tests:
    files:
      - '**/*'
    base-directory: target/surefire-reports
    file-format: JUNITXML
```

A report group:
- logically groups related reports across builds.

AWS documentation supports common result formats including:
- JUnit XML,
- Cucumber JSON.

Important distinction:

```text
test command exit status
→ determines build/action success

test report
→ stores/presents structured test results
```

Therefore:

```text
report exists
≠ pipeline automatically failed
```

The executing test command/action must communicate failure correctly.

---

#### 3.4.12.6 CodeBuild Report Permissions

CodeBuild reporting requires appropriate service-role permissions including:

```text
CreateReportGroup
CreateReport
UpdateReport
BatchPutTestCases
```

Code coverage reporting additionally requires:

```text
BatchPutCodeCoverages
```

Exam clue:

```text
tests execute
+
report creation receives AccessDenied
→ inspect CodeBuild service-role permissions
```

---

#### 3.4.12.7 CodePipeline as Orchestrator

CodePipeline can orchestrate:

```text
Source
→ Build/Test
→ Deploy Test
→ Integration Test
→ Approval
→ Deploy Production
```

Role separation:

```text
CodePipeline
→ sequence + gates

CodeBuild
→ test execution

CodeDeploy
→ deployment + lifecycle validation
```

CodePipeline itself:
- is not the unit/integration test framework.

A failed action:
- prevents normal progression to later actions/stages.

---

#### 3.4.12.8 Fail Fast Before Deployment

Prefer inexpensive deterministic tests before expensive deployment work.

Example:

```text
compile
→ unit tests
→ package
→ deploy test environment
→ integration tests
→ production deployment
```

Benefit:
- earlier feedback,
- less wasted deployment work,
- lower release risk.

Unit-level defects should normally be found:
- before production deployment lifecycle validation.

---

#### 3.4.12.9 Post-Deployment Validation

Some defects appear only in the deployed environment.

Examples:
- wrong runtime configuration,
- broken dependency integration,
- permissions failure,
- routing problem,
- runtime startup failure.

Therefore:

```text
deploy candidate
→ invoke candidate
→ assert expected behavior
```

Infrastructure deployment success alone:
- does not prove application correctness.

---

#### 3.4.12.10 CodeDeploy AppSpec Hooks

The CodeDeploy AppSpec `hooks` section connects:
- deployment lifecycle events

to:
- validation logic.

For Lambda and ECS:

```text
lifecycle hook
→ Lambda validation function
```

For EC2/on-premises:

```text
lifecycle hook
→ script
```

This is the primary AWS-native mechanism in the supplied source for:
- automated deployment-lifecycle validation.

---

#### 3.4.12.11 Lambda Deployment Validation Hooks

Lambda CodeDeploy deployments provide:

```text
BeforeAllowTraffic
AfterAllowTraffic
```

Flow:

```text
new Lambda version
       |
       v
BeforeAllowTraffic
→ validate candidate
       |
       v
traffic shift
       |
       v
AfterAllowTraffic
→ validate after traffic
```

##### `BeforeAllowTraffic`

Use to:
- invoke/check the updated version before production traffic,
- smoke-test critical dependencies,
- fail deployment before exposure.

##### `AfterAllowTraffic`

Use to:
- validate live behavior after traffic shift,
- run final smoke/integration checks.

Fast discriminator:

```text
Lambda candidate before production traffic
→ BeforeAllowTraffic

Lambda after traffic shift
→ AfterAllowTraffic
```

---

#### 3.4.12.12 Validation Hook Result

A Lambda validation function must report its result to CodeDeploy using:

```text
PutLifecycleEventHookExecutionStatus
```

Result:

```text
Succeeded
```

or:

```text
Failed
```

Therefore:

```text
validation Lambda logs "success"
≠ CodeDeploy was notified of success
```

The lifecycle status callback is required.

AWS documentation cited by the source states:

```text
CodeDeploy not notified within one hour
→ deployment considered failed
```

High-value exam trap:
- hook invoked successfully,
- but status never reported.

---

#### 3.4.12.13 ECS Blue/Green Validation Hooks

ECS CodeDeploy blue/green lifecycle hooks include:

```text
BeforeInstall
AfterInstall
AfterAllowTestTraffic
BeforeAllowTraffic
AfterAllowTraffic
```

The most distinctive deployment-testing hook is:

```text
AfterAllowTestTraffic
```

Do not mechanically transfer:
- ECS hook names

to:
- Lambda deployments.

---

#### 3.4.12.14 ECS Test Listener

CodeDeploy ECS blue/green can use:
- an optional test listener.

Architecture:

```text
PRODUCTION LISTENER
→ original task set

TEST LISTENER
→ replacement task set
```

This allows:

```text
test traffic
→ green/replacement task set
→ validation
→ production cutover only after successful validation
```

The test listener therefore provides:
- candidate-specific traffic before production rerouting.

---

#### 3.4.12.15 `AfterAllowTestTraffic`

Conceptual flow:

```text
replacement task set created
        |
        v
test listener sends test traffic
        |
        v
AfterAllowTestTraffic
        |
        v
Lambda validation
        |
        +-- Failed → deployment fails
        |
        '-- Succeeded → continue toward production traffic
```

This is a strong exam pattern:

```text
validate ECS green task set before cutover
→ test listener
+ AfterAllowTestTraffic
+ validation Lambda
```

---

#### 3.4.12.16 ECS Lifecycle Sequence

Conceptually:

```text
BeforeInstall
→ replacement task set
→ AfterInstall
→ test traffic
→ AfterAllowTestTraffic
→ BeforeAllowTraffic
→ production traffic
→ AfterAllowTraffic
```

Each hook:
- represents a different deployment lifecycle point.

Do not treat them:
- as interchangeable validation names.

---

#### 3.4.12.17 Candidate Targeting

Critical rule:

```text
deployment test
→ must exercise the NEW candidate
```

Bad pattern:

```text
test
→ old production target
→ passes
```

Result:

```text
test passed
≠ candidate validated
```

Candidate-specific mechanisms include:
- ECS test listener,
- Lambda version under deployment,
- green/candidate endpoint.

For gradual Lambda routing:

```text
production alias
→ may route to old OR new version
```

Therefore a candidate validation test must:
- target the updated version appropriately,
- not assume a weighted production alias proves the new version.

---

#### 3.4.12.18 Validation Failure vs Rollback

Testing answers:

```text
is the candidate acceptable?
```

Rollback configuration answers:

```text
what happens when it is not?
```

Therefore:

```text
validation failure
→ deployment fails/stops

validation failure
+ automatic rollback configured
→ rollback
```

Do not assume:

```text
validation hook
= automatic rollback
```

This preserves the boundary with:
- 3.4.8 rollback behavior.

---

#### 3.4.12.19 CloudWatch Alarms as Deployment Gates

CodeDeploy deployment groups can monitor:
- CloudWatch alarms.

Example:

```text
new release
→ error rate increases
→ CloudWatch alarm enters ALARM
→ CodeDeploy stops deployment
→ rollback if configured
```

This provides:
- metric-based release validation.

Compare:

```text
validation function
→ explicit functional assertion

CloudWatch alarm
→ runtime metric threshold
```

They can be:
- complementary.

---

#### 3.4.12.20 Infrastructure Health vs Application Correctness

Example:

```text
container RUNNING
+
load balancer target HEALTHY
```

does not necessarily prove:

```text
checkout works
orders persist correctly
permissions are correct
```

Stronger release validation:

```text
infrastructure health
+
application-level validation
```

#### 3.4.12.21 Testing Levels in Delivery

##### Unit Test

```text
small code unit
→ isolated behavior
```

Best placed:
- early in build/CI.

##### Integration Test

```text
multiple components
→ work together
```

Example:

```text
API Gateway
→ Lambda
→ DynamoDB
```

Can run after:
- deployment to a development/test environment.

##### Smoke Test

Asks:

```text
does the deployed candidate basically work?
```

Good fit for:
- deployment lifecycle hooks.

##### End-to-End Test

Exercises:
- broader/full application path.

Useful after:
- deployment into a representative environment.

Tradeoff:
- slower,
- more environment-dependent.

Exam-level ordering:

```text
fast code-level tests
→ before deployment

environment-dependent tests
→ after candidate deployment
```

---

#### 3.4.12.22 Test Data and Determinism

Deployment gates should be:
- focused,
- reliable,
- bounded in execution time.

Ideal:

```text
same candidate
+
same relevant state
→ same result
```

Flaky deployment tests can cause:
- false rollback,
- false release confidence.

Test data should preferably be:
- isolated,
- repeatable,
- safe,
- idempotent where appropriate.

Avoid:
- corrupting production data,
- dependence on unpredictable user state.

#### 3.4.12.23 Deployment Strategies and Testing

Deployment strategy:
- controls exposure/progression.

Deployment testing:
- determines candidate acceptability.

##### Canary

```text
small production exposure
→ observe/test
→ healthy?
   yes → continue
   no  → stop/rollback if configured
```

Canary alone:
- limits blast radius,
- does not itself provide a functional assertion.

##### Blue/Green

```text
BLUE
→ current production

GREEN
→ candidate
→ validate before cutover
```

Natural fit for:
- candidate testing before production switch.

##### Rolling

```text
batch
→ health/progression validation
→ next batch
```

Service health controls:
- are not identical to explicit application functional tests.

Detailed strategy configuration remains:
- 3.4.11.

For EC2/on-premises CodeDeploy, the CodeDeploy agent supports:

```text
deploy-local
```

Use to validate:
- AppSpec integrity,
- deployment content,
- lifecycle scripts

on a local instance before remote deployment.

```text
deploy-local
```

#### 3.4.12.25 Manual Approval Is Not Automated Testing

Manual approval:

```text
human governance gate
```

Automated test:

```text
machine-executed assertion
```

Pipeline can contain both:

```text
automated test
→ manual approval
→ production
```

But they solve:
- different problems.

#### 3.4.12.26 Practical Pattern Summary

| Requirement | Correct direction |
|---|---|
| Run unit tests during CI | CodeBuild + project test framework |
| Store structured test results | CodeBuild reports/report group |
| Sequence automated quality gates | CodePipeline |
| Validate Lambda before production traffic | `BeforeAllowTraffic` |
| Validate Lambda after traffic shift | `AfterAllowTraffic` |
| Validate ECS green task set before cutover | test listener + `AfterAllowTestTraffic` |
| Tell CodeDeploy hook passed/failed | `PutLifecycleEventHookExecutionStatus` |
| Detect runtime metric degradation | CloudWatch alarm |
| Recover automatically after deployment failure | configure automatic rollback separately |
| Validate EC2 CodeDeploy AppSpec/package locally | `codedeploy-agent deploy-local` |
| Test during gradual release | target the actual candidate |
| Healthy infrastructure but uncertain functionality | add application-level validation |

#### 3.4.12.28 Common Exam Traps

##### "CodePipeline executes unit tests itself"
- False.
- It orchestrates actions.

##### "CodeBuild invents application tests"
- False.
- The test framework defines/executes them; CodeBuild runs the commands.

##### "A CodeBuild report automatically fails the build"
- False.
- The test command/action must return failure appropriately.

##### "Lambda validation function only needs to log success"
- False.
- It must report lifecycle status to CodeDeploy.

##### "A hook that never reports status eventually succeeds"
- False.
- The cited AWS behavior is failure after one hour without notification.

##### "`AfterAllowTestTraffic` is a Lambda deployment hook"
- False.
- It is part of the ECS CodeDeploy lifecycle.

##### "ECS green must receive production traffic before testing"
- False.
- An optional test listener can route test traffic before cutover.

##### "Validation failure always rolls back"
- False.
- Automatic rollback is separate configuration.

##### "Healthy load balancer target proves application correctness"
- False.

##### "Manual approval is automated testing"
- False.

##### "Canary deployment automatically validates functionality"
- False.
- Canary controls exposure; tests/alarms judge health.

##### "Testing a weighted Lambda production alias guarantees the new version was tested"
- False.
- Candidate targeting must be deterministic.

#### 3.4.12.31 Exam-Level Knowledge Frame

Know these cold.

**CodeBuild**  
→ execute automated test commands.

**CodeBuild reports**  
→ structured test-result reporting.

**CodePipeline**  
→ orchestrate test/deployment gates.

**CodeDeploy AppSpec hooks**  
→ deployment-lifecycle validation.

**Lambda `BeforeAllowTraffic`**  
→ validate candidate before production traffic.

**Lambda `AfterAllowTraffic`**  
→ validate after traffic shift.

**ECS test listener**  
→ route test traffic to replacement task set before production cutover.

**ECS `AfterAllowTestTraffic`**  
→ validate replacement task set after test traffic is enabled.

**`PutLifecycleEventHookExecutionStatus`**  
→ validation Lambda reports `Succeeded`/`Failed` to CodeDeploy.

**CloudWatch alarm**  
→ metric-based deployment health gate.

**Automatic rollback**  
→ separate configuration from validation itself.

**Candidate targeting**  
→ deployment test must exercise the actual new release.

Fastest discriminator:

```text
unit tests?
→ CodeBuild

structured test results?
→ CodeBuild reports

pipeline quality gate?
→ CodePipeline + test action

Lambda before traffic?
→ BeforeAllowTraffic

Lambda after traffic?
→ AfterAllowTraffic

ECS green before cutover?
→ test listener + AfterAllowTestTraffic

hook result callback?
→ PutLifecycleEventHookExecutionStatus

runtime metric degradation?
→ CloudWatch alarm

failed deployment should recover automatically?
→ automatic rollback configuration

local EC2 AppSpec/package validation?
→ deploy-local
```

Final principle:

**Automate deployment testing by placing validation at the correct delivery boundary. Use CodeBuild for pre-deployment application tests and structured reports, CodePipeline to gate progression on action success, and CodeDeploy lifecycle hooks to validate the actual deployment candidate. For Lambda, validate around traffic shifting with `BeforeAllowTraffic` and `AfterAllowTraffic`; for ECS blue/green, use candidate-specific test traffic and `AfterAllowTestTraffic` before production cutover. Validation functions must explicitly report lifecycle status, and rollback remains a separate configuration.**
