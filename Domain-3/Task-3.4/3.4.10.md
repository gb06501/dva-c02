### 3.4.10 Use existing runtime configurations to create dynamic deployments

#### 3.4.10.1 Exam and Task Context

##### 3.4.10.1.1 Domain and Task
- Domain 3 is **Deployment**.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.10 is **Use existing runtime configurations to create dynamic deployments**.
- The exam guide example refers to:
  - **API Gateway stage variables** used with Lambda.

##### 3.4.10.1.2 Position Inside Task 3.4
- 3.4.9:
  - source branches/tags identify release revisions.
- 3.4.10:
  - runtime configuration changes environment-specific behavior.
- 3.4.11:
  - deployment strategies control how a new version is introduced.

Core question:

**How can one deployed API/application structure select different runtime backends or values for dev/test/prod without duplicating the source or API definition?**

#### 3.4.10.2 Core Mental Model

```text
same API/application definition
          |
          +--> beta stage
          |      |
          |      '--> beta runtime configuration
          |
          '--> prod stage
                 |
                 '--> prod runtime configuration
```

Key idea:

```text
same deployed structure
+
stage/runtime configuration
→ environment-specific behavior
```

Do not confuse:

```text
source version
→ what code

runtime configuration
→ how that code/API behaves in one environment
```

#### 3.4.10.3 API Gateway Stage and Stage Variable

##### 3.4.10.3.1 Stage
An API Gateway stage is:
- a named lifecycle/deployment reference.

Typical names:
- `dev`,
- `test`,
- `beta`,
- `prod`,
- `v2`.

For HTTP APIs:
- `$default` is also supported.

##### 3.4.10.3.2 Stage Variable
AWS defines stage variables as:
- key/value pairs associated with a stage.

Conceptually:

```text
stage
→ environment/lifecycle target

stage variable
→ configuration attached to that stage
```

Example:

```text
beta:
  backend = beta.example.com

prod:
  backend = example.com
```

The API integration can reference:

```text
${stageVariables.backend}
```

#### 3.4.10.4 What "Dynamic Deployment" Means Here

For this skill, dynamic deployment does **not** mean:
- dynamically generating arbitrary infrastructure.

The exam-guide pattern is:

```text
existing API/application structure
+
stage-specific runtime value
→ different backend/behavior
```

Example:

```text
GET /orders
    |
    v
API Gateway
    |
    +-- beta → BetaOrdersFunction
    |
    '-- prod → OrdersFunction
```

The API method can:
- reference a stage variable,
instead of:
- hard-coding one backend.

#### 3.4.10.5 Dynamic HTTP Backend Selection

Stage variables can parameterize HTTP integration URIs.

Example:

```text
http://${stageVariables.url}
```

Stage values:

```text
beta:
url = beta.example.com

prod:
url = example.com
```

Result:

```text
beta stage
→ beta.example.com

prod stage
→ example.com
```

For REST APIs, stage variables can also appear in URI components such as:
- host/domain,
- subdomain,
- path,
- query string.

Example:

```text
http://backend/${stageVariables.version}/orders
```

This changes:
- integration values,
not:
- integration type.

#### 3.4.10.6 Dynamic Lambda Function Selection

API Gateway can use a stage variable for:
- Lambda function name.

Concept:

```text
${stageVariables.function}
```

Values:

```text
beta:
function = OrdersBeta

prod:
function = OrdersProd
```

Result:

```text
same API method
+
different stage variable
→ different Lambda function
```

This is directly aligned with the exam-guide example.

#### 3.4.10.7 Dynamic Lambda Version or Alias Selection

Stage variables can also qualify:
- Lambda version,
- Lambda alias.

Example:

```text
Orders:${stageVariables.alias}
```

Stage values:

```text
beta:
alias = beta

prod:
alias = prod
```

Runtime chain:

```text
API stage
→ stage variable
→ Lambda alias
→ published Lambda version
```

Keep the layers separate:

```text
stage variable
→ string/configuration value

Lambda alias
→ Lambda resource pointing to published version
```

#### 3.4.10.8 Passing Stage Metadata to Lambda

A stage variable does not have to select:
- a different function.

The same Lambda can receive:
- stage-specific metadata.

Example:

```text
beta:
table = OrdersBeta

prod:
table = Orders
```

Then API Gateway passes:

```text
tableName = stage variable
```

Lambda receives:
- the selected table name.

Result:

```text
same Lambda code
+
different runtime configuration
→ environment-specific behavior
```

#### 3.4.10.9 Mapping Templates and Parameter Mapping

For REST APIs, mapping templates can access:

```text
$stageVariables.<name>
```

Example:

```json
{
  "stageName": "$stageVariables.stageName"
}
```

Stage variables can also participate in:
- request/response parameter mappings,
- headers,
- integration parameters.

Mental model:

```text
stage configuration
→ API Gateway mapping
→ backend receives environment-specific value
```

For DVA-C02:
- understand the capability,
- not every mapping-template syntax variant.

#### 3.4.10.10 REST API vs HTTP API Stage Variables

##### 3.4.10.10.1 REST API
Stage variables can be used in areas including:
- HTTP integration URIs,
- AWS integration URIs,
- Lambda function name/version/alias,
- parameter mappings,
- mapping templates,
- selected integration credential/reference fields.

##### 3.4.10.10.2 HTTP API
HTTP APIs also support stage variables.

AWS documents use for:
- HTTP integration URI,
- Lambda function integration name/alias,
- AWS integration credentials.

Therefore:

```text
stage variables
≠ REST-only feature
```

But:
- REST APIs expose broader mapping-template capabilities.

#### 3.4.10.11 Cannot Dynamically Change Integration Type

This is a strong rejection rule.

A stage variable can customize:
- values within an already configured integration.

It cannot make:

```text
beta
→ HTTP integration

prod
→ Lambda integration
```

for the same configured route/method simply by changing a stage variable.

Rule:

```text
stage variable
→ parameterizes integration

stage variable
≠ changes integration type
```

#### 3.4.10.12 Stage Variables Are Not Secret Storage

AWS explicitly states:
- stage variables are not intended for sensitive data.

Do not place:
- passwords,
- API keys,
- database credentials,
- secret tokens
in stage variables.

Use an appropriate mechanism such as:
- AWS Secrets Manager,
- Systems Manager Parameter Store,
depending on the requirement.

Fast rule:

```text
secret?
→ not stage variable
```

#### 3.4.10.13 Lambda Permission Requirement

Dynamic selection does not bypass:
- authorization.

If API Gateway selects a Lambda function through a stage variable:

```text
API Gateway
→ still requires invoke permission
```

AWS documentation notes:
- invocation permission may need to exist for every Lambda function that can be selected.

Otherwise a request can fail, for example with:
- `500 Internal Server Error`.

General rule:

```text
configuration selects resource
≠ permission automatically granted
```

#### 3.4.10.14 Same-Account Lambda Restriction

AWS documents the stage-variable Lambda pattern with this restriction:

```text
API Gateway stage variable selects Lambda
→ Lambda must be in same AWS account as API
```

Exam rejection rule:

```text
stage variable dynamically selects Lambda in another account
→ reject
```

#### 3.4.10.15 Runtime Configuration vs Source Version

3.4.9 covers:
- source identity.

3.4.10 covers:
- runtime configuration.

Distinction:

```text
branch/tag/commit
→ source release

stage/runtime value
→ environment-specific behavior
```

Therefore:

```text
same source revision
+
different runtime configuration
→ different runtime behavior
```

Do not create:
- environment-specific source branches
only because:
- runtime values differ.

#### 3.4.10.16 Runtime Configuration vs Deployment Strategy

3.4.11 covers:
- canary,
- blue/green,
- rolling,
- other rollout strategies.

Those answer:

**How is a new release introduced?**

3.4.10 answers:

**How does the deployed structure select environment-specific runtime behavior?**

Different dimensions:

```text
deployment strategy
→ traffic/version rollout

runtime configuration
→ backend/value selection
```

#### 3.4.10.17 Runtime Configuration vs API Deployment

Keep these separate:

```text
API deployment
→ snapshot of API configuration

API stage
→ lifecycle/deployment reference

stage variable
→ stage-specific runtime configuration
```

The exam's "dynamic deployment" wording should not imply:
- every variation requires a new API deployment or separate API definition.

#### 3.4.10.18 Runtime Configuration vs Rollback

Changing a stage variable back:
- might restore behavior in some designs.

But:

```text
configuration change
≠ universally deployment rollback
```

Rollback should use:
- the mechanism that owns the failed release.

Detailed rollback:
- 3.4.8.

#### 3.4.10.19 Managing Configuration Safely

Manual stage-variable changes can create:

```text
IaC says A
runtime says B
```

which is:
- configuration drift.

Engineering guidance:
- manage important runtime configuration through:
  - IaC,
  - controlled CI/CD,
  - reviewed configuration changes.

This provides:

```text
configuration
→ versioned
→ reviewed
→ reproducible
```

The exact IaC syntax:
- depends on API type/resource model.

#### 3.4.10.20 Same Code Across Environments

Strong pattern:

```text
same application code
+
environment-specific runtime configuration
→ dev/test/prod behavior
```

Avoid hard-coding:

```text
if prod:
  use production endpoint
else:
  use test endpoint
```

when the difference belongs in:
- environment configuration.

This improves:
- source consistency,
- release traceability,
- environment portability.

#### 3.4.10.21 Related Configuration Services

##### 3.4.10.21.1 Lambda Environment Variables
Use when:
- configuration belongs to the Lambda runtime/function.

They are not:
- API Gateway stage variables.

##### 3.4.10.21.2 AWS AppConfig
Use when:
- application configuration should be managed and deployed independently with AppConfig controls.

Do not automatically replace:
- API Gateway routing configuration
with:
- AppConfig.

##### 3.4.10.21.3 Systems Manager Parameter Store
Use when:
- application needs centralized parameters/configuration.

##### 3.4.10.21.4 Secrets Manager
Use when:
- value is sensitive.

Key rule:

```text
which layer owns the configuration?
→ choose service accordingly
```

#### 3.4.10.22 Common Scenarios

##### 3.4.10.22.1 Same API, Different HTTP Backend

```text
beta → beta.example.com
prod → example.com
```

Use:
- stage variable in HTTP integration URI.

##### 3.4.10.22.2 Same API, Different Lambda Functions

```text
beta → OrdersBeta
prod → OrdersProd
```

Use:
- stage variable for Lambda function selection.

##### 3.4.10.22.3 Same Function, Different Lambda Aliases

```text
beta stage → beta alias
prod stage → prod alias
```

Use:
- stage variable for Lambda alias/version qualifier.

##### 3.4.10.22.4 Same Lambda, Different Table

```text
beta → OrdersBeta
prod → Orders
```

Use:
- stage variable passed through mapping/request configuration.

##### 3.4.10.22.5 Database Password Per Stage
Reject:
- stage variable.

Use:
- secret-management service.

##### 3.4.10.22.6 Beta Uses HTTP, Prod Uses Lambda
Reject:
- one stage variable dynamically changing integration type.

##### 3.4.10.22.7 Cross-Account Lambda Selection
Reject:
- documented stage-variable Lambda-selection pattern.

##### 3.4.10.22.8 Dynamic Lambda Returns 500
Check:
- Lambda invocation permission for API Gateway.

#### 3.4.10.23 Decision Flow

##### 3.4.10.23.1 Is the Difference Runtime Configuration?

```text
yes
→ use configuration mechanism
```

not:
- source fork by default.

##### 3.4.10.23.2 Does API Gateway Stage Own the Value?

```text
yes
→ stage variable
```

##### 3.4.10.23.3 What Must Vary?

```text

→ stage variable in integration URI

Lambda function?
→ stage variable for function name

Lambda version/alias?
→ stage variable for qualifier

backend metadata?
→ stage variable through mapping/request configuration
```

##### 3.4.10.23.4 Is It Sensitive?

```text
yes
→ do NOT use stage variable
```

##### 3.4.10.23.5 Does Integration Type Change?

```text
yes
→ stage variable cannot solve it
```

##### 3.4.10.23.6 Dynamic Lambda Selection?

Check:
- same AWS account,
- invoke permission.

##### 3.4.10.23.7 Need Canary/Blue-Green/Rolling?


#### 3.4.10.27 Exam-Level Knowledge Frame

##### 3.4.10.27.1 Know These Cold

**API Gateway stage**
→ named lifecycle/deployment reference.

**Stage variable**
→ stage-specific key/value configuration.

**HTTP backend selection**
→ stage variable in integration URI.

**Lambda selection**
→ stage variable can select Lambda function name.

**Lambda alias/version selection**
→ stage variable can qualify Lambda integration.

**Metadata injection**
→ stage variable can be passed through mapping/request configuration.

**Sensitive data**
→ do not store in stage variables.

**Integration type**
→ stage variable cannot dynamically change it.

**Cross-account Lambda**
→ unsupported for documented stage-variable Lambda-selection pattern.

**Permissions**
→ dynamically selected Lambda still requires invoke permission.

**Source vs runtime configuration**
→ branches/tags identify source; stage variables alter runtime behavior.

**Deployment strategy**
→ separate concept from runtime configuration.

##### 3.4.10.27.2 Fastest Exam Discriminator

```text
same API, different backend by stage?
→ stage variable

same API, different Lambda by stage?
→ stage variable

same function, different alias by stage?
→ stage variable + Lambda alias

same Lambda, stage-specific metadata?
→ stage variable + mapping/request configuration

secret?
→ not stage variable

different integration type?
→ stage variable cannot do it

cross-account Lambda?
→ reject documented stage-variable Lambda pattern

500 after dynamic Lambda selection?
→ check invoke permission

different source release?
→ branch/tag/versioning

canary/blue-green/rolling?
→ deployment strategy
```

##### 3.4.10.27.3 Final Principle
- **Use runtime configuration when the deployed API/application structure can remain the same but environment-specific behavior must differ. API Gateway stage variables are stage-scoped key/value values that can parameterize HTTP integration URIs, select Lambda functions or Lambda aliases/versions, and pass stage-specific metadata to a backend. Keep stage, stage variable, Lambda alias, source revision, and deployment strategy separate. Stage variables are non-secret configuration, cannot change the underlying integration type, do not bypass invocation permissions, and the documented Lambda stage-variable selection pattern requires the Lambda function to be in the same AWS account as the API.**
