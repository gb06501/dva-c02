### 3.4.1 Describe Lambda deployment packaging options

#### 3.4.1.1 Exam and Task Context

##### 3.4.1.1.1 Domain
- Domain 3 is **Deployment**, representing 24% of scored content.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.1 is **Describe Lambda deployment packaging options**.

##### 3.4.1.1.2 Position Inside Task 3.4
- This skill answers:
  - **What deployable artifact can AWS Lambda execute?**
- Later Task 3.4 skills own:
  - IaC updates,
  - CI/CD workflows,
  - deployment strategies,
  - traffic shifting and rollback.
- Keep packaging separate from release strategy.

#### 3.4.1.2 Core Mental Model

##### 3.4.1.2.1 Two Function Package Types
AWS Lambda supports exactly two function deployment package types:

```text
Lambda function
├── .zip archive
└── container image
```

##### 3.4.1.2.2 Lambda Layer Is Not a Third Package Type
- A Lambda layer is supplementary `.zip` content.
- Layers can be attached only to `.zip`-based functions.
- Container-image functions package dependencies inside the image.

##### 3.4.1.2.3 Packaging Pipeline

```text
source
→ build
→ package
→ publish/store artifact
→ deploy Lambda
```

- `.zip` → direct upload or Amazon S3.
- container image → Amazon ECR.

#### 3.4.1.3 `.zip` Deployment Packages

##### 3.4.1.3.1 Contents
- Function code.
- Required dependencies not otherwise available to the function.
- Runtime-specific handler/application structure.

##### 3.4.1.3.2 Archive Structure
- Lambda must be able to locate the handler and dependencies.
- Exact archive layout depends on runtime.
- An unnecessary parent directory can cause module/handler lookup failures.

##### 3.4.1.3.3 Native Dependencies
- Native binaries must match:
  - Lambda's Linux environment,
  - selected architecture: `x86_64` or `arm64`.
- A binary built only for macOS/Windows or the wrong architecture can fail at runtime.

##### 3.4.1.3.4 Size Limits
- Direct `.zip` upload through Lambda API/SDK or console:
  - **50 MB compressed**.
- Uncompressed package:
  - **250 MB**, including layers and custom runtime content.
- If the compressed archive exceeds the direct-upload limit but remains within the uncompressed limit:
  - deploy it through Amazon S3.

##### 3.4.1.3.5 S3 Role
```text
function.zip
→ S3
→ Lambda
```

- S3 stores/transports the artifact.
- Using S3 does **not** create a different Lambda package type.

#### 3.4.1.4 Container Image Deployment Packages

##### 3.4.1.4.1 Flow

```text
Dockerfile
→ build image
→ push to Amazon ECR
→ deploy image to Lambda
```

##### 3.4.1.4.2 Size
- Maximum uncompressed container image size:
  - **10 GB**, including image layers.

##### 3.4.1.4.3 Repository
- Lambda container images are stored in:
  - **Amazon ECR**.
- ECR repository and Lambda function must be:
  - in the same AWS Region.
- Cross-account ECR use is possible with appropriate permissions.

##### 3.4.1.4.4 Architecture
- Lambda container images must be Linux-based.
- Image must target one Lambda-supported architecture:
  - `x86_64`,
  - `arm64`.
- Do not use one multi-architecture image as the Lambda function image.

#### 3.4.1.5 Container Base-Image Options

##### 3.4.1.5.1 AWS Lambda Base Image
Contains:
- operating system,
- supported language runtime,
- Lambda Runtime Interface Client (RIC),
- Runtime Interface Emulator (RIE) for local testing.

Use when:
- AWS-provided runtime/base image fits the application.

##### 3.4.1.5.2 AWS OS-Only Base Image
Contains:
- Amazon Linux,
- RIE.

Does not provide:
- complete language runtime for the application.

Useful for:
- compiled languages,
- custom runtimes.

Application must provide:
- required runtime components,
- Runtime Interface Client.

##### 3.4.1.5.3 Non-AWS Linux Base Image
- Supported if made Lambda-compatible.
- Must include:
  - Runtime Interface Client.

Core rule:

```text
ordinary Linux container
≠ automatically Lambda-compatible
```

#### 3.4.1.6 RIC vs RIE

##### 3.4.1.6.1 Runtime Interface Client — RIC
- Connects the runtime/application to:
  - Lambda Runtime API.
- Required for Lambda execution when the chosen base image does not already include it.

##### 3.4.1.6.2 Runtime Interface Emulator — RIE
- Supports:
  - local testing of Lambda-compatible container images.

##### 3.4.1.6.3 Exam Distinction

```text
RIC → production runtime integration
RIE → local emulation/testing
```

#### 3.4.1.7 Lambda Layers

##### 3.4.1.7.1 Purpose
- Reusable supplementary `.zip` content such as:
  - libraries,
  - dependencies,
  - custom runtime components,
  - extensions.

##### 3.4.1.7.2 Runtime Location
- Layer contents are extracted under:
  - `/opt`.
- Archive structure must match runtime expectations.

##### 3.4.1.7.3 Versioning
- Publishing a layer creates:
  - a layer version.
- Functions reference:
  - a specific layer version ARN.

##### 3.4.1.7.4 Limits
- Up to:
  - **five layers per function**.
- For `.zip` functions:
  - function package + layers + custom runtime content must remain within the **250 MB uncompressed** limit.

##### 3.4.1.7.5 Package-Type Restriction
- Lambda layers work only with:
  - `.zip` functions.
- For container-image functions:
  - put dependencies/runtime content into the image.

##### 3.4.1.7.6 Lambda Layer vs OCI Image Layer
- Lambda layer:
  - separate Lambda resource containing supplementary `.zip` content.
- OCI/container image layer:
  - filesystem layer inside the image.
- Same word:
  - different mechanisms.

#### 3.4.1.8 Choosing the Packaging Model

##### 3.4.1.8.1 Choose `.zip` When
- Managed Lambda runtime is suitable.
- Code/dependencies fit `.zip` limits.
- Packaging is straightforward.
- You want the conventional Lambda packaging model.

##### 3.4.1.8.2 Consider a Lambda Layer When
- Several `.zip` functions need:
  - reusable/shared dependencies or runtime content.
- Separate layer version management is useful.

##### 3.4.1.8.3 Choose Container Image When
- Artifact/dependencies require substantially more package capacity.
- Custom OS/runtime components are needed.
- Native/system dependencies are complex.
- Existing container build tooling is useful.
- Greater control over runtime contents is required.

##### 3.4.1.8.4 Container Image Does Not Mean ECS
- Packaging changes.
- Lambda execution semantics remain:
  - Lambda/serverless semantics.
- A container image does not provide:
  - ECS task behavior,
  - arbitrary long-running daemon semantics.

#### 3.4.1.9 Package Type Is Fixed Per Function

##### 3.4.1.9.1 AWS Rule
- An existing Lambda function cannot switch between:
  - `.zip`,
  - container image.

##### 3.4.1.9.2 If Package Type Must Change
- Create:
  - a new Lambda function.

#### 3.4.1.10 Container Image Updates and Artifact Identity

##### 3.4.1.10.1 Updating an ECR Tag
- Pushing a new image under an existing tag does not automatically redeploy Lambda.
- Lambda must be updated to deploy the new image.

```text
push new image
→ update Lambda function code/image
```

##### 3.4.1.10.2 Tag vs Digest
- Tag:
  - human-readable,
  - can be mutable.
- Digest:
  - immutable content identity.
- For controlled promotion:
  - image digest gives stronger exact artifact identity.

#### 3.4.1.11 CI/CD Packaging Context

##### 3.4.1.11.1 `.zip` Path

```text
source
→ build/test
→ function.zip
→ S3/direct deployment
→ Lambda
```

##### 3.4.1.11.2 Container Path

```text
source
→ build/test
→ image
→ ECR
→ Lambda
```

##### 3.4.1.11.3 Build Once
- Prefer promoting the same tested artifact through environments.
- Do not unnecessarily rebuild different application artifacts for dev/test/prod.

##### 3.4.1.11.4 Configuration Is Separate
- Environment-specific configuration/secrets should generally remain outside the artifact where appropriate.
- Packaging answers:
  - **what code artifact executes?**
- Configuration answers:
  - **how does that deployed function behave in this environment?**

#### 3.4.1.12 Common Failure Patterns

##### 3.4.1.12.1 Missing Dependency
- Deployment succeeds.
- Invocation fails with module/class loading error.
- Check:
  - function package,
  - layer,
  - image contents.

##### 3.4.1.12.2 Wrong Native Architecture
- Native dependency built for incompatible OS/architecture.
- Rebuild for:
  - Lambda Linux,
  - selected architecture.

##### 3.4.1.12.3 Oversized `.zip`
- Direct upload exceeds compressed limit.
- If uncompressed package remains valid:
  - use S3.
- If package fundamentally exceeds `.zip` model:
  - consider container image.

##### 3.4.1.12.4 Layer Pushes Package Over Limit
- Layers count toward:
  - 250 MB uncompressed `.zip` package limit.

##### 3.4.1.12.5 Layer Attached to Image Function
- Not supported.
- Put dependency/runtime content:
  - inside image.

##### 3.4.1.12.6 New ECR Image Does Not Change Lambda
- Pushing image:
  - is not Lambda deployment.
- Update:
  - Lambda function code/image reference.

##### 3.4.1.12.7 Custom Image Missing RIC
- Image is not Lambda-compatible.
- Include:
  - appropriate Runtime Interface Client.

#### 3.4.1.13 Decision Flow

##### 3.4.1.13.1 Package Selection

```text
Fits normal Lambda package model?
→ .zip

Shared dependency among .zip functions?
→ consider Lambda layer

Need much larger/custom runtime package?
→ container image
```

##### 3.4.1.13.2 Storage Selection

```text
small/normal .zip
→ direct upload

larger valid .zip
→ S3

container image
→ ECR
```

##### 3.4.1.13.3 Compatibility

```text
native dependency?
→ Lambda Linux + correct architecture

custom/non-AWS image?
→ include RIC

local image testing?
→ RIE
```

#### 3.4.1.14 Common Exam Traps

##### 3.4.1.14.1 Layer Is a Third Package Type
- Wrong.
- Lambda function package types:
  - `.zip`,
  - container image.

##### 3.4.1.14.2 Layers Work with Image Functions
- Wrong.
- Lambda layers:
  - `.zip` functions only.

##### 3.4.1.14.3 S3 Creates a Different Package Type
- Wrong.
- S3:
  - stores/transports a `.zip`.

##### 3.4.1.14.4 New ECR Tag Automatically Updates Lambda
- Wrong.
- Lambda still requires:
  - function code/image update.

##### 3.4.1.14.5 Existing Function Can Switch Package Type
- Wrong.
- Create:
  - new function.

##### 3.4.1.14.6 Any Linux/Docker Image Works Unchanged
- Wrong.
- Lambda runtime-interface and architecture requirements still apply.

##### 3.4.1.14.7 RIC and RIE Are Interchangeable
- Wrong.
- RIC:
  - runtime integration.
- RIE:
  - local testing.

##### 3.4.1.14.8 250 MB Is the Direct Compressed Upload Limit
- Wrong.
- Direct compressed `.zip` upload:
  - 50 MB.
- Uncompressed package including layers:
  - 250 MB.

#### 3.4.1.17 Exam-Level Knowledge Frame

##### 3.4.1.17.1 Package Types
- `.zip` archive OR container image.
- Lambda layer:
  - not a third package type.

##### 3.4.1.17.2 `.zip`
- Direct compressed upload:
  - 50 MB.
- Uncompressed package including layers:
  - 250 MB.
- Larger valid archive:
  - S3.

##### 3.4.1.17.3 Container Image
- Maximum uncompressed:
  - 10 GB.
- Stored:
  - ECR.
- Same Region as Lambda.
- Must satisfy:
  - Linux,
  - architecture,
  - Lambda runtime-interface requirements.

##### 3.4.1.17.4 Layers
- `.zip` functions only.
- Up to five.
- Extracted:
  - `/opt`.
- Specific layer version ARN.

##### 3.4.1.17.5 Fastest Exam Discriminator

```text
simple Lambda package?
→ .zip

shared .zip dependency?
→ layer

large/custom runtime package?
→ container image

large valid .zip?
→ S3

container artifact?
→ ECR

custom base image?
→ RIC

local container emulation?
→ RIE

switch .zip ↔ image?
→ new function

exact image identity?
→ digest
```

##### 3.4.1.17.6 Final Principle
- **Lambda has two function deployment package types: `.zip` archives and container images. Use layers only as supplementary reusable content for `.zip` functions. Package the code and dependencies required by the target Linux/architecture/runtime model, use S3 for larger valid `.zip` artifacts and ECR for container images, and keep artifact packaging distinct from configuration and deployment strategy.**
