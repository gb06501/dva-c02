### 3.4.9 Use labels and branches for version and release management

#### 3.4.9.1 Exam and Task Context

##### 3.4.9.1.1 Domain and Task
- Domain 3 is **Deployment**.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.9 is **Use labels and branches for version and release management**.

##### 3.4.9.1.2 Position Inside Task 3.4
- 3.4.6:
  - source changes trigger automation.
- 3.4.7:
  - orchestrate delivery across environments.
- 3.4.8:
  - roll back to a known-good release.
- 3.4.9:
  - identify and select source revisions for release.
- 3.4.10:
  - change runtime behavior through configuration.

Core question:

**How do commits, branches, and Git tags identify and select the source revision that enters a release workflow?**

#### 3.4.9.2 Core Mental Model

```text
repository
   |
   +--> branch: main
   |       |
   |       +--> commit A
   |       +--> commit B
   |       '--> commit C
   |
   +--> branch: feature-x
   |       '--> commit D
   |
   '--> Git tag: v2.1
           '--> commit B
```

Keep the identities separate:

```text
commit
→ exact source revision

branch
→ movable reference to a development line

Git tag
→ named reference useful as a release label
```

Release management decides:

```text
which branch/tag/event
→ triggers which pipeline/release process
```

#### 3.4.9.3 Commit as Exact Source Identity

A commit represents:
- a snapshot of repository contents and changes.

The commit ID identifies:
- the exact source revision.

Example:

```text
main
→ commit 7f93a1...
```

The branch tells you:
- which line of development was selected.

The commit tells you:
- exactly what source state was selected.

Critical distinction:

```text
main today
≠ necessarily main tomorrow

commit 7f93a1...
→ same source revision
```

For deterministic delivery:
- capture the exact source revision used by the pipeline.

#### 3.4.9.4 Branch as Movable Reference

AWS CodeCommit documentation describes a branch as:
- a pointer/reference to a commit.

Branches can:
- isolate development work,
- maintain different lines of development,
- support release stabilization.

Examples:

```text
main
→ current integration/stable line

feature/payment
→ isolated feature work

release/2.4
→ release stabilization line
```

The names are:
- team conventions.

AWS does not mandate:
- `main`,
- `develop`,
- `feature/*`,
- `release/*`.

#### 3.4.9.5 Branch Movement and Release Identity

Suppose:

```text
main → commit A
```

After another merge:

```text
main → commit B
```

Therefore:

**A branch name alone is not an immutable release identity.**

Use:
- the exact commit/source revision
for:
- traceability,
- reproducibility,
- rollback mapping.

#### 3.4.9.6 Git Tag as Release Label

A Git tag provides:
- a human-readable reference to a Git object/revision.

Example:

```text
commit 8a31...
→ tag v2.1.0
```

This lets release discussions use:

```text
v2.1.0
```

instead of:
- only a long commit SHA.

Useful purposes:
- identify a release revision,
- trigger a release pipeline,
- connect release metadata to source,
- support rollback traceability.

#### 3.4.9.7 Git Tag vs AWS Resource Tag

This distinction is exam-relevant.

##### 3.4.9.7.1 Git Tag

```text
Git repository
→ named reference to Git object/revision
```

Examples:
- `v2.1.0`,
- `beta`,
- `release`.

##### 3.4.9.7.2 AWS Resource Tag

```text
AWS resource
→ key/value metadata
```

Examples:

```text
Environment=Production
CostCenter=1234
```

Therefore:

```text
Git tag
≠
AWS resource tag
```

They operate at:
- different layers,
- for different purposes.

#### 3.4.9.8 Branch Is Not Environment

Do not equate:

```text
branch = environment
```

They are different concepts.

```text
branch
→ source-control reference

environment
→ runtime/deployment target
```

A single source revision can be promoted through:

```text
dev
→ test
→ prod
```

without requiring:
- one source branch per environment.

This supports:
- build-once/promote-same-release workflows.

#### 3.4.9.9 Git Tag Is Not Deployable Artifact

Git tag:

```text
→ source identity/reference
```

Deployable artifact:

```text
→ build output
```

Examples of artifacts:
- Lambda ZIP,
- container image,
- JAR,
- application bundle,
- packaged SAM/CloudFormation output.

Strong traceability:

```text
Git tag
→ commit SHA
→ pipeline execution
→ build artifact
→ deployment
```

They should be linked.
They are not:
- the same object.

#### 3.4.9.10 Release Identity Chain

Strong model:

```text
Git tag v2.1.0
       |
       v
commit SHA
       |
       v
pipeline execution
       |
       v
build artifact
       |
       v
deployment
```

Useful release metadata can include:
- release label,
- commit SHA,
- build ID,
- artifact version/digest,
- pipeline execution ID,
- deployment ID.

This answers:

```text
what source
→ produced what artifact
→ deployed where
→ through which execution?
```

#### 3.4.9.11 CodePipeline Source Revision

CodePipeline tracks:
- the source revision associated with a pipeline execution.

For Git-based sources:
- this includes commit identity/details.

Therefore:

```text
branch/tag event
→ pipeline starts
→ exact source revision retained
```

The pipeline should deploy:
- the source revision that triggered the execution,

not:
- whatever the branch points to later.

#### 3.4.9.12 CodePipeline Trigger Model

For supported connection-based Git sources, CodePipeline supports trigger filtering for:
- push events,
- pull-request events.

Push filters can use:
- Git tags,
- branches,
- file paths.

Pull-request filters can use:
- branches,
- file paths.

Mental model:

```text
repository event
+
trigger filter
→ pipeline execution
```

This turns:
- source-control structure
into:
- explicit release policy.

#### 3.4.9.13 Branch Push Filters

Example:

```text
push to main
→ production/release pipeline
```

or:

```text
push to release/*
→ release-validation pipeline
```

Trigger filters can:
- include branch patterns,
- exclude branch patterns.

Example:

```text
include:
release/*

exclude:
release/experimental/*
```

Purpose:
- only qualifying branches trigger a release workflow.

#### 3.4.9.14 Git Tag Push Filters

Current CodePipeline connection triggers can filter:
- Git tag push events.

Example:

```text
push tag v*
→ release pipeline
```

This enables:

```text
normal commits
→ CI/test

release tag v2.3.1
→ release pipeline
```

This is the clearest AWS-supported implementation of:
- labels/tags for release management.

#### 3.4.9.15 Branch and File-Path Filters

CodePipeline can combine:
- branch,
- file path.

Example:

```text
push to main
AND
change under service-a/**
→ service-a pipeline
```

Useful in:
- monorepositories.

Keep the distinction:

```text
branch
→ source reference

file-path filter
→ trigger selection criterion
```

#### 3.4.9.16 Pull-Request Triggers

Connection-based CodePipeline triggers can react to:
- pull-request events.

Example:

```text
PR toward main
→ validation pipeline
```

Then:

```text
merge/push to main
→ release pipeline
```

This separates:
- pre-merge validation,
- post-merge release.

#### 3.4.9.17 `BranchName` vs Trigger Filters

A source action can define:
- `BranchName`.

Current trigger filtering can also define:
- one or more branch patterns.

Therefore:

```text
BranchName
≠ only possible branch-selection mechanism
```

When trigger branch filtering is used:
- the configured trigger determines which branch events start the pipeline.

#### 3.4.9.18 Exact Commit Selection

AWS documents that filtered branch push events can:
- start the pipeline,
- fetch the exact commit associated with the event.

Mental model:

```text
push event
→ filter matches
→ exact commit selected
→ pipeline execution
```

This preserves:
- deterministic source identity.

#### 3.4.9.19 Branching Strategy Is Not Prescribed by AWS

Possible team models include:
- trunk-based development,
- GitHub Flow,
- release branches,
- GitFlow-like models.

The exam skill requires understanding:
- how branches and labels support version/release management.

It does not require:
- memorizing one universal branching methodology.

Exam focus:

```text
commit
→ exact source revision

branch
→ separate/select development line

Git tag
→ release label/reference

trigger filter
→ select which events start release automation
```

#### 3.4.9.20 Feature, Release, and Hotfix Branches

##### 3.4.9.20.1 Feature Branch
Typical purpose:

```text
main
  |
  '-- feature-x
```

Use:
- isolated feature development.

It is not automatically:
- a release.

##### 3.4.9.20.2 Release Branch
Typical purpose:

```text
main/develop
→ release/2.4
```

Can support:
- stabilization,
- final testing,
- limited fixes.

This is:
- engineering convention,
not:
- AWS requirement.

##### 3.4.9.20.3 Hotfix Branch
Typical purpose:

```text
production defect
→ hotfix branch
→ validate
→ merge/release
```

Again:
- naming is a team convention.

Exam concept:
- branch isolates/selects the source line.

#### 3.4.9.21 Environment Branches and Artifact Promotion

Long-lived branch-per-environment model:

```text
dev branch
test branch
prod branch
```

is possible.

But it can create:

```text
same application
→ divergent source histories
```

If the requirement is:

```text
same tested release
→ promote through environments
```

prefer:

```text
exact source revision
→ build artifact once
→ test
→ promote same artifact
```

rather than:
- rebuilding from different environment branches.

This is engineering guidance supporting release traceability.

#### 3.4.9.22 Tag Stability

Git technically allows:
- deleting/recreating,
- force-moving
tag references.

But moving a published release tag creates ambiguity.

Bad:

```text
v2.1 yesterday → commit A
v2.1 today     → commit B
```

Then:

```text
what was v2.1?
→ ambiguous
```

Engineering guidance:
- treat published release tags as stable.

#### 3.4.9.23 Branch Protection and Release Integrity

Controlled release branches can require:
- restricted pushes,
- pull-request review,
- controlled merge permissions.

AWS CodeCommit documentation includes IAM patterns for:
- limiting pushes,
- limiting merges
to selected branches.

Concept:

```text
feature branch
→ developer changes

main/release branch
→ controlled merge/update
```

Purpose:
- protect release input.

Do not over-expand this into:
- full repository-governance design.

#### 3.4.9.24 Repository Provider Is Secondary

The underlying concepts are:
- Git commits,
- branches,
- tags,
- release selection.

Modern CodePipeline workflows can integrate external Git providers through:
- AWS CodeConnections.

Therefore:

```text
branch/tag release model
→ not limited to CodeCommit
```

CodeCommit documentation remains useful because:
- it explicitly documents Git concepts used in the source material.

#### 3.4.9.25 CodeCommit Availability Context

The source material notes:
- CodeCommit availability changed for new customers.

For exam learning:
- branch/commit/tag concepts remain relevant,
- current CodePipeline architectures may use external Git providers through CodeConnections.

Do not infer:

```text
all release repositories
→ must use CodeCommit
```

#### 3.4.9.26 Tag-Triggered vs Branch-Triggered Release

##### 3.4.9.26.1 Tag-Triggered

```text
merge to main
→ normal CI

release decision
→ create tag v2.4.0

tag push
→ release pipeline
```

Benefit:
- explicit release intent.

##### 3.4.9.26.2 Branch-Triggered

```text
merge/push to main
→ build/test/deploy
```

Benefit:
- simple continuous delivery/deployment.

Tradeoff:
- every qualifying main change can become a release candidate.

##### 3.4.9.26.3 Release-Branch Trigger

```text
push release/2.*
→ release pipeline
```

Useful when:
- release line must be maintained separately.

Tradeoff:
- more merge/backport complexity.

There is no universally correct model.
Choose according to:
- release policy.

#### 3.4.9.27 Version-Control Identity vs Runtime/Artifact Identity

Keep these layers separate:

```text
Git
→ source version

ECR
→ image tag / image digest

Lambda
→ published version / alias

Elastic Beanstalk
→ application version
```

They can use matching labels for traceability,
but are not:
- the same object.

##### 3.4.9.27.1 Git Tag vs ECR Image Tag

```text
Git tag
→ repository source reference

ECR image tag
→ container registry reference
```

For strongest container identity:

```text
image digest
→ immutable image identity
```

Possible release chain:

```text
Git tag v2.1
→ commit SHA
→ image build
→ image digest
```

##### 3.4.9.27.2 Git Branch vs Lambda Alias

```text
Git branch
→ points into source history

Lambda alias
→ points to published Lambda version
```

They are:
- different release-management layers.

##### 3.4.9.27.3 Git Tag vs Lambda Version

```text
Git tag
→ source revision label

Lambda version
→ immutable published function snapshot
```

A pipeline can map:

```text
Git tag v2.1
→ build/deploy
→ Lambda version 42
```

But:

```text
v2.1
≠ Lambda version 42
```

unless release metadata maps them.

#### 3.4.9.28 Rollback Connection

3.4.8 needs:
- known-good release identity.

3.4.9 provides:
- source/release labeling.

Example:

```text
v2.3.0 → known good
v2.4.0 → bad
```

Rollback can map:

```text
v2.3.0
→ exact commit
→ known-good artifact
→ redeploy
```

Strong release management makes rollback:
- deterministic.

#### 3.4.9.29 Dynamic Configuration Boundary

3.4.10 covers:
- runtime configuration.

Therefore:

```text
same source release
+
different runtime configuration
→ different runtime behavior
```

Do not create source branches only to represent:
- runtime configuration,
when the application is intentionally designed to externalize that configuration.

#### 3.4.9.30 Common Failure Patterns

##### 3.4.9.30.1 Pipeline Released Wrong Revision
Check:
- source revision recorded by execution,
- branch/tag event,
- trigger filter.

Do not use:
- current branch HEAD
as proof of what an older execution deployed.

##### 3.4.9.30.2 Release Tag Points to Unexpected Commit
Check:
- tag target,
- whether tag was moved/recreated.

Published release labels should remain:
- stable.

##### 3.4.9.30.3 Wrong Branch Triggers Release
Check:
- source `BranchName`,
- trigger include/exclude filters,
- repository event type.

##### 3.4.9.30.4 Monorepo Pipeline Runs for Irrelevant Changes
Use:
- branch + file-path filtering where appropriate.

##### 3.4.9.30.5 Test and Production Artifacts Differ
Possible cause:
- rebuilt from branch instead of promoting tested artifact.

Preserve:
- source/artifact identity.

##### 3.4.9.31.4 Release Promotion

```text

→ preserve source/artifact identity

```

#### 3.4.9.35 Exam-Level Knowledge Frame

##### 3.4.9.35.1 Know These Cold

**Commit**
→ exact source revision.

**Branch**
→ named movable reference to a line of development.

**Git tag**
→ named Git reference useful as a release label.

**AWS resource tag**
→ key/value resource metadata; not a Git tag.

**Branch trigger**
→ pipeline starts for qualifying branch event.

**Git tag trigger**
→ pipeline starts for qualifying Git tag push.

**Pull-request trigger**
→ pipeline validates qualifying PR event.

**Source revision**
→ exact source version tracked by the pipeline execution.

**Release traceability**
→ tag/label → commit → artifact → deployment.

**Environment**
→ runtime target; not a Git branch.

**ECR image tag**
→ registry reference; not a Git tag.

**Lambda alias**
→ runtime pointer to Lambda version; not a Git branch.

##### 3.4.9.35.2 Fastest Exam Discriminator

```text
exact source snapshot?
→ commit

independent development line?
→ branch

human-readable release label?
→ Git tag

AWS resource classification?
→ AWS resource tag

release only on v*?
→ Git tag push trigger

deploy only main?
→ branch trigger/filter

validate PR?
→ pull-request trigger

monorepo service selection?
→ branch + file-path filter

container identity?
→ ECR tag/digest

Lambda runtime version routing?
→ version/alias

same tested build through environments?
→ promote preserved artifact identity
```

##### 3.4.9.35.3 Final Principle
- **Use commits, branches, and Git tags for different release-management purposes. A commit provides exact source identity, a branch is a movable reference that isolates or selects a line of development, and a Git tag provides a human-readable release label tied to a revision. CodePipeline can turn qualifying branch, Git tag, and pull-request events into release policy through trigger filters while retaining the exact source revision for each execution. Keep Git tags separate from AWS resource tags, ECR image tags, Lambda versions/aliases, deployable artifacts, and runtime environments. AWS provides the mechanisms but does not prescribe one universal branching strategy.**
