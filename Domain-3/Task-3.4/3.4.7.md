### 3.4.7 Use orchestrated workflows to deploy code to different environments

#### 3.4.7.1 Exam and Task Context

##### 3.4.7.1.1 Domain and Task
- Domain 3 is **Deployment**.
- Task 3.4 is **Deploy code by using AWS Continuous Integration and Continuous Delivery (CI/CD) services**.
- Skill 3.4.7 is **Use orchestrated workflows to deploy code to different environments**.

##### 3.4.7.1.2 Position Inside Task 3.4
- 3.4.6:
  - source change starts delivery automation.
- 3.4.7:
  - orchestrate build, test, approval, and deployment across environments.
- 3.4.8:
  - perform rollback.
- 3.4.9:
  - manage release identity with branches/labels.
- 3.4.11:
  - configure deployment strategies.

Core question:

**How do you coordinate source, build, test, approval, and deployment actions so that the same known release moves through multiple environments in a controlled order?**

#### 3.4.7.2 Core Mental Model

```text
SOURCE
  |
  v
BUILD
  |
  v
TEST
  |
  v
DEPLOY TEST
  |
  v
INTEGRATION TEST
  |
  v

  |
  v

```

CodePipeline defines:
- order,
- dependencies,
- artifact handoff,
- gates,
- target environments.

The connected AWS services perform:
- build,
- test,
- infrastructure changes,
- application deployment,
- validation.

Critical distinction:

```text
CodePipeline
→ orchestrates

CodeBuild / CloudFormation / CodeDeploy / ECS / Beanstalk / Lambda
→ execute specific work
```

#### 3.4.7.3 Pipeline, Stage, and Action

##### 3.4.7.3.1 Pipeline
A CodePipeline pipeline is:
- the complete software-delivery workflow.

Example:

```text
OrdersDelivery

Source
→ Build
→ Test
→ DeployTest
→ Approval
→ DeployProd
```

##### 3.4.7.3.2 Stage
A stage is:
- a logical unit in the pipeline,
- containing one or more actions,
- often aligned with a release phase or environment.

Examples:
- Source,
- Build,
- Test,
- DeployTest,
- DeployProd.

Do not confuse:

```text
CodePipeline stage
→ CI/CD workflow stage

API Gateway stage
→ API deployment environment
```

##### 3.4.7.3.3 Action
An action performs:
- source,
- build,
- test,
- deploy,
- approval,
- invoke
work.

Examples:

```text
Source action
→ retrieve source revision

Build action
→ invoke CodeBuild

Deploy action
→ invoke CodeDeploy / CloudFormation / service-specific deployment

Approval action
→ wait for explicit human decision
```

#### 3.4.7.4 Stage Sequencing and Run Order

##### 3.4.7.4.1 Sequential Stages
Stages normally progress in pipeline order:

```text
Source
→ Build
→ Test
→ Deploy
```

A later stage begins only after:
- the prior required stage succeeds.

This creates:
- release gates.

##### 3.4.7.4.2 Parallel Actions
Multiple actions in the same stage can run in parallel when:
- they have the same run order.

Example:

```text
BuildArtifact
   |
   +--> Unit Tests
   +--> Security Tests
   '--> Static Analysis
```

The stage succeeds only when:
- required actions succeed.

##### 3.4.7.4.3 Run Order
Actions within one stage can be sequenced:

```text
RunOrder 1
→ deploy test stack

RunOrder 2
→ smoke test
```

Keep separate:

```text
parallel actions
→ within one execution/stage

PARALLEL execution mode
→ multiple pipeline executions
```

#### 3.4.7.5 Artifact Flow

##### 3.4.7.5.1 Source Artifact

```text
Git revision
→ source action
→ SourceArtifact
```

The source artifact:
- represents the selected source entering the workflow.

##### 3.4.7.5.2 Build Artifact

```text
SourceArtifact
→ CodeBuild
→ BuildArtifact
```

Examples:
- compiled JAR,
- Lambda ZIP,
- container metadata,
- application bundle,
- packaged template.

##### 3.4.7.5.3 Artifact Handoff

```text
Source
→ SourceArtifact

Build
→ AppArtifact

DeployTest
→ consumes AppArtifact

DeployProd
→ consumes AppArtifact
```

CodePipeline's artifact model allows:
- outputs from one action,
- to become inputs to another.

#### 3.4.7.6 Build Once, Promote the Known Release

Strong model:

```text
commit A
→ build artifact X
→ test X
→ deploy X to test
→ validate X
→ deploy X to prod
```

Weaker model:

```text
commit A
→ build X for test

later
→ rebuild source
→ build Y for prod
```

Rebuilding can introduce:
- a different artifact.

Exam-level principle:
- preserve release identity across environments.

Important nuance:
- AWS does not require every pipeline to reuse one identical build artifact in every environment.
- **Build once, promote the tested artifact** is an engineering best practice supported by CodePipeline's artifact model.

#### 3.4.7.7 Environment Promotion

The environment stays stable.
The release moves.

```text
artifact X
→ dev
→ test
→ staging
→ prod
```

Do not think:

```text
dev environment
→ becomes prod
```

Instead:
- the same approved release is deployed to different target environments.

Examples:

```text
DeployTest
→ test CloudFormation stack

DeployProd
→ prod CloudFormation stack
```

or:

```text
DeployTest
→ Lambda test alias

DeployProd
→ Lambda prod alias
```

or:

```text
DeployTest
→ ECS test service

DeployProd
→ ECS prod service
```

#### 3.4.7.8 Environment-Specific Configuration

Same artifact does not mean:
- identical environment configuration.

Example:

```text
artifact X

test:
DB_TABLE=orders-test

prod:
DB_TABLE=orders-prod
```

Environment-specific values can come from:
- stack parameters,
- Lambda environment variables,
- AppConfig,
- Systems Manager Parameter Store,
- Secrets Manager,
- deployment parameters.

Keep separate:

```text
release identity
→ same tested artifact/version

environment configuration
→ target-specific values/resources
```

Do not embed:
- production secrets,
- production endpoints
into a supposedly environment-neutral build artifact.

#### 3.4.7.9 Promotion Gates

A promotion gate answers:

**What must be true before this release reaches the next environment?**

Examples:
- tests pass,
- smoke test passes,
- health checks pass,
- security check passes,
- change set reviewed,
- manual approval granted.

Concept:

```text
DEPLOY TEST
→ VALIDATE
→ GATE
→ DEPLOY PROD
```

This is the core of orchestrated delivery.

#### 3.4.7.10 Automated Test Gates

Example:

```text
DeployTest
→ IntegrationTest
     |
     +-- PASS → continue
     |
     '-- FAIL → stop
```

The deployment action only proves:
- deployment mechanics completed.

A smoke/integration test proves:
- the deployed application behaves as required.

Example:

```text
DeployTest
→ SmokeTest
→ IntegrationTest
→ Approval
→ DeployProd
```

#### 3.4.7.11 Manual Approval

##### 3.4.7.11.1 Purpose
A CodePipeline manual approval action:

```text
pipeline reaches approval
→ pauses
→ authorized user approves or rejects
```

Approved:
- pipeline continues.

Rejected:
- action fails,
- downstream stages do not continue.

No response within the AWS-documented approval window:
- approval action fails.

##### 3.4.7.11.2 Approval Is a Gate

```text
manual approval
≠ deployment
```

It is:
- a decision point before a later deployment action.

##### 3.4.7.11.3 SNS Notification
Approval actions can optionally notify through:
- Amazon SNS.

Distinction:

```text
SNS
→ notification

CodePipeline approval
→ decision gate
```

#### 3.4.7.16 Cross-Account Deployment

Common model:

```text
Dev Account
Test Account
Prod Account
```

Central delivery model:

```text
Pipeline Account
→ assume role in target account
→ deploy target resources
```

Cross-account deployment can require:
- target-role trust,
- target-role permissions,
- artifact-bucket access,
- KMS permissions,
- permissions on target resources.

Critical rule:

```text
cross-account deployment
≠ AssumeRole only
```

#### 3.4.7.17 Cross-Account Artifact and KMS Access

A cross-account action may fail even when:
- role assumption succeeds.

Troubleshoot separately:

```text
can assume target role?
can read artifact?
can decrypt artifact?
can modify target resource?
```

If artifacts use:
- a customer-managed KMS key,

the target role/account may need:
- IAM permission,
- KMS key policy/grant authorization.

High-value exam model:

```text
IAM trust
+
target authorization
+
S3 artifact access
+
KMS authorization
```

#### 3.4.7.18 Cross-Region Deployment

CodePipeline can include supported actions in:
- a different AWS Region from the pipeline.

Concept:

```text
Pipeline Region A
→ deploy action Region B
```

Cross-Region artifact model:

```text
Pipeline Region
→ artifact bucket

Each additional action Region
→ artifact bucket in that Region
```

CodePipeline:
- copies required input artifacts to the target action Region.

For IaC/API reasoning:

```text
artifactStore
→ single Region

artifactStores
→ Region-to-artifact-store mapping
```

Important restriction from current AWS documentation:
- cross-Region source actions:
  - unsupported.
- cross-Region third-party actions:
  - unsupported.
- cross-Region custom actions:
  - unsupported.

Exam clue:

```text
deploy AWS workload to another Region
→ cross-Region action + artifact store in that Region
```

#### 3.4.7.19 Pipeline Execution Identity

Each pipeline run has:
- an execution identity,
- a source revision.

Example:

```text
Execution A
→ commit 123

Execution B
→ commit 456
```

Traceability should preserve:

```text
source commit
→ pipeline execution
→ artifact
→ test result
→ approval
→ deployment
```

This supports:
- audit,
- release verification,
- rollback context.

#### 3.4.7.20 Execution Modes

Current CodePipeline execution modes:
- `SUPERSEDED`,
- `QUEUED`,
- `PARALLEL`.

##### 3.4.7.20.1 SUPERSEDED
- Default mode.
- Newer execution can supersede older waiting execution between stages.

Correct mental model:

```text
old execution actively running action
→ not arbitrarily killed halfway through

older execution waiting between stages
→ can be superseded by newer execution
```

Use when:
- latest release should take priority.

##### 3.4.7.20.2 QUEUED

```text
A
→ B
→ C
```

Executions:
- run sequentially,
- in queued order.

Use when:
- every execution must run in order.

Current AWS requirement:
- QUEUED requires pipeline type V2.

##### 3.4.7.20.3 PARALLEL

```text
A ─────────>
B ─────────>
C ─────────>
```

Executions:
- run independently and concurrently.

Use when:
- isolated releases/tests can safely overlap.

Risk:
- shared mutable environments can conflict.

Current AWS requirements/restrictions:
- PARALLEL requires pipeline type V2.
- stage rollback is unavailable in PARALLEL mode.

#### 3.4.7.21 Parallel Actions vs Parallel Executions

Do not confuse:

```text
parallel actions
→ multiple actions inside one pipeline execution/stage

PARALLEL execution mode
→ multiple pipeline executions at the same time
```

They solve:
- different problems.

#### 3.4.7.22 Stage Failure and Retry

##### 3.4.7.22.1 Stage Failure
If a required action fails:

```text
stage fails
→ downstream stage does not run
```

Example:

```text
integration test fails
→ production deployment never starts
```

##### 3.4.7.22.2 Retry
Retry can be appropriate for:
- transient,
- corrected
failures.

Do not use retry to hide:
- deterministic application defects.

#### 3.4.7.23 Disabled Stage Transition

A stage's inbound transition can be disabled.

Example:

```text
Test succeeds
→ Prod transition disabled
→ release waits
```

Useful for:
- release freeze,
- maintenance window,
- temporary administrative hold.

Keep separate:

```text
disabled transition
→ administrative flow control

manual approval
→ explicit per-execution decision gate
```

In `SUPERSEDED` behavior:
- newer waiting executions can supersede older waiting executions at the blocked transition.

#### 3.4.7.24 Artifacts vs Variables

##### 3.4.7.24.1 Artifact
Carries files/bundles:

```text
AppArtifact.zip
```

##### 3.4.7.24.2 Variable
Carries metadata/value:

```text
COMMIT_SHA=abc123
```

CodePipeline actions can expose:
- variables for later actions.

Use:

```text
artifact
→ files/data bundle

variable
→ metadata/configuration value
```

Do not confuse them.

#### 3.4.7.25 IAM Role Boundaries

##### 3.4.7.25.1 Pipeline Service Role
Used for:
- orchestration,
- accessing artifact stores,
- invoking action providers,
- assuming configured action roles.

##### 3.4.7.25.2 Action/Cross-Account Role
Used for:
- target-specific permissions,
- cross-account deployment,
- least-privilege separation.

Principle:

```text
pipeline role
→ orchestration permissions

action/target role
→ environment-specific execution permissions
```

Do not solve every deployment issue by:
- giving the pipeline role administrator access.

#### 3.4.7.26 Environment Isolation

A multi-environment workflow should prevent accidental cross-environment access.

Example:

```text
test deploy
→ test account
→ test database
→ test secrets

prod deploy
→ prod account
→ prod database
→ prod secrets
```

Environment isolation can be implemented through:
- different accounts,
- different stacks,
- different services/resources,
- different roles,
- different configuration/secrets.

Same artifact:
- can be promoted safely.

Environment-specific dependencies:
- remain isolated.

#### 3.4.7.27 Common Failure Patterns

##### 3.4.7.27.1 Wrong Artifact Rebuilt for Production
Problem:

```text
test artifact X
→ passes

prod stage rebuilds source
→ artifact Y
```

Now production does not deploy:
- the exact tested artifact.

Better:
- promote X.

##### 3.4.7.27.2 Production Starts Before Tests Finish
Cause:
- incorrect stage/action ordering.

Fix:
- place production deployment after required test gate.

##### 3.4.7.27.3 Approval Exists but Does Not Gate Production
Check:
- approval stage position,
- run order,
- deployment action path.

An approval only gates:
- downstream work.

##### 3.4.7.27.4 Cross-Account `AccessDenied`
Check separately:
- role assumption,
- target-role trust,
- target permissions,
- artifact bucket,
- KMS decrypt.

##### 3.4.7.27.5 Cross-Region Action Cannot Find Artifact
Check:
- action Region,
- Regional artifact store,
- artifactStores mapping,
- S3/KMS permissions.

##### 3.4.7.27.6 Older Commit Never Reaches Production
If mode is:
- `SUPERSEDED`,

this can be expected.

If every release must run:
- consider `QUEUED`.

##### 3.4.7.27.7 Parallel Executions Corrupt Shared Test Environment
If using:
- `PARALLEL`,

multiple releases can modify/test simultaneously.

Possible remedies:
- isolated environments,
- serialize executions,
- use another execution mode.

##### 3.4.7.27.8 Manual Approval Expires
Approval is:
- not indefinite.

Ensure:
- approvers are notified,
- ownership exists.

#### 3.4.7.29 Common Exam Traps

##### 3.4.7.29.1 CodePipeline Builds the Application
- False.
- CodeBuild/build provider does.

##### 3.4.7.29.2 CodePipeline Directly Performs Every Deployment
- False.
- It invokes deployment providers/actions.

##### 3.4.7.29.3 CodePipeline Stage = API Gateway Stage
- False.

##### 3.4.7.29.4 Manual Approval Is a Deployment Strategy
- False.
- It is a workflow gate.

##### 3.4.7.29.5 Rebuild Artifact for Each Environment
- Not required.
- Prefer the same validated artifact when practical.

##### 3.4.7.29.6 Cross-Account Requires Only `AssumeRole`
- False.
- Artifact/KMS access can also be required.

##### 3.4.7.29.7 Cross-Region Uses One Artifact Bucket
- False for pipelines with actions in multiple Regions.

##### 3.4.7.29.8 PARALLEL Actions = PARALLEL Execution Mode
- False.

##### 3.4.7.29.9 CodePipeline = Step Functions
- False.
- CodePipeline:
  - software delivery.
- Step Functions:
  - application/business workflow orchestration.

##### 3.4.7.29.10 Same Artifact Means Same Secrets
- False.
- Configuration/secrets remain environment-specific.

#### 3.4.7.32 Exam-Level Knowledge Frame

##### 3.4.7.32.1 Know These Cold

**Pipeline**
→ complete CI/CD workflow.

**Stage**
→ logical release phase/environment boundary containing actions.

**Action**
→ performs source/build/test/deploy/approval/invoke work.

**Run order**
→ sequences actions inside a stage.

**Artifact**
→ files/bundles passed between actions.

**Variable**
→ metadata/value exposed to later actions.

**Manual approval**
→ explicit release gate.

**SUPERSEDED**
→ default; newer execution can supersede older waiting execution between stages.

**QUEUED**
→ executions run in order; requires V2.

**PARALLEL**
→ executions run independently/concurrently; requires V2; no stage rollback.

**Cross-account**
→ role assumption + artifact/KMS access + target authorization.

**Cross-Region**
→ supported action in another Region + artifact store in that Region.

```text
business/application workflow?

```

##### 3.4.7.32.3 Final Principle
- **Skill 3.4.7 is about release orchestration across environments. CodePipeline is the workflow layer: pipelines contain ordered stages, stages contain serial or parallel actions, and actions consume and produce artifacts. Use automated tests and approvals as promotion gates, preserve source/artifact identity as the release moves through environments, and keep environment configuration isolated. For account-separated targets, account for role assumption plus artifact/KMS access; for multi-Region targets, configure Regional artifact stores; and choose SUPERSEDED, QUEUED, or PARALLEL execution behavior according to how overlapping releases should progress.**
