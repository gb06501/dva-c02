### 1.1.13 Implement resilient application code for third-party service integrations

#### 1.1.13.1 Exam Context

##### 1.1.13.1.1 Skill Scope
- DVA-C02 Skill 1.1.13 requires implementing resilient application code for third-party service integrations.
- The exam guide explicitly gives retry logic, circuit breakers, and error-handling patterns as examples.
- This skill applies general resilience principles specifically to dependencies that the application does not control.
- A third-party dependency can fail, throttle, become slow, return malformed data, change behavior, or be unreachable even while the AWS-hosted application itself remains healthy.

##### 1.1.13.1.2 Core Mental Model
- A remote dependency is a failure boundary.
- Never assume a remote call will succeed quickly or consistently.
- A resilient client controls:
  - how long it waits,
  - which failures it retries,
  - how frequently it retries,
  - when it stops calling,
  - how it behaves when the dependency remains unavailable,
  - and how the failure is observed.
- The basic flow is:
  - call → timeout/error classification → retry if transient → circuit breaker if persistent → fallback/degrade/fail explicitly.

#### 1.1.13.2 Failure Types

##### 1.1.13.2.1 Transient Failure
- Temporary network interruption.
- Connection reset or timeout.
- Temporary service unavailability.
- Rate limiting/throttling.
- Selected server-side 5xx failures.
- Transient failures can be candidates for bounded retry.

##### 1.1.13.2.2 Persistent Failure
- Invalid credentials.
- Invalid request.
- Unsupported operation.
- Permanent authorization failure.
- Invalid endpoint/configuration.
- Repeated service failure that is unlikely to recover within the caller's latency budget.
- Persistent failures should generally fail fast rather than being retried repeatedly.

##### 1.1.13.2.3 Slow Dependency
- A dependency can be technically available but respond too slowly.
- Slow calls consume threads, connections, memory, concurrency, and request budget.
- Timeouts are therefore a resilience mechanism, not only a networking setting.

#### 1.1.13.3 Timeouts

##### 1.1.13.3.1 Why Timeouts Matter
- Every remote call should have a bounded wait time.
- Without timeouts, blocked calls can exhaust application resources.
- Timeout values should reflect the application's end-to-end latency requirement and the dependency's expected behavior.

##### 1.1.13.3.2 Connection Timeout
- Bounds how long the client waits to establish a connection.
- A short connection timeout can fail quickly when the remote endpoint is unreachable.

##### 1.1.13.3.3 Request/Read Timeout
- Bounds how long the client waits for the remote operation/response.
- Configure it according to expected service latency and caller latency budget.
- Do not use an arbitrarily large timeout merely to hide an unreliable dependency.

##### 1.1.13.3.4 Timeout Budget
- A request may call several downstream services.
- Individual dependency timeouts must fit within the overall request deadline.
- Retry attempts also consume the same end-to-end latency budget.

#### 1.1.13.4 Retry

##### 1.1.13.4.1 Retry Purpose
- Retry is appropriate when a failure is likely to be temporary.
- AWS Prescriptive Guidance identifies throttling, temporary network problems, and temporary service unavailability as typical retry-with-backoff scenarios.
- Retry should improve the chance of recovery without overwhelming the failing dependency.

##### 1.1.13.4.2 Bounded Retry
- Set a maximum number of attempts or maximum elapsed time.
- Do not retry indefinitely.
- Once the retry budget is exhausted, produce an explicit failure/fallback outcome.

##### 1.1.13.4.3 Retry Only Appropriate Errors
- Retry transient failures.
- Do not automatically retry every exception or HTTP error.
- Authentication, authorization, validation, and other deterministic failures normally require a change rather than another identical attempt.

#### 1.1.13.5 Exponential Backoff

##### 1.1.13.5.1 Backoff
- Increase the delay between subsequent retry attempts.
- Backoff reduces pressure on a dependency that might already be overloaded.
- Immediate repeated retries can amplify an outage.

##### 1.1.13.5.2 Exponential Backoff
- Delay increases exponentially as attempts continue.
- The exact formula is implementation-dependent.
- Keep a maximum delay and overall retry limit.

##### 1.1.13.5.3 Jitter
- Add randomness to retry delays.
- Without jitter, many clients can retry simultaneously and create synchronized traffic spikes.
- AWS Well-Architected explicitly recommends exponential backoff with jitter.

#### 1.1.13.6 Idempotency

##### 1.1.13.6.1 Retry Safety
- Before retrying a mutating remote operation, determine whether repeating it is safe.
- A timeout does not prove that the remote operation failed; the server might have completed the operation while the response was lost.
- Retrying a non-idempotent operation can therefore create duplicate side effects.

##### 1.1.13.6.2 Idempotency Key
- If the third-party API supports idempotency keys/tokens, use them for retryable mutating operations.
- Reuse the same key for retries of the same logical operation.
- Do not generate a new key for each retry because that can make each attempt appear to be new work.

##### 1.1.13.6.3 Application-Side Protection
- If the dependency has no idempotency mechanism, application logic may need to track operation state or reconcile ambiguous outcomes.
- Do not assume a client library can make a fundamentally non-idempotent API safe.

#### 1.1.13.7 Retry Storms

##### 1.1.13.7.1 Multiplicative Retries
- If multiple layers independently retry, attempts can multiply.
- Example: caller retries a service that retries an HTTP client that also retries.
- AWS Well-Architected recommends understanding retry behavior and implementing retries at an appropriate layer rather than blindly stacking them.

##### 1.1.13.7.2 Retry Amplification
- During an outage, retries add traffic exactly when the dependency has reduced capacity.
- Backoff, jitter, bounded attempts, and circuit breakers reduce amplification.
- Observe total attempts across all client/library layers.

#### 1.1.13.8 Circuit Breaker

##### 1.1.13.8.1 Purpose
- A circuit breaker stops repeated calls to a dependency that is persistently failing or timing out.
- It prevents wasting resources on requests that are unlikely to succeed.
- It also gives the dependency time to recover.

##### 1.1.13.8.2 Closed
- Calls are allowed normally.
- Failures are monitored.
- Repeated failures reaching the configured threshold cause the circuit to open.

##### 1.1.13.8.3 Open
- Calls fail fast without contacting the dependency.
- The application can return an error, use cached data, queue work, or degrade functionality according to requirements.
- After a configured recovery interval, the circuit can test whether the dependency has recovered.

##### 1.1.13.8.4 Half-Open
- A limited number of test calls are allowed.
- Successful calls can close the circuit.
- Continued failure reopens it.

##### 1.1.13.8.5 Retry vs Circuit Breaker
- Retry assumes the failure is transient and another attempt might soon succeed.
- Circuit breaker assumes repeated calls are currently harmful or unlikely to succeed.
- The two patterns complement one another when configured carefully.

#### 1.1.13.9 Rate Limiting and Throttling

##### 1.1.13.9.1 Third-Party Limits
- External APIs often impose request-rate or quota limits.
- Respect documented limits rather than relying on 429 responses as normal flow control.
- Client-side rate limiting can protect both the dependency and the application.

##### 1.1.13.9.2 HTTP 429
- A 429 response indicates that requests are being rate limited.
- Retry only according to the API's documented semantics.
- Honor Retry-After or equivalent provider guidance when present.
- Apply backoff and jitter rather than immediately resending requests.

##### 1.1.13.9.3 Concurrency Control
- Limit concurrent calls to fragile or quota-constrained dependencies.
- Unbounded parallelism can overwhelm a third-party service even when average request rate appears acceptable.

#### 1.1.13.10 Error Classification

##### 1.1.13.10.1 Transport Errors
- DNS failure.
- Connection failure/reset.
- TLS/network errors.
- Timeout.
- Often transient, but retry policy must remain bounded.

##### 1.1.13.10.2 HTTP Client Errors
- 4xx generally indicate a request, authentication, authorization, or business problem.
- Do not treat every 4xx as retryable.
- 408 and 429 can represent transient/retryable conditions depending on provider semantics.

##### 1.1.13.10.3 HTTP Server Errors
- 5xx indicates server-side failure.
- Some 5xx errors are appropriate for retry.
- Use the third party's API documentation when it defines specific retry semantics.

##### 1.1.13.10.4 Application-Level Errors
- A successful HTTP transport response can still contain a business failure.
- Separate transport/protocol success from business-operation success.
- Retry only if the business error is explicitly transient.

#### 1.1.13.11 Graceful Degradation and Fallback

##### 1.1.13.11.1 Graceful Degradation
- Preserve core application functionality when a non-critical dependency fails.
- Disable or postpone only the feature that requires the unavailable dependency when possible.
- Make degraded behavior explicit and observable.

##### 1.1.13.11.2 Cached/Stale Data
- If business requirements allow, serve recently cached data when the live third-party service is unavailable.
- Clearly define acceptable staleness.
- Do not use stale data where correctness or safety requires current information.

##### 1.1.13.11.3 Default/Fallback Response
- A fallback can return a safe default or reduced response.
- Do not fabricate business data merely to hide dependency failure.
- Fallback behavior must be intentional and domain-correct.

##### 1.1.13.11.4 Asynchronous Deferral
- If immediate completion is unnecessary, queue work and process it later.
- Amazon SQS can decouple application availability from third-party availability.
- This is especially useful for notifications, synchronization, and other eventually completed work.

#### 1.1.13.12 Bulkhead / Failure Isolation

##### 1.1.13.12.1 Isolate Dependency Resources
- Do not allow one failing dependency to consume all application resources.
- Separate connection pools, concurrency limits, queues, or worker capacity where appropriate.
- A failure in one integration should not automatically exhaust capacity needed for unrelated application functions.

##### 1.1.13.12.2 Bounded Queues
- Asynchronous buffering must also be bounded operationally.
- A dependency outage can cause queue depth and message age to grow.
- Monitor backlog and define what happens when recovery takes too long.

#### 1.1.13.13 Authentication and Secrets

##### 1.1.13.13.1 Third-Party Credentials
- Third-party API keys, client secrets, and tokens should not be hard-coded in application source.
- Store secrets in an appropriate managed secrets mechanism.
- AWS Secrets Manager is explicitly in scope for DVA-C02 and is the primary AWS service for managed secret storage/rotation scenarios.

##### 1.1.13.13.2 Retrieval
- Application code retrieves the required secret at runtime using appropriate AWS permissions.
- Cache secrets appropriately when repeated retrieval would add unnecessary latency/cost, while still supporting rotation requirements.
- Do not log retrieved secret values.

##### 1.1.13.13.3 Rotation and Expiration
- Third-party credentials can expire or be rotated.
- Distinguish credential-expiration/authentication failure from transient network failure.
- Repeatedly retrying invalid credentials does not restore service.

##### 1.1.13.13.4 Domain Boundary
- Detailed secret management, IAM, encryption, and authentication belong to Domain 2.
- Here the key resilience point is that external credentials are managed safely and authentication failures are classified correctly.

#### 1.1.13.14 API Gateway and EventBridge Options

##### 1.1.13.14.1 API Gateway
- Amazon API Gateway can expose or mediate APIs but does not eliminate the need for resilience when application code calls a third party.
- If Lambda/backend code performs the external call, that code owns timeout, retry, circuit-breaker, and error-classification behavior.
- API-specific creation and transformations belong to Skill 1.1.6.

##### 1.1.13.14.2 EventBridge API Destinations
- EventBridge API destinations can deliver events to HTTPS endpoints.
- When EventBridge owns the delivery, use its connection, retry, rate, and DLQ capabilities rather than duplicating all delivery logic in custom code.
- This can be preferable when the requirement is event delivery rather than synchronous request/response application logic.
- EventBridge implementation belongs to Skill 1.1.12.

##### 1.1.13.14.3 SQS Buffer
- SQS can sit between application work and a worker that calls the third-party API.
- The queue absorbs temporary dependency outages and rate differences.
- Visibility timeout, retries, DLQ, and idempotency then become part of the integration design.
- Messaging implementation belongs to Skill 1.1.8.

#### 1.1.13.15 Lambda Considerations

##### 1.1.13.15.1 Timeout Relationship
- A Lambda function calling a third party must use client timeouts shorter than the Lambda function's remaining execution time.
- Otherwise the runtime can terminate the invocation before application error handling completes.

##### 1.1.13.15.2 Concurrency
- Lambda can scale quickly and generate more concurrent third-party calls than the external service can accept.
- Control concurrency when the dependency has strict rate/concurrency limits.
- Detailed Lambda concurrency configuration belongs to Task 1.2.

##### 1.1.13.15.3 Retry Multiplication
- Understand both Lambda/event-source retry behavior and HTTP-client retry behavior.
- Combining platform retries with application retries can multiply attempts.
- Design the complete retry path rather than configuring each layer independently.

#### 1.1.13.16 Observability

##### 1.1.13.16.1 Metrics
- Measure dependency request count.
- Measure latency.
- Measure timeout count.
- Measure errors by class/status.
- Measure retry count.
- Measure circuit-breaker state/open events.
- Measure throttling/rate-limit responses.

##### 1.1.13.16.2 Logging
- Log enough context to identify the dependency, operation, correlation identifier, status/error class, and retry outcome.
- Do not log API keys, authorization headers, tokens, or sensitive payloads.

##### 1.1.13.16.3 CloudWatch
- Amazon CloudWatch is explicitly in scope for DVA-C02.
- Application metrics, logs, and alarms can make third-party degradation visible.
- Detailed observability/troubleshooting belongs to Domain 4.

#### 1.1.13.17 Testing Resilience

##### 1.1.13.17.1 Simulate Failures
- Test timeout behavior.
- Test connection failures.
- Test 429 throttling.
- Test retryable 5xx responses.
- Test non-retryable 4xx responses.
- Test malformed responses.
- Test persistent failure that opens the circuit breaker.

##### 1.1.13.17.2 Verify Retry Safety
- Confirm duplicate attempts do not create duplicate business effects.
- Verify idempotency behavior for mutating operations.
- Verify the maximum retry count/time is actually bounded.

##### 1.1.13.17.3 Verify Degradation
- Test the fallback/degraded path.
- Verify queues/backlogs remain observable.
- Verify the application recovers when the third party becomes healthy again.

#### 1.1.13.18 Third-Party Integration Decision Model

##### 1.1.13.18.1 Transient Network/5xx Failure
- Retry if the operation is safe.
- Use bounded exponential backoff with jitter.
- Respect the overall latency budget.

##### 1.1.13.18.2 429 Rate Limit
- Respect provider retry guidance/Retry-After.
- Back off.
- Reduce request rate/concurrency.
- Do not create a retry storm.

##### 1.1.13.18.3 Authentication/Validation Failure
- Fail fast.
- Do not repeatedly retry identical invalid requests.
- Correct credentials/input/configuration.

##### 1.1.13.18.4 Dependency Repeatedly Failing
- Open the circuit breaker.
- Fail fast or use an intentional fallback.
- Probe later through half-open behavior.

##### 1.1.13.18.5 Immediate Response Not Required
- Decouple with SQS or another asynchronous mechanism.
- Process when the third party is available.
- Use DLQ/backlog monitoring for persistent failure.

##### 1.1.13.18.6 Event Must Be Delivered to External HTTPS API
- Consider EventBridge API destinations.
- Let EventBridge manage delivery retries/rate/DLQ where its model fits.
- Avoid custom integration code when a managed integration satisfies the requirement.

##### 1.1.13.18.7 Third-Party Secret Required
- Store/retrieve it through an appropriate managed secret mechanism such as AWS Secrets Manager.
- Do not hard-code it.
- Treat expired/invalid credentials as non-transient.

#### 1.1.13.19 Important Distinctions

##### 1.1.13.19.1 Timeout vs Retry
- Timeout limits one attempt.
- Retry decides whether another attempt should occur.
- A retry strategy without a timeout can still block too long.

##### 1.1.13.19.2 Retry vs Circuit Breaker
- Retry tries again because recovery is expected soon.
- Circuit breaker stops trying because repeated calls are currently counterproductive.

##### 1.1.13.19.3 Circuit Breaker vs Rate Limiter
- Circuit breaker reacts to dependency failure.
- Rate limiter controls how much traffic is sent.
- Both can protect a dependency but solve different problems.

##### 1.1.13.19.4 Retry vs Queue
- Retry repeats an operation within a bounded attempt/time policy.
- Queueing defers work and decouples processing from immediate dependency availability.
- Long outages often fit asynchronous deferral better than very long synchronous retry chains.

##### 1.1.13.19.5 Fallback vs Silent Failure
- Fallback is an intentional documented degraded behavior.
- Silent failure hides lost or incomplete work.
- Never treat swallowing an exception as resilience.

##### 1.1.13.19.6 AWS SDK Retry vs Third-Party Client Retry
- AWS SDK retry behavior applies to calls to AWS services.
- Third-party HTTP/API clients have their own retry behavior or may have none.
- Do not assume AWS SDK retry configuration automatically protects external API calls.

#### 1.1.13.21 In-Scope Service Check

##### 1.1.13.21.1 DVA-C02 Alignment
- This skill is primarily an application-code resilience skill rather than a single-service skill.
- Relevant explicitly in-scope AWS services include:
  - Amazon API Gateway for API integration boundaries.
  - Amazon EventBridge for API destinations and managed event delivery.
  - Amazon SQS for asynchronous buffering and DLQs.
  - AWS Lambda for application compute that commonly calls external APIs.
  - AWS Secrets Manager for third-party credentials.
  - Amazon CloudWatch for monitoring external dependency health.
  - AWS X-Ray for tracing distributed calls where applicable.
- Use these services to support the resilience design when they fit the scenario; do not replace code-level resilience with unrelated AWS services.

##### 1.1.13.21.2 Exam Depth
- Know timeouts.
- Know transient vs persistent error classification.
- Know bounded retries with exponential backoff and jitter.
- Know idempotency requirements before retrying mutating operations.
- Know circuit breaker closed/open/half-open states.
- Know graceful degradation/fallback.
- Know how queues can decouple external outages.
- Know how rate limits and retry storms interact.
- Know that third-party secrets must be managed safely.
- Know where EventBridge API destinations can replace custom event-delivery code.

##### 1.1.13.22.2 AWS Well-Architected Reliability Pillar
- Set client timeouts.
- Control and limit retry calls.
- Use exponential backoff and jitter.
- Avoid retry storms across multiple layers.
- Verify idempotency before retrying.
- Fail fast when errors are non-transient.
- Use graceful degradation and fault isolation.

- Retry with backoff pattern.
- Circuit breaker pattern.
- Retry for transient errors such as throttling, temporary network failures, and temporary service unavailability.
- Fail fast/circuit-break when continued calls are unlikely to succeed.
