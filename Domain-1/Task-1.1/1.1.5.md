### 1.1.5 Create fault-tolerant and resilient applications in a programming language

#### 1.1.5.1 Reliability, Resilience, and Fault Tolerance

##### 1.1.5.1.1 Resilience
- AWS defines resiliency as the ability of a workload to recover from infrastructure or service disruptions, dynamically acquire computing resources to meet demand, and mitigate disruptions such as misconfigurations or transient network issues.
- Resilient application code assumes that failures will occur and handles them in a controlled, recoverable way.
- Recovery behavior should be part of normal application design rather than treated as an exceptional afterthought.

##### 1.1.5.1.2 Fault Tolerance
- Fault tolerance means the application continues to provide required functionality despite failures of individual components or dependencies.
- Fault isolation limits the impact of a failure to a defined boundary so components outside that boundary remain unaffected.
- Fault-tolerant code avoids turning a localized failure into a workload-wide failure.

##### 1.1.5.1.3 Failure as a Normal Condition
- Distributed applications experience network latency, timeouts, throttling, temporary unavailability, dependency failures, and partial failures.
- Application code should distinguish transient failures from failures that are unlikely to succeed if immediately retried.
- Failure behavior should be explicit, bounded, observable, and testable.

#### 1.1.5.2 Timeouts

##### 1.1.5.2.1 Client Timeouts
- Remote calls must have finite timeouts.
- A caller should not wait indefinitely for an unhealthy or unreachable dependency.
- Timeouts release resources and bound how long a failed dependency can block application processing.
- Connection timeouts and request/read timeouts can require separate configuration.
- AWS SDKs provide language-specific timeout configuration.

##### 1.1.5.2.2 Timeout Selection
- A timeout should reflect the expected latency and business requirement of the operation.
- A timeout that is too long delays failure detection and consumes resources.
- A timeout that is too short can cause valid slow requests to fail unnecessarily.
- Timeout behavior should be tested under realistic latency and failure conditions.

#### 1.1.5.3 Retries

##### 1.1.5.3.1 Retry Transient Failures
- Retries are useful for failures that are temporary, such as transient network issues, temporary service unavailability, or throttling.
- Do not retry every error.
- Permission errors, invalid configuration, invalid requests, and other non-transient failures generally require correction rather than repeated execution.

##### 1.1.5.3.2 Exponential Backoff
- Retry attempts should be separated by progressively longer delays.
- Exponential backoff reduces pressure on a dependency that is already impaired or overloaded.
- Immediate repeated retries can worsen a failure and contribute to a retry storm.

##### 1.1.5.3.3 Jitter
- Add randomness to retry delays.
- Without jitter, many clients can retry at the same intervals and create synchronized traffic spikes.
- Jitter spreads retries over time and reduces coordinated retry bursts.

##### 1.1.5.3.4 Bounded Retries
- Set a maximum number of retries or maximum elapsed retry time.
- Unlimited retries consume resources, increase latency, and can create large backlogs.
- The application must eventually stop retrying and take an explicit failure path.

##### 1.1.5.3.5 Retry at the Correct Layer
- Avoid retrying the same failure at multiple layers of an application stack.
- Nested retries multiply request volume and can create retry storms.
- Choose the layer that has enough context to decide whether retrying is safe and useful.

##### 1.1.5.3.6 Prefer Proven Retry Implementations
- AWS SDKs include configurable retry behavior.
- Use SDK or established library retry mechanisms where they satisfy the workload requirement.
- Do not assume defaults are correct; verify and test retry behavior.

#### 1.1.5.4 Idempotency

##### 1.1.5.4.1 Idempotent Operations
- An idempotent operation can be repeated without causing additional unintended side effects.
- Multiple identical requests should have the same effect as a single request.
- Idempotency makes retries safer.

##### 1.1.5.4.2 Idempotency Tokens
- A client can provide a unique idempotency token with a mutating request.
- Repeated requests use the same token.
- The service can recognize that the operation was already processed and avoid duplicating the side effect.

##### 1.1.5.4.3 Event and Message Processing
- Event-driven and queued systems can deliver the same message more than once.
- Consumers should be designed so duplicate delivery does not create duplicate business effects.
- Idempotency identifiers should be propagated downstream where multiple services participate in processing.

##### 1.1.5.4.4 Examples of Side Effects to Protect
- Creating duplicate orders
- Charging a customer twice
- Sending the same command more than once
- Inserting duplicate records
- Applying the same state transition repeatedly

#### 1.1.5.5 Fail Fast

##### 1.1.5.5.1 Fail Fast Behavior
- When a request cannot succeed, return or propagate failure promptly rather than consuming resources indefinitely.
- Failing fast allows resources such as threads, connections, and memory to be released.
- It can help an impaired service recover by preventing useless work.

##### 1.1.5.5.2 Non-Retryable Failures
- Fail fast when the error is known to be non-transient.
- Examples include authorization failures, malformed requests, incompatible configuration, or other conditions that will not change through immediate retry.

##### 1.1.5.5.3 Queue Limits
- Queues can smooth traffic and isolate components, but queue growth must be bounded.
- Very large backlogs can cause stale work to be processed after it is no longer useful.
- Queue depth, message age, and consumer capacity should be monitored.

#### 1.1.5.6 Graceful Degradation

##### 1.1.5.6.1 Soft Dependencies
- AWS recommends transforming applicable hard dependencies into soft dependencies.
- An application component should continue delivering its core business function when a non-critical dependency is unavailable.
- The application might return slightly stale data, alternate data, partial results, or omit non-essential data.

##### 1.1.5.6.2 Core vs Optional Functionality
- Identify which dependencies are required for the core business function.
- Optional features should not unnecessarily make the entire application unavailable.
- Degraded behavior should be predictable and explicitly designed.

##### 1.1.5.6.3 Partial Failure
- Avoid turning a single failed dependency into total application failure when useful partial output is possible.
- Avoid leaving inconsistent state after partially completed operations.
- Compensation, rollback, or another recovery path can be required when work spans several steps.

#### 1.1.5.7 Circuit Breakers

##### 1.1.5.7.1 Circuit Breaker Purpose
- A circuit breaker prevents repeated calls to a dependency that is known to be failing or timing out.
- It protects both caller and dependency from repeated unsuccessful work.
- It is especially useful when failures are likely to persist longer than a normal transient retry window.

##### 1.1.5.7.2 Circuit States
- Closed: calls flow normally.
- Open: calls fail immediately without invoking the unhealthy dependency.
- Half-open or probe behavior: limited calls test whether the dependency has recovered.

##### 1.1.5.7.3 Retry vs Circuit Breaker
- Retry with backoff addresses transient failures that are expected to recover quickly.
- Circuit breaker addresses repeated or persistent dependency failures where continuing to retry would waste resources or worsen the problem.
- Both patterns can be combined, but retries must remain bounded.

##### 1.1.5.7.4 Scope Boundary
- Circuit breakers are relevant to general resilient application code here.
- Detailed resilience specifically for third-party service integrations is expanded in Skill 1.1.13.

#### 1.1.5.8 Fault Isolation

##### 1.1.5.8.1 Isolation Boundaries
- A failure should affect the smallest practical portion of the workload.
- Code and architecture should prevent one failed component from consuming all shared resources or propagating failure across the system.
- Independent components should have clear failure boundaries.

##### 1.1.5.8.2 Bulkhead Pattern
- AWS uses bulkhead or cell-based architecture to constrain failures to isolated portions of a workload.
- Separate cells or resource pools reduce the blast radius of defects, overload, or bad deployments.
- The programming-level equivalent is to avoid unrestricted sharing of critical resources across unrelated workloads.

##### 1.1.5.8.3 Resource Isolation
- Use bounded thread pools, connection pools, concurrency limits, queues, or other appropriate resource controls.
- A failing dependency or workload class should not exhaust resources required by unrelated processing.

#### 1.1.5.9 Load Protection and Backpressure

##### 1.1.5.9.1 Throttling
- Protect dependencies from receiving more work than they can process.
- Rate limiting and throttling prevent overload from spreading through the system.

##### 1.1.5.9.2 Buffering
- Queues can absorb short-lived differences between producer and consumer processing rates.
- Buffering should be finite and observable.
- Queues are not a substitute for sufficient processing capacity.

##### 1.1.5.9.3 Backpressure
- A system should have a strategy when producers generate work faster than consumers can process it.
- Strategies include rejecting work, throttling producers, limiting queue depth, shedding lower-priority work, or scaling consumers.
- Unbounded work accumulation is a reliability risk.

#### 1.1.5.10 Recovery and Fallback

##### 1.1.5.10.1 Recovery Paths
- Define what happens after retries are exhausted or a dependency remains unavailable.
- Possible outcomes include returning an error, placing work in a durable queue, invoking a compensating action, or switching to degraded behavior.
- Recovery logic should preserve data consistency and avoid hidden failure.

##### 1.1.5.10.2 Fallbacks
- A fallback can provide alternate behavior when a dependency fails.
- Fallbacks should be simple, well tested, and safe under the same failure conditions.
- A fallback that depends on another fragile system can create additional failure modes.
- Do not use fallback behavior that hides serious failures without observability.

#### 1.1.5.11 Error Handling in Application Code

##### 1.1.5.11.1 Categorize Errors
- Distinguish transient failures from permanent or application-level failures.
- Use service and SDK error information rather than retrying generically.
- Error handling should preserve enough context for diagnosis without exposing sensitive data.

##### 1.1.5.11.2 Explicit Failure Paths
- Every remote interaction should define success, timeout, retryable failure, non-retryable failure, and final failure behavior.
- Avoid swallowing exceptions and continuing with invalid or incomplete state.
- Return meaningful errors or emit appropriate failure events when processing cannot continue.

##### 1.1.5.11.3 Resource Cleanup
- Release resources when requests fail or time out.
- Close or return connections, streams, locks, and other resources according to the language/runtime model.
- Failure handling itself should not leak resources.

#### 1.1.5.12 Observability for Resilience

##### 1.1.5.12.1 Detect Repeated Failures
- Monitor timeout rates, retry counts, throttling, dependency errors, circuit-breaker state, queue depth, and message age where applicable.
- Repeated retries should be visible so the underlying problem is not hidden by successful eventual retries.

##### 1.1.5.12.2 Correlation
- Preserve request, trace, message, or correlation identifiers across component boundaries.
- Correlation allows a distributed failure path to be reconstructed.

##### 1.1.5.12.3 Scope Boundary
- This skill requires resilient code to be observable enough to verify its behavior.
- Full logging, metrics, tracing, and observability implementation is expanded under Domain 4.

#### 1.1.5.13 Testing Resilience

##### 1.1.5.13.1 Test Failure Paths
- Test timeouts, throttling, transient failures, duplicate requests, unavailable dependencies, and retry exhaustion.
- Verify that recovery behavior produces the intended application state.

##### 1.1.5.13.2 Verify Retry Behavior
- Confirm actual SDK/library retry configuration rather than assuming defaults.
- Verify maximum attempts, backoff, jitter, and which errors are retried.
- Test that retries do not amplify load excessively.

##### 1.1.5.13.3 Verify Idempotency
- Repeat mutating operations and duplicate messages in tests.
- Verify that repeated processing does not create duplicate business effects.

##### 1.1.5.13.4 Resilience Testing
- AWS distinguishes deterministic resilience testing from chaos engineering.
- Resilience tests should validate known mechanisms such as retries, circuit breakers, failover, or fallback.

#### 1.1.5.14 Programming-Language Mindset

##### 1.1.5.14.1 Language Independence
- The exam guide explicitly allows languages such as Java, C#, Python, JavaScript, TypeScript, and Go.
- The resilience principles are language-independent.
- Language-specific implementation differs through SDK configuration, exception handling, concurrency primitives, HTTP clients, libraries, and framework behavior.

##### 1.1.5.14.2 Prefer Platform and Library Capabilities
- Use AWS SDK retry and timeout capabilities where appropriate.
- Use established resilience libraries when they provide tested implementations of retry, circuit breaker, timeout, rate limiting, or bulkhead behavior.
- Custom resilience logic should be introduced only when existing mechanisms do not satisfy the requirement.

#### 1.1.5.15 Resilience Decision Model

##### 1.1.5.15.1 Remote Call
- Set an appropriate timeout.
- Classify the error.
- Retry only if the failure is transient and the operation is safe to retry.
- Use exponential backoff, jitter, and bounded retries.

##### 1.1.5.15.2 Mutating Operation
- Make retries safe through idempotency.
- Detect duplicate requests or messages.
- Preserve consistency if processing partially succeeds.

##### 1.1.5.15.3 Persistent Dependency Failure
- Fail fast instead of repeatedly consuming resources.
- Consider a circuit breaker.
- Use graceful degradation when the dependency is not required for the core function.

##### 1.1.5.15.4 Overload
- Throttle or rate limit work.
- Buffer only when asynchronous processing is acceptable.
- Limit queue depth and apply backpressure.
- Protect unrelated work through resource and fault isolation.

##### 1.1.5.15.5 Final Failure
- Produce an explicit and observable outcome.
- Preserve or compensate state correctly.
- Do not silently discard work.
