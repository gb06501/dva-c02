### 1.1.6 Create, extend, and maintain APIs

#### 1.1.6.1 API Development Scope

##### 1.1.6.1.1 API Lifecycle
- Create an API contract and expose application functionality through defined operations.
- Connect API operations to backend integrations.
- Validate incoming requests before sending them to the backend where appropriate.
- Transform requests and responses when the external API contract differs from the backend contract.
- Return meaningful HTTP responses and status codes.
- Extend an existing API without unnecessarily breaking existing consumers.
- Maintain the API definition and integrations as the application evolves.

##### 1.1.6.1.2 AWS API Services in Scope
- Amazon API Gateway is the primary AWS service for creating REST, HTTP, and WebSocket APIs.
- AWS AppSync provides managed GraphQL APIs.
- This skill's explicit examples—request/response transformation, validation rules, and status-code overrides—map directly to API Gateway capabilities.

#### 1.1.6.2 Choose the API Interaction Model

##### 1.1.6.2.1 REST API
- API Gateway REST APIs expose resources and HTTP methods.
- A resource represents an addressable entity or path.
- A method represents an HTTP operation such as GET, POST, PUT, PATCH, or DELETE.
- REST APIs provide API management features including request validation, API keys, per-client throttling, custom gateway responses, caching, and AWS WAF integration.
- Choose REST APIs when these advanced API Gateway features are required.

##### 1.1.6.2.2 HTTP API
- API Gateway HTTP APIs expose routes that integrate with Lambda functions or routable HTTP endpoints.
- HTTP APIs provide a smaller feature set than REST APIs and are designed as a simpler, lower-cost option.
- HTTP APIs support capabilities such as OIDC/OAuth 2.0 authorization, CORS configuration, request/response parameter mapping, and automatic deployment.
- Request body validation is a REST API feature rather than an HTTP API feature in API Gateway.

##### 1.1.6.2.3 WebSocket API
- WebSocket APIs provide stateful, full-duplex communication between clients and backends.
- Either side can send messages after the connection is established.
- Incoming messages are routed to integrations according to configured route keys.
- Use WebSocket APIs when the backend must push messages to connected clients without repeated client polling.

##### 1.1.6.2.4 GraphQL API
- AWS AppSync provides managed GraphQL APIs.
- A GraphQL API is defined by a schema containing types and fields.
- Client operations are validated against the schema.
- Resolvers connect schema fields and operations to data sources or business logic.
- Keep detailed AppSync implementation proportional to the scenario; the examples named by Skill 1.1.6 primarily emphasize API Gateway.

#### 1.1.6.3 API Contract

##### 1.1.6.3.1 Resources, Routes, and Methods
- Define what clients can address and which operations they can perform.
- For REST APIs, resources form paths and methods define HTTP operations on those resources.
- For HTTP APIs, routes combine an HTTP method and a path.
- For WebSocket APIs, route selection determines which backend integration handles a message.

##### 1.1.6.3.2 Request Contract
- Define accepted path parameters, query-string parameters, headers, and request bodies.
- Mark required request elements explicitly.
- Define schemas where payload structure must be validated.
- Avoid making backend implementation details part of the external contract unless required.

##### 1.1.6.3.3 Response Contract
- Define expected HTTP status codes, headers, and response payloads.
- Clients should be able to distinguish successful, client-error, and server-error outcomes.
- Keep external responses stable where possible even when backend implementations change.

#### 1.1.6.4 Backend Integrations

##### 1.1.6.4.1 Integration
- An API operation must be connected to a backend that performs the requested work.
- API Gateway can integrate with AWS Lambda, HTTP endpoints, and AWS services.
- Integration configuration defines how API Gateway sends requests to the backend and returns backend results to the client.

##### 1.1.6.4.2 Proxy Integration
- In a proxy integration, API Gateway passes the request to the backend with minimal transformation.
- The backend is responsible for interpreting the request and constructing the expected response.
- With Lambda proxy integration, the Lambda function returns a response in the format expected by API Gateway.
- AWS recommends proxy integration for REST APIs when possible because configuration is simpler and can evolve with the backend more easily.

##### 1.1.6.4.3 Non-Proxy Integration
- A non-proxy integration allows API Gateway to explicitly map between the external method contract and backend integration contract.
- Request parameters and payloads can be transformed before backend invocation.
- Backend responses can be transformed into the API method response.
- Use this when the API contract must be different from the backend contract or when transformations are required at the gateway.

#### 1.1.6.5 Request Transformations

##### 1.1.6.5.1 Purpose
- Transform the client request when the backend expects a different path, parameter, header, or payload shape.
- Transformations allow the external API contract and internal backend contract to evolve more independently.

##### 1.1.6.5.2 REST API Parameter Mapping
- Method request data can be mapped into integration request parameters.
- Path parameters, query strings, and headers can participate in mappings.
- Static values can also be supplied where supported.

##### 1.1.6.5.3 REST API Mapping Templates
- Non-proxy REST integrations can use mapping templates to transform request bodies.
- Mapping templates use Velocity Template Language (VTL).
- They are useful when the backend requires a different payload structure than the client sends.

##### 1.1.6.5.4 HTTP API Parameter Mapping
- HTTP APIs can modify requests before they reach the backend integration.
- Supported transformations include headers, query strings, and request paths.
- Parameter mappings can append, overwrite, or remove supported values.

#### 1.1.6.6 Response Transformations

##### 1.1.6.6.1 Purpose
- Transform backend output when it does not match the API response contract.
- Hide backend-specific representation from API consumers.
- Normalize responses from different backend implementations.

##### 1.1.6.6.2 REST API Integration Response
- For non-proxy REST integrations, an integration response maps backend output to a method response.
- Response headers can be mapped.
- Response bodies can be transformed using mapping templates.
- Backend outcomes can be selected and mapped to defined method response status codes.

##### 1.1.6.6.3 HTTP API Response Mapping
- HTTP APIs can modify integration responses before returning them to the client.
- Response headers can be appended, overwritten, or removed.
- Response status codes can be overwritten through response parameter mapping.

#### 1.1.6.7 Request Validation

##### 1.1.6.7.1 Why Validate at the API Boundary
- Reject malformed requests before invoking backend code.
- Reduce unnecessary backend processing.
- Enforce the published API contract at the gateway.

##### 1.1.6.7.2 REST API Request Validators
- API Gateway REST APIs can validate request parameters, request bodies, or both.
- Required URI parameters, query-string parameters, and headers can be checked for presence and non-blank values.
- Parameter validation checks presence; it does not validate parameter type or format.

##### 1.1.6.7.3 Request Body Validation
- API Gateway REST APIs can validate request payloads against a configured model.
- Models use JSON Schema.
- Validation is performed according to the content type associated with the model.
- `$default` can be used when the same model should apply regardless of content type.
- Requests that fail configured validation are rejected before backend invocation.

##### 1.1.6.7.4 Backend Validation Still Exists
- API Gateway provides basic contract validation.
- Application-specific and business-rule validation remains a backend responsibility.
- Gateway validation should not be treated as a replacement for all application validation.

#### 1.1.6.8 HTTP Status Codes

##### 1.1.6.8.1 Method Response
- A REST API method response defines what the client receives.
- It can define an HTTP status code, response headers, and response models.
- Non-proxy integration responses map backend outcomes to method responses.

##### 1.1.6.8.2 Overriding Status Codes
- API Gateway mapping templates can override response status codes for REST APIs.
- HTTP API response mappings can also overwrite the response status code.
- Status-code overrides are useful when the backend's native response does not match the external API contract.

##### 1.1.6.8.3 Mapping Backend Errors
- For non-proxy Lambda integrations, selection patterns can map Lambda error output to an appropriate HTTP method response.
- For HTTP or AWS service backends, integration response selection can map backend status outcomes.
- Unmapped backend responses should have a defined default path; AWS notes that a `500` default can be reasonable for unexpected integration responses.

##### 1.1.6.8.4 Gateway-Generated Errors
- API Gateway can produce errors before the request reaches the backend, for example authorization or API configuration errors.
- REST API gateway responses can be customized for supported response types.
- Keep gateway-generated and backend-generated errors consistent enough for clients to handle predictably.

#### 1.1.6.9 Extending an Existing API

##### 1.1.6.9.1 Additive Change
- Prefer additive changes when possible.
- Add new resources, routes, optional request fields, or response fields in ways that preserve existing consumer behavior.
- Avoid changing existing behavior unexpectedly for consumers that depend on the current contract.

##### 1.1.6.9.2 OpenAPI
- API Gateway supports importing REST API definitions using OpenAPI 2.0 and OpenAPI 3.0, subject to API Gateway support limitations.
- OpenAPI provides a machine-readable API contract that can be version-controlled and reviewed.
- API Gateway-specific OpenAPI extensions can describe integrations, validators, and other gateway configuration.

##### 1.1.6.9.3 Update by Merge
- API Gateway can update an existing REST API using merge mode.
- Non-conflicting definitions from the imported API are added to the existing API.
- When definitions conflict, imported method definitions replace the corresponding existing definitions.
- Merge is useful when extending an API without replacing the entire definition.

##### 1.1.6.9.4 Update by Overwrite
- Overwrite mode replaces the API definition with the imported definition.
- Configuration not included in the imported definition can be reset to default values.
- Use overwrite only when the imported definition fully represents the desired API configuration.

#### 1.1.6.10 Maintaining the API

##### 1.1.6.10.1 Contract Stability
- Treat the API contract as an interface consumed independently from its implementation.
- Maintain compatibility where possible when backend services change.
- Transformation at API Gateway can help preserve an external contract while backend representations evolve.

##### 1.1.6.10.2 API Definition as Code
- Keep API definitions in a reproducible form such as OpenAPI, AWS SAM, AWS CloudFormation, or AWS CDK where appropriate.
- Version-controlled API definitions make changes reviewable and repeatable.
- Detailed infrastructure-as-code deployment belongs to Domain 3.

##### 1.1.6.10.3 Documentation
- API Gateway can import API documentation parts from OpenAPI.
- Documentation should describe resources/operations, requests, responses, and important client-visible behavior.
- Documentation maintenance should follow API contract changes.

##### 1.1.6.10.4 Testing Changes
- Verify request validation, transformations, integrations, response mappings, and error paths after changing an API.
- API Gateway REST APIs support test invocations.
- Broader unit and integration testing are expanded under Skill 1.1.7 and Domain 3 testing skills.

#### 1.1.6.11 Important Distinctions

##### 1.1.6.11.1 API Contract vs Backend Contract
- The public API does not need to expose the backend's native request and response structure.
- Mapping and transformation can isolate clients from backend changes.
- Proxy integration intentionally reduces this separation by delegating more responsibility to the backend.

##### 1.1.6.11.2 Validation vs Transformation
- Validation determines whether an incoming request satisfies defined rules.
- Transformation changes request or response representation.
- A request can be valid yet still require transformation before backend invocation.

##### 1.1.6.11.3 Proxy vs Non-Proxy
- Proxy: less gateway mapping, more responsibility in backend code.
- Non-proxy: more gateway configuration and explicit control over mapping between API and backend contracts.
- Prefer proxy integration when no gateway-level transformation requirement justifies additional mapping complexity.

##### 1.1.6.11.4 REST API vs HTTP API
- Both provide RESTful HTTP APIs in API Gateway.
- REST APIs provide the broader API management feature set.
- HTTP APIs are simpler and lower cost but do not implement every REST API feature.
- Do not assume a feature available for REST APIs is automatically available for HTTP APIs.

##### 1.1.6.11.5 API Version vs Stage
- A stage is a deployed lifecycle environment/reference such as `dev`, `beta`, or `prod`.
- A stage can also be named `v2`, but a stage and an API contract version are conceptually different things.
- Detailed API Gateway stages and deployment behavior belong primarily to Domain 3.

#### 1.1.6.12 Create / Extend / Maintain Decision Model

##### 1.1.6.12.1 Create
- Identify the required interaction model: REST/HTTP, WebSocket, or GraphQL.
- Define resources/routes/operations and request/response contracts.
- Choose backend integrations.
- Decide whether proxy or explicit transformations are required.
- Add basic validation at the gateway where supported and useful.
- Define expected success and error responses.

##### 1.1.6.12.2 Extend
- Determine whether the change can remain backward compatible.
- Prefer additive contract changes when possible.
- Add or update routes/resources and integrations.
- Update validation schemas and transformations consistently.
- Use OpenAPI merge/controlled updates when managing definition-based APIs.

##### 1.1.6.12.3 Maintain
- Keep contract, implementation, validation, transformation, and documentation synchronized.
- Test both success and failure paths after changes.
- Preserve client-facing behavior where possible while allowing backend implementation to evolve.
