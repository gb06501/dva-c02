### 1.1.10 Handle streaming data using AWS services

#### 1.1.10.1 Streaming Data Scope

##### 1.1.10.1.1 Streaming Data
- Streaming data is continuously generated data that is processed as records arrive rather than waiting for a complete bounded dataset.
- Typical examples include application events, logs, telemetry, clickstreams, financial transactions, and device data.
- AWS streaming architectures separate producers that write records from consumers that process those records.
- This skill focuses on handling streaming data in application code and selecting the relevant AWS streaming mechanisms.

##### 1.1.10.1.2 Core AWS Service
- The DVA-C02 in-scope services list names **Amazon Kinesis** under Analytics rather than only one Kinesis sub-service.
- Amazon Kinesis Data Streams is the primary AWS service for custom real-time streaming applications in this skill.
- Producers write records to a stream.
- Consumers read records independently and process them.
- Multiple applications can consume the same stream concurrently.
- AWS services such as Lambda, Amazon Data Firehose, Amazon Managed Service for Apache Flink, and EventBridge can integrate with Kinesis Data Streams.

##### 1.1.10.1.3 Kinesis Family Awareness
- Amazon Kinesis is a family of streaming capabilities rather than only Kinesis Data Streams.
- For this skill, treat Kinesis Data Streams as the core programming model.
- Also recognize Amazon Data Firehose as a managed streaming-delivery service.
- Recognize Amazon Managed Service for Apache Flink as a service for stateful/complex stream processing.
- Recognize Kinesis Video Streams as a specialized service for ingesting and processing video/media streams.
- Keep the last two at recognition level unless a scenario explicitly requires them.

#### 1.1.10.2 Kinesis Data Stream

##### 1.1.10.2.1 Stream
- A Kinesis data stream is an ordered sequence of data records intended to be written and read in real time.
- A stream contains one or more shards.
- Records remain available for a configured retention period rather than disappearing immediately after one consumer reads them.
- This allows multiple consumers to read the same records independently.

##### 1.1.10.2.2 Producer
- A producer application writes records to Kinesis Data Streams.
- Producers can use AWS SDK operations such as PutRecord and PutRecords.
- Each record must include data and a partition key.
- The partition key influences which shard receives the record.

##### 1.1.10.2.3 Consumer
- A consumer application reads and processes records from a Kinesis data stream.
- Consumers can use the Kinesis Client Library (KCL), AWS SDK APIs, Lambda, or other AWS services.
- Multiple consumers can process the same stream independently.
- Consumer design must account for throughput, ordering, checkpointing, error handling, and processing lag.

#### 1.1.10.3 Records

##### 1.1.10.3.1 Data Record
- A Kinesis record contains a data blob, partition key, and sequence number.
- Kinesis treats the data blob as opaque; it does not interpret or modify the application payload.
- Producers and consumers therefore own the serialization format and message contract.
- Current AWS API documentation defines a maximum total record size of 10 MiB for the payload plus partition key.

##### 1.1.10.3.2 Partition Key
- The partition key determines the shard to which a record is assigned.
- Kinesis hashes the partition key and maps the resulting value to a shard's hash-key range.
- Records with the same partition key map to the same shard.
- The number of distinct partition keys should normally be much larger than the number of shards to distribute load evenly.
- A high-volume single partition key can create a hot shard.

##### 1.1.10.3.3 Sequence Number
- Kinesis assigns a sequence number after a record is written.
- A sequence number uniquely identifies a record within its shard.
- Sequence numbers generally increase over time for records with the same partition key.
- Sequence numbers are not general indexes for arbitrary datasets.
- Partition keys or separate streams should be used for logical grouping.

#### 1.1.10.4 Shards

##### 1.1.10.4.1 Shard
- A shard is a uniquely identified sequence of records within a stream.
- Shards provide the fundamental unit of stream capacity and parallelism.
- Stream capacity is the aggregate capacity of its shards in provisioned mode.
- Producers distribute records across shards through partition keys.
- Consumers process records from individual shards.

##### 1.1.10.4.2 Provisioned Capacity
- In provisioned mode, applications explicitly manage shard count.
- AWS documents per-shard write and read capacity limits.
- Increasing shard count increases stream capacity and parallelism.
- Reducing shard count decreases available capacity.
- Capacity planning must account for both record count and data volume.

##### 1.1.10.4.3 On-Demand Capacity
- Kinesis Data Streams also supports on-demand capacity modes.
- On-demand mode manages stream capacity automatically according to service behavior and limits.
- Use on-demand when variable or unpredictable throughput makes explicit shard planning undesirable.
- Understand that partition-key distribution still matters even when capacity management is automated.

#### 1.1.10.5 Partitioning and Ordering

##### 1.1.10.5.1 Ordering Boundary
- Kinesis preserves record ordering within a shard.
- Records with the same partition key are routed to the same shard and can therefore be processed in order.
- Kinesis does not provide a single global order across all shards.
- Application code must define the smallest business boundary that actually requires ordering.

##### 1.1.10.5.2 Partition-Key Design
- Choose a partition key with sufficiently high cardinality to distribute records.
- Avoid using a value where one key receives most of the traffic.
- Good examples can include customer ID, device ID, account ID, or another business identifier when traffic is naturally distributed.
- If one business entity dominates traffic, add a distribution strategy only if the application can tolerate reduced per-entity ordering.

##### 1.1.10.5.3 Hot Shard
- A hot shard occurs when one shard receives disproportionate traffic.
- Poor partition-key distribution is a common cause.
- Symptoms include throttled producer requests or uneven consumer load.
- Increasing total shard count alone may not solve a single hot partition key if the same key always maps to one shard.

#### 1.1.10.6 Writing Records

##### 1.1.10.6.1 PutRecord
- PutRecord writes one record to a stream.
- The producer supplies the stream identifier, data, and partition key.
- The response includes the shard ID and sequence number assigned to the record.
- Handle throttling and service errors according to the workload's retry policy.

##### 1.1.10.6.2 PutRecords
- PutRecords writes multiple records in one API request.
- Batching reduces request overhead and can increase producer efficiency.
- A PutRecords call can partially succeed.
- Producer code must inspect the result of each record rather than assuming the entire request succeeded or failed.

##### 1.1.10.6.3 Partial Failure
- Batch APIs require per-record failure handling.
- Retry only failed records rather than blindly resending successful records.
- Retrying side-effecting downstream processing must remain idempotent where duplicates are possible.

##### 1.1.10.6.4 Kinesis Producer Library
- AWS provides the Kinesis Producer Library (KPL) for high-performance producers.
- KPL can aggregate and batch user records to improve throughput.
- Use KPL when its batching/aggregation capabilities fit the application's throughput needs.
- Direct AWS SDK operations remain valid for simpler producers.

#### 1.1.10.7 Reading Records

##### 1.1.10.7.1 Shared-Throughput Consumer
- Standard consumers read records using shared shard throughput.
- Multiple shared consumers contend for the same per-shard read capacity.
- Polling consumers use shard iterators and GetRecords.
- AWS Lambda can also use the standard iterator through an event source mapping.

##### 1.1.10.7.2 Shard Iterator
- A shard iterator identifies the position in a shard from which reading should begin.
- GetShardIterator creates the starting iterator.
- GetRecords returns records and a next shard iterator for subsequent reads.
- Iterator type determines whether reading begins at a particular sequence number, timestamp, latest record, or other supported position.

##### 1.1.10.7.3 Enhanced Fan-Out Consumer
- Enhanced fan-out gives each registered consumer dedicated read throughput per shard.
- AWS currently documents up to 2 MB/second per shard for each enhanced fan-out consumer.
- Kinesis pushes records to enhanced fan-out consumers rather than requiring them to poll.
- Enhanced fan-out reduces contention when several applications consume the same stream.

##### 1.1.10.7.4 Shared vs Enhanced Fan-Out
- Shared throughput: consumers share shard read capacity.
- Enhanced fan-out: each consumer gets dedicated shard read throughput.
- Choose enhanced fan-out when multiple consumers require low-latency independent consumption or shared read throughput is a bottleneck.
- Shared throughput is simpler and can be sufficient for lower consumer counts or less demanding workloads.

#### 1.1.10.8 Kinesis Client Library

##### 1.1.10.8.1 KCL
- Kinesis Client Library helps build fault-tolerant Kinesis consumer applications.
- KCL coordinates processing across workers so shard processing is distributed among them.
- It handles shard assignment, load balancing, checkpointing, and changes in shard topology.
- AWS currently recommends using current KCL versions rather than older KCL 1.x/2.x releases.

##### 1.1.10.8.2 Checkpointing
- A checkpoint records consumer progress within a shard.
- After restart or reassignment, processing can resume from the checkpoint.
- Checkpoint only after the application has safely processed the relevant records.
- Incorrect checkpoint timing can cause records to be repeated or skipped depending on failure behavior.

##### 1.1.10.8.3 Consumer Scaling
- Additional consumer workers can increase parallelism up to the number of shards available for processing.
- One shard cannot normally be processed by multiple KCL workers simultaneously as one ordered sequence.
- Increasing worker count above useful shard parallelism does not automatically improve throughput.

#### 1.1.10.9 Lambda as a Stream Consumer

##### 1.1.10.9.1 Event Source Mapping
- Lambda uses an event source mapping to read records from Kinesis Data Streams.
- The mapping polls the stream or uses an enhanced fan-out consumer depending on configuration.
- Lambda invokes the function with batches of records.
- Multiple event source mappings can process the same stream with different Lambda functions.

##### 1.1.10.9.2 Batch Processing
- Lambda receives multiple Kinesis records in a batch.
- Batch size influences invocation overhead, latency, and failure scope.
- Function code should iterate through the records and handle individual data payloads correctly.
- Do not assume one invocation equals one stream record.

##### 1.1.10.9.3 Starting Position
- Event source mappings define where Lambda begins reading the stream.
- Common positions include LATEST and TRIM_HORIZON, with other starting-position options available.
- Starting position matters for whether historical retained records are processed.

##### 1.1.10.9.4 Stream Failure Handling
- Lambda event source mappings provide stream-specific error handling such as retry limits, maximum record age, batch bisection, and failure destinations where supported.
- Lambda-specific stream lifecycle and failure handling are expanded under Task 1.2.
- This skill only needs the streaming model and the relationship between the stream and consumer code.

#### 1.1.10.13 Amazon Data Firehose

##### 1.1.10.13.1 Managed Streaming Delivery
- Amazon Data Firehose is a fully managed service for delivering streaming data to supported destinations.
- It is designed for delivery pipelines rather than custom shard-oriented consumer applications.
- Firehose can receive streaming records directly or use Kinesis Data Streams as a source.
- It buffers records before delivery according to service configuration.

##### 1.1.10.13.2 Transformation
- Firehose can optionally transform records before delivery.
- AWS Lambda can be used for record transformation in supported Firehose delivery streams.
- Transformation is useful when destination format or structure differs from the incoming record format.
- Keep transformation logic focused; more complex stateful stream processing belongs to services such as Managed Service for Apache Flink.

##### 1.1.10.13.3 Destinations
- Firehose delivers records to supported destinations rather than exposing a retained stream for arbitrary consumers.
- Important exam-relevant destinations include Amazon S3 and Amazon OpenSearch Service.
- Supported destinations can evolve; use current AWS Firehose documentation for the complete list.
- The destination owns long-term storage/search/analytics after Firehose delivery.

##### 1.1.10.13.4 Data Streams vs Firehose
- Kinesis Data Streams: application-controlled streaming log with producers, shards/partitioning, multiple consumers, retention, and replay.
- Amazon Data Firehose: managed delivery pipeline that buffers and delivers records to configured destinations.
- Choose Data Streams when custom consumers, replay, shard-level ordering, or multiple independent processing applications are required.
- Choose Firehose when the requirement is primarily to deliver streaming data to a destination with minimal consumer-management code.

#### 1.1.10.14 Managed Service for Apache Flink

##### 1.1.10.14.1 Recognition-Level Scope
- Amazon Managed Service for Apache Flink runs Apache Flink applications for processing streaming data.
- It supports stateful, continuous stream-processing applications.
- It is relevant when the requirement goes beyond simple record-by-record consumption into transformations, aggregations, windows, joins, or other stream-processing logic.
- For DVA-C02, keep this at recognition level unless a question clearly points to complex/stateful stream processing.

#### 1.1.10.15 Kinesis Video Streams

##### 1.1.10.15.1 Recognition-Level Scope
- Kinesis Video Streams is specialized for securely ingesting, storing, and processing video streams and time-encoded media/data.
- It is not the default choice for generic application event streams.
- For DVA-C02, recognition is sufficient unless the scenario explicitly involves video/media streaming.

#### 1.1.10.13 Retention and Replay

##### 1.1.10.13.1 Retention
- Kinesis retains records for a period of time rather than deleting them after one consumer reads them.
- AWS currently documents 24 hours as the default retention period.
- Retention can be increased up to 365 days.
- Retention greater than the default can incur additional cost.

##### 1.1.10.13.2 Replay
- Because records remain in the stream during retention, a consumer can re-read historical records.
- Replay is useful for rebuilding derived state, recovering after consumer defects, or reprocessing data with new logic.
- Replay behavior depends on starting position and retained data availability.

##### 1.1.10.13.3 Queue vs Stream
- SQS is primarily a work queue where messages are consumed and deleted.
- Kinesis is a retained ordered log where multiple consumers can independently read the same records.
- Use a stream when replay, ordered sequences, multiple independent consumers, or continuous real-time data processing are important.

#### 1.1.10.14 Consumer Lag

##### 1.1.10.14.1 Processing Lag
- Consumer lag is the delay between record arrival and successful consumer processing.
- Increasing lag indicates that the consumer is falling behind the producer.
- Causes include insufficient consumer capacity, downstream latency, throttling, or processing failures.

##### 1.1.10.14.2 Iterator Age
- Lambda exposes iterator-age metrics for Kinesis event source mappings.
- Increasing iterator age indicates that the function is processing older records and falling behind the stream.
- Stream consumers should monitor lag as a primary health indicator.

##### 1.1.10.14.3 Recovery
- Scale consumer processing when possible.
- Reduce processing time per record.
- Increase stream/consumer capacity if throttling is the bottleneck.
- Remove or isolate slow downstream dependencies.

#### 1.1.10.15 Serialization

##### 1.1.10.15.1 Payload Format
- Kinesis stores application data as opaque bytes.
- Producer and consumer must agree on serialization.
- Common choices include JSON, Avro, Protobuf, or another explicit application format.
- Serialization choice affects payload size, schema evolution, performance, and interoperability.

##### 1.1.10.15.2 Schema Evolution
- Stream consumers can remain active for long periods while producer schemas evolve.
- Prefer backward-compatible schema changes.
- Consumers should not depend on undocumented producer implementation details.
- Schema management can be used when the ecosystem requires stronger contract governance.

#### 1.1.10.16 Failure Handling

##### 1.1.10.16.1 Producer Failure
- Handle throttling and retryable service errors using AWS SDK retry behavior and application-level policies where needed.
- Retry only failed records from batch writes.
- Keep retries bounded and use backoff/jitter.

##### 1.1.10.16.2 Consumer Failure
- Do not advance checkpoints or acknowledge successful processing before business processing has actually completed.
- Failed records can be retried depending on the consumer implementation.
- Consumer code should be idempotent where replay or retry can cause repeated processing.

##### 1.1.10.16.3 Poison Record
- A record that consistently fails can block progress for an ordered shard depending on consumer behavior.
- Use the failure-isolation mechanisms provided by the consumer integration where applicable.
- Lambda provides stream-specific controls such as batch bisection and record-age limits.
- Custom consumers need an explicit policy for persistent failures.

#### 1.1.10.17 Scaling Model

##### 1.1.10.17.1 Producer Scaling
- Producer throughput is distributed across shards according to partition keys.
- Increase stream capacity or change capacity mode when aggregate throughput exceeds available capacity.
- Fix hot-key distribution when one partition dominates traffic.

##### 1.1.10.17.2 Consumer Scaling
- Consumer parallelism is fundamentally related to shard count.
- More shards can provide more independent units of ordered processing.
- Enhanced fan-out provides dedicated throughput to multiple independent consumers.
- Consumer code and downstream dependencies must also be capable of handling increased parallelism.

##### 1.1.10.17.3 Ordering vs Parallelism
- Increasing shard count increases potential parallelism.
- Records that require ordering should remain within the same partition/shard boundary.
- Global ordering limits horizontal scale and should not be assumed unless explicitly required.

#### 1.1.10.18 Streaming Decision Model

##### 1.1.10.18.1 Need Continuous Real-Time Record Processing
- Consider Kinesis Data Streams.
- Producers continuously write records.
- Consumers process independently as data arrives.

##### 1.1.10.18.2 Need Replay
- Use a retained stream such as Kinesis Data Streams.
- Configure sufficient retention for the recovery/reprocessing requirement.

##### 1.1.10.18.3 Need Ordered Processing per Entity
- Use a stable partition key for that entity.
- Ensure all related records map to the same shard.
- Avoid assuming global order across shards.

##### 1.1.10.18.4 Multiple Independent Consumers
- Kinesis allows several applications to consume the same stream.
- Use enhanced fan-out when dedicated read throughput/low latency is required.
- Use shared throughput when contention is acceptable.

##### 1.1.10.18.5 Need Managed Delivery to S3/OpenSearch
- Consider Amazon Data Firehose when the main requirement is to ingest streaming records and deliver them to a supported destination.
- Prefer Firehose when you do not need to manage custom stream consumers, shard processing, or replay.
- Use Kinesis Data Streams as the source when the same stream must also feed other consumers.

##### 1.1.10.18.6 Need Complex Stateful Stream Processing
- Consider Amazon Managed Service for Apache Flink when processing requires stateful transformations, windows, aggregations, or joins.
- Keep implementation depth low for this exam unless the scenario explicitly requires this processing model.

##### 1.1.10.18.7 Need Simple Background Work Queue
- Prefer SQS when records are independent work items that do not require replay or retained ordered history.
- Queue-specific programming belongs to Skill 1.1.8.

##### 1.1.10.18.8 Need Near-Real-Time Serverless Processing
- Lambda can consume Kinesis through an event source mapping.
- Configure batch size, starting position, concurrency/failure controls according to workload needs.
- Detailed Lambda stream processing belongs to Task 1.2.

#### 1.1.10.19 Important Distinctions

##### 1.1.10.19.1 Stream vs Queue
- Stream: retained ordered log; multiple consumers can independently read the same records.
- Queue: work distribution; messages are typically removed after successful consumption.
- Both are asynchronous but solve different problems.

##### 1.1.10.19.2 Partition Key vs Sequence Number
- Partition key controls shard placement.
- Sequence number identifies a record within its shard.
- Sequence numbers do not control placement and are not general dataset indexes.

##### 1.1.10.19.3 Shard Ordering vs Global Ordering
- Ordering exists within each shard.
- Records across multiple shards do not have one global sequence.
- Partition only by the business boundary that needs ordering.

##### 1.1.10.19.4 Retention vs Persistence
- Kinesis retains records for a configured period, not indefinitely by default.
- Long-term business storage should use an appropriate durable data store or delivery destination.

##### 1.1.10.19.5 Shared vs Enhanced Fan-Out
- Shared consumers compete for shard read throughput.
- Enhanced fan-out consumers receive dedicated throughput.
- Enhanced fan-out is primarily a consumer-throughput/latency choice, not a different stream type.
