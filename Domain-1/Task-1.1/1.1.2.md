### 1.1.2 Describe differences between stateful and stateless concepts

#### 1.1.2.1 State

##### 1.1.2.1.1 State
- Information retained about previous interactions, requests, sessions, or application processing
- State that must persist needs a durable or appropriately resilient location
- State can include session data, user data, workflow state, or persistent application data

#### 1.1.2.2 Stateless

##### 1.1.2.2.1 Stateless Application or Service
- Does not require knowledge of previous interactions to process the current request
- Does not depend on session information stored locally on the compute instance between requests
- Any available compute resource can service a request
- Compute resources can be replaced without losing required application state
- Supports horizontal scaling because requests are not tied to a particular compute instance
- Tolerates failure or replacement of individual compute nodes more easily
- AWS recommends making systems stateless where possible

##### 1.1.2.2.2 Externalizing State
- Stateless does not mean the application has no data or persistent state
- Required state is moved outside the compute layer
- Session or application state can be stored in a database, cache, or external storage
- AWS examples include Amazon DynamoDB, Amazon ElastiCache, Amazon EFS, Amazon S3, and suitable databases
- Requests can also carry state that is appropriate to pass with the request

##### 1.1.2.2.3 AWS Compute Examples
- AWS Lambda is naturally suited to stateless processing
- AWS Fargate can run stateless application components
- EC2-based application tiers can also be designed stateless
- Stateless design is an architectural property, not a property exclusive to serverless services

#### 1.1.2.3 Stateful

##### 1.1.2.3.1 Stateful Application or Service
- Processing depends on information retained from previous interactions or application activity
- State must be preserved somewhere for subsequent processing
- If required state exists only on a specific compute node, requests can become dependent on that node
- Node replacement or failure can affect availability when state is not stored resiliently
- Scaling and failover require consideration of how state is preserved, replicated, or transferred

##### 1.1.2.3.2 Stateful Backing Services
- Persistent state is often intentionally handled by dedicated backing services
- Databases, caches, object storage, and file systems can provide state to otherwise stateless application components
- A system can therefore contain both stateless compute and stateful data services

#### 1.1.2.4 Stateful vs Stateless

##### 1.1.2.4.1 Request Dependency
- Stateless: current request does not depend on locally retained information from previous requests
- Stateful: current processing depends on retained state

##### 1.1.2.4.2 Scaling
- Stateless: another equivalent compute instance can generally handle the next request
- Stateful: scaling must account for availability and location of required state

##### 1.1.2.4.3 Failure and Replacement
- Stateless: compute instances can generally be replaced without losing required state
- Stateful: required state must survive node/service failure through durable storage, replication, or another resilience mechanism

##### 1.1.2.4.4 Architectural Preference
- Prefer stateless compute where practical
- Keep necessary state in an appropriate resilient backing service
- Stateful components remain necessary when the workload inherently requires persistent state

#### 1.1.2.5 Common AWS Architecture

##### 1.1.2.5.1 Stateless Compute with External State
- Client sends request to any available application instance
- Application instance performs processing without relying on local session state
- Persistent or session state is retrieved from or written to an external service
- Load balancing can distribute requests across equivalent compute resources
- Compute resources can scale horizontally and be replaced independently of persisted state

##### 1.1.2.5.2 Example Shape
- Client → Load Balancer/API → stateless compute
- Stateless compute → DynamoDB / ElastiCache / RDS / S3 / other backing service
- The backing service retains the state; the compute layer performs processing

#### 1.1.2.6 Important Distinctions

##### 1.1.2.6.1 Stateless Does Not Mean No Persistence
- A stateless service can read and write persistent data
- The distinction is whether processing depends on state retained locally between requests

##### 1.1.2.6.2 Application State vs Network Stateful/Stateless
- This skill belongs to application development and application architecture
- AWS also uses stateful/stateless terminology for networking, such as security groups, network ACLs, and Network Firewall
- Those networking meanings concern tracking network connection/traffic context
- Do not confuse them with application session or processing state in this skill
