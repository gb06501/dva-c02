### 1.1.8 Write code that uses messaging services

#### 1.1.8.1 Messaging Scope

##### 1.1.8.1.1 Messaging
- Messaging lets distributed application components exchange information without requiring direct point-to-point processing between every producer and consumer.
- AWS messaging services can decouple microservices, distributed systems, and serverless applications.
- Application code typically acts as a producer, consumer, publisher, or subscriber.
- This skill requires programming against messaging services, not only recognizing messaging architecture.

##### 1.1.8.1.2 Core AWS Messaging Services
- Amazon SQS provides managed message queues.
- Amazon SNS provides publish/subscribe messaging through topics.
- Amazon EventBridge provides event routing between producers and targets and is expanded specifically under Skill 1.1.12.
- Amazon MQ provides managed message brokers for workloads requiring broker engines or standard messaging protocols; it is less central for cloud-native AWS application code than SQS/SNS.

#### 1.1.8.2 Queue-Based Messaging

##### 1.1.8.2.1 Amazon SQS
- Amazon SQS is a secure, durable, available hosted queue for integrating and decoupling distributed components.
- Producers send messages to a queue.
- Consumers receive messages from the queue when ready to process them.
- The queue stores messages between production and consumption.
- Producers and consumers do not need to be concurrently available.

##### 1.1.8.2.2 Producer Code
- Obtain or configure the target queue URL.
- Construct the message body.
- Add message attributes when metadata is useful for processing.
- Call the SQS SendMessage API through an AWS SDK.
- Handle service errors according to the application's resilience requirements.
- Batch APIs can reduce API-call overhead when sending multiple messages.

##### 1.1.8.2.3 Consumer Code
- Call ReceiveMessage to retrieve available messages when using polling consumers.
- Process the returned message body and attributes.
- Delete a message only after successful processing.
- If the message is not deleted, it can become visible again after the visibility timeout.
- Batch receive/delete operations can improve efficiency where appropriate.

#### 1.1.8.3 SQS Message Lifecycle

##### 1.1.8.3.1 Send
- Producer sends a message to the queue.
- SQS stores the message redundantly.
- The message remains available until consumed, deleted, or its retention period expires.

##### 1.1.8.3.2 Receive
- A consumer receives a message.
- Receiving does not delete the message.
- The message remains stored by SQS while processing occurs.

##### 1.1.8.3.3 Visibility Timeout
- After a consumer receives a message, SQS temporarily hides it from other consumers.
- This period is the visibility timeout.
- The timeout should be long enough for normal processing to finish.
- If processing needs longer, application code can change the message visibility timeout.
- If processing fails or the consumer does not delete the message, it becomes visible again after the timeout.

##### 1.1.8.3.4 Delete
- After successful processing, the consumer calls DeleteMessage using the receipt handle.
- Deleting prevents normal redelivery of that received message.
- Application code must not treat receipt as equivalent to successful completion.

#### 1.1.8.4 Standard Queues

##### 1.1.8.4.1 Delivery
- Standard queues provide at-least-once delivery.
- More than one copy of a message can be delivered.
- Standard queues provide best-effort ordering rather than strict ordering.
- Application code must tolerate duplicate delivery and possible out-of-order processing.

##### 1.1.8.4.2 Throughput
- Standard queues support very high throughput.
- They are appropriate when strict ordering is unnecessary and the application can handle duplicates.

##### 1.1.8.4.3 Idempotent Consumers
- Consumers should make repeated processing safe where duplicate messages can occur.
- Use a stable business/message identifier to detect already-processed work when the business operation is not naturally idempotent.
- Do not rely on a Standard queue to provide exactly-once delivery.

#### 1.1.8.5 FIFO Queues

##### 1.1.8.5.1 Ordering
- FIFO queues preserve ordering within a message group.
- Messages with the same message group ID are processed in order.
- Multiple message groups can enable parallel processing while preserving order inside each group.

##### 1.1.8.5.2 Deduplication
- FIFO queues support deduplication.
- Producers provide a message deduplication ID unless content-based deduplication is used.
- Deduplication prevents duplicate messages caused by repeated SendMessage calls within the deduplication interval.

##### 1.1.8.5.3 Message Group ID
- The message group ID defines the ordered processing group.
- Messages in the same group are processed one at a time in strict order.
- Poor group design can unnecessarily limit concurrency.
- Use multiple groups when independent ordered sequences can be processed in parallel.

##### 1.1.8.5.4 When to Choose FIFO
- Choose FIFO when message order or duplicate suppression is a business requirement.
- Choose Standard when maximum throughput and simple unordered work distribution are more important.
- FIFO does not remove the need for correct application-level error handling and idempotency.

#### 1.1.8.6 Polling SQS

##### 1.1.8.6.1 Short Polling
- Short polling samples a subset of SQS servers and returns immediately.
- It can return an empty response even when messages exist elsewhere in the distributed queue.
- Repeated short polling can create unnecessary API calls when queues are often empty.

##### 1.1.8.6.2 Long Polling
- Long polling waits for messages to become available up to the configured wait time.
- It reduces empty responses and can reduce polling cost.
- Long polling is generally preferable for custom polling consumers when immediate empty responses are unnecessary.

##### 1.1.8.6.3 Receive Batch
- ReceiveMessage can return multiple messages per call up to the API-supported maximum.
- Batch processing can improve efficiency.
- Code must track the success/failure of individual messages when processing a batch.

#### 1.1.8.7 Failed Message Handling

##### 1.1.8.7.1 Retry Through Redelivery
- If a consumer fails to delete a message, the message can become visible and be received again.
- This naturally provides retry behavior.
- Consumers must therefore tolerate repeated delivery.

##### 1.1.8.7.2 Dead-Letter Queue
- A dead-letter queue (DLQ) receives messages that cannot be successfully processed after repeated receives.
- The source queue redrive policy defines the DLQ and maximum receive count.
- DLQs isolate repeatedly failing messages from normal processing.
- Application teams should inspect, diagnose, and intentionally reprocess or discard DLQ messages.

##### 1.1.8.7.3 Poison Messages
- A message that consistently causes processing failure can repeatedly consume resources.
- A DLQ prevents such a message from cycling indefinitely through the normal queue.
- Fix the cause before blindly replaying failed messages.

##### 1.1.8.7.4 Redrive
- SQS supports moving messages from a DLQ back to a source or another queue.
- Redrive should follow diagnosis and correction of the processing problem.
- Replayed processing must remain safe against duplicate business effects.

#### 1.1.8.8 SQS Message Data

##### 1.1.8.8.1 Message Body
- The message body contains the application payload.
- Producers and consumers need an agreed payload contract.
- Prefer explicit, evolvable message formats rather than coupling consumers to producer implementation details.

##### 1.1.8.8.2 Message Attributes
- Message attributes provide structured metadata separate from the body.
- They can carry information useful to consumers without embedding all metadata in the payload.
- Message attributes contribute to the total message size.

##### 1.1.8.8.3 Message Size
- SQS has a maximum message size defined by the service.
- For payloads larger than the supported message size, AWS documents patterns that store the payload externally and place a reference in SQS.
- Application code should avoid using queues as general large-object storage.

#### 1.1.8.9 Publish/Subscribe Messaging

##### 1.1.8.9.1 Amazon SNS
- Amazon SNS separates publishers from subscribers using topics.
- Publishers send messages to a topic.
- Subscribers receive messages through supported endpoint types.
- Application-to-application subscribers include SQS queues, Lambda functions, and HTTP/S endpoints.
- One publication can be delivered to multiple subscribers.

##### 1.1.8.9.2 Publisher Code
- Identify the SNS topic ARN.
- Construct the message.
- Add message attributes when needed.
- Call Publish through an AWS SDK.
- Handle publish failures according to application requirements.

##### 1.1.8.9.3 Subscriber
- A subscription connects an endpoint to a topic.
- Published messages are delivered to subscribed endpoints according to the subscription configuration.
- Some endpoint types require subscription confirmation.
- Consumer code depends on the subscriber type; for example, an SQS subscriber consumes from its queue rather than directly polling SNS.

#### 1.1.8.10 Fanout

##### 1.1.8.10.1 SNS to Multiple Consumers
- A single SNS publication can be delivered to multiple subscribers.
- This implements a fanout messaging pattern.
- Each consumer can perform a different action based on the same published event/message.

##### 1.1.8.10.2 SNS to SQS
- SNS can publish the same message to multiple SQS queues.
- SNS provides push-based distribution while SQS provides durable queue-based asynchronous processing.
- Each subscriber queue retains its own copy for independent consumption.
- Consumers can process at different rates and can be temporarily unavailable without requiring the publisher to wait.

##### 1.1.8.10.3 Why Combine SNS and SQS
- SNS alone provides immediate push delivery to subscribers.
- SQS provides persistence and consumer-controlled processing.
- Combining them supports both fanout and temporal decoupling.

#### 1.1.8.11 SNS Message Filtering

##### 1.1.8.11.1 Subscription Filter Policies
- SNS subscription filter policies determine which published messages a subscription receives.
- Filtering can use message attributes or, where configured, the message body.
- Subscribers receive only messages matching their filter policy.
- Filtering avoids implementing all routing decisions inside every consumer.

##### 1.1.8.11.2 Publisher Design
- Publish sufficient metadata for subscribers to filter appropriately.
- Avoid hard-coding knowledge of individual subscribers into producer code.
- The producer should generally publish the business message/event and let subscriptions select what they need.

#### 1.1.8.12 Event Messaging with EventBridge

##### 1.1.8.12.1 EventBridge
- EventBridge is a serverless service for connecting application components through events.
- Events represent changes in an environment, application, or service.
- Event buses route events from sources to zero or more targets.
- Rules select events and route them to matching targets.

##### 1.1.8.12.2 Boundary with Skill 1.1.12
- EventBridge is part of the messaging/event integration landscape and should be recognized here.
- Skill 1.1.12 explicitly requires creating event-driven applications with EventBridge.
- Detailed EventBridge event structure, rules, event buses, targets, schemas, and application implementation should therefore be expanded under 1.1.12 rather than duplicated here.

#### 1.1.8.13 Message Contract Design

##### 1.1.8.13.1 Explicit Contract
- Producers and consumers must agree on the meaning and structure of messages.
- A message contract should describe required fields, semantics, identifiers, and version expectations.
- Consumers should not depend on producer implementation details that are not part of the contract.

##### 1.1.8.13.2 Backward Compatibility
- Prefer additive message changes where possible.
- Consumers should tolerate fields they do not use when the serialization format allows it.
- Removing or changing the meaning/type of an existing field can break independent consumers.

##### 1.1.8.13.3 Versioning
- When incompatible evolution is unavoidable, use an explicit versioning strategy.
- Version information can be part of the message envelope, payload, topic/queue architecture, or another documented contract mechanism.
- Do not introduce unnecessary version complexity when additive evolution is sufficient.

#### 1.1.8.14 Message Processing Correctness

##### 1.1.8.14.1 Acknowledge/Delete After Success
- Do not remove queued work before the required processing has completed successfully.
- For SQS, delete the message after successful processing.
- Premature deletion can turn a consumer failure into lost work.

##### 1.1.8.14.2 Idempotency
- Assume duplicate processing can occur unless the complete system guarantees otherwise.
- Use idempotent operations or duplicate detection for side-effecting business operations.
- Idempotency is particularly important for Standard SQS queues and retry/redrive scenarios.

##### 1.1.8.14.3 Ordering
- Do not depend on strict ordering with SQS Standard queues.
- Use FIFO and appropriate message groups when ordering is required.
- Design consumers so independent message groups can process concurrently where possible.

##### 1.1.8.14.4 Partial Failure
- When processing a batch, one failed message should not unnecessarily cause successfully processed messages to be repeated.
- Track success at the granularity supported by the integration/runtime.
- Lambda-specific partial batch response behavior is expanded under Task 1.2.

#### 1.1.8.15 Security in Messaging Code

##### 1.1.8.15.1 Least Privilege
- Producers need only the permissions required to send/publish to the intended resources.
- Consumers need only the permissions required to receive/delete or otherwise consume from the intended resources.
- Do not grant broad messaging permissions when resource-specific access is sufficient.

##### 1.1.8.15.2 Resource Policies
- SQS queues and SNS topics can use resource-based policies.
- Cross-service or cross-account integrations can require resource policies in addition to identity permissions.
- Detailed IAM policy construction belongs to Domain 2.

##### 1.1.8.15.3 Encryption
- SQS and SNS support server-side encryption.
- AWS KMS can be used where customer-managed key control is required.
- Application code must have appropriate KMS permissions when a customer-managed key requires them.
- Detailed encryption and KMS decisions belong to Domain 2.

#### 1.1.8.16 Observability

##### 1.1.8.16.1 Queue Health
- Monitor queue depth and age of the oldest message.
- Growing depth can indicate that producers exceed consumer capacity.
- Increasing message age indicates delayed processing.

##### 1.1.8.16.2 Failed Processing
- Monitor DLQ message counts and processing failures.
- A DLQ containing messages is an operational signal requiring investigation, not merely a storage destination.

##### 1.1.8.16.3 Correlation
- Include or propagate identifiers that allow message processing to be traced across distributed components.
- Avoid putting sensitive information in identifiers or logs.
- Detailed logging and observability belong to Domain 4.

#### 1.1.8.17 Programming with AWS SDKs

##### 1.1.8.17.1 SDK Operations
- Application code normally calls messaging APIs through an AWS SDK.
- Common SQS operations include SendMessage, ReceiveMessage, DeleteMessage, ChangeMessageVisibility, and their batch variants.
- Common SNS producer operations include Publish.

##### 1.1.8.17.2 SDK Responsibilities
- AWS SDKs handle request signing and service communication.
- SDKs also implement retry/error-handling behavior according to SDK configuration.
- Application code still owns business-level retry safety, idempotency, message lifecycle, and failure outcomes.

##### 1.1.8.17.3 Scope Boundary
- This skill applies AWS SDK usage specifically to messaging.
- General use of AWS APIs and SDKs is Skill 1.1.9.

#### 1.1.8.18 Messaging Decision Model

##### 1.1.8.18.1 One Producer → Work Processed by Consumers
- Use queue-based messaging such as SQS.
- Producer places work in the queue.
- Consumers process when capacity is available.

##### 1.1.8.18.2 One Message → Multiple Independent Consumers
- Use publish/subscribe or fanout.
- SNS can distribute one publication to multiple subscribers.
- SNS → SQS combines fanout with durable independent processing.

##### 1.1.8.18.3 Need Strict Processing Order
- Consider SQS FIFO.
- Define message group IDs according to the required ordering boundary.
- Avoid forcing unrelated work into one group.

##### 1.1.8.18.4 Need Maximum Throughput; Order Not Required
- Consider SQS Standard.
- Design consumers for at-least-once delivery and possible out-of-order processing.

##### 1.1.8.18.5 Consumer Temporarily Fails
- Do not delete the SQS message.
- Let visibility timeout/redelivery provide another processing attempt.
- Use a DLQ to isolate repeatedly failing messages.

##### 1.1.8.18.6 Need Content-Based Event Routing
- SNS subscription filtering can route published messages to selected subscribers.
- EventBridge provides richer event routing and is expanded under Skill 1.1.12.

#### 1.1.8.19 Important Distinctions

##### 1.1.8.19.1 Queue vs Topic
- SQS queue: consumers retrieve stored messages for processing.
- SNS topic: publisher sends once and SNS pushes copies to matching subscribers.
- Use SNS + SQS when both fanout and durable queueing are required.

##### 1.1.8.19.2 Receive vs Delete
- Receiving an SQS message does not remove it from the queue.
- Successful consumers explicitly delete the message.
- Visibility timeout controls temporary invisibility during processing.

##### 1.1.8.19.3 At-Least-Once vs Idempotency
- At-least-once delivery means duplicate delivery is possible.
- Idempotency is an application technique that makes duplicate processing safe.
- Do not confuse a delivery guarantee with application-side duplicate protection.

##### 1.1.8.19.4 Ordering vs Parallelism
- Stronger ordering constraints can reduce parallelism.
- FIFO message groups provide an ordering boundary while allowing parallelism across different groups.
- Choose the smallest ordering scope that satisfies the business requirement.

##### 1.1.8.19.5 Message vs Event
- A message is data transferred between components.
- An event communicates that something occurred.
- AWS services and documentation sometimes use overlapping messaging/event terminology, but architecture should distinguish a command/work item from a fact about something that happened when that distinction matters.
