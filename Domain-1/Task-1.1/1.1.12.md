### 1.1.12 Use Amazon EventBridge to implement event-driven patterns

#### 1.1.12.1 Exam Context

##### 1.1.12.1.1 Skill Scope
- DVA-C02 Skill 1.1.12 explicitly requires using Amazon EventBridge to implement event-driven patterns.
- Amazon EventBridge is explicitly included in the DVA-C02 in-scope services under Application Integration.
- This skill connects the architectural event-driven concepts from Skill 1.1.1 with concrete AWS implementation mechanisms.

##### 1.1.12.1.2 Core Mental Model
- An event represents a change in state or occurrence.
- Event producers emit events without directly invoking every downstream consumer.
- Amazon EventBridge receives events, evaluates routing/filtering configuration, and delivers matching events to targets.
- The core event-bus flow is:
  - source → event bus → rule/event pattern → target
- EventBridge therefore separates event production from event consumption and supports loosely coupled event-driven applications.

#### 1.1.12.2 Events

##### 1.1.12.2.1 Event
- An EventBridge event is a JSON object describing an occurrence.
- Events contain top-level metadata and a detail field containing event-specific information.
- Important common fields include source, detail-type, detail, id, time, account, region, resources, and version.
- Consumers should depend on an explicit event contract rather than assumptions about producer implementation.

##### 1.1.12.2.2 Event Source
- An event source produces events.
- Sources can include AWS services, custom applications, and supported SaaS/partner integrations.
- A custom application can send events by using the EventBridge PutEvents API.
- AWS services can publish service events to the default event bus.

##### 1.1.12.2.3 Event Detail
- The detail object contains information specific to the event type.
- Event patterns can inspect fields within detail as well as top-level event metadata.
- Design detail around the fact that something happened rather than around a direct command to a particular consumer when using an event-notification model.

#### 1.1.12.3 Event Buses

##### 1.1.12.3.1 Event Bus
- An EventBridge event bus is a router that receives events and delivers matching events to zero or more targets.
- Rules associated with the bus evaluate incoming events.
- One event can match multiple rules.
- Each matching rule can route the event independently.

##### 1.1.12.3.2 Default Event Bus
- Every AWS account has a default event bus.
- Events from many AWS services are delivered to the default bus.
- Custom applications can also send events to the default bus.
- Use rules to select the AWS or application events that matter to the workload.

##### 1.1.12.3.3 Custom Event Bus
- Custom event buses can receive events from custom applications.
- Separate buses can provide logical or permission boundaries between application domains or integration contexts.
- Event buses can use resource-based policies to control which principals/accounts may send events.

##### 1.1.12.3.4 Cross-Account Routing
- An EventBridge event bus can be a target of a rule.
- This enables routing events between event buses, including across AWS accounts where configured.
- Cross-account designs require appropriate permissions on the receiving bus and sender side.
- Use this pattern to centralize or distribute events without embedding cross-account consumer knowledge in producers.

#### 1.1.12.4 Rules

##### 1.1.12.4.1 Rule
- A rule defines which events should be routed to which targets.
- Event-driven rules use event patterns to match incoming events.
- A rule is associated with one event bus.
- When an event matches, EventBridge sends it to the rule's configured targets.

##### 1.1.12.4.2 Multiple Rules
- The same event can match multiple rules.
- This enables independent consumers and fanout without changing the producer.
- Adding a new rule/consumer does not require the producer to directly invoke that consumer.

##### 1.1.12.4.3 Multiple Targets
- A single event-bus rule can currently have up to five targets.
- Targets are invoked independently.
- This provides direct fanout from one matching rule.
- For larger or independently governed fanout, multiple rules can match the same event.

#### 1.1.12.5 Event Patterns

##### 1.1.12.5.1 Event Pattern
- An event pattern is a JSON structure that describes the event fields a rule should match.
- Only include fields relevant to the routing decision.
- Fields omitted from the pattern do not need to match.
- If the event contains the required fields and values according to the pattern, the rule matches.

##### 1.1.12.5.2 Common Match Fields
- source identifies the event producer namespace.
- detail-type identifies the type/category of event.
- detail contains event-specific values.
- account, region, resources, and other supported fields can also participate in matching.

##### 1.1.12.5.3 Content-Based Filtering
- EventBridge supports declarative content filtering.
- Patterns can match exact values and supported comparison operators.
- Filtering at EventBridge avoids invoking consumers for events they do not need.
- Prefer infrastructure-level filtering when the routing condition can be expressed in an event pattern.

##### 1.1.12.5.4 Pattern Testing
- Event patterns can be tested against sample events before deployment.
- AWS provides the TestEventPattern API/CLI capability and EventBridge Sandbox functionality.
- Test both events that should match and events that should not match.
- Incorrect event patterns commonly produce silent non-delivery because unmatched events simply do not invoke the target.

#### 1.1.12.6 Targets

##### 1.1.12.6.1 Target
- A target is the resource or endpoint EventBridge invokes when an event matches a rule.
- EventBridge requires permission to invoke the target.
- Target choice determines how the event enters the next stage of processing.

##### 1.1.12.6.2 Important In-Scope Targets
- AWS Lambda function → execute serverless application logic.
- Amazon SQS queue → buffer work and decouple downstream processing.
- Amazon SNS topic → publish to subscribers.
- AWS Step Functions state machine → start workflow orchestration.
- Amazon Kinesis Data Streams → place events into a stream.
- Amazon Data Firehose → deliver events into a managed delivery pipeline.
- Amazon ECS task → run containerized processing.
- Amazon API Gateway → invoke an API endpoint.
- AWS CodeBuild and CodePipeline can also be EventBridge targets for development/deployment workflows.
- Prefer DVA-C02 in-scope services when reasoning about exam scenarios.

##### 1.1.12.6.3 Asynchronous Target Semantics
- Several EventBridge target integrations invoke the target asynchronously.
- For example, EventBridge invokes Lambda functions asynchronously for event-bus rules.
- Distinguish EventBridge delivery retry from processing retries performed inside or downstream of the target service.

#### 1.1.12.7 Input Transformation

##### 1.1.12.7.1 Why Transform
- A target might not need the complete source event.
- The target might require a different JSON structure.
- EventBridge can transform event data before delivery.
- This reduces simple adapter code in consumers.

##### 1.1.12.7.2 Input Transformer
- Input transformers extract values from the original event and place them into a target-specific template.
- Use transformation to reshape data, rename/rearrange information, or send only required fields.
- The original producer does not need to know each consumer's target-specific payload shape.

##### 1.1.12.7.3 Transformation Boundary
- Use EventBridge transformation for straightforward payload mapping.
- Use Lambda or another compute/enrichment mechanism when transformation requires complex business logic, external lookups, or substantial computation.
- Keep routing infrastructure from becoming hidden business logic.

#### 1.1.12.8 PutEvents

##### 1.1.12.8.1 Custom Events
- Applications can publish custom events by using PutEvents.
- Each entry describes an event and includes values such as source, detail type, and JSON detail.
- The application publishes to an event bus rather than directly addressing every consumer.

##### 1.1.12.8.2 Batch Semantics
- PutEvents accepts multiple event entries in one request.
- Individual entries can fail even when other entries in the request succeed.
- Application code must inspect FailedEntryCount and individual result entries.
- Retry failed entries rather than blindly assuming the entire request failed.

##### 1.1.12.8.3 Producer Responsibility
- Define meaningful event source and detail-type values.
- Produce valid JSON event detail.
- Keep event contracts stable enough for independent consumers.
- Handle API errors and partial failures.
- Do not assume successful publication means every downstream consumer successfully processed the event.

#### 1.1.12.9 Event-Driven Fanout

##### 1.1.12.9.1 One Producer, Multiple Consumers
- A producer emits one event.
- Multiple EventBridge rules can independently match it.
- Each rule can send the event to one or more targets.
- This implements fanout while keeping consumers independent of the producer.

##### 1.1.12.9.2 Consumer Independence
- One consumer can process the event with Lambda.
- Another can buffer it in SQS.
- Another can start a Step Functions workflow.
- Another can route it to another event bus.
- Consumers can evolve independently when the event contract remains compatible.

##### 1.1.12.9.3 EventBridge vs SNS Fanout
- SNS is topic-based publish/subscribe and directly fans messages to subscriptions.
- EventBridge is event routing with rich content-based rules and event buses.
- Choose EventBridge when routing depends on event attributes, multiple sources must share routing infrastructure, or event-bus capabilities are required.
- Choose SNS when the primary requirement is straightforward topic-based pub/sub delivery.
- Both are in-scope Application Integration services and can appear together.

#### 1.1.12.10 Delivery Failure and Retry

##### 1.1.12.10.1 Retriable Delivery Failure
- EventBridge retries target delivery for retriable errors.
- The target retry policy controls maximum event age and retry attempts.
- AWS currently documents a default of up to 24 hours and 185 attempts with exponential backoff and jitter.
- Treat these as current service defaults, not universal application retry requirements.

##### 1.1.12.10.2 Permanent Failure
- Some delivery failures are not retried.
- Permission/configuration problems can cause events to fail immediately.
- Diagnose whether failure is transient target availability/throttling or permanent configuration/authorization.

##### 1.1.12.10.3 Dead-Letter Queue
- A target can be configured with an EventBridge dead-letter queue.
- EventBridge DLQs use standard Amazon SQS queues.
- The DLQ stores events EventBridge could not successfully deliver.
- This preserves failed events for investigation and later processing.

##### 1.1.12.10.4 Retry vs DLQ
- Retry handles transient delivery failures automatically.
- DLQ preserves events that still cannot be delivered.
- Configure both according to the application's durability requirements.
- A DLQ without an operational redrive/investigation process only stores failure; it does not resolve it.

#### 1.1.12.11 Idempotency and Delivery Semantics

##### 1.1.12.11.1 Duplicate Processing
- Event-driven systems must tolerate the possibility that processing is attempted more than once.
- Consumers should be idempotent when duplicate side effects would be harmful.
- Use a stable business/event identifier or persistence strategy where deduplication is required.

##### 1.1.12.11.2 Event ID
- EventBridge events include an id field.
- The ID can help correlate and trace an event.
- Business-level idempotency often needs an application-defined identifier because replay or producer behavior can create semantically duplicate work.

##### 1.1.12.11.3 Ordering
- Do not assume EventBridge event buses provide the shard-style ordering guarantees of Kinesis Data Streams or FIFO semantics of SQS FIFO.
- If strict ordering is a core requirement, select an integration mechanism that explicitly provides the required ordering semantics.
- EventBridge is primarily optimized for routing events, not for maintaining a globally ordered event log.

#### 1.1.12.12 Archive and Replay

##### 1.1.12.12.1 Archive
- EventBridge can archive events received by an event bus.
- An archive can use an event pattern to select which events to retain.
- Retention can be configured.
- Archives provide a managed mechanism for retaining events for later replay.

##### 1.1.12.12.2 Replay
- Archived events can be replayed to the event bus from which they were archived.
- Replay can help recover from consumer defects or process historical events after adding functionality.
- Replaying does not remove events from the archive.
- Consumers must be designed to tolerate reprocessing.

##### 1.1.12.12.3 Archive vs Kinesis Retention
- EventBridge archive is an optional event-bus feature for later replay.
- Kinesis Data Streams inherently retains stream records for its configured retention period.
- Choose based on the architectural requirement: event routing with optional archive/replay versus ordered retained streaming data.

#### 1.1.12.13 Schema Registry

##### 1.1.12.13.1 Event Schema
- A schema describes the structure of an event.
- EventBridge provides schemas for AWS service events.
- Custom schemas can also be created or uploaded.

##### 1.1.12.13.2 Schema Discovery
- EventBridge can infer schemas from events on an event bus when schema discovery is enabled.
- This can reduce manual effort when developing consumers.
- Evaluate privacy/security implications before enabling discovery on event buses carrying sensitive data.

##### 1.1.12.13.3 Code Bindings
- EventBridge schemas can generate/download code bindings for supported programming languages.
- Code bindings make event structure easier to consume from strongly typed application code.
- They improve developer ergonomics but do not remove the need for compatible schema evolution.

#### 1.1.12.14 EventBridge Pipes

##### 1.1.12.14.1 Pipe
- EventBridge Pipes provides point-to-point integration between one supported source and one target.
- A pipe can filter events and optionally enrich or transform them before delivery.
- Pipes reduce custom integration code for common source-to-target flows.

##### 1.1.12.14.2 Pipe Flow
- source → optional filter → optional enrichment → optional transformation → target
- Each pipe has a single source and a single target.
- This differs from an event bus, which routes events from many sources to potentially many targets.

##### 1.1.12.14.3 Filtering
- Pipes use event patterns to filter source records/events.
- Filtering prevents unnecessary target invocations.
- Filtering semantics depend partly on the source type.

##### 1.1.12.14.4 Enrichment
- Pipes can invoke a supported enrichment step before the target.
- Enrichment is useful when the incoming event lacks information required downstream.
- Example mental model: receive identifier → enrichment fetches additional data → enriched event sent to target.

##### 1.1.12.14.5 Pipes vs Event Bus
- Pipe: point-to-point integration from one source to one target, optionally filtered/enriched/transformed.
- Event bus: many-to-many event routing using rules.
- Use a pipe to reduce glue code between a supported source and target.
- Use an event bus when multiple producers/consumers and routing rules form the architectural center.

#### 1.1.12.15 API Destinations

##### 1.1.12.15.1 External HTTP Target
- EventBridge API destinations allow HTTPS endpoints to be targets of event-bus rules.
- This supports integration with applications and SaaS APIs outside AWS.
- EventBridge manages invocation according to the configured connection and destination.

##### 1.1.12.15.2 Connection
- A connection stores authorization configuration used for an API destination.
- EventBridge supports configured authorization mechanisms according to current service capabilities.
- Do not embed third-party credentials directly into event payloads.

##### 1.1.12.15.3 Third-Party Integration Boundary
- API destinations provide managed event-to-HTTP delivery.
- Skill 1.1.13 separately covers resilient application code for third-party service integrations.
- If EventBridge itself owns HTTP delivery, use EventBridge retry/DLQ/configuration mechanisms.
- If application code directly calls the third party, apply application-level resilience patterns from Skill 1.1.13.

#### 1.1.12.16 Permissions

##### 1.1.12.16.1 Producer Permission
- A custom producer requires permission to call PutEvents on the intended event bus.
- Apply least privilege to the allowed bus/resource where possible.

##### 1.1.12.16.2 EventBridge Target Permission
- EventBridge must be authorized to invoke the target.
- Depending on the target, authorization can involve a resource-based policy or an IAM role used by EventBridge.
- Correct event matching does not guarantee delivery when target permissions are wrong.

##### 1.1.12.16.3 Event Bus Resource Policy
- Event buses support resource-based policies.
- Policies can authorize cross-account or other permitted producers.
- Use policies deliberately to control who can publish or interact with the bus.

#### 1.1.12.17 Observability

##### 1.1.12.17.1 Delivery Metrics
- Monitor EventBridge delivery and failure metrics.
- FailedInvocations indicates failed target invocations.
- InvocationsSentToDLQ indicates events sent to a configured DLQ.
- IngestionToInvocationSuccessLatency can expose delivery delay including retry effects.

##### 1.1.12.17.2 Troubleshooting Flow
- Confirm the event reached the expected event bus.
- Confirm the event matches the rule's event pattern.
- Confirm the rule is enabled.
- Confirm the correct target is configured.
- Confirm EventBridge has permission to invoke the target.
- Inspect target errors, retry metrics, and DLQ messages.
- Separate routing failure from target application-processing failure.

#### 1.1.12.18 EventBridge Decision Model

##### 1.1.12.18.1 Need Content-Based Event Routing
- Use EventBridge event bus + rules.
- Match source, detail-type, detail, or other relevant event fields.
- Route only matching events to each target.

##### 1.1.12.18.2 Need One Event to Trigger Multiple Independent Consumers
- Use multiple matching rules and/or multiple targets.
- Keep producer unaware of individual consumers.
- This is an EventBridge implementation of event-driven fanout.

##### 1.1.12.18.3 Need Point-to-Point Integration
- Consider EventBridge Pipes.
- Use optional filtering, enrichment, and transformation.
- Avoid writing Lambda glue code when the pipe can express the integration directly.

##### 1.1.12.18.4 Need Managed HTTP Delivery to External API
- Consider EventBridge API destinations.
- Configure connection/authorization, target payload, retries, and DLQ appropriately.
- Do not build custom HTTP-calling code solely for routing if EventBridge can own the integration.

##### 1.1.12.18.5 Need Historical Reprocessing
- Configure EventBridge archive and replay when the event-bus architecture requires later replay.
- Ensure consumers are safe for reprocessing.

##### 1.1.12.18.6 Need Durable Work Buffer
- Prefer SQS when the primary requirement is buffering work until a consumer processes it.
- EventBridge can route events into SQS.
- EventBridge itself is not a substitute for queue backlog semantics.

##### 1.1.12.18.7 Need Retained Ordered Stream
- Prefer Kinesis Data Streams when records require stream retention/replay and shard-based ordering/processing.
- EventBridge can route events into Kinesis when both routing and streaming are required.

##### 1.1.12.18.8 Need Workflow Coordination
- Route an event to Step Functions when the reaction requires a multi-step orchestrated workflow.
- EventBridge decides that the workflow should start; Step Functions coordinates the workflow itself.

#### 1.1.12.19 Important Distinctions

##### 1.1.12.19.1 Event Bus vs Queue
- Event bus routes events according to rules.
- Queue stores work until consumers retrieve/process it.
- EventBridge and SQS often complement rather than replace one another.

##### 1.1.12.19.2 EventBridge vs SNS
- EventBridge provides event buses and rich content-based routing.
- SNS provides topic-based publish/subscribe.
- Both support fanout but their routing models differ.

##### 1.1.12.19.3 EventBridge vs Kinesis
- EventBridge is primarily an event router.
- Kinesis Data Streams is a retained ordered stream.
- Choose based on routing versus stream-processing requirements.

##### 1.1.12.19.4 Rule vs Event Pattern
- Rule is the routing configuration.
- Event pattern is the matching criteria inside an event-driven rule.
- A matching pattern causes the rule to route the event to its target(s).

##### 1.1.12.19.5 Input Transformation vs Enrichment
- Transformation reshapes existing event data.
- Enrichment obtains/adds information through an enrichment step.
- Do not invoke compute merely to rename or select fields when a transformer is sufficient.

##### 1.1.12.19.6 EventBridge Retry vs Consumer Retry
- EventBridge retry concerns delivery to the target.
- Consumer/application retry concerns processing performed after delivery.
- Diagnose and configure the correct layer.
