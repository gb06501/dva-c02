### 1.1.7 Write and run unit tests in development environments

#### 1.1.7.1 Unit Testing Scope

##### 1.1.7.1.1 Unit Test
- A unit test verifies a small, isolated unit of application behavior such as a function, method, class, or component.
- Unit tests should execute quickly and provide deterministic results.
- Dependencies outside the unit under test should normally be isolated when the purpose is to test only the unit's behavior.
- AWS guidance for serverless applications recommends separating business logic from service integrations so logic can be tested without deploying the complete application.

##### 1.1.7.1.2 Development Environment
- Unit tests are written and executed during development rather than only after deployment.
- Tests should be runnable locally and in automated build environments.
- The same test suite should produce consistent results across developer machines and CI environments when dependencies and runtime versions are controlled.

#### 1.1.7.2 Testable Application Design

##### 1.1.7.2.1 Separate Business Logic from Integration Code
- Keep core business logic separate from code that directly invokes AWS services or other external systems.
- Thin handlers/controllers make application behavior easier to test.
- Business logic can then be exercised with normal language testing frameworks without requiring live AWS resources.

##### 1.1.7.2.2 Dependency Injection
- Supply external dependencies to application code rather than constructing every dependency internally.
- Dependencies can include AWS SDK clients, repositories, clocks, configuration providers, and external API clients.
- Tests can replace these dependencies with controlled test implementations or mocks.
- Dependency injection reduces the need for live infrastructure in unit tests.

##### 1.1.7.2.3 Small Units
- Keep functions and components focused enough that expected behavior can be tested independently.
- Large functions with many responsibilities require more setup and produce less precise failures.
- Testability is therefore partly an application-design concern.

#### 1.1.7.3 Test Structure

##### 1.1.7.3.1 Arrange
- Prepare inputs, expected values, configuration, and dependency behavior.
- Create the unit under test in a known state.

##### 1.1.7.3.2 Act
- Execute the function or operation being tested.
- Keep the action focused on one behavior where practical.

##### 1.1.7.3.3 Assert
- Verify returned values, state changes, emitted calls, or errors.
- Assertions should describe the externally observable behavior expected from the unit.

##### 1.1.7.3.4 Test Naming
- Test names should make the behavior and expected outcome understandable.
- A useful structure communicates the condition, action, and expected result.
- Naming conventions depend on the programming language and framework.

#### 1.1.7.4 Test Cases

##### 1.1.7.4.1 Happy Path
- Verify expected behavior for valid normal inputs.
- Confirm the unit returns or produces the intended result.

##### 1.1.7.4.2 Boundary Cases
- Test minimum, maximum, empty, null/undefined, and other boundary conditions where applicable.
- Boundary tests are especially important around validation, pagination, sizes, time windows, and numeric limits.

##### 1.1.7.4.3 Invalid Input
- Verify malformed or unsupported inputs are rejected correctly.
- Confirm the application produces the expected error rather than silently accepting invalid state.

##### 1.1.7.4.4 Dependency Failure
- Simulate dependency errors such as exceptions, throttling, timeout responses, or unavailable services.
- Verify the unit follows the intended resilience/error-handling path.

##### 1.1.7.4.5 Duplicate and Retry Cases
- Where operations are designed to be idempotent, execute duplicate or repeated inputs.
- Verify retries do not create unintended duplicate side effects.

#### 1.1.7.5 Test Doubles

##### 1.1.7.5.1 Mock
- A mock replaces a dependency and allows the test to control responses and verify interactions.
- AWS SDK clients can be mocked so tests do not invoke live AWS services.
- Use mocks when interaction with the dependency itself is part of the behavior being tested.

##### 1.1.7.5.2 Stub
- A stub provides predetermined data or behavior to the unit under test.
- It is useful when the test needs controlled dependency output but does not need to verify detailed interactions.

##### 1.1.7.5.3 Fake
- A fake provides a simplified working implementation of a dependency.
- It can be useful when an in-memory or lightweight implementation makes tests clearer than extensive mocking.

##### 1.1.7.5.4 Avoid Over-Mocking
- Mock external boundaries rather than every internal implementation detail.
- Tests coupled too closely to internal calls can fail during harmless refactoring.
- Prefer assertions about meaningful behavior over assertions about incidental implementation details.

#### 1.1.7.6 AWS SDK Dependencies

##### 1.1.7.6.1 SDK Client Isolation
- Application code that calls AWS services should expose a boundary that can be replaced during unit testing.
- Inject or otherwise substitute SDK clients instead of requiring real AWS credentials and network calls.
- Tests should define expected SDK responses and service errors explicitly.

##### 1.1.7.6.2 AWS SDK Mocking
- Mocking techniques depend on the language and AWS SDK.
- AWS documentation and AWS code examples demonstrate language-specific mocking approaches.
- The principle is consistent: unit tests should control the behavior of the AWS dependency rather than depend on a live service.

##### 1.1.7.6.3 Service Error Simulation
- Test AWS service errors that application logic is expected to handle.
- Examples include throttling, conditional-operation failures, not-found responses, and access errors where relevant to the code.
- Verify that retryable and non-retryable outcomes are handled according to application requirements.

#### 1.1.7.7 AWS Lambda Unit Testing

##### 1.1.7.7.1 Handler Design
- Keep the Lambda handler small.
- Separate event parsing and AWS-specific integration from domain/business logic where practical.
- Business logic can then be unit tested independently of the Lambda runtime.

##### 1.1.7.7.2 Event Inputs
- Construct representative event objects for the Lambda event source.
- Test required fields, missing fields, malformed input, and edge cases.
- Event examples can be stored as test fixtures when useful.

##### 1.1.7.7.3 Context and Environment
- Mock or construct Lambda context information only when application behavior depends on it.
- Control environment variables and configuration during tests.
- Avoid tests that depend on configuration accidentally inherited from the developer's machine.

##### 1.1.7.7.4 Powertools for AWS Lambda
- AWS Lambda Powertools provides utilities that can improve testability and operational consistency for supported runtimes.
- Some Powertools features provide testing utilities or patterns for event handling and AWS integrations.
- Powertools is useful where applicable but is not a requirement for understanding unit testing.

#### 1.1.7.8 Local AWS Development Tools

##### 1.1.7.8.1 AWS SAM CLI
- AWS SAM CLI supports local testing and debugging of serverless applications.
- `sam local invoke` can invoke a Lambda function locally with an event.
- `sam local start-api` can run API Gateway-style local endpoints backed by Lambda functions.
- SAM local execution uses containers to approximate the Lambda execution environment.

##### 1.1.7.8.2 Unit Test vs Local Integration Test
- Running a Lambda function locally with SAM is not automatically a unit test.
- If the test executes multiple application components or real/emulated integrations, it moves toward integration testing.
- Unit tests should remain isolated and fast even when SAM is also used in the development workflow.

##### 1.1.7.8.3 Cloud-Based Testing
- AWS serverless testing guidance notes that cloud-based tests provide the greatest fidelity for cloud services.
- Local/unit testing remains useful for isolated business logic and fast developer feedback.
- Do not assume local emulation perfectly reproduces every managed AWS service behavior.

#### 1.1.7.9 Deterministic Tests

##### 1.1.7.9.1 Control External Inputs
- Control time, random values, identifiers, network responses, and other nondeterministic dependencies when they affect behavior.
- Inject clocks or generators when deterministic behavior is required.

##### 1.1.7.9.2 Independent Tests
- Tests should not depend on execution order.
- A test should create the state it requires and clean up any local resources it owns.
- Shared mutable state makes test results harder to reproduce.

##### 1.1.7.9.3 Repeatability
- Re-running the same unit test with the same inputs should produce the same result.
- Flaky tests reduce trust in automated test suites.

#### 1.1.7.10 Running Tests

##### 1.1.7.10.1 Language Test Framework
- Use the standard or established testing framework for the application's programming language.
- Examples include JUnit for Java, pytest/unittest for Python, Jest for JavaScript/TypeScript, xUnit/NUnit for .NET, and Go's `testing` package.
- The exam skill is language-independent; exact framework syntax is secondary to understanding the testing principles.

##### 1.1.7.10.2 Local Execution
- Developers should be able to execute the test suite before committing or deploying code.
- Test commands should be reproducible and documented through the project's build tooling.

##### 1.1.7.10.3 Automated Execution
- Unit tests should be suitable for execution in CI/build pipelines.
- A failing unit test should fail the build or quality gate according to project policy.
- Detailed CI/CD pipeline implementation belongs to Domain 3.

#### 1.1.7.11 Coverage

##### 1.1.7.11.1 Code Coverage
- Coverage tools can identify code paths that tests execute or miss.
- Coverage can reveal untested branches and error paths.

##### 1.1.7.11.2 Coverage Is Not Correctness
- A high coverage percentage does not prove that behavior is correct.
- Assertions and meaningful test scenarios matter more than executing lines without validating outcomes.
- Prioritize critical business behavior, failure paths, and edge cases.

#### 1.1.7.12 What Unit Tests Should Not Depend On

##### 1.1.7.12.1 Live AWS Services
- A pure unit test should not require a live DynamoDB table, S3 bucket, SQS queue, Lambda function, or other deployed AWS resource.
- Tests using live AWS resources are integration or end-to-end tests rather than isolated unit tests.

##### 1.1.7.12.2 Developer Credentials
- Unit tests should not require personal AWS credentials to exercise isolated application logic.
- Requiring credentials makes tests less portable and increases risk.

##### 1.1.7.12.3 Network Availability
- Unit tests should not fail merely because an external network or third-party service is unavailable.
- Replace network dependencies with controlled test doubles.

#### 1.1.7.13 Unit vs Integration vs End-to-End Testing

##### 1.1.7.13.1 Unit Test
- Tests a small isolated piece of code.
- External dependencies are replaced or controlled.
- Fast and suitable for frequent execution.

##### 1.1.7.13.2 Integration Test
- Tests interaction between components or with an external service.
- Can verify that application code correctly integrates with AWS services.
- Higher fidelity but usually slower and requires more environment setup.

##### 1.1.7.13.3 End-to-End Test
- Exercises a complete application flow through deployed components.
- Provides high confidence in overall behavior but has higher execution cost and failure complexity.

##### 1.1.7.13.4 AWS Testing Strategy
- AWS serverless testing guidance recommends combining multiple testing approaches rather than relying on only one level.
- Unit tests provide fast feedback; cloud integration and end-to-end tests validate actual managed-service behavior.

#### 1.1.7.14 Unit-Test Decision Model

##### 1.1.7.14.1 Pure Business Logic
- Call the function directly.
- Provide controlled inputs.
- Assert returned values or state changes.
- No AWS infrastructure should be necessary.

##### 1.1.7.14.2 Code Using an AWS Service
- Inject or replace the AWS SDK client.
- Configure expected service responses/errors.
- Execute application logic.
- Assert application behavior and important service interactions.

##### 1.1.7.14.3 Lambda Handler
- Keep handler logic thin.
- Supply representative event input.
- Mock AWS dependencies.
- Test parsing, validation, delegation, and response/error behavior.

##### 1.1.7.14.4 Need to Verify Actual AWS Behavior
- This is no longer purely a unit-test concern.
- Use an integration test against an appropriate AWS development/test environment.
- Do not compensate for missing integration testing by making unit tests depend on live infrastructure.
