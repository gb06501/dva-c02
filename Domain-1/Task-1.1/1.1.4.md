### 1.1.4 Describe differences between synchronous and asynchronous patterns

#### 1.1.4.1 Communication Patterns

##### 1.1.4.1.1 Distributed Communication
- AWS identifies synchronous, asynchronous, and batch as major communication styles in distributed systems.
- This skill focuses on synchronous and asynchronous interaction.
- A workload can use both patterns; the correct choice depends on the interaction's latency, consistency, availability, and processing requirements.
- The core distinction is whether the caller must wait for the dependency to produce a response before the caller can continue.

#### 1.1.4.2 Synchronous Communication

##### 1.1.4.2.1 Synchronous Request/Response
- A client sends a request to a service and waits for the service to respond before proceeding.
- Common examples include HTTP/HTTPS, REST, and RPC request/response interactions.
- Reads such as HTTP GET and mutations such as HTTP PUT can use synchronous communication.
- The request path has a direct runtime dependency on the called service.

##### 1.1.4.2.2 Benefits
- Predictable flow control and a clear request/response cycle.
- Immediate result or confirmation is available to the caller.
- Errors can propagate directly to the caller.
- Familiar protocols and interaction models make implementation and troubleshooting comparatively straightforward.
- Appropriate when the caller requires an immediate response.

##### 1.1.4.2.3 Trade-offs
- Creates temporal coupling: caller and dependency must be available at the same time.
- Dependency latency becomes part of caller latency.
- Dependency failure can directly affect the caller.
- Chains of synchronous dependencies become increasingly brittle because every dependency in the path must succeed.
- Open connections and waiting callers consume resources.
- Failures can cascade through synchronous call chains.

##### 1.1.4.2.4 Resilience Considerations
- Avoid unnecessarily long chains of synchronous dependencies.
- Set timeouts instead of waiting indefinitely.
- Determine appropriate error-handling and retry behavior.
- Prefer failing fast to waiting indefinitely for an unhealthy dependency.
- Minimize chatty interactions that require many dependency calls for one request.
- Detailed resilience implementation belongs to Skills 1.1.5 and 1.1.13.

#### 1.1.4.3 Asynchronous Communication

##### 1.1.4.3.1 Asynchronous Interaction
- The caller initiates work without waiting for the complete processing result before continuing.
- The caller may receive an acknowledgement that the request was accepted while actual processing occurs later.
- Communication commonly uses an intermediary such as a queue, event bus, topic, or stream.
- Producer and consumer do not necessarily need to be available at the same time.
- Asynchronous interaction can temporally decouple components.

##### 1.1.4.3.2 Benefits
- Caller can continue other processing without waiting for the dependency.
- Improves fault isolation by reducing direct runtime dependency between services.
- Allows consumers to process work according to their available capacity.
- Queues can buffer traffic spikes and differences between producer and consumer processing rates.
- Naturally supports event-driven architectures.
- Can improve scalability and resilience of distributed workloads.

##### 1.1.4.3.3 Trade-offs
- The final result is not immediately available to the caller.
- Returning a later result requires an additional mechanism when the caller needs that result.
- Troubleshooting can require tracing work across multiple components.
- Testing can require coordination across several asynchronous systems.
- Message delivery can involve duplicates; consumers should not assume exactly-once delivery.
- Ordering, retries, failed-message handling, and eventual processing must be considered where relevant.

#### 1.1.4.4 Asynchronous Interaction Patterns

##### 1.1.4.4.1 Fire and Forget
- Client submits work and does not wait for the completed processing result.
- The service can acknowledge that the work was accepted before processing completes.
- AWS guidance recommends acknowledging only after the work is durably persisted, such as in a queue or database.
- Idempotency, failed-message handling, and processing monitoring are important considerations.

##### 1.1.4.4.2 Claim Check
- Large or separately retrievable data can be stored outside the message flow.
- The communication contains a reference that can be used to retrieve the data or result.
- This can also support workflows where a client polls for an asynchronously produced result.

##### 1.1.4.4.3 Callback
- Client provides a location or mechanism through which the service can communicate completion later.
- Client does not remain blocked waiting for the operation to finish.
- Callback endpoints require appropriate security, retry, and timeout handling.

##### 1.1.4.4.4 Bidirectional Communication
- Client and service maintain a connection that permits both sides to send messages.
- Communication can still be asynchronous even though a stateful connection is maintained.
- Ordering, connection state, error handling, and observability become important considerations.

#### 1.1.4.5 Synchronous vs Asynchronous

##### 1.1.4.5.1 Caller Behavior
- Synchronous: caller waits for the response before continuing.
- Asynchronous: caller can continue without waiting for final processing to complete.

##### 1.1.4.5.2 Availability Dependency
- Synchronous: caller and dependency generally need to be available concurrently.
- Asynchronous: an intermediary can allow producer and consumer to operate at different times.

##### 1.1.4.5.3 Latency
- Synchronous: downstream processing time directly contributes to request latency.
- Asynchronous: caller latency can be separated from downstream processing latency.

##### 1.1.4.5.4 Result Handling
- Synchronous: result or error can be returned directly in the request/response interaction.
- Asynchronous: result may be delivered later through polling, callback, events, messages, or another mechanism.

##### 1.1.4.5.5 Failure Propagation
- Synchronous: dependency failure can immediately propagate to the caller.
- Asynchronous: intermediaries can isolate temporary consumer failure and retain work for later processing.

##### 1.1.4.5.6 Traffic Spikes
- Synchronous: downstream services must handle incoming demand as requests arrive.
- Asynchronous: queues and similar intermediaries can buffer work so consumers process according to capacity.

##### 1.1.4.5.7 Complexity
- Synchronous: generally simpler control flow, direct error handling, and easier tracing.
- Asynchronous: introduces additional concerns such as message lifecycle, duplicate handling, delayed results, ordering, and distributed observability.

#### 1.1.4.6 Choosing the Pattern

##### 1.1.4.6.1 Prefer Synchronous When
- The caller requires an immediate response or result.
- The interaction is latency-sensitive.
- A direct request/response model matches the business requirement.
- Immediate confirmation of an operation is required.

##### 1.1.4.6.2 Prefer Asynchronous When
- The caller does not need the final result immediately.
- Processing can happen later.
- Producer and consumer should be temporally decoupled.
- Workloads must tolerate traffic spikes or differences in processing capacity.
- Failure isolation between producer and consumer is important.
- An event should initiate background or independent processing.

##### 1.1.4.6.3 Hybrid Communication
- Real systems commonly combine synchronous and asynchronous interactions.
- A synchronous request can accept work and return an acknowledgement while downstream processing continues asynchronously.
- A workflow orchestrator can mix synchronous and asynchronous invocations.
- Pattern selection should be made per interaction rather than labeling an entire application as exclusively synchronous or asynchronous.

#### 1.1.4.7 AWS Mechanisms and Examples

##### 1.1.4.7.1 Synchronous Examples
- HTTP/REST APIs are common synchronous request/response mechanisms.
- Amazon API Gateway can expose APIs used for synchronous application interactions.
- Direct service or microservice API calls can be synchronous when the caller waits for the response.

##### 1.1.4.7.2 Amazon SQS
- Amazon SQS provides managed message queues for decoupling distributed components.
- Producers can store work in a queue without requiring consumers to be concurrently available.
- Consumers process queued messages independently.
- SQS is a common mechanism for asynchronous processing.

##### 1.1.4.7.3 Amazon SNS
- Amazon SNS provides push-based messaging and publish/subscribe capabilities.
- A message can be distributed to multiple subscribers.
- SNS and SQS can be combined so notifications are distributed while durable queues allow consumers to process later.

##### 1.1.4.7.4 Amazon EventBridge
- EventBridge supports asynchronous event-driven communication.
- Producers publish events without directly integrating with every consumer.
- Rules can filter and route events to targets.
- AWS recommends EventBridge where synchronous communication is not required and routing logic should be decoupled from microservices.

##### 1.1.4.7.5 AWS Step Functions
- Workflow orchestration can combine synchronous and asynchronous invocations.
- The communication style of an individual interaction is therefore separate from the choice to use orchestration.

#### 1.1.4.8 Important Distinctions

##### 1.1.4.8.1 Synchronous Is Not the Same as Tightly Coupled
- Synchronous communication creates temporal coupling because caller and dependency must be available together.
- However, coupling has additional dimensions such as contracts, shared data, implementation assumptions, and deployment dependencies.
- The broader tight-vs-loose coupling model belongs to Skill 1.1.3.

##### 1.1.4.8.2 Asynchronous Is Not the Same as Event-Driven
- Asynchronous describes whether the caller waits for completion.
- Event-driven describes an architecture in which components produce and react to events.
- Event-driven systems commonly use asynchronous communication, but the concepts are not identical.

##### 1.1.4.8.3 Asynchronous Is Not Automatically More Resilient
- Asynchronous intermediaries can improve fault isolation and absorb temporary processing differences.
- Correct handling still requires consideration of retries, duplicate delivery, idempotency, failed messages, and observability.
- These concerns are expanded in later skills.

##### 1.1.4.8.4 Acknowledgement Is Not Completion
- An asynchronous system can synchronously acknowledge that work was accepted.
- That acknowledgement does not mean the requested business processing has completed successfully.
