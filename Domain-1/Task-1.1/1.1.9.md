### 1.1.9 Write code that interacts with AWS services by using APIs and AWS SDKs

#### 1.1.9.1 AWS API and SDK Scope

##### 1.1.9.1.1 AWS Service APIs
- AWS services expose programmatic operations through service APIs.
- Application code can call those operations directly over supported protocols, but AWS SDKs are the normal developer abstraction.
- AWS SDKs provide language-specific clients and models for AWS service APIs.
- The SDKs handle common cross-service concerns such as request signing, endpoint resolution, credential discovery, retries, and serialization.

##### 1.1.9.1.2 AWS SDKs
- AWS provides SDKs for common programming languages including Java, JavaScript/TypeScript, Python, .NET, Go, C++, PHP, Ruby, Rust, Kotlin, Swift, and others.
- Each SDK exposes service clients that map to AWS service operations.
- The exact client type and method names vary by language, but the interaction model is consistent: configure client → build request → call service operation → process response/error.

#### 1.1.9.2 Service Clients

##### 1.1.9.2.1 Client Object
- To access an AWS service programmatically, create a client for that service.
- The client contains configuration such as Region, credentials provider, retry behavior, and service endpoint behavior.
- A service client is then used to invoke API operations for that AWS service.
- AWS SDK reference guidance notes that in many SDKs service client objects are immutable after construction.

##### 1.1.9.2.2 Client Reuse
- Reuse service clients when practical instead of creating a new client for every operation.
- Client creation can involve configuration resolution, credential providers, HTTP connection pools, and other setup.
- Reusing clients helps reuse underlying connections and reduces avoidable overhead.
- Create separate clients when materially different configuration is required, such as another Region, endpoint, or retry policy.

##### 1.1.9.2.3 Region
- Most AWS service clients operate against a Region.
- Region can be configured explicitly in code or resolved from standardized configuration sources.
- Application code should use the intended Region rather than relying on accidental developer-machine defaults.
- Region selection can affect endpoint, data locality, latency, and resource identity.

#### 1.1.9.3 Credential Provider Chain

##### 1.1.9.3.1 Credential Resolution
- AWS SDKs use a credential provider chain to search supported credential sources in a defined order.
- Once valid credentials are found, the search stops.
- The specific provider order varies by SDK, but many providers and settings are standardized across SDKs.

##### 1.1.9.3.2 Common Credential Sources
- Environment-based credentials
- Shared AWS config/credentials files
- AWS IAM Identity Center credentials
- Assume-role credentials
- Web identity/OIDC credentials
- Container credentials for ECS/EKS workloads
- EC2 instance-profile credentials through IMDS
- Custom process providers where supported

##### 1.1.9.3.3 Temporary Credentials
- Prefer temporary credentials obtained from roles or other credential providers over long-lived access keys in application code.
- AWS SDK credential providers can automatically refresh temporary credentials before or after expiration according to provider behavior.
- Application code should not manually rotate temporary credentials when the SDK/provider can manage refresh automatically.

##### 1.1.9.3.4 Do Not Hard-Code Credentials
- Do not embed access key IDs, secret access keys, or session tokens in source code.
- Use IAM roles, workload identity, environment/configuration providers, or Secrets Manager only where appropriate for non-AWS secrets.
- Detailed authentication/authorization design belongs to Domain 2.

#### 1.1.9.4 Request Authentication and Signing

##### 1.1.9.4.1 AWS Signature
- AWS service requests are authenticated by signing requests with AWS credentials.
- AWS SDKs perform request signing automatically for supported services.
- Application code normally does not need to manually implement Signature Version 4 when using an SDK.

##### 1.1.9.4.2 Permission Evaluation
- Successful signing proves the request identity but does not itself grant permission.
- The caller's IAM permissions and relevant resource policies determine whether the operation is authorized.
- An SDK call can therefore be correctly signed and still receive an access-denied response.

#### 1.1.9.5 Building Requests

##### 1.1.9.5.1 Request Object
- SDK operations typically accept a request object or parameter structure.
- Set required parameters and only the optional parameters needed for the use case.
- Request models provide language-level representations of service API fields.

##### 1.1.9.5.2 Resource Identifiers
- Use the identifier format required by the API, such as ARN, resource name, URL, key, queue URL, or table name.
- Do not assume all services identify resources the same way.
- Read the service API reference for exact required fields and constraints.

##### 1.1.9.5.3 Validation
- Many SDKs perform basic client-side model validation or type checking.
- Service-side validation remains authoritative.
- Invalid parameter combinations can return service errors even if local compilation/type checks succeed.

#### 1.1.9.6 Invoking Operations

##### 1.1.9.6.1 Synchronous Invocation
- Many SDKs provide blocking/synchronous operation methods.
- The caller waits for the AWS service response.
- Application code must set suitable timeouts and handle service errors.

##### 1.1.9.6.2 Asynchronous Invocation
- Many SDKs also provide async/non-blocking APIs appropriate to the language runtime.
- Async SDK calls can avoid blocking threads while the network request is in flight.
- Using an asynchronous SDK method does not change the semantics of the AWS service operation itself.

##### 1.1.9.6.3 Operation Result
- Successful calls return a response object containing service-defined output.
- Application code should read only the fields required by its business logic.
- Do not assume optional response fields are always present.

#### 1.1.9.7 Error Handling

##### 1.1.9.7.1 Service Errors
- AWS services return structured errors for invalid input, authorization failure, throttling, conflicts, missing resources, quota limits, and other conditions.
- SDKs translate service errors into language-specific exceptions or error objects.
- Application code should distinguish business-relevant error types rather than treating all failures identically.

##### 1.1.9.7.2 Retryable vs Non-Retryable
- Transient failures and throttling can be retryable.
- Invalid requests, authorization failures, and many business-rule errors are generally non-retryable without a change in input or configuration.
- Let the SDK handle supported transport/service retries where appropriate, then add application-level handling only where the business operation requires it.

##### 1.1.9.7.3 Preserve Context
- Log or propagate enough error context to diagnose the failed operation.
- Include operation/resource/correlation identifiers where appropriate.
- Do not log secret values, credentials, tokens, or sensitive payloads.

#### 1.1.9.8 SDK Retry Behavior

##### 1.1.9.8.1 Standard Retry Mode
- AWS SDKs provide standardized retry modes.
- Standard mode is the general default/recommended mode for most workloads.
- It retries supported transient and throttling failures using exponential backoff with jitter.
- It uses a retry quota so clients fail rather than retry indefinitely when failures persist.

##### 1.1.9.8.2 Adaptive Retry Mode
- Adaptive mode adds client-side rate limiting in response to throttling.
- AWS recommends it only for appropriate throttling-heavy, latency-tolerant scenarios.
- It is not a general replacement for standard mode.

##### 1.1.9.8.3 Legacy Retry Mode
- Legacy mode exists for backward compatibility in SDKs that support it.
- Behavior varies across SDKs and is not standardized.
- New code should prefer standardized retry behavior.

##### 1.1.9.8.4 Max Attempts
- SDK retry configuration includes the total maximum number of attempts.
- Attempts include the initial request.
- Keep retry behavior bounded.
- Do not layer uncontrolled application retries on top of SDK retries.

#### 1.1.9.9 Pagination

##### 1.1.9.9.1 Paginated APIs
- Many AWS list/search APIs return results in pages rather than returning all matching resources at once.
- Responses include a continuation token or similar marker when more results exist.
- Application code must continue until the service indicates there are no more pages when complete enumeration is required.

##### 1.1.9.9.2 SDK Paginators
- Many AWS SDKs provide paginator abstractions for paginated operations.
- A paginator handles continuation tokens and repeated requests.
- Prefer SDK paginator support instead of manually reimplementing token handling when the SDK provides it.

##### 1.1.9.9.3 Do Not Assume One Page
- A successful list operation can return only the first page.
- Code that processes only one response can silently miss resources/data.
- Whether to read all pages or stop early should be an explicit application decision.

#### 1.1.9.10 Waiters

##### 1.1.9.10.1 Eventual State Changes
- Some AWS API operations return before a resource reaches its final desired state.
- Examples include resource creation, deletion, or state transitions.
- Immediately issuing a dependent operation can fail if the resource is not yet ready.

##### 1.1.9.10.2 SDK Waiters
- AWS SDKs provide waiter abstractions for supported operations.
- Waiters repeatedly poll the relevant describe/get API until a target state or failure condition is reached.
- Prefer SDK waiters over custom polling loops when appropriate.
- Waiters must still be bounded by timeout/attempt limits.

#### 1.1.9.11 Timeouts and HTTP Behavior

##### 1.1.9.11.1 Connection Timeout
- Limits how long the client waits to establish a network connection.
- Prevents requests from blocking indefinitely when an endpoint cannot be reached.

##### 1.1.9.11.2 Request/Read Timeout
- Limits how long the client waits for a response after connection.
- Appropriate values depend on the service operation and workload latency requirements.

##### 1.1.9.11.3 HTTP Connection Reuse
- SDK clients normally manage HTTP connection pools.
- Reusing service clients enables connection reuse.
- Recreating clients for every request can lose connection-pooling benefits.

#### 1.1.9.12 Configuration Precedence

##### 1.1.9.12.1 Configuration Sources
- AWS SDKs resolve settings from multiple sources such as explicit code configuration, environment variables, and shared configuration files.
- Explicit settings in code/client configuration generally take precedence over external defaults.
- Exact precedence can vary by SDK and setting.

##### 1.1.9.12.2 Standardized Settings
- AWS SDKs standardize many cross-SDK settings including Region, credentials, retries, endpoints, dual-stack/FIPS behavior, and others.
- Use the SDK reference guide to understand portable configuration behavior.
- Use the language-specific SDK documentation for features that differ by SDK.

#### 1.1.9.13 Endpoint Configuration

##### 1.1.9.13.1 Service Endpoints
- SDKs resolve the correct AWS service endpoint based on service, Region, and configuration.
- Applications normally should not hard-code public AWS service URLs.

##### 1.1.9.13.2 Custom Endpoints
- SDKs allow endpoint overrides for supported use cases such as testing, local tools, private environments, or special endpoint requirements.
- Endpoint overrides should be explicit and controlled because they change where signed requests are sent.

##### 1.1.9.13.3 Dual-Stack and FIPS
- Standardized SDK settings can select dual-stack or FIPS endpoints where supported.
- Use only when the workload requirement calls for them.

#### 1.1.9.14 Serialization and Data Types

##### 1.1.9.14.1 SDK Serialization
- SDKs convert language objects into the wire-format required by the service API.
- SDKs deserialize service responses back into language-level response objects.
- Application code should use SDK models instead of manually constructing AWS protocol payloads unless there is a specific need.

##### 1.1.9.14.2 Binary and Structured Data
- Some APIs support binary values, streams, JSON documents, maps, or service-specific types.
- Use the SDK's type/model guidance for the relevant language.
- Be mindful of payload size limits and streaming APIs where applicable.

#### 1.1.9.15 Idempotency in API Calls

##### 1.1.9.15.1 Idempotent APIs
- Some AWS operations are naturally idempotent.
- Some mutating APIs support a client token/idempotency token.
- Reusing the same token allows safe retries for supported operations.

##### 1.1.9.15.2 Application Responsibility
- SDK retries do not automatically make every business operation idempotent.
- Application code must understand the semantics of the specific API operation.
- For side-effecting operations, use the service's idempotency features where available and design application-level idempotency where necessary.

#### 1.1.9.16 Concurrency and Client Safety

##### 1.1.9.16.1 Client Reuse Across Threads/Tasks
- Many AWS SDK service clients are designed to be reused safely, but exact thread-safety guarantees are SDK-specific.
- Check the language SDK documentation before sharing clients across threads/tasks.
- Do not infer identical concurrency behavior across all SDKs.

##### 1.1.9.16.2 Async Runtime Integration
- Use the SDK variant appropriate to the language/runtime model.
- Avoid blocking an event loop with synchronous I/O in runtimes designed for async processing.
- Runtime-specific implementation detail remains secondary to the AWS interaction model.

#### 1.1.9.17 Testing AWS API Interaction

##### 1.1.9.17.1 Unit Tests
- Isolate AWS SDK clients behind dependency boundaries.
- Mock or fake SDK responses/errors for unit tests.
- Verify application behavior without requiring live AWS infrastructure.
- Detailed unit testing belongs to Skill 1.1.7.

##### 1.1.9.17.2 Integration Tests
- Use a controlled AWS development/test environment when verifying actual service behavior.
- Integration tests validate permissions, endpoint behavior, service semantics, and serialization that mocks cannot fully reproduce.
- Deployed-environment testing belongs primarily to Domain 3.

#### 1.1.9.18 API/SDK Decision Model

##### 1.1.9.18.1 Need to Call an AWS Service
- Use the AWS SDK for the application's language unless there is a strong reason to use the raw API.
- Create/reuse the appropriate service client.
- Configure Region and credential provider correctly.

##### 1.1.9.18.2 Need Credentials
- Use the SDK credential provider chain.
- Prefer workload roles/temporary credentials.
- Do not hard-code long-lived credentials.

##### 1.1.9.18.3 Need to List Many Resources
- Check whether the operation is paginated.
- Use the SDK paginator when available.
- Continue until there is no continuation token if complete enumeration is required.

##### 1.1.9.18.4 Need to Wait for Resource State
- Use an SDK waiter when supported.
- Avoid unbounded custom polling.

##### 1.1.9.18.5 API Call Fails
- Inspect the structured SDK/service error.
- Allow the SDK to retry supported transient/throttling failures.
- Handle non-retryable/business errors explicitly.
- Keep additional application retries bounded and idempotent.

##### 1.1.9.18.6 High Call Volume
- Reuse SDK clients.
- Use connection pooling.
- Use pagination/batching where the service API supports it.
- Avoid unnecessary repeated calls for the same data.

#### 1.1.9.19 Important Distinctions

##### 1.1.9.19.1 AWS SDK vs AWS CLI
- AWS SDKs are libraries embedded in application code.
- AWS CLI is an interactive/automation command-line tool.
- Both call AWS APIs and use similar credential/configuration concepts, but this skill is about application code.

##### 1.1.9.19.2 Authentication vs Authorization
- SDKs authenticate/sign the request using credentials.
- IAM/resource policies determine whether the authenticated principal is authorized.
- Detailed authorization belongs to Domain 2.

##### 1.1.9.19.3 SDK Retry vs Business Retry
- SDK retries address transport/service-level retryable failures.
- Business workflows may require separate retry/compensation decisions.
- Do not multiply retries across layers without understanding the total effect.

##### 1.1.9.19.4 Pagination vs Batching
- Pagination retrieves a large result set across multiple response pages.
- Batching sends or processes multiple items in one API call where the service supports batch operations.
- They solve different problems.

##### 1.1.9.19.5 Waiter vs Retry
- A retry repeats a failed request.
- A waiter polls for a resource to reach a desired state after an operation may already have succeeded.
- Do not treat them as the same mechanism.
