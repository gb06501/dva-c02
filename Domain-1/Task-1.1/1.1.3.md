### 1.1.3 Describe differences between tightly coupled and loosely coupled components

#### 1.1.3.1 Coupling

##### 1.1.3.1.1 Coupling
- Coupling describes the degree of dependency or interdependence between components.
- AWS architecture guidance favors loose coupling where practical so changes and failures in one component have minimal impact on others.
- A component can be code, configuration, and AWS resources that together deliver a requirement.
- Coupling can arise through direct communication, shared data, shared implementation assumptions, or dependencies on another component's availability and behavior.

#### 1.1.3.2 Tightly Coupled Components

##### 1.1.3.2.1 Tight Coupling
- Components have strong dependencies on one another.
- A change to one component can require changes to components that depend on it.
- Failure or degraded performance in one component can propagate to dependent components.
- Components can depend directly on another component being available at the same time.
- Direct point-to-point calls without failover or asynchronous processing can create tight runtime dependencies.
- Shared databases or other shared data stores can reintroduce tight coupling between otherwise separate components.
- Chatty interactions with many calls between components increase coupling and latency.

##### 1.1.3.2.2 Consequences
- Changes have a larger blast radius.
- Independent deployment becomes harder.
- Independent scaling becomes harder when components depend directly on each other's capacity or behavior.
- Failures can cascade across component boundaries.
- Teams can have less freedom to change internal implementations.

#### 1.1.3.3 Loosely Coupled Components

##### 1.1.3.3.1 Loose Coupling
- Components minimize assumptions and dependencies about each other's internal implementation.
- Dependent components interact through a published, versioned interface or another defined contract.
- A component's implementation can change while minimizing impact on its consumers.
- Failures can be isolated more effectively at component boundaries.
- Components can be scaled independently according to their own resource needs.
- Loose coupling improves resiliency and agility.

##### 1.1.3.3.2 Independent Change
- A component can modify code or add functionality while minimizing risk to dependent components.
- The underlying implementation of a dependency can potentially change without consumers changing, provided the contract remains compatible.
- Well-defined APIs and service contracts help preserve this boundary.

##### 1.1.3.3.3 Independent Scaling
- Individual components can scale according to their own workload.
- Producers and consumers do not necessarily need identical processing capacity.
- Intermediate messaging or streaming layers can absorb differences in processing rate.

##### 1.1.3.3.4 Failure Isolation
- Failure of one component is less likely to immediately cause failure of another.
- Intermediate durable services can allow work to remain available while a consumer is temporarily unavailable.
- Loose coupling reduces the surface area over which a component failure propagates.

#### 1.1.3.4 Temporal Coupling

##### 1.1.3.4.1 Temporally Coupled Interaction
- Components must be available at the same time for an interaction to complete.
- Synchronous request/response commonly creates this dependency.
- The caller waits for the dependency to respond.
- Failure or latency of the dependency directly affects the caller.

##### 1.1.3.4.2 Temporal Decoupling
- Components do not need to be available or processing at exactly the same time.
- Asynchronous communication can place an intermediary between producer and consumer.
- The producer can continue processing without waiting for the consumer to finish.
- AWS recommends asynchronous interaction where an immediate response is not required.

#### 1.1.3.5 Mechanisms for Loose Coupling on AWS

##### 1.1.3.5.1 Queues
- Amazon SQS can integrate and decouple distributed components.
- Producers place messages in a queue instead of requiring direct processing by a consumer.
- Consumers retrieve and process messages independently.
- A queue can provide a durable intermediate layer between components.
- Queues are appropriate when components do not require synchronous communication.

##### 1.1.3.5.2 Events
- Amazon EventBridge supports loosely coupled distributed event-driven architectures.
- Event producers can be abstracted from event consumers.
- Producers do not need direct point-to-point integration with every consumer.

##### 1.1.3.5.3 Publish/Subscribe
- Amazon SNS can provide push-based many-to-many messaging.
- Publishers can send to topics and fan out messages to multiple subscriber endpoints.
- Publishers do not need direct knowledge of each subscriber implementation.

##### 1.1.3.5.4 Streaming
- Streaming systems such as Amazon Kinesis can provide an intermediary between producers and consumers.
- Producers and consumers can process at different times and rates within the characteristics of the stream.

##### 1.1.3.5.5 Workflows
- AWS Step Functions can orchestrate distributed application components.
- Workflow orchestration can decouple dependencies by placing coordination logic in the workflow rather than embedding direct dependencies throughout application components.

##### 1.1.3.5.6 Load Balancing
- Load balancers can decouple callers from individual compute instances.
- Callers target the load-balancing endpoint instead of depending on a particular backend instance.

##### 1.1.3.5.7 Microservices and APIs
- Microservices can be built as small independent components communicating through well-defined APIs.
- Loose coupling allows components to be developed, deployed, and scaled more independently.
- AWS identifies shared data as a common source of tight coupling; database-per-service is one pattern for reducing data-layer coupling.

#### 1.1.3.6 Tight vs Loose Coupling

##### 1.1.3.6.1 Change Dependency
- Tightly coupled: changing one component can force changes in dependent components.
- Loosely coupled: consumers primarily depend on a stable published contract rather than internal implementation.

##### 1.1.3.6.2 Availability Dependency
- Tightly coupled: one component can require another to be immediately available.
- Loosely coupled: asynchronous intermediaries can allow components to operate at different times.

##### 1.1.3.6.3 Failure Propagation
- Tightly coupled: failures and latency can propagate directly through dependencies.
- Loosely coupled: component boundaries and intermediaries help isolate failures.

##### 1.1.3.6.4 Scaling
- Tightly coupled: scaling characteristics of components can influence each other strongly.
- Loosely coupled: components can scale more independently.

##### 1.1.3.6.5 Implementation Knowledge
- Tightly coupled: consumers can depend on implementation details or shared structures.
- Loosely coupled: consumers depend primarily on defined interfaces, contracts, messages, or events.

#### 1.1.3.7 Common Tight-Coupling Anti-Patterns Identified by AWS

##### 1.1.3.7.1 Direct API Dependency Without Resilience
- Directly invoking APIs between workload tiers without failover or asynchronous processing increases dependency between components.

##### 1.1.3.7.2 Shared Data
- Sharing databases or tightly coupled data storage between components can couple their schemas, behavior, and lifecycle.
- Separate components should avoid using a shared data layer when it prevents independent evolution.

##### 1.1.3.7.3 Ignoring Back Pressure
- A producer can overwhelm a slower consumer if the architecture has no mechanism to control or buffer incoming work.
- Decoupling mechanisms can help accommodate different processing rates.

##### 1.1.3.7.4 Chatty Communication
- Requiring many calls to a dependency for one request increases coupling and latency.
- Minimize unnecessary dependency calls.

#### 1.1.3.8 Important Distinctions

##### 1.1.3.8.1 Loose Coupling Does Not Mean No Coupling
- Components still require a contract for interaction.
- The objective is to minimize unnecessary dependency, not eliminate communication.
- Versioned APIs, message schemas, and event contracts are still dependencies that must be managed.

##### 1.1.3.8.2 Asynchronous Does Not Automatically Mean Loosely Coupled
- Asynchronous communication is an important technique for temporal decoupling.
- Components can still be tightly coupled through shared schemas, shared databases, implementation assumptions, or rigid message contracts.
- Overall coupling depends on the complete relationship between components.

##### 1.1.3.8.3 Synchronous Does Not Automatically Mean Bad Architecture
- Some interactions require an immediate response.
- AWS distinguishes synchronous, asynchronous, and batch distributed systems based on workload requirements.
- The goal is to choose the interaction model appropriate to the requirement while controlling failure propagation.
