### 1.1.1 Describe architectural patterns

#### 1.1.1.1 Application Structure

##### 1.1.1.1.1 Monolithic
- Application functionality packaged/run largely as one unit
- Traditionally one process and one data store
- Components are more closely coupled
- Simpler distributed-system concerns
- Growth can make independent change/scaling harder

##### 1.1.1.1.2 Microservices
- Application decomposed into fine-grained services
- Services communicate across a network
- Independent fault domains
- Services can be independently deployed/scaled
- Can use different technologies/data stores
- Trade-off: distributed-system complexity

#### 1.1.1.2 Event-Driven Architecture

##### 1.1.1.2.1 Event-driven
- Something happens → event
- Producers publish events
- Consumers react to events
- Producer doesn't directly control consumers
- Promotes loose coupling
- Commonly asynchronous

#### 1.1.1.3 Coordination

##### 1.1.1.3.1 Choreography
- No central coordinator
- Components react to work/events
- Component performs its own work
- May emit event/task for subsequent work
- Services can operate/scale relatively independently
- Common in event-driven architectures

##### 1.1.1.3.2 Orchestration
- Central orchestrator coordinates workflow
- Determines which services execute
- Controls sequence or parallelism
- Can manipulate intermediate responses
- Centralizes workflow/branching logic
- AWS example: Step Functions

#### 1.1.1.4 Event Distribution

##### 1.1.1.4.1 Fanout
- One published message/event
- Replicated to multiple destinations
- Consumers process independently
- Enables parallel processing
- AWS classic: SNS → multiple SQS queues

##### 1.1.1.4.2 Publish/Subscribe
- Publisher sends to a topic/channel
- Publisher doesn't address individual consumers
- Multiple subscribers can receive the message
- Fanout is a common pub/sub distribution shape

#### 1.1.1.5 Distributed Transaction Pattern

##### 1.1.1.5.1 Saga
- Business transaction spans multiple services
- Each service performs a local transaction
- Failure can require compensating transactions
- Goal: maintain consistency without one ACID transaction

###### 1.1.1.5.1.1 Saga Choreography
- Participants react to events

###### 1.1.1.5.1.2 Saga Orchestration
- Coordinator controls the saga

#### 1.1.1.6 State Through Events

##### 1.1.1.6.1 Event Sourcing
- Persist state-changing events
- Event store is append-only / ordered
- Current state can be reconstructed by replaying events
- Preserves history
- Useful for auditability / point-in-time reconstruction

#### 1.1.1.7 Other AWS-Documented Patterns

##### 1.1.1.7.1 Hexagonal Architecture
- Isolate business logic from external technologies/interfaces

##### 1.1.1.7.2 Scatter-Gather
- Distribute request/work → gather multiple results

##### 1.1.1.7.3 Strangler Fig
- Incrementally replace a monolith
