### 1.3.6 Use, manage, and maintain data stores

#### 1.3.6.1 Exam Context

##### 1.3.6.1.1 Skill Scope
- DVA-C02 Domain 1, Task 3 is **Use data stores in application development**.
- Skill 1.3.6 requires developers to **use, manage, and maintain data stores**.
- Unlike Skills 1.3.1–1.3.5, this wording is deliberately broad and is not restricted to DynamoDB.
- The developer perspective is:
  - connect to the appropriate store,
  - perform correct read/write operations,
  - choose and manage capacity/scaling behavior,
  - protect data,
  - monitor operational behavior,
  - maintain availability and recoverability.
- This is not a database-administrator certification objective. Focus on application-facing AWS-managed data-store operations.

##### 1.3.6.1.2 Core Mental Model
- Treat a data store as an operational dependency with a lifecycle:

  `provision/configure`
  → `connect`
  → `read/write`
  → `scale`
  → `monitor`
  → `protect`
  → `recover`
  → `modify/maintain`

- The application's job is not only to store data.
- It must use the store in a way that matches:
  - access pattern,
  - capacity,
  - consistency,
  - availability,
  - durability,
  - cost,
  - failure behavior.

#### 1.3.6.2 Data-Store Categories in Scope

##### 1.3.6.2.1 Key-Value / NoSQL
- Amazon DynamoDB.
- Developer concerns:
  - tables and indexes,
  - read/write APIs,
  - capacity modes,
  - throttling,
  - transactions,
  - backups,
  - global replication.

##### 1.3.6.2.2 Relational
- Amazon RDS and Amazon Aurora.
- Developer concerns:
  - database endpoints,
  - connections,
  - transactions,
  - read/write routing,
  - connection pooling,
  - replicas,
  - backups/failover.

##### 1.3.6.2.3 Object Storage
- Amazon S3 is also an in-scope persistent store.
- Application concerns include:
  - PUT/GET/DELETE,
  - object keys,
  - versioning,
  - lifecycle,
  - replication.
- Detailed lifecycle behavior belongs mainly to Skill 1.3.7.

##### 1.3.6.2.4 Specialized Stores
- Specialized data stores are addressed explicitly by Skill 1.3.9.
- Do not expand them fully here.

#### 1.3.6.3 Using a Data Store

##### 1.3.6.3.1 Application Interaction
- Applications normally interact with AWS data stores through:
  - AWS SDKs/API operations,
  - database drivers,
  - higher-level persistence libraries.

##### 1.3.6.3.2 Basic Operation Categories
- Create/write.
- Read.
- Update.
- Delete.
- Query/search.
- Batch/transaction operations where supported.

##### 1.3.6.3.3 Correct Abstraction
- AWS SDK:
  - natural for service APIs such as DynamoDB and S3.
- Database driver/protocol:
  - natural for relational engines in RDS/Aurora.
- Higher-level mapping:
  - can reduce serialization/persistence boilerplate.
- Serialization itself belongs to Skill 1.3.5.

#### 1.3.6.4 DynamoDB Data Operations

##### 1.3.6.4.1 Single-Item Operations
- Common DynamoDB APIs include:
  - `GetItem`,
  - `PutItem`,
  - `UpdateItem`,
  - `DeleteItem`.

##### 1.3.6.4.2 Query Operations
- `Query` retrieves items through partition-key and optional sort-key conditions.
- `Scan` reads broadly.
- Their detailed distinction belongs to Skill 1.3.3.

##### 1.3.6.4.3 Conditional Operations
- DynamoDB supports condition expressions.
- A write can be accepted only if the specified condition evaluates successfully.

##### 1.3.6.4.4 Why Conditions Matter
- Conditions can enforce application invariants without a separate read-before-write sequence.
- Typical patterns:
  - create only if item does not exist,
  - update only if a value/version is still expected,
  - delete only when state permits it.

#### 1.3.6.5 Optimistic Concurrency

##### 1.3.6.5.1 Problem
- Two application instances can:
  - read the same item,
  - independently modify it,
  - attempt to write competing changes.

##### 1.3.6.5.2 Pattern
- Store a version/revision value.
- Update only when the persisted version still equals the version originally read.
- Increment the version after a successful update.

##### 1.3.6.5.3 DynamoDB Mechanism
- Conditional writes can implement optimistic concurrency control.
- Some DynamoDB object persistence libraries provide optimistic-locking support.

##### 1.3.6.5.4 Result
- Instead of silently overwriting another writer's update, the stale writer receives a conditional failure and can decide how to react.

#### 1.3.6.6 Batch Operations

##### 1.3.6.6.1 Purpose
- Reduce request overhead when processing multiple independent items.

##### 1.3.6.6.2 DynamoDB APIs
- `BatchGetItem`.
- `BatchWriteItem`.

##### 1.3.6.6.3 BatchWriteItem
- Can contain up to 25 `PutItem` or `DeleteItem` operations in one request.
- It does not support `UpdateItem`.
- It does not support condition expressions for the individual operations.

##### 1.3.6.6.4 Partial Completion
- Batch operations can return unprocessed items.
- Application code must retry the unprocessed portion rather than assuming the whole batch completed.

##### 1.3.6.6.5 Important Distinction
- Batch operation ≠ transaction.
- Batch optimizes grouped operations.
- Transaction provides all-or-nothing semantics.

#### 1.3.6.7 DynamoDB Transactions

##### 1.3.6.7.1 Purpose
- DynamoDB transactions provide ACID semantics for coordinated changes to multiple items.

##### 1.3.6.7.2 APIs
- `TransactWriteItems`.
- `TransactGetItems`.

##### 1.3.6.7.3 Transactional Write
- Can combine actions such as:
  - Put,
  - Update,
  - Delete,
  - ConditionCheck.
- The transaction succeeds or fails as a unit.

##### 1.3.6.7.4 Use Case
- Use when business correctness requires multiple DynamoDB item changes to be atomic.

##### 1.3.6.7.5 Cost/Work
- Transactional operations require additional underlying read/write work compared with equivalent non-transactional operations.
- Do not use transactions when independent operations are sufficient.

#### 1.3.6.8 Batch vs Transaction

##### 1.3.6.8.1 Batch
- Goal:
  - efficiency/throughput.
- Individual operations can be processed independently.
- Partial/unprocessed results are possible.

##### 1.3.6.8.2 Transaction
- Goal:
  - atomic correctness.
- All actions commit or the transaction fails.

##### 1.3.6.8.3 Decision
- "Process many unrelated items efficiently" → batch.
- "All related changes must succeed together" → transaction.

#### 1.3.6.9 DynamoDB Capacity Modes

##### 1.3.6.9.1 Two Modes
- DynamoDB supports:
  - on-demand capacity,
  - provisioned capacity.

##### 1.3.6.9.2 Why Capacity Matters
- Capacity mode determines:
  - how read/write throughput is managed,
  - how the table is billed.

#### 1.3.6.10 On-Demand Capacity

##### 1.3.6.10.1 Model
- DynamoDB automatically accommodates application traffic within service behavior/quotas.
- Applications pay per request rather than explicitly provisioning read/write capacity units.

##### 1.3.6.10.2 Good Fit
- Unknown traffic.
- Variable/unpredictable workloads.
- New applications without reliable capacity history.
- Workloads where operational simplicity is more important than explicitly managing provisioned throughput.

##### 1.3.6.10.3 Developer Mental Model
- On-demand reduces capacity-planning work.
- It does not remove the need for:
  - good partition-key design,
  - monitoring,
  - awareness of throttling/service quotas.

#### 1.3.6.11 Provisioned Capacity

##### 1.3.6.11.1 Model
- Configure read and write capacity for the table.
- Provisioned-mode GSIs also have capacity settings.

##### 1.3.6.11.2 Good Fit
- Predictable workloads.
- Capacity can be planned.
- Cost can be optimized around known utilization.

##### 1.3.6.11.3 Risk
- Provision too little:
  - throttling.
- Provision too much:
  - unnecessary cost.

#### 1.3.6.12 DynamoDB Auto Scaling

##### 1.3.6.12.1 Purpose
- DynamoDB auto scaling adjusts provisioned throughput based on workload.

##### 1.3.6.12.2 Configuration
- Configure:
  - minimum capacity,
  - maximum capacity,
  - target utilization.

##### 1.3.6.12.3 Scope
- Auto scaling can manage:
  - table read capacity,
  - table write capacity,
  - GSI capacity.

##### 1.3.6.12.4 Monitoring
- CloudWatch tracks metrics including:
  - provisioned capacity,
  - consumed capacity,
  - throttled events,
  - latency.

#### 1.3.6.13 Throttling

##### 1.3.6.13.1 Meaning
- A request can be throttled when the workload exceeds available/allowed throughput for the relevant resource or partition.

##### 1.3.6.13.2 Causes
- Insufficient provisioned capacity.
- Traffic concentrated on hot partition-key values.
- Sudden workload growth.
- GSI capacity/distribution bottlenecks.
- Quota/throughput boundaries.

##### 1.3.6.13.3 Application Response
- AWS SDKs provide retry behavior for retryable failures.
- Exponential backoff with jitter is the general resilient approach.
- Do not implement immediate tight retry loops.

##### 1.3.6.13.4 Root Cause
- Retries absorb transient failures.
- They do not fix:
  - permanently insufficient capacity,
  - poor partition-key design,
  - sustained hot-key traffic.

#### 1.3.6.14 Monitoring DynamoDB

##### 1.3.6.14.1 Amazon CloudWatch
- DynamoDB publishes operational metrics to CloudWatch.

##### 1.3.6.14.2 Important Developer Signals
- Consumed vs provisioned capacity.
- Throttled requests/events.
- Request latency.
- Errors.
- Table/index behavior.

##### 1.3.6.14.3 Why
- Application failures can be symptoms of the data store reaching capacity or experiencing skewed access.
- Observability must connect application symptoms to data-store metrics.

#### 1.3.6.15 DynamoDB Backups

##### 1.3.6.15.1 On-Demand Backup
- Creates a full table backup for retention/recovery.
- Managed by DynamoDB.
- Backup creation does not affect production table performance/availability.

##### 1.3.6.15.2 Point-in-Time Recovery
- PITR provides continuous backups.
- Current DynamoDB documentation supports a configurable recovery period from 1 to 35 days.
- Recovery points have per-second granularity.

##### 1.3.6.15.3 Protection Goal
- PITR is particularly useful for recovery from:
  - accidental writes,
  - accidental deletes,
  - application/data corruption within the recovery window.

#### 1.3.6.16 DynamoDB Restore

##### 1.3.6.16.1 New Table
- DynamoDB backup/PITR restore creates a **new table**.
- It does not overwrite the existing table.

##### 1.3.6.16.2 Operational Consequence
- Application cutover/routing to the restored table is a separate operational concern.

##### 1.3.6.16.3 Settings Not Automatically Restored
- AWS documents settings that must be re-established on a restored table, including examples such as:
  - auto scaling policies,
  - IAM policies,
  - CloudWatch alarms,
  - tags,
  - Streams settings,
  - TTL settings,
  - deletion protection,
  - PITR settings.

##### 1.3.6.16.4 Exam Trap
- "Restore DynamoDB backup over the damaged existing table" → wrong mental model.
- Restore produces a separate table.

#### 1.3.6.17 DynamoDB Availability and Durability

##### 1.3.6.17.1 Regional Resilience
- DynamoDB automatically replicates data across multiple Availability Zones within an AWS Region.

##### 1.3.6.17.2 Developer Consequence
- Applications do not build their own intra-Region table replication mechanism for normal DynamoDB durability.

##### 1.3.6.17.3 Multi-Region
- DynamoDB global tables provide multi-Region replication.
- Use when application requirements need data available across Regions.

#### 1.3.6.18 DynamoDB Global Tables

##### 1.3.6.18.1 Purpose
- Replicate DynamoDB table data across AWS Regions.

##### 1.3.6.18.2 Application Uses
- Multi-Region availability.
- Local data access for geographically distributed applications.
- Disaster-recovery architectures.

##### 1.3.6.18.3 Consistency Connection
- Current DynamoDB global tables can use:
  - multi-Region eventual consistency (MREC),
  - multi-Region strong consistency (MRSC), where supported/configured.
- Detailed consistency belongs to Skill 1.3.2.

##### 1.3.6.18.4 Transaction Caveat
- For MREC global tables, DynamoDB transactions are atomic only in the Region where invoked; transaction changes are not replicated to other Regions as one atomic unit.
- MRSC global tables do not support DynamoDB transaction operations.
- Do not assume "global table + transaction" means cross-Region ACID transaction.

#### 1.3.6.19 Relational Data Stores

##### 1.3.6.19.1 Amazon RDS
- Amazon RDS is a managed relational database service.
- AWS handles infrastructure-level tasks such as:
  - hardware provisioning,
  - backups,
  - software patching,
  - monitoring capabilities.

##### 1.3.6.19.2 Amazon Aurora
- Aurora is an AWS relational database engine compatible with MySQL/PostgreSQL ecosystems.
- From the developer perspective, applications use relational connections and SQL while AWS manages significant database infrastructure.

##### 1.3.6.19.3 Application Responsibility
- Managed service does not remove application concerns such as:
  - connection management,
  - transaction boundaries,
  - query efficiency,
  - retry/failover handling,
  - credentials/security.

#### 1.3.6.20 Relational Connections

##### 1.3.6.20.1 Stateful Connections
- Relational databases typically use network database connections.
- Opening/maintaining large numbers of connections consumes database resources.

##### 1.3.6.20.2 Application Pooling
- Connection pools reuse established database connections.
- This reduces repeated:
  - network setup,
  - TLS negotiation,
  - authentication,
  - database connection allocation.

##### 1.3.6.20.3 Serverless Challenge
- Highly concurrent Lambda/serverless workloads can create large bursts of database connections.
- Database connection capacity may become the bottleneck before compute capacity.

#### 1.3.6.21 Amazon RDS Proxy

##### 1.3.6.21.1 Purpose
- RDS Proxy sits between applications and supported RDS/Aurora databases.
- It pools and shares database connections.

##### 1.3.6.21.2 Benefits
- Reduce database CPU/memory overhead from connection management.
- Absorb unpredictable connection surges.
- Reuse/multiplex backend connections.
- Improve application resilience during some database failover scenarios.

##### 1.3.6.21.3 Serverless Fit
- Particularly relevant when many Lambda invocations or distributed application instances could otherwise create excessive direct database connections.

##### 1.3.6.21.4 Security
- RDS Proxy can enforce IAM authentication for client connections.
- It can use IAM database authentication or credentials stored in AWS Secrets Manager to connect to supported databases.

#### 1.3.6.22 RDS/Aurora Endpoints

##### 1.3.6.22.1 Abstraction
- Applications should connect through the AWS-provided database/cluster endpoint rather than hardcoding individual host identities where managed endpoint behavior is intended.

##### 1.3.6.22.2 Writer
- Writer endpoints direct traffic to the writable database instance.

##### 1.3.6.22.3 Reader
- Supported cluster architectures expose reader endpoints for read-only workloads.
- Read traffic can be distributed to reader instances.

##### 1.3.6.22.4 Developer Decision
- Writes → writer.
- Scalable read-only traffic → reader endpoint/read replicas where supported.

#### 1.3.6.23 Read Replicas vs High Availability

##### 1.3.6.23.1 Read Replica
- Primary purpose:
  - scale read workloads.
- Replication to read replicas is generally asynchronous in RDS read-replica patterns.

##### 1.3.6.23.2 Multi-AZ
- Primary purpose:
  - high availability/failover.
- Do not automatically treat every standby as an application read-scaling target.

##### 1.3.6.23.3 Modern RDS Nuance
- RDS Multi-AZ **DB cluster** deployments include readable reader DB instances.
- Therefore the older blanket rule "Multi-AZ standbys cannot serve reads" is not universally correct across all RDS deployment models.

##### 1.3.6.23.4 Exam Mental Model
- Identify the architecture named in the question:
  - classic Multi-AZ DB instance deployment → HA focus,
  - read replica → read scaling,
  - Multi-AZ DB cluster → HA plus readable reader instances.

#### 1.3.6.24 Relational Transactions

##### 1.3.6.24.1 Purpose
- Group related SQL operations into a unit with transactional semantics provided by the database engine.

##### 1.3.6.24.2 Application Responsibility
- Explicitly define:
  - transaction start,
  - commit,
  - rollback
  where the driver/framework does not manage this automatically.

##### 1.3.6.24.3 Failure Handling
- Do not assume a failed multi-statement workflow partially succeeded safely.
- Understand transaction boundaries and retry implications.

#### 1.3.6.25 S3 as a Persistent Store

##### 1.3.6.25.1 Model
- S3 stores data as objects in buckets.
- Applications interact through S3 APIs/SDKs.

##### 1.3.6.25.2 Basic Operations
- Put/upload object.
- Get/download object.
- Delete object.
- List/find by key/prefix semantics where appropriate.

##### 1.3.6.25.3 Management Features
- S3 provides features for:
  - versioning,
  - lifecycle management,
  - replication,
  - access control,
  - storage-class management.

##### 1.3.6.25.4 Scope Connection
- Detailed lifecycle/expiration decisions belong primarily to Skill 1.3.7.

#### 1.3.6.26 S3 Versioning

##### 1.3.6.26.1 Purpose
- Keep multiple versions of an object under the same object key.

##### 1.3.6.26.2 Protection
- Helps recover from:
  - accidental deletion,
  - accidental overwrite,
  - application mistakes.

##### 1.3.6.26.3 Delete Behavior
- In a versioning-enabled bucket, a normal delete typically creates a delete marker rather than immediately destroying previous object versions.

##### 1.3.6.26.4 Maintenance Consequence
- Old versions consume storage.
- Lifecycle rules can manage noncurrent versions.

#### 1.3.6.27 Data Protection Layers

##### 1.3.6.27.1 Availability
- Keep the service usable during infrastructure failures.
- Examples:
  - DynamoDB multi-AZ architecture,
  - RDS Multi-AZ,
  - Aurora architecture.

##### 1.3.6.27.2 Backup
- Preserve recoverable historical copies.
- Examples:
  - DynamoDB on-demand backup/PITR,
  - RDS/Aurora backups/snapshots.

##### 1.3.6.27.3 Versioning
- Preserve previous logical versions of stored data.
- Example:
  - S3 Versioning.

##### 1.3.6.27.4 Replication
- Maintain data in additional locations.
- Examples:
  - DynamoDB global tables,
  - S3 Replication,
  - relational replicas.

##### 1.3.6.27.5 Important Rule
- Availability, backup, versioning, and replication solve different failure modes.
- Replication alone is not necessarily a backup:
  - bad writes/deletes can also replicate.

#### 1.3.6.28 Monitoring and Maintenance Loop

##### 1.3.6.28.1 Observe
- Monitor:
  - latency,
  - errors,
  - throttling,
  - connections,
  - capacity/utilization,
  - storage behavior.

##### 1.3.6.28.2 Diagnose
- Determine whether the problem is:
  - application behavior,
  - access-pattern design,
  - insufficient capacity,
  - hot partitions,
  - connection exhaustion,
  - query inefficiency,
  - service/resource failure.

##### 1.3.6.28.3 Adjust
- Possible actions:
  - change capacity,
  - enable/tune auto scaling,
  - redesign key/index access,
  - use connection pooling/RDS Proxy,
  - add/read-route to replicas,
  - adjust retry behavior,
  - enable recovery/protection features.

##### 1.3.6.28.4 Verify
- Confirm the operational signal improves after the change.
- Maintenance is a feedback loop, not a one-time configuration.

#### 1.3.6.29 Application Failure Model

##### 1.3.6.29.1 Transient Failure
- Retryable network/service/throttling condition.
- Use bounded retries/backoff according to SDK/service guidance.

##### 1.3.6.29.2 Persistent Capacity Problem
- Repeated retries alone worsen pressure.
- Fix capacity/distribution/access pattern.

##### 1.3.6.29.3 Connection Exhaustion
- Common relational concern.
- Reduce churn, pool connections, consider RDS Proxy.

##### 1.3.6.29.4 Data Corruption / Accidental Mutation
- Retry is irrelevant.
- Recovery features such as PITR/versioning/backups are needed.

##### 1.3.6.29.5 Infrastructure Failure
- Use managed HA/failover/replication mechanisms appropriate to the store.

#### 1.3.6.30 Decision Model

##### 1.3.6.30.1 DynamoDB Traffic Unknown
- Consider on-demand capacity.

##### 1.3.6.30.2 DynamoDB Traffic Predictable
- Provisioned capacity + auto scaling can be appropriate.

##### 1.3.6.30.3 DynamoDB Throttling
- Check:
  - consumed/provisioned capacity,
  - partition-key distribution,
  - GSI behavior,
  - retry metrics.

##### 1.3.6.30.4 Multiple DynamoDB Writes Must Be Atomic
- Use transaction APIs.

##### 1.3.6.30.5 Many Independent DynamoDB Writes
- Consider batch operations.
- Retry unprocessed items.

##### 1.3.6.30.6 Need Recovery From Accidental DynamoDB Mutation
- PITR.

##### 1.3.6.30.7 Lambda Causes RDS Connection Storm
- Consider RDS Proxy / controlled connection pooling.

##### 1.3.6.30.8 Relational Read Bottleneck
- Consider reader endpoints/read replicas according to the deployment architecture.

##### 1.3.6.30.9 Need S3 Protection From Overwrite/Delete
- Enable S3 Versioning.
- Consider lifecycle for old versions.

#### 1.3.6.31 Important Distinctions

##### 1.3.6.31.1 Batch vs Transaction
- Batch → throughput efficiency.
- Transaction → atomic correctness.

##### 1.3.6.31.2 On-Demand vs Provisioned
- On-demand → AWS manages capacity scaling for request-driven usage.
- Provisioned → explicit throughput configuration, optionally auto scaled.

##### 1.3.6.31.3 Retry vs Scaling
- Retry handles transient failure.
- Scaling/design fixes sustained insufficient capacity.

##### 1.3.6.31.4 Backup vs Replication
- Backup → historical recovery.
- Replication → additional current copies/availability.

##### 1.3.6.31.5 Multi-AZ vs Read Replica
- HA and read scaling are different goals.
- Read behavior depends on the exact RDS deployment type.

##### 1.3.6.31.6 Serialization vs Store Operation
- Serialization converts representation.
- Store APIs persist/read that representation.
- Serialization belongs to Skill 1.3.5.

##### 1.3.6.31.7 Data Lifecycle vs Maintenance
- Maintenance keeps the store operational and recoverable.
- Lifecycle focuses on retention, transition, expiration, and deletion policy and belongs to Skill 1.3.7.

#### 1.3.6.32 Common Exam Traps

##### 1.3.6.32.1 "BatchWriteItem Is Atomic"
- False.
- Use DynamoDB transactions when all-or-nothing semantics are required.

##### 1.3.6.32.2 "BatchWriteItem Supports UpdateItem"
- False.
- BatchWriteItem supports Put and Delete operations.

##### 1.3.6.32.3 "Retry the Entire Batch Blindly"
- Wrong.
- Handle and retry returned unprocessed items.

##### 1.3.6.32.4 "On-Demand Fixes Hot Keys"
- False.
- Poor partition-key distribution remains an architectural problem.

##### 1.3.6.32.5 "PITR Restores Over Existing DynamoDB Table"
- False.
- Restore creates a new table.

##### 1.3.6.32.6 "Replication Is Backup"
- False as a general assumption.
- Replication can propagate unwanted mutations.

##### 1.3.6.32.7 "Lambda Can Open Unlimited RDS Connections"
- False.
- Database connection capacity is finite; RDS Proxy can help pool/multiplex connections.

##### 1.3.6.32.8 "Every Multi-AZ RDS Standby Is a Read Replica"
- False.
- Readability depends on the deployment model.

##### 1.3.6.32.9 "Managed Database Means Application Has No Operational Responsibility"
- False.
- AWS manages infrastructure responsibilities, while developers still own correct access, connection, transaction, capacity, resilience, and recovery behavior at the application boundary.
