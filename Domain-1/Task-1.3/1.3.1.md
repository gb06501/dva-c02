### 1.3.1 Describe high-cardinality partition keys for balanced partition access

#### 1.3.1.1 Exam Context

##### 1.3.1.1.1 Skill Scope
- DVA-C02 Domain 1, Task 3 is **Use data stores in application development**.
- Skill 1.3.1 requires describing high-cardinality partition keys for balanced partition access.
- The primary in-scope service for this skill is Amazon DynamoDB.
- The skill is about how partition-key choice affects data distribution, throughput utilization, and throttling.

##### 1.3.1.1.2 Core Mental Model
- DynamoDB uses the partition-key value as input to an internal hash function.
- The resulting hash determines where the item is stored.
- Therefore partition-key design determines how data and request traffic are distributed across DynamoDB partitions.
- Good design aims for:
  - many distinct partition-key values,
  - reasonably even request activity across those values,
  - avoidance of a small number of disproportionately hot keys.

#### 1.3.1.2 Partition Key

##### 1.3.1.2.1 Simple Primary Key
- A DynamoDB table can use a simple primary key consisting only of a partition key.
- Each partition-key value must uniquely identify one item.

##### 1.3.1.2.2 Composite Primary Key
- A table can use:
  - partition key,
  - plus sort key.
- Multiple items can share the same partition-key value as long as their sort-key values differ.
- All items with the same partition-key value form an item collection.

##### 1.3.1.2.3 Physical Placement
- DynamoDB hashes the partition-key value.
- The hash result determines the physical partition where the item is stored.
- The sort key does not determine physical partition placement.

#### 1.3.1.3 Cardinality

##### 1.3.1.3.1 Definition
- Cardinality describes how many distinct values an attribute can have.
- High-cardinality attributes have many distinct values.
- Low-cardinality attributes have only a small set of possible values.

##### 1.3.1.3.2 High-Cardinality Examples
- User ID.
- Customer ID.
- Order ID.
- Device ID.
- Session ID.
- Account ID when there are many accounts with reasonably distributed traffic.

##### 1.3.1.3.3 Low-Cardinality Examples
- Status such as `ACTIVE`, `INACTIVE`.
- Boolean values.
- Country when only a small set dominates traffic.
- Date/hour bucket when all writes for a period share one value.

#### 1.3.1.4 Why High Cardinality Matters

##### 1.3.1.4.1 Data Distribution
- More distinct partition-key values give DynamoDB more key space over which to distribute items.
- AWS recommends choosing partition keys with a large number of distinct values relative to the number of items in the table.

##### 1.3.1.4.2 Request Distribution
- Balanced performance depends not only on stored data distribution but also on which partition-key values are actively accessed.
- A table can contain many keys but still be imbalanced if nearly all requests target only a few of them.

##### 1.3.1.4.3 Throughput Utilization
- Requests spread across many partition-key values can use DynamoDB's distributed throughput more effectively.
- Requests concentrated on a small number of key values can overload individual partitions even when the overall table still has unused capacity elsewhere.

#### 1.3.1.5 Hot Partitions

##### 1.3.1.5.1 Hot Partition
- A hot partition receives disproportionately high read or write traffic.
- Hot partitions can cause throttling and inefficient use of available table capacity.

##### 1.3.1.5.2 Common Causes
- Low-cardinality partition key.
- One highly popular key value.
- Time-based key such as current date/hour where all current writes target the same logical key.
- Sequential ingestion pattern that repeatedly writes one partition-key value before moving to another.

##### 1.3.1.5.3 Important Distinction
- High cardinality alone does not guarantee balanced access.
- Example:
  - millions of device IDs exist,
  - but 80% of traffic targets one device.
- The key space is high-cardinality, but the access pattern is still hot.

#### 1.3.1.6 AWS Capacity Boundary

##### 1.3.1.6.1 Per-Partition Capacity
- Current AWS documentation states that each DynamoDB partition is designed to support up to:
  - 3,000 read units per second,
  - 1,000 write units per second.
- A hot key can become constrained by partition-level limits even when aggregate table capacity is higher.

##### 1.3.1.6.2 Implication
- Increasing total table capacity does not automatically solve a workload concentrated on one partition key.
- Better partition-key distribution can be required.

##### 1.3.1.6.3 Current-Service Fact
- Treat these numeric limits as current AWS service values.
- Verify current AWS documentation because limits and capacity behavior can evolve.

#### 1.3.1.7 Uniform Access

##### 1.3.1.7.1 AWS Recommendation
- AWS recommends designing for uniform activity across partition keys in the table and its secondary indexes.

##### 1.3.1.7.2 Practical Meaning
- Not every key must receive exactly the same traffic.
- The objective is to avoid a workload where a small number of keys dominate read/write activity.

##### 1.3.1.7.3 Access Ratio
- AWS notes that throughput efficiency generally improves as more distinct partition-key values are actively accessed relative to the total key space.

#### 1.3.1.8 Good vs Bad Partition-Key Examples

##### 1.3.1.8.1 User ID
- Usually good when:
  - there are many users,
  - traffic is reasonably distributed among them.

##### 1.3.1.8.2 Device ID
- Good when:
  - there are many devices,
  - each produces roughly similar traffic.
- Bad when:
  - one device produces most requests.

##### 1.3.1.8.3 Status
- Usually poor.
- Only a few possible values.
- Large numbers of items/requests concentrate under the same keys.

##### 1.3.1.8.4 Date/Hour
- Often poor for write-heavy ingestion.
- All current events can target the same time-bucket key.
- Older buckets receive little or no traffic while the newest key becomes hot.

#### 1.3.1.9 Write Sharding

##### 1.3.1.9.1 Purpose
- Write sharding expands a low-cardinality or hot partition-key space.
- Multiple logical partition-key values are created for what would otherwise be one hot key.

##### 1.3.1.9.2 Random Suffix
- Add a random shard number to the partition key.
- Example:
  - `2026-08-25#17`
  instead of only
  - `2026-08-25`.
- Writes are distributed among multiple logical keys.

##### 1.3.1.9.3 Calculated Suffix
- Calculate the shard value deterministically from another attribute.
- This can preserve the ability to determine which shard contains a particular item.

##### 1.3.1.9.4 Trade-Off
- Sharding improves write distribution.
- Queries may need to read multiple shards and combine results.
- Do not shard unless required by the access pattern because it adds application complexity.

#### 1.3.1.10 Sequential Data Ingestion

##### 1.3.1.10.1 Problem
- Even with many partition-key values, processing all items for one key before moving to the next can concentrate writes temporarily.
- AWS specifically documents this as an inefficient bulk-upload pattern.

##### 1.3.1.10.2 Better Pattern
- Interleave writes across different partition-key values.
- Example:
  - write one item for user A,
  - then user B,
  - then user C,
  - then continue their next items.
- This keeps more DynamoDB partitions active simultaneously.

#### 1.3.1.11 Adaptive Capacity

##### 1.3.1.11.1 Purpose
- DynamoDB adaptive capacity helps handle uneven workloads automatically.
- It can increase effective capacity available to hotter partitions when table capacity and partition limits permit.

##### 1.3.1.11.2 Important Boundary
- Adaptive capacity does not make partition-key design irrelevant.
- AWS still recommends high-cardinality, well-distributed partition keys.
- A single hot key can still reach per-partition limits.

##### 1.3.1.11.3 Exam Rule
- Think of adaptive capacity as help for imperfect real-world distributions.
- Do not use it as justification for intentionally poor low-cardinality key design.

#### 1.3.1.12 Global Secondary Indexes

##### 1.3.1.12.1 Separate Partition-Key Design
- A GSI has its own partition key and optional sort key.
- The GSI's partition-key design determines distribution within the index independently of the base table's primary-key design.

##### 1.3.1.12.2 Hot GSI
- A well-designed base table can still have a poorly distributed GSI.
- Example:
  - base table partition key = high-cardinality customer ID,
  - GSI partition key = low-cardinality status.
- If most items have `status=ACTIVE`, the GSI can become hot.

##### 1.3.1.12.3 Mitigation
- Use higher-cardinality index keys.
- Combine low-cardinality values with a higher-cardinality component where the access pattern allows it.
- Apply write sharding where appropriate.

#### 1.3.1.13 Access Pattern First

##### 1.3.1.13.1 DynamoDB Design Principle
- Choose keys from known application access patterns.
- A theoretically high-cardinality key is not useful if the application cannot query data efficiently through that key.

##### 1.3.1.13.2 Balance
- A good partition key must satisfy both:
  - distribution requirements,
  - application access requirements.

##### 1.3.1.13.3 Exam Mindset
- First ask:
  - what requests will the application make?
- Then ask:
  - will those requests spread across many partition-key values?
- Do not choose keys only from schema aesthetics.

#### 1.3.1.14 Partition Key vs Sort Key

##### 1.3.1.14.1 Partition Key
- Determines physical partition placement through hashing.
- Primary mechanism for distributing data and traffic.

##### 1.3.1.14.2 Sort Key
- Orders items with the same partition-key value.
- Enables range queries and hierarchical/item-collection patterns.
- Does not independently distribute those items across physical partitions.

##### 1.3.1.14.3 Exam Trap
- Adding a high-cardinality sort key does not fix a low-cardinality partition key.
- If every item uses `status=ACTIVE` as partition key and unique IDs as sort keys, the logical access concentration remains under the `ACTIVE` partition-key value.

#### 1.3.1.15 Composite-Key Design

##### 1.3.1.15.1 Goal
- Composite values can be used to increase useful partition-key cardinality.
- Example:
  - `tenantId#userId`,
  - `status#customerId`,
  depending on required access patterns.

##### 1.3.1.15.2 Requirement
- The resulting key must still support required application queries.
- Higher cardinality that breaks required access patterns is not a good design.

#### 1.3.1.16 Multi-Tenant Considerations

##### 1.3.1.16.1 Tenant ID Alone
- Tenant ID can be high-cardinality across the platform.
- It can still become hot if one large tenant produces a disproportionate share of traffic.

##### 1.3.1.16.2 Composite Tenant Key
- A large tenant can sometimes be distributed using a key such as:
  - `tenantId#entityId`
  or another domain-appropriate subdivision.

##### 1.3.1.16.3 Boundary
- Detailed multi-tenant data-access patterns belong to later security/data-access skills.
- Here the point is that high overall tenant count does not guarantee balanced traffic.

#### 1.3.1.17 Partition-Key Decision Model

##### 1.3.1.17.1 Many Distinct Values + Even Traffic
- Good candidate.
- Example: broadly active user IDs.

##### 1.3.1.17.2 Few Distinct Values
- Poor candidate for high-volume workloads.
- Example: boolean or status code.

##### 1.3.1.17.3 Many Values but One Dominates
- Still a hot-key risk.
- Redesign or shard the dominant access path.

##### 1.3.1.17.4 Time-Based Write Key
- Likely hot for current writes.
- Consider adding a shard component.

##### 1.3.1.17.5 GSI Uses Low-Cardinality Key
- GSI can throttle independently.
- Redesign the GSI key or shard it.

##### 1.3.1.17.6 Bulk Upload
- Distribute writes across partition-key values rather than uploading one logical key at a time.

#### 1.3.1.18 Important Distinctions

##### 1.3.1.18.1 High Cardinality vs Uniform Traffic
- High cardinality = many distinct values.
- Uniform traffic = workload distributed reasonably across those values.
- Both matter.

##### 1.3.1.18.2 Logical Partition Key vs Physical Partition
- Application supplies a partition-key value.
- DynamoDB hashes it and maps data to physical partitions.
- They are related concepts but not the same thing.

##### 1.3.1.18.3 Partition Key vs Sort Key
- Partition key controls distribution.
- Sort key controls ordering within a partition-key item collection.

##### 1.3.1.18.4 Table Capacity vs Partition Capacity
- Overall table capacity can be available while one hot partition throttles.
- Balanced key access matters even with adequate aggregate capacity.

##### 1.3.1.18.5 Adaptive Capacity vs Good Key Design
- Adaptive capacity mitigates imbalance.
- It does not eliminate the need for sound partition-key design.

##### 1.3.1.18.6 Base Table vs GSI
- Base table and each GSI have their own partition-key distribution behavior.
- Evaluate hot-key risk separately for every index.
