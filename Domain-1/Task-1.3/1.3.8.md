### 1.3.8 Use data caching services

#### 1.3.8.1 Exam Context

##### 1.3.8.1.1 Skill Scope
- DVA-C02 Domain 1, Task 3 is **Use data stores in application development**.
- Skill 1.3.8 requires developers to **use data caching services**.
- This skill follows data-store access and lifecycle skills because caching is an optimization layer around authoritative data, not a replacement for understanding the underlying store.
- The primary AWS caching technologies relevant to this skill are:
  - Amazon ElastiCache,
  - DynamoDB Accelerator (DAX).
- Other AWS services also cache data in specific layers, but this skill should stay centered on **data caching** rather than CDN/API caching.

##### 1.3.8.1.2 Core Mental Model
- Without cache:

  `application → data store`

- With cache:

  `application → cache → data store`

- Desired behavior:

  `frequent/repeated read`
  → `cache hit`
  → `fast in-memory response`
  → `avoid backend read`

- Cache miss:

  `cache miss`
  → `read authoritative store`
  → `populate cache`
  → `return result`

##### 1.3.8.1.3 Why Cache
- Reduce read latency.
- Reduce repeated work against the underlying data store.
- Reduce load on databases.
- Absorb read-heavy traffic.
- Improve scalability for frequently reused data.
- Potentially reduce backend read cost.

##### 1.3.8.1.4 Fundamental Trade-Off
- A cache creates another representation of data.
- Therefore the central problem becomes:

  **performance vs freshness/consistency**

#### 1.3.8.2 Cache Terminology

##### 1.3.8.2.1 Cache Hit
- Requested data exists in cache and is usable.
- Application can return it without reading the authoritative store.

##### 1.3.8.2.2 Cache Miss
- Requested data is absent or expired.
- Application must retrieve it from the underlying source.

##### 1.3.8.2.3 Hit Rate
- Proportion of requests served from cache.
- Higher useful hit rates generally mean more backend work is avoided.

##### 1.3.8.2.4 Eviction
- Cache removes entries to:
  - reclaim memory,
  - honor expiration,
  - follow eviction policy.

##### 1.3.8.2.5 TTL
- Time to live defines how long a cached entry remains valid before expiration.

#### 1.3.8.3 Cache Is Not the Source of Truth

##### 1.3.8.3.1 Authoritative Store
- Normally the persistent data store remains the system of record.
- Examples:
  - DynamoDB,
  - RDS/Aurora.

##### 1.3.8.3.2 Cache
- Holds a temporary copy or derived result optimized for access speed.

##### 1.3.8.3.3 Failure Model
- Applications should generally be designed so cache loss does not imply loss of authoritative business data.

##### 1.3.8.3.4 Exam Mindset
- "Need lower read latency / reduce database load" → cache may help.
- "Need durable authoritative persistence" → cache alone is usually not the answer.

#### 1.3.8.4 Cache-Aside / Lazy Loading

##### 1.3.8.4.1 Pattern
- Application first asks the cache.
- If hit:
  - return cached value.
- If miss:
  - read database,
  - write result into cache,
  - return result.

##### 1.3.8.4.2 Flow

  `GET key`
  → `cache?`
  → hit → `return`

  miss
  → `database read`
  → `cache SET`
  → `return`

##### 1.3.8.4.3 Benefit
- Only data actually requested is cached.
- Avoids filling cache with data nobody reads.

##### 1.3.8.4.4 Trade-Off
- First request after a miss is slower.
- Cached values can become stale when the underlying database changes.

#### 1.3.8.5 Lazy Loading Failure Behavior

##### 1.3.8.5.1 Empty Cache
- New/restarted cache does not break correctness if the authoritative store is available.
- Requests simply miss and repopulate cache.

##### 1.3.8.5.2 Read Penalty
- A miss involves:
  - cache lookup,
  - database read,
  - cache write.

##### 1.3.8.5.3 Staleness
- If database data changes while an old cached copy remains, readers can receive stale data.

##### 1.3.8.5.4 Mitigation
- Combine lazy loading with:
  - TTL,
  - explicit invalidation,
  - write-through/update logic where appropriate.

#### 1.3.8.6 Write-Through Caching

##### 1.3.8.6.1 Pattern
- When application writes authoritative data, it also updates the cache.

##### 1.3.8.6.2 Flow

  `application write`
  → `database`
  + `cache update`

##### 1.3.8.6.3 Benefit
- Cached values stay fresher after application writes.
- Subsequent reads are more likely to hit current cached data.

##### 1.3.8.6.4 Trade-Off
- Every write performs additional cache work.
- Data that is written but never read can unnecessarily consume cache memory.
- Write path can have additional latency/complexity.

#### 1.3.8.7 Lazy Loading + Write-Through + TTL

##### 1.3.8.7.1 Combined Pattern
- Lazy loading:
  - cache only requested data.
- Write-through:
  - refresh cached data when application updates it.
- TTL:
  - eventually remove old/unused entries.

##### 1.3.8.7.2 Why Combine
- AWS documents these strategies as complementary:
  - lazy loading prevents unnecessary initial population,
  - write-through reduces staleness,
  - TTL limits cache clutter and bounds stale-data lifetime.

##### 1.3.8.7.3 Mental Model
- There is no universally best caching strategy.
- Choose based on:
  - read/write ratio,
  - freshness requirement,
  - miss penalty,
  - memory pressure,
  - failure behavior.

#### 1.3.8.8 Cache TTL

##### 1.3.8.8.1 Purpose
- Expire cache entries after a defined interval.

##### 1.3.8.8.2 Short TTL
- Fresher data.
- More cache misses.
- More backend reads.

##### 1.3.8.8.3 Long TTL
- Higher chance of cache hits.
- Lower backend load.
- Greater chance/duration of stale data.

##### 1.3.8.8.4 Decision
- TTL should reflect how long the application can tolerate cached data being stale.

#### 1.3.8.9 Cache TTL vs Data Lifecycle TTL

##### 1.3.8.9.1 Cache TTL
- Removes a temporary cached copy.
- Authoritative data remains in the persistent store.

##### 1.3.8.9.2 DynamoDB TTL
- Removes the authoritative DynamoDB item itself after expiration.

##### 1.3.8.9.3 Key Distinction
- Same term — TTL — different purpose.

##### 1.3.8.9.4 Connection
- Persistent-data lifecycle TTL belongs to Skill 1.3.7.
- Cache TTL belongs here.

#### 1.3.8.10 Cache Invalidation

##### 1.3.8.10.1 Problem
- Cached data can become inconsistent with its source.

##### 1.3.8.10.2 Approaches
- TTL expiration.
- Explicit delete/invalidation after source update.
- Write-through cache update.
- Versioned cache keys in some application designs.

##### 1.3.8.10.3 Principle
- Every caching design needs an answer to:

  **When the source changes, how does the cache stop serving the old value?**

#### 1.3.8.11 Amazon ElastiCache

##### 1.3.8.11.1 Purpose
- Amazon ElastiCache provides managed in-memory caching/data-store capabilities.

##### 1.3.8.11.2 Supported Engines
- Current ElastiCache supports:
  - Valkey,
  - Redis OSS,
  - Memcached.

##### 1.3.8.11.3 Typical Developer Use
- Cache frequently accessed application/database data.
- Store temporary/session-like data where appropriate.
- Reduce database read pressure.
- Support low-latency access patterns.

##### 1.3.8.11.4 Architecture
- Application explicitly interacts with ElastiCache.
- Application normally owns the caching strategy and cache-key design.

#### 1.3.8.12 ElastiCache Serverless vs Node-Based

##### 1.3.8.12.1 Serverless
- AWS manages cache capacity automatically.
- Useful when developers want reduced capacity-management work and elastic scaling.

##### 1.3.8.12.2 Node-Based
- Developer chooses cluster/node topology and capacity.
- Provides more explicit infrastructure sizing/control.

##### 1.3.8.12.3 Exam Mindset
- Do not assume "ElastiCache" always means manually sized nodes.
- Current AWS offers serverless cache options as well as node-based deployments.

#### 1.3.8.13 Valkey / Redis OSS

##### 1.3.8.13.1 Model
- In-memory key-value/data-structure engine.

##### 1.3.8.13.2 Capabilities
- Supports richer data structures than simple opaque values.
- Common structures include concepts such as:
  - strings,
  - hashes,
  - lists,
  - sets,
  - sorted sets.

##### 1.3.8.13.3 Typical Uses
- Application caching.
- Session data.
- Counters.
- Leaderboards.
- Frequently accessed derived data.
- Other low-latency data-structure patterns.

##### 1.3.8.13.4 AWS Direction
- Valkey is the current open-source engine AWS prominently supports alongside Redis OSS compatibility.

#### 1.3.8.14 Memcached

##### 1.3.8.14.1 Model
- Distributed in-memory object caching system.

##### 1.3.8.14.2 Strength
- Simple caching model.
- Horizontal distribution across cache nodes.

##### 1.3.8.14.3 Typical Use
- Straightforward cache-aside patterns where application data can be represented by cache keys and values.

##### 1.3.8.14.4 Strategy
- AWS documentation explicitly describes:
  - lazy loading,
  - write-through,
  - TTL
  for Memcached caching designs.

#### 1.3.8.15 ElastiCache Cache Keys

##### 1.3.8.15.1 Purpose
- Cache key identifies the cached representation.

##### 1.3.8.15.2 Good Key
- Deterministically represents the underlying request/data.

##### 1.3.8.15.3 Example
- `customer:123`
- `product:ABC`
- `orders:customer:123:page:1`

##### 1.3.8.15.4 Query Results
- If caching query results, the key must include every request parameter that changes the result.
- Otherwise different requests can incorrectly share one cached response.

#### 1.3.8.16 What Should Be Cached?

##### 1.3.8.16.1 Good Candidates
- Frequently requested data.
- Expensive database queries.
- Expensive computed/derived results.
- Data where some staleness is acceptable.
- Read-heavy data.

##### 1.3.8.16.2 Poor Candidates
- Data rarely read more than once.
- Highly volatile data requiring immediate consistency.
- Very large values with poor reuse.
- Sensitive data where cache handling/security requirements are not satisfied.
- Data where a cache miss cannot safely fall back to an authoritative source.

#### 1.3.8.17 Cache Hit Ratio

##### 1.3.8.17.1 Meaning
- Measures how often requests are served from cache.

##### 1.3.8.17.2 High Hit Ratio
- More backend requests avoided.
- Caching is likely providing useful acceleration.

##### 1.3.8.17.3 Low Hit Ratio
- Cache may be:
  - too small,
  - using poor keys,
  - using TTLs that are too short,
  - caching low-reuse data,
  - serving a workload unsuitable for caching.

##### 1.3.8.17.4 DAX Relevance
- AWS specifically notes that DAX performs best for workloads with high cache hit rates and repeated reads.

#### 1.3.8.18 Cache Eviction

##### 1.3.8.18.1 Why
- Cache memory is finite.

##### 1.3.8.18.2 Causes
- Entry TTL expires.
- Cache reaches memory limits.
- Eviction policy removes entries to make room.

##### 1.3.8.18.3 Application Requirement
- Application correctness should not depend on a particular cache entry remaining present forever.

#### 1.3.8.19 Cache Stampede / Thundering Herd

##### 1.3.8.19.1 Problem
- A popular cache entry expires.
- Many requests miss simultaneously.
- All requests query the backend.
- Backend experiences a sudden load spike.

##### 1.3.8.19.2 Mitigation Concepts
- TTL jitter.
- Request coalescing/locking.
- Refresh before hard expiration.
- Controlled fallback/retry.

##### 1.3.8.19.3 Exam Boundary
- Understand the failure pattern.
- Detailed distributed-lock algorithms are beyond this skill.

#### 1.3.8.20 DynamoDB Accelerator (DAX)

##### 1.3.8.20.1 Purpose
- DAX is a managed in-memory cache designed specifically for DynamoDB.

##### 1.3.8.20.2 Performance Goal
- DynamoDB normally provides single-digit-millisecond response times.
- DAX targets microsecond response times for suitable eventually consistent read workloads.

##### 1.3.8.20.3 Compatibility
- DAX provides a DynamoDB-compatible API model through the DAX client.
- This reduces application complexity compared with building a generic external cache around DynamoDB.

##### 1.3.8.20.4 Best Fit
- Read-heavy DynamoDB workloads.
- Repeated reads.
- Eventually consistent data is acceptable.
- Microsecond read latency is useful.
- Need to offload repeated reads from DynamoDB.

#### 1.3.8.21 DAX Read Flow

##### 1.3.8.21.1 Eventually Consistent Read
- DAX checks cache first.

##### 1.3.8.21.2 Cache Hit
- Return cached data without accessing DynamoDB.

##### 1.3.8.21.3 Cache Miss
- DAX sends request to DynamoDB.
- DynamoDB returns result.
- DAX caches it.
- DAX returns it to application.

##### 1.3.8.21.4 Read-Through Behavior
- Application does not manually implement the normal cache-miss/population sequence for supported DynamoDB operations.

#### 1.3.8.22 DAX Item Cache

##### 1.3.8.22.1 Operations
- Item cache stores results for:
  - `GetItem`,
  - `BatchGetItem`.

##### 1.3.8.22.2 Keying
- Items are cached by primary-key values.

##### 1.3.8.22.3 Eviction
- Entries are subject to:
  - configured TTL,
  - least-recently-used behavior when cache space is needed.

#### 1.3.8.23 DAX Query Cache

##### 1.3.8.23.1 Operations
- Query cache stores result sets from:
  - `Query`,
  - `Scan`.

##### 1.3.8.23.2 Keying
- Result sets are cached based on request parameter values.

##### 1.3.8.23.3 Important Difference
- Query cache is independent from the item cache.

##### 1.3.8.23.4 Staleness Consequence
- Updating an individual item does not automatically invalidate previously cached Query/Scan result sets.
- Query-cache freshness therefore depends heavily on query-cache TTL.

#### 1.3.8.24 DAX Write-Through

##### 1.3.8.24.1 Behavior
- Writes made through the DAX client are passed synchronously to DynamoDB.
- After DynamoDB confirms success, DAX updates its item cache.

##### 1.3.8.24.2 Supported Write Operations
- Includes:
  - `PutItem`,
  - `UpdateItem`,
  - `DeleteItem`,
  - `BatchWriteItem`,
  - `TransactWriteItems`.

##### 1.3.8.24.3 Benefit
- Application does not manually maintain DAX item-cache consistency for writes sent through DAX.

##### 1.3.8.24.4 Failure
- If DynamoDB write fails, DAX does not cache the failed write.

#### 1.3.8.25 DAX Write-Around

##### 1.3.8.25.1 Pattern
- Application writes directly to DynamoDB rather than through DAX.

##### 1.3.8.25.2 Why
- Can reduce write latency by avoiding an extra DAX network hop.
- Can avoid polluting cache during bulk/write-heavy workloads where much written data will never be read.

##### 1.3.8.25.3 Trade-Off
- DAX is not automatically informed about direct DynamoDB writes.
- Existing cached items can therefore remain stale until:
  - TTL expiration,
  - eviction,
  - later write-through update.

#### 1.3.8.26 DAX and Strongly Consistent Reads

##### 1.3.8.26.1 Requirement
- Strongly consistent reads cannot be served directly from DAX cache.

##### 1.3.8.26.2 Behavior
- When `ConsistentRead=true` is requested:
  - DAX passes the read through to DynamoDB,
  - returns DynamoDB's result,
  - does not cache that result.

##### 1.3.8.26.3 Transactional Reads
- DAX similarly passes `TransactGetItems` to DynamoDB rather than serving it from cache.

##### 1.3.8.26.4 Exam Rule
- Need strong consistency → DAX does not accelerate that read from cache.

#### 1.3.8.27 DAX Consistency

##### 1.3.8.27.1 Eventually Consistent Model
- DAX cached reads are designed around eventually consistent DynamoDB reads.

##### 1.3.8.27.2 Cluster Replication
- Updates are replicated among DAX nodes asynchronously/eventually consistently.

##### 1.3.8.27.3 Application Requirement
- Applications using DAX should tolerate eventual consistency.

##### 1.3.8.27.4 Connection
- Database consistency models belong to Skill 1.3.2.
- Here consistency determines whether caching is appropriate.

#### 1.3.8.28 DAX Negative Caching

##### 1.3.8.28.1 Meaning
- If DynamoDB returns no matching item/result after a DAX cache miss, DAX can cache that negative/empty result.

##### 1.3.8.28.2 Benefit
- Repeated requests for nonexistent data do not repeatedly hit DynamoDB.

##### 1.3.8.28.3 Risk
- If the item is subsequently created directly in DynamoDB, DAX can continue returning the cached negative result until its cache state changes/expires.

##### 1.3.8.28.4 Mitigation
- Use appropriate TTL.
- If application semantics require it, bypass/check DynamoDB when DAX returns an empty result.

#### 1.3.8.29 DAX High Availability

##### 1.3.8.29.1 Cluster
- DAX uses a cluster of nodes.

##### 1.3.8.29.2 AWS Recommendation
- For high availability, AWS recommends at least three DAX nodes distributed across multiple Availability Zones.

##### 1.3.8.29.3 Client
- DAX client uses the cluster endpoint and performs routing/load balancing across nodes.

#### 1.3.8.30 DAX vs ElastiCache

##### 1.3.8.30.1 DAX
- DynamoDB-specific.
- DynamoDB-compatible API.
- Managed read-through/write-through behavior.
- Best for repeated, eventually consistent DynamoDB reads.
- Minimal custom caching logic for supported DynamoDB access.

##### 1.3.8.30.2 ElastiCache
- General-purpose in-memory cache/data store.
- Works with many backend types and application patterns.
- Application owns:
  - cache keys,
  - lookup strategy,
  - invalidation,
  - population logic.

##### 1.3.8.30.3 Decision
- DynamoDB + microsecond repeated eventually consistent reads + minimal cache-code changes → consider DAX.
- General application/database caching or richer cache-specific data structures → consider ElastiCache.

#### 1.3.8.31 DAX vs DynamoDB Direct

##### 1.3.8.31.1 DynamoDB Direct
- Single-digit-millisecond performance is already sufficient for many applications.
- Supports strong reads on tables/LSIs when requested.
- No DAX cluster cost/operational layer.

##### 1.3.8.31.2 Add DAX When
- Repeated read load is high.
- Microsecond latency matters.
- Eventual consistency is acceptable.
- Cache hit ratio can be high.

##### 1.3.8.31.3 Avoid DAX When
- Strongly consistent reads dominate.
- Workload is write-heavy.
- Reads are rarely repeated.
- DynamoDB's native latency already meets requirements.

#### 1.3.8.32 Caching and Database Load

##### 1.3.8.32.1 Read Offload
- Cache hits prevent equivalent reads from reaching the backend.

##### 1.3.8.32.2 Effect
- Lower backend read traffic can:
  - reduce database load,
  - reduce required capacity,
  - improve resilience under read bursts.

##### 1.3.8.32.3 Limitation
- Cache cannot compensate indefinitely for:
  - inefficient access patterns,
  - incorrect indexes,
  - pathological database queries.
- Fix the data model where the underlying access is fundamentally wrong.

#### 1.3.8.33 Caching and Failure

##### 1.3.8.33.1 Cache Unavailable
- Application may fall back to authoritative data store where architecture permits.

##### 1.3.8.33.2 Backend Unavailable
- Cache may temporarily serve existing cached data in some designs.
- Do not assume this provides complete database failover:
  - uncached data cannot be retrieved,
  - stale data may remain,
  - writes still require authoritative persistence.

##### 1.3.8.33.3 Principle
- Cache improves performance.
- High availability/recovery of the authoritative store remains a separate architectural concern.

#### 1.3.8.34 Monitoring Cache Effectiveness

##### 1.3.8.34.1 Important Signals
- Cache hits.
- Cache misses.
- Hit ratio.
- Evictions.
- Memory/capacity utilization.
- Latency.
- Connection/client behavior.
- Backend read reduction.

##### 1.3.8.34.2 DAX
- DAX publishes operational metrics to Amazon CloudWatch.
- AWS specifically documents metrics such as throttled request counts for cluster health/capacity evaluation.

##### 1.3.8.34.3 Goal
- Do not measure cache success only by "cache is running."
- Measure whether it actually reduces latency/backend work for the intended access pattern.

#### 1.3.8.35 Decision Model

##### 1.3.8.35.1 Expensive Repeated Database Reads
- Cache is a strong candidate.

##### 1.3.8.35.2 Data Rarely Reused
- Cache provides little benefit.

##### 1.3.8.35.3 Freshness Critical
- Short TTL, explicit invalidation, or no cache.
- If DynamoDB strong consistency is required, DAX cache cannot serve that read.

##### 1.3.8.35.4 Read-Heavy DynamoDB + Microsecond Requirement
- DAX.

##### 1.3.8.35.5 General RDS/Aurora/Application Cache
- ElastiCache.

##### 1.3.8.35.6 Only Cache Requested Data
- Lazy loading/cache-aside.

##### 1.3.8.35.7 Keep Cache Updated on Writes
- Write-through.

##### 1.3.8.35.8 Limit Staleness / Remove Unused Entries
- TTL.

##### 1.3.8.35.9 Popular Key Expires and Backend Is Flooded
- Cache stampede.
- Consider jitter/coalescing/controlled refresh.

#### 1.3.8.36 Important Distinctions

##### 1.3.8.36.1 Cache Hit vs Cache Miss
- Hit → cache serves.
- Miss → backend required.

##### 1.3.8.36.2 Lazy Loading vs Write-Through
- Lazy loading → populate on read miss.
- Write-through → update cache during writes.

##### 1.3.8.36.3 Cache TTL vs DynamoDB TTL
- Cache TTL → temporary copy expires.
- DynamoDB TTL → persisted table item becomes eligible for deletion.

##### 1.3.8.36.4 DAX vs ElastiCache
- DAX → DynamoDB-specific transparent-ish acceleration.
- ElastiCache → general-purpose application-managed cache.

##### 1.3.8.36.5 DAX Item Cache vs Query Cache
- Item cache → `GetItem` / `BatchGetItem`.
- Query cache → `Query` / `Scan` result sets.

##### 1.3.8.36.6 DAX Eventual vs Strong Read
- Eventually consistent read → can be served/cached by DAX.
- Strong read → passed through to DynamoDB and not cached.

##### 1.3.8.36.7 Cache vs Read Replica
- Cache → temporary in-memory copies/derived results.
- Read replica → database replica serving database reads.
- They solve overlapping performance problems through different mechanisms.

#### 1.3.8.37 Common Exam Traps

##### 1.3.8.37.1 "Cache Is Durable Source of Truth"
- Wrong mental model.
- Cache normally accelerates access to authoritative persistent data.

##### 1.3.8.37.2 "Long TTL Is Always Better"
- False.
- It improves hit probability but increases stale-data risk.

##### 1.3.8.37.3 "Lazy Loading Keeps Data Fresh"
- False.
- Cached data can become stale after backend updates.

##### 1.3.8.37.4 "Write-Through Caches Only Frequently Read Data"
- False.
- It can cache writes that are never subsequently read.

##### 1.3.8.37.5 "DAX Accelerates Strongly Consistent Reads"
- False.
- Strong reads are passed through to DynamoDB and not cached.

##### 1.3.8.37.6 "DAX Is General-Purpose Redis"
- False.
- DAX is purpose-built for DynamoDB.

##### 1.3.8.37.7 "Direct DynamoDB Write Automatically Updates DAX"
- False.
- Bypassing DAX can leave existing DAX cache entries stale.

##### 1.3.8.37.8 "DAX Item Write Invalidates Query Cache"
- False.
- Item and query caches are independent; query result freshness depends on query-cache TTL.

##### 1.3.8.37.9 "Every Workload Benefits From DAX"
- False.
- AWS explicitly identifies strong-read, write-heavy, and low-repeat-read workloads as poor fits.

##### 1.3.8.37.10 "Cache Miss Is an Error"
- False.
- In cache-aside/read-through designs, miss is normal behavior that causes backend retrieval/population.
