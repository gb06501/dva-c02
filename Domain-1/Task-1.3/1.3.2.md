### 1.3.2 Describe database consistency models

#### 1.3.2.1 Exam Context

##### 1.3.2.1.1 Skill Scope
- DVA-C02 Domain 1, Task 3 is **Use data stores in application development**.
- Skill 1.3.2 requires describing database consistency models.
- The exam guide explicitly gives:
  - strongly consistent,
  - eventually consistent.
- Amazon DynamoDB is the primary in-scope service where the application explicitly chooses between these models for reads.
- Current DynamoDB also supports two global-table consistency modes:
  - Multi-Region Eventual Consistency (MREC),
  - Multi-Region Strong Consistency (MRSC).

##### 1.3.2.1.2 Core Mental Model
- After a successful write, ask:
  - **Must the next read see that latest write?**
- If yes:
  - strong consistency may be required.
- If no:
  - eventual consistency can provide lower read cost and can fit distributed/replicated architectures well.
- Consistency is a correctness requirement, not simply a performance setting.

#### 1.3.2.2 What Consistency Means

##### 1.3.2.2.1 Basic Question
- A database can maintain multiple copies/replicas of data.
- A write must propagate to the relevant copies.
- Consistency defines what a read is allowed to observe while those copies converge.

##### 1.3.2.2.2 Freshness
- Strong consistency prioritizes reading the latest successfully committed value.
- Eventual consistency allows a read to temporarily return an older value after a successful write.

##### 1.3.2.2.3 Convergence
- With eventual consistency, replicas converge over time when updates stop.
- "Eventual" does not mean data is permanently inconsistent.

#### 1.3.2.3 DynamoDB Write Semantics

##### 1.3.2.3.1 Successful Write
- When DynamoDB returns HTTP `200 OK` for a write, the write has completed successfully and has been durably persisted.

##### 1.3.2.3.2 Read-Committed Isolation
- DynamoDB provides read-committed isolation.
- Reads return committed values.
- A read does not expose a value from a write that ultimately failed.

##### 1.3.2.3.3 Important Boundary
- Read-committed isolation does not guarantee that the item cannot change immediately after the read.
- Consistency and transaction/isolation concepts are related but not identical.

#### 1.3.2.4 Eventually Consistent Reads

##### 1.3.2.4.1 DynamoDB Default
- Eventually consistent reads are the default DynamoDB read model.

##### 1.3.2.4.2 Behavior
- A read immediately after a successful write might not return the latest value.
- Repeating the read after a short time should eventually return the newer value.

##### 1.3.2.4.3 Supported Resources
- Eventually consistent reads are supported for:
  - DynamoDB tables,
  - local secondary indexes (LSIs),
  - global secondary indexes (GSIs).
- DynamoDB Streams reads are also eventually consistent.

##### 1.3.2.4.4 Cost
- Eventually consistent reads consume half the read capacity of strongly consistent reads for the same item size.
- For an item up to 4 KB:
  - eventual read → 0.5 RCU,
  - strong read → 1 RCU.

#### 1.3.2.5 Strongly Consistent Reads

##### 1.3.2.5.1 Behavior
- A strongly consistent DynamoDB read returns the most up-to-date data.
- It reflects all prior successful writes before the read.

##### 1.3.2.5.2 API Control
- DynamoDB read operations such as:
  - `GetItem`,
  - `Query`,
  - `Scan`
  support the `ConsistentRead` parameter where strong consistency is supported.
- Set:
  - `ConsistentRead=true`
  to request a strongly consistent read.

##### 1.3.2.5.3 Supported Resources
- Strongly consistent reads are supported on:
  - base tables,
  - local secondary indexes.

##### 1.3.2.5.4 Not Supported
- Strongly consistent reads are not supported on:
  - global secondary indexes,
  - DynamoDB Streams.

#### 1.3.2.6 DynamoDB Default Decision

##### 1.3.2.6.1 Default
- If the application does not request strong consistency, DynamoDB reads are eventually consistent.

##### 1.3.2.6.2 Use Eventual When
- Briefly stale data is acceptable.
- Examples can include:
  - feeds,
  - catalogs,
  - dashboards,
  - non-critical profile/display data,
  depending on business requirements.

##### 1.3.2.6.3 Use Strong When
- The application must immediately observe the latest committed state.
- Examples can include:
  - immediate read-after-write validation,
  - state transitions where stale data could lead to an incorrect decision,
  - workflows requiring the latest current item state.

##### 1.3.2.6.4 Do Not Overuse Strong Reads
- Strong reads cost twice as much read capacity as eventual reads.
- Request strong consistency only when the access pattern actually requires it.

#### 1.3.2.7 Read-After-Write

##### 1.3.2.7.1 Typical Scenario
- Application:
  1. updates an item,
  2. immediately reads it,
  3. expects to see the new value.

##### 1.3.2.7.2 Eventual Read
- The immediate read can return an older value.

##### 1.3.2.7.3 Strong Read
- A supported strongly consistent read returns the latest successfully committed value.

##### 1.3.2.7.4 Alternative Application Design
- Sometimes an application does not need to read the item again immediately because it already knows the value it successfully wrote.
- Avoid unnecessary reads when the application can safely use the write result/local state.
- This is an application-design optimization, not a different consistency model.

#### 1.3.2.8 Local Secondary Index Consistency

##### 1.3.2.8.1 LSI
- An LSI shares the base table's partition key.
- DynamoDB supports both:
  - eventual,
  - strong
  reads from LSIs.

##### 1.3.2.8.2 API
- A Query against an LSI can request `ConsistentRead=true`.

##### 1.3.2.8.3 Exam Rule
- **Table + LSI** → strong consistency is available.

#### 1.3.2.9 Global Secondary Index Consistency

##### 1.3.2.9.1 GSI
- A GSI has its own partition-key structure and is maintained separately from the base table.

##### 1.3.2.9.2 Consistency
- GSI reads are eventually consistent only.
- `ConsistentRead=true` is not supported for GSI reads.

##### 1.3.2.9.3 Exam Rule
- **GSI → eventual only.**
- If the requirement explicitly demands a strongly consistent index read, a GSI does not satisfy that requirement.

#### 1.3.2.10 DynamoDB Streams Consistency

##### 1.3.2.10.1 Stream Reads
- DynamoDB Streams reads are eventually consistent.

##### 1.3.2.10.2 Interpretation
- A stream is intended for change/event processing, not as a strongly consistent query interface to current table state.

##### 1.3.2.10.3 Connection
- Lambda processing of DynamoDB Streams belongs primarily to Skill 1.2.7.

#### 1.3.2.11 Single-Region vs Multi-Region Consistency

##### 1.3.2.11.1 Single-Region Table
- For ordinary DynamoDB tables:
  - eventual reads are default,
  - strong reads are available for tables and LSIs.

##### 1.3.2.11.2 Global Table
- A global table has replicas in multiple AWS Regions.
- Consistency must also be considered across Regions.

##### 1.3.2.11.3 Current DynamoDB Modes
- Current global tables support:
  - Multi-Region Eventual Consistency (MREC),
  - Multi-Region Strong Consistency (MRSC).

#### 1.3.2.12 Multi-Region Eventual Consistency (MREC)

##### 1.3.2.12.1 Default Global-Table Mode
- MREC is the default consistency mode for DynamoDB global tables.

##### 1.3.2.12.2 Replication
- Changes are asynchronously replicated to other Regions.
- AWS states replication is typically within a second or less.

##### 1.3.2.12.3 Cross-Region Read
- A read in another Region can temporarily return stale data before replication arrives.

##### 1.3.2.12.4 Strong Read Caveat
- A strongly consistent read in an MREC replica returns the latest version if the latest update occurred in that Region.
- It can still return stale data when the latest update occurred in another Region and has not yet replicated.

##### 1.3.2.12.5 Conflict Resolution
- Concurrent updates to the same item in different MREC Regions are resolved using last-writer-wins based on DynamoDB's internal timestamps.
- Replicas eventually converge.

#### 1.3.2.13 Multi-Region Strong Consistency (MRSC)

##### 1.3.2.13.1 Purpose
- MRSC provides strongly consistent reads across supported DynamoDB global-table Regions.

##### 1.3.2.13.2 Replication
- Before a successful write response, DynamoDB synchronously replicates the item change to at least one other Region.

##### 1.3.2.13.3 Strong Reads
- Strongly consistent reads from any MRSC replica return the latest version of the item.

##### 1.3.2.13.4 Conditional Writes
- Conditional writes evaluate against the latest item version across the MRSC global table.

##### 1.3.2.13.5 Availability Architecture
- Current MRSC global tables use exactly three Regions:
  - three replicas,
  - or two replicas plus one witness.
- MRSC is available only in supported Region sets.

##### 1.3.2.13.6 RPO
- AWS documents MRSC with an RPO of zero for its supported multi-Region architecture.

#### 1.3.2.14 MREC vs MRSC

##### 1.3.2.14.1 MREC
- Asynchronous cross-Region replication.
- Lower write latency.
- Can temporarily return stale cross-Region data.
- Last-writer-wins conflict resolution.
- RPO depends on replication delay.
- Flexible Region topology.

##### 1.3.2.14.2 MRSC
- Synchronous replication to another Region before successful write completion.
- Strong reads can return latest state from any replica.
- Higher write latency than MREC.
- RPO zero.
- More constrained Region topology/features.

##### 1.3.2.14.3 Decision
- Need lower latency and can tolerate temporary cross-Region staleness → MREC.
- Need latest-value strong reads across Regions / RPO zero → MRSC.

#### 1.3.2.15 Global Table Consistency Is Chosen at Creation

##### 1.3.2.15.1 Mode
- A global table has one consistency mode.
- Its replicas cannot mix MREC and MRSC.

##### 1.3.2.15.2 Immutability
- Current AWS documentation states that the global table's consistency mode cannot be changed after creation.

##### 1.3.2.15.3 Exam Implication
- MREC vs MRSC is an architectural decision, not a per-request switch like `ConsistentRead` on an ordinary supported DynamoDB read.

#### 1.3.2.16 Transactions vs Consistency

##### 1.3.2.16.1 Different Concepts
- Read consistency answers:
  - "How fresh is the value I read?"
- Transactions answer:
  - "Do multiple operations succeed/fail atomically under transaction semantics?"

##### 1.3.2.16.2 DynamoDB Transactions
- DynamoDB supports ACID transactions for appropriate single-Region/MREC use cases.
- Transaction operations are not simply another form of `ConsistentRead`.

##### 1.3.2.16.3 MREC Global Tables
- Transactions are atomic only within the Region where they execute.
- Transaction changes replicate to other MREC replicas individually rather than as one atomic cross-Region transaction.
- Another Region can temporarily observe a partially replicated transaction.

##### 1.3.2.16.4 MRSC Current Restriction
- Current AWS documentation states that MRSC global tables do not support DynamoDB transaction operations.

#### 1.3.2.17 Consistency vs Availability and Latency

##### 1.3.2.17.1 Distributed-System Trade-Off
- Stronger cross-Region consistency requires more coordination before writes can complete.
- More coordination can increase write latency and constrain availability behavior during failures.

##### 1.3.2.17.2 MREC
- Prioritizes low-latency local writes and broad multi-Region availability while accepting temporary replica divergence.

##### 1.3.2.17.3 MRSC
- Prioritizes global latest-value consistency and zero-RPO behavior while requiring synchronous multi-Region coordination.

##### 1.3.2.17.4 Exam Mindset
- Do not automatically select "strong" because it sounds safer.
- Select the weakest consistency model that still satisfies the application's correctness requirements.

#### 1.3.2.18 Consistency Decision Model

##### 1.3.2.18.1 Brief Staleness Acceptable
- Use eventually consistent reads.
- Lower DynamoDB read-capacity cost.

##### 1.3.2.18.2 Immediate Latest Value Required
- Use `ConsistentRead=true` on a supported table/LSI read.

##### 1.3.2.18.3 Querying a GSI
- Eventual consistency only.
- Do not expect `ConsistentRead=true` to provide strong GSI reads.

##### 1.3.2.18.4 Reading DynamoDB Streams
- Eventual consistency only.

##### 1.3.2.18.5 Multi-Region + Temporary Staleness Acceptable
- MREC global table.

##### 1.3.2.18.6 Multi-Region + Global Latest-Value Requirement
- Consider MRSC global tables when Region/feature constraints fit.

##### 1.3.2.18.7 Atomic Multi-Item Operation
- Think DynamoDB transactions, not merely strong reads.
- Verify global-table mode restrictions separately.

#### 1.3.2.19 Important Distinctions

##### 1.3.2.19.1 Eventual vs Strong
- Eventual → may temporarily return stale committed data.
- Strong → returns latest successful committed data within the supported consistency scope.

##### 1.3.2.19.2 Strong Consistency vs Read-Committed Isolation
- Read committed prevents observing unsuccessful/uncommitted values.
- Strong consistency additionally concerns freshness relative to successful prior writes.

##### 1.3.2.19.3 Strong Read vs Transaction
- Strong read guarantees freshness of a supported read.
- Transaction provides atomicity/isolation across transaction operations.
- They solve different correctness problems.

##### 1.3.2.19.4 Table/LSI vs GSI
- Table → eventual or strong.
- LSI → eventual or strong.
- GSI → eventual only.

##### 1.3.2.19.5 Local Strong Read vs Global Strong Consistency
- `ConsistentRead=true` on an MREC replica does not guarantee visibility of a not-yet-replicated write made in another Region.
- MRSC is the DynamoDB model for strong consistency across supported Regions.

##### 1.3.2.19.6 MREC vs MRSC
- MREC → asynchronous cross-Region replication.
- MRSC → synchronous multi-Region coordination for strong reads.

#### 1.3.2.20 Other In-Scope AWS Data Stores

##### 1.3.2.20.1 Amazon S3
- Amazon S3 provides strong read-after-write consistency for object PUT and DELETE operations and for LIST operations in all AWS Regions.
- After a successful write, a subsequent read returns the latest object state.
- There is no DynamoDB-style eventual-vs-strong read switch for ordinary S3 object reads.

##### 1.3.2.20.2 Relational Databases
- Amazon RDS and Amazon Aurora expose relational database transaction/isolation behavior.
- Their consistency model is not configured with DynamoDB's `ConsistentRead` parameter.
- Read replicas can introduce replica-lag considerations depending on architecture.

##### 1.3.2.20.3 Exam Boundary
- Because the exam guide examples explicitly name strongly and eventually consistent models and nearby Task 1.3 skills focus heavily on DynamoDB, DynamoDB should be the primary study model.
- Understand that "consistency" is service-specific; do not apply DynamoDB API rules mechanically to S3, RDS, Aurora, ElastiCache, or OpenSearch.

#### 1.3.2.21 Common Exam Traps

##### 1.3.2.21.1 "Strong Reads Everywhere"
- False.
- DynamoDB GSIs and Streams do not support strongly consistent reads.

##### 1.3.2.21.2 "Strong Read Means Transaction"
- False.
- Freshness and transaction atomicity are separate concerns.

##### 1.3.2.21.3 "Eventually Consistent Means Uncommitted"
- False.
- DynamoDB reads use read-committed isolation.
- Eventual reads can return an older committed value.

##### 1.3.2.21.4 "Global Table Strong Read Is Always Globally Strong"
- False for MREC.
- A strong read in an MREC replica can still be stale relative to a recent write in another Region.

##### 1.3.2.21.5 "DynamoDB Global Tables Are Always Eventually Consistent"
- Outdated.
- Current DynamoDB supports MREC and MRSC global-table modes.

##### 1.3.2.21.6 "Eventual Is Always Worse"
- False.
- Eventual consistency can be the correct design when brief staleness is acceptable and lower read cost/lower coordination are valuable.
