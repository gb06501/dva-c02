### 1.3.7 Manage data lifecycles

#### 1.3.7.1 Exam Context

##### 1.3.7.1.1 Skill Scope
- DVA-C02 Domain 1, Task 3 is **Use data stores in application development**.
- Skill 1.3.7 requires developers to **manage data lifecycles**.
- The exam guide does not restrict this skill to one AWS service.
- The developer perspective is:
  - determine how long data remains operationally useful,
  - transition aging data when cheaper storage is appropriate,
  - expire data that is no longer needed,
  - preserve historical data when retention is required,
  - automate these decisions with managed AWS features.

##### 1.3.7.1.2 Core Mental Model
- Data changes value over time.
- A useful lifecycle model is:

  `create`
  → `active / hot`
  → `less frequently accessed`
  → `archive / retain`
  → `expire / delete`

- Not every dataset passes through every stage.
- Lifecycle management means expressing the required retention/access policy so AWS can automate the appropriate action.

##### 1.3.7.1.3 Three Questions
- **How long must the data exist?**
- **How quickly must it remain accessible?**
- **What should happen when it is no longer active?**

- These questions drive:
  - retention,
  - storage-class transition,
  - archival,
  - expiration,
  - deletion.

#### 1.3.7.2 Lifecycle vs Maintenance

##### 1.3.7.2.1 Maintenance
- Keeps the data store operational:
  - capacity,
  - monitoring,
  - backups,
  - availability,
  - recovery.
- Covered primarily by Skill 1.3.6.

##### 1.3.7.2.2 Lifecycle
- Controls what happens to data as it ages:
  - remain active,
  - move to cheaper storage,
  - archive,
  - expire,
  - permanently delete.

##### 1.3.7.2.3 Key Distinction
- Backup answers:
  - "How can I recover lost/corrupted data?"
- Lifecycle answers:
  - "How long should this data remain, and in what storage state?"

#### 1.3.7.3 Retention

##### 1.3.7.3.1 Definition
- Retention is the period for which data must remain available or preserved.

##### 1.3.7.3.2 Drivers
- Business requirements.
- Application requirements.
- Cost.
- Audit/compliance requirements.
- Operational usefulness.

##### 1.3.7.3.3 Developer Responsibility
- Encode retention requirements using the appropriate service feature rather than relying on ad-hoc manual cleanup jobs where a managed mechanism exists.

#### 1.3.7.4 Expiration

##### 1.3.7.4.1 Definition
- Expiration marks data as no longer required after a defined time.

##### 1.3.7.4.2 AWS Examples
- DynamoDB Time to Live (TTL).
- S3 Lifecycle Expiration.

##### 1.3.7.4.3 Important Principle
- Expiration mechanisms are commonly asynchronous.
- "Eligible for expiration" does not necessarily mean "physically deleted at that exact instant."

#### 1.3.7.5 Archival

##### 1.3.7.5.1 Definition
- Archival retains historical data while moving it away from the primary high-performance access path.

##### 1.3.7.5.2 Purpose
- Reduce cost while preserving data that:
  - is rarely accessed,
  - must be retained,
  - may be needed later.

##### 1.3.7.5.3 AWS Pattern
- Hot operational data:
  - DynamoDB or S3 frequent-access class.
- Historical data:
  - lower-cost S3 storage class / S3 Glacier storage class.
- Eventually:
  - expiration if retention permits deletion.

#### 1.3.7.6 Amazon DynamoDB TTL

##### 1.3.7.6.1 Purpose
- DynamoDB TTL automatically removes individual items that are no longer needed.
- It is designed for data with a known per-item expiration time.

##### 1.3.7.6.2 Configuration
- Enable TTL on the table.
- Select one attribute name as the TTL attribute.
- Individual items can then contain an expiration value in that attribute.

##### 1.3.7.6.3 Per-Item Behavior
- TTL is configured at table level.
- Expiration is controlled per item.
- Items without a valid TTL attribute are not expired by TTL.

#### 1.3.7.7 DynamoDB TTL Attribute

##### 1.3.7.7.1 Required Representation
- TTL value must be:
  - DynamoDB Number type,
  - Unix epoch time,
  - in **seconds**.

##### 1.3.7.7.2 Example
- Application determines:
  - item should expire 7 days after creation.
- It calculates:
  - current epoch seconds + 7 days.
- It stores that value in the configured TTL attribute.

##### 1.3.7.7.3 Invalid Representation
- If the TTL attribute is not a Number, DynamoDB ignores it for TTL processing.
- Milliseconds instead of seconds produce the wrong timestamp semantics.

##### 1.3.7.7.4 Attribute Name
- The configured TTL attribute name is case sensitive.
- Application writes must use the exact configured attribute name.

#### 1.3.7.8 Computing TTL

##### 1.3.7.8.1 Creation-Based Expiration
- Common pattern:

  `expireAt = createdAt + retentionPeriod`

##### 1.3.7.8.2 Activity-Based Expiration
- Another pattern:

  `expireAt = updatedAt + retentionPeriod`

- Updating the item can therefore refresh its lifetime.

##### 1.3.7.8.3 Application Responsibility
- DynamoDB does not infer the business retention period.
- Application code calculates and stores the expiration timestamp.

#### 1.3.7.9 TTL Deletion Is Asynchronous

##### 1.3.7.9.1 Expiration Time
- The TTL timestamp makes an item eligible for expiration.

##### 1.3.7.9.2 Physical Deletion
- DynamoDB deletes expired items asynchronously.
- AWS states that expired items are typically deleted within a few days.

##### 1.3.7.9.3 Consequence
- An expired item can still:
  - exist,
  - appear in reads,
  - consume storage/read cost
  until DynamoDB actually removes it.

##### 1.3.7.9.4 Application Rule
- Do not use TTL as an exact-time correctness mechanism.
- If data must become logically invalid at an exact time, application logic should evaluate the expiration time itself.

#### 1.3.7.10 Reading Expired DynamoDB Items

##### 1.3.7.10.1 Pending Deletion
- Expired items pending TTL deletion can still appear in `Query` and `Scan` operations.

##### 1.3.7.10.2 Filtering
- Applications can use filter expressions to remove logically expired items from returned results.

##### 1.3.7.10.3 Important Cost Point
- Filtering occurs after the read.
- These expired items can therefore still contribute to read cost until physically deleted.

##### 1.3.7.10.4 Connection
- Filter behavior belongs fundamentally to Skill 1.3.3.

#### 1.3.7.11 Updating Expired Items

##### 1.3.7.11.1 Pending Items Remain Mutable
- An expired item can still be updated while waiting for TTL deletion.

##### 1.3.7.11.2 Reviving an Item
- Before deletion, an application can:
  - remove the TTL attribute,
  - or change it to a future timestamp.
- The item is then no longer eligible for TTL deletion.

##### 1.3.7.11.3 Concurrency
- AWS recommends using condition expressions when updating expired items to ensure the item has not already been deleted or unexpectedly changed.

#### 1.3.7.12 TTL Cost Behavior

##### 1.3.7.12.1 Source Region
- DynamoDB's TTL deletion itself does not consume write throughput in the Region where expiration occurs.

##### 1.3.7.12.2 Storage
- Expired items still consume storage until DynamoDB physically deletes them.

##### 1.3.7.12.3 Read Cost
- Reads that encounter expired-but-not-yet-deleted items can still consume read resources.

#### 1.3.7.13 TTL and Secondary Indexes

##### 1.3.7.13.1 Deletion
- When DynamoDB deletes an expired item through TTL, corresponding entries are also removed from:
  - LSIs,
  - GSIs.

##### 1.3.7.13.2 Mental Model
- TTL deletes the table item as a service-managed delete.
- Index maintenance follows the base-table deletion automatically.

#### 1.3.7.14 TTL and DynamoDB Streams

##### 1.3.7.14.1 Stream Record
- A TTL deletion can appear in DynamoDB Streams.

##### 1.3.7.14.2 Service Deletion
- TTL deletes are identifiable as service-originated deletes in the Region where the TTL deletion occurred.

##### 1.3.7.14.3 Use
- This enables downstream processing when data expires.

#### 1.3.7.15 TTL-to-Archive Pattern

##### 1.3.7.15.1 Requirement
- Remove old data from the primary DynamoDB table but preserve it for historical/compliance purposes.

##### 1.3.7.15.2 AWS-Documented Pattern
- DynamoDB item expires.
- TTL removes it.
- DynamoDB Streams captures the service deletion.
- A Lambda consumer processes the stream event.
- Historical representation is written to long-term storage such as Amazon S3 / archival storage.

##### 1.3.7.15.3 Mental Model

  `DynamoDB active data`
  → `TTL expiry`
  → `DynamoDB Stream`
  → `Lambda`
  → `long-term archive`

##### 1.3.7.15.4 Why
- Keeps the operational table smaller while retaining historical information.

#### 1.3.7.16 TTL and Global Tables

##### 1.3.7.16.1 MREC Global Tables
- Current MREC global tables support TTL.
- TTL configuration is synchronized across replicas.
- A TTL deletion in one replica is replicated to the other replicas.

##### 1.3.7.16.2 Replicated Delete Cost
- The original TTL deletion does not consume write capacity in the Region where it occurs.
- Replicated TTL deletes consume replicated write capacity in replica Regions and incur the corresponding cost.

##### 1.3.7.16.3 MRSC Global Tables
- Current AWS documentation states that MRSC global tables do **not** support TTL.

##### 1.3.7.16.4 Exam Value
- Do not assume every global-table consistency mode supports the same lifecycle features.

#### 1.3.7.17 Amazon S3 Lifecycle

##### 1.3.7.17.1 Purpose
- S3 Lifecycle automates actions on objects as they age.

##### 1.3.7.17.2 Main Action Families
- **Transition**
  - move objects to another S3 storage class.
- **Expiration**
  - expire/delete objects.

##### 1.3.7.17.3 Versioned Objects
- Lifecycle can separately manage:
  - current versions,
  - noncurrent versions,
  - expired delete markers.

##### 1.3.7.17.4 Operational Cleanup
- Lifecycle can also abort incomplete multipart uploads.

#### 1.3.7.18 S3 Lifecycle Rule Structure

##### 1.3.7.18.1 Rule
- Lifecycle behavior is expressed through rules attached to the bucket.

##### 1.3.7.18.2 Filter
- A rule can select objects using criteria such as:
  - object-key prefix,
  - object tags,
  - object size,
  - combinations of supported filters.

##### 1.3.7.18.3 Action
- Define what S3 should do:
  - transition,
  - expire,
  - manage noncurrent versions,
  - clean up incomplete multipart uploads.

##### 1.3.7.18.4 Time
- Define when the action becomes applicable:
  - object age in days,
  - or supported date-based configuration.

##### 1.3.7.18.5 Mental Model

  `which objects?`
  + `after how long?`
  + `what action?`

  = S3 Lifecycle rule.

#### 1.3.7.19 S3 Lifecycle Filters

##### 1.3.7.19.1 Prefix
- Apply lifecycle policy only to objects under a logical key prefix.
- Example:
  - `logs/`.

##### 1.3.7.19.2 Tags
- Apply lifecycle behavior based on object tags.

##### 1.3.7.19.3 Size
- Lifecycle filters can include object-size criteria.

##### 1.3.7.19.4 Benefit
- Different classes of data in the same bucket can have different retention policies.

#### 1.3.7.20 S3 Transition Actions

##### 1.3.7.20.1 Purpose
- Move aging objects to a storage class that better matches their reduced access frequency.

##### 1.3.7.20.2 Examples
- Frequently accessed active object:
  - S3 Standard.
- Less frequently accessed:
  - Standard-IA where appropriate.
- Archive:
  - S3 Glacier Flexible Retrieval,
  - S3 Glacier Deep Archive.

##### 1.3.7.20.3 Decision
- Transition instead of delete when:
  - the data must still exist,
  - but frequent/low-latency access is no longer required.

##### 1.3.7.20.4 Constraints
- S3 storage classes have different:
  - access characteristics,
  - minimum-storage-duration considerations,
  - retrieval characteristics/costs.
- Lifecycle design must respect supported transition rules.

#### 1.3.7.21 S3 Expiration

##### 1.3.7.21.1 Purpose
- Remove objects when retention is no longer required.

##### 1.3.7.21.2 Nonversioned Bucket
- Lifecycle expiration permanently removes the object asynchronously.

##### 1.3.7.21.3 Versioning-Enabled Bucket
- Expiration of the current version generally creates a delete marker.
- The former current version becomes noncurrent.
- It is **not** automatically permanently erased merely because the current version expired.

##### 1.3.7.21.4 Consequence
- In versioned buckets, lifecycle design must also address noncurrent versions if permanent cleanup is required.

#### 1.3.7.22 Current vs Noncurrent S3 Versions

##### 1.3.7.22.1 Current Version
- The version returned by a normal GET for that key unless a delete marker is current.

##### 1.3.7.22.2 Noncurrent Version
- An older version retained after a newer version replaces it or after lifecycle/delete behavior makes it noncurrent.

##### 1.3.7.22.3 Lifecycle Actions
- S3 provides separate actions for:
  - current-version transition/expiration,
  - noncurrent-version transition,
  - noncurrent-version expiration.

##### 1.3.7.22.4 Cost
- Noncurrent versions continue consuming storage until transitioned or permanently deleted.

#### 1.3.7.23 S3 Delete Markers

##### 1.3.7.23.1 Meaning
- In a versioning-enabled bucket, a normal delete generally creates a delete marker.

##### 1.3.7.23.2 Logical Effect
- The object appears deleted to ordinary GET requests.
- Previous object versions still exist.

##### 1.3.7.23.3 Expired Object Delete Marker
- When only a delete marker remains for an object key, S3 Lifecycle can remove the expired delete marker.

##### 1.3.7.23.4 Exam Trap
- Delete marker ≠ permanent deletion of historical versions.

#### 1.3.7.24 S3 Versioning + Lifecycle

##### 1.3.7.24.1 Protection
- Versioning preserves previous object versions after overwrite/delete operations.

##### 1.3.7.24.2 Cost
- Every retained version consumes storage.

##### 1.3.7.24.3 Lifecycle Role
- Lifecycle can:
  - transition noncurrent versions,
  - permanently expire noncurrent versions,
  - retain a configured number of newer noncurrent versions where supported,
  - remove expired delete markers.

##### 1.3.7.24.4 Combined Mental Model
- Versioning provides recoverability/history.
- Lifecycle prevents that history from growing indefinitely.

#### 1.3.7.25 Incomplete Multipart Uploads

##### 1.3.7.25.1 Problem
- Multipart upload parts can remain stored when an upload is initiated but never completed.

##### 1.3.7.25.2 Lifecycle
- S3 Lifecycle can automatically abort incomplete multipart uploads after a configured number of days.

##### 1.3.7.25.3 Why It Matters
- Prevents abandoned upload parts from consuming storage indefinitely.

#### 1.3.7.26 S3 Lifecycle Is Asynchronous

##### 1.3.7.26.1 Eligibility vs Completion
- An object can become eligible for transition/expiration before S3 physically performs the action.

##### 1.3.7.26.2 AWS Behavior
- Lifecycle processing is asynchronous and there can be a delay after the configured date/age is reached.

##### 1.3.7.26.3 Design Consequence
- Do not treat lifecycle completion time as an exact application scheduling mechanism.

#### 1.3.7.27 Lifecycle Rule Conflicts

##### 1.3.7.27.1 Multiple Rules
- An object can match more than one lifecycle rule.

##### 1.3.7.27.2 AWS Precedence
- When actions become eligible on the same day, AWS documents general precedence including:
  - permanent deletion over transition,
  - transition over creation of delete markers.

##### 1.3.7.27.3 Developer Lesson
- Lifecycle policies should be designed intentionally when filters overlap.

#### 1.3.7.28 Lifecycle and Replication

##### 1.3.7.28.1 S3 Replication
- Replication and lifecycle are separate mechanisms.
- Replication creates/maintains copies in another destination.
- Lifecycle governs aging/retention actions.

##### 1.3.7.28.2 Important Behavior
- AWS documents interactions between replication status and lifecycle processing.
- Objects with certain pending/failed replication states can have lifecycle transition/expiration actions blocked until replication state permits them.

##### 1.3.7.28.3 Rule
- Do not assume lifecycle and replication operate independently when both are enabled.

#### 1.3.7.29 Data Temperature

##### 1.3.7.29.1 Hot Data
- Frequently accessed.
- Requires fast access.
- Often belongs in operational stores/classes optimized for active workloads.

##### 1.3.7.29.2 Warm Data
- Access frequency has decreased.
- Still needs reasonably accessible storage.

##### 1.3.7.29.3 Cold / Archived Data
- Rarely accessed.
- Retention matters more than immediate retrieval.

##### 1.3.7.29.4 Expired Data
- No longer required.
- Delete when policy permits.

##### 1.3.7.29.5 Mental Model
- Lifecycle design often follows decreasing access frequency:

  `hot → warm → cold/archive → delete`

#### 1.3.7.30 Lifecycle Policy Decision Model

##### 1.3.7.30.1 Temporary DynamoDB Item
- Known expiration timestamp.
- Use DynamoDB TTL.

##### 1.3.7.30.2 DynamoDB Item Must Disappear Exactly at Deadline
- TTL alone is insufficient because physical deletion is asynchronous.
- Application must enforce logical expiration.

##### 1.3.7.30.3 Old DynamoDB Data Must Be Preserved
- Consider TTL + DynamoDB Streams + Lambda → archival store.

##### 1.3.7.30.4 S3 Object Becomes Rarely Accessed
- Use Lifecycle transition to an appropriate lower-cost storage class.

##### 1.3.7.30.5 S3 Object No Longer Required
- Use Lifecycle expiration.

##### 1.3.7.30.6 Versioned S3 Bucket Growing Indefinitely
- Add lifecycle handling for noncurrent versions.

##### 1.3.7.30.7 Abandoned Multipart Upload Storage
- Use lifecycle abort-incomplete-multipart-upload action.

#### 1.3.7.31 Lifecycle vs Application Cleanup Code

##### 1.3.7.31.1 Managed Lifecycle
- Prefer managed features when the requirement maps naturally to:
  - DynamoDB TTL,
  - S3 Lifecycle.

##### 1.3.7.31.2 Benefits
- Less custom scheduling/cleanup code.
- Service-managed execution.
- Lower operational complexity.

##### 1.3.7.31.3 Custom Logic Still Needed
- When:
  - expiration must be exact,
  - deletion depends on complex business state,
  - data must be transformed before archival,
  - lifecycle event triggers additional domain behavior.

#### 1.3.7.32 Important Distinctions

##### 1.3.7.32.1 TTL vs S3 Lifecycle
- DynamoDB TTL:
  - expires individual table items based on a per-item epoch timestamp.
- S3 Lifecycle:
  - applies rules to object groups and can transition or expire objects/versions.

##### 1.3.7.32.2 Expiration vs Transition
- Expiration:
  - data is no longer needed.
- Transition:
  - data is still needed but a different storage class better matches its access pattern.

##### 1.3.7.32.3 Expiration vs Exact Deletion
- Expiration makes data eligible for service-managed deletion.
- Physical removal can occur later.

##### 1.3.7.32.4 Versioning vs Lifecycle
- Versioning:
  - preserves history.
- Lifecycle:
  - controls aging/cleanup of that history.

##### 1.3.7.32.5 Backup vs Archive
- Backup:
  - recover operational data after loss/corruption.
- Archive:
  - intentionally retain historical data for later retrieval/compliance.

##### 1.3.7.32.6 Lifecycle vs Cache Expiration
- Data-store lifecycle controls persistence/retention.
- Cache TTL controls how long cached copies remain useful.
- Caching belongs to Skill 1.3.8.

#### 1.3.7.33 Common Exam Traps

##### 1.3.7.33.1 "DynamoDB TTL Deletes Exactly at the Timestamp"
- False.
- The timestamp makes the item eligible; deletion is asynchronous.

##### 1.3.7.33.2 "DynamoDB TTL Uses Milliseconds"
- False.
- TTL requires Unix epoch time in seconds.

##### 1.3.7.33.3 "Expired DynamoDB Items Cannot Be Read"
- False.
- They can remain visible until physically deleted.

##### 1.3.7.33.4 "TTL Delete Always Costs WCU"
- False for the originating TTL deletion.
- Replicated TTL deletes in global-table replicas can consume replicated write capacity.

##### 1.3.7.33.5 "S3 Lifecycle Expiration Permanently Deletes a Current Version in a Versioned Bucket"
- Not generally.
- It normally creates a delete marker and makes the previous current version noncurrent.

##### 1.3.7.33.6 "S3 Versioning Automatically Cleans Old Versions"
- False.
- Lifecycle rules are needed if noncurrent versions should transition or expire automatically.

##### 1.3.7.33.7 "Delete Marker Means Old Data Is Gone"
- False.
- Historical versions can remain.

##### 1.3.7.33.8 "Transition Means Delete"
- False.
- Transition keeps the object but changes its storage class.

##### 1.3.7.33.9 "Lifecycle Is a Backup Mechanism"
- False.
- Lifecycle manages aging/retention; backup serves recovery.

#### 1.3.7.35 In-Scope Service Check

##### 1.3.7.35.1 Primary Services
- Amazon DynamoDB:
  - TTL,
  - Streams integration for expiration events.
- Amazon S3:
  - Lifecycle,
  - Versioning,
  - storage-class transitions,
  - expiration,
  - noncurrent-version management.

##### 1.3.7.35.2 Supporting In-Scope Services
- AWS Lambda:
  - process lifecycle-related DynamoDB Stream events.
- Amazon S3 Glacier storage classes:
  - archival targets through S3 lifecycle transitions.
- DynamoDB global tables:
  - lifecycle behavior differs by consistency mode.

##### 1.3.7.35.3 Scope Control
- Do not turn this skill into:
  - complete compliance/governance architecture,
  - legal-retention analysis,
  - full S3 storage-class pricing memorization,
  - full backup/disaster-recovery design.
- Focus on how developers automate the useful lifetime of persisted data.

#### 1.3.7.36 Exam-Level Knowledge Frame

##### 1.3.7.36.1 DynamoDB
- Know what TTL solves.
- Know per-item epoch-seconds attribute.
- Know TTL deletion is asynchronous.
- Know expired items can remain visible.
- Know TTL deletes can appear in Streams.
- Understand TTL → Streams → Lambda → archive.
- Know global-table TTL implications.

##### 1.3.7.36.2 S3
- Know lifecycle transition vs expiration.
- Know filters determine which objects a rule affects.
- Know current vs noncurrent version lifecycle.
- Know versioned expiration creates delete-marker behavior rather than necessarily erasing history.
- Know lifecycle can clean expired delete markers and incomplete multipart uploads.
- Know lifecycle actions are asynchronous.

##### 1.3.7.36.3 Overall Decision
- Need data actively → keep in operational store.
- Need data but less frequently → transition/archive.
- No longer need data → expire/delete.
- Need recoverability → version/backup rather than confusing that requirement with lifecycle expiration.
