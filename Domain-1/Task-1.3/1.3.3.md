### 1.3.3 Describe differences between query and scan operations

#### 1.3.3.1 Exam Context

##### 1.3.3.1.1 Skill Scope
- DVA-C02 Domain 1, Task 3 is **Use data stores in application development**.
- Skill 1.3.3 requires describing differences between `Query` and `Scan` operations.
- Amazon DynamoDB is the defining in-scope service for this skill.
- The exam focus is how each operation selects data, how much data it reads, how filtering behaves, how capacity is consumed, and why `Query` is usually preferred when the access pattern supports it.

##### 1.3.3.1.2 Core Mental Model
- `Query`:
  - starts from one known partition-key value,
  - optionally narrows with a sort-key condition,
  - reads only that key range.
- `Scan`:
  - reads every item in the table or index segment,
  - then optionally filters the results.
- Key rule:
  - **Query selects by key first.**
  - **Scan reads broadly first, then filters.**

#### 1.3.3.2 Query Operation

##### 1.3.3.2.1 Required Partition Key
- `Query` requires equality on one partition-key value.
- DynamoDB returns items with that partition-key value.

##### 1.3.3.2.2 Optional Sort-Key Condition
- If a sort key exists, `Query` can further narrow results.
- Common operators include:
  - equality,
  - `<`, `<=`, `>`, `>=`,
  - `BETWEEN`,
  - `begins_with`.

##### 1.3.3.2.3 KeyConditionExpression
- Partition key must use equality.
- Sort-key conditions narrow the read within that partition.
- Key conditions determine which items DynamoDB reads.

#### 1.3.3.3 Scan Operation

##### 1.3.3.3.1 Full Table or Index Read
- `Scan` reads every item in a table or secondary-index segment.
- It does not require a partition-key value.
- It is therefore suitable for broad inspection or processing when no useful key-based access path exists.

##### 1.3.3.3.2 Sequential by Default
- A normal `Scan` proceeds sequentially.
- Large scans can consume substantial read capacity.

##### 1.3.3.3.3 Parallel Scan
- DynamoDB supports parallel scans using:
  - `TotalSegments`,
  - `Segment`.
- Multiple workers scan different logical segments concurrently.
- This reduces elapsed scan time but can consume read capacity much faster.

#### 1.3.3.4 Selection Behavior

##### 1.3.3.4.1 Query
- Uses the partition key to directly target one item collection.
- Can efficiently narrow by sort key.

##### 1.3.3.4.2 Scan
- Does not use the key structure to constrain the initial read.
- Examines all items in the scanned scope.

##### 1.3.3.4.3 Exam Rule
- Known partition key / designed access pattern → `Query`.
- Broad inspection with no suitable key → `Scan`.

#### 1.3.3.5 FilterExpression

##### 1.3.3.5.1 Query Filter
- `Query` can use `FilterExpression`.
- The filter is applied **after** DynamoDB reads the items selected by the key condition.

##### 1.3.3.5.2 Scan Filter
- `Scan` can also use `FilterExpression`.
- The scan still reads the items first and only then removes non-matching items.

##### 1.3.3.5.3 Capacity Consequence
- Filtering does not reduce the read capacity already consumed by the items read.
- This is one of the most important exam distinctions.

##### 1.3.3.5.4 Key Attributes
- Partition-key and sort-key conditions belong in `KeyConditionExpression`.
- AWS states Query filters cannot contain partition-key or sort-key attributes.

#### 1.3.3.6 Query Efficiency

##### 1.3.3.6.1 Why Query Is Efficient
- DynamoDB can directly locate the requested partition-key value.
- It avoids reading unrelated table data.

##### 1.3.3.6.2 Access-Pattern Design
- Frequent application reads should ideally be modeled so they can be served by:
  - the table primary key,
  - or an appropriate secondary index.

##### 1.3.3.6.3 Query Can Still Be Broad
- A Query can still consume significant capacity if one partition-key value contains many items.
- A broad Query followed by a heavy filter can still be inefficient.

#### 1.3.3.7 Scan Cost and Performance

##### 1.3.3.7.1 Reads Everything in Scope
- `Scan` consumes capacity based on items read, not only items returned.

##### 1.3.3.7.2 Large Tables
- AWS recommends avoiding Scan on large tables/indexes where a Query-based access pattern is possible.
- A scan can consume enough throughput to affect production traffic.

##### 1.3.3.7.3 Correct Uses
- Background/administrative processing.
- Historical sweeps.
- One-time inspection.
- Small tables where an additional index is not justified.
- Do not use Scan as the default application read path.

#### 1.3.3.8 Pagination

##### 1.3.3.8.1 1 MB Page Limit
- A single `Query` or `Scan` reads up to 1 MB before returning a page.
- The limit applies before `FilterExpression` or `ProjectionExpression` removes data from the response.

##### 1.3.3.8.2 LastEvaluatedKey
- If more data remains, DynamoDB returns `LastEvaluatedKey`.
- Use it as `ExclusiveStartKey` for the next request.

##### 1.3.3.8.3 Empty Page Trap
- A Query can return zero items while still returning `LastEvaluatedKey` if the page was fully filtered out.
- An empty page therefore does not necessarily mean the operation is complete.

#### 1.3.3.9 Count vs ScannedCount

##### 1.3.3.9.1 Count
- Number of items returned after filtering for the page.

##### 1.3.3.9.2 ScannedCount
- Number of items evaluated before filtering for the page.

##### 1.3.3.9.3 Diagnostic Use
- Large `ScannedCount` with small `Count` indicates that many reads were discarded.
- This often signals an inefficient access pattern.

#### 1.3.3.10 Sort Order

##### 1.3.3.10.1 Query Ordering
- Query results are sorted by sort-key value.
- Default is ascending.
- `ScanIndexForward=false` reverses the order.

##### 1.3.3.10.2 Scan
- Scan does not provide the same logical sort-key ordering guarantee across the table.
- Use Query when ordered retrieval by sort key is required.

#### 1.3.3.11 Consistency

##### 1.3.3.11.1 Query
- Eventually consistent by default.
- Strong reads are available for:
  - base tables,
  - LSIs.
- GSIs are eventual only.

##### 1.3.3.11.2 Scan
- Eventually consistent by default.
- `ConsistentRead=true` can request strong item-level reads where supported.

##### 1.3.3.11.3 Strong Scan Is Not Snapshot Isolation
- AWS explicitly states that strongly consistent Scan does not provide a single point-in-time snapshot of the table.
- Each item may be read strongly, but the full scan is not an atomic snapshot.

#### 1.3.3.12 ProjectionExpression

##### 1.3.3.12.1 Purpose
- `ProjectionExpression` controls which attributes are returned.

##### 1.3.3.12.2 Capacity
- Projection can reduce response size.
- It does not generally reduce read capacity for base-table items already read.

#### 1.3.3.13 Querying Indexes

##### 1.3.3.13.1 Table
- Query using table partition key and optional sort key.

##### 1.3.3.13.2 LSI
- Query with the table partition key and the LSI sort key.
- Strong reads are supported.

##### 1.3.3.13.3 GSI
- Query using the GSI partition key and optional sort key.
- GSI reads are eventually consistent only.

##### 1.3.3.13.4 Design Implication
- If an alternate lookup is frequent, an index is often preferable to repeatedly scanning the base table.

#### 1.3.3.14 Parallel Scan

##### 1.3.3.14.1 Purpose
- Parallel Scan reduces wall-clock time for broad scans.

##### 1.3.3.14.2 Trade-Off
- More workers increase throughput consumption.
- AWS warns that parallel scans can starve production workloads.

##### 1.3.3.14.3 Appropriate Context
- Large background/historical workloads.
- Spare read capacity exists.
- Sequential scan is too slow.
- Not a substitute for proper key/index design.

#### 1.3.3.15 Decision Model

##### 1.3.3.15.1 Know Partition Key
- Use Query.

##### 1.3.3.15.2 Need Sort-Key Range
- Use Query with `KeyConditionExpression`.

##### 1.3.3.15.3 Need Alternate Key Lookup
- Query an appropriate index.
- If no suitable index exists and the access is frequent, redesign the model/index.

##### 1.3.3.15.4 Need Every Item
- Use Scan.

##### 1.3.3.15.5 Need Rare Broad Search
- Scan can be acceptable for small/background workloads.

##### 1.3.3.15.6 Filter Removes Most Results
- Prefer a better key/index design for frequent access.
- FilterExpression does not avoid the read cost.

#### 1.3.3.16 Important Distinctions

##### 1.3.3.16.1 KeyConditionExpression vs FilterExpression
- Key condition determines what Query reads.
- Filter determines what already-read items are returned.

##### 1.3.3.16.2 Query vs Scan
- Query reads a known key range.
- Scan reads all items in scope.

##### 1.3.3.16.3 Count vs ScannedCount
- Count = returned after filtering.
- ScannedCount = evaluated before filtering.

##### 1.3.3.16.4 Projection vs Filter
- Projection removes attributes from the response.
- Filter removes items from the response.
- Neither makes Scan equivalent to Query.

##### 1.3.3.16.5 Parallel Scan vs Query
- Parallel Scan makes a broad scan faster through concurrency.
- Query avoids reading unrelated data in the first place.

##### 1.3.3.16.6 Strong Scan vs Snapshot
- Strong item reads do not make the full scan a transactional snapshot.

#### 1.3.3.17 Common Exam Traps

##### 1.3.3.17.1 "FilterExpression Saves Capacity"
- False.
- Filtering happens after items are read.

##### 1.3.3.17.2 "Scan with Filter Is Like Query"
- False.
- Scan still reads broadly.

##### 1.3.3.17.3 "Query Can Omit Partition Key"
- False.
- Query requires one partition-key value.

##### 1.3.3.17.4 "One API Call Returns All Data"
- False for results larger than 1 MB.
- Handle pagination.

##### 1.3.3.17.5 "Empty Query Page Means Finished"
- False if `LastEvaluatedKey` exists.

##### 1.3.3.17.6 "Strong Scan Is a Snapshot"
- False.
