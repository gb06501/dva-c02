### 1.3.4 Define Amazon DynamoDB keys and indexing

#### 1.3.4.1 Exam Context

##### 1.3.4.1.1 Skill Scope
- DVA-C02 Domain 1, Task 3 is **Use data stores in application development**.
- Skill 1.3.4 requires defining Amazon DynamoDB keys and indexing.
- This skill connects DynamoDB data modeling to application access patterns.
- The central question is:
  - **How should data be keyed and indexed so the application can retrieve it efficiently with Query rather than broad Scan operations?**

##### 1.3.4.1.2 Core Mental Model
- DynamoDB access begins with keys.
- The table primary key defines:
  - item identity,
  - physical distribution,
  - grouping and ordering when a sort key exists.
- Secondary indexes provide alternate query paths.
- Think:
  - **primary key → primary access pattern**
  - **secondary index → alternate access pattern**
- Keys and indexes should therefore be designed from known application access patterns.

#### 1.3.4.2 Primary Key

##### 1.3.4.2.1 Purpose
- Every DynamoDB table has a primary key.
- The primary key uniquely identifies each item in the table.

##### 1.3.4.2.2 Two Forms
- Simple primary key:
  - partition key only.
- Composite primary key:
  - partition key + sort key.

#### 1.3.4.3 Simple Primary Key

##### 1.3.4.3.1 Structure
- One attribute acts as the partition key.
- Example:
  - `UserId = USER#123`.

##### 1.3.4.3.2 Uniqueness
- No two table items can have the same partition-key value when the table uses a simple primary key.

##### 1.3.4.3.3 Distribution
- DynamoDB hashes the partition-key value to determine where the item is stored.
- Balanced partition-key design is covered in Skill 1.3.1.

#### 1.3.4.4 Composite Primary Key

##### 1.3.4.4.1 Structure
- Two attributes:
  - partition key,
  - sort key.

##### 1.3.4.4.2 Uniqueness
- Multiple items can share the same partition-key value.
- The combination:
  - partition key + sort key
  must be unique.

##### 1.3.4.4.3 Example
- `PK = CUSTOMER#123`
- `SK = ORDER#456`
- Another item can use:
  - `PK = CUSTOMER#123`
  - `SK = ORDER#789`.

##### 1.3.4.4.4 Purpose
- Composite keys allow related items to be grouped under one partition-key value and ordered/queryable through the sort key.

#### 1.3.4.5 Partition Key

##### 1.3.4.5.1 Role
- DynamoDB applies an internal hash function to the partition-key value.
- The result determines physical storage placement.

##### 1.3.4.5.2 Query Requirement
- A DynamoDB `Query` requires equality on one partition-key value.
- Therefore partition-key choice directly determines which access patterns can be served efficiently.

##### 1.3.4.5.3 Design Goal
- Partition keys should:
  - support application access patterns,
  - have sufficient cardinality,
  - distribute activity reasonably across values.
- Distribution details belong to Skill 1.3.1.

#### 1.3.4.6 Sort Key

##### 1.3.4.6.1 Role
- Items sharing a partition-key value are stored together and ordered by sort-key value.
- The sort key is sometimes called a range key.

##### 1.3.4.6.2 Query Capability
- Query can narrow an item collection using sort-key conditions such as:
  - equality,
  - `<`, `<=`, `>`, `>=`,
  - `BETWEEN`,
  - `begins_with`.

##### 1.3.4.6.3 Design Benefit
- AWS identifies two major benefits of well-designed sort keys:
  - grouping related information for efficient queries,
  - representing hierarchical relationships.

#### 1.3.4.7 Item Collections

##### 1.3.4.7.1 Definition
- An item collection is the set of items sharing the same partition-key value in a table that uses a composite primary key.

##### 1.3.4.7.2 Mental Model
- Example:
  - `PK = CUSTOMER#123`
    - `SK = PROFILE`
    - `SK = ORDER#2026-001`
    - `SK = ORDER#2026-002`
    - `SK = ADDRESS#HOME`.
- These related items can be retrieved through one partition-key Query.

##### 1.3.4.7.3 Importance
- Item collections are fundamental to DynamoDB relationship modeling.
- Instead of relational joins, applications can deliberately colocate data needed by the same access pattern.

#### 1.3.4.8 Composite Sort Keys

##### 1.3.4.8.1 Pattern
- Multiple logical dimensions can be encoded into one sort-key value.
- AWS commonly shows hierarchy components separated with delimiters such as `#`.

##### 1.3.4.8.2 Example
- `SK = ORDER#2026#08#12345`
- or hierarchical geography:
  - `country#region#state#city`.

##### 1.3.4.8.3 Prefix Queries
- `begins_with` can retrieve a logical subtree/prefix.
- Example:
  - `begins_with(SK, "ORDER#2026")`.

##### 1.3.4.8.4 Purpose
- Composite sort keys create useful hierarchy and range-query semantics without adding separate physical indexes for every hierarchy level.

#### 1.3.4.9 Secondary Indexes

##### 1.3.4.9.1 Problem They Solve
- The table primary key supports one primary key structure.
- Applications often require alternate lookup paths.
- A secondary index reorganizes a subset of table data under another key schema.

##### 1.3.4.9.2 Querying
- Applications can `Query` secondary indexes similarly to tables.
- This allows alternate access patterns without scanning the base table.

##### 1.3.4.9.3 Types
- DynamoDB supports:
  - Global Secondary Index (GSI),
  - Local Secondary Index (LSI).

#### 1.3.4.10 Local Secondary Index (LSI)

##### 1.3.4.10.1 Key Structure
- LSI uses:
  - the **same partition key** as the base table,
  - a **different sort key**.

##### 1.3.4.10.2 Mental Model
- LSI answers:
  - "For the same logical partition/entity group, how can I order/query these items differently?"

##### 1.3.4.10.3 Example
- Table:
  - PK = `CustomerId`
  - SK = `OrderId`.
- LSI:
  - PK = `CustomerId`
  - SK = `OrderDate`.
- The application can query one customer's orders by an alternate sort dimension.

##### 1.3.4.10.4 Consistency
- LSI queries can use:
  - eventually consistent reads,
  - strongly consistent reads.
- This differs from GSIs.

##### 1.3.4.10.5 Capacity
- LSIs share read/write throughput with the base table.

##### 1.3.4.10.6 Creation
- LSIs must be defined when the table is created.
- They cannot be added to an existing table later.

##### 1.3.4.10.7 Quantity
- A table can have up to 5 LSIs.

#### 1.3.4.11 LSI Item-Collection Size Limit

##### 1.3.4.11.1 Constraint
- When a table has one or more LSIs, each item collection is limited to 10 GB.
- This includes:
  - base-table items sharing the partition-key value,
  - corresponding projected LSI data.

##### 1.3.4.11.2 Why
- LSI data remains local to the same base-table partition-key value and cannot distribute that item collection across multiple physical partitions in the same way as unrestricted table data.

##### 1.3.4.11.3 Exam Significance
- Very large item collections are an important reason an LSI may be inappropriate.

#### 1.3.4.12 Global Secondary Index (GSI)

##### 1.3.4.12.1 Key Structure
- GSI can use:
  - a different partition key,
  - and optionally a different sort key
  from the base table.

##### 1.3.4.12.2 Mental Model
- GSI answers:
  - "How can I query the same data through a completely different access key?"

##### 1.3.4.12.3 Example
- Base table:
  - PK = `CustomerId`
  - SK = `OrderId`.
- GSI:
  - PK = `OrderStatus`
  - SK = `OrderDate`.
- This can support an access pattern such as:
  - retrieve orders with a given indexed status ordered by date.
- The GSI partition key itself must still be designed to avoid hot-key problems.

##### 1.3.4.12.4 Scope
- A GSI spans data across the whole base table rather than being restricted to one base-table partition-key value.

##### 1.3.4.12.5 Consistency
- GSI reads are eventually consistent only.
- `ConsistentRead=true` is not supported for GSI queries.

##### 1.3.4.12.6 Capacity
- A GSI has capacity behavior separate from the base table.
- In provisioned mode, GSIs have their own provisioned read/write capacity settings.

##### 1.3.4.12.7 Creation Lifecycle
- GSIs can be created when the table is created and can also be added to an existing table later.

##### 1.3.4.12.8 Quantity
- Current DynamoDB default quota is 20 GSIs per table.

#### 1.3.4.13 LSI vs GSI

##### 1.3.4.13.1 Partition Key
- LSI:
  - same partition key as table.
- GSI:
  - partition key can be different.

##### 1.3.4.13.2 Sort Key
- LSI:
  - different sort key from table.
- GSI:
  - optional sort key can be different.

##### 1.3.4.13.3 Scope
- LSI:
  - local to one base-table partition-key value.
- GSI:
  - spans the table.

##### 1.3.4.13.4 Consistency
- LSI:
  - eventual or strong.
- GSI:
  - eventual only.

##### 1.3.4.13.5 Capacity
- LSI:
  - shares table capacity.
- GSI:
  - separate capacity behavior/settings.

##### 1.3.4.13.6 Creation
- LSI:
  - table creation only.
- GSI:
  - can be added later.

##### 1.3.4.13.7 Size Constraint
- LSI:
  - 10 GB item-collection limit.
- GSI:
  - does not have the LSI 10 GB item-collection constraint.

#### 1.3.4.14 Index Keys

##### 1.3.4.14.1 Allowed Key Attribute Types
- DynamoDB index key attributes must be top-level scalar attributes of type:
  - String,
  - Number,
  - Binary.
- Document, set, Boolean, and null types cannot be index key attributes.

##### 1.3.4.14.2 Uniqueness
- Base-table primary key must uniquely identify each item.
- Secondary-index key values do **not** need to be unique.
- Multiple base-table items can therefore map to the same secondary-index key.

#### 1.3.4.15 Attribute Projection

##### 1.3.4.15.1 Definition
- Projection is the set of base-table attributes copied into a secondary index.

##### 1.3.4.15.2 Automatically Projected
- Base-table primary-key attributes are always projected.
- Index key attributes are also part of the index.

##### 1.3.4.15.3 Projection Options
- `KEYS_ONLY`
- `INCLUDE`
- `ALL`.

#### 1.3.4.16 KEYS_ONLY Projection

##### 1.3.4.16.1 Contents
- Contains:
  - base-table primary-key attributes,
  - index key attributes.

##### 1.3.4.16.2 Benefit
- Smallest index.
- Lowest index storage/write amplification among projection choices.

##### 1.3.4.16.3 Trade-Off
- Non-key attributes needed by the application are not stored in the index.

#### 1.3.4.17 INCLUDE Projection

##### 1.3.4.17.1 Contents
- Key attributes plus explicitly selected non-key attributes.

##### 1.3.4.17.2 Benefit
- Useful when queries repeatedly need a small known set of attributes.

##### 1.3.4.17.3 Trade-Off
- Larger index and additional write/storage cost compared with `KEYS_ONLY`.

#### 1.3.4.18 ALL Projection

##### 1.3.4.18.1 Contents
- All base-table attributes are copied into the index.

##### 1.3.4.18.2 Benefit
- Index queries can return the complete indexed item without needing additional access.

##### 1.3.4.18.3 Trade-Off
- Largest index.
- More storage and write cost.

#### 1.3.4.19 GSI vs LSI Attribute Retrieval

##### 1.3.4.19.1 GSI
- GSI queries can return only attributes projected into the GSI.
- DynamoDB cannot automatically fetch non-projected attributes from the base table as part of a GSI Query.
- Application code must perform a separate base-table read if additional attributes are needed.

##### 1.3.4.19.2 LSI
- LSI queries can request non-projected attributes.
- DynamoDB can fetch those attributes from the base table automatically.

##### 1.3.4.19.3 LSI Fetch Trade-Off
- Base-table fetches add:
  - latency,
  - base-table read-capacity consumption.
- Frequently needed attributes should therefore often be projected.

#### 1.3.4.20 Index Maintenance

##### 1.3.4.20.1 Automatic Maintenance
- Application code does not manually write the same item to each secondary index.
- DynamoDB maintains secondary indexes as base-table items change.

##### 1.3.4.20.2 Write Amplification
- If an item participates in secondary indexes, table writes can also require index writes.
- More/larger indexes therefore increase:
  - storage,
  - write work/cost.

##### 1.3.4.20.3 Design Rule
- Create indexes for real access patterns.
- Do not index every potentially searchable attribute by default.

#### 1.3.4.21 Sparse Indexes

##### 1.3.4.21.1 Mechanism
- An item appears in a secondary index only when the required index key attributes exist on that item.
- If an index key attribute is absent, DynamoDB does not create an index entry for that item.

##### 1.3.4.21.2 Result
- An index can intentionally contain only a subset of base-table items.
- This is called a sparse index.

##### 1.3.4.21.3 Example
- Base table stores all orders.
- Only open orders contain:
  - `OpenOrderDate`.
- GSI:
  - PK = suitable workload-distributed key,
  - SK = `OpenOrderDate`.
- When the attribute is removed after completion, that item no longer participates in the index.

##### 1.3.4.21.4 Benefit
- Efficiently query a relatively small subset without scanning the full table.
- Can reduce index storage and write requirements.

#### 1.3.4.22 Index Overloading

##### 1.3.4.22.1 Concept
- DynamoDB items in one table do not need identical schemas.
- The same GSI key attributes can represent different logical meanings for different item types.

##### 1.3.4.22.2 Purpose
- One GSI can support several access patterns rather than creating a separate GSI for every logical attribute.

##### 1.3.4.22.3 Exam Depth
- Understand the concept.
- Detailed single-table modeling is beyond what the wording "define keys and indexing" requires.
- Do not assume one business query always requires one physical GSI.

#### 1.3.4.23 Access-Pattern-Driven Index Design

##### 1.3.4.23.1 Start With Queries
- Before creating an index, identify:
  - what value is known at query time,
  - what related records are needed,
  - required ordering/range conditions,
  - expected traffic distribution.

##### 1.3.4.23.2 Primary Key
- Use the table primary key for the dominant/native access patterns.

##### 1.3.4.23.3 Alternate Access Pattern
- Use an LSI when:
  - same partition key is appropriate,
  - alternate sort order/query is needed,
  - and the LSI constraints fit.
- Use a GSI when:
  - an alternate partition key is needed,
  - the access pattern crosses base-table partition keys.

##### 1.3.4.23.4 Avoid Scan as Schema
- A frequent query that requires scanning the whole table is often evidence that:
  - the primary-key model,
  - or secondary-index model
  does not represent that access pattern.

#### 1.3.4.24 Example Access-Pattern Model

##### 1.3.4.24.1 Requirement
- Store customers and orders.
- Access patterns:
  - get customer profile,
  - get customer's orders,
  - get customer's orders in date range,
  - find orders by another business dimension.

##### 1.3.4.24.2 Table Key
- `PK = CUSTOMER#<id>`
- `SK` examples:
  - `PROFILE`
  - `ORDER#<date>#<orderId>`.

##### 1.3.4.24.3 Native Queries
- `PK = CUSTOMER#123`
  - retrieves customer item collection.
- `PK = CUSTOMER#123 AND begins_with(SK, "ORDER#")`
  - retrieves orders.
- Sort-key range can support date-oriented access when encoded appropriately.

##### 1.3.4.24.4 Alternate Query
- If the application must query orders by a different dimension not represented in the table key, create a suitable GSI rather than scanning the whole table.

##### 1.3.4.24.5 Lesson
- The model is not driven by entity normalization.
- It is driven by the reads/writes the application must perform.

#### 1.3.4.25 Index Distribution

##### 1.3.4.25.1 GSI Partition Keys
- A GSI has its own partition key.
- It therefore has its own data/traffic distribution considerations.

##### 1.3.4.25.2 Hot Index
- A well-distributed base table can still have a hot GSI if its GSI partition key has low cardinality or skewed traffic.

##### 1.3.4.25.3 Connection
- Apply the high-cardinality/balanced-access principles from Skill 1.3.1 independently to GSI keys.

#### 1.3.4.26 Important Distinctions

##### 1.3.4.26.1 Primary Key vs Partition Key
- Primary key = complete unique identifier.
- It can be:
  - partition key only,
  - partition key + sort key.
- Partition key is one component of the key schema.

##### 1.3.4.26.2 Partition Key vs Sort Key
- Partition key determines distribution and Query partition.
- Sort key orders/groups items within one partition-key value.

##### 1.3.4.26.3 Base Table vs Secondary Index
- Base table primary key defines native access.
- Secondary index provides an alternate key-based access path.

##### 1.3.4.26.4 LSI vs GSI
- LSI → same PK, alternate SK.
- GSI → alternate PK and optional alternate SK.

##### 1.3.4.26.5 Projection vs Index Key
- Index key determines how index data can be queried.
- Projection determines what additional attributes are available from the index.
- Projecting an attribute does not make it searchable as an index key.

##### 1.3.4.26.6 Sparse Index vs Filter
- Sparse index excludes items because index-key attributes do not exist.
- FilterExpression reads matching key-range data and filters afterward.
- Sparse indexing can therefore avoid storing/reading irrelevant items for that access path.

#### 1.3.4.27 Common Exam Traps

##### 1.3.4.27.1 "Sort Key Distributes Data"
- False.
- Partition key drives physical distribution.

##### 1.3.4.27.2 "GSI Must Use Table Partition Key"
- False.
- That restriction describes LSI.

##### 1.3.4.27.3 "LSI Can Be Added Later"
- False.
- LSI must be defined at table creation.

##### 1.3.4.27.4 "GSI Supports Strong Reads"
- False.
- GSI reads are eventual only.

##### 1.3.4.27.5 "Index Keys Must Be Unique"
- False.
- Secondary-index key values can repeat.

##### 1.3.4.27.6 "Projected Attribute Is Queryable as a Key"
- False.
- Projection makes an attribute available in index results; it does not turn the attribute into an index key.

##### 1.3.4.27.7 "More Indexes Are Always Better"
- False.
- Indexes add storage and write overhead and should support defined access patterns.

##### 1.3.4.27.8 "LSI and GSI Retrieve Non-Projected Attributes the Same Way"
- False.
- LSI can fetch from the base table.
- GSI cannot fetch non-projected attributes as part of the index Query.
