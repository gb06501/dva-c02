### 1.3.9 Use specialized data stores based on access patterns

#### 1.3.9.1 Exam Context

##### 1.3.9.1.1 Skill Scope
- DVA-C02 Domain 1, Task 3 is **Use data stores in application development**.
- Skill 1.3.9 requires developers to **use specialized data stores based on access patterns (for example, Amazon OpenSearch Service)**.
- The wording makes the decision principle explicit:
  - start with the application's **access pattern**,
  - then select the store designed for that pattern.
- Amazon OpenSearch Service is explicitly named by the exam guide and therefore receives the deepest treatment here.
- Other in-scope purpose-built stores are included primarily as comparison points.

##### 1.3.9.1.2 Core Mental Model
- Do not start with:

  `we use database X → how can we force this requirement into it?`

- Start with:

  `what does the application need to do with the data?`
  → `what access pattern does that imply?`
  → `which data model/indexing mechanism supports it naturally?`
  → `which AWS data store fits?`

##### 1.3.9.1.3 Purpose-Built Data
- Different stores optimize different dimensions:
  - relationships,
  - keys,
  - full-text search,
  - time,
  - documents,
  - analytics,
  - low-latency in-memory access.
- AWS Well-Architected guidance recommends selecting purpose-built data stores that best support the workload's data access and storage requirements.

#### 1.3.9.2 Access Pattern First

##### 1.3.9.2.1 Access Pattern Questions
- How is data identified?
- Which fields are searched?
- Are exact-key lookups dominant?
- Are relationships traversed?
- Is full-text relevance required?
- Is data ordered primarily by time?
- Are analytical aggregations required?
- Is the workload transactional?
- Is sub-millisecond/microsecond access required?
- What read/write scale is expected?

##### 1.3.9.2.2 Decision Principle
- Data shape alone is not enough.
- The same business entity can legitimately exist in multiple stores because different applications need different access patterns.

##### 1.3.9.2.3 Example
- Product data:
  - DynamoDB → product lookup by known ID/access patterns.
  - OpenSearch → user searches `"wireless noise cancelling headphones"` with relevance/filtering.
- Same domain data.
- Different access pattern.
- Different optimized representation.

#### 1.3.9.3 Polyglot Persistence

##### 1.3.9.3.1 Concept
- One application/system can use multiple persistence technologies.

##### 1.3.9.3.2 Why
- One store rarely optimizes every access pattern equally well.

##### 1.3.9.3.3 Example
- DynamoDB:
  - operational source of truth.
- OpenSearch:
  - search-optimized projection.
- S3:
  - durable object/history/archive storage.

##### 1.3.9.3.4 Trade-Off
- More stores introduce:
  - synchronization,
  - consistency,
  - operational,
  - cost
  complexity.
- Add a specialized store only when its access-pattern benefit justifies that complexity.

#### 1.3.9.4 Primary Store vs Specialized Projection

##### 1.3.9.4.1 Primary Store
- Holds authoritative operational data.

##### 1.3.9.4.2 Specialized Store
- Can hold a representation optimized for a different query pattern.

##### 1.3.9.4.3 Example

  `DynamoDB`
  → `change/event pipeline`
  → `OpenSearch index`

- Application writes authoritative state to DynamoDB.
- Search application reads the search-optimized OpenSearch representation.

##### 1.3.9.4.4 Consequence
- Search projection can be eventually consistent with the primary store.
- Application architecture must understand which store is authoritative.

#### 1.3.9.5 Amazon OpenSearch Service

##### 1.3.9.5.1 Purpose
- Amazon OpenSearch Service is a managed AWS service for deploying, operating, and scaling OpenSearch.

##### 1.3.9.5.2 Core Workloads
- Search.
- Full-text search.
- Log analytics.
- Real-time application monitoring.
- Clickstream analysis.
- Operational analytics.
- Vector/semantic search in current OpenSearch capabilities.

##### 1.3.9.5.3 Developer Perspective
- Ingest/index documents.
- Search indexed data.
- Filter.
- Sort.
- Aggregate.
- Analyze.
- Build application search experiences.

#### 1.3.9.6 OpenSearch Mental Model

##### 1.3.9.6.1 Flow

  `source data`
  → `index document`
  → `OpenSearch index`
  → `query`
  → `matching documents ranked/aggregated`
  → `application`

##### 1.3.9.6.2 Key Difference From Key-Value Lookup
- DynamoDB normally expects access through known key/index patterns.
- OpenSearch builds searchable indexes over document fields so applications can search data by content.

##### 1.3.9.6.3 Key Difference From Relational Query
- OpenSearch is a search and analytics engine.
- It should not automatically replace a relational transactional database merely because it supports powerful queries.

#### 1.3.9.7 Documents

##### 1.3.9.7.1 Basic Unit
- OpenSearch stores/indexes data as JSON documents.

##### 1.3.9.7.2 Example

  Product:
  - productId
  - name
  - description
  - category
  - brand
  - price

##### 1.3.9.7.3 Searchable Representation
- Fields can be mapped/indexed according to how they need to be searched, filtered, sorted, or aggregated.

#### 1.3.9.8 Index

##### 1.3.9.8.1 Concept
- An OpenSearch index contains documents and the structures needed to search them.

##### 1.3.9.8.2 Analogy
- Do not equate an OpenSearch index directly with a DynamoDB secondary index.
- In OpenSearch, the index is the central searchable collection of documents.

##### 1.3.9.8.3 Developer Operations
- Index documents.
- Update documents.
- Delete documents.
- Search documents.

#### 1.3.9.9 Mapping

##### 1.3.9.9.1 Purpose
- Mapping defines how document fields are represented/indexed.

##### 1.3.9.9.2 Why It Matters
- Field type influences supported:
  - search,
  - sorting,
  - filtering,
  - aggregation behavior.

##### 1.3.9.9.3 Mental Model
- DynamoDB:
  - key/index design starts from known access patterns.
- OpenSearch:
  - document mapping/indexing design starts from how content will be searched and analyzed.

#### 1.3.9.10 Text vs Keyword

##### 1.3.9.10.1 Text
- Intended for analyzed full-text content.
- Text can be broken into searchable terms during analysis.

##### 1.3.9.10.2 Keyword
- Intended for exact-value behavior.
- Useful for:
  - exact filtering,
  - sorting,
  - aggregations.

##### 1.3.9.10.3 Example
- `description` → text.
- `productCategory` → keyword.
- `brand` may need exact filtering/aggregation and therefore a keyword representation.

##### 1.3.9.10.4 Exam Mindset
- Full-text relevance field and exact filter field are different access patterns even inside the same document.

#### 1.3.9.11 Analysis

##### 1.3.9.11.1 Purpose
- Full-text search requires transforming text into searchable terms.

##### 1.3.9.11.2 Analyzer Concept
- Analysis can include:
  - character processing,
  - tokenization,
  - token filters.

##### 1.3.9.11.3 Consequence
- Search can match terms within human-language text rather than requiring exact whole-string equality.

#### 1.3.9.12 Inverted Index

##### 1.3.9.12.1 Mental Model
- Instead of only asking:

  `document ID → document`

- Search engines maintain structures conceptually like:

  `term → documents containing term`

##### 1.3.9.12.2 Why
- Enables efficient full-text retrieval across large document collections.

##### 1.3.9.12.3 Skill Value
- You do not need implementation-level search-engine internals.
- Understand why OpenSearch naturally supports text-search access patterns that key-value databases do not.

#### 1.3.9.13 Full-Text Search

##### 1.3.9.13.1 Requirement
- User searches natural-language text.

##### 1.3.9.13.2 Example
- Search:
  - `"wireless headphones"`
- Desired:
  - relevant products containing/matching those concepts,
  - not merely a record whose primary key exactly equals the query.

##### 1.3.9.13.3 OpenSearch Fit
- Search engine:
  - analyzes text,
  - finds matching documents,
  - ranks results by relevance.

#### 1.3.9.14 Relevance

##### 1.3.9.14.1 Search Requirement
- Search often asks:
  - "Which results are most relevant?"
- This differs from:
  - "Which item has this exact key?"

##### 1.3.9.14.2 Ranking
- OpenSearch can score matching documents and order results according to relevance.

##### 1.3.9.14.3 Use Cases
- Ecommerce product search.
- Documentation search.
- Content discovery.
- Knowledge search.

#### 1.3.9.15 Filtering

##### 1.3.9.15.1 Purpose
- Restrict results using exact conditions.

##### 1.3.9.15.2 Example
- Search:
  - `"running shoes"`
- Filter:
  - category = `shoes`
  - brand = `X`
  - price range.

##### 1.3.9.15.3 Combination
- OpenSearch is useful when applications need:
  - text relevance
  + structured filtering
  + sorting/aggregation.

#### 1.3.9.16 Aggregations

##### 1.3.9.16.1 Purpose
- Summarize/indexed data across matching documents.

##### 1.3.9.16.2 Examples
- Count by category.
- Average value.
- Distribution over time.
- Top terms.
- Buckets by field/range.

##### 1.3.9.16.3 Application Use
- Search facets.
- Operational dashboards.
- Log analytics.
- Exploratory analysis.

#### 1.3.9.17 Search vs Querying a Database

##### 1.3.9.17.1 Known Key
- Requirement:
  - get customer ID 123.
- Natural fit:
  - key-value/database lookup.

##### 1.3.9.17.2 Known Relational Condition
- Requirement:
  - transactional relational query/join with integrity constraints.
- Natural fit:
  - relational database.

##### 1.3.9.17.3 Human Search
- Requirement:
  - find documents/products/log messages by terms, relevance, filters, facets.
- Natural fit:
  - OpenSearch.

##### 1.3.9.17.4 Rule
- "Search" in normal language does not automatically mean OpenSearch.
- Identify the actual access pattern.

#### 1.3.9.18 OpenSearch Domains

##### 1.3.9.18.1 Provisioned Model
- An OpenSearch Service domain represents a managed OpenSearch cluster.

##### 1.3.9.18.2 Domain Configuration
- Includes settings such as:
  - engine/version,
  - instance types,
  - instance counts,
  - storage,
  - networking/security,
  - availability configuration.

##### 1.3.9.18.3 Developer Boundary
- Know that a domain is the provisioned OpenSearch Service deployment.
- Detailed production cluster sizing is beyond the core DVA skill.

#### 1.3.9.19 OpenSearch Serverless

##### 1.3.9.19.1 Model
- OpenSearch Serverless provides an on-demand, auto-scaling OpenSearch option without developers managing clusters/instances directly.

##### 1.3.9.19.2 Collection
- Serverless organizes data in **collections** rather than provisioned domains.

##### 1.3.9.19.3 Current Collection Types
- Search.
- Time series.
- Vector search.

##### 1.3.9.19.4 Selection
- Collection type is selected according to:
  - data being ingested,
  - how it will be queried.

##### 1.3.9.19.5 Exam Mindset
- Provisioned OpenSearch → domain.
- OpenSearch Serverless → collection.

#### 1.3.9.20 OpenSearch Search Collection

##### 1.3.9.20.1 Access Pattern
- Full-text application search.

##### 1.3.9.20.2 Examples
- Ecommerce search.
- Internal document search.
- Content discovery.

##### 1.3.9.20.3 Storage Behavior
- Current Serverless search collections keep data in hot storage for fast query response.

#### 1.3.9.21 OpenSearch Time-Series Collection

##### 1.3.9.21.1 Access Pattern
- Large volumes of semi-structured machine-generated data ordered/analyzed over time.

##### 1.3.9.21.2 Examples
- Logs.
- Operational telemetry.
- Security/event analysis.

##### 1.3.9.21.3 Storage
- Current Serverless time-series collections use hot and warm storage so recent data can be optimized for frequent access.

#### 1.3.9.22 OpenSearch Vector Search

##### 1.3.9.22.1 Access Pattern
- Similarity/semantic search over vector embeddings.

##### 1.3.9.22.2 Difference
- Keyword search:
  - matches terms/text.
- Vector search:
  - finds items close in embedding/vector space.

##### 1.3.9.22.3 Use Cases
- Semantic search.
- Recommendation/similarity.
- Generative-AI retrieval patterns.

##### 1.3.9.22.4 Exam Boundary
- Current AWS OpenSearch supports vector search, so recognize the access pattern.
- Do not expand into detailed embedding/RAG implementation unless another exam objective requires it.

#### 1.3.9.23 Search Application Architecture

##### 1.3.9.23.1 AWS-Documented Pattern

  `client`
  → `API Gateway`
  → `Lambda`
  → `OpenSearch Service`

##### 1.3.9.23.2 Why Backend
- AWS advises against exposing unsigned public OpenSearch APIs directly to browser/client code.

##### 1.3.9.23.3 Developer Role
- Application backend:
  - authenticates/authorizes,
  - constructs search request,
  - calls OpenSearch,
  - transforms result,
  - returns application response.

#### 1.3.9.24 Data Ingestion

##### 1.3.9.24.1 Requirement
- Data must reach OpenSearch before it can be searched.

##### 1.3.9.24.2 Options
- Application indexes documents directly through OpenSearch APIs.
- Bulk indexing.
- AWS integrations/pipelines.
- OpenSearch Ingestion for supported pipeline patterns.

##### 1.3.9.24.3 Mental Model
- Search performance depends not only on queries but also on how searchable representations are produced and indexed.

#### 1.3.9.25 OpenSearch as Secondary Search Index

##### 1.3.9.25.1 Common Pattern

  `application write`
  → `primary database`
  → `event/change`
  → `OpenSearch`

##### 1.3.9.25.2 Benefit
- Primary store optimized for transactional/key access.
- OpenSearch optimized for discovery/search.

##### 1.3.9.25.3 Trade-Off
- Search view can lag behind primary state.
- Synchronization failures must be observable/recoverable.

##### 1.3.9.25.4 Exam Rule
- If OpenSearch is a projection, do not automatically treat it as authoritative for transactional state.

#### 1.3.9.26 DynamoDB

##### 1.3.9.26.1 Data Model
- Key-value/document.

##### 1.3.9.26.2 Best-Fit Access Patterns
- Known partition-key access.
- Predictable key/index query patterns.
- Massive operational scale with low-latency key access.

##### 1.3.9.26.3 Not Natural For
- Arbitrary full-text relevance search across many fields.

##### 1.3.9.26.4 Decision
- Known key/predictable access → DynamoDB.
- Search text/content/relevance → OpenSearch.

#### 1.3.9.27 RDS / Aurora

##### 1.3.9.27.1 Data Model
- Relational.

##### 1.3.9.27.2 Best-Fit Access Patterns
- Relational transactions.
- Referential integrity.
- SQL.
- Structured relationships/joins.
- Traditional relational application models.

##### 1.3.9.27.3 Decision
- Need relational integrity/transactions → relational database.
- Do not choose OpenSearch merely because flexible querying is desired.

#### 1.3.9.28 ElastiCache

##### 1.3.9.28.1 Data Model
- In-memory caching/data structures.

##### 1.3.9.28.2 Best-Fit Access Patterns
- Frequently reused data requiring very low latency.
- Cache/session/counter/leaderboard patterns depending on engine.

##### 1.3.9.28.3 Distinction
- Cache optimizes repeated access.
- OpenSearch optimizes search/discovery.
- Detailed caching belongs to Skill 1.3.8.

#### 1.3.9.29 S3

##### 1.3.9.29.1 Data Model
- Object storage.

##### 1.3.9.29.2 Best-Fit Access Patterns
- Retrieve/store objects by object key.
- Large durable object storage.
- Data lake/archive/static content patterns.

##### 1.3.9.29.3 Distinction
- S3 stores objects durably.
- OpenSearch indexes searchable representations.
- An architecture can use both.

#### 1.3.9.30 Document Database

##### 1.3.9.30.1 Purpose-Built Model
- AWS identifies Amazon DocumentDB as a document database for JSON-like/semi-structured data.

##### 1.3.9.30.2 Access Pattern
- Application works naturally with document-oriented records and document queries.

##### 1.3.9.30.3 Distinction From OpenSearch
- Document database:
  - primary operational document persistence.
- OpenSearch:
  - search/analytics indexing over documents.

##### 1.3.9.30.4 Scope
- Include as purpose-built comparison only if it is present in the exam's current in-scope service list.

#### 1.3.9.31 Graph Database

##### 1.3.9.31.1 Purpose-Built Model

##### 1.3.9.31.2 Access Pattern
- Traverse relationships between highly connected data.

##### 1.3.9.31.3 Examples
- Social graphs.
- Recommendation relationships.
- Fraud relationship analysis.
- Knowledge graphs.

##### 1.3.9.31.4 Decision
- "Find records containing this text" → search.
- "Find paths/relationships between connected entities" → graph.

##### 1.3.9.31.5 Scope

##### 1.3.9.32.3 Examples

##### 1.3.9.32.4 OpenSearch Comparison

##### 1.3.9.33.1 Purpose-Built Model

#### 1.3.9.34 Access-Pattern Decision Tree

##### 1.3.9.34.1 Known Key / Predictable NoSQL Access
- → DynamoDB.

##### 1.3.9.34.2 Relational Transactions / SQL / Integrity
- → RDS or Aurora.

##### 1.3.9.34.3 Full-Text / Relevance / Faceted Search / Log Search
- → OpenSearch Service.

##### 1.3.9.34.4 Frequently Reused Data / Cache
- → ElastiCache.
- DynamoDB-specific repeated read acceleration → DAX.

##### 1.3.9.34.5 Durable Object by Key
- → S3.

##### 1.3.9.34.6 Highly Connected Relationship Traversal
- → Neptune, when in exam scope.

##### 1.3.9.34.7 Time-Ordered Measurements
- → Timestream, when in exam scope.

##### 1.3.9.34.8 JSON-Like Operational Documents
- → DocumentDB, when in exam scope.

##### 1.3.9.34.9 Cassandra/Wide-Column Pattern
- → Keyspaces, when in exam scope.

#### 1.3.9.35 OpenSearch Decision Clues

##### 1.3.9.35.1 Strong Clues
- Full-text.
- Search relevance.
- Search across many text fields.
- Fuzzy/discovery-oriented search.
- Facets.
- Aggregations over search results.
- Log analytics.
- Clickstream analytics.
- Operational search.
- Semantic/vector similarity.

##### 1.3.9.35.2 Weak Clues
- "Need to query data."
- "Need low latency."
- "Need scalable database."
- These alone do not imply OpenSearch.

##### 1.3.9.35.3 Rejection Clues
- Strong ACID transaction is central.
- Exact primary-key lookup dominates.
- Authoritative durable object storage is the main requirement.
- Strong relational integrity is required.

#### 1.3.9.36 Search Data Duplication

##### 1.3.9.36.1 Duplication Can Be Intentional
- Search index can duplicate data from the source database.

##### 1.3.9.36.2 Why
- The duplicate representation is optimized for a different access pattern.

##### 1.3.9.36.3 Cost
- Additional:
  - storage,
  - ingestion,
  - synchronization,
  - failure handling.

##### 1.3.9.36.4 Principle
- Duplication is justified when it creates a materially better access path.

#### 1.3.9.37 Consistency of Specialized Projections

##### 1.3.9.37.1 Asynchronous Update
- Event-driven indexing commonly introduces eventual consistency.

##### 1.3.9.37.2 User Effect
- A newly updated database record may not immediately appear in search results.

##### 1.3.9.37.3 Design Question
- Is that delay acceptable for the search experience?

##### 1.3.9.37.4 If Not
- Architecture may require:
  - synchronous indexing,
  - read-after-write fallback,
  - different source-of-truth behavior,
  depending on requirements.

#### 1.3.9.38 Failure Model

##### 1.3.9.38.1 Primary Write Succeeds, Indexing Fails
- Authoritative data exists.
- Search projection becomes stale/incomplete.

##### 1.3.9.38.2 Required Capability
- Detect failed indexing.
- Retry/replay.
- Rebuild index from authoritative data when necessary.

##### 1.3.9.38.3 Principle
- Derived specialized indexes should be reproducible where practical.

#### 1.3.9.39 Monitoring

##### 1.3.9.39.1 OpenSearch Operational Signals
- Cluster/domain health.
- Storage.
- CPU/memory pressure.
- indexing/search latency.
- errors.
- shard behavior.

##### 1.3.9.39.2 Application Signals
- Search latency.
- zero-result rate.
- indexing lag.
- indexing failures.
- search relevance/business quality where measurable.

##### 1.3.9.39.3 Why
- A technically healthy search cluster can still provide poor application search if:
  - mapping is wrong,
  - data is stale,
  - relevance is poor.

##### 1.3.9.40.1 OpenSearch Access

  - encryption capabilities.

##### 1.3.9.40.2 Application Pattern
- Prefer controlled backend access rather than exposing unrestricted OpenSearch endpoints directly to public clients.

##### 1.3.9.40.3 Scope

#### 1.3.9.41 Common Exam Traps

##### 1.3.9.41.1 "OpenSearch Is a Faster General Database"
- Wrong.
- It is specialized for search and analytics access patterns.

##### 1.3.9.41.2 "Need Search → Always OpenSearch"
- Wrong.
- Exact key lookup or structured relational query is also colloquially called searching.
- Look for full-text/relevance/analytics requirements.

##### 1.3.9.41.3 "DynamoDB Can Replace OpenSearch With Enough GSIs"
- Poor mental model.
- GSIs provide alternate key-based access patterns, not general full-text relevance search.

##### 1.3.9.41.4 "OpenSearch Should Be the Transactional Source of Truth"
- Usually wrong when the workload fundamentally requires transactional database semantics.

##### 1.3.9.41.5 "Duplicating Data Into OpenSearch Is Always Bad"
- False.
- A search-optimized projection is a legitimate purpose-built architecture.

##### 1.3.9.41.6 "Search Index Is Immediately Consistent With Source Database"
- Not necessarily.
- Asynchronous ingestion commonly creates eventual consistency.

##### 1.3.9.41.7 "OpenSearch Index = DynamoDB Secondary Index"
- False.
- They are fundamentally different indexing/storage concepts.

##### 1.3.9.41.8 "ElastiCache and OpenSearch Solve the Same Problem"
- False.
- Cache optimizes repeated access.
- OpenSearch provides a specialized search access path.

##### 1.3.9.41.9 "One Database Should Store Everything"
- AWS purpose-built guidance rejects this as a default assumption.
- Select stores according to workload access patterns.
