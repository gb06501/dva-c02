### 1.3.5 Serialize and deserialize data to provide persistence to a data store

#### 1.3.5.1 Exam Context

##### 1.3.5.1.1 Skill Scope
- DVA-C02 Domain 1, Task 3 is **Use data stores in application development**.
- Skill 1.3.5 requires the developer to **serialize and deserialize data to provide persistence to a data store**.
- The exam guide does not name a specific service or serialization format for this skill.
- Therefore the frame is broader than DynamoDB alone:
  - application data exists as language/runtime objects,
  - a persistent store accepts a defined representation,
  - application code must convert between those two forms.
- DynamoDB is the clearest AWS-documented example because the AWS SDKs expose explicit mappings between application objects and DynamoDB attribute values.

##### 1.3.5.1.2 Core Mental Model
- In-memory application representation:
  - object,
  - class instance,
  - record,
  - collection,
  - domain type.
- Serialization:
  - application representation → storable representation.
- Persistence:
  - write the serialized representation to the data store.
- Retrieval:
  - read the stored representation.
- Deserialization:
  - stored representation → application representation.

##### 1.3.5.1.3 End-to-End Flow
- Think:

  `domain object`
  → `mapping / serialization`
  → `data-store representation`
  → `persistent storage`
  → `read`
  → `deserialization / mapping`
  → `domain object`

- Correctness depends on the two directions agreeing about:
  - field names,
  - types,
  - nested structures,
  - optional/null values,
  - custom types,
  - schema/version evolution.

#### 1.3.5.2 Serialization

##### 1.3.5.2.1 Definition
- Serialization converts an in-memory representation into a representation suitable for storage or transmission.

##### 1.3.5.2.2 Examples
- Java object → DynamoDB attribute map.
- Application object → JSON document.
- Domain-specific type → String/Number/Binary representation.
- Nested object → DynamoDB Map attribute.

##### 1.3.5.2.3 Persistence Boundary
- Serialization itself does not persist data.
- Persistence occurs when the resulting representation is written to a durable data store.

#### 1.3.5.3 Deserialization

##### 1.3.5.3.1 Definition
- Deserialization reconstructs an application-level representation from stored data.

##### 1.3.5.3.2 Example
- DynamoDB returns attribute values.
- The application or SDK mapping layer converts those values into:
  - strings,
  - numbers,
  - collections,
  - nested objects,
  - domain objects.

##### 1.3.5.3.3 Symmetry
- A value written through a serialization rule must be interpretable by the corresponding deserialization rule.
- Custom mappings therefore normally require transformations in both directions.

#### 1.3.5.4 Representation vs Persistence

##### 1.3.5.4.1 Different Concerns
- Serialization answers:
  - **How is the application's value represented?**
- Persistence answers:
  - **Where and how is that representation stored durably?**

##### 1.3.5.4.2 Example
- JSON serialization can produce a JSON string/document.
- That serialized representation could then be persisted in different stores.
- JSON itself is a representation, not a persistence service.

##### 1.3.5.4.3 Exam Trap
- Do not confuse:
  - serialization format,
  - database data model,
  - storage operation.

#### 1.3.5.5 DynamoDB Data Representation

##### 1.3.5.5.1 Schemaless Items
- DynamoDB is schemaless except for primary-key attributes.
- Items in the same table do not need identical non-key attributes.

##### 1.3.5.5.2 Scalar Types
- DynamoDB scalar attribute types include:
  - String,
  - Number,
  - Binary,
  - Boolean,
  - Null.

##### 1.3.5.5.3 Document Types
- DynamoDB document types are:
  - List,
  - Map.
- They can represent nested structures similar to JSON documents.

##### 1.3.5.5.4 Set Types
- DynamoDB supports:
  - String Set,
  - Number Set,
  - Binary Set.

##### 1.3.5.5.5 Key-Type Restriction
- DynamoDB primary-key and index-key attributes must use:
  - String,
  - Number,
  - Binary.
- This is a storage-model constraint that serialization/mapping code must respect.

#### 1.3.5.6 Low-Level DynamoDB Mapping

##### 1.3.5.6.1 Low-Level Client
- A low-level DynamoDB SDK client exposes DynamoDB operations directly.
- Application code works explicitly with DynamoDB attribute values.

##### 1.3.5.6.2 Example Mental Model
- Application:
  - `customer.id` is a language String.
- DynamoDB request:
  - `customerId` is represented as a DynamoDB String attribute.
- Application code or an SDK abstraction performs that mapping.

##### 1.3.5.6.3 Benefit
- Maximum control over:
  - exact attribute names,
  - DynamoDB types,
  - request structure.

##### 1.3.5.6.4 Trade-Off
- More mapping/serialization code is handled explicitly by the developer.

#### 1.3.5.7 Object Persistence Interfaces

##### 1.3.5.7.1 AWS Concept
- AWS documents higher-level DynamoDB object persistence interfaces.
- These allow developers to work with application objects rather than manually constructing every low-level data-plane representation.

##### 1.3.5.7.2 Current SDK Examples
- AWS SDK for Java 2.x:
  - DynamoDB Enhanced Client.
- AWS SDK for .NET:
  - object persistence model is also available.
- Exact SDK APIs differ by programming language.

##### 1.3.5.7.3 Mental Model
- Define how:
  - application class/property
  maps to
  - DynamoDB table/item/attribute.
- The mapper handles conversion during:
  - writes,
  - reads.

#### 1.3.5.8 DynamoDB Enhanced Client — Java 2.x

##### 1.3.5.8.1 Purpose
- The DynamoDB Enhanced Client provides a high-level API for mapping client-side Java classes to DynamoDB items.

##### 1.3.5.8.2 Mapping
- A `TableSchema` defines how an application object maps to DynamoDB attributes.
- The mapping can be built using:
  - annotated classes,
  - programmatic schema builders.

##### 1.3.5.8.3 Write Flow
- Java object
  → TableSchema/converters
  → DynamoDB AttributeValues
  → table item.

##### 1.3.5.8.4 Read Flow
- DynamoDB item
  → AttributeValues
  → TableSchema/converters
  → Java object.

##### 1.3.5.8.5 Exam Meaning
- This is a concrete AWS example of serialization/deserialization used to provide persistence without manually handling every attribute conversion.

#### 1.3.5.9 Static vs Dynamic Item Structures

##### 1.3.5.9.1 Consistent Structure
- When items have a consistent application structure, AWS documents using a statically typed `TableSchema`.
- The application can map a class directly to the table representation.

##### 1.3.5.9.2 Dynamic Structure
- When items vary in structure, the DynamoDB Enhanced Document API supports document-oriented access.
- A `DocumentTableSchema` requires a statically defined primary key while document contents can vary.

##### 1.3.5.9.3 Decision
- Stable domain model → typed object mapping is natural.
- Flexible/document model → document-oriented mapping can be more appropriate.

#### 1.3.5.10 Attribute Conversion

##### 1.3.5.10.1 Problem
- Programming languages have richer type systems than many persistence stores.
- Not every application type has a one-to-one native database type.

##### 1.3.5.10.2 Converter
- A converter defines:
  - application type → DynamoDB attribute type,
  - DynamoDB attribute type → application type.

##### 1.3.5.10.3 Java Enhanced Client
- AWS SDK for Java 2.x provides `AttributeConverter` and `AttributeConverterProvider`.
- Built-in converters handle many common Java types.
- Custom converters can handle application-specific types.

#### 1.3.5.11 Custom Types

##### 1.3.5.11.1 Example Domain Type
- Application type:
  - `Address`,
  - `Money`,
  - `Coordinates`,
  - domain identifier.

##### 1.3.5.11.2 Storage Choices
- A custom type can be mapped into a DynamoDB-supported representation such as:
  - String,
  - Number,
  - Binary,
  - Map.

##### 1.3.5.11.3 Example
- `Address` object:
  - street,
  - city,
  - postal code.
- Serialize as a DynamoDB Map.
- Deserialize the Map back into an `Address` object.

##### 1.3.5.11.4 Design Requirement
- The stored representation should preserve the information needed to reconstruct the domain value correctly.

#### 1.3.5.12 Nested Objects and Collections

##### 1.3.5.12.1 Nested Object
- AWS SDK mapping can convert nested Java beans to DynamoDB Map document attributes.

##### 1.3.5.12.2 Collections
- Application collections can map to DynamoDB structures such as:
  - List,
  - Map,
  - supported Set types.

##### 1.3.5.12.3 Implication
- Serialization does not need to flatten every domain model into primitive top-level attributes.
- DynamoDB document types can preserve nested structures where appropriate.

#### 1.3.5.13 JSON

##### 1.3.5.13.1 Role
- JSON is a common serialized representation for structured application data.
- It is especially common across:
  - APIs,
  - events,
  - documents.

##### 1.3.5.13.2 DynamoDB Document API
- The Java 2.x Enhanced Document API can create DynamoDB documents from JSON.
- It can also work with schemaless/document-style item content.

##### 1.3.5.13.3 Important Distinction
- DynamoDB's native storage model is typed `AttributeValue` data.
- JSON is one way application/document data can be represented and converted.
- Do not assume that every DynamoDB item is simply stored internally as an arbitrary JSON string.

#### 1.3.5.14 Attribute Names

##### 1.3.5.14.1 Application Name vs Stored Name
- Application property names do not necessarily have to equal DynamoDB attribute names.

##### 1.3.5.14.2 Mapping
- Mapping configuration/annotations can define the persisted attribute name.

##### 1.3.5.14.3 Why Useful
- Allows:
  - domain naming conventions in code,
  - independent persisted naming,
  - controlled schema evolution.

#### 1.3.5.15 Ignored / Non-Persistent Fields

##### 1.3.5.15.1 Application-Only Data
- Not every property of an application object must be persisted.

##### 1.3.5.15.2 Java Enhanced Client
- AWS documents annotations such as `@DynamoDbIgnore` for excluding properties from DynamoDB mapping.

##### 1.3.5.15.3 Use Cases
- Calculated values.
- Runtime-only state.
- Internal helper fields.
- Data that should not be stored.

#### 1.3.5.16 Null, Missing, and Optional Data

##### 1.3.5.16.1 Distinction
- Application code should distinguish where relevant between:
  - field absent,
  - explicit null,
  - empty value,
  - default value.

##### 1.3.5.16.2 DynamoDB
- DynamoDB supports a Null attribute type.
- It also naturally supports items where an optional non-key attribute is absent.

##### 1.3.5.16.3 Deserialization
- Mapping code must define how missing/null stored values map back into the application's type system.

##### 1.3.5.16.4 Exam Mindset
- Serialization correctness is not only about the happy path; optional data must round-trip predictably.

#### 1.3.5.17 Dates and Times

##### 1.3.5.17.1 Storage Representation
- DynamoDB does not have a dedicated date/time scalar type.
- Applications map time values to supported DynamoDB types.

##### 1.3.5.17.2 Common Representations
- ISO-8601 String.
- Numeric epoch timestamp.

##### 1.3.5.17.3 Design Consequence
- Representation affects:
  - sorting,
  - range queries,
  - readability,
  - interoperability.

##### 1.3.5.17.4 Important Connection
- If the attribute participates in a key or query pattern, choose a serialized representation whose ordering semantics support that access pattern.

#### 1.3.5.18 Numeric Representation

##### 1.3.5.18.1 DynamoDB Number
- DynamoDB transmits numbers over its API as strings to preserve compatibility across programming languages.
- DynamoDB treats them as Number attributes for mathematical operations.

##### 1.3.5.18.2 Application Conversion
- SDKs/mappers convert between application numeric types and DynamoDB Number values.

##### 1.3.5.18.3 Precision
- Developers should ensure the chosen application type and conversion preserve required numeric precision.

#### 1.3.5.19 Binary Data

##### 1.3.5.19.1 DynamoDB Binary
- DynamoDB supports Binary attributes.

##### 1.3.5.19.2 Serialization
- Application binary values must be represented through the SDK's binary representation.

##### 1.3.5.19.3 Design Boundary
- "Can be stored as Binary" does not mean DynamoDB is automatically the correct store for arbitrarily large binary objects.
- Data-store selection based on access pattern belongs primarily to Skill 1.3.9.

#### 1.3.5.20 Schema Evolution

##### 1.3.5.20.1 Persistent Data Outlives Code
- Stored data can remain after application classes and serialization logic change.

##### 1.3.5.20.2 Compatibility Question
- New application code may need to deserialize data written by an older application version.

##### 1.3.5.20.3 DynamoDB Advantage
- Non-key attributes are schemaless.
- New attributes can be added to newer items without redefining a table-wide relational schema.

##### 1.3.5.20.4 Application Responsibility
- Schemaless storage does not eliminate compatibility concerns.
- Application deserialization must still handle:
  - missing older fields,
  - newly added fields,
  - changed representations,
  - defaults.

#### 1.3.5.21 Versioned Representations

##### 1.3.5.21.1 Pattern
- For complex persisted payloads, applications can include a schema/version indicator.

##### 1.3.5.21.2 Purpose
- Deserialization code can determine which representation it is reading and apply the appropriate conversion.

##### 1.3.5.21.3 Exam Boundary
- The DVA-C02 guide does not explicitly require schema-versioning strategies for this skill.
- Treat this as a practical consequence of persistent serialization rather than a separate AWS service requirement.

#### 1.3.5.22 Serialization and Keys

##### 1.3.5.22.1 Key Representation Matters
- If a serialized value becomes:
  - partition key,
  - sort key,
  - index key,
  its representation affects database access behavior.

##### 1.3.5.22.2 Example
- A date serialized as:
  - `2026-08-26T08:30:00Z`
  can preserve chronological lexicographic ordering when consistently formatted.

##### 1.3.5.22.3 Connection
- Key and index design belongs to Skill 1.3.4.
- Here the important point is that serialization choices must be compatible with the chosen key/access model.

#### 1.3.5.23 Serialization and Query Semantics

##### 1.3.5.23.1 Stored Form Is Queried
- Database comparisons operate on the persisted representation.

##### 1.3.5.23.2 Consequence
- A custom domain object serialized into one String is not automatically queryable by each of its internal fields.

##### 1.3.5.23.3 Example
- If `Address` is stored as one encoded String:
  - DynamoDB cannot independently query `city` unless city is represented as its own queryable attribute/index key.
- If stored as a Map:
  - nested attributes exist structurally, but efficient Query access still depends on table/index keys.

##### 1.3.5.23.4 Rule
- Choose serialization together with access-pattern design, not independently.

#### 1.3.5.24 Object Mapping vs Manual Serialization

##### 1.3.5.24.1 Object Mapper
- Benefits:
  - less boilerplate,
  - centralized mappings,
  - automatic conversion,
  - domain-oriented code.
- Trade-off:
  - abstraction can hide exact persisted representation unless the developer understands the mapping.

##### 1.3.5.24.2 Manual Mapping
- Benefits:
  - explicit control,
  - clear persisted schema,
  - useful for dynamic structures or specialized representations.
- Trade-off:
  - more conversion code.

##### 1.3.5.24.3 Decision
- Use the abstraction level appropriate to the application's model and required control.
- The exam skill is about understanding the conversion/persistence boundary, not memorizing one mapper API.

#### 1.3.5.25 Serialization Format Decision Model

##### 1.3.5.25.1 Native Database Attributes
- Prefer when:
  - fields need independent access,
  - database operators/indexes should work on those fields,
  - the data store naturally represents the types.

##### 1.3.5.25.2 Document Structure
- Prefer when:
  - nested data belongs together,
  - flexible structure is useful,
  - the database supports document types.

##### 1.3.5.25.3 Opaque Serialized Payload
- Can be appropriate when:
  - the store only needs to persist/retrieve the whole value,
  - internal fields do not need database-side querying/indexing.
- Trade-off:
  - database cannot efficiently reason about hidden internal structure.

#### 1.3.5.26 Failure and Validation Considerations

##### 1.3.5.26.1 Serialization Failure
- Conversion can fail when:
  - input values are invalid,
  - a custom converter cannot represent a value,
  - the value violates the target data store's type/size constraints.

##### 1.3.5.26.2 Deserialization Failure
- Conversion can fail when:
  - stored representation is malformed,
  - expected fields/types changed incompatibly,
  - an application version no longer understands old data.

##### 1.3.5.26.3 Developer Responsibility
- Validate important assumptions at the persistence boundary.
- Do not assume all historical stored data matches the current in-memory model.

#### 1.3.5.27 Important Distinctions

##### 1.3.5.27.1 Serialization vs Deserialization
- Serialization:
  - object → stored representation.
- Deserialization:
  - stored representation → object.

##### 1.3.5.27.2 Serialization vs Persistence
- Serialization creates the representation.
- Persistence stores it durably.

##### 1.3.5.27.3 Object Mapper vs Database
- Mapper converts between representations.
- DynamoDB stores/query items.
- The mapper is not the database.

##### 1.3.5.27.4 JSON vs DynamoDB Attribute Model
- JSON is a serialization/document representation.
- DynamoDB exposes typed attribute values including scalar, document, and set types.

##### 1.3.5.27.5 Schemaless vs Schema-Free Application
- DynamoDB does not require a fixed non-key table schema.
- Application code still has an expected data contract when it serializes/deserializes domain objects.

##### 1.3.5.27.6 Stored Representation vs Domain Model
- They do not need to be identical.
- Mapping is the explicit boundary between them.

#### 1.3.5.28 Common Exam Traps

##### 1.3.5.28.1 "Serialization Means Writing to the Database"
- False.
- Serialization creates a storable representation; the write operation provides persistence.

##### 1.3.5.28.2 "DynamoDB Is Schemaless, So Types Do Not Matter"
- False.
- DynamoDB attributes have explicit types and key attributes have additional type restrictions.

##### 1.3.5.28.3 "Every Application Type Maps Natively"
- False.
- Custom/domain types can require converters.

##### 1.3.5.28.4 "Store Everything as One JSON String"
- Usually poor if individual fields must be queried/indexed.
- Serialization should support required access patterns.

##### 1.3.5.28.5 "Object Mapper Removes Need to Understand Storage"
- False.
- Developers still need to understand how fields/types/keys are represented.

##### 1.3.5.28.6 "Schemaless Means Old Data Automatically Works With New Code"
- False.
- Application deserialization must still handle representation evolution.

#### 1.3.5.30 In-Scope Service Check

##### 1.3.5.30.1 Primary Concrete Example
- Amazon DynamoDB.
- It directly exposes:
  - typed attributes,
  - document types,
  - SDK object persistence/mapping interfaces,
  - custom type conversion.

##### 1.3.5.30.2 Related In-Scope Data Stores
- Amazon S3 can persist serialized objects/documents as S3 objects.
- Amazon RDS/Aurora applications commonly map language objects/values to relational columns through database drivers or application persistence libraries.
- Amazon OpenSearch Service consumes structured documents for indexing/search.
- These demonstrate that serialization is a general application-persistence concern rather than a DynamoDB-only concept.

##### 1.3.5.30.3 Scope Control
- Do not turn this skill into:
  - full ORM/JPA theory,
  - full JSON specification,
  - full Avro/Protobuf schema design,
  - complete DynamoDB single-table modeling.
- Those are broader than the wording of Skill 1.3.5.

##### 1.3.5.30.4 Exam Depth
- Explain serialization vs deserialization.
- Explain why persistence requires a representation understood by the target store.
- Understand DynamoDB scalar/document/set types.
- Understand object → AttributeValue mapping.
- Recognize object persistence interfaces such as the DynamoDB Enhanced Client.
- Understand built-in vs custom converters.
- Understand nested/document mappings.
- Understand that representation affects keys, indexing, sorting, and querying.
- Recognize compatibility/schema-evolution concerns.
- Distinguish serialization from the database write itself.
