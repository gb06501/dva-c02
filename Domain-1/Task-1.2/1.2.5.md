### 1.2.5 Integrate Lambda functions with AWS services

#### 1.2.5.1 Exam Context

##### 1.2.5.1.1 Skill Scope
- DVA-C02 Domain 1, Task 2 is **Develop code for AWS Lambda**.
- Skill 1.2.5 requires integrating Lambda functions with AWS services.
- The exam guide gives no narrower examples for this skill, so DVA-C02 in-scope services define the primary integration boundary.

##### 1.2.5.1.2 Core Mental Model
- Lambda integrations have two directions:
  - **AWS service → Lambda**: an event causes Lambda code to run.
  - **Lambda → AWS service**: function code calls AWS APIs through an AWS SDK.
- For inbound integrations identify:
  1. direct/push invocation or event source mapping/pull,
  2. synchronous, asynchronous, or batch/stream semantics,
  3. permissions,
  4. batching/filtering/scaling behavior,
  5. retry and failure ownership.

#### 1.2.5.2 Direct Invocation vs Event Source Mapping

##### 1.2.5.2.1 Direct / Push
- Many AWS services invoke Lambda directly.
- Relevant in-scope examples include API Gateway, S3, SNS, EventBridge, and Step Functions.
- The source service pushes the event to Lambda.

##### 1.2.5.2.2 Event Source Mapping / Pull
- Lambda event source mappings read from queue and stream sources.
- Lambda-managed pollers retrieve records, batch them, and invoke the function.
- Relevant in-scope examples are SQS, Kinesis Data Streams, and DynamoDB Streams.

##### 1.2.5.2.3 Why It Matters
- Direct triggers and event source mappings differ in permissions, batching, scaling, retries, and error handling.
- Do not treat every Lambda trigger as the same invocation mechanism.

#### 1.2.5.3 Synchronous Invocation

##### 1.2.5.3.1 Model
- caller/service → Lambda → result/error → caller/service.
- The caller waits for completion.
- Function latency directly affects caller latency.

##### 1.2.5.3.2 In-Scope Examples
- API Gateway → Lambda.
- Step Functions → Lambda when the workflow waits for the result.
- Direct request-response Lambda invocation.

##### 1.2.5.3.3 Retry Ownership
- For direct synchronous invocation, the caller/invoking service controls retries.
- Detailed lifecycle behavior belongs to Skill 1.2.3.

#### 1.2.5.4 Asynchronous Invocation

##### 1.2.5.4.1 Model
- source → Lambda asynchronous queue → function.
- The source does not wait for final processing.
- Lambda manages asynchronous retry/failure behavior.

##### 1.2.5.4.2 In-Scope Examples
- S3 notifications → Lambda.
- SNS → Lambda.
- EventBridge event-bus rule → Lambda.

##### 1.2.5.4.3 Failure Handling
- Lambda Destinations and Lambda DLQs can apply to asynchronous invocation.
- Detailed retry/event-age/DLQ behavior belongs to Skill 1.2.3.

#### 1.2.5.5 Amazon API Gateway → Lambda

##### 1.2.5.5.1 Purpose
- API Gateway can expose APIs backed by Lambda.
- The common model is synchronous request/response.

##### 1.2.5.5.2 Lambda Proxy Integration
- API Gateway passes request information to Lambda as an event.
- Lambda returns the response structure expected by API Gateway.
- Function code commonly controls status code, headers, and body.

##### 1.2.5.5.3 Permission
- API Gateway requires permission to invoke Lambda.
- A Lambda resource-based policy can grant `lambda:InvokeFunction` to API Gateway.
- This is separate from the Lambda execution role.

##### 1.2.5.5.4 Mental Model
- HTTP request → API Gateway → synchronous Lambda → response → client.

#### 1.2.5.6 Amazon S3 → Lambda

##### 1.2.5.6.1 Purpose
- S3 event notifications can invoke Lambda for configured bucket events such as object creation or deletion.

##### 1.2.5.6.2 Invocation
- S3 invokes Lambda asynchronously.
- The event supplies S3 metadata such as bucket and object information.

##### 1.2.5.6.3 Permissions
- Lambda resource policy permits S3 to invoke the function.
- If code then reads/writes S3, the execution role separately needs S3 API permissions.

##### 1.2.5.6.4 Recursion Risk
- A function triggered by a bucket can recursively invoke itself if it writes objects matching the same trigger.
- Separate input/output paths or filter notifications appropriately.

##### 1.2.5.6.5 Mental Model
- object event → S3 notification → asynchronous Lambda → processing.

#### 1.2.5.7 Amazon SNS → Lambda

##### 1.2.5.7.1 Purpose
- Lambda can subscribe to SNS topics.
- This supports publish/subscribe and fanout.

##### 1.2.5.7.2 Invocation
- SNS invokes Lambda asynchronously.
- The event contains the SNS message and metadata.

##### 1.2.5.7.3 Permissions
- Lambda's resource-based policy allows SNS invocation.
- The Lambda function is subscribed to the topic.

##### 1.2.5.7.4 Mental Model
- publisher → SNS topic → Lambda subscriber(s).

#### 1.2.5.8 Amazon EventBridge → Lambda

##### 1.2.5.8.1 Event Bus Rule
- EventBridge rules match events with event patterns.
- Lambda can be a rule target.
- Event-bus rules invoke Lambda asynchronously.

##### 1.2.5.8.2 Filtering
- Filter irrelevant events at EventBridge when the condition can be expressed declaratively.
- Avoid invoking Lambda merely to discard events.

##### 1.2.5.8.3 Permission
- Lambda must permit EventBridge to invoke the function.

##### 1.2.5.8.4 Pipes
- EventBridge Pipes can use Lambda as a supported target or enrichment step.
- Pipes can filter, transform, and enrich before delivery.
- EventBridge depth belongs to Skill 1.1.12.

##### 1.2.5.8.5 Mental Model
- producer → EventBridge → rule/filter → asynchronous Lambda.

#### 1.2.5.9 Amazon SQS → Lambda

##### 1.2.5.9.1 Integration Model
- SQS does not directly push each message to Lambda.
- Lambda uses an event source mapping to poll the queue.
- Pollers batch messages and invoke the function.

##### 1.2.5.9.2 Permissions
- The execution role needs permissions to read/manage source-queue messages.
- AWS provides `AWSLambdaSQSQueueExecutionRole` for common required permissions.

##### 1.2.5.9.3 Region
- Lambda and the SQS queue must be in the same Region.
- They can be in different AWS accounts with appropriate configuration.

##### 1.2.5.9.4 Batch Processing
- One invocation can contain multiple messages.
- Code must iterate records correctly.
- Partial batch responses can avoid unnecessary retries of successful records.

##### 1.2.5.9.5 Standard vs FIFO
- Lambda supports standard and FIFO SQS queues.
- FIFO ordering is maintained within message groups and constrains concurrency accordingly.

##### 1.2.5.9.6 Mental Model
- producer → SQS → Lambda pollers/event source mapping → batch → function.

#### 1.2.5.10 Amazon Kinesis Data Streams → Lambda

##### 1.2.5.10.1 Integration Model
- Lambda uses an event source mapping to read Kinesis records.
- Lambda polls shards and invokes the function with batches.

##### 1.2.5.10.2 Standard Iterator
- Standard iterator consumption shares shard read throughput with other consumers.

##### 1.2.5.10.3 Enhanced Fan-Out
- Enhanced fan-out provides a dedicated-throughput consumer model.

##### 1.2.5.10.4 Starting Position
- Supported starting positions include:
  - `LATEST`,
  - `TRIM_HORIZON`,
  - `AT_TIMESTAMP`.
- Starting position determines where a newly created mapping begins consuming.

##### 1.2.5.10.5 Permissions
- The execution role needs permissions to read the stream.
- AWS provides `AWSLambdaKinesisExecutionRole` for common permissions.

##### 1.2.5.10.6 Mental Model
- producer → Kinesis shards → Lambda event source mapping → batch → function.

#### 1.2.5.11 DynamoDB Streams → Lambda

##### 1.2.5.11.1 Integration Model
- DynamoDB Streams records item-level changes.
- Lambda uses an event source mapping to read stream records in batches.

##### 1.2.5.11.2 Typical Uses
- React to item changes.
- Maintain derived data.
- Trigger downstream work.
- Implement asynchronous side effects from table changes.

##### 1.2.5.11.3 Permissions
- The execution role needs permission to read DynamoDB Streams.
- AWS provides `AWSLambdaDynamoDBExecutionRole` for common permissions.

##### 1.2.5.11.4 Ordering
- Stream ordering/shards matter.
- Repeated failures can block later records in an affected shard.
- Detailed error handling belongs to Skill 1.2.3.

##### 1.2.5.11.5 Mental Model
- DynamoDB change → stream → event source mapping → Lambda batch.

#### 1.2.5.12 AWS Step Functions → Lambda

##### 1.2.5.12.1 Purpose
- Step Functions can invoke Lambda as a workflow task.
- Step Functions handles sequencing, branching, retries, parallelism, and workflow state.

##### 1.2.5.12.2 Responsibility Boundary
- Lambda performs focused application logic.
- Step Functions performs workflow orchestration.
- Avoid embedding complex orchestration in one Lambda when Step Functions fits the requirement.

##### 1.2.5.12.3 Permissions
- The Step Functions execution role needs permission to invoke Lambda.
- Lambda's execution role separately controls AWS calls made by the function.

##### 1.2.5.12.4 Mental Model
- state machine → Lambda task → result → next state.

#### 1.2.5.13 Lambda → AWS Services Through SDKs

##### 1.2.5.13.1 Outbound Integration
- Lambda code can call AWS APIs through AWS SDKs.
- In-scope examples:
  - DynamoDB read/write,
  - S3 get/put,
  - SNS publish,
  - SQS send,
  - EventBridge PutEvents,
  - Step Functions StartExecution,
  - Secrets Manager GetSecretValue.

##### 1.2.5.13.2 Credentials
- Lambda provides temporary credentials derived from the execution role.
- Do not embed long-term AWS access keys in function code.

##### 1.2.5.13.3 Permissions
- The execution role must allow the API operations used by code.
- Apply least privilege.

##### 1.2.5.13.4 Client Reuse
- Initialize SDK clients outside the handler when practical so warm execution environments can reuse them.
- SDK details belong to Skill 1.1.9; performance details to Skill 1.2.6.

#### 1.2.5.14 Resource-Based Policy vs Execution Role

##### 1.2.5.14.1 Resource-Based Policy
- Attached to the Lambda function.
- Controls which principals/services may invoke or access the function.
- Common for push integrations such as S3, SNS, API Gateway, and EventBridge.

##### 1.2.5.14.2 Execution Role
- Assumed by Lambda while function code runs.
- Grants AWS API permissions to the code.
- Also supplies source-read permissions needed by event source mappings such as SQS, Kinesis, and DynamoDB Streams.

##### 1.2.5.14.3 Exam Rule
- **Service pushes into Lambda** → think Lambda resource-based invocation permission.
- **Lambda reads/calls a service** → think Lambda execution role.
- Some complete integrations need both.

#### 1.2.5.15 Event Filtering

##### 1.2.5.15.1 Why Filter
- Avoid unnecessary invocations and processing.
- Express routing criteria at the integration layer where supported.

##### 1.2.5.15.2 EventBridge
- EventBridge rules provide content-based filtering.

##### 1.2.5.15.3 Event Source Mapping Filtering
- Lambda event source mappings support filter criteria for supported sources such as SQS, Kinesis, and DynamoDB Streams.
- Only matching records are sent to the function according to the integration's filtering semantics.

##### 1.2.5.15.4 Boundary
- Use infrastructure filtering for declarative routing.
- Keep business/domain decisions in application code.

#### 1.2.5.16 Batching

##### 1.2.5.16.1 Batch Size
- Event source mappings can send multiple records in one invocation.
- Larger batches can improve throughput and reduce invocation overhead.
- They also increase the amount of work affected by one failed invocation.

##### 1.2.5.16.2 Batching Window
- Supported mappings can wait for additional records before invoking.
- This trades latency for batching efficiency.

##### 1.2.5.16.3 Code Responsibility
- Do not assume one record per invocation.
- Iterate records correctly.
- Use partial batch failure mechanisms where supported.

#### 1.2.5.17 Scaling and Backpressure

##### 1.2.5.17.1 Push Sources
- Push sources can produce invocations as events arrive.
- Lambda concurrency and source-specific behavior determine effective scaling.

##### 1.2.5.17.2 SQS
- The queue buffers producer/consumer rate differences.
- Lambda pollers scale consumption according to event source mapping behavior.

##### 1.2.5.17.3 Streams
- Scaling relates to shards, parallelization, and event source mapping configuration.
- Ordering can constrain parallelism.

##### 1.2.5.17.4 Backpressure
- SQS provides durable queue backlog.
- Kinesis retains stream records according to retention.
- Direct push integrations do not provide the same backlog semantics.

#### 1.2.5.18 Integration Decision Model

##### 1.2.5.18.1 HTTP Request Must Run Lambda
- API Gateway → Lambda.
- Usually synchronous.

##### 1.2.5.18.2 Object Upload Must Trigger Processing
- S3 → Lambda.
- Asynchronous push.
- Avoid recursive trigger loops.

##### 1.2.5.18.3 Published Message Must Fan Out
- SNS → Lambda and/or other subscribers.

##### 1.2.5.18.4 Rich Event Routing Required
- EventBridge → Lambda.
- Filter by event content before invocation.

##### 1.2.5.18.5 Durable Work Queue Required
- SQS → Lambda event source mapping.
- Queue buffers work.
- Design visibility timeout, redrive/DLQ, batching, and idempotency.

##### 1.2.5.18.6 Ordered Retained Stream Required
- Kinesis → Lambda event source mapping.
- Respect shard ordering and select the appropriate starting/consumer model.

##### 1.2.5.18.7 React to DynamoDB Item Changes
- DynamoDB Streams → Lambda event source mapping.

##### 1.2.5.18.8 Multi-Step Workflow Required
- Step Functions → Lambda tasks.
- Keep orchestration in Step Functions.

##### 1.2.5.18.9 Lambda Must Call AWS Service
- Use an AWS SDK.
- Grant required permissions through the execution role.

#### 1.2.5.19 Important Distinctions

##### 1.2.5.19.1 Trigger vs Event Source Mapping
- Direct trigger: source pushes an event.
- Event source mapping: Lambda polls a queue/stream and invokes the function.

##### 1.2.5.19.2 Synchronous vs Asynchronous vs Event Source Mapping
- API Gateway commonly waits for the result.
- S3/SNS/EventBridge event-bus rules invoke asynchronously.
- SQS/Kinesis/DynamoDB Streams use event source mappings; do not confuse this with ordinary Lambda asynchronous invocation.

##### 1.2.5.19.3 Resource Policy vs Execution Role
- Resource policy: who may invoke/access Lambda.
- Execution role: what Lambda may read/call.

##### 1.2.5.19.4 SNS vs SQS
- SNS pushes asynchronously to subscribed Lambda functions.
- Lambda polls SQS.
- SNS is pub/sub fanout; SQS is durable queueing.

##### 1.2.5.19.5 EventBridge vs SQS
- EventBridge routes matching events.
- SQS stores work until consumers process it.
- They can be combined when both routing and durable buffering are required.

##### 1.2.5.19.6 Kinesis vs SQS
- Kinesis is a retained ordered stream partitioned into shards.
- SQS is a queue.
- Lambda scaling, ordering, batching, and retry semantics differ.
