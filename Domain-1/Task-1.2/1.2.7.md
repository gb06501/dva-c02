### 1.2.7 Use Lambda functions to process and transform data in near real time

#### 1.2.7.1 Exam Context

##### 1.2.7.1.1 Skill Scope
- DVA-C02 Domain 1, Task 2 is **Develop code for AWS Lambda**.
- Skill 1.2.7 requires using Lambda functions to process and transform data in near real time.
- The exam guide does not name example services for this individual skill.
- The strongest overlap with the in-scope service list and official Lambda documentation is:
  - Amazon Kinesis Data Streams,
  - DynamoDB Streams,
  - AWS Lambda event source mappings.
- Amazon Data Firehose is also relevant when Lambda is used specifically as a transformation step in a delivery stream.

##### 1.2.7.1.2 Core Mental Model
- Near-real-time Lambda stream processing is:
  - producer/change
  - → retained stream
  - → Lambda event source mapping
  - → batch of records
  - → transform/process
  - → downstream action/storage.
- The main tuning dimensions are:
  - starting position,
  - batch size,
  - batching window,
  - shard/partition concurrency,
  - filtering,
  - error handling,
  - idempotency,
  - consumer lag.
- "Near real time" does not mean that Lambda receives every record as an individual invocation.
- Lambda normally reads and processes stream records in batches.

#### 1.2.7.2 Near Real Time

##### 1.2.7.2.1 Meaning
- Near-real-time processing handles data shortly after it arrives rather than waiting for a scheduled batch job.
- Lambda is event-driven and can process newly available records continuously.
- Actual latency depends on:
  - source behavior,
  - polling,
  - batching,
  - function duration,
  - concurrency,
  - retries,
  - downstream latency.

##### 1.2.7.2.2 Real Time vs Near Real Time
- Do not interpret "near real time" as a deterministic zero-latency guarantee.
- Lambda stream integrations use polling and batching.
- Configuration can trade latency for throughput/efficiency.

#### 1.2.7.3 Primary Pattern: Kinesis Data Streams → Lambda

##### 1.2.7.3.1 Flow
- producer → Kinesis Data Stream → shard → Lambda event source mapping → Lambda batch → transformation/business logic → destination.

##### 1.2.7.3.2 Event Source Mapping
- Lambda uses an event source mapping to consume Kinesis records.
- The mapping manages polling, batching, checkpoints, invocation, scaling behavior, and failure controls.
- This is not ordinary Lambda asynchronous invocation.

##### 1.2.7.3.3 Processing Order
- Lambda processes records in each Kinesis shard in order.
- If processing fails, later records in the affected shard can be delayed until the failure is resolved or discarded according to configured failure behavior.

#### 1.2.7.4 Kinesis Record Structure

##### 1.2.7.4.1 Important Fields
- A Kinesis record contains:
  - data payload,
  - partition key,
  - sequence number,
  - approximate arrival timestamp,
  - stream/shard metadata.

##### 1.2.7.4.2 Data
- Kinesis record data is Base64-encoded in the Lambda event representation.
- Function code decodes/deserializes the application payload before transformation.

##### 1.2.7.4.3 Partition Key
- Producer selects the partition key.
- Kinesis uses it to determine shard placement.
- Records with the same partition key preserve ordering relative to one another.

##### 1.2.7.4.4 Sequence Number
- Sequence number identifies a record's position within a shard.
- It is not a global ordering value across the entire stream.

#### 1.2.7.5 Starting Position

##### 1.2.7.5.1 `LATEST`
- Begin with records arriving after the event source mapping reaches its effective starting point.
- Appropriate when only new data matters.

##### 1.2.7.5.2 `TRIM_HORIZON`
- Begin with the oldest records still available in the stream.
- Appropriate when retained backlog must be processed.

##### 1.2.7.5.3 `AT_TIMESTAMP`
- Kinesis event source mappings can begin from records at/after a specified timestamp.
- Useful for time-based replay/startup scenarios.

##### 1.2.7.5.4 Creation Caveat
- AWS documents that event source mapping creation/update is eventually consistent.
- With `LATEST`, records can potentially be missed while a newly created/updated mapping becomes active.
- AWS recommends `TRIM_HORIZON` or `AT_TIMESTAMP` when missing records during that interval is unacceptable.

#### 1.2.7.6 Polling and Consumers

##### 1.2.7.6.1 Standard Iterator
- Lambda can map to a Kinesis shared-throughput consumer.
- Read throughput is shared with other consumers of the shard.

##### 1.2.7.6.2 Enhanced Fan-Out
- Lambda can map to a Kinesis dedicated-throughput consumer using enhanced fan-out.
- The consumer receives dedicated read throughput.
- This is useful when multiple consumers compete for stream read capacity or low consumer latency is important.

##### 1.2.7.6.3 Selection
- Standard/shared consumption:
  - simpler,
  - shared shard read throughput.
- Enhanced fan-out:
  - dedicated consumer throughput,
  - useful for multiple/high-throughput consumers.

#### 1.2.7.7 Batch Size

##### 1.2.7.7.1 Purpose
- `BatchSize` controls the maximum number of records Lambda sends to the function in one invocation.
- Current AWS documentation allows Kinesis batch sizes up to 10,000 records.

##### 1.2.7.7.2 Larger Batch
- Fewer invocations per record.
- Higher processing efficiency/throughput potential.
- More records affected by one failed invocation.
- Larger per-invocation workload.

##### 1.2.7.7.3 Smaller Batch
- Lower per-invocation work.
- Potentially lower latency.
- Smaller failure scope.
- More invocation overhead per record.

##### 1.2.7.7.4 Payload Limit
- Lambda can invoke before the configured record count is reached when the invocation payload limit is reached.
- Batch size is therefore a maximum record count, not a guarantee that every batch contains that many records.

#### 1.2.7.8 Batching Window

##### 1.2.7.8.1 Purpose
- `MaximumBatchingWindowInSeconds` allows Lambda to wait briefly for additional records before invoking the function.
- Default for Kinesis is 0 seconds.

##### 1.2.7.8.2 Trade-Off
- Longer window:
  - potentially larger/more efficient batches,
  - increased record-processing latency.
- Shorter window:
  - lower latency,
  - potentially smaller batches/more invocations.

##### 1.2.7.8.3 Invocation Condition
- Lambda invokes when one of the applicable conditions is reached:
  - batch size,
  - batching window,
  - payload-size limit.

#### 1.2.7.9 Parallelization Factor

##### 1.2.7.9.1 Purpose
- `ParallelizationFactor` allows multiple batches from one Kinesis shard to be processed concurrently.
- Current AWS documentation supports values from 1 through 10.

##### 1.2.7.9.2 Throughput
- Increasing the factor can improve processing throughput when stream backlog/iterator age grows.

##### 1.2.7.9.3 Ordering
- AWS maintains in-order processing at the partition-key level when parallelization factor is increased.
- Do not interpret parallelization as arbitrary reordering of records sharing the same partition key.

#### 1.2.7.10 Consumer Lag

##### 1.2.7.10.1 Iterator Age
- `IteratorAge` / `IteratorAgeMilliseconds` is a key signal for stream consumers.
- It indicates how far processing has fallen behind the latest stream records.

##### 1.2.7.10.2 Increasing Iterator Age
- Possible causes:
  - function duration too high,
  - insufficient concurrency,
  - hot/insufficient shards,
  - downstream bottleneck,
  - repeated failures/retries,
  - batch configuration not suited to workload.

##### 1.2.7.10.3 Response
- Identify the bottleneck before changing configuration.
- Possible actions:
  - improve function duration,
  - increase memory/CPU,
  - adjust batch size/window,
  - increase parallelization factor,
  - scale Kinesis capacity,
  - improve downstream throughput,
  - fix poison/failing records.

#### 1.2.7.11 Transforming Records

##### 1.2.7.11.1 Typical Transformations
- Decode/deserialise source payload.
- Validate schema/content.
- Filter or classify records.
- Normalize fields.
- Enrich from another data source/service.
- Aggregate.
- Convert to another representation.
- Write/publish transformed results downstream.

##### 1.2.7.11.2 Keep Transformations Focused
- Lambda is well suited to bounded event transformations.
- Avoid unnecessary orchestration or long-running workflows inside the stream handler.
- Use appropriate managed services for downstream workflow/routing/storage.

##### 1.2.7.11.3 Output
- A Kinesis-triggered Lambda handler's return value is not automatically written back to the source stream.
- Code must explicitly call the desired downstream service when transformed data needs to be persisted or published.

#### 1.2.7.12 Event Filtering

##### 1.2.7.12.1 Purpose
- Lambda event filtering can prevent irrelevant stream records from being sent to the function.
- Filtering reduces unnecessary Lambda invocations and code-level discard logic.

##### 1.2.7.12.2 Kinesis Filtering
- Kinesis event source mappings support filtering on the `data` key.
- The payload must meet Lambda's JSON filtering requirements when filtering on data contents.

##### 1.2.7.12.3 Design Rule
- Declarative routing/filter condition → prefer event-source filtering where supported.
- Business/domain decision → keep in function code.

#### 1.2.7.13 Failure Behavior

##### 1.2.7.13.1 Shard Blocking
- Lambda processes a shard in order.
- A failed batch can prevent later records in that shard from progressing.
- Unbounded retries can therefore increase consumer lag.

##### 1.2.7.13.2 Maximum Retry Attempts
- Kinesis event source mappings support `MaximumRetryAttempts`.
- Current default `-1` means retry until the record expires from the stream.
- Configure a bounded value when indefinitely blocking a shard is unacceptable.

##### 1.2.7.13.3 Maximum Record Age
- `MaximumRecordAgeInSeconds` can prevent Lambda from continuing to process records beyond an acceptable age.
- The stream's own retention period still provides the outer data-availability boundary.

#### 1.2.7.14 Bisect Batch on Function Error

##### 1.2.7.14.1 Purpose
- `BisectBatchOnFunctionError` splits a failed batch into two smaller batches.
- Lambda retries the smaller batches to isolate problematic records.

##### 1.2.7.14.2 Benefit
- One poison record does not require repeatedly reprocessing the complete original batch.
- This can reduce recovery time and unnecessary duplicate work.

##### 1.2.7.14.3 Distinction
- Bisection finds a smaller failing batch.
- Partial batch response allows function code to explicitly report record-level failures.
- Detailed failure lifecycle belongs to Skill 1.2.3.

#### 1.2.7.15 Partial Batch Response

##### 1.2.7.15.1 `ReportBatchItemFailures`
- Configure `FunctionResponseTypes` with `ReportBatchItemFailures`.
- Function code reports failed record identifiers.
- Lambda can retry from the reported failure instead of replaying the entire successful prefix unnecessarily.

##### 1.2.7.15.2 Code Responsibility
- Process records carefully.
- Track failures.
- Return the response shape expected by Lambda.
- Preserve business ordering requirements.

#### 1.2.7.16 Failed-Record Destination

##### 1.2.7.16.1 Purpose
- Kinesis event source mappings support a destination for records discarded after configured failure handling.
- Current Lambda documentation supports standard SQS queues and standard SNS topics for discarded stream records.

##### 1.2.7.16.2 Recovery
- A failure destination preserves information needed for investigation/recovery.
- It does not eliminate the need for:
  - monitoring,
  - root-cause correction,
  - controlled replay/reprocessing.

#### 1.2.7.17 Idempotency

##### 1.2.7.17.1 Delivery Semantics
- Lambda event source mappings process events at least once.
- Duplicate processing can occur.

##### 1.2.7.17.2 Requirement
- Stream handlers should be idempotent when duplicate side effects would be harmful.
- Possible techniques:
  - conditional writes,
  - event/record identifiers,
  - deduplication state,
  - business-state checks.

##### 1.2.7.17.3 Key Rule
- Stream ordering does not imply exactly-once business effects.
- Ordering and idempotency solve different problems.

#### 1.2.7.18 DynamoDB Streams → Lambda

##### 1.2.7.18.1 Flow
- DynamoDB table mutation → DynamoDB Stream → Lambda event source mapping → batch → function.

##### 1.2.7.18.2 Stream Records
- DynamoDB Streams captures item-level changes.
- Depending on stream configuration, records can contain keys and/or old/new item images.

##### 1.2.7.18.3 Near-Real-Time Use Cases
- Maintain derived/denormalized data.
- Update search/index projections.
- Trigger downstream events.
- React to business-state changes.
- Perform asynchronous side effects after table updates.

##### 1.2.7.18.4 Retention
- DynamoDB Streams retains stream records for 24 hours.
- Consumers therefore have a bounded recovery/replay window.

#### 1.2.7.19 DynamoDB Streams Event Source Mapping

##### 1.2.7.19.1 Similar Controls
- DynamoDB Streams mappings support many of the same controls as Kinesis:
  - batch size,
  - batching window,
  - starting position,
  - parallelization factor,
  - filtering,
  - maximum retry attempts,
  - maximum record age,
  - batch bisection,
  - partial batch response,
  - failure destination,
  - tumbling windows.

##### 1.2.7.19.2 Starting Position
- DynamoDB Streams supports:
  - `LATEST`,
  - `TRIM_HORIZON`.
- Unlike Kinesis mappings, DynamoDB Streams does not use `AT_TIMESTAMP` as a starting-position option.

##### 1.2.7.19.3 Ordering
- DynamoDB stream processing follows shard ordering constraints.
- Repeated failures can delay later records in the affected shard.

#### 1.2.7.20 Kinesis vs DynamoDB Streams

##### 1.2.7.20.1 Kinesis Data Streams
- General-purpose streaming ingestion service.
- Applications explicitly publish records.
- Partition key controls shard placement.
- Configurable retention.
- Supports shared consumers and enhanced fan-out.
- Kinesis mapping supports `AT_TIMESTAMP`.

##### 1.2.7.20.2 DynamoDB Streams
- Change-data stream attached to a DynamoDB table.
- Records originate from table item mutations.
- 24-hour retention.
- Used primarily for change-data capture/reactive processing.
- Starting positions are `LATEST` or `TRIM_HORIZON`.

##### 1.2.7.20.3 Common Lambda Model
- Both use Lambda event source mappings.
- Both are batch-oriented.
- Both require attention to:
  - ordering,
  - lag,
  - retries,
  - duplicates,
  - idempotency.

#### 1.2.7.21 Tumbling Windows

##### 1.2.7.21.1 Purpose
- Lambda supports tumbling windows for stateful processing of Kinesis and DynamoDB stream records.
- A tumbling window groups records into non-overlapping time intervals.

##### 1.2.7.21.2 Stateful Aggregation
- Ordinary Lambda invocations should not depend on retained local state between invocations.
- Tumbling-window processing allows Lambda to pass aggregate state between invocations for the active window.

##### 1.2.7.21.3 Current Limits
- AWS currently supports tumbling windows up to 900 seconds.
- Aggregate state is limited; current AWS documentation specifies up to 1 MB per shard.

##### 1.2.7.21.4 Example
- Continuously calculate an aggregate such as:
  - count,
  - sum,
  - minimum/maximum,
  - rolling window-specific statistics
  for each configured time window.

#### 1.2.7.22 Amazon Data Firehose + Lambda Transformation

##### 1.2.7.22.1 Role
- Amazon Data Firehose can invoke Lambda to transform incoming source records before delivering them to a configured destination.
- This is a different pattern from Lambda directly consuming a Kinesis stream through an event source mapping.

##### 1.2.7.22.2 Flow
- source/direct PUT/Kinesis Data Streams
  → Data Firehose
  → optional Lambda transformation
  → buffering/format processing
  → destination.

##### 1.2.7.22.3 Use
- Transform records as part of a managed delivery pipeline.
- Examples:
  - normalize records,
  - add fields,
  - change structure,
  - prepare records for destination ingestion.

##### 1.2.7.22.4 Distinction
- **Kinesis Data Streams → Lambda event source mapping**
  - Lambda is the stream consumer/application processor.
- **Data Firehose → Lambda transform**
  - Lambda is an optional transformation stage inside a managed delivery pipeline.

#### 1.2.7.23 Near-Real-Time Transformation Decision Model

##### 1.2.7.23.1 General Event Stream
- Use Kinesis Data Streams when applications need a retained ordered stream with one or more consumers.
- Use Lambda event source mapping for serverless processing/transformation.

##### 1.2.7.23.2 DynamoDB Change Processing
- Enable DynamoDB Streams.
- Map the stream to Lambda.
- Process item changes asynchronously.

##### 1.2.7.23.3 Only Certain Records Matter
- Use event filtering in the event source mapping.
- Avoid invoking Lambda for records that can be discarded declaratively.

##### 1.2.7.23.4 Throughput Is Too Low
- Inspect iterator age.
- Tune:
  - memory/CPU,
  - batch size,
  - parallelization factor,
  - stream/shard capacity,
  - downstream capacity.

##### 1.2.7.23.5 Latency Is Too High
- Inspect:
  - iterator age,
  - batching window,
  - function duration,
  - retries,
  - downstream latency.
- Reduce batching delay only if batching is actually the bottleneck.

##### 1.2.7.23.6 One Record Blocks a Shard
- Consider:
  - bounded retries,
  - maximum record age,
  - batch bisection,
  - partial batch response,
  - failure destination.

##### 1.2.7.23.7 Time-Window Aggregation Required
- Consider Lambda tumbling windows for supported stream event sources.

##### 1.2.7.23.8 Managed Delivery with Transformation Required
- Consider Data Firehose with Lambda transformation rather than building the complete delivery pipeline manually.

#### 1.2.7.24 Important Distinctions

##### 1.2.7.24.1 Stream vs Queue
- Kinesis/DynamoDB Streams are retained ordered streams.
- SQS is a work queue.
- Both can trigger Lambda through event source mappings, but processing semantics differ.

##### 1.2.7.24.2 Kinesis vs Data Firehose
- Kinesis Data Streams: general-purpose retained stream for custom consumers.
- Data Firehose: managed delivery pipeline to supported destinations.
- Lambda can consume the former or transform records inside the latter.

##### 1.2.7.24.3 Batch Size vs Batching Window
- Batch size limits number of records.
- Batching window limits how long Lambda waits to accumulate records.
- Both influence throughput/latency.

##### 1.2.7.24.4 Shard Scaling vs Parallelization Factor
- More Kinesis shards increase stream capacity and partitioning.
- Parallelization factor allows Lambda to process multiple batches from one shard concurrently.
- They solve different bottlenecks.

##### 1.2.7.24.5 Starting Position vs Checkpoint
- Starting position defines where a new mapping begins.
- Checkpoint/progress tracks how far an active consumer has successfully processed.
- Do not confuse initial position with ongoing processing state.

##### 1.2.7.24.6 Ordering vs Exactly Once
- Streams provide ordering within their ordering boundary.
- Lambda event source mappings are at-least-once.
- Idempotency is still required for safe duplicate processing.

##### 1.2.7.24.7 Filtering vs Transformation
- Filtering determines whether a record reaches function code.
- Transformation changes/processes a record after it reaches the function.
