### 1.2.3 Handle the event lifecycle and errors by using code

#### 1.2.3.1 Exam Context

##### 1.2.3.1.1 Skill Scope
- DVA-C02 Skill 1.2.3 requires handling the Lambda event lifecycle and errors by using code.
- The exam guide explicitly gives Lambda Destinations and dead-letter queues as examples.
- Error behavior depends strongly on how the function is invoked.
- The central exam requirement is therefore not "Lambda retries errors" but knowing **which component owns retry and failure handling for each invocation model**.

##### 1.2.3.1.2 Core Mental Model
- First identify the invocation model:
  - synchronous invocation,
  - asynchronous invocation,
  - queue-based event source mapping,
  - stream-based event source mapping.
- Then reason about:
  - where the event waits,
  - who retries,
  - what constitutes success/failure,
  - whether batches are retried,
  - where exhausted/failed events go,
  - and whether duplicate processing is possible.

#### 1.2.3.2 Function Errors vs Invocation Errors

##### 1.2.3.2.1 Function Error
- Function code can throw/return an error.
- Runtime failures and function timeouts can also produce function errors.
- The invocation reached the function, but processing failed.

##### 1.2.3.2.2 Invocation Error
- An invocation can fail before the function code successfully runs.
- Examples include permissions, malformed invocation parameters, configuration problems, concurrency limits, or service-level failures.
- Lambda API 4xx/5xx responses represent invocation-level errors rather than ordinary handler errors.

##### 1.2.3.2.3 Why the Distinction Matters
- Retry behavior differs between function errors and invocation errors.
- A synchronous Lambda Invoke API response can return HTTP 200 even when the function itself returned an error; function-error information is returned separately.
- Application code must inspect the invocation result rather than treating transport success as proof of business success.

#### 1.2.3.3 Synchronous Invocation

##### 1.2.3.3.1 Lifecycle
- Caller → Lambda → function → response/error → caller.
- The caller waits for the function result.
- Examples include direct synchronous Invoke and request/response integrations such as API Gateway.

##### 1.2.3.3.2 Retry Ownership
- Lambda does not automatically retry function-code errors for direct synchronous invocation.
- The caller or invoking AWS service determines whether to retry.
- Retrying code must account for the possibility that the function executed partially or completely before the caller observed the error.

##### 1.2.3.3.3 Error Handling
- Catch expected application errors where useful.
- Return the response/error contract expected by the caller/integration.
- Log enough context to diagnose unexpected failures.
- Do not expose internal implementation details or sensitive information unnecessarily.

#### 1.2.3.4 Asynchronous Invocation

##### 1.2.3.4.1 Lifecycle
- Producer → Lambda asynchronous event queue → function.
- The producer receives an acceptance response without waiting for function execution.
- Lambda owns the internal event queue and subsequent invocation attempts.

##### 1.2.3.4.2 Function-Error Retry
- For standard Lambda asynchronous invocation, AWS currently retries a function error two additional times by default.
- AWS documents waits of approximately one minute before the second attempt and two minutes before the third.
- Maximum retry attempts can be configured from 0 to 2.

##### 1.2.3.4.3 Throttling/System Errors
- For throttling and 500-series system errors, Lambda returns the event to its asynchronous queue.
- AWS currently retries for up to 6 hours by default.
- Retry intervals increase with exponential backoff, up to a documented maximum interval of 5 minutes.

##### 1.2.3.4.4 Maximum Event Age
- Maximum event age controls how long Lambda keeps attempting to process an asynchronous event.
- AWS currently allows configuration up to 6 hours.
- An event that exceeds its maximum age can be discarded and routed to configured failure handling.

#### 1.2.3.5 Lambda Destinations

##### 1.2.3.5.1 Purpose
- Lambda Destinations retain records of asynchronous invocation results.
- Separate destinations can be configured for success and failure.
- A destination receives an invocation record containing request and response/error context.

##### 1.2.3.5.2 Supported Async Destinations
- Current AWS documentation supports:
  - Amazon SQS standard queue,
  - Amazon SNS standard topic,
  - Amazon S3 bucket for failure,
  - another Lambda function,
  - Amazon EventBridge event bus.
- Destination support varies by event/invocation mechanism; do not assume every destination is valid for every source.

##### 1.2.3.5.3 On-Success
- Receives an invocation record after successful asynchronous processing.
- Useful for chaining processing, auditing, or post-processing.

##### 1.2.3.5.4 On-Failure
- Receives an invocation record after retries are exhausted or the event exceeds configured age.
- The record includes richer invocation information than a traditional Lambda DLQ.

##### 1.2.3.5.5 Delivery Failure
- If Lambda cannot send an invocation record to a configured destination, Lambda emits the `DestinationDeliveryFailures` CloudWatch metric.
- Permissions, unsupported destination configuration, or size constraints can cause delivery failure.

#### 1.2.3.6 Lambda Dead-Letter Queue

##### 1.2.3.6.1 Purpose
- For asynchronous invocations, a Lambda DLQ retains events that could not be successfully processed after retry/age handling.
- Supported Lambda DLQ targets are an Amazon SQS standard queue or Amazon SNS standard topic.

##### 1.2.3.6.2 DLQ Payload
- Lambda DLQ handling stores the original event payload rather than the richer invocation record provided by Lambda Destinations.
- This is a key distinction between a traditional Lambda DLQ and an on-failure destination.

##### 1.2.3.6.3 Reprocessing
- Failed events in an SQS DLQ can be inspected and reprocessed.
- A DLQ is not a complete recovery process by itself.
- Applications need monitoring, investigation, correction, and redrive/reprocessing procedures.

#### 1.2.3.7 Destination vs DLQ

##### 1.2.3.7.1 Lambda Destination
- Supports success and failure routing.
- Carries an invocation record with request/response context.
- Supports more target types.

##### 1.2.3.7.2 Lambda DLQ
- Failure-only.
- Carries the original event.
- Uses standard SQS or standard SNS.
- Simpler legacy failure-capture mechanism.

##### 1.2.3.7.3 Decision
- Prefer destinations when richer invocation context or success routing is useful.
- Use DLQ when simple failed-event capture is sufficient or required by the architecture.
- Do not confuse a **Lambda function DLQ** with an **SQS source queue's DLQ**.

#### 1.2.3.8 SQS Event Source Mapping

##### 1.2.3.8.1 Lifecycle
- Producer → SQS queue → Lambda event source mapping polls queue → Lambda batch → function.
- SQS, not Lambda's asynchronous invocation queue, stores the source messages.
- Lambda polls the queue and invokes the function synchronously with batches.

##### 1.2.3.8.2 Successful Batch
- When a batch succeeds, Lambda deletes the successfully processed messages from the queue.

##### 1.2.3.8.3 Failed Batch
- By default, if processing fails for a batch, messages become visible again after the SQS visibility timeout.
- Lambda can receive and process them again.
- Therefore function code must tolerate repeated processing.

##### 1.2.3.8.4 Visibility Timeout
- Visibility timeout temporarily hides messages while a consumer processes them.
- The Lambda function timeout must not exceed the queue visibility timeout.
- AWS recommends configuring sufficient visibility time for processing and retry behavior.

##### 1.2.3.8.5 SQS Redrive Policy
- Repeatedly failed messages can be moved by SQS to an SQS dead-letter queue.
- `maxReceiveCount` determines how many receives are allowed before redrive.
- This DLQ belongs to the SQS queue, not the Lambda function's asynchronous invocation configuration.

#### 1.2.3.9 Partial Batch Responses

##### 1.2.3.9.1 Problem
- Without partial batch response, one failed record can cause successfully processed records in the same batch to be retried.
- This increases duplicate work.

##### 1.2.3.9.2 SQS Partial Batch Response
- Configure the event source mapping with `ReportBatchItemFailures`.
- Function code returns identifiers for records that failed.
- Lambda then retries failed items rather than treating the entire batch as failed.

##### 1.2.3.9.3 Code Responsibility
- Catch per-record failures.
- Record failed item identifiers in the required response format.
- Do not incorrectly report a failed record as successful.
- Keep processing idempotent because duplicates can still occur.

#### 1.2.3.10 Stream Event Source Mapping

##### 1.2.3.10.1 Sources
- Important in-scope examples are Amazon Kinesis Data Streams and DynamoDB Streams.
- Lambda polls stream shards and invokes the function with batches of records.

##### 1.2.3.10.2 Ordering Consequence
- A repeatedly failing batch can block processing of later records in the affected shard.
- This is fundamentally different from independent queue messages.
- Monitor stream consumer lag/iterator age.

##### 1.2.3.10.3 Retry Configuration
- Stream event source mappings support controls such as:
  - maximum retry attempts,
  - maximum record age,
  - bisect batch on function error,
  - failure destinations.
- Current defaults can allow failed records to retry until they expire from the stream unless bounded settings are configured.

#### 1.2.3.11 Bisect Batch on Function Error

##### 1.2.3.11.1 Purpose
- `BisectBatchOnFunctionError` splits a failed stream batch into two smaller batches and retries them.
- This helps isolate a poison record without repeatedly processing the complete original batch.

##### 1.2.3.11.2 Behavior
- Lambda recursively narrows the failing portion as batches are split.
- It is particularly useful when one record in a larger Kinesis/DynamoDB Streams batch consistently fails.

##### 1.2.3.11.3 Distinction
- Batch bisection changes retry batch size.
- Partial batch response lets code identify specific failed records.
- They are related but distinct mechanisms.

#### 1.2.3.12 Stream Partial Batch Response

##### 1.2.3.12.1 ReportBatchItemFailures
- Kinesis and DynamoDB Streams integrations can use partial batch failure reporting.
- Function code reports the sequence/item identifier where processing failed.
- Lambda can checkpoint/retry based on the reported failure rather than replaying unnecessary successful work.

##### 1.2.3.12.2 Ordering
- Stream processing must still respect ordering requirements.
- Code should not casually skip failed records merely to increase throughput if doing so violates business semantics.

#### 1.2.3.13 Idempotency

##### 1.2.3.13.1 At-Least-Once Reality
- Event source mappings process events at least once.
- Duplicate processing can occur.
- Asynchronous invocation can also occasionally deliver an event more than once.

##### 1.2.3.13.2 Idempotent Handler
- Processing the same logical event more than once should not create unintended duplicate side effects.
- Common protection mechanisms include:
  - business idempotency keys,
  - conditional writes,
  - deduplication records,
  - state checks before performing side effects.

##### 1.2.3.13.3 AWS Lambda Powertools
- AWS Lambda Powertools provides utilities that can help implement idempotency in supported runtimes.
- Treat Powertools as a development aid; understand the underlying idempotency requirement independently.

#### 1.2.3.14 Poison Events

##### 1.2.3.14.1 Poison Event
- A poison event consistently fails because of its data or processing assumptions.
- Repeated retry cannot repair deterministic bad input.

##### 1.2.3.14.2 Handling
- Validate input.
- Bound retries where appropriate.
- Isolate the failed event/batch.
- Send exhausted failures to an appropriate destination or DLQ.
- Alert operators when failures accumulate.
- Correct the underlying issue before redriving when necessary.

#### 1.2.3.15 Error Handling in Code

##### 1.2.3.15.1 Expected Errors
- Validate input and explicitly handle expected business/validation conditions.
- Return or throw errors according to the invocation contract.

##### 1.2.3.15.2 Unexpected Errors
- Preserve enough context in logs/telemetry for diagnosis.
- Allow the invocation mechanism to observe failure when retry/failure routing should occur.
- Do not swallow an exception and return success if the event must actually be retried.

##### 1.2.3.15.3 Per-Record Handling
- For batch processing, isolate record-level failures where the integration supports partial responses.
- A single malformed record should not unnecessarily replay all successful records if AWS provides a supported mechanism to report individual failures.

#### 1.2.3.16 Observability

##### 1.2.3.16.1 CloudWatch
- Amazon CloudWatch is explicitly in scope.
- Monitor function errors, throttles, duration, concurrency, asynchronous-event metrics, destination delivery failures, queue depth, DLQ depth, and stream lag as appropriate.

##### 1.2.3.16.2 Logs
- Log correlation/event identifiers and failure context.
- Do not log sensitive payloads or credentials.
- Structured logging improves troubleshooting.

##### 1.2.3.16.3 X-Ray
- AWS X-Ray is explicitly in scope.
- Tracing can help distinguish function processing time from downstream dependency latency/failure.
- Detailed observability belongs to Domain 4.

#### 1.2.3.17 Failure Decision Model

##### 1.2.3.17.1 Direct Synchronous Invocation Fails
- Caller owns retry strategy.
- Lambda does not automatically retry handler errors.
- Make retrying safe through idempotency where required.

##### 1.2.3.17.2 Async Lambda Invocation Fails
- Lambda owns asynchronous retry.
- Configure maximum retry attempts/event age as needed.
- Configure on-failure destination or DLQ when failed events must be retained.

##### 1.2.3.17.3 Need Rich Async Failure Context
- Use Lambda Destinations.
- The destination receives request/response invocation information.

##### 1.2.3.17.4 Need Simple Async Failed-Event Capture
- Use a Lambda DLQ with standard SQS or SNS.

##### 1.2.3.17.5 SQS Record Fails
- Message becomes visible again after visibility timeout.
- Use SQS redrive policy/DLQ for repeated failures.
- Use partial batch response to avoid retrying successful records unnecessarily.

##### 1.2.3.17.6 Kinesis/DynamoDB Stream Record Fails
- Understand that the affected shard can stall.
- Consider maximum retry attempts/record age.
- Consider batch bisection and partial batch failure reporting.
- Configure an appropriate failure destination where required.

##### 1.2.3.17.7 Duplicate Processing Is Harmful
- Make processing idempotent.
- Do not rely on Lambda/event-source delivery to guarantee exactly-once business effects.

#### 1.2.3.18 Important Distinctions

##### 1.2.3.18.1 Synchronous vs Asynchronous Retry
- Synchronous: caller/invoker owns retry.
- Asynchronous: Lambda manages the event queue and retry policy.

##### 1.2.3.18.2 Async Invocation vs Event Source Mapping
- Async invocation: event is placed in Lambda's asynchronous queue.
- Event source mapping: Lambda polls an external source such as SQS or Kinesis.
- Retry and failure semantics are different.

##### 1.2.3.18.3 Lambda DLQ vs SQS DLQ
- Lambda DLQ captures failed **asynchronous Lambda invocation events**.
- SQS DLQ captures source queue messages after exceeding the queue's redrive policy.
- They exist at different layers.

##### 1.2.3.18.4 Destination vs DLQ
- Destination can handle success or failure and contains richer invocation records.
- Lambda DLQ is failure-only and stores the original event.

##### 1.2.3.18.5 Queue Failure vs Stream Failure
- SQS messages can independently become visible and be retried/redriven.
- Stream failures can block later records in the same shard because ordering matters.

##### 1.2.3.18.6 Retry vs Idempotency
- Retry determines whether work is attempted again.
- Idempotency makes repeated attempts safe.
- Robust event-driven code usually needs both concepts.
