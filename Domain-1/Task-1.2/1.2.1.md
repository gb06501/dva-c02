### 1.2.1 Describe the access of private resources in VPCs from Lambda code

#### 1.2.1.1 Exam Context

##### 1.2.1.1.1 Skill Scope
- DVA-C02 Domain 1, Task 2 is **Develop code for AWS Lambda**.
- Skill 1.2.1 requires describing how Lambda code accesses private resources in Amazon VPCs.
- The skill is about the application-developer networking model, not designing complete VPC infrastructure.
- Amazon VPC and AWS Lambda are both explicitly in scope for DVA-C02.
- Closely related in-scope services include Amazon RDS, Amazon Aurora, Amazon ElastiCache, Amazon EFS, Amazon S3, AWS Secrets Manager, AWS Systems Manager, and IAM.

##### 1.2.1.1.2 Core Mental Model
- Every Lambda function runs in networking infrastructure owned and managed by the Lambda service.
- By default, that Lambda-managed environment is not connected to private resources inside the customer's VPC.
- To reach private VPC resources, configure the Lambda function with:
  - a VPC,
  - one or more subnets,
  - and one or more security groups.
- Lambda then uses **Hyperplane Elastic Network Interfaces (Hyperplane ENIs)** to provide network connectivity from the function to the selected VPC.
- The simplest exam mental model is:
  - Lambda → Hyperplane ENI → customer VPC → private resource.

#### 1.2.1.2 Default Lambda Networking

##### 1.2.1.2.1 Lambda-Managed VPC
- Lambda functions run inside a VPC that AWS Lambda owns and manages.
- This Lambda-managed VPC is not visible or configurable by the customer.
- Configuring a function for customer-VPC access does not move the function out of the Lambda-managed VPC.
- Instead, Lambda creates connectivity between the Lambda service and the customer's VPC.

##### 1.2.1.2.2 Default External Access
- A Lambda function that is not attached to a customer VPC can normally reach public endpoints, including public AWS service APIs, subject to IAM permissions and service configuration.
- It cannot directly reach private IP addresses or private-only endpoints inside a customer VPC unless network connectivity is configured.

#### 1.2.1.3 Attaching Lambda to a VPC

##### 1.2.1.3.1 VPC Configuration
- A Lambda VPC configuration identifies:
  - the VPC,
  - subnets,
  - security groups.
- Lambda uses this configuration to create or reuse Hyperplane ENIs in the selected subnets.
- The function can then communicate with resources reachable through the VPC's routing and security configuration.

##### 1.2.1.3.2 Subnets
- Select subnets that provide network reachability to the private resources the function must access.
- For high availability, select subnets in multiple Availability Zones when the workload and target resources support it.
- Subnet choice affects available IP addresses and routing paths.
- A Lambda function does not gain a public IP address merely because it is configured with a public subnet.

##### 1.2.1.3.3 Security Groups
- The function's VPC configuration includes one or more security groups.
- The Lambda-associated security group controls network traffic from the function-side ENI.
- The target resource's security group must allow the required inbound traffic from the Lambda function's security group or another permitted source.
- Security groups are stateful, so return traffic for an allowed connection is automatically permitted.

#### 1.2.1.4 Hyperplane ENIs

##### 1.2.1.4.1 Purpose
- Lambda uses Hyperplane ENIs to connect functions to customer VPCs.
- These ENIs provide network access to resources reachable from the configured subnets and security groups.
- Application code does not create or manage these network interfaces directly.

##### 1.2.1.4.2 Sharing
- Lambda can reuse a Hyperplane ENI for functions that use the same subnet/security-group combination.
- This reduces the older one-ENI-per-execution-environment behavior that historically caused larger VPC cold-start impact.
- Developers should understand ENIs as the connectivity mechanism rather than design application code around individual ENI identities.

##### 1.2.1.4.3 IP Capacity
- Hyperplane ENIs consume IP addresses from the configured subnets.
- Subnets therefore need sufficient address capacity.
- Very constrained subnet CIDR ranges can become a scaling or deployment problem.

#### 1.2.1.5 IAM Permissions for VPC Connectivity

##### 1.2.1.5.1 Execution Role Permissions
- To initially attach a Lambda function to a VPC, Lambda needs permissions to create and manage the required network interfaces.
- AWS provides the managed policy **AWSLambdaVPCAccessExecutionRole** for these permissions.
- The documented permissions include EC2 network-interface and subnet operations required by Lambda.

##### 1.2.1.5.2 Least Privilege
- AWS documentation states that the execution role needs these ENI permissions to create the VPC networking configuration, not to invoke the function itself after the ENIs exist.
- AWS also notes that granting these EC2 permissions to the execution role means the function code can call those EC2 APIs unless additional controls are applied.
- Follow least-privilege guidance and do not grant broader EC2 permissions than required.

##### 1.2.1.5.3 Resource Access Permissions
- VPC network reachability and IAM authorization are separate concerns.
- Example: reaching an RDS database over TCP requires network access; calling Secrets Manager requires IAM permission to the service API.
- A function can have correct network connectivity but still receive an authorization error.
- A function can have correct IAM permission but still fail because routing or security-group rules block the network path.

#### 1.2.1.6 Accessing Private In-Scope Resources

##### 1.2.1.6.1 Amazon RDS / Amazon Aurora
- A Lambda function can connect to a private RDS or Aurora database when the function has VPC connectivity to the database endpoint.
- The database security group must allow the database port from the Lambda security group.
- Database credentials and IAM/database authentication are separate from network connectivity.
- RDS Proxy can be relevant for managing Lambda-to-database connection behavior, but detailed integration belongs to later Lambda/data-store skills.

##### 1.2.1.6.2 Amazon ElastiCache
- ElastiCache nodes are typically accessed through private VPC networking.
- Lambda therefore needs VPC connectivity and security-group access to the cache endpoint.
- The target cache security group must allow the required port from the Lambda security group.

##### 1.2.1.6.3 Amazon EFS
- Lambda can mount Amazon EFS file systems.
- The Lambda function must be connected to the VPC containing network access to the EFS mount targets.
- EFS access for Lambda uses an EFS access point.
- Network security groups must allow NFS traffic as required.
- Detailed EFS/Lambda configuration is secondary to the networking model for this skill.

##### 1.2.1.6.4 Private HTTP Services
- Lambda can call internal HTTP services running on EC2, ECS, EKS, or behind an internal load balancer when routing and security rules permit.
- The endpoint can remain private; no public internet path is required.

#### 1.2.1.7 Internet Access After VPC Attachment

##### 1.2.1.7.1 Important Behavior
- Attaching a Lambda function to a customer VPC changes how the function reaches the internet.
- The function does not automatically retain internet access simply because its subnet is labeled public.
- AWS explicitly states that connecting a Lambda function to a public subnet does **not** give the function internet access.

##### 1.2.1.7.2 Private Subnet + NAT Gateway
- For IPv4 internet access, the common architecture is:
  - Lambda in private subnet → route table → NAT gateway in public subnet → internet gateway → internet.
- The Lambda function itself remains in the private subnet.
- The NAT gateway provides outbound internet connectivity without assigning a public IP to the function.

##### 1.2.1.7.3 No NAT Required for Purely Private Workloads
- If the function only needs private VPC resources and private AWS service endpoints, internet access might not be required.
- Avoid adding NAT solely because a function is VPC-connected if all required destinations are reachable privately.

#### 1.2.1.8 Accessing AWS Services Privately

##### 1.2.1.8.1 VPC Endpoints
- A VPC-connected Lambda function in a subnet without internet access can reach supported AWS services through VPC endpoints.
- Traffic through VPC endpoints stays on the AWS network rather than traversing the public internet.
- This is a key alternative to NAT when the function only needs supported AWS service APIs.

##### 1.2.1.8.2 Interface Endpoints
- Interface VPC endpoints use AWS PrivateLink.
- They create private IP addresses in the VPC for supported service APIs.
- Security groups associated with the endpoint control inbound traffic to the endpoint ENIs.
- Examples relevant to DVA-C02 can include Secrets Manager, Systems Manager, and other supported AWS APIs.

##### 1.2.1.8.3 Gateway Endpoints
- Amazon S3 supports gateway VPC endpoints.
- A gateway endpoint adds routes so private subnet resources can access S3 without NAT or an internet gateway.
- S3 is explicitly in scope for DVA-C02.

##### 1.2.1.8.4 Endpoint Policies
- VPC endpoints can have endpoint policies that restrict which principals/actions/resources can use the endpoint.
- Endpoint policy is an additional authorization layer; it does not replace IAM permissions.

#### 1.2.1.9 DNS

##### 1.2.1.9.1 VPC DNS
- Lambda code normally connects to resources using DNS names such as database endpoints, internal load balancers, or AWS service names.
- VPC DNS settings and private hosted zones can therefore affect name resolution.
- Network connectivity can fail even when IP routing is correct if the expected hostname does not resolve to a reachable address.

##### 1.2.1.9.2 Private DNS for Interface Endpoints
- Interface VPC endpoints can use private DNS so standard AWS service hostnames resolve to the endpoint's private IP addresses inside the VPC.
- This lets application code often continue using normal AWS SDK service endpoints while traffic is routed privately.

#### 1.2.1.10 Route Tables and Network ACLs

##### 1.2.1.10.1 Route Tables
- Subnet route tables determine where traffic from the Lambda ENI can be sent.
- Private-resource traffic must have a valid route to the destination.
- Internet-bound IPv4 traffic from a private subnet needs an appropriate NAT route if internet access is required.

##### 1.2.1.10.2 Network ACLs
- Network ACLs are stateless subnet-level controls.
- If restrictive NACLs are used, both request and return traffic must be allowed.
- AWS Lambda networking troubleshooting guidance notes that ephemeral port ranges must be permitted where restrictive NACLs would otherwise block return traffic.
- For exam reasoning, check security groups first, but remember that NACLs and routes can also block connectivity.

#### 1.2.1.11 IPv6

##### 1.2.1.11.1 Dual-Stack Support
- Lambda VPC networking can support outbound IPv6 traffic when the selected subnets are dual stack and the function configuration enables IPv6 traffic.
- All selected subnets must have both IPv4 and IPv6 CIDR blocks for this Lambda option.
- Lambda VPC configuration does not support connecting a function to IPv6-only subnets.

##### 1.2.1.11.2 Internet Egress
- IPv6 internet access does not use a NAT gateway.
- Routing and an egress-only internet gateway can be relevant for private outbound IPv6 architectures.
- Detailed VPC network design remains outside the developer-level scope of this skill.

#### 1.2.1.12 Common Failure Modes

##### 1.2.1.12.1 Timeout to Private Resource
- Check that the function is configured for the correct VPC/subnets.
- Check the Lambda security-group outbound rules.
- Check the target resource security-group inbound rules.
- Check route tables and NACLs.
- Check DNS resolution and target endpoint/port.

##### 1.2.1.12.2 VPC-Connected Function Cannot Reach Internet
- Do not move the function to a public subnet expecting internet access.
- Verify that private-subnet route tables send internet-bound IPv4 traffic through a NAT gateway.
- Verify that the NAT gateway has the required route through an internet gateway.
- Alternatively, use VPC endpoints for AWS services that do not require public internet access.

##### 1.2.1.12.3 AWS Service API Call Times Out
- If the subnet has no NAT/internet path, determine whether the required AWS service has a VPC endpoint.
- Create/use the appropriate endpoint and verify endpoint security-group/policy configuration.
- IAM permission still needs to allow the AWS API call.

##### 1.2.1.12.4 Access Denied
- AccessDenied is generally an IAM/resource-policy issue rather than a subnet-routing problem.
- Distinguish authorization failures from network timeouts/refused connections.

##### 1.2.1.12.5 ENI/IP Problems
- Insufficient subnet IP space or VPC ENI quotas can prevent VPC networking from scaling or being configured.
- Treat subnet capacity as part of Lambda VPC readiness.

#### 1.2.1.13 Access Decision Model

##### 1.2.1.13.1 Lambda Needs Only Public AWS APIs
- Do not attach the function to a VPC solely for this reason.
- Use the default Lambda networking model and IAM permissions unless another requirement needs VPC connectivity.

##### 1.2.1.13.2 Lambda Needs Private RDS/Aurora/ElastiCache/Internal Service
- Attach Lambda to the VPC.
- Select subnets with network reachability to the resource.
- Configure Lambda and target security groups.
- Add any resource-level authentication/authorization required by the service.

##### 1.2.1.13.3 Lambda Needs Private Resource + Public Internet
- Attach Lambda to private subnets.
- Provide outbound IPv4 internet access through NAT when required.
- Do not assume a public subnet gives Lambda a public IP.

##### 1.2.1.13.4 Lambda Needs Private Resource + AWS APIs Without Internet
- Attach Lambda to the VPC.
- Use VPC endpoints for supported AWS services.
- Use gateway endpoint for S3 where appropriate.
- Keep IAM and endpoint policies aligned.

##### 1.2.1.13.5 Lambda Needs EFS
- Configure VPC connectivity.
- Ensure network access to EFS mount targets.
- Use an EFS access point and required NFS security rules.

#### 1.2.1.14 Important Distinctions

##### 1.2.1.14.1 Lambda-Managed VPC vs Customer VPC
- Lambda always runs in AWS-managed Lambda networking.
- VPC configuration adds access to the customer's VPC; it does not mean the execution environment becomes an EC2 instance in the customer's subnet.

##### 1.2.1.14.2 Public Subnet vs Public IP
- A public subnet has a route to an internet gateway.
- Lambda VPC ENIs do not receive public IP addresses.
- Therefore placing Lambda in a public subnet does not itself provide internet access.

##### 1.2.1.14.3 Network Reachability vs IAM Permission
- VPC configuration answers: **Can packets reach the destination?**
- IAM/resource authentication answers: **Is the function allowed to perform the operation?**
- Both can be required, and failures look different.

##### 1.2.1.14.4 NAT Gateway vs VPC Endpoint
- NAT provides general outbound IPv4 internet access.
- VPC endpoints provide private access to supported AWS services.
- Prefer the mechanism that matches the destination requirement.

##### 1.2.1.14.5 Security Group vs Execution Role
- Security group controls network traffic.
- Execution role controls AWS API permissions used by the function code.
- Do not use IAM policies as a substitute for network rules or vice versa.
