### 1.2.4 Write and run test code by using AWS services and tools

#### 1.2.4.1 Exam Context

##### 1.2.4.1.1 Skill Scope
- DVA-C02 Domain 1, Task 2 is **Develop code for AWS Lambda**.
- Skill 1.2.4 requires writing and running test code by using AWS services and tools.
- The skill is narrower than general software testing: the Lambda/serverless context determines what must be tested and which AWS tools are useful.
- AWS documentation emphasizes both local testing and tests against deployed cloud resources.

##### 1.2.4.1.2 Core Mental Model
- Test Lambda at progressively larger boundaries:
  - isolated business logic,
  - function handler with representative events,
  - local serverless integration,
  - deployed AWS service integration,
  - end-to-end application flow.
- Local tests provide fast feedback.
- Cloud tests provide higher fidelity for AWS-managed service behavior.
- The strongest serverless test strategy uses both rather than assuming local emulation is identical to AWS.

#### 1.2.4.2 What Must Be Tested

##### 1.2.4.2.1 Business Logic
- Test deterministic application logic independently from Lambda and AWS service calls where practical.
- Examples:
  - validation,
  - calculations,
  - transformations,
  - mapping,
  - business rules.
- These tests should be fast and isolated.

##### 1.2.4.2.2 Handler Behavior
- Test that the Lambda handler correctly:
  - accepts the expected event shape,
  - extracts required fields,
  - invokes business logic,
  - handles expected errors,
  - returns the required response structure.

##### 1.2.4.2.3 AWS Service Integrations
- Test that the function interacts correctly with managed AWS services.
- Verify:
  - service is actually called,
  - correct parameters are supplied,
  - permissions allow the operation,
  - configuration is correct,
  - responses/errors are handled correctly.

##### 1.2.4.2.4 Event Flow
- Serverless applications frequently depend on event-driven chains.
- Test that events actually move through the expected AWS services and invoke the correct consumers.
- Example:
  - SQS message → Lambda → DynamoDB write.

#### 1.2.4.3 Unit Tests

##### 1.2.4.3.1 Purpose
- Unit tests verify isolated blocks of application code.
- AWS Lambda testing guidance explicitly retains traditional unit testing as part of serverless testing.

##### 1.2.4.3.2 Isolation
- Separate business logic from infrastructure-specific handler code where practical.
- Inject or abstract external dependencies so unit tests do not require live AWS resources.
- Mock or stub AWS SDK clients when the purpose is to test application logic rather than AWS itself.

##### 1.2.4.3.3 What Unit Tests Should Prove
- Correct output for valid input.
- Correct behavior at boundary values.
- Correct validation behavior.
- Correct handling of expected dependency responses/errors.
- Correct business decisions.

##### 1.2.4.3.4 What Unit Tests Cannot Prove
- Real IAM permissions.
- Real service configuration.
- Actual event delivery.
- AWS service semantics.
- Network configuration.
- Deployed runtime/infrastructure correctness.
- These require higher-fidelity tests.

#### 1.2.4.4 Integration Tests

##### 1.2.4.4.1 Purpose
- Integration tests verify interactions between two or more components/services.
- AWS recommends automated tests that verify function behavior when interacting with managed AWS services.

##### 1.2.4.4.2 Examples
- Lambda writes expected item to DynamoDB.
- Lambda consumes an SQS message.
- API Gateway invokes Lambda and returns the expected response.
- Lambda stores an object in S3.
- EventBridge rule delivers an event to the intended target.

##### 1.2.4.4.3 Cloud Fidelity
- AWS states that cloud-based tests provide the most accurate measure of serverless application quality.
- Managed AWS service behavior cannot always be reproduced perfectly in local environments.
- CI should therefore include tests against provisioned AWS resources before promotion to later environments.

#### 1.2.4.5 End-to-End Tests

##### 1.2.4.5.1 Purpose
- End-to-end tests verify behavior across the complete application path.
- They validate both application code and infrastructure/integration behavior.

##### 1.2.4.5.2 Example
- Send an API request.
- API Gateway invokes Lambda.
- Lambda performs processing.
- Lambda writes to DynamoDB.
- Verify the final externally observable result.

##### 1.2.4.5.3 Trade-Off
- End-to-end tests provide high confidence but are slower and more expensive than isolated unit tests.
- Use them for critical business flows rather than replacing all lower-level tests.

#### 1.2.4.6 Lambda Console Test Events

##### 1.2.4.6.1 Test Event
- The Lambda console can synchronously invoke a function with a JSON test event.
- Lambda converts the event JSON into the runtime-specific object passed to the handler.
- If no input is required, the event can be an empty JSON object.

##### 1.2.4.6.2 Uses
- Quick manual verification.
- Reproduce a known event.
- Validate handler parsing.
- Inspect execution result and logs.
- Test representative event payloads without configuring the original producer.

##### 1.2.4.6.3 Limitation
- A console test event directly invokes Lambda.
- It does not prove that the actual upstream service can deliver the event correctly.
- Example: manually testing an SQS-shaped JSON payload does not test the real SQS event source mapping.

#### 1.2.4.7 AWS SAM

##### 1.2.4.7.1 Purpose
- AWS Serverless Application Model (AWS SAM) is an AWS framework for building serverless applications with infrastructure as code.
- AWS SAM CLI supports building, locally testing, debugging, deploying, and monitoring serverless applications.

##### 1.2.4.7.2 Local Testing
- `sam local` provides commands for local serverless testing.
- AWS SAM uses local containers to approximate the Lambda execution environment.
- This provides faster feedback before deploying to AWS.

#### 1.2.4.8 `sam local invoke`

##### 1.2.4.8.1 Purpose
- `sam local invoke` performs a one-time local invocation of a Lambda function.
- Supply representative event payloads to exercise handler code.

##### 1.2.4.8.2 Typical Flow
- Build the application.
- Generate or prepare an event.
- Invoke the function locally.
- Inspect result/log output.
- Correct code and repeat.

##### 1.2.4.8.3 Example Mental Model
- event JSON → `sam local invoke` → local Lambda runtime container → handler → result.

#### 1.2.4.9 `sam local start-api`

##### 1.2.4.9.1 Purpose
- `sam local start-api` runs Lambda-backed APIs through a local HTTP server.
- It is useful for testing API Gateway + Lambda application behavior locally.

##### 1.2.4.9.2 Use
- Start the local API.
- Send HTTP requests using a browser, curl, test framework, or API client.
- Validate routing, request handling, and Lambda responses.

##### 1.2.4.9.3 Limitation
- Local API emulation accelerates development but does not replace deployed API Gateway integration tests.

#### 1.2.4.10 `sam local start-lambda`

##### 1.2.4.10.1 Purpose
- `sam local start-lambda` starts a local endpoint that emulates the Lambda invoke endpoint.
- Automated integration tests can invoke the local function through AWS SDK/API-compatible mechanisms.

##### 1.2.4.10.2 Reusable Tests
- AWS documents that tests can be written against this local endpoint and later run against deployed Lambda without modifying the test logic.
- This helps reuse integration-test code across local and cloud execution.

#### 1.2.4.11 Generating Test Events

##### 1.2.4.11.1 `sam local generate-event`
- AWS SAM can generate sample AWS service event payloads.
- Generated events help avoid manually reconstructing complex event JSON structures.

##### 1.2.4.11.2 Typical Sources
- Use representative events corresponding to the actual integration being tested.
- Relevant DVA-C02 examples include events associated with:
  - S3,
  - SQS,
  - SNS,
  - API Gateway,
  - EventBridge,
  - Kinesis,
  - DynamoDB Streams.

##### 1.2.4.11.3 Modify the Event
- Generated events are starting points.
- Replace placeholder fields with test values relevant to the application's assumptions and edge cases.

#### 1.2.4.12 Cloud Testing with AWS SAM

##### 1.2.4.12.1 `sam remote invoke`
- AWS SAM CLI can invoke supported deployed AWS resources in the cloud.
- This supports testing against actual AWS infrastructure rather than only local emulation.

##### 1.2.4.12.2 `sam remote test-event`
- AWS SAM CLI provides commands for working with shareable Lambda test events in the cloud.
- Test events can support repeatable testing of deployed functions.

##### 1.2.4.12.3 Why Cloud Testing Matters
- Cloud tests validate real:
  - IAM permissions,
  - service configuration,
  - event integrations,
  - runtime environment,
  - network behavior,
  - managed-service semantics.
- These are areas local unit/emulation tests cannot fully prove.

#### 1.2.4.13 Debugging with AWS SAM

##### 1.2.4.13.1 Step-Through Debugging
- AWS SAM supports local step-through debugging.
- Developers can:
  - set breakpoints,
  - inspect variables,
  - execute code line by line,
  - identify errors before cloud deployment.

##### 1.2.4.13.2 Debug Port
- `sam local invoke` and `sam local start-api` support a debug-port option.
- A compatible debugger can attach to the locally running function.

##### 1.2.4.13.3 AWS Toolkits
- AWS Toolkits integrate AWS development/debugging capabilities into supported IDEs.
- They can be used with AWS SAM for local Lambda debugging.

#### 1.2.4.14 Test Doubles and Mocking

##### 1.2.4.14.1 Mocking AWS SDK Calls
- For unit tests, replace external AWS SDK interactions with mocks/stubs/fakes when the purpose is to test application logic.
- Control dependency responses deterministically.
- Test success and expected failure branches.

##### 1.2.4.14.2 Do Not Over-Mock
- A mock proves that code behaves against the mock contract.
- It does not prove the real AWS service, IAM policy, event source, or deployed configuration behaves as assumed.
- Complement mocked unit tests with cloud integration tests.

#### 1.2.4.15 Representative Test Cases

##### 1.2.4.15.1 Happy Path
- Valid event.
- Expected dependency responses.
- Expected output/side effect.

##### 1.2.4.15.2 Invalid Event
- Missing required field.
- Invalid format.
- Unsupported value.
- Verify controlled validation behavior.

##### 1.2.4.15.3 Dependency Failure
- AWS SDK call fails.
- Downstream service times out.
- Permission denied.
- Verify the function handles or propagates the error according to the intended lifecycle.

##### 1.2.4.15.4 Duplicate Event
- Process the same logical event multiple times.
- Verify idempotent behavior where the event source can redeliver.
- This connects directly to Skill 1.2.3.

##### 1.2.4.15.5 Batch Failure
- For SQS/Kinesis/DynamoDB Streams integrations, test multiple records including failures.
- Verify batch/partial-batch behavior expected by the integration.

#### 1.2.4.16 Testing Configuration

##### 1.2.4.16.1 Environment Variables
- Tests should supply representative environment-specific configuration.
- Validate missing or invalid required configuration.

##### 1.2.4.16.2 IAM
- Local mocks cannot validate actual IAM authorization.
- Use deployed integration tests to verify the execution role can perform required AWS API operations.

##### 1.2.4.16.3 VPC
- Local tests cannot fully validate Lambda-to-VPC routing/security-group behavior.
- Use deployed tests for private-resource connectivity.
- VPC behavior belongs primarily to Skill 1.2.1.

##### 1.2.4.16.4 Timeout and Memory
- Local functional success does not prove the workload behaves correctly with deployed Lambda resource limits.
- Performance/resource validation should include cloud execution where relevant.
- Detailed tuning belongs to Skill 1.2.6.

#### 1.2.4.17 Test Strategy Decision Model

##### 1.2.4.17.1 Testing Pure Business Logic
- Use fast unit tests.
- Avoid AWS infrastructure dependencies.

##### 1.2.4.17.2 Testing Handler Against Event Shape
- Use unit tests and/or Lambda console/SAM test events.
- Include valid and malformed payloads.

##### 1.2.4.17.3 Testing Function Locally
- Use `sam local invoke`.
- Use generated/representative AWS events.

##### 1.2.4.17.4 Testing API Gateway + Lambda Locally
- Use `sam local start-api`.

##### 1.2.4.17.5 Automated Local Lambda Integration
- Use `sam local start-lambda` and invoke from automated test code.

##### 1.2.4.17.6 Testing Real AWS Integration
- Deploy isolated test resources.
- Run cloud integration tests against actual services.
- Verify IAM, configuration, and event behavior.

##### 1.2.4.17.7 Testing Complete Business Flow
- Run end-to-end tests against a deployed test environment.

#### 1.2.4.18 Local vs Cloud Testing

##### 1.2.4.18.1 Local
- Fast feedback.
- Low iteration cost.
- Easy debugging.
- Good for business logic and handler behavior.
- AWS SAM provides useful local Lambda/API emulation.

##### 1.2.4.18.2 Cloud
- Highest fidelity for managed-service behavior.
- Tests actual IAM, networking, configuration, event routing, and AWS service semantics.
- Slower and requires provisioned resources.

##### 1.2.4.18.3 Correct Strategy
- Local and cloud testing are complementary.
- AWS explicitly recommends cloud-based testing because serverless applications depend heavily on managed AWS services.

#### 1.2.4.19 Important Distinctions

##### 1.2.4.19.1 Unit vs Integration Test
- Unit: isolated code behavior.
- Integration: interaction between components/services.

##### 1.2.4.19.2 Integration vs End-to-End
- Integration: selected components interacting.
- End-to-end: complete application/business path.

##### 1.2.4.19.3 Test Event vs Real Event Source
- Test event: directly supplies representative JSON to Lambda.
- Real event source: validates actual service delivery/integration behavior.

##### 1.2.4.19.4 Local Emulation vs AWS Cloud
- Local emulation accelerates development.
- Cloud testing validates actual AWS-managed behavior.
- Do not assume local success proves deployed integration correctness.

##### 1.2.4.19.5 Mocked AWS SDK vs Real AWS Service
- Mock: verifies application behavior against controlled dependency responses.
- Real service: verifies actual API contract, IAM, configuration, and service behavior.

##### 1.2.4.19.6 Testing vs Debugging
- Testing detects whether behavior meets expectations.
- Debugging investigates why observed behavior is wrong.
- AWS SAM supports both workflows.
