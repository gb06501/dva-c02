Core question:

**How should application health signals be designed so infrastructure can decide whether an instance should be restarted, whether it should receive traffic, and whether startup has completed successfully?**

---

#### 4.2.8.2 Core Mental Model

```text
APPLICATION INSTANCE
       |
       +--> Is it functioning?
       |        |
       |        v
       |     LIVENESS
       |
       +--> Can it receive traffic now?
       |        |
       |        v
       |     READINESS
       |
       '--> Has initialization completed?
                |
                v
             STARTUP
```

Essential distinction:

```text
liveness failure
→ restart/replace may help

readiness failure
→ stop routing traffic

startup failure
→ initialization has not succeeded
```

Do not treat them as:
- interchangeable signals.

---

#### 4.2.8.3 Health Checks Answer Operational Questions

A health check evaluates whether:
- an application,
- container,
- target

is sufficiently healthy for:
- a specific operational purpose.

Possible questions:

```text
Is the process responsive?
Has initialization completed?
Can this instance serve requests?
Is a critical dependency available?
```

A good health check:
- answers one clearly defined question.

---

#### 4.2.8.4 Health Is Contextual

An application can be:

```text
alive
but
not ready
```

Example:

```text
process responsive
database temporarily unavailable
```

Restarting:
- may not repair the database.

Removing the instance from traffic:
- may be appropriate.

Therefore:

```text
alive
≠ ready
```

---

#### 4.2.8.5 Liveness

Liveness asks:

```text
Should this instance be restarted/replaced?
```

Typical failures:
- deadlock,
- event loop permanently stuck,
- unrecoverable internal state.

If liveness fails:
- restart/replacement is usually the intended recovery action.

---

#### 4.2.8.6 Readiness

Readiness asks:

```text
Should this instance receive traffic now?
```

If readiness fails:

```text
keep process running
+
remove from traffic
```

until:
- it becomes ready again.

This supports:
- temporary self-recovery,
- dependency recovery,
- graceful traffic withdrawal.

---

#### 4.2.8.7 Startup

Startup asks:

```text
Has initialization completed successfully?
```

Use when:
- startup is long,
- startup duration is variable,
- early liveness checks would cause restart loops.

Startup protection prevents:

```text
slow start
→ liveness fails
→ restart
→ slow start
→ restart
```

---

#### 4.2.8.8 Why Liveness and Readiness Must Be Separate

Suppose:

```text
application process
→ functioning

database
→ unavailable
```

If database availability is part of:
- liveness,

then:

```text
database outage
→ every application instance restarts
```

This:
- does not fix the database,
- can amplify the incident.

Better:

```text
liveness
→ is application itself healthy?

readiness
→ can it serve traffic now?
```

---

#### 4.2.8.9 Health Endpoint Pattern

Typical application endpoints:

```text
/health
/health/live
/health/ready
/ready
```

Exact path:
- is an application design choice.

What matters:
- the endpoint semantics.

---

#### 4.2.8.10 Liveness Endpoint

Example:

```http
GET /health/live
```

Success means:
- runtime/application is responsive.

It should usually avoid:
- unnecessary dependency checks.

Reason:

```text
dependency outage
≠ application necessarily needs restart
```

---

#### 4.2.8.11 Readiness Endpoint

Example:

```http
GET /health/ready
```

Success means:
- instance can receive workload traffic.

It may verify:
- initialization complete,
- required local resources loaded,
- critical dependency state,
- ability to perform essential work.

But dependency checks must:
- reflect real service capability.

---

#### 4.2.8.12 Health Endpoint Design

A health endpoint should be:
- fast,
- deterministic,
- inexpensive,
- safe,
- stable.

It should not:
- execute expensive business transactions,
- return large payloads,
- block on long dependency calls,
- expose sensitive diagnostics.

---

#### 4.2.8.13 HTTP Status Semantics

Typical pattern:

```text
2xx
→ healthy/ready

non-success
→ unhealthy/not ready
```

But the accepted success range:
- depends on the consuming health checker.

For ALB:
- success codes are configurable through the matcher.

---

#### 4.2.8.14 Do Not Leak Sensitive Details

Bad:

```json
{
  "databasePassword": "...",
  "internalHost": "...",
  "stackTrace": "..."
}
```

Health endpoints should expose:
- only what the health consumer needs.

Detailed diagnosis belongs in:
- logs,
- traces,
- metrics,
- protected observability systems.

---

#### 4.2.8.15 Shallow vs Deep Checks

Shallow:

```text
application responds
```

Deep:

```text
application
+
database
+
cache
+
external API
```

Neither is automatically correct.

Use:
- the depth appropriate to the health decision.

---

#### 4.2.8.16 Deep Checks Can Cause Cascading Failure

Suppose every readiness probe checks:
- database,
- cache,
- external API.

A brief external outage could cause:

```text
all instances
→ not ready
→ all traffic removed
```

even if:
- application could degrade gracefully.

Rule:

```text
dependency should affect readiness
only if
its failure really prevents useful service
```

---

#### 4.2.8.17 Critical vs Optional Dependencies

Critical:

```text
application cannot serve meaningful requests without it
```

Optional:

```text
feature can degrade / fallback
```

Do not automatically fail readiness because:
- an optional dependency is unavailable.

Health semantics should match:
- application behavior.

---

#### 4.2.8.18 Dependency Timeout

If a health check calls a dependency:
- use a strict short timeout.

Otherwise:

```text
dependency hangs
→ health endpoint hangs
→ health checker times out
→ additional work/connections accumulate
```

Health checking must not:
- become a failure amplifier.

---

#### 4.2.8.19 Application Load Balancer Health Checks

ALB periodically:
- sends health-check requests to registered targets.

Each target group has:
- its own health-check configuration.

Normal routing:
- prefers targets considered healthy.

---

#### 4.2.8.20 ALB Health Check Flow

```text
ALB
 |
 | HTTP/HTTPS health request
 v
target health endpoint
 |
 +--> accepted status
 |      |
 |      v
 |    healthy
 |
 '--> timeout / wrong status / failure
        |
        v
     unhealthy
```

---

#### 4.2.8.21 ALB Health Check Configuration

Important settings:

```text
HealthCheckProtocol
HealthCheckPort
HealthCheckPath
HealthCheckTimeoutSeconds
HealthCheckIntervalSeconds
HealthyThresholdCount
UnhealthyThresholdCount
Matcher
```

These determine:
- target routing eligibility.

---

#### 4.2.8.22 ALB Health Check Path

Example:

```text
/health/ready
```

The ALB check should usually represent:

```text
Can this target receive ALB traffic?
```

Therefore:
- readiness semantics are typically the closest fit.

---

#### 4.2.8.23 ALB Interval and Timeout

`HealthCheckIntervalSeconds`:

```text
how frequently ALB checks the target
```

Shorter:
- faster detection/recovery,
- more health-check traffic.

`HealthCheckTimeoutSeconds`:

```text
how long ALB waits for response
```

The endpoint should normally respond:
- comfortably before the timeout.

---

#### 4.2.8.24 ALB Healthy and Unhealthy Thresholds

`HealthyThresholdCount`:

```text
consecutive successful checks required
before unhealthy target becomes healthy
```

`UnhealthyThresholdCount`:

```text
consecutive failed checks required
before healthy target becomes unhealthy
```

Thresholds protect against:
- transient failures,
- transient recoveries.

---

#### 4.2.8.25 ALB Success Matcher

For HTTP/1.1 and HTTP/2 health checks, the source records that ALB can configure success codes from:

```text
200–499
```

Default:

```text
200
```

Example:

```text
Matcher = 200-299
```

Use a matcher that:
- matches the endpoint contract.

---

#### 4.2.8.26 ALB Target Health States

ALB states can include:

```text
initial
healthy
unhealthy
unused
draining
unavailable
```

Exam focus:
- healthy vs unhealthy,
- reason for state.

---

#### 4.2.8.27 ALB Unhealthy Reason Examples

Examples:

```text
Target.ResponseCodeMismatch
Target.Timeout
Target.FailedHealthChecks
Elb.InternalError
```

These help distinguish:

```text
wrong application response
```

from:

```text
no timely response
```

---

#### 4.2.8.28 Registered Does Not Mean Ready

After registration:
- target must pass health evaluation.

Do not assume:

```text
registered
=
ready for production traffic
```

Health checks provide:
- admission/routing signal.

---

#### 4.2.8.29 ALB Fail-Open Behavior

Important current behavior:

```text
if all registered targets in a target group are unhealthy
→ ALB routes to all targets
```

This is:
- fail-open behavior.

Do not assume:

```text
all targets unhealthy
→ no traffic is sent
```

This is a major exam nuance. fileciteturn147file0L89-L102

---

#### 4.2.8.30 ALB Health Checks and WebSockets

Current ALB documentation states:
- health checks do not use WebSocket sessions.

Health checks use:
- supported health-check protocols/endpoints.

---

#### 4.2.8.31 ECS Container Health Checks

ECS can evaluate container health using:
- a command defined in the task definition.

The command runs:

```text
inside the container
```

Success:

```text
exit code 0
```

Failure:

```text
non-zero exit code
```

This differs from:
- an external ALB health check.

---

#### 4.2.8.32 ECS Health Check Configuration

Key parameters:

```text
command
interval
timeout
retries
startPeriod
```

These determine:
- container health evaluation.

---

#### 4.2.8.33 ECS `CMD` vs `CMD-SHELL`

`CMD`:

```json
[
  "CMD",
  "curl",
  "-f",
  "http://localhost/health"
]
```

Use when:
- shell interpretation is unnecessary.

`CMD-SHELL`:

```json
[
  "CMD-SHELL",
  "curl -f http://localhost/health || exit 1"
]
```

Use when:
- shell operators/features are required.

---

#### 4.2.8.34 ECS Interval, Timeout, Retries

The source records current ECS ranges/defaults:

```text
interval
→ 5–300 seconds
→ default 30

timeout
→ 2–60 seconds
→ default 5

retries
→ 1–10
→ default 3
```

Use exact values only when:
- scenario asks for configuration detail.

---

#### 4.2.8.35 ECS `startPeriod`

`startPeriod` is:
- optional startup grace period.

During it:
- failed checks do not count toward the retry limit.

The source records:

```text
range
→ 0–300 seconds

default
→ disabled
```

Important nuance:

```text
if health check succeeds during startPeriod
→ container becomes healthy
→ subsequent failures count normally
```

Therefore:
- early success ends the effective grace behavior.

---

#### 4.2.8.36 ECS Health States

Container health:

```text
HEALTHY
UNHEALTHY
UNKNOWN
```

`UNKNOWN` can occur when:
- no health check exists,
- evaluation is incomplete,
- ECS cannot determine health under documented conditions.

---

#### 4.2.8.37 ECS Task Health

For tasks with essential containers that have health checks:

```text
essential container unhealthy
→ task unhealthy
```

Container importance:
- matters.

---

#### 4.2.8.38 ECS Service Reaction

When an essential container becomes unhealthy:
- ECS service scheduling can stop/replace the task.

Therefore:

```text
health-check failure
→ lifecycle consequence
```

not merely:
- monitoring information.

---

#### 4.2.8.39 ECS vs ALB Health

ECS container health:

```text
inside container
→ command
→ container/task lifecycle
```

ALB target health:

```text
from load balancer
→ network/application endpoint
→ routing eligibility
```

These are:
- complementary,
- not interchangeable.

---

#### 4.2.8.40 Kubernetes / EKS Probes

Kubernetes supports:

```text
livenessProbe
readinessProbe
startupProbe
```

Amazon EKS:
- uses Kubernetes probe semantics.

The kubelet:
- executes the probes.

---

#### 4.2.8.41 Probe Mechanisms

Common mechanisms include:

```text
exec
HTTP GET
TCP socket
```

Current Kubernetes also supports:
- additional mechanisms such as gRPC in supported versions.

For DVA-C02:
- understand semantics first,
- do not over-focus on version-specific mechanics.

---

#### 4.2.8.42 EKS Liveness Probe

Liveness detects:

```text
restart may repair this instance
```

Example:

```text
process exists
but
deadlocked
```

Persistent liveness failure:
- causes container restart according to Kubernetes behavior.

---

#### 4.2.8.43 EKS Readiness Probe

Readiness controls:

```text
whether Pod should receive service traffic
```

On failure:

```text
Pod remains running
but
is removed from ready endpoints
```

This is the central readiness rule. fileciteturn146file0L985-L998

---

#### 4.2.8.44 EKS Startup Probe

Startup probe:
- protects slow-starting applications.

Until it succeeds:
- liveness and readiness probes are disabled. fileciteturn147file0L143-L149

If startup continues failing beyond its configured threshold window:
- container is restarted.

---

#### 4.2.8.45 Readiness Is Not Restart

Critical distinction:

```text
readiness failure
→ stop traffic

liveness failure
→ restart container
```

Exam clue:

```text
temporarily prevent traffic
without restarting application
→ readiness
```

---

#### 4.2.8.46 Startup Is Not Readiness

Startup:

```text
Has initialization completed?
```

Readiness:

```text
Can the running application serve traffic now?
```

A service can:

```text
startup succeeds
→ ready
→ temporarily unready
→ ready again
```

without:
- restart.

---

#### 4.2.8.47 Kubernetes Probe Timing Parameters

Common controls:

```text
initialDelaySeconds
periodSeconds
timeoutSeconds
successThreshold
failureThreshold
```

These influence:
- detection time,
- restart timing,
- traffic restoration timing.

---

#### 4.2.8.48 Initial Delay

`initialDelaySeconds`:
- delays first probe after startup.

Useful when:
- startup duration is predictable.

For long/variable startup:
- startup probe is often cleaner.

---

#### 4.2.8.49 Period and Timeout

`periodSeconds`:

```text
probe frequency
```

Shorter:
- faster detection,
- more probe traffic.

`timeoutSeconds`:

```text
maximum probe duration
```

Normal endpoint response should be:
- significantly faster than this timeout.

---

#### 4.2.8.50 Failure and Success Thresholds

`failureThreshold`:

```text
consecutive failures before failure action
```

Purpose:
- tolerate transient errors.

`successThreshold`:

```text
consecutive successes required for recovery
where supported
```

Readiness can use:
- multiple successes before restoring traffic.

Exam focus:
- stabilization principle,
not every numeric Kubernetes default.

---

#### 4.2.8.51 Health Timing Model

Approximate failure detection depends on:

```text
interval
×
failure threshold
+
timeout behavior
```

Recovery depends on:

```text
interval
×
success threshold
```

Therefore:

```text
health-check configuration
→ affects outage detection and recovery speed
```

---

#### 4.2.8.52 Too Aggressive Health Checks

Example:

```text
very short interval
tiny timeout
failure threshold = 1
```

A brief latency spike can cause:

```text
healthy instances removed/restarted
→ remaining capacity overloaded
→ more failures
```

Health checks can:
- create cascading failure when too sensitive.

---

#### 4.2.8.53 Too Lenient Health Checks

Example:

```text
long interval
high failure threshold
```

Result:

```text
bad instance
→ receives traffic too long
```

Tune according to:
- workload behavior,
- failure-recovery requirements.

---

#### 4.2.8.54 Health Checks Must Be Narrow Enough

Weak:

```text
/health
→ sequentially queries ten downstream systems
```

Problems:
- slow,
- expensive,
- ambiguous failure,
- high coupling.

Prefer:
- clear semantics,
- bounded checks,
- short timeouts.

---

#### 4.2.8.55 Readiness During Deployment

New instance:

```text
starts
→ initializes
→ readiness=false
→ initialization complete
→ readiness=true
→ receives traffic
```

Purpose:
- prevent premature traffic.

---

#### 4.2.8.56 Readiness During Temporary Failure

Running instance:

```text
ready
→ temporary critical condition
→ not ready
→ condition recovers
→ ready
```

No restart is required if:
- application can self-recover.

---

#### 4.2.8.57 Liveness During Deadlock

A process can exist while:
- making no progress.

Simple process monitoring can report:
- healthy.

Application-level liveness can detect:
- unresponsiveness.

Then:
- restart may recover service.

---

#### 4.2.8.58 Startup During Slow Initialization

Without startup protection:

```text
slow startup
→ liveness fails
→ restart loop
```

With startup probe/start grace:

```text
startup allowed
→ initialization completes
→ normal health evaluation begins
```

---

#### 4.2.8.59 Health Checks vs Monitoring

Health check:

```text
Should this instance receive traffic / be restarted?
```

Monitoring:

```text
How is the service behaving over time?
```

Do not replace:
- metrics,
- logs,
- traces,
- alarms

with:
- one `/health` endpoint.

---

#### 4.2.8.60 Health Check vs Alarm

Health check:
- drives local lifecycle/routing.

Alarm:
- evaluates telemetry and triggers notification/action.

Example:

```text
ALB target health
→ remove target from routing

CloudWatch alarm on UnHealthyHostCount
→ notify operators
```

They:
- complement each other.

---

#### 4.2.8.61 Health Check vs Synthetic Monitoring

Readiness:

```text
instance can answer /ready
```

does not prove:

```text
real user journey works end-to-end
```

Synthetic monitoring:
- validates broader external behavior.

Keep local health checks:
- narrow and purposeful.

---

#### 4.2.8.62 Health Endpoint Access and Security

Infrastructure must be able to:
- call the endpoint.

But endpoint should not expose:
- sensitive internals.

Common design:
- lightweight status response,
- network-level access control where appropriate.

Avoid:
- fragile user-authentication flows for health checks unless architecture requires them.

---

#### 4.2.8.63 Health Endpoint Performance

Health checks occur continuously.

Avoid:
- expensive queries,
- large responses,
- blocking calls,
- heavyweight processing.

Health checking should consume:
- negligible capacity.

---

#### 4.2.8.64 Multiple Capabilities

A service may support:
- reads,
- writes,
- asynchronous processing.

One binary readiness signal:
- may not represent every capability perfectly.

For exam-level design:
- expose the signal matching the workload/traffic being controlled.

Avoid:
- unnecessary complexity.

---

#### 4.2.8.65 ALB vs Kubernetes Readiness

Both conceptually ask:

```text
Should this instance receive traffic?
```

But:

```text
Kubernetes readiness
→ Pod/service endpoint participation

ALB target health
→ load-balancer target routing
```

In EKS:
- both can participate in traffic admission.

---

#### 4.2.8.66 ECS vs Kubernetes Liveness

ECS:

```text
container health command
→ HEALTHY/UNHEALTHY
→ task/service lifecycle
```

Kubernetes:

```text
liveness probe
→ restart on persistent failure
```

Mechanisms differ.

Shared principle:

```text
detect failure that restart/replacement can repair
```

---

#### 4.2.8.67 Implementation Decision Flow

```text
What operational question?
        |
        +--> Is process stuck/dead?
        |        |
        |        v
        |     LIVENESS
        |
        +--> Can instance receive traffic?
        |        |
        |        v
        |     READINESS
        |
        '--> Has initialization completed?
                 |
                 v
              STARTUP
```

Then:

```text
Where does workload run?
        |
        +--> ALB target
        |      → target-group health check
        |
        +--> ECS container
        |      → task-definition healthCheck
        |
        '--> EKS/Kubernetes
               → liveness/readiness/startup probes
```

---

#### 4.2.8.68 Dependency Decision Flow

```text
dependency unavailable
        |
        v
Can instance still serve useful traffic?
       / \
     yes  no
      |    |
      v    v
 remain   readiness
 ready    fails
      |
      v
degrade/fallback
```

Do not automatically:
- make every dependency a readiness dependency.

---

#### 4.2.8.69 Troubleshooting ALB Health

If local health works but ALB marks target unhealthy, check:
- path,
- port,
- protocol,
- network/security path,
- timeout,
- matcher,
- returned status,
- target-health reason code.

Do not assume:
- application health endpoint itself is the only cause.

Wrong.

Wrong.

Wrong.

Wrong.

#### 4.2.8.71 Fast Scenario Mapping

```text
restart deadlocked process?
→ liveness

temporarily remove traffic?
→ readiness

long/variable startup?
→ startup probe / startup grace

ALB route only to ready targets?
→ target-group health check against readiness endpoint

ECS replace internally unhealthy task?
→ ECS container health check

ALB health returns 503?
→ fails unless matcher explicitly accepts it

dependency unavailable but app can degrade?
→ remain ready where appropriate

need faster failure detection?
→ tune interval + timeout + failure threshold

need faster recovery?
→ tune interval + success/healthy threshold

local endpoint works but ALB unhealthy?
→ path + port + protocol + network + timeout + matcher + response
```

#### 4.2.8.74 Exam-Level Knowledge Frame

Know these cold.

**Liveness**  
→ should this application/container be restarted?

**Readiness**  
→ should this instance receive traffic?

**Startup**  
→ has initialization completed?

**ALB Health Check**  
→ external load-balancer test controlling target routing eligibility.

**ECS Container Health Check**  
→ command executed inside container; exit `0` means success.

**`startPeriod`**  
→ ECS startup grace before failures count normally.

**Kubernetes Readiness Probe**  
→ removes Pod from ready endpoints without restart.

**Kubernetes Liveness Probe**  
→ persistent failure leads to restart.

**Startup Probe**  
→ disables liveness/readiness until startup succeeds.

**Threshold**  
→ stabilizes health decisions and controls detection/recovery speed.

**Health Endpoint**  
→ fast, deterministic, inexpensive, safe signal.

**Dependency Check**  
→ include only if dependency state genuinely determines the health decision.

**ALB Fail Open**  
→ all targets unhealthy can still result in ALB routing to all registered targets.

Fastest discriminator:

```text
restart stuck process?
→ liveness

temporarily stop traffic?
→ readiness

protect slow initialization?
→ startup

load-balancer routing?
→ ALB health check

container-local health?
→ ECS healthCheck

transient failure?
→ thresholds prevent overreaction

health endpoint slow?
→ poor design

dependency outage?
→ do not automatically make it liveness failure

all ALB targets unhealthy?
→ fail-open behavior

need detailed diagnosis?
→ logs + metrics + traces
```

---

#### 4.2.8.75 Final Principle

**Application health checks must represent the action the platform should take. Liveness indicates whether restart or replacement is appropriate; readiness indicates whether the instance should receive traffic now; startup checks protect initialization before normal health evaluation begins. Keep health endpoints fast, deterministic, inexpensive, safe, and dependency-aware, and include downstream dependencies only when their availability genuinely determines whether the controlled workload can be served. ALB target-group health checks externally test application targets and use path/protocol, timeout, interval, success matcher, and consecutive success/failure thresholds to control routing. ECS container health checks run commands inside containers and use exit status together with interval, timeout, retries, and `startPeriod`. EKS/Kubernetes explicitly separates liveness, readiness, and startup probes. Tune checks to balance fast detection against false positives and cascading failure, and retain metrics, logs, traces, and alarms for the diagnostic detail that binary health signals intentionally do not provide.**
