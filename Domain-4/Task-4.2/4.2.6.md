### 4.2.6 Implement tracing

#### 4.2.6.1 Exam and Task Context

##### 4.2.6.1.1 Domain and Task
- **Domain 4:** Troubleshooting and Optimization.
- **Task 4.2:** Instrument code for observability.

```text

```

Core question:

**How should distributed tracing be enabled and instrumented so a request can be followed across application components and downstream dependencies, while preserving trace context, controlling telemetry volume, and using the correct AWS tracing model?**

---

#### 4.2.6.2 Core Mental Model

```text
REQUEST / EVENT
      |
      v
trace context created or received
      |
      v
SERVICE A
segment / span
      |
      +--> internal work
      |      '--> subsegment / span
      |
      '--> downstream call
              |
              | trace context propagated
              v
           SERVICE B
           segment / span
              |
              '--> dependency
```

Tracing answers:

```text
Where did this request go?
Which service was slow?
Which dependency failed?
How much time was spent at each hop?
Did the transaction cross all expected components?
```

---

#### 4.2.6.3 Distributed Tracing

Distributed tracing:
- follows one request or transaction through multiple components.

Example:

```text
Client
  |
  v
API Gateway
  |
  v
Lambda
  |
  +--> DynamoDB
  |
  '--> downstream HTTP service
```

Without tracing:
- each component may appear independently.

With tracing:
- related work can be reconstructed as one request path.

---

#### 4.2.6.4 Trace and Trace ID

An X-Ray trace:
- contains traced work belonging to one request.

A trace ID:
- identifies that end-to-end request.

Concept:

```text
Trace ID
   |
   +--> API segment
   +--> Lambda segment
   +--> application segment
   '--> downstream subsegments
```

Trace IDs are useful for:
- trace lookup,
- log correlation,
- incident investigation.

They are high-cardinality request identifiers, so:
- do not treat them as normal low-cardinality metric dimensions.

---

#### 4.2.6.5 Segment

A segment records:
- work performed by a service/resource for the request.

It can contain:
- service/resource name,
- request information,
- response information,
- start/end times,
- errors/faults/exceptions,
- annotations,
- metadata,
- subsegments.

Mental model:

```text
segment
→ one service/resource's view of the request
```

---

#### 4.2.6.6 Subsegment

A subsegment gives:
- finer-grained timing or dependency information inside a segment.

Examples:

```text
DynamoDB PutItem
HTTP request
SQL query
validateOrder
calculatePrice
reserveInventory
```

Use subsegments to expose:
- important downstream calls,
- expensive internal operations,
- code paths that would otherwise be invisible.

---

#### 4.2.6.7 Trace Map

X-Ray processes trace data into:
- a service/trace map.

The map can show:
- application/service nodes,
- upstream clients,
- downstream dependencies,
- relationships between services,
- error and latency relationships.

Current CloudWatch terminology combines:
- the former X-Ray service map,
- ServiceLens map

into:
- the **X-Ray trace map**.

Use the trace map to answer:

```text
Which service/dependency appears unhealthy?
```

---

#### 4.2.6.8 Trace Timeline

A trace timeline shows:
- ordering,
- duration,
- overlap

of segments/subsegments.

Example:

```text
API Gateway      |----------------------|
Lambda              |----------------|
Validation            |-|
Payment HTTP            |------------|
DynamoDB                           |--|
```

This helps identify:
- bottlenecks,
- slow dependencies,
- unexpected wait time.

---

#### 4.2.6.9 Trace Context

Distributed tracing requires:
- context propagation across supported boundaries.

Concept:

```text
Service A
   |
   | trace identity + sampling decision
   v
Service B
   |
   v
Service C
```

Without propagation:

```text
one logical transaction
→ multiple disconnected traces
```

Trace context is therefore:
- a core implementation concern.

---

#### 4.2.6.10 `X-Amzn-Trace-Id`

X-Ray uses the HTTP tracing header:

```text
X-Amzn-Trace-Id
```

It carries information including:
- trace ID,
- parent information,
- sampling decision.

Supported/instrumented services:
- propagate this tracing context.

Do not manually invent tracing IDs where:
- framework/service instrumentation already manages propagation.

---

#### 4.2.6.11 Sampling

Tracing every request can increase:
- telemetry volume,
- processing overhead,
- cost.

Sampling decides:

```text
which requests are recorded
```

Classic X-Ray default SDK sampling behavior:

```text
first request each second
+
5% of additional requests
```

Supported non-Lambda SDK contexts can:
- use custom sampling rules.

---

#### 4.2.6.12 Why Sampling Matters

If a request is absent from trace search:

```text
missing trace
≠ tracing necessarily failed
```

Possible explanations:
- request was not sampled,
- tracing was disabled,
- permissions were missing,
- trace context was not propagated,
- integration did not support the expected tracing path.

Always consider:
- sampling before assuming misconfiguration.

---

#### 4.2.6.13 Sampling Decision Propagation

An upstream component can make:
- the sampling decision.

That decision can travel with:
- trace context.

Downstream services can:
- honor the same decision.

Benefit:

```text
one request
→ one coherent sampled/unsampled decision
```

This helps avoid:
- fragmented traces.

---

#### 4.2.6.14 Instrumentation

Tracing implementation can include:
- incoming request tracing,
- AWS SDK call tracing,
- outgoing HTTP call tracing,
- database/SQL tracing,
- custom subsegments/spans,
- annotations,
- metadata.

The mechanism depends on:
- runtime,
- framework,
- deployment model,
- chosen tracing library.

---

#### 4.2.6.15 Automatic vs Manual Instrumentation

##### Automatic instrumentation

Use when:
- framework/library/agent can capture standard operations.

Examples:
- incoming HTTP request,
- AWS SDK call,
- outbound HTTP client call.

##### Manual instrumentation

Use when:
- important application-specific work is otherwise invisible.

Example:

```text
processOrder()
→ reserveInventory()
```

If inventory reservation is operationally important:
- trace it as a custom subsegment/span.

Rule:

```text
standard dependency
→ automatic instrumentation where supported

important custom operation
→ manual instrumentation
```

---

#### 4.2.6.16 Custom Subsegment Pattern

Concept:

```text
begin subsegment
      |
      v
perform operation
      |
      v
record context/error
      |
      v
end subsegment
```

Always:
- close custom subsegments correctly.

Unclosed subsegments can:
- interfere with correct trace completion/reporting.

---

#### 4.2.6.17 Trace Granularity

Too coarse:

```text
Lambda
→ 4 seconds
```

No clue:
- what consumed the time.

Too fine:

```text
hundreds of tiny subsegments
```

Result:
- noise,
- overhead,
- hard-to-read traces.

Prefer:
- operationally meaningful boundaries.

Examples:
- external service call,
- database operation,
- major business step,
- expensive internal work.

---

#### 4.2.6.18 Errors, Faults, and Exceptions

Trace data can expose:
- errors,
- faults,
- exceptions.

Tracing helps answer:

```text
request failed
     |
     v
which segment?
     |
     v
which dependency/call?
```

This provides:
- failure location and timing

that an aggregate error metric cannot.

---

#### 4.2.6.19 Metrics, Logs, and Traces

##### Metric

```text
PaymentFailures = 37
```

Answers:

```text
how much?
how often?
```

##### Trace

```text
API
→ Lambda
→ Payment API
→ timeout
```

Answers:

```text
where/how did this request fail?
```

##### Log

```text
Payment provider timed out for request abc
```

Answers:
- detailed application/event context.

Strong observability:

```text
metric detects
→ trace localizes
→ log explains
```

---

#### 4.2.6.20 Log/Trace Correlation

Where practical, include:

```text
traceId
requestId
```

in logs.

Then:

```text
trace
↔ logs
```

can be correlated.

Typical flow:

```text
trace identifies slow PaymentService
→ logs reveal exact provider error
```

Do not use trace IDs:
- as metric dimensions by default.

---

#### 4.2.6.21 Annotations and Metadata

Annotations:
- indexed trace attributes,
- searchable/filterable.

Metadata:
- non-indexed trace detail.

Detailed annotation strategy:
- belongs primarily to 4.2.4.

For 4.2.6, know:

```text
need searchable trace attribute
→ annotation

need rich detail after opening trace
→ metadata
```

---

#### 4.2.6.22 AWS Lambda Tracing Modes

Lambda supports:

```text
Active
PassThrough
```

for X-Ray tracing.

This distinction is:
- highly exam-relevant.

---

#### 4.2.6.23 Lambda `Active`

With Active tracing:
- Lambda automatically creates/sends sampled service traces.

Use when:

```text
Lambda invocation itself
→ should appear automatically in X-Ray/CloudWatch trace data
```

---

#### 4.2.6.24 Lambda `PassThrough`

Current documented behavior:

```text
PassThrough
→ propagates X-Ray tracing context downstream
→ does not automatically send Lambda traces
```

This remains true even if:
- an upstream tracing header includes a sampling decision.

Therefore:

```text
need automatic Lambda traces
→ Active
```

---

#### 4.2.6.25 Default Lambda Tracing Mode

If Active tracing is not enabled:
- Lambda defaults to `PassThrough`.

Therefore:

```text
function executes
+
upstream service is traced
```

does **not** automatically guarantee:
- a Lambda trace.

---

#### 4.2.6.26 Enable Active Tracing

CLI concept:

```bash
aws lambda update-function-configuration \
  --function-name my-function \
  --tracing-config Mode=Active
```

CloudFormation:

```yaml
TracingConfig:
  Mode: Active
```

SAM:

```yaml
Tracing: Active
```

Exam principle:

```text
service-level tracing configuration
→ can be enabled through infrastructure configuration
```

---

#### 4.2.6.27 Lambda Trace Permissions

Lambda requires:

```text
xray:PutTraceSegments
xray:PutTelemetryRecords
```

These are included in:

```text
AWSXRayDaemonWriteAccess
```

If Active tracing is enabled but traces are missing:
- verify execution-role permissions.

---

#### 4.2.6.28 Lambda Sampling

For Lambda Active tracing, AWS documents:

```text
1 request per second
+
5% of additional requests
```

for requests without:
- an upstream sampling decision.

Important:

```text
Lambda X-Ray sampling rate
→ cannot be configured directly on the function
```

Do not propose:
- a Lambda setting for an arbitrary sampling percentage.

---

#### 4.2.6.29 Upstream Sampling with Lambda

If an upstream service supplies:
- tracing context with a sampling decision,

Lambda Active tracing:
- uses that decision.

Therefore:
- distributed sampling can begin upstream.

---

#### 4.2.6.30 Lambda Segment Ownership

Lambda:
- creates the parent segment for the function invocation.

Application code:
- does not replace that parent segment.

For deeper tracing:
- create subsegments/spans.

Fast rule:

```text
Lambda parent segment
→ owned by Lambda service

application work
→ subsegments/spans
```

---

#### 4.2.6.31 Lambda Application Instrumentation

Inside Lambda, tracing can capture:
- AWS SDK calls,
- HTTP dependencies,
- application methods,
- annotations,
- metadata.

Traditional/current options can include:
- X-Ray SDK,
- Powertools,
- ADOT/OpenTelemetry.

Current AWS direction:
- favors OpenTelemetry for new instrumentation.

---

#### 4.2.6.32 API Gateway and Lambda

Typical path:

```text
Client
→ API Gateway
→ Lambda
→ downstream service
```

With correct tracing and propagation, traces can reveal:
- API latency,
- Lambda duration,
- downstream latency,
- failure location.

Use:
- the timeline

to determine:
- which component dominates latency.

---

#### 4.2.6.33 Event-Driven Tracing

Asynchronous applications are harder to trace.

Example:

```text
producer
→ queue/topic
→ consumer
```

Trace context must:
- cross asynchronous boundaries where supported.

Do not assume:
- synchronous HTTP-style behavior for every event source.

---

#### 4.2.6.34 SQS and Lambda

Current Lambda/X-Ray integrations can:
- link upstream producer traces associated with SQS to downstream Lambda traces.

This can provide:
- end-to-end event-driven visibility.

But tracing behavior:
- depends on integration support.

---

#### 4.2.6.35 Event Source Limitations

Current Lambda documentation states X-Ray tracing is not supported for Lambda functions using event source mappings for:
- Amazon MSK,
- self-managed Apache Kafka,
- Amazon MQ,
- Amazon DocumentDB.

Therefore:

```text
Lambda supports X-Ray
≠ every Lambda event source supports identical tracing
```

This is a strong rejection rule.

---

#### 4.2.6.36 AWS Step Functions

Step Functions supports:
- X-Ray tracing.

A traced workflow can expose:
- state-machine execution path,
- supported service integrations,
- execution timing,
- service-map nodes.

Use when:
- workflow topology and service latency matter.

---

#### 4.2.6.37 Unsupported/Uninstrumented Downstream Service

A downstream service does not always need to emit:
- its own X-Ray segment.

An instrumented upstream call can create:
- a subsegment,
- inferred downstream node.

Example:

```text
Lambda
→ DynamoDB
```

Even if DynamoDB does not emit its own X-Ray segment:
- the upstream subsegment can provide dependency visibility.

---

#### 4.2.6.38 Two-Sided Instrumentation

When both sides are instrumented:

```text
upstream subsegment
→ caller's view of request

downstream segment
→ server's view of processing
```

This helps distinguish:
- network/round-trip time,
- downstream processing time.

---

#### 4.2.6.39 Stable Service Naming

Segment/service names should represent:
- logical services/resources.

Stable naming makes:
- trace maps understandable.

Avoid:
- highly dynamic service names.

Good:

```text
checkout-service
payment-service
```

Weak:

```text
checkout-service-request-123456
```

---

#### 4.2.6.40 X-Ray Filter Expressions and Groups

X-Ray supports:
- filter expressions.

They can find traces by:
- service information,
- response/error properties,
- indexed annotations,
- other supported trace attributes.

X-Ray groups:
- classify matching traces using filter expressions.

A group can produce:
- its own trace/service view,
- CloudWatch metrics for matching traces.

Use for:
- operational segmentation of trace data.

---

#### 4.2.6.41 Trace Retention

Current X-Ray documentation states:
- trace data is retained for 30 days,
- service graph data is retained for 30 days.

Therefore:

```text
X-Ray
≠ indefinite audit archive
```

Use another storage/audit mechanism when:
- longer retention is required.

---

#### 4.2.6.42 Tracing Overhead

Instrumentation can add:
- CPU work,
- telemetry processing,
- network activity,
- data volume,
- cost.

Control overhead with:
- sampling,
- meaningful instrumentation,
- bounded context.

Do not trace:
- every line/function manually.

---

#### 4.2.6.43 Sampling vs Debugging

Sampling provides:
- representative observability.

If a particular class of request must be prioritized:
- supported sampling rules can target that traffic in non-Lambda SDK contexts.

Do not globally disable sampling:
- without considering volume/cost.

For Lambda:
- remember sampling percentage is not directly configurable on the function.

---

#### 4.2.6.44 Security Boundary

Trace telemetry can contain:
- URLs,
- resource names,
- operation names,
- errors,
- annotations,
- metadata.

Do not record:
- passwords,
- tokens,
- private keys,
- sensitive request bodies

merely because:
- tracing data is internal.

Observability telemetry:
- still requires security/privacy controls.

#### 4.2.6.62 Final Principle

**Distributed tracing reconstructs individual requests across service boundaries so developers can see topology, timing, downstream dependencies, and failure location. In X-Ray, traces contain service segments and finer-grained subsegments connected by trace IDs and propagated tracing context. Sampling controls telemetry volume, so an absent trace does not automatically indicate tracing failure. For Lambda, enable Active tracing when sampled invocation traces should be sent automatically, ensure the execution role can call `xray:PutTraceSegments` and `xray:PutTelemetryRecords`, and add deeper application instrumentation through subsegments or spans rather than attempting to replace the Lambda-created parent segment. Instrument meaningful dependencies and business operations, preserve trace-context propagation, and correlate traces with logs and metrics. For new implementations, AWS now recommends OpenTelemetry/ADOT; the X-Ray SDKs and daemon entered maintenance mode on February 25, 2026, while X-Ray traces, segments, subsegments, sampling, and Lambda integration remain important DVA-C02 concepts.**

##### 4.2.6.63.11 Source Priority
1. DVA-C02 exam guide defines the exact tracing skill boundary.
2. X-Ray Concepts defines the core trace data model.
3. Lambda X-Ray documentation defines Lambda tracing modes, sampling, permissions, and integration limits.
4. X-Ray Lambda integration defines parent-segment ownership.
5. Trace/trace-map documentation defines investigation workflows.
6. Step Functions documentation covers workflow tracing.
7. Current migration/support documentation establishes OpenTelemetry/ADOT as the preferred new-instrumentation direction.
8. Annotation design remains primarily in 4.2.4.
9. Structured logging remains in 4.2.7.
