### 4.2.3 Implement code that emits custom metrics

#### 4.2.3.1 Exam and Task Context

##### 4.2.3.1.1 Domain and Task
- Domain 4 is **Troubleshooting and Optimization**.
- Task 4.2 is **Instrument code for observability**.
- Skill 4.2.3 is **Implement code that emits custom metrics**.

##### 4.2.3.1.2 Position Inside Task 4.2
- 4.2.2:
  - implement application logging.
- 4.2.3:
  - emit application-defined numerical telemetry.
- 4.2.4:
  - add tracing annotations.

  - implement notification alerts.

Core question:

**How should application code publish meaningful numerical signals to CloudWatch when AWS-native service metrics do not represent the application or business behavior you need to monitor?**

#### 4.2.3.2 Core Mental Model

```text
APPLICATION BEHAVIOR
        |
        v
numerical signal worth monitoring?
        |
        v
CUSTOM METRIC
        |
        +--> namespace
        +--> metric name
        +--> value
        +--> unit
        +--> dimensions
        +--> timestamp/resolution
        |
        v
     CLOUDWATCH
        |
        +--> statistics
        +--> dashboards
        +--> alarms
        '--> troubleshooting
```

Custom metrics answer questions such as:

```text
How many orders failed?
How many payments were declined?
How long does checkout processing take?
How many items remain in an application workflow?
```

#### 4.2.3.3 Native AWS Metrics vs Custom Metrics

AWS services already publish many infrastructure metrics.

Examples:

```text
Lambda Invocations
Lambda Errors
Lambda Duration
Lambda Throttles
SQS queue metrics
DynamoDB metrics
```

Use those when:
- they already express the required signal.

Custom metrics are needed when AWS cannot infer:
- application semantics,
- business outcomes,
- internal application behavior.

Examples:

```text
CheckoutValidationFailures
OrdersCompleted
PaymentProviderFailures
InventoryReservationFailures
RetryCount
```

Rule:

```text
AWS already exposes the signal?
→ use native metric

business/application-specific signal missing?
→ custom metric
```

#### 4.2.3.4 CloudWatch Metric Identity

A metric is:
- a time-ordered set of numerical data points.

CloudWatch identifies a metric time series using:

```text
namespace
+
metric name
+
dimension combination
```

Therefore:

```text
same metric name
+
different dimensions
→ different metric time series
```

This is central to:
- cardinality,
- cost,
- queryability.

#### 4.2.3.5 Namespace

A namespace:
- groups related metrics.

Example:

```text
MyCompany/Checkout
```

Possible metrics:

```text
OrdersCreated
PaymentFailures
CheckoutDuration
```

Use:
- a custom namespace

rather than:
- AWS-owned namespaces.

Keep namespaces:
- stable,
- meaningful.

#### 4.2.3.6 Metric Name

Metric names should describe:
- the measured quantity.

Good:

```text
PaymentFailures
OrderProcessingDuration
ItemsProcessed
RetryCount
```

Weak:

```text
Value
Thing
Metric1
```

Avoid dynamic names such as:

```text
CheckoutFailure_Order_123
CheckoutFailure_Order_456
```

because dynamic metric names can create:
- uncontrolled cardinality,
- poor comparability.

#### 4.2.3.7 Value

A metric data point contains:
- a numeric value.

Examples:

```text
PaymentFailure = 1
ProcessingDuration = 325
ActiveJobs = 17
```

CloudWatch aggregates data over time using:
- statistics.

#### 4.2.3.8 Unit

Use the unit that matches metric meaning.

Examples:

```text
Count
Seconds
Milliseconds
Bytes
Percent
```

Avoid ambiguous values:

```text
duration = 500
```

without specifying:
- seconds or milliseconds.

#### 4.2.3.9 Dimensions

A dimension is:
- a name/value characteristic attached to a metric.

Example:

```text
Metric:
PaymentFailures

Dimension:
Provider=Primary
```

Useful bounded dimensions:

```text
Environment=prod
Service=checkout
Operation=payment
Provider=primary
Result=success|failure
```

Dimensions enable:
- grouping,
- filtering,
- per-category analysis.

#### 4.2.3.10 Dimension Limit

CloudWatch currently supports:
- up to 30 dimensions per custom metric.

But:

```text
maximum supported
≠ recommended design target
```

Use only dimensions that:
- support real operational questions.

#### 4.2.3.11 Cardinality

High-cardinality dimensions include:

```text
requestId
userId
orderId
timestamp
random UUID
```

If values are mostly unique:

```text
1 metric
× many unique values
→ many metric time series
```

This can increase:
- cost,
- complexity,
- operational noise.

Rule:

```text
bounded operational category
→ dimension

unique diagnostic identifier
→ logs/traces/metadata
```

#### 4.2.3.12 Metadata vs Dimensions

With EMF or Powertools:

```text
dimension
→ part of metric identity

metadata
→ detailed log context
```

Example:

```text
dimension:
Service=checkout

metadata:
requestId=abc
orderId=123456
```

This preserves:
- troubleshooting context

without:
- exploding metric cardinality.

#### 4.2.3.13 `PutMetricData`

CloudWatch provides:

```text
PutMetricData
```

for:
- direct custom-metric publication.

Conceptual request:

```text
Namespace = MyApp/Orders
MetricName = OrdersCreated
Value = 1
Unit = Count
```

If the metric does not yet exist:
- CloudWatch creates it when data is first published.

#### 4.2.3.14 Direct API Publishing

Path:

```text
application code
→ CloudWatch SDK/API
→ PutMetricData
→ custom metric
```

Benefits:
- explicit,
- direct,
- works outside Lambda.

Tradeoff:
- application makes a CloudWatch API call.

For high-throughput/serverless workloads:
- asynchronous telemetry approaches can be preferable.

#### 4.2.3.15 IAM Permission for `PutMetricData`

Code that calls CloudWatch directly requires:

```text
cloudwatch:PutMetricData
```

This permission belongs to:
- the application execution identity/role.

Do not confuse it with:
- reading metrics,
- configuring alarms.

#### 4.2.3.16 `PutMetricData` Example — Java Concept

```java
MetricDatum datum = MetricDatum.builder()
    .metricName("OrdersCreated")
    .unit(StandardUnit.COUNT)
    .value(1.0)
    .build();

PutMetricDataRequest request = PutMetricDataRequest.builder()
    .namespace("MyApp/Orders")
    .metricData(datum)
    .build();

cloudWatchClient.putMetricData(request);
```

Exam meaning:

```text
application
→ SDK
→ PutMetricData
→ CloudWatch metric
```

#### 4.2.3.17 Embedded Metric Format

CloudWatch Embedded Metric Format (EMF) uses:

```text
structured log event
→ CloudWatch Logs
→ asynchronous custom metric extraction
```

Flow:

```text
application
→ EMF JSON
→ CloudWatch Logs
→ metric extraction
→ CloudWatch Metrics
```

The log event remains available for:
- detailed troubleshooting.

#### 4.2.3.18 Why EMF Matters for Lambda

AWS positions EMF as useful for:
- Lambda,
- containers,
- ephemeral workloads.

Instead of:

```text
Lambda invocation
→ synchronous PutMetricData call
```

use:

```text
Lambda
→ EMF log
→ CloudWatch asynchronously extracts metric
```

Benefit:
- no separate synchronous metric API call in the invocation path.

#### 4.2.3.19 EMF Correlation Benefit

One event can include:

```text
metric:
PaymentFailures = 1
```

plus:

```text
requestId
orderId
provider
errorType
```

Then:

```text
metric
→ detects aggregate problem

log
→ explains individual event
```

This supports:
- correlation without high-cardinality metric dimensions.

#### 4.2.3.20 EMF Structure

Conceptual example:

```json
{
  "_aws": {
    "CloudWatchMetrics": [
      {
        "Namespace": "MyApp",
        "Dimensions": [["Service"]],
        "Metrics": [
          {
            "Name": "PaymentFailures",
            "Unit": "Count"
          }
        ]
      }
    ]
  },
  "Service": "checkout",
  "PaymentFailures": 1,
  "orderId": "123"
}
```

CloudWatch extracts:

```text
MyApp
PaymentFailures
Service=checkout
```

while:

```text
orderId
```

can remain:
- log metadata.

#### 4.2.3.21 EMF Key Concept

Important:

```text
valid JSON
≠ automatically EMF
```

EMF needs:
- its metric metadata structure,
- including `_aws` / `CloudWatchMetrics`.

Detailed EMF schema:
- remains implementation detail,
- but recognize the mechanism.

#### 4.2.3.22 Powertools for AWS Lambda Metrics

Powertools provides:
- Metrics utilities.

For Java, Powertools Metrics:
- emits EMF through standard output,
- validates metric configuration,
- handles dimensions,
- supports metadata,
- supports aggregation/flushing patterns.

Concept:

```text
application
→ Powertools Metrics
→ EMF
→ CloudWatch Logs
→ CloudWatch Metrics
```

#### 4.2.3.23 Powertools Example — Java Concept

```java
metrics.addMetric(
    "OrdersCreated",
    1,
    MetricUnit.COUNT
);
```

With configured:
- namespace,
- service,
- dimensions,

Powertools produces:
- EMF output.

#### 4.2.3.24 Powertools Metadata

Powertools can add metadata for:
- request IDs,
- order IDs,
- other high-cardinality context.

Use metadata when:

```text
need diagnostic detail
but
do not need separate metric time series
```

#### 4.2.3.25 Default Dimensions

Powertools can define default dimensions such as:

```text
Service=checkout
Environment=prod
```

Use carefully because:

```text
each dimension combination
→ distinct metric identity
```

Default dimensions should be:
- stable,
- bounded.

#### 4.2.3.26 Metric Aggregation

Applications can reduce API overhead by:
- batching/aggregating data.

CloudWatch `PutMetricData` supports:
- multiple metric data points,
- statistic sets,
- value/count arrays.

Purpose:
- reduce API calls,
- improve efficiency.

#### 4.2.3.27 Statistic Set

A statistic set contains:

```text
SampleCount
Sum
Minimum
Maximum
```

Example:

```text
5 observations
sum = 1000
min = 100
max = 300
```

Use when:
- aggregated data is sufficient.

#### 4.2.3.28 Percentile Caveat

General percentile calculation is strongest when:
- raw observations are available.

If only statistic sets are published:
- percentile calculation has AWS-documented restrictions.

Therefore:

```text
p95 / p99 important?
→ understand publication format
```

Do not assume:
- every aggregation preserves all percentile behavior.

#### 4.2.3.29 Standard Resolution

Standard custom metrics:

```text
1-minute granularity
```

Use when:
- sub-minute visibility is unnecessary.

This should be:
- the normal default.

#### 4.2.3.30 High Resolution

High-resolution custom metrics:

```text
1-second granularity
```

Use when:
- short spikes matter,
- sub-minute visibility is required.

Tradeoff:
- additional cost.

Rule:

```text
need sub-minute detection?
→ high resolution

otherwise
→ standard resolution
```

#### 4.2.3.31 High-Resolution Alarms

High-resolution custom metrics can support alarms with:
- 10-second,
- 30-second
periods.

Use only when:
- faster detection justifies cost.

Do not confuse:

```text
metric storage resolution
```

with:

```text
alarm evaluation period
```

#### 4.2.3.32 Timestamp

Custom metric data can include:
- timestamp.

Important for:
- delayed/batched observations.

Correct timestamps preserve:
- event chronology.

Avoid:
- unsupported future/old timestamps.

#### 4.2.3.33 Zero vs Missing Data

These are different:

```text
0
→ measured zero
```

```text
missing
→ no data point was published
```

This affects:
- statistics,
- alarms,
- heartbeat interpretation.

#### 4.2.3.34 Heartbeat Pattern

Example:

```text
ApplicationHeartbeat = 1
```

published periodically.

Then:

```text
heartbeat missing
→ application may not be executing/publishing
```

Compare with:

```text
WorkItemsProcessed = 0
```

which means:

```text
application ran
but processed zero items
```

#### 4.2.3.35 Counter Pattern

For discrete events:

```text
OrderCreated
PaymentFailed
RetryAttempted
```

emit:

```text
value = 1
unit = Count
```

Then:

```text
Sum
```

answers:
- how many events occurred.

#### 4.2.3.36 Duration Pattern

For latency:

```text
OrderProcessingDuration
value = 325
unit = Milliseconds
```

Useful statistics can include:
- Average,
- p95,
- p99,
- Maximum.

Statistic choice depends on:
- operational question,
- publication format.

#### 4.2.3.37 Gauge Pattern

For current state:

```text
ActiveJobs = 17
QueueDepth = 42
```

publish:
- current numeric observation.

Do not mechanically use:
- `Sum`

for a gauge.

#### 4.2.3.38 Statistic Selection

Choose statistic according to metric semantics.

```text
event count
→ Sum

latency
→ Average / percentile / Maximum

current utilization/state
→ Average / Maximum

heartbeat
→ SampleCount / presence
```

Do not default to:
- Average for every metric.

#### 4.2.3.39 Business Metrics

Strong custom metrics often represent:
- business outcomes.

Examples:

```text
OrdersAccepted
OrdersRejected
PaymentFailures
InventoryReservationFailures
CheckoutDuration
```

These complement:
- infrastructure metrics.

#### 4.2.3.40 Technical Application Metrics

Examples:

```text
RetryCount
CacheMisses
DependencyFailures
ItemsProcessed
InvalidMessages
```

Use when they reveal:
- application behavior AWS cannot infer automatically.

#### 4.2.3.41 Avoid Duplicating Native Metrics

If Lambda already publishes:

```text
Errors
Duration
Invocations
Throttles
```

do not recreate identical custom metrics unless:
- there is a specific application semantic reason.

Prefer:
- business/application-specific measurements.

#### 4.2.3.42 Metric vs Log

Need:

```text
Payment failed for order 123 because provider timed out
```

→ log.

Need:

```text
payment failures per 5 minutes
```

→ metric.

Often:
- both are useful.

#### 4.2.3.43 Metric vs Trace

Need:

```text
where did this request spend 2 seconds?
```

→ trace.

Need:

```text
p95 checkout duration over 24 hours
```

→ metric.

Do not force:
- one telemetry type to answer every question.

#### 4.2.3.44 Metrics and Alarms

Once a custom metric exists:

```text
PaymentFailures
      |
      v
CloudWatch alarm
      |
      v
notification/action
```

Metric creation:
- 4.2.3.

Notification-alert implementation:
- 4.2.5.

#### 4.2.3.45 Metrics and Dashboards

Custom metrics can appear on:
- CloudWatch dashboards.

Useful for:
- trends,
- release comparisons,
- application health,
- business KPIs.

A dashboard:
- consumes the metric,
- does not create the application signal.

#### 4.2.3.46 Metric Math

CloudWatch metric math can derive:

```text
FailureRate =
PaymentFailures / PaymentAttempts * 100
```

Therefore code can emit:
- primitive counters

and CloudWatch can derive:
- ratios/rates.

This separates:

```text
raw observation
from
derived monitoring logic
```

#### 4.2.3.47 Error-Rate Pattern

Emit:

```text
Requests = 1
Failures = 1 when failure occurs
```

Then derive:

```text
FailureRate
```

with:
- metric math.

This preserves:
- raw counts,
- flexibility.

#### 4.2.3.48 Emit at the Correct Semantic Point

Example:

```text
payment succeeds
→ order persistence succeeds
→ business completion becomes true
```

`OrderCompleted` should increment:
- only when the business condition defining completion is actually true.

Bad instrumentation can be:
- technically valid,
- semantically wrong.

#### 4.2.3.49 Avoid Double Counting

Retries can execute the same code path multiple times.

If metric means:

```text
PaymentAttempt
```

count:
- every attempt.

If metric means:

```text
UniqueOrderCompleted
```

do not count:
- each retry.

Metric semantics must be:
- explicit.

#### 4.2.3.50 Success/Failure Metric Design

Two valid approaches:

```text
PaymentAttempts
PaymentSuccesses
PaymentFailures
```

or:

```text
PaymentRequests
Dimension:
Result=Success|Failure
```

Choose based on:
- query simplicity,
- dimension strategy,
- alarm requirements,
- cardinality.

#### 4.2.3.51 Instrument Failure Paths

Instrumentation should cover:
- successful paths,
- meaningful failure paths.

Conceptual example:

```java
try {
    process();
    metrics.addMetric("Processed", 1, COUNT);
} catch (Exception e) {
    metrics.addMetric("ProcessingFailures", 1, COUNT);
    throw e;
}
```

Otherwise dashboards may:
- only reflect successful behavior.

#### 4.2.3.52 Metric Emission Must Not Become the Primary Failure Mode

Observability code should not casually become:
- a critical business dependency.

Direct synchronous metric calls can introduce:
- latency,
- throttling,
- metric-publication failure handling.

This is one reason:
- EMF,
- OpenTelemetry
can be attractive.

#### 4.2.3.53 EMF vs `PutMetricData`

```text
PutMetricData
→ direct CloudWatch API publication
```

```text
EMF
→ structured log
→ asynchronous metric extraction
```

For Lambda/serverless:

```text
EMF / Powertools
→ strong implementation fit
```

For other workloads:
- direct API,
- EMF,
- OpenTelemetry,
- collectors/agents
may all be valid depending on architecture.

#### 4.2.3.54 OpenTelemetry

Current CloudWatch documentation recommends:
- OpenTelemetry for new custom-metric implementations.

OpenTelemetry provides:
- vendor-neutral instrumentation/export.

Concept:

```text
application
→ OpenTelemetry instrumentation
→ collector/exporter
→ CloudWatch
```

Potential benefits:
- standardized instrumentation,
- portability,
- unified telemetry pipeline.

#### 4.2.3.55 `PutMetricData` Still Matters

Even with current OpenTelemetry guidance:

```text
PutMetricData
```

remains:
- the fundamental CloudWatch direct API,
- exam relevant.

Know the three paths:

```text

→ PutMetricData

asynchronous log-based
→ EMF / Powertools

vendor-neutral instrumentation
→ OpenTelemetry
```

##### 4.2.3.63.3 Final Principle
- **Emit custom metrics when application-specific numerical behavior is not already represented by AWS service metrics. Define stable namespaces and metric names, use meaningful units, and keep dimensions bounded because namespace + metric name + dimension combination defines the CloudWatch time series. Use `PutMetricData` for direct publication, EMF/Powertools for asynchronous Lambda-friendly metric creation, and recognize OpenTelemetry as the current vendor-neutral path recommended by CloudWatch for new implementations. Keep high-cardinality request, user, and business identifiers in logs, traces, or metadata instead of dimensions. Use standard resolution unless sub-minute detection justifies high-resolution cost, choose statistics according to metric semantics, distinguish zero from missing data, and emit each metric at the business or technical point that accurately represents what it claims to measure.**
