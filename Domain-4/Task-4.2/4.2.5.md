#### 4.2.5.2 Core Mental Model

```text
OBSERVABLE SIGNAL
      |
      +--> metric
      +--> log condition
      +--> AWS event
      |
      v
DETECTION / RULE
      |
      +--> CloudWatch alarm
      '--> EventBridge rule
      |
      v
ACTION / ROUTING
      |
      +--> SNS
      +--> Lambda
      +--> Systems Manager
      '--> other EventBridge target
      |
      v
HUMAN OR AUTOMATION
```

Keep the layers separate:

```text
signal
≠ alarm
≠ notification
```

Example:

```text
PaymentFailures metric
→ CloudWatch alarm
→ SNS topic
→ email/operator
```

---

#### 4.2.5.3 Start With the Condition

Do not begin with:

```text
Which notification service should I use?
```

Begin with:

```text
What condition is actionable?
```

Examples:

```text
error rate > threshold
queue age too high
business failures increasing
dependency unavailable
specific AWS event occurred
```

A good alert:
- represents meaningful impact or risk,
- reaches an appropriate owner or automation,
- avoids unnecessary noise.

---

#### 4.2.5.4 Metric-Based Alerting

Use a CloudWatch metric alarm when the question is:

```text
Did a numerical signal cross a condition?
```

Examples:

```text
Errors > 5
p95 latency > 2 s
queue age > 300 s
failure rate > 5%
```

Metric alarms can evaluate:
- a metric,
- a metric-math expression,
- supported query-based alarm data.

---

#### 4.2.5.5 CloudWatch Alarm States

CloudWatch alarms commonly use:

```text
OK
ALARM
INSUFFICIENT_DATA
```

##### `OK`

```text
condition
→ within configured threshold/state
```

##### `ALARM`

```text
condition
→ breached
```

##### `INSUFFICIENT_DATA`

```text
not enough usable data
→ state cannot be determined normally
```

Important:

```text
INSUFFICIENT_DATA
≠ automatically application failure
```

---

#### 4.2.5.6 Alarm Actions Are State-Transition Driven

CloudWatch alarm actions execute when:
- the alarm transitions into a configured state.

Example:

```text
OK
→ ALARM
→ SNS notification
```

If the alarm remains:

```text
ALARM
```

the normal state-transition action does **not** automatically execute every evaluation period simply because the metric is still breaching.

This is a high-value exam distinction.

---

#### 4.2.5.7 Recovery and Other State Actions

Actions can be configured for states including:

```text
ALARM
OK
INSUFFICIENT_DATA
```

Typical pattern:

```text
ALARM
→ "Checkout failure rate high"

OK
→ "Checkout recovered"
```

CloudWatch API concepts include:

```text
AlarmActions
OKActions
InsufficientDataActions
```

Recovery notifications:
- help close the operational feedback loop.

---

#### 4.2.5.8 Alarm Evaluation Model

A metric alarm is defined by concepts such as:

```text
metric / expression
statistic
period
threshold
comparison operator
EvaluationPeriods
DatapointsToAlarm
missing-data behavior
```

Mental model:

```text
signal
→ aggregate over period
→ evaluate against threshold
→ count breaching datapoints
→ determine alarm state
```

---

#### 4.2.5.9 Period

The period defines:
- the aggregation interval used for alarm evaluation.

Examples:

```text
60 seconds
5 minutes
```

Shorter periods can:
- detect changes faster,

but:
- metric resolution,
- volatility,
- cost/noise

still matter.

---

#### 4.2.5.10 Evaluation Periods and M-out-of-N

`EvaluationPeriods`:

```text
N
→ number of recent periods evaluated
```

`DatapointsToAlarm`:

```text
M
→ number of breaching datapoints required
```

Example:

```text
EvaluationPeriods = 5
DatapointsToAlarm = 3
```

means:

```text
3 breaching datapoints
out of 5 evaluated periods
→ ALARM
```

This is commonly called:

```text
M out of N
```

Benefit:
- reduces alerts from isolated spikes.

---

#### 4.2.5.11 Threshold and Comparison Operator

Example:

```text
PaymentFailures > 10
```

But threshold alone is incomplete.

Always ask:

```text
using which statistic?
over which period?
for how many periods?
how are missing datapoints treated?
```

Common comparison concepts:

```text
GreaterThanThreshold
GreaterThanOrEqualToThreshold
LessThanThreshold
LessThanOrEqualToThreshold
```

---

#### 4.2.5.12 Statistic

Alarm statistics can include:

```text
Average
Sum
Minimum
Maximum
SampleCount
percentiles
```

Typical mapping:

```text
PaymentFailures
→ Sum

Latency
→ p95 / p99 / Average / Maximum
depending on requirement
```

Wrong statistic:
- can make an alarm technically valid but operationally misleading.

---

#### 4.2.5.13 Error Count vs Error Rate

Raw error count alone can misrepresent user impact.

Example:

```text
10 errors / 100 requests
→ 10%

10 errors / 1,000,000 requests
→ 0.001%
```

Metric math can derive:

```text
ErrorRate =
Errors / Requests
```

Use a rate when:
- impact depends on traffic volume.

---

#### 4.2.5.14 Percentile Alarms

Latency alarms often use:

```text
p95
p99
```

because:

```text
average
→ can hide slow tail requests
```

Percentile alarms require:
- appropriate sample volume,
- suitable metric publication.

CloudWatch supports controls for:
- low sample-count percentile evaluation.

Use them according to:
- workload behavior.

---

#### 4.2.5.15 High-Resolution Alarms

High-resolution custom metrics can support alarm periods such as:

```text
10 seconds
30 seconds
```

Use when:
- very fast detection is required.

Tradeoff:
- higher cost,
- greater sensitivity to short-lived spikes.

Do not choose high resolution:
- automatically.

---

#### 4.2.5.16 Missing Data

Metrics do not always publish:
- one datapoint every period.

CloudWatch supports treating missing data as:

```text
breaching
notBreaching
ignore
missing
```

The right setting depends on:
- metric semantics.

---

#### 4.2.5.17 Sparse Error Metric Example

Suppose:

```text
ErrorCount = 1
```

is emitted only when:
- an error occurs.

Then:

```text
no datapoint
```

may mean:
- no errors occurred.

Treating every missing period as:
- `breaching`

could create:
- false alerts.

Possible approaches:
- use `notBreaching` where appropriate,
- or explicitly emit zero when semantically correct.

---

#### 4.2.5.18 Heartbeat Example

Suppose:

```text
Heartbeat = 1
every minute
```

Then:

```text
missing datapoint
```

may mean:
- publisher/application stopped.

Here:

```text
missing
→ may itself represent failure
```

This is the opposite of:
- sparse error metrics.

Core rule:

```text
missing-data policy
→ must match what absence means
```

---

#### 4.2.5.19 `ignore` and `missing`

##### `ignore`

```text
missing datapoints
→ alarm retains current state
```

Use only when:
- maintaining current state is desired.

##### `missing`

If all relevant datapoints are missing:
- the alarm can enter `INSUFFICIENT_DATA`.

Useful when:
- absence is ambiguous.

---

#### 4.2.5.20 Amazon SNS

Amazon SNS provides:
- publish/subscribe messaging.

Classic operational notification path:

```text
CloudWatch alarm
→ SNS topic
→ subscribers
```

Supported subscription patterns can include:
- email,
- HTTP/S,
- SQS,
- Lambda,
- mobile push,
- other supported SNS endpoints.

---

#### 4.2.5.21 SNS Fanout

A topic decouples:
- the alarm

from:
- notification consumers.

Example:

```text
CloudWatch alarm
       |
       v
    SNS topic
       |
       +--> email
       +--> Lambda
       +--> SQS
       '--> HTTPS endpoint
```

Benefit:

```text
one detected condition
→ multiple independent consumers
```

---

#### 4.2.5.22 SNS Subscription Confirmation

For protocols such as:
- email,
- HTTP/S,

subscriptions may require:
- confirmation.

Exam scenario:

```text
alarm is configured
SNS topic exists
email never arrives
```

Check:
- subscription confirmation status.

---

#### 4.2.5.23 SNS Topic Policy and Permissions

Successful notification can depend on:
- topic resource policy,
- cross-account permissions,
- encryption-related permissions/configuration.

Do not assume:

```text
SNS topic ARN configured
→ delivery path automatically works
```

The full path must be valid.

---

#### 4.2.5.24 CloudWatch Does Not Validate Every Target

AWS documents that CloudWatch does not fully validate:
- every alarm action target when configured.

Therefore:

```text
alarm exists
≠ notification path proven
```

You must test:
- action execution,
- permissions,
- SNS publication,
- subscription delivery.

---

#### 4.2.5.25 Alarm to Lambda

CloudWatch alarms can invoke:
- Lambda functions on configured state changes.

Pattern:

```text
alarm
→ Lambda
→ custom remediation / integration
```

Use when:
- the response should be programmatic.

---

#### 4.2.5.26 Human Notification vs Automation

Human-oriented:

```text
alarm
→ SNS
→ operator
```

Automated:

```text
alarm
→ Lambda
→ remediation
```

Do not assume:
- every technical condition should page a human.

If safe automation can resolve it:
- automated action may be preferable.

---

#### 4.2.5.27 EventBridge

CloudWatch emits alarm state-change events to:
- Amazon EventBridge.

Concept:

```text
CloudWatch Alarm State Change
→ EventBridge rule
→ target
```

EventBridge enables:
- flexible event matching,
- routing by event content,
- multiple downstream workflows.

---

#### 4.2.5.28 EventBridge Alarm Pattern

Conceptual event pattern:

```json
{
  "source": ["aws.cloudwatch"],
  "detail-type": ["CloudWatch Alarm State Change"]
}
```

Rules can filter further by:
- alarm name,
- state,
- account,
- Region,
- event details.

No polling is required.

---

#### 4.2.5.29 SNS vs EventBridge

Use SNS when:

```text
publish notification
→ fan out to subscribers
```

Use EventBridge when:

```text
match event content
→ route to selected targets
```

They can be combined.

Example:

```text
EventBridge
→ SNS topic
→ subscribers
```

---

#### 4.2.5.30 Event-Based Alerting

Not every alert needs:
- a metric alarm.

If the condition itself is an AWS event:

```text
AWS event
→ EventBridge rule
→ target
```

may be more direct.

Use EventBridge when the question is:

```text
Did a particular event occur?
```

Examples:

```text
resource state change
alarm state change
specific AWS service event
```

High-value distinction:

```text
numerical condition
→ CloudWatch alarm

specific event occurrence
→ EventBridge
```

---

#### 4.2.5.31 Log-Based Alerting

Classic exam path:

```text
log event
→ CloudWatch Logs metric filter
→ custom metric
→ CloudWatch alarm
→ SNS
```

Example:

```text
"PaymentProviderUnavailable"
→ metric filter
→ PaymentProviderFailures
→ alarm
→ SNS
```

Use when:
- the application already emits a recognizable log pattern.

---

#### 4.2.5.32 CloudWatch Log Alarms

Current CloudWatch also supports:
- Log Alarms based on Logs Insights query results.

Supported actions can include:
- SNS,
- Lambda,
- Systems Manager OpsItem creation.

For DVA-C02:
- know the classic metric-filter pattern first,
- also recognize current Log Alarm capability.

Mental model:

```text
classic:

current:

```

#### 4.2.5.33 Composite Alarms

A composite alarm evaluates:
- states of other CloudWatch alarms.

It does **not**:
- monitor raw metrics directly.

Example:

```text
ALARM(HighLatency)
AND
ALARM(HighErrorRate)
```

Then:
- the composite alarm becomes actionable.

---

#### 4.2.5.34 Why Composite Alarms Matter

Primary purpose:
- reduce alarm noise.

Instead of:

```text
10 related alarms
→ 10 notifications
```

use:

```text
underlying alarms
→ composite alarm
→ one actionable notification
```

This is especially useful when:
- many symptoms represent one incident.

---

#### 4.2.5.35 Composite Alarm Boolean Logic

Composite alarm rules can use:

```text
ALARM(...)
OK(...)
INSUFFICIENT_DATA(...)

AND
OR
NOT
```

Example:

```text
ALARM("CheckoutErrors")
AND
ALARM("PaymentDependencyErrors")
```

Meaning:

```text
checkout unhealthy
AND
payment dependency unhealthy
→ notify
```

---

#### 4.2.5.36 Composite Alarm Scope

Current AWS documentation requires underlying alarms to be:
- in the same account,
- in the same Region

as the composite alarm.

Therefore:

```text
cross-account composite alarm
→ unsupported
```

This is exam-relevant.

---

#### 4.2.5.37 Composite Alarm Actions

Composite alarms support selected actions such as:
- SNS,
- Lambda,
- Systems Manager operational actions,
- supported CloudWatch operational integrations.

They do not necessarily support:
- every action available to metric alarms.

---

#### 4.2.5.38 Anomaly Detection

CloudWatch anomaly detection can model:
- expected metric behavior,
- dynamic upper/lower bands.

Use when:

```text
normal baseline changes over time
→ static threshold is weak
```

Fast distinction:

```text
known fixed boundary
→ static threshold

variable normal baseline
→ anomaly detection may fit
```

---

#### 4.2.5.39 Metric Math Alarms

CloudWatch alarms can evaluate:
- metric math expressions.

Example:

```text
FailureRate =
Failures / Requests * 100
```

Then:

```text
FailureRate > 5%
→ ALARM
```

Use when:
- a derived signal is more meaningful than raw metrics.

---

#### 4.2.5.40 Alert on User Impact

Where practical, alert on:
- user/service impact.

Examples:

```text
error rate
latency
failed business operations
queue age
availability
```

Infrastructure metrics remain useful,
but may be:
- supporting evidence rather than the primary page.

---

#### 4.2.5.41 Alert Noise

Weak design:

```text
every error
→ page human
```

Better:

```text
actionable sustained condition
→ notify appropriate owner
```

Alert quality depends on:
- signal,
- threshold,
- statistic,
- period,
- evaluation,
- missing-data behavior,
- routing,
- ownership.

---

#### 4.2.5.42 Symptoms vs Root Incident

Example:

```text
database unavailable
```

may cause:
- API errors,
- Lambda errors,
- queue growth,
- latency increase.

Four independent notifications can:
- describe one incident.

Composite alarms or event correlation can:
- reduce duplicate noise.

---

#### 4.2.5.43 Alarm Naming and Description

Good alarm names communicate:
- environment,
- service,
- condition.

Example:

```text
prod-checkout-high-error-rate
```

Weak:

```text
alarm1
```

Alarm descriptions should help the responder understand:
- meaning,
- expected owner,
- troubleshooting/runbook context.

An alert should:
- help someone act,
not merely:
- announce a number.

---

#### 4.2.5.44 Notification Routing

Route notifications according to:
- service,
- severity,
- environment,
- ownership.

Example:

```text
prod critical
→ on-call / operations

dev warning
→ team channel

security event
→ security workflow
```

Avoid:
- one undifferentiated notification topic

unless that is:
- an intentional design.

---

#### 4.2.5.45 Alarm State vs Operational Severity

CloudWatch states:

```text
OK
ALARM
INSUFFICIENT_DATA
```

are not automatically:

```text
P1
P2
P3
```

Operational severity:
- is organization-specific routing/classification.

#### 4.2.5.46 `ActionsEnabled`

CloudWatch alarms expose:

```text
ActionsEnabled
```

If disabled:

```text
alarm can enter ALARM
but
configured actions are not executed
```

Troubleshooting clue:

```text
alarm is ALARM
but no notification
→ check ActionsEnabled
```

#### 4.2.5.47 Testing Alarm Actions

CloudWatch `SetAlarmState` can temporarily:
- set an alarm state.

If the new state differs from the previous state:
- actions for that state can be invoked.

Use for:
- testing alert wiring.

Caution:
- a metric alarm normally returns to its actual evaluated state quickly.

#### 4.2.5.48 Alarm History

Alarm history helps answer:


Use it when:

#### 4.2.5.49 Complete Notification Path

A classic path:

```text
metric
→ alarm
→ SNS
→ subscriber
```

Failure can occur at any layer.

Troubleshoot in order:

```text
1. Is the metric present?
2. Did the alarm transition?
3. Are actions enabled?
4. Is the action target correct?
5. Can CloudWatch/SNS publish as required?
6. Is the subscription confirmed?
7. Did downstream delivery/processing succeed?
```

Do not jump directly to:
- email troubleshooting

if the alarm:
- never changed state.

#### 4.2.5.58 Exam-Level Knowledge Frame

Know these cold.

**CloudWatch Alarm**  
→ evaluates a metric/query condition and changes state.

**`ALARM`**  
→ configured condition is breached.

**`OK`**  
→ condition is within the configured state.

**`INSUFFICIENT_DATA`**  
→ not enough data to determine the state.

**M-out-of-N**  
→ M breaching datapoints among N evaluated periods.

**Missing-data treatment**  
→ configurable interpretation of absent metric datapoints.

**SNS**  
→ publish/subscribe notification fanout.

**EventBridge**  
→ event matching and routing.

**Composite Alarm**  
→ alarm state based on Boolean combinations of other alarm states.

**Alarm Action**  
→ action executed when alarm transitions into a configured state.

Fastest discriminator:

```text
numerical threshold?
→ CloudWatch alarm

specific AWS event?
→ EventBridge

human/subscriber notification?
→ SNS

programmatic response?
→ Lambda

3 of 5 breaches?
→ M-out-of-N

no datapoint?
→ missing-data semantics matter

too many related alerts?
→ composite alarm

recovery notification?
→ OK action

alarm stays ALARM?
→ normal action does not repeat every period

log pattern?
→ metric filter → alarm
or current Log Alarm
```

#### 4.2.5.59 Final Principle

**Effective notification alerting separates signal generation, condition detection, and notification routing. Use CloudWatch alarms for numerical thresholds, rates, metric math, and supported query conditions; use EventBridge when the occurrence of an event itself is the trigger. Configure statistic, period, threshold, M-out-of-N evaluation, and missing-data behavior according to the semantics of the signal rather than relying on arbitrary defaults. Route straightforward human notifications through SNS, use Lambda or Systems Manager for programmatic responses, and use EventBridge when flexible event routing is required. CloudWatch alarm actions are primarily state-transition driven, so configure recovery or insufficient-data actions explicitly when needed. Reduce noise with meaningful thresholds and composite alarms, and validate the complete notification path rather than assuming that an alarm configuration or SNS subscription guarantees successful delivery.**
