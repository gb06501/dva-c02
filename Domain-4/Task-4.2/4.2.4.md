### 4.2.4 Add annotations for tracing services

#### 4.2.4.1 Exam and Task Context

##### 4.2.4.1.1 Domain and Task
- **Domain 4:** Troubleshooting and Optimization.
- **Task 4.2:** Instrument code for observability.
- **Skill 4.2.4:** **Add annotations for tracing services.**

##### 4.2.4.1.2 Position Inside Task 4.2

```text
4.2.3
→ implement code that emits custom metrics

4.2.4
→ add annotations for tracing services

4.2.5
→ implement notification alerts

```

Core question:

**How should application-specific context be added to distributed traces so traces can be searched and filtered without confusing indexed annotations with non-indexed diagnostic metadata?**

---

#### 4.2.4.2 Core Mental Model

```text
REQUEST / EVENT
      |
      v
     TRACE
      |
      +--> segment
      |      |
      |      +--> annotation
      |      |    → indexed/searchable
      |      |
      |      '--> metadata
      |           → stored/not indexed
      |
      '--> subsegment
             |
             +--> annotation
             '--> metadata
```

Fastest discriminator:

```text
Need to SEARCH/FILTER traces by the value?
→ annotation

Need detail only after opening the trace?
→ metadata
```

---

#### 4.2.4.3 Why Application Context Matters

Tracing can automatically expose technical topology such as:

```text
API Gateway
→ Lambda
→ DynamoDB
```

AWS cannot automatically infer application semantics such as:

```text
orderType=EXPRESS
tenantTier=PREMIUM
paymentProvider=PRIMARY
workflow=CHECKOUT
```

Annotations allow:
- selected application semantics
- to become searchable trace attributes.

---

#### 4.2.4.4 Trace, Segment, and Subsegment

##### 4.2.4.4.1 Trace
A trace represents:
- the end-to-end path of a request or transaction through instrumented components.

Example:

```text
Trace
 |
 +-- API Gateway
 |
 +-- Lambda Checkout
 |      |
 |      '-- DynamoDB PutItem
 |
 '-- downstream service
```

##### 4.2.4.4.2 Segment
An X-Ray segment represents:
- work performed by a service/application while handling a request.

It can contain:
- timing,
- request/response information,
- errors/faults,
- annotations,
- metadata,
- subsegments.

##### 4.2.4.4.3 Subsegment
A subsegment represents:
- work within a segment.

Examples:

```text
validateOrder
calculatePrice
callPaymentProvider
DynamoDB PutItem
serializeResponse
```

Custom subsegments can:
- time important code sections,
- group downstream work,
- record errors,
- carry annotations,
- carry metadata.

---

#### 4.2.4.5 X-Ray Annotation

An X-Ray annotation is:
- an **indexed key-value pair**
- attached to a segment or subsegment.

Supported value types:

```text
String
Number
Boolean
```

Use annotations when:
- the value must support trace search/filtering.

Example:

```text
orderType = "EXPRESS"
```

Conceptual filter:

```text
annotation.orderType = "EXPRESS"
```

Operational question:

```text
Show traces for EXPRESS orders.
```

---

#### 4.2.4.6 X-Ray Metadata

Metadata is:
- additional trace information,
- not indexed for filter expressions.

Metadata can contain:
- richer values,
- objects,
- lists.

Use metadata when:

```text
I need this information while inspecting the trace
but
I do not need to search traces by it.
```

Example:

```text
annotation:
paymentProvider = "PRIMARY"

metadata:
paymentRequestSummary = {...}
```

---

#### 4.2.4.7 Annotation vs Metadata Decision

```text
Need extra trace context?
        |
        v
Need to SEARCH/FILTER by it?
      |             |
     yes            no
      |             |
 annotation      metadata
      |
      v
String / Number / Boolean?
      |
      v
safe + useful + intentional?
      |
      v
attach to relevant segment/subsegment
```

This distinction is the core of the skill.

---

#### 4.2.4.8 Annotation Limits

Current X-Ray documentation specifies:
- annotation keys up to 500 alphanumeric characters,
- keys may contain periods but not spaces or other symbols,
- annotation values up to 1,000 Unicode characters,
- up to 50 annotations per trace.

Therefore:

```text
annotation
≠ unlimited context storage
```

Use annotations:
- selectively.

---

#### 4.2.4.9 Stable Annotation Design

Good annotation keys:

```text
orderType
paymentProvider
workflow
result
tenantTier
featureVariant
```

Good values are typically:
- meaningful,
- stable,
- operationally useful.

Examples:

```text
Environment=prod
OrderType=EXPRESS
PaymentProvider=PRIMARY
Result=FAILED
```

Avoid:
- dynamically generated keys.

Stable keys make:
- filters reusable,
- trace groups understandable,
- troubleshooting predictable.

---

#### 4.2.4.10 High-Cardinality Values

Values such as:

```text
requestId
orderId
userId
```

may technically be valid annotations.

But first ask:

```text
Do I genuinely need indexed trace search by this exact value?
```

If not:
- use metadata,
- logs,
- correlation mechanisms.

Rule:

```text
searchable operational category
→ annotation

diagnostic identifier/details
→ metadata/logs unless indexed search is genuinely required
```

Unlike CloudWatch metric dimensions, an X-Ray annotation does not create a metric time series. The concern here is:
- intentional indexing,
- usefulness,
- privacy/security,
not metric cardinality semantics.

---

#### 4.2.4.11 Sensitive Data

Anyone authorized to read trace data may see:
- annotations,
- metadata.

Do not place:
- passwords,
- access tokens,
- secrets,
- private keys,
- sensitive payloads

into tracing telemetry.

Tracing is:
- observability data,
- not a secret store.

---

#### 4.2.4.12 Java X-Ray Annotation and Metadata

Legacy X-Ray SDK concept:

```java
AWSXRay.getCurrentSubsegment()
       .putAnnotation("orderType", "EXPRESS");
```

Meaning:

```text
putAnnotation
→ indexed trace attribute
```

Metadata:

```java
AWSXRay.getCurrentSubsegment()
       .putMetadata("order", orderSummary);
```

Meaning:

```text
putMetadata
→ stored diagnostic detail
→ not indexed for filtering
```

These APIs remain useful for understanding the DVA-C02 concept even though AWS now recommends OpenTelemetry for new instrumentation.

---

#### 4.2.4.13 Reusing Annotation Keys

If the same segment/subsegment receives:

```text
result=PENDING
result=FAILED
```

for the same annotation key:
- the later value replaces the earlier value.

Therefore annotations represent:
- attributes/state,

not:
- chronological event history.

For event sequences use:
- logs.

---

#### 4.2.4.14 Annotation vs Log vs Metric

##### Annotation

```text
paymentProvider=PRIMARY
```

Purpose:
- search/group traces.

##### Log

```text
RECEIVED
VALIDATED
PAYMENT_STARTED
PAYMENT_FAILED
```

Purpose:
- chronological/detail-rich event context.

##### Metric

```text
PaymentFailures = 1
```

Purpose:
- numerical aggregation over time.

Rule:

```text
find category of distributed requests?
→ trace annotation

understand detailed event history?
→ log

measure trend/rate/count?
→ metric
```

---

#### 4.2.4.15 Trace Filtering and Groups

X-Ray filter expressions can use:
- indexed annotation values.

Concept:

```text
annotation[orderType] = "EXPRESS"
```

Annotations can therefore support trace groups such as:

```text
failed premium checkout traces
```

This enables:
- operational segmentation,
- focused troubleshooting.

---

#### 4.2.4.16 User Field

X-Ray also supports:
- an indexed user field.

This is:
- separate from annotations.

Therefore:
- not every searchable trace attribute must be an annotation.

Identity-related trace data must still respect:
- privacy,
- security requirements.

---

#### 4.2.4.17 Custom Subsegments

Example application flow:

```text
Lambda invocation
 |
 +-- validateOrder
 |
 +-- calculatePrice
 |
 +-- processPayment
 |
 '-- persistOrder
```

Without internal tracing:

```text
Lambda duration = 1500 ms
```

With subsegments:

```text
validation       10 ms
pricing          20 ms
payment        1400 ms
persistence      40 ms
```

Now:
- the slow operation becomes visible.

Annotations can then add:
- searchable application context to the relevant operation.

---

#### 4.2.4.18 Closing Custom Subsegments

With the X-Ray SDK, custom subsegments must be closed correctly.

Concept:

```text
beginSubsegment
try
    work
finally
    endSubsegment
```

An unclosed subsegment can interfere with:
- parent segment completion/sending.

Subsegments can also record:
- exceptions,
- failure context.

---

#### 4.2.4.19 Downstream Calls

Instrumentation can expose subsegments for:
- AWS SDK calls,
- HTTP calls,
- SQL/database operations.

Example:

```text
Lambda
 |
 '-- DynamoDB PutItem
```

Trace timing shows:
- where time was spent.

Annotations answer:
- which application category experienced the issue.

---

#### 4.2.4.20 Lambda Segment Ownership

Lambda is important because:
- the Lambda service creates the parent trace segment.

Function code does **not**:
- create a replacement parent Lambda segment.

AWS documents:

```text
Lambda-created parent segment
→ cannot be modified by function code
```

Application code instead:
- creates subsegments,
- attaches annotations/metadata to those subsegments.

Fast rule:

```text
Lambda application-specific trace context
→ application subsegment
→ annotation / metadata
```

---

#### 4.2.4.21 Lambda Active vs PassThrough

Lambda tracing modes include:

```text
Active
PassThrough
```

##### Active

With `Active`:
- Lambda automatically creates/sends traces for sampled invocations.

##### PassThrough

Current documented behavior:

```text
PassThrough
→ propagates trace context
→ does not automatically send Lambda traces
```

Therefore if automatic Lambda service tracing is required:

```text
Mode=Active
```

is the relevant choice.

---

#### 4.2.4.22 Active Tracing Configuration

CLI concept:

```text
aws lambda update-function-configuration
  --function-name my-function
  --tracing-config Mode=Active
```

CloudFormation:

```yaml
TracingConfig:
  Mode: Active
```

SAM:

```yaml
Tracing: Active
```

Exam principle:
- tracing must actually be enabled/configured.

Instrumentation code alone:
- does not guarantee Lambda service traces.

---

#### 4.2.4.23 Lambda Trace Permissions

Lambda requires trace-write permissions:

```text
xray:PutTraceSegments
xray:PutTelemetryRecords
```

These are included in:

```text
AWSXRayDaemonWriteAccess
```

If traces are absent, check:
- tracing mode,
- IAM permissions.

---

#### 4.2.4.24 Sampling

X-Ray does not necessarily trace:
- every request.

Sampling determines:
- which requests are recorded.

Therefore:

```text
one request absent from tracing
≠ tracing automatically broken
```

It may:
- not have been sampled.

For Lambda active tracing:
- upstream sampling decisions can be honored.

AWS documents default Lambda sampling behavior for requests without an upstream decision as:
- one request per second,
- plus 5% of additional requests.

The Lambda X-Ray sampling rate:
- is not directly configurable on the function.

---

#### 4.2.4.25 Trace Context Propagation

Distributed tracing requires:
- trace context to cross service boundaries.

```text
Service A
   |
   | trace context
   v
Service B
   |
   v
Service C
```

Without propagation:
- traces can become disconnected.

This is broader tracing behavior, but it matters when annotations appear in only part of the expected request path.

---

#### 4.2.4.26 Event-Driven Tracing

Current Lambda/X-Ray integrations can link some upstream message-producer traces to downstream Lambda traces.

Support:
- varies by service/event source.

Current Lambda documentation notes unsupported X-Ray tracing for certain event source mappings, including:
- Amazon MSK,
- self-managed Apache Kafka,
- Amazon MQ,
- Amazon DocumentDB.

Exam rule:
- do not assume every event source produces identical tracing behavior.

---

#### 4.2.4.27 Service Map and Timeline

X-Ray trace data can produce:
- service topology,
- dependency relationships,
- error information,
- latency relationships.

Trace timelines show:
- segment/subsegment timing,
- slow operations,
- downstream latency,
- failures.

Annotations add:
- searchable application semantics

to:
- technical topology and timing.

#### 4.2.4.28 Strong vs Weak Annotation Candidates

Strong:

```text
operation
workflow
tenantTier
orderType
paymentProvider
resultCategory
featureVariant
```

Weak:

```text
debugText
entireRequestBody
stackTrace
largeObject
```

Weak candidates generally belong:
- in metadata/logs when safe and useful.

Design test:

```text
What useful trace filter would I write with this field?
```

If there is no good answer:
- it probably should not be indexed.

#### 4.2.4.29 Example — Payment Failure

Trace:

```text
API Gateway
→ Checkout Lambda
   → Payment API
```

Annotations:

```text
orderType=EXPRESS
paymentProvider=PRIMARY
result=FAILED
```

Metadata:

```text

```

Workflow:

```text

AND result=FAILED

→ inspect metadata and subsegment timing
```

#### 4.2.4.30 Annotation vs Correlation ID

Correlation ID:

```text
requestId=abc
→ find one transaction
```

Annotation category:

```text
orderType=EXPRESS
→ find a class of transactions
```

A unique identifier can be indexed when exact trace search is genuinely required, but:
- it should be an intentional design choice.

---

#### 4.2.4.31 Annotation vs CloudWatch Metric Dimension

CloudWatch dimension:

```text
Provider=PRIMARY
```

means:
- part of a metric time-series identity.

X-Ray annotation:

```text
Provider=PRIMARY
```

means:
- indexed trace attribute.

Same business vocabulary:
- different telemetry semantics.

A strong observability model may consistently use:

```text
metric dimension:
Provider=PRIMARY

trace annotation:
Provider=PRIMARY

log field:
provider=PRIMARY
```

while respecting:
- each signal's own indexing/cardinality semantics.

#### 4.2.4.32 Powertools for AWS Lambda

Powertools for AWS Lambda provides:
- tracing utilities,
- handler/method instrumentation,
- annotation/metadata helpers.

For Java, `@Tracing` is a language annotation used to:
- enable tracing instrumentation around code.

Concept:

```java
@Tracing
public Response handleRequest(...) {
    ...
}
```

Important terminology trap:

```text
Java @Tracing annotation
≠
X-Ray annotation key/value
```

`@Tracing`:
- instrumentation mechanism.

X-Ray annotation:
- indexed trace data.

#### 4.2.4.38 Common Exam Traps

##### 4.2.4.38.1 Annotation and Metadata Are Equivalent
Wrong.

```text
annotation
→ indexed

metadata
→ not indexed
```

##### 4.2.4.38.2 Put Large Objects in Annotations
Wrong.
- Annotations support String/Number/Boolean.
- Use metadata for richer diagnostic objects when safe.

##### 4.2.4.38.3 Metadata Is Searchable with Annotation Filters
Wrong.
- Metadata is not indexed for X-Ray filter expressions.

##### 4.2.4.38.4 Lambda Code Should Create a New Parent Segment
Wrong.
- Lambda owns the parent function segment.
- Application code creates subsegments.

##### 4.2.4.38.5 Lambda Code Can Modify the Lambda-Created Parent Segment
Wrong.
- Add application annotations/metadata to application subsegments.

##### 4.2.4.38.6 Active Tracing Means Every Request Is Traced
Wrong.
- Sampling still applies.

##### 4.2.4.38.7 PassThrough Automatically Records Lambda Traces
Wrong under current documented behavior.
- It propagates context but does not automatically send Lambda traces.

##### 4.2.4.38.8 Tracing Needs No IAM Permission
Wrong.

Know:

```text
xray:PutTraceSegments
xray:PutTelemetryRecords
```

##### 4.2.4.38.9 Annotation Replaces a Metric
Wrong.
- Annotation = trace search context.
- Metric = numerical time series.

##### 4.2.4.38.10 Annotation Replaces Logs
Wrong.
- Annotation = indexed attribute.
- Log = detailed chronological context.

##### 4.2.4.38.11 `@Tracing` Means X-Ray Annotation
Wrong.
- `@Tracing` = Java/Powertools instrumentation annotation.
- X-Ray annotation = indexed key/value trace attribute.

##### 4.2.4.38.12 X-Ray SDK Is AWS's Preferred New Instrumentation Standard
Outdated.
- AWS now recommends OpenTelemetry.

#### 4.2.4.41 Exam-Level Knowledge Frame

Know these cold.

**Trace**  
→ end-to-end request/transaction path.

**Segment**  
→ work performed by a service/application.

**Subsegment**  
→ work performed within a segment.

**Annotation**  
→ indexed String/Number/Boolean trace attribute.

**Metadata**  
→ non-indexed richer trace detail.

**Active tracing**  
→ Lambda automatically records sampled invocation traces.

**PassThrough**  
→ propagates trace context without automatically recording Lambda traces under current behavior.

**Sampling**  
→ determines which requests are traced.

**AWSXRayDaemonWriteAccess**  
→ managed policy containing standard X-Ray write permissions.

**OpenTelemetry**  
→ current AWS-recommended instrumentation direction.

Fastest exam discriminator:

```text
searchable trace attribute?
→ annotation

rich trace detail, no search?
→ metadata

time internal operation?
→ subsegment

Lambda service traces?
→ Active tracing

Lambda app-specific context?
→ subsegment + annotation/metadata

no trace?
→ mode + permissions + sampling + integration

aggregate trend?
→ metric

chronological detail?
→ log

new tracing instrumentation in 2026?
→ OpenTelemetry / ADOT
```

#### 4.2.4.42 Final Principle

**Trace annotations enrich distributed traces with indexed application-specific context. Use annotations for stable String, Number, or Boolean attributes that you genuinely need to search or filter traces by; use metadata for richer diagnostic information that does not need indexing. Attach context to the segment or subsegment representing the relevant operation. In Lambda, AWS creates and owns the parent function segment, so application code adds custom subsegments and places annotations or metadata there. Trace availability also depends on tracing mode, trace-write permissions, sampling, supported integrations, and context propagation. Preserve X-Ray terminology for DVA-C02, while recognizing that AWS placed the X-Ray SDKs and daemon into maintenance mode on February 25, 2026 and recommends OpenTelemetry for new instrumentation.**
