#### 4.2.1.2 Core Mental Model

```text
APPLICATION / INFRASTRUCTURE
          |
          v
       TELEMETRY
          |
    +-----+-----+
    |     |     |
    v     v     v
 metrics logs traces
    |     |     |
    +-----+-----+
          |
          v
     MONITORING
 known signals / conditions
          |
          v
    OBSERVABILITY
 understand internal behavior
 investigate unexpected problems
 correlate across the system
```

Keep the concepts separate:

```text
logging
→ record events

monitoring
→ assess known health/behavior

observability
→ understand internal system behavior from telemetry
```

#### 4.2.1.3 Logging

AWS Prescriptive Guidance defines application logging as:
- collecting application-generated events,
- recording them for later use.

Example:

```json
{
  "timestamp": "2026-08-26T08:15:00Z",
  "level": "ERROR",
  "service": "checkout",
  "requestId": "abc-123",
  "message": "Payment provider timed out"
}
```

Logging is:
- event-oriented,
- historical,
- detailed.

#### 4.2.1.4 What Logs Answer

Logs are strong for:

```text
What happened?
What error occurred?
Which request failed?
What state/input was present?
Which code path executed?
```

Examples:

```text
request received
authentication failed
order created
exception thrown
retry started
```

Logs provide:
- detailed discrete context.

#### 4.2.1.5 Logging Is Not Monitoring

Example:

```text
ERROR payment timeout
```

Writing that event:
- is logging.

Counting those events and evaluating:

```text
PaymentTimeoutCount > 50 in 5 minutes
```

is:
- monitoring.

Rule:

```text
logging
→ records evidence

monitoring
→ evaluates health/behavior using evidence
```

#### 4.2.1.6 Logs Alone Are Not Full Observability

Having many logs does not automatically mean:
- effective monitoring,
- good observability.

Weak logs:

```text
"failed"
```

with no:
- service,
- request ID,
- trace ID,
- operation,
- version,
- structured context

may be:
- difficult to correlate.

Core principle:

```text
more logs
≠ automatically more observability
```

#### 4.2.1.7 Monitoring

AWS describes monitoring as:
- assessing application/system health and performance.

Monitoring commonly asks:

```text
Is the system healthy?
Did a known threshold get exceeded?
Is a known failure condition occurring?
```

Examples:

```text
Is error rate > 5%?
Is Lambda throttling?
Is queue age > 10 minutes?
Is API p95 latency > 1 second?
```

These are:
- predefined health questions.

#### 4.2.1.8 Monitoring Uses Telemetry

Monitoring can use:
- metrics,
- logs,
- events,
- traces,
- alarms,
- health checks.

Therefore:

```text
monitoring
≠ metrics only
```

Metrics are simply:
- especially efficient monitoring signals.

#### 4.2.1.9 Monitoring Detects Symptoms

Example:

```text
Checkout error rate
1% → 18%
```

Monitoring tells you:

```text
something is wrong
```

It may not tell you:

```text
why
```

This is the key transition toward:
- observability.

#### 4.2.1.10 Alerting

Alerting is:
- notification/action after a monitored condition is detected.

Example:

```text
CloudWatch metric
→ alarm enters ALARM
→ SNS notification
```

Alerting is part of:
- monitoring/operations.

It is not:
- synonymous with observability.

#### 4.2.1.11 Dashboarding

A dashboard is:

```text
telemetry
→ visualization
```

It supports:
- monitoring,
- observability.

But:

```text
dashboard
≠ monitoring itself
≠ observability itself
```

It is:
- a presentation/analysis mechanism.

#### 4.2.1.12 Observability

AWS Cloud Adoption Framework describes observability as:
- how well you can understand what is happening in a system,
- typically through telemetry such as metrics, logs, and traces.

Observability supports:
- detection,
- investigation,
- troubleshooting,
- understanding internal behavior,
- KPI/SLO measurement.

#### 4.2.1.13 Observability Is a Capability of the System

Important:

```text
CloudWatch
≠ observability itself
```

CloudWatch provides:
- observability capabilities.

A system becomes observable when:
- it emits sufficient useful telemetry,
- the telemetry can be correlated,
- internal behavior can be inferred from it.

#### 4.2.1.14 Monitoring vs Observability

Useful exam distinction:

```text
MONITORING
→ known signals
→ known thresholds
→ known symptoms

OBSERVABILITY
→ broader system understanding
→ exploratory investigation
→ unexpected failure modes
```

Example:

```text
Monitoring:
p95 checkout latency > 2 seconds

Observability:
Which service, operation, dependency,
request type, or downstream call explains it?
```

#### 4.2.1.15 Monitoring Is Part of Observability

AWS guidance treats monitoring as:
- an important component of observability.

Therefore:

```text
monitoring
≠ observability

but

monitoring
→ contributes to observability
```

Do not treat them as:
- competing approaches.

#### 4.2.1.16 Known Conditions vs Exploratory Questions

Monitoring is strongest when you know:

```text
what bad looks like
```

Example:

```text
Errors > 10
→ alarm
```

Observability is especially useful when the question was not predefined:

```text
Why are only checkout requests
through one dependency slow
after the release,
while aggregate CPU remains normal?
```

This needs:
- exploratory correlation.

#### 4.2.1.17 Three Primary Telemetry Signals

The central signals are:

```text
METRICS
LOGS
TRACES
```

They overlap,
but each is strongest for:
- a different class of question.

#### 4.2.1.18 Metrics

Metrics are:
- numerical measurements over time.

Examples:

```text
RequestCount
ErrorRate
Duration
CPUUtilization
QueueDepth
CheckoutFailures
```

Best for:

```text
How many?
How much?
How fast?
How often?
Is a value abnormal?
```

Strengths:
- compact,
- aggregatable,
- efficient for dashboards,
- efficient for alarms,
- good for trends.

#### 4.2.1.19 Metric Limitation

A metric can say:

```text
Errors = 200
```

but usually not:

```text
which requests?
which exception?
which customer path?
which dependency?
```

Therefore:
- use logs/traces for deeper context.

#### 4.2.1.20 Logs as an Observability Signal

Logs are strongest for:

```text
What exactly happened?
What exception?
What input/state?
Which request?
```

Example:

```text
ERROR requestId=abc
payment provider timeout
attempt=3
```

Limitation:
- raw logs can be high-volume,
- noisy,
- hard to correlate across services without identifiers.

#### 4.2.1.21 Traces

A distributed trace follows:
- one request/transaction across participating services.

Example:

```text
Trace abc
 |
 +-- API Gateway        20 ms
 |
 +-- Lambda Checkout   110 ms
 |
 +-- Payment API      1900 ms  ← slow
 |
 '-- DynamoDB           15 ms
```

Best for:

```text
Where did the request spend time?
Which dependency failed?
Which service path executed?
```

#### 4.2.1.22 Span

A trace contains:
- spans.

A span represents:
- one unit of work.

Examples:
- HTTP request,
- Lambda invocation,
- database operation,
- downstream API call.

Mental model:

```text
trace
→ end-to-end transaction

span
→ one operation inside that transaction
```

#### 4.2.1.23 Trace Limitation

Tracing is not usually the best primary tool for:

```text
How many failures happened over one month?
```

Metrics:
- are generally better for aggregate trends.

Logs:
- are generally better for exact event detail.

#### 4.2.1.24 Signals Complement Each Other

Strong exam model:

```text
METRIC
→ detect

TRACE
→ localize

LOG
→ explain
```

Example:

```text
metric:
p99 latency ↑

trace:
PaymentService span slow

log:
provider timeout after 2000 ms
```

This is:
- correlated observability.

Important nuance:
- this is a useful synthesis,
- not an exclusive rule that each signal can perform only one function.

#### 4.2.1.25 Correlation Is Central

Useful shared context includes:
- timestamp,
- service,
- operation,
- environment,
- version,
- request/correlation ID,
- trace ID,
- result/dependency.

Then:

```text
metric anomaly
→ trace
→ log details
```

can be followed efficiently.

#### 4.2.1.26 High-Cardinality Context

Identifiers such as:

```text
requestId
traceId
userId
orderId
```

are valuable in:
- logs,
- traces.

But they can be poor:
- classic CloudWatch metric dimensions,
because of:
- high cardinality,
- cost.

Keep:

```text
bounded dimensions
→ metrics

high-cardinality identifiers
→ logs/traces
```

#### 4.2.1.27 Telemetry

Telemetry is:
- operational data emitted or collected from a system.

Common telemetry:

```text
metrics
logs
traces
events
```

Telemetry is:
- the raw evidence.

Observability is:
- the capability enabled by useful telemetry and analysis.

#### 4.2.1.28 Instrumentation

Instrumentation means:
- adding/configuring mechanisms that generate telemetry.

Examples:
- structured logs,
- custom metrics,
- trace spans,
- annotations,
- OpenTelemetry SDK,
- AWS Distro for OpenTelemetry.

Task 4.2 is specifically:

```text
Instrument code for observability
```

#### 4.2.1.29 Instrumentation Is Not Observability by Itself

Example:

```text
application emits 10 GB/day of logs
```

but logs lack:
- useful identifiers,
- service context,
- structured fields,
- trace correlation.

Then:

```text
instrumentation exists
but
observability remains poor
```

Quality and correlation matter more than:
- raw telemetry volume.

#### 4.2.1.30 CloudWatch Role

Amazon CloudWatch provides capabilities including:
- metrics,
- alarms,
- dashboards,
- logs,
- log querying,
- APM/traces,
- Application Signals,
- infrastructure monitoring,
- cross-account observability,
- OpenTelemetry support.

AWS describes CloudWatch as providing:
- system-wide observability for application performance,
- operational health,
- resource utilization.

#### 4.2.1.31 CloudWatch Metrics

CloudWatch metrics can support:

```text
monitoring
→ track numerical signals

observability
→ correlate metrics with logs/traces
```

Examples:
- Lambda Errors,
- Lambda Duration,
- DynamoDB throttles,
- custom OrderFailures.

#### 4.2.1.32 CloudWatch Logs

CloudWatch Logs supports:
- collection/storage,
- searching,
- Logs Insights,
- metric filters,
- anomaly analysis,
- subscriptions/routing.

Therefore logs can support:
- logging,
- monitoring,
- observability.

Example:

```text
"LoginFailed"
→ metric filter
→ FailedLoginCount
```

This demonstrates:

```text
log data
→ can become monitoring signal
```

#### 4.2.1.33 AWS X-Ray / Traces

AWS X-Ray provides:
- distributed tracing,
- end-to-end request visibility,
- service/component maps,
- latency/error investigation.

Tracing is:
- a major observability signal.

Use when:
- distributed request path and timing matter.

#### 4.2.1.34 CloudWatch Application Signals

Application Signals provides:
- application/service-centric health views.

It can expose:
- services,
- operations,
- dependencies,
- latency,
- availability,
- faults/errors,
- SLOs.

This is a higher-level example of:

```text
correlated raw telemetry
→ application observability
```

#### 4.2.1.35 OpenTelemetry

OpenTelemetry is:
- open source,
- vendor neutral,
- an observability instrumentation framework.

CloudWatch supports OpenTelemetry across:
- metrics,
- logs,
- traces.

Core concept:

```text
one instrumentation model
→ multiple correlated telemetry signals
```

#### 4.2.1.36 AWS Distro for OpenTelemetry

AWS Distro for OpenTelemetry (ADOT) is:
- an AWS-supported OpenTelemetry distribution.

It can collect/send telemetry such as:
- metrics,
- traces,
- other supported telemetry

to:
- AWS,
- compatible observability backends.

Exam-level importance:
- instrumentation/collection path,
- not a replacement definition for observability.

#### 4.2.1.37 Distributed Systems Need Correlation

Example:

```text
CloudFront
→ API Gateway
→ Lambda
→ SQS
→ Lambda
→ DynamoDB
```

A component-only view can miss:
- cross-service causality.

Every component can appear individually healthy while:
- end-to-end latency remains poor.

Tracing/correlated telemetry can reveal:
- one downstream call dominates the total path.

#### 4.2.1.38 Business Observability

Observability should include:
- application/business outcomes when relevant.

Examples:

```text
OrdersCreated
PaymentDeclines
CheckoutCompletionRate
FailedBusinessValidation
```

Possible condition:

```text
Lambda healthy
DynamoDB healthy
but CheckoutCompletionRate ↓
```

Infrastructure health:
- does not guarantee business health.

#### 4.2.1.39 SLI/SLO Connection

Observability can support:
- KPIs,
- SLIs,
- SLOs.

Example:

```text
SLI:
checkout availability

SLO:
99.9%
```

Monitoring:
- detects current health/threshold behavior.

Observability:
- helps explain why an SLO is not being met.

Detailed SLO interpretation belongs mainly to:
- 4.1.5.

#### 4.2.1.40 Proactive vs Reactive

Do not oversimplify:

```text
monitoring = proactive
observability = reactive
```

Both can support:
- proactive detection,
- reactive investigation.

The stronger distinction is:

```text
monitoring
→ known health questions

observability
→ broad explainability and exploration
```

#### 4.2.1.41 Signal Quality and Cost

More telemetry is not automatically better.

Poor instrumentation can create:
- excessive cost,
- noise,
- difficult queries,
- hidden important signals.

Strong observability requires telemetry that is:
- intentional,
- structured,
- correlated,
- manageable.

#### 4.2.1.42 Centralized / Cross-Account Observability

Distributed systems can span:
- services,
- accounts,
- Regions.

CloudWatch cross-account observability can allow:

```text
monitoring account
→ source-account telemetry
```

Supported observability data can include:
- metrics,
- log groups,
- X-Ray traces,
- Application Signals services/SLOs,
- other supported resources.

Purpose:
- reduce account-boundary fragmentation during investigation.

#### 4.2.1.43 Detection-to-Root-Cause Workflow

```text
MONITORING
metric/alarm detects anomaly
       |
       v
OBSERVABILITY
correlate telemetry
       |
       +--> metric trend
       +--> trace path
       +--> log detail
       |
       v
ROOT-CAUSE HYPOTHESIS
```

Monitoring and observability:
- complement each other.

#### 4.2.1.49 Exam-Level Knowledge Frame

##### 4.2.1.49.1 Know These Cold

**Logging**
→ recording application/system events and context.

**Monitoring**
→ measuring and assessing known system health/behavior.

**Observability**
→ ability to understand internal system behavior from telemetry.

**Metric**
→ numerical measurement over time.

**Log**
→ detailed event/history/context.

**Trace**
→ end-to-end path of a transaction/request.

**Span**
→ one unit of work in a trace.

**Telemetry**
→ operational data emitted/collected from systems.

**Instrumentation**
→ mechanisms/code that generate telemetry.

**OpenTelemetry**
→ vendor-neutral open-source observability framework.

##### 4.2.1.49.2 Fastest Exam Discriminator

```text
record event?
→ logging

watch known health condition?
→ monitoring

understand why distributed system behaves this way?
→ observability

how many/how fast?
→ metric

what exactly happened?
→ log

where did request go/spend time?
→ trace

known threshold exceeded?
→ monitoring/alarm

unknown distributed root cause?
→ correlate metrics + logs + traces
```

##### 4.2.1.49.3 Final Principle
- **Logging, monitoring, and observability are related but not interchangeable. Logging records detailed events and historical context. Monitoring uses telemetry to measure known health and performance signals, detect abnormal conditions, and drive alarms or dashboards. Observability is the broader capability to understand internal system behavior from externally available telemetry and to investigate both expected and unexpected failure modes. Metrics are strongest for aggregate numerical trends, logs for detailed event context, and traces for distributed request paths. Effective AWS observability correlates these signals so that monitoring detects a symptom and engineers can move from that symptom to the responsible service, request, dependency, and detailed error.**
