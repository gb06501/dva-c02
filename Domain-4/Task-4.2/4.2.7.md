### 4.2.7 Implement structured logging

#### 4.2.7.1 Exam and Task Context

##### 4.2.7.1.1 Domain and Task
- **Domain 4:** Troubleshooting and Optimization.
- **Task 4.2:** Instrument code for observability.
- **Skill 4.2.7:** **Implement structured logging.**

##### 4.2.7.1.2 Position Inside Task 4.2

```text
4.2.5
→ implement notification alerts

4.2.6
→ implement tracing

4.2.7
→ implement structured logging
```

Core question:

**How should application events be emitted as stable machine-queryable fields so CloudWatch Logs can search, filter, aggregate, and correlate them without fragile free-text parsing?**

---

#### 4.2.7.2 Core Mental Model

```text
APPLICATION EVENT
      |
      v
structured log record
      |
      +--> timestamp
      +--> level
      +--> message
      +--> requestId
      +--> traceId
      +--> service
      +--> operation
      +--> business context
      '--> error context
              |
              v
       CloudWatch Logs
              |
              v
      Logs Insights query
```

Key principle:

```text
human-readable message
+
machine-readable fields
```

is better than:

```text
one large unstructured string
```

---

#### 4.2.7.3 Unstructured vs Structured Logging

Unstructured:

```text
INFO Order 8472 failed payment with provider PRIMARY after 2 retries
```

A human can read it.

A machine must:
- parse the text to recover fields.

Structured:

```json
{
  "level": "INFO",
  "message": "Payment failed",
  "orderId": "8472",
  "provider": "PRIMARY",
  "retryCount": 2
}
```

Now fields can be:
- filtered,
- grouped,
- aggregated,
- reused across queries.

---

#### 4.2.7.4 Why JSON?

JSON is commonly used because it:
- represents key-value data,
- supports nested structures,
- is machine-readable,
- works naturally with log analytics.

AWS Lambda recommends:
- JSON logging when machine search/filtering is useful,
unless:
- existing workflows depend on plain text.

Important:

```text
recommended
≠ default
```

Standard Lambda managed runtimes still default to:
- `Text`.

---

#### 4.2.7.5 Structure Is More Than JSON Syntax

This is technically JSON:

```json
{
  "message": "Order 8472 failed payment with PRIMARY after 2 retries"
}
```

But the useful information is still:
- buried in one string.

Better:

```json
{
  "message": "Payment failed",
  "orderId": "8472",
  "provider": "PRIMARY",
  "retryCount": 2
}
```

Structured logging means:
- operational context is represented as fields.

---

#### 4.2.7.6 Stable Schema

Prefer consistent names such as:

```text
service
operation
requestId
traceId
orderId
result
durationMs
errorType
```

Avoid unnecessary variation:

```text
requestId
request_id
req
requestIdentifier
```

Stable fields make:
- queries reusable,
- dashboards consistent,
- incident response faster.

---

#### 4.2.7.7 One Meaningful Event per Record

Each log record should describe:
- one useful application event.

Example:

```json
{
  "level": "WARN",
  "message": "Payment provider timeout",
  "provider": "PRIMARY",
  "timeoutMs": 2000,
  "attempt": 2
}
```

Prefer:
- selected event context

over:
- arbitrary state dumps.

---

#### 4.2.7.8 Typed Fields

Preserve meaningful data types.

Numeric:

```json
{
  "durationMs": 482
}
```

is better than:

```text
"operation took 482 ms"
```

Boolean:

```json
{
  "coldStart": true
}
```

is better than:

```text
"coldStart=true"
```

Why:
- direct filtering,
- direct aggregation,
- less parsing.

---

#### 4.2.7.9 Log Levels

Common application levels:

```text
TRACE
DEBUG
INFO
WARN
ERROR
FATAL
```

Exact support:
- depends on runtime and logging configuration.

Use levels according to:
- operational meaning.

##### `DEBUG`
Use for:
- detailed diagnosis/development.

Avoid excessive permanent production DEBUG when:
- volume,
- cost,
- sensitive data risk

are concerns.

##### `INFO`
Use for:
- normal meaningful application/business events.

Avoid:
- every trivial internal step.

##### `WARN`
Use when:
- unexpected/degraded behavior occurs,
- processing can continue.

##### `ERROR`
Use when:
- an operation failed,
- diagnostic attention is required.

Include:
- operation,
- relevant safe identifiers,
- error type,
- correlation context.

---

#### 4.2.7.10 Log Level as a Filtering Tool

Concept:

```text
normal production
→ INFO and above

temporary diagnosis
→ DEBUG and above
```

Lambda advanced logging controls can:
- filter logs before onward delivery.

This can reduce:
- ingestion volume,
- storage,
- query noise.

---

#### 4.2.7.11 Lambda Default Log Format

For standard Lambda managed runtimes:

```text
default LogFormat
→ Text
```

Lambda Managed Instances:
- support JSON only.

Do not assume:

```text
Lambda logs
→ JSON by default
```

across all Lambda execution environments.

---

#### 4.2.7.12 Lambda JSON Logging

Lambda can configure:

```text
LogFormat = JSON
```

For supported runtimes/logging methods:
- application logs can be captured as structured JSON,
- Lambda system/platform logs can also be emitted as JSON.

This does not require:
- manually concatenating JSON strings in every log statement.

---

#### 4.2.7.13 Native Structured Application Logging Support

Current Lambda native structured application logging supports:
- managed runtime logging methods for supported runtimes.

Examples include:
- Java,
- .NET,
- Node.js,
- Python,
- Ruby,
- Rust.

Runtime/version and logger requirements:
- vary.

For Java, supported patterns include:
- `LambdaLogger`,
- Log4j2.

Do not assume:
- arbitrary stdout from every runtime becomes rich structured JSON fields.

---

#### 4.2.7.14 Lambda JSON Application Fields

Current Lambda JSON application logs include core fields such as:

```text
timestamp
level
message
```

and request identity such as:

```text
requestId
```

or Java-specific:

```text
AWSrequestId
```

Additional fields:
- depend on runtime/logger.

---

#### 4.2.7.15 Lambda JSON System Logs

Lambda-generated platform/system logs use a structure based on:

```text
time
type
record
```

Application JSON schema and system JSON schema:
- are not identical.

Do not assume:
- every Lambda log event has the same field layout.

---

#### 4.2.7.16 Lambda `LoggingConfig`

Current Lambda `LoggingConfig` supports:

```text
ApplicationLogLevel
SystemLogLevel
LogFormat
LogGroup
```

This provides:
- centralized logging configuration.

---

#### 4.2.7.17 Application Log Level

Current Lambda application log levels include:

```text
TRACE
DEBUG
INFO
WARN
ERROR
FATAL
```

Lambda can filter:
- application records below the selected threshold.

---

#### 4.2.7.18 System Log Level

Lambda system-log filtering supports:

```text
DEBUG
INFO
WARN
```

This controls:
- Lambda platform/system logs

separately from:
- application logs.

---

#### 4.2.7.19 Log-Level Filtering Requires JSON

Current Lambda documentation states:

```text
advanced log-level filtering
→ requires JSON format
```

Therefore:

```text
ApplicationLogLevel configured
+
LogFormat = Text
```

does not provide:
- the advanced Lambda filtering behavior.

This is a high-value exam rule.

---

#### 4.2.7.20 Lambda Custom Log Group

Default:

```text
/aws/lambda/<function-name>
```

Current Lambda configuration can specify:
- a different CloudWatch Logs log group.

Use when:
- related functions should share organization/retention/security settings.

Custom log group selection:
- changes destination organization,
not:
- application event semantics.

---

#### 4.2.7.21 CloudWatch Logs

CloudWatch Logs provides:
- storage,
- retention,
- search,
- filtering,
- Logs Insights,
- subscriptions/integrations.

Structured logging improves:
- field-based analysis.

---

#### 4.2.7.22 CloudWatch Logs Insights

Logs Insights:
- queries CloudWatch Logs.

For JSON logs:
- fields can be automatically discovered.

Example:

```json
{
  "level": "ERROR",
  "provider": "PRIMARY",
  "retryCount": 3
}
```

can expose:

```text
level
provider
retryCount
```

as directly queryable fields.

---

#### 4.2.7.23 Logs Insights Example

Concept:

```text
fields @timestamp, provider, retryCount
| filter level = "ERROR"
| filter provider = "PRIMARY"
| sort @timestamp desc
```

The important principle:

```text
explicit fields
→ direct query
```

Detailed Logs Insights syntax:
- belongs primarily to 4.1.3.

---

#### 4.2.7.24 Nested JSON Fields

Logs Insights supports:
- discovered nested JSON fields,
- dot notation.

Example:

```json
{
  "order": {
    "type": "EXPRESS"
  }
}
```

Conceptually:

```text
order.type
```

can be queried.

---

#### 4.2.7.25 CloudWatch System Fields

Logs Insights exposes system fields beginning with:

```text
@
```

Examples:

```text
@timestamp
@message
@logStream
```

Lambda log analysis can also expose:
- request context,
- duration/memory data,
- trace identifiers when available.

---

#### 4.2.7.26 X-Ray Correlation Fields

When trace data is available, Lambda logs can expose:

```text
@xrayTraceId
@xraySegmentId
```

This enables:

```text
log
↔ trace
```

correlation.

---

#### 4.2.7.27 Correlation IDs

A correlation identifier connects:
- related log events.

Examples:

```text
requestId
traceId
orderId
eventId
```

Choose based on:
- investigation boundary.

---

#### 4.2.7.28 Request ID vs Trace ID

Request ID:

```text
one invocation/request at a service
```

Trace ID:

```text
distributed transaction across traced components
```

Therefore:

```text
requestId
≠ traceId
```

Both can be useful.

---

#### 4.2.7.29 Business Identifiers

Useful examples:

```text
orderId
shipmentId
jobId
```

These can help locate:
- a business incident in logs.

But consider:
- privacy,
- sensitivity,
- whether the identifier is actually needed.

Logs tolerate high-cardinality identifiers better than:
- metric dimensions.

---

#### 4.2.7.30 Cross-Service Correlation

Example:

```text
API service
{
  "traceId": "abc",
  "orderId": "8472"
}

Payment service
{
  "traceId": "abc",
  "orderId": "8472"
}
```

Shared fields allow:
- one transaction to be followed across services.

---

#### 4.2.7.31 Contextual Logging

Useful fields can include:

```text
service
environment
operation
requestId
traceId
result
dependency
durationMs
retryCount
```

Only include fields that:
- answer likely troubleshooting questions.

---

#### 4.2.7.32 Do Not Log Everything

Poor pattern:

```text
serialize entire object graph
→ log it
```

Problems:
- sensitive data,
- excessive volume,
- cost,
- noisy queries,
- unstable schema.

Prefer:
- selected operational context.

---

#### 4.2.7.33 Sensitive Data

Do not log:
- passwords,
- access tokens,
- API keys,
- private keys,
- session secrets,
- unnecessary PII,
- full sensitive payloads.

Logs often have:
- broad operational visibility,
- long retention.

Treat logs as:
- persistent data.

---

#### 4.2.7.34 Logging Incoming Events

Lambda events may contain:
- headers,
- tokens,
- customer data,
- message bodies,
- identifiers.

Therefore:

```text
log entire incoming event
```

is not automatically safe.

Powertools intentionally keeps:
- automatic event logging disabled by default.

Use:
- selected safe fields.

---

#### 4.2.7.35 Redaction

If a useful field is sensitive:
- redact or mask it.

Example:

```text
email = "g***@example.com"
```

Prefer:
- omitting sensitive values entirely
when unnecessary.

---

#### 4.2.7.36 Exception Logging

Useful error context can include:
- meaningful message,
- exception type,
- stack/error context,
- operation,
- correlation identifiers.

Example:

```json
{
  "level": "ERROR",
  "message": "Payment request failed",
  "provider": "PRIMARY",
  "orderId": "8472",
  "errorType": "TimeoutException"
}
```

---

#### 4.2.7.37 Avoid Double-Logging Exceptions

Weak pattern:

```text
lower layer logs
→ throws
→ upper layer logs
→ runtime logs uncaught error
```

Result:
- duplicate noise.

Choose:
- one useful ownership boundary for logging the failure.

---

#### 4.2.7.38 Error Taxonomy

Useful structured fields:

```text
errorType
failureCategory
```

Example values:

```text
VALIDATION
DEPENDENCY_TIMEOUT
THROTTLING
INTERNAL
```

Benefits:
- direct grouping,
- stable dashboards/queries,
- less parsing.

---

#### 4.2.7.39 Retry Context

Retries can make one logical failure look like:
- several independent failures.

Useful fields:

```text
attempt
messageId
requestId
```

Then operators can distinguish:

```text
three independent failures
```

from:

```text
one message retried three times
```

---

#### 4.2.7.40 Event-Driven Logging

For SQS consumer logs, useful fields might include:

```text
messageId
eventType
correlationId
attempt
result
```

For EventBridge:

```text
eventId
source
detailType
correlationId
```

Use:
- identifiers appropriate to the event boundary.

---

#### 4.2.7.41 Idempotency Context

For event-driven applications, safe idempotency/business keys can help answer:

```text
Was this event processed before?
Was a retry suppressed?
```

Only log the key if:
- security/privacy requirements allow it.

---

#### 4.2.7.42 Cold Start Context

For Lambda:

```text
latency spike
↔ cold start
```

can be diagnostically useful.

Powertools can automatically include:
- cold-start context.

This is better than:
- inferring cold starts from free-form text.

---

#### 4.2.7.43 Structured Logging vs Metrics

Logs answer:

```text
what happened in this event?
```

Metrics answer:

```text
how much/how often over time?
```

Do not derive every aggregate operational signal from:
- repeated log scans.

If the application already knows:
- a numerical signal,

a custom metric can be cleaner.

---

#### 4.2.7.44 Structured Logging vs Tracing

Logging:

```text
what happened inside this component?
```

Tracing:

```text
where did this request travel and spend time?
```

Strong correlation:

```text
traceId in structured logs
→ fast trace-to-log drilldown
```

---

#### 4.2.7.45 Structured Logs and Alerts

Classic path:

```text
structured log
→ metric filter/query
→ alarm
→ notification
```

But:
- direct custom metrics may be more appropriate for known numerical signals.

Alert implementation:
- belongs primarily to 4.2.5.

---

#### 4.2.7.46 Powertools for AWS Lambda Logging

Powertools Logging provides:
- an opinionated Lambda-oriented structured JSON logger.

Current Java capabilities include:
- SLF4J integration,
- Log4j2 or Logback,
- Lambda context,
- cold-start context,
- additional structured fields,
- X-Ray correlation,
- DEBUG sampling/buffering features.

Use when:
- Lambda-specific context and conventions add value.

---

#### 4.2.7.47 Powertools Standard Fields

Current Java Powertools output includes standard fields such as:

```text
timestamp
level
service
message
```

and, where applicable:

```text
xray_trace_id
error
sampling_rate
```

Lambda context can add:
- cold start,
- function name,
- function version,
- memory size,
- function ARN,
- request ID.

---

#### 4.2.7.48 Stable Powertools Service Name

Prefer:

```text
service = payment
```

Use:
- a logical service name.

Avoid:
- per-request dynamic service names.

Stable names improve:
- cross-function queries,
- dashboards,
- ownership clarity.

---

#### 4.2.7.49 Additional Structured Keys

Powertools can append application-specific keys.

Example:

```text
provider=PRIMARY
orderType=EXPRESS
retryCount=2
```

Prefer this to:

```text
"PRIMARY|EXPRESS|2"
```

inside one message string.

---

#### 4.2.7.50 Reserved Keys

Powertools defines:
- standard/reserved keys.

Do not reuse them for:
- unrelated application meanings.

Otherwise:
- behavior can become inconsistent,
- fields can be ignored or overwritten.

---

#### 4.2.7.51 Powertools `@Logging`

Java Powertools supports:

```java
@Logging
```

for Lambda handler/method instrumentation.

It provides:
- Lambda-aware logging context.

Do not confuse:

```text
@Logging
```

with:
- CloudWatch/Lambda logging configuration.

It is:
- application instrumentation.

---

#### 4.2.7.52 DEBUG Log Sampling

Powertools can emit DEBUG logs for:
- a configured percentage of invocations.

Purpose:

```text
detailed diagnostics for sample traffic
without global DEBUG
```

Do not confuse:
- log sampling

with:
- X-Ray trace sampling.

They control:
- different telemetry signals.

---

#### 4.2.7.53 Lambda Native JSON vs Powertools JSON

Current Lambda can:
- natively format supported application logging methods as JSON.

Powertools can:
- produce richer structured JSON.

If application logs are already JSON:
- Lambda JSON mode does not double-encode them.

Therefore:

```text
Powertools JSON
+
Lambda LogFormat=JSON
```

can coexist.

---

#### 4.2.7.54 When Native Lambda JSON Is Enough

Use native Lambda JSON when:
- supported runtime/logger behavior provides enough structure.

Benefits:
- Lambda-managed formatting,
- standardized envelope,
- advanced log-level filtering,
- JSON platform/system logs.

---

#### 4.2.7.55 When Powertools Adds Value

Use Powertools when you want:
- service conventions,
- cold-start context,
- X-Ray correlation,
- structured application keys,
- DEBUG sampling,
- Lambda-specific context.

Powertools is:
- helpful,
- not mandatory.

---

#### 4.2.7.56 Plain Text Still Exists

JSON is preferred for:
- machine analysis.

Plain text may still be appropriate when:
- existing tooling depends on it.

AWS notes:
- JSON can increase log size due to additional metadata/structure.

Tradeoff:

```text
better queryability
↔ more bytes
```

---

#### 4.2.7.57 Log Cost

More logging can increase:
- ingestion,
- storage,
- query volume,
- downstream processing.

Control cost with:
- appropriate levels,
- retention,
- concise fields,
- no duplicate events,
- no unnecessary payload logging.

---

#### 4.2.7.58 Retention

CloudWatch Logs retention should be:
- deliberately configured.

Base it on:
- operational need,
- compliance,
- cost,
- sensitivity.

Retention:
- is separate from log schema.

Do not assume:
- every log must be retained indefinitely.

---

#### 4.2.7.59 Field Cardinality

Logs can reasonably contain fields such as:

```text
orderId
requestId
traceId
```

because logs:
- are event records.

The same values as metric dimensions can create:
- excessive metric cardinality/cost.

This is an important telemetry distinction.

#### 4.2.7.63 Common Exam Traps

##### 4.2.7.63.1 JSON String Automatically Means Structured Logging
Wrong.

If all context is inside:

```text
message
```

then:
- field-based queryability is still weak.

##### 4.2.7.63.2 Lambda Logs Are JSON by Default
Wrong for standard managed runtimes.

Current default:
- `Text`.

##### 4.2.7.63.3 Structured Logging Requires Manual JSON String Construction
Wrong.
- Lambda native logging and Powertools can emit structured JSON.

##### 4.2.7.63.4 Log-Level Filtering Works with Text Format
Wrong for current Lambda advanced logging.

```text
log-level filtering
→ requires JSON
```

##### 4.2.7.63.5 Request ID = Trace ID
Wrong.

```text
requestId
→ service/invocation identity

traceId
→ distributed request identity
```

##### 4.2.7.63.6 Log Every Lambda Event
Wrong.
- Events can contain sensitive data.

##### 4.2.7.63.7 Use Request IDs as Metric Dimensions
Usually wrong.
- They are high cardinality.

##### 4.2.7.63.8 DEBUG Should Always Be Enabled in Production
Wrong.
- Use appropriate filtering/sampling.

##### 4.2.7.63.9 Structured Logs Replace Metrics
Wrong.

##### 4.2.7.63.10 Structured Logs Replace Traces
Wrong.

##### 4.2.7.63.11 Powertools JSON Is Double-Encoded by Lambda JSON
Wrong.
- Existing JSON application logs are not double-encoded.

##### 4.2.7.63.12 More Fields Always Means Better Logs
Wrong.
- More fields increase volume, noise, and sensitive-data risk.

Fastest discriminator:

```text

```

#### 4.2.7.68 Final Principle

**Structured logging records meaningful application events as stable machine-queryable fields instead of burying operational context inside free-form strings. Prefer JSON for Lambda when logs will be searched or analyzed, while remembering that standard managed runtimes still default to text. Use explicit typed fields for identifiers, outcomes, durations, dependencies, retry information, and error categories, and include request or trace identifiers when correlation is useful. Current Lambda advanced logging controls support JSON/Text selection, separate application and system log-level filtering, and custom log groups; log-level filtering requires JSON. CloudWatch Logs Insights automatically discovers JSON fields and makes them directly queryable. Powertools can add Lambda-specific context, cold-start information, trace correlation, structured keys, and controlled DEBUG sampling. Keep logs operationally intentional: avoid secrets and unnecessary payloads, prevent duplicate exception logging, control volume and retention, and combine logs with metrics and traces rather than treating one telemetry signal as a replacement for the others.**
