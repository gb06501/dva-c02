### 4.3.5 Cache content based on request headers

#### 4.3.5.1 Exam and Task Context

##### 4.3.5.1.1 Domain
- **Domain 4:** Troubleshooting and Optimization.

##### 4.3.5.1.2 Task
- **Task 4.3:** Optimize applications by using AWS services and features.

##### 4.3.5.1.3 Skill
- **Skill 4.3.5:** **Cache content based on request headers.**

##### 4.3.5.1.4 Position Inside Task 4.3
- 4.3.1:
  - define concurrency.
- 4.3.2:
  - profile application performance.
- 4.3.3:
  - determine minimum memory and compute power.
- 4.3.4:
  - optimize messaging with subscription filter policies.
- 4.3.5:
  - control cached variants based on request characteristics.

##### 4.3.5.1.5 Core Question
- **When an origin returns different content for the same URL depending on an HTTP request header, how should CloudFront distinguish the cached variants without unnecessarily destroying the cache hit ratio?**

---

#### 4.3.5.2 Core Mental Model

##### 4.3.5.2.1 Default Cache Identity
- CloudFront needs a:
  - cache key.
- The cache key determines:
  - whether a viewer request matches an already cached object.

##### 4.3.5.2.2 Default Shape

```text
viewer request
     |
     v
CloudFront
     |
     | derive cache key
     v
cached object?
   /      \
 yes      no
 |         |
 v         v
edge      origin
response  request
```

##### 4.3.5.2.3 Header Variation
- Suppose:

```text
GET /index.html
Accept-Language: en
```

returns:
- English content.

But:

```text
GET /index.html
Accept-Language: de
```

returns:
- German content.

Then:
- the header value affects the representation.
- Therefore:
  - the relevant header should participate in the cache key.

##### 4.3.5.2.4 Core Principle
- **If a viewer-request value changes the representation returned by the origin, include that value in the cache key.**
- If it does not change the representation:
  - avoid putting it in the cache key.

---

#### 4.3.5.3 The Cache Key

##### 4.3.5.3.1 Definition
- The cache key:
  - uniquely identifies a cached object variant.

##### 4.3.5.3.2 CloudFront Default
- By default, CloudFront's cache key includes:
  - distribution domain name,
  - URL path.

##### 4.3.5.3.3 Additional Dimensions
- A cache policy can additionally include:
  - HTTP headers,
  - cookies,
  - URL query strings.

##### 4.3.5.3.4 Consequence

```text
same cache key
→ same cached representation

different cache key
→ potentially different cached representation
```

---

#### 4.3.5.4 Why Request Headers Matter

##### 4.3.5.4.1 Same URL, Different Representation
- An origin may vary content according to:
  - language,
  - device characteristics,
  - geography,
  - protocol characteristics,
  - application-specific request metadata.

##### 4.3.5.4.2 Example

```text
/index.html + Accept-Language=en
→ English page

/index.html + Accept-Language=de
→ German page
```

##### 4.3.5.4.3 Correct Cache Behavior
- CloudFront must not:
  - serve the English cached object to a request that requires the German representation.

##### 4.3.5.4.4 Solution
- Include:
  - the representation-changing header
in:
  - the cache key.

---

#### 4.3.5.5 Cache Policy

##### 4.3.5.5.1 Purpose
- A CloudFront cache policy controls:
  - what participates in the cache key,
  - TTL settings,
  - compressed-object caching behavior.

##### 4.3.5.5.2 Request Values
- Cache-key settings can include:
  - headers,
  - cookies,
  - query strings.

##### 4.3.5.5.3 Attachment
- A cache policy is attached to:
  - one or more CloudFront cache behaviors.

##### 4.3.5.5.4 Exam Mental Model

```text
cache behavior
   |
   '-- cache policy
          |
          +-- headers
          +-- cookies
          +-- query strings
          '-- TTL/compression settings
```

---

#### 4.3.5.6 Header Configuration in a Cache Policy

##### 4.3.5.6.1 None
- Do not include viewer HTTP headers:
  - in the cache key.

##### 4.3.5.6.2 Include Specified Headers
- Specify:
  - the header names that should affect the cache key.

##### 4.3.5.6.3 Example
- Configure:

```text
Accept-Language
```

- Viewer sends:

```text
Accept-Language: en-US
```

- CloudFront includes:
  - the header and its value
in:
  - cache-key calculation.

##### 4.3.5.6.4 Important Detail
- Configuration identifies:
  - header names.
- Actual request values:
  - distinguish cache variants.

---

#### 4.3.5.7 Header-Based Cache Variants

##### 4.3.5.7.1 Example

```text
URL: /catalog
Header: Accept-Language
```

Requests:

```text
/catalog + en
/catalog + de
/catalog + fr
```

can produce:

```text
cache variant 1
cache variant 2
cache variant 3
```

##### 4.3.5.7.2 Benefit
- Correct content:
  - can still be served from CloudFront edge cache.

##### 4.3.5.7.3 Tradeoff
- Every additional variation:
  - potentially creates additional cache entries.

---

#### 4.3.5.8 Cache Hit Ratio

##### 4.3.5.8.1 Definition
- Cache hit ratio describes:
  - the proportion of viewer requests satisfied from cache.

##### 4.3.5.8.2 Fewer Cache-Key Dimensions
- Generally:

```text
fewer relevant variants
→ more requests share cache entries
→ higher potential cache hit ratio
```

##### 4.3.5.8.3 More Cache-Key Dimensions
- Generally:

```text
more varying values
→ more cache-key variants
→ fewer requests per variant
→ lower potential cache hit ratio
```

##### 4.3.5.8.4 Optimization Goal
- Include:
  - every value required for correctness.
- Exclude:
  - values that do not change the returned object.

---

#### 4.3.5.9 The Cardinality Problem

##### 4.3.5.9.1 Low Cardinality
- Example:

```text
language = en | de | fr
```

- Few possible variants.
- Often reasonable:
  - if origin really returns different content.

##### 4.3.5.9.2 High Cardinality
- Example:

```text
X-Request-ID = unique per request
```

##### 4.3.5.9.3 Effect

```text
unique header value per request
→ unique cache key per request
→ almost no reuse
```

##### 4.3.5.9.4 Principle
- Avoid including:
  - high-cardinality headers
unless:
  - they genuinely determine distinct cacheable representations.

---

#### 4.3.5.10 User-Specific Headers

##### 4.3.5.10.1 Example

```text
Authorization: Bearer <user-specific-token>
```

##### 4.3.5.10.2 Problem
- Highly variable user/session values can:
  - fragment the cache.

##### 4.3.5.10.3 Decision
- Ask:

```text
Does this value actually determine a reusable cache representation?
```

##### 4.3.5.10.4 Exam Principle
- Do not include:
  - user-specific/session-specific values
in a shared cache key casually.
- They can:
  - create huge numbers of variants,
  - reduce cache effectiveness.

---

#### 4.3.5.11 Cache Policy vs Origin Request Policy

The key distinction is whether a viewer-request value changes the cached representation.

```text
changes returned representation?
→ cache policy
→ include in cache key
→ value is also forwarded to origin

origin needs it, but representation does not change?
→ origin request policy
→ forward without changing cache identity
```

Examples:

```text
Accept-Language changes localized content
→ cache policy

X-Tracking-ID used only for analytics
→ origin request policy
```

Do not add a value to the cache key merely because:
- the origin needs to receive it.

All values included in the cache key are automatically:
- sent to the origin.

Use the origin request policy only for additional headers, cookies, or query strings that the origin needs but that should not fragment the cache.

---

#### 4.3.5.12 CloudFront-Generated Headers

##### 4.3.5.12.1 Capability
- CloudFront can add:
  - certain headers derived from viewer-request characteristics.

##### 4.3.5.12.2 Use
- These can support:
  - device,
  - location,
  - protocol-related origin logic,
depending on:
  - header and configuration.

##### 4.3.5.12.3 Cache-Key Use
- Certain CloudFront-generated headers can:
  - be included in the cache key.

##### 4.3.5.12.4 Exam Principle
- If CloudFront-derived request context:
  - changes the returned representation,
it can become:
  - a cache-key dimension where supported.

---

#### 4.3.5.13 Accept-Encoding and Compression

##### 4.3.5.13.1 Special Handling
- Cache policies have explicit settings for:
  - Gzip,
  - Brotli.

##### 4.3.5.13.2 When Enabled
- CloudFront can normalize:
  - `Accept-Encoding`
and include the normalized value:
  - in the cache key.

##### 4.3.5.13.3 Why
- Compressed and uncompressed representations:
  - may require separate cached variants.

##### 4.3.5.13.4 Exam Principle
- Use:
  - cache-policy compression settings
rather than:
  - treating `Accept-Encoding` blindly as an arbitrary high-variation header.

---

#### 4.3.5.14 TTL Context

Cache policies also define:
- Minimum TTL,
- Default TTL,
- Maximum TTL.

Do not confuse:
- TTL selection

with:
- cache-key selection.

Important AWS behavior:

```text
Minimum TTL > 0
→ CloudFront caches for at least that duration
```

even if the origin sends:

```text
Cache-Control: no-cache
Cache-Control: no-store
Cache-Control: private
```

If:

```text
Minimum TTL = 0
Default TTL = 0
Maximum TTL = 0
```

then caching is disabled for that policy, so header-based cache variation no longer provides cache reuse.

---

#### 4.3.5.12 Correctness vs Cache Reuse

A CloudFront cache key must be precise enough to prevent incorrect reuse, but no more specific than necessary.

```text
too few cache-key dimensions
→ different representations collapse into one key
→ wrong cached variant can be served

too many cache-key dimensions
→ same representation stored many times
→ cache fragmentation
→ lower hit ratio
→ more origin requests
```

Optimization target:

```text
minimum cache key
that still uniquely identifies
the correct representation
```

High-cardinality values such as:
- unique request IDs,
- session IDs,
- correlation IDs

normally should not participate in a shared cache key unless they genuinely produce distinct reusable representations.

Forwarding and cache identity remain separate concepts:

```text
origin needs value only
→ origin request policy

value changes response representation
→ cache policy
```

#### 4.3.5.15 Cache Behavior

##### 4.3.5.15.1 CloudFront Distribution
- Contains:
  - cache behaviors.

##### 4.3.5.15.2 Cache Policy
- Attached to:
  - a cache behavior.

##### 4.3.5.15.3 Therefore
- Different path patterns can:
  - use different cache policies.

##### 4.3.5.15.4 Example

```text
/static/*
→ simple cache key

/localized/*
→ include Accept-Language

/api/*
→ different caching strategy
```

#### 4.3.5.12 Managed vs Custom Cache Policies

##### 4.3.5.12.1 Managed
- AWS provides:
  - managed cache policies
for:
  - common use cases.

##### 4.3.5.12.2 Custom
- Create custom cache policy when:
  - application-specific headers,
  - cookies,
  - query strings,
  - TTL behavior
must be controlled.

##### 4.3.5.12.3 Exam Decision
- Requirement explicitly names:
  - a custom response-changing request header.
- Likely direction:
  - custom cache policy including that header.

#### 4.3.5.13 Query Strings and Cookies Are Parallel Concepts

##### 4.3.5.13.1 Cache Policy
- Can include:
  - headers,
  - cookies,
  - query strings.

##### 4.3.5.13.2 Same Rule
- Ask:
  - does the value change the returned representation?

##### 4.3.5.13.3 If Yes
- Include:
  - relevant value in cache key.

##### 4.3.5.13.4 If No but Origin Needs It
- Use:
  - origin request policy.

##### 4.3.5.13.5 Skill Focus
- 4.3.5 explicitly names:
  - request headers.
- Understand cookies/query strings:
  - as parallel cache-key dimensions,
not:
  - the primary focus.

#### 4.3.5.14 Cache-Key Decision Flow

##### 4.3.5.14.1 Step 1

```text
Does origin return different content for the same path?
```

- No:
  - do not add unnecessary cache-key dimensions.
- Yes:
  - continue.

##### 4.3.5.14.2 Step 2

```text
Which request value causes the variation?
```

- Header?
- Cookie?
- Query string?

##### 4.3.5.14.3 Step 3

```text
Does this header actually determine the representation?
```

- Yes:
  - include in cache policy.
- No:
  - exclude from cache key.

##### 4.3.5.14.4 Step 4

```text
Does origin still need the excluded header?
```

- Yes:
  - origin request policy.
- No:
  - do not forward unnecessarily.

##### 4.3.5.14.5 Step 5
- Keep:
  - cache-key cardinality as low as correctness allows.

---

#### 4.3.5.19 Practical Pattern Summary

| Requirement | Correct CloudFront choice |
|---|---|
| Same path returns different content by request header | Include the response-changing header in the cache policy/cache key |
| Origin needs header only for telemetry/logging | Forward with origin request policy |
| Cache hit ratio is poor | Remove unnecessary high-cardinality headers/cookies/query strings from cache key |
| Wrong cached variant is served | Add the missing representation-changing request value to cache key |
| Language determines representation | Include the relevant language header |
| Unique correlation/session ID does not change content | Keep it out of cache key; forward only if origin needs it |
| Gzip/Brotli representation handling | Use cache-policy compression settings |
| Application-specific response-changing header | Usually use a custom cache policy |

#### 4.3.5.20 Common Exam Traps

##### 4.3.5.20.1 Forward Every Header
- Bad optimization.
- It can:
  - unnecessarily vary cache behavior in legacy configurations,
  - expose origin to irrelevant request data.
- Prefer:
  - explicit policy configuration.

##### 4.3.5.20.2 Include Every Header in Cache Key
- Wrong.
- Causes:
  - cache fragmentation.

##### 4.3.5.20.3 Never Include Headers
- Wrong.
- If header changes response:
  - it must be represented in cache identity.

##### 4.3.5.20.4 Origin Request Policy Changes Cache Key
- False.
- It forwards:
  - additional values without adding them to cache key.

##### 4.3.5.20.5 Cache Policy Only Controls TTL
- False.
- It also controls:
  - cache-key values.

##### 4.3.5.20.6 Header in Cache Key Is Not Sent to Origin
- False.
- Cache-key values are:
  - automatically included in origin requests.

##### 4.3.5.20.7 Maximize Hit Ratio by Ignoring Response-Changing Header
- Wrong.
- That can:
  - serve incorrect content.

##### 4.3.5.20.8 Forward Analytics Header via Cache Policy
- Usually wrong if:
  - header does not change content.
- Prefer:
  - origin request policy.

##### 4.3.5.21.1 Same URL, Different Content by Header
- Use:

  - relevant header in cache key.

##### 4.3.5.21.2 Origin Needs Header, Cached Content Is Same
- Use:
  - origin request policy.

##### 4.3.5.21.3 Cache Hit Ratio Is Poor
- Check:
  - unnecessary headers,
  - high-cardinality cookies,
  - unnecessary query strings

  - cache key.

##### 4.3.5.21.4 Wrong Variant Served
- Check:
  - whether representation-changing header is missing from cache key.

- Include:
  - relevant language header
if:
  - origin uses it to vary content.

##### 4.3.5.21.6 Need Telemetry Header at Origin
- Forward:
  - with origin request policy.
- Do not:
  - add to cache key unless it changes representation.

##### 4.3.5.21.7 Need Gzip/Brotli Variants
- Use:
  - cache-policy compression support.

#### 4.3.5.19 Exam-Level Knowledge Frame

##### 4.3.5.19.1 Cache Key
- Determines:
  - whether viewer request matches cached object.

##### 4.3.5.19.2 Cache Policy
- Controls:
  - headers,
  - cookies,
  - query strings
included in:
  - cache key.
- Also controls:
  - TTL,
  - compression settings.

##### 4.3.5.19.3 Header Rule

```text
header changes representation
→ include in cache key
```

##### 4.3.5.19.4 Origin Request Policy Rule

```text
origin needs header
but header does not change representation
→ forward without adding to cache key
```

##### 4.3.5.19.5 Optimization Rule

```text
correctness first
+
minimum necessary cache-key dimensions
→ best cache reuse
```

##### 4.3.5.19.6 Fastest Exam Discriminator

```text
same URL + different response by header
→ cache policy

origin needs header only
→ origin request policy

poor cache hit ratio
→ remove unnecessary cache-key variation

wrong cached variant
→ add missing response-changing dimension

unique request/session ID
→ normally keep out of shared cache key
```

##### 4.3.5.19.7 Final Principle
- **A CloudFront cache key should contain the smallest set of viewer-request values necessary to uniquely identify the representation returned by the origin. Include a request header when it changes the content; forward it with an origin request policy instead when the origin needs it but it does not change the cached representation.**
