#### 4.3.9.4 Structured Performance Logs and Logs Insights

Performance logs are most useful when they contain explicit fields for:
- identity,
- operation,
- timing,
- dependency,
- workload size,
- outcome.

Example:

```json
{
  "level": "INFO",
  "requestId": "abc-123",
  "operation": "loadCustomer",
  "dependency": "DynamoDB",
  "durationMs": 184,
  "itemCount": 25
}
```

CloudWatch Logs Insights automatically discovers fields in JSON logs, which enables direct filtering and aggregation without fragile text parsing.

Core workflow:

```text
logs
→ filter relevant events
→ select/extract fields
→ aggregate duration
→ sort/group
→ identify dominant operation or outlier
```

Useful query patterns:

```text
# slow individual requests
fields @timestamp, requestId, operation, durationMs
| filter durationMs > 1000
| sort durationMs desc
```

```text
# compare operations
stats avg(durationMs), max(durationMs), count(*)
by operation
```

```text
# tail latency
stats avg(durationMs), pct(durationMs, 95), pct(durationMs, 99)
by operation
```

Interpretation:

```text
one operation consistently slow
→ investigate that operation/dependency

average acceptable + p95/p99 high
→ investigate slow minority of requests
```

Useful comparison dimensions:
- operation,
- dependency,
- request type,
- payload/item/batch size,
- version,
- result,
- retry count.

For legacy unstructured logs:
- use `parse` where necessary.

For new instrumentation:
- prefer structured fields.

#### 4.3.9.5 Lambda Platform Log Analysis

Lambda emits platform/runtime information including:

```text
START
END
REPORT
```

`REPORT` can contain:
- `Duration`,
- `Billed Duration`,
- `Memory Size`,
- `Max Memory Used`,
- `Init Duration` where applicable,
- runtime status/error information in current formats.

CloudWatch Logs Insights automatically discovers Lambda fields such as:

```text
@timestamp
@requestId
@duration
@billedDuration
@memorySize
@maxMemoryUsed
@xrayTraceId
@xraySegmentId
```

##### 4.3.9.5.1 Slow Invocation

```text
filter @type = "REPORT"
| fields @timestamp, @requestId, @duration
| sort @duration desc
```

High `@duration` tells you:
- which invocation was slow.

It does not by itself tell you:
- why.

Use `@requestId` to correlate with application logs.

##### 4.3.9.5.2 Memory Pressure

Pattern:

```text
@maxMemoryUsed ≈ @memorySize
```

may indicate:
- memory pressure.

Do not treat one value as proof of OOM.

Correlate with:
- duration,
- errors,
- payload/input size,
- Lambda Insights runtime metrics.

Important AWS nuance:
- `Max Memory Used` can reflect maximum memory across invocations sharing an execution environment.

##### 4.3.9.5.3 Cold Starts

```text
slow invocation
+
high/present Init Duration
→ initialization contributed to latency
```

Compare:
- cold vs warm invocations.

Do not attribute:
- all Lambda latency

to:
- handler code.

##### 4.3.9.5.4 Timeout and Runtime Failure
Timeout is:
- an outcome.

Repeated timeout can result from:
- slow dependencies,
- excessive work,
- resource pressure,
- retry amplification.

Use logs to determine:
- what consumed the execution time.

#### 4.3.9.6 Correlation and Bottleneck Isolation

##### 4.3.9.6.1 Request ID
Use request ID to connect:
- Lambda platform invocation information,
- application log events.

Workflow:

```text
find slow REPORT
→ obtain @requestId
→ query all events for request
→ reconstruct operation sequence
→ identify slow step
```

##### 4.3.9.6.2 Trace ID
When available:

```text
slow log event
→ trace ID
→ distributed trace
→ slow dependency/subsegment
```

Logs explain:
- application events.

Traces explain:
- distributed path.

##### 4.3.9.6.3 Dependency and Stage Timing
Log explicit durations for meaningful stages/dependencies.

Example:

```text
validate:    4 ms
fetch:     280 ms
transform:  12 ms
persist:     9 ms
```

Conclusion:
- investigate `fetch`.

Useful fields:

```text
operation
dependency
durationMs
requestId
```

##### 4.3.9.6.4 Workload Size
Performance may scale with:
- payload bytes,
- item count,
- batch size,
- record count.

Pattern:

```text
duration rises
as
workload size rises
```

Then investigate:
- algorithm,
- batching,
- memory,
- downstream calls,
- parallelism.

##### 4.3.9.6.5 Retries
Retries can:
- increase latency,
- multiply dependency calls,
- amplify load.

Useful fields:
- attempt,
- dependency,
- status/error,
- backoff,
- final outcome.

Pattern:

```text
slow request
+
multiple attempts
→ retry behavior contributes to latency
```

Final success:
- does not prove the request was performant.

##### 4.3.9.6.6 Errors and Warnings
Correlate WARN/ERROR events with:
- latency spikes,
- throttling,
- dependency failures,
- retry activity,
- timeout precursors.

##### 4.3.9.6.7 Time and Deployment Correlation
Always compare:
- normal period,
- slow period.

Useful version fields:
- application version,
- Lambda version/alias,
- release/build identifier.

Pattern:

```text
release
→ slow logs begin immediately after
```

supports:
- regression investigation.

#### 4.3.9.7 Runtime Logs and Supporting Evidence

Lambda Insights provides performance log events and workflows for analyzing:
- CPU,
- memory,
- disk,
- network,
- cold starts,
- execution-environment behavior.

Use the three log layers deliberately:

```text
application logs
→ operation/dependency/business timing

Lambda platform logs
→ invocation duration/memory/init/runtime status

Lambda Insights performance logs
→ execution-environment resource behavior
```

Strong analysis:
- correlates the relevant layers.

Useful log fields include:
- operation,
- dependency,
- version,
- environment,
- result/status,
- request type,
- duration,
- payload size,
- item count,
- retry count,
- request ID,
- trace ID.

Avoid:
- secrets,
- credentials,
- unnecessary sensitive data.

Logging itself has overhead:
- ingestion cost,
- storage cost,
- query cost,
- noise.

Therefore:

```text
capture meaningful timing/context
≠ log everything
```

Signal boundary:

```text
metrics
→ aggregate monitoring

logs
→ detailed event investigation

traces
→ distributed request path
```

General multi-signal performance diagnosis:
- 4.3.8.

This skill:
- uses logs as the primary evidence source.

#### 4.3.9.8 Practical Pattern Summary

| Observation / Requirement | Best log-centered approach |
|---|---|
| Need search large Lambda log set | CloudWatch Logs Insights |
| Need find slowest invocations | Query `@duration` |
| Need inspect Lambda memory pressure | Correlate `@maxMemoryUsed` + `@memorySize` + errors/runtime metrics |
| Need quantify cold-start contribution | Inspect `Init Duration` |
| Need find slow internal step | Log stage durations + correlate by request ID |
| Need compare dependencies | Log dependency + duration and aggregate by dependency |
| Need tail-latency cause | p95/p99 + inspect slow events |
| Need connect log to distributed request | X-Ray trace ID |
| Need CPU/memory/disk/network context | Lambda Insights |
| Successful request still slow | Inspect retries and dependency timing |

#### 4.3.9.9 Common Exam Traps

##### 4.3.9.9.1 Search Manually Through Every Log
- Poor approach at scale.
- Prefer:
  - CloudWatch Logs Insights.

##### 4.3.9.9.2 Log Only "Started" and "Finished"
- Insufficient for complex bottleneck analysis.
- Add:
  - operation/dependency timing.

##### 4.3.9.9.3 Average Duration Proves All Requests Are Fast
- Wrong.
- Analyze:
  - percentiles/outliers.

##### 4.3.9.9.4 `Duration` Identifies the Slow Code
- Wrong.
- It identifies:
  - slow invocation.
- Need:
  - application timing/correlation to isolate cause.

##### 4.3.9.9.5 `Max Memory Used` Alone Proves OOM
- Wrong.
- Interpret:
  - with errors,
  - workload,
  - runtime metrics.

##### 4.3.9.9.6 Cold Start Means Every Invocation Is Slow
- Wrong.
- Initialization:
  - applies when a new execution environment initializes.

##### 4.3.9.9.7 Successful Request Has No Performance Problem
- Wrong.
- Retries:
  - can make a successful request slow.

##### 4.3.9.9.8 Unstructured Logs Are Always Enough
- Wrong.
- Structured logs:
  - improve querying and aggregation.

##### 4.3.9.9.9 Log More Data to Solve Everything
- Wrong.
- Log:
  - relevant context,
  - not indiscriminate volume.

##### 4.3.9.9.10 Logs Replace Tracing
- Wrong.
- Distributed dependency latency:
  - often needs trace correlation.

#### 4.3.9.12 Exam-Level Knowledge Frame

##### 4.3.9.12.1 Core Rule

```text
slow application
→ find slow events
→ correlate by request/trace
→ break duration into operations/dependencies
→ identify dominant contributor
```

##### 4.3.9.12.2 Lambda Rule

```text
REPORT
→ Duration
→ Memory Size
→ Max Memory Used
→ Init Duration where applicable
```

##### 4.3.9.12.3 Logs Insights Rule

```text
structured fields
→ filter
→ stats
→ sort/group
→ bottleneck pattern
```

##### 4.3.9.12.4 Correlation Rule

```text
request ID
→ same invocation/application events

trace ID
→ distributed request path
```

##### 4.3.9.12.5 Fastest Exam Discriminator

```text
search/analyze CloudWatch logs?
→ Logs Insights

slow Lambda invocation?
→ @duration

memory evidence?
→ @maxMemoryUsed + @memorySize

cold-start contribution?
→ Init Duration

which internal step is slow?
→ structured stage-duration logs

which dependency is slow?
→ dependency-duration logs + trace correlation

system-level Lambda performance?
→ Lambda Insights
```

##### 4.3.9.12.6 Final Principle
- **A useful performance log records identity, operation, timing, workload context, and outcome. Use CloudWatch Logs Insights to aggregate those fields, identify slow requests or operations, then correlate request IDs and trace IDs to determine what actually consumed the time.**
