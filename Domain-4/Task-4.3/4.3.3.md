### 4.3.3 Determine minimum memory and compute power for an application

#### 4.3.3.1 Exam and Task Context

##### 4.3.3.1.1 Domain
- **Domain 4:** Troubleshooting and Optimization.

##### 4.3.3.1.2 Task
- **Task 4.3:** Optimize applications by using AWS services and features.

##### 4.3.3.1.3 Skill
- **Skill 4.3.3:** **Determine minimum memory and compute power for an application.**

##### 4.3.3.1.4 Position Inside Task 4.3
- 4.3.1:
  - define concurrency.
- 4.3.2:
  - profile application performance.
- 4.3.3:
  - use measured workload behavior to determine sufficient memory and compute.
- The logical sequence is:

```text
understand simultaneous workload
→ profile actual performance
→ identify resource pressure
→ right-size memory/compute
→ verify performance and cost
```

##### 4.3.3.1.5 Core Question
- **What is the smallest resource configuration that still satisfies the application's performance and reliability requirements?**

---

#### 4.3.3.2 Core Mental Model

##### 4.3.3.2.1 Right-Sizing
- Right-sizing means:
  - provide enough resources to satisfy workload requirements,
  - avoid unnecessary over-provisioning.
- The target is not:
  - minimum memory at any cost.
- The target is:

```text
minimum sufficient resources
for the required performance envelope
```

##### 4.3.3.2.2 Two Failure Modes

```text
UNDER-PROVISIONED
→ slow execution
→ memory pressure
→ timeouts/errors
→ poor throughput

OVER-PROVISIONED
→ unused capacity
→ unnecessary cost
```

##### 4.3.3.2.3 Evidence First
- Determine sizing from:
  - profiling,
  - representative tests,
  - runtime metrics,
  - latency requirements,
  - workload characteristics.
- Do not size only from:
  - intuition,
  - average payload,
  - default configuration.

---

#### 4.3.3.3 Memory and Compute Are Workload-Specific

##### 4.3.3.3.1 Memory-Bound Workload
- Examples:
  - large in-memory transformations,
  - large object graphs,
  - buffering large payloads,
  - memory-intensive libraries.
- Primary concern:
  - enough memory for the working set.

##### 4.3.3.3.2 CPU-Bound Workload
- Examples:
  - compression,
  - encryption,
  - image processing,
  - computation,
  - expensive serialization.
- Primary concern:
  - enough CPU to complete within the required duration.

##### 4.3.3.3.3 I/O-Bound Workload
- Examples:
  - waiting for database,
  - waiting for external API,
  - waiting for object storage.
- More CPU may:
  - provide little benefit if the dominant bottleneck is remote latency.

##### 4.3.3.3.4 Mixed Workload
- Most real applications:
  - combine compute,
  - memory,
  - network,
  - downstream waits.
- Right-sizing requires:
  - measuring the dominant constraint.

---

#### 4.3.3.4 AWS Lambda Memory Model

##### 4.3.3.4.1 Memory Configuration
- Standard Lambda functions support configurable memory from:
  - **128 MB to 10,240 MB**,
  - in **1 MB increments**.

##### 4.3.3.4.2 CPU Scales with Memory
- Lambda allocates CPU power:
  - proportionally to configured memory.
- Therefore increasing memory can also:
  - increase compute power.

##### 4.3.3.4.3 One-vCPU Reference Point
- AWS currently documents:
  - at **1,769 MB**,
  - a standard Lambda function has the equivalent of one vCPU.

##### 4.3.3.4.4 Critical Exam Distinction
- For standard Lambda:

```text
you do not independently configure CPU
```

- Instead:

```text
increase MemorySize
→ Lambda allocates more CPU proportionally
```

##### 4.3.3.4.5 Consequence
- A CPU-bound Lambda may become faster when memory is increased:
  - even when it did not need the additional memory capacity itself.

---

#### 4.3.3.5 Lambda Memory Is a Performance Lever

##### 4.3.3.5.1 Lowest Setting Is Not Automatically Optimal
- 128 MB is:
  - the minimum standard Lambda memory setting.
- AWS recommends it mainly for:
  - simple functions with modest requirements.

##### 4.3.3.5.2 Increasing Memory Can Improve
- CPU capacity,
- computational power,
- performance for imported libraries,
- performance for memory-bound work,
- performance for some network/I/O-bound workloads.

##### 4.3.3.5.3 Why
- Lambda resource allocation is coupled.
- Memory configuration affects more than:
  - RAM alone.

##### 4.3.3.5.4 Exam Trap
- Do not reason:

```text
function uses only 300 MB
→ configure approximately 300 MB
```

- If the function is CPU-bound:
  - a larger memory setting may still be optimal.

#### 4.3.3.6 Determine Actual Memory Usage

##### 4.3.3.6.1 Lambda REPORT Entry
- Lambda invocation reports expose:
  - configured memory,
  - maximum memory used,
  - duration.

##### 4.3.3.6.2 Important Field
- `Max Memory Used`
  helps determine:
  - whether the function approaches its configured memory,
  - whether memory is substantially over-provisioned.

##### 4.3.3.6.3 Interpretation

```text
Memory Size: 1024 MB
Max Memory Used: 950 MB
```

- Indicates:
  - little memory headroom.

```text
Memory Size: 4096 MB
Max Memory Used: 250 MB
```

- Indicates:
  - RAM capacity itself is not the reason for the high configuration.
- But:
  - CPU requirements may still justify the larger setting.

##### 4.3.3.6.4 Critical Distinction
- Low memory utilization does not automatically mean:
  - reduce Lambda memory.
- First check:
  - duration,
  - CPU-bound behavior,
  - cost/performance.

#### 4.3.3.8 Memory-Bound Lambda

##### 4.3.3.8.1 Symptoms
- Memory utilization approaches:
  - configured maximum.
- Function:
  - fails because memory is exhausted,
  - or experiences memory pressure.

##### 4.3.3.8.2 Correct Direction
- Increase:
  - Lambda memory configuration.
- Then:
  - retest.

##### 4.3.3.8.3 Also Investigate
- large buffers,
- unnecessary object retention,
- excessive allocations,
- oversized payload processing,
- unnecessary in-memory copies.

##### 4.3.3.8.4 Principle
- Do not use resource sizing to hide:
  - obviously inefficient application behavior.
- But do not under-size:
  - a legitimately memory-intensive workload.

---

#### 4.3.3.9 CPU-Bound Lambda

##### 4.3.3.9.1 Symptoms
- High compute demand.
- Long execution duration.
- Profiling identifies:
  - CPU-heavy application code.
- Memory itself may:
  - remain well below the configured maximum.

##### 4.3.3.9.2 Correct Direction
- Increase:
  - Lambda memory,
  which also increases:
  - CPU allocation.

##### 4.3.3.9.3 Result
- Execution can become:
  - significantly faster.

##### 4.3.3.9.4 Cost Implication
- More memory:
  - raises the resource rate.
- Shorter execution:
  - reduces billed duration.
- Therefore:
  - higher memory does not necessarily mean proportionally higher total cost.

---

#### 4.3.3.10 I/O-Bound Lambda

##### 4.3.3.10.1 Symptoms
- CPU usage:
  - modest.
- Memory:
  - sufficient.
- Trace:
  - most time spent waiting for dependency.

##### 4.3.3.10.2 Increasing Memory
- May improve:
  - some network-bound workloads,
  because Lambda resource allocation scales with memory.
- But:
  - it cannot fix an inherently slow downstream service.

##### 4.3.3.10.3 Correct Reasoning
- First identify:
  - where the wait occurs.
- Then determine:
  - whether resource increase changes measured performance.

---

#### 4.3.3.11 Minimum Does Not Mean Lowest Possible

##### 4.3.3.11.1 Bad Interpretation
- "Minimum memory" means:
  - configure 128 MB whenever the function runs.

##### 4.3.3.11.2 Correct Interpretation
- Minimum means:
  - the lowest configuration that still meets:
    - latency,
    - throughput,
    - reliability,
    - workload,
    - cost objectives.

##### 4.3.3.11.3 Example

```text
128 MB
→ 4.0 s

512 MB
→ 1.2 s

1024 MB
→ 0.7 s

2048 MB
→ 0.65 s
```

- If:
  - 1 second is required,
then:
  - 1024 MB may be the minimum performance-compliant setting.
- If:
  - 2 seconds is acceptable,
then:
  - 512 MB may be sufficient.
- Exact choice requires:
  - cost comparison too.

---

#### 4.3.3.12 Cost vs Performance

##### 4.3.3.12.1 Optimization Has Two Axes

```text
performance
+
cost
```

##### 4.3.3.12.2 More Memory
- Higher configured memory:
  - increases available compute,
  - can shorten execution.

##### 4.3.3.12.3 Faster Can Be Economically Better
- A function using:
  - more memory,
  - for much less time,
may have:
  - similar,
  - or sometimes lower,
  execution cost than a slow low-memory configuration.

##### 4.3.3.12.4 Therefore
- Do not optimize:
  - memory setting alone.
- Optimize:
  - **cost × performance behavior**.

---

#### 4.3.3.13 Performance Testing

##### 4.3.3.13.1 AWS Guidance
- AWS explicitly recommends:
  - performance testing Lambda functions
  to determine the optimum memory configuration.

##### 4.3.3.13.2 Test Multiple Configurations
- Example:

```text
128 MB
256 MB
512 MB
1024 MB
2048 MB
...
```

- Measure:
  - duration,
  - memory usage,
  - errors,
  - cost,
  - relevant business latency.

##### 4.3.3.13.3 Representative Workload
- Test with:
  - realistic payload sizes,
  - realistic data,
  - realistic dependencies,
  - realistic concurrency.

##### 4.3.3.13.4 Upper Bounds
- Include:
  - reasonably expected large inputs.
- Otherwise:
  - a configuration that works for average requests may fail at peak input size.

#### 4.3.3.14 AWS Lambda Power Tuning

##### 4.3.3.14.1 Purpose
- AWS Lambda documentation recommends considering:
  - the open-source **AWS Lambda Power Tuning** tool.

##### 4.3.3.14.2 What It Does
- It runs a Lambda function:
  - at multiple memory configurations,
  - measures performance,
  - enables cost/performance comparison.

##### 4.3.3.14.3 Architecture
- The tool uses:
  - AWS Step Functions
  to coordinate tests.

##### 4.3.3.14.4 Important Property
- The tested function runs:
  - in the user's AWS account,
  - with actual SDK/HTTP interactions where applicable.
- This provides:
  - realistic workload measurements.

##### 4.3.3.14.5 Exam Mental Model

```text
Need choose optimal Lambda memory
+
must compare cost/performance experimentally
→ Lambda Power Tuning
```

#### 4.3.3.15 Power Tuning Output

##### 4.3.3.15.1 Compare Configurations
- The useful question is not:

```text
which memory setting is fastest?
```

- It is:

```text
which setting gives the required performance
at acceptable cost?
```

##### 4.3.3.15.2 Possible Optimization Objectives
- lowest cost,
- lowest latency,
- balanced cost/performance.

##### 4.3.3.15.3 Workload-Specific Result
- There is:
  - no universal optimal Lambda memory size.
- Different functions:
  - produce different performance curves.

#### 4.3.3.16 AWS Compute Optimizer

##### 4.3.3.16.1 Lambda Memory Recommendations
- AWS Lambda documentation states:
  - eligible functions can receive memory recommendations from AWS Compute Optimizer.

##### 4.3.3.16.2 Purpose
- Recommendations help identify:
  - potentially over-provisioned,
  - or under-provisioned
  Lambda memory configurations.

##### 4.3.3.16.3 Architecture Constraint
- Current Lambda documentation notes:
  - Compute Optimizer Lambda memory recommendations support eligible **x86_64** functions.

##### 4.3.3.16.4 Exam Distinction
- Compute Optimizer:
  - recommendation based.
- Lambda Power Tuning:
  - experimentally executes the function across memory settings.

---

#### 4.3.3.17 Timeout Is Not Compute Power

##### 4.3.3.17.1 Timeout
- Lambda timeout:
  - limits how long an invocation may run.

##### 4.3.3.17.2 Increasing Timeout
- Does not:
  - provide more CPU,
  - provide more memory,
  - make slow code faster.

##### 4.3.3.17.3 Exam Trap

```text
CPU-bound function is too slow
→ increase timeout
```

- This only:
  - allows it to run longer.
- It does not:
  - solve the compute bottleneck.

##### 4.3.3.17.4 Correct Direction
- Profile.
- If CPU-bound:
  - increase memory/CPU allocation or optimize code.

---

#### 4.3.3.18 Concurrency Is Not Per-Invocation Compute

##### 4.3.3.18.1 Concurrency
- Concurrency determines:
  - how many invocations can be in progress.

##### 4.3.3.18.2 Memory
- Standard Lambda memory setting determines:
  - per-execution-environment memory,
  - proportional CPU allocation.

##### 4.3.3.18.3 Exam Trap
- Increasing concurrency:
  - does not make one CPU-bound invocation execute faster.

##### 4.3.3.18.4 Relationship
- More per-invocation compute:
  - can reduce duration.
- Lower duration:
  - can reduce concurrency required for the same request rate.

---

#### 4.3.3.19 Resource Sizing and Concurrency

##### 4.3.3.19.1 Recall

```text
Concurrency
≈ requests/second × average duration
```

##### 4.3.3.19.2 Example

```text
100 RPS
duration = 1 second
→ ~100 concurrent executions
```

- Increase memory/CPU.
- New duration:

```text
0.25 seconds
```

- Approximate concurrency:

```text
100 × 0.25
= 25
```

##### 4.3.3.19.3 Consequence
- Right-sizing can affect:
  - latency,
  - throughput,
  - concurrency consumption,
  - downstream pressure,
  - cost.

---

#### 4.3.3.20 Memory Headroom

##### 4.3.3.20.1 Do Not Size to One Exact Observation
- Example:

```text
maximum observed = 500 MB
configure exactly 500 MB
```

- Weak approach.

##### 4.3.3.20.2 Why
- Real workloads vary by:
  - payload,
  - runtime behavior,
  - library behavior,
  - traffic,
  - input distribution.

##### 4.3.3.20.3 Better Approach
- Test:
  - representative and upper-bound workloads.
- Maintain:
  - sufficient operational headroom.

---

#### 4.3.3.21 Average Workload Is Not Enough

##### 4.3.3.21.1 Example
- Average payload:
  - 1 MB.
- Maximum expected payload:
  - 20 MB.

##### 4.3.3.21.2 Risk
- Sizing only from:
  - 1 MB tests
may produce:
  - memory exhaustion,
  - timeout,
  - latency spikes
for large requests.

##### 4.3.3.21.3 AWS Guidance
- Test:
  - realistic data sizes,
  - including reasonable upper bounds.

---

#### 4.3.3.22 CPU and Parallelism

##### 4.3.3.22.1 More CPU Can Help
- CPU-bound work may improve with:
  - greater Lambda memory allocation.

##### 4.3.3.22.2 Multiple vCPUs
- At higher standard Lambda memory allocations:
  - more than one vCPU can become available.

##### 4.3.3.22.3 Application Requirement
- To benefit from multiple cores:
  - application/runtime behavior must be able to use them.

##### 4.3.3.22.4 Exam Principle
- Extra compute is useful only when:
  - the workload can consume it.

---

#### 4.3.3.23 Network-Bound Workloads

##### 4.3.3.23.1 AWS Guidance
- Lambda documentation notes that increasing memory can improve performance for:
  - CPU-bound,
  - memory-bound,
  - and some network-bound functions.

##### 4.3.3.23.2 Reasoning
- Lambda resource capacity scales with:
  - memory configuration.

##### 4.3.3.23.3 But
- If the dominant delay is:
  - downstream service processing,
then:
  - additional local compute may not materially help.

---

#### 4.3.3.24 Libraries and Runtime Footprint

##### 4.3.3.24.1 Imported Libraries
- Large or demanding libraries may:
  - increase memory requirements,
  - increase initialization work.

##### 4.3.3.24.2 Lambda Layers
- Layers can add:
  - libraries/runtime content.
- Resource impact depends on:
  - what the function loads and executes.

##### 4.3.3.24.3 Principle
- Size based on:
  - actual runtime behavior,
not:
  - package size alone.

---

#### 4.3.3.25 Resource Reuse

##### 4.3.3.25.1 Execution Environment Reuse
- AWS Lambda best practices recommend:
  - initializing reusable SDK clients,
  - database connections,
  outside the handler where appropriate.

##### 4.3.3.25.2 Benefit
- Subsequent invocations in the same environment can:
  - reuse resources,
  - reduce execution duration.

##### 4.3.3.25.3 Sizing Impact
- Better runtime efficiency can change:
  - duration,
  - CPU demand,
  - memory behavior.
- Therefore:
  - profile after meaningful implementation changes.

---

#### 4.3.3.26 Right-Sizing Is Iterative

##### 4.3.3.26.1 Iterative Loop
```text
choose reasonable starting resources
→ measure duration / CPU / memory / errors / cost
→ adjust resources
→ rerun representative tests
```

Application or workload changes can shift the optimum, so revalidate after meaningful changes.

#### 4.3.3.27 CI/CD and Performance Tuning

##### 4.3.3.27.1 AWS Lambda Power Tuning
- AWS documentation notes that Power Tuning can be incorporated into:
  - CI/CD processes.

##### 4.3.3.27.2 Why
- New code may change:
  - CPU profile,
  - memory use,
  - execution duration,
  - optimal memory configuration.

##### 4.3.3.27.3 Principle
- Resource configuration is:
  - part of application performance engineering,
not:
  - a permanent one-time guess.

#### 4.3.3.28 Decision Flow

##### 4.3.3.28.1 Right-Sizing Flow

```text
profile the bottleneck
→ measure memory / CPU / duration / dependency latency
→ test multiple resource configurations
→ compare performance + reliability + cost
→ select the smallest compliant configuration with headroom
→ revalidate after code/workload/dependency changes
```

#### 4.3.3.29 Evidence Pattern Summary

| Evidence | Correct sizing direction |
|---|---|
| Memory approaches configured maximum or invocation runs out of memory | Increase memory, then inspect allocation/buffering behavior |
| CPU-heavy code dominates duration while memory use is low | Test higher Lambda memory because CPU scales with memory |
| Trace shows downstream dependency consumes most execution time | Fix/investigate the dependency before adding Lambda compute |
| Very high configured memory, low actual memory use, no CPU pressure, lower settings still meet latency | Test lower memory for cost reduction |
| Function reaches timeout because CPU-bound work is slow | Profile and test more compute; timeout alone does not add resources |

The evidence identifies the constrained resource or dependency. Select the smallest configuration that still satisfies performance, reliability, and cost requirements.

#### 4.3.3.30 Common Exam Traps

##### 4.3.3.30.1 Minimum Memory = 128 MB
- False.
- Minimum means:
  - minimum sufficient for the workload.

##### 4.3.3.30.2 Memory Setting Controls Only RAM
- False for standard Lambda.
- It also controls:
  - proportional CPU allocation.

##### 4.3.3.30.3 Low Max Memory Used Means Reduce Memory
- Not necessarily.
- CPU requirements may:
  - justify the setting.

##### 4.3.3.30.4 Increase Timeout for CPU Bottleneck
- Wrong.
- Timeout:
  - permits longer execution.
- It does not:
  - add compute.

##### 4.3.3.30.5 Increase Concurrency to Make One Invocation Faster
- Wrong.
- Concurrency:
  - controls simultaneous work.
- It does not:
  - increase one invocation's CPU.

##### 4.3.3.30.6 Highest Memory Is Always Fastest and Best
- Wrong.
- Additional resources can:
  - reach diminishing returns.
- Optimize:
  - required performance against cost.

##### 4.3.3.30.7 Average Input Is Enough for Sizing
- Wrong.
- Include:
  - realistic upper-bound inputs.

##### 4.3.3.30.8 More Lambda CPU Fixes Slow External API
- Usually wrong.
- Profile:
  - dependency latency first.

##### 4.3.3.30.9 One-Time Sizing Is Permanent
- Wrong.
- Code/workload changes:
  - can change the optimum.

##### 4.3.3.30.10 Power Tuning Is Only a Cost Tool
- Wrong.
- It compares:
  - memory,
  - performance,
  - cost.

#### 4.3.3.34 Exam-Level Knowledge Frame

##### 4.3.3.34.1 Know These Cold

**Lambda standard memory range**
→ 128 MB–10,240 MB in 1 MB increments.

**Lambda CPU**
→ scales proportionally with configured memory.

**1 vCPU reference**
→ approximately equivalent to one vCPU at 1,769 MB.

**`Max Memory Used`**
→ evidence of actual per-invocation memory usage.

**CPU-bound Lambda**
→ higher memory can improve performance even if RAM is not exhausted.

**Memory-bound Lambda**
→ increase memory and investigate memory behavior.

**I/O-bound Lambda**
→ identify whether wait is local resource capacity or downstream latency.

**Timeout**
→ execution limit, not additional compute.

**Concurrency**
→ simultaneous work, not per-invocation CPU.

**Lambda Power Tuning**
→ experimentally compare memory settings for cost/performance.

**Compute Optimizer**
→ recommendations for eligible Lambda memory configurations.

##### 4.3.3.34.2 Fastest Exam Discriminator

```text
What is actually constrained?
```

`Memory near limit?`
→ more memory / optimize memory behavior.

`CPU-bound?`
→ test more Lambda memory because CPU scales with it.

`Slow dependency?`
→ fix/investigate dependency, not blindly add compute.

`Need optimum Lambda memory?`
→ benchmark multiple settings / Lambda Power Tuning.

`Need AWS-generated memory recommendation?`
→ Compute Optimizer where eligible.

##### 4.3.3.34.3 Final Principle
- **The minimum resource configuration is not the lowest number the platform allows; it is the smallest configuration that reliably meets the workload's performance requirements. For standard Lambda, memory is also the primary compute lever because CPU scales with memory, so right-size by measuring real workloads across configurations and comparing performance, memory use, and cost.**
