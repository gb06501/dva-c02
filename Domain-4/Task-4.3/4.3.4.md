### 4.3.4 Use subscription filter policies to optimize messaging

#### 4.3.4.1 Exam and Task Context

##### 4.3.4.1.1 Domain
- **Domain 4:** Troubleshooting and Optimization.

##### 4.3.4.1.2 Task
- **Task 4.3:** Optimize applications by using AWS services and features.

##### 4.3.4.1.3 Skill
- **Skill 4.3.4:** **Use subscription filter policies to optimize messaging.**

##### 4.3.4.1.4 Position Inside Task 4.3
- 4.3.1:
  - define concurrency.
- 4.3.2:
  - profile application performance.
- 4.3.3:
  - determine sufficient memory and compute.
- 4.3.4:
  - reduce unnecessary message delivery and subscriber processing by routing only relevant messages.

##### 4.3.4.1.5 Core Question
- **How can one publisher send different categories of events through an SNS topic while each subscriber receives only the events it needs?**

---

#### 4.3.4.2 Core Mental Model

##### 4.3.4.2.1 Without Filtering

```text
Publisher
   |
   v
SNS topic
   |
   +----> Subscriber A → receives everything → filters in code
   |
   +----> Subscriber B → receives everything → filters in code
   |
   '----> Subscriber C → receives everything → filters in code
```

- Consequences:
  - unnecessary deliveries,
  - unnecessary Lambda invocations,
  - unnecessary SQS messages,
  - subscriber-side filtering logic,
  - wasted compute and downstream work.

##### 4.3.4.2.2 With Subscription Filtering

```text
Publisher
   |
   v
SNS topic
   |
   +----> Subscription A [filter: order-created]
   |                         |
   |                         v
   |                    Subscriber A
   |
   +----> Subscription B [filter: order-cancelled]
   |                         |
   |                         v
   |                    Subscriber B
   |
   '----> Subscription C [filter: high-value]
                             |
                             v
                        Subscriber C
```

##### 4.3.4.2.3 Optimization Principle
- Let SNS:
  - evaluate routing criteria,
  - suppress irrelevant deliveries.
- Do not make every consumer:
  - receive every message,
  - deserialize it,
  - inspect it,
  - discard most of it.

##### 4.3.4.2.4 Key Architectural Idea
- The filter belongs to:
  - the **subscription**.
- Therefore:
  - different subscribers to the same topic can define different interests.

---

#### 4.3.4.3 Default SNS Fanout Behavior

##### 4.3.4.3.1 No Filter Policy
- By default:
  - a topic subscriber receives every message published to the topic.

##### 4.3.4.3.2 Subscriber-Specific Filtering
- To receive only a subset:
  - assign a filter policy to that subscription.

##### 4.3.4.3.3 Important Distinction
- Filter policy is not:
  - a topic-wide rule.
- It is:
  - a subscription attribute.

##### 4.3.4.3.4 Consequence
- One topic can support:
  - many consumers,
  - each with different filtering criteria.

---

#### 4.3.4.4 Subscription Filter Policy

##### 4.3.4.4.1 Definition
- A filter policy is:
  - a JSON object,
  - containing properties that define which messages a subscription receives.

##### 4.3.4.4.2 Evaluation
- SNS evaluates:
  - the configured policy
against:
  - message attributes,
  - or message-body properties,
depending on:
  - `FilterPolicyScope`.

##### 4.3.4.4.3 Match
- If the message satisfies:
  - the subscription's filter conditions,
then:
  - SNS delivers the message to that subscriber.

##### 4.3.4.4.4 No Match
- If it does not satisfy:
  - the filter policy,
then:
  - SNS does not deliver that message to that subscription.

---

#### 4.3.4.5 FilterPolicyScope

##### 4.3.4.5.1 Two Scopes
- `MessageAttributes`
- `MessageBody`

##### 4.3.4.5.2 Default
- If an existing filter policy has no explicit scope:
  - the scope defaults to `MessageAttributes`.

##### 4.3.4.5.3 Decision

```text
Routing metadata already exists as SNS message attributes?
→ MessageAttributes

Routing fields are inside JSON payload?
→ MessageBody
```

---

#### 4.3.4.6 Attribute-Based Filtering

##### 4.3.4.6.1 Scope

```text
FilterPolicyScope = MessageAttributes
```

##### 4.3.4.6.2 Example Message
- Message attributes:

```text
eventType = "OrderCreated"
region    = "eu"
priority  = "high"
```

##### 4.3.4.6.3 Example Policy

```json
{
  "eventType": ["OrderCreated"],
  "region": ["eu"]
}
```

##### 4.3.4.6.4 Result
- Subscriber receives:
  - matching `OrderCreated` events from `eu`.
- It does not receive:
  - messages failing one of the required policy properties.

---

#### 4.3.4.7 Payload-Based Filtering

##### 4.3.4.7.1 Scope

```text
FilterPolicyScope = MessageBody
```

##### 4.3.4.7.2 Requirement
- For payload-based filtering:
  - the message body must be a well-formed JSON object.

##### 4.3.4.7.3 Example Message

```json
{
  "eventType": "OrderCreated",
  "customer": {
    "tier": "gold"
  },
  "amount": 250
}
```

##### 4.3.4.7.4 Example Policy

```json
{
  "eventType": ["OrderCreated"],
  "customer": {
    "tier": ["gold"]
  }
}
```

##### 4.3.4.7.5 Benefit
- Routing fields can remain:
  - in the application event payload.
- Publisher does not necessarily need:
  - duplicate SNS message attributes solely for filtering.

---

#### 4.3.4.8 Message Attributes vs Message Body

##### 4.3.4.8.1 MessageAttributes
- Best when:
  - routing metadata is explicitly separated from payload.
- Default filtering scope.
- Attribute-based policies:
  - do not support nested filter policies.

##### 4.3.4.8.2 MessageBody
- Best when:
  - routing information already exists in JSON payload.
- Supports:
  - nested filtering.

##### 4.3.4.8.3 Exam Distinction

```text
nested JSON field must be filtered
→ MessageBody

SNS metadata attribute must be filtered
→ MessageAttributes
```

---

#### 4.3.4.9 Matching Across Policy Keys

##### 4.3.4.9.1 AND Across Keys
- Different property names in a filter policy:
  - must all match.

Example:

```json
{
  "event": ["order_placed"],
  "region": ["eu"]
}
```

means:

```text
event matches
AND
region matches
```

##### 4.3.4.9.2 Failure of One Required Key
- If:
  - one required property does not match,
then:
  - the subscription rejects the message.

##### 4.3.4.9.3 Missing Required Property
- If a policy requires a property:
  - and the evaluated message does not contain it,
the message:
  - does not match.

---

#### 4.3.4.10 Matching Within a Value Array

##### 4.3.4.10.1 OR Within Values
- Multiple values for one key:
  - represent alternatives.

```json
{
  "event": [
    "order_placed",
    "order_updated"
  ]
}
```

means:

```text
event = order_placed
OR
event = order_updated
```

##### 4.3.4.10.2 Combined Logic

```json
{
  "event": ["order_placed", "order_updated"],
  "region": ["eu", "us"]
}
```

Conceptually:

```text
(event = order_placed OR order_updated)
AND
(region = eu OR us)
```

---

#### 4.3.4.11 Filter Operators

SNS filter policies support several matching operators. The exam-relevant decision is to recognize what each operator expresses rather than memorize large example payloads.

| Requirement | Operator / pattern |
|---|---|
| Exact allowed value | exact string/value match |
| Any of several allowed values | multiple values in one key array → OR |
| Several independent properties must match | different policy keys → AND |
| Value must not match specified value(s) | `anything-but` |
| String starts with text | `prefix` |
| String ends with text | `suffix` |
| Numeric comparison or range | `numeric` |
| Property must exist or be absent | `exists` |
| Additional string matching where supported | SNS string operators such as case-insensitive/wildcard matching |

Example:

```json
{
  "eventType": ["ORDER_CREATED", "ORDER_UPDATED"],
  "region": ["eu-central-1"]
}
```

Meaning:

```text
eventType
→ ORDER_CREATED OR ORDER_UPDATED

AND

region
→ eu-central-1
```

For body-based filtering, the same selection principle applies to JSON payload properties, including nested properties where supported.

#### 4.3.4.12 Filter at the Earliest Appropriate Layer

##### 4.3.4.12.1 Weak Pattern

```text
SNS
→ subscriber
→ deserialize
→ inspect event
→ discard
```

##### 4.3.4.12.2 Better Pattern

```text
SNS
→ evaluate subscription filter
→ deliver only relevant events
```

##### 4.3.4.12.3 Why
- Avoid:
  - unnecessary data movement,
  - unnecessary compute,
  - unnecessary subscriber complexity.

---

#### 4.3.4.13 Publisher and Subscriber Responsibilities

##### 4.3.4.13.1 Publisher
- Publishes:
  - message body,
  - and/or routing attributes.

##### 4.3.4.13.2 SNS Subscription
- Defines:
  - subscriber-specific interest.

##### 4.3.4.13.3 Subscriber
- Processes:
  - messages already selected for it.

##### 4.3.4.13.4 Architectural Benefit
- Publisher does not need:
  - detailed knowledge of every consumer's filtering rules.

---

#### 4.3.4.14 Filtering Does Not Transform the Message

##### 4.3.4.14.1 Purpose
- SNS filtering determines:

```text
deliver?
or
do not deliver?
```

##### 4.3.4.14.2 It Does Not Mean
- rewrite payload,
- map schema,
- enrich data,
- transform event.

##### 4.3.4.14.3 Exam Trap
- If requirement is:
  - transform message content,
then:
  - subscription filter policy alone is not the solution.

---

#### 4.3.4.15 Filtering Does Not Replace Authorization

##### 4.3.4.15.1 Filter Policy
- Controls:
  - message selection for a subscription.

##### 4.3.4.15.2 IAM / Resource Policies
- Control:
  - who can publish,
  - subscribe,
  - modify resources,
  - perform AWS API actions.

##### 4.3.4.15.3 Principle

```text
filter policy
≠ security authorization policy
```

---

#### 4.3.4.16 Filtering Does Not Replace Delivery Reliability

##### 4.3.4.16.1 Filter Match
- Answers:
  - should this message be delivered to this subscription?

##### 4.3.4.16.2 Delivery Failure
- Happens after:
  - a message was selected for delivery,
but:
  - endpoint delivery fails.

##### 4.3.4.16.3 Different Mechanisms
- Filtering:
  - selection/routing.
- Retry policy / DLQ:
  - delivery-failure handling.

---

#### 4.3.4.17 Raw Message Delivery

##### 4.3.4.17.1 Distinction
- Raw message delivery:
  - changes how the delivered payload is wrapped/formatted.

##### 4.3.4.17.2 Filter Policy
- Determines:
  - whether delivery occurs.

##### 4.3.4.17.3 AWS Documentation
- Raw message delivery:
  - is not required for subscription filtering.

##### 4.3.4.17.4 Exam Trap

```text
Need SNS filtering
→ enable RawMessageDelivery
```

- Wrong.
- Configure:
  - `FilterPolicy`,
  - and optionally `FilterPolicyScope`.

#### 4.3.4.20 Removing a Filter Policy

##### 4.3.4.20.1 Empty Policy
- AWS documents removing filtering by setting:

```json
{}
```

##### 4.3.4.20.2 Result
- Subscription again accepts:
  - every message published to the topic.

##### 4.3.4.20.3 Important Distinction
- Empty filter policy:

```text
{}
```

means:
  - no filtering,
not:
  - reject all messages.

#### 4.3.4.12 Eventual Consistency

##### 4.3.4.12.1 AWS Behavior
- SNS uses:
  - a distributed model.
- Additions or changes to filter policies:
  - can take up to **15 minutes** to fully take effect.

##### 4.3.4.12.2 Operational Consequence
- Immediately after changing a policy:
  - observed delivery may not yet fully reflect the new configuration.

##### 4.3.4.12.3 Exam/Troubleshooting Trap
- Do not immediately conclude:
  - policy syntax is wrong
only because:
  - behavior has not changed everywhere instantly.

---

#### 4.3.4.13 Filter Policy Constraints

##### 4.3.4.13.1 Maximum Keys
- Current SNS documentation:
  - maximum **5 keys** in a filter policy.

##### 4.3.4.13.2 Maximum Combinations
- Current documented total combinations:
  - maximum **150**.

##### 4.3.4.13.3 Maximum Size
- Current maximum filter policy size:
  - **256 KB**.

##### 4.3.4.13.4 Why It Matters
- Filter policies are intended for:
  - routing criteria,
not:
  - arbitrary complex business-rule engines.

---

#### 4.3.4.14 Attribute-Based Constraints

##### 4.3.4.14.1 No Nested Policy
- `MessageAttributes` filtering:
  - does not support nested filter policies.

##### 4.3.4.14.2 Supported Attribute Types
- Current SNS documentation supports filtering on relevant message attributes including:
  - `String`,
  - `String.Array`,
  - numeric values for numeric matching.

##### 4.3.4.14.3 Binary
- Binary message attributes:
  - are ignored for filtering.

##### 4.3.4.14.4 Nested Requirement
- If filtering must navigate:
  - nested JSON,
use:
  - `MessageBody`.

---

#### 4.3.4.15 Payload-Based Constraints

##### 4.3.4.15.1 JSON Requirement
- Message body:
  - must be a valid JSON object for payload-based filtering.

##### 4.3.4.15.2 Nested Policies
- Payload-based filtering:
  - supports nested policies.

##### 4.3.4.15.3 Key Counting
- For nested payload policies:
  - AWS counts leaf keys toward the key limit.

#### 4.3.4.16 Filter Policy Design

##### 4.3.4.16.1 Stable Routing Fields
- Prefer fields such as:
  - event type,
  - region,
  - category,
  - state,
  - priority,
  - business domain.

##### 4.3.4.16.2 Avoid Over-Specific Filters
- Extremely detailed policies:
  - become hard to maintain,
  - can hit policy complexity limits.

##### 4.3.4.16.3 Event Contract
- Subscribers depend on:
  - routing fields remaining stable.
- Treat filtering fields as:
  - part of the event contract.

#### 4.3.4.17 Filter Policy and Event Evolution

##### 4.3.4.17.1 Risk
- Producer renames:

```text
eventType
→ event_type
```

- Existing subscriptions:
  - may stop matching.

##### 4.3.4.17.2 Consequence
- Message-schema evolution can affect:
  - routing behavior.

##### 4.3.4.17.3 Principle
- Version/change routing fields:
  - deliberately.

#### 4.3.4.18 Filter Policy and Loose Coupling

##### 4.3.4.18.1 Publisher
- Publishes:
  - an event.

##### 4.3.4.18.2 Subscribers
- Independently define:
  - which events they need.

##### 4.3.4.18.3 Benefit
- New subscriber can often be added:
  - without changing publisher code.

##### 4.3.4.18.4 Optimization
- Loose coupling:
  - plus server-side filtering
reduces:
  - publisher branching,
  - consumer waste.

#### 4.3.4.19 Standard and FIFO Topics

##### 4.3.4.19.1 SNS FIFO
- Current AWS documentation:
  - SNS FIFO topics support message filtering.

##### 4.3.4.19.2 FIFO Fanout
- SQS FIFO or standard queues can subscribe:
  - according to supported SNS FIFO subscription behavior.
- Each subscription can:
  - define its own filter.

##### 4.3.4.19.3 Important Warning
- AWS documents that applying message filtering to SNS FIFO topics:
  - changes the effective delivery semantics from exactly-once to at-most-once for filtered delivery scenarios.

##### 4.3.4.19.4 Exam Principle
- Filtering:
  - affects which messages are intentionally delivered.
- Do not assume:
  - FIFO semantics make every filtered-out message appear downstream.

##### 4.3.4.20.1 Without Filtering

#### 4.3.4.13 Practical Pattern Summary

| Requirement | Best fit |
|---|---|
| One topic carries multiple event types; each subscriber needs only some | SNS subscription filter policy |
| Routing data already exists in SNS message attributes | `FilterPolicyScope=MessageAttributes` |
| Routing data exists inside JSON message body | `FilterPolicyScope=MessageBody` |
| Need nested JSON filtering | `MessageBody` |
| Need high-value orders only | numeric filter |
| Need everything except one category | `anything-but` |
| Consumer receives everything and discards most | move selection to SNS subscription filter |
| Need message transformation | filter policy is insufficient |
| Need authorization/security isolation | IAM/resource policy, not filter policy |

#### 4.3.4.14 Common Exam Traps

##### 4.3.4.14.1 Filter in Every Consumer
- Usually inefficient when:
  - SNS can perform the routing.

##### 4.3.4.14.2 Filter Policy Is Topic-Wide
- False.
- It belongs to:
  - each subscription.

##### 4.3.4.14.3 MessageBody Is the Default Scope
- False.
- Default:
  - `MessageAttributes`.

##### 4.3.4.14.4 Attribute Filters Support Nested JSON
- False.
- Use:
  - payload-based `MessageBody` filtering for nested policies.

##### 4.3.4.14.5 Filter Policy Transforms Payload
- False.
- It decides:
  - deliver/not deliver.

##### 4.3.4.14.6 Filter Policy Is IAM Authorization
- False.
- It is:
  - message-routing logic.

##### 4.3.4.14.7 Raw Message Delivery Is Required
- False.
- Raw delivery:
  - is independent of filter functionality.

##### 4.3.4.14.8 Empty Filter Rejects Everything
- False.
- `{}` removes filtering:
  - subscriber receives all topic messages.

##### 4.3.4.14.9 Policy Changes Are Instant Everywhere
- False.
- AWS documents:
  - up to 15 minutes for changes to fully take effect.

##### 4.3.4.14.10 Same Key Values Are AND
- False.
- Alternatives within a value array:
  - are OR-like matches.
- Different required keys:
  - combine as AND.

#### 4.3.4.18 Exam-Level Knowledge Frame

##### 4.3.4.18.1 Subscription Filter Policy
- JSON rule attached to:
  - an SNS subscription.
- Determines:
  - which topic messages that subscriber receives.

##### 4.3.4.18.2 Default
- No filter:
  - subscriber receives all topic messages.

##### 4.3.4.18.3 FilterPolicyScope

```text
MessageAttributes
→ default
→ filter SNS message attributes

MessageBody
→ filter JSON payload
→ supports nested policies
```

##### 4.3.4.18.4 Logic

```text
different keys
→ AND

multiple alternatives for one key
→ OR
```

##### 4.3.4.18.5 Optimization
- Filter before subscriber processing:
  - fewer unnecessary deliveries,
  - fewer Lambda invocations,
  - fewer irrelevant queue messages,
  - less application-side filtering.

##### 4.3.4.18.6 Operational Detail
- Policy changes:
  - can require up to 15 minutes to fully take effect.

##### 4.3.4.18.7 Fastest Exam Discriminator

```text
One SNS topic
+
subscribers need different subsets
→ subscription filter policies

routing data in SNS attributes
→ MessageAttributes

routing data in JSON body
→ MessageBody

nested JSON
→ MessageBody

subscriber receives everything and discards most
→ move filtering to SNS

need transform payload
→ filter policy is not enough

need authorization
→ IAM/resource policy, not filter policy
```

##### 4.3.4.18.8 Final Principle
- **Amazon SNS subscription filter policies optimize fanout by moving message-selection logic from subscribers into the messaging layer: each subscription declares the events it needs, SNS evaluates either message attributes or JSON message-body properties, and nonmatching messages are not delivered to that subscriber.**
