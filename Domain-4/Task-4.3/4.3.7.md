#### 4.3.7.2 Core Mental Model

##### 4.3.7.2.1 Resource Optimization Is Not "Use the Smallest"
- The goal is not:
  - minimum memory,
  - minimum concurrency,
  - minimum database capacity
at all costs.
- The goal is:
  - the most efficient resource configuration that still satisfies workload requirements.

##### 4.3.7.2.2 Optimization Loop

```text
measure
  |
  v
identify waste / bottleneck
  |
  v
change one relevant resource or behavior
  |
  v
measure again
  |
  v
compare latency + throughput + errors + cost
```

##### 4.3.7.2.3 Core Principle
- **Right-size from evidence, not assumptions.**

#### 4.3.7.5 Lambda Resource Optimization

##### 4.3.7.5.1 Memory and CPU Coupling
Standard Lambda functions allow:

```text
128 MB → 10,240 MB
```

CPU allocation increases proportionally with configured memory.

Therefore:

```text
increase memory
→ more memory
+
more CPU
```

A CPU-bound function may become:
- faster,
- potentially cheaper overall

at a higher memory setting because execution duration can fall.

Use:
- `Duration`,
- `Billed Duration`,
- `Memory Size`,
- `Max Memory Used`

to evaluate actual behavior.

Do not assume:

```text
low Max Memory Used
→ lower memory is automatically better
```

because CPU demand can still justify a larger allocation.

##### 4.3.7.5.2 Lambda Power Tuning
AWS Lambda Power Tuning:
- uses Step Functions,
- invokes the function at multiple memory settings,
- compares performance and cost.

Use when:

```text
need evidence-based Lambda memory/cost optimum
→ Lambda Power Tuning
```

##### 4.3.7.5.3 Execution-Environment Reuse
Initialize reusable resources outside the handler where appropriate:
- AWS SDK clients,
- database connections,
- reusable static resources.

Warm execution environments can reuse them.

Benefits:
- less setup work,
- fewer repeated network operations,
- lower duration.

Persistent connections:
- should use keep-alive where appropriate,
- must tolerate stale/closed connections.

Do not use execution-environment reuse as:
- shared durable state.

##### 4.3.7.5.4 Recursive Invocation Protection
Unintended recursive Lambda invocations can multiply:
- invocation count,
- concurrency,
- cost.

AWS emergency mitigation:

```text
reserved concurrency = 0
```

to stop new executions while correcting the loop.

##### 4.3.7.5.5 Concurrency Controls
Reserved concurrency:

```text
capacity allocation
+
maximum function concurrency
```

Use it to:
- protect critical functions,
- protect slower downstream services.

Provisioned concurrency:

```text
pre-initialized execution environments
→ lower cold-start latency
```

It:
- is not a resource-efficiency mechanism by itself,
- incurs additional cost.

##### 4.3.7.5.6 Timeout
Timeout should match:
- measured normal behavior,
- realistic upper-bound execution time.

Too long:
- failed work consumes resources longer than necessary.

Too short:
- valid work is terminated,
- retries/duplicate work can increase.

##### 4.3.7.5.7 Retry Efficiency
For transient failures use:
- bounded retries,
- exponential backoff,
- jitter.

Avoid:

```text
dependency throttles
→ immediate synchronized retries
→ more load
→ more throttling
```

The optimization target is:
- less useless repeated work.

#### 4.3.7.6 DynamoDB Resource Optimization

##### 4.3.7.6.1 Capacity Modes

```text
unpredictable / variable / bursty traffic
→ on-demand often fits

steady / predictable traffic
→ provisioned can fit
```

Current AWS guidance positions on-demand as:
- the default and recommended throughput option for most workloads.

On-demand:
- removes manual capacity planning,
- bills per request.

Provisioned:
- configures read/write capacity,
- can be more efficient for predictable usage,
- risks throttling when too low,
- wastes money when too high.

##### 4.3.7.6.2 DynamoDB Auto Scaling
For provisioned capacity, auto scaling can manage:
- minimum capacity,
- maximum capacity,
- target utilization.

Purpose:

```text
reduce throttling
+
reduce unused provisioned capacity
```

##### 4.3.7.6.3 Read Efficiency
Prefer:
- targeted key-based access patterns,
- retrieving only required data.

Avoid:

```text
read large result
→ discard most of it in application
```

because this wastes:
- database throughput,
- network,
- memory,
- CPU.

---

#### 4.3.7.7 Remove Unnecessary Work

Resource optimization is often more effective when unnecessary work is removed before adding capacity.

##### 4.3.7.7.1 Payload Efficiency
Large payloads consume:
- network,
- serialization/deserialization CPU,
- memory,
- execution time.

Prefer:
- only required fields,
- fewer redundant transformations,
- fewer repeated transfers.

##### 4.3.7.7.2 Batching
Batching can reduce:
- network round trips,
- API calls,
- repeated fixed overhead.

Tradeoffs:
- more memory per batch,
- larger per-batch latency,
- more complex partial failure handling.

##### 4.3.7.7.3 Event Filtering
Avoid invoking expensive application code for events that are immediately discarded.

Where AWS integrations support it:

```text
filter before processing
→ fewer invocations
→ less compute
→ fewer downstream calls
```

SNS subscription filtering is covered in:
- 4.3.4.

##### 4.3.7.7.4 Caching and Reuse
Repeated database reads, API calls, or computations can sometimes be replaced with:
- caching,
- local reuse,
- connection reuse.

Detailed caching:
- belongs to 4.3.6.

##### 4.3.7.7.5 Observability Overhead
Observability should not dominate application work.

Examples:
- prefer EMF over synchronous metric API calls where appropriate,
- use useful structured logs rather than uncontrolled verbosity,
- apply sensible retention.

##### 4.3.7.7.6 Storage and Retention
Do not retain:
- temporary,
- duplicate,
- obsolete

data indefinitely.

Use lifecycle/retention policies according to:
- business,
- operational,
- compliance

requirements.

#### 4.3.7.8 Optimization Method

##### 4.3.7.8.1 Bottleneck vs Waste

```text
too little resource
→ performance/reliability problem

too much resource
→ cost without useful benefit
```

Target:

```text
efficient operating range
```

##### 4.3.7.8.2 Measure Before Optimizing
Use evidence from:
- CloudWatch metrics,
- Lambda REPORT logs,
- application logs,
- traces,
- profiling,
- load tests.

Ask:
- CPU-bound?
- memory-bound?
- network-bound?
- database-bound?
- downstream throttled?
- too much concurrency?
- repeated work?
- oversized resource?

##### 4.3.7.8.3 Load Test
Validate under:
- realistic request rates,
- concurrency,
- data volume,
- dependency behavior.

Measure:
- latency,
- throughput,
- errors,
- throttles,
- utilization,
- downstream effects,
- cost.

##### 4.3.7.8.4 End-to-End Optimization
A local improvement can harm the system.

Example:

```text
Lambda concurrency ↑
→ function throughput ↑
→ DB connection limit exceeded
→ system reliability ↓
```

Optimize:
- the complete request path,
not:
- one component in isolation.

##### 4.3.7.8.5 Order of Operations

```text
measure
→ identify bottleneck/waste
→ remove unnecessary work
→ right-size
→ scale only when needed
→ load test
→ measure again
```

##### 4.3.7.8.6 Practical Pattern Summary

| Observation | Best direction |
|---|---|
| CPU-bound Lambda | Test more memory / optimize code |
| Lambda memory clearly over-provisioned | Test lower memory |
| Lambda overwhelms backend | Bound concurrency |
| Need lower cold-start latency | Consider provisioned concurrency |
| Clients/connections recreated each invocation | Reuse execution environment |
| Unpredictable DynamoDB traffic | On-demand |
| Predictable DynamoDB traffic | Provisioned + auto scaling |
| Repeated expensive work | Cache / batch / filter / reuse |
| Dependency throttling | Backoff + jitter + capacity/concurrency control |
| Excess data fetched | Retrieve only required fields |

#### 4.3.7.9 Common Exam Traps

##### 4.3.7.9.1 Always Choose Minimum Lambda Memory
- Wrong.
- Lower memory also means:
  - less CPU.

##### 4.3.7.9.2 Always Choose Maximum Lambda Memory
- Wrong.
- Benchmark:
  - cost/performance.

##### 4.3.7.9.3 Scale Lambda Without Considering Dependencies
- Wrong.
- Downstream:
  - may become bottleneck.

##### 4.3.7.9.4 Provisioned Concurrency Saves Resources
- Not necessarily.
- It primarily:
  - reduces startup latency,
  - incurs additional cost.

##### 4.3.7.9.5 Provisioned and Reserved Concurrency Are the Same
- Wrong.
- They solve:
  - different problems.

##### 4.3.7.9.6 Provisioned DynamoDB Capacity for Highly Unpredictable Workload
- Often inferior to:
  - on-demand
when capacity cannot be predicted efficiently.

##### 4.3.7.9.7 On-Demand Is Always Cheapest
- Wrong.
- Workload pattern:
  - matters.

##### 4.3.7.9.8 Increase Capacity Before Removing Waste
- Wrong.
- First determine:
  - why resources are consumed.

##### 4.3.7.9.9 Ignore Max Memory Used
- Wrong.
- It is:
  - an important Lambda right-sizing signal.

##### 4.3.7.9.10 Optimize One Service in Isolation
- Wrong.
- Evaluate:
  - end-to-end effects.

#### 4.3.7.12 Exam-Level Knowledge Frame

##### 4.3.7.12.1 Core Rule

```text
measure
→ identify constrained/wasted resource
→ remove unnecessary work
→ right-size
→ load test
→ measure again
```

##### 4.3.7.12.2 Lambda Rule

```text
Lambda memory ↑
→ memory ↑
→ CPU ↑

therefore:
memory setting
is also a compute-performance setting
```

##### 4.3.7.12.3 Concurrency Rule

```text
application can scale faster than dependency
→ bound concurrency to protect dependency
```

##### 4.3.7.12.4 DynamoDB Rule

```text
unpredictable traffic
→ on-demand

predictable traffic
→ provisioned may fit
→ auto scaling can adjust capacity
```

##### 4.3.7.12.5 Waste-Removal Rule

```text
repeated work
→ cache / reuse

irrelevant work
→ filter

excess round trips
→ batch / reuse connections

oversized resource
→ right-size
```

##### 4.3.7.12.6 Fastest Exam Discriminator

```text
Lambda CPU-bound
→ test more memory

find best Lambda memory/cost point
→ Lambda Power Tuning

Lambda overwhelms DB
→ reserved concurrency / bound concurrency

cold-start latency requirement
→ provisioned concurrency

unpredictable DynamoDB traffic
→ on-demand

steady predictable DynamoDB traffic
→ provisioned + auto scaling

repeated client initialization
→ initialize outside handler
```

##### 4.3.7.12.7 Final Principle
- **Optimize application resources by measuring actual workload behavior, eliminating unnecessary work, right-sizing resources, and respecting end-to-end capacity constraints. The cheapest or smallest configuration is not automatically the most efficient configuration.**
