### 4.3.2 Profile application performance

#### 4.3.2.1 Exam and Task Context

##### 4.3.2.1.1 Domain
- Domain 4 is **Troubleshooting and Optimization**.
- Task 4.3 is **Optimize applications by using AWS services and features**.
- Skill 4.3.2 is **Profile application performance**.

##### 4.3.2.1.2 Position Inside Task 4.3
- 4.3.1 established **concurrency**:
  - how much work is simultaneously in progress,
  - how Lambda concurrency can be controlled,
  - why downstream capacity matters.
- 4.3.2 now asks:

  **Where does the application actually spend time and resources, and which component or code path is responsible for poor performance?**

- Later Task 4.3 skills continue toward:
  - 4.3.3 → minimum memory and compute power,
  - 4.3.4 → messaging optimization with subscription filter policies,
  - 4.3.5 → request-header-based caching,
  - 4.3.6 → application-level caching,
  - 4.3.7 → resource-usage optimization,
  - 4.3.8 → analysis of application performance issues,
  - 4.3.9 → using application logs to identify bottlenecks.
- Therefore 4.3.2 should focus on **measurement and profiling**, not prematurely jump to a specific optimization.

##### 4.3.2.1.3 Core Question
- **Which part of the application consumes the time or resource that limits performance?**

#### 4.3.2.2 Core Mental Model

##### 4.3.2.2.1 Profile Before Optimizing
- Performance optimization should begin with evidence.
- A useful sequence is:

  `observe symptom`
  → `measure`
  → `localize bottleneck`
  → `identify cause`
  → `change`
  → `measure again`

- Do not begin with:

  `application is slow`
  → `increase everything`

##### 4.3.2.2.2 Profiling
- Profiling examines how an application behaves while it runs.
- Depending on the tool and workload, profiling can reveal:
  - where execution time is spent,
  - which functions/methods consume CPU,
  - memory usage,
  - runtime behavior,
  - slow dependencies,
  - initialization overhead,
  - request-path latency.

##### 4.3.2.2.3 Bottleneck
- A bottleneck is the component that constrains application performance.
- Examples:
  - CPU-heavy code,
  - memory pressure,
  - repeated serialization,
  - slow database call,
  - slow downstream API,
  - excessive network activity,
  - Lambda initialization,
  - inefficient algorithm.

##### 4.3.2.2.4 Essential Principle
- **Measure the workload before deciding what to optimize.**

#### 4.3.2.3 Performance Dimensions

##### 4.3.2.3.1 Latency
- Time required to complete an operation.
- Example:
  - API request takes 800 ms.

##### 4.3.2.3.2 Throughput
- Amount of work completed per unit time.
- Example:
  - 500 requests/second.

##### 4.3.2.3.3 Resource Utilization
- How much compute/runtime capacity the application consumes.
- Relevant examples:
  - CPU,
  - memory,
  - network,
  - disk,
  - connections.

##### 4.3.2.3.4 Error and Fault Rate
- Performance analysis should not look at latency alone.
- A system that responds quickly because requests are failing is not healthy.
- Correlate:
  - latency,
  - errors,
  - faults,
  - resource usage.

#### 4.3.2.4 Average vs Tail Latency

##### 4.3.2.4.1 Average Can Hide Problems
- Example:

  `average latency = 100 ms`

  does not prove:
  - most users receive 100 ms responses,
  - slow outliers do not exist.

##### 4.3.2.4.2 Percentiles
- Percentiles expose the distribution.
- Example:
  - p50 → median request,
  - p90 → 90% complete at or below this latency,
  - p99 → 99% complete at or below this latency.

##### 4.3.2.4.3 Exam Principle
- For user-facing performance:
  - tail latency can reveal problems hidden by averages.

#### 4.3.2.5 Profiling vs Monitoring vs Tracing

##### 4.3.2.5.1 Monitoring
- Answers questions such as:
  - Is latency increasing?
  - Is CPU high?
  - Is memory usage growing?
  - Are errors increasing?

##### 4.3.2.5.2 Tracing
- Follows an individual request through components.
- Helps answer:
  - **Which service/dependency added the latency?**

##### 4.3.2.5.3 Code Profiling
- Examines execution inside the application/runtime.
- Helps answer:
  - **Which method or code path consumes the CPU/time?**

##### 4.3.2.5.4 Logs
- Explain discrete application events and context.
- Useful for:
  - request timing,
  - dependency timing,
  - slow-operation context,
  - correlation IDs,
  - application-specific details.

##### 4.3.2.5.5 Critical Distinction
- `metrics` → **where/when is the symptom?**
- `traces` → **which distributed component contributes?**
- `profiler` → **which code path consumes runtime resources?**
- `logs` → **what happened around the operation?**

#### 4.3.2.6 Start with a Baseline

##### 4.3.2.6.1 Baseline
- A baseline is the known performance of the application under representative conditions.
- Useful measurements:
  - latency percentiles,
  - throughput,
  - error rate,
  - CPU,
  - memory,
  - Lambda duration,
  - cold-start behavior,
  - dependency latency.

##### 4.3.2.6.2 Why Baseline Matters
- Without a baseline, a later number such as:

  `duration = 600 ms`

  has little meaning.
- With a baseline:

  `before = 250 ms`
  → `after = 600 ms`

  indicates a measurable regression.

##### 4.3.2.6.3 Compare Like with Like
- Compare:
  - same workload,
  - similar traffic,
  - same data shape,
  - same runtime/configuration where possible.
- Otherwise:
  - apparent performance changes can be caused by different test conditions.

#### 4.3.2.7 Representative Workload

##### 4.3.2.7.1 Realistic Inputs
- Performance can vary with:
  - request size,
  - payload complexity,
  - data volume,
  - cache state,
  - concurrency,
  - dependency behavior.

##### 4.3.2.7.2 Warm vs Cold Behavior
- For Lambda, distinguish:
  - initialization,
  - warm invocation execution.
- A workload dominated by cold starts has a different optimization problem from:
  - a warm function with slow business logic.

##### 4.3.2.7.3 Load Matters
- A function may look fast:
  - under one request,
  but degrade:
  - under realistic concurrency.
- Profile under conditions representative of production behavior.

#### 4.3.2.8 Amazon CloudWatch as the Starting Point

##### 4.3.2.8.1 Purpose
- CloudWatch provides operational metrics, logs, dashboards, alarms, and application observability capabilities.
- Use it to identify:
  - which workload is slow,
  - when the degradation occurs,
  - whether it correlates with errors or resource usage.

##### 4.3.2.8.2 Narrow the Problem
- Example:

  `API latency increases`
  → identify affected service
  → inspect service/function metrics
  → inspect dependency latency/traces
  → inspect runtime metrics
  → profile code if required

##### 4.3.2.8.3 Do Not Guess from One Metric
- High duration can be caused by:
  - CPU,
  - memory/GC behavior,
  - downstream wait,
  - network,
  - initialization,
  - lock/contention,
  - retries.
- Correlation is required before remediation.

#### 4.3.2.9 CloudWatch Application Signals

##### 4.3.2.9.1 Purpose
- CloudWatch Application Signals provides an application-centric view of:
  - services,
  - operations,
  - dependencies,
  - application health and performance.

##### 4.3.2.9.2 Standard Application Signals
- Current AWS documentation describes standard application metrics including:
  - latency,
  - faults,
  - errors.
- Application Signals also provides:
  - call volume,
  - availability context,
  - service/dependency relationships.

##### 4.3.2.9.3 Runtime Metrics
- Application Signals can collect runtime metrics such as:
  - memory usage,
  - CPU usage,
  - garbage collection.
- These can be viewed in the context of service performance.

##### 4.3.2.9.4 Correlation
- Example:

  `latency spike`
  +
  `CPU spike at same time`

  suggests:
  - investigate CPU-intensive application behavior.

- Example:

  `latency spike`
  +
  `runtime resources normal`
  +
  `dependency latency high`

  suggests:
  - investigate downstream dependency.

##### 4.3.2.9.5 Application Map
- Application Signals can show relationships between:
  - services,
  - operations,
  - dependencies.
- This helps localize:
  - where a distributed performance problem is occurring.

#### 4.3.2.10 AWS X-Ray

##### 4.3.2.10.1 Purpose
- X-Ray trace data can visualize the components involved in a request.
- It helps identify:
  - performance bottlenecks,
  - latency spikes,
  - failing requests,
  - slow downstream calls.

##### 4.3.2.10.2 Trace Mental Model

  `client`
  → `API/service`
  → `Lambda`
  → `database`
  → `downstream API`

- A trace helps determine:
  - how total request time is distributed across these components.

##### 4.3.2.10.3 Service/Trace Map
- X-Ray can construct a service/trace map from trace data.
- Use it to see:
  - application components,
  - dependencies,
  - latency contribution,
  - errors/faults.

##### 4.3.2.10.4 Trace Detail
- A trace can show:
  - segments,
  - subsegments,
  - timing,
  - downstream calls.
- This is more useful than a single total-duration metric when:
  - the application spans multiple services.

#### 4.3.2.11 Trace the Critical Path

##### 4.3.2.11.1 Critical Path
- The critical path is the sequence of operations that determines end-to-end response time.

##### 4.3.2.11.2 Example

  `API Gateway: 20 ms`
  → `Lambda: 500 ms`
  → `DynamoDB: 15 ms`

- Primary investigation:
  - Lambda execution.

Another request:

  `API Gateway: 20 ms`
  → `Lambda: 500 ms`
     - `external API: 430 ms`

- Primary investigation:
  - downstream API latency,
  not necessarily Lambda CPU.

##### 4.3.2.11.3 Principle
- **Optimize the dominant contributor on the critical path.**

#### 4.3.2.12 CloudWatch Lambda Insights

##### 4.3.2.12.1 Purpose
- Lambda Insights is a monitoring and troubleshooting capability for Lambda.
- It collects and summarizes system-level runtime performance information.

##### 4.3.2.12.2 Runtime Information
- Current AWS documentation includes metrics/information for:
  - CPU time,
  - memory,
  - disk,
  - network,
  - cold starts,
  - worker shutdowns.

##### 4.3.2.12.3 Performance Event
- The Lambda Insights extension emits a performance log event for invocations.
- CloudWatch extracts metrics from these events by using embedded metric format.

##### 4.3.2.12.4 Useful Lambda Metrics
- Relevant Lambda Insights metrics include:
  - `cpu_total_time`,
  - `init_duration`,
  - `memory_utilization`,
  - `used_memory_max`,
  - network receive/transmit metrics.

##### 4.3.2.12.5 Diagnostic Use
- If Lambda duration increases:
  - check memory utilization,
  - check CPU time,
  - check initialization duration,
  - check network behavior,
  - correlate with traces/dependency timing.

#### 4.3.2.13 Lambda Duration Profiling

##### 4.3.2.13.1 Total Duration
- Lambda `Duration` tells you:
  - how long function execution takes.
- It does not by itself explain:
  - why execution took that long.

##### 4.3.2.13.2 Initialization
- Initialization time can contribute to startup latency.
- Lambda Insights `init_duration` can help distinguish:
  - initialization overhead,
  from:
  - handler/runtime work.

##### 4.3.2.13.3 Memory and CPU Relationship
- Lambda CPU capacity scales with configured memory.
- Therefore:
  - a CPU-bound function can sometimes become faster when memory is increased.
- Exact right-sizing belongs primarily to:
  - **4.3.3 Determine minimum memory and compute power for an application**.

##### 4.3.2.13.4 Skill Boundary
- 4.3.2:
  - identify the performance/resource pattern.
- 4.3.3:
  - choose appropriate memory/compute sizing.

#### 4.3.2.14 CPU-Bound Work

##### 4.3.2.14.1 Indicators
- High CPU time.
- Duration rises with CPU-intensive operations.
- Traces do not show a dominant downstream wait.
- Code profiler identifies hot methods.

##### 4.3.2.14.2 Examples
- compression,
- encryption,
- image transformation,
- large JSON processing,
- inefficient loops,
- expensive calculations.

##### 4.3.2.14.3 Investigation
- Profile:
  - hot code path,
  - algorithm,
  - serialization/deserialization,
  - repeated computation.

#### 4.3.2.15 Memory-Bound or Memory-Pressure Work

##### 4.3.2.15.1 Indicators
- High memory utilization.
- Memory approaches configured limit.
- Increased garbage collection/runtime overhead.
- Out-of-memory failures may occur at the extreme.

##### 4.3.2.15.2 Investigate
- large objects,
- unnecessary buffering,
- large payload materialization,
- retained references,
- caches,
- repeated allocations.

##### 4.3.2.15.3 Do Not Conclude Too Early
- High memory allocation does not automatically mean:
  - a memory leak.
- Profile over time and correlate with:
  - workload,
  - garbage collection,
  - retained memory.

#### 4.3.2.16 I/O-Bound Work

##### 4.3.2.16.1 Indicators
- CPU is not saturated.
- Total request duration is high.
- Traces show time waiting on:
  - database,
  - API,
  - storage,
  - network.

##### 4.3.2.16.2 Typical Cause
- The application spends most of its time:
  - waiting rather than computing.

##### 4.3.2.16.3 Optimization Direction
- Depending on the later analysis:
  - reduce calls,
  - parallelize independent I/O carefully,
  - cache appropriate results,
  - optimize data access,
  - fix downstream bottleneck.
- Profiling identifies:
  - which direction is justified.

#### 4.3.2.17 Dependency Latency

##### 4.3.2.17.1 Distributed Applications
- End-to-end latency may be dominated by:
  - another AWS service,
  - database,
  - third-party API,
  - internal microservice.

##### 4.3.2.17.2 Trace Evidence
- Example:

  `request total = 900 ms`
  - application code = 80 ms
  - downstream API = 760 ms

- Rewriting local code:
  - will not materially solve the primary bottleneck.

##### 4.3.2.17.3 Principle
- **Attribute latency before optimizing code.**

#### 4.3.2.18 Sequential vs Parallel Dependency Calls

##### 4.3.2.18.1 Sequential

  `call A: 200 ms`
  → `call B: 300 ms`
  → `call C: 150 ms`

- Approximate dependency path:
  - 650 ms.

##### 4.3.2.18.2 Independent Parallel Calls
- If calls are independent and safe to parallelize:
  - elapsed time may approach the slowest call rather than the sum.
- But parallelism can increase:
  - concurrency,
  - downstream load,
  - rate-limit pressure.

##### 4.3.2.18.3 Link to 4.3.1
- Profiling may show sequential I/O as a bottleneck.
- 4.3.1 reminds you:
  - increasing concurrency/parallelism is not free.

#### 4.3.2.19 Code-Level Profiling

##### 4.3.2.19.1 Purpose
- Code profiling identifies:
  - functions,
  - methods,
  - call stacks,
  - code paths
  that consume execution resources.

##### 4.3.2.19.2 Sampling Profiler
- A sampling profiler periodically samples execution.
- Over many samples:
  - frequently observed stack frames indicate where runtime time is concentrated.

##### 4.3.2.19.3 Benefit
- Lower instrumentation overhead than:
  - tracing every method invocation in many scenarios.
- Appropriate for:
  - identifying hot code paths.

#### 4.3.2.20 Amazon CodeGuru Profiler

##### 4.3.2.20.1 Purpose
- CodeGuru Profiler collects runtime profiling data from applications.
- AWS analyzes the data to provide:
  - visualizations,
  - flame graphs,
  - reports,
  - optimization recommendations.

##### 4.3.2.20.2 Profiling Group
- A profiling group groups application profiling data for analysis.

##### 4.3.2.20.3 Agent
- The profiling agent:
  - collects runtime data from the application,
  - sends profiling information for analysis.

##### 4.3.2.20.4 Lambda
- AWS documentation includes CodeGuru Profiler integration for supported Lambda runtime scenarios.
- For short-running Lambda functions:
  - enough invocations/samples are needed to build useful profiling data.

##### 4.3.2.20.5 Exam Use
- If the question asks:
  - **Which methods/functions consume CPU or runtime inside application code?**
- Think:
  - code profiler / CodeGuru Profiler,
  not only CloudWatch aggregate metrics.

#### 4.3.2.21 Flame Graph

##### 4.3.2.21.1 Purpose
- Flame graphs visualize sampled call-stack activity.

##### 4.3.2.21.2 Reading Conceptually
- Wider areas:
  - represent code observed more frequently in profiling samples.
- This can indicate:
  - expensive/hot code paths.

##### 4.3.2.21.3 Exam Depth
- Know:
  - what flame graphs are for.
- Do not need:
  - advanced profiler implementation internals.

#### 4.3.2.22 Profiling Overhead

##### 4.3.2.22.1 Measurement Changes the System
- Instrumentation and profiling:
  - consume some resources.
- More detailed instrumentation can:
  - increase overhead.

##### 4.3.2.22.2 Practical Principle
- Choose:
  - enough detail to identify the bottleneck,
  - without unnecessarily distorting workload behavior.

##### 4.3.2.22.3 Sampling
- Sampling-based profiling helps:
  - control overhead while still identifying dominant code paths.

#### 4.3.2.23 Cold Start Profiling

##### 4.3.2.23.1 Cold Start
- A Lambda cold start includes initialization before invocation processing can proceed in a new execution environment.

##### 4.3.2.23.2 Investigate
- initialization duration,
- dependency initialization,
- large framework startup,
- static initialization,
- package/runtime startup.

##### 4.3.2.23.3 Distinguish
- `cold-start latency`
  is not the same problem as:
- `slow warm-handler execution`.

##### 4.3.2.23.4 Later Optimization
- Depending on evidence, later optimization might involve:
  - reducing initialization work,
  - deployment/package improvements,
  - provisioned concurrency,
  - Lambda SnapStart where supported and appropriate.
- 4.3.2's job:
  - identify startup as the bottleneck first.

#### 4.3.2.24 Memory Profiling

##### 4.3.2.24.1 Questions
- How much memory does the workload actually use?
- Does usage rise with request size?
- Does memory remain high between operations?
- Is garbage collection correlated with latency?

##### 4.3.2.24.2 Lambda
- Lambda Insights provides:
  - memory utilization,
  - maximum used memory information.
- Use this evidence before:
  - right-sizing memory in 4.3.3.

##### 4.3.2.24.3 Application Runtime
- Runtime-level profiling can help distinguish:
  - expected working set,
  - allocation pressure,
  - retained objects.

#### 4.3.2.25 CPU Profiling

##### 4.3.2.25.1 Question
- Which code consumes CPU?

##### 4.3.2.25.2 Evidence Sources
- Lambda Insights:
  - CPU time.
- Code profiler:
  - hot methods/call stacks.

##### 4.3.2.25.3 Interpretation
- High Lambda duration + high CPU time + hot application method:
  - likely code/compute bottleneck.
- High Lambda duration + low CPU + slow trace subsegment:
  - likely waiting on I/O/dependency.

#### 4.3.2.26 Network Profiling

##### 4.3.2.26.1 Symptoms
- Large network transfer.
- Slow remote dependency.
- Large payloads.
- Repeated remote calls.

##### 4.3.2.26.2 Lambda Insights
- Network metrics can help identify:
  - receive/send activity.

##### 4.3.2.26.3 Correlation
- Network bytes alone do not prove:
  - network is the bottleneck.
- Correlate with:
  - duration,
  - traces,
  - dependency latency.

#### 4.3.2.27 Garbage Collection

##### 4.3.2.27.1 Runtime Cost
- Managed runtimes reclaim unused memory through garbage collection.
- Excessive allocation/GC can:
  - consume CPU,
  - introduce pauses,
  - increase latency.

##### 4.3.2.27.2 Application Signals Runtime Metrics
- Current Application Signals documentation includes garbage-collection runtime metrics for supported instrumentation/runtime scenarios.

##### 4.3.2.27.3 Investigation
- Correlate:
  - GC activity,
  - memory,
  - CPU,
  - latency.

#### 4.3.2.28 Performance Regression

##### 4.3.2.28.1 Definition
- Performance regression:
  - application becomes slower or more resource-intensive after a change.

##### 4.3.2.28.2 Compare
- previous version,
- current version,
- equivalent workload.

##### 4.3.2.28.3 Useful Signals
- duration,
- p95/p99 latency,
- CPU,
- memory,
- error rate,
- dependency timing.

##### 4.3.2.28.4 Deployment Correlation
- If performance changes immediately after deployment:
  - compare telemetry before and after the deployment.

#### 4.3.2.29 Performance Test vs Profiling

##### 4.3.2.29.1 Performance Test
- Generates workload and measures:
  - response time,
  - throughput,
  - behavior under load.

##### 4.3.2.29.2 Profiling
- Explains:
  - where resources/time are spent inside or across the application.

##### 4.3.2.29.3 Together
- Load test reveals:

  `performance degrades at 500 RPS`

- Profiling reveals:

  `CPU-heavy serialization consumes most execution time`

- Both answer:
  - different parts of the problem.

#### 4.3.2.30 Avoid Premature Optimization

##### 4.3.2.30.1 Weak Approach
- Assume:
  - database is slow,
  - Lambda needs more memory,
  - caching will fix everything,
  - concurrency must increase.

##### 4.3.2.30.2 Better Approach
- Establish:
  - baseline,
  - bottleneck,
  - evidence,
  - expected effect.

##### 4.3.2.30.3 Verify
- After change:
  - rerun comparable workload,
  - compare telemetry,
  - confirm improvement,
  - check side effects.

#### 4.3.2.31 Profiling Decision Flow

##### 4.3.2.31.1 First Question

  `Application is slow`
  → **Where is the latency?**

##### 4.3.2.31.2 Distributed Request

  `multiple services/dependencies`
  → use traces/Application Signals
  → identify slow component

##### 4.3.2.31.3 Lambda Runtime

  `Lambda itself appears slow`
  → Lambda Insights
  → CPU / memory / init / network

##### 4.3.2.31.4 Application Code

  `CPU/runtime points to application logic`
  → code profiler
  → hot methods / flame graph

##### 4.3.2.31.5 Final Step

  `bottleneck identified`
  → choose targeted optimization
  → measure again

#### 4.3.2.32 Signal-to-Tool Mapping

##### 4.3.2.32.1 High End-to-End Latency
- Use:
  - Application Signals,
  - X-Ray/traces.

##### 4.3.2.32.2 High Lambda Duration
- Use:
  - Lambda metrics,
  - Lambda Insights,
  - traces.

##### 4.3.2.32.3 High CPU
- Use:
  - Lambda Insights/runtime metrics,
  - code profiler.

##### 4.3.2.32.4 High Memory
- Use:
  - Lambda Insights/runtime metrics.

##### 4.3.2.32.5 Slow Downstream Call
- Use:
  - traces,
  - service/dependency metrics.

##### 4.3.2.32.6 Unknown Hot Method
- Use:
  - CodeGuru Profiler/code profiler.

##### 4.3.2.32.7 Regression After Deployment
- Compare:
  - before/after metrics,
  - traces,
  - runtime profile,
  - deployment timing.

#### 4.3.2.33 Evidence Pattern Summary

Use correlated evidence rather than a single metric:

| Evidence | Likely investigation direction |
|---|---|
| High duration + high CPU + hot method | CPU/code bottleneck |
| High duration + low CPU + slow trace subsegment | I/O/dependency bottleneck |
| Slow requests correlate with high initialization duration | Lambda cold-start/startup bottleneck |
| High memory + increased GC + latency | allocation/memory pressure |
| Good low-load latency + rising dependency latency under concurrency | downstream capacity bottleneck |

The finding selects the next investigation; it does not by itself prescribe a specific optimization.

#### 4.3.2.38 Common Exam Traps

##### 4.3.2.38.1 Optimize Before Measuring
- Wrong.
- Profile first:
  - identify the dominant bottleneck.

##### 4.3.2.38.2 CloudWatch Duration Identifies the Slow Method
- Wrong.
- Duration shows:
  - total execution time.
- A code profiler is needed for:
  - method-level hotspots.

##### 4.3.2.38.3 X-Ray Is a CPU Profiler
- Wrong.
- X-Ray is distributed tracing.
- It helps attribute:
  - request latency across services/dependencies.

##### 4.3.2.38.4 Code Profiler Replaces Tracing
- Wrong.
- Profiler:
  - code-level runtime.
- Trace:
  - distributed request path.

##### 4.3.2.38.5 High Lambda Duration Means Increase Memory
- Wrong.
- First determine:
  - CPU-bound?
  - initialization?
  - downstream I/O?
  - network?
  - retry?
- Right-sizing belongs after:
  - measurement.

##### 4.3.2.38.6 Average Latency Is Enough
- Wrong.
- Tail latency can:
  - reveal slow requests hidden by averages.

##### 4.3.2.38.7 High Memory Means Memory Leak
- Wrong.
- It may be:
  - legitimate workload,
  - allocation pressure,
  - buffering,
  - cache,
  - retained state.
- Profile before concluding.

##### 4.3.2.38.8 Slow Lambda Means Lambda Is the Root Cause
- Wrong.
- Lambda may spend most of its duration:
  - waiting for a dependency.

##### 4.3.2.38.9 More Instrumentation Is Always Better
- Wrong.
- Instrumentation/profiling:
  - has cost and overhead.
- Collect:
  - the detail needed to answer the performance question.

##### 4.3.2.38.10 One Fast Test Proves Performance
- Wrong.
- Use:
  - representative workload,
  - repeatable baseline,
  - realistic concurrency/data.

#### 4.3.2.39 Exam Scenario Mapping

##### 4.3.2.39.1 Need Identify Slow Microservice
- Use:
  - distributed tracing/Application Signals.

##### 4.3.2.39.2 Need Identify Slow Method in Java Application
- Use:
  - code profiling/CodeGuru Profiler.

##### 4.3.2.39.3 Need Determine Lambda CPU and Memory Behavior
- Use:
  - CloudWatch Lambda Insights.

##### 4.3.2.39.4 Need Determine Whether Lambda Cold Starts Cause Latency

- Lambda runtime/system metrics.

  - CPU,
  - memory,
  - disk,
  - network,

- Code-level runtime profiling.
- Think:
  - hot methods,

  - flame graphs,
  - optimization recommendations.

##### 4.3.2.42.7 Fastest Exam Discriminator

**Where is the suspected bottleneck?**

`Across services?`
→ trace / Application Signals / X-Ray.

`Inside Lambda runtime resources?`
→ Lambda Insights.

`Inside application methods/code?`
→ profiler / CodeGuru Profiler.

`Need only overall duration/error trend?`
→ CloudWatch metrics.

`Need detailed event context?`
→ logs.

##### 4.3.2.42.8 Final Principle
- **Profile first, optimize second: use metrics to locate the symptom, traces to attribute distributed latency, runtime metrics to identify resource pressure, and code profiling to find hot execution paths; then make the smallest targeted change and measure again.**

##### 4.3.2.43.2 Amazon CloudWatch — Application Signals
- Application Signals:
  - automatically collects application metrics and traces for supported environments,
  - provides service/dependency relationships,
  - exposes performance signals such as call volume, availability, latency, faults, and errors,
  - supports application-performance troubleshooting.
- Official AWS documentation:
  - https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Application-Monitoring-Sections.html
  - https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Services.html

##### 4.3.2.43.3 Amazon CloudWatch — Application Signals Metrics
- Standard application metrics include:
  - latency,
  - faults,
  - errors.
- Runtime metrics can include:
  - memory,
  - CPU,
  - garbage collection.
- These runtime signals can be correlated with service performance.
- Official AWS documentation:
  - https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/AppSignals-MetricsCollected.html

##### 4.3.2.43.4 AWS Lambda — CloudWatch Lambda Insights
- Lambda Insights:
  - collects and aggregates runtime performance metrics and logs,
  - includes system-level information such as CPU time, memory, disk, and network,
  - provides diagnostic information such as cold starts,
  - supports troubleshooting individual Lambda functions.
- Official AWS documentation:
  - https://docs.aws.amazon.com/lambda/latest/dg/monitoring-insights.html

##### 4.3.2.43.5 Amazon CloudWatch — Lambda Insights Metrics
- Lambda Insights metrics include:
  - `cpu_total_time`,
  - `init_duration`,
  - `memory_utilization`,
  - `used_memory_max`,
  - network-related metrics.
- These are useful for:
  - profiling Lambda runtime behavior,
  - distinguishing resource pressure from downstream wait.
- Official AWS documentation:
  - https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Lambda-Insights-metrics-lambda-functions.html

##### 4.3.2.43.6 AWS Lambda — AWS X-Ray
- X-Ray integration can:
  - visualize application components,
  - identify performance bottlenecks,
  - troubleshoot slow/error requests,
  - produce service maps and searchable trace summaries.
- Official AWS documentation:
  - https://docs.aws.amazon.com/lambda/latest/dg/services-xray.html
