### 4.3.6 Implement application-level caching to improve performance

- **Skill 4.3.6:** **Implement application-level caching to improve performance.**

##### 4.3.6.1.4 Position Inside Task 4.3
- 4.3.1:
  - define concurrency.
- 4.3.2:
  - profile application performance.
- 4.3.3:
  - determine minimum memory and compute power.
- 4.3.4:

##### 4.3.6.1.5 Core Question
- **When an application repeatedly retrieves or computes the same data, where should caching be introduced so repeated requests can be served faster without unnecessary backend work?**

#### 4.3.6.2 Core Mental Model

##### 4.3.6.2.1 Without Application Cache

```text
request
  |
  v
application
  |
  v
database / service / expensive computation
  |
  v
response
```

- Every request may repeat:
  - database reads,
  - network calls,
  - expensive calculations,
  - serialization or transformation.

##### 4.3.6.2.2 With Application Cache

```text
request
  |
  v
application
  |
  v
cache lookup
 /        \
hit       miss
 |          |
 v          v
return    backend
cached      |
value       v
          result
            |
            v
        populate cache
            |
            v
          return
```

##### 4.3.6.2.3 Optimization Principle
- Cache:
  - expensive,
  - frequently reused,
  - sufficiently stable
data or results.

##### 4.3.6.2.4 Goal
- Reduce:
  - latency,
  - backend requests,
  - database load,
  - repeated computation,
  - application execution time.

---

#### 4.3.6.3 What Application-Level Caching Means

##### 4.3.6.3.1 Layer
- Application-level caching happens:
  - inside the application,
  - immediately beside it,
  - or in a dedicated cache service used by the application.

##### 4.3.6.3.2 Common Targets
- database query results,
- frequently accessed objects,
- expensive calculations,
- configuration/reference data,
- API responses,
- session-like application data where appropriate.

##### 4.3.6.3.3 Different from CloudFront
- CloudFront:
  - caches content near viewers.
- Application cache:
  - avoids repeated backend/application work.

##### 4.3.6.3.4 Different Optimization Layer

```text
viewer
→ edge cache
→ API/application
→ application cache
→ database/backend
```

---

#### 4.3.6.4 Cache Hit and Cache Miss

##### 4.3.6.4.1 Cache Hit
- Requested value:
  - exists in cache,
  - is usable.
- Application avoids:
  - backend retrieval/computation.

##### 4.3.6.4.2 Cache Miss
- Requested value:
  - is absent,
  - expired,
  - or invalidated.
- Application must:
  - retrieve/recompute it.

##### 4.3.6.4.3 Performance Goal
- A useful cache should:
  - produce enough hits
to justify:
  - its cost and complexity.

##### 4.3.6.4.4 Exam Mental Model

```text
high repeated-read locality
→ caching likely valuable

mostly unique requests
→ caching likely less valuable
```

#### 4.3.6.5 Caching Strategies and Freshness

##### 4.3.6.5.1 Cache-Aside / Lazy Loading

```text
application reads cache
      |
      +-- hit → return cached value
      |
      '-- miss
            |
            v
         read backend
            |
            v
       populate cache
            |
            v
          return
```

Advantages:
- caches only data that is actually requested,
- avoids populating unused entries,
- backend remains the source of truth.

Tradeoff:
- the first request after a miss, expiry, or eviction still pays backend latency.

##### 4.3.6.5.2 Write-Through

```text
application write
      |
      +--> backend
      '--> cache
```

Benefit:
- cached values can remain fresher after writes.

Tradeoffs:
- every write performs additional work,
- cache can contain data that is written but never read.

##### 4.3.6.5.3 Combined Pattern
AWS guidance presents:
- lazy loading,
- write-through,
- TTL

as complementary strategies.

A common model:

```text
reads
→ lazy loading

writes
→ update cache

all entries
→ bounded by TTL
```

##### 4.3.6.5.4 TTL

```text
short TTL
→ fresher data
→ more misses/backend load

long TTL
→ more reuse
→ greater stale-data risk
```

TTL is not a substitute for:
- invalidation,
- update logic

when freshness requirements are stricter.

##### 4.3.6.5.5 Core Tradeoff
Caching creates a copy of data.

Therefore every cache needs a freshness strategy:

```text
expire
or
update
or
invalidate
```

---

#### 4.3.6.6 Choosing What to Cache

##### 4.3.6.6.1 Strong Candidates
- Frequently read.
- Expensive to retrieve.
- Expensive to compute.
- Reused by many requests.
- Changes relatively infrequently.
- Can tolerate defined freshness window.

##### 4.3.6.6.2 Weak Candidates
- Mostly unique values.
- Extremely write-heavy data.
- Data requiring immediate consistency.
- Cheap backend lookups where cache complexity adds little value.
- Highly sensitive per-request data without an appropriate isolation model.

##### 4.3.6.6.3 Core Question

```text
Will the same result be reused enough
to avoid meaningful repeated work?
```

---

#### 4.3.6.7 ElastiCache and DAX

##### 4.3.6.7.1 Amazon ElastiCache
Amazon ElastiCache provides:
- managed in-memory caching.

Use when:
- application data is repeatedly read,
- a general shared cache is required,
- backend/database calls are expensive,
- cached values can tolerate a defined freshness strategy.

Current engine choices include:
- Valkey,
- Redis OSS,
- Memcached.

Exam focus:
- application-level caching behavior,
not:
- engine internals.

Typical pattern:

```text
application
   |
   +--> ElastiCache
   |
   '--> database/backend
```

##### 4.3.6.7.2 DynamoDB Accelerator (DAX)
DAX is:
- a DynamoDB-compatible managed caching service.

Use when:

```text
DynamoDB
+
read-heavy workload
+
repeated reads
+
microsecond access needed
+
eventually consistent reads acceptable
→ DAX
```

DAX is less suitable when:
- strongly consistent reads are mandatory,
- workload is mostly writes,
- reads are mostly unique,
- normal DynamoDB latency already satisfies requirements.

##### 4.3.6.7.3 DAX vs ElastiCache

| Requirement | Better fit |
|---|---|
| DynamoDB-specific repeated-read acceleration | DAX |
| General shared application cache | ElastiCache |
| Microsecond cached DynamoDB reads | DAX |
| Cache arbitrary DB/API/computed data | ElastiCache |
| Strong consistency required | Do not blindly choose DAX |

Core rule:

```text
DynamoDB-specific acceleration
→ DAX

general-purpose application cache
→ ElastiCache
```

#### 4.3.6.8 API Gateway Caching

API Gateway REST API caching can:
- cache endpoint responses,
- reduce integration calls,
- reduce latency.

```text
client
  |
  v
API Gateway
  |
  +-- cache hit → cached response
  |
  '-- cache miss → integration endpoint
```

Key behavior:
- cache is provisioned for a stage,
- method-level caching can be enabled/overridden,
- `GET` methods are the natural default candidates.

Current documented TTL values:
- default: **300 seconds**,
- maximum: **3600 seconds**.

If request parameters change the response:
- include the relevant parameters in the API Gateway cache key.

Monitoring:
- `CacheHitCount`,
- `CacheMissCount`,
- latency,
- 4xx/5xx,
- backend behavior.

Invalidation:
- stage cache can be flushed,
- authorized clients can request refresh of an individual entry with `Cache-Control: max-age=0`.

Caching must be:
- explicitly provisioned/configured,
- load tested,
- sized according to observed hit rate and backend reduction.

---

#### 4.3.6.9 Lambda Execution-Environment Reuse

AWS Lambda best practices recommend reusing initialized resources across warm invocations.

Initialize outside the handler where appropriate:
- AWS SDK clients,
- database connections,
- other reusable clients.

```text
cold start
→ initialize once

warm invocation
→ reuse initialized object
```

This reduces:
- repeated setup work,
- execution duration,
- cost.

Important boundary:

```text
execution-environment reuse
≠ shared distributed cache
```

Each Lambda execution environment is independent.

##### 4.3.6.9.1 `/tmp` as a Transient Cache
Lambda can reuse files in:

```text
/tmp
```

while the same execution environment remains available.

Current configurable ephemeral storage:
- **512 MB to 10,240 MB**.

Good candidates:
- static assets,
- downloaded models/files,
- temporary reusable artifacts.

Critical rules:
- `/tmp` is not durable storage,
- the function must still work when the local cache is absent,
- do not use execution-environment reuse for unsafe cross-invocation user/security-sensitive state.

Use durable services such as:
- S3,
- DynamoDB

for required durable state.

#### 4.3.6.6 Cache Design and Operational Risks

##### 4.3.6.6.1 Invalidation and Freshness
Because a cache contains copies:

```text
source changes
→ cached copy must eventually expire, update, or invalidate
```

Common controls:
- TTL,
- delete-on-update,
- write-through/update-on-write,
- explicit flush/invalidation.

##### 4.3.6.6.2 Cache Stampede
Pattern:

```text
popular entry expires
→ many requests miss simultaneously
→ backend load spikes
```

Caching can:
- shift load rather than eliminate it.

TTL and application design:
- matter.

##### 4.3.6.6.3 Warm-Up and Eviction
Cold cache:
- initially produces misses.

Finite-capacity cache:
- can evict entries.

Therefore:

```text
cache miss
→ normal condition
```

The durable backend should normally remain:
- the source of truth.

##### 4.3.6.6.4 Cache Key Design

```text
too broad
→ different results collide
→ wrong response

too specific
→ equivalent results get many keys
→ poor hit rate
```

Use:
- the minimum dimensions necessary to identify the reusable result correctly.

##### 4.3.6.6.5 Granularity
Fine-grained:
- records,
- objects,
- fragments.

Coarse-grained:
- complete query results,
- full API responses,
- larger computed objects.

Choose according to:
- access pattern,
- invalidation complexity,
- memory use,
- reuse.

##### 4.3.6.6.6 Workload Fit

```text
many repeated reads
→ caching often valuable

many writes + few repeated reads
→ lower cache value
```

Caching is especially valuable when:
- access has locality,
- a small subset of data becomes hot,
- repeated reads overload a backend.

##### 4.3.6.6.7 Cost and Effectiveness
A cache should be measured, not assumed effective.

Track:
- hits,
- misses,
- hit ratio,
- latency,
- backend request volume,
- evictions,
- memory/capacity,
- stale-data behavior,
- cost.

Low hit ratio can mean:
- poor key design,
- poor TTL choice,
- low request reuse,
- cache is not justified.

#### 4.3.6.6 Decision Flow

```text
What repeated work is expensive?
        |
        v
Are results reused enough?
      /   \
    no     yes
    |       |
 no cache   v
       How fresh must data be?
              |
              v
        choose cache layer
```

Service mapping:

```text
DynamoDB repeated reads + microsecond latency
→ DAX

general shared application cache
→ ElastiCache

REST API response cache
→ API Gateway caching

Lambda reusable clients/connections
→ initialize outside handler

Lambda reusable static/local artifact
→ /tmp
```

Then define:
- cache key,
- TTL,
- update/invalidation strategy.

Finally measure:
- hit ratio,
- latency,
- backend load,
- cost.

##### 4.3.6.6.1 Practical Pattern Summary

| Requirement | Best fit |
|---|---|
| DynamoDB + repeated microsecond reads | DAX |
| General database/API/computed-data cache | ElastiCache |
| REST `GET` repeatedly invokes expensive backend | API Gateway cache |
| Lambda recreates SDK/DB client every invocation | Initialize outside handler |
| Lambda repeatedly downloads reusable static asset | `/tmp` |
| Strongly consistent DynamoDB reads required | Do not blindly choose DAX |
| Mostly unique reads | Cache may add cost with little value |
| Database overloaded by repeated reads | Introduce appropriate cache before only scaling backend |
| Cache hit rate is low | Revisit access pattern, key, TTL, and whether caching is suitable |

#### 4.3.6.6 Common Exam Traps

##### 4.3.6.6.1 Cache Everything
- Wrong.
- Cache:
  - reusable, expensive, appropriate data.

##### 4.3.6.6.2 Cache Is Durable Storage
- Wrong.
- Cache:
  - is normally an optimization copy.

##### 4.3.6.6.3 DAX for Any Database
- Wrong.
- DAX:
  - is DynamoDB-specific.

##### 4.3.6.6.4 DAX for Strongly Consistent Reads
- Wrong.
- DAX:
  - is not ideal when strong consistency is required.

##### 4.3.6.6.5 DAX for Write-Heavy Workload
- Usually poor fit.
- DAX:
  - is primarily valuable for repeated read workloads.

##### 4.3.6.6.6 ElastiCache Automatically Maintains Database Consistency
- Wrong.
- Application/cache strategy must handle:
  - TTL,
  - update,
  - invalidation.

##### 4.3.6.6.7 Long TTL Is Always Better
- Wrong.
- Longer TTL:
  - improves reuse,
  - increases stale-data risk.

##### 4.3.6.6.8 Short TTL Is Always Better
- Wrong.
- Very short TTL:
  - reduces cache effectiveness,
  - increases backend calls.

##### 4.3.6.6.9 Lambda `/tmp` Is Durable
- Wrong.
- It is:
  - transient execution-environment storage.

##### 4.3.6.6.10 Lambda Global State Is Shared Across All Instances
- Wrong.
- Reuse applies:
  - within a reused execution environment,
not:
  - globally across every concurrent environment.

##### 4.3.6.6.11 API Gateway Cache Applies Automatically to Everything
- Wrong.
- Cache must:
  - be provisioned/configured,
  - and method behavior matters.

##### 4.3.6.6.12 Cache Hit Ratio Does Not Matter
- Wrong.
- Low reuse:
  - can make cache cost/complexity unjustified.

##### 4.3.6.15.5 Critical Distinctions
- DAX:
  - DynamoDB-specific.
- ElastiCache:
  - general-purpose.
- API Gateway cache:
  - response caching before integration.
- Lambda local reuse:
  - transient and per execution environment.

##### 4.3.6.15.6 Fastest Exam Discriminator

```text
DynamoDB read-heavy + microseconds
→ DAX

database overloaded by repeated reads
→ ElastiCache / appropriate cache

GET API repeatedly calls expensive backend
→ API Gateway cache

Lambda repeatedly creates clients
→ initialize outside handler

Lambda repeatedly downloads same static asset
→ /tmp cache

strong consistency mandatory
→ do not blindly choose DAX

mostly unique reads
→ caching may not help
```

##### 4.3.6.15.7 Final Principle
- **Application-level caching improves performance by serving reusable results from a faster layer instead of repeatedly invoking the original database, service, computation, or initialization path. Select the cache according to the workload, define a freshness strategy, and verify that real cache hits reduce latency and backend load.**
