### 4.3.1 Define concurrency

#### 4.3.1.1 Exam and Task Context

##### 4.3.1.1.1 Domain and Task
- **Domain 4:** Troubleshooting and Optimization.
- **Task 4.3:** Optimize applications by using AWS services and features.
- **Skill 4.3.1:** **Define concurrency.**

##### 4.3.1.1.2 Position Inside Task 4.3

```text
4.3.1
→ define concurrency

4.3.2
→ profile application performance

4.3.3
→ determine minimum memory and compute power

4.3.4

```

Core question:

**How much work can be in progress at the same time, how does that differ from request rate or throughput, and how do Lambda concurrency controls affect scaling, throttling, latency, cost, and downstream protection?**

---

#### 4.3.1.2 Core Mental Model

Concurrency answers:

```text
How many units of work are in progress at the same time?
```

Example:

```text
Request A  |----------|
Request B     |----------|
Request C        |-----|
Request D           |------|
```

At one point:

```text
A + B + C + D
→ 4 concurrent requests
```

Critical distinction:

```text
concurrency
≠ requests per second
```

Concurrency depends on:
- arrival rate,
- execution duration,
- overlap.

---

#### 4.3.1.3 Concurrency vs Parallelism vs Throughput

##### 4.3.1.3.1 Concurrency

Concurrency:

```text
multiple operations are in progress during overlapping time
```

Examples:
- simultaneous Lambda invocations,
- simultaneous HTTP requests,
- concurrent message processing,
- simultaneous database operations.

##### 4.3.1.3.2 Parallelism

Parallelism:

```text
multiple operations literally execute at the same instant
```

For AWS exam scenarios, the more important practical question is:

```text
How many requests/jobs can be active at once?
```

##### 4.3.1.3.3 Throughput

Throughput:

```text
how much work completes per unit time
```

Concurrency:

```text
how much work is simultaneously in progress
```

Example:

```text
100 requests/s
100 ms average duration
```

Approximate concurrency:

```text
100 × 0.1
= 10
```

Therefore:

```text
100 RPS
≠ 100 concurrency
```

---

#### 4.3.1.4 Concurrency Formula

For relatively steady traffic:

```text
Concurrency
≈
Requests per second × Average duration in seconds
```

Example:

```text
RPS = 200
Duration = 500 ms = 0.5 s

Concurrency
≈ 200 × 0.5
≈ 100
```

This is the key Lambda capacity relationship.

---

#### 4.3.1.5 Duration Directly Affects Concurrency

Same traffic:

```text
100 RPS
```

Application A:

```text
100 ms duration
→ ~10 concurrency
```

Application B:

```text
2 s duration
→ ~200 concurrency
```

Therefore:

```text
reduce execution duration
→ reduce required concurrency
```

even when:
- traffic stays constant.

---

#### 4.3.1.6 Burst Traffic

Average request rate can hide:
- short concurrency spikes.

Example:

```text
average = 100 RPS
```

but:

```text
1-second burst = 2,000 requests
```

may require:
- much more immediate concurrency.

Optimization must consider:
- peak traffic,
- burst traffic,
not averages only.

---

#### 4.3.1.7 AWS Lambda Concurrency

AWS Lambda defines concurrency as:
- the number of in-flight requests a function is handling at one time.

For normal Lambda execution:

```text
one execution environment
→ processes one invocation at a time
```

If another request arrives while it is busy:

```text
Lambda
→ uses/creates another execution environment
```

subject to:
- concurrency quotas,
- scaling behavior,
- request-rate limits.

Conceptually:

```text
concurrent invocations
≈
active Lambda execution environments
```

---

#### 4.3.1.8 Why Lambda Concurrency Matters

Concurrency affects:
- scaling,
- throttling,
- downstream load,
- account capacity,
- latency,
- database connections,
- external API calls,
- event processing speed.

Therefore concurrency is both:
- a performance mechanism,
- a protection mechanism.

---

#### 4.3.1.9 Regional Account Concurrency

Lambda has:
- a Regional account concurrency quota shared by functions.

The source records the current default:

```text
1,000 concurrent executions per Region
```

This quota:
- can be increased.

Always distinguish:

```text
Regional account concurrency
```

from:

```text
function-specific concurrency configuration
```

---

#### 4.3.1.10 Unreserved Concurrency

Functions without reserved concurrency:
- use the account's unreserved concurrency pool.

Concept:

```text
Regional account concurrency
        |
        +--> reserved for Function A
        +--> reserved for Function B
        |
        '--> unreserved pool
               |
               +--> Function C
               +--> Function D
               '--> Function E
```

Functions sharing that pool:
- can compete for available concurrency.

---

#### 4.3.1.11 Reserved Concurrency

Reserved concurrency:

```text
reserves capacity
+
sets a maximum concurrency
```

for one function.

This dual behavior is one of the most important exam distinctions.

---

#### 4.3.1.12 Reserved Concurrency Example

Account quota:

```text
1,000
```

Function A:

```text
reserved concurrency = 200
```

Then Function A:
- has up to 200 concurrency dedicated to it,
- cannot scale beyond 200.

Reserved concurrency therefore acts as:
- a guarantee,
- a ceiling.

---

#### 4.3.1.13 Reserved Concurrency Does Not Pre-Initialize Environments

Reserved concurrency means:

```text
capacity reserved
```

It does not mean:

```text
execution environments already initialized
```

Lambda still creates environments:
- on demand.

Therefore:
- cold starts remain possible.

---

#### 4.3.1.14 Reserved Concurrency Cost

Current AWS behavior:

```text
reserved concurrency
→ no additional charge
```

It is:
- a capacity control.

Do not confuse it with:
- provisioned concurrency pricing.

---

#### 4.3.1.15 Reserved Concurrency as Downstream Protection

Suppose a database safely supports:

```text
100 concurrent connections
```

If every Lambda invocation opens one connection:

```text
traffic spike
→ Lambda scales
→ hundreds of DB connections
→ database overload
```

Reserved concurrency can:

```text
cap Lambda parallelism
→ protect downstream dependency
```

This is a major optimization pattern.

---

#### 4.3.1.16 Reserved Concurrency as Capacity Guarantee

Suppose:

```text
Function A
→ critical API

Function B
→ heavy background work
```

Without reservation:

```text
Function B consumes shared concurrency
→ Function A may throttle
```

Reserve capacity for Function A:
- protects critical traffic.

---

#### 4.3.1.17 Reserved Concurrency Tradeoff

Reserved capacity:

```text
protects one function
```

but:

```text
removes that capacity from general sharing
```

Over-reserving:
- can unnecessarily constrain other functions.

Use according to:
- workload priority,
- measured need.

---

#### 4.3.1.18 Reserved Concurrency = 0

Setting:

```text
reserved concurrency = 0
```

means:

```text
function has no concurrency available
→ invocations are throttled
```

This can be used to:
- stop function processing quickly.

Exam trap:

```text
reserved concurrency = 0
≠ unlimited
```

---

#### 4.3.1.19 Provisioned Concurrency

Provisioned concurrency:
- creates and keeps execution environments initialized.

Purpose:

```text
reduce cold-start latency
```

Useful for:
- latency-sensitive APIs,
- interactive workloads,
- predictable traffic.

---

#### 4.3.1.20 Provisioned Concurrency Mental Model

On-demand:

```text
request
→ initialize environment if needed
→ execute
```

Provisioned:

```text
initialized environment already waiting
        |
        v
request
→ execute
```

Provisioned concurrency is primarily:
- a startup-latency mechanism.

---

#### 4.3.1.21 Provisioned Concurrency Is Not the Function Maximum

Provisioned concurrency means:

```text
number of pre-initialized environments
```

It does not inherently mean:

```text
maximum function concurrency
```

Traffic above provisioned capacity can:
- use on-demand concurrency,
if function/account capacity is available.

---

#### 4.3.1.22 Provisioned Concurrency Cost

Provisioned concurrency:
- incurs additional charges.

Reason:
- AWS keeps environments initialized.

Use it when:
- latency benefit justifies cost.

---

#### 4.3.1.23 Reserved vs Provisioned Concurrency

| Characteristic | Reserved | Provisioned |
|---|---|---|
| Reserves capacity | Yes | Pre-initializes capacity |
| Sets function maximum | Yes | No, not inherently |
| Reduces cold starts | No | Yes, within provisioned capacity |
| Additional charge | No | Yes |
| Protects downstream | Yes | Not primarily |
| Primary purpose | Capacity isolation/control | Low startup latency |

Memorize this distinction.

---

#### 4.3.1.24 Reserved and Provisioned Together

Example:

```text
reserved concurrency = 100
provisioned concurrency = 40
```

Meaning:

```text
40
→ pre-initialized

up to 100 total
→ function concurrency ceiling
```

The remaining capacity:

```text
40 → 100
```

can be created:
- on demand.

---

#### 4.3.1.25 Provisioned Concurrency and Reserved Concurrency

If a function has reserved concurrency:

```text
provisioned concurrency
≤
reserved concurrency
```

Provisioned capacity cannot:
- exceed the reserved ceiling.

Provisioned concurrency is configured for:
- published versions,
- aliases.

It is not configured directly for:
- `$LATEST`.

---

#### 4.3.1.26 Estimating Provisioned Concurrency

Use:

```text
RPS × average duration
```

to estimate:
- required steady-state concurrency.

AWS guidance also recommends:
- buffer above typical need.

Example:

```text
expected peak concurrency = 200
10% buffer
→ 220 provisioned concurrency
```

The exact buffer:
- depends on workload variability.

---

#### 4.3.1.27 Lambda Throttling

Lambda can throttle when:
- reserved concurrency is exhausted,
- account concurrency is exhausted,
- scaling limits are reached,
- request-rate limits are reached.

Throttling behavior depends on:
- invocation model.

---

#### 4.3.1.28 Synchronous Throttling

For synchronous invocation:

```text
client
→ Lambda
→ concurrency unavailable
→ throttling response
```

The caller:
- sees the failure,
- decides retry behavior.

Use where appropriate:
- retry,
- exponential backoff,
- jitter.

---

#### 4.3.1.29 Asynchronous Throttling

For asynchronous invocation:

```text
event accepted
→ Lambda internal queue
→ execution attempted
```

If execution is throttled:
- Lambda's asynchronous retry/event lifecycle applies.

Therefore:

```text
throttling
≠ always immediate producer-facing error
```

---

#### 4.3.1.30 SQS Event Source Concurrency

For SQS:

```text
SQS queue
→ Lambda event source mapping
→ concurrent Lambda invocations
```

Concurrency is affected by:
- event-source scaling,
- batch behavior,
- queue characteristics,
- function concurrency,
- account concurrency.

---

#### 4.3.1.31 SQS Maximum Concurrency

SQS event source mappings support:

```text
MaximumConcurrency
```

This limits:

```text
how many concurrent function instances
this one event source mapping can invoke
```

This is:
- an event-source-level control.

---

#### 4.3.1.32 Event-Source vs Function Concurrency

Suppose:

```text
Queue A
 \
  → Lambda Function
 /
Queue B
```

Queue A:

```text
maximum concurrency = 20
```

Queue B:

```text
maximum concurrency = 10
```

Potential source demand:

```text
20 + 10 = 30
```

If function reserved concurrency is:

```text
20
```

the event sources:
- can compete,
- can experience throttling.

Rule:

```text
event-source maximum
→ one mapping

reserved concurrency
→ entire function
```

---

#### 4.3.1.33 SQS Standard Queue Scaling

For standard SQS queues, Lambda:
- increases concurrent consumption while backlog exists,
- scales down when traffic falls.

Exam principle:

```text
queue backlog
→ Lambda scales consumers
→ until event-source/function/account limits constrain it
```

Exact scaling values:
- can change,
- should be verified against current documentation.

---

#### 4.3.1.34 SQS FIFO Concurrency

FIFO queues use:

```text
messageGroupId
```

Ordering rule:

```text
same message group
→ ordered processing
```

Concurrency is therefore constrained by:
- number of active message groups,
- configured maximum concurrency.

Example:

```text
Group A: A1 → A2 → A3
Group B: B1 → B2 → B3
```

Possible:

```text
A1 and B1
→ concurrent
```

Not:

```text
A1 and A2
→ concurrently violate same-group order
```

---

#### 4.3.1.35 SQS Provisioned Polling vs Lambda Provisioned Concurrency

Current SQS integration also supports:
- provisioned polling mode.

Do not confuse:

```text
SQS provisioned pollers
```

with:

```text
Lambda provisioned concurrency
```

They solve different problems.

Lambda provisioned concurrency:

```text
pre-initialized execution environments
→ reduce cold starts
```

SQS provisioned polling:

```text
dedicated event pollers
→ more predictable/faster polling behavior
```

---

#### 4.3.1.36 Downstream Concurrency

Lambda can scale faster than:
- databases,
- legacy services,
- external APIs,
- SaaS quotas.

Therefore optimization is not:

```text
maximize concurrency
```

It is:

```text
choose safe useful concurrency
```

---

#### 4.3.1.37 Database Example

Suppose:

```text
database safe connections = 80
```

Each invocation uses:
- one connection.

Unbounded function concurrency can:
- overwhelm the database.

Possible controls:
- reserved concurrency,
- connection reuse,
- connection pooling/proxy,
- queue buffering.

Concurrency control can:
- protect system stability.

---

#### 4.3.1.38 Third-Party API Example

Third-party API limit:

```text
50 concurrent requests
```

Lambda could otherwise scale to:

```text
hundreds
```

Without control:

```text
Lambda scales
→ API throttles
→ retries increase
→ more pressure
```

Bound concurrency near:
- sustainable downstream capacity.

---

#### 4.3.1.39 Backpressure

Backpressure means:

```text
downstream capacity
→ limits how quickly upstream work should proceed
```

Queue-based model:

```text
producer
→ SQS backlog
→ controlled Lambda concurrency
→ downstream
```

Benefits:
- excess work waits in the queue,
- downstream avoids uncontrolled overload.

---

#### 4.3.1.40 Retry Storms

Failure pattern:

```text
many concurrent requests fail
→ all retry
→ concurrency rises further
→ dependency remains overloaded
```

Mitigate with:
- concurrency limits,
- exponential backoff,
- jitter,
- queues,
- circuit breakers where appropriate.

Concurrency is:
- part of resilience design.

---

#### 4.3.1.41 Idempotency

More concurrency can increase:
- simultaneous/repeated processing.

Event-driven systems must still account for:
- retries,
- duplicates,
- at-least-once delivery.

Concurrency does not provide:
- exactly-once processing.

Use:
- idempotent consumers where needed.

---

#### 4.3.1.42 Concurrency and Shared State

Concurrent execution can introduce:
- race conditions,
- lost updates,
- inconsistent state,
- locking contention.

More concurrency can improve throughput,
but also increases:
- coordination complexity.

Application code must handle:
- shared-state access safely.

---

#### 4.3.1.43 Optimistic vs Pessimistic Concurrency

Optimistic concurrency concept:

```text
read item + version
→ modify
→ write only if version unchanged
```

If version changed:
- reject/retry/conflict.

Pessimistic concurrency:

```text
lock
→ modify
→ unlock
```

These are:
- data/application concurrency-control concepts.

Do not confuse them with:
- Lambda concurrency quotas.

For DVA-C02, Lambda/service concurrency is the main focus.

---

#### 4.3.1.44 Concurrency vs Rate Limiting

Concurrency limit:

```text
maximum simultaneous work
```

Rate limit:

```text
maximum work admitted per unit time
```

Example:

```text
10 concurrent requests
≠
10 requests/second
```

This distinction is exam-relevant.

---

#### 4.3.1.45 API Gateway Throttling

API Gateway uses:
- rate limits,
- burst limits.

When exceeded, clients can receive:

```text
429 Too Many Requests
```

API Gateway throttling controls:

```text
request admission rate/burst
```

It does not directly control:

```text
Lambda simultaneous execution count
```

---

#### 4.3.1.46 API Gateway + Lambda Protection Layers

```text
Client
  |
  v
API Gateway
  | rate/burst control
  v
Lambda
  | concurrency control
  v
Database
```

Possible controls:

```text
API Gateway throttling
→ limits admitted request rate

Lambda reserved concurrency
→ limits simultaneous execution

database
→ protected from excessive parallel load
```

---

#### 4.3.1.47 The Bottleneck Limits Throughput

Example:

```text
API Gateway capacity = high
Lambda capacity = high
Database safe concurrency = 50
```

Increasing Lambda concurrency from:

```text
100 → 500
```

can make performance:
- worse,
not better.

Optimization must consider:
- the complete request path.

---

#### 4.3.1.48 Concurrency and Latency

Too little concurrency:

```text
work waits
→ queueing latency rises
```

Too much concurrency:

```text
dependency overload
→ throttling/contention/retries
→ latency rises
```

Therefore:

```text
optimal concurrency
≠ maximum possible concurrency
```

---

#### 4.3.1.49 CPU-Bound vs I/O-Bound Work

CPU-bound:

```text
too much local concurrency
→ contention/context switching
```

For Lambda:
- CPU allocation grows with configured memory.

I/O-bound:

```text
waiting on network/storage/API
```

Concurrency can:
- overlap waits,
- improve utilization.

But downstream constraints:
- still limit safe parallelism.

Memory/CPU sizing is covered more directly by:
- 4.3.3.

---

#### 4.3.1.50 Lambda Scaling Rate

Concurrency quota answers:

```text
How much concurrency can exist?
```

Scaling rate answers:

```text
How quickly can Lambda add execution environments?
```

These are different limits.

The source records current AWS behavior:

```text
1,000 additional execution environments
every 10 seconds
per function per Region
```

for on-demand scaling.

Exact service limits:
- should always be checked against current AWS documentation.

---

#### 4.3.1.51 Scaling Rate vs Concurrency Limit

Example:

```text
account concurrency available = 5,000
```

does not mean:

```text
function instantly scales from 0 → 5,000
```

Scaling rate:
- controls how quickly capacity can grow.

This matters for:
- sudden synchronous bursts.

---

#### 4.3.1.52 Lambda Request-Rate Limits

Lambda also has:
- request-rate limits related to concurrency.

Therefore a function can be constrained by:
- concurrency,
- scaling rate,
- request rate.

Available concurrency does not imply:
- unlimited RPS.

This matters especially for:
- very short-duration functions.

---

#### 4.3.1.53 Short vs Long Duration Functions

Short-duration example:

```text
duration = 10 ms
```

One environment can complete:
- many sequential invocations per second.

Throughput may hit:
- request-rate constraints

before concurrency is fully consumed.

Long-duration example:

```text
duration = 30 s
RPS = 20
```

Concurrency:

```text
20 × 30
= 600
```

Long duration:
- consumes concurrency for longer.

Optimization of duration can:
- free concurrency capacity.

---

#### 4.3.1.54 Monitoring Lambda Concurrency

Useful metrics include:

```text
ConcurrentExecutions
UnreservedConcurrentExecutions
ProvisionedConcurrentExecutions
ProvisionedConcurrencyUtilization
Throttles
ClaimedAccountConcurrency
```

Use them to understand:
- actual peak concurrency,
- throttling,

---

#### 4.3.1.55 `ConcurrentExecutions`

`ConcurrentExecutions` shows:
- active function instances processing events at a point in time.

Use it to understand:
- actual concurrency consumption.

---

#### 4.3.1.56 `Throttles`

`Throttles` indicates invocation requests that:
- could not execute because relevant Lambda limits were reached.

If:

```text
ConcurrentExecutions near limit
+
Throttles rising
```

a concurrency limit may be:
- constraining throughput.

But ask first:
- whether the limit intentionally protects a downstream system.

---

#### 4.3.1.57 Provisioned Concurrency Utilization

Provisioned concurrency metrics answer:

```text
Did we provision too little?
Did we provision too much?
```

Low utilization:
- may indicate wasted cost.

Frequent spillover/on-demand usage:
- may indicate too little provisioned capacity for latency-sensitive traffic.

#### 4.3.1.62 Common Exam Traps

##### 4.3.1.62.1 Concurrency = RPS
Wrong.

```text
concurrency
≈ RPS × duration
```

##### 4.3.1.62.2 Reserved Concurrency Prevents Cold Starts
Wrong.

```text
reserved
→ reserves/caps capacity

provisioned
→ pre-initializes environments
```

##### 4.3.1.62.3 Provisioned Concurrency Is the Function Maximum
Wrong.
- Reserved concurrency is the ceiling mechanism.

##### 4.3.1.62.4 Reserved Concurrency Only Guarantees Minimum Capacity
Wrong.
- It also caps maximum concurrency.

##### 4.3.1.62.5 Reserved Concurrency Costs Extra
Wrong.
- Current AWS behavior: no additional charge.

##### 4.3.1.62.6 Provisioned Concurrency Is Free
Wrong.
- It incurs additional cost.

##### 4.3.1.62.7 More Concurrency Always Improves Performance
Wrong.
- It can overload dependencies and increase retries/latency.

##### 4.3.1.62.8 Account Concurrency = Reserved Concurrency
Wrong.

```text
account concurrency
→ Regional shared capacity

reserved concurrency
→ function-specific reservation + ceiling
```

##### 4.3.1.62.9 SQS Maximum Concurrency = Reserved Concurrency
Wrong.

```text
SQS maximum
→ one event source mapping

reserved
→ whole function
```

##### 4.3.1.62.10 FIFO Concurrency Ignores Message Groups
Wrong.
- FIFO ordering limits concurrency within each group.

##### 4.3.1.62.11 API Gateway Rate Limit = Lambda Concurrency
Wrong.
- Rate/burst and simultaneous execution are different concepts.

##### 4.3.1.62.12 Concurrency Quota Means Instant Scaling
Wrong.
- Scaling rate also matters.

##### 4.3.1.62.13 SQS Provisioned Pollers = Lambda Provisioned Concurrency
Wrong.
- Different resources, different purpose.

##### 4.3.1.62.14 Throttling Always Means Increase Concurrency
Wrong.
- A limit may intentionally protect downstream capacity.

**Lambda concurrency estimate**  
→ approximately `RPS × average duration in seconds`.

**Reserved concurrency**  
→ function-specific capacity reservation **and maximum**.

**Provisioned concurrency**  
→ pre-initialized execution environments for lower startup latency.

**Unreserved concurrency**  
→ shared account pool.

**Throttling**  
→ work cannot execute because relevant Lambda limits are reached.

**SQS maximum concurrency**  
→ event-source-level limit on concurrent Lambda invocations.

**FIFO concurrency**  
→ constrained by message-group ordering.

**Backpressure**  
→ prevents upstream work from overwhelming slower downstream capacity.

#### 4.3.1.67 Final Principle

**Concurrency is the amount of work simultaneously in progress, not the same as request rate or throughput. For steady Lambda workloads, required concurrency is approximately requests per second multiplied by average execution duration in seconds, so both traffic and runtime determine capacity consumption. Reserved concurrency simultaneously protects capacity for a function and caps its maximum concurrency, making it useful for workload isolation and downstream protection; it does not pre-initialize execution environments and has no additional charge. Provisioned concurrency keeps execution environments initialized to reduce cold-start latency and incurs additional cost, but it is not inherently the function's maximum. Event-source controls such as SQS maximum concurrency can bound one source, while FIFO message groups constrain parallel processing through ordering semantics. API Gateway rate/burst throttling controls request admission, not Lambda execution concurrency. Optimize concurrency against the capacity of the entire request path rather than maximizing parallel execution in isolation.**
