---

#### 4.3.8.2 Core Mental Model

##### 4.3.8.2.1 Performance Is End-to-End

```text
client
  |
  v
API / entry point
  |
  v
application
  |
  +----> dependency A
  |
  +----> dependency B
  |
  '---> database
```

- User-visible latency:
  - is the result of the entire request path.
- A slow application:
  - does not automatically mean slow application code.

##### 4.3.8.2.2 Analysis Goal

```text
symptom
→ quantify
→ correlate
→ isolate
→ verify
→ optimize
```

##### 4.3.8.2.3 Core Principle
- **Locate the bottleneck before changing resources.**

---

#### 4.3.8.3 Performance Symptoms

##### 4.3.8.3.1 Latency
- Requests:
  - take longer than expected.

##### 4.3.8.3.2 Throughput
- Application:
  - processes fewer requests/items per unit time than required.

##### 4.3.8.3.3 Throttling
- A service:
  - rejects or delays work because a quota/capacity boundary is reached.

##### 4.3.8.3.4 Errors and Timeouts
- Performance degradation can:
  - become timeout/error behavior.

##### 4.3.8.3.5 Backlog
- Queues/streams:
  - accumulate work faster than consumers process it.

---

#### 4.3.8.4 Performance Analysis Signals

##### 4.3.8.4.1 Metrics
- Answer:
  - **what changed?**
  - **when?**
  - **how much?**

##### 4.3.8.4.2 Traces
- Answer:
  - **where did request time go?**

##### 4.3.8.4.3 Logs
- Answer:
  - **what happened inside the application?**

##### 4.3.8.4.4 Runtime Metrics
- Answer:
  - **was CPU, memory, disk, network, or runtime behavior correlated with the slowdown?**

##### 4.3.8.4.5 Combined Model

```text
metrics
→ detect anomaly

traces
→ isolate service/dependency

logs
→ explain application behavior

runtime metrics
→ confirm resource pressure
```

#### 4.3.8.5 Baseline Before Diagnosis

##### 4.3.8.5.1 Need a Reference
- "Slow" requires comparison with:
  - normal latency,
  - expected throughput,
  - previous deployment,
  - SLO,
  - known workload level.

##### 4.3.8.5.2 Compare Time Windows
- Before issue.
- During issue.
- After issue.

##### 4.3.8.5.3 Compare Dimensions
- Function version.
- API operation.
- Dependency.
- Region/environment.
- Request type.

##### 4.3.8.5.4 Principle
- A metric value without:
  - historical or workload context
can be:
  - misleading.

#### 4.3.8.6 Average vs Percentile Latency

##### 4.3.8.6.1 Average
- Useful for:
  - broad trend.
- Can hide:
  - slow outliers.

##### 4.3.8.6.2 Percentiles
- Examples:
  - p50,
  - p90,
  - p95,
  - p99.

##### 4.3.8.6.3 Interpretation
- p95:
  - 95% of observed values are at or below that value.
- Slowest:
  - 5% are above it.

##### 4.3.8.6.4 Exam Principle

```text
average stable
+
p95/p99 rising
→ tail-latency problem
```

---

#### 4.3.8.7 Correlation Is Central

##### 4.3.8.7.1 Example

```text
latency spike
+
ConcurrentExecutions spike
+
Throttles spike
```

suggests:
- capacity/concurrency pressure.

##### 4.3.8.7.2 Another Example

```text
latency spike
+
Lambda CPU/memory stable
+
downstream trace segment slow
```

suggests:
- dependency bottleneck.

##### 4.3.8.7.3 Principle
- Do not diagnose:
  - from one isolated metric.

#### 4.3.8.8 Lambda Performance Analysis

##### 4.3.8.8.1 Core Metrics

Key Lambda metrics:

```text
Duration
→ execution latency

Invocations
→ function invocation count

Errors
→ failed invocations

Throttles
→ requests rejected because concurrency is unavailable

ConcurrentExecutions
→ active concurrent executions
```

Interpret them together.

Example:

```text
ConcurrentExecutions reaches limit
+
Throttles rise
→ concurrency constraint
```

High concurrency alone:
- is not automatically a problem.

It becomes relevant when correlated with:
- throttles,
- backlog,
- latency,
- downstream overload.

##### 4.3.8.8.2 Error Rate and Time Correlation
Analyze:
- `Errors` relative to `Invocations`,
- whether errors rise at the same time as latency.

Performance degradation can cause:
- timeouts,
- retries,
- downstream failures.

##### 4.3.8.8.3 Lambda Insights
CloudWatch Lambda Insights adds runtime-level evidence including:
- CPU,
- memory,
- disk,
- network,
- cold starts,
- worker diagnostic information.

Use it when:

```text
Lambda is slow
→ need to know whether runtime resource pressure explains it
```

##### 4.3.8.8.4 Resource-Pressure Patterns

Memory-bound:

```text
memory usage approaches configured memory
+
duration/errors rise
→ investigate memory pressure / allocation / input size
```

CPU-bound:

```text
dependency latency low
+
memory sufficient
+
compute work dominates
→ investigate CPU/code path
```

For Lambda:
- CPU allocation increases with configured memory.

I/O/dependency-bound:

```text
local CPU/memory normal
+
duration high
+
trace dependency slow
→ investigate remote dependency/network
```

Cold-start pattern:

```text
only some invocations slow
+
initialization correlates with slowdown
→ investigate cold-start behavior
```

Do not increase Lambda memory automatically before locating where time is spent.

#### 4.3.8.9 Distributed Performance Analysis

##### 4.3.8.9.1 X-Ray / Trace Model

Distributed traces show:
- request path,
- service/dependency timing,
- errors/faults,
- segments/subsegments,
- upstream/downstream relationships.

Use the trace map/timeline to answer:

```text
Which service, dependency, node, or edge dominates latency?
```

Example:

```text
API Gateway        5 ms
Lambda local      20 ms
DynamoDB         300 ms
```

Correct conclusion:
- investigate DynamoDB/downstream behavior.

Wrong conclusion:
- Lambda is slow, so immediately add memory.

##### 4.3.8.9.2 Upstream vs Downstream Timing
The caller observes:
- round-trip latency.

The downstream service observes:
- its own processing duration.

Difference can reveal:
- network time,
- queueing,
- integration/client overhead.

When possible:
- analyze both perspectives.

##### 4.3.8.9.3 CloudWatch Application Signals
Application Signals provides:
- call volume,
- availability,
- latency,
- faults,
- errors,
- services,
- operations,
- dependencies,
- topology,
- SLO context.

Use it to:
- identify the slow/unhealthy service,
- drill into dependency relationships,
- correlate to traces.

##### 4.3.8.9.4 Runtime Metrics
For supported instrumented applications, Application Signals runtime metrics can include:
- CPU,
- memory,
- garbage collection.

Correlation pattern:

```text
latency spike
+
memory/GC spike
→ investigate runtime pressure
```

This connects:
- user-visible performance

to:
- runtime behavior.

#### 4.3.8.10 Workload and Dependency Signals

##### 4.3.8.10.1 Traffic Context
Always interpret latency relative to:
- request volume,
- concurrency,
- throughput,
- dependency load.

Example:

```text
latency rises
+
traffic doubles
→ capacity/load hypothesis

latency rises
+
traffic unchanged
→ code/dependency/configuration hypothesis
```

##### 4.3.8.10.2 Throttling
Throttling indicates:
- a quota/capacity boundary.

It can cause:
- rejected requests,
- retries,
- queue growth,
- increased latency,
- lower effective throughput.

Determine:
- which service throttles,
- which limit is reached,
- whether traffic changed.

##### 4.3.8.10.3 Queue/Stream Backlog

```text
producer rate
>
consumer processing rate
→ backlog/record age grows
```

Possible causes:
- slow consumer,
- insufficient effective concurrency,
- downstream throttling,
- errors/retries.

Correlate:
- backlog/age,
- consumer duration,
- errors,
- concurrency,
- throttles.

##### 4.3.8.10.4 Database Bottlenecks
If trace/database timing dominates, inspect:
- access pattern,
- request volume,
- throttling,
- capacity,
- repeated reads,
- scan/query behavior where applicable.

More application compute:
- does not automatically fix a database bottleneck.

##### 4.3.8.10.5 Cache Performance
Cache problems can appear as:

```text
cache misses rise
→ backend requests rise
→ latency rises
```

Investigate:
- TTL,
- cache key,
- evictions,
- working-set size,
- invalidation.

Detailed cache implementation:
- 4.3.6.

##### 4.3.8.10.6 Deployment Correlation

```text
deployment
→ latency regression
```

Compare:
- before vs after,
- old vs new version,
- code/configuration/dependency/payload changes.

##### 4.3.8.10.7 Intermittent / Tail Problems
Average latency can hide:
- sporadic slow requests.

Use:
- p95/p99,
- duration-filtered traces,
- correlated logs.

Common sources:
- cold starts,
- specific dependencies,
- large inputs,
- retries,
- contention,
- occasional external-service latency.

##### 4.3.8.10.8 Custom Metrics
Infrastructure metrics may be insufficient.

Useful application metrics can include:
- operation duration,
- cache misses,
- payload size,
- items processed,
- external API latency.

Use custom metrics when they add:
- application/business context

to:
- performance analysis.

#### 4.3.8.11 Bottleneck Categories

| Pattern | Likely category |
|---|---|
| Compute dominates, dependency time low | CPU/code bound |
| Memory/GC pressure correlates with latency | Memory/runtime bound |
| Local resources normal, remote call dominates | I/O/network/dependency bound |
| Throttles/backlog appear at quota boundary | Capacity bound |
| High parallel demand causes shared-resource pressure | Contention/concurrency bound |

---

#### 4.3.8.12 Analysis Workflow

```text
define symptom
→ establish time window and baseline
→ inspect traffic / latency / errors / throttles / concurrency
→ inspect trace path / topology
→ inspect suspect component runtime/service metrics
→ use logs for detailed behavior
→ form hypothesis
→ verify with correlated evidence
→ optimize
```

Questions to answer:
- Is the problem latency, throughput, timeout, throttling, backlog, or cost?
- Is it constant, intermittent, or load-dependent?
- Did traffic change?
- Did deployment/configuration change?
- Which service/dependency dominates time?
- Is local runtime under CPU/memory/GC pressure?
- Is a quota/capacity boundary reached?
- Is backlog growing because consumers cannot keep pace?

##### 4.3.8.12.1 Practical Pattern Summary

| Observation | Investigation direction |
|---|---|
| Duration doubled, local memory unchanged, dependency trace doubled | Dependency latency |
| `ConcurrentExecutions` hits limit + `Throttles` rise | Concurrency constraint |
| Average stable, p95/p99 rises | Tail-latency requests |
| Memory/GC and latency rise together | Runtime memory/GC pressure |
| Queue age rises while consumer duration rises | Consumer/dependency throughput problem |
| Latency rises immediately after release, traffic unchanged | Deployment regression |
| CPU/memory low but duration high | I/O/network/dependency wait |
| Traffic increases, throttles begin | Find first constrained capacity boundary |

#### 4.3.8.13 Common Exam Traps

##### 4.3.8.13.1 Slow Lambda Means Add Memory
- Wrong.
- First determine:
  - where time is spent.

##### 4.3.8.13.2 Average Latency Is Enough
- Wrong.
- Tail latency:
  - may require percentiles.

##### 4.3.8.13.3 High Concurrency Means Bottleneck
- Not necessarily.
- Look for:
  - limits,
  - throttles,
  - backlog,
  - dependency pressure.

##### 4.3.8.13.4 Errors Are Unrelated to Performance
- Wrong.
- Timeouts/retries/throttling:
  - connect performance and reliability.

##### 4.3.8.13.5 Trace Only the Application Service
- Wrong for distributed systems.
- Need:
  - end-to-end dependency visibility.

##### 4.3.8.13.6 Increase Producer Throughput When Consumer Is Behind
- Wrong.
- Can:
  - worsen backlog.

##### 4.3.8.13.7 Low CPU Means No Performance Problem
- Wrong.
- Application may:
  - wait on I/O/dependencies.

##### 4.3.8.13.8 One Metric Proves Root Cause
- Usually wrong.
- Correlate:
  - multiple signals.

##### 4.3.8.13.9 Optimize Before Measuring
- Wrong.
- Establish:
  - evidence and baseline first.

##### 4.3.8.13.10 Logs Are the Only Performance Tool
- Wrong.
- Use:
  - metrics,
  - traces,
  - runtime metrics,
  - logs.
- Skill 4.3.9 specifically deepens:
  - log-based bottleneck analysis.

#### 4.3.8.16 Exam-Level Knowledge Frame

##### 4.3.8.16.1 Core Rule

```text
performance symptom
→ quantify with metrics
→ locate with traces/topology
→ explain with runtime metrics/logs
→ verify root cause
→ optimize
```

##### 4.3.8.16.2 Lambda Signals

```text
Duration
→ execution latency

Errors
→ failed invocations

Throttles
→ rejected requests due to unavailable concurrency

ConcurrentExecutions
→ active concurrency
```

##### 4.3.8.16.3 Trace Rule

```text
distributed request slow
→ find dominant segment/node/edge
→ investigate that dependency/component
```

##### 4.3.8.16.4 Runtime Rule

```text
latency spike
+
CPU/memory/GC spike
→ investigate runtime/resource pressure
```

##### 4.3.8.16.5 Tail-Latency Rule

```text
average normal
+
p95/p99 high
→ inspect slow minority of requests
```

##### 4.3.8.16.6 Fastest Exam Discriminator

```text
which service is slow?
→ X-Ray trace / Application Signals

Lambda CPU-memory-network evidence?
→ Lambda Insights

Lambda reaches concurrency + throttles?
→ concurrency constraint

average hides sporadic slowdown?
→ percentiles

local resources normal + dependency trace slow?
→ downstream bottleneck

backlog age rising?
→ consumer throughput < incoming work
```

##### 4.3.8.16.7 Final Principle
- **Analyze application performance from the user-visible symptom inward. Use metrics to establish when and how performance changed, traces to locate where request time is spent, and runtime metrics/logs to explain why that component is slow. Change resources only after the evidence identifies the bottleneck.**
