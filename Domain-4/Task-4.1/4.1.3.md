### 4.1.3 Query logs to find relevant data

#### 4.1.3.1 Exam and Task Context

##### 4.1.3.1.1 Domain and Task
- Domain 4 is **Troubleshooting and Optimization**.
- Task 4.1 is **Assist in a root cause analysis**.
- Skill 4.1.3 is **Query logs to find relevant data**.

##### 4.1.3.1.2 Position Inside Task 4.1
- 4.1.2:
  - interpret metrics, logs, and traces.
- 4.1.3:
  - query existing logs to isolate relevant evidence.
- 4.1.4:
  - implement custom metrics.

Core question:

**How do you reduce a large CloudWatch Logs dataset into the small set of events, fields, counts, and time windows needed for troubleshooting?**

#### 4.1.3.2 Core Mental Model

```text
large log dataset
      |
      v
correct log group(s)
      |
      v
narrow time range
      |
      v
filter
      |
      v
fields / parse
      |
      v
stats / sort / limit
      |
      v
small evidence set
```

The goal is not:

```text
read every log line
```

It is:

```text
ask a precise question
→ query only the evidence needed
```

#### 4.1.3.3 CloudWatch Logs Insights

CloudWatch Logs Insights is:
- the primary AWS log-query capability for this skill.

It can:
- search log events,
- filter them,
- extract fields,
- aggregate values,
- sort results,
- create time-based summaries,
- visualize aggregated results.

Current CloudWatch Log Analytics provides a broader console experience around:
- Logs Insights,
- Live Tail,
- Contributor Insights.

For DVA-C02:
- **Logs Insights query semantics are the core exam knowledge.**

#### 4.1.3.4 Query Pipeline

Logs Insights QL uses commands separated by:

```text
|
```

Example:

```text
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 20
```

Mental model:

```text
input
→ select fields
→ filter
→ aggregate/order
→ return useful result
```

#### 4.1.3.5 Important System Fields

For supported Standard-class log groups, Logs Insights automatically exposes fields including:

```text
@message
@timestamp
@ingestionTime
@logStream
@log
```

Know these:

```text
@timestamp
→ event time

@message
→ raw log event

@ingestionTime
→ when CloudWatch Logs received the event

@logStream
→ source log stream

@log
→ account/log-group identifier
```

#### 4.1.3.6 Event Time vs Ingestion Time

```text
@timestamp
→ when event occurred

@ingestionTime
→ when CloudWatch received it
```

If:

```text
@ingestionTime
>>
@timestamp
```

possible explanation:
- delivery/ingestion delay.

For normal incident chronology:
- usually start with `@timestamp`.

#### 4.1.3.7 Query Scope First

AWS explicitly recommends:
- select only required log groups,
- use the narrowest useful time range.

Weak:

```text
30 days
+
all production log groups
+
one request ID
```

Better:

```text
14:00–14:10
+
relevant Lambda/API log groups
+
request ID
```

Benefits:
- less scanned data,
- lower query cost,
- faster result,
- less noise.

Core rule:

```text
scope first
→ query second
```

#### 4.1.3.8 `fields`

`fields`:
- selects displayed/queryable fields,
- can create calculated values.

Example:

```text
fields @timestamp, @message, requestId
```

Use it to:
- reduce noise,
- focus on meaningful columns,
- derive fields where needed.

#### 4.1.3.9 `filter`

`filter` keeps:
- only matching events.

Structured example:

```text
filter level = "ERROR"
```

Unstructured example:

```text
filter @message like /Exception/
```

This is the primary command for:

```text
large dataset
→ relevant subset
```

#### 4.1.3.10 Structured Field vs Raw-Text Search

If a structured field already exists:

```text
filter requestId = "abc-123"
```

prefer it over:

```text
filter @message like /abc-123/
```

Why:
- more precise,
- easier to maintain,
- compatible with field indexing,
- avoids accidental text matches.

Rule:

```text
structured field exists
→ query field directly
```

#### 4.1.3.11 `like`, `not like`, and Multiple Conditions

##### 4.1.3.11.1 `like`

```text
filter @message like /Exception/
```

Useful for:
- text/pattern matching.

##### 4.1.3.11.2 `not like`

```text
filter @message not like /healthcheck/
```

Useful for:
- excluding known noisy events.

##### 4.1.3.11.3 Multiple Conditions

```text
filter level = "ERROR"
  and service = "checkout"
```

Use:
- `and` when all conditions must match,
- `or` when either condition is relevant.

#### 4.1.3.12 Query by Request or Correlation ID

Known request ID:

```text
fields @timestamp, @message
| filter requestId = "abc-123"
| sort @timestamp asc
```

Purpose:

```text
one request
→ chronological execution
```

Known correlation ID:

```text
fields @timestamp, @log, @message
| filter correlationId = "order-123"
| sort @timestamp asc
```

Purpose:
- follow one business transaction across selected logs.

If an identifier is known:
- start narrow.

#### 4.1.3.13 `sort`

Use:

```text
sort field asc
```

or:

```text
sort field desc
```

Common examples:

```text
sort @timestamp desc
→ newest first
```

```text
sort @timestamp asc
→ chronological request flow
```

#### 4.1.3.14 `limit`

Use:

```text
limit N
```

to restrict:
- returned rows.

Example:

```text
limit 20
```

Current AWS documentation states:
- omitted `limit` returns up to 10,000 events,
- explicit `limit` can be up to 100,000.

Critical rule:

```text
limit 20
→ limits returned results

does not necessarily
→ reduce scanned data
```

So regular `limit` is not:
- the main cost optimization.

#### 4.1.3.15 `limit any`

Current Logs Insights QL supports:

```text
limit any N
```

This can stop scanning:
- once enough matching events are found.

Example:

```text
fields @message
| filter @message like /ERROR/
| limit any 1
```

Use when:

```text
I only need any matching example
```

Tradeoff:
- result ordering is not guaranteed.

#### 4.1.3.16 `stats`

`stats` performs:
- aggregation.

Examples:

```text
stats count(*)
```

```text
stats count(*) by errorType
```

```text
stats avg(duration) by operation
```

Common functions:
- `count()`,
- `sum()`,
- `avg()`,
- `min()`,
- `max()`.

Use when the question is:

```text
how many?
which group dominates?
what is average?
what is worst?
```

#### 4.1.3.17 Count and Rank Errors

Example:

```text
filter level = "ERROR"
| stats count(*) as failures by errorType
| sort failures desc
```

Question:

```text
Which error type occurs most?
```

Top contributor pattern:

```text
stats count(*) as failures by customerId
| sort failures desc
| limit 10
```

Question:

```text
Which customers/resources account for most failures?
```

#### 4.1.3.18 `bin()`

`bin()` creates:
- time buckets.

Example:

```text
stats count(*) by bin(5m)
```

Question:

```text
How did event frequency change every five minutes?
```

Error trend:

```text
filter level = "ERROR"
| stats count(*) as errors by bin(5m)
```

This can reveal:
- incident start,
- deployment regression,
- burst behavior.

#### 4.1.3.19 `parse`

Use `parse` to extract:
- fields from unstructured text.

Example log:

```text
method=GET, latency=125
```

Query:

```text
parse @message "method=*, latency=*" as method, latency
```

Now:

```text
method
latency
```

can be:
- filtered,
- grouped,
- aggregated.

Mental model:

```text
unstructured text
→ parse
→ structured fields
```

#### 4.1.3.20 Parse Modes

Useful parsing approaches include:
- glob,
- regular expression,
- other structured extraction modes documented by AWS.

Glob example:

```text
parse @message "status=*, duration=*" as status, duration
```

Regex example:

```text
parse @message /user=(?<user>.*?), latency=(?<latency>\d+)/
```

Use:
- glob for predictable text,
- regex when flexible matching is required.

#### 4.1.3.21 Parse Then Aggregate

Example:

```text
parse @message "method=*, latency=*" as method, latency
| stats avg(latency) by method
```

Question:

```text
Which operation has highest average latency?
```

Core pattern:

```text
text
→ parse
→ stats
```

#### 4.1.3.22 Structured JSON Logs

If logs are structured JSON, Logs Insights can automatically discover supported fields.

Example:

```json
{
  "level": "ERROR",
  "requestId": "abc",
  "duration": 1500
}
```

Then:

```text
filter level = "ERROR"
| stats avg(duration)
```

No manual parsing is needed.

Preferred mental model:

```text
structured field exists
→ query directly

unstructured message
→ parse
```

#### 4.1.3.23 `dedup`

`dedup` removes duplicate result rows based on selected fields.

Example:

```text
dedup requestId
```

Useful when:
- many log events represent the same logical item,
- one representative result is enough.

Do not use when:
- duplicate events themselves are the symptom.

#### 4.1.3.24 `pattern`

`pattern` groups:
- recurring log-message shapes.

Useful when:

```text
large unknown log set
→ what message patterns dominate?
```

This helps:
- discover common log structures,
- identify unexpected new classes of messages.

#### 4.1.3.25 `diff`

`diff` compares:
- the current time range,
- with the previous equal-length time range.

Question:

```text
What log patterns are new or changed since the incident/deployment?
```

Useful for:
- regression analysis.

Example thinking:

```text
before release
vs
after release
→ identify newly appearing error pattern
```

#### 4.1.3.26 Field Indexes and `filterIndex`

Field indexes can reduce:
- data scanned for exact indexed-field searches.

Concept:

```text
indexed requestId
→ exact requestId query
→ reduce irrelevant scan
```

`filterIndex` can direct Logs Insights to use:
- a field index/value where supported.

Important limitation:
- `filterIndex` is not supported for Infrequent Access log groups.

Rule:

```text
field-index optimization
→ depends on log class/support
```

#### 4.1.3.27 `SOURCE`

`SOURCE` can select log groups programmatically based on criteria such as:
- name prefix,
- account,
- log class.

Important restriction:

```text
SOURCE
→ CLI/API programmatic query context

not
→ CloudWatch console query editor
```

Use when:
- querying broad multi-group estates programmatically.

#### 4.1.3.28 Cross-Account Querying

With CloudWatch cross-account observability:

```text
monitoring account
→ query configured source-account log groups
```

Do not assume:
- cross-account logs are automatically visible.

Required:
- observability configuration,
- appropriate permissions/access.

#### 4.1.3.29 Query by Resource Tag

Current Logs Insights capabilities can expose AWS resource-tag context for supported scenarios.

Example concept:

```text
filter @aws.tag.env = "production"
```

Useful for:

```text
shared log estate
→ isolate production/team/application resources
```

For DVA-C02:
- know the filtering concept,
- not every tag-field implementation detail.

#### 4.1.3.30 Common Troubleshooting Queries

##### 4.1.3.30.1 Latest Errors

```text
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 20
```

##### 4.1.3.30.2 One Exact Exception

```text
fields @timestamp, @message
| filter @message like /AccessDeniedException/
| sort @timestamp desc
```

##### 4.1.3.30.3 Exception Frequency Over Time

```text
filter @message like /Exception/
| stats count(*) by bin(5m)
```

##### 4.1.3.30.4 Slowest Operations

```text
stats avg(duration) as avgDuration,
      max(duration) as maxDuration
  by operation
| sort avgDuration desc
| limit 10
```

#### 4.1.3.31 Service-Specific Log Examples

##### 4.1.3.31.1 Lambda
Typical investigation:

```text
fields @timestamp, @message
| filter @message like /ERROR|Exception|Task timed out/
| sort @timestamp desc
| limit 50
```

Then narrow by:
- request ID,
- exception,
- incident time.

##### 4.1.3.31.2 API Gateway
Possible questions:
- which routes fail?
- which 5xx status codes dominate?
- which requests show high latency?

Example:

```text
filter status >= 500
| stats count(*) by routeKey
```

Available fields depend on:
- configured log format.

##### 4.1.3.31.3 VPC Flow Logs
Useful question:

```text
Is traffic being rejected?
```

Logs Insights can aggregate:
- `REJECT` records,
- source/destination,
- packets/bytes.

##### 4.1.3.31.4 CloudTrail Logs
If CloudTrail events are delivered to CloudWatch Logs:

```text
filter errorCode = "AccessDenied"
| stats count(*) by eventName
```

Useful for:
- authorization/API-call troubleshooting.

#### 4.1.3.32 Logs Insights vs Other Telemetry Tools

##### 4.1.3.32.1 Logs Insights vs Metrics
Logs Insights:

```text
queries log events
```

CloudWatch Metrics:

```text
queries/visualizes metric time series
```

Even when Logs Insights aggregates:
- the source remains logs.

##### 4.1.3.32.2 Logs Insights vs X-Ray
Logs Insights:
- searches logs.

X-Ray:
- traces distributed requests.

A trace ID can connect them:

```text
X-Ray trace
↔ traceId in logs
```

but they remain:
- different telemetry systems.

##### 4.1.3.32.3 Logs Insights vs Live Tail
Live Tail:

```text
what is happening now?
```

Logs Insights:

```text
what happened in this stored incident window?
```

##### 4.1.3.32.4 Logs Insights vs Contributor Insights
Contributor Insights:
- continuous/top-contributor analysis using rules.

Logs Insights:
- ad hoc interactive investigation.

For one-off troubleshooting:
- Logs Insights is usually the direct fit.

#### 4.1.3.33 Query Cost Mental Model

Query cost/performance is driven mainly by:

```text
data scanned
```

Optimize with:

```text
narrow time range
+
only necessary log groups
+
precise filters/indexes where useful
```

Not merely:

```text
limit 10
```

Strong query:

```text
known request ID
+
10-minute window
+
correct log groups
```

Weak query:

```text
"ERROR"
+
all production logs
+
30 days
```

#### 4.1.3.34 Start Broad vs Start Narrow

##### 4.1.3.34.1 Root Cause Unknown

```text
1. choose incident window
2. inspect errors/recent events
3. identify pattern/field
4. narrow filter
5. aggregate
6. isolate request/component
```

Do not:
- over-filter before understanding the evidence.

##### 4.1.3.34.2 Identifier Known

If you already know:
- request ID,
- trace ID,
- order ID,
- error code,

start with:
- exact field filter.

No need to:
- rediscover broadly.

#### 4.1.3.35 Natural-Language Query Assistance

Current CloudWatch Logs capabilities can help:
- generate queries from natural language,
- summarize query results.

These can accelerate:
- query authoring,
- interpretation.

But:

```text
AI-generated query/summary
≠ evidence
```

Always verify:
- generated query,
- actual returned events,
- aggregation semantics.

#### 4.1.3.36 Decision Flow

##### 4.1.3.36.1 Scope

```text
incident time known?
→ narrow time range

service/application known?
→ select only relevant log groups
```

##### 4.1.3.36.2 Structure

```text
structured field exists?
→ filter field directly

unstructured text?
→ parse @message
```

##### 4.1.3.36.3 Question Type

```text
need individual events?
→ fields + filter + sort + limit

need counts/averages/groups?
→ stats

need time trend?
→ stats ... by bin(...)

need unknown recurring patterns?
→ pattern

need changes vs previous window?
→ diff

need one arbitrary example?
→ limit any

need indexed exact-field optimization?
→ field index / filterIndex where supported
```

#### 4.1.3.37 Common Exam Traps

##### 4.1.3.37.1 `limit 20` Means Only 20 Events Are Scanned
- False.

##### 4.1.3.37.2 Query All Log Groups for Safety
- Usually wrong.
- Select only necessary groups.

##### 4.1.3.37.3 Use Longest Possible Time Range
- Wrong.
- Use narrowest useful range.

##### 4.1.3.37.4 `parse` Filters Events
- False.
- `parse` extracts fields.
- `filter` selects events.

##### 4.1.3.37.5 `stats` Returns Raw Events
- False.
- `stats` aggregates.

##### 4.1.3.37.6 `sort @timestamp desc` Means Oldest First
- False.
- It means newest first.

##### 4.1.3.37.7 `@message` Is Timestamp
- False.

```text
@message
→ raw event

@timestamp
→ event time
```

##### 4.1.3.37.8 `@ingestionTime` = `@timestamp`
- False.

##### 4.1.3.37.9 JSON Logs Must Always Be Parsed
- False.
- Supported structured fields can be discovered automatically.

##### 4.1.3.37.10 `SOURCE` Works in Console Query Editor
- False.

##### 4.1.3.37.11 `filterIndex` Works for Every Log Class
- False.

##### 4.1.3.37.12 Logs Insights Queries Native Metrics
- False.

#### 4.1.3.40 Exam-Level Knowledge Frame

##### 4.1.3.40.1 Know These Cold

**`fields`**
→ select/calculate fields.

**`filter`**
→ keep matching events.

**`parse`**
→ extract fields from text.

**`stats`**
→ aggregate.

**`sort`**
→ order results.

**`limit`**
→ restrict returned results.

**`limit any`**
→ stop after enough arbitrary matches.

**`bin()`**
→ group into time buckets.

**`pattern`**
→ cluster recurring message patterns.

**`diff`**
→ compare current vs previous equal-length window.

**`@timestamp`**
→ event time.

**`@message`**
→ raw log event.

**Query scope**
→ minimize scanned data with narrow time range and relevant log groups.

##### 4.1.3.40.2 Fastest Exam Discriminator

```text
find matching events?
→ filter

show fields?
→ fields

extract fields from text?
→ parse

count/group/average?
→ stats

time buckets?
→ bin()

newest first?
→ sort @timestamp desc

oldest first?
→ sort @timestamp asc

top 20 returned?
→ limit 20

stop after any N matches?
→ limit any N

unknown recurring message shapes?
→ pattern

compare with previous time window?
→ diff

raw event?
→ @message

event time?
→ @timestamp
```

##### 4.1.3.40.3 Final Principle
- **Query logs by narrowing the search space before increasing query complexity. Select only the relevant CloudWatch log groups and the smallest useful time window, then use Logs Insights QL to transform raw events into evidence: `filter` isolates matching events, `fields` focuses the result, `parse` extracts structure from text, `stats` aggregates, `bin()` creates time buckets, `sort` orders results, and `limit` controls returned rows. Prefer discovered structured fields and exact identifiers such as request IDs when available. Remember that regular `limit` does not inherently reduce scanned data; query scope and time range are the primary controls, while field indexes and `limit any` can reduce work in suitable cases. Use `pattern` or `diff` when the problem is discovering recurring or newly introduced log behavior.**
