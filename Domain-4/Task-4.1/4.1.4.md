### 4.1.4 Implement custom metrics (for example, Amazon CloudWatch embedded metric format [EMF])

#### 4.1.4.1 Exam and Task Context

##### 4.1.4.1.1 Domain and Task
- Domain 4 is **Troubleshooting and Optimization**.
- Task 4.1 is **Assist in a root cause analysis**.
- Skill 4.1.4 is **Implement custom metrics (for example, Amazon CloudWatch embedded metric format [EMF])**.

##### 4.1.4.1.2 Position Inside Task 4.1

  - interpret metrics, logs, and traces.
- 4.1.3:
  - query logs.
- 4.1.4:
  - create application-specific metrics.
- 4.1.5:
  - review application health with dashboards and insights.

Core question:

**How do you expose application or business behavior as CloudWatch metrics when native AWS metrics do not provide the signal you need?**

#### 4.1.4.2 Core Mental Model

```text
application event
      |
      v
measurement
      |
      v
CUSTOM METRIC
      |
      +--> namespace
      +--> metric name
      +--> value
      +--> unit
      +--> dimensions
      +--> resolution
      |
      v
CloudWatch
      |
      +--> graph
      +--> alarm
      +--> dashboard
      '--> root-cause correlation
```

The key design problem is not only:

```text
how do I emit a number?
```

It is:

```text
what does this metric mean
+
how is it identified
+
how expensive will its dimensional model become?
```

#### 4.1.4.3 Native Metric vs Custom Metric

##### 4.1.4.3.1 Native AWS Metric
Published automatically by AWS services.

Example:

```text
AWS/Lambda
→ Invocations
→ Errors
→ Duration
→ Throttles
```

Use the native metric when:
- it already answers the operational question.

##### 4.1.4.3.2 Custom Metric
Created by:
- application code,
- telemetry pipeline,
- log-derived mechanism.

Examples:

```text
CheckoutFailures
PaymentLatency
OrderValue
InvalidPayloadCount
RetryCount
```

Use when:

```text
AWS service health
≠ enough to describe application/business behavior
```

#### 4.1.4.4 Metric Identity

CloudWatch custom metric identity is built from:

```text
namespace
+
metric name
+
dimension combination
```

Therefore:

```text
same metric name
+
different dimensions
→ different time series
```

This is central to:
- analysis,
- cardinality,
- cost.

#### 4.1.4.5 Namespace

Custom metrics use:
- a custom CloudWatch namespace.

Examples:

```text
OrdersService
CheckoutApplication
ServerlessEcommerce
```

Do not use:

```text
AWS/...
```

for a custom namespace because:
- AWS-reserved namespaces use the `AWS` prefix.

Good principle:
- keep namespace stable,
- group related metrics together.

Avoid:
- namespace per request,
- namespace per user,
- namespace per deployment.

#### 4.1.4.6 Metric Name and Value

##### 4.1.4.6.1 Metric Name
Strong:

```text
CheckoutFailures
OrderProcessingLatency
PaymentDeclines
ItemsProcessed
```

Weak:

```text
Metric1
Value
Data
```

Metric name should describe:
- what is measured.

##### 4.1.4.6.2 Metric Value
Metric data points are numeric.

Examples:

```text
CheckoutFailures = 1
OrderLatency = 245
QueueRetries = 3
```

Interpretation depends on:
- unit,
- statistic,
- period,
- dimensions.

#### 4.1.4.7 Unit

Examples of supported semantic units include:

```text
Count
Milliseconds
Seconds
Bytes
Percent
Count/Second
None
```

Choose the unit that matches:
- measurement meaning.

Example:

```text
OrderProcessingLatency
→ Milliseconds
```

Do not publish ambiguous values when:
- consumers need reliable interpretation.

#### 4.1.4.8 Dimensions

Dimensions are:

```text
name=value pairs
```

that help define:
- a metric time series.

Example:

```text
Metric:
CheckoutFailures

Dimensions:
Environment=prod
Service=Checkout
```

Each unique dimension combination creates:
- a distinct custom metric/time series.

Current CloudWatch custom metrics support:
- up to 30 dimensions per metric.

But:

```text
maximum allowed
≠ recommended design target
```

Use only dimensions that:
- answer a real operational question.

#### 4.1.4.9 Cardinality

##### 4.1.4.9.1 High Cardinality
Dangerous examples:

```text
requestId
userId
orderId
traceId
timestamp
```

If used as dimensions:

```text
many unique values
→ many unique metric identities
→ higher custom metric count
→ potentially higher cost
```

##### 4.1.4.9.2 Better Dimension Candidates
Typically bounded examples:

```text
Environment
Service
Operation
Region
Result
PaymentProvider
```

provided:
- value sets remain bounded.

Example:

```text
Result=Success|Failure
```

is much safer than:

```text
OrderId=<millions of values>
```

#### 4.1.4.10 Dimension vs Metadata

This distinction is especially important with EMF.

```text
dimension
→ part of metric identity
→ affects cardinality/cost
```

```text
metadata
→ remains in log event
→ queryable for troubleshooting
→ does not create separate metric time series
```

Good pattern:

```text
Environment
→ dimension

requestId
→ log metadata
```

Fast rule:

```text
need to aggregate/filter metric by value?
→ maybe dimension

need detailed request context?
→ metadata/log field
```

#### 4.1.4.11 Embedded Metric Format

CloudWatch EMF is:

```text
structured JSON log format
```

that tells CloudWatch:

```text
extract these numeric fields
→ create custom metrics
```

Flow:

```text
application
→ EMF JSON log event
→ CloudWatch Logs
→ asynchronous metric extraction
→ CloudWatch Metrics
```

The log event remains:
- available as log data.

This is a major EMF benefit:

```text
metric
+
diagnostic context
→ same structured event
```

#### 4.1.4.12 Why EMF Matters

Without EMF:

```text
application
→ PutMetricData
→ CloudWatch Metrics
```

With EMF:

```text
application
→ structured log
→ CloudWatch Logs
→ metric extraction
```

Advantages:
- asynchronous metric extraction,
- avoids synchronous metric API call in request path,
- keeps detailed context in logs,
- good fit for Lambda, containers, ephemeral compute.

#### 4.1.4.13 EMF Structure

Conceptual example:

```json
{
  "_aws": {
    "Timestamp": 1750000000000,
    "CloudWatchMetrics": [
      {
        "Namespace": "OrdersService",
        "Dimensions": [["Environment"]],
        "Metrics": [
          {
            "Name": "OrderLatency",
            "Unit": "Milliseconds"
          }
        ]
      }
    ]
  },
  "Environment": "prod",
  "OrderLatency": 245,
  "requestId": "abc-123"
}
```

CloudWatch extracts:

```text
Namespace:
OrdersService

Metric:
OrderLatency

Dimension:
Environment=prod

Value:
245 ms
```

while:

```text
requestId
```

remains:
- log context.

#### 4.1.4.14 `_aws` and `CloudWatchMetrics`

##### 4.1.4.14.1 `_aws`
EMF requires:
- valid `_aws` metadata.

It carries:
- timestamp,
- metric directives,
- namespace,
- dimensions,
- metric definitions.

Important:

```text
JSON log
≠ automatically EMF
```

##### 4.1.4.14.2 `CloudWatchMetrics`
Defines:
- namespace,
- dimension sets,
- metrics to extract.

Mental model:

```text
payload values
+
CloudWatchMetrics declaration
→ metric extraction
```

#### 4.1.4.15 Metric Definition

Each EMF metric definition can include:

```text
Name
Unit
StorageResolution
```

Example:

```json
{
  "Name": "OrderLatency",
  "Unit": "Milliseconds",
  "StorageResolution": 60
}
```

The numeric value appears:
- elsewhere in the same JSON event under the metric name.

#### 4.1.4.16 Standard vs High Resolution

##### 4.1.4.16.1 Standard Resolution

```text
60-second granularity
```

Use when:
- one-minute detail is sufficient,
- normal monitoring is adequate.

##### 4.1.4.16.2 High Resolution

```text
StorageResolution = 1
→ 1-second granularity
```

Useful for:
- short spikes,
- burst behavior,
- sub-minute detection.

Tradeoff:
- potentially higher cost.

Rule:

```text
need sub-minute visibility?
→ high resolution

otherwise
→ standard resolution
```

Do not select high resolution:
- by default.

#### 4.1.4.17 EMF Limits and Delivery Semantics

Current EMF specification includes:
- maximum 1 MB log event size,
- up to 100 metric definitions per metric directive,
- at-least-once delivery.

Important implication:

```text
duplicate extracted metric values
→ can occasionally occur
```

Therefore custom metrics are:
- observability signals,

not:
- exactly-once transactional records.

Do not use metrics as:
- financial/accounting source of truth.

#### 4.1.4.18 EMF Validation

If:

```text
EMF log visible
but
metric missing
```

check:
- valid JSON,
- `_aws`,
- `CloudWatchMetrics`,
- namespace,
- metric value numeric,
- dimension fields present,
- unit/resolution valid.

CloudWatch publishes EMF processing metrics under:

```text
AWS/Logs
```

which can indicate:
- parsing,
- validation,
- extraction failures.

#### 4.1.4.19 PutMetricData

Alternative:

```text
application
→ CloudWatch PutMetricData API
→ CloudWatch Metrics
```

A request can specify:
- namespace,
- metric name,
- value/statistic set,
- unit,
- dimensions,
- timestamp,
- resolution.

Use when:
- direct metric API publishing is appropriate.

Example:

```bash
aws cloudwatch put-metric-data \
  --namespace OrdersService \
  --metric-name CheckoutFailures \
  --value 1 \
  --unit Count \
  --dimensions Environment=prod
```

#### 4.1.4.20 EMF vs PutMetricData

##### 4.1.4.20.1 EMF

```text
structured log
→ CloudWatch Logs
→ async metric extraction
```

Strong when:
- workload already logs,
- Lambda/container workload,
- metric + detailed context needed,
- request-path latency should stay low.

##### 4.1.4.20.2 PutMetricData

```text
explicit CloudWatch API call
→ direct custom metric
```

Strong when:
- direct API publication is appropriate,
- telemetry is not naturally log-driven.

High-value exam clue:

```text
Lambda custom metric
+
minimize request latency
→ EMF
```

#### 4.1.4.21 Lambda and EMF

AWS Lambda best practices recommend:

```text
emit custom metrics asynchronously using EMF
```

instead of:
- synchronous CloudWatch metric API calls from Lambda code.

Reason:
- lower latency / better performance.

Therefore:

```text
Lambda invocation
→ structured EMF log
→ asynchronous metric extraction
```

is a strong default mental model.

#### 4.1.4.22 Powertools for AWS Lambda Metrics

Powertools Metrics helps:
- emit EMF correctly.

Capabilities include:
- metric buffering,
- EMF formatting,
- validation,
- dimensions,
- metadata,
- flush/publish helpers.

Concept:

```text
application code
→ Powertools Metrics
→ EMF JSON
→ logs
→ CloudWatch metric
```

Example concept:

```java
metrics.addMetric(
    "OrderCreated",
    MetricUnit.COUNT,
    1
);
```

Exact API:
- depends on language.

For DVA-C02:
- know Powertools simplifies EMF creation.

#### 4.1.4.23 Default Dimensions

Powertools can apply default dimensions such as:

```text
service=Orders
environment=prod
```

Use carefully.

Default dimensions should be:
- stable,
- bounded,
- useful.

Do not use:

```text
requestId
```

as a default dimension.

#### 4.1.4.24 Metric Filters

CloudWatch Logs metric filters provide another path:

```text
existing logs
→ pattern match
→ custom metric
```

Use when:
- logs already contain identifiable events,
- a simple metric can be derived,
- application code does not need to change.

Example:

```text
"Login failed"
→ metric filter
→ FailedLoginCount
```

#### 4.1.4.25 EMF vs Metric Filter

##### 4.1.4.25.1 EMF
Best for:
- structured application metrics,
- multiple metrics/context in one event,
- richer dimension design.

##### 4.1.4.25.2 Metric Filter
Best for:
- deriving a metric from existing log patterns,
- simple count/value extraction,
- avoiding application code changes.

Fast rule:

```text
application can emit metric-aware structured JSON?
→ EMF

existing text log already has event?
→ metric filter
```

#### 4.1.4.26 Count Metrics

For discrete events:

```text
OrderCreated
CheckoutFailure
Retry
```

publish:

```text
value = 1
unit = Count
```

Then use:

```text
Sum
```

to get:
- total events during a period.

Example:

```text
CheckoutFailure = 1
→ Sum over 5 minutes
→ number of failed checkouts
```

#### 4.1.4.27 Latency Metrics

For latency:

```text
value = elapsed time
unit = Milliseconds
```

Then inspect statistics such as:
- Average,
- p95,
- p99,
- Max.

Choose statistic according to:
- troubleshooting question.

#### 4.1.4.28 Ratios and Metric Math

Instead of always publishing a ratio directly, publish useful raw counters:

```text
SuccessCount
FailureCount
```

Then derive:

```text
FailureRate =
FailureCount /
(SuccessCount + FailureCount)
```

using:
- CloudWatch metric math where appropriate.

Benefits:
- preserves raw information,
- allows multiple derived calculations.

#### 4.1.4.29 Zero vs Missing Data

Important distinction:

```text
metric value = 0
≠
no datapoint
```

If zero is semantically meaningful:
- publish zero intentionally.

Example:

```text
QueueRetries = 0
```

This distinguishes:
- explicitly observed zero,

from:
- nothing emitted.

This matters for:
- dashboards,
- alarm missing-data behavior.

#### 4.1.4.30 Timestamp

Custom metrics can include:
- explicit timestamp.

Use when:
- event occurred earlier than emission time.

Be careful:
- do not publish stale/future timestamps outside supported limits.

With EMF:

```text
log event timestamp
```

and:

```text
EMF metric Timestamp
```

are related but:
- conceptually distinct metadata.

#### 4.1.4.31 Metric Aggregation

If multiple application instances emit:

```text
same namespace
same metric name
same dimensions
```

CloudWatch aggregates them into:
- the same time series.

This is useful for:
- service-level metrics.

If per-instance visibility is needed:
- use a bounded instance dimension only where justified.

Avoid dimensioning by:
- ephemeral Lambda execution environment,
- short-lived container instance
by default.

#### 4.1.4.32 Business and Technical Metrics

##### 4.1.4.32.1 Business Metrics

Examples:

```text
OrdersCreated
CheckoutFailures
PaymentDeclines
FraudChecksFailed
CartAbandonment
```

These can reveal:

```text
Lambda Errors = 0
but
PaymentDeclines ↑
```

meaning:
- infrastructure is healthy,
- business outcome is degraded.

##### 4.1.4.32.2 Technical Application Metrics

Examples:

```text
CacheHitRatio
DependencyLatency
RetryCount
ValidationFailures
MessageProcessingTime
```

Use when:
- they answer a concrete operational question.

#### 4.1.4.33 Metric Design Should Support Questions

Before creating a metric or dimension, ask:

```text
What operational question will this answer?
```

Examples:

```text
Which operation started failing?
Which dependency slowed down?
Did retry volume increase?
Did invalid requests spike?
Did a business path degrade?
```

If the metric cannot support:
- diagnosis,
- alerting,
- health review,

it may be:
- unnecessary telemetry.

#### 4.1.4.34 Dimension Design Examples

##### 4.1.4.34.1 Environment

```text
Environment=dev|test|prod
```

Good because:
- bounded,
- supports environment-specific dashboards/alarms.

##### 4.1.4.34.2 Operation

```text
Operation=CreateOrder
Operation=CancelOrder
```

Good when:
- operation set is bounded.

##### 4.1.4.34.3 Result

```text
Result=Success|Failure
```

May be useful.

But sometimes separate metrics:

```text
SuccessCount
FailureCount
```

are simpler.

##### 4.1.4.34.4 Service

```text
Namespace = Ecommerce
Metric = RequestLatency
Service = Checkout
```

Useful when:
- namespace is shared.

Potentially redundant when:
- each service already has its own namespace.

#### 4.1.4.35 Cardinality Mental Model

Before adding a dimension, ask:

```text
How many unique values can it have?
```

Then:

```text
How many combinations with existing dimensions?
```

Example:

```text
Environment = 3
Service = 10
Operation = 20
Result = 2
```

Potential combinations:

```text
3 × 10 × 20 × 2
= 1,200
```

Cardinality multiplies.

Therefore:

```text
namespace
+
metric name
+
dimension combination
→ unique custom metric
```

#### 4.1.4.36 High-Cardinality Identifiers

##### 4.1.4.36.1 Request ID

```text
requestId
→ usually metadata/log field
```

not:
- metric dimension.

##### 4.1.4.36.2 User ID

```text
UserId
→ potentially millions of values
```

If question is:

```text
which users fail most?
```

prefer:
- structured logs,
- Logs Insights,
- Contributor Insights

instead of:
- one metric series per user.

##### 4.1.4.36.3 Order ID

Same rule:

```text
OrderId
→ metadata
```

not:
- metric dimension by default.

#### 4.1.4.37 Metrics and Other Telemetry

##### 4.1.4.37.1 Metric vs Log

```text
metric
→ aggregate numeric signal

log
→ detailed event/context
```

Strong combination:

```text
CheckoutFailures ↑
→ query logs
→ requestId / reason
```

EMF can provide:
- both from one structured event.

##### 4.1.4.37.2 Metric vs Trace

```text
metric
→ how much/how often?

trace
→ where in distributed path?
```

Example:

```text
DependencyLatency ↑
→ inspect trace
→ payment provider subsegment slow
```

#### 4.1.4.38 Permissions

Direct `PutMetricData` requires:
- permission for the CloudWatch metric API.

EMF usually relies on:
- application ability to emit logs to the configured CloudWatch Logs destination.

Distinction:

```text
EMF
→ log delivery path

PutMetricData
→ direct metric API permission
```

- metric directive,
- numeric metric value,
- dimension fields,
- unit,

##### 4.1.4.39.2 Metric Exists, Dashboard Series Missing
Check exact:
- namespace,
- metric name,
- dimension names,

- exact.

Source material notes:
- metric statistics may take a short time to become retrievable,
- new metrics can take longer to appear in listing APIs.

Do not immediately conclude:
- publication failed.

#### 4.1.4.42 Common Exam Traps

##### 4.1.4.42.1 Request ID Is a Good Metric Dimension
- Usually false.
- It causes high cardinality.

##### 4.1.4.42.2 EMF Performs a Synchronous Metric API Call
- False.

```text
EMF log
→ CloudWatch Logs
→ asynchronous metric extraction
```

##### 4.1.4.42.3 EMF Data Is Only a Metric
- False.
- The structured log remains queryable.

##### 4.1.4.42.4 More Dimensions Always Means Better Observability
- False.
- More dimensions can increase cardinality and cost.

##### 4.1.4.42.5 Use `AWS/...` for Custom Namespace
- False.
- AWS prefix is reserved.

##### 4.1.4.42.6 High Resolution Is Always Better
- False.
- Use only when sub-minute detail is required.

##### 4.1.4.42.7 Missing Metric Data Means Zero
- False.

##### 4.1.4.42.8 Every Searchable Log Field Should Be a Dimension
- False.

##### 4.1.4.42.9 Lambda Should Call `PutMetricData` on Every Invocation
- Usually not preferred.
- AWS Lambda best practices favor EMF.

##### 4.1.4.42.10 EMF Guarantees Exactly-Once Delivery
- False.
- Delivery is at least once.

##### 4.1.4.42.11 Any JSON Log Is EMF
- False.
- Valid `_aws` metadata is required.

##### 4.1.4.42.12 Metric Name Alone Defines Time Series
- False.
- Namespace and dimensions also matter.

**Metric name**
→ what is measured.

**Unit**
→ semantic meaning of value.

**Dimension**
→ key/value that helps define metric time series.

→ number of unique metric dimension combinations.

**EMF**
→ structured log format from which CloudWatch asynchronously extracts metrics.

**`PutMetricData`**

**Metric filter**

##### 4.1.4.45.2 Fastest Exam Discriminator

```text
business/application measurement missing?
→ custom metric

Lambda low-latency custom metric?
→ EMF

direct metric API?
→ PutMetricData

→ metric filter

prod/test split?
→ Environment dimension

requestId/userId/orderId?
→ metadata/log field

sub-minute visibility?
→ high-resolution metric

metric + detailed diagnostic context?
→ EMF

many unique dimension values?
→ cardinality/cost problem
```

##### 4.1.4.45.3 Final Principle
- **Implement custom metrics only for application or business behavior that native AWS metrics do not already expose. Define a stable namespace, meaningful metric name, correct unit, bounded dimensions, and the minimum resolution required by the operational use case. EMF is the exam's explicit example and is especially important for Lambda because AWS recommends asynchronously embedding custom metrics in structured logs rather than making synchronous CloudWatch metric API calls in the request path. EMF preserves detailed log context while CloudWatch extracts graphable and alarmable metrics. Keep high-cardinality identifiers such as request IDs, user IDs, and order IDs as log metadata instead of dimensions, because each unique dimension combination creates a distinct custom metric. Use `PutMetricData` for explicit direct publication, metric filters when existing logs already contain a simple measurable pattern, and high-resolution metrics only when sub-minute visibility is truly needed.**

##### 4.1.4.46.2 CloudWatch — Embedded Metric Format
Official AWS documentation defines EMF as:
- structured log data,
- written to CloudWatch Logs,
- asynchronously extracted into custom CloudWatch metrics,
- while retaining detailed log context.

Official AWS documentation:
- https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Embedded_Metric_Format.html
