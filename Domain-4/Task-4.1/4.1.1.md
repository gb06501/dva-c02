### 4.1.1 Debug code to identify defects

#### 4.1.1.1 Exam and Task Context

##### 4.1.1.1.1 Domain and Task
- Domain 4 is **Troubleshooting and Optimization**.
- Task 4.1 is **Assist in a root cause analysis**.
- Skill 4.1.1 is **Debug code to identify defects**.

##### 4.1.1.1.2 Position Inside Task 4.1
The neighboring skills separate code debugging from broader observability work:

```text
4.1.1
→ debug code to identify defects

4.1.2
→ interpret metrics, logs, and traces

4.1.3
→ query logs

4.1.4
→ implement custom metrics

4.1.5
→ review application health

4.1.6
→ troubleshoot deployment failures

4.1.7
→ debug service integration issues
```

Core question:

**How do you use concrete runtime evidence to determine whether the defect is in application code and isolate the first incorrect behavior?**

#### 4.1.1.2 Core Mental Model

```text
observed failure
      |
      v
reproduce / identify failing request
      |
      v
collect evidence
      |
      +--> exact error
      +--> request/event
      +--> logs
      +--> deployed version
      +--> trace/context
      |
      v
narrow failing code path
      |
      v
form hypothesis
      |
      v
test one hypothesis
      |
      +-- wrong → gather more evidence
      |
      '-- correct
             |
             v
         fix defect
             |
             v
       regression test
             |
             v
       verify behavior
```

Debugging is:

```text
evidence
→ hypothesis
→ controlled verification
```

not:

```text
guess
→ change many things
→ redeploy
```

#### 4.1.1.3 Symptom vs Defect

A symptom is:
- what is observed.

A defect is:
- the underlying incorrect implementation.

Example:

```text
symptom
→ Lambda fails for S3 object names containing spaces

defect
→ code uses URL-encoded S3 event key without decoding it
```

Root cause analysis requires:
- moving from symptom to defect.

#### 4.1.1.4 First Debugging Decision: Where Did It Fail?

Possible layers:

```text
request/event
→ application code
→ AWS SDK call
→ AWS service
→ downstream dependency
→ response handling
```

Before changing code:
- identify the fault domain.

A Lambda failure does not automatically mean:
- application-code defect.

Possible causes include:
- code,
- configuration,
- IAM,
- deployment/package,
- network,
- downstream dependency,
- service quota.

#### 4.1.1.5 Reproduce and Minimize the Failure

##### 4.1.1.5.1 Reproduce
Capture:
- request/event payload,
- relevant parameters/headers,
- environment/configuration,
- deployed function version/alias,
- exact error response.

Goal:

```text
same relevant input/context
→ same failing path
```

##### 4.1.1.5.2 Minimal Reproduction
Prefer:
- the smallest input that still triggers the defect.

Example:

```text
works:
photo.jpg

fails:
my photo.jpg
```

Difference:

```text
space in object key
```

This narrows the hypothesis toward:
- encoding/decoding.

##### 4.1.1.5.3 Compare Working vs Failing Cases
Compare:
- payload,
- configuration,
- version,
- permissions/context,
- downstream state,
- timing.

The smallest meaningful difference often:
- reveals the defect.

#### 4.1.1.6 Read the Exact Error

Use:
- exception type,
- message,
- stack trace,
- AWS SDK/service error code,
- request ID,
- failing operation.

Example:

```text
NoSuchKey
≠
AccessDenied
```

even if both happen during:

```text
S3 GetObject
```

Different errors point to:
- different fault domains.

#### 4.1.1.7 Stack Traces and Exception Types

##### 4.1.1.7.1 Stack Trace
A stack trace helps identify:
- where the exception surfaced,
- the call path,
- application/library boundaries.

Do not assume:
- the first visible frame is the root cause.

##### 4.1.1.7.2 Exception Classification
Examples:

```text
NullPointerException
→ unexpected null state

TypeError
→ invalid type/operation

JSON parse error
→ malformed/unexpected payload

AccessDenied
→ authorization/policy issue

ResourceNotFound
→ identifier/resource mismatch

timeout
→ execution/dependency/performance path
```

Exact interpretation:
- depends on runtime and AWS service.

#### 4.1.1.8 Lambda Invocation Error vs Function Error

This distinction is critical.

##### 4.1.1.8.1 Function Execution Error
The function:
- was invoked,
- but application/runtime execution failed.

For synchronous invocation, Lambda can return:

```text
HTTP 200
+
X-Amz-Function-Error
```

Therefore:

```text
HTTP 200 from Invoke
≠ function code succeeded
```

##### 4.1.1.8.2 Invocation Error
The invocation itself fails before successful function execution.

Possible causes:
- invalid request,
- permissions,
- configuration,
- capacity/limits.

These can produce:
- 4xx/5xx responses.

Fast distinction:

```text
invocation failure
→ request/configuration/permission/capacity

function error
→ runtime/code/dependency path
```

#### 4.1.1.9 Lambda Failure Phases

Useful phases:

```text
INIT
→ runtime/module initialization

INVOKE
→ handler/event processing

RETURN
→ completion/result/async behavior
```

##### 4.1.1.9.1 Initialization Defects
Possible causes:
- missing dependency,
- incompatible library,
- static initialization error,
- invalid environment/configuration.

If failure happens before handler execution:
- debug initialization/package path first.

##### 4.1.1.9.2 Handler Defects
Investigate:
- payload assumptions,
- null/missing fields,
- parsing,
- business logic,
- SDK parameters,
- async behavior.

##### 4.1.1.9.3 Return-Path Defects
A function can perform work but return too early.

Typical Node.js clue:

```text
start async operation
→ handler returns
→ async operation was not awaited
```

Inspect:
- missing `await`,
- missing promise return.

#### 4.1.1.10 Event and Payload Defects

##### 4.1.1.10.1 Unexpected Event Shape
Common serverless defect:

```text
code expects shape A
actual event has shape B
```

Debug:

```text
inspect actual event
→ compare with parser assumptions
→ correct code or contract
```

##### 4.1.1.10.2 JSON Encoding/Decoding
Common issues:
- malformed JSON,
- wrong field type,
- double encoding,
- unexpected escaping,
- character handling.

Flow:

```text
capture raw payload
→ inspect serialized form
→ compare with expected schema
→ isolate parser/serializer behavior
```

##### 4.1.1.10.3 Boundary Conditions
Common triggers:
- null,
- empty,
- zero,
- maximum/minimum,
- special characters,
- large payload,
- missing optional fields,
- duplicates,
- unexpected ordering.

##### 4.1.1.10.4 Payload Size
Separate:

```text
code defect
→ mishandles valid payload

service limit
→ payload exceeds supported limit
```

Different root cause:
- different remediation.

#### 4.1.1.11 S3 Event Key Encoding Example

AWS documents a concrete Lambda debugging pattern.

Object key:

```text
james beswick.jpg
```

can arrive:
- URL encoded in the S3 event.

If code directly uses:

```javascript
event.Records[0].s3.object.key
```

without decoding:
- S3 lookup can fail with `NoSuchKey`.

Correct reasoning:

```text
S3 service works
+
application interprets event incorrectly
→ code defect
```

Exam clue:

```text
S3 key with spaces/special characters fails
→ inspect URL decoding
```

#### 4.1.1.12 Async/Await Defect

Weak pattern:

```javascript
exports.handler = async () => {
  doAsyncWork();
  return "done";
};
```

Potential result:

```text
work starts
→ handler returns
→ intended work may not complete
```

Typical correction:

```javascript
await doAsyncWork();
```

or:
- return the promise when appropriate.

Exam clue:

```text
Lambda returns before async work/SDK call completes
→ inspect promise/await handling
```

#### 4.1.1.13 Code vs Configuration, IAM, and Resource Failures

##### 4.1.1.13.1 AccessDenied
Likely first checks:
- caller identity,
- execution role,
- action,
- resource,
- resource policy,
- conditions.

Do not:
- rewrite otherwise-correct business logic first.

##### 4.1.1.13.2 ResourceNotFound / NoSuchKey
Possible causes:
- wrong identifier,
- wrong Region/account,
- wrong environment/stage,
- encoding issue,
- stale value.

First inspect:
- the exact identifier actually sent.

##### 4.1.1.13.3 Downstream Failure
Ask:

```text
Did our code fail?
or
Did dependency fail and code handled it poorly?
```

Possible downstream behavior:
- timeout,
- throttling,
- temporary unavailability.

Do not classify every downstream failure as:
- application-code defect.

#### 4.1.1.14 AWS SDK Error Inspection

When an SDK call fails, inspect:
- service error code,
- HTTP status where applicable,
- request ID,
- exception type,
- retry context.

Do not reduce:

```text
AccessDenied
Throttling
ResourceNotFound
ValidationException
```

to:

```text
"AWS call failed"
```

Each points toward:
- a different root-cause path.

#### 4.1.1.15 Diagnostic Logging

When evidence is insufficient:
- add targeted, safe logging.

Good:

```text
requestId=...
operation=GetObject
bucket=...
decodedKey=...
```

Weak:

```text
"something failed"
```

Useful context:
- request ID,
- operation,
- selected identifiers,
- branch/path,
- error context.

Do not log:
- passwords,
- tokens,
- private keys,
- secrets,
- unnecessary sensitive personal data.

#### 4.1.1.16 Lambda Logs

Lambda commonly sends function logs to:
- CloudWatch Logs,
when execution-role permissions allow it.

Typical log group:

```text
/aws/lambda/<function-name>
```

For exam debugging:
- CloudWatch Logs is the primary mental model.

Detailed querying:
- 4.1.3.

##### 4.1.1.16.1 Missing Logs
Possible causes:
- missing log permissions,
- wrong destination/log group,
- logging throttling/quota,
- no invocation.

Therefore:

```text
no logs
≠ proof handler never executed
```

##### 4.1.1.16.2 Logging Permissions
Common managed policy:

```text
AWSLambdaBasicExecutionRole
```

If logs are missing:
- inspect execution-role log permissions.

This is:
- configuration troubleshooting,
not necessarily:
- code debugging.

##### 4.1.1.16.3 Log Levels
Current Lambda structured logging supports levels including:
- TRACE,
- DEBUG,
- INFO,
- WARN,
- ERROR,
- FATAL.

For debugging:
- DEBUG/TRACE can add detail.

Tradeoff:
- more volume,
- more cost,
- greater risk of logging unnecessary data.

#### 4.1.1.17 Correlation and One-Request Debugging

Use identifiers such as:
- Lambda request ID,
- application correlation ID,
- trace ID,
- business-safe transaction ID.

Goal:

```text
request
→ code path
→ downstream call
→ failure
```

Prefer:

```text
one known failing request
→ follow its evidence
```

over:
- scanning thousands of unrelated events.

Metrics/log/trace interpretation in depth:
- 4.1.2.

#### 4.1.1.18 Verify the Deployed Version

A correct fix does not help if:
- another version is serving traffic.

Verify:
- invoked ARN,
- alias,
- published version,
- environment/stage.

Example:

```text
developer fixes version 42
prod alias still points to 41
→ production still fails
```

Wrong conclusion:
- fix is ineffective.

Actual issue:
- wrong release identity is active.

Exam clue:

```text
old behavior after deployment
→ verify version/alias
```

#### 4.1.1.19 Local vs AWS Runtime Differences

Code can:

```text
work locally
→ fail in AWS
```

Compare:
- runtime version,
- architecture,
- environment variables,
- dependencies,
- IAM,
- network,
- event shape,
- filesystem assumptions.

Do not assume:
- local and Lambda execution contexts are identical.

#### 4.1.1.20 Dependency and Runtime Defects

Typical symptoms:
- cannot import,
- class not found,
- missing module,
- native library load failure.

Possible causes:
- missing package dependency,
- wrong architecture,
- incompatible runtime,
- incorrect layer,
- dependency-path issue.

This may be:
- packaging/runtime defect,
not:
- business-logic defect.

After runtime upgrade, investigate:
- runtime behavior changes,
- library compatibility,
- deprecated behavior,
- initialization differences.

#### 4.1.1.21 Timeout Debugging

Symptom:

```text
Task timed out
```

Possible causes:
- infinite/slow loop,
- slow dependency,
- missing network route,
- blocked connection,
- timeout set too low,
- excessive work,
- deadlock/wait.

Do not immediately:
- increase timeout.

First determine:
- where execution spends time.

Root-cause principle:

```text
increase timeout
→ changes symptom threshold

does not necessarily
→ fix defect
```

#### 4.1.1.22 Deterministic vs Intermittent Defects

##### 4.1.1.22.1 Deterministic

```text
same input
→ always fails
```

Focus on:
- input transformation,
- parsing,
- branch logic,
- fixed configuration.

##### 4.1.1.22.2 Intermittent

```text
same logical request
→ sometimes succeeds
```

Investigate:
- concurrency,
- race conditions,
- dependency state,
- retries,
- eventual consistency,
- shared mutable state,
- timing.

#### 4.1.1.23 Warm Lambda Execution State

Lambda execution environments can be reused.

Good:
- reusable SDK clients/connections.

Danger:

```text
mutable request-specific global state
→ survives into later invocation
```

If failure occurs only after previous requests:
- inspect global/static state.

#### 4.1.1.24 Concurrency and Idempotency Defects

##### 4.1.1.24.1 Concurrency
Symptoms:
- lost updates,
- race conditions,
- duplicate behavior,
- non-thread-safe shared state,
- ordering-sensitive failures.

If failure appears only under parallel load:
- inspect concurrency/shared state.

Detailed concurrency:
- 4.3.1.

##### 4.1.1.24.2 Idempotency
Event-driven systems can deliver:
- duplicates,
- retries.

If duplicate delivery is valid service behavior but application corrupts state:
- the defect can be application handling.

Question:

```text
Can this event legitimately be processed more than once?
```

If yes:
- idempotent handling may be required.

#### 4.1.1.25 Controlled Debugging

##### 4.1.1.25.1 One Hypothesis at a Time
Weak:

```text
change code
change IAM
change timeout
change memory
redeploy
```

If it works:
- root cause remains unknown.

Strong:

```text
one hypothesis
→ one controlled test/change
→ observe result
```

##### 4.1.1.25.2 Debugger
Breakpoints allow:

```text
pause
→ inspect variables
→ step through path
```

Useful goal:
- find the **first incorrect state**,
not only:
- the final exception.

AWS Lambda tooling can support:
- remote debugging from Visual Studio Code.

Exam-level principle:
- controlled debugging can occur against the actual AWS execution context when needed.

#### 4.1.1.26 Error Handling Must Preserve Evidence

Avoid replacing a useful error with:

```javascript
catch (e) {
  throw new Error("failed");
}
```

Better error handling preserves:
- original exception/cause,
- operation context,
- request identifiers.

Also avoid swallowing meaningful failures:

```javascript
try {
  await operation();
} catch (e) {
  console.log("ignored");
}
```

If the operation matters:
- propagate or handle intentionally.

Public responses can remain generic while internal logs preserve:
- useful diagnostic context.

#### 4.1.1.27 Retry Can Hide Root Cause

Retries are useful for:
- transient failures.

But during debugging:

```text
attempt fails
→ retry succeeds
```

can hide:
- throttling,
- intermittent dependency failure,
- timing problems.

Inspect:
- retry count,
- latency,
- intermediate/final error,
- throttling evidence.

Do not classify:
- every retried failure
as:
- code defect.

#### 4.1.1.28 Distributed Debugging Context

A defect can surface downstream:

```text
API Gateway
→ Lambda A
→ service
→ Lambda B
→ DynamoDB
```

Use telemetry to:
- identify the component/code path that deserves debugging.

Detailed metrics/logs/traces interpretation:
- 4.1.2.

Examples of transformation boundaries:
- API Gateway request → Lambda event,
- S3 event → Lambda parser,
- producer object → serialized queue message → consumer event.

Do not assume:
- producer's in-memory representation equals consumer's received payload.

#### 4.1.1.29 Amazon Q Developer

Current AWS material includes:
- **Diagnose with Amazon Q**
for supported AWS Management Console errors.

It can help with issues such as:
- insufficient permissions,
- incorrect configuration,
- service-limit problems.

Use it as:

```text
error
→ explanation / hypothesis / troubleshooting suggestion
```

not as:

```text
Amazon Q suggestion
→ root cause proven
```

Always verify:
- actual code,
- configuration,
- logs,
- service behavior,
- least-privilege implications.

#### 4.1.1.30 Regression Test and Fix Verification

Once the defect is isolated:

```text
failing production/example input
→ automated regression test
→ test fails
→ apply fix
→ test passes
```

Then also test:
- previously working case,
- relevant boundary cases,
- negative/error behavior.

Do not stop at:

```text
code looks correct
```

Verify:

```text
original failing case
→ now succeeds
```

A symptom-suppressing change is not necessarily:
- root-cause correction.

#### 4.1.1.31 Common Failure Patterns

##### 4.1.1.31.1 S3 Key with Spaces Fails
Likely:
- URL-encoding defect.

Action:
- decode before `GetObject`.

##### 4.1.1.31.2 Function Returns Before Work Completes
Likely:
- missing `await` / promise return.

##### 4.1.1.31.3 Invoke Returns HTTP 200 but Function Failed
Inspect:
- `X-Amz-Function-Error`,
- function error payload/logs.

##### 4.1.1.31.4 Lambda Logs Missing
Check:
- execution-role log permissions,
- log destination/configuration,
- invocation evidence.

##### 4.1.1.31.5 Import Works Locally but Fails in Lambda
Check:
- deployment package,
- runtime,
- architecture,
- dependency/layer compatibility.

##### 4.1.1.31.6 Production Still Shows Old Behavior
Check:
- function version,
- alias,
- stage/environment target.

##### 4.1.1.31.7 Function Times Out
First:
- determine blocking/slow code or dependency path.

##### 4.1.1.31.8 Failure Appears After Previous Invocation
Inspect:
- reused global/static mutable state.

##### 4.1.1.31.9 Failure Appears Only Under Parallel Load
Inspect:
- concurrency,
- races,
- shared state.

#### 4.1.1.32 Decision Flow

##### 4.1.1.32.1 Reproduction

```text
Can failure be reproduced?
→ yes: preserve failing input
→ no: identify request/correlation evidence
```

##### 4.1.1.32.2 Error Class

```text
AccessDenied?
→ IAM/resource permissions

ResourceNotFound / NoSuchKey?
→ identifier / Region / environment / encoding

function returned too early?
→ async/promise handling

input-specific?
→ parsing / validation / encoding

timeout?
→ locate slow/blocking path
```

##### 4.1.1.32.3 Lambda Boundary

```text
Invoke 4xx/5xx?
→ invocation/configuration/permission path

Invoke 200 + FunctionError?
→ function/runtime path
```

##### 4.1.1.32.4 Deployment Identity

```text
local fix works but production does not?
→ verify version / alias / stage
```

##### 4.1.1.32.5 Evidence

```text
need more detail?
→ targeted safe logging
→ request/correlation IDs
→ controlled debugger / trace context
```

##### 4.1.1.32.6 After Defect Found

```text
regression test
→ smallest corrective change
→ verify failing and working cases
```

#### 4.1.1.36 Exam-Level Knowledge Frame

##### 4.1.1.36.1 Know These Cold

**Debugging**
→ evidence → hypothesis → controlled verification.

**Symptom**
→ observed failure.

**Defect**
→ underlying incorrect implementation.

**Lambda function error**
→ function/runtime failed; synchronous Invoke can still return HTTP 200.

**Invocation error**
→ request/configuration/permission/capacity failure.

**Actual event**
→ inspect real shape, fields, encoding.

**S3 key with spaces**
→ inspect URL decoding.

**Async defect**
→ missing `await`/promise return can cause early completion.

**Missing logs**
→ may be logging permission/configuration issue.

**Version/alias**
→ verify which code is really executing.

**Timeout**
→ locate slow/blocking path before increasing timeout.

**Amazon Q**
→ troubleshooting assistant, not proof.

**Regression test**
→ preserve the failing case after fix.

##### 4.1.1.36.2 Fastest Exam Discriminator

```text
same input always fails?
→ reproduce and inspect code path

AccessDenied?
→ permissions first

S3 key with spaces?
→ URL decode

Node.js returns before async work?
→ await/promise handling

Invoke HTTP 200 but function failed?
→ X-Amz-Function-Error

no Lambda logs?
→ check logging permissions/config

old behavior after deployment?
→ version/alias

timeout?
→ find blocking/slow path

console permission/config error?
→ Amazon Q can assist diagnosis

defect fixed?
→ regression test + verify
```

##### 4.1.1.36.3 Final Principle
- **Debug code by reducing a failure to evidence that identifies the first incorrect application state. Reproduce the failing case, inspect the exact exception and actual request/event, distinguish invocation/configuration problems from function-code failures, and verify the deployed version. For Lambda, pay particular attention to event shape and encoding, asynchronous completion, packaged dependencies, runtime differences, warm-state behavior, and version/alias identity. Use targeted logging, correlation IDs, traces, or controlled remote debugging only to narrow the defective code path. Once isolated, preserve the failing case as a regression test, make the smallest corrective change, and verify both the original failure and existing successful behavior.**
