### 4.1.2 Interpret application metrics, logs, and traces

#### 4.1.2.1 Exam and Task Context

##### 4.1.2.1.1 Domain and Task
- Domain 4 is **Troubleshooting and Optimization**.
- Task 4.1 is **Assist in a root cause analysis**.
- Skill 4.1.2 is **Interpret application metrics, logs, and traces**.

##### 4.1.2.1.2 Position Inside Task 4.1
- 4.1.1:
  - debug code to identify defects.
- 4.1.2:
  - interpret existing telemetry.
- 4.1.3:
  - query logs.
- 4.1.4:
  - implement custom metrics.
- 4.1.5:
  - review application health.

Core question:

**How do you combine metrics, logs, and traces to determine the scope, location, and likely mechanism of an application problem?**

#### 4.1.2.2 Core Mental Model

```text
USER / SYSTEM SYMPTOM
        |
        v
METRIC
→ what changed?
→ how much?
→ when?
        |
        v
TRACE
→ which path/component is slow or failing?
        |
        v
LOG
→ what exactly happened inside that component?
        |
        v
ROOT-CAUSE HYPOTHESIS
```

Practical interpretation:

```text
metrics
→ establish scope and timing

traces
→ localize distributed path/component

logs
→ explain detailed execution/error
```

The order can vary, but the signal roles remain distinct.

#### 4.1.2.3 Metrics, Logs, and Traces Answer Different Questions

##### 4.1.2.3.1 Metrics
Best for:

```text
WHAT changed?
HOW MUCH?
WHEN?
HOW OFTEN?
```

Examples:
- errors,
- latency,
- invocations,
- throttles,
- concurrency,
- backlog age.

##### 4.1.2.3.2 Logs
Best for:

```text
WHAT exactly happened?
WHY did this execution fail?
WHAT input/state/error was observed?
```

Examples:
- exception,
- request ID,
- validation failure,
- application state.

##### 4.1.2.3.3 Traces
Best for:

```text
WHERE did time/error occur?
WHICH dependency was involved?
HOW did the request propagate?
```

Examples:
- API Gateway → Lambda → DynamoDB,
- service A → service B → external API.

#### 4.1.2.4 Telemetry Correlation

Strong troubleshooting:

```text
metric:
Errors increase at 14:05
        |
        v
trace:
slow/failing requests spend 2.4 s in DynamoDB
        |
        v
log:
ProvisionedThroughputExceededException
```

This supports:
- a coherent root-cause hypothesis.

Weak troubleshooting:

```text
one log line
→ assume system-wide root cause
```

Correlate signals by:
- time,
- resource/version,
- environment,
- request ID,
- trace ID.

#### 4.1.2.5 Metric Interpretation Model

A CloudWatch metric is:
- time-series data about system/application behavior.

Interpret it with:

```text
namespace
+
metric name
+
dimensions
+
statistic
+
period
+
time window
```

Metric name alone is not enough.

Example:

```text
AWS/Lambda
Errors
FunctionName=Orders
Sum
1 minute
```

is much more meaningful than:

```text
Errors
```

#### 4.1.2.6 Namespace and Dimensions

##### 4.1.2.6.1 Namespace
Examples:

```text
AWS/Lambda
AWS/ApiGateway
AWS/DynamoDB
custom/application namespace
```

Same metric name in different namespaces:
- can have different semantics.

##### 4.1.2.6.2 Dimensions
Dimensions select:
- resource/context.

Lambda examples:
- `FunctionName`,
- `Resource`,
- `ExecutedVersion`.

Rule:

```text
same metric name
+
different dimension set
→ different time series
```

Do not compare different scopes as if they were identical.

#### 4.1.2.7 Period and Statistic

##### 4.1.2.7.1 Period
Examples:
- 1 minute,
- 5 minutes,
- 1 hour.

A coarse period:
- smooths short spikes,
- reduces temporal detail.

##### 4.1.2.7.2 Statistic
Common statistics:
- `Sum`,
- `Average`,
- `Minimum`,
- `Maximum`,
- percentiles.

Use:
- the statistic that matches metric meaning.

Do not default to:
- `Average` for everything.

#### 4.1.2.8 Count Metrics and Error Rate

For Lambda outcome metrics such as:
- `Invocations`,
- `Errors`,
- `Throttles`,

AWS documentation emphasizes:
- count interpretation using `Sum`.

Example:

```text
Errors
Sum
1 minute
→ failed invocations during that minute
```

Error rate:

```text
Errors / Invocations
```

Example:

```text
Errors = 50
Invocations = 10,000
error rate = 0.5%
```

Raw error count without workload volume:
- can mislead.

#### 4.1.2.9 Lambda Throttles

Critical distinction:

```text
Invocations
→ function code actually invoked
```

Throttled requests:

```text
Throttles
→ rejected before code runs
```

AWS explicitly states:

```text
throttled request
→ not Invocations
→ not Errors
```

Therefore:

```text
Throttles ↑
Errors stable
```

can still indicate:
- serious availability/capacity pressure.

#### 4.1.2.10 Lambda Errors

Lambda `Errors` can include:
- application exceptions,
- runtime exceptions,
- timeouts,
- some configuration/runtime execution failures.

Therefore:

```text
Errors ↑
```

does not identify:
- one specific exception type.

Use:
- logs,
- traces
to explain the exact failure.

#### 4.1.2.11 Duration and Tail Latency

Lambda `Duration` measures:
- function processing time.

Useful statistics:
- `Average`,
- `Maximum`,
- p95,
- p99.

Example:

```text
Average stable
p95 rising
```

Interpretation:
- most requests remain normal,
- a subset is getting slow.

Exam clue:

```text
some users very slow
→ inspect percentiles
```

Average can hide:
- tail latency.

#### 4.1.2.12 Maximum and Concurrency

`Maximum` answers:

```text
highest observed value in the period
```

Useful for:
- peak concurrency,
- worst latency,
- burst pressure.

But:
- one outlier can dominate.

For Lambda `ConcurrentExecutions`, AWS commonly recommends:
- `Max` when evaluating closeness to concurrency limits.

Pattern:

```text
ConcurrentExecutions near limit
+
Throttles ↑
→ concurrency exhaustion likely
```

#### 4.1.2.13 Provisioned Concurrency

Metric:

```text
ProvisionedConcurrencyUtilization
```

Concept:

```text
used provisioned concurrency
/
configured provisioned concurrency
```

If consistently near 1:
- provisioned pool is heavily utilized.

Possible effect:
- spillover to on-demand concurrency.

#### 4.1.2.14 Backlog and IteratorAge

For Lambda stream event sources, `IteratorAge` represents:
- age of the last processed record.

If rising:

```text
consumer is falling behind
```

Possible causes:
- slow function,
- slow downstream dependency,
- insufficient concurrency,
- incoming traffic exceeds processing capacity.

General pattern:

```text
age / lag ↑
→ backlog pressure
```

Examples:
- Lambda `IteratorAge`,
- SQS age metrics,
- Kafka lag concepts.

#### 4.1.2.15 Metric Correlation

One metric rarely proves root cause.

Example:

```text
Duration ↑
ConcurrentExecutions at limit
Throttles ↑
```

Combined interpretation:
- requests take longer,
- concurrency remains occupied longer,
- incoming requests are rejected.

This is stronger than:
- interpreting each metric independently.

#### 4.1.2.16 Time Alignment and Baseline

##### 4.1.2.16.1 Time Alignment
Correlate signals only when:
- their time windows align.

Strong:

```text
14:05 Errors ↑
14:05 Duration ↑
14:05 downstream trace latency ↑
```

Weak:

```text
14:05 Errors ↑
11:00 CPU ↑
```

Do not claim causation from unrelated timestamps.

##### 4.1.2.16.2 Baseline
Interpret metric values relative to:
- normal workload,
- previous period,
- request volume,
- deployment/change time.

Example:

```text
100 errors/hour
```

can be:
- catastrophic at 200 requests/hour,
- negligible at very high volume.

#### 4.1.2.17 Missing Data vs Zero

A missing metric point is not automatically:

```text
0
```

Possible causes:
- resource idle,
- metric emitted only with activity,
- telemetry gap,
- wrong account/Region,
- permissions/configuration issue.

Exam rule:

```text
no metric data
≠ zero activity
```

#### 4.1.2.18 Logs Mental Model

CloudWatch Logs provides:
- timestamped event records
from applications and AWS services.

Interpret logs as:

```text
sequence of events
for a request/execution/component
```

not:
- an unstructured text dump.

Detailed querying:
- 4.1.3.

#### 4.1.2.19 Log Groups and Streams

##### 4.1.2.19.1 Log Group
A log group:
- collects related log streams.

Lambda example:

```text
/aws/lambda/OrdersFunction
```

##### 4.1.2.19.2 Log Stream
A log stream:
- contains ordered log events from a source/execution environment.

Lambda can have:
- multiple log streams.

Therefore:
- correlate an invocation by request ID,
not only:
- stream name.

#### 4.1.2.20 Log Severity and Structure

##### 4.1.2.20.1 Severity
Typical labels:
- DEBUG,
- INFO,
- WARN,
- ERROR,
- FATAL.

Do not infer operational impact only from the label.

An `ERROR` can be:
- handled/expected.

A `WARN` can be:
- operationally important.

Read:
- context,
- outcome,
- frequency.

##### 4.1.2.20.2 Structured Logs
Example:

```json
{
  "level": "ERROR",
  "requestId": "abc",
  "operation": "CreateOrder",
  "errorType": "ConditionalCheckFailedException"
}
```

Benefits:
- easier filtering,
- reliable field extraction,
- better correlation.

Implementation details:
- 4.2.7.

#### 4.1.2.21 Request and Correlation IDs

Lambda request IDs help correlate:
- one invocation's log events.

Application correlation IDs can span:

```text
client
→ API
→ Lambda
→ queue
→ worker
```

Use when:
- service-native IDs do not span the whole business flow.

Key principle:

```text
timestamp
+
request/correlation ID
→ stronger evidence than timestamp alone
```

#### 4.1.2.22 Logs Explain Metric Spikes

Example:

```text
metric:
Errors +500

logs:
AccessDeniedException
```

Interpretation changes from:
- generic application error

to:
- authorization/configuration issue.

Pattern:

```text
metrics
→ scale

logs
→ detail
```

One error log does not establish:
- system-wide error rate.

Metrics provide:
- population context.

#### 4.1.2.23 Trace Mental Model

An X-Ray trace represents:
- one distributed request path.

It groups:
- segments sharing one trace ID.

A trace answers:

```text
which services participated?
how long did each take?
where did error/fault occur?
```

#### 4.1.2.24 Segment and Subsegment

##### 4.1.2.24.1 Segment
A segment represents:
- work performed by one service/resource for the request.

It can contain:
- request/response information,
- timing,
- error/fault details,
- subsegments.

##### 4.1.2.24.2 Subsegment
A subsegment gives:
- more granular work inside a segment.

Examples:
- AWS SDK call,
- SQL query,
- external HTTP call,
- internal work block.

A slow subsegment can identify:
- the downstream dependency causing latency.

#### 4.1.2.25 Service Graph and Trace ID

##### 4.1.2.25.1 Service Graph
The X-Ray service graph visualizes:
- service/resource nodes,
- request edges.

Use it to identify:
- which component shows latency/errors/faults
before drilling into traces.

##### 4.1.2.25.2 Trace ID
Trace ID links:
- all segments in one request path.

Use it to move:

```text
failing user request
→ distributed trace
→ specific segment/subsegment
→ relevant logs
```

#### 4.1.2.26 Trace Timeline

Example:

```text
API Gateway     50 ms
Lambda        2500 ms
  DynamoDB    2200 ms
```

Interpretation:

```text
majority of latency
→ DynamoDB call
```

Do not optimize:
- API Gateway first.

Trace timelines help separate:
- upstream application time,
- downstream dependency time.

#### 4.1.2.27 X-Ray Error, Fault, and Throttle

AWS X-Ray uses specific terms:

```text
Error
→ 4xx class

Fault
→ 5xx class

Throttle
→ 429
```

Interpretation:
- `Error`:
  - client/request-side class.
- `Fault`:
  - server/service-side failure class.
- `Throttle`:
  - quota/capacity/rate-control issue.

Do not use these terms interchangeably.

#### 4.1.2.28 Sampling

X-Ray does not necessarily trace:
- every request.

Therefore:

```text
no trace
≠ request never happened
```

Also:

```text
trace count
≠ request count
```

when sampling is enabled.

Metrics:
- are better for population-level counts/rates.

Traces:
- are representative request-path evidence.

Rare failures can be missed by:
- sampling.

This is another reason to correlate:
- metrics,
- logs,
- traces.

#### 4.1.2.29 Annotations vs Metadata

##### 4.1.2.29.1 Annotation
- indexed,
- searchable/filterable.

Examples:

```text
customerTier=premium
operation=checkout
```

##### 4.1.2.29.2 Metadata
- additional context,
- not indexed for trace filtering.

Rule:

```text
annotation
→ searchable

metadata
→ descriptive only
```

Detailed instrumentation:
- 4.2.4.

#### 4.1.2.30 Signal-to-Signal Correlation

##### 4.1.2.30.1 Metric → Trace

```text
p95 latency spikes
→ inspect traces from same time window
→ find slow segment/subsegment
```

##### 4.1.2.30.2 Trace → Log

```text
trace shows Lambda fault
→ trace/request ID
→ relevant CloudWatch logs
→ exact exception/state
```

##### 4.1.2.30.3 Log → Metric

```text
log shows throttling
→ check Throttles/concurrency/request-rate metrics
```

Goal:
- determine whether event is isolated or systemic.

#### 4.1.2.31 Common Interpretation Patterns

##### 4.1.2.31.1 Latency Spike, Errors Stable

```text
p95 latency ↑
Errors stable
```

Possible:
- dependency slower,
- application still succeeds.

Next:
- inspect slow traces.

##### 4.1.2.31.2 Errors Spike, Duration Stable

```text
Errors ↑
Duration stable
```

Possible:
- fast deterministic failures,
- validation,
- permissions,
- missing resources.

Next:
- logs/failing traces.

##### 4.1.2.31.3 Errors and Duration Spike

```text
Errors ↑
Duration ↑
```

Possible:
- downstream timeout,
- dependency degradation,
- retry exhaustion.

Trace:
- localize slow/failing dependency.

##### 4.1.2.31.4 Throttles Spike

```text
Throttles ↑
ConcurrentExecutions near limit
```

Interpretation:
- concurrency pressure.

Not:
- function-code exception rate.

##### 4.1.2.31.5 IteratorAge Rising

```text
IteratorAge ↑
Errors normal
```

Possible:
- consumer succeeds but cannot keep up.

Check:
- duration,
- concurrency,
- incoming rate,
- downstream latency.

##### 4.1.2.31.6 Error Logs but Error Metric Stable
Possible:
- application logs handled conditions as `ERROR`,
- CloudWatch metric semantics differ from text severity.

Do not expect:

```text
text "ERROR" count
=
Lambda Errors metric
```

#### 4.1.2.32 Deployment and Version Correlation

Always ask:

```text
Did telemetry change after deployment/configuration change?
```

Example:

```text
14:00 deploy v42
14:03 Errors ↑
14:03 Duration ↑
```

Strong clue:
- release regression.

Where supported, compare:
- old vs new version,
- resource/alias-specific dimensions,
- traces/logs by version.

Aggregation across versions can hide:
- candidate-specific failure.

#### 4.1.2.33 Environment, Account, and Region Scope

Do not mix:

```text
dev
test
prod
```

telemetry.

If production fails, verify:
- production resource,
- stage,
- account,
- Region.

CloudWatch telemetry is scoped by:
- account,
- Region,
unless centralized/cross-account observability is configured.

Wrong scope:
- wrong conclusion.

- higher-level service/application views derived from telemetry.

Useful concepts:
- service health,
- operations,
- dependencies,
- latency,
- availability,
- error rates.

For this skill:
- treat it as a correlated operational view.

Detailed instrumentation/configuration:

#### 4.1.2.35 Golden Signals as a Reading Framework

Useful interpretation model:

```text
LATENCY
→ how slow?

ERRORS
→ how often failing?

TRAFFIC
→ how much load?

SATURATION
→ how close to capacity?
```

This is:
- an engineering interpretation framework.

It is not:
- required DVA-C02 terminology.

#### 4.1.2.36 Correlation Does Not Prove Causation

Example:

```text
CPU ↑
Errors ↑
```

at the same time does not prove:

```text
CPU caused errors
```

Use:
- traces,
- logs,
- service-specific evidence
to establish mechanism.

Telemetry correlation generates:
- hypotheses.

Root-cause evidence validates them.

#### 4.1.2.41 Exam-Level Knowledge Frame

##### 4.1.2.41.1 Know These Cold

**Metric**
→ aggregate time-series behavior.

**Log**
→ detailed event/execution evidence.

**Trace**
→ distributed request path.

**Sum**
→ count metrics such as Lambda `Errors`/`Invocations`.

**Average**
→ central tendency; can hide tail latency.

**p95/p99**
→ tail-performance interpretation.

**Throttles**
→ Lambda requests rejected before code executes; not `Errors` or `Invocations`.

**ConcurrentExecutions**
→ use peak/`Max` to understand concurrency pressure.

**IteratorAge**
→ stream-processing backlog age.

**Segment**
→ one service/resource's work in a request.

**Subsegment**
→ granular downstream/internal work.

**X-Ray Error/Fault/Throttle**
→ 4xx / 5xx / 429.

**Sampling**
→ trace data may not be exhaustive.

**Annotation**
→ indexed/searchable.

**Metadata**
→ non-indexed context.

##### 4.1.2.41.2 Fastest Exam Discriminator

```text
How many failures?
→ metric

What exact exception/state?
→ log

Which downstream component is slow?
→ trace

Lambda error count?
→ Errors Sum

Lambda error rate?
→ Errors / Invocations

tail latency?
→ p95 / p99

rejected before function runs?
→ Throttles

concurrency pressure?
→ ConcurrentExecutions Max + Throttles

stream consumer falling behind?
→ IteratorAge

X-Ray 400?
→ Error

X-Ray 500?
→ Fault

X-Ray 429?
→ Throttle

no trace?
→ sampling may explain it
```

##### 4.1.2.41.3 Final Principle
- **Interpret telemetry according to the question each signal can answer. Metrics quantify aggregate behavior over time, so verify namespace, dimensions, period, statistic, and scope; for Lambda, counts such as `Errors` and `Invocations` use `Sum`, tail latency may require percentiles, `Throttles` represents rejected requests rather than function errors, and `IteratorAge` reveals stream backlog. Logs provide request/execution detail, while X-Ray traces localize distributed latency and failures through segments, subsegments, trace IDs, and the service graph. X-Ray `Error`, `Fault`, and `Throttle` have specific 4xx, 5xx, and 429 meanings, and traces are sampled rather than exhaustive. Correlate all evidence by time, resource/version, environment, request ID, and trace ID: metrics establish scope, traces localize the path, and logs explain the mechanism.**
