### 4.1.7 Debug service integration issues in applications

#### 4.1.7.1 Exam and Task Context

##### 4.1.7.1.1 Domain and Task
- Domain 4 is **Troubleshooting and Optimization**.
- Task 4.1 is **Assist in a root cause analysis**.
- Skill 4.1.7 is **Debug service integration issues in applications**.

##### 4.1.7.1.2 Position Inside Task 4.1
- 4.1.6:
  - troubleshoot deployment failures using deployment/service output.
- 4.1.7:
  - troubleshoot runtime service-to-service integration failures.

Core question:

**When individually healthy AWS components do not work together correctly, where does the integration path break: invocation permission, execution-role permission, resource policy, event source mapping, event shape, configuration, networking, encryption, throttling, retry, batching, or downstream service behavior?**

#### 4.1.7.2 Core Mental Model

```text
PRODUCER / CALLER
       |
       v
INTEGRATION MECHANISM
       |
       +--> direct SDK/API call
       +--> direct service trigger
       +--> event source mapping
       '--> API integration
       |
       v
TARGET / CONSUMER
       |
       v
DOWNSTREAM SERVICE
```

Debug each boundary independently:

```text
1. Was a request/event produced?
2. Did it reach the integration boundary?
3. Was the target allowed to receive/be invoked?
4. Did the target execute?
5. Did it understand the payload?
6. Could it call downstream services?
7. Did the downstream service accept the request?
8. What happened to failures/retries?
```

The first boundary where:
- expected evidence disappears,
- or an explicit error appears

is usually:
- the highest-value investigation point.

#### 4.1.7.3 Integration Failure vs Component Failure

Example:

```text
Lambda works when tested manually
SQS contains messages
but Lambda is never invoked
```

Likely:
- trigger/event-source integration issue.

Another example:

```text
Lambda is invoked
but DynamoDB PutItem returns AccessDenied
```

Likely:
- execution-role/downstream authorization issue.

Key principle:

```text
healthy components
≠ healthy integration
```

#### 4.1.7.4 Follow the Request/Event Path

Do not debug:

```text
API Gateway → Lambda → DynamoDB
```

as one black box.

Ask at each edge:

```text
API Gateway → Lambda
→ did Lambda receive invocation?

Lambda → DynamoDB
→ did SDK request leave Lambda?
→ did DynamoDB authorize it?
```

This narrows:
- where to inspect logs,
- which permission model applies,
- whether networking/configuration matters.

#### 4.1.7.5 Two Fundamental Permission Directions

This is one of the strongest exam distinctions:

```text
AWS service → Lambda
```

and:

```text
Lambda → AWS service
```

use:
- different authorization models.

#### 4.1.7.6 AWS Service Invokes Lambda

For supported AWS services directly invoking Lambda:

```text
SNS / API Gateway / EventBridge
          |
          | lambda:InvokeFunction
          v
        Lambda
```

Lambda commonly needs:
- a resource-based policy
allowing:
- the service principal,
- expected source ARN,
- source account where applicable.

Fast rule:

```text
service cannot invoke Lambda
→ inspect Lambda resource-based permission
```

#### 4.1.7.7 Lambda Calls Another AWS Service

When Lambda code calls:

```text
DynamoDB
S3
SNS
SQS
Secrets Manager
```

it uses:
- temporary credentials from the Lambda execution role.

Concept:

```text
Lambda code
→ execution-role credentials
→ AWS API
```

Fast rule:

```text
Lambda cannot call DynamoDB/S3/etc.
→ inspect execution-role authorization
```

#### 4.1.7.8 Invocation Permission vs Execution Permission

```text
API Gateway cannot invoke Lambda
→ Lambda resource-based policy

Lambda cannot PutItem to DynamoDB
→ Lambda execution role
```

Do not solve:
- one direction with the other's permission model.

#### 4.1.7.9 Resource-Based Policy Conditions

Invocation permissions should normally restrict:
- service principal,
- source ARN,
- source account where applicable.

Example:

```text
allow API Gateway
+
restrict SourceArn to expected API/stage
```

If `SourceArn` is wrong:
- legitimate invocation can fail.

#### 4.1.7.10 `iam:PassRole` Is Different

`iam:PassRole` is used when:
- a principal configures an AWS service to use a role.

Example:

```text
developer configures Lambda execution role
→ may need iam:PassRole
```

It is not:
- the permission used by running Lambda code to call DynamoDB.

Running function:

```text
Lambda → DynamoDB
→ execution role needs dynamodb action
```

#### 4.1.7.11 AWS SDK Credentials in Lambda

Lambda supplies:
- temporary execution-role credentials.

AWS SDKs normally obtain them through:
- the default credential provider chain.

Therefore:

```text
hard-code AWS access keys in Lambda
```

is not:
- the correct fix for missing downstream authorization.

#### 4.1.7.12 `AccessDenied` Debugging Pattern

When a downstream call returns:

```text
AccessDenied
```

determine:

```text
WHO?
→ principal/role

WHAT?
→ denied API action

WHICH RESOURCE?
→ ARN/resource

WHICH POLICY LAYER?
→ identity policy
→ resource policy
→ KMS key policy
→ other applicable policy layer
```

Then:
- correct the smallest missing/conflicting permission.

#### 4.1.7.13 Resource Policies Can Matter

An identity policy allowing an operation does not always mean:
- final authorization succeeds.

Resource-based policies can affect access to:
- S3 buckets,
- SQS queues,
- SNS topics,
- Lambda functions,
- KMS keys.

Rule:

```text
identity permission present
+
resource policy denies/restricts
→ access can still fail
```

#### 4.1.7.14 KMS as an Additional Boundary

Encrypted integration resources can require:
- KMS permissions in addition to service permissions.

Example:

```text
Lambda consumes encrypted SQS queue
```

may require:
- SQS permissions,
- `kms:Decrypt`.

Therefore:

```text
SQS authorization looks correct
but encrypted source still fails
→ inspect KMS
```

#### 4.1.7.15 Configuration Is Part of the Integration

Correct IAM does not guarantee:
- correct integration.

Common configuration failures:
- wrong ARN,
- wrong Region,
- wrong queue URL,
- wrong table name,
- wrong endpoint,
- disabled event source mapping,
- wrong environment variable,
- incorrect alias/version.

Do not reduce every integration problem to:
- IAM.

#### 4.1.7.16 Lambda Environment Variables

Environment variables can carry:
- resource names,
- endpoint names,
- feature flags,
- configuration.

Current Lambda behavior:
- environment variable values are literal strings,
- they are not automatically expanded.

Example:

```text
TABLE_NAME=${STAGE}-orders
```

does not automatically become:

```text
prod-orders
```

Expansion must be performed by:
- deployment logic,
- application logic.

#### 4.1.7.17 Version-Specific Configuration

Lambda environment variables are:
- version-specific.

When a Lambda version is published:
- its environment-variable configuration is fixed with that version.

Therefore:

```text
prod alias → older version
```

can also mean:
- older integration configuration.

When dev works but prod does not:
- compare alias/version and configuration,
not only source code.

#### 4.1.7.18 Region Constraints

Some integrations require:
- compatible Regions.

Important SQS example:

```text
Lambda function
+
SQS event source mapping
→ same Region required
```

They can:
- be in different accounts,
subject to supported cross-account configuration.

If trigger does not fire:
- verify Region/topology.

#### 4.1.7.19 Networking vs IAM

A Lambda can have:
- correct IAM permission

but fail because:
- it cannot reach the endpoint.

Symptoms such as:

```text
timeout
connection refused
DNS failure
UnknownHostException
```

point first toward:
- networking,
- endpoint configuration,
- downstream latency.

Fast distinction:

```text
AccessDenied
→ authorization

timeout/DNS/connection error
→ connectivity
```

#### 4.1.7.20 Lambda Networking Model

By default, Lambda has connectivity through:
- the Lambda-managed networking environment.

When Lambda is configured to access resources inside:
- your VPC,

you become responsible for:
- the applicable VPC network path.

Check as needed:
- routes,
- NAT,
- VPC endpoints,
- security groups,
- DNS,
- NACLs.

#### 4.1.7.21 Public Subnet Trap

Attaching Lambda to:
- a public subnet

does not automatically provide:
- internet access.

A VPC-connected Lambda commonly needs:
- appropriate private-subnet routing,
- NAT for internet access where required,
- or VPC endpoints for supported AWS services.

This is a high-value exam trap.

#### 4.1.7.22 VPC Endpoints

For private connectivity to supported AWS services:

```text
VPC-connected Lambda
→ VPC endpoint
→ AWS service
```

can avoid:
- internet/NAT path.

Use when:
- supported by the target service,
- private AWS service access is required.

#### 4.1.7.23 Timeout Is a Symptom

A timeout can mean:
- unreachable endpoint,
- blocked route,
- DNS issue,
- slow dependency,
- application deadlock,
- insufficient timeout.

Therefore:

```text
timeout
≠ automatically increase timeout
```

First determine:
- where elapsed time is spent.

#### 4.1.7.24 API Gateway → Lambda Integration

Debug the chain:

```text
client
→ API Gateway
→ Lambda invocation
→ Lambda execution
→ Lambda response
→ API Gateway response handling
```

Failure can occur:
- before Lambda invocation,
- inside Lambda,
- in response-contract handling.

#### 4.1.7.25 API Gateway `500`

An API Gateway `500` can indicate:
- integration/invocation configuration problem.

Example:
- API Gateway lacks permission to invoke Lambda.

Check:
- API Gateway integration/access evidence,
- Lambda invocation evidence,
- Lambda resource-based permission,
- integration configuration.

#### 4.1.7.26 API Gateway `502`

A common Lambda proxy integration failure:

```text
Lambda executes successfully
but returns malformed proxy response
→ API Gateway returns 502
```

Therefore:

```text
Lambda invocation succeeded
≠ API integration succeeded
```

#### 4.1.7.27 Lambda Proxy Response Contract

Conceptually, Lambda proxy responses require a structure such as:

```json
{
  "statusCode": 200,
  "headers": {},
  "body": "..."
}
```

If output does not match:
- API Gateway can reject it.

This is:
- an integration contract failure,
not necessarily:
- an invocation failure.

#### 4.1.7.28 Manual Lambda Test vs End-to-End Test

A manual Lambda test proves:
- the handler can execute with that supplied test event.

It does not prove:
- API Gateway permission,
- event source mapping,
- real event shape,
- request/response mapping,
- network path.

Rule:

```text
manual function test succeeds
but automatic integration fails
→ debug integration path
```

#### 4.1.7.29 Event Shape Mismatch

A function may work with:
- a hand-crafted test event

but fail with:
- real service event.

Reasons:
- field paths differ,
- body is encoded/stringified,
- batch structure differs,
- event version differs,
- headers/attributes differ.

Use:
- actual event contract/sample,
- structured logs.

#### 4.1.7.30 SQS → Lambda Event Source Mapping

This model is essential:

```text
Lambda event source mapping
→ polls SQS
→ batches messages
→ invokes Lambda synchronously
```

SQS does not:
- simply push each message directly to Lambda.

This explains:
- polling,
- batching,
- visibility timeout,
- retry,
- redelivery behavior.

#### 4.1.7.31 SQS Event Source Mapping State

If messages exist but Lambda is not processing them, check:
- event source mapping exists,
- mapping enabled,
- source ARN correct,
- target function correct,
- Region compatible,
- execution role can read/delete messages,
- KMS permissions if encrypted,
- throttling/concurrency.

#### 4.1.7.32 SQS Execution Role Permissions

Lambda execution role needs permissions to:
- receive/read messages,
- delete messages,
- retrieve queue attributes as required by the integration.

AWS provides:

```text
AWSLambdaSQSQueueExecutionRole
```

as a standard managed-policy baseline.

Encrypted queues can additionally require:
- `kms:Decrypt`.

#### 4.1.7.33 SQS Visibility Timeout

AWS requires:

```text
Lambda function timeout
<=
SQS visibility timeout
```

AWS also recommends:
- visibility timeout of at least six times the Lambda function timeout,
- adjusted for batching window when used.

Why:

```text
Lambda receives batch
→ messages become temporarily invisible

success
→ messages deleted

failure
→ messages can become visible again
```

Poor visibility settings can contribute to:
- duplicate/repeated processing.

#### 4.1.7.34 SQS Default Batch Failure

By default:

```text
one record causes batch failure
→ whole batch can become visible again
```

Result:
- messages that already succeeded can be retried.

Therefore consumers should be:
- idempotent.

#### 4.1.7.35 Partial Batch Response

Enable:

```text
ReportBatchItemFailures
```

to report:
- only failed records.

Result:
- successful records do not need to be retried with failed ones.

Important trap:

```text
uncaught function exception
→ entire batch treated as failed
```

For partial batch reporting:
- application logic must catch/process failures,
- return the required failed-item structure.

#### 4.1.7.36 FIFO Partial Batch Behavior

For FIFO queues:
- ordering must be preserved.

AWS guidance:
- after first failure,
- stop processing later records when continuing would violate order,
- report failed/unprocessed records appropriately.

#### 4.1.7.37 SQS Retry Backoff and Backpressure

When SQS-triggered Lambda processing fails:
- Lambda uses backoff behavior.

Behavior differs for:
- function-code errors,
- throttling.

A growing queue can reflect:
- function errors,
- throttling,
- insufficient concurrency,
- slow processing,
- inadequate batch throughput.

Useful source metrics:

```text
ApproximateAgeOfOldestMessage ↑
ApproximateNumberOfMessagesVisible ↑
```

These indicate:
- backlog/backpressure.

#### 4.1.7.38 SQS Dead-Letter Queue

Repeatedly unprocessed messages can move to:
- an SQS DLQ through redrive policy.

The source records AWS guidance of:
- `maxReceiveCount` at least 5 as a general Lambda/SQS starting recommendation.

DLQ growth means:
- repeated processing failure.

It does not reveal:
- exact cause.

#### 4.1.7.39 Event Source Mapping vs Async Invocation

Do not confuse:

```text
SQS event source mapping
```

with:

```text
Lambda asynchronous invocation
```

SQS:
- is polled by Lambda,
- invokes Lambda synchronously with batches.

Therefore:
- retry/DLQ semantics differ from native asynchronous Lambda invocation.

#### 4.1.7.40 Stream Event Sources

Lambda event source mappings also support:
- Kinesis,
- DynamoDB Streams.

Core model:

```text
event source mapping
→ reads records
→ batches
→ invokes Lambda
```

But:
- retry/order behavior differs from SQS.

#### 4.1.7.41 Stream Batch Blocking

For stream sources, a failing record/batch can:
- block progress for the affected shard while retries continue.

Symptoms:
- iterator age grows,
- old records are retried,
- downstream records are delayed.

#### 4.1.7.42 Stream Error Controls

Depending on source, Lambda supports controls such as:

```text
BisectBatchOnFunctionError
MaximumRetryAttempts
MaximumRecordAgeInSeconds
DestinationConfig
ReportBatchItemFailures
```

These help:
- isolate,
- bound,
- redirect
poison-record behavior.

`BisectBatchOnFunctionError`:

```text
failed batch
→ split in two
→ retry smaller batches
```

Purpose:
- narrow problematic records.

#### 4.1.7.43 Event Source Mapping Metrics and Logs

Correlate:
- source metrics,
- Lambda metrics,
- Lambda logs.

Example SQS pattern:

```text
oldest message age ↑
visible messages ↑
Lambda Errors ↑
concurrency ↓
```

Then:
- inspect function logs for processing cause.

#### 4.1.7.44 Idempotency

Event-driven systems can process:
- the same event more than once.

AWS Lambda SQS documentation explicitly recommends:
- idempotent function code.

Idempotent means:

```text
same event processed again
→ no unintended duplicate side effect
```

Example:
- do not charge a customer twice.

#### 4.1.7.45 Direct SDK Integration

For:

```text
Lambda
→ AWS SDK
→ DynamoDB
```

debug:

```text
request parameters
→ execution credentials
→ Region/endpoint
→ service response
```

Preserve:
- exact SDK/service error code,
- relevant request context.

#### 4.1.7.46 DynamoDB `AccessDenied`

If Lambda logs show:

```text
AccessDeniedException
for dynamodb:PutItem
```

inspect:
- Lambda execution role,
- relevant resource policy if applicable.

Do not inspect first:
- Lambda invocation resource policy.

#### 4.1.7.47 DynamoDB Throttling

If authorization succeeds but DynamoDB throttles:
- this is capacity/access-pattern/service behavior.

Investigate:
- throttling metrics,
- partition/access pattern,
- retry behavior,
- capacity configuration.

Do not:
- add IAM permissions.

#### 4.1.7.48 Retryable vs Non-Retryable Failures

Distinguish:

```text
transient
→ retry may succeed

permanent/configuration
→ retry repeats failure
```

Examples:

```text
throttling / temporary service failure
→ retry with backoff

AccessDenied / invalid parameter
→ fix configuration/permission
```

Blind retries:
- increase load,
- delay diagnosis.

#### 4.1.7.49 Retry Multiplication

Retry layers can stack:

```text
SQS redelivery
× Lambda retry/batch retry
× AWS SDK retry
× custom application retry
```

Result:
- unexpectedly high downstream call volume.

When repeated calls appear:
- identify every retry layer.

#### 4.1.7.50 Timeout Budget

For synchronous chains:

```text
client
→ API Gateway
→ Lambda
→ downstream service
```

each layer has:
- its own timeout constraints.

If downstream timeout nearly consumes:
- the whole Lambda/API budget,

there may be:
- insufficient time for retries/recovery.

Debug:
- the complete timeout chain.

#### 4.1.7.51 Correlation IDs and Traces

To follow one request across services:
- propagate correlation/request IDs where practical.

Use in:
- structured logs,
- traces,
- downstream metadata.

Do not normally use:
- request ID as a CloudWatch metric dimension,
because:
- cardinality becomes high.

Distributed tracing helps answer:

```text
which service was called?
how long did each segment take?
where did failure occur?
```

Then:
- service logs/API errors provide detail.

#### 4.1.7.52 Metrics, Logs, and Traces

Strong integration debugging:

```text
metrics
→ when/where behavior changed

traces
→ which service boundary/path failed

logs/service errors
→ exact reason/context
```

Detailed telemetry interpretation belongs to:
- 4.1.2–4.1.5.

#### 4.1.7.53 Failure-Location Patterns

##### 4.1.7.53.1 Event Not Produced
If target receives nothing:
- first verify producer emitted the event.

Do not immediately:
- change consumer IAM.

##### 4.1.7.53.2 Event Produced, Target Not Invoked
Likely:
- trigger/mapping disabled,
- invocation permission missing,
- filter/event pattern mismatch,
- wrong ARN/Region,
- source policy issue,
- throttling/concurrency.

##### 4.1.7.53.3 Target Invoked, Fails Immediately
Likely:
- payload/event shape,
- missing configuration,
- initialization/code exception.

Check:
- target logs.

##### 4.1.7.53.4 Target Runs, Downstream Call Fails
Likely:
- execution-role permission,
- resource policy,
- KMS,
- networking,
- wrong endpoint/resource,
- downstream throttling/error.

Check:
- SDK/service response,
- network evidence.

#### 4.1.7.54 Environment-Specific Integration Failure

If dev works but prod does not, compare:
- IAM roles/policies,
- resource policies,
- ARNs,
- Regions,
- environment variables,
- VPC/subnets/security groups,
- KMS keys,
- aliases/versions,
- event source mappings.

Do not assume:
- application code differs.

#### 4.1.7.55 Manual Works, Automatic Fails

Example:

```text
manual Lambda test works
SQS trigger does not
```

Strong clue:
- trigger/event source/configuration/permission path.

Manual invocation:
- bypasses source integration.

#### 4.1.7.56 Works Outside VPC, Fails Inside VPC

Strong clue:
- network architecture.

Check:
- routes,
- NAT,
- VPC endpoints,
- security groups,
- DNS.

Do not broaden IAM unless:
- authorization error says so.

#### 4.1.7.57 Works for Some Messages Only

Possible:
- payload-dependent defect,
- poison message,
- batch handling,
- message size/format,
- ordering,
- data-dependent downstream failure.

Use:
- record identifiers,
- structured logs,
- partial batch response where appropriate.

#### 4.1.7.58 Duplicate Processing

Possible causes:
- retries,
- redelivery,
- batch failure,
- visibility timeout,
- client retries,
- at-least-once delivery.

Correct response:
- understand retry layer,
- make consumer idempotent.

Do not assume:
- producer generated duplicate business events.

#### 4.1.7.59 Integration Stops Under Load

Check:
- Lambda throttles/concurrency,
- queue backlog,
- downstream throttling,
- connection/resource limits,
- batch throughput,
- timeouts.

This may be:
- capacity/backpressure,
not:
- static integration misconfiguration.

#### 4.1.7.60 Error Taxonomy

Use error type as a routing signal:

```text
AccessDenied
→ IAM/resource/KMS policy

timeout / DNS / connection error
→ network/downstream latency

ResourceNotFound
→ resource name/ARN/Region/config

TooManyRequests / throttling
→ capacity/concurrency/retry

Malformed response
→ integration contract

messages repeatedly return
→ batch failure/visibility/idempotency

no invocation
→ producer/trigger/mapping/invoke permission
```

#### 4.1.7.61 Debugging Sequence

##### 4.1.7.61.1 Draw the Integration Path

Example:

```text
API Gateway
→ Lambda
→ DynamoDB
```

##### 4.1.7.61.2 Find Last Known Successful Boundary

Example:

```text
API request reached API Gateway
Lambda invocation absent
```

Focus:
- API Gateway → Lambda.

##### 4.1.7.61.3 Classify Failure

```text
authorization?
network?
configuration?
payload?
throttling?
retry/batch?
```

##### 4.1.7.61.4 Inspect Correct Evidence

Use as appropriate:
- service output,
- metrics,
- function logs,
- traces,
- event source mapping state,
- IAM/resource/KMS policies.

##### 4.1.7.61.5 Fix the Narrowest Cause
Do not:
- broadly expand unrelated permissions,
- change network and IAM simultaneously,
- add uncontrolled retries.

##### 4.1.7.61.6 Verify End-to-End
A manual unit test is insufficient when:
- production behavior depends on the actual service integration.

#### 4.1.7.62 Permission Decision Flow

```text
Who initiates failing action?
        |
        +--> AWS service invokes Lambda
        |      → Lambda resource-based policy
        |
        +--> Lambda calls AWS API
        |      → execution role
        |
        +--> encrypted resource
        |      → KMS permissions/key policy
        |
        '--> target resource has policy
               → resource policy too
```

#### 4.1.7.63 Connectivity Decision Flow

```text
AccessDenied?
→ authorization

Timeout / DNS / connection failure?
→ networking

ResourceNotFound?
→ name / ARN / Region / config

Throttling?
→ capacity / concurrency / retry

Malformed integration response?
→ payload/contract
```

#### 4.1.7.64 SQS-Lambda Decision Flow

```text
messages accumulating
       |
       v
event source mapping enabled?
       |
       v
execution role can read queue?
       |
       v
KMS decrypt if encrypted?
       |
       v
Lambda invoked?
       |
       +--> no
       |     → mapping/config/permission/throttle
       |
       '--> yes
              |
              v
          function errors?
              |
              +--> yes → logs/batch handling
              |
              '--> no → throughput/backpressure
```

#### 4.1.7.65 API Gateway-Lambda Decision Flow

```text
client error
   |
   v
request reached API Gateway?
   |
   v
Lambda invoked?
   |
   +--> no
   |     → integration config / invoke permission
   |
   '--> yes
          |
          v
      Lambda error?
          |
          +--> yes → function logs
          |
          '--> no
                 |
                 v
         valid proxy/integration response?
                 |
                 +--> no → response contract/mapping
                 '--> yes → downstream/client path
```

#### 4.1.7.66 Common Exam Traps

##### 4.1.7.66.1 Lambda Execution Role Lets API Gateway Invoke Lambda
- False.
- Direct service invocation uses:
  - Lambda resource-based permission.

##### 4.1.7.66.2 Lambda Resource Policy Lets Function Write DynamoDB
- False.
- Function code uses:
  - execution role.

##### 4.1.7.66.3 Hard-Code AWS Credentials to Fix SDK Access
- False.

##### 4.1.7.66.4 Public Subnet Automatically Gives VPC Lambda Internet
- False.

##### 4.1.7.66.5 SQS Pushes Every Message Directly to Lambda
- False.
- Lambda polls through event source mapping.

##### 4.1.7.66.6 One Failed SQS Record Retries Only That Record by Default
- False.
- Whole batch can be retried.

##### 4.1.7.66.7 Successful Manual Lambda Test Proves Trigger Works
- False.

##### 4.1.7.66.8 Timeout Means IAM Problem
- False.

##### 4.1.7.66.9 `AccessDenied` Means Network Problem
- False.

##### 4.1.7.66.10 Increase Lambda Timeout for Every Integration Timeout
- False.

##### 4.1.7.66.11 Retry `AccessDenied` Until It Works
- False.

##### 4.1.7.66.12 Duplicate SQS Processing Means Lambda Is Broken
- False.
- At-least-once/retry behavior requires idempotency.

##### 4.1.7.66.13 Lambda Environment Variable References Auto-Expand
- False.
- Values are literal strings.

##### 4.1.7.66.14 Service Permission Alone Guarantees Encrypted Resource Access
- False.
- KMS can be an additional boundary.

#### 4.1.7.67 Connections and Scope Boundary

#### 4.1.7.69 Exam-Level Knowledge Frame

##### 4.1.7.69.1 Know These Cold

**Lambda resource-based policy**
→ allows supported services/principals to invoke Lambda.

**Lambda execution role**
→ credentials function code uses to call AWS services.

**`iam:PassRole`**
→ permission to configure a service to use a role; not normal runtime SDK authorization.

**Event source mapping**
→ Lambda-managed polling/batching for supported queues/streams.

**SQS visibility timeout**
→ period message remains hidden after receipt.

**`ReportBatchItemFailures`**
→ report individual failed records instead of retrying successful records with them.

**Idempotency**
→ repeated processing causes no unintended duplicate side effect.

**VPC endpoint**
→ private connectivity to supported AWS service.

**KMS permission**
→ additional authorization for encrypted resources.

**API Gateway proxy response**
→ Lambda must return expected integration response shape.

**Backpressure**
→ producer rate exceeds consumer throughput.

##### 4.1.7.69.2 Fastest Exam Discriminator

```text
service cannot invoke Lambda?
→ Lambda resource policy

Lambda cannot call AWS service?
→ execution role

encrypted source?
→ KMS too

SQS messages accumulate, Lambda not invoked?
→ event source mapping + role + Region + concurrency

SQS retries whole batch?
→ default batch failure behavior

retry only failed records?
→ ReportBatchItemFailures

VPC Lambda times out?
→ network path / NAT / VPC endpoint

API Gateway 502 after Lambda ran?
→ proxy response contract

manual test works, trigger fails?
→ integration path

duplicates?
→ retries/redelivery + idempotency
```

##### 4.1.7.69.3 Final Principle
- **Debug AWS service integrations by modeling the application as explicit service boundaries and identifying the first boundary where expected evidence disappears or an error appears. Separate invocation authorization from execution authorization: supported AWS services invoking Lambda use Lambda resource-based permissions, while Lambda code calling downstream AWS APIs uses temporary credentials from its execution role. Then distinguish authorization from resource/KMS policy, configuration, networking, event contract, throttling, batching, and retry behavior. For SQS and stream integrations, reason from Lambda event source mapping semantics—polling, batching, visibility/retry behavior, partial failures, backpressure, and idempotency—rather than assuming direct push. For API Gateway/Lambda, verify both invocation permission and the response contract. Use metrics to find the unhealthy edge, traces to follow the path, and logs/API errors to establish the exact root cause.**
