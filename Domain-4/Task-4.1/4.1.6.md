### 4.1.6 Troubleshoot deployment failures by using service output logs

#### 4.1.6.1 Exam and Task Context

##### 4.1.6.1.1 Domain and Task
- Domain 4 is **Troubleshooting and Optimization**.
- Task 4.1 is **Assist in a root cause analysis**.
- Skill 4.1.6 is **Troubleshoot deployment failures by using service output logs**.

##### 4.1.6.1.2 Position Inside Task 4.1
- 4.1.5:
  - review application health by using dashboards and insights.
- 4.1.6:
  - troubleshoot deployment failures from deployment-service output.
- 4.1.7:
  - debug runtime service-integration issues.

Core question:

**When deployment fails, which AWS service performed the failing step, what exact unit failed, and what does that service's output say about the underlying cause?**

#### 4.1.6.2 Core Mental Model

```text
DEPLOYMENT FAILED
       |
       v
Which service performed the failed step?
       |
       +--> CloudFormation / SAM
       +--> CodePipeline
       +--> CodeBuild
       +--> CodeDeploy
       '--> Lambda direct deployment
       |
       v
failed resource / action / phase / lifecycle event
       |
       v
status reason / command output / service error
       |
       v
follow provider boundary
       |
       v
underlying cause
```

Fast rule:

```text
deployment failed
→ inspect deployment service output first
→ identify exact failing component
→ inspect deeper logs only where evidence points
```

#### 4.1.6.3 Deployment Failure vs Runtime Failure

##### 4.1.6.3.1 Deployment Failure
The new revision/infrastructure:
- could not be created,
- updated,
- built,
- packaged,
- validated,
- or shifted into service.

Examples:

```text
CloudFormation CREATE_FAILED
CodeBuild build FAILED
CodeDeploy lifecycle hook failed
Lambda UpdateFunctionCode rejected
```

##### 4.1.6.3.2 Runtime Failure
Deployment:
- completed successfully.

Application:
- fails after receiving traffic.

Examples:

```text
Lambda exception
API returns 500
dependency timeout
business logic defect
```

Rule:

```text
deployment status FAILED
→ 4.1.6

deployment SUCCEEDED but app unhealthy
→ 4.1.5 / 4.1.7
```

#### 4.1.6.4 Service Output Is the First Evidence

AWS deployment services expose failure information through:
- status,
- events,
- action/phase details,
- status reasons,
- command output,
- lifecycle results,
- service error responses.

Think:

```text
FAILED
→ WHERE?
→ WHY?
→ WHICH SERVICE RETURNED THE ERROR?
```

Do not begin with:
- unrelated application logs,
- broad dashboards,
- random service logs.

#### 4.1.6.5 CloudFormation Stack Events

When CloudFormation deployment fails:

```text
stack
→ Events
→ failed resource
→ ResourceStatusReason
```

Typical statuses include:

```text
CREATE_FAILED
UPDATE_FAILED
DELETE_FAILED
ROLLBACK_IN_PROGRESS
UPDATE_ROLLBACK_IN_PROGRESS
```

The most useful evidence is usually:
- the first relevant failed resource,
- its `ResourceStatusReason`.

#### 4.1.6.6 CloudFormation Resource Failure

Example:

```text
AWS::Lambda::Function
CREATE_FAILED

ResourceStatusReason:
The role defined for the function cannot be assumed by Lambda.
```

Correct direction:
- Lambda execution-role trust configuration.

Wrong direction:
- unrelated S3/DynamoDB runtime behavior.

#### 4.1.6.7 Underlying Service Errors

CloudFormation calls:
- underlying AWS service APIs.

Therefore:

```text
CloudFormation resource failure
→ can contain Lambda/IAM/S3/API Gateway/etc. error
```

Mental model:

```text
CloudFormation
→ requests resource operation
→ target service rejects it
→ error appears in stack event
```

CloudFormation may be:
- the orchestrator,
not:
- the true failing service.

#### 4.1.6.8 Find the Earliest Relevant Failure

A root failure can trigger many secondary events.

Example:

```text
Lambda CREATE_FAILED
Stack CREATE_FAILED
ROLLBACK_IN_PROGRESS
DELETE_IN_PROGRESS
ROLLBACK_COMPLETE
```

Root cause:
- Lambda `CREATE_FAILED` status reason.

Not:
- final `ROLLBACK_COMPLETE`.

Rule:

```text
rollback state
→ consequence

earliest meaningful *_FAILED event
→ likely cause
```

#### 4.1.6.9 CloudFormation Operation Filtering

Current CloudFormation supports:
- operation IDs,
- filtering events by operation,
- failure-focused event views.

Use when:
- stack event history is large.

Goal:

```text
failed stack operation
→ only events for that operation
→ failed resource
```

#### 4.1.6.10 Rollback Status Is Not Root Cause

`ROLLBACK_COMPLETE` means:
- stack creation failed,
- rollback completed.

`UPDATE_ROLLBACK_COMPLETE` means:
- update failed,
- rollback completed.

Neither answers:

```text
why did the original operation fail?
```

Always search earlier for:
- `CREATE_FAILED`,
- `UPDATE_FAILED`,
- corresponding resource status reason.

#### 4.1.6.11 CloudFormation Permission Failures

Example:

```text
AccessDenied
not authorized to perform ...
```

Possible principal:
- deploying identity,
- CloudFormation service role,
- underlying resource role.

Do not automatically modify:
- Lambda execution role.

First determine:

```text
WHO called the denied API?
WHAT action?
ON WHICH resource?
```

Then:
- correct least-privilege permission/trust.

#### 4.1.6.12 CloudFormation Resource Conflicts

Examples:

```text
resource already exists
name already in use
invalid property
unsupported configuration
```

These are:
- provisioning/configuration problems.

Application runtime logs:
- usually irrelevant.

#### 4.1.6.13 EC2 Bootstrap Failures

When CloudFormation points to:
- EC2/bootstrap/configuration failure,

AWS documents deeper evidence such as:
- `cloud-init` logs,
- CloudFormation helper (`cfn`) logs.

Use them only after:
- stack events point to instance bootstrap.

#### 4.1.6.14 AWS SAM Deployment Failures

SAM commonly deploys through:
- CloudFormation.

Typical path:

```text
sam deploy fails
→ inspect SAM/CLI output
→ inspect CloudFormation stack events
→ locate failed resource/status reason
```

SAM is not:
- a completely separate provisioning engine.

#### 4.1.6.15 SAM Template/Transform Failure

Failure can occur before:
- normal resource creation.

Possible causes:
- invalid template,
- invalid SAM property,
- packaging issue,
- transformation problem.

If template processing fails:

```text
no resource runtime exists yet
→ runtime application logs may not exist
```

#### 4.1.6.16 Direct Lambda Deployment

When updating Lambda directly through:
- API,
- AWS CLI,
- SDK,
- console,

Lambda returns:
- deployment error directly.

Use:
- that Lambda response as primary evidence.

#### 4.1.6.17 Lambda Through an Orchestrator

AWS Lambda documentation explicitly directs deployments performed through:
- CloudFormation,
- CodeDeploy,
- CodePipeline

to:
- the logs/event stream of the orchestrating service.

Pattern:

```text
orchestrator
→ failed action/resource
→ Lambda response
```

Start where:
- the deployment was initiated.

#### 4.1.6.18 Lambda Deployment Failure Categories

Common categories include:
- package too large,
- missing dependency/module/class,
- invalid handler,
- incompatible package,
- layer/package problem,
- code storage quota,
- invalid configuration.

Keep distinct:

```text
deployment/package rejected
≠ function invoked and then throws runtime exception
```

#### 4.1.6.19 Lambda Package Size

Example:

```text
RequestEntityTooLargeException
```

Direction:
- package/deployment mechanism/size.

Do not:
- increase Lambda timeout.

#### 4.1.6.20 Lambda Import/Class Errors

Examples:

```text
Cannot find module
Unable to import module
Class not found
No such file or directory
```

Likely causes:
- package layout,
- missing dependency,
- wrong runtime artifact,
- incorrect handler/package structure.

#### 4.1.6.21 Lambda Handler Error

Examples:

```text
invalid handler
undefined method handler
```

Investigate:
- configured handler,
- package code/layout.

Do not start with:
- VPC networking.

#### 4.1.6.22 CodePipeline Failure View

CodePipeline orchestrates:
- stages/actions.

Troubleshooting sequence:

```text
pipeline
→ failed stage
→ failed action
→ action execution details
→ provider error/output
```

CodePipeline often tells you:
- which downstream service failed.

Then inspect:
- that provider.

#### 4.1.6.23 CodePipeline Is Often Not Root Cause

Example:

```text
CodePipeline
→ CodeBuild action FAILED
```

Possible actual cause:

```text
npm test
→ exit status 1
```

Therefore:

```text
pipeline failed
≠ CodePipeline itself is defective
```

#### 4.1.6.24 Source, Build, and Deploy Actions

##### 4.1.6.24.1 Source Failure
Inspect:
- repository/provider connection,
- permissions,
- revision,
- source artifact access.

Do not jump to:
- deployment target logs.

##### 4.1.6.24.2 Build Failure
If CodeBuild action fails:
- open CodeBuild build details/logs.

Inspect:
- phase,
- command,
- exit code,
- stderr/output.

##### 4.1.6.24.3 Deploy Failure
If deploy action fails:
- follow the provider.

Examples:
- CloudFormation,
- CodeDeploy,
- ECS,
- Lambda.

CodePipeline:
- identifies the failing action.

Provider:
- usually contains the detailed reason.

#### 4.1.6.25 CodeBuild Build Phases

Common phases:

```text
INSTALL
PRE_BUILD
BUILD
POST_BUILD
UPLOAD_ARTIFACTS
```

A failed phase narrows:
- the kind of operation that failed.

Example:

```text
BUILD
COMMAND_EXECUTION_ERROR
npm test
exit status 1
```

Interpretation:
- build/test command failed.

Not:
- CodeDeploy lifecycle issue.

#### 4.1.6.26 CodeBuild Command and Dependency Failures

Commands such as:

```text
npm install
mvn package
pip install
```

can fail because of:
- dependency resolution,
- repository access,
- credentials,
- network,
- package/version problem.

Use:
- command output.

#### 4.1.6.27 CodeBuild Image Pull Failure

Example:

```text
BUILD_CONTAINER_UNABLE_TO_PULL_IMAGE
```

Direction:
- build image availability,
- access,
- configuration.

Not:
- production deployment target.

#### 4.1.6.28 CodeBuild Parameter/Secret/Artifact Access

If build cannot retrieve:
- Parameter Store value,
- secret,
- artifact/cache,
- source dependency,

inspect:
- CodeBuild service-role permissions,
- resource access.

Identity:

```text
CodeBuild service role
```

not necessarily:
- developer IAM identity.

#### 4.1.6.29 CodeBuild Logs

CodeBuild integrates with:
- CloudWatch Logs.

Diagnostic sequence:

```text
failed build
→ failed phase
→ failed command
→ command output
```

Use logs to inspect:
- compile/test failures,
- packaging errors,
- dependency problems,
- artifact upload problems.

Advanced tools such as:
- CodeBuild sandbox,
- Session Manager

may exist, but:
- logs/output are the exam-level first evidence.

#### 4.1.6.30 CodeDeploy Is Platform-Specific

CodeDeploy supports:
- EC2/On-Premises,
- Lambda,
- ECS.

Troubleshooting differs by:
- compute platform.

Do not assume:
- EC2 agent-log behavior applies to Lambda/ECS.

#### 4.1.6.31 CodeDeploy Deployment Details

Start with:

```text
deployment
→ status
→ deployment details/events
→ failed target/lifecycle event
```

Goal:
- identify where rollout stopped.

#### 4.1.6.32 EC2/On-Premises Lifecycle Events

Common lifecycle events include:

```text
ApplicationStop
DownloadBundle
BeforeInstall
Install
AfterInstall
ApplicationStart
ValidateService
```

If one fails:
- inspect that lifecycle event,
- inspect script output.

Example:

```text
AfterInstall
→ script returned non-zero exit code
```

Direction:
- script/log output.

#### 4.1.6.33 EC2/On-Premises CodeDeploy Logs

AWS documents agent/deployment logs on instances.

Linux examples:

```text
/var/log/aws/codedeploy-agent/codedeploy-agent.log

/opt/codedeploy-agent/deployment-root/
  deployment-logs/codedeploy-agent-deployments.log
```

Per-deployment script output is available under:
- deployment-root deployment directories.

For multiple instances:
- CloudWatch Logs centralization is preferred over manually connecting to each host.

#### 4.1.6.34 CodeDeploy Log Scope Trap

AWS explicitly notes:
- EC2/On-Premises CodeDeploy deployment log files are not the Lambda/ECS troubleshooting model.

Therefore:

```text
Lambda/ECS CodeDeploy failure
→ do not search EC2 agent paths
```

Use:
- deployment events,
- validation-hook/application logs,
- relevant service output.

#### 4.1.6.35 Lambda CodeDeploy Hooks

Lambda deployments can use hooks such as:

```text
BeforeAllowTraffic
AfterAllowTraffic
```

These hooks:
- are Lambda functions.

Their execution output:
- appears in CloudWatch Logs.

Troubleshooting:

```text
CodeDeploy event
→ failed hook
→ hook Lambda CloudWatch Logs
→ validation error
```

#### 4.1.6.36 Hook Status Callback

Validation hooks must report:
- lifecycle event status.

If the hook runs but does not correctly report completion:

```text
hook execution exists
→ deployment can still time out/fail
```

This is especially important in:
- Lambda/ECS CodeDeploy flows.

#### 4.1.6.37 ECS Hook Timeout

AWS documents timeout cases where:
- CodeDeploy waits for lifecycle status callback.

Possible cause:
- hook Lambda lacks permission for:

```text
codedeploy:PutLifecycleEventHookExecutionStatus
```

Diagnostic path:

```text
CodeDeploy timeout
→ hook Lambda logs
→ callback/IAM permission
```

#### 4.1.6.38 Traffic-Shifting Deployment Failures

For Lambda/ECS, failure can occur during:
- validation,
- lifecycle hooks,
- traffic shift,
- alarm-triggered rollback.

Do not assume:
- deployment failure means only "artifact installation failed."

#### 4.1.6.39 Rollback Is Secondary Evidence

Rollback means:
- recovery/protection behavior activated.

It does not explain:
- the original cause.

Pattern:

```text
rollback visible
→ find earlier failure/alarm/hook
```

If deployment rolled back because a CloudWatch alarm entered `ALARM`:
- inspect the alarm,
- underlying metric,
- candidate-version behavior.

#### 4.1.6.40 IAM Failure Pattern

Deployment services use different identities:

```text
CloudFormation service role
CodeBuild service role
CodeDeploy service role
Lambda execution role
deployment caller
```

When output says:

```text
AccessDenied
```

first ask:

```text
WHO attempted the denied action?
```

Then identify:
- action,
- resource,
- policy/trust.

Do not choose:
- broad `AdministratorAccess`
when a least-privilege correction is sufficient.

#### 4.1.6.41 Artifact Failure Pattern

Possible artifacts:
- Lambda ZIP,
- container image,
- CodeBuild output,
- CodeDeploy revision,
- CloudFormation/SAM template.

Typical failures:
- missing artifact,
- wrong location,
- inaccessible S3 object,
- wrong image/tag,
- malformed package,
- missing files.

Follow:
- service output to the referenced artifact.

#### 4.1.6.42 Configuration Failure Pattern

Examples:

```text
invalid handler
invalid environment configuration
wrong runtime
invalid template property
wrong deployment group
incorrect alias/version
```

These are:
- deployment definition/configuration failures.

They can happen:
- before application runtime.

#### 4.1.6.43 Quota Failure Pattern

Deployment can fail due to:
- package size,
- code storage,
- resource quotas,
- memory/configuration constraints,
- service limits.

If output identifies:
- quota/limit condition,

do not classify it as:
- transient application error.

#### 4.1.6.44 Network Failure Pattern

Build/deployment processes may need:
- source access,
- package repository access,
- AWS endpoint access,
- target connectivity.

If logs show:
- DNS failure,
- connection timeout,
- network error,

investigate:
- the network path of the failing component.

#### 4.1.6.45 Version/Alias Failure Pattern

Lambda deployments may involve:
- versions,
- aliases,
- weighted traffic.

A deployment can fail due to:
- invalid/inconsistent alias configuration.

The source notes a CodeDeploy case where:
- a manually stopped deployment leaves an alias weighted across two versions,
- a later deployment then fails.

Direction:
- inspect alias/version state.

#### 4.1.6.46 Build Failure vs Deployment Failure

```text
compile/test/package fails
→ build failure
→ CodeBuild output

artifact exists but target update fails
→ deployment failure
→ deployment provider output
```

The distinction determines:
- which logs/events matter.

#### 4.1.6.47 Template Failure vs Resource Failure

```text
template invalid
→ validation/transformation problem

template accepted
resource CREATE_FAILED
→ provisioning/underlying-service problem
```

Do not search runtime logs if:
- provisioning never occurred.

#### 4.1.6.48 Deployment Failure vs Integration Failure

Example:

```text
Lambda deployed successfully
but cannot write to DynamoDB at runtime
```

Primarily:
- service-integration/runtime problem,
- covered by 4.1.7.

But:

```text
CloudFormation cannot create Lambda because IAM role is invalid
```

is:
- deployment failure.

#### 4.1.6.49 Troubleshooting Sequence

##### 4.1.6.49.1 Identify the Deployment Service

```text
CloudFormation?
SAM?
CodePipeline?
CodeBuild?
CodeDeploy?
Lambda direct API?
```

##### 4.1.6.49.2 Identify the Failed Unit

```text
resource
stage/action
build phase
lifecycle event
API operation
```

##### 4.1.6.49.3 Read the Explicit Output
Look for:
- service error,
- failed command,
- denied action,
- missing artifact,
- invalid configuration,
- quota,
- callback timeout.

##### 4.1.6.49.4 Follow the Provider Boundary

Example:

```text
CodePipeline
→ CodeBuild
→ build command
→ dependency repository
```

or:

```text
CloudFormation
→ Lambda resource
→ IAM role error
```

##### 4.1.6.49.5 Correct the Smallest Root Cause
Avoid:
- unrelated changes,
- broad permission expansion,
- blind retries.

##### 4.1.6.49.6 Redeploy and Verify
Confirm:
- deployment succeeds,
- expected version/resource is active,
- application health remains acceptable.

#### 4.1.6.51 Common Exam Traps

##### 4.1.6.51.1 Read Application Logs First for Every Deployment Failure
- False.
- Start with deployment-service output.

##### 4.1.6.51.2 `ROLLBACK_COMPLETE` Is Root Cause
- False.
- It is the result of an earlier failure.

##### 4.1.6.51.3 CodePipeline Failure Means CodePipeline Is Broken
- False.
- It may surface a provider/action failure.

##### 4.1.6.51.4 CloudFormation Error Is Always CloudFormation's Own Error
- False.
- It often surfaces underlying service errors.

##### 4.1.6.51.5 `AccessDenied` Means Lambda Execution Role
- False.
- Identify the actual calling principal.

##### 4.1.6.51.6 EC2 CodeDeploy Agent Logs Apply to Lambda/ECS
- False.

##### 4.1.6.51.7 Build Failure = Deployment Failure
- False.

##### 4.1.6.51.8 Successful Rollback Means Deployment Succeeded
- False.
- It means recovery succeeded after failure.

##### 4.1.6.51.9 Increase Timeout for Package-Size Error
- False.

##### 4.1.6.51.10 Retry Repeatedly Without Reading Output
- Poor troubleshooting.
- Deterministic IAM/config/package errors persist until corrected.

#### 4.1.6.54 Exam-Level Knowledge Frame

##### 4.1.6.54.1 Know These Cold

**CloudFormation Events**
→ first place for stack resource provisioning failures.

**`ResourceStatusReason`**
→ explains why a resource operation failed.

**Rollback status**
→ recovery result, not original root cause.

**CodePipeline action details**
→ identify failed provider/action.

**CodeBuild phase + logs**
→ identify failed command/build step.

**CodeDeploy lifecycle event**
→ identify failed deployment step.

**EC2 CodeDeploy agent/script logs**
→ EC2/On-Premises deployment evidence.

**Lambda CodeDeploy hook logs**
→ CloudWatch Logs for validation-hook function.

**Direct Lambda deployment**
→ inspect Lambda API/CLI error directly.

**AccessDenied**
→ identify exact caller, action, resource.

**Provider boundary**
→ orchestrator points to underlying failing service.

##### 4.1.6.54.2 Fastest Exam Discriminator

```text
SAM/CloudFormation stack failed?
→ stack Events / ResourceStatusReason

pipeline failed?
→ failed action/provider

CodeBuild failed?
→ phase + command logs

EC2 CodeDeploy hook failed?
→ lifecycle event + agent/script logs

Lambda CodeDeploy hook failed?
→ hook Lambda CloudWatch Logs

ECS CodeDeploy timeout?
→ hook callback / PutLifecycleEventHookExecutionStatus

direct Lambda update rejected?
→ Lambda deployment error

rollback visible?
→ search earlier for original failure

AccessDenied?
→ identify actual caller/service role
```

##### 4.1.6.54.3 Final Principle
- **Troubleshoot deployment failures from the outside in. Start with the AWS service that orchestrated or executed the failed deployment, identify the failed resource, stage/action, build phase, lifecycle event, or API operation, and read its status reason or command output. CloudFormation stack events identify failed resources and frequently surface underlying AWS service errors; CodePipeline identifies the failing provider action; CodeBuild phases and CloudWatch Logs identify failing build commands; CodeDeploy events and platform-specific logs identify lifecycle failures; and direct Lambda deployments expose Lambda deployment errors directly. Treat rollback as secondary evidence, identify the real calling principal for IAM failures, and follow orchestration boundaries until the lowest meaningful failing operation is clear.**
