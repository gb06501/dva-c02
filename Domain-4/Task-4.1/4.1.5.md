### 4.1.5 Review application health by using dashboards and insights

#### 4.1.5.1 Exam and Task Context

##### 4.1.5.1.1 Domain and Task
- Domain 4 is **Troubleshooting and Optimization**.
- Task 4.1 is **Assist in a root cause analysis**.
- Skill 4.1.5 is **Review application health by using dashboards and insights**.

##### 4.1.5.1.2 Position Inside Task 4.1
- 4.1.4:
  - implement custom metrics.
- 4.1.5:
  - use aggregated health views to identify the unhealthy service/resource.
- 4.1.6:
  - troubleshoot deployment failures by using service output logs.
- 4.1.7:
  - debug service integration issues.

Core question:

**How do you use CloudWatch dashboards and insight-oriented views to move from a broad application symptom to the smallest unhealthy service, operation, dependency, or resource?**

#### 4.1.5.2 Core Mental Model

```text
APPLICATION HEALTH
       |
       v
HIGH-LEVEL VIEW
       |
       +--> CloudWatch dashboard
       +--> Application Signals
       +--> Lambda Insights
       |
       v
ABNORMAL SIGNAL
       |
       +--> latency
       +--> availability
       +--> faults/errors
       +--> traffic
       +--> throttling/saturation
       +--> backlog
       +--> unhealthy SLI/SLO
       |
       v
AFFECTED COMPONENT
       |
       v
metrics / traces / logs
       |
       v
ROOT-CAUSE EVIDENCE
```

High-level health views answer:

```text
Where should I investigate first?
```

They do not automatically answer:

```text
What exact code/configuration defect caused the problem?
```

#### 4.1.5.3 CloudWatch Dashboards

A CloudWatch dashboard is:
- a reusable consolidated operational view.

It can combine:
- metrics,
- alarms,
- log/query results,
- text,
- service/resource health information.

Primary value:

```text
many signals
→ one visual context
```

A dashboard:
- organizes telemetry,
- does not create the underlying health signal.

#### 4.1.5.4 Automatic vs Custom Dashboards

CloudWatch provides:
- automatic/pre-built dashboards,
- custom dashboards.

Use automatic dashboards when:
- AWS already understands the service/resource model,
- quick resource-level review is needed.

Use custom dashboards when:
- application-specific signals must be combined.

Example:

```text
API Gateway 5XX
+
Lambda Errors
+
Lambda Duration p95
+
DynamoDB throttling
+
custom CheckoutFailures
```

#### 4.1.5.5 Health Signals

Useful application-health dimensions include:

```text
traffic
latency
availability
errors/faults
throttling
resource saturation
backlog
business failures
```

Do not judge application health from:
- one metric only.

Example:

```text
Lambda Errors = 0
resource utilization = normal
PaymentDeclines = 35%
```

Infrastructure can be:
- technically healthy,

while the application/business flow is:
- unhealthy.

This is why:
- custom metrics from 4.1.4 can belong on application dashboards.

#### 4.1.5.6 Dashboard Interpretation Rules

A dashboard does not change the semantics of the underlying metric.

Always verify:
- time range,
- statistic,
- period,
- dimensions/resource scope,
- traffic volume,
- account/Region/environment.

##### 4.1.5.6.1 Time Range

```text
24 h average
→ can hide a 5-minute incident
```

Example:

```text
24 h average latency = 120 ms
14:05–14:10 latency = 4 s
```

Troubleshooting:
- narrow to the incident window.

##### 4.1.5.6.2 Statistic

Examples:

```text
Lambda Errors
→ Sum

Lambda Duration tail
→ p95 / p99

ConcurrentExecutions
→ Max
```

Wrong statistic:
- can produce misleading health interpretation.

##### 4.1.5.6.3 Period

```text
1 hour period
→ short spike may disappear

1 minute period
→ short spike becomes visible
```

Align period to:
- incident duration.

#### 4.1.5.7 Correlated Signals

Strong health review looks for:
- multiple signals changing together.

Example:

```text
Latency ↑
ConcurrentExecutions ↑
Throttles ↑
```

Possible hypothesis:
- slower requests hold concurrency longer,
- capacity becomes saturated,
- requests are throttled.

Another example:

```text
API latency ↑
Lambda Duration ↑
DynamoDB throttling ↑
```

Likely investigation direction:
- DynamoDB capacity/access path.

Dashboard evidence:
- prioritizes investigation.

Detailed traces/logs:
- confirm the mechanism.

#### 4.1.5.8 CloudWatch Application Signals

Application Signals provides:
- application-centric operational health views.

Current AWS documentation describes signals including:
- call volume,
- availability,
- latency,
- faults,
- errors.

It also exposes:
- services,
- operations,
- dependencies,
- application topology,
- SLO health.

Mental model:

```text
application
→ service
→ operation
→ dependency
```

This is especially useful for:
- distributed applications.

#### 4.1.5.9 Resource-Centric vs Application-Centric View

Traditional resource monitoring:

```text
Lambda function
DynamoDB table
API Gateway API
```

Application Signals starts from:

```text
application
→ service
→ operation
→ dependency
```

Exam discriminator:

```text
individual resource health
→ CloudWatch resource/dashboard views

distributed application/service health
→ Application Signals
```

#### 4.1.5.10 Application Signals Services Page

The Services page helps identify services with:
- high fault rate,
- high latency,
- unhealthy SLIs.

Troubleshooting pattern:

```text
Services
→ identify unhealthy service
→ open service detail
```

Do not use only absolute fault count.

Consider:
- fault rate,
- call volume,
- business criticality.

Example:

```text
Service A fault rate = 0.1%
Service B fault rate = 20%
Service C fault rate = 0%
```

Start investigation with:
- Service B.

#### 4.1.5.11 Service Detail

Service detail helps inspect:
- service metrics,
- operations,
- dependencies,
- related traces,
- client requests,
- associated synthetic calls where available.

Mental model:

```text
global symptom
→ unhealthy service
→ operation
→ dependency
→ trace/log evidence
```

#### 4.1.5.12 Application Map

Application Map visualizes:
- application topology,
- service/dependency relationships,
- operational health.

Example:

```text
Client
  |
  v
API
  |
  v
Order Service
  |
  +--> DynamoDB
  |
  '--> Payment Service
```

Use it when:
- the application is distributed,
- the failing dependency is not obvious.

Question it helps answer:

```text
Which node/dependency is unhealthy?
```

#### 4.1.5.13 Application Signals Visibility and Time Filter

Application Signals shows services/operations based on:
- telemetry activity in the selected time filter.

Current source notes:
- default view may use a recent-hours window,
- inactive services may not appear.

Therefore:

```text
service not visible
≠ service does not exist
```

Possible explanations:
- no activity in selected time range,
- telemetry/discovery delay.

Immediately after:
- deployment,
- instrumentation,
- first traffic,

missing topology can mean:
- discovery has not completed yet.

#### 4.1.5.14 SLI

SLI means:

```text
measurable indicator of service performance
```

Typical examples:
- latency,
- availability.

Example:

```text
Latency < 200 ms
```

or:

```text
Availability
```

SLI answers:

```text
What are we measuring?
```

#### 4.1.5.15 SLO

SLO combines:

```text
SLI
+
threshold
+
attainment goal
+
evaluation interval
```

Example:

```text
99.9% of requests
must satisfy availability objective
over rolling 30 days
```

SLO answers:

```text
How good must the service be over a defined interval?
```

#### 4.1.5.16 SLI vs SLO

```text
SLI
→ measurement

SLO
→ target applied to measurement
```

Do not confuse:
- metric,
- indicator,
- objective.

#### 4.1.5.17 Application Signals Availability

Current AWS documentation defines standard Application Signals Availability as:

```text
(1 - Fault Rate) × 100
```

Faults:
- HTTP 5xx responses.

Important current behavior:

```text
4xx
→ treated as successful for this availability calculation
```

Therefore:

```text
many 4xx responses
```

may not reduce:
- standard Application Signals Availability.

This is a high-value exam trap.

If 4xx responses are considered a business failure:
- supplement with additional metrics/SLOs.

#### 4.1.5.18 Latency

Application Signals latency helps identify:
- slow service,
- slow operation,
- slow dependency.

Flow:

```text
service latency high
→ inspect operations
→ inspect dependencies
→ inspect traces
```

Question:

```text
Is the service itself slow,
or is a downstream dependency slow?
```

#### 4.1.5.19 SLO Dashboard

SLO views show:
- met objective,
- unmet objective,
- reliability/performance health relative to defined target.

This differs from:
- raw metric inspection.

SLO dashboard answers:

```text
Are critical service objectives being met?
```

#### 4.1.5.20 Error Budget

Error budget is:
- allowed unreliability while still satisfying the SLO.

Example:

```text
SLO = 99.9%
allowed failure/unavailability budget = 0.1%
```

As failures accumulate:

```text
remaining error budget
→ decreases
```

Error budget answers:

```text
How much reliability margin remains?
```

#### 4.1.5.21 Burn Rate

Burn rate means:
- how quickly the error budget is being consumed.

Concept:

```text
burn rate too high
→ reliability budget is being consumed too quickly
```

A service can:
- still meet its SLO now,
- while burn rate indicates it is trending toward violation.

#### 4.1.5.22 Period-Based vs Request-Based SLO

Application Signals supports:

```text
period-based SLO
request-based SLO
```

##### 4.1.5.22.1 Period-Based

```text
evaluate each time period
→ period is good/bad
→ calculate attainment across periods
```

##### 4.1.5.22.2 Request-Based

```text
good requests / total requests
→ attainment
```

Know:
- both models exist,
- they measure health differently.

#### 4.1.5.23 Calendar vs Rolling Interval

SLO interval can be:

```text
calendar
→ aligned to month/week/etc.

rolling
→ continuously moving recent window
```

Calendar:
- useful for calendar-aligned commitments.

Rolling:
- useful for current/recent user experience.

#### 4.1.5.24 SLO Is Not an Alarm

```text
SLO
→ reliability/performance objective

Alarm
→ evaluates metric condition and changes state
```

An SLO can have:
- associated alarms.

But:

```text
SLO ≠ alarm
```

#### 4.1.5.25 Alarm State on Dashboards

Common CloudWatch alarm states:

```text
OK
ALARM
INSUFFICIENT_DATA
```

Do not stop at:
- alarm color/status.

Inspect:
- underlying metric,
- threshold,
- trend,
- duration,
- recovery behavior.

##### 4.1.5.25.1 `INSUFFICIENT_DATA`

Means:
- not enough data to determine threshold state.

It does not automatically mean:

```text
application is down
```

Possible causes:
- no traffic,
- missing telemetry,
- new alarm,
- publication gap.

#### 4.1.5.26 Cross-Region Dashboards

Custom CloudWatch dashboards can display:
- metrics from multiple Regions.

Useful for:

```text
multi-Region application
→ single operational view
```

Do not assume:
- dashboard metrics must all come from one Region.

#### 4.1.5.27 Cross-Account Observability

CloudWatch cross-account observability can provide:

```text
monitoring account
→ source accounts
```

Useful when:
- application spans multiple AWS accounts.

Do not assume:
- cross-account telemetry is automatically centralized without configuration.

#### 4.1.5.28 Lambda Insights

CloudWatch Lambda Insights provides:
- enhanced monitoring and troubleshooting for Lambda functions.

It collects/aggregates:
- system-level metrics,
- diagnostic information,
- performance data.

Use it when the problem appears:
- Lambda-specific.

Examples:
- memory pressure,
- runtime performance,
- duration,
- invocation behavior,
- cold starts.

#### 4.1.5.29 Lambda Insights vs Application Signals

```text
Lambda Insights
→ Lambda runtime/resource performance

Application Signals
→ application/service/operation/dependency health
```

Fast discriminator:

```text
Lambda resource/performance issue?
→ Lambda Insights

distributed service topology/health?
→ Application Signals
```

#### 4.1.5.30 Lambda Memory and CPU Context

Lambda Insights can reveal:
- high memory utilization,
- runtime pressure.

Example:

```text
Duration high
+
memory utilization near configured memory
```

Investigation direction:
- function resource sizing.

Lambda CPU allocation increases with:
- configured memory.

Detailed optimization:
- belongs to Task 4.3.

For this skill:
- recognize the health signal,
- know where to drill down.

#### 4.1.5.31 Cold Starts

If:

```text
latency spikes
+
cold starts correlate
```

possible cause:
- initialization overhead.

Do not assume:
- every latency spike is a downstream dependency problem.

#### 4.1.5.32 Logs Insights Drilldown

High-level health view:

```text
Errors ↑
```

Logs Insights answers:

```text
Which error?
How often?
Which request/operation?
```

Typical flow:

```text
dashboard/Application Signals
→ unhealthy component
→ Logs Insights
→ exact log evidence
```

Detailed query syntax:
- 4.1.3.

#### 4.1.5.33 Trace Drilldown

Application Signals can use metrics/traces to:
- discover service relationships,
- expose topology.

Typical flow:

```text
Application Signals
→ unhealthy service
→ slow/failing operation
→ trace
→ failing dependency
```

Trace data:
- localizes the request path.

Detailed trace interpretation:
- 4.1.2.

#### 4.1.5.34 CloudWatch Synthetics

Synthetics canaries:
- simulate user/application interactions on a schedule.

Use when:

```text
need scheduled synthetic endpoint/user journey
→ Synthetics
```

Useful because:
- availability can be tested even without real user traffic.

Application Signals can associate:
- synthetic calls with services when tracing is configured.

#### 4.1.5.35 CloudWatch RUM

Real User Monitoring provides:
- client-side user-experience telemetry.

Use when:

```text
backend metrics appear healthy
but
users report poor experience
```

RUM can expose:
- browser/client-side degradation,
- real user performance issues.

#### 4.1.5.36 Synthetics vs RUM

```text
Synthetics
→ controlled synthetic journeys

RUM
→ actual user/browser experience
```

Both complement:
- backend application health.

#### 4.1.5.37 Resource Health vs User Health

Example:

```text
Lambda healthy
DynamoDB healthy
API healthy
```

but:

```text
RUM page load time high
```

Possible issue:
- frontend,
- client/network,
- external dependency.

Therefore:

```text
resource health
≠ complete user health
```

#### 4.1.5.38 Application Signals Investigation Flow

A strong operational sequence from the source is:

```text
SLO view
→ identify critical objective degradation

Services page
→ find high-fault/high-latency service

Service detail
→ inspect operation/dependency

Application Map
→ inspect topology

trace/log/metric drilldown
→ establish root cause
```

This is the primary exam mental model.

#### 4.1.5.39 Traffic Context

Always interpret:
- faults/errors relative to traffic.

Example:

```text
100 faults
```

means different things at:

```text
200 calls
vs
10,000,000 calls
```

Use:
- call volume,
- rates,
- criticality.

Do not rank health by:
- raw counts alone.

#### 4.1.5.40 Faults, Errors, Throttles, Business Failures

Telemetry may distinguish:
- faults,
- errors,
- throttles,
- business failures.

Do not treat:
- all failure-like terms as equivalent.

Interpret them according to:
- service/tool semantics.

For Application Signals standard Availability:
- 5xx faults matter,
- 4xx do not reduce Availability.

#### 4.1.5.41 Baseline Comparison

A health view should answer:

```text
Is this abnormal for this application?
```

Compare:
- before vs after deployment,
- current vs historical behavior,
- same service/operation,
- normal traffic window.

Absolute value alone:
- may not indicate a problem.

#### 4.1.5.42 Deployment Correlation

Example:

```text
13:55 healthy
14:00 deployment
14:03 latency ↑
14:04 faults ↑
```

Strong hypothesis:
- release regression.

Next steps:
- compare telemetry by version/resource,
- inspect deployment/service output when relevant.

Detailed deployment-failure troubleshooting:
- 4.1.6.

#### 4.1.5.43 Healthy SLO Does Not Mean No Incident

SLO is evaluated:
- over an interval.

A short incident may:
- consume error budget,
- without immediately violating the full SLO.

Therefore:

```text
current incident signals
≠ SLO status
```

They answer:
- different questions.

#### 4.1.5.44 Unhealthy SLO Does Not Identify Root Cause

Unhealthy SLO means:

```text
service is not meeting objective
```

It does not identify:

```text
specific dependency
specific configuration
specific code defect
```

Use:
- service detail,
- Application Map,
- traces,
- logs.

#### 4.1.5.45 Dashboard Design for Troubleshooting

A useful dashboard prioritizes:

```text
user-impact signals
→ service health
→ dependencies
→ saturation/capacity
```

Avoid:

```text
every available AWS metric
```

Good signal set might include:

```text
traffic
errors
latency
availability
throttling
backlog
critical business metric
```

More widgets:
- do not automatically improve diagnosis.

Signal-to-noise matters.

#### 4.1.5.46 Alarm Context

Show:

```text
alarm state
+
underlying metric
```

because:

```text
ALARM
```

alone does not reveal:
- trend,
- severity,
- duration,
- recovery,
- workload context.

#### 4.1.5.47 Event-Driven Application Health

For asynchronous systems:

```text
user-facing request succeeds
```

can coexist with:

```text
background processing is unhealthy
```

Useful signals:
- queue depth,
- age of oldest message,
- consumer errors,
- throttles,
- DLQ activity,
- processing latency.

Example:

```text
API healthy
producer Lambda healthy
SQS age ↑
consumer errors ↑
```

Interpretation:
- asynchronous path is unhealthy.

Application health must reflect:
- architecture.

#### 4.1.5.48 Multi-Service Application Example

```text
API Gateway
→ Lambda A
→ SQS
→ Lambda B
→ DynamoDB
```

Resource dashboards:
- show component-level metrics.

Application Signals:
- shows service/dependency relationships.

Use both:
- for different diagnostic levels.

#### 4.1.5.50 Application Signals vs Custom Dashboard

Application Signals:
- standardized application-centric view,
- service/dependency topology,
- health/SLO context.

Custom dashboard:
- manually curated telemetry,
- application/business-specific composition.

Use Application Signals when:
- topology and service health matter.

Use custom dashboard when:
- organization-specific signals must be combined.

Often:
- both complement each other.

#### 4.1.5.52 Common Exam Traps

##### 4.1.5.52.1 Dashboard Automatically Finds Root Cause
- False.
- It identifies abnormal signals and investigation direction.

##### 4.1.5.52.2 Application Signals Is Only a Dashboard
- False.
- It provides application-centric metrics, traces, topology, services, dependencies, and SLOs.

##### 4.1.5.52.3 Lambda Insights = Logs Insights
- False.

##### 4.1.5.52.4 SLI = SLO
- False.

```text
SLI
→ measurement

SLO
→ target
```

##### 4.1.5.52.5 4xx Always Reduces Application Signals Availability
- False.
- Standard Availability treats 4xx as successful.

##### 4.1.5.52.6 `INSUFFICIENT_DATA` Means Application Is Down
- False.

##### 4.1.5.52.7 Healthy SLO Means No Recent Errors
- False.
- Errors can occur within the error budget.

##### 4.1.5.52.8 Unhealthy SLO Identifies Exact Defect
- False.
- It identifies objective violation, not exact root cause.

##### 4.1.5.52.9 Missing Service in Application Signals Means Deleted
- False.
- Check time filter and discovery activity.

##### 4.1.5.52.10 Average Is Always Best Dashboard Statistic
- False.

##### 4.1.5.52.11 More Dashboard Widgets Always Means Better Health Review
- False.
- Signal-to-noise matters.

##### 4.1.5.52.12 Resource Health Equals User Experience
- False.
- RUM/Synthetics/business metrics can reveal user-facing degradation.

##### 4.1.5.55.1 Know These Cold

**CloudWatch Dashboard**
→ reusable consolidated telemetry view.

**Application Signals**
→ application-centric health, services, operations, dependencies, topology, metrics, and SLOs.

**Services Page**
→ identify high-fault/high-latency/unhealthy services.

**Service Detail**
→ inspect operations/dependencies and related telemetry.

**Application Map**
→ service/dependency topology.

**SLI**
→ measured service-performance indicator.

→ target for an SLI over an interval.

→ unreliability allowed while meeting the SLO.

→ rate of error-budget consumption.

**Synthetics**

##### 4.1.5.55.3 Final Principle
- **Review application health from the highest useful level and then drill down. CloudWatch dashboards consolidate the metrics, alarms, and operational context that matter to an application; Application Signals provides an application-centric view of services, operations, dependencies, latency, availability, faults, errors, topology, and SLO health; and Lambda Insights provides enhanced Lambda-specific performance visibility. Understand SLI versus SLO, error budget, burn rate, and the specific semantics of Application Signals Availability. Always validate dashboard time range, period, statistic, traffic volume, and telemetry scope before drawing conclusions. Once the unhealthy component is identified, use metrics, traces, and logs to establish the actual root cause.**

##### 4.1.5.56.5 Application Signals — Service Level Objectives
Official AWS documentation defines:
- SLI,
- SLO,
- attainment goal,
- calendar/rolling intervals,
- period-based/request-based objectives,
- error budgets,
- burn rates,
- SLO dashboards.

It also defines standard Application Signals Availability as:

```text
(1 - Fault Rate) × 100
```

with:
- 5xx responses treated as faults,
- 4xx responses treated as successful for this metric.

Official AWS documentation:
- https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-ServiceLevelObjectives.html

##### 4.1.5.56.7 Source Priority
1. DVA-C02 exam guide defines the exact health-review scope.
2. Current CloudWatch dashboard documentation defines the consolidated health-view model.
3. Current Application Signals documentation defines service/operation/dependency health, topology, SLOs, and Availability semantics.
4. Current Lambda Insights documentation defines Lambda-specific enhanced health/performance visibility.
5. Logs Insights, X-Ray, Synthetics, and RUM are included only as supporting drilldown/user-health mechanisms.
6. Detailed log querying remains in 4.1.3.
7. Custom metric implementation remains in 4.1.4.
8. Deployment failure troubleshooting remains in 4.1.6.
